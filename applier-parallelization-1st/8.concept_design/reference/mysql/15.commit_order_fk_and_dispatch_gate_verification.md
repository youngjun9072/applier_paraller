# 15. COMMIT_ORDER·FK·dispatch 게이트 — 코드 검증

> **이 문서의 목적.** "COMMIT_ORDER로 충돌을 막을 때 FK가 들어오면 `last_committed`를 분리하는가" 그리고 "의존성 기반 dispatch를 *누가*(코디네이터냐 워커냐) 하는가"라는 두 질문을, **MySQL 8.0.46 LTS 소스(`/Workspace/mysql-server`)** 를 직접 읽어 검증한 기록이다. 결론만 먼저: **(1) COMMIT_ORDER는 FK를 보지 않는다 — `last_committed`를 분리/조정하지 않는다.** FK 안전은 마스터 commit 순서가 자동으로 보장한다. **(2) 의존성 기반 dispatch 게이트는 *코디네이터*(SQL 스레드)가 집행하고, *워커*는 commit *순서*만 집행한다.** 둘은 다른 게이트다.
>
> 03·04·05·06·11의 내용과 겹치는 부분은 요약하고 cross-ref만 단다. 이 문서는 그 위에서 **FK ↔ COMMIT_ORDER ↔ dispatch 게이트**를 한 줄로 잇는 검증에 집중한다.

분석 대상 트리: `mysql-server` = **8.0.46 LTS**. (8.4+/9.7에서 `binlog_transaction_dependency_tracking` 변수는 제거됐지만 `get_dependency`의 2단 합성 로직은 동일 — `14.dependency_tracking_version_history.md` 및 메모 참조.)

---

## A. 두 단계, 두 장소 — 큰 그림

MySQL 병렬 복제는 **의존성을 source(마스터)가 계산**하고, **replica(슬레이브)가 그 결과로 병렬 실행 + 순서 보존**한다. 이 문서가 다루는 코드는 정확히 세 지점이다.

| 단계 | 장소 | 핵심 클래스/함수 | 파일 |
|---|---|---|---|
| ① 의존성 *계산* (`last_committed`/`sequence_number`) | **source** | `Commit_order_trx_dependency_tracker` / `Writeset_trx_dependency_tracker` | `sql/rpl_trx_tracking.cc` |
| ② 의존성 기반 *dispatch* (언제 워커에 보낼지) | **replica 코디네이터(SQL 스레드)** | `Mts_submode_logical_clock::schedule_next_event` / `wait_for_last_committed_trx` | `sql/rpl_mta_submode.cc` |
| ③ commit *순서* 집행 (durable commit 차례) | **replica 워커** | `Commit_order_manager` | `sql/rpl_replica_commit_order_manager.cc` |

FK가 영향을 주는 곳은 **①의 WRITESET 경로뿐**이다. COMMIT_ORDER(①)·dispatch(②)·commit 순서(③) 어디에도 FK 분기는 없다.

## B. ① source 의존성 계산 — COMMIT_ORDER는 FK를 안 본다

### B.1 COMMIT_ORDER tracker — FK 분기 없음

`Commit_order_trx_dependency_tracker::get_dependency()` (`rpl_trx_tracking.cc:149-178`):

```c++
void Commit_order_trx_dependency_tracker::get_dependency(
    THD *thd, bool parallelization_barrier, int64 &sequence_number,
    int64 &commit_parent) {
  Transaction_ctx *trn_ctx = thd->get_transaction();
  ...
  sequence_number =
      trn_ctx->sequence_number - m_max_committed_transaction.get_offset();

  if (trn_ctx->last_committed <= m_max_committed_transaction.get_offset())
    commit_parent = SEQ_UNINIT;
  else
    commit_parent =
        std::max(trn_ctx->last_committed, m_last_blocking_transaction) -
        m_max_committed_transaction.get_offset();

  if (is_trx_unsafe_for_parallel_slave(thd) || parallelization_barrier)
    m_last_blocking_transaction = trn_ctx->sequence_number;
}
```

- `commit_parent`(= replica가 받는 `last_committed`)은 `trn_ctx->last_committed`에서만 나온다. **FK 검사 코드가 없다.**
- 병렬을 막는(=`commit_parent`를 올리는) 유일한 조건은 `is_trx_unsafe_for_parallel_slave()` 또는 `parallelization_barrier`다. `is_trx_unsafe_for_parallel_slave`는 `rpl_trx_tracking.cc:120-134`에서 보듯 **DDL류**(ANALYZE/REPAIR/OPTIMIZE/CREATE·ALTER·DROP DB, partition ALTER)만 잡는다 — FK 아님.
- `trn_ctx->last_committed` 자체는 group-commit prepare 시점에 `max_committed_timestamp` 스냅샷으로 채워진다(원리: `03`·`04`, 8.0.46 binlog.cc의 `store_commit_parent`). 즉 **"내가 commit에 진입할 때 이미 commit돼 있던 마지막 트랜잭션의 seq"** 이고, FK와 무관하게 commit 타이밍만 본다.

**결론 B.1**: COMMIT_ORDER에서 FK가 들어와도 `last_committed`를 따로 분리하거나 조정하지 않는다. 그냥 commit 순서 그대로다.

### B.2 그런데 왜 그래도 FK가 안전한가 (자동 보장)

마스터에서 자식 INSERT가 FK 검사를 통과하려면 그 시점에 **부모 행이 이미 commit돼 보여야** 한다. 부모가 없으면 자식 트랜잭션은 마스터에서 에러로 죽어 **binlog에 안 실린다.** 따라서 binlog에 실린 트랜잭션 열은 항상 "부모 commit → 자식 commit" 순서이고, 논리 시계가 그 순서를 보존한다:

```
부모.sequence_number  ≤  자식.last_committed  <  자식.sequence_number
```

자식의 `last_committed`가 부모의 `sequence_number` 이상이므로, replica는 FK를 몰라도 자식을 부모 뒤로만 스케줄한다(C절). **FK 안전이 commit 순서에 이미 인코딩돼 있어** COMMIT_ORDER 코드에 FK 분기가 필요 없는 것이다.

### B.3 FK가 실제로 코드에 나타나는 곳 — WRITESET 경로뿐

`Writeset_trx_dependency_tracker::get_dependency()` (`rpl_trx_tracking.cc:246-316`)의 `can_use_writesets` 조건:

```c++
bool can_use_writesets =
    (writeset->size() != 0 || write_set_ctx->get_has_missing_keys() ||
     is_empty_transaction_in_binlog_cache(thd)) &&
    !is_create_table_as_query_block(thd) &&
    (global_system_variables.transaction_write_set_extraction ==
     thd->variables.transaction_write_set_extraction) &&
    // must not use foreign keys
    !write_set_ctx->get_has_related_foreign_keys() &&   // ← rpl_trx_tracking.cc:264
    !write_set_ctx->was_write_set_limit_reached();
```

`get_has_related_foreign_keys()`가 참이면 `can_use_writesets = false` → writeset로 `commit_parent`를 낮추는 블록(`:303-310`의 `commit_parent = std::min(last_parent, commit_parent)`)을 **건너뛴다.** 그리고:

```c++
if (exceeds_capacity || !can_use_writesets) {
  m_writeset_history_start = sequence_number;
  m_writeset_history.clear();              // rpl_trx_tracking.cc:313-316
}
```

즉 **WRITESET에서도 FK를 만나면 "writeset 최적화를 끄고 COMMIT_ORDER 값을 그대로 사용"** 한다. `last_committed`를 별도 값으로 분리하는 게 아니라, *낮추기를 포기*하고 history를 비운다(보수적). 상세는 `11.writeset_fk_dependency_tracking.md`.

### B.4 FK 플래그는 어디서 세워지나 — `add_pke()`

`sql/rpl_write_set_handler.cc`의 `add_pke()`:

- **자식 테이블(FK 보유, `table->s->foreign_keys > 0`, `:1000~1103`)**: 참조하는 부모의 unique key 정보(`referenced_table_db`/`referenced_table_name` 등, `:1050-1051`)와 FK 컬럼 값을 해시로 만들어 **자기 writeset에 추가**한다(`generate_hash_pke`). → 부모-자식 충돌을 writeset 해시로 잡으려는 시도.
- **부모 테이블(`table->s->foreign_key_parents > 0`, `:1107-1108`)**: `ws_ctx->set_has_related_foreign_keys()`를 호출. → cascade 가능성 때문에 writeset만으로 의존을 다 못 잡으므로 B.3의 fallback을 트리거.
- writeset 해시를 하나도 못 넣었으면 `:1115`에서 `set_has_missing_keys()`(PK/UK 없는 테이블 → 역시 COMMIT_ORDER로 보수화).

**정리(①)**: FK는 COMMIT_ORDER 계산에 일절 영향이 없고(B.1), WRITESET 계산에서만 "최적화 포기 → COMMIT_ORDER로 fallback"으로 작용한다(B.3). 어느 쪽도 `last_committed`를 *분리*하지 않는다.

## C. ② replica dispatch 게이트 — **코디네이터**가 집행한다

여기가 이번 검증의 핵심이다. "자식을 부모 commit 전에 보내지 않는다"를 *누가* 보장하는가?

### C.1 schedule_next_event는 코디네이터(SQL) 스레드에서 돈다

`Mts_submode_logical_clock::schedule_next_event()` (`rpl_mta_submode.cc:574`)의 호출자는 `Log_event::get_slave_worker()` 경로(`sql/log_event.cc:2688`, `:2711`, `:2720`)다. 이 경로는 **워커에게 이벤트를 나눠주기 *전*에 코디네이터 스레드가 실행**한다(주석 `rpl_mta_submode.cc:565-567`: "the global Scheduler (Coordinator thread)").

### C.2 의존성 미충족이면 코디네이터가 대기

`schedule_next_event` 본문 (`rpl_mta_submode.cc:678-713`):

```c++
/*
  The coordinator waits till all transactions on which the current one
  depends on are applied.
*/
if (!is_new_group) {
  longlong lwm_estimate = estimate_lwm_timestamp();

  if (!clock_leq(last_committed, lwm_estimate) &&
      rli->gaq->assigned_group_index != rli->gaq->entry) {
    ...
    if (wait_for_last_committed_trx(rli, last_committed)) {   // ← 코디네이터 블록
      ...
    }
  }
}
```

주석 `:679-680`이 그대로 못박는다 — **"The coordinator waits till all transactions on which the current one depends on are applied."** 조건은 `clock_leq(last_committed, lwm)` — 즉 **이 트랜잭션의 `last_committed` 이하가 모두 commit(=lwm 도달)될 때까지** 코디네이터가 다음 트랜잭션을 워커에 *배정하지 않는다.*

### C.3 wait_for_last_committed_trx — 무엇을 기다리나

`Mts_submode_logical_clock::wait_for_last_committed_trx()` (`rpl_mta_submode.cc:515-559`):

```c++
if ((!rli->info_thd->killed && !is_error) &&
    !clock_leq(last_committed_arg, get_lwm_timestamp(rli, true))) {
  ...
  thd->ENTER_COND(&rli->logical_clock_cond, &rli->mts_gaq_LOCK,
                  &stage_worker_waiting_for_commit_parent, &old_stage);
  do {
    mysql_cond_wait(&rli->logical_clock_cond, &rli->mts_gaq_LOCK);
  } while ((!rli->info_thd->killed && !is_error) &&
           !clock_leq(last_committed_arg, estimate_lwm_timestamp()));
  ...
}
```

- 대기 조건: `last_committed ≤ lwm`(low water mark)이 될 때까지 `logical_clock_cond`에서 블록. 대기 stage 이름이 `stage_worker_waiting_for_commit_parent`다.
- **`lwm`(=`estimate_lwm_timestamp`, `:444-478`)** 은 GAQ(group assigned queue)에서 **gap 없이 commit이 끝난 연속 prefix의 끝 sequence_number**(`rli->gaq->lwm.sequence_number`)다. 워커가 그룹을 commit 완료하면 전진한다.
- 즉 dispatch 게이트는 "**의존 선행이 실제로 commit될 때까지**"를 기다린다. 단순히 "실행 시작"이 아니라 "commit 완료(lwm 도달)"가 기준이다.

### C.4 그래서 FK 시나리오에 무슨 일이 일어나나

```
Tx1: 부모 테이블 수정,  sequence_number = 1
Tx2: 자식(FK 참조),    sequence_number = 2,  last_committed ≥ 1   (B.2)
```

코디네이터는 `Tx2.last_committed(≥1) ≤ lwm` 이 될 때까지 — 즉 **Tx1이 commit돼 lwm이 1 이상이 될 때까지** — Tx2를 **워커에 배정조차 하지 않는다**(`schedule_next_event`에서 블록). 따라서 "Tx2가 다른 워커에서 먼저 실행/flush되어 FK 검사가 부모를 못 본다"는 상황은 **발생할 수 없다.** 자식의 FK 검사는 항상 commit된 부모를 본다.

**핵심**: 이 안전을 만드는 것은 commit *순서* 게이트(③/SPCO)가 아니라 **dispatch 게이트(②, 코디네이터)** 다. dispatch 게이트가 의존 트랜잭션의 *시작 자체*를 막는다.

상세 메커니즘(GAQ·LWM·get_least_occupied_worker)은 `05.mts_coordinator_dispatch.md` 참조. 이 문서는 "게이트가 코디네이터에 있고, 그것이 FK 안전의 출처"라는 점을 검증한 것이다.

## D. ③ replica commit 순서 게이트 — **워커**가 집행 (별개)

dispatch 게이트(②)와 자주 혼동되는 것이 commit 순서 게이트다. 이것은 **워커**가 하고, FK 안전과는 다른 목적이다.

`replica_preserve_commit_order=ON`일 때 `Commit_order_manager` (`sql/rpl_replica_commit_order_manager.cc`):

- `register_trx()` (`:58`) — 워커가 자기 순번 등록.
- `wait_for_its_turn_before_flush_stage()` (`:650`) / `wait()` (`:272`, `:501`) — 워커가 **flush/commit 직전에 자기 commit 차례가 올 때까지 대기**.
- `wait_and_finish()` (`:521`) — commit 후 다음 워커를 깨움.

이 게이트는 **이미 병렬 실행 중인 (서로 독립인) 트랜잭션들**의 *durable commit*을 source commit 순서로 강제한다. 목적은 외부 일관성·gap-free 복구이지 FK 의존이 아니다 — FK 의존은 ②가 이미 막았다. 상세는 `06.replica_preserve_commit_order.md`.

**구분 한 줄**: ②는 "언제 *시작*해도 되나"(코디네이터), ③은 "언제 *durable commit*해도 되나"(워커). 워커는 충돌·의존을 전혀 판단하지 않는다.

## F. CUBRID 설계(D.x)로의 매핑

본 설계는 위 MySQL 모델을 차용했으므로 구조가 1:1 대응한다. 단 *용어*와 *watermark 의미 일부*는 CUBRID 고유다.

| MySQL (검증) | CUBRID 설계 | 메모 |
|---|---|---|
| source `Commit_order_trx_dependency_tracker` | 마스터가 `commit_seq`/`dependency_seq` 계산 (D.5) | 1차 COMMIT_ORDER |
| source WRITESET + FK fallback | v2 WRITESET(`(class,PK)`∪FK부모) (D.5 향후 확장) | 인터페이스 공용, 계산만 교체 |
| `last_committed` (commit_parent) | `dependency_seq` | 기다려야 할 마지막 선행 |
| `sequence_number` | `commit_seq` | commit 순번 |
| `lwm` (low water mark) | `slave_committed_seq` | **차이**: CUBRID는 gap-free *durable* commit prefix로 정의(재시작 멱등 skip 정합 G.2 때문). MySQL lwm은 스케줄링용 commit 완료 prefix |
| 코디네이터 `schedule_next_event` 대기 | 코디네이터 dispatch 게이트 `dependency_seq ≤ slave_committed_seq` (D.6) | "언제 시작" |
| 워커 `Commit_order_manager` (SPCO) | 워커 durable commit 차례 게이트 (D.4) | "언제 durable commit" |

**FK 안전의 출처가 같다**: MySQL이 COMMIT_ORDER에 FK 코드를 안 두고 commit 순서로 자동 보장하듯, CUBRID 1차 설계도 `dependency_seq`만으로 FK를 푼다(자식 `dependency_seq ≥ 부모 commit_seq` 자동, D.6). 슬레이브는 FK를 몰라도 된다.

**CUBRID 고유 결정 1가지**: dispatch watermark(`slave_committed_seq`)를 **durable·gap-free**로 묶어 FK 안전 + 재시작 정합을 한 게이트로 잡은 것. MySQL의 lwm은 스케줄링 목적의 commit 완료 prefix이고, 재시작은 relay log position + SPCO로 따로 처리한다(D.6/G.2의 추가 articulation).
