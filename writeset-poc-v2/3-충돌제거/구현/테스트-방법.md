# writeset v2 — 테스트 케이스

> **문서 규칙**
> 1. 대상 브랜치: `feature/parallel_applylogdb_writeset_poc` (stage 1 커밋 781274c5e, 6feb8450f 이후).
> 2. 모든 테스트는 debug 빌드 + 격리 단일 노드 HA(active) 환경 기준. 운영 install은 건드리지 않는다.
> 3. 여기의 계측 로그는 전부 임시(TEST ONLY)로 심은 것이라 검증이 끝나면 제거 예정이다.

## 1. 어떤 로그로 병렬성을 보는가

writeset의 계산 결과는 서버 er_log(`log/<db>_*.err`)에 `er_log_debug`로 찍힌다. debug 빌드는 기본으로 보이고, release 빌드도 `er_log_debug=yes`면 의존 라벨 로그는 보인다. 전제: `ha_mode=on`(복제 커밋 경로에서만 writeset이 동작) + PK 있는 테이블.

### 1-1. 키 수집 로그 — 무엇이 해시됐나
```
writeset insert hash: trid=<N> kind=WRITE|REF class=<OID> packed_len=<n> hash=<16진수>
```
트랜잭션이 키 하나를 writeset에 넣을 때마다 찍힌다. `kind=WRITE`는 그 행을 실제로 쓴 키(PK·UNIQUE old/new), `kind=REF`는 자식이 부모를 가리킨 FK 참조다. **자식의 REF 해시가 부모의 WRITE 해시와 class·hash 모두 동일하면 FK 매칭이 성립**한 것이다.

### 1-2. 의존 라벨 로그 — 누구 뒤에 서는가 (핵심)
```
writeset probe trid=<N> ws_keys=<k> dependency_seq=<페이지|오프셋> (ws_parent=... prev_commit=... history_start=...)
```
커밋마다 한 줄. `dependency_seq`가 이 트랜잭션이 기다려야 할 마지막 선행 커밋(LSA)이며, MySQL의 `last_committed`에 해당한다. 읽는 법:
- **낮은 값(history_start 근처)** = 독립 → 병렬 가능
- **특정 커밋의 LSA** = 그 커밋 뒤에만 서면 됨 (해시 매칭 결과)
- **prev_commit과 같은 값** = 직전 커밋 뒤 → 사실상 직렬 (보수 처리)
- 어떤 트랜잭션의 커밋 LSA가 필요하면 **바로 다음 커밋의 probe 라인에 찍히는 `prev_commit`** 으로 얻는다.

필드 의미:
- `ws_keys` — 이 트랜잭션이 수집한 해시 엔트리 수(WRITE+REF 합. 값이 같아도 엔트리별로 센다).
- `ws_parent` — 이력에서 매칭된 커밋 LSA들의 최댓값. 매칭이 없으면 `history_start`(floor).
- `dependency_seq` = min(`ws_parent`, `prev_commit`) — prev_commit이 항상 크거나 같으므로 사실상 ws_parent.
- LSA 표기 = `페이지ID|오프셋`. `-1|-1` = NULL LSA = 독립.

### 1-3. 보수 처리 로그 — 왜 직렬이 됐나
```
writeset FALLBACK(overflow) trid=... ws_keys reached per-tx limit ...   ← 트랜잭션이 키 한도 초과
writeset probe trid=... OVERFLOW->commit_order dependency_seq=...       ← 그 트랜잭션의 격하 판정
writeset history CLEAR (full): ...                                      ← 이력 가득 참 → 전체 clear + floor 상승
writeset history INIT (server boot): cap_limit=...                      ← 부팅 초기화(CLEAR와 구분)
```
파동이 기대보다 직렬로 나오면 이 라인들로 원인을 구분한다.

### 1-4. 패킹 동치 자가검증 (debug 전용, 참고)
```
writeset SELFCHECK[<케이스>]: PASS|FAIL (parent_len=... ref_len=... cast_was_needed=yes|no)
```
최초 FK 참조 수집 시 1회 실행된다. FK 값을 부모 PK 도메인으로 캐스트해 패킹한 바이트가 부모와 동일한지의 자가검증으로, 6케이스 전부 PASS여야 한다.

### 한계
이 로그들은 **마스터의 계산까지만** 보여준다. 슬레이브 applylogdb가 라벨대로 실제 병렬/대기하는지는 2노드 정합 테스트(ha-test)에서 별도로 확인한다.

## 2. 기본 파동 테스트 (T1~T5)

자료조사 3-6-5(MySQL 실측 파동)의 CUBRID 재현. 목적: **무관 트랜잭션이 부모에 끌려가지 않고, 자식은 정확히 부모 뒤에만 서며, 형제끼리는 병렬**임을 확인한다. MySQL은 같은 시나리오가 `T1 | T2 | T3 T4 | T5`로 직렬화됐다(부모 폴백 + 형제 사슬).

### 준비 (판정 대상 아님)
```sql
CREATE TABLE ta (id INT PRIMARY KEY, v INT);
CREATE TABLE tc (id INT PRIMARY KEY, v INT);
CREATE TABLE bparent (id INT PRIMARY KEY, v INT);
CREATE TABLE bchild (id INT PRIMARY KEY, pid INT,
                     FOREIGN KEY (pid) REFERENCES bparent(id));
INSERT INTO bparent VALUES (1, 0);   -- T0 (판정 외, T2의 매칭 앵커)
```
서버 재시작 없이 진행한다. T0의 부모 PK 해시가 이력에 남으므로 T2가 거기에 매칭되는 것까지 관찰 대상이다.

**T0가 필요한 이유 (= 왜 T2가 UPDATE인가).** T2가 `UPDATE bparent WHERE id=1`이라서 갱신할 행이 미리 있어야 하고, T4·T5도 FK 제약상 참조할 부모 행이 존재해야 마스터를 통과한다 — T0가 그 행(id=1)을 만든다. 사실 INSERT도 쓰기이므로 T2 자체를 `INSERT INTO bparent VALUES (1, 0)`으로 바꾸면 T0 없이도 같은 파동이 나온다(T4·T5의 REF는 T2의 WRITE 해시에 그대로 매칭). 그런데도 T0+UPDATE 구성을 기본으로 한 이유는 검증 폭이다:
1. UPDATE의 **old/new 키 수집 경로**가 함께 확인된다 (같은 PK 값이라 동일 해시 2개, `ws_keys=2`).
2. T2가 T0에 매칭되면서 **"같은 행을 쓴 선행 커밋과의 WRITE↔WRITE 매칭"** 까지 덤으로 검증된다.
3. MySQL 3-6-5 원본도 "이미 존재하는 부모 행에 쓰기"라서, 같은 모양이어야 파동을 번호 그대로 대조할 수 있다.

**번호를 T0로 둔 이유**: 판정 대상은 측정 5커밋뿐이라 T1~T5를 MySQL 3-6-5와 1:1로 대응시키고, 준비 INSERT는 판정 밖이지만 T2의 매칭 앵커로 로그에 등장하므로 번호 없는 트랜잭션이 생기지 않게 T0를 부여했다. 최소 시나리오를 원하면 T2를 INSERT로 바꾸고 T0를 빼면 되고, 그 경우 T2의 기대 dependency만 "T0의 커밋 LSA"에서 "독립"으로 바뀐다.

### 측정 5커밋 (autocommit ON, 한 문장 = 한 트랜잭션, 순차)
```sql
INSERT INTO ta VALUES (1, 1);                      -- T1 무관
UPDATE bparent SET v = v + 1 WHERE id = 1;         -- T2 부모 행 쓰기
INSERT INTO tc VALUES (1, 1);                      -- T3 무관
INSERT INTO bchild VALUES (10, 1);                 -- T4 자식 (pid=1)
INSERT INTO bchild VALUES (20, 1);                 -- T5 자식 (다른 행, 같은 부모)
```

### 예상 결과
기대 파동: **{T1 T2 T3} | {T4 T5}**

| tx | 기대 dependency_seq | 근거 |
|---|---|---|
| T1 | 독립 (낮은 값) | 아무와도 안 겹침 |
| T2 | T0(준비 INSERT)의 커밋 LSA | 같은 부모 행(PK 해시)을 쓴 선행 커밋에 매칭 — 정상 동작 |
| T3 | 독립 | **부모(T2)에 끌려가지 않아야 함** — MySQL과의 차이점 |
| T4 | = T2의 커밋 LSA | 자식 REF 해시가 부모 WRITE 해시에 매칭 |
| T5 | = T2의 커밋 LSA (**T4 아님**) | REF는 이력에 실리지 않으므로 형제 사슬 없음 |

보조 판정: T4·T5의 `kind=REF` 해시 = T2의 `kind=WRITE` 해시 (class·hash 동일). T2의 커밋 LSA는 T3 probe 라인의 `prev_commit`으로 확보해 대조.

- **trid=42 (T1, 무관 ta)**

- **trid=43 (T2, 부모 UPDATE)**

- **trid=44 (T3, 무관 tc)**

- **trid=45 (T4, 자식)**
  - insert hash 2줄: **REF ff83…**(class가 자식이 아니라 **부모 0|215|4**인 이유 — REF는 자식 FK 값을 부모 키처럼 해시하기 때문) + WRITE e01c78…(bchild PK 10). ws_keys=2.

- **trid=46 (T5, 자식)**
  - REF ff83… + WRITE e01c8a…(bchild PK 20). ws_keys=2.
  - probe: `ff83… → 여전히 865|12416(T2)` — T4가 안 덮었으므로 → **dependency=865|12416 = T2**. prev_commit=865|14352는 T4의 커밋 LSA인데 dependency가 이 값이 **아니라는 것**이 형제 사슬 없음의 증거다. MySQL(#110071)이라면 T4가 FK 해시를 장부에 실어 주인이 T4로 덮였고, T5는 865|14352를 받았을 것이다.

관찰 메모(판정 외): 준비 DDL 4건(trid 37~40)은 `ws_keys=0`에 dependency `-1|-1`(독립)로 찍혔다. DDL/statement 복제의 보수 격하(commit-order)는 아직 없는 상태 — 설계문서의 남는 보수처리 항목과 연결되는 후속 확인 거리.

| 49 (T4) | INSERT wchild(10) | `866\|12368` = T2, REF 해시=wparent PK1과 동일 | ✅ |
| 50 (T5) | INSERT wchild(20) | `866\|12368` = T2 (T4의 `866\|14304` 아님) | ✅ 형제 병렬 |

파동 = {T1 T2 T3} | {T4 T5} 유지. 슬레이브 정합 wparent=1(v=1)·wchild=2·wta=1·wtc=1. §6 프로브 lag는 조회 지연 포함 상한만 확보(즉시 반영 체감). 부수 확인: 같은 class OID·값 조합의 해시가 전일 실측과 바이트 단위 동일 — 해시 결정성.

주의(격하 빌드에서 §2 원판을 다시 돌릴 때): 준비 DDL이 floor를 올리므로 T1·T3의 기대 dependency는 `-1|-1`(독립)이 아니라 **마지막 준비 커밋의 floor 값**이다. 판정 본질(측정 5커밋끼리의 파동)은 동일.

## 3. 역방향 반례 — 자식 참조 후 부모 DELETE CASCADE (5-2 ①)

옵션 C의 안전 전제("부모 수정은 자식 행을 건드려 WRITE로 남으므로, 참조를 이력에 싣지 않아도 역방향 순서가 잡힌다")를 직접 검증한다. 8종 반례 중 가장 간단한 케이스.

### 준비 (판정 외 — 기존 bchild는 RESTRICT라 CASCADE용 테이블을 새로 만든다)
```sql
CREATE TABLE p2 (id INT PRIMARY KEY);
CREATE TABLE c2 (id INT PRIMARY KEY, pid INT,
                 FOREIGN KEY (pid) REFERENCES p2(id) ON DELETE CASCADE);
INSERT INTO p2 VALUES (1);          -- T0' (부모 행, T1'의 매칭 앵커)
```

### 측정 3커밋 (autocommit ON, 순차)
```sql
INSERT INTO c2 VALUES (10, 1);      -- T1': 자식 — 부모를 참조만 함 (REF)
INSERT INTO ta VALUES (2, 1);       -- T2': 무관 (prev_commit 분리용)
DELETE FROM p2 WHERE id = 1;        -- T3': 부모 삭제 → cascade로 c2(10)도 삭제
```

### 예상 결과
기대 파동: **{T1' T2'} | T3'**

등장할 해시 2개 (값은 실행해야 알지만 구조는 확정):
- `H_p` = hash(p2 class + id=1) — T0'의 WRITE, T1'의 REF, T3'의 WRITE(부모 old PK)·REF로 반복 등장
- `H_c` = hash(c2 class + id=10) — T1'의 WRITE, T3'의 WRITE(cascade가 지운 자식 old PK)로 등장

| tx | 기대 수집 (insert hash 라인) | ws_keys | 기대 dependency_seq |
|---|---|---|---|
| T0' INSERT p2(1) | WRITE `H_p` | 1 | 독립 (`-1\|-1`) |
| T1' INSERT c2(10,1) | REF `H_p` + WRITE `H_c` | 2 | = T0'의 커밋 LSA (REF→T0' WRITE 매칭, 순방향) |
| T2' INSERT ta(2,1) | WRITE(ta id=2) | 1 | 독립 (기본 파동의 ta id=1과 값이 달라 매칭 없음) |
| T3' DELETE p2 id=1 | WRITE `H_p`(부모 old PK) + **WRITE `H_c`(cascade 자식 old PK)** + REF `H_p`(cascade 자식 삭제의 old FK) | 3 | **= T1'의 커밋 LSA** |

T3'의 dependency가 T1'이 되는 계산(장부 추적): 장부의 `H_p` 주인 = T0'(T1'의 REF는 안 실렸으므로), `H_c` 주인 = T1'. dependency = 매칭 최댓값 = T1' LSA — 부모 삭제가 자식 참조 커밋 **뒤에** 서는 역방향 순서가, REF 슬롯 없이 **cascade 자식 WRITE 덕분에** 잡힌다.

판정 기준:
- ✅ 위와 일치 → 옵션 C의 역방향 공집합 논거 실증 (5-2 ① 통과)
- ❌ T3'에 `H_c` WRITE 라인이 없음 → cascade 자식이 writeset에 수집 안 됨 = 전제 붕괴
- ❌ T3'의 dependency가 T0' LSA나 독립 → 역방향 구멍 실증 = **슬롯 격상 트리거**

부수 확인: T3'의 ws_keys가 3인지 — cascade 재진입 경로가 FK REF 수집 분기까지 타는지의 확인이며, 2로 나오면(REF 누락) 정합성 문제는 아니므로 원인만 기록한다. T1'의 커밋 LSA는 T2' 라인의 prev_commit에서 읽는다.

## 4. 전 직렬 — 같은 행 연쇄 갱신 (기다려야 할 때 다 기다리는가)

### 측정 5커밋
```sql
UPDATE bparent SET v = v + 1 WHERE id = 1;   -- T1 ~ T5, 같은 문장 5번 순차 커밋
```

### 예상 결과
기대 파동: **T1 | T2 | T3 | T4 | T5** (완전 사슬)

| tx | 기대 dependency_seq | 비고 |
|---|---|---|
| T1 | 장부의 `H_p` 직전 주인 (선행 테스트에서 그 행을 마지막으로 쓴 커밋) | |
| T2~T5 | **각각 바로 앞 트랜잭션의 커밋 LSA** | 사슬 |

읽을 때 주의: 여기서는 의존 상대가 마침 직전 커밋이라 **dependency와 prev_commit이 같은 값**으로 나온다. 우연(보수 처리)이 아니라 매칭임은 `ws_parent`가 `-1|-1`이 아닌 같은 값으로 찍히는 것으로 구분한다. 각 UPDATE는 old/new PK 수집으로 ws_keys=2(동일 해시 2엔트리).

## 6. 복제 지연 측정 — 타임스탬프 프로브

파동 판정(er_log)과 별개로 "마스터에서 실행한 문장이 슬레이브에 언제 보이는가"를 문장 단위로 재는 방법. 원리: INSERT는 행 복제라 `SYSDATETIME`이 **마스터에서 평가된 값 그대로** 슬레이브에 실린다 → 슬레이브에서 그 값과 현재 시각의 차이가 복제 지연이다.

### 준비 (마스터, 1회)
```sql
CREATE TABLE repl_probe (id INT PRIMARY KEY, tag VARCHAR(32), master_ts DATETIME);
```

### DML 지연
마스터:
```sql
INSERT INTO repl_probe VALUES (1, 'dml', SYSDATETIME);
```
슬레이브 — 보일 때까지 폴링 후 차이 계산:
```bash
while :; do
  csql -u dba demodb -c "SELECT id FROM repl_probe WHERE id=1" | grep -q "1 row" && break
  sleep 0.1
done
csql -u dba demodb -c "SELECT id, master_ts, SYSDATETIME, TIMEDIFF(SYSDATETIME, master_ts) AS lag FROM repl_probe WHERE id=1"
```
(폴링 간격 0.1초가 측정 해상도의 하한이다.)

### DDL 지연 (배리어 비용 포함)
DDL 직후 프로브를 같은 세션에서 연속 커밋:
```sql
CREATE TABLE ddl_probe_1 (id INT PRIMARY KEY);            -- 측정 대상 DDL
INSERT INTO repl_probe VALUES (2, 'after-ddl', SYSDATETIME);
```
DDL은 프로브보다 앞 커밋이므로, 슬레이브에서 id=2가 보이는 순간 DDL은 이미 반영돼 있다 — 그 시점의 `TIMEDIFF(SYSDATETIME, master_ts)`가 "DDL 배리어 포함 반영 지연"이다. statement 복제 격하(커밋 순서 배리어) 이후 DDL은 자기보다 앞선 커밋을 전부 기다리므로, **슬레이브 백로그가 클수록 이 값이 커지는 것이 정상 동작**이다. 부하(벤치) 중에 한 번 끼워 넣으면 "부하 중 DDL 배리어의 실제 비용"이 수치로 남는다.

### 주의
1. **시계 오차**: 두 노드가 NTP 동기화돼 있어야 절대값이 유효하다. 먼저 `date; ssh <슬레이브> date`로 어긋남을 확인하고, 어긋나 있으면 절대값 대신 "벤치 전/중/후 변화량"으로 해석한다.
2. **er_log_debug**: 처리량·지연을 제대로 재려면 양 노드 `er_log_debug=no`로 끄고 잰다(TEST ONLY 계측이 행마다 로그 I/O를 해 수치를 왜곡). 파동 판정을 할 때만 다시 켠다.
3. **백로그 확인**: 측정 직전 슬레이브 applylogdb 로그의 `reader_progress`에서 `final=`(마스터 끝)과 `committed=`(슬레이브 완료) 차이로 lag를 확인한다 — lag 0에서 잰 값이 순수 파이프라인 지연이고, lag가 있으면 대기 시간이 합산된다.
