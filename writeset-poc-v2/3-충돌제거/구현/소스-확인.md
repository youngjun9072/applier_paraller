# 소스 확인 — 복제 식별 키와 cascade 처리 (CUBRID)

[[설계]]가 "폴백 없이 매칭만으로 정합성을 확보한다"고 말하는 근거를 CUBRID 소스에서 확인한 기록이다. 크게 둘이다. 복제가 행을 무엇으로 식별하는가(소스 확인 1), FK cascade가 복제에서 어떻게 처리되는가(소스 확인 2). 라인 번호는 확인 시점(2026-08-20) 기준이라 함수명과 함께 본다.

## 소스 확인 1 — 복제 행 식별 키와 키 변경 처리

### 1-1. FK는 기본키만 참조할 수 있다 (확정)

`smt_check_foreign_key()`(`schema_template.c:1642`)는 참조 테이블의 제약을 오직 PK로만 해석한다. PK를 `classobj_find_class_primary_key()`로 찾고(`:1689`, 자기참조는 `classobj_find_cons_primary_key` `:1663`), 없으면 `ER_FK_REF_CLASS_HAS_NOT_PK`를 낸다(`:1666`, `:1692`). **UNIQUE 인덱스를 찾는 분기 자체가 없으므로** NOT NULL UNIQUE는 FK 참조 대상이 될 수 없다. 컬럼 수 일치(`:1701-1710`, `:1721-1725`), 각 참조 컬럼의 PK 멤버 여부(`:1754-1765`), 타입·콜레이션 일치(`smt_check_type_collation_match_4_fk` `:1767`)까지 전부 강제된다.

실측(2026-08-20, csql)에서도 복합 PK `t1(a,b,c)`의 선행 접두사만 참조하는 FK 생성이 DDL 단계에서 거부됨을 확인했다.

```
csql> CREATE TABLE t2 (d INT PRIMARY KEY, FOREIGN KEY (d) REFERENCES t1(a));
ERROR: The number of keys of the foreign key 'fk_t2_d' is different
       from that of the primary key 'pk_t1_a_b_c'.
```

위 소스의 `ER_FK_NOT_MATCH_KEY_COUNT` 경로가 실제로 작동하는 모습이다. MySQL 8.x는 이런 부분 참조 FK를 허용했다가 9.x에서야 신규 생성을 막았지만(레거시 잔존), CUBRID는 처음부터 불가능해 레거시 걱정도 없다. 부모 키 해시와 자식 FK 해시의 값 개수·모양이 어긋나는 문제가 생길 수 없다는 뜻이다.

### 1-2. 복제 레코드의 행 식별 키는 PK 전용이다

`repl_log_insert()`(`replication.c:293`)는 클래스 이름과 **단일 키 DB_VALUE 하나만** 복제 데이터에 담는다(`or_pack_mem_value` `:391-419`). 행 이미지는 복제 레코드에 없다. 키 생성 게이트는 `index->type == BTREE_PRIMARY_KEY`로 한정되고(`locator_sr.c:8097-8103`), **PK가 없으면 `need_replication = false`로 그 테이블은 복제에서 제외된다**(`:8432-8441`). applier도 PK 인덱스로만 행을 찾는다(`btree_get_pkey_btid` + `xbtree_find_unique` `:6849-6856`).

즉 복제 식별은 PK 전용이며 NOT NULL UNIQUE 폴백은 없다. 한때 "PK 또는 NOT NULL UNIQUE"로 전제했던 것은 아직 반영되지 않은 브랜치의 내용이 섞인 혼동이었다.

### 1-3. 키 값이 바뀌는 UPDATE의 처리

마스터에서는 **UPDATE 레코드 1건**으로 남고 키는 **OLD PK**다. `locator_update_index()`(`locator_sr.c:8328`)가 `repl_old_key`에 OLD PK를 복사해(`:8840-8841`) `repl_log_insert(RVREPL_DATA_UPDATE, ...)`를 행당 정확히 한 번 호출한다(`:8922-8924`). DELETE+INSERT로 쪼개지지 않는다. NEW PK는 복제 레코드가 아니라 힙 로그(target_lsa)의 전체 새 이미지 안에 있다.

applier는 `la_apply_update_log()`(`log_applier.c:8479`)가 target_lsa에서 전체 NEW 이미지를 읽고(`:8507`), 서버의 `locator_repl_prepare_force()`(`locator_sr.c:6811`)가 **OLD PK로 기존 행을 찾은 뒤**(`xbtree_find_unique` `:6855`, 실패 시 `ER_OBJ_OBJECT_NOT_FOUND` `:6858`) 새 이미지로 통째 덮어쓴다(`:6868`).

함의: old→new 키 전환의 정확성은 적용 순서에 달려 있다. 슬레이브가 그 시점에 아직 OLD PK 행을 들고 있어야 하므로, 같은 키 계열을 만지는 트랜잭션들의 순서가 반드시 지켜져야 한다. v2에서 PK 값 변경 UPDATE는 old·new를 둘 다 해시해야 하는 이유가 적용 메커니즘 쪽에서도 확인된다.

### 1-4. UNIQUE 값만 바뀌는 UPDATE와 v2 해시 재료

식별 키는 여전히 PK다(`:8485-8490`, `:8838-8841`). 유니크 컬럼 변경은 키 교체가 아니라 내용 변경으로 취급된다. 변경 내용은 전체 NEW recdes로 전달되고(`log_applier.c:8507`) 적용 시 old_recdes도 확보되므로(`locator_sr.c:6868`), old/new 전체 행 이미지가 모두 실체화된다.

마스터의 인덱스 루프는 인덱스별 old_key/new_key를 이미 들고 있다(`:8565-8570`). 현 PoC도 UNIQUE/REVERSE_UNIQUE에 대해 old_key를 항상, 값이 바뀌면 new_key까지 `log_writeset_add_dbvalue`로 수집하고(`:8651-8662`), PK는 OLD/NEW 둘 다 수집한다(`:8848-8853`). old/new 유니크 해시를 만들 재료는 이미 갖춰져 있다.

### 요약 (소스 확인 1)

- FK = PK만 참조(UNIQUE 참조 분기 자체가 없음) → 비표준 참조 문제 원천 차단.
- 복제 식별 키 = PK 전용, PK 없으면 복제 제외 → NOT NULL UNIQUE 폴백 없음.
- 키 변경 UPDATE = OLD PK 단일 레코드 + 힙의 전체 NEW 이미지, applier가 OLD PK로 찾아 덮어씀 → 순서가 정확성 그 자체이며, old·new 키 해시 재료는 현 PoC가 이미 수집 중.

## 소스 확인 2 — cascade의 HA 복제 처리

### 2-1. cascade는 트리거가 아니라 서버 locator 계층에서 실행된다

부모 행 DELETE는 `locator_delete_force`(`locator_sr.c:6117`)에서 시작해, 인덱스 정리 중 FK 게이트(`:8060`)가 `locator_check_primary_key_delete`(`:4210`)를 부른다. 이 함수가 자식들을 스캔해 CASCADE면 자식마다 다시 `locator_delete_force`(`:4470`)를, SET NULL이면 `locator_attribute_info_force`(`:4499-4503`)를 실행한다. UPDATE 쪽은 `locator_check_primary_key_update`(`:4589`)로 대칭이다. 트리거 엔진(`tr_*.c`)은 전혀 경유하지 않는다.

### 2-2. cascade로 바뀐 자식 행은 전부 복제 레코드로 남는다 (확정)

자식 삭제·갱신은 일반 DML과 같은 경로로 복제 레코드를 만든다. CASCADE 자식 삭제는 `need_replication=true`로 진입해(`:6350`) `repl_log_insert(RVREPL_DATA_DELETE)`(`:8097-8103`)를, SET NULL 자식 갱신은 `repl_log_insert(RVREPL_DATA_UPDATE)`(`:8868-8903`)를 탄다. 모두 부모 변경과 **같은 트랜잭션**에 쌓이고 커밋 시 함께 flush된다. 마스터에서만 생성되도록 `!LOG_CHECK_LOG_APPLIER` 게이트가 걸려 있다.

함의: MySQL이 폴백 근거로 삼았던 "cascade 변경분이 복제 스트림에 없다"는 사정이 CUBRID에는 없다. 부모 트랜잭션의 writeset은 cascade 자식 변경까지 포함해 완전하다.

### 2-3. 슬레이브에서 cascade가 한 번 더 실행된다 (멱등 수렴)

applylogdb의 재적용도 일반 `locator_delete_force`(`:7059`, `:7286`)를 쓰는데 FK 체크를 끄는 수단이 없다. RESTRICT/NO ACTION 분기는 `!LOG_CHECK_LOG_APPLIER`로 applier에서 스킵되지만(`:4253`, `:4631`), **CASCADE/SET NULL 분기(`:4271`)에는 applier 가드가 없다.** 그래서 슬레이브가 부모 DELETE 레코드를 적용하는 순간 cascade가 재실행되고, 마스터가 보낸 자식 레코드도 별도로 적용되어 **이중 실행**이 된다. 현재는 멱등성으로 수렴한다. 이미 삭제된 자식에 대한 DELETE는 무시되고(`:4439-4450`), 로그 순서상 자식 레코드가 부모보다 먼저 쌓이므로 어느 쪽이 먼저 적용돼도 결과가 같다.

이 이중 실행은 v2가 만드는 문제가 아니라 기존 직렬 applier에도 있던 동작이다. 병렬화 단위가 트랜잭션이므로 v2에서도 직렬과 똑같이 멱등으로 무시된다. 남는 것은 슬레이브가 부모 삭제마다 자식을 헛스캔하는 성능 낭비 정도이며, applier에서 cascade 재실행을 막는 것은 정합성 개선이 아니라 최적화 카드다.

### 2-4. 매뉴얼 경고("HA에서 referential action 비권장")의 실체

경고는 실제로는 **트리거 객체**(HA 미지원)에 대한 것이다. FK cascade는 트리거 엔진을 경유하지 않고, 마스터가 자식 레코드를 남기며, 슬레이브 재실행도 멱등으로 수렴하므로, 소스상 FK cascade 고유의 불일치 경로는 확인되지 않았다. 다만 이 수렴은 마스터·슬레이브가 이미 일치한다는 전제 위의 결론이며, 다단계·자기참조 cascade 같은 극단 케이스까지 증명한 것은 아니다.

### 요약 (소스 확인 2)

- cascade 자식 변경은 부모와 같은 트랜잭션의 복제 레코드로 **무조건 남는다**(`locator_sr.c:8100`, `:8903`).
- 슬레이브 이중 실행은 기존에도 있던 동작으로 멱등으로 수렴한다. 트랜잭션 단위 병렬화에서 직렬과 동일하게 무해하다(성능 낭비만).
- 매뉴얼의 불일치 경고는 트리거 대상이며, FK cascade 자체의 불일치 경로는 확인되지 않았다.
