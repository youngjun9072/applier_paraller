# 병렬화 실험 — 방법 (벤치 구성·실행)

이 문서는 CUBRID FK 병렬 적용 실험을 어떤 브랜치·테이블·트랜잭션으로 어떤 순서로 실행했는지의 방법이다. 실측 결과와 40초 공백의 원인은 [[병렬화-결과와원인]]에 있다.

**방법**
1. `feature/parallel_applylogdb_writeset_poc_fk`는 기존 writeset PoC에 무엇을 추가했는가?
2. FK 벤치마크 shell은 어떤 테이블·트랜잭션을 어떤 순서로 만들고 실행하는가?

## 2. 브랜치와 구현 범위

분석 시점의 CUBRID 소스는 다음과 같다.

```text
저장소: /home/youngjun/Workspace/cubrid
현재 브랜치: feature/parallel_applylogdb_writeset_poc_fk
현재 HEAD: d1f87c393
            writeset PoC fix: demote statement-replicated transactions to commit order
```

비교 기준은 다음 두 브랜치다.

```text
기준: feature/parallel_applylogdb_writeset_poc
대상: feature/parallel_applylogdb_writeset_poc_fk
```

FK 브랜치의 핵심 추가점은 다음과 같다.

```text
기존 writeset PoC
  PK/UNIQUE 등 실제 WRITE key로 트랜잭션 간 충돌을 찾음

FK 확장 PoC
  + child FK 값을 parent PK와 동일한 방식으로 hash
  + hash entry에 WRITE/REF 종류를 기록
  + REF도 history를 probe하여 정확한 부모 commit을 찾음
  + REF는 history에 publish하지 않아 형제 child끼리 사슬을 만들지 않음
```

> [!warning] 현재 FK PoC의 알려진 설계 범위
> 현재 구현은 REF를 history에서 조회만 하고 게시하지 않는다. 그래서 `parent WRITE → child REF` 순방향은 잡지만, 이미 완료된 `child REF → 나중 parent WRITE/DELETE` 역방향을 REF history만으로 표현하지는 못한다. DELETE/CASCADE/RESTRICT 반례와 해결 아이디어는 [[5. writeset_v2_한계_부모삭제_순서역전_가능성]]에서 별도로 다룬다. 이 문서의 실측은 **부모 INSERT → 자식 INSERT** 순방향 벤치마크다.

의미는 다음과 같다.

```text

  각 table에 100,000행
```

### 3.3 schema 생성

**파일**: `bin/init_constraint_tables.sh`  
**라인**: 65–81

```bash
for ((i = 1; i <= NTABLES; i += $(fk_group_size))); do
    parent_table=$(constraint_table_name "$i")
    run_sql_master \
      "CREATE TABLE ${parent_table} (id INT PRIMARY KEY, ${cols});"

    for ((child_no = i + 1;
          child_no <= i + FK_CHILD_TABLES_PER_PARENT;
          child_no++)); do
        child_table=$(constraint_table_name "$child_no")

        run_sql_master \
          "CREATE TABLE ${child_table} (
             id INT PRIMARY KEY,
             parent_id INT,
             ${cols},
             FOREIGN KEY (parent_id)
               REFERENCES ${parent_table}(id));"
    done
done
```

`--control true`를 사용하면 FK 대신 일반 index를 만들어 제약 자체의 영향을 비교할 수도 있다.

### 3.4 parent SQL 생성

**파일**: `lib/constraint_dataset.sh`  
**함수**: `write_fk_parent_dataset()`  
**라인**: 209–217

```bash
echo ";autocommit off"

      'INSERT INTO ${table} (...) VALUES(...)';"
```

현재 `TOTAL_DATA == TRANSACTION_DATA == 100000`이고 마지막 행에서는 중간 COMMIT 조건이 거짓이므로 parent table 하나가 100,000행짜리 transaction 하나가 된다.

### 3.5 child SQL 생성과 2개 transaction 분할

**파일**: `lib/constraint_dataset.sh`  
**함수**: `write_fk_child_dataset()`  
**라인**: 237–264

```bash
base_count=$((
  TOTAL_DATA / FK_CHILD_TRANSACTIONS_PER_TABLE
))

...

echo ";autocommit off"
echo "PREPARE st_${child_table}_child${batch_no} FROM
      'INSERT INTO ${child_table}

       VALUES(...)';"

      row_no <= child_batch_count;

done

echo "COMMIT;"
```

2개로 분할한 한 자식 table의 실제 모양은 다음과 같다.

```text
child batch 1
  id=1..50,000
  parent_id=1..50,000
  COMMIT

child batch 2
  id=50,001..100,000
  parent_id=50,001..100,000
  COMMIT
```

두 transaction은 같은 parent table을 보지만 서로 다른 child PK를 쓴다. REF를 history에 게시하지 않으므로 둘 다 같은 parent commit을 dependency로 가져야 하고 서로의 commit을 dependency로 가져서는 안 된다.

### 3.6 parent wave와 child wave 실행 순서

**파일**: `bin/run_constraint.sh`  
**라인**: 83–103

```bash
parent_files=(... 부모 SQL 5개 ...)
child_files=(... 자식 SQL 10개 ...)

run_phase_sbr_marker "insert" "start" "$INSERT_LOG_TABLE"
wait_for_slave_phase_marker "$INSERT_LOG_TABLE" "insert_start"

# 5개 parent csql을 병렬 실행하고 모두 끝날 때까지 wait
run_constraint_files "${parent_files[@]}"

# 그 다음 10개 child csql을 병렬 실행하고 모두 끝날 때까지 wait
run_constraint_files "${child_files[@]}"

master_end_ms=$(epoch_ms)
```

`run_constraint_files()`는 각 파일을 background로 호출한다.

**파일**: `bin/run_constraint.sh`  
**함수**: `run_constraint_files()`  
**라인**: 35–58

```bash
for file in "$@"; do
    run_sql_file_master "$file" >/dev/null &
    pids+=("$!")
done

for pid in "${pids[@]}"; do
    if ! wait "$pid"; then
        rc=1
    fi
done
```

여기서 두 종류의 순서를 구분해야 한다.

```text
master benchmark 순서
  parent csql 5개가 master에서 모두 끝남
  → child csql 10개를 master에서 시작

slave correctness 순서
  child COMMIT을 reader가 봄
  → 해당 child.dep가 가리키는 parent의 slave 적용 완료를 확인
  → child worker dispatch
```

shell은 slave 부모 적용 완료를 기다렸다가 child를 master에서 시작하는 것이 아니다. master에서 parent file들이 끝난 뒤 child file들을 시작한다. slave에서는 writeset gate가 실제 부모 적용 완료 순서를 보장한다.

### 3.7 SBR 시간 마커는 workload와 분리돼 있다

**파일**: `lib/common.sh`  
**함수**: `run_phase_sbr_marker()`  
**라인**: 195–207

```bash
{
    echo ";autocommit off"
    echo "INSERT /*+ USE_SBR */ INTO ${log_table}
          (table_name, event_ts)
          VALUES ('${phase}_${boundary}', SYS_DATETIME);"
    echo "COMMIT;"
} > "$marker_file"

run_sql_file_master "$marker_file"
```

START/END SBR은 각각 별도 파일, 별도 transaction이다. parent/child workload SQL 안에는 SBR이 없다.

```text
START SBR transaction + COMMIT
  ↓ slave marker 확인
parent RBR transactions
child RBR transactions
  ↓ slave 최종 row count 확인
END SBR transaction + COMMIT
```

따라서 SBR의 commit-order fallback이 workload transaction의 writeset을 오염시키지 않는다.

## 4. 전체 end-to-end 흐름

처음 보는 독자를 위해 전체 경로를 먼저 한 장으로 정리한다.

```text
MASTER

1. parent INSERT
   locator index 처리
     → WRITE H(parent table, parent.id)

2. child INSERT
   locator FK index 처리
     → child.parent_id를 parent PK domain으로 cast
     → REF H(parent table, parent.id)
   child PK 처리
     → WRITE H(child table, child.id)

3. COMMIT
   log_writeset_commit_probe()
     → history에서 모든 WRITE/REF hash 조회
     → child REF와 parent WRITE가 매칭
     → child.dependency_seq = parent.commit_lsa

   LOG_DUMMY_WS_LABEL(dependency_seq)
   LOG_COMMIT
     → 두 record를 인접하게 기록

   log_writeset_commit_flush()
     → WRITE만 history에 게시
     → REF는 게시하지 않음

                   HA log shipping
                          ↓

SLAVE

4. applylogdb reader
   LOG_DUMMY_WS_LABEL 읽기
     → dependency_seq 임시 보관
   LOG_COMMIT 읽기
     → LA_APPLY_TASK 생성
     → task.commit_lsa와 task.dependency_seq 설정

5. dependency gate
   dep == NULL                  → 즉시 dispatch
   dep <= frontier             → 즉시 dispatch
   completed_set에 exact dep 있음 → 즉시 dispatch
   그 외                       → pending queue에 PARK

6. worker
   la_apply_repl_log()
   la_flush_repl_items()
   la_commit_transaction()
   ws_apply END 기록
   완료 result enqueue

7. reader/coordinator
   worker result 수집
   exact commit_lsa를 completed_set에 등록
   frontier 전진
   pending dependency 재검사 및 dispatch
```
