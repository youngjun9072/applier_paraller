# 병렬화 실험 — 결과와 40초 공백 원인

> [!summary] 한 문장 결론
> FK 부모 5개와 자식 트랜잭션 10개는 각각 slave에서 실제로 병렬 적용됐다. 부모 최종 완료와 자식 최초 시작 사이에 약 40.729초가 보이지만, 이는 applylogdb 전체가 멈춘 시간이 아니다. 부모는 이미 flush와 DB commit까지 끝났고, 그 사이에도 reader와 worker는 다른 독립 commit task를 계속 처리했다. 자식은 50,000행을 모두 실행해 COMMIT record가 생기고 그 record를 slave reader가 읽은 뒤에야 하나의 apply task가 되므로, 현재 공백의 주된 후보는 **master의 대형 자식 트랜잭션 생성 + 로그 전송/reader 도달 지연**이다. 2026-08-27 2차 실험에서 이 해석이 검증됐다(첫 자식이 master 전체 종료보다 먼저 slave에서 시작, §10.5). 3차 실험에서는 트랜잭션별 커밋 시각 계측으로 공백을 분해해 전달 기여가 0임을 확정했다(§10.6).

이 문서는 위 방법으로 수행한 FK 병렬 적용 실험의 실측 결과와, 부모 완료와 자식 시작 사이 40초 공백의 원인이다. 벤치 구성·실행 순서는 [[병렬화-방법]]에 있다.

**결과**
3. 2026-08-25 실측에서 부모와 자식은 실제로 병렬 적용됐는가?

**원인**
4. 부모 최종 END와 자식 최초 START 사이의 40.729초는 무엇인가?
5. 그 40초 동안 부모와 무관한 트랜잭션도 병렬로 처리할 수 있는가?
6. 위 결과의 근거 — dependency는 master에서 어떻게 계산되고 slave의 reader·gate·worker에서 어떻게 집행되는가? (구현 상세는 코드 문서로 분리)

5번 질문이 특히 중요하다. worker 로그에서 FK 대상만 골라 그리면 다음처럼 보인다.

```text
부모들 [병렬 실행] ── END
                         <약 40초 동안 아무것도 없어 보임>
                                                    자식들 [병렬 실행]
```

이 그림만 보면 “부모 dependency 때문에 applylogdb 전체가 40초간 정지했다”고 오해하기 쉽다. 그러나 코드와 전체 로그를 함께 보면 실제 의미는 다르다.

```text
부모들 [병렬 실행] ── END
                         <FK 대상 자식 task가 아직 시작되지 않은 구간>
                         <다른 독립 task는 계속 dispatch/실행 가능>
                                                    자식들 [병렬 실행]
```

## 6. parent worker 실측 — 5개가 겹쳐 실행됨

모든 시각은 slave `youngjun4`의 applylogdb 로그 기준이다.

| parent table | worker | commit LSA | dependency | START | END | 수행시간 |
|---|---:|---|---|---|---|---:|
| `tbl_ws5` | 0 | `477277\|13536` | `459070\|14896` | 22:53:40.274 | 22:53:46.576 | 6.302초 |
| `tbl_ws7` | 1 | `478180\|7960` | `459070\|14896` | 22:53:41.793 | 22:53:48.416 | 6.623초 |
| `tbl_ws3` | 2 | `478932\|400` | `459070\|14896` | 22:53:42.890 | 22:53:49.281 | 6.391초 |
| `tbl_ws1` | 3 | `479549\|4560` | `459070\|14896` | 22:53:44.188 | 22:53:50.763 | 6.576초 |
| `tbl_ws9` | 4 | `480190\|10072` | `459070\|14896` | 22:53:45.092 | 22:53:52.821 | 7.729초 |

각 트랜잭션의 `applied=100000`, `ins=100000`, `err=0`도 확인했다.

다섯 parent의 dependency가 모두 `459070|14896`으로 같은 것도 정상이다. 이 LSA는 workload 밖에서 먼저 실행한 START SBR 경계가 만든 보수적 floor다. shell은 START marker가 slave에 반영된 것을 확인한 뒤 parent wave를 시작하므로, 다섯 parent가 worker에 들어올 때는 이 공통 dependency가 이미 만족돼 있다.

```text
START SBR commit 459070|14896
  ↓ slave 반영 확인

tbl_ws1.dep = 459070|14896 ─┐
tbl_ws3.dep = 459070|14896  │
tbl_ws5.dep = 459070|14896  ├─ 같은 경계 뒤에서 서로 병렬
tbl_ws7.dep = 459070|14896  │
tbl_ws9.dep = 459070|14896 ─┘
```

이것은 `parent1 → parent2 → parent3` 같은 commit-order 사슬이 아니다. SBR marker를 각 parent workload transaction 안에 넣었다면 parent마다 직전 commit을 dependency로 받아 직렬화됐겠지만, 현재는 marker가 별도 transaction 하나이므로 모든 parent가 같은 출발선 뒤에 설 수 있다.

겹침을 상대 시간으로 그리면 다음과 같다. 기준점은 첫 parent START인 22:53:40.274다.

```text
초      0    2    4    6    8   10   12
        |----|----|----|----|----|----|
tbl_ws5 [============]                         6.302s
tbl_ws7    [=============]                     6.623s
tbl_ws3      [=============]                   6.391s
tbl_ws1         [=============]                6.576s
tbl_ws9           [===============]            7.729s
```

다섯 구간이 동시에 겹치므로 parent wave는 직렬이 아니라 병렬이다. START가 완전히 같은 밀리초가 아닌 이유는 reader가 각 COMMIT을 발견하고 worker queue에 넣는 시점이 조금씩 다르기 때문이다. 병렬성 판단은 START 동일 여부가 아니라 **START–END 구간의 중첩**으로 해야 한다.

## 9. 원인 — dependency 메커니즘 (코드는 코드 문서로)

> 구현 상세(파일·함수·라인·코드)는 [[writeset_v2_FK_브랜치_변경분_코드리뷰]]로 옮겼다: master가 REF를 만드는 §3~§6, slave가 dependency를 읽고 gate로 실행하는 §7, SBR/DDL 직렬화 §8. 여기서는 위 결과를 설명하는 데 필요한 개념만 둔다.

**master 측.** FK child DML에서 child가 참조하는 부모 키를 REF로 수집한다. child FK 값을 부모 PK domain으로 cast해 부모 class OID와 함께 해시하면, 부모가 INSERT 때 남긴 WRITE 해시와 바이트 단위로 같아진다. 커밋 시점에 이 해시들로 history를 조회해 매칭되는 부모 커밋 LSA를 `dependency_seq`로 확정하고 `LOG_COMMIT` 바로 앞에 라벨로 남긴다. **부모 WRITE만 history에 게시하고 child REF는 게시하지 않아**, 같은 부모를 참조하는 형제들은 서로 의존하지 않고 부모에만 의존한다(형제 병렬).

**slave 측.** reader가 `LOG_DUMMY_WS_LABEL`에서 dependency를 읽어 바로 다음 COMMIT의 task에 붙인다. gate는 세 경우에 즉시 dispatch한다 — dependency가 없거나(NULL), gap-free frontier 이하이거나, 먼저 끝난 부모의 exact commit이 completed set에 있을 때. 그 외에는 그 task만 대기 큐로 PARK하고, reader는 계속 읽어 뒤의 독립 트랜잭션은 별도로 dispatch한다(reader 자체가 멈추지 않는다).

따라서 자식은 **전역 진행선이 자기 순번에 도달할 때까지가 아니라, 자기 부모 한 건의 완료만** 기다리면 풀린다. 위 결과에서 "자식이 부모 완료 직후 시작"으로 나타난 이유가 이것이다. (MySQL은 이와 달리 복제본 FK 처리에서 같은 부모의 자식들을 직렬화한다 — [[2. writeset_MySQL_FK_병렬화_실측_2026-08-26]] 6.3절.)

## 10. 40.729초 공백은 무엇인가

### 10.1 먼저 배제되는 해석: parent flush가 40초 더 걸렸다

마지막 parent 로그는 다음이다.

```text
Time: 08/25/26 22:53:52.821
ws_apply END worker=4
  trid=32333899
  commit_lsa=480190|10072
  class=dba.tbl_ws9
  elapsed_usec=7728563
  applied=100000
  ins=100000
  err=0
```

worker는 `ws_apply END`를 기록하기 전에 다음 호출을 모두 끝낸다(상세는 [[writeset_v2_FK_브랜치_변경분_코드리뷰]] §7.4).

```cpp
la_apply_repl_log (...);
la_flush_repl_items (...);
la_commit_transaction (...);
LA_BENCH_TIMING_LOG ("ws_apply END ...");
```

따라서 22:53:52.821 뒤 40초를 “parent가 flush되어 서버에 반영되는 시간”이라고 설명할 수 없다.

### 10.2 배제되는 해석: 전역 last_committed가 parent 위치까지 와야 했다

자식 dependency 만족 조건에는 exact completed-set membership이 있다.

```cpp
if (dep <= frontier)
  return true;

return completed_set.contains (dep);
```

마지막 parent가 END 후 result로 수집되면 `480190|10072`가 exact completed set에 들어간다. 전역 gap-free frontier가 그 위치까지 오지 않았더라도 이 parent를 기다리는 `tbl_ws10`은 풀릴 수 있다.

따라서 “마지막으로 반영한 LSA가 증가해서 자식의 last_committed 차례가 될 때까지 40초 기다렸다”는 설명도 현재 코드와 맞지 않는다.

### 10.3 실제로 자식이 시작되려면 두 조건이 모두 필요하다

```text
조건 A
  slave에서 parent dependency가 완료돼야 한다.

조건 B
  master가 child transaction을 COMMIT하고,
  그 COMMIT record를 slave reader가 읽어
  LA_APPLY_TASK를 만들어야 한다.
```

실제 child dispatch 가능 시각은 개념적으로 다음과 같다.

```text
child dispatch time = max(
  parent dependency completed time,
  child COMMIT seen by reader time
)
```

이번에는 조건 A가 22:53:52.821 직후 이미 충족됐다. 그러나 child는 50,000행짜리 큰 transaction이다.

```text
master child csql
  INSERT 1
  INSERT 2
  ...
  INSERT 50,000
  COMMIT
      ↓
copylogdb 전송
      ↓
slave reader가 COMMIT을 읽음
      ↓
dependency 검사
      ↓
이미 parent 완료 → dispatch
```

그러므로 현재 40초의 가장 유력한 구성 요소는 다음이다.

1. master에서 child 50,000행 transaction 10개를 생성·실행하는 시간
2. commit log가 copylogdb를 통해 slave에 도달하는 시간
3. applylogdb reader가 해당 COMMIT record까지 읽는 시간
4. worker queue에 dispatch되는 짧은 대기

### 10.4 현재 시간만으로 40초를 정확히 분해할 수 없는 이유

확보한 경계는 다음뿐이다.

```text
parent slave END        22:53:52.821
master 전체 workload END 22:54:24.241
first child slave START 22:54:33.550
```

따라서 확실히 말할 수 있는 것은:

```text
마지막 parent slave END → master 전체 END = 31.420초
master 전체 END → 첫 child slave START      =  9.309초
합계                                        = 40.729초
```

다만 첫 child transaction의 master COMMIT이 `master 전체 END`보다 먼저 발생했을 수 있다. `master_end_time`은 10개 child csql이 **모두** 끝난 시각이므로 첫 child의 정확한 commit 시각이 아니다. 따라서 31.420초와 9.309초를 각각 “master 생성 시간”과 “순수 복제 지연”으로 단정해서는 안 된다.

현재 증거로 가능한 정확한 표현은 다음이다.

> 부모 slave 적용은 22:53:52.821에 이미 끝났다. 첫 자식은 그보다 40.729초 뒤 시작했다. 이 공백은 부모 flush나 전역 last_committed gate 대기가 아니라, 대형 child transaction이 master에서 COMMIT 경계에 도달하고 그 COMMIT을 slave reader가 볼 수 있게 되는 경로의 지연이 포함된 구간이다. 정확한 구성비는 child master COMMIT과 reader COMMIT_SEEN 계측이 없어 아직 분리할 수 없다.

### 10.5 2차 실험 (2026-08-27) — 40초 공백 해석의 검증

§10의 해석(공백은 부모 반영 시간이 아니라 자식 COMMIT의 생성·도달 대기)을 같은 조건으로 재실험해 검증했다. 코드와 워크로드는 08-25와 동일하다(빌드 d1f87c3, 부모 5개 × 100,000행, 자식 10개 × 50,000행, dataset 캐시 재사용). 측정 방법도 동일하다: slave 시각은 applylogdb 워커의 `ws_apply START/END` 로그(END는 slave DB commit까지 끝난 뒤 기록, §10.1), master 시각은 benchmark report의 `master_start_time/master_end_time`(부모+자식 csql이 모두 끝난 시각)이다.

**실측 타임라인**

```text
MASTER (youngjun3)
14:48:27.365  워크로드 시작
      │  부모 csql 5개 병렬 실행 (각 100,000행 + COMMIT 1회)
≈14:49:30     부모 wave 종료(추정치: 마지막 부모의 slave 적용
              시각 14:49:35.9에서 전달 지연을 역산) → 자식 csql 10개 병렬 시작
      │  자식들 각 50,000행 실행 중 (커밋 아직 없음)
≈14:49:55~    빨리 끝난 자식부터 순차 COMMIT
14:50:03.441  마지막 자식 COMMIT = master_end_time

SLAVE (youngjun4, applylogdb 워커 로그)
14:49:23.483  첫 부모 START   ─┐ 부모 5개 병렬 적용 (각 4.1~5.3초)
14:49:40.275  마지막 부모 END ─┘ (slave DB commit까지 완료)
      │
      │   공백 19.467초
      │
14:49:59.742  첫 자식 START   ← master_end보다 3.70초 빠름
      │  자식들이 commit LSA 순서대로 순차 START
14:50:10.965  마지막 자식 END (master 종료 후 7.4초 = 실측 복제 후행)
```

**관측 결과**

1. 공백이 40.729초에서 19.467초로 줄었다. 코드 변경은 없다.
2. 첫 자식의 slave START(14:49:59.742)가 master 전체 종료(14:50:03.441)보다 3.70초 앞선다. 이것은 인과 역전이 아니다. master_end_time은 자식 csql 10개가 **모두** 끝난 시각(= 가장 늦은 자식의 커밋)이고, 자식 10개는 master에서 동시에 실행되어 각자 자기 시점에 커밋한다. 즉 먼저 커밋한 자식은 아직 실행 중인 형제들을 기다리지 않고 슬레이브로 흘러가 적용이 시작됐다. 자식 하나하나를 보면 항상 "자기 master COMMIT → slave START" 순서가 지켜진다. 자식 10개의 slave START 순서가 commit LSA 순서와 정확히 일치한 것이 그 증거다(reader는 로그를 순서대로 읽으므로, 이 일치는 "커밋된 순서대로 도달하는 즉시 적용"을 의미한다).
3. 자식 10개의 dependency는 이번에도 전부 정확한 자기 부모의 commit LSA였고(tbl_ws6→tbl_ws5, tbl_ws10→tbl_ws9, tbl_ws4→tbl_ws3, tbl_ws8→tbl_ws7, tbl_ws2→tbl_ws1), 같은 테이블의 두 트랜잭션은 서로 의존하지 않았다.
4. 마지막 자식은 커밋 시각을 아는 유일한 트랜잭션이다(master_end_time = 마지막 csql 종료 ≈ 그 COMMIT 시각). 이 트랜잭션의 커밋 → slave START 간격이 **약 3.44초**(14:50:03.441 → 14:50:06.883)로, 순수 파이프라인 비용(로그 flush → copylogdb 전송 → reader가 선행 페이로드를 스캔해 COMMIT 레코드에 도달)이 직접 측정됐다. dependency로 인한 추가 대기는 측정 한계 안에서 0이다.

**08-25 런과의 구간 비교**

| 구간 | 08-25 런 | 08-27 2차 런 | 차이 |
|---|---:|---:|---:|
| 마지막 부모 slave END → master_end | 31.42초 | 23.17초 | −8.2초 |
| master_end → 첫 자식 slave START | +9.31초 | −3.70초 (선행) | −13.0초 |
| 합계 (공백) | 40.73초 | 19.47초 | −21.3초 |

**해석**

- 슬레이브가 기다린 것은 부모의 완료가 아니라 **자식 자신의 master COMMIT이 생성되어 슬레이브에 도달하는 것**이다. 부모 dependency는 공백이 시작되는 시점에 이미 충족돼 있었다.
- 공백이 두 런에서 21초나 다르다는 사실 자체가 이 공백이 코드가 만든 고정 대기가 아니라 두 가변 요인의 합이라는 방증이다.
  - 첫째 구간(−8.2초): master가 08-25에 더 느려서 자식 커밋이 늦게 생겼다. 자식 wave의 master 실행 시간이 약 49초에서 약 33초로 줄었다.
  - 둘째 구간(−13.0초): 08-25에는 자식이 전부 커밋된 뒤에도 9.31초가 지나서야 첫 자식이 시작됐다(전달·스캔이 뒤처짐). 2차 런에서는 reader가 커밋을 실시간으로 따라잡아 wave가 끝나기 전에 적용이 시작됐다. 08-25는 applylogdb 벤치 로그가 5.88GB까지 커진 상태여서 로그 I/O가 reader와 worker를 함께 눌렀고, 같은 신호로 부모 적용 시간도 6.3~7.7초 vs 4.1~5.3초로 느렸다(§12.3의 계측 주의사항과 일치).
- 소스 근거 보강: 복제 레코드(LOG_REPLICATION_DATA)는 행 DML 실행 중에는 트랜잭션 메모리에 버퍼링만 되고 **커밋 시점에 일괄로** 로그에 배출된다(이어서 WS 라벨, COMMIT 레코드 순으로 같은 뮤텍스 구간에서 append). 따라서 자식이 커밋하기 전에는 슬레이브가 적용할 데이터 자체가 로그에 존재하지 않는다. 호출 체인 상세는 [[writeset_v2_FK_브랜치_변경분_코드리뷰]] 참조.

**측정 조건 기록**

- 같은 날 1차 런(13:56)은 벤치 도구(ha_bench_tool)의 설정 파일 config/default.json에서 slave.host가 빈 값이어서, "슬레이브 반영 대기" 폴링이 전부 master 자신을 조회했다. 그래서 report의 slave 수치(replication_lag 301ms)가 무효였고 이 문서에서는 제외한다. 2차 런은 slave.host를 youngjun4로 수정한 뒤 실행했고, report의 slave_end(14:50:10.829)와 applylogdb 마지막 END(14:50:10.965)가 0.1초 안에서 일치해 계측 정합이 확인됐다.
- 시점 오염 방지를 위해 applylogdb 로그의 실행 전 offset(64,370,372 bytes)을 워터마크로 남기고 그 이후 기록만 사용했다.
- 후속 계측: run_constraint.sh에 csql 파일별 START/END 시각(ms) 기록을 추가했다(log/csql_timing.log). csql은 COMMIT 응답 직후 종료하므로 END 시각이 곧 그 트랜잭션의 master 커밋 시각이다. 다음 런부터 공백을 "master 생성 시간"과 "커밋 후 전달·스캔 시간"으로 트랜잭션별로 분해할 수 있다.


### 10.6 3차 실험 (2026-08-27) — 트랜잭션별 커밋 시각 계측으로 공백 분해 확정

10.5가 남긴 한계는 "자식들의 master 커밋 시각을 몰라 공백을 생성 시간과 전달 시간으로 나누지 못한다"였다. 이를 해소하기 위해 벤치마크 shell(run_constraint.sh)에 csql 파일별 시작/종료 시각(ms)을 기록하는 계측을 추가하고(log/csql_timing.log) 같은 구성으로 재실험했다. csql은 마지막 COMMIT 응답 직후 종료하므로 **csql 종료 시각 ≈ 그 트랜잭션의 master 커밋 시각**이다. 두 호스트의 시계 차이는 +0.08초(slave가 빠름, 3회 측정)로 무시 가능한 수준이다.

**실측 타임라인**

```text
MASTER (youngjun3, csql_timing.log)
17:07:39.711  부모 csql 5개 동시 시작 (12ms 안에 5개 모두 출발)
17:08:30.050  부모 커밋 시작 ~ 17:08:34.157 마지막 부모 커밋 (실행 50.3~54.4초)
17:08:34.165  자식 csql 10개 동시 시작 (마지막 부모 커밋 8ms 뒤, 33ms 안에 10개 출발)
17:09:05.422  첫 자식 커밋 ~ 17:09:08.875 마지막 자식 커밋 (실행 31.3~34.7초)

SLAVE (youngjun4, applylogdb 워커 로그)
17:08:30.042  첫 부모 START  ← 자기 master 커밋과 사실상 동시
17:08:38.660  마지막 부모 END (적용 각 ~4.5초)
      │
      │   공백 26.596초
      │
```

그림 해석: 위 두 줄이 master의 부모/자식 csql 실행 구간(끝의 검은 눈금이 커밋), 아래 파랑/초록 막대가 slave 적용 구간이다. 파란 부모 막대들의 시작이 master 커밋 눈금 바로 아래에 있고, 초록 점선(첫 자식)에서 master 커밋과 slave START가 같은 세로선에 놓인다. 빨간 화살표 구간(공백 26.6초) 동안 master 줄을 보면 자식들이 아직 실행 중이라 커밋이 없다.

**관측 결과**

1. **공백의 분해가 실측으로 확정됐다.** 공백 26.596초 = 첫 자식의 master 실행 31.26초(자식 wave 시작 34.165 → 첫 커밋 05.422) − 마지막 부모의 slave 적용 꼬리 4.5초(부모는 커밋 직후부터 적용되므로 자식이 실행되는 동안 부모 적용이 함께 진행) + 전달·dispatch ≈ 0초. 즉 공백은 전부 "master가 자식 트랜잭션을 아직 만드는 중"인 시간이며, 로그 전달의 기여는 없다.
2. **reader는 로그를 실시간으로 따라가고 있었다.** 부모 5개와 초기 자식들의 slave START가 각자 자기 master 커밋과 ±0.3초 안에서 일치한다. 행 데이터(redo)는 트랜잭션 실행 중에 이미 전달되고, 커밋 시점의 복제 레코드 묶음만 도착하면 즉시 task가 만들어지기 때문이다.
3. **커밋이 몰리면 reader 스캔이 적체된다.** 자식 10개의 커밋이 3.5초 안에 몰리자 자식별 "커밋 → slave START" 지연이 뒤로 갈수록 커졌다: 1~4번째 ≈0초, 5~7번째 +0.5~0.7초, 8~10번째 +5.4초. 이때 워커들은 4초 이상 유휴 상태였으므로 워커 부족이 아니라 reader가 선행 트랜잭션들의 페이로드(각 50,000 레코드)를 순차 스캔하는 시간이 병목이다. 10.5의 2차 실험에서 근사했던 "커밋→적용 3.4초"는 마지막 자식 기준이라 적체가 포함된 값이었고, 첫 자식 기준으로는 ≈0초다. 즉 전달 지연은 상수가 아니라 커밋 밀도에 따른 적체다.
4. **master의 두 wave 모두 병렬 실행이 맞다.** 부모 5개는 12ms 안에, 자식 10개는 33ms 안에 동시 출발해 실행 구간이 전부 겹쳤다. 서버가 직렬 처리했다면 총 500,000행 × 건당 0.5ms ≈ 250초가 걸렸어야 하는데 실측 wave는 54.4초(부모)·34.7초(자식)로, 트랜잭션 하나 몫의 시간만 걸렸다.
5. **입력 총량이 같은데 자식 wave가 빠른 이유는 병렬도 차이다.** 두 wave 모두 총 500,000행이지만, wave 시간은 총량이 아니라 "트랜잭션 하나가 순차로 처리하는 행 수 × 건당 왕복시간"으로 정해진다. 부모는 5개 트랜잭션이라 하나가 100,000회, 자식은 10개라 하나가 50,000회만 왕복하면 된다. 절반(약 26초)까지 내려가지 않고 31~35초인 이유는 자식의 건당 비용이 더 크기 때문이다(행마다 FK 검사로 부모 PK 조회, 인덱스 2개 유지, 동시 세션 10개의 경합: 건당 0.50→0.65ms). 같은 이유로, master 실행 시간의 대부분은 엔진의 쓰기 비용이 아니라 csql 단건 EXECUTE의 클라이언트-서버 왕복이다. 같은 100,000행을 slave 워커는 왕복 없이 4.5초에 적용했다.
6. dependency는 이번에도 자식 10개 전부 정확한 자기 부모의 commit LSA였고(형제 상호 미의존), 자식 첫 배치는 워커 7개(0~6)에서 동시 실행됐다.

**측정 조건 기록**

- 계측: run_constraint.sh가 wave 경계와 csql별 START/END(ms)를 log/csql_timing.log에 기록. 자식 파일명이 child1/child2 모두 tbl_wsN.sql로 같아 로그만으로는 두 트랜잭션이 구분되지 않는데, master 커밋 순서와 slave commit LSA 순서의 테이블 시퀀스가 완전히 일치해 짝을 확정했다.
- applylogdb 벤치 로그가 941MB(시작)~1.12GB(종료) 상태에서 실행됐다(유휴 중에도 empty commit 로그가 분당 ~13MB 누적). 로그 I/O 부하가 있는 조건이므로 절대치 비교 시 참고.
- report(20260827_170923)의 slave 수치는 유효하며(replication_lag 8.6초), applylogdb 로그의 마지막 END와 정합.

## 11. 40초 동안 다른 트랜잭션으로 공백을 채울 수 있는가

### 11.1 코드상 답: 가능하다

reader는 child를 PARK해도 다음 log record를 계속 읽는다.

```cpp
if (la_gate_is_satisfied (&child.dependency_seq))
  dispatch (child);
else
  enqueue_pending (child);

// 함수가 끝난 뒤 reader는 다음 log record 처리를 계속한다.
```

그 뒤 부모와 무관한 transaction X의 COMMIT을 만나면:

```cpp
X.dependency_seq == NULL
  → la_gate_is_satisfied() == true
  → 즉시 dispatch
```

또는 X가 다른 정확한 dependency를 가지더라도 그 dependency가 completed set에 있으면 dispatch된다.

```text
parent P 관련 child C는 아직 task가 없거나 PARK

reader가 독립 X COMMIT 발견
  X.dep = NULL
  → worker 2에 dispatch

reader가 독립 Y COMMIT 발견
  Y.dep = NULL
  → worker 3에 dispatch

나중에 C COMMIT 발견
  C.dep = P.commit
  P는 이미 completed set에 있음
  → C도 즉시 dispatch
```

### 11.2 이번 원본 로그에서도 applier 전체가 멈추지 않았다

40초 공백 내부인 22:54:00 시점의 대표 로그다.

```text
Time: 08/25/26 22:54:00.000
ws_apply END worker=0 trid=32404393
  commit_lsa=486626|14368
  class=<none> elapsed_usec=54 applied=0 err=0

Time: 08/25/26 22:54:00.004
ws_apply END worker=0 trid=32404394
  commit_lsa=486628|3496
  class=<none> elapsed_usec=98 applied=0 err=0

Time: 08/25/26 22:54:00.013
ws_apply END worker=0 trid=32404399
  commit_lsa=486634|11496
  class=<none> elapsed_usec=77 applied=0 err=0
```

같은 형태의 empty commit task가 이 구간에 대량으로 처리됐다. 이것이 보여주는 사실은 다음과 같다.

```text
확정 가능:
  reader/coordinator와 worker가 전역 dependency barrier에 멈춰 있지 않았다.
  FK 대상 child가 시작하지 않은 동안에도 다른 commit task가 dispatch·완료됐다.

이 로그만으로 확정 불가:
  의미 있는 별도 업무 DML이 40초 동안 처리됐다는 것.
  위 샘플은 applied=0인 empty commit이므로 실제 데이터 처리량 증거는 아니다.
```

즉 이번 실측은 “전체 정지 아님”을 직접 보여주고, 코드는 “독립 데이터 트랜잭션도 같은 방식으로 실행 가능”함을 보여준다. 다음 혼합 workload 실험에서 실제 independent DML로 공백을 채우는 그림을 검증해야 한다.

### 11.3 독립 트랜잭션도 실행되지 못하는 예외

다음 조건에서는 부모와 논리적으로 무관해 보여도 즉시 실행되지 않을 수 있다.

1. 아직 master에서 COMMIT되지 않아 task 자체가 없다.
2. copylogdb/reader가 그 COMMIT record까지 도달하지 않았다.
3. 실제 writeset hash가 다른 선행 transaction과 충돌한다.
4. SBR/DDL이 있어 commit-order fallback에 걸렸다.
5. 10개 worker가 모두 긴 작업을 실행 중이다.
6. worker queue나 다른 자원 제약에 걸렸다.

그러므로 보고서에서 “40초를 무조건 100% 활용한다”고 쓰는 것도 과장이다. 정확한 표현은 다음과 같다.

> 40.729초는 FK dependency가 applylogdb 전체에 만든 전역 정지 시간이 아니다. 이 구간에 COMMIT이 reader에게 보이고 dependency가 만족된 독립 트랜잭션은 가용 worker에서 병렬 실행될 수 있으므로, 실제 workload가 존재한다면 공백을 유용한 적용 작업으로 채울 수 있다.

### 11.4 기대하는 혼합 workload 타임라인

```text
시간 ─────────────────────────────────────────────────────▶

parent FK       [==========] END
child FK                                             [==========]

independent X1              [=======]
independent X2                 [==========]
independent X3                       [======]
independent X4                           [========]

                ← FK 그래프만 보면 공백 →
                ← 전체 worker 관점에서는 활용 가능 →
```

이것이 writeset 병렬 적용의 핵심 기대 효과다. 전체 commit order를 한 줄로 지키는 것이 아니라, 실제로 충돌하는 parent–child 간선만 지키고 나머지 transaction은 빈 worker에서 진행시킨다.

## 12. 현재 테스트가 증명한 것과 아직 증명하지 못한 것

### 12.1 증명한 것

- parent 5개 transaction의 START–END 구간이 겹쳤다.
- child 10개 transaction의 START–END 구간이 겹쳤다.
- child의 dependency LSA가 정확한 자기 parent table의 commit LSA와 일치했다.
- 같은 child table의 두 transaction은 서로가 아니라 같은 parent commit을 dependency로 가졌다.
- parent END는 final flush와 slave DB commit 뒤에 기록됐다.
- child release는 전역 `committed_lsa`가 아니라 exact completed set으로도 가능하다.
- 40초 공백 중에도 applier reader/worker가 다른 empty commit task를 처리했다.
- workload 밖으로 분리된 SBR marker는 parent/child RBR writeset을 commit-order fallback으로 오염시키지 않았다.

### 12.2 아직 증명하지 못한 것

- 40.729초 중 master child 실행, copylog 전송, reader scan이 각각 몇 초인지
- child COMMIT을 reader가 정확히 언제 처음 봤는지
- child가 처음 PARK됐다가 풀렸는지, 발견 시 이미 dependency가 만족돼 즉시 DISPATCH됐는지
- 40초 동안 실제 `applied>0`인 독립 업무 transaction이 FK와 병렬 적용되는지
- topology 1:4와 1:9에서도 같은 형태로 확장되는지
- child transaction 수를 1, 2, 그 이상으로 바꿀 때 COMMIT 가시성과 worker 점유가 어떻게 달라지는지
- 역방향 `child DELETE → parent DELETE` 정합성 문제의 해결 여부

### 12.3 절대 성능 수치의 계측 주의사항

현재 `LA_BENCH_TIMING_LOG`는 `applied=0`인 empty commit을 포함해 worker가 받은 모든 task에 START/END 두 줄을 남긴다.

```cpp
#define LA_BENCH_TIMING_LOG(...) _er_log_debug (__VA_ARGS__)

// 모든 task에서 실행
LA_BENCH_TIMING_LOG ("ws_apply START ...");
...
LA_BENCH_TIMING_LOG ("ws_apply END ...");
```

실측 slave의 applylogdb 로그는 확인 시점에 약 5.88GB까지 증가해 있었다. 이번 문서의 START–END 중첩은 병렬성의 존재를 판정하는 데 유효하지만, 다음 값은 로그 I/O 오버헤드의 영향을 받을 수 있다.

```text
각 worker의 절대 수행시간
master 대비 slave의 절대 lag
초당 transaction/row 처리량
```

기능 검증이 끝나면 다음 중 하나로 timing 로그를 줄이는 편이 좋다.

1. `applied > 0`인 transaction만 END를 기록하고 START는 대상 task만 기록한다.
2. benchmark 대상 class/table만 allowlist로 기록한다.
3. START/END 개별 로그 대신 worker별 누적 histogram과 주기적 summary를 기록한다.
4. 혼합 workload 검증에 필요한 `COMMIT_SEEN/PARK/RELEASE`만 sampling하거나 대상 trid에 한정한다.

따라서 이 문서의 6.3~11.2초 worker 시간과 40.729초 공백은 현재 계측 조건에서 관찰된 값이며, 제품 성능의 최종 수치로 인용하기 전에는 최소 로그 빌드로 재측정해야 한다.

## 13. 다음 검증에서 필요한 최소 계측

대량 `er_log_debug`를 켜면 현재처럼 수 GB 로그가 생겨 성능 측정 자체를 오염시킬 수 있다. 다음 세 종류만 release-visible benchmark 로그로 제한하는 것이 좋다.

### 13.1 reader가 COMMIT을 본 시각

```text
ws_gate COMMIT_SEEN
  trid=<id>
  class=<table or workload tag>
  commit=<lsa>
  dep=<lsa>
  time=<timestamp>
```

### 13.2 즉시 실행인지 PARK인지

```text
ws_gate DISPATCH
  trid=<id> commit=<lsa> dep=<lsa>

ws_gate PARK
  trid=<id> commit=<lsa> dep=<lsa>
```

### 13.3 PARK 해제 시각과 대기시간

```text
ws_gate RELEASE
  trid=<id>
  commit=<lsa>
  dep=<lsa>
  waited_usec=<n>
```

이 세 시각이 있으면 다음처럼 정확히 나눌 수 있다.

```text
master child COMMIT
  → copylog/reader COMMIT_SEEN 지연
  → dependency PARK 대기
  → worker queue 대기
  → START
```

### 13.4 혼합 workload 검증 시나리오

40초 활용 가능성을 눈으로 보여주려면 parent wave와 child wave 사이에 별도 독립 table transaction을 master에서 계속 발생시킨다.

```text
FK graph:
  P1..P5 → C1..C5

독립 graph:
  X1, X2, X3, ...
  FK table과 class OID 및 PK 공간이 겹치지 않음
```

기대 결과:

```text
P wave END
  ↓
X transaction들이 worker에서 계속 START/END
  ↓
C COMMIT_SEEN
  ↓ parent exact dependency 이미 완료
C wave START
```

판정 기준:

1. X의 `dependency_seq`가 NULL 또는 자기 graph의 선행만 가리킨다.
2. X의 START–END가 40초 FK 공백 안에 존재한다.
3. C의 dependency는 기존처럼 정확한 P commit이다.
4. 최종 master/slave row count와 checksum이 일치한다.
5. X를 넣지 않은 baseline과 비교해 C의 정합성과 dependency가 바뀌지 않는다.

## 14. child transaction 개수에 따른 예상 변화

현재는 child table당 2개 transaction이므로 50,000행마다 COMMIT한다.

| child table당 transaction 수 | transaction당 행 수 | 예상되는 COMMIT 가시성 | 예상 worker 작업 크기 |
|---:|---:|---|---|
| 1 | 100,000 | 가장 늦게 task가 생김 | 가장 큼 |
| 2 | 50,000 | 현재 기준 | 현재 기준 |
| 4 | 25,000 | 더 일찍 첫 task가 생길 가능성 | 더 작음 |
| 10 | 10,000 | commit task가 더 자주 생김 | 더 작지만 commit overhead 증가 |

한 개 transaction으로 합치면 같은 child table의 100,000행을 한 worker가 처리한다.

```text
장점:
  transaction/commit overhead 감소
  dependency entry 수 감소

단점:
  master가 100,000행 뒤 COMMIT할 때까지 slave가 시작 불가
  한 child table이 worker 하나만 사용
  긴 transaction 하나가 worker를 오래 점유
```

두 개 이상으로 나누면 첫 COMMIT이 빨리 보일 수 있고 같은 parent를 보는 child transaction들이 REF를 게시하지 않으므로 부모 완료 뒤 병렬화할 수 있다. 다만 transaction을 지나치게 잘게 나누면 commit과 gate 관리 비용이 커진다. 이 옵션의 목적은 정답 하나를 고르는 것이 아니라, **COMMIT 가시성 지연과 병렬 worker 활용의 trade-off를 실측하는 것**이다.

## 15. 최종 결론

이번 테스트에서 확인된 실행 형태는 다음과 같다.

```text
parent 5개 병렬
  {tbl_ws1, tbl_ws3, tbl_ws5, tbl_ws7, tbl_ws9}

각 parent의 slave DB commit 완료
  ↓
FK 대상 로그에서 40.729초 공백
  ↓ 이 구간은 전체 applier 정지가 아님
  ↓ 독립 transaction의 commit이 보이면 worker에서 실행 가능

child transaction 10개 병렬
  {tbl_ws2×2, tbl_ws4×2, tbl_ws6×2, tbl_ws8×2, tbl_ws10×2}
```

코드가 보장하는 핵심은 “자식은 전체 선행 commit을 기다려라”가 아니다.

```text
자식은 자신이 참조하는 정확한 부모 commit 하나가
slave에 적용 완료될 때까지만 기다려라.
```

그리고 부모 완료가 exact completed set에 기록되면 global frontier에 hole이 있어도 자식은 풀릴 수 있다. 따라서 40초를 `last_committed` 순번 대기로 설명해서는 안 된다.

현재 40초는 큰 child transaction이 COMMIT 가능한 상태가 되고 그 COMMIT을 slave reader가 보는 경로가 포함된 시간이다. 이 구간은 writeset 설계상 독립 transaction으로 채울 수 있다. 다음 실험의 목표는 단순히 공백을 줄이는 것뿐 아니라, **공백 중 실제 독립 DML이 병렬 적용되는 타임라인을 보여 주는 것**이어야 한다.

## 16. 부록 A — 용어

### 16.1 master와 slave

- **master**: 사용자의 INSERT/UPDATE/DELETE를 실행하고 HA 복제 로그를 생성한다.
- **slave**: `copylogdb`로 로그를 받고 `applylogdb`로 DB에 다시 적용한다.

이 테스트에서 시간 축은 하나가 아니다.

```text
master SQL 실행 시간
    ↓
master commit 및 로그 기록 시간
    ↓
copylogdb가 slave에 로그를 전달하는 시간
    ↓
applylogdb reader가 commit record까지 읽는 시간
    ↓
worker가 row replication item을 적용하고 slave DB에 commit하는 시간
```

따라서 “master에서 부모가 commit됐다”, “slave reader가 부모 COMMIT을 봤다”, “slave worker가 부모를 DB에 commit했다”는 서로 다른 사건이다.

### 16.2 트랜잭션 단위 적용

applylogdb의 병렬 작업 단위는 **행 한 개가 아니라 트랜잭션 하나**다.

```sql
;autocommit off

EXECUTE child_insert USING 1, ...;
EXECUTE child_insert USING 2, ...;
...
EXECUTE child_insert USING 50000, ...;

COMMIT;
```

slave reader는 위 트랜잭션의 중간 25,000행 지점에서 worker에 작업을 넘길 수 없다. 마지막 `COMMIT` record를 읽어야 트랜잭션의 경계가 확정되고 하나의 `LA_APPLY_TASK`를 만들 수 있다.

### 16.3 `commit_lsa`

트랜잭션의 COMMIT log record 위치다. 문서와 로그에서는 다음처럼 표기한다.

```text
480190|10072
  page | offset
```

이 값은 master commit 순서상 트랜잭션을 식별하는 번호처럼 사용된다.

### 16.4 `dependency_seq`

현재 트랜잭션이 slave에서 실행되기 전에 완료돼야 하는 선행 트랜잭션의 `commit_lsa`다.

```text
dependency_seq = NULL(-1|-1)
  → 선행 dependency가 없음
  → 즉시 병렬 실행 가능

dependency_seq = 480190|10072
  → commit_lsa=480190|10072인 선행 트랜잭션이 완료된 뒤 실행 가능
```

이름이 `seq`지만 현재 PoC에서는 실제 값으로 LSA를 사용한다.

### 16.5 WRITE와 REF

FK 확장 브랜치는 writeset key를 두 종류로 구분한다.

```text
WRITE
  해당 키의 행을 실제로 썼다.
  예: parent.id=1 INSERT

REF
  자식 FK가 부모 키를 참조한다.
  예: child.parent_id=1 INSERT
```

부모의 WRITE와 자식의 REF가 같은 해시가 되면 자식은 정확한 부모 commit을 dependency로 얻는다.

### 16.6 gate frontier와 completed set

slave gate는 완료 상태를 두 방식으로 기억한다.

```text
frontier
  이 LSA 이하의 모든 commit이 구멍 없이 완료됐다는 연속 하한선

completed set
  frontier보다 앞서 out-of-order로 먼저 완료된 개별 commit LSA 집합
```

이 둘을 구분해야 “전역 last_committed가 올라와야 자식이 풀린다”는 오해를 피할 수 있다.
