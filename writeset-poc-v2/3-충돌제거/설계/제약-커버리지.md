# 제약조건 커버리지 공백 — MySQL 9.7 대조

writeset이 트랜잭션 사이의 순서를 잡으려면, 순서에 영향을 주는 모든 변경이 빠짐없이 비교 가능한 해시로 기록돼야 한다. 이 문서는 CUBRID writeset이 어떤 제약조건을 제대로 잡고 어떤 것을 놓치는지, 같은 목적의 MySQL 9.7 구현(`rpl_write_set_handler.cc`)과 대조해 정리한다. 놓치는 것 중 순서를 뒤집을 수 있는 것(정합성 위험)과 단지 과직렬화에 그치는 것(성능 손해)을 구분하는 것이 핵심이다.

분석 대상은 CUBRID `feature/parallel_applylogdb_writeset_rw_slot` 브랜치이며 읽기 전용 분석이다. 코드 근거는 file:line으로 인라인 표기한다.

## 1. CUBRID 현황

**키 수집.** 모두 `locator_sr.c`의 행 기반 복제(RBR) 경로에서만 수집한다.

- PK는 쓰기(WRITE) 키로 수집한다(INSERT/DELETE `:8172`, UPDATE는 OLD·NEW 둘 다 `:8925`).
- UNIQUE/REVERSE_UNIQUE도 쓰기 키다(`:8041`, UPDATE `:8726`). nullability와 무관하게 모든 유니크 인덱스를 수집한다.
- FK는 부모 참조(REF) 키로 수집한다(`:8052`). 부모 PK 도메인으로 캐스팅해 부모 PK 쓰기 해시와 같은 값이 되도록 맞춘다.

**해시 입력.** `class_oid(8바이트) + 팩된 키 값`을 FNV-1a로 해시한다(`log_writeset.c:90-115`). 즉 **테이블과 값만으로 식별**하며, 인덱스 이름·DB명·테이블명·collation은 입력에 없다.

**격하(commit-order 폴백) 지점은 두 곳뿐이다.** 트랜잭션당 키 한도를 넘으면 그 writeset을 통째로 버리고 격하하고(`log_writeset.c:190`), DDL 같은 문장 복제는 행 이미지가 없어 표현이 불가능해 격하한다(`replication.c:540`). 전역 히스토리 용량 초과는 격하가 아니라 히스토리를 비우고 기준선을 올리는 처리다.

**NULL 처리.** 참조(FK) 경로만 NULL을 건너뛴다(`log_writeset.c:363`). 쓰기(PK/UNIQUE) 경로는 NULL 검사가 없어 NULL 유니크 값도 그대로 해시한다(뒤의 G2).

## 2. 정합성 위험 — 순서를 뒤집을 수 있는 것 (2건)

### G1. 문자열 키의 collation 정규화 (확정)

MySQL은 키 값을 collation으로 정규화한(`make_sort_key` = `strnxfrm`) 바이트로 해시한다(`rpl_write_set_handler.cc:971-986`). 그래서 대소문자를 구분하지 않는(ci) collation에서 `'abc'`와 `'ABC'`가 같은 해시가 되어 같은 유니크 값으로 충돌을 잡는다.

CUBRID는 `or_pack_mem_value`의 데이터 경로가 **원본 문자 바이트를 그대로** 팩하고 해시한다. collation 정규화를 하는 인덱스 전용 경로와 별개다. 따라서 ci/ai collation을 쓰는 PK·UNIQUE에서 마스터는 `'abc'`/`'ABC'`를 같은 값으로 직렬화하지만, writeset 해시는 서로 달라 두 트랜잭션을 독립으로 판정한다. 슬레이브가 순서를 뒤집으면 UNIQUE 위반이 조용히 지나간다.

- **발현 조건**: ci/ai collation을 쓰는 유니크 키가 있을 때만. data 경로가 정규화를 안 하는 것은 코드로 확정.
- **심각도**: 정합성(HIGH), 조건부.

### G3. 복합(다중열) FK → 복합 부모키 (확정, 코드가 명시적으로 스킵)

MySQL은 복합 컬럼 FK도 참조 컬럼 전부로 키를 만들어 writeset에 넣는다. CUBRID는 부모 PK 도메인이 다중열(`DB_TYPE_MIDXKEY`)이면 REF 수집을 **건너뛴다**(`log_writeset.c:369`, 주석 "packed midxkey equivalence not yet proven, skip").

그 결과 복합 PK 부모 + 복합 FK 자식일 때 자식이 부모 커밋 뒤로 게이트되지 않는다. 부모와 자식이 다른 트랜잭션이고 공유 키가 없으면 슬레이브가 자식을 먼저 적용해 FK 위반(조용한 skip)이 난다.

- **발현 조건**: 복합키 FK 사용 시. 코드에 이미 알려진 한계로 표기됨.
- **심각도**: 정합성(MEDIUM~HIGH).

## 3. 성능 손해 — 안전하지만 과직렬화 (3건)

이쪽은 실제로는 독립인 트랜잭션을 불필요하게 직렬화하는 것으로, 정합성은 안전하고 처리량만 손해다.

- **G2. NULL을 포함한 유니크 키** — MySQL은 키 파트에 NULL이 있으면 그 키를 건너뛴다("NULL은 어떤 값과도 충돌하지 않는다"). CUBRID는 쓰기 경로에 NULL 검사가 없어 NULL 유니크 값을 모두 같은 해시로 묶는다. nullable UNIQUE에 NULL이 많으면 독립 행들이 직렬화된다. (확정, 안전)
- **G6. 인덱스 정체성 미구분** — 해시 입력이 `테이블 + 값`뿐이라, 같은 테이블에서 PK=5인 행과 UNIQUE=5인 행이 같은 해시가 되어 거짓 충돌한다. 다만 인덱스 이름을 안 넣는 이 설계 덕에 FK 참조가 부모 PK 쓰기와 손쉽게 충돌하도록 맞춰진 것이라, 의도된 트레이드오프다. (확정)
- **G14. `foreign_key_checks=0`** — MySQL은 FK 체크를 끄면 FK writeset을 건너뛴다. CUBRID는 이 상황을 따로 거르지 않아 FK 참조를 그대로 수집한다. 안전, 경미한 성능 손해.

## 4. 확인 필요 (2건)

- **G4. 참조되는 부모 테이블(cascade 대비)** — MySQL은 수정 대상이 다른 테이블의 FK 부모이면 writeset을 통째로 포기하고 격하한다(cascade 자식 변경을 못 잡기 때문). CUBRID는 cascade 자식 변경도 같은 트랜잭션의 복제 레코드로 실제 수집하므로([[소스-확인]] 2-2) MySQL식 통째 격하가 불필요하고 오히려 정밀하다. 다만 cascade 경로 중 writeset 수집을 우회하는 것이 없는지 확인이 필요하다. 확인되면 해당 없음, 우회 경로가 있으면 정합성 위험.
- **G5. PK 없는 테이블의 행 정체성** — 쓰기 키가 PK 게이트에 묶여 있어, PK도 NOT NULL UNIQUE도 없는 테이블은 행 정체성을 못 남긴다. 코드 TODO(RK)가 "PK → RK(PK 또는 NOT NULL UNIQUE)" 전환을 예고하고 있어, 그 로드맵에 이미 포함된 알려진 항목이다.

## 5. 해당 없음 / 이미 커버 (G7~G13)

- **G7 비유니크 참조 FK** — CUBRID FK는 항상 부모 PK/유니크를 참조하므로 성립하지 않음.
- **G8 CTAS·DDL** — 모든 DDL이 문장 복제로 격하되어 커버됨.
- **G9 non-ROW 포맷** — writeset 수집이 RBR 경로에서만이라 등가.
- **G10 개수·메모리 한계** — 트랜잭션당 한도와 전역 용량 양쪽 존재, 등가.
- **G11 임시테이블·복제필터** — 복제 게이트가 담당, 해당 없음.
- **G12 multi-value(JSON 배열) 인덱스** — 기능 부재.
- **G13 함수형·prefix·가상컬럼 인덱스** — 유니크 값이 그대로 수집되고, CUBRID 유니크/PK는 prefix를 안 쓰므로 저위험.

## 6. 조치 우선순위

| 항목 | 공백 | 심각도 | 상태 |
| --- | --- | --- | --- |
| G1 collation 정규화 | ci/ai collation 유니크에서 해시 불일치 | 정합성(HIGH) | 확정, ci/ai 사용 시 발현 |
| G3 복합 FK 부모키 | 복합키 FK 자식이 부모 뒤로 게이트 안 됨 | 정합성(MED~HIGH) | 확정, 코드가 명시 스킵 |
| G5 PK 없는 테이블 | 행 정체성 미수집 | 정합성 | RK 전환으로 해결 예정 |
| G4 cascade 부모 | 우회 수집 경로 있으면 공백 | 정합성 | 확인 필요(정밀할 것으로 추정) |
| G2 NULL 유니크 | NULL 행 과직렬화 | 성능 | 확정(안전) |
| G6 인덱스 미구분 | 같은 값 다른 제약 거짓 충돌 | 성능 | 확정(의도된 트레이드오프) |
| G14 FK 체크 off | FK 참조 과직렬화 | 성능 | 경미 |
| G7~G13 | — | — | 해당 없음 / 이미 커버 |

**최우선 확인 2건은 G1(collation 정규화)과 G3(복합키 FK)다.** 나머지 공백은 과직렬화(성능 손해)로 안전 측 편향이고, G5는 RK 전환 로드맵에 이미 들어 있다.
