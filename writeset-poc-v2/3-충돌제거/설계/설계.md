# writeset v2 설계 — FK·UNIQUE 확장과 형제 병렬

writeset 병렬 적용의 충돌 판정을 PK 전용(v1)에서 **UNIQUE와 FK까지** 넓힌다. FK는 MySQL처럼 폴백(부모 테이블에 쓰기가 있으면 writeset을 포기하고 커밋 순서로 보수 처리)으로 우회하지 않고, **자식의 FK 해시를 부모 PK 해시와 같은 값으로 만들어 매칭만으로 부모-자식 순서를 잡는다.** 여기에 마스터의 전역 히스토리 맵을 쓰기·참조 두 슬롯으로 나눠, 같은 부모를 참조하는 형제 트랜잭션끼리는 줄을 서지 않게 한다.

읽는 독자는 HA 복제·applylogdb를 아는 팀원을 전제한다. MySQL 쪽 상세 근거와 실측은 [[자료조사]]와 [[fk-병렬화-실측]]에, 이 설계를 뒷받침하는 CUBRID 소스 근거는 [[소스-확인]]에 있다.

## 1. 요약

대표 시나리오(무관한 T1·T3, 부모 T2, 자식 T4·T5)에서 병렬 파동이 어떻게 달라지는지로 요약하면 다음과 같다.

```
현재 MySQL (부모 폴백):      T1 | T2 | T3 T4 | T5
v2, 폴백 제거만:             {T1 T2 T3} | T4 | T5
v2 + 쓰기/참조 슬롯 분리:     {T1 T2 T3} | {T4 T5}    ← 이번 PoC의 목표
```

슬레이브는 트랜잭션마다 자신의 의존(dependency)을 이미 적용된 LSA와 비교해, 실행 가능하면 바로 적용한다. 무관한 트랜잭션(T1·T3)은 의존이 없어 즉시 실행되고, 자식(T4·T5)은 정확히 부모(T2) 뒤에만 서며, 형제끼리는 병렬이 된다. 마지막 줄의 형제 병렬은 MySQL이 5년째 방치 중인 과직렬화(#110071)를 구조적으로 푸는 것으로, MySQL은 원리상 불가능하고 CUBRID만 가능하다(3절).

## 2. v1의 한계 — PK만으로 놓치는 것

v1은 행 식별을 PK로만 하므로, 서로 다른 PK를 건드린 트랜잭션은 무조건 독립으로 본다. 그런데 병렬 적용의 정합성에는 PK 말고도 두 가지가 더 걸린다.

첫째, **유니크 값 재사용**이다. `t(id PK, email UNIQUE)`에서 T1이 id=1을 지워 email='X'를 비우고, T2가 id=2로 'X'를 다시 넣는다고 하자. PK로는 두 트랜잭션이 독립이라 병렬이 되고, 슬레이브에서 T2가 먼저 적용되는 순간 UNIQUE 위반이 난다. 유니크 값도 해시에 넣으면 두 트랜잭션이 'X'로 겹쳐 순서가 잡힌다.

둘째, **FK 부모-자식 순서**다. 자식 행은 부모 행이 있어야 적용되므로, 부모를 만든 트랜잭션보다 자식이 먼저 적용되면 안 된다. PK 해시만으로는 이 관계가 보이지 않는다.

## 3. 왜 CUBRID는 폴백 없이 갈 수 있나

MySQL은 이 문제를 "부모 테이블에 쓰기가 있는 트랜잭션은 writeset을 포기하고 커밋 순서로 보수 처리"하는 폴백으로 덮었다. 그 근거는 writeset 충돌 검사의 전제, 즉 "모든 변경이 빠짐없이 비교 가능한 해시로 기록된다"가 깨질 수 있는 세 구멍이다. CUBRID에서는 셋 다 원천적으로 막혀 있음을 소스와 실측으로 확인했다([[소스-확인]]).

| MySQL의 구멍 | 내용 | CUBRID 상태 |
| --- | --- | --- |
| ① 변경분 누락 | cascade 자식 변경이 복제 스트림에 안 담김 | cascade 자식도 부모와 **같은 트랜잭션의 복제 레코드로 전부 남음** |
| ② 식별 키 부재 | PK/UNIQUE 없는 테이블은 해시 불가 | PK 없으면 **복제 대상 자체가 아님** |
| ③ 해시 불일치 | 비유니크·부분 참조 FK는 부모 해시와 모양이 달라 매칭 불가 | FK는 **부모 PK 전체만** 참조 가능(컬럼 수까지 강제), 부분 참조가 스키마 단계에서 불가라 레거시도 없음 |

전제가 항상 성립하므로 폴백 없이 매칭만으로 정합성이 확보된다. 폴백이 사라지면 MySQL이 부모 쓰기 때마다 히스토리를 비워 무관한 트랜잭션까지 직렬화하던 비용도 함께 사라진다.

## 4. 설계 결정 (2026-08-20 인터뷰 확정)

| # | 항목 | 결정 |
| --- | --- | --- |
| 1 | 1차 구현 범위 | UNIQUE 소비 + FK 매칭(폴백 없음) + 쓰기/참조 슬롯 분리(형제 병렬) 전부 포함 |
| 2 | 완료 기준 | 파동 재현 실측 + HA 2노드 정합 + 기존 회귀 + 성능 벤치 (6절) |
| 3 | 성능 목표 | 수치 미고정. 우선 지표는 applier 병렬성 향상, 마스터 오버헤드(해시+로그)는 측정만 |
| 4 | 코드 수정 범위 | 제약 없음 (서버 코어 포함, PoC 단계) |
| 5 | 폴백 복귀 스위치 | PoC에는 없음(단일 경로). 정식 이식 단계로 이월 |
| 6 | cascade 이중 실행 | 기존 동작 유지(develop에도 존재, 멱등 수렴). 차단하지 않음 |
| 7 | 작업 브랜치 | `feature/parallel_applylogdb_writeset_poc` 직접 작업 |

여기서 "UNIQUE 소비"는 위 2절의 유니크 값 재사용 순서를 잡는 것, "폴백 복귀 스위치"는 정식 제품에서 FK 폴백 경로를 다시 켤 수 있게 하는 설정을 말한다. 행 식별은 현 코드 그대로 **PK 전용**이다(NOT NULL UNIQUE 식별은 아직 반영되지 않은 브랜치 대비 사항이라 아래 부록에만 둔다).

## 5. 핵심 설계

### 5.1 해시 대상

해시 대상은 세 종류다. 해시를 만들 값은 마스터의 인덱스 정리 루프가 이미 들고 있어, 새로 수집하는 경로를 만들 필요가 없다.

- **PK 해시(old·new)** — 행 식별이자 쓰기 충돌의 기본. 키 값이 바뀌는 UPDATE는 old와 new를 모두 해시한다. 복제 레코드가 OLD 키로 기록되고 applier가 OLD 키로 행을 찾으므로, 같은 키 계열의 순서가 곧 적용 정확성이기 때문이다.
- **UNIQUE 해시(old·new)** — 유니크 값 재사용 충돌 보호(2절). 값이 NULL인 유니크 키는 어떤 값과도 충돌하지 않으므로 해시를 만들지 않는다.
- **FK 해시** — 자식 행을 쓸 때 그 FK 값을 부모 PK 해시와 **같은 방식으로 정규화**(컬럼 순서, 구분자, 길이 인코딩까지)해 해시한다. 값이 같으면 부모 행 키와 같은 해시가 되어 부모-자식이 이어진다. NULL FK는 참조가 없는 것이므로 제외한다.

### 5.2 히스토리 맵 — 쓰기/참조 슬롯 분리 (형제 병렬)

MySQL은 같은 부모를 참조하는 자식들끼리 FK 해시가 겹쳐 사슬처럼 직렬화된다(#110071). 형제는 서로 다른 행을 쓰므로 진짜 충돌이 없고 필요한 순서는 "부모 뒤" 하나뿐인데, 형제끼리도 줄을 선다. 원인은 두 가지가 맞물린 데 있다.

1. 부모가 폴백 때문에 자기 해시를 히스토리에 남기지 못해, "부모 키 모양의 해시" 자리를 첫째 자식의 FK 해시가 차지한다.
2. 히스토리 맵은 키 해시마다 슬롯 하나에 "그 키를 마지막으로 건드린 트랜잭션"만 담는다. 어떤 트랜잭션이 그 키를 조회하면, 조회한 자신이 그 슬롯의 새 주인이 된다. 이 규칙은 같은 행을 실제로 쓰는 진짜 충돌에는 맞지만, 행을 쓰는 게 아니라 가리키기만 하는 참조에까지 적용되어 형제가 서로 얽힌다.

**CUBRID v2의 위치.** 폴백이 없으므로 원인 1은 자동으로 사라진다(부모 해시가 히스토리에 남아 첫째 자식이 진짜 부모에 매칭된다). 원인 2는 우리가 새로 만드는 히스토리 맵의 갱신 규칙이라 설계로 정할 수 있다. MySQL은 원인 1이 고정이라 이 개선 자체가 불가능하다.

**해결 — 쓰기/참조 슬롯 분리.** 키 해시마다 슬롯을 두 개 둔다.

- **쓰기 슬롯** — 그 키를 마지막으로 **쓴** 트랜잭션. PK·UNIQUE 해시(쓰기)만 갱신한다.
- **참조 슬롯** — 그 키를 마지막으로 **참조한** 트랜잭션. FK 해시(참조)만 갱신한다.

판정 규칙은 두 가지다.

- 자식의 FK 해시는 **쓰기 슬롯만 읽는다.** 그래서 모든 형제가 부모의 쓰기 트랜잭션에 매칭되고, 형제끼리는 서로를 보지 못해 얽히지 않는다.
- 부모 키에 대한 다음 쓰기는 **쓰기 슬롯과 참조 슬롯 중 나중 것 뒤**에 선다. 그래서 부모의 다음 쓰기가 기존 자식들 뒤에 서는 역방향 순서도 보장된다.

**MySQL 9.7 실측과의 대비**(수치·재현은 [[fk-병렬화-실측]]).

| 항목 | MySQL 9.7 | CUBRID writeset v2 |
| --- | --- | --- |
| 부모 → 자식 순서 | 보장 (커밋 순서) | 보장 (의존 = 부모 커밋 LSA) |
| 부모행 분리 형제 | 병렬 | 병렬 |
| **부모행 공유 형제** | **직렬 (#110071)** | **병렬 (참조를 히스토리에 안 남김)** |
| 부모 쓰기의 부수효과 | 히스토리 전체 clear로 무관한 트랜잭션까지 병렬 하한 상승 | 없음 |

CUBRID v2는 자식의 부모 참조 해시를 **조회에만 쓰고 히스토리에 남기지 않으므로**, 형제들이 서로의 흔적을 볼 수 없어 몇 개든 전부 부모 하나에만 의존한다. 한 부모에 자식 트랜잭션이 잇달아 붙는 실무형 워크로드에서 이 차이가 구조적 이점이 된다.

**구현 시 검토할 것**: 슬롯이 둘로 늘어나는 히스토리 메모리 비용, 부모 키가 바뀌는 UPDATE(old/new 키)에서 두 슬롯의 갱신 규칙, 참조 슬롯 갱신의 동시성 처리.

### 5.3 폴백이 사라진 뒤에도 남는 보수 처리

FK 때문에 히스토리를 비우고 하한선을 세우던 처리는 없어진다. 다만 히스토리 맵은 유한하므로 **용량 초과** 시, 그리고 행 해시로는 영향을 표현할 수 없는 **DDL류** 처리 시의 보수화(하한선 + 히스토리 비우기)는 v2에도 그대로 필요하다. 목록에서 FK만 빠지는 것이다.

### 5.4 순서 집행과 불변식

applylogdb는 순서가 어긋나면 오류를 내는 게 아니라 **조용히 잘못 적용**된다. 즉 의존성 메타(커밋 순서·의존 순서·적용 완료 순서)가 곧 정합성이다. 워커 배정은 트랜잭션 단위를 지킨다(한 트랜잭션의 복제 레코드는 한 워커가 원래 순서대로 적용). 이 위에서는 슬레이브의 cascade 이중 실행도 직렬 적용 때와 똑같이 멱등으로 수렴하므로 손대지 않는다(결정 6, [[소스-확인]]).

## 6. 완료 기준

1. **파동 재현** — 대표 시나리오를 CUBRID HA에서 재현했을 때 의존성 메타가 `{T1 T2 T3} | {T4 T5}`로 계산되고 그대로 병렬 적용된다(형제 병렬 포함).
2. **정합성** — HA 2노드에서 FK·UNIQUE·cascade 시나리오 실행 후 마스터·슬레이브 데이터가 완전히 일치하고, 순서 위반으로 인한 잘못된 skip이 0건이다.
3. **기존 회귀** — 빌드 검증, 기존 시나리오, 재시작 멱등성이 유지된다.
4. **성능 벤치** — applier 병렬성 향상을 벤치로 보인다. 마스터 오버헤드 측정치를 함께 보고하되 목표 수치는 측정 후 확정한다.

## 부록 — NOT NULL UNIQUE 복제 지원 브랜치 대비 (미반영)

현 코드의 복제 식별 키는 PK 전용이지만([[소스-확인]]), **NOT NULL UNIQUE로도 복제가 가능해지는 브랜치**가 예정돼 있다. 그 브랜치가 병합되면 PK 없는 테이블도 NOT NULL UNIQUE를 식별 키로 삼아 복제 대상이 된다. v2 설계가 그때 흔들리지 않도록 달라지는 지점을 미리 정리해 둔다.

**무엇이 달라지나**

- 키 생성 게이트가 PK 전용에서 해당 유니크 인덱스까지 넓어져야 하고, applier의 행 검색도 PK 고정에서 식별 인덱스 선택으로 확장돼야 한다.
- 식별 키 후보가 여럿일 수 있다(NOT NULL UNIQUE가 둘 이상). 마스터와 슬레이브가 **같은 인덱스를 결정론적으로 선택**하는 규칙이 필요하다. 어긋나면 applier가 행을 못 찾는다.
- FK 쪽은 영향이 없다. FK는 PK만 참조하므로, NOT NULL UNIQUE만으로 복제되는 테이블은 부모가 될 수 없다. FK 해시 매칭 설계는 그대로 유효하다(그런 테이블이 자식이 되는 것은 무방하다).

**핵심 복잡도 — 식별 키인 NOT NULL UNIQUE 값이 바뀔 때**

PK 변경 UPDATE와 같은 모델이 필요하다. 복제 레코드의 키는 OLD 값이어야 하고, applier는 OLD 값으로 행을 찾아 NEW 이미지로 덮어쓴다. PK보다 조심할 점이 있다.

- **변경 빈도** — PK는 잘 안 바뀌지만 NOT NULL UNIQUE(email, 사번 등)는 업무적으로 바뀐다. "값 변경 → 옛 값 재사용" 체인이 더 자주 생긴다.
- **순서 민감성** — 슬레이브가 OLD 값으로 행을 찾으려면 그 시점에 아직 OLD 값 행이 있어야 한다. 같은 유니크 값 계열을 만지는 트랜잭션들의 순서가 곧 정확성이다. 이를 잡으려면 old·new 유니크 값을 둘 다 해시해야 하고, 재료는 이미 준비돼 있다.
- **NULL 걱정 없음** — NOT NULL이라 해시가 항상 존재한다.

정리하면, 브랜치 병합 시 v2에 추가로 필요한 것은 "식별 인덱스의 결정론적 선택 규칙"과 "OLD 키 기반 적용 모델의 유니크 확장" 둘이고, writeset 쪽은 이미 계획된 old/new 유니크 해시 수집으로 커버된다. FK 매칭 설계는 영향받지 않는다.
