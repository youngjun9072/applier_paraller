# 한계 — child DELETE → parent DELETE 순서 역전

FK 부모-자식이 있을 때, 마스터에서 `자식 DELETE → 부모 DELETE` 순으로 커밋한 것이 슬레이브에서 `부모 DELETE → 자식 DELETE`로 뒤집힐 수 있다. 이 문서는 그 역전이 왜 생기고 무엇이 문제인지 코드와 실측으로 확인하고(1~5절), 쓰기/참조 슬롯 분리로 역전이 사라지는 것을 재실측으로 보인다(6절).

> [!summary] 결론
> - **역전은 실제로 일어난다.** 세 FK 액션(RESTRICT / CASCADE / SET NULL) 모두에서, 부모 DELETE가 자식 DELETE보다 0.67~0.77초 먼저 슬레이브에 커밋되는 것을 실측했다.
> - **최종 데이터는 셋 다 수렴한다.** 다만 그 사이에 "마스터 이력에 없던 중간 상태"가 잠깐 열린다(RESTRICT는 부모 없는 자식(orphan), CASCADE는 자식 조기 삭제 + fail_counter 1,000 증가, SET NULL은 자식 FK가 NULL인 상태).
> - **원인은 하나다.** 자식의 부모 참조(REF)가 히스토리에 게시되지 않아, 부모 DELETE가 직전 자식 DELETE에 대한 의존을 얻지 못한다.
> - **해결도 하나다.** 쓰기/참조 슬롯 분리([[설계]] 5.2절)로 부모 DELETE가 자식 뒤에 서게 하면 세 창이 액션 구분 없이 동시에 닫힌다. 슬롯 분리 구현판으로 세 액션 모두 역전이 사라짐을 재실측했다(6절).

## 1. 어떤 역전인가

```text
마스터 커밋 순서:      T1 자식 DELETE → T2 부모 DELETE
슬레이브에서 가능한 순서: T2 부모 DELETE → T1 자식 DELETE   (역전)
```

실측 워크로드는 자식 DELETE를 큰 트랜잭션(5만 행), 부모 DELETE를 작은 트랜잭션(1,000행)으로 두었다. 자식 DELETE가 슬레이브에서 약 1초 적용되는 동안 부모 DELETE가 그 사이에 끼어들 수 있는 조건이다.

## 2. 왜 역전이 생기나

writeset은 자식이 부모를 가리키는 참조(REF)를 히스토리에 **게시하지 않는다.** 게시하면 같은 부모를 참조하는 형제 자식들이 서로 얽혀 직렬화되기 때문이다([[설계]] 5.2절). 그 대가로 이 방향의 순서가 빈다.

- 부모 INSERT(P0)는 부모 키를 쓰기(WRITE)로 히스토리에 남긴다.
- 자식 DELETE(T1)는 부모 키를 참조(REF)로 **조회만** 하고 히스토리에는 안 남긴다. 그래서 T1의 의존은 옛 부모 INSERT(P0)를 가리킨다.
- 부모 DELETE(T2)도 부모 키를 쓰기로 조회하는데, 히스토리에는 여전히 P0만 있다. 그래서 T2의 의존도 P0을 가리킨다.

결국 T1과 T2가 둘 다 "P0 뒤"라는 이미 충족된 의존만 들고 있어, P0이 적용된 슬레이브에서는 **둘 다 즉시 실행 가능**하다. 큰 T1이 아직 적용 중일 때 작은 T2가 먼저 끝나면 역전이 성립한다. 코드 근거는 [[소스-확인]]과 [[코드-근거]]에 있다.

## 3. 액션별로 무슨 일이 벌어지나

역전으로 "부모가 이력보다 일찍 사라진 창"이 열린 순간, 그 부모를 참조하던 자식을 어떻게 처리하느냐만 FK 액션이 정한다. 슬레이브는 마스터가 이미 검증한 변경을 재검증 없이 반영하지만, CASCADE·SET NULL 참조 액션은 슬레이브 서버가 자기 데이터 상태를 보고 직접 실행한다(applylogdb 클라이언트에 대한 가드가 이 분기에는 없다).

- **RESTRICT / NO ACTION** — 슬레이브 적용에서는 "참조하는 자식이 있는가" 검사 자체가 실행되지 않는다(applylogdb 클라이언트는 그 검사 블록을 건너뛴다). 그래서 참조 자식이 아직 있는데도 부모가 그냥 삭제된다. 에러도, fail도 없다. 대신 부모 없는 자식(orphan)이 잠깐 보인다.
- **CASCADE** — 슬레이브가 부모 DELETE를 적용하는 순간 자식을 다시 cascade로 지운다. 뒤늦게 도착한 명시적 자식 DELETE는 이미 없는 행을 만나 대상 없음(`ER_OBJ_OBJECT_NOT_FOUND`)으로 건너뛰고, 그 수가 fail_counter에 집계된다.
- **SET NULL** — 슬레이브가 부모 DELETE를 적용하며 자식의 FK를 NULL로 바꾼다(행은 남긴다). 뒤이은 자식 DELETE는 PK로 그 행을 찾아 정상 삭제하므로 fail은 없다. 대신 "부모 없음 + 자식 FK=NULL"이라는, 마스터엔 없던 상태가 잠깐 열린다.

## 4. 실측 — 세 액션 모두 역전 재현 (2026-08-27~28)

세 실측 모두 부모 DELETE가 자식 DELETE 적용 도중 끼어들어 0.67~0.77초 먼저 커밋됐다. 결정적 증거는 세 런 모두 부모 DELETE의 의존이 직전 자식 DELETE가 아니라 한참 전의 부모 INSERT를 가리킨다는 점이다(2절 그대로).

| | RESTRICT | CASCADE | SET NULL |
| --- | --- | --- | --- |
| 순서 역전 | 발생 (부모가 0.757초 먼저) | 발생 (0.67초 먼저) | 발생 (0.769초 먼저) |
| 역전 시 슬레이브 동작 | 자식 둔 채 부모만 삭제 | 부모 삭제 + 자식 재-cascade 삭제 | 부모 삭제 + 자식 FK를 NULL로 |
| 관측 가능한 신호 | **없음** (fail=0, 에러 0건) | fail_counter만 증가 (fail=1000) | **없음** (fail=0) |
| 열린 창 | orphan 노출 0.757초 | 자식 조기 삭제 0.67초 | 자식 FK=NULL 0.769초 |
| 최종 데이터 | 수렴 | 수렴 | 수렴 |

폴러(0.2초 간격)가 세 창을 각각 직접 포착했다. RESTRICT는 "부모 0 / 자식 1000"을, SET NULL은 "부모 0 / 자식 FK=NULL 1000"을 여러 번 잡았고, CASCADE는 부모·자식이 동시에 0으로 떨어지고 fail=1000이 `db_ha_apply_info`에 누적됐다.

## 5. 하나의 문제, 세 단면

세 케이스는 서로 다른 결함 셋이 아니라 **하나의 원인이 액션에 따라 다른 표면으로 보인 것**이다.

```
공통 원인:  자식 참조(REF)가 히스토리에 없음
            → 부모 DELETE가 자식 DELETE 의존을 못 얻음
            → 부모가 이력보다 일찍 사라지는 창이 열림

액션은 그 창에서 자식을 어떻게 처리할지만 정한다:
  RESTRICT → 자식 그대로       → orphan 노출
  CASCADE  → 자식 같이 삭제     → 자식 조기 소멸 (+ 뒤 자식 DELETE가 빈자리 만나 fail=1000)
  SET NULL → 자식 FK만 NULL로   → 마스터에 없던 NULL 상태
```

이 관점의 실익은 해결책이 하나로 모인다는 것이다. 부모 DELETE가 자식에 대한 의존을 얻으면 창 자체가 열리지 않으므로, orphan·fail·NULL 창이 액션 구분 없이 동시에 사라진다. 평가 변수도 "어느 액션이 위험한가"가 아니라 "창이 열리는가, 얼마나 오래(=자식 트랜잭션의 남은 적용 시간)"뿐이다. 큰 트랜잭션이거나 reader가 적체되면 창은 초 단위 이상으로 커질 수 있다.

## 6. 해결 — 쓰기/참조 슬롯 분리와 차단 재실측 (2026-09-01)

[[설계]] 5.2절의 쓰기/참조 슬롯 분리를 구현한 빌드로 4절과 같은 시나리오를 재실측했다. 히스토리 엔트리를 키당 `{쓰기 슬롯, 참조 슬롯}`으로 나누고, 자식 참조는 참조 슬롯에 도장을 찍는다. 부모의 다음 쓰기는 참조 슬롯도 보므로 자식들 뒤에 선다. 이때 의존이 참조 유래임을 1비트 플래그(read_dep)로 표시하고, 슬레이브 게이트는 참조 유래 의존을 "그 지점까지 전부 적용 완료(프론티어)"로만 통과시킨다.

세 액션 모두 부모 DELETE가 자식들의 참조 슬롯 흔적을 보고(`hits=1000`, `read_dep=1`) 의존을 자식 DELETE의 커밋 LSA로 잡았고, 게이트가 그 의존을 프론티어 대기로 처리해 부모를 자식 뒤에 세웠다.

| 액션 | 단일 슬롯 (역전) | 슬롯 분리 (차단) | 부모 의존 = 자식 커밋 LSA |
| --- | --- | --- | --- |
| RESTRICT | orphan 창 0.757초 | 차단, fail=0 | 18067\|13688 |
| CASCADE | fail=1000 + 조기삭제 0.67초 | 차단, fail=0 | 41815\|6120 |
| SET NULL | FK=NULL 창 0.769초 | 차단, child_null=0 | 58023\|10960 |

세 케이스 공통으로 부모 DELETE의 의존이 직전 자식 DELETE의 커밋 LSA와 정확히 일치했고, 폴러는 세 창(orphan / 조기삭제 / NULL)을 한 번도 포착하지 못했다. 마스터 부하 증분과 계측 세부는 [[b-해시단가-결과]]에 있다.

> [!question] 검토: 후속 설계 아이디어(무관 트랜잭션 대기)
> 슬롯 분리는 참조 유래 의존을 프론티어 대기로 처리하므로, 부모 DELETE가 자식뿐 아니라 그 앞 무관한 트랜잭션의 홀까지 기다린다. 무관 트랜잭션을 전혀 끌어들이지 않으려면 "부모 키별 참조 세대(active REF set)에 대한 다중 의존" 같은 더 정밀한 표현이 필요하다. 이는 확정안이 아니라 후속 설계 검토용 아이디어로, 로그 크기·게이트 복잡도·재시작 안전성을 함께 따져 선택한다. 이 절을 정리본에 어느 수준으로 남길지 검토.
