# 4. FK 버그와 한계 (인터넷 이슈)

> 목차: [[0-자료조사-목차|자료조사 목차]]


#### 4-1. Bug #109923 — 보조 인덱스 참조 시 자식이 부모보다 먼저 적용 (실측 5-6·5-7)
- 증상: 부모의 **보조 인덱스(secondary index)** 를 참조하는 FK에서, 자식 행의 `last_committed`가 실제보다 **작게** 계산되어 리플리카가 **자식을 부모보다 먼저** 적용 → `HA_ERR_NO_REFERENCED_ROW`(참조할 부모 없음, Err 1452)로 SQL 스레드 abort.
- 근본 원인: 폴백을 켜는 `set_has_related_foreign_keys()` 호출이 **"PK가 있는 테이블일 때만 진입하는 블록"**([코드 4]의 `if (primary_key < MAX_KEY)`) 안에 있었다. 부모가 유니크 키 없이 보조 인덱스만 있으면 이 블록을 건너뛰어 **폴백이 안 켜진다.** 여기서 핵심은 폴백이 하는 일이다. 폴백은 "부모가 자기 writeset을 안 쓰는 것"에 그치지 않고, **뒤따르는 자식을 부모 뒤에 붙드는 장벽(하한선)을 세운다.** 정상 부모(PK 있음)도 writeset을 안 쓰는 건 마찬가지지만, 이 장벽이 순서를 지켜 준다. 장벽이 안 세워지면 PK를 가진 자식은 자기 writeset으로 `commit_parent`를 부모 seq 아래까지 낮춰도 막을 게 없어 **부모보다 먼저 적용**된다(위 증상). 즉 원인은 "낮춤을 못 해서"가 아니라 **장벽을 못 세워서**다.

**[코드 10] Bug #109923 — 폴백 플래그 위치 문제**
  ```c
  // (버그) 폴백 트리거가 PK-필요 블록 안에 있어 no-PK 부모에서 누락
  if (table->key_info && table->s->primary_key < MAX_KEY) {
     ...
     if (table->s->foreign_key_parents > 0) set_has_related_foreign_keys();  // ← 이 위치가 문제
  }
  // (리포터 제안 패치: 트리거를 블록 밖으로 — 채택되지 않음, 아래 결말 참조)
  ```
- **결말 (9.7.0 소스 확인)**: 제안 패치는 **미채택** — 플래그는 9.7.0에도 여전히 위 블록 안에 있다. MySQL의 실제 대응은 writeset 코드 수정이 아니라 **DDL 차단**이었다: `restrict_fk_on_non_standard_key`(기본 ON, 9.7에도 존재)가 비유니크/부분 키를 참조하는 FK **생성 자체를 거부**한다(4-3). 단 **리플리카 적용 스레드는 이 제한을 스스로 끈다**(`rpl_replica.cc` — 구버전 마스터가 만든 FK DDL을 적용하기 위한 호환) → 업그레이드로 살아남은 레거시 비표준 FK에서는 이 구멍이 이론상 여전히 열려 있다.
- **잔존 확인 (MySQL 9.7.2 실측)**: 이 구멍은 레거시 전용이 아니다. DDL 차단이 막는 것은 **비유니크/부분 참조뿐**이고, **"PK 없는 부모 + UNIQUE 참조"는 지금도 합법으로 생성된다**. 그 부모는 [코드 4]의 대문에서 걸러져 해시도, 폴백 플래그도 받지 못하므로 자식이 부모를 기다리지 않는 동일 증상이 재현된다 — 실측은 5-7.

#### 4-2. Bug #110071 — 자식 FK 해시로 인한 과직렬화 (실측 5-3·5-4·5-5)
- 증상: 자식의 FK 해시 때문에, **같은 부모 값을 참조하는 자식 INSERT들이 서로 직렬화**된다(같은 부모키 → 같은 해시 → 의존으로 판정). 예: "한 주문(order)에 상품 여러 개 담기"가 통째로 직렬.
- 이건 폴백이 아니라 **writeset을 정상적으로 쓰는 상태에서 해시가 겹쳐 생기는 부작용**이다. "FK를 writeset 의존성 추적에 넣지 말자"는 개선 요청이 올라와 있다.
- **상태 (이슈 사실)**: 2023-02 Verified 후 **미수정** — 2024년 코멘트 기준 8.0.46·8.4.11에도 존재.
- **리포터 주장 검증 (이슈 내용이 아니라 이 문서의 코드 확인)**: 리포터는 "자식에 PK가 있으면 FK 체크는 무용(useless)"이라고 주장했다. [코드 8]로 확인하면 맞는 말이다 —
  - FK 해시가 하려던 일 = 자식을 **부모** 뒤에 세우기. 그런데 부모 쓰기 트랜잭션은 항상 폴백하며 자기 해시를 이력에 **넣지 못하므로**(insert가 `can_use_writesets` 블록 안), 이 매칭은 **일어날 기회가 없다.** 자식-부모 순서는 FK 해시가 아니라 **하한선**이 잡는다(3-1).
  - FK 해시가 실제로 하는 일 = **형제끼리 줄 세우기**(5-5의 T4→T5)뿐. 형제는 서로 다른 행이라 진짜 충돌이 없으므로, 이건 정합성에 불필요한 순수 손해다.
- **9.7 기본 모드에서 주장이 더 강해진다 (이 문서의 코드 확인)**: 3-4에서 봤듯 9.7 기본(SQL 계층 FK)에서는 cascade 자식 변경까지 독립 행 이벤트로 binlog와 writeset에 담긴다. 폴백의 공식 근거였던 cascade 사정이 데이터 흐름에서 사라졌는데도 FK 해시와 부모 폴백은 그대로 남아 있다(5-4 실측이 9.7.2 기본 설정에서 폴백이 여전히 발동함을 보여준다). 리포터의 제거 주장이 성립할 조건은 오히려 좋아졌지만 이슈는 여전히 미수정이다.

**형제 직렬이 만들어지는 정확한 메커니즘 (이 문서의 코드 확인, 9.7.2에도 미해결)**

이력 맵은 해시당 슬롯이 하나이며 "그 해시를 마지막으로 남긴 트랜잭션의 seq"를 저장하고, 조회에 성공한 트랜잭션도 주인을 자기로 덮어쓴다([코드 8]의 `it->second = seq`). 그리고 부모 쓰기는 폴백 때문에 자기 키 해시를 맵에 등록하지 못하므로(3-1), "부모 키 모양의 해시" 자리를 처음 차지하는 것은 부모가 아니라 **첫째 자식의 FK 해시**다. 이 둘이 결합해 형제 사슬이 만들어진다.

```
(부모 T2가 폴백 + clear. 하한선=2, 맵은 비어 있음)

T4 (bchild1 삽입, fk=1) 커밋:
  조회 H(bparent,1) → 없음 → lc = 하한선(2)
  등록: H(bchild1,1)→4,  H(bparent,1)→4
        ← 자기 PK 해시와 "부모 키 모양의 FK 해시"를 둘 다 이력에 등록

T5 (bchild2 삽입, fk=1) 커밋:
  조회 H(bparent,1) → 있음, 주인 = 4        ← 부모 키 모양이지만 주인은 형제!
  lc = 4 (T4 뒤로 직렬). 주인을 5로 갱신

T6 (같은 부모를 참조하는 자식이 또 오면):
  주인 = 5 → lc = 5                          ← 부채꼴이 아니라 사슬로 늘어섬
```

- T4의 lc=2는 부모 seq와 숫자가 같아 매칭처럼 보이지만, 실제로는 하한선이 만든 값이다. 매칭이 진짜 됐다면 T5도 2를 받았어야 한다.
- 원인은 둘이다. ① 부모가 폴백으로 자기 해시를 등록하지 못한다. ② 조회한 트랜잭션이 주인을 자기로 덮어쓴다. ②는 같은 행을 쓰는 진짜 쓰기 충돌에는 올바른 규칙이지만("마지막으로 쓴 트랜잭션 뒤"), 행을 쓰는 게 아니라 **가리키기만 하는 참조**에까지 같은 규칙이 적용되어 형제끼리 얽힌다.
- 실측 대응: 5-3의 lc 체인(0, 1, 1, 3)과 5-5의 T5=4가 이 메커니즘 그대로다.

#### 4-3. 부분/비표준 FK 참조 (선행 접두사) 와 8.4의 제한 (실측 5-1·5-2)
- MySQL/InnoDB 8.0은 비표준 완화가 있어, 복합 PK `(a,b,c)`에서 **선행 접두사**를 FK가 참조할 수 있다: `REFERENCES t1(a)`, `t1(a,b)` 허용. 단 중간 컬럼 `t1(b)`나 역순 `t1(b,a)`는 거부(ERROR 1822).
- 이런 부분 참조는 **FK 해시의 값 개수가 부모 키 해시와 달라 영원히 매칭되지 않는다**(자식은 `a` 하나만, 부모 PK는 `a,b,c` 셋). 즉 writeset으로는 순서를 못 잡고, **부모 폴백(장벽)만이** 순서를 보장한다.
- MySQL 8.4부터 `restrict_fk_on_non_standard_key`(기본 ON)가 이런 부분/비유니크 참조를 **거부**(`ER_FK_NO_UNIQUE_INDEX_PARENT`), OFF 시 `ER_WARN_DEPRECATED_NON_STANDARD_KEY` 경고. → MySQL이 **"완전한 유니크 키 참조"** 표준으로 수렴 중.

#### 4-4. Bug #97836 — 부모에 PK가 있어도: 선행 접두사 참조로 그룹복제 applier 중단 (실측 없음 — 그룹복제 경로)
- 부모가 복합 PK `(a,b,c)`를 **갖고 있는데도**, 자식 FK가 선행 접두사 `a`만 참조하는 구성에서 그룹복제 세컨더리가 자식을 부모보다 먼저 적용 → FK 위반으로 applier가 그룹에서 이탈. (리포터의 우회책: `slave_parallel_workers=0` = 병렬 포기)
- 2019년 보고·Verified, 2024년 코멘트 기준 **8.0.35·8.4.2에도 재현** — 5년+ 미수정. 4-3의 "부분 참조는 값 개수가 달라 영원히 매칭되지 않는다"의 실사례.
- 주의: 그룹복제 경로(인증 기반)는 이 문서에서 코드 분석하지 않은 영역이다 — 비동기 복제의 부모 폴백(3-1)과 보호 장치가 다를 수 있다.
