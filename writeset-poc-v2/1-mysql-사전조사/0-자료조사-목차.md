## 목적과 배경

### 배경 지식
writeset 병렬 적용이란, 마스터가 각 트랜잭션이 건드린 "행 키"들을 해시(=writeset)로 저장하고 비교하는 방식이다. 여기서 "건드린 행"은 둘이다. 트랜잭션이 쓴 행(INSERT/UPDATE/DELETE의 키)과, 자식 행을 쓸 때 FK가 가리키는 부모 행(참조, 상세는 3절)이다. 읽기만 하는 트랜잭션(SELECT)은 쓰는 게 없으므로 writeset이 만들어지지 않는다. 서로 다른 행을 건드린 트랜잭션들은 리플리카에서 동시에(병렬로) 적용해도 안전하고, 같은 행을 건드린 것끼리만 순서를 지키면 된다. 이 과정은 두 단계로 나뉜다. 행마다 키 해시를 계산해 두는 **추출(write set extraction)** 단계와, 그 해시 값들을 최근 커밋 이력(history)과 비교해 이 트랜잭션이 어떤 트랜잭션 **이후에** 수행 가능한지를 정하는 **의존성 추적(dependency tracking)** 단계다.

판정 결과는 binlog에 트랜잭션마다 실리는 두 숫자로 표현된다. **`sequence_number`(seq)** 는 커밋 순서대로 붙는 트랜잭션 고유 번호이고, **`last_committed`** 는 "seq가 이 값인 트랜잭션까지 적용이 끝나야 나를 시작할 수 있다"는 선행 조건이다. 리플리카의 병렬 워커들은 이 규칙 하나로 움직인다. last_committed가 **작을수록 일찍 출발**하고, 값이 **같은 것끼리는 동시에 출발**한다(=병렬).

last_committed의 계산은 두 단계다. 먼저 커밋 순서 기준의 **보수값**이 배정된다. 순차 커밋이면 직전 트랜잭션의 seq(내 seq − 1)이고, "직전 것을 기다려라"는 뜻이라 느릴 뿐 항상 안전하다. 이어 의존성 추적이 이 값을 **낮춘다**: 내 해시들과 겹친 과거 트랜잭션 중 가장 최신 seq를 이력에서 찾아(아무와도 안 겹치면 이력의 하한선까지 내려간다) `commit_parent = min(그 값, 보수값)` 으로 낮춘다. 즉 writeset에는 값을 **올리는 연산이 없고 min으로 낮추는 연산뿐**이며, 많이 낮출수록 병렬성이 커진다. (코드는 [[1-공통-기반|1장]], 하한선은 [[3-fk-처리|3-1]]·[[5-FK 동작 실측|5-5]].)

### v1 한 줄 요약
행을 쓸 때 `(인덱스이름, 스키마, 테이블, 키값)`을 이어붙여 해시로 만들고(추출), 커밋 시 그 해시들을 최근 커밋 이력과 견줘 겹치면 "의존(순서 지켜라)", 안 겹치면 "독립(병렬 가능)"으로 판정한다(의존성 추적). 커밋 순서 방식은 마스터에서 같이 커밋된 것끼리만 병렬이고, writeset 방식은 행만 안 겹치면 병렬이라 병렬성이 훨씬 크다.


### v2 에서 다루는 내용
현행(v1)은 **PK만을 대상으로 충돌(겹침)을 판정**한다. 즉 서로 다른 PK를 건드린 트랜잭션은 병렬로 본다. 그러나 실제로는 **UNIQUE 키 충돌**(PK가 달라도 같은 UNIQUE 값을 쓰면 충돌), **FK로 인한 부모-자식 순서 의존**도 병렬 적용의 정합성에 영향을 주는데, v1은 이것들을 보지 못한다. v2는 이 **UNIQUE·FK 충돌까지 writeset으로 판정**하도록 확장하는 것을 PoC한다. 이 문서는 그 설계에 필요한 "MySQL이 UNIQUE·FK를 writeset에서 실제로 어떻게 다루는가"를 모은다.

## 4. 한눈 정리 — MySQL은 UNIQUE/FK를 이렇게 다룬다

to ai: 이것도 좀 더 정리됏으면.. .

| 대상          | 추출(add_pke)                                  | 의존성 추적(get_dependency)                 |
| ----------- | -------------------------------------------- | -------------------------------------- |
| PK / UNIQUE | 인덱스이름+테이블+키값 → 해시(복합키=1개, NULL=제외, 프리픽스=2개)  | 해시 겹치면 의존, 아니면 병렬                      |
| 자식 FK       | 참조 유니크 인덱스이름+부모테이블+FK값 → 해시(비유니크 참조·NULL=제외) | 부모키 해시와 매칭되면 순서 잡힘                     |
| 참조당하는 부모    | `has_related_foreign_keys` 플래그 set           | **writeset 포기 → 커밋 순서 + 이력 clear(장벽)** |

핵심 결론:
- writeset은 **하나**(add_pke 산출물)이고, FK도 그 안에 해시로 들어간다.
- 그러나 **"참조당하는 부모"를 건드리는 트랜잭션은 그 writeset을 안 쓰고 커밋 순서로 폴백**한다(정합성 안전 우선). 이유는 부모 변경이 다른 테이블 자식으로 번지고(cascade), 부분/보조 인덱스 참조에선 해시가 부모와 안 맞아 순서를 못 잡기 때문(#109923).
