# 1. writeset 처리 흐름

> 목차: [[0-자료조사-목차|자료조사 목차]]


0장의 두 단계(추출, 의존성 추적)를 코드로 따라가면 주요 함수는 다음 3개다. 
* *`add_pke`가 해시 문자열을 조립. 
* `generate_hash_pke`가 그것을 해시로 바꿔 트랜잭션의 write set에 저장(여기까지 추출). 
* 커밋 시점에는 `get_dependency`가 그 해시 집합을 이력과 대조해 `last_committed`를 정함(의존성 추적). 
아래 [코드 1]~[코드 3]이 이 흐름을 설명한다.

**(1) `add_pke` — 추출의 진입점.** 행이 쓰이거나 바뀔 때마다 호출되어(`handler.cc`, `rpl_injector.cc`), 그 행의 **PK·UNIQUE·FK 해시 문자열(pke)** 을 모두 만든다. 파일은 `sql/rpl_write_set_handler.cc`. 키 종류별 상세 동작은 2장(PK/UNIQUE)과 3장(FK)에서 본다.

**[코드 1] `add_pke` — 행에서 해시 만드는 진입점**
```c
bool add_pke(...) {
  if (table->key_info && primary_key < MAX_KEY) {   // PK 있는 테이블만 진입
    for (key_number ...) {                // PK/UNIQUE 키마다 (인라인 블록 → 2장)
      pke = 인덱스명 + 스키마/테이블 + 키값;  //   해시할 문자열 조립
      generate_hash_pke(pke, thd);        //   → 해시해서 write set에 추가  ★
    }
    /* Foreign keys handling. */          // FK도 pke 조립 후 generate_hash_pke (인라인 블록 → 3장)
    if (foreign_key_parents > 0)
      set_has_related_foreign_keys();     // "참조당하는 부모"면 표시 → 의존성 추적 단계에서 writeset 포기(commit-order 폴백)
  }
  if (!writeset_hashes_added)
    set_has_missing_keys();               // PK/UNIQUE 해시가 하나도 없으면 표시 → 역시 commit-order 폴백
}
```

**(2) `generate_hash_pke` — 조립된 문자열을 해시로 바꿔 저장하는 곳.** [코드 1]이 키마다 부르던 바로 그 함수다. 같은 파일의 `static` 함수라 **add_pke 안에서만** 쓰이며, 유니크 키·멀티밸류·FK 세 경로에서 호출된다.

**[코드 2] `generate_hash_pke` — 해시 하나를 write set에 저장**
```c
static bool generate_hash_pke(const std::string &pke, THD *thd, ...) {
  // pke = "인덱스이름 <SEP> db <SEP> len(db) 테이블 <SEP> len(테이블) 값 <SEP> len(값) ..." 문자열
  uint64 hash = MY_XXH64(pke.c_str(), pke.size(), 0);       // xxHash64
  // 이 트랜잭션의 write set(해시 집합)에 추가
  thd->get_transaction()->get_transaction_write_set_ctx()->add_write_set(hash);
  return false;
}
```
정리하면 추출 쪽은 `add_pke`가 문자열을 조립하고 `generate_hash_pke`가 해시로 저장하는 2단 구성이다. PK든 UNIQUE든 FK든 **모두 이 길을 거쳐 같은 해시 집합**에 들어가며, 의존성 추적 단계는 이 집합만 볼 뿐 어느 키에서 온 해시인지 구분하지 않는다.

**(3) `get_dependency` — 의존성 추적을 수행하는 곳.** 커밋 시점에 한 번 호출된다(`sql/rpl_trx_tracking.cc`). 0장에서 설명한 계산 두 단계, 즉 커밋 순서가 보수값을 주고 writeset이 그 값을 낮추는 구조가 코드에 그대로 보인다.

**[코드 3] `get_dependency` — 의존성 추적(병렬/직렬 결정)**
```c
void get_dependency(THD *thd, int64 &seq, int64 &commit_parent) {
  m_commit_order.get_dependency(...);   // 1) 기본값: 커밋 순서 기준 (보수적 = 거의 직렬)
  m_writeset.get_dependency(...);       // 2) 개선: 겹치지 않으면 commit_parent를 낮춰 병렬↑
}
```
`commit_parent`가 binlog에 `last_committed`로 기록되는 그 값이다. 낮을수록 더 많은 트랜잭션과 병렬로 적용되며, writeset의 역할은 이 값을 **낮춰 주는** 것이다.
