## [USER-3Y-01] 새 RK 규칙이 기존 변경 누락을 막는 과정을 사용자가 이해할 수 없다

- 분류: 컨셉
- 심각도: Critical
- 근거 위치: 원문 1절의 RK 필수 조건과 4-2절의 RK 변경 제약
- 사실/추론 구분: 문서에서 도출한 추론
- 영향 대상: 일반 사용자, 애플리케이션 데이터, 복제 정합성

### 문제
문서는 PK 또는 `NOT NULL UNIQUE KEY`가 있으면 RK로 쓴다고 설명하지만, 기존에 PK 속성을 바꿀 때 왜 DML이 누락됐고 새 규칙이 어느 단계에서 이를 막는지는 설명하지 않는다. 대체 후보가 있으면 DDL을 허용한다는 규칙만으로 과거 로그까지 안전한지 알 수 없다.

### 왜 중요한가
사용자는 “키가 하나 있으니 무조건 안전하다”고 이해할 수 있다. 그러나 UPDATE가 옛 PK 값으로 기록된 뒤 replica가 새 UK를 사용하면 대상 행을 찾지 못할 수 있다. 해결 원리를 모르면 위험한 변경과 안전한 변경을 구분할 수 없다.

### 재현 또는 구체적 예제
`account(id PRIMARY KEY, email VARCHAR(100) NOT NULL UNIQUE, balance INT)`에서 `id=10`의 balance를 900으로 바꾼 직후 RK를 email로 교체한다. replica가 아직 UPDATE를 적용하지 않았다면 옛 `id=10`으로 찾는지 새 email로 찾는지가 없다. 기대 결과는 두 노드에서 정확히 같은 행 하나만 900이 되는 것이다.

### 권고안
“DML이 생성될 때의 RK와 DDL 적용 순서를 함께 보존한다”처럼 해결 원리를 그림과 단계 예제로 설명한다. 안전 기준을 허용된 RK 변경 뒤 누락 0건, `fail_count` 증가 0회, failover 후 결과 일치로 명시한다.

### 검증 방법
복제 지연을 만든 뒤 DML–RK 교체–DML 순으로 실행한다. source와 replica의 행별 값, 적용 로그, `fail_count`를 비교해 설명과 일치하는지 확인한다.

## [USER-3Y-02] PK 없는 기존 테이블에 대한 선택지와 비용 안내가 부족하다

- 분류: 컨셉
- 심각도: Major
- 근거 위치: 원문 2-1·3·7절의 키 없는 ON 테이블과 HA 시작 실패
- 사실/추론 구분: 확인된 사실
- 영향 대상: 기존 DB 사용자, 마이그레이션 담당자

### 문제
PK 없는 테이블을 발견했을 때 PK 추가, NOT NULL UK 추가, OFF 전환 중 무엇을 선택해야 하는지 기준이 없다. 모든 컬럼을 키로 삼는 방식은 왜 지원하지 않는지와 각 선택의 성능·데이터 보호 차이도 설명하지 않는다.

### 왜 중요한가
PK/UK 추가는 기존 중복이나 NULL 때문에 실패할 수 있고 큰 테이블에서는 오래 걸린다. OFF는 쉽지만 failover 후 데이터가 없을 수 있다. 사용자는 단순히 HA를 빨리 시작하려고 OFF를 선택했다가 중요한 데이터를 잃은 것으로 느낄 수 있다.

### 재현 또는 구체적 예제
`event_log(ts, message)`에 동일한 행이 있고 PK가 없다. `UNIQUE(ts,message)`는 중복 때문에 실패할 수 있고 긴 message 비교는 비싸다. `event_id BIGINT PRIMARY KEY` 추가는 데이터 채우기가 필요하다. OFF로 바꾸면 신규 event가 replica에 가지 않는다.

### 권고안
테이블 용도별 결정표와 중복/NULL 확인 SQL, 키 추가 전 백업, 대형 테이블 주의, OFF 권장·금지 사례를 제공한다. 모든 컬럼 비교 방식은 비지원임을 명확히 하고 이유를 초급 수준으로 설명한다.

### 검증 방법
키 없음, 중복 있음, NULL 있음의 세 테이블로 가이드를 따라간다. 사용자가 각 경우에 실행 가능한 조치와 failover 결과를 문서만으로 올바르게 선택하는지 확인한다.

## [USER-3Y-03] REPLICATION=OFF의 의미가 “복제를 잠시 끔”으로 오해되기 쉽다

- 분류: 컨셉
- 심각도: Critical
- 근거 위치: 원문 1·4·6절의 OFF 데이터 불일치 면책
- 사실/추론 구분: 확인된 사실
- 영향 대상: 일반 사용자, 업무 데이터, failover 서비스

### 문제
OFF에서 DDL은 replica에 전달되지만 DML은 전달되지 않는다는 핵심 결과가 여러 절에 흩어져 있다. 다시 ON으로 바꾸면 빠진 데이터가 자동 보충되는지, failover 후 어느 데이터가 보이는지도 없다.

### 왜 중요한가
사용자는 테이블 구조가 standby에 있으므로 데이터도 있을 것이라 생각하기 쉽다. OFF는 단순 성능 옵션이 아니라 장애 조치 뒤 결과를 바꾸는 데이터 보호 정책이다. “책임지지 않는다”는 문장만으로는 실수를 막지 못한다.

### 재현 또는 구체적 예제
`payment_history(id PRIMARY KEY, amount) REPLICATION=OFF`에 source에서 100행을 INSERT한 뒤 failover한다. standby에는 테이블만 있고 행은 0개일 수 있다. ON으로 되돌렸을 때 100행이 자동 전송되는지도 문서에 없다.

### 권고안
OFF 정의 바로 아래에 DDL/DML/failover/ON 복귀 결과를 표로 보여 준다. 생성·변경 시 강한 경고를 출력하고 캐시·재생성 가능한 데이터 외에는 OFF를 피하도록 안내한다. 누락 데이터 재동기화 절차도 제공한다.

### 검증 방법
OFF 테이블에 INSERT/UPDATE/DELETE 후 switchover하고 각 노드 결과를 비교한다. 경고와 실제 결과가 문서 표와 같고 공식 절차로 재동기화 가능한지 확인한다.

## [USER-3Y-04] RK 후보와 실제 RK를 구분하지 않아 변경 가능 여부를 예측할 수 없다

- 분류: 모호성
- 심각도: Blocker
- 근거 위치: 원문 1절의 PK 우선·여러 UK 중 엔진 선택과 4-2절의 “복제키 후보”
- 사실/추론 구분: 확인된 사실
- 영향 대상: 스키마 변경 사용자, 복제 정합성

### 문제
PK와 여러 UK가 모두 “후보”인지, 실제 선택된 하나가 무엇인지 조회할 수 없다. 여러 UK 중 명시 순서가 빠른 것을 고른다는 내용도 보장 규칙이 아니라 예시로 적혀 있다. 재시작이나 dump/load 뒤에도 유지되는지 없다.

### 왜 중요한가
사용자는 삭제하려는 UK가 실제 RK인지 알아야 한다. 노드마다 다른 UK를 고르면 같은 변경을 다른 키로 찾을 수 있다. 이름과 선언 순서만 보고 추측하는 것은 안전하지 않다.

### 재현 또는 구체적 예제
`member(email NOT NULL UNIQUE, phone NOT NULL UNIQUE)`에서 어떤 UK가 RK인지 모른다. email UK 삭제가 허용돼 phone으로 바뀌는지, 실제 RK여서 다른 처리가 필요한지 예측할 수 없다. 재시작 뒤 phone이 선택될 가능성도 문서상 열려 있다.

### 권고안
“후보”와 “선택된 RK”를 별도로 정의하고 PK 우선, 그 다음 UK 선택 기준을 확정 문장으로 쓴다. 실제 RK 제약명·컬럼·후보 목록을 조회하는 명령과 변경 전후 출력 예를 제공한다.

### 검증 방법
PK 없음/있음, UK 한 개/여러 개 테이블을 만들고 조회한다. source와 replica, 재시작과 unload/load 전후에 선택 결과가 규칙대로 동일한지 확인한다.

## [USER-3Y-05] 기본 ON과 모드별 실패 시점이 사용자 기대와 맞지 않는다

- 분류: 호환성
- 심각도: Major
- 근거 위치: 원문 2-1절의 생략 시 ON, 1·3·9절의 single/SA/HA 표현
- 사실/추론 구분: 확인된 사실
- 영향 대상: 기존 SQL 사용자, 테스트·운영 환경

### 문제
옵션을 생략하면 ON이지만 키 없는 테이블은 single에서 생성에 성공하고 HA에서만 생성 또는 시작이 실패한다. 1절은 HA 외 모두 single이라 하고 9절은 single과 SA를 별도로 적어 같은 SQL의 결과를 예측하기 어렵다.

### 왜 중요한가
개발 환경에서 성공한 마이그레이션이 운영 HA에서 실패할 수 있다. 생성 시점과 HA 전환 시점이 멀면 원인을 찾기 어렵고, 기존에 옵션 없이 동작하던 SQL의 호환성도 바뀐다.

### 재현 또는 구체적 예제
개발 single에서 `CREATE TABLE import_stage(raw VARCHAR(1000));`가 성공한다. 같은 SQL을 HA 운영에 배포하면 기본 ON인데 RK가 없어 ERROR가 난다. SA에서 결과가 어느 쪽인지도 문서가 모순된다.

### 권고안
single/SA/HA별 CREATE ON/OFF, OFF→ON, ON→OFF, RK 변경의 결과 표를 제공하고 현재 모드 확인 명령을 적는다. single에서 키 없는 기본 ON 테이블을 만들 때 “향후 HA 시작 불가” 경고를 출력한다.

### 검증 방법
세 모드에서 옵션 생략·ON·OFF와 키 유무를 조합해 실행한다. 결과와 오류가 표와 같고 기존 SQL 사용자가 사전 경고로 운영 실패를 발견할 수 있는지 확인한다.

## [USER-3Y-06] CREATE와 ALTER 문법의 적용 위치와 오류 계약이 완성되지 않았다

- 분류: 문서 품질
- 심각도: Major
- 근거 위치: 원문 2절의 `REPLICATION={ON|OFF}`와 예시 5~7
- 사실/추론 구분: 확인된 사실
- 영향 대상: SQL 사용자, 마이그레이션 도구 사용자

### 문제
옵션의 정확한 grammar, 대소문자·공백 허용, 다른 테이블 옵션과의 순서가 없다. `ALTER TABLE tbl REPLICATION=ON`은 HA에서만 실패하는지 모든 모드에서 실패하는지 예시에 환경이 빠졌고 오류는 단순 `ERROR`다.

### 왜 중요한가
일반 사용자는 문법 예제를 그대로 사용한다. 오류 코드와 사유가 없으면 문법 오류, 권한 오류, 모드 제한, RK 부족을 구분하지 못한다. 배포 도구도 재시도 또는 수정 방법을 선택할 수 없다.

### 재현 또는 구체적 예제
`CREATE TABLE t(id INT PRIMARY KEY) REUSE_OID REPLICATION=ON;`과 옵션 순서를 바꾼 SQL 중 무엇이 유효한지 없다. `ALTER TABLE t REPLICATION=ON;`이 이미 ON일 때 성공/no-op/오류인지도 알 수 없다.

### 권고안
공식 grammar와 다른 옵션 조합, idempotent 동작을 명시한다. 모든 실패 예에 모드, 초기 상태, 안정된 오류 코드, 전체 메시지, 해결 SQL을 넣는다.

### 검증 방법
공백·대소문자·옵션 순서·중복 실행 조합을 parser 테스트로 실행한다. 문서의 기대 결과와 실제 코드가 모두 일치하는지 확인한다.

## [USER-3Y-07] 키 추가·삭제·속성 변경의 허용 상태표가 불완전하다

- 분류: 누락
- 심각도: Blocker
- 근거 위치: 원문 4-2절의 PK/UK 추가·삭제 일부 예
- 사실/추론 구분: 확인된 사실
- 영향 대상: 스키마 변경 사용자, 복제 정합성

### 문제
단일 키 삭제 예만 있고 복합 PK/UK, 타입·길이 변경, 컬럼 rename, `NOT NULL` 제거, 제약 rename과 후보 추가 후 기존 키 삭제의 전체 흐름이 없다. “다른 후보가 있으면 모든 DDL 허용”도 너무 넓다.

### 왜 중요한가
UK가 있어도 구성 열이 NULL을 허용하면 문서 기준 RK가 아니다. 복합 키의 한 열을 삭제하거나 문자열 비교 방식을 바꾸면 행 식별 의미가 달라진다. 사용자는 어떤 ALTER가 안전하게 거부될지 알아야 한다.

### 재현 또는 구체적 예제
`shipment(tenant_id INT NOT NULL, tracking_no VARCHAR(40) NOT NULL, UNIQUE(tenant_id,tracking_no))`의 유일한 후보에서 tracking_no를 rename, VARCHAR(80)으로 변경, NULL 허용으로 변경한다. 마지막 변경은 후보를 없애므로 HA에서 거부돼야 할 것 같지만 문서에 없다.

### 권고안
키/컬럼 DDL별 single·SA·HA 허용 여부, 변경 전후 RK, 오류 코드, 데이터 검사와 rollback을 표로 제공한다. 복합 키와 여러 후보 사례를 반드시 포함한다.

### 검증 방법
표의 각 변경을 단일/복합 PK와 UK에 실행한다. 성공 시 실제 RK와 양 노드 스키마가 같고 실패 시 어떤 속성도 부분 변경되지 않았는지 확인한다.

## [USER-3Y-08] 한 ALTER에서 키를 교체할 때 모두 성공하거나 모두 취소된다는 보장이 없다

- 분류: 정확성
- 심각도: Blocker
- 근거 위치: 원문 2-2절 예시 7과 4-2절 예시 13의 DROP+ADD
- 사실/추론 구분: 확인이 필요한 질문
- 영향 대상: 마이그레이션 사용자, 애플리케이션 가용성

### 문제
문서는 multiple ALTER를 사용하라고 하지만 새 키 생성이 실패할 때 옛 키 삭제도 취소되는지 설명하지 않는다. 제약 이름과 완전한 SQL, 실행 중 DML 처리도 빠졌다.

### 왜 중요한가
“원자적”이라는 말은 둘 다 성공하거나 둘 다 실패한다는 뜻이다. 이메일 중복 때문에 새 UK가 실패했는데 PK만 사라지면 HA를 유지할 수 없고 테이블 접근도 예상치 못하게 바뀐다.

### 재현 또는 구체적 예제
중복 email이 있는 `users(id PK, email NOT NULL)`에 `ALTER TABLE users DROP CONSTRAINT pk_users, ADD CONSTRAINT uq_users_email UNIQUE(email);`을 실행한다. 기대 결과는 전체 실패와 id PK/RK 유지다. replica에서만 ADD가 실패한 경우도 같은 결과여야 한다.

### 권고안
사전 중복 검사, 완전한 SQL, 잠금/대기, 실패 rollback과 두 노드 적용 규칙을 명시한다. 원자성을 보장할 수 없다면 이 변경을 HA 중 금지하고 안전한 중지 절차를 제시한다.

### 검증 방법
정상·중복 데이터와 replica 적용 실패를 만들어 실행한다. 모든 실패 뒤 PK/UK, 선택 RK, 데이터가 변경 전과 같은지 양 노드에서 조회한다.

### 검증 방법
두 세션의 시작·커밋 순서를 교차해 UPDATE/DELETE/RK 값 UPDATE를 실행한다. 세션 결과, 양 노드 데이터와 로그 순서가 문서와 일치하는지 확인한다.

한 번의 옵션 실수가 서비스 중단 또는 데이터 재구축으로 이어질 수 있다. OFF 전환 이전에 큐에 있던 변경이 어디까지 적용되는지도 없어 두 노드 차이를 예측할 수 없다.

### 검증 방법
복제 지연 중 OFF 전환과 전후 DML을 발생시킨다. 경계 결과를 확인하고 문서 절차만으로 ON 복귀 후 양 노드 checksum을 같게 만들 수 있는지 시험한다.

## [USER-3Y-12] 복합 RK와 RK 값 자체 UPDATE의 결과가 없다

- 분류: 정확성
- 심각도: Critical
- 근거 위치: 원문 1절의 PK/UK 규칙과 4-2절의 단일 키 중심 예제
- 사실/추론 구분: 확인이 필요한 질문

### 문제
복합 PK/UK도 RK인지 명시적 예가 없고, RK 구성 값을 UPDATE할 때 replica가 이전 값과 새 값 중 무엇으로 행을 찾는지 없다. 타입·길이·collation 변경도 식별 결과에 영향을 줄 수 있다.

### 왜 중요한가
복합 키는 여러 열을 함께 봐야 유일하다. replica에는 아직 옛 값만 있으므로 새 값으로 찾으면 행을 못 찾는다. 넓은 문자열 키는 로그와 비교 비용도 커진다.

### 재현 또는 구체적 예제

### 권고안
복합 키 지원 범위, 컬럼 순서, NULL·타입·문자 비교 규칙과 최대 크기를 명시한다. 키 UPDATE에는 이전 키로 찾고 새 값을 적용한다는 계약 또는 실제 동작을 예제로 설명한다.

### 검증 방법
2~3열 숫자/문자 복합 PK·UK에서 각 열을 변경하고 중복 충돌을 발생시킨다. 양 노드 행과 오류, apply 성능이 문서와 같은지 확인한다.

- 분류: 누락
- 심각도: Critical
- 근거 위치: 원문 5절의 ON 자식이 참조하는 부모도 ON이어야 한다는 규칙

새 FK 생성 예는 있으나 이미 연결된 부모를 OFF로 바꾸는 경우, OFF 자식이 ON 부모를 참조하는 경우, `ON DELETE CASCADE`/`ON UPDATE CASCADE`의 복제 방식은 없다.

### 왜 중요한가
부모 변경이 복제되지 않는데 자식 변경만 복제되면 replica의 관계가 깨질 수 있다. 연쇄 삭제가 source와 replica에서 두 번 실행되거나 전혀 실행되지 않는지도 알아야 한다.

`customers ON`과 `orders ON`을 `ON DELETE CASCADE`로 연결한다. customers를 OFF로 바꾼 뒤 고객을 삭제하면 source 주문도 삭제된다. replica에서 부모는 남고 주문만 삭제되는지, 전환이 거부되는지 문서가 답하지 않는다.

### 권고안
부모/자식 ON·OFF 조합과 FK 생성·삭제·상태 변경, CASCADE/SET NULL/RESTRICT 결과를 표로 제공한다. 위험 조합을 만드는 ALTER는 명확한 오류로 거부한다.

### 검증 방법
네 상태 조합과 각 연쇄 옵션으로 INSERT/UPDATE/DELETE 및 failover를 실행한다. 오류와 양 노드 데이터가 표와 일치하는지 확인한다.

지원 대량 명령별 복제 여부, batch 단위, 취소·재시작, 진행률과 failover 제한을 표로 제공한다. 안전하지 않은 도구는 명확히 경고한다.

### 검증 방법
ON/OFF에서 일반 INSERT와 bulk/TRUNCATE를 실행하고 중간 failover한다. 문서가 말한 batch 경계와 최종 행 수가 같은지 본다.

## [USER-3Y-26] 대형 키 추가 작업의 진행률과 취소 방법이 없다

- 분류: 운영성
- 심각도: Major
- 근거 위치: 원문 3·7절은 PK/UK 추가를 해결책으로 제시하지만 실행 시간·잠금은 누락한다.
- 사실/추론 구분: 확인이 필요한 질문
- 영향 대상: 일반 운영 사용자, 서비스 가용성

### 문제
대형 테이블에 UK를 추가할 때 online인지, 쓰기가 얼마나 대기하는지, 진행률·남은 시간·취소 후 상태를 알 수 없다.

### 왜 중요한가
모든 행의 중복을 검사하고 인덱스를 만드는 작업은 오래 걸린다. 사용자는 작은 테스트처럼 즉시 끝날 것으로 생각해 업무 시간에 실행할 수 있다.

### 재현 또는 구체적 예제
```sql
ALTER TABLE customer ADD CONSTRAINT uq_email UNIQUE(email);
```
5억 행에서 60% 진행 중 취소하면 기존 RK와 서비스가 그대로인지, 임시 공간을 지우는지 없다.

### 권고안
잠금 수준, online 지원, 예상 공간·시간, 진행률 조회, cancel·retry 결과와 운영 시간 권장을 제공한다.

### 검증 방법
대형 샘플의 쓰기 부하 중 DDL을 실행·취소한다. 화면/명령 진행률, 요청 지연, 정리 후 상태가 문서와 같은지 확인한다.

## [USER-3Y-27] RK 후보가 될 수 없는 데이터 타입을 알 수 없다

- 분류: 정확성
- 심각도: Major
- 근거 위치: 원문 1절은 PK/NOT NULL UK만 말하고 타입별 적합성은 누락한다.
- 사실/추론 구분: 확인이 필요한 질문
- 영향 대상: JSON·LOB·실수·다국어 키 사용자

### 문제
floating point, LOB, JSON과 같은 타입이 UNIQUE/RK 후보가 될 수 있는지, 문자열 collation이 다른 노드에서 같은 비교를 보장하는지 없다. 실제 지원 타입은 대상 버전 확인이 필요하다.

### 왜 중요한가
실수 값은 표현·반올림 문제가 있고 큰 값은 로그와 비교 비용이 크다. 문자열 정렬 규칙이 바뀌면 이전에 서로 다른 값이 같아질 수 있다.

### 재현 또는 구체적 예제
```sql
CREATE TABLE item (
  external_value DOUBLE NOT NULL UNIQUE,
  description VARCHAR(4000)
) REPLICATION=ON;
```
DOUBLE UK가 RK가 되는지, 값 비교와 UPDATE가 안전한지 없다.

### 권고안
지원/비지원 타입, 최대 키 크기, collation·정밀도 조건과 부적격 오류를 표로 제공한다. 안정적인 정수 surrogate key 권장 사례도 설명한다.

### 검증 방법
지원 후보 타입의 경계값, 긴 문자열, locale/collation을 조합해 CREATE와 DML/failover를 실행한다. 비지원 타입은 이해 가능한 오류로 거부되는지 본다.

## [USER-3Y-28] 인덱스 재구축과 제약 이름 변경이 RK를 바꾸는지 없다

- 분류: 모호성
- 심각도: Major
- 근거 위치: 원문 4-2절은 DROP INDEX만 다루고 유지보수 작업은 누락한다.
- 사실/추론 구분: 확인이 필요한 질문
- 영향 대상: 정기 유지보수 사용자, 복제 안정성

### 문제
UNIQUE 의미를 유지한 index rebuild, constraint rename, 통계 갱신 후 실제 RK가 유지되는지 알 수 없다.

### 왜 중요한가
사용자는 성능 유지보수일 뿐이라고 생각한다. 이 작업으로 RK가 바뀌면 대기 로그 적용 또는 이후 DDL 허용 결과가 달라질 수 있다.

### 재현 또는 구체적 예제
email UK가 RK인 `member`의 index를 지원되는 명령으로 rebuild하고 이름을 바꾼다. 변경 전 UPDATE 로그도 변경 후 정상 적용돼야 한다.

### 권고안
지원 유지보수 명령별 RK 유지·변경, 잠금, 경고와 조회 결과를 표로 제공한다. optimizer 통계는 RK 선택과 분리해야 한다.

### 검증 방법
작업 전후 실제 RK를 조회하고 replica 지연 상태에서 DML을 적용한다. 재시작·failover 뒤도 동일 결과인지 확인한다.

## [USER-3Y-29] 오류 메시지의 언어가 바뀌어도 같은 조치를 찾을 수 있어야 한다

- 분류: 문서 품질
- 심각도: Major

- 사실/추론 구분: 확인된 사실
- 영향 대상: 한국어·영어 사용자, 자동 진단, 고객지원

### 문제
오류 코드, 객체명, 원인과 해결 링크 없이 자연어만 있으면 locale별 메시지가 달라진다. 사용자는 검색 결과를 찾기 어렵고 도구는 문자열을 안정적으로 판독할 수 없다.

### 왜 중요한가
같은 “RK 없음” 오류라도 한국어 운영과 영어 지원팀이 다른 문구를 본다. 코드가 없으면 같은 사고인지 빠르게 합의하기 어렵다.

### 재현 또는 구체적 예제

### 권고안
언어와 무관한 안정된 코드, owner.table/constraint, 원인·조치·문서 링크를 정의하고 한국어/영어 전체 출력 예를 제공한다.

### 검증 방법
locale을 바꿔 RK·FK·모드 오류를 발생시킨다. 코드는 같고 번역된 문구·객체·조치가 누락되지 않는지 확인한다.

## [USER-3Y-31] 네트워크 분할 중 서비스가 안전한지 사용자가 알 방법이 없다

- 분류: 운영성
- 심각도: Critical
- 근거 위치: 원문 4·7절은 정상 HA와 failover만 설명하고 degraded/split-brain 사용자 상태는 누락한다.
- 사실/추론 구분: 확인이 필요한 질문
- 영향 대상: 서비스 사용자, 운영 담당자, 데이터 정합성

네트워크 분할 때 쓰기가 안전하게 한 노드로 제한되는지, 위험 DDL이 금지되는지, 현재 read-only/degraded 상태를 사용자가 확인할 수 있는지 없다.

### 왜 중요한가
두 노드가 모두 쓰기를 받으면 서로 다른 RK와 데이터가 만들어질 수 있다. 사용자는 DB 연결이 성공한다는 이유로 정상이라고 오해할 수 있다.

노드 A에서 `orders OFF`, 분리된 B에서 RK 변경을 시도한다. 안전한 설계는 한쪽 쓰기/DDL을 막고 사용자에게 명확한 degraded 상태를 보여 주는 것이다.

### 권고안
단일 writer/fencing 정책, 분할 중 허용 읽기·쓰기·DDL, 상태 조회와 애플리케이션 오류를 문서화한다. 강제 작업의 위험과 관리자 연락 절차를 제공한다.

### 검증 방법
heartbeat와 복제 network를 분리한 뒤 양쪽 SQL과 상태 조회를 실행한다. 한쪽 쓰기가 차단되고 사용자가 상태와 조치를 올바르게 알 수 있는지 확인한다.

## [USER-3Y-32] 임시·시스템·도구 테이블에도 기본 ON이 적용되는지 없다

- 분류: 누락
- 심각도: Major
- 근거 위치: 원문 2-1·7절은 테이블 일반 규칙만 말하고 객체 유형 예외는 누락한다.
- 사실/추론 구분: 확인이 필요한 질문
- 영향 대상: 임시 작업 사용자, 관리 도구, HA 시작

### 문제
대상 버전에서 지원하는 임시 테이블, 시스템 객체, 도구가 만든 내부 테이블에 ON 기본값과 RK 필수 규칙이 적용되는지 없다.

세션용 임시 객체 때문에 HA 시작이 막히면 불필요한 장애다. 반대로 영구 도구 테이블이 제외되면 중요한 운영 상태가 failover 후 없을 수 있다.

### 재현 또는 구체적 예제
import 도구가 키 없는 `tool_stage(value INT)`를 자동 생성한다고 하자. 영구 user table인지 session temporary인지에 따라 검사 결과가 달라야 한다.

### 권고안
지원 객체 유형별 옵션 허용, 기본값, DDL/DML 복제, HA 검사 포함 여부를 표로 제공한다. 오류에는 객체 유형과 생성 도구를 표시한다.

### 검증 방법
지원되는 임시·영구·시스템/도구 객체를 만들고 상태 조회와 HA 검사를 실행한다. 포함·제외 결과가 표와 일치하는지 확인한다.
