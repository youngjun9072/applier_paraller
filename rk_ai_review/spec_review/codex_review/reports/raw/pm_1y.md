- 대상 문서: ../../../user_spec/user_spec.html

- 리뷰 항목 수: 20

## [PM-1Y-01] RK 도입이 기존 누락 원인을 어떻게 차단하는지 연결 설명이 없다

- 분류: 컨셉
- 심각도: Critical
- 근거 위치: 원문 1절의 RK 필수 조건과 4-2절의 RK 후보 변경 제약
- 사실/추론 구분: 문서에서 도출한 추론
- 영향 대상: 제품 기획, 사용자, 복제 정합성, 지원 조직

### 문제
문서는 복제 테이블에 PK 또는 `NOT NULL UNIQUE KEY` 기반 RK가 있어야 한다고 정하지만, 기존 장애의 원인인 “HA 실행 중 PK 컬럼 속성 변경 → 변경 누락 → `fail_count` 증가”가 새 규칙으로 어떤 단계에서 차단되는지 설명하지 않는다. RK 후보가 하나 더 있으면 “모든 DDL 허용”이라고만 하므로, 로그가 옛 키를 참조하는 동안 새 키로 바뀌는 문제까지 해결되는지 알 수 없다.

### 왜 중요한가
PM이 기능의 성공을 판정하려면 해결하려는 사고와 새 동작 사이의 인과관계가 있어야 한다. 단지 키가 항상 하나 존재하는 것과, 이미 생성된 DML 로그가 standby에서 올바른 행을 찾는 것은 다른 조건이다. 키 정의가 DDL 전후로 달라질 때 로그가 어느 정의를 쓰는지 없으면 같은 데이터 불일치가 형태만 바뀌어 재발할 수 있다.

### 재현 또는 구체적 예제
초기에 `account(id PK, email NOT NULL UNIQUE, balance)`가 있고 RK는 `id`라고 한다. 트랜잭션 A가 `UPDATE account SET balance=900 WHERE id=10;`을 기록한 직후, 트랜잭션 B가 하나의 `ALTER TABLE`로 PK를 `email`로 교체한다. replica가 DDL을 먼저 인식한 뒤 A의 로그에서 `id=10`을 받으면 어느 키 정의로 행을 찾는지 문서상 불명확하다. 기대 결과는 A와 B의 순서가 양 노드에서 같고 업데이트가 정확히 한 행에 적용되는 것이다.

### 권고안
문제 정의에 “각 DML 로그는 생성 당시 RK 식별자와 값을 보존하며, 관련 DDL과 같은 전역 순서로 적용한다” 같은 해결 불변식을 넣거나 실제 설계가 다르면 그 규칙을 명시한다. 성공 조건을 “허용된 RK 변경 시 변경 누락 0건, RK 관련 apply 오류로 인한 `fail_count` 증가 0회, failover 후 행 단위 불일치 0건”으로 정한다.

### 검증 방법
PK→UK, UK→PK, UK→다른 UK 전환 각각에서 DDL 전후 DML 1,000건을 섞고 복제 지연을 준다. 적용 완료 후 양 노드의 행 수와 행별 체크섬을 비교하고 `fail_count` 증분 및 apply 로그를 확인한다.

## [PM-1Y-02] 모든 컬럼 비교 대안과 선택한 설계의 범위가 비교되지 않는다

- 분류: 컨셉
- 심각도: Major
- 근거 위치: 원문 1절의 PK 또는 NOT NULL UK 선택 규칙
- 사실/추론 구분: 확인이 필요한 질문
- 영향 대상: 제품 의사결정자, PK 없는 테이블 사용자, 성능 담당자

### 문제
문서는 PK가 없는 행을 모든 컬럼으로 찾는 대안, 복제를 끄는 대안, UK를 추가하는 대안의 장단점을 보여 주지 않는다. 따라서 왜 PK 없는 테이블은 자동 복제하지 않고 HA 시작을 막는지, PostgreSQL 계열 개념 중 정확히 무엇을 채용한 것인지 제품 결정의 근거가 부족하다.

### 왜 중요한가
모든 컬럼 비교는 넓은 문자열·LOB·`NULL`·중복 값 때문에 느리거나 한 행을 유일하게 찾지 못할 수 있다. 반면 UK 추가는 기존 중복 데이터를 정리해야 하며 업무상 유일하지 않은 테이블에는 적용할 수 없다. 사용자가 비용을 이해하지 못하면 편의를 위해 `REPLICATION=OFF`를 선택하고 failover에서 데이터를 잃은 것처럼 느낄 수 있다.

### 재현 또는 구체적 예제
`event_log(ts DATETIME, message VARCHAR(4000), payload JSON)`에 PK/UK가 없고 1억 행이 있다고 하자. 모든 컬럼 비교는 긴 값을 로그와 검색에 사용해야 하고 동일 이벤트 두 건을 구분하지 못할 수 있다. `event_id BIGINT PRIMARY KEY`를 추가하면 식별은 쉬워지지만 1억 행 백필과 애플리케이션 변경이 필요하다. `REPLICATION=OFF`이면 failover 후 신규 이벤트가 없다. 문서는 세 결과를 비교하지 않는다.

### 권고안
대안 결정표를 추가해 정확성, 쓰기·적용 성능, 기존 데이터 마이그레이션, failover 결과를 비교한다. “모든 컬럼 키는 지원하지 않는다”, “사용자 지정 RK는 이번 범위가 아니다”처럼 비지원 범위도 선언하고 PostgreSQL과 같다고 암시하지 말고 채용 요소만 설명한다.

### 검증 방법
PK 없음, 좁은 정수 PK, 3열 문자열 UK의 대표 테이블로 설계 검토를 수행한다. 각 유형에 대해 지원 여부, 권장 마이그레이션, 예상 오류가 문서 한 곳에서 답해지는지 초보 사용자 3명이 문서만 읽고 설명하게 한다.

## [PM-1Y-03] REPLICATION=OFF의 제품 책임과 허용 용도가 지나치게 넓다

- 분류: 컨셉
- 심각도: Critical
- 근거 위치: 원문 1절의 “불일치는 책임지지 않는다”, 4절과 6절의 노드 간 데이터 불일치 허용
- 사실/추론 구분: 확인된 사실
- 영향 대상: 사용자, 서비스 운영자, 법무·지원, 데이터 정합성

### 문제
문서는 `REPLICATION=OFF`로 인한 데이터 불일치를 책임지지 않는다고만 한다. 어떤 테이블에 사용해도 되는지, DML이 source에만 남는다는 경고, failover·failback 때 데이터가 어떻게 되는지, 사용자가 명시적으로 위험을 승인해야 하는지 제품 계약이 없다.

### 왜 중요한가
옵션 이름만 보면 “복제 성능 최적화” 정도로 오해할 수 있다. 실제로는 장애 조치 후 해당 테이블 데이터가 없거나 오래될 수 있고, 그 테이블을 읽는 뷰와 애플리케이션 결과도 변한다. 면책 문장만으로는 안전한 사용을 유도하거나 지원 분쟁을 줄일 수 없다.

### 재현 또는 구체적 예제
`payment_audit(id, amount) REPLICATION=OFF`에 source에서 결제 기록 100건을 넣은 뒤 failover한다. DDL은 복제되어 테이블은 보이지만 standby 데이터는 비어 있을 수 있다. 사용자는 `SELECT COUNT(*)`가 0을 반환하는 것을 장애로 신고할 수 있다. 기대 계약은 “세션 임시성·재생성 가능 데이터만 권장”처럼 용도와 결과를 사전에 알리는 것이다.

### 권고안
OFF의 의미를 “DDL은 전달되나 이 테이블의 DML은 전달되지 않음”으로 풀어 쓰고, 영구 업무 데이터·FK 대상·권한/감사 데이터에는 사용 금지 또는 강한 경고를 둔다. 생성·변경 시 경고, failover 전 OFF 테이블 목록 확인, failback 시 재동기화 또는 폐기 절차를 제품 범위로 정의한다.

### 검증 방법
OFF 테이블에 INSERT/UPDATE/DELETE 후 switchover와 failover를 각각 실행한다. 문서에 예고된 결과와 실제 결과를 비교하고, 관리 도구가 OFF 목록과 데이터 비동기 위험을 눈에 띄게 표시하는지 확인한다.

## [PM-1Y-04] RK 후보와 실제 RK, 여러 UK 선택 기준이 사용자 계약으로 고정되지 않았다

- 분류: 모호성
- 심각도: Blocker
- 근거 위치: 원문 1절의 PK 우선, PK가 없으면 UK, 여러 UK 중 엔진 선택 예시와 4-2절의 “복제키 후보” 표현
- 사실/추론 구분: 확인된 사실
- 영향 대상: 사용자, DBA, 복제 엔진, 업그레이드 담당자

### 문제
문서는 후보와 실제 RK를 혼용하고, 여러 UK에서 “테이블 내 명시된 순서 중 가장 빠른 순서”를 예시로만 든다. 선택 규칙이 보장인지 예시인지, 재시작·DDL·백업 복원·버전 업그레이드 뒤에도 같은 UK가 유지되는지 알 수 없다. 실제 RK를 조회하는 방법도 없다.

### 왜 중요한가
두 노드가 서로 다른 UK를 RK로 선택하면 source가 `email` 값을 기록했는데 replica는 `phone` 값으로 해석하는 식의 치명적 오류가 생길 수 있다. 같은 노드라도 재시작 후 선택이 바뀌면 이전 로그를 적용하지 못할 수 있다. 초보자는 UK가 두 개면 둘 다 함께 쓰는 것으로 오해할 수 있다.

### 재현 또는 구체적 예제
`member(id 없음, email NOT NULL UNIQUE, phone NOT NULL UNIQUE)`를 만든다. 처음 RK가 `email`이고 `UPDATE member SET phone='010-2' WHERE email='a@x';` 로그가 쌓인 상태에서 재시작 후 RK가 `phone`으로 선택된다고 가정하면 과거 로그 해석이 불명확하다. 기대 결과는 카탈로그에 단 하나의 실제 RK 식별자가 저장되고 모든 노드가 동일하게 유지하는 것이다.

### 권고안
후보와 선택된 RK를 정의하고, 결정적 우선순위(예: PK 우선, 그 외에는 영구 제약 ID 기준)를 규범 문장으로 정한다. 선택 결과를 카탈로그 및 `SHOW CREATE TABLE`과 별도 조회 명령에서 노출하고, 변경 이벤트를 로그에 남긴다. 선택 지속성의 범위를 재시작·복원·업그레이드별로 명시한다.

### 검증 방법
동일 스키마를 제약 선언 순서만 바꾸어 생성하고 source/replica, 재시작 전후, unload/load 전후의 실제 RK를 조회한다. 모두 규칙과 일치하는지, 대기 중 로그도 정상 적용되는지 확인한다.

## [PM-1Y-05] 기본값 ON은 기존 SQL에 새로운 HA 실패를 만들지만 경고와 전환 정책이 없다

- 분류: 호환성
- 심각도: Major
- 근거 위치: 원문 2-1절의 옵션 생략 시 ON과 3·7절의 RK 없는 ON 테이블에 대한 HA 시작 거부
- 사실/추론 구분: 확인된 사실
- 영향 대상: 기존 사용자, 신규 사용자, 배포 담당자

### 문제
기존 `CREATE TABLE` 문은 자동으로 `REPLICATION=ON`이 된다. single 모드에서는 RK 없는 ON 테이블도 만들 수 있지만 나중에 HA 시작이 실패한다. 기존 사용자가 새 옵션을 모르고 만든 작업용 테이블 하나 때문에 전체 HA가 시작되지 않을 수 있는데, 릴리스 전환·경고·기본값 선택 근거가 없다.

### 왜 중요한가
기본값은 아무 옵션도 쓰지 않은 다수 사용자의 동작이다. 생성 시 성공하고 훨씬 뒤 HA 전환 때 실패하면 원인과 생성 작업을 연결하기 어렵다. 이는 이전 버전에서 정상인 자동 배포가 새 버전에서 운영 중단으로 이어질 수 있는 호환성 변화다.

### 재현 또는 구체적 예제
마이그레이션이 `CREATE TABLE import_stage(raw_line VARCHAR(4000));`만 실행한다. single 테스트에서는 성공한다. 운영자가 한 달 뒤 `cubrid hb start`를 실행하면 `import_stage`에 RK가 없어 전체 시작이 실패한다. 기대 결과는 생성 시 경고 또는 HA 준비 검사에서 테이블명과 해결 SQL을 미리 받는 것이다.

### 권고안
기본 ON을 유지한다면 릴리스 노트에 호환성 영향을 명시하고, single 생성 시 “HA 전환 불가” 경고를 제공한다. 읽기 전용 사전 점검 명령과 `ALTER TABLE ... REPLICATION=OFF` 또는 키 추가 예를 제공한다. 기본값 변경 여부는 기존 데이터 보호와 신규 사용성 기준으로 명시적으로 승인받는다.

### 검증 방법
옵션을 생략한 RK 있음/없음 테이블을 구버전 호환 SQL로 만든다. 생성 경고, 카탈로그 값, HA 사전 검사 오류, 수정 후 시작 결과가 문서와 일치하는지 검증한다.

## [PM-1Y-06] single·SA·HA 모드 정의와 허용 동작 표가 서로 맞지 않는다

- 분류: 정확성
- 심각도: Major
- 근거 위치: 원문 1절의 hb start 외 모두 single, 3절의 Single, 9절의 “싱글이나 SA”
- 사실/추론 구분: 확인된 사실
- 영향 대상: 초보 사용자, QA, 문서·지원 조직

### 문제
1절은 HA가 아니면 모두 single이라고 정의하지만 9절은 single과 SA를 별도 모드처럼 쓴다. 3절은 “제약은 없다”고 하면서 HA 전환을 위한 수정 책임을 둔다. 모드별로 CREATE, `ALTER ... ON/OFF`, RK 변경, FK 검사가 언제 허용되는지 한눈에 알 수 없다.

### 왜 중요한가
사용자는 현재 접속 모드가 무엇인지에 따라 같은 SQL이 성공하거나 실패하는 이유를 알아야 한다. 용어가 모순되면 QA도 어떤 환경을 시험해야 하는지 빠뜨리고, 지원팀도 재현 조건을 잘못 안내할 수 있다.

### 재현 또는 구체적 예제
`ALTER TABLE cache REPLICATION=ON;`은 2-2절 예시에선 HA에서 ERROR로 보이며 single에서는 가능한 것으로 읽힌다. SA 모드에서는 허용되는지, 서버 프로세스가 떠 있지만 heartbeat만 멈춘 상태는 무엇인지 불명확하다. 기대 결과는 현재 모드별 성공/실패와 오류 사유가 표로 정해지는 것이다.

### 권고안
공식 모드명을 정의하고 `CREATE ON/OFF`, OFF→ON, ON→OFF, RK 추가·삭제·교체, FK 추가별 허용 표를 추가한다. 모드 판정 기준과 사용자가 현재 모드를 확인하는 명령도 제공한다.

### 검증 방법
문서에 정의된 각 모드를 실제로 구성하여 동일한 SQL 세트를 실행한다. 허용 표와 결과·오류 코드가 모두 일치하고, 초보 사용자가 모드 확인 명령으로 자신의 상태를 구분할 수 있는지 확인한다.

## [PM-1Y-07] RK 후보의 추가·삭제·교체 상태 전이가 완전하게 정의되지 않았다

- 분류: 누락
- 심각도: Blocker
- 근거 위치: 원문 4-2절의 후보가 하나면 제한, 다른 후보가 있으면 모든 DDL 허용
- 사실/추론 구분: 확인된 사실
- 영향 대상: 스키마 변경 사용자, 애플리케이션, 복제 정합성

### 문제
문서는 단일 PK/UK의 삭제 예만 들고 복합 키 일부 컬럼 변경, `NOT NULL` 제거, 타입 변경, 컬럼 이름 변경, UK 후보 추가 후 기존 RK 삭제 등 전체 상태 전이를 규정하지 않는다. “후보가 함께 존재하면 모든 DDL 허용”은 RK 자격을 잃는 복합 ALTER까지 허용한다고 읽힐 수 있다.

### 왜 중요한가
RK 자격은 제약 이름만이 아니라 구성 컬럼, 유일성, `NULL` 가능 여부에 의존한다. `NULL` 허용으로 바꾸거나 복합 UK의 한 컬럼을 삭제하면 제약이 남아 보여도 행을 유일하게 식별하지 못할 수 있다. 모든 전이 후 유효한 RK가 정확히 무엇인지 보장해야 한다.

### 재현 또는 구체적 예제
`shipment(tenant_id INT NOT NULL, tracking_no VARCHAR(40) NOT NULL, UNIQUE(tenant_id, tracking_no), note)`에서 이 복합 UK만 RK 후보라고 하자. `ALTER TABLE shipment MODIFY tracking_no VARCHAR(80);`, 이름 변경, `DROP NOT NULL`, 복합 UK 재생성 각각이 허용되는지 없다. 특히 `DROP NOT NULL`은 RK 자격을 잃으므로 기대 동작은 대체 후보가 없으면 명확한 오류로 거부하는 것이다.

### 권고안
상태 전이 표에 PK/UK 추가·삭제·이름 변경, 컬럼 추가·삭제·rename·타입·collation·NULL 속성 변경, 복합 키 일부 변경을 열거한다. 각 전이에 대해 허용 모드, 선택 전/후 RK, 잠금, 오류 코드, rollback 결과를 정한다.

### 검증 방법
단일·복합 PK/UK 테이블에 상태 전이 표의 SQL을 하나씩 실행한다. 성공 후에는 RK가 유효하고 양 노드에 동일하며, 실패 후에는 스키마와 RK가 전혀 바뀌지 않았는지 확인한다.

## [PM-1Y-08] 하나의 ALTER에서 키 교체가 원자적인지와 예시 문법이 확정되지 않았다

- 분류: 모호성
- 심각도: Blocker
- 근거 위치: 원문 2-2절 예시 7과 4-2절 예시 13의 DROP과 ADD를 함께 수행하는 SQL
- 사실/추론 구분: 확인이 필요한 질문
- 영향 대상: DBA, 애플리케이션 배포, 복제 정합성

### 문제
문서는 multiple ALTER를 권장하지만 전체 문법, 제약 이름, 검증 순서, 실패 시 rollback, replica 적용 원자성을 설명하지 않는다. 예시 13은 `DROP CONSTRAINT PRIMARY KEY`와 다시 `PRIMARY KEY(a)`를 써서 실제 대상 컬럼도 혼란스럽다.

### 왜 중요한가
키 삭제와 추가 사이에 잠시 RK가 0개가 되면 DML을 식별할 수 없다. 새 키 추가가 중복 데이터 때문에 실패했는데 옛 키 삭제만 반영되면 테이블이 HA 불가 상태가 된다. 원자성은 “둘 다 성공하거나 둘 다 취소”된다는 뜻이며 명시적 계약이어야 한다.

### 재현 또는 구체적 예제
`user_tbl(id PK, email NOT NULL)`에 중복 email 두 건이 있다. `ALTER TABLE user_tbl DROP CONSTRAINT pk_user, ADD CONSTRAINT uq_email UNIQUE(email);`을 실행하면 ADD가 실패한다. 기대 결과는 DROP도 취소되고 `id` RK가 유지되는 것이다. source 성공·replica 실패가 발생했을 때 HA를 중단하는지 rollback하는지도 필요하다.

### 권고안
실행 가능한 제약 이름을 사용한 완전한 SQL과 사전 데이터 검증을 싣는다. 복합 ALTER는 단일 트랜잭션/로그 단위이며 어느 단계든 실패하면 양 노드에서 기존 스키마와 RK를 유지한다는 수용 기준을 명시한다. 보장할 수 없다면 해당 변경을 금지하고 안전 절차를 제공한다.

### 검증 방법
성공 데이터, 중복 데이터, replica DDL 적용 실패를 각각 주입한다. 각 실패 뒤 PK/UK 카탈로그, 선택 RK, DML 가능 여부가 변경 전과 같고 부분 DDL이 없는지 양 노드에서 조회한다.

## [PM-1Y-09] DDL과 DML 동시 실행 때 로그 순서와 허용 행동이 없다

- 분류: 정확성
- 심각도: Blocker
- 근거 위치: 원문 4절의 모든 DDL 복제와 RK 변경 허용 규칙
- 사실/추론 구분: 확인이 필요한 질문
- 영향 대상: 온라인 배포 사용자, 복제 엔진, 데이터 정합성

### 문제
온라인 서비스에서 RK 변경 DDL과 INSERT/UPDATE/DELETE가 동시에 실행될 때 DML을 대기·거부·허용하는지 없다. source의 커밋 순서와 replica의 적용 순서, DML 로그에 이전·새 RK 중 무엇을 담는지도 정의하지 않았다.

### 왜 중요한가
DDL 직전의 UPDATE가 옛 키로 기록되고 DDL 직후 replica에 도착할 수 있다. 특히 RK 값 자체를 바꾸는 UPDATE는 행을 찾을 때 이전 값이 필요하다. 순서 계약이 없으면 변경 누락과 `fail_count` 증가라는 원래 문제가 그대로 남는다.

### 재현 또는 구체적 예제
RK가 `id`인 `customer(id, email UNIQUE NOT NULL)`에서 A가 `UPDATE customer SET id=11 WHERE id=10;`, B가 PK를 email로 교체하고 각각 커밋한다. A가 먼저 시작했지만 B가 먼저 커밋하는 경우도 포함한다. 기대 결과는 문서가 잠금/직렬화 규칙과 replica 적용 순서를 정하고 정확히 한 행만 변경하는 것이다.

### 권고안
DDL 시작·커밋 전후의 DML 처리, RK 값 UPDATE 시 before/after 값, 로그 스키마 버전, replica 재시도 규칙을 상태 순서도로 추가한다. 사용자 수준에서는 “대기”, “오류로 거부”, “허용” 중 하나와 오류 코드를 명시한다.

### 검증 방법
두 세션에서 DDL과 네 종류 DML(INSERT, DELETE, 비키 UPDATE, RK UPDATE)의 시작·커밋 순서를 교차한다. 복제 지연과 재시작도 넣고 최종 데이터, 로그 적용 순서, `fail_count`를 검사한다.

## [PM-1Y-10] failover 중 RK 변경의 완료 기준과 복구 상태가 없다

- 분류: 누락
- 심각도: Critical
- 근거 위치: 원문 4절의 운영 중 ALTER와 7절의 HA 전환 검사
- 사실/추론 구분: 확인이 필요한 질문
- 영향 대상: 장애 조치 운영자, 애플리케이션, 복제 정합성

### 문제
RK 교체 DDL이 source에는 커밋됐지만 replica에는 아직 적용되지 않은 시점에 failover하면 새 primary가 옛 RK를 가질 수 있다. 문서는 DDL 적용 완료를 기다리는지, 승격을 막는지, 자동 복구하는지 설명하지 않는다.

### 왜 중요한가
failover는 장애 시 가장 혼란스러운 시점에 실행된다. 스키마와 RK가 다른 노드가 승격되면 이후 쓰기가 서로 다른 키 계약으로 기록되어 failback도 어려워진다. 정상 시나리오만 맞아서는 HA 기능의 목적을 달성하지 못한다.

### 재현 또는 구체적 예제
source가 `ALTER TABLE account ...`로 RK를 id에서 email로 바꿔 커밋한 직후 replica apply를 멈추고 source를 종료한다. replica를 승격하려 할 때 기대 동작은 “해당 DDL LSA까지 적용 전 승격 거부” 또는 설계된 복구 절차 중 하나여야 한다. 현재 문서에서는 결과가 없다.

### 권고안
승격 가능 조건에 스키마/RK 버전 일치 여부를 넣고, 불일치 시 오류 메시지와 수동 복구 절차를 정한다. 계획된 switchover와 비계획 failover를 나누어 허용 데이터 손실 범위(RPO)와 복구 시간 목표(RTO)를 명시한다.

### 검증 방법
RK DDL 로그의 생성, 전송, 적용 각 지점에서 source 장애를 주입한다. 승격이 안전하게 차단되거나 완료된 뒤 모든 DML이 일관되게 적용되는지, failback 시에도 RK가 같은지 확인한다.

## [PM-1Y-11] REPLICATION ON→OFF 전환 중 대기 DML과 다시 ON으로 만드는 절차가 없다

- 분류: 운영성
- 심각도: Critical
- 근거 위치: 원문 2-2절의 HA에서 ON→OFF 허용·OFF→ON 금지와 4절의 DML만 제외
- 사실/추론 구분: 문서에서 도출한 추론
- 영향 대상: 운영자, 애플리케이션, 데이터 정합성

### 문제
HA 운영 중 ON 테이블을 OFF로 바꿀 수 있으나 이미 전송 중인 DML을 어디까지 적용하는지 컷오버 경계가 없다. HA에서는 OFF→ON이 금지되므로 실수 후 되돌리는 절차도 single 전환 외에는 제시되지 않는다.

### 왜 중요한가
노드마다 마지막으로 복제된 행의 시점이 다르면 OFF라는 같은 카탈로그 값이어도 데이터 내용은 예측할 수 없다. 단순 설정 실수가 서비스 중단과 전체 HA 재구성으로 이어질 수 있으므로 되돌림 비용을 제품 문서가 알려야 한다.

### 재현 또는 구체적 예제
`session_store REPLICATION=ON`에 1~100번 INSERT 로그가 쌓였고 replica는 80번까지 적용했다. source에서 OFF로 전환한 후 101번을 넣는다. replica가 81~100을 적용하는지 버리는지 불명확하다. 이후 ON으로 복귀하려면 어느 노드 데이터를 기준으로 동기화할지도 없다.

### 권고안
OFF DDL의 커밋 LSA를 경계로 이전 로그는 모두 적용하고 이후 로그는 생성하지 않는다는 식의 규칙을 정한다. 전환 전 경고·확인, 진행 상태 조회, HA 정지 후 재동기화하고 ON으로 복귀하는 공식 절차를 제공한다.

### 검증 방법
복제 지연 상태에서 ON→OFF를 실행하고 경계 전후 번호를 가진 DML을 발생시킨다. replica 최종 행 집합이 규칙과 일치하는지 확인하고, 문서 절차만으로 재동기화 후 ON 및 HA 재시작이 가능한지 시험한다.

## [PM-1Y-12] 복합 키와 키 값 변경 시 행 식별 규칙이 빠졌다

- 분류: 정확성
- 심각도: Critical
- 근거 위치: 원문 1절의 PK/NOT NULL UK 일반 규칙과 4-2절의 단일 컬럼 중심 예제
- 사실/추론 구분: 확인이 필요한 질문
- 영향 대상: 복합 키 사용자, 복제 정합성, 성능 담당자

### 문제
복합 PK/UK도 RK 후보인지 명시적 예와 규칙이 없고, RK 구성 값 자체를 UPDATE할 때 이전 값과 새 값 중 무엇으로 replica 행을 찾는지 없다. 문자열·collation·타입 변경에 따른 비교 의미도 빠졌다.

### 왜 중요한가
복합 키는 여러 열을 함께 보아야 유일하다. 새 값으로 먼저 찾으면 replica에는 아직 옛 값만 있어 행을 못 찾는다. 문자열 비교 규칙이 노드마다 다르거나 키가 넓으면 정확성과 성능 모두 영향을 받는다.

### 재현 또는 구체적 예제
`order_line(order_id INT, line_no INT, sku VARCHAR(40), PRIMARY KEY(order_id,line_no))`에서 `(100,1)`을 `(100,2)`로 UPDATE한다. replica에는 `(100,1)`만 있으므로 이전 키로 찾아 새 키로 바꿔야 한다. 동시에 `(100,2)`가 이미 있으면 source에서 제약 오류가 나야 하며 replica까지 부분 반영되면 안 된다.

### 권고안
복합 키 지원 여부, 최대 열 수·타입·크기, NULL/정렬 규칙을 명시한다. RK UPDATE 로그에는 before key로 대상을 찾고 after key와 나머지 값을 원자적으로 적용한다는 계약 또는 실제 설계를 설명한다.

### 검증 방법
2~3열 정수/문자열 복합 PK와 UK를 만들고 각 구성 열을 단독·동시 변경한다. 중복 충돌, 긴 문자열, collation이 있는 경우를 포함해 양 노드 결과와 apply 성능을 확인한다.

## [PM-1Y-13] FK 규칙이 연쇄 동작과 기존 관계의 상태 변경을 다루지 않는다

- 분류: 누락
- 심각도: Critical
- 근거 위치: 원문 5절의 복제 테이블이 참조하는 테이블도 ON이어야 한다는 규칙
- 사실/추론 구분: 확인된 사실
- 영향 대상: FK 사용자, 애플리케이션, 데이터 정합성

### 문제
새 FK 생성 예는 있으나 이미 FK로 연결된 부모를 ON→OFF로 변경할 수 있는지, `ON DELETE CASCADE`/`ON UPDATE CASCADE`가 어느 노드에서 실행되는지, OFF 자식→ON 부모 조합은 허용되는지 없다. “외래키를 포함하는 복제 테이블” 방향만 설명한다.

### 왜 중요한가
부모 DML이 복제되지 않는데 자식 DML만 복제되면 replica의 참조 무결성이 깨진다. 연쇄 삭제가 source에서 별도 자식 로그를 생성하는지 replica가 제약으로 다시 실행하는지에 따라 중복 삭제나 누락이 생길 수 있다.

### 재현 또는 구체적 예제
`customers`와 `orders REPLICATION=ON`이 FK `ON DELETE CASCADE`로 연결됐다고 하자. `ALTER TABLE customers REPLICATION=OFF` 후 고객을 삭제하면 source의 주문도 연쇄 삭제된다. replica에는 부모 삭제가 없는데 자식 삭제만 오는지조차 문서에서 알 수 없다. 기대 동작은 위험한 OFF 전환 거부 또는 명확한 로그 규칙이다.

### 권고안
부모/자식 ON·OFF 4가지 조합과 FK 생성·삭제·부모 상태 변경을 표로 정의한다. CASCADE, SET NULL, RESTRICT 각각의 복제 동작과 기존 FK 검사 시점을 명시하고 위험 상태로 만드는 ALTER를 원자적으로 거부한다.

### 검증 방법
네 조합에서 FK 추가와 부모/자식 ON→OFF를 실행하고 각 연쇄 옵션으로 UPDATE/DELETE한다. 기대 오류 코드, 양 노드 데이터, failover 후 제약 검사를 비교한다.

## [PM-1Y-14] OFF 테이블을 포함한 VIEW를 “제약 없음”이라 부르는 것은 사용자 결과 계약과 충돌한다

- 분류: 정확성
- 심각도: Major
- 근거 위치: 원문 6절의 failover 후 뷰 사용 제약 없음과 결과 불일치 면책
- 사실/추론 구분: 확인된 사실
- 영향 대상: 조회 사용자, 리포트·애플리케이션, 데이터 정합성

### 문제
VIEW DDL이 존재한다는 의미에서는 사용할 수 있지만, OFF 테이블 데이터가 없으면 결과가 달라진다. 이를 “제약이 없다”고 표현하면 기능 가용성과 결과 정확성을 혼동하게 한다. 경고, 의존성 조회, failover 전 차단 여부가 없다.

### 왜 중요한가
뷰는 여러 테이블을 하나의 결과처럼 보여 준다. 사용자는 SQL이 성공하면 데이터도 유효하다고 믿기 쉽다. 빈 결과는 오류보다 발견이 늦어 잘못된 보고서나 업무 결정을 만들 수 있다.

### 재현 또는 구체적 예제
`orders ON`과 `local_discount OFF`를 조인하는 `CREATE VIEW payable AS SELECT ...`를 만든다. source에서는 할인 적용 금액 9,000원이지만 failover 후 할인 행이 없어 10,000원이 되거나 INNER JOIN이면 주문 자체가 사라진다. SQL은 성공해도 의미상 잘못된 결과다.

### 권고안
“DDL은 복제되지만 결과 정합성은 보장하지 않는다”로 고쳐 쓴다. ON 업무 테이블의 VIEW가 OFF 테이블에 의존하면 생성 시 경고 또는 정책에 따라 거부하고, 의존 VIEW 목록을 조회하는 관리 기능과 failover 체크리스트를 제공한다.

### 검증 방법
INNER/LEFT JOIN, 집계, 중첩 VIEW에서 OFF 테이블을 참조한 뒤 failover한다. 경고와 의존성 조회가 정확한지, 문서에 제시한 source/replica 결과가 실제와 일치하는지 확인한다.

## [PM-1Y-15] HA 시작 전 검사의 원자성·비용·오류 출력 형식이 정해지지 않았다

- 분류: 운영성
- 심각도: Major
- 근거 위치: 원문 7절의 제약 검사와 “에러와 함께 파일 리스트” 출력
- 사실/추론 구분: 확인된 사실
- 영향 대상: 운영자, 자동화 도구, 대규모 스키마 사용자

### 문제
검사 중 다른 세션이 스키마를 바꾸면 일관된 한 시점의 결과인지, 수만 테이블에서 시간이 얼마나 드는지, “파일 리스트”가 실제로 테이블 목록인지 알 수 없다. 모든 위반을 한 번에 보여 주는지 첫 오류에서 중단하는지도 없다.

### 왜 중요한가
운영자는 시작 실패를 신속히 고쳐야 한다. 검사 직후 상태가 바뀔 수 있거나 오류가 한 건씩만 나오면 여러 번 재시작해야 한다. 자동화는 안정된 오류 코드와 구조화된 객체명이 없으면 원인을 판별할 수 없다.

### 재현 또는 구체적 예제
RK 없는 `stage_a`, `stage_b`와 OFF 부모를 참조하는 `orders`가 있다. `cubrid hb start`가 “ERROR, file list”만 출력하면 어떤 DB·스키마·테이블·제약을 고쳐야 하는지 모른다. 검사 도중 `stage_a`에 PK를 추가할 때 결과가 어느 시점 기준인지도 없다.

### 권고안
카탈로그의 일관된 snapshot 또는 DDL 차단 구간을 정의한다. 오류마다 DB/owner/table/constraint, 사유, 권장 SQL, 안정된 오류 코드를 출력하고 모든 위반을 모아 보여 준다. 별도 dry-run 명령과 대규모 스키마 성능 목표를 제공한다.

### 검증 방법
세 종류 위반을 동시에 만들고 사전 검사와 실제 시작을 실행한다. 목록이 누락 없이 동일한지, 동시 DDL 중 결과가 일관적인지 확인한다. 1만 테이블 환경에서 시간·메모리를 측정해 명시 목표를 만족하는지 본다.

## [PM-1Y-16] fail_count 억제만으로는 기존 불일치 탐지와 복구가 되지 않는다

- 분류: 누락
- 심각도: Critical
- 근거 위치: 원문 전체, 특히 4절과 7절에 apply 실패·불일치 복구 절차가 없음
- 사실/추론 구분: 확인된 사실
- 영향 대상: 운영자, 고객지원, 복제 정합성

### 문제
문제 배경의 핵심인 `fail_count`가 문서에 정의되지 않으며 증가 조건, 경보 기준, 초기화 조건, 테이블·LSA 추적 방법이 없다. 새 제약을 도입해도 이미 누락된 데이터가 자동으로 발견되거나 복구되지는 않는다.

### 왜 중요한가
오류 횟수가 더 늘지 않는 것과 데이터가 같은 것은 별개다. 과거 UPDATE 한 건이 빠졌다면 카운터가 안정돼도 failover 후 잘못된 잔액을 서비스한다. 운영자는 영향 범위를 찾고 안전하게 재동기화할 방법이 필요하다.

### 재현 또는 구체적 예제
source의 `account(id=10,balance=900)`과 replica의 같은 행 `balance=1000`이 이미 다르고 `fail_count=5`라고 하자. 새 버전 업그레이드 후 추가 오류가 없어도 값은 계속 다르다. 어떤 테이블/로그에서 다섯 번 실패했는지와 전체 재구축 없이 교정 가능한지 문서가 답하지 않는다.

### 권고안
`fail_count`의 범위·증가·초기화·노출 위치와 경보 기준을 명시한다. 업그레이드 전후 checksum/row comparison 절차, 불일치 테이블 격리, 재동기화, 검증 후 카운터 승인 초기화 절차를 제공한다. 성공 지표에 기존 불일치 탐지율과 복구 성공률을 포함한다.

### 검증 방법
의도적으로 UPDATE 누락, 대상 행 중복, DDL apply 실패를 주입한다. 카운터와 오류 로그가 원인을 연결하고, 문서 절차로 데이터 일치를 복원한 뒤 재검사와 카운터 처리가 정확한지 확인한다.

## [PM-1Y-17] unload/load의 구버전 기본 처리에 문서 내부 모순이 있다

- 분류: 호환성
- 심각도: Blocker
- 근거 위치: 원문 8절의 변수 없음=ON과 9절 요약 5의 옵션 없음=OFF
- 사실/추론 구분: 확인된 사실
- 영향 대상: 업그레이드 사용자, 백업·복원 담당자, 데이터 가용성

### 문제
8절은 복제 여부 변수가 없는 구버전 unload 파일을 load하면 모두 `REPLICATION=ON`이라고 한다. 9절은 정보를 포함하지 않는 테이블은 모두 복제 제외라고 한다. 같은 입력이 ON과 OFF라는 반대 결과를 가져 핵심 호환 동작을 결정할 수 없다.

### 왜 중요한가
ON이면 RK 없는 테이블 때문에 HA 시작이 실패할 수 있고, OFF이면 업무 데이터가 replica로 전달되지 않을 수 있다. 둘 중 어느 쪽도 조용히 선택해서는 안 되며 복원은 재해 상황에서 쓰이므로 예측 가능해야 한다.

### 재현 또는 구체적 예제
구버전에서 `legacy_event(message VARCHAR(100))`를 unload해 REPLICATION 필드가 없는 파일을 만든다. 새 버전 single에서 load한 뒤 8절대로면 ON이라 HA 시작이 실패하고, 9절대로면 OFF라 시작은 되지만 이벤트 DML이 복제되지 않는다.

### 권고안
하나의 기본 정책으로 통일하고 SUMMARY를 본문과 일치시킨다. 안전성을 위해 필드 없음은 경고/명시 옵션 요구 또는 사전 보고서를 권장한다. load 결과에 테이블별 ON/OFF, RK 후보 유무, HA 전환 가능 여부를 출력하고 사용자가 override할 방법을 둔다.

### 검증 방법
REPLICATION 필드가 없는 구버전 파일, ON, OFF가 명시된 새 파일을 각각 load한다. 문서 규칙대로 카탈로그 값이 정해지고 경고·요약이 출력되는지, unload→load 왕복 시 값이 보존되는지 확인한다.

## [PM-1Y-18] 혼합 버전 HA와 롤링 업그레이드 정책이 없다

- 분류: 호환성
- 심각도: Blocker
- 근거 위치: 원문 2절의 새 SQL·카탈로그 속성과 8절의 파일 호환성만 언급
- 사실/추론 구분: 확인이 필요한 질문
- 영향 대상: 업그레이드 운영자, 복제 프로토콜, 서비스 가용성

### 문제
새 버전은 `REPLICATION` 카탈로그와 RK 선택·DDL 규칙을 알지만 구버전 노드는 모를 수 있다. source와 replica를 한 번에 내리지 않는 롤링 업그레이드에서 새 DDL/로그를 구버전이 어떻게 처리하는지, 지원하는 버전 조합이 없다.

### 왜 중요한가
구버전 replica가 새 옵션을 무시하거나 DDL parse에 실패하면 스키마가 달라지고 apply가 멈춘다. 반대 방향에서는 새 노드가 구버전 로그에 RK 메타데이터가 없어서 행을 찾지 못할 수 있다. 이는 무중단 업그레이드 가능 여부를 결정한다.

### 재현 또는 구체적 예제
구버전 replica를 둔 채 source만 새 버전으로 올리고 `CREATE TABLE cache(id INT) REPLICATION=OFF;`를 실행한다. 구버전이 문법 오류를 내는지 옵션을 무시해 ON처럼 복제하는지 불명확하다. 그 상태에서 failover하면 결과는 더 예측하기 어렵다.

### 권고안
지원 버전 행렬과 업그레이드 순서, 기능 활성화 시점을 명시한다. 혼합 버전에서는 새 DDL을 차단하거나 capability negotiation으로 안전하게 처리한다. downgrade 가능 조건과 새 카탈로그/로그를 사용한 뒤 되돌릴 수 없는 시점도 선언한다.

### 검증 방법
old→new와 new→old 방향으로 source/replica 조합을 구성해 CREATE/ALTER ON/OFF, RK 교체, DML, failover를 시험한다. 지원하지 않는 조합은 시작 또는 SQL 단계에서 명확히 차단되고 데이터가 부분 적용되지 않는지 확인한다.

## [PM-1Y-19] 예제 SQL의 오탈자와 실행 오류가 초보 학습을 방해한다

- 분류: 문서 품질
- 심각도: Major
- 근거 위치: 원문 2-1절 예시 2, 4-2절 예시 13, 5-1절 제목과 5-2절 예시
- 사실/추론 구분: 확인된 사실
- 영향 대상: 초보 사용자, QA, 기술 문서 담당자

### 문제
`CRATE TABLE` 오탈자, 마지막 컬럼 뒤 쉼표, 불완전한 `DROP CONSTRAINT ...`, 제약 이름 없는 ADD, `DROP FOREIGN KEY (name)` 문법 등 실행 가능성이 의심되는 예제가 다수다. 예시 번호 14 다음에 15가 나오지만 원문 구조상 설명 연결도 약하고, 단순 `ERROR`만 있어 학습할 수 없다.

### 왜 중요한가
1년차 사용자는 예제를 그대로 복사해 기능을 배운다. 문법 오류로 실패하면 제품 기능이 실패한 것인지 문서가 틀린 것인지 구분하지 못한다. 오류 이유와 수정법이 없으면 새 안전 기능의 채택이 늦어진다.

### 재현 또는 구체적 예제
예시 2의 `CREATE TABLE repl_table_without_rk(a INT,);`는 마지막 쉼표 때문에 RK 정책을 검사하기 전에 SQL parser 오류가 날 수 있다. 사용자는 기대한 “single에서는 OK, HA에서는 ERROR”를 관찰하지 못한다. `CRATE TABLE` 제목도 검색과 이해를 방해한다.

### 권고안
모든 예제를 깨끗한 DB에서 그대로 실행 가능한 setup–SQL–expected output 묶음으로 다시 쓴다. 실제 제약 이름과 정확한 CUBRID 문법, 오류 코드·메시지를 넣고 `CRATE`를 `CREATE`로 고친다. 자동 문서 테스트에 예제 SQL을 포함한다.

### 검증 방법
문서에서 모든 코드 블록을 추출해 single/SA/HA 지정 환경에서 자동 실행한다. 예상 성공·실패와 실제 오류 코드가 일치해야 문서 빌드를 통과하도록 한다.

## [PM-1Y-20] 기능 수용 기준과 처음부터 끝까지 이어지는 사용자 예제가 없다

- 분류: 문서 품질
- 심각도: Major
- 근거 위치: 원문 1~9절의 개별 규칙·단편 예제와 9절 SUMMARY
- 사실/추론 구분: 확인된 사실
- 영향 대상: PM, QA, 신규 사용자, 고객지원

### 문제
문서는 개별 SQL 성공/실패를 나열하지만 기존 위험 테이블을 발견하고, RK를 안전하게 교체하고, HA를 시작하고, failover 뒤 검증하는 전체 흐름이 없다. 성능·정합성·오류 감소에 대한 측정 가능한 출시 기준도 없다.

### 왜 중요한가
기능은 문법 추가만으로 완료되지 않는다. 사용자는 자신의 기존 테이블을 어떻게 분류하고 언제 서비스를 멈추며 어떤 결과를 확인해야 하는지 알아야 한다. QA는 수용 기준이 없으면 “구현 완료”를 객관적으로 판정할 수 없다.

### 재현 또는 구체적 예제
초보 운영자가 `customer(id PK, email UK)`와 PK 없는 `stage`를 가진 single DB를 HA로 전환한다고 하자. 필요한 흐름은 사전 검사 → `stage OFF` 결정과 경고 → customer 실제 RK 조회 → HA 시작 → source UPDATE → 동기화 대기 → switchover → 양 노드 checksum 비교이다. 현재는 이 흐름이 여러 절에 흩어져 있고 마지막 검증 예가 없다.

### 권고안
“기존 single DB를 안전하게 HA로 전환” 튜토리얼을 추가해 명령, 초기 상태, 기대 출력, 실패 시 되돌리기를 단계별로 설명한다. 출시 수용 기준으로 허용된 모든 RK 전이에서 불일치 0건, 관련 `fail_count` 증가 0회, 사전 검사의 위반 탐지 100%, 대표 부하에서 합의한 성능 한도를 정한다.

### 검증 방법
제품을 처음 보는 테스터가 튜토리얼만 사용해 예제 DB를 HA로 전환하고 계획된 switchover까지 수행하게 한다. 별도 설명 없이 성공하는지, 각 수용 지표를 자동 테스트 결과로 증명할 수 있는지 확인한다.

## [PM-1Y-21] 복제 정책을 변경할 권한과 감사 책임이 정의되지 않았다

- 분류: 보안
- 심각도: Critical
- 근거 위치: 원문 2-1절과 2-2절은 사용자가 `REPLICATION`을 지정·변경할 수 있다고만 한다.
- 사실/추론 구분: 확인된 사실
- 영향 대상: PM, 보안 관리자, DBA, 감사 조직

### 문제
누가 ON→OFF를 실행할 수 있는지, 일반 `ALTER` 권한만 있으면 되는지, 변경 이유와 실행자를 어디에 기록하는지 없다. OFF는 데이터 보호 수준을 낮추므로 일반 스키마 변경보다 강한 통제가 필요할 수 있다.

### 왜 중요한가
초보 사용자가 성능 문제를 피하려고 업무 테이블을 OFF로 바꾸면 failover 후 데이터가 없다. 실행자가 남지 않으면 사고 원인과 책임 범위를 확인하기 어렵다.

### 재현 또는 구체적 예제
`app_owner`에게 orders의 일반 ALTER 권한만 준 상태에서 다음을 실행한다.

```sql
ALTER TABLE orders REPLICATION=OFF;
```

성공해야 하는지 별도 관리자 권한이 필요한지 문서에 없다.

### 권고안
CREATE 시 지정, ON→OFF, OFF→ON, RK 교체별 최소 권한을 정한다. 실행자·시각·이전/새 값·승인 사유를 감사 로그에 남기고 중요 테이블에는 별도 권한 또는 정책 승인을 요구한다.

### 검증 방법
DBA, owner, 일반 DML 사용자 계정으로 각 변경을 실행한다. 권한 표와 결과가 같고 성공·실패 시도 모두 감사 기록에서 추적되는지 확인한다.

## [PM-1Y-22] 파티션 테이블의 복제 정책과 RK 범위가 정의되지 않았다

- 분류: 누락
- 심각도: Critical
- 근거 위치: 원문 1~9절은 일반 테이블만 설명하며 2-3절 `db_class` 예제에는 `partitioned` 정보가 보인다.
- 사실/추론 구분: 확인이 필요한 질문
- 영향 대상: 파티션 기능 사용자, DBA, 복제 정합성

### 문제
CUBRID에서 이 기능과 함께 사용할 수 있는 파티션 테이블의 정확한 지원 범위는 확인이 필요하다. 지원한다면 부모와 파티션이 ON/OFF를 각각 가질 수 있는지, RK가 전체 테이블에서 유일해야 하는지, 파티션 추가·분할·교환 시 규칙이 없다.

### 왜 중요한가
한 논리 테이블의 일부 파티션만 복제되면 기간별 데이터가 빠질 수 있다. 파티션 안에서만 유일한 키는 전체 행을 식별하지 못할 가능성이 있다.

### 재현 또는 구체적 예제
지원 문법은 공식 참조로 확인해야 하지만, 개념적으로 `sales`를 월별 파티션하고 `(sale_id)` UK를 둔 뒤 새 파티션을 추가한다고 하자.

```sql
SELECT class_name, partitioned, replication
FROM db_class WHERE class_name='sales';
```

부모와 자식의 정책 및 실제 RK를 어디서 보는지 불명확하다.

### 권고안
파티션 기능 지원 여부를 명시하고 지원 시 정책 상속, 전체/지역 유일성, ADD/DROP/SPLIT/REORGANIZE별 동작을 표로 제공한다. 미지원이면 DDL 단계에서 명확한 오류를 낸다.

### 검증 방법
공식 지원 파티션 DDL마다 ON/OFF와 PK/UK 조합을 시험한다. 파티션 이동 전후 양 노드의 전체 행 집합과 실제 RK가 같고 미지원 조합은 사전 거부되는지 확인한다.

## [PM-1Y-23] 한 트랜잭션에서 ON과 OFF 테이블을 함께 바꾸면 원자성이 달라진다

- 분류: 정확성
- 심각도: Critical
- 근거 위치: 원문 1절과 4절은 OFF 테이블 DML만 복제하지 않는다고 한다.
- 사실/추론 구분: 문서에서 도출한 추론
- 영향 대상: 애플리케이션, 사용자, failover 정합성

### 문제
하나의 source 트랜잭션이 ON과 OFF 테이블을 함께 변경할 때 standby에는 ON 변경만 보일 수 있다. source에서 “둘 다 성공 또는 둘 다 실패”였던 업무 단위가 failover 후 절반만 남는다.

### 왜 중요한가
트랜잭션은 여러 변경을 한 단위로 묶는다. 복제 정책이 이 단위를 나누면 주문과 그 상태 기록처럼 함께 있어야 하는 데이터가 갈라진다.

### 재현 또는 구체적 예제

```sql
BEGIN;
INSERT INTO orders(id,status) VALUES (100,'PAID');       -- ON
INSERT INTO local_payment_note(order_id,note) VALUES (100,'approved'); -- OFF
COMMIT;
```

failover 후 첫 행만 존재하는 것이 허용되는지, 경고가 있는지 없다.

### 권고안
혼합 ON/OFF 트랜잭션의 정확한 결과를 명시한다. 중요 데이터에서는 이를 금지하는 strict 모드나 commit 경고를 제공하고, OFF 사용 가이드에 교차 테이블 불변식을 두지 말라고 설명한다.

### 검증 방법
성공·rollback·deadlock 트랜잭션에서 ON/OFF 두 테이블을 함께 변경한 뒤 failover한다. 문서의 행 집합과 일치하고 strict 정책이 위험한 commit을 차단하는지 확인한다.

## [PM-1Y-24] trigger와 서버 내부에서 생성되는 DML의 복제 정책이 없다

- 분류: 누락
- 심각도: Critical
- 근거 위치: 원문 4절은 테이블의 DML 복제 여부만 말하고 trigger 또는 자동 생성 DML은 다루지 않는다.
- 사실/추론 구분: 확인이 필요한 질문
- 영향 대상: trigger 사용자, 복제 엔진, 데이터 정합성

### 문제
CUBRID에서 지원하는 trigger의 실제 동작은 공식 확인이 필요하다. ON 테이블 변경이 OFF 테이블 trigger DML을 만들거나 그 반대인 경우, 내부 변경을 source 결과로 기록하는지 standby에서 trigger를 다시 실행하는지 없다.

### 왜 중요한가
source 결과와 trigger 재실행을 둘 다 적용하면 중복되고, 둘 다 제외하면 누락된다. ON/OFF 경계를 넘으면 어느 정책을 우선할지도 결정해야 한다.

### 재현 또는 구체적 예제
지원 문법을 확인한 trigger가 `orders` INSERT 때 `local_audit OFF`에 행을 추가한다고 하자.

```sql
INSERT INTO orders(id,status) VALUES (101,'NEW');
SELECT COUNT(*) FROM local_audit WHERE order_id=101;
```

failover 후 audit 행의 기대 유무가 없다.

### 권고안
trigger, 자동 증가, default expression, cascade처럼 서버가 생성한 변경의 로깅 위치와 중복 실행 방지 규칙을 명시한다. 위험한 ON/OFF 참조는 생성 시 경고 또는 거부한다.

### 검증 방법
ON→OFF, OFF→ON, ON→ON trigger 조합에서 INSERT/UPDATE/DELETE를 실행한다. trigger 실행 횟수와 양 노드 행이 규칙에 맞는지 확인한다.

## [PM-1Y-25] TRUNCATE·대량 적재·테이블 복사 명령의 DDL/DML 분류가 없다

- 분류: 모호성
- 심각도: Critical
- 근거 위치: 원문 1절과 4절은 “모든 DDL 복제, ON 데이터만 복제”라고 하지만 경계 명령을 열거하지 않는다.
- 사실/추론 구분: 확인이 필요한 질문
- 영향 대상: 배치 사용자, DBA, 데이터 정합성

### 문제
`TRUNCATE`, `INSERT ... SELECT`, `CREATE TABLE ... AS SELECT`처럼 구조와 데이터를 함께 다루거나 대량 변경하는 명령이 OFF에서 어떻게 처리되는지 없다. 실제 CUBRID 지원 문법은 확인이 필요하다.

### 왜 중요한가
TRUNCATE가 DDL로 복제되면 OFF 테이블도 standby 로컬 데이터가 지워질 수 있다. 반대로 DML 제외라면 남는다. 사용자가 “OFF 데이터는 노드별 독립”이라는 기대를 정할 수 없다.

### 재현 또는 구체적 예제

```sql
TRUNCATE TABLE local_cache;
INSERT INTO archive SELECT * FROM orders;
```

각 대상이 OFF일 때 standby에서 구조·데이터가 어떻게 변하는지 불명확하다.

### 권고안
지원하는 SQL을 schema-only, replicated data, local data로 분류한 명령 표를 제공한다. 혼합 명령은 source/standby 결과와 경고를 예제로 보여 준다.

### 검증 방법
ON/OFF 각각에 bulk insert, truncate, copy/CTAS 지원 명령을 실행한다. 양 노드 행 수·스키마와 로그 생성량이 표와 일치하는지 확인한다.

## [PM-1Y-26] 물리 백업과 시점 복구에서 RK 정의를 보존하는 계약이 없다

- 분류: 호환성
- 심각도: Critical
- 근거 위치: 원문 8절은 `unloaddb`/`loaddb`만 다루며 일반 백업과 PITR은 없다.
- 사실/추론 구분: 확인이 필요한 질문
- 영향 대상: 백업 사용자, 재해 복구, 감사

### 문제
백업 시점과 RK 변경 로그 시점이 어긋날 때 어떤 RK 정의로 후속 로그를 적용하는지 없다. 선택된 RK가 후보로부터 다시 계산되는지도 알 수 없다.

### 왜 중요한가
PITR은 백업 뒤의 로그를 시간 순서대로 재생한다. 복원된 카탈로그에 해당 로그의 RK 정의가 없으면 복구가 완료되지 않거나 잘못된 행을 바꿀 수 있다.

### 재현 또는 구체적 예제

```sql
-- 10:00 backup
-- 10:05 RK 교체
ALTER TABLE customer DROP PRIMARY KEY,
  ADD CONSTRAINT uk_customer_email UNIQUE(email);
-- 10:10 UPDATE 후 10:11 시점으로 복구
```

10:00~10:11의 두 RK 세대를 어떻게 재생하는지 없다.

### 권고안
지원 backup/PITR 범위, 선택 RK와 버전의 보존, DDL 로그 재생 순서, 복구 후 HA 재가입 절차를 규정한다. 지원하지 않는 복구 경로는 명시적으로 차단한다.

### 검증 방법
RK 교체 직전·도중·직후 백업을 만들고 여러 시점으로 복구한다. 선택 RK, 데이터 checksum, 이후 HA 연결이 원본과 일치하는지 확인한다.

## [PM-1Y-27] loaddb 중간 실패의 원자성과 재시도 절차가 없다

- 분류: 운영성
- 심각도: Major
- 근거 위치: 원문 8절은 load 결과만 설명하고 부분 실패·재시작은 다루지 않는다.
- 사실/추론 구분: 확인된 사실
- 영향 대상: 마이그레이션 사용자, DBA, 복구 시간

### 문제
수백 테이블 중 일부를 생성한 뒤 RK 오류나 디스크 부족으로 load가 멈추면 생성된 테이블을 유지하는지 모두 되돌리는지 없다. 같은 파일 재실행 시 중복 객체 처리도 알 수 없다.

### 왜 중요한가
대용량 load 실패는 흔한 운영 사건이다. 처음부터 다시 해야 하는지 이어서 할 수 있는지에 따라 복구 시간이 크게 달라진다.

### 재현 또는 구체적 예제
첫 테이블 `a`는 ON+PK, 둘째 `b`는 ON이지만 키가 없고, 셋째 `c`는 OFF인 dump를 HA에서 load한다고 하자.

```sql
SELECT class_name, replication FROM db_class
WHERE class_name IN ('a','b','c');
```

`b` 실패 뒤 `a`와 `c`의 존재 여부가 정의되지 않았다.

### 권고안
load의 transaction 단위, stop/continue 정책, checkpoint, cleanup, idempotent resume 방법을 명시한다. 시작 전 전체 스키마 dry-run으로 RK/FK/기본값 위반을 먼저 찾는다.

### 검증 방법
객체 생성·데이터 적재·index 생성 단계마다 실패를 주입한다. 재실행만으로 중복·누락 없이 완료되거나 문서의 rollback 절차로 깨끗한 상태가 되는지 확인한다.

## [PM-1Y-28] RK 인덱스 구축 중 자원 고갈의 사용자 결과가 없다

- 분류: 성능
- 심각도: Critical
- 근거 위치: 원문 4-2절은 후보 추가와 키 교체를 허용하지만 대형 테이블 비용과 실패 경로는 없다.
- 사실/추론 구분: 확인이 필요한 질문
- 영향 대상: 운영자, 애플리케이션 가용성, 복제 정합성

### 문제
새 UK/PK를 만들 때 디스크·메모리·임시 공간이 부족하거나 시간이 오래 걸리는 경우 진행률, 취소, rollback, DML 영향이 없다.

### 왜 중요한가
짧은 ALTER 문도 10억 행의 유일성을 검사하고 index를 만들면 장시간 작업이다. 디스크 full이 DB 전체 장애로 번질 수 있다.

### 재현 또는 구체적 예제

```sql
ALTER TABLE billion_event
  ADD CONSTRAINT uk_event_uuid UNIQUE(event_uuid);
```

90% 구축 후 임시 공간 부족이 발생하면 기존 RK와 서비스 상태가 보존돼야 한다.

### 권고안
사전 용량 추정, 진행률, 잠금 구간, 취소 가능 시점, 실패 cleanup, 원래 RK 보존을 제품 계약으로 둔다. 대표 크기별 성능 목표를 공개한다.

### 검증 방법
작은 디스크 quota와 동시 부하에서 key build를 실행한다. 실패 후 임시 객체가 정리되고 기존 RK·DML·복제가 정상이며 경고가 충분한지 확인한다.

## [PM-1Y-29] 장기 트랜잭션과 느린 replica가 구 RK 보관 기간을 무한히 늘릴 수 있다

- 분류: 운영성
- 심각도: Critical
- 근거 위치: 원문 4절은 운영 중 RK 변경을 허용하지만 장기 transaction, apply lag, 로그 보관은 없다.
- 사실/추론 구분: 문서에서 도출한 추론
- 영향 대상: 운영자, 저장 공간, 복제 정합성

### 문제
RK 변경 전 시작한 장기 트랜잭션이나 오랫동안 중지된 replica가 구 RK 로그를 나중에 적용해야 할 수 있다. 구 정의와 로그를 언제까지 보관하며 한계를 넘으면 어떻게 되는지 없다.

### 왜 중요한가
안전을 위해 무기한 보관하면 디스크가 차고, 빨리 삭제하면 지연 replica가 복구 불가능하다. 제품이 어느 쪽을 선택하는지 사용자가 알아야 한다.

### 재현 또는 구체적 예제

```sql
BEGIN;
UPDATE account SET balance=80 WHERE id=10;
-- 6시간 뒤 commit, 그 사이 RK를 email로 교체
COMMIT;
```

동시에 DR replica가 하루 정지됐다고 하면 필요한 로그·RK 세대 보관 조건이 없다.

### 권고안
최대 지원 lag, log/RK epoch 보존량, 경고 임계값, 지연 replica 재-seed 조건을 정의한다. RK DDL 전에 장기 transaction과 lag를 사전 검사한다.

### 검증 방법
장기 transaction과 replica 정지를 만들고 RK를 교체한다. 임계값 전에는 정상 재생되고 초과 시 조용한 누락이 아니라 명확한 차단·재가입 안내가 발생하는지 확인한다.

## [PM-1Y-30] 정상 복제 여부를 보여 주는 성공 지표가 없다

- 분류: 운영성
- 심각도: Major
- 근거 위치: 원문 2-3절은 테이블 ON/OFF 조회만, 전체는 실패 예시만 제공한다.
- 사실/추론 구분: 확인된 사실
- 영향 대상: 운영자, PM, 고객지원

### 문제
ON이고 `fail_count`가 늘지 않는 것만으로 최근 로그가 전달·적용되는지 알 수 없다. 테이블별 마지막 적용 시각, lag, RK 세대 일치, OFF 전환 경계 같은 정상 상태 관측 항목이 없다.

### 왜 중요한가
오류가 없다는 것과 복제가 진행된다는 것은 다르다. apply 프로세스가 멈춰도 새 실패가 없으므로 카운터가 그대로일 수 있다.

### 재현 또는 구체적 예제

```sql
INSERT INTO health_probe(id,created_at) VALUES (1001,CURRENT_DATETIME);
```

standby에서 언제 확인되어야 하는지, 지연이 얼마면 위험한지 기준이 없다.

### 권고안
노드·DB·테이블별 send/apply LSA, 초/byte lag, 마지막 성공, 현재 RK epoch, 실패 상태를 제공한다. 출시 성공 지표와 기본 경보 임계값을 정한다.

### 검증 방법
정상, apply 중지, network 단절, 지연 회복을 차례로 만든다. 지표와 경보가 실제 상태를 구분하고 회복 시 정상으로 돌아오는지 확인한다.

## [PM-1Y-31] 진단 정보에 개인정보 RK가 노출될 수 있다

- 분류: 보안
- 심각도: Major
- 근거 위치: 원문 7절은 오류와 목록 출력만 요구하고 apply 오류 진단 내용과 접근 권한은 없다.
- 사실/추론 구분: 확인이 필요한 질문
- 영향 대상: 사용자, 보안·개인정보 담당자, 지원 조직

### 문제
email, 전화번호, 주민 식별값 같은 UK가 RK가 될 수 있다. 행 탐색 실패 로그에 RK 원문을 기록하면 로그 수집·지원 티켓을 통해 개인정보가 퍼질 수 있다.

### 왜 중요한가
진단에는 실패 행을 구분할 정보가 필요하지만 운영 로그는 DB보다 더 많은 사람이 오래 보관할 수 있다. 숨기기만 하면 복구가 어려워 균형이 필요하다.

### 재현 또는 구체적 예제

```sql
UPDATE member SET status='ACTIVE' WHERE email='person@example.com';
```

이 변경의 apply 실패 메시지에 email 원문이 포함되는지 알 수 없다.

### 권고안
기본 로그에는 제약 이름과 salted/hash 식별자를 쓰고, 권한 있는 진단 명령만 제한적으로 원문을 보이게 한다. 보존 기간·마스킹·감사 정책을 문서화한다.

### 검증 방법
민감 UK와 일반 정수 PK 실패를 만들고 일반 로그, 관리자 화면, 지원 bundle을 검사한다. 최소 정보로 사건을 연결하면서 원문이 불필요하게 노출되지 않는지 확인한다.

## [PM-1Y-32] 기능 활성화와 긴급 비활성화 정책이 없다

- 분류: 호환성
- 심각도: Major
- 근거 위치: 원문 1~9절은 기능 도입 후 동작만 설명하고 기능 flag, edition, 단계적 공개, backout은 없다.
- 사실/추론 구분: 확인이 필요한 질문
- 영향 대상: 릴리스 관리자, 기존 고객, 지원 조직

### 문제
새 parser/catalog/log 동작을 업그레이드 즉시 강제하는지, 기능을 DB별로 활성화하는지, 문제가 생겼을 때 되돌릴 수 있는지 없다. 라이선스·edition별 차이도 확인되지 않았다.

### 왜 중요한가
새 기본값이 HA 시작과 데이터 복제에 영향을 주므로 전체 고객에게 한 번에 활성화하면 위험하다. 한번 새 로그를 쓰면 구버전으로 돌아가지 못할 수도 있다.

### 재현 또는 구체적 예제

```sql
CREATE TABLE cache (id INT PRIMARY KEY) REPLICATION=OFF;
```

이 DDL을 한 번 실행한 뒤 기능 flag를 끄거나 이전 버전으로 되돌릴 수 있는지 알 수 없다.

### 권고안
기능 탐지, opt-in/기본 활성화 일정, 새 DDL 허용 시점, 되돌릴 수 없는 경계, emergency disable의 데이터 의미를 release plan에 넣는다. edition 차이가 있으면 지원표를 제공한다.

### 검증 방법
비활성→활성→새 DDL 사용→비활성/rollback 각 단계를 시험한다. 지원하지 않는 되돌림은 실행 전에 차단되고 기존 데이터가 부분 변환되지 않는지 확인한다.

## [PM-1Y-33] HA 시작 실패의 범위가 DB·노드·클러스터 중 어디인지 없다

- 분류: 모호성
- 심각도: Critical
- 근거 위치: 원문 1절과 7절은 위반 시 “HA 모드를 실행할 수 없다”고만 한다.
- 사실/추론 구분: 확인이 필요한 질문
- 영향 대상: 다중 DB 운영자, 서비스 가용성, 지원 조직

### 문제
한 DB의 무키 ON 테이블이 같은 서버의 다른 DB, 한 노드, 전체 HA 그룹까지 막는지 실패 범위가 없다. 일부 DB만 제외하고 시작할 수 있는지도 알 수 없다.

### 왜 중요한가
작은 개발 DB 하나의 문제로 무관한 운영 서비스까지 시작되지 않으면 장애 범위가 예상보다 커진다. PM은 의도한 fail-closed 범위를 결정해야 한다.

### 재현 또는 구체적 예제
같은 HA 운영 단위에 `prod`와 `sandbox`가 있고 sandbox에 다음 테이블만 있다고 하자.

```sql
CREATE TABLE scratch (v INT) REPLICATION=ON;
```

`prod`까지 시작이 막히는지 문서에서 답할 수 없다.

### 권고안
검사·차단 단위를 database/node/HA group으로 명시하고 부분 시작의 지원 여부와 위험을 정한다. 오류에는 영향을 받은 서비스 범위를 표시한다.

### 검증 방법
여러 DB 중 하나에만 RK/FK 위반을 만들고 시작한다. 차단 범위, 정상 DB 가용성, 오류 목록이 명세와 일치하는지 확인한다.

## [PM-1Y-34] 테이블 복제·이름 변경 시 REPLICATION과 RK의 상속 규칙이 없다

- 분류: 누락
- 심각도: Major
- 근거 위치: 원문 2절은 기본 CREATE와 ALTER만 설명하고 LIKE/복사/rename 계열 생성 경로는 없다.
- 사실/추론 구분: 확인이 필요한 질문
- 영향 대상: 개발자, 마이그레이션 도구, 데이터 정합성

### 문제
CUBRID가 지원하는 정확한 테이블 복사 문법은 확인이 필요하다. 기존 OFF 테이블을 LIKE/복사해 만들면 OFF를 상속하는지 기본 ON인지, rename 시 RK logical identity가 유지되는지 없다.

### 왜 중요한가
같은 구조를 복사하는 도구는 새 옵션을 명시하지 않을 수 있다. 암묵적 ON으로 바뀌면 HA 시작이 실패하고, 암묵적 OFF면 데이터가 보호되지 않는다.

### 재현 또는 구체적 예제
지원되는 복사 문법으로 `local_cache OFF`와 같은 새 테이블 `local_cache_2`를 만든다고 하자.

```sql
ALTER TABLE local_cache RENAME TO local_cache_old;
SHOW CREATE TABLE local_cache_old;
```

정책과 선택 RK identity의 유지 여부가 불명확하다.

### 권고안
CREATE LIKE/AS, clone, rename, schema 이동 등 실제 지원 경로별 정책 상속과 RK identity 규칙을 표로 정한다. 모호한 복사에는 명시 옵션을 요구한다.

### 검증 방법
지원되는 각 복제·rename 경로를 ON/OFF 및 복수 UK 테이블에 실행한다. 새/이름 변경 객체의 정책, RK, DDL 복제가 문서와 같은지 확인한다.

## [PM-1Y-35] replica의 OFF 테이블 로컬 쓰기와 향후 재가입 충돌이 정의되지 않았다

- 분류: 정확성
- 심각도: Critical
- 근거 위치: 원문 1절·4절은 OFF 데이터가 복제되지 않는다고 하지만 각 노드에서의 쓰기 허용과 데이터 소유권은 없다.
- 사실/추론 구분: 확인이 필요한 질문
- 영향 대상: 애플리케이션, failover·failback, 데이터 정합성

### 문제
standby에서 OFF 테이블을 직접 수정할 수 있는지, failover 후 각 노드에서 독립적으로 생긴 같은 키 데이터를 어떻게 처리할지 없다. OFF→ON 복귀 때 유일성 충돌도 생길 수 있다.

### 왜 중요한가
노드 A와 B가 같은 PK에 다른 값을 가진 채 역할을 바꾸면 조회 결과가 역할에 따라 바뀐다. 자동 병합은 어느 값이 맞는지 결정할 수 없다.

### 재현 또는 구체적 예제

```sql
-- node A local_cache
INSERT INTO local_cache VALUES (1,'A');
-- node B local_cache
INSERT INTO local_cache VALUES (1,'B');
```

failover/failback 또는 재동기화 시 `id=1`의 권위 값이 없다.

### 권고안
OFF를 node-local로 정의하고 standby 직접 쓰기 허용 여부, 승격 시 초기화/보존, 재가입 시 폐기 정책을 정한다. OFF→ON 전에는 권위 snapshot을 선택하고 대상 데이터를 재생성하도록 한다.

### 검증 방법
양 노드 OFF 테이블에 충돌 값을 만든 뒤 switchover·failback·ON 복귀 절차를 수행한다. 조용한 병합 없이 문서가 정한 데이터 수명 주기로 처리되는지 확인한다.

# 추가 조사 종료 기록

- 추가 조사 목표: 최대 30개
- 실제 추가 항목 수: 15개
- 최종 리뷰 항목 수: 35개
- 30개를 채우지 않은 경우의 사유: 가치 있는 독립 쟁점을 더 찾지 못했으며, 기존 항목의 반복이나 근거 없는 추측으로 수량을 채우지 않음
- 추가 조사에서 확인하지 못한 영역: CUBRID의 파티션·trigger·테이블 복사 문법별 실제 지원 범위, 물리 백업/PITR의 현행 동작, edition·라이선스별 기능 차이, standby에서 OFF 테이블에 직접 쓰기 가능한지 여부
