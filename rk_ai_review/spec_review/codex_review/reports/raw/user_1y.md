## [USER-1Y-01] 새 RK 규칙이 원래 문제를 어떻게 막는지 설명이 없다

- 분류: 컨셉
- 심각도: Major
- 근거 위치: 원문 1절의 HA에서 RK 필수 규칙과 PK/UK 자동 선택
- 사실/추론 구분: 확인된 사실 — RK를 요구하는 규칙은 있지만 PK 변경이 누락과 오류를 만드는 과정은 설명되지 않는다
- 영향 대상: 처음 사용하는 사용자, 데이터 정합성, 기술 지원

### 문제
문서는 “RK가 없으면 HA를 실행할 수 없다”고 바로 규칙을 제시한다. 그러나 RK가 왜 필요한지, PK를 바꾸면 기존 복제에서 왜 행을 못 찾는지 단계별 설명이 없다. 사용자는 제한이 늘어난 이유를 이해하지 못하고 단지 오류를 피하려고 OFF를 선택할 수 있다.

### 왜 중요한가
RK는 replica에서 변경할 한 행을 찾기 위한 주소다. 주소가 사라지거나 갑자기 다른 컬럼으로 바뀌면 `UPDATE`를 어느 행에 적용할지 알 수 없다. 이때 변경이 누락되어 두 노드의 값이 달라질 수 있다는 인과관계를 알아야 사용자가 키 변경을 신중하게 계획한다.

### 재현 또는 구체적 예제

```sql
CREATE TABLE account (
  id INT PRIMARY KEY,
  name VARCHAR(50)
) REPLICATION = ON;
INSERT INTO account VALUES (1, 'Kim');
UPDATE account SET name = 'Lee' WHERE id = 1;
```

처음에는 `id=1`이 양 노드에서 같은 행을 찾는 주소다. UPDATE 로그가 이동하는 동안 PK를 없애면 replica가 id를 주소로 계속 사용할 수 있는지 불분명해진다. 기대 결과는 문서가 이 흐름을 그림이나 순서로 먼저 설명하는 것이다.

### 권고안
1절 앞에 “source의 DML → 로그에 RK 기록 → replica에서 RK로 행 검색 → 변경 적용” 네 단계를 추가한다. PK 변경 전후 어떤 오류와 불일치가 발생했는지 작은 표로 보여 주고, 이번 규칙이 막는 문제와 막지 못하는 문제를 구분한다.

### 검증 방법
HA를 처음 배우는 사용자 5명에게 설명을 읽힌 뒤 “RK가 왜 필요한가”, “PK를 삭제하면 왜 위험한가”, “OFF가 해결책인가”를 질문한다. 세 질문에 SQL 예제를 들어 정확히 답할 수 있어야 한다.

## [USER-1Y-02] MySQL·PostgreSQL 개념과 실제 CUBRID 동작의 경계가 보이지 않는다

- 분류: 컨셉
- 심각도: Major
- 근거 위치: 원문 1절의 CUBRID RK 선택 규칙; 대안이나 참고한 개념의 범위는 없음
- 사실/추론 구분: 확인이 필요한 질문 — 다른 DB의 어떤 개념을 채택했고 어떤 동작은 채택하지 않았는지 원문에서 확인할 수 없다
- 영향 대상: 다른 DB 경험이 있는 사용자, 마이그레이션 사용자, 교육 담당자

### 문제
다른 DB를 사용해 본 사람은 PK가 없으면 모든 컬럼을 사용하거나 사용자가 replica identity를 고르는 동작을 기대할 수 있다. 원문은 CUBRID가 PK 또는 NOT NULL UK를 자동 선택한다고만 하므로, 기존 지식을 어디까지 버려야 하는지 설명하지 않는다.

### 왜 중요한가
비슷한 용어가 있어도 제품마다 지원 SQL과 실패 조건은 다를 수 있다. 사용자가 PostgreSQL과 같다고 가정해 RK를 직접 지정하려 하거나, MySQL처럼 키 없는 테이블도 ON으로 복제될 것이라고 생각하면 배포가 실패한다.

### 재현 또는 구체적 예제

```sql
CREATE TABLE log_entry (
  created_at DATETIME,
  message VARCHAR(500)
) REPLICATION = ON;
```

모든 컬럼 비교 방식을 기대한 사용자는 HA에서도 성공한다고 생각할 수 있다. 원문 규칙으로는 PK/NOT NULL UK가 없어 거부되어야 한다. 기대 결과는 CUBRID에서는 왜 이 SQL이 실패하고 어떤 선택지가 있는지 바로 설명하는 것이다.

### 권고안
비교 제품의 동작은 공식 근거를 확인한 뒤 별도 참고 표로 분리한다. CUBRID 계약에는 “모든 컬럼을 RK로 사용하지 않음”, “사용자가 활성 RK를 직접 지정할 수 없음”처럼 차이를 명시하고, 다른 제품과 동일한 안전성을 추정하지 말라는 주의를 넣는다.

### 검증 방법
MySQL 또는 PostgreSQL 경험자에게 키 없는 테이블과 UK 두 개 테이블의 CUBRID 결과를 예측하게 한다. 문서를 읽은 뒤에는 ON 생성 실패와 엔진 자동 선택을 정확히 답하는지 확인한다.

## [USER-1Y-03] OFF를 선택하면 무엇을 잃는지 초보자가 알기 어렵다

- 분류: 컨셉
- 심각도: Critical
- 근거 위치: 원문 1절과 4절의 OFF 데이터 미복제 및 불일치 면책, 6절의 VIEW 결과 불일치
- 사실/추론 구분: 확인된 사실 — OFF 데이터가 replica에 복제되지 않지만 구체적인 사용자 결과와 권장 용도가 없다
- 영향 대상: 최종 사용자, 애플리케이션 데이터, 장애 조치

### 문제
`REPLICATION=OFF`가 간단한 성능 설정처럼 보인다. 실제로는 failover 뒤 해당 테이블의 행이 없거나 다른 값일 수 있다. “책임지지 않는다”만으로는 어떤 데이터에 사용하면 안 되는지 이해하기 어렵다.

### 왜 중요한가
초보 사용자는 PK가 없는 테이블 오류를 빨리 해결하려고 OFF로 바꿀 가능성이 있다. 주문·회원·감사 데이터에 OFF를 쓰면 장애 조치 후 행을 찾지 못한다. 이 결과는 SQL 오류가 아니라 정상적인 빈 조회로 나타날 수 있어 더 위험하다.

### 재현 또는 구체적 예제

```sql
CREATE TABLE orders (
  order_id INT PRIMARY KEY,
  amount INT
) REPLICATION = OFF;
INSERT INTO orders VALUES (100, 5000);
SELECT * FROM orders WHERE order_id = 100;
```

source에서는 1행이 나오지만, 장애 조치 후 새 primary에서는 0행일 수 있다고 문서에서 추론된다. 사용자는 주문이 삭제됐다고 생각할 수 있다.

### 권고안
OFF를 “장애 조치 후 데이터가 보장되지 않는 노드 로컬 테이블”로 정의한다. 재생성 가능한 캐시·임시 데이터와 주문·계정 같은 금지 사례를 나란히 보여 준다. OFF 생성과 변경 시 명시적 경고 및 확인 방법을 제공한다.

### 검증 방법
사용자에게 캐시, 주문, 임시 통계, 감사 로그 네 사례를 주고 ON/OFF를 선택하게 한다. 주문과 감사 로그에 OFF를 선택한 사용자가 있다면 경고와 예제를 보완한다. 실제 failover 전후 SELECT 결과도 문서와 비교한다.

## [USER-1Y-04] PK·UK·RK 후보·활성 RK 용어가 섞여 있다

- 분류: 모호성
- 심각도: Major
- 근거 위치: 원문 1절의 선택 규칙과 4-2절의 “후보가 1개인 경우(=복제키)”
- 사실/추론 구분: 확인된 사실 — 후보와 실제 선택된 RK의 차이를 별도 정의하지 않는다
- 영향 대상: 처음 사용하는 사용자, DBA 문의 담당자, 문서 독자

### 문제
PK와 UK는 테이블 제약이고, RK 후보는 그중 조건을 만족하는 키이며, 활성 RK는 실제 복제에 쓰이는 하나의 키다. 원문은 이 네 개를 오가면서 설명해 UK가 있으면 모두 RK인지, 하나만 RK인지 혼동하게 한다.

### 왜 중요한가
사용자가 삭제하려는 UK가 활성 RK인지 단순 후보인지에 따라 결과가 달라질 수 있다. 용어가 분리되지 않으면 “UK가 하나 더 있으니 안전하다” 또는 “모든 UK를 삭제할 수 없다”처럼 잘못 이해한다.

### 재현 또는 구체적 예제

```sql
CREATE TABLE member (
  id INT PRIMARY KEY,
  email VARCHAR(100) NOT NULL UNIQUE,
  phone VARCHAR(20) NOT NULL UNIQUE
) REPLICATION = ON;
```

문서 우선순위로 PK가 활성 RK일 가능성은 설명되지만 email과 phone을 “RK”라고 불러야 하는지 “후보”라고 불러야 하는지 명확하지 않다. 기대 결과는 활성 하나와 후보 목록을 구분해서 보여 주는 것이다.

### 권고안
용어 표와 색상 없는 간단한 관계도를 추가한다: PK/조건을 만족한 UK → RK 후보 목록 → 엔진이 선택한 활성 RK 1개. 모든 예제에 “변경 전 활성 RK”와 “변경 후 활성 RK”를 표시한다.

### 검증 방법
PK 1개와 UK 2개인 예제를 사용자에게 주고 PK, UK, 후보, 활성 RK를 각각 표시하게 한다. 문서를 읽은 사용자의 답이 일치해야 한다.

## [USER-1Y-05] 생략하면 ON이라는 기본값과 모드별 결과가 눈에 띄지 않는다

- 분류: 모호성
- 심각도: Critical
- 근거 위치: 원문 2-1절의 기본 ON, 3절 single, 4절 HA, 9절 single/SA 사용 가능
- 사실/추론 구분: 확인된 사실 — 옵션 생략은 ON이며 RK 없는 테이블은 single에서 생성되지만 HA 시작 때 오류가 난다
- 영향 대상: 초보 사용자, 개발 환경, 운영 전환

### 문제
사용자가 기존 방식대로 옵션 없이 테이블을 만들면 자동 ON이다. 키가 없어도 single에서는 성공하여 문제가 없는 것처럼 보이다가 나중에 HA 시작이 실패한다. SA와 single의 관계도 명확하지 않다.

### 왜 중요한가
오류가 원인 SQL 실행 시점이 아니라 수개월 뒤 운영 전환 시점에 나타나면 어떤 테이블 때문인지 찾기 어렵다. 기본값은 문서의 작은 문장보다 예제와 경고에서 반복해서 보여 줘야 한다.

### 재현 또는 구체적 예제

```sql
-- 개발 환경
CREATE TABLE upload_buffer (line VARCHAR(1000));
-- 운영에서 나중에 cubrid hb start
```

첫 SQL은 기본 ON이고 RK가 없다. 기대 결과는 생성 직후 “현재는 가능하지만 HA 시작 전 PK/NOT NULL UK 추가 또는 OFF 변경 필요” 경고를 보는 것이다.

### 권고안
문서 첫 사용 예제에 옵션 생략=ON을 굵은 주의로 표시한다. single/SA/HA별 생성·변경·시작 결과 표와 HA 준비 검사 명령을 제공한다. 오류를 늦게 발견하지 않도록 키 없는 기본 ON 생성 시 경고한다.

### 검증 방법
옵션을 모르는 사용자가 키 없는 테이블을 만든 뒤 HA 준비 과제를 수행하게 한다. 실제 HA 시작 전에 경고나 검사 명령으로 문제를 발견하고 올바른 수정법을 선택하는지 확인한다.

## [USER-1Y-06] CREATE 예제의 후행 쉼표가 핵심 오류를 가린다

- 분류: 문서 품질
- 심각도: Major
- 근거 위치: 원문 2-1절 예시 2 등 컬럼 목록 끝의 쉼표와 4-1절의 단순 `ERROR`
- 사실/추론 구분: 확인된 사실 — 일부 SQL은 마지막 컬럼 뒤 쉼표가 있어 정책 검사 전에 문법 오류가 날 수 있다
- 영향 대상: 입문 사용자, 실습자, QA

### 문제
키 없는 ON 테이블이 모드에 따라 어떻게 되는지 보여 주려는 예제가 실행되지 않을 수 있다. 사용자는 문법 오류를 RK 오류로 오해하거나, 쉼표를 고쳐도 왜 다른 오류가 나는지 알지 못한다.

### 왜 중요한가
초보자는 예제를 그대로 복사해 배운다. 하나의 예제에는 하나의 학습 목표만 있어야 한다. 문법 오류와 HA 정책 오류가 겹치면 어떤 규칙을 배워야 하는지 알 수 없다.

### 재현 또는 구체적 예제

```sql
CREATE TABLE repl_table_without_rk (
  a INT,
) REPLICATION = ON;
```

후행 쉼표를 제거한 SQL이 single에서는 성공하고 HA에서는 “RK 후보 없음”으로 실패하는 것이 의도된 비교로 보인다. 현재 예제는 이를 분명히 재현하지 못한다.

### 권고안
모든 예제를 자동 실행해 문법을 고친다. 각 예제에 실행 모드, 예상 오류 코드·메시지, 테이블 생성 여부, 다음 수정 SQL을 적는다. 문법 오류 예제는 별도 교육 목적이 아니면 넣지 않는다.

### 검증 방법
새 빈 DB에서 예제 1~23의 SQL을 복사해 실행한다. 각 코드 블록이 의도한 정책 단계까지 도달하고 결과와 사후 스키마가 문서 설명과 같은지 확인한다.

## [USER-1Y-07] 한 ALTER에서 PK를 바꾸는 완전한 예제가 없다

- 분류: 누락
- 심각도: Critical
- 근거 위치: 원문 2-2절 예시 7의 `...`와 4-2절 예시 13의 불완전한 제약 표현
- 사실/추론 구분: 확인된 사실 — 실제 테이블·제약 이름·데이터·실패 결과가 없는 축약 예시다
- 영향 대상: 스키마를 변경하는 사용자, 복제 정합성, 기술 지원

### 문제
문서는 기존 키 삭제와 새 키 추가를 하나의 ALTER로 하라고 하지만 복사 가능한 SQL이 없다. 새 키에 중복이나 NULL이 있으면 어떻게 되는지, 실패 후 이전 PK가 유지되는지도 없다.

### 왜 중요한가
사용자가 DROP과 ADD를 두 SQL로 나누면 중간에 RK가 없는 상태가 생길 수 있다. 반대로 하나의 SQL로 묶어도 새 제약 검증이 실패할 수 있으므로 전체가 취소되는지 알아야 안전하다.

### 재현 또는 구체적 예제

```sql
CREATE TABLE customer (
  id INT CONSTRAINT pk_customer PRIMARY KEY,
  email VARCHAR(100)
) REPLICATION = ON;
INSERT INTO customer VALUES (1, 'same@x'), (2, 'same@x');

ALTER TABLE customer
  DROP CONSTRAINT pk_customer,
  ADD CONSTRAINT uq_customer_email UNIQUE (email);
```

email이 중복이므로 새 UK는 만들 수 없다. 기대 결과는 전체 ALTER가 실패하고 기존 PK/RK가 id로 유지되는 것이다. 원문은 이를 설명하지 않는다.

### 권고안
성공 예제와 중복·NULL 실패 예제를 완전한 SQL로 제공한다. “DROP과 ADD를 별도 문장으로 실행하지 말 것”, 실패 시 전체 롤백, 오류 메시지와 확인용 `SHOW CREATE TABLE`을 함께 적는다.

### 검증 방법
사용자에게 PK→PK와 PK→UK 변경 과제를 주고 문서만 보고 한 문장으로 수행하게 한다. 성공 뒤 활성 RK와 실패 뒤 기존 PK 유지 여부를 조회해 예상과 같은지 확인한다.

## [USER-1Y-08] 컬럼 이름·타입·NULL 변경의 허용 여부를 찾을 수 없다

- 분류: 누락
- 심각도: Critical
- 근거 위치: 원문 4-2절의 PK/UK 추가·삭제 예시와 다른 후보가 있으면 모든 DDL 허용 문장
- 사실/추론 구분: 확인된 사실 — 키 컬럼 rename, 타입, NOT NULL, 복합 키 일부 변경 예제가 없다
- 영향 대상: 사용자, 스키마 마이그레이션, 복제 정합성

### 문제
사용자는 제약을 직접 삭제하지 않고도 RK의 성질을 바꿀 수 있다. UK 컬럼의 NOT NULL을 제거하거나 타입과 이름을 바꾸는 DDL이 허용되는지 문서에서 알 수 없다. “모든 DDL 허용”은 초보자에게 안전하다는 뜻으로 오해된다.

### 왜 중요한가
NOT NULL이 없어지면 NULL 값은 행 주소로 적합하지 않을 수 있다. 문자열 타입이나 비교 규칙 변경은 같은 값을 판단하는 방식도 바꿀 수 있다. 다른 후보가 있어도 언제 그 후보로 전환되는지 알아야 한다.

### 재현 또는 구체적 예제

```sql
CREATE TABLE device (
  serial VARCHAR(30) NOT NULL UNIQUE,
  old_id INT NOT NULL UNIQUE
) REPLICATION = ON;

ALTER TABLE device ALTER COLUMN serial DROP NOT NULL;
ALTER TABLE device RENAME COLUMN old_id AS legacy_id;
```

활성 RK가 무엇인지에 따라 결과가 다를 수 있다. 기대 결과는 각 SQL의 허용/거부, 자동 전환 여부, 변경 후 활성 RK가 표시되는 것이다.

### 권고안
PK/UK 추가·삭제뿐 아니라 컬럼 add/drop/rename, 타입·NOT NULL 변경을 표로 정리한다. 활성 RK, 다른 후보, 마지막 후보 상황별 결과와 해결 SQL을 예제로 제공한다.

### 검증 방법
표의 각 DDL을 단일 UK·UK 두 개·PK+UK 테이블에서 실행한다. 문서 결과와 실제 오류가 같고, 성공 뒤 사용자가 조회 명령으로 새 RK를 확인할 수 있는지 검증한다.

## [USER-1Y-09] DDL과 DML을 동시에 실행하면 무엇이 기다리는지 설명이 없다

- 분류: 모호성
- 심각도: Blocker
- 근거 위치: 원문 4절의 DDL 복제와 4-2절의 운영 중 키 변경 허용
- 사실/추론 구분: 확인이 필요한 질문 — 키 변경 중 UPDATE의 대기·거부·적용 순서가 정의되지 않았다
- 영향 대상: 사용자, 애플리케이션, 복제 정합성

### 문제
사용자가 운영 중 PK를 바꾸는 동안 애플리케이션이 계속 UPDATE할 수 있는지 알 수 없다. 성공, 대기, timeout, 실패 중 어느 결과인지와 안전한 재시도 방법이 없다.

### 왜 중요한가
키 변경 전 로그는 옛 주소를, 변경 후 로그는 새 주소를 사용할 수 있다. 순서가 섞이면 replica가 행을 못 찾아 변경이 누락될 수 있다. 사용자는 점검 시간에 쓰기를 멈춰야 하는지 알아야 한다.

### 재현 또는 구체적 예제

```sql
-- 세션 A
UPDATE wallet SET amount = amount + 10 WHERE id = 7;
-- A가 아직 COMMIT하지 않은 동안 세션 B
ALTER TABLE wallet DROP PRIMARY KEY,
  ADD CONSTRAINT pk_wallet_code PRIMARY KEY (wallet_code);
```

세션 B가 A를 기다리는지, A가 실패하는지 원문으로 예측할 수 없다. 기대 결과는 허용된 한 가지 순서와 사용자에게 보이는 대기/오류가 정해지는 것이다.

### 권고안
두 세션 타임라인 예제를 추가한다. 키 전환 DDL이 선행 쓰기를 기다리는지, timeout 후 재시도 가능한지, 전환 중 새 쓰기를 받는지 명시한다. 안전한 운영 절차로 쓰기 중단 필요 여부를 적는다.

### 검증 방법
두 csql 세션으로 UPDATE와 ALTER의 시작·커밋 순서를 바꿔 실행한다. 문서와 같은 세션이 대기하거나 실패하는지, 양 노드 데이터와 `fail_count`가 정상인지 확인한다.

## [USER-1Y-10] HA 시작 오류가 어느 테이블을 어떻게 고칠지 알려주지 않는다

- 분류: 운영성
- 심각도: Critical
- 근거 위치: 원문 7절의 제약 위반 시 오류와 “파일 리스트” 출력, single에서 ALTER 후 재시작 안내
- 사실/추론 구분: 확인된 사실 — 출력 대상, 오류 형식, 여러 위반을 한 번에 보여 주는지 불명확하다
- 영향 대상: 처음 HA를 설정하는 사용자, DBA 지원 창구

### 문제
“파일 리스트”가 실제 파일인지 문제가 있는 테이블 목록인지 알 수 없다. 테이블 이름, 위반 이유, 수정 예제, 모든 오류를 한 번에 출력하는지 없다. 사용자는 시작을 여러 번 실패하며 하나씩 고칠 수 있다.

### 왜 중요한가
HA 시작 실패는 서비스 시작 지연이다. 초보자는 `RK 없음`과 `OFF 부모 FK 참조`에 서로 다른 조치를 해야 한다. 정확한 객체와 다음 명령이 없으면 잘못 OFF로 바꿔 데이터를 복제 대상에서 제외할 수 있다.

### 재현 또는 구체적 예제

```sql
CREATE TABLE event_log (message VARCHAR(100)) REPLICATION = ON;
CREATE TABLE local_parent (id INT PRIMARY KEY) REPLICATION = OFF;
CREATE TABLE child (
  id INT PRIMARY KEY,
  parent_id INT,
  FOREIGN KEY (parent_id) REFERENCES local_parent(id)
) REPLICATION = ON;
```

HA 시작은 두 문제를 owner.table과 제약 이름으로 모두 보여 줘야 한다. event_log에는 키 추가 또는 OFF 선택, child에는 부모 ON 전환 또는 FK 설계 변경이 필요하다.

### 권고안
“파일 리스트”를 정확한 용어로 고친다. 오류에 테이블·제약·현재 ON/OFF·원인·가능한 수정 SQL을 표시하고, 시작 전에 실행할 수 있는 `CHECK HA READINESS`와 전체 위반 보고서를 제공한다.

### 검증 방법
서로 다른 위반 10개를 만든 뒤 한 번의 검사에서 모두 출력되는지 본다. 1년차 사용자가 출력만 보고 각 문제를 올바른 SQL로 수정하고 재검사 1회에 통과하는지 확인한다.

## [USER-1Y-11] failover 후 사용자가 무엇을 확인해야 하는지 없다

- 분류: 누락
- 심각도: Critical
- 근거 위치: 원문 5~6절의 failover 결과와 7절의 HA 시작; failover 직후 확인 절차 없음
- 사실/추론 구분: 확인된 사실 — 승격 후 ON 데이터, OFF 데이터, VIEW, 활성 RK를 확인하는 기본 흐름이 없다
- 영향 대상: 최종 사용자, 운영자, 애플리케이션

### 문제
문서는 failover가 발생할 수 있다고 설명하지만 사용자가 새 primary에서 무엇을 확인해야 하는지 제시하지 않는다. ON 테이블은 같아야 하고 OFF 테이블과 이를 포함한 VIEW는 다를 수 있다는 차이를 한 흐름에서 보여 주지 않는다.

### 왜 중요한가
장애 직후에는 빠른 확인이 필요하다. 모든 테이블을 똑같이 비교하면 의도된 OFF 차이를 장애로 오인하고, 반대로 VIEW의 다른 결과를 정상이라고 넘길 수 있다.

### 재현 또는 구체적 예제

```sql
SELECT COUNT(*) FROM customer;       -- ON 테이블
SELECT COUNT(*) FROM local_cache;    -- OFF 테이블
SELECT COUNT(*) FROM customer_view;  -- OFF 테이블을 포함할 수도 있음
```

기대 결과는 customer의 행 수·표본 값·RK가 전환 전과 같고, local_cache와 영향 VIEW는 별도 정책에 따라 확인하는 것이다. 문서에는 체크 순서가 없다.

### 권고안
“failover 후 첫 10분 확인” 절차를 추가한다. 새 primary 역할, 복제 오류, ON 핵심 테이블 체크섬, 활성 RK, OFF 목록, 영향 VIEW, 애플리케이션 읽기/쓰기를 순서대로 확인하고 이상 시 중단·문의 기준을 적는다.

### 검증 방법
교육용 클러스터에서 planned failover를 수행하게 하고 체크리스트 누락 없이 완료하는지 본다. ON 데이터 차이는 장애로, 문서에 정의된 OFF 차이는 정책대로 분류하는지 평가한다.

## [USER-1Y-12] 복합 키와 NULL의 의미가 예제로 설명되지 않는다

- 분류: 누락
- 심각도: Major
- 근거 위치: 원문 1절의 Not Null Unique Key 후보 규칙; 복합 UK 예제 없음
- 사실/추론 구분: 확인이 필요한 질문 — 복합 UK의 모든 컬럼이 NOT NULL이어야 하는지 원문의 표현만으로는 초보자가 확신하기 어렵다
- 영향 대상: 사용자, 데이터 모델링, 복제 정합성

### 문제
`NOT NULL UNIQUE KEY`가 한 컬럼만 뜻하는지, 복합 UK의 모든 컬럼이 NOT NULL이어야 하는지 설명이 없다. NULL이 왜 행 주소로 부적합한지도 없다.

### 왜 중요한가
복합 키는 두 값의 조합으로 한 행을 찾는다. 둘 중 하나가 NULL이면 키 후보 자격을 잃을 수 있다. 사용자가 UNIQUE만 있으면 충분하다고 생각하면 HA 시작에서 처음 오류를 발견한다.

### 재현 또는 구체적 예제

```sql
CREATE TABLE parcel (
  tenant_id INT NOT NULL,
  tracking_no VARCHAR(50),
  CONSTRAINT uq_parcel UNIQUE (tenant_id, tracking_no)
) REPLICATION = ON;
```

tracking_no가 NULL 가능하다. 이 UK가 RK 후보가 되는지 원문 예제로 확인할 수 없다. 기대 결과가 “후보 아님”이라면 `tracking_no NOT NULL`로 고치는 예제를 함께 보여 줘야 한다.

### 권고안
단일 UK, 올바른 복합 UK, NULL 가능 컬럼이 포함된 잘못된 복합 UK를 나란히 제공한다. 후보 여부와 이유, 수정 SQL, 컬럼 순서가 활성 RK에 미치는 의미를 설명한다.

### 검증 방법
세 예제를 single과 HA에서 생성해 후보 조회와 시작 결과를 확인한다. 사용자에게 각 테이블이 HA 준비됐는지 묻고 이유까지 정확히 답하는지 평가한다.

## [USER-1Y-13] 외래키 규칙은 부모·자식 ON/OFF 네 조합을 설명하지 않는다

- 분류: 정확성
- 심각도: Critical
- 근거 위치: 원문 5절의 ON 자식은 ON 부모만 참조해야 한다는 규칙과 예시 17~23
- 사실/추론 구분: 확인된 사실 — ON 자식→OFF 부모 외의 조합과 기존 관계에서 옵션 변경은 빠져 있다
- 영향 대상: 사용자, 데이터 정합성, 애플리케이션

### 문제
초보자는 어느 테이블이 부모이고 자식인지부터 이해해야 한다. 문서는 금지 예시는 있지만 OFF 자식→ON 부모가 가능한지, 부모를 나중에 OFF로 바꿀 수 있는지, `ON DELETE CASCADE` 결과는 어떤지 없다.

### 왜 중요한가
부모 행이 replica에 없는데 자식 행만 오면 FK 검사가 실패한다. 반면 OFF 자식은 노드마다 다르므로 부모 삭제에 따른 연쇄 삭제도 달라질 수 있다. 테이블을 OFF로 바꾸기 전에 모든 관계를 확인해야 한다.

### 재현 또는 구체적 예제

```sql
CREATE TABLE customer (id INT PRIMARY KEY) REPLICATION = ON;
CREATE TABLE local_note (
  id INT PRIMARY KEY,
  customer_id INT,
  FOREIGN KEY (customer_id) REFERENCES customer(id) ON DELETE CASCADE
) REPLICATION = OFF;

ALTER TABLE customer REPLICATION = OFF;
```

이 ALTER가 허용되는지, 기존 FK 때문에 거부되는지 없다. customer 삭제가 local_note에 미치는 결과도 노드별로 다를 수 있다.

### 권고안
부모/자식 ON/OFF 2×2 그림과 각 조합의 허용 여부를 제공한다. CREATE FK, 기존 테이블 ON/OFF 변경, CASCADE/SET NULL/RESTRICT를 각각 설명하고 오류에 부모·자식 이름과 해결법을 표시한다.

### 검증 방법
네 조합을 실제 생성하고 INSERT/DELETE 및 옵션 변경을 실행한다. 사용자에게 실행 전 결과를 예측하게 한 뒤 실제 결과와 비교하고, 허용 조합의 failover 후 FK 유효성을 확인한다.

## [USER-1Y-14] OFF 테이블을 포함한 VIEW는 정상처럼 보여 더 위험하다

- 분류: 정확성
- 심각도: Major
- 근거 위치: 원문 6절의 VIEW 사용 제약 없음과 결과 불일치 면책
- 사실/추론 구분: 확인된 사실 — VIEW DDL은 존재하지만 OFF 데이터 때문에 결과가 다를 수 있다
- 영향 대상: 최종 사용자, 보고서 사용자, 보안·집계 애플리케이션

### 문제
“사용에 제약이 없다”는 표현은 결과도 정상이라는 뜻으로 읽힌다. 실제로는 쿼리가 성공하면서 0행이나 다른 합계를 반환할 수 있다. 어떤 VIEW가 OFF 테이블을 참조하는지 확인하는 방법도 없다.

### 왜 중요한가
SQL 오류라면 사용자가 문제를 알아차리지만 잘못된 정상 결과는 알아차리기 어렵다. 주문 합계나 권한 필터 VIEW가 달라지면 업무 판단이나 데이터 노출에 영향을 준다.

### 재현 또는 구체적 예제

```sql
CREATE TABLE orders (id INT PRIMARY KEY, region VARCHAR(10)) REPLICATION = ON;
CREATE TABLE local_region (region VARCHAR(10) PRIMARY KEY) REPLICATION = OFF;
CREATE VIEW visible_orders AS
  SELECT o.* FROM orders o JOIN local_region r ON r.region = o.region;
```

standby의 local_region이 비어 있으면 failover 후 VIEW가 0행을 반환할 수 있다. 쿼리는 성공하므로 사용자는 장애를 모를 수 있다.

### 권고안
“실행은 가능하지만 결과 일치를 보장하지 않는다”로 고친다. VIEW 생성 시 OFF 의존 경고를 내고, 직접·간접 의존 VIEW 목록 조회법과 failover 전후 비교 예제를 제공한다.

### 검증 방법
직접·중첩 VIEW와 조인·집계 예제를 만들고 failover 전후 결과를 비교한다. 사용자에게 경고를 보여 준 뒤 어떤 VIEW 결과를 믿을 수 없는지 정확히 선택하게 한다.

## [USER-1Y-15] `fail_count`가 무엇이고 어디서 보는지 없다

- 분류: 운영성
- 심각도: Major
- 근거 위치: 원문 전체; 복제 오류는 다루지만 `fail_count` 용어와 조회 예제 없음
- 사실/추론 구분: 확인된 사실 — `fail_count`의 증가·초기화·확인·대응이 사용자 스펙에 없다
- 영향 대상: 초보 운영자, 기술 지원, 복제 정합성

### 문제
사용자는 복제가 실패했는지 알기 위한 기본 지표를 문서에서 찾을 수 없다. 같은 오류를 재시도할 때 숫자가 매번 증가하는지, 0으로 돌아오는지, 어느 테이블 때문인지도 없다.

### 왜 중요한가
복제 오류는 source 쿼리가 성공해도 replica에서 발생할 수 있다. 사용자가 카운터와 경보를 보지 않으면 failover 때까지 불일치를 모른다. 숫자만 보여도 의미를 모르면 잘못 정상으로 판단한다.

### 재현 또는 구체적 예제

```sql
CREATE TABLE inventory (sku INT PRIMARY KEY, qty INT) REPLICATION = ON;
UPDATE inventory SET qty = qty - 1 WHERE sku = 404;
```

replica에 404 행이 없어서 적용 실패한다고 가정한다. 사용자는 어떤 명령이나 화면에서 실패 테이블, 오류, 첫 발생 시각과 현재 미해결 여부를 봐야 하는지 알 수 없다.

### 권고안
`fail_count`를 초급 용어로 정의하고 조회 명령, 정상값, 경고 기준, 증가·초기화 규칙을 예제로 제공한다. 오류별 테이블·로그 위치·현재 RK와 “재시작 전에 할 일” runbook을 연결한다.

### 검증 방법
적용 오류를 한 건 발생시키고 초보 사용자에게 문서만으로 탐지·원인 확인·담당자 전달을 시킨다. 테이블, 오류 코드, 발생 시각, 미해결 수를 정확히 보고해야 한다.

## [USER-1Y-16] 오류 뒤 데이터를 비교하고 고치는 기본 절차가 없다

- 분류: 누락
- 심각도: Blocker
- 근거 위치: 원문 4절과 6절의 불일치 가능성, 7절의 스키마 수정만 안내
- 사실/추론 구분: 확인된 사실 — 행 데이터 불일치 확인·교정·재검증 절차가 없다
- 영향 대상: 사용자, DBA 지원, 복제 정합성

### 문제
문서는 키나 FK를 고친 뒤 HA를 다시 시작하라고 하지만, 그전에 이미 누락된 데이터가 있는지 확인하지 않는다. 사용자가 단순 재시작만 하면 스키마는 정상이어도 값 차이가 계속 남는다.

### 왜 중요한가
오류 원인을 고치는 것과 오류로 생긴 결과를 고치는 것은 별개다. 수도관을 수리해도 이미 빠진 물이 자동으로 채워지지 않는 것과 같다. 데이터 비교 없이 failover하면 오래된 값이 서비스된다.

### 재현 또는 구체적 예제
source의 `account(1)` balance는 100, replica는 누락 때문에 90이라고 가정한다.

```sql
SELECT id, balance FROM account WHERE id = 1;
```

키를 올바르게 만든 뒤 양쪽에서 같은 SELECT를 해야 차이를 알 수 있다. 기대 결과는 안전한 비교 도구와 권한 있는 담당자의 교정 후 재검증이다.

### 권고안
“오류 발견 → 쓰기 영향 확인 → 일관된 시점에 비교 → 정답 노드 승인 → 재동기화 → 체크섬 재검증 → failover 허용” 절차를 제공한다. 초보 사용자가 직접 임의 UPDATE하지 말아야 하는 경우도 경고한다.

### 검증 방법
행 누락과 값 차이를 만든 교육 환경에서 사용자가 절차 순서대로 처리하게 한다. 동시 쓰기를 잃지 않고 최종 데이터가 같으며, 재검증 기록과 승인자가 남는지 확인한다.

## [USER-1Y-17] 구버전 load의 기본 결과가 8절과 9절에서 반대다

- 분류: 호환성
- 심각도: Critical
- 근거 위치: 원문 8절은 값이 없으면 ON, 9절 5항은 포함하지 않는 테이블은 OFF
- 사실/추론 구분: 확인된 사실 — 같은 입력의 기본값이 ON과 OFF로 상충한다
- 영향 대상: 업그레이드 사용자, 데이터 이관, HA 준비

### 문제
복제 정보가 없는 구버전 unload 파일을 load하면 ON인지 OFF인지 알 수 없다. 어느 문장을 믿느냐에 따라 데이터 보호와 HA 시작 결과가 완전히 달라진다.

### 왜 중요한가
ON이면 키 없는 테이블 때문에 HA가 시작되지 않을 수 있다. OFF이면 키가 있는 중요한 테이블도 장애 조치 후 데이터를 잃은 것처럼 보일 수 있다. 초보 사용자는 load 뒤 수백 테이블을 일일이 판단하기 어렵다.

### 재현 또는 구체적 예제

```sql
-- 구버전 파일에 옵션 없이 저장됐다고 가정
CREATE TABLE customer (id INT PRIMARY KEY);
CREATE TABLE raw_log (message VARCHAR(100));
```

8절대로면 둘 다 ON, 9절대로면 둘 다 OFF다. 기대 결과는 load 전에 사용자가 기본 정책을 명시적으로 고르고 테이블별 결과를 미리 보는 것이다.

### 권고안
상충 문장을 통일하고 값이 없으면 `ON|OFF|ERROR` 중 선택하는 load 옵션을 제공한다. 초보자용 안전 기본은 dry-run 후 중단이며, RK 없는 ON과 중요한 OFF 후보를 경고한다.

### 검증 방법
복제 필드 없음/ON/OFF 파일을 각각 load한다. 선택 옵션, 사전 보고서, 실제 카탈로그와 HA 준비 결과가 일치하고 사용자가 customer와 raw_log의 결과를 사전에 정확히 설명하는지 확인한다.

## [USER-1Y-18] 업그레이드와 백업 복원 후 확인 절차가 없다

- 분류: 호환성
- 심각도: Major
- 근거 위치: 원문 8절의 unload/load; 일반 backup/restore, 롤링 업그레이드와 다른 버전 노드는 없음
- 사실/추론 구분: 확인이 필요한 질문 — ON/OFF와 활성 RK가 백업·복원 및 혼합 버전에서 보존되는지 원문으로 확인할 수 없다
- 영향 대상: 기존 사용자, 복구 담당자, HA 가용성

### 문제
사용자는 unload/load 외의 일반 백업과 복원에서도 새 속성이 유지된다고 가정할 수 있다. 한 노드씩 업그레이드하는 동안 구버전 노드가 새 문법을 이해하는지, 언제부터 사용할 수 있는지도 없다.

### 왜 중요한가
복원 후 OFF가 ON으로 바뀌거나 활성 RK가 달라지면 원래와 다른 복제가 시작될 수 있다. 구버전 replica가 새 DDL을 적용하지 못하면 양 노드 스키마가 갈라진다.

### 재현 또는 구체적 예제

```sql
CREATE TABLE local_cache (
  cache_key VARCHAR(50) PRIMARY KEY,
  value VARCHAR(500)
) REPLICATION = OFF;
```

이 DB를 백업·복원했을 때 OFF가 유지돼야 하는지, 신버전 primary와 구버전 replica 조합에서 CREATE가 허용되는지 문서에 없다.

### 권고안
backup/restore/unload/load별 보존 항목과 지원 버전 표를 제공한다. 롤링 업그레이드 중 새 문법 사용 가능 시점, 비지원 시 오류, 롤백 절차와 복원 후 확인 명령을 단계별로 적는다.

### 검증 방법
ON/OFF와 PK/여러 UK 테이블을 백업·복원해 설정과 활성 RK를 비교한다. 신·구 버전 노드 조합에서 CREATE/ALTER/failover를 수행하고 문서상 허용 여부와 실제 결과가 같은지 확인한다.

- 분류: 문서 품질
- 심각도: Major
- 근거 위치: 원문 2~5절 예시의 단순 `OK`/`ERROR` 결과

마지막 RK 삭제, HA에서 OFF→ON, OFF 부모 참조가 모두 `ERROR`로만 표시된다. 사용자는 SQL 문법 문제인지 HA 정책 문제인지, 재시도해야 하는지, 어떤 키나 옵션을 고쳐야 하는지 알 수 없다.

좋은 오류는 “무엇이 실패했는가, 왜 실패했는가, 무엇을 하면 되는가”를 알려준다. 초보자가 이유를 모르면 같은 SQL을 반복하거나 위험하게 OFF로 바꿀 수 있다.

### 재현 또는 구체적 예제

```sql
ALTER TABLE only_key_table DROP PRIMARY KEY;
ALTER TABLE local_table REPLICATION = ON;
```

첫 SQL은 마지막 RK를 제거해서, 둘째는 HA 운영 중 금지된 전환이라 실패한다. 서로 다른 오류 코드와 해결법이 필요하다.

### 권고안
모든 실패 예제에 안정된 오류 코드, 테이블·제약 이름, 현재 모드와 설정, 이유, 한두 개의 안전한 수정 예를 넣는다. 오류가 전체 롤백됐는지 확인하는 SQL도 제공한다.

### 검증 방법
초보 사용자에게 오류 출력만 주고 원인과 다음 SQL을 선택하게 한다. 마지막 RK, 문법, 모드, FK 위반을 모두 구분하고 위험한 수정 없이 해결해야 한다.

## [USER-1Y-20] 오탈자와 모드 용어가 기본 사용 흐름을 끊는다

- 분류: 문서 품질
- 심각도: Minor
- 근거 위치: 원문 5-1절 `CRATE TABLE`, 7절 “파일 리스트”·“재시작해아한다”, 9절의 single/SA 및 “HA 전환” 표현
- 사실/추론 구분: 확인된 사실 — 여러 오탈자와 일관되지 않은 모드 표현이 있다
- 영향 대상: 처음 읽는 사용자, 검색 사용자, 번역·교육 담당자

### 문제
`CRATE TABLE`은 SQL 키워드로 검색할 때 찾기 어렵고, “HA 전환”이 최초 HA 시작인지 장애 조치인지 모호하다. `cubrid hb start` 이외를 모두 single로 부르는 설명과 SA 표현도 일치하지 않는다.

### 왜 중요한가
초보자는 용어를 문자 그대로 따라 한다. HA 시작 전 single에서 수정하는 절차와 장애 중 failover 절차를 혼동하면 잘못 서비스를 중단할 수 있다. 오탈자는 복사한 SQL의 실패 원인이 되기도 한다.

### 재현 또는 구체적 예제

```text
1) non-HA 서버 실행
2) standalone(SA) 관리 작업
3) HA 클러스터 최초 시작
4) primary 장애 후 standby 승격(failover)
5) 원래 노드로 복귀(failback)
```

원문 용어만으로는 각 절이 다섯 상황 중 어디에 적용되는지 항상 구분되지 않는다.

### 권고안
모드와 사건을 용어집에서 분리하고 문서 전체에 같은 표현을 쓴다. `CRATE`를 `CREATE`로, “파일 리스트”를 의도한 테이블/제약 목록으로, 기타 맞춤법을 고친다. 처음 생성→조회→HA 준비→시작→failover 확인의 기본 튜토리얼을 추가한다.

### 검증 방법
용어·오탈자 정적 검사를 실행한다. 처음 보는 사용자가 다섯 상황을 올바른 순서로 설명하고 각 상황에서 허용되는 SQL과 확인 명령을 문서에서 찾을 수 있는지 사용성 시험을 한다.

```sql
SELECT class_name, partitioned, replication
FROM db_class WHERE class_name='sales';
```

이 출력만으로 파티션별 상태를 알 수 없다.

### 권고안

### 검증 방법
지원되는 파티션 작업을 ON/OFF와 키 있음/없음에 실행하고 사용자가 결과를 문서 표대로 예측하는지 확인한다.

## [USER-1Y-23] ON과 OFF 테이블을 한 트랜잭션에서 바꾸면 일부만 남을 수 있다

- 심각도: Critical

- 영향 대상: 최종 사용자, 애플리케이션 데이터, failover

### 문제
한 번의 COMMIT으로 ON과 OFF 테이블을 함께 바꾸면 source에서는 모두 성공하지만 새 primary에는 ON 변경만 있을 수 있다는 설명이 없다.

### 왜 중요한가
트랜잭션은 여러 작업을 한 묶음으로 만든다. 복제 뒤 묶음이 갈라지면 주문은 있는데 관련 메모는 없는 상태가 된다.

```sql
BEGIN;

COMMIT;
```

failover 후 첫 행만 있을 수 있다.

### 권고안

### 검증 방법
사용자에게 두 테이블의 failover 결과를 예측하게 하고 실제로 commit·rollback 뒤 양 노드를 비교한다.

지원 타입과 경계 길이별 UK를 만들고 후보 조회, HA 시작, 로그 크기와 오류 메시지를 확인한다.

## [USER-1Y-33] 여러 DB 중 한 곳의 오류가 어디까지 시작을 막는지 없다

- 분류: 모호성
- 심각도: Major
- 근거 위치: 원문 1절·7절은 위반 시 HA 실행 불가라고만 한다.
- 사실/추론 구분: 확인이 필요한 질문
- 영향 대상: 여러 DB를 쓰는 사용자, 서비스 가용성

### 문제
한 DB의 무키 ON 테이블 때문에 해당 DB만 실패하는지, 같은 서버의 다른 DB까지 멈추는지 알 수 없다.

### 왜 중요한가
작은 test DB 문제로 production 서비스까지 막히면 사용자 예상보다 장애 범위가 커진다. 부분 시작도 HA가 정상인 것처럼 오해할 수 있다.

### 재현 또는 구체적 예제
prod는 정상이고 sandbox에 다음 테이블만 있다고 하자.

```sql
CREATE TABLE scratch (v INT) REPLICATION=ON;
```

`cubrid hb start` 뒤 prod의 상태가 불명확하다.

### 권고안
검사·차단 범위를 DB/node/HA group으로 쉽게 설명하고 오류에 영향받은 서비스 목록과 안전한 다음 행동을 표시한다.

### 검증 방법
여러 DB 중 하나만 위반시켜 시작한다. 초보 사용자가 출력만 보고 실제 실행 상태와 영향 범위를 정확히 설명하는지 확인한다.

## [USER-1Y-34] OFF 테이블의 노드별 데이터가 충돌할 때 정리 방법이 없다

- 분류: 정확성
- 심각도: Critical
- 근거 위치: 원문 1절·4절은 OFF 데이터 불일치를 허용하지만 노드별 쓰기와 재가입은 없다.
- 사실/추론 구분: 확인이 필요한 질문
- 영향 대상: 최종 사용자, failover/failback

### 문제
두 노드의 OFF 테이블에 같은 키와 다른 값이 생기면 failback 또는 ON 복귀 때 어떤 값을 남기는지 없다.

### 왜 중요한가
역할을 바꿀 때마다 다른 값이 보이면 사용자는 데이터가 사라지고 돌아오는 것으로 느낀다. 자동 병합에는 정답 기준이 없다.

### 재현 또는 구체적 예제

```sql
-- 노드 A
INSERT INTO local_cache VALUES (1,'A');
-- 노드 B
INSERT INTO local_cache VALUES (1,'B');
```

다시 A로 전환하거나 ON으로 만들 때 충돌한다.

### 권고안
OFF를 노드 로컬 데이터로 설명하고 역할 전환 시 초기화/보존, 재가입 시 삭제, ON 복귀 전 기준 노드 선택 절차를 제공한다. 자동 합치기를 하지 않는다고 명시한다.

### 검증 방법
양 노드에 충돌 값을 만든 뒤 failover·failback·ON 복귀 교육 절차를 수행한다. 사용자가 예상한 수명 주기와 실제 결과가 같은지 확인한다.
