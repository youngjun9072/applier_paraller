## [PM-3Y-01] RK 후보 유지가 기존 PK 변경 누락을 막는다는 인과관계가 불완전하다

- 분류: 컨셉
- 심각도: Blocker
- 근거 위치: 1절의 PK 또는 NOT NULL UK 중 RK 선택, 4-2절의 다른 후보가 있으면 RK 관련 DDL 허용
- 사실/추론 구분: 문서에서 도출한 추론
- 영향 대상: 복제 정합성, 사용자, DBA, 제품 출시

### 문제
문서는 RK 후보를 하나 이상 유지하면 PK 변경 중 복제 누락을 막을 수 있다고 전제하지만, 이미 생성된 DML 로그가 어느 키 정의와 값을 담는지 설명하지 않는다. 후보가 존재한다는 사실만으로 DDL 전후 로그가 올바른 행을 찾는다는 보장은 없다.

### 왜 중요한가
복제 적용기는 원본 행의 주소가 아니라 키 값으로 대상 행을 찾는다. DML이 옛 PK로 기록된 뒤 PK가 바뀌고, standby가 새 RK만 알고 있다면 여전히 행을 못 찾을 수 있다. 이는 이 기능이 해결하려는 `fail_count` 증가와 데이터 불일치를 그대로 남긴다.

### 재현 또는 구체적 예제
```sql
CREATE TABLE account (id INT PRIMARY KEY, email VARCHAR(100) NOT NULL UNIQUE,
                      balance INT) REPLICATION=ON;
UPDATE account SET balance=900 WHERE id=10; -- 옛 RK id=10으로 로그가 생성됐다고 가정
ALTER TABLE account DROP PRIMARY KEY,
  ADD CONSTRAINT pk_account_email PRIMARY KEY(email);
```
standby가 DDL을 먼저 반영하거나 적용 시점에 `email`만 RK로 사용하면 앞선 UPDATE의 `id=10`을 해석할 수 있는지가 불명확하다. 기대 결과는 두 노드 모두 같은 행의 `balance=900`이다.

### 권고안
제품 요구사항에 “각 DML 로그는 사용한 RK의 식별자·스키마 버전·옛 키 값을 보존하며, DDL과 같은 커밋 순서로 적용한다” 같은 불변식을 명시한다. 이를 보장하지 못하면 관련 DDL을 대기 또는 거부하도록 범위를 축소한다.

### 검증 방법
복제 지연을 만든 뒤 UPDATE와 PK 교체를 교차 실행하고 로그 적용 순서를 바꾼 시험을 수행한다. 최종 데이터 체크섬 일치, 적용 오류 0, `fail_count` 불증가를 출시 수용 기준으로 삼는다.

## [PM-3Y-02] 모든 컬럼 비교 대안과 선택한 설계의 장단점이 측정 가능한 형태가 아니다

- 분류: 컨셉
- 심각도: Major
- 근거 위치: 1절의 RK 후보 규칙과 문서 전체의 PK/UK 중심 설계
- 사실/추론 구분: 확인이 필요한 질문
- 영향 대상: 제품 의사결정자, 성능 민감 사용자, 지원 조직

### 문제
문서는 왜 PK/NOT NULL UK 방식이 모든 컬럼 비교보다 적합한지, 대신 PK 없는 ON 테이블을 금지하는 비용은 무엇인지 설명하지 않는다. PostgreSQL 개념을 일부 채용했다는 배경도 원문에는 없으며 비교 수치도 없다.

### 왜 중요한가
모든 컬럼 비교는 넓은 행에서 느릴 수 있지만 기존 PK 없는 테이블을 그대로 복제할 수 있다. 반대로 RK 필수 방식은 성능을 예측하기 쉽지만 사용자가 스키마를 바꾸거나 복제를 끄게 만든다. PM은 성능 향상과 호환성 손실을 함께 수용 기준으로 관리해야 한다.

### 재현 또는 구체적 예제
```sql
CREATE TABLE event_log (
  created_at DATETIME, payload VARCHAR(4000), source VARCHAR(100)
); -- 기존에는 PK가 없다고 가정
```
1억 행 테이블에 UK를 추가하면 전체 중복 검사와 인덱스 생성 시간이 발생할 수 있다. OFF로 바꾸면 failover 후 최신 로그가 없다. 어느 비용을 제품이 선택하는지 문서만으로 판단할 수 없다.

### 권고안
대안 비교표에 지원 범위, 로그 크기, 행 검색 비용, 마이그레이션 비용, 정합성 보장을 적는다. 대표 데이터 크기별 성능 목표와 “PK 없는 기존 테이블은 명시적 조치 필요”라는 제품 결정을 공개한다.

### 검증 방법
정수 PK, 복합 문자열 UK, 키 없음/모든 컬럼 비교의 동일 DML 처리량과 로그 크기를 측정한다. 마이그레이션 대상 테이블 수와 인덱스 생성 시간도 기록해 승인된 목표와 비교한다.

## [PM-3Y-03] REPLICATION OFF의 위험을 ‘책임지지 않는다’로만 처리한다

- 분류: 컨셉
- 심각도: Critical
- 근거 위치: 1절과 6절의 OFF로 인한 불일치를 복제 모듈이 책임지지 않는다는 문장
- 사실/추론 구분: 확인된 사실
- 영향 대상: 사용자, 서비스 연속성, 고객 지원, 법적·운영 책임

### 문제
OFF는 기능이 제공하는 정상 설정인데도 데이터 손실 범위, 허용 용도, 경고, failover 후 행동을 정의하지 않은 채 책임만 배제한다. 사용자는 “DDL은 복제되므로 테이블도 쓸 수 있다”고 오해할 수 있다.

### 왜 중요한가
standby에는 테이블 구조만 있고 데이터가 없을 수 있다. 전환 후 쿼리가 빈 결과를 정상 결과로 반환하면 오류보다 발견이 늦고, 이를 근거로 후속 쓰기까지 발생한다.

### 재현 또는 구체적 예제
```sql
CREATE TABLE exchange_rate (code VARCHAR(3) PRIMARY KEY, rate NUMERIC)
  REPLICATION=OFF;
INSERT INTO exchange_rate VALUES ('USD', 1400);
```
primary에서는 1행이지만 failover한 standby에서는 0행일 수 있다. 애플리케이션이 0행을 “지원하지 않는 통화”로 처리하면 금액 계산이 달라진다.

### 권고안
OFF의 권장 대상을 노드 로컬 임시·캐시 데이터로 한정하고, 설정 시 경고와 의존성 검사를 제공한다. failover 체크리스트, 데이터 재적재 절차, 제품 지원 경계를 명확한 사용자 계약으로 쓴다.

### 검증 방법
OFF 테이블에만 데이터를 넣고 failover 후 직접 조회, VIEW, FK 관련 쿼리 결과를 확인한다. 문서 경고와 관리 도구의 사전 진단이 이 위험을 정확히 표시하는지 사용자 시험을 한다.

## [PM-3Y-04] RK 후보와 실제 선택된 RK를 조회하는 계약이 없다

- 분류: 모호성
- 심각도: Major
- 근거 위치: 1절의 엔진 자동 선택, 2-3절의 REPLICATION ON/OFF 조회만 제공
- 사실/추론 구분: 확인된 사실
- 영향 대상: 사용자, DBA, 지원 조직

### 문제
문서는 후보(PK/NOT NULL UK)와 실제 RK를 구분하지만 조회 예제는 복제 여부만 보여 준다. 사용자는 어떤 키를 보호해야 하는지 알 수 없다.

### 왜 중요한가
UK가 둘 이상이면 한 UK를 삭제해도 다른 후보가 남아 문법상 허용될 수 있다. 그러나 삭제 대상이 현재 RK인지, 즉 로그 형식이 전환되는 중요한 작업인지 알 수 없으면 변경 계획과 장애 분석이 불가능하다.

### 재현 또는 구체적 예제
```sql
CREATE TABLE member (email VARCHAR(100) NOT NULL UNIQUE,
                     phone VARCHAR(20) NOT NULL UNIQUE) REPLICATION=ON;
SHOW CREATE TABLE member;
```
현재 예제 형식은 두 UK와 `REPLICATION ON`만 보여 주며 `email`과 `phone` 중 실제 RK가 무엇인지 알려 주지 않는다.

### 권고안
카탈로그 또는 `SHOW REPLICATION KEY member` 같은 공식 조회 계약에 키 이름, 구성 컬럼 순서, 선택 이유, 스키마 버전을 제공한다. “후보”와 “활성 RK” 용어도 정의한다.

### 검증 방법
PK 1개와 UK 2개가 있는 테이블에서 PK 삭제 전후 조회 결과를 수집한다. 활성 RK가 정확히 하나 표시되고 노드 간 동일하며 변경 이력과 연결되는지 확인한다.

## [PM-3Y-05] 기본값 ON이 기존 사용자에게 주는 실패 동작이 명확하지 않다

- 분류: 호환성
- 심각도: Major
- 근거 위치: 2-1절의 옵션 생략 시 ON, 3절의 single에서는 키 없는 ON 테이블 허용, 7절의 HA 시작 거부
- 사실/추론 구분: 확인된 사실
- 영향 대상: 기존 사용자, 신규 사용자, 배포 자동화

### 문제
생략 기본값 ON은 기존 SQL의 의미를 유지하는 듯 보이지만, single에서 만든 키 없는 테이블 하나 때문에 나중에 HA 전체 시작이 실패한다. “기본값”이 안전한 기본 동작인지 설명되지 않는다.

### 왜 중요한가
사용자는 새 키워드를 모르는 상태에서도 위험한 구성을 만들 수 있다. 실패가 HA 전환 시점까지 지연되면 서비스 전환 일정에 직접 영향을 준다.

### 재현 또는 구체적 예제
```sql
CREATE TABLE import_stage (line_no INT, raw_text VARCHAR(1000));
-- 수개월 뒤: cubrid hb start
```
옵션을 생략했으므로 ON이 되고 RK가 없어 HA 시작이 거부된다. 사용자는 생성 시 성공했기 때문에 원인을 연결하기 어렵다.

### 권고안
single에서 키 없는 생략형 CREATE에 경고를 내고, HA 준비 검사 명령을 상시 제공한다. 문서에 ON 기본값을 택한 호환성 이유와 `REPLICATION=OFF`를 명시해야 할 사례를 적는다.

### 검증 방법
신규·업그레이드 DB에서 옵션 생략/ON/OFF와 RK 유무 조합을 시험한다. 생성 시 경고, 준비 검사, HA 시작 오류가 같은 테이블과 조치 방법을 가리키는지 확인한다.

## [PM-3Y-06] 여러 UK 중 선택 규칙이 결정적이고 지속적인지 보장하지 않는다

- 분류: 정확성
- 심각도: Blocker
- 근거 위치: 1절의 “엔진에 의해 하나 선택(ex. 테이블 내 명시된 순서 중 가장 빠른 순서)”
- 사실/추론 구분: 확인된 사실
- 영향 대상: 복제 정합성, 백업·복원, 구현팀

### 문제
`ex.`로 제시한 규칙은 규격이 아니다. 카탈로그 순서, 제약 이름, 생성 순서 중 무엇을 쓰는지와 unload/load 후에도 같은 키가 선택되는지가 없다.

### 왜 중요한가
source와 standby가 서로 다른 UK를 RK로 선택하면 같은 로그를 서로 다르게 해석할 수 있다. 자동 선택은 모든 노드와 복구 경로에서 동일해야 한다.

### 재현 또는 구체적 예제
```sql
CREATE TABLE contact (
  email VARCHAR(100) NOT NULL UNIQUE,
  phone VARCHAR(20) NOT NULL UNIQUE
) REPLICATION=ON;
```
source가 첫 UK인 email, 복원된 standby가 phone을 고르면 RK 값의 형식부터 달라진다. 기대 결과는 재시작·복원 후에도 동일한 제약을 선택하는 것이다.

### 권고안
PK 우선, UK는 안정적인 카탈로그 식별자 또는 명시적 정렬 기준으로 선택하도록 규범화한다. 더 안전하게는 실제 RK 식별자를 카탈로그와 unload 파일에 저장하고 자동 재선택 조건을 제한한다.

### 검증 방법
제약 생성 순서를 바꾼 스키마, unload/load, 재시작, 두 노드 독립 복원에서 활성 RK를 조회한다. 모든 경우 동일한 결과를 요구한다.

## [PM-3Y-07] 복합 ALTER의 원자성과 중간 상태 처리 규칙이 없다

- 분류: 정확성
- 심각도: Blocker
- 근거 위치: 2-2절 예시 7과 4-2절 예시 13의 DROP과 ADD 동시 수행
- 사실/추론 구분: 확인이 필요한 질문
- 영향 대상: 복제 정합성, 애플리케이션, DBA

### 문제
하나의 `ALTER TABLE`에 옛 키 삭제와 새 키 추가를 함께 쓰면 안전하다고 암시하지만 검증 순서, 잠금, 실패 시 롤백, 복제 단위가 정의되지 않았다.

### 왜 중요한가
DROP만 적용된 중간 상태가 보이거나 ADD가 중복 데이터 때문에 실패하면 RK가 0개가 될 수 있다. 그때 DML이 들어오면 다시 복제 대상 행을 찾지 못한다.

### 재현 또는 구체적 예제
```sql
CREATE TABLE t (id INT PRIMARY KEY, email VARCHAR(50), value INT) REPLICATION=ON;
ALTER TABLE t DROP PRIMARY KEY,
  ADD CONSTRAINT uk_t_email UNIQUE(email);
```
`email`에는 NULL 또는 중복이 있을 수 있어 새 제약 추가가 실패한다. 기대 결과는 전체 ALTER 롤백과 기존 PK/RK 유지다.

### 권고안
문장 단위 원자성, 사전 데이터 검증, DML 잠금/대기 정책, 복제 로그의 단일 스키마 변경 이벤트를 명세한다. 새 후보가 유효해진 뒤 옛 RK를 해제한다는 수용 기준을 둔다.

### 검증 방법
중복값, 디스크 부족, 강제 종료를 ADD 단계에 주입한다. 어느 실패에서도 기존 PK와 RK가 남고 source/standby 카탈로그 및 데이터가 일치하는지 확인한다.

## [PM-3Y-08] 데이터 타입·이름·NULL 속성 변경 상태표가 빠졌다

- 분류: 누락
- 심각도: Major
- 근거 위치: 4-2절의 “RK를 수정하는 DDL 제한”과 일부 DROP 예제
- 사실/추론 구분: 확인된 사실
- 영향 대상: 사용자, 마이그레이션 도구, 복제 정합성

### 문제
컬럼 삭제만 예시하고 RK 컬럼의 타입 변경, 이름 변경, NOT NULL 제거, 복합 키 일부 변경을 허용하는지 제시하지 않는다.

### 왜 중요한가
이 작업들은 키 값의 표현 또는 후보 자격을 바꾼다. 단순 DDL 성공 여부가 제품 버전이나 실행 모드마다 다르면 배포 자동화가 예측 불가능해진다.

### 재현 또는 구체적 예제
```sql
CREATE TABLE sku (tenant INT NOT NULL, code VARCHAR(20) NOT NULL,
  UNIQUE(tenant, code)) REPLICATION=ON;
ALTER TABLE sku ALTER COLUMN code VARCHAR(100);
ALTER TABLE sku RENAME COLUMN code TO sku_code;
ALTER TABLE sku ALTER COLUMN tenant DROP NOT NULL;
```
마지막 문장은 RK 후보 자격을 없애며 앞선 두 문장은 로그 키의 메타데이터를 바꾼다. 각 결과가 문서에 없다.

### 권고안
single/SA/HA × 활성 RK/비활성 후보 × DDL 종류의 상태 전이표를 제공한다. 각 셀에 허용·거부·대기와 오류 코드를 적는다.

### 검증 방법
단일·복합 PK/UK 각각에 타입 확대/축소, rename, NOT NULL 추가/삭제를 실행한다. 전이표와 실제 결과 및 복제 후 데이터가 일치하는지 자동 시험한다.

## [PM-3Y-09] DDL과 DML 동시 실행 시 순서 계약이 없다

- 분류: 정확성
- 심각도: Critical
- 근거 위치: 4절의 모든 DDL 복제 및 4-2절의 RK 변경 허용
- 사실/추론 구분: 확인이 필요한 질문
- 영향 대상: 복제 정합성, 애플리케이션, 운영팀

### 문제
DDL 트랜잭션과 DML 트랜잭션이 겹칠 때 잠금, 커밋 순서, 로그에 기록되는 RK 버전을 정하지 않았다.

### 왜 중요한가
정상 배포 중에도 애플리케이션 쓰기는 계속된다. 어느 트랜잭션이 먼저 보이는지에 따라 UPDATE가 옛 키 또는 새 키를 사용하므로 경계 정의가 없으면 간헐적 장애가 된다.

### 재현 또는 구체적 예제
```sql
-- A
UPDATE customer SET email='new@x' WHERE id=10;
-- A는 아직 COMMIT하지 않음
-- B
ALTER TABLE customer DROP PRIMARY KEY,
 ADD CONSTRAINT pk_customer_email PRIMARY KEY(email);
```
B가 대기하는지, 거부되는지, 성공 후 A가 어떤 RK로 로그를 남기는지 불명확하다. 기대 결과는 직렬화 가능한 단일 순서다.

### 권고안
DDL 잠금과 진행 중 트랜잭션 처리 정책을 명세하고, 로그는 트랜잭션 시작이 아닌 커밋 시 유효한 스키마 버전과 결합한다고 명시하거나 DDL을 대기시킨다.

### 검증 방법
두 세션의 시작·커밋 순서를 전 조합으로 바꾸고 복제 지연도 주입한다. 허용된 결과 집합, 오류 코드, 최종 체크섬을 자동 검증한다.

## [PM-3Y-10] HA 중 OFF 전환 시 어느 시점부터 DML 복제가 중단되는지 없다

- 분류: 모호성
- 심각도: Critical
- 근거 위치: 2-2절의 HA에서 `REPLICATION=OFF` 허용, 4절의 ON 데이터만 복제
- 사실/추론 구분: 확인이 필요한 질문
- 영향 대상: 사용자, 복제 정합성, 장애 조치

### 문제
ON→OFF DDL 전에 커밋했지만 아직 적용되지 않은 DML, 같은 트랜잭션의 DML, OFF 이후 로그의 처리 경계를 설명하지 않는다.

### 왜 중요한가
경계가 다르면 standby의 마지막 데이터 시점이 달라진다. 사용자는 OFF가 성공했다는 것만으로 어느 데이터까지 복제됐는지 알 수 없다.

### 재현 또는 구체적 예제
```sql
UPDATE audit SET status='done' WHERE id=1; -- 복제 큐에 대기
ALTER TABLE audit REPLICATION=OFF;
UPDATE audit SET status='archived' WHERE id=1;
```
standby에 `done`이 남는지, 이전 값이 남는지 정의가 없다. 기대 결과는 DDL 커밋 이전 로그까지 적용 후 OFF 전환이다.

### 권고안
전환을 로그 순서의 장벽으로 정의하고 이전 DML 적용 완료 여부를 확인할 방법을 제공한다. 완료 전 failover 시 보장 범위도 명시한다.

### 검증 방법
적용 지연 상태에서 위 순서를 실행하고 DDL 직전·직후 failover한다. 문서가 정한 마지막 복제 값과 실제 값이 일치하는지 확인한다.

## [PM-3Y-11] HA 시작 전 검사가 원자적이지 않으면 검사 직후 위반이 생길 수 있다

- 분류: 운영성
- 심각도: Critical
- 근거 위치: 7절의 HA 실행 시 RK와 FK 조건 검사
- 사실/추론 구분: 문서에서 도출한 추론
- 영향 대상: DBA, 서비스 가용성, 복제 정합성

### 문제
검사 대상 스냅샷, DDL 차단 시점, 검사 도중 스키마 변경 처리 및 대형 카탈로그 비용이 없다.

### 왜 중요한가
검사와 HA 활성화 사이에 키가 삭제되면 검사는 통과했지만 시작 상태는 위반이다. 반대로 오래 잠그면 시작 시간이 서비스 목표를 넘을 수 있다.

### 재현 또는 구체적 예제
```sql
-- 세션 A: cubrid hb start가 카탈로그 검사 중
-- 세션 B: 검사 완료된 테이블의 유일 후보를 삭제
ALTER TABLE payment DROP CONSTRAINT uk_payment_ref;
```
B가 언제부터 차단되는지 없다. 기대 결과는 검사 시작부터 HA 제약 활성화까지 빈틈 없는 상태 전이다.

### 권고안
일관된 카탈로그 스냅샷과 전환 락을 명세하고, 검사 시간 목표와 진행률을 제공한다. 시작 성공 시 모든 ON 테이블의 불변식이 같은 시점에 성립해야 한다.

### 검증 방법
수천 개 테이블 환경에서 검사 중 DDL을 반복하고 시작 성공/실패를 관찰한다. 성공한 모든 실행에서 즉시 재검사 결과가 0건이며 시간 목표를 만족해야 한다.

## [PM-3Y-12] 복합 UK와 UK 값 갱신 시 옛 값·새 값 사용 규칙이 없다

- 분류: 정확성
- 심각도: Critical
- 근거 위치: 1절의 NOT NULL UK 허용과 4-2절의 UK 기반 RK
- 사실/추론 구분: 확인이 필요한 질문
- 영향 대상: 복제 정합성, 애플리케이션

### 문제
복합 RK 자체를 UPDATE할 때 standby에서 행을 찾는 값과 변경 값의 구분이 없다.

### 왜 중요한가
행은 변경 전 키로 찾아야 하고 변경 후 키로 갱신해야 한다. 새 키만 로그에 있으면 기존 행을 못 찾고, 구성 컬럼 순서가 다르면 잘못된 비교가 된다.

### 재현 또는 구체적 예제
```sql
CREATE TABLE inventory (warehouse INT NOT NULL, sku VARCHAR(20) NOT NULL,
 qty INT, UNIQUE(warehouse, sku)) REPLICATION=ON;
UPDATE inventory SET warehouse=2, sku='B' WHERE warehouse=1 AND sku='A';
```
로그에는 `(1,'A')`와 `(2,'B')` 중 무엇이 들어가는가가 불명확하다. 기대 결과는 옛 키로 정확히 한 행을 찾고 새 키 유일성을 검사하는 것이다.

### 권고안
RK UPDATE 로그에 이전 키 전체와 새 키 전체, 컬럼 순서, NULL 불가 검증을 포함한다고 명시한다. 0행/2행 이상 검색 결과는 명시적 정합성 오류로 처리한다.

### 검증 방법
복합 RK의 첫째·둘째·전체 컬럼 변경, 값 교환, 충돌을 시험한다. 결과 행 수, 오류 코드, `fail_count`, 양 노드 데이터가 명세와 일치하는지 본다.

## [PM-3Y-13] FK 규칙이 전이 방향과 연쇄 동작을 모두 다루지 않는다

- 분류: 누락
- 심각도: Critical
- 근거 위치: 5절의 ON 자식이 참조하는 부모는 ON이어야 한다는 규칙
- 사실/추론 구분: 확인된 사실
- 영향 대상: 데이터 정합성, 사용자, 애플리케이션

### 문제
FK 생성만 주로 다루며, 참조 중인 부모를 OFF로 바꾸는 경우, 자식을 OFF로 바꾸는 경우, `ON DELETE/UPDATE CASCADE`가 어느 노드에서 실행·복제되는지 없다.

### 왜 중요한가
부모가 OFF가 되면 standby에 자식만 남을 수 있다. 연쇄 삭제가 source에서 DML로 복제되는지 standby FK가 다시 실행하는지에 따라 중복 적용 또는 고아 행이 생길 수 있다.

### 재현 또는 구체적 예제
```sql
CREATE TABLE parent (id INT PRIMARY KEY) REPLICATION=ON;
CREATE TABLE child (id INT PRIMARY KEY, parent_id INT,
 FOREIGN KEY(parent_id) REFERENCES parent(id) ON DELETE CASCADE) REPLICATION=ON;
ALTER TABLE parent REPLICATION=OFF;
DELETE FROM parent WHERE id=1;
```
ALTER가 거부되는지와 child 삭제가 standby에 어떻게 반영되는지 문서에 없다.

### 권고안
ON/OFF 조합별 FK 생성·삭제·전환 상태표와 CASCADE 처리 주체를 명시한다. ON 자식이 하나라도 있으면 부모 OFF 전환을 거부하는 정책을 수용 기준으로 검토한다.

### 검증 방법
부모/자식 각각 ON/OFF 전환과 CASCADE/SET NULL/RESTRICT를 조합해 source와 standby의 부모·자식 행 수 및 오류를 비교한다.

## [PM-3Y-14] OFF 테이블 포함 VIEW를 ‘제약 없음’이라 부르는 것은 사용자 결과 계약과 충돌한다

- 분류: 정확성
- 심각도: Major
- 근거 위치: 6절의 failover 후 VIEW 사용 제약 없음과 노드별 결과 불일치
- 사실/추론 구분: 확인된 사실
- 영향 대상: 최종 사용자, 애플리케이션, 분석 결과

### 문제
실행 가능하다는 뜻의 “제약 없음”과 결과가 달라진다는 중대한 의미가 한 문단에 공존한다. VIEW 의존성을 사전 식별하거나 경고하는 기능도 없다.

### 왜 중요한가
쿼리가 오류 없이 성공하면 사용자는 결과를 신뢰한다. 빈 조인 결과나 다른 집계는 장애 감지 없이 업무 의사결정을 왜곡한다.

### 재현 또는 구체적 예제
```sql
CREATE TABLE orders (id INT PRIMARY KEY, code VARCHAR(3)) REPLICATION=ON;
CREATE TABLE rate (code VARCHAR(3) PRIMARY KEY, value INT) REPLICATION=OFF;
CREATE VIEW order_value AS
 SELECT o.id, r.value FROM orders o JOIN rate r ON o.code=r.code;
```
source에서는 행이 보이고 failover 후에는 0행일 수 있다. SQL 성공 여부만으로는 안전하지 않다.

### 권고안
“실행은 허용되나 결과 정합성을 보장하지 않음”으로 고치고, OFF 테이블에 직접·간접 의존하는 VIEW 목록 조회와 경고를 제공한다.

### 검증 방법
중첩 VIEW와 조인·외부 조인·집계를 구성해 failover 전후 결과를 비교한다. 진단 명령이 모든 간접 의존성을 찾아내는지 확인한다.

## [PM-3Y-15] fail_count의 예방·해석·초기화와 경보 기준이 빠졌다

- 분류: 운영성
- 심각도: Major
- 근거 위치: 원문 전체에 `fail_count` 설명 및 운영 절차가 없음
- 사실/추론 구분: 확인된 사실
- 영향 대상: DBA, 고객 지원, SRE, 제품 성공 지표

### 문제
변경 목적의 핵심인 복제 실패 감소를 측정할 카운터 계약이 원문에 없다. 어떤 오류가 증가시키며 성공 재시도나 재시작 시 어떻게 되는지도 알 수 없다.

### 왜 중요한가
카운터가 계속 증가해도 단일 사건인지 반복 손실인지 구별 못 하면 경보가 무의미하다. 반대로 초기화되면 기존 장애 흔적을 잃는다.

### 재현 또는 구체적 예제
```sql
UPDATE account SET balance=100 WHERE id=10;
-- standby에서 대상 행을 찾지 못해 같은 로그를 3회 재시도했다고 가정
```
`fail_count`가 1인지 3인지, 어느 테이블·LSA·오류와 연결되는지 문서에 없다.

### 권고안
증가 단위, 재시도 관계, 보존·초기화, 조회 위치를 정의한다. 테이블·로그 위치·오류 코드·최초/최근 시각을 함께 노출하고 출시 지표를 “RK 관련 적용 실패 0”으로 둔다.

### 검증 방법
행 없음, 중복 행, 스키마 버전 불일치 오류를 의도적으로 발생시키고 재시도·재시작한다. 카운터와 상세 이벤트가 명세대로 연결되고 경보가 한 사건을 중복 집계하지 않는지 확인한다.

## [PM-3Y-16] HA 시작 오류가 ‘파일 리스트’라고 되어 있어 조치가 불가능하다

- 분류: 문서 품질
- 심각도: Major
- 근거 위치: 7절의 제약 위반 시 “에러와 함께 파일 리스트” 출력
- 사실/추론 구분: 확인된 사실
- 영향 대상: DBA, 사용자, 지원 조직

### 문제
검사 대상은 테이블과 FK인데 출력은 파일 리스트라고 표현한다. 오류 코드, 객체 이름, 위반 이유, 수정 SQL, 여러 오류의 최대 출력 수가 없다.

### 왜 중요한가
HA 시작이 막힌 긴급 상황에서 사용자는 실패 객체를 빠르게 찾아야 한다. 단순 ERROR나 잘못된 대상 목록은 복구 시간을 늘린다.

### 재현 또는 구체적 예제
```sql
CREATE TABLE no_key (v INT); -- 기본 ON
CREATE TABLE local_parent (id INT PRIMARY KEY) REPLICATION=OFF;
-- ON 자식이 local_parent를 참조하는 기존 스키마가 있다고 가정
```
시작 시 `no_key`의 RK 없음과 FK 위반을 각각 테이블·제약 이름으로 보여줘야 하지만 현재 계약은 없다.

### 권고안
구조화된 오류 형식을 정의한다: 오류 코드, `owner.table`, 위반 유형, 관련 제약, 권장 ALTER 예시. “파일 리스트”가 실제로 무엇인지 바로잡고 모든 위반을 한 번에 출력한다.

### 검증 방법
두 유형의 위반을 여러 개 만들고 시작한다. 출력만 보고 초급 운영자가 대상과 조치를 식별할 수 있는지, 수정 후 재검사 성공하는지 확인한다.

## [PM-3Y-17] 구버전 unload 파일의 기본 처리 규칙이 8절과 9절에서 상충한다

- 분류: 호환성
- 심각도: Critical
- 근거 위치: 8절은 변수가 없으면 ON, 9절 5항은 복제 여부를 포함하지 않으면 OFF
- 사실/추론 구분: 확인된 사실
- 영향 대상: 업그레이드 사용자, 백업·복원, 데이터 가용성

### 문제
같은 입력 파일을 ON으로 읽을지 OFF로 읽을지 서로 반대로 적었다. 구현팀과 사용자가 어느 규칙도 확정할 수 없다.

### 왜 중요한가
ON이면 키 없는 테이블 때문에 HA 시작이 실패할 수 있고, OFF이면 사용자는 복제된다고 믿은 데이터가 standby에 전달되지 않는다. 어느 쪽이든 조용한 기본 처리는 위험하다.

### 재현 또는 구체적 예제
```sql
-- 구버전 unload에 다음 테이블 정의가 있고 replication 필드가 없다고 가정
CREATE TABLE legacy_log (message VARCHAR(1000));
```
8절대로면 ON이며 RK 없음 검사가 실패한다. 9절대로면 OFF라서 load는 되지만 데이터가 복제되지 않는다.

### 권고안
단일 정책을 결정하고 두 절을 일치시킨다. 안전하게는 불명확한 파일 load 시 명시 옵션을 요구하거나 강한 경고와 결과 요약을 제공하며, 자동 선택 값을 감사 로그에 남긴다.

### 검증 방법
구버전 파일, 신버전 ON/OFF 파일, 필드 손상 파일을 load한다. 생성 상태, 경고, HA 준비 검사 결과가 승인된 호환성 표와 일치하는지 확인한다.

## [PM-3Y-18] 롤링 업그레이드와 혼합 버전 HA 지원 정책이 없다

- 분류: 호환성
- 심각도: Blocker
- 근거 위치: 8절의 하위 버전 unload만 언급하며 실행 중 노드 버전 차이는 문서 전체에서 누락
- 사실/추론 구분: 확인이 필요한 질문
- 영향 대상: 기존 HA 고객, 릴리스 운영, 지원 조직

### 문제
신버전 source가 `REPLICATION` DDL 또는 RK 메타데이터를 구버전 standby로 보낼 때의 행동과 업그레이드 순서가 정의되지 않았다.

### 왜 중요한가
HA 제품은 보통 노드를 순서대로 업그레이드하므로 잠시 혼합 버전이 된다. 구버전이 새 로그를 무시하거나 다르게 해석하면 장애 없는 업그레이드 약속이 깨진다.

### 재현 또는 구체적 예제
```sql
-- 신버전 primary
ALTER TABLE session_cache REPLICATION=OFF;
-- 구버전 standby가 이 구문/카탈로그 필드를 모른다고 가정
```
적용 중단, 무시, 연결 거부 중 무엇인지 없다. 이후 failover하면 구버전 노드에 데이터가 어느 수준인지도 모른다.

### 권고안
지원 버전 행렬, 권장 업그레이드 순서, 기능 활성화 게이트를 명시한다. 모든 노드가 지원 버전이 되기 전 새 DDL을 거부하거나 호환 로그로 처리하는 정책을 정한다.

### 검증 방법
구→신, 신→구 조합에서 DDL/DML과 failover/failback을 시험한다. 미지원 조합은 시작 전에 명확히 차단되고 지원 조합은 데이터·카탈로그가 일치해야 한다.

## [PM-3Y-19] SQL 예제가 그대로 실행되지 않고 기대 오류 정보가 없다

- 분류: 문서 품질
- 심각도: Minor
- 근거 위치: 2-1절 예시 2의 후행 쉼표, 2-2·4절의 `ERROR`만 표시, 5-1절의 `CRATE TABLE`
- 사실/추론 구분: 확인된 사실
- 영향 대상: 초급 사용자, 문서 QA, 기술 지원

### 문제
예시 2의 `a INT,`는 문법 오류이며 “CRATE” 오탈자가 있다. 다수 실패 예제가 실제 오류 코드·메시지 없이 `ERROR`만 보여 원래 의도한 제약 오류와 SQL 문법 오류를 구분할 수 없다.

### 왜 중요한가
입문자는 예제를 복사해 기능을 학습한다. 잘못된 SQL이 실패하면 RK 규칙 때문이라고 오해하고, 자동 문서 테스트도 만들기 어렵다.

### 재현 또는 구체적 예제
```sql
CREATE TABLE repl_table_without_rk(
  a INT,
) REPLICATION=ON;
```
single에서도 후행 쉼표 때문에 실패할 가능성이 있다. 문서가 말하는 “single에서는 성공, HA에서는 제약”을 검증하지 못한다.

### 권고안
후행 쉼표와 제목을 수정하고 모든 예제에 사전 모드, 기대 성공/실패, 실제 오류 코드와 이유를 쓴다. 문서 SQL을 CI에서 실행 가능한 형태로 관리한다.

### 검증 방법
문서의 23개 예제를 추출해 single/SA/HA의 지정 환경에서 실행한다. 문법 오류 0건과 기대 코드 완전 일치를 릴리스 체크리스트에 포함한다.

## [PM-3Y-20] SA와 single의 정의 및 1~9절의 사용자 여정이 일관되지 않다

- 분류: 문서 품질
- 심각도: Major
- 근거 위치: 1절은 HA 외 모두 single, 3절은 Single, 9절은 “싱글이나 SA”로 별도 표기
- 사실/추론 구분: 확인된 사실
- 영향 대상: 사용자, QA, 문서·지원 조직

### 문제
SA가 single과 같은 것인지 별도 모드인지 상충하며, 모드별 허용 동작을 한눈에 볼 수 없다. 또한 생성→HA 준비 검사→시작→운영 중 변경→failover→복원이라는 사용자 흐름이 절별 규칙으로 흩어져 있다.

### 왜 중요한가
같은 SQL이 모드에 따라 성공하거나 실패한다. 용어가 불명확하면 사용자는 잘못된 환경에서 명령을 실행하고 QA도 기대 결과를 합의할 수 없다.

### 재현 또는 구체적 예제
```sql
CREATE TABLE staging (v INT) REPLICATION=ON;
ALTER TABLE staging REPLICATION=OFF;
ALTER TABLE staging REPLICATION=ON;
```
single에서는 모두 가능한 것으로 보이지만 SA가 같은지, HA에서는 마지막 문장만 실패하는지, HA 중지 직후에는 어떤지 명확한 표가 없다.

### 권고안
single, SA, HA 실행 중, HA 중지 상태를 정의하고 CREATE/ON→OFF/OFF→ON/RK DDL의 허용 표를 제공한다. 이어서 신규 구축과 기존 DB 업그레이드의 단계별 사용자 여정을 예제로 제시한다.

### 검증 방법
각 모드에서 위 세 문장과 RK 추가·삭제를 실행해 표와 비교한다. 처음 읽는 사용자 3명 이상이 별도 설명 없이 HA 전환 준비 순서를 정확히 수행하는 문서 사용성 시험도 한다.

## [PM-3Y-21] 복제 정책을 바꿀 수 있는 권한과 승인 경계가 없다

- 분류: 보안
- 심각도: Critical
- 근거 위치: 2-2절은 `ALTER TABLE ... REPLICATION` 사용자를 포괄적으로 표현하지만 권한을 설명하지 않음
- 사실/추론 구분: 확인이 필요한 질문
- 영향 대상: 보안 관리자, DBA, 테이블 소유자, 데이터 보호

### 문제
누가 ON→OFF, OFF→ON 또는 RK 후보를 바꿀 수 있는지 정의되지 않았다. 일반 `ALTER` 권한만 있으면 데이터 복제를 끌 수 있는지, DBA 전용 권한이나 별도 승인이 필요한지 알 수 없다.

### 왜 중요한가
OFF는 단순 스키마 변경이 아니라 failover 시 데이터를 잃어 보이게 만드는 보호 수준 변경이다. 개발 계정이 성능 문제를 해결하려고 OFF로 바꾸면 보안 통제를 우회해 중요 데이터가 standby에 남지 않을 수 있다.

### 재현 또는 구체적 예제
```sql
-- 애플리케이션 배포 계정에 일반 ALTER 권한만 있다고 가정
ALTER TABLE payment_history REPLICATION=OFF;
```
이 문장이 성공하는지, 별도 권한 오류가 나는지 없다. 성공한다면 결제 이력 DML이 더 이상 복제되지 않는 중대한 정책 변경이다.

### 권고안
CREATE 시 지정, ON→OFF, OFF→ON, RK 변경, 상태 조회에 필요한 권한을 표로 정의한다. 최소 권한 원칙에 따라 복제 정책 변경은 별도 시스템 권한과 운영 승인 대상으로 두고, 중요 테이블에는 정책 잠금 기능을 검토한다.

### 검증 방법
DBA, owner, ALTER-only, SELECT-only 계정으로 각 명령을 실행한다. 승인된 권한 행렬과 오류 코드가 일치하고 권한 우회 경로가 없는지 확인한다.

## [PM-3Y-22] 복제 상태와 RK 변경의 감사 이력이 정의되지 않았다

- 분류: 운영성
- 심각도: Major
- 근거 위치: 2-3절은 현재 REPLICATION 값만 조회하며 변경 이력은 문서 전체에서 누락
- 사실/추론 구분: 확인된 사실
- 영향 대상: 감사 담당자, 사고 대응, 고객지원

### 문제
현재 ON/OFF만 알 수 있고 누가 언제 왜 바꿨는지, 이전·새 RK가 무엇인지 확인할 방법이 없다. 실패한 변경 시도와 자동 엔진 선택 변화도 감사 대상인지 미정이다.

### 왜 중요한가
failover 후 특정 테이블만 비어 있으면 운영자는 OFF가 의도된 것인지 사고인지 확인해야 한다. 변경 이력이 없으면 배포 로그와 사람 기억에 의존해 복구가 늦어진다.

### 재현 또는 구체적 예제
월요일 `orders`가 OFF로 바뀌고 금요일 failover 후 주문이 부족하다고 하자. `db_class`에는 현재 OFF만 보인다. 변경 사용자, DDL, 시각, 당시 HA 모드가 없으면 원인을 규명하기 어렵다.

### 권고안
복제 상태·선택 RK·후보 변경마다 actor, timestamp, transaction/DDL, old/new 값, 성공/실패, source node를 감사 로그에 남긴다. 보존 기간과 조회 권한, 외부 SIEM 연동 필드도 정의한다.

### 검증 방법
성공·실패한 ON/OFF와 RK 교체를 여러 계정으로 실행한다. 감사 이벤트가 누락 없이 생성되고 rollback된 DDL은 실패로 구분되며 검색 가능한지 확인한다.

## [PM-3Y-23] 파티션 테이블의 복제 상태와 RK 범위가 정의되지 않았다

- 분류: 누락
- 심각도: Critical
- 근거 위치: 1~4절은 일반 테이블만 설명하고 파티션 객체 상호작용은 누락
- 사실/추론 구분: 확인이 필요한 질문
- 영향 대상: 대용량 테이블 사용자, DBA, 복제 정합성

### 문제
CUBRID에서 대상 버전이 파티션 테이블을 지원하는 경우, ON/OFF가 부모와 파티션별 중 어디에 저장되는지, RK의 유일성이 전체 테이블인지 파티션 내부인지, 파티션 추가·교환·분할 때 정책이 상속되는지 없다.

### 왜 중요한가
파티션별로만 유일한 키를 전체 RK로 사용하면 다른 파티션의 같은 값 두 행을 구별하지 못할 수 있다. 새 파티션이 기본 OFF 또는 RK 없음으로 만들어지면 일부 기간 데이터만 복제되지 않는다.

### 재현 또는 구체적 예제
```sql
-- 실제 파티션 문법과 지원 범위는 대상 CUBRID 버전에서 확인 필요
CREATE TABLE sales (sale_date DATE, id INT, amount INT, PRIMARY KEY(sale_date,id))
REPLICATION=ON;
```
월별 파티션을 추가할 때 ON과 복합 RK가 자동 상속되는지, 파티션 교환 데이터도 복제되는지 문서에 없다.

### 권고안
지원 여부를 먼저 명시하고, 지원한다면 부모/자식 상태, global/local uniqueness, attach/detach/exchange/split/merge의 상태 전이와 오류를 별도 표로 제공한다.

### 검증 방법
지원되는 파티션 DDL별로 ON/OFF와 RK 후보를 조합한다. 파티션 경계 양쪽에 같은 키 값을 넣고 DML·failover 후 행이 정확히 일치하는지 확인한다.

## [PM-3Y-24] CREATE LIKE·복제·테이블 복사 시 REPLICATION 상속 정책이 없다

- 분류: 호환성
- 심각도: Major
- 근거 위치: 2-1절은 직접 CREATE TABLE만 다루며 기존 테이블 기반 생성은 누락
- 사실/추론 구분: 확인이 필요한 질문
- 영향 대상: 배치 개발자, 스키마 도구, 임시·백업 테이블 사용자

### 문제
대상 버전에서 `CREATE TABLE ... LIKE`, `AS SELECT` 또는 유사 복사 기능을 지원한다면 원본의 ON/OFF와 PK/UK를 새 테이블이 상속하는지 없다. 문법 지원 여부도 원문에서 확인되지 않는다.

### 왜 중요한가
구조 복사 명령은 보관·스테이징 테이블에 자주 쓰인다. 키 제약은 복사되지 않고 ON만 기본 적용되면 HA 모드에서 생성 실패할 수 있고, OFF 원본을 ON으로 복사하면 의도와 다른 복제 비용이 생긴다.

### 재현 또는 구체적 예제
```sql
-- 정확한 지원 문법은 확인 필요
CREATE TABLE orders_archive LIKE orders;
```
`orders`가 ON이고 PK가 있을 때 archive의 상태와 키, 또는 `cache OFF`를 복사할 때 새 테이블 상태가 무엇인지 정의되지 않았다.

### 권고안
지원하는 모든 파생 생성 문법별로 데이터·제약·REPLICATION 상속 여부를 표로 정한다. 위험한 암묵 상속보다 명시 옵션을 요구하거나 결과 경고를 제공한다.

### 검증 방법
ON/OFF와 PK/UK 유무가 다른 원본을 각 파생 문법으로 복사한다. 생성 결과, HA 허용 여부, `SHOW CREATE`가 승인된 행렬과 일치하는지 확인한다.

## [PM-3Y-25] bulk load·TRUNCATE 등 대량 변경 경로의 복제 계약이 없다

- 분류: 누락
- 심각도: Critical
- 근거 위치: 1절은 일반 DDL/DML을 언급하지만 대량 적재·TRUNCATE의 취급은 누락
- 사실/추론 구분: 확인이 필요한 질문
- 영향 대상: 배치 사용자, 데이터 이관, 복제 성능·정합성

### 문제
일반 INSERT 외 load utility, bulk insert, `TRUNCATE TABLE`, direct-path에 해당하는 기능이 REPLICATION ON/OFF를 어떻게 따르는지 없다. `loaddb`는 DB 복원만 설명하고 운영 중 대량 적재와 구분되지 않는다.

### 왜 중요한가
대량 경로가 row log를 우회하면 ON인데도 데이터가 복제되지 않을 수 있다. 반대로 수억 건을 row-by-row 로그로 보내면 저장 공간과 apply 지연이 급증해 failover 준비가 늦어진다.

### 재현 또는 구체적 예제
```sql
TRUNCATE TABLE event_stage;
-- 이후 지원되는 bulk 도구로 1억 행 적재
```
TRUNCATE가 DDL로 양 노드에 반영되는지, bulk 데이터는 ON에서 전달되고 OFF에서 제외되는지, 진행 중 failover 결과가 없다.

### 권고안
지원되는 모든 대량 변경 경로를 목록화하고 log 생성, atomicity, 취소, 복제 지연·공간 요구와 failover 제한을 명시한다. HA-safe/unsafe 도구를 구분한다.

### 검증 방법
일반 INSERT, bulk utility, TRUNCATE 후 적재를 ON/OFF에서 실행하고 중간 failover를 주입한다. 행 수·checksum과 로그량이 문서 계약과 같은지 확인한다.

## [PM-3Y-26] 온라인 DDL의 진행률·취소·서비스 영향 계약이 없다

- 분류: 운영성
- 심각도: Major
- 근거 위치: 4-2절은 운영 중 RK 변경을 허용하지만 실행 시간과 취소 절차를 설명하지 않음
- 사실/추론 구분: 확인이 필요한 질문
- 영향 대상: 운영 배포, 대형 테이블, 애플리케이션 가용성

### 문제
RK 후보 UK를 대형 테이블에 추가할 때 online 동작인지, 어떤 잠금이 걸리는지, 진행률·예상 시간·취소 후 상태가 무엇인지 없다. 온라인 DDL 지원 범위 자체도 확인 필요하다.

### 왜 중요한가
새 UK는 모든 행의 중복을 검사하고 인덱스를 만들어야 한다. 수억 행에서 장시간 쓰기를 막으면 데이터 보호 기능을 켜는 작업이 서비스 장애를 만들 수 있다.

### 재현 또는 구체적 예제
```sql
ALTER TABLE customer ADD CONSTRAINT uq_customer_email UNIQUE(email);
```
5억 행에서 60% 진행 중 배포를 취소하거나 lock timeout이 나면 부분 index가 남는지, 기존 RK와 서비스가 유지되는지 없다.

### 권고안
DDL별 lock 수준, 온라인 지원, 진행률 조회, resource limit, 취소·재시도·cleanup, 최대 허용 정지 시간을 정의한다. 대형 테이블 권장 단계와 유지보수 창 판단 기준을 제공한다.

### 검증 방법
대형 테이블 쓰기 부하 중 UK 생성·취소·timeout·재시도를 수행한다. 요청 지연, 진행률, cleanup과 양 노드 RK가 수용 기준을 만족하는지 확인한다.

## [PM-3Y-27] 병렬 apply에서 RK DDL이 순서 장벽인지 정의되지 않았다

- 분류: 정확성
- 심각도: Blocker
- 근거 위치: 4절의 DDL/DML 복제 순서만 언급하고 병렬 적용 상호작용은 누락
- 사실/추론 구분: 확인이 필요한 질문
- 영향 대상: 복제 엔진, 고처리량 고객, 데이터 정합성

### 문제
대상 버전에서 병렬 apply를 지원하거나 향후 지원할 경우, 서로 다른 worker가 옛 RK DML과 새 RK DDL을 재정렬할 수 있는지 없다. DDL 전후 작업을 모두 drain하는 barrier가 필요한지 미정이다.

### 왜 중요한가
source commit 순서가 맞아도 replica worker가 DDL을 먼저 적용하면 옛 키 로그를 해석하지 못한다. 병렬성은 성능을 높이지만 schema 변경 경계에서는 정확성을 위해 순서를 제한해야 한다.

### 재현 또는 구체적 예제
T1이 `UPDATE account ... WHERE id=10`, T2가 id→email RK 변경, T3가 email 기반 UPDATE를 순서대로 커밋한다. 세 worker가 T2, T1, T3 순으로 적용하면 첫 DML이 실패할 수 있다.

### 권고안
병렬 apply 지원 여부를 명시하고 RK/REPLICATION DDL을 전역 barrier로 정의한다. barrier 전 transaction 완료, schema cache 무효화, 이후 worker 재개 조건을 규정한다.

### 검증 방법
worker 수를 바꾸고 transaction 처리 시간을 인위적으로 지연시킨다. 모든 interleaving에서 source commit 순서와 동등한 결과 및 `fail_count=0`을 확인한다.

## [PM-3Y-28] PITR 시점과 복제 로그 보관 한계의 복구 계약이 없다

- 분류: 호환성
- 심각도: Critical
- 근거 위치: 8절은 unload/load만 설명하며 시점 복구와 후속 로그 적용은 누락
- 사실/추론 구분: 확인이 필요한 질문
- 영향 대상: 재해 복구, 백업 담당자, RPO/RTO

### 문제
PITR(point-in-time recovery)을 대상 구성에서 지원하는지, 백업 시점의 선택 RK와 이후 DDL/DML 로그가 함께 보존되는지 없다. 필요한 RK 정의 로그가 보관 만료되면 후속 DML을 해석할 수 있는지도 미정이다.

### 왜 중요한가
PITR은 백업 이후 로그를 순서대로 재생해 특정 시점으로 돌아가는 방식이다. 중간 RK 변경 기록이 없고 DML만 남으면 어느 키로 행을 찾을지 알 수 없어 목표 시점 복구가 불가능하다.

### 재현 또는 구체적 예제
01:00 full backup, 02:00 id→email RK 변경, 03:00 email DML, 04:00 사고라고 하자. 03:30으로 복구할 때 02:00 DDL 로그가 만료됐다면 03:00 로그만 적용할 수 없다.

### 권고안
지원 복구 방식별 backup manifest에 REPLICATION·RK version을 넣고 DDL/DML 로그의 공동 보관 하한을 정의한다. 보관 부족 시 사전 경고와 새 baseline backup 요구를 제공한다.

### 검증 방법
RK 변경 전 backup을 복원해 변경 후 로그를 적용하고 여러 목표 시점을 시험한다. 필요한 로그를 일부 제거했을 때 조용한 부분 복구가 아니라 명확히 차단되는지 확인한다.

## [PM-3Y-29] 디스크 full·메모리 부족 시 RK 변경의 제품 동작이 없다

- 분류: 운영성
- 심각도: Critical
- 근거 위치: 4-2절의 RK 교체 성공/단순 ERROR 예만 있으며 자원 고갈은 누락
- 사실/추론 구분: 확인이 필요한 질문
- 영향 대상: 대형 테이블, source/replica, 장애 대응

### 문제
새 UK index 생성, DDL 로그 저장, replica apply 중 디스크나 메모리가 부족할 때 rollback, retry, HA 상태가 정의되지 않았다. source만 성공하고 standby가 실패하는 부분 성공이 특히 위험하다.

### 왜 중요한가
자원 고갈은 일반 운영에서 발생한다. standby가 옛 RK에 멈춘 채 source가 새 RK DML을 계속 보내면 오류가 연쇄적으로 늘고 안전한 failover가 불가능해진다.

### 재현 또는 구체적 예제
source에서 email UK 생성은 성공하지만 standby index build 90%에 디스크가 가득 찬다. 이후 email을 RK로 쓰는 UPDATE와 source 장애가 발생하면 standby를 승격할 수 있는지 없다.

### 권고안
자원 사전 산정·예약, source/standby 원자성의 한계, apply barrier, 자동 retry와 수동 resync 조건을 정의한다. 불완전 RK DDL이 있는 노드는 승격 불가로 표시한다.

### 검증 방법
source와 standby 각각에 disk full·메모리 제한을 단계별 주입한다. 부분 schema가 남지 않고 후속 로그/승격이 안전하게 차단되며 복구 절차가 성공하는지 확인한다.

## [PM-3Y-30] 네트워크 분할과 split-brain에서 OFF/RK 변경 충돌 정책이 없다

- 분류: 정확성
- 심각도: Blocker
- 근거 위치: 4·7절은 정상적인 master/slave와 failover만 가정하며 네트워크 분할은 누락
- 사실/추론 구분: 확인이 필요한 질문
- 영향 대상: HA coordinator, 애플리케이션, 데이터 정합성

### 문제
네트워크 분할로 두 노드가 모두 쓰기를 받는 split-brain 상황에서 한쪽은 OFF, 다른 쪽은 RK 변경을 수행할 수 있는지, 재결합 시 어느 스키마와 데이터를 선택하는지 없다.

### 왜 중요한가
같은 행에 서로 다른 RK와 데이터가 생기면 단순 로그 재생으로 합칠 수 없다. OFF 테이블은 양쪽 변경이 원래부터 복제되지 않아 충돌 범위를 더 찾기 어렵다.

### 재현 또는 구체적 예제
노드 A는 `orders REPLICATION=OFF`로 바꾸고 주문 101을 생성하며, 분리된 노드 B는 PK를 email UK로 바꾸고 주문 102를 생성한다. 네트워크 복구 후 자동 병합은 안전하지 않다.

### 권고안
quorum/fencing으로 단일 writer를 보장하고 fencing이 없는 상태에서는 RK·REPLICATION DDL을 금지한다. split-brain 탐지, 권위 노드 선택, 폐기·재구축 조건을 장애 절차로 명시한다.

### 검증 방법
heartbeat와 복제 네트워크를 분리해 양쪽 DDL/DML을 시도한다. 한쪽 쓰기가 차단되고 재결합 후 schema/RK/data가 하나의 권위 상태로 수렴하는지 확인한다.

## [PM-3Y-31] 반복 apply 실패와 재시작에 대한 격리·재시도 한계가 없다

- 분류: 운영성
- 심각도: Major
- 근거 위치: 문서 전체에 `fail_count` 이후 자동 retry·quarantine 정책이 없음
- 사실/추론 구분: 확인이 필요한 질문
- 영향 대상: 운영자, 복제 가용성, 장애 자동화

### 문제
같은 RK 관련 로그가 계속 실패할 때 무한 재시도하는지, 건너뛰는지, 노드를 격리하는지 없다. 재시작할 때 `fail_count`와 실패 위치가 보존되는지도 미정이다.

### 왜 중요한가
무한 재시도는 CPU와 로그를 소모하고 후속 변경 적용을 막는다. 건너뛰면 데이터가 조용히 어긋난다. 재시작만으로 카운터가 초기화되면 장애가 해결된 것처럼 보일 수 있다.

### 재현 또는 구체적 예제
standby가 RK로 찾을 행이 없어 같은 UPDATE에서 100회 실패하고 프로세스가 재시작된다. 다시 첫 로그부터 100회 실패한다면 장애 폭주가 반복된다.

### 권고안
오류별 최대 retry/backoff, fatal barrier, node quarantine, operator acknowledgement와 resync 조건을 정의한다. 실패 LSA와 원인은 재시작 후에도 보존하고 상태 API에 노출한다.

### 검증 방법
영구 row-not-found와 일시 I/O 오류를 각각 주입하고 재시작한다. 일시 오류는 제한 내 복구되고 영구 오류는 건너뛰지 않은 채 격리·경보되는지 확인한다.

## [PM-3Y-32] ORM·schema diff 도구가 새 메타데이터를 보존할 계약이 없다

- 분류: 호환성
- 심각도: Major
- 근거 위치: 2-3절의 csql 조회 예만 있고 드라이버·도구 API는 누락
- 사실/추론 구분: 확인이 필요한 질문

### 문제
드라이버 metadata API, ORM introspection, schema diff가 REPLICATION과 선택 RK를 읽고 다시 생성할 수 있는지 없다. 지원하지 않는 도구가 OFF를 누락하면 기본 ON으로 재생성할 수 있다.

### 왜 중요한가
현업은 수동 SQL보다 migration 도구를 사용한다. round-trip에서 정책이 사라지면 배포 성공 후에야 복제 부하나 failover 결과가 달라진 것을 발견한다.

`cache REPLICATION=OFF`를 ORM이 introspect하고 migration을 생성한다. 새 DB CREATE에 OFF가 빠지면 동일 모델인데 운영 계약은 ON으로 바뀐다.

### 권고안
표준 metadata 필드와 지원 드라이버/ORM 버전, 미지원 시 raw SQL 및 post-deploy 검증을 문서화한다. schema diff에서 ON/OFF와 선택 RK를 first-class 속성으로 취급한다.

### 검증 방법
지원 도구마다 introspect→diff→recreate round-trip을 수행한다. REPLICATION과 RK가 보존되고 변경 없는 schema에 불필요한 migration이 생기지 않는지 확인한다.

## [PM-3Y-33] 인덱스 재구축·제약 rename·통계 갱신이 RK를 바꾸는지 없다

- 분류: 모호성
- 심각도: Major
- 근거 위치: 1절의 엔진 선택과 4-2절의 DROP INDEX만 설명, 유지보수 작업은 누락
- 사실/추론 구분: 확인이 필요한 질문
- 영향 대상: DBA 유지보수, 선택 RK 지속성, 성능

### 왜 중요한가
성능 유지보수는 정기적으로 수행된다. 논리 스키마가 같아도 내부 index ID가 바뀌어 RK가 바뀐다면 대기 로그와 충돌할 수 있다. 통계 때문에 RK가 바뀌면 결과를 재현하기도 어렵다.

### 권고안
RK 선택은 optimizer 통계와 분리하고 논리적 영구 ID에 연결한다. rename/rebuild/reorganize별 RK 유지·변경 규칙과 로그 호환성을 표로 정의한다.

### 검증 방법
각 유지보수 작업 전후 선택 RK ID와 대기 DML apply를 비교한다. 통계 값을 크게 바꿔도 RK 선택이 계약대로 안정적인지 확인한다.

## [PM-3Y-34] 기능 플래그·라이선스·에디션별 사용 가능 범위가 없다

- 분류: 호환성
- 심각도: Major
- 근거 위치: 문서 전체가 기능이 항상 사용 가능하다고 가정하고 배포 활성화 조건은 누락
- 사실/추론 구분: 확인이 필요한 질문
- 영향 대상: 제품 배포, 영업·지원, 자동화 사용자

### 문제
새 문법이 버전 업그레이드 즉시 활성화되는지, 기능 플래그가 필요한지, 에디션/라이선스에 따라 차이가 있는지 없다. 실제로 차이가 없다면 그 사실도 사용자 계약으로 명시할 필요가 있다.

### 왜 중요한가
노드별 설정이 다르면 source는 DDL을 허용하고 standby는 알지 못할 수 있다. 자동 배포는 환경마다 다른 오류를 내고, downgrade 또는 긴급 rollback 계획도 세우기 어렵다.

### 재현 또는 구체적 예제
신버전 source에서 플래그 ON, standby에서 OFF인 상태로 `ALTER TABLE cache REPLICATION=OFF`를 실행한다고 하자. 연결 차단, DDL 거부, apply 실패 중 무엇인지 없다.

### 권고안
버전·에디션·라이선스·feature flag 행렬과 클러스터 전체 활성화 사전 조건을 제공한다. capability가 다르면 HA 시작 또는 DDL 전에 명확히 차단한다.

### 검증 방법
지원되는 설정 조합과 불일치 조합을 구성한다. 지원 기능은 일관되게 작동하고 불일치는 사전 진단에서 탐지되며 부분 적용되지 않는지 확인한다.

## [PM-3Y-35] downgrade 시 되돌릴 수 없는 카탈로그·로그 경계가 없다

- 분류: 호환성
- 심각도: Blocker
- 근거 위치: 8절은 하위 버전 unload 입력만 다루고 신버전에서 구버전으로 되돌리는 절차는 누락
- 사실/추론 구분: 확인이 필요한 질문
- 영향 대상: 릴리스 rollback, 기존 HA 고객, 지원 조직

### 문제
새 REPLICATION catalog 필드나 RK log record를 한 번 사용한 뒤 binary downgrade가 가능한지, 구버전이 모르는 정보를 어떻게 보존할지 없다. 롤링 업그레이드 실패 시 원복 가능한 마지막 지점도 미정이다.

### 왜 중요한가
배포 장애 때 제품팀은 빠르게 이전 버전으로 돌아가려 한다. 구버전이 새 로그를 읽지 못하면 실행은 되더라도 복제가 중단되거나 OFF를 ON으로 해석할 수 있어 단순 binary 교체가 위험하다.

### 재현 또는 구체적 예제
신버전에서 `cache OFF`와 PK→UK RK 변경을 실행한 뒤 엔진 문제로 구버전 binary로 되돌린다. 구버전 catalog reader와 replica가 이 상태를 읽는지, full rebuild가 필요한지 없다.

### 권고안
upgrade epoch와 irreversible operation을 정의하고 그 전/후 rollback 절차를 나눈다. downgrade 전 새 DDL 금지·상태 변환·새 baseline backup/full resync 요구와 자동 호환성 검사를 제공한다.

### 검증 방법
새 기능 미사용/ON-OFF 사용/RK 변경의 세 시점에서 downgrade를 시험한다. 지원 경로는 데이터·복제 상태를 보존하고 미지원 경로는 실행 전에 명확히 차단되는지 확인한다.
