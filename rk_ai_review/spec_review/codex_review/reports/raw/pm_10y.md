## [PM-10Y-01] 해결하려는 장애와 RK 정책 사이의 수용 기준이 없다

- 분류: 컨셉
- 심각도: Blocker
- 근거 위치: 문서 전체 및 1절; RK가 없으면 HA를 시작할 수 없고 엔진이 PK/UK에서 RK를 고른다고 설명한다.
- 사실/추론 구분: 문서에서 도출한 추론
- 영향 대상: 제품 의사결정자, 복제 정합성, QA, 사용자

### 문제
문서는 새 RK 정책을 설명하지만 원래 문제인 PK 변경 중 복제 누락, `fail_count` 증가, 마스터·슬레이브 불일치를 어떤 조건에서 완전히 차단해야 하는지 명시하지 않는다. 기능이 구현돼도 원래 장애가 해결됐는지 판정할 수 없다.

### 왜 중요한가
RK 후보가 항상 있다는 사실과 복제 로그가 올바른 키 버전을 사용한다는 사실은 다르다. PK를 A에서 B로 바꾸는 동안 이미 기록된 DML이 옛 키 A를 참조한다면, 새 키 B만 아는 슬레이브는 여전히 행을 찾지 못할 수 있다.

### 재현 또는 구체적 예제
`t(a PRIMARY KEY, b NOT NULL UNIQUE, v)`에서 `UPDATE t SET v=1 WHERE a=10` 로그가 생성된 직후 PK를 `b`로 교체한다. 복제가 지연된 슬레이브에 DDL이 먼저 보이거나 로그에 RK 버전이 없다면 업데이트가 누락될 수 있다. 기대 결과는 어떤 순서에서도 누락 0건, `fail_count` 증가 0, 양 노드 체크섬 일치다.

### 권고안
제품 수용 기준에 “지원되는 모든 RK 변경과 장애 주입 시 DML 누락 0건, 잘못된 행 변경 0건, 적용 실패 0건, 최종 데이터 일치”를 넣고 보장 방식도 로그 순서 또는 스키마 버전으로 명시한다.

### 검증 방법
복제 지연, DDL 직전·직후 크래시, failover를 조합한 회귀 시험에서 행 단위 결과와 `fail_count`를 비교한다.

## [PM-10Y-02] MySQL식 전체 컬럼 식별과 제안 방식의 비교가 검증되지 않았다

- 분류: 컨셉
- 심각도: Major
- 근거 위치: 문서 전체; PK 또는 NOT NULL UK를 RK로 제한하는 설계만 제시한다.
- 사실/추론 구분: 확인이 필요한 질문
- 영향 대상: 제품 전략, 성능, PK 없는 기존 사용자

### 문제
제안이 PK 없는 테이블에서 모든 컬럼을 사용하는 방법보다 빠르다는 배경은 타당할 수 있지만, 대상 워크로드와 정량 기준이 없다. 그 대신 PK/UK 없는 테이블을 HA에서 거부하여 호환성 비용을 사용자에게 넘긴다.

### 왜 중요한가
성능과 호환성은 교환 관계다. 작은 테이블은 전체 컬럼 비교도 충분히 빠를 수 있지만, 새 정책은 그 테이블을 아예 복제하지 못하게 한다. 반대로 큰 문자열 UK는 PK보다 로그와 인덱스 비용이 클 수 있다.

### 재현 또는 구체적 예제
10행짜리 설정 테이블 `config(k, v)`에 키가 없다고 가정한다. 기존에는 HA가 시작됐지만 새 버전에서는 RK 부재로 중단될 수 있다. 제품은 “중단 시간”과 “절감된 복제 비용” 중 무엇을 우선하는지 설명해야 한다.

### 권고안
대표 테이블 크기와 키 형태별 벤치마크, 기존 PK 없는 테이블 수, 전환 비용을 제시하고 전체 컬럼 fallback을 지원하지 않는 이유를 명시한다. 타 DB 비교는 공식 문서와 특정 버전을 인용한다.

### 검증 방법
정수 PK, 짧은 UK, 긴 복합 UK, 키 없음 워크로드에서 처리량·로그 크기·적용 지연과 마이그레이션 실패율을 측정한다.

## [PM-10Y-03] REPLICATION OFF가 정합성 문제를 기능이 아닌 면책 문구로 남긴다

- 분류: 컨셉
- 심각도: Critical
- 근거 위치: 1절, 4절, 6절; OFF 데이터 불일치는 책임지지 않으며 DDL은 복제된다고 한다.
- 사실/추론 구분: 확인된 사실
- 영향 대상: 최종 사용자, failover 안전성, 지원 조직

### 문제
OFF 테이블의 스키마만 슬레이브에 있고 데이터는 없다는 위험을 단순히 책임 범위 밖으로 둔다. 그러나 VIEW, FK, 애플리케이션 조인 등 다른 객체가 OFF 테이블에 의존하면 ON 테이블까지 의미가 달라진다.

### 왜 중요한가
사용자는 HA를 데이터가 보존되는 기능으로 이해한다. 빈 테이블이 정상적으로 조회된다는 점은 명시적 오류보다 위험하다. 잘못된 빈 결과가 비즈니스 결정에 사용될 수 있기 때문이다.

### 재현 또는 구체적 예제
`tax_rate`를 OFF, `orders`를 ON으로 두고 둘을 조인하는 뷰를 만든다. failover 후 주문은 남지만 세율이 없어 합계가 `NULL` 또는 0으로 계산될 수 있다. SQL은 성공하므로 사용자가 장애를 즉시 알기 어렵다.

### 권고안
OFF를 로컬/휘발성 데이터라는 명시적 제품 개념으로 정의하고, 의존 객체 생성 시 경고 또는 거부 정책, failover 전 영향 목록, 관리 화면 표시를 제공한다.

### 검증 방법
VIEW·트리거·FK·프로시저·조인 의존성을 구성하고 failover 전후 결과 및 경고가 계약과 일치하는지 검사한다.

## [PM-10Y-04] RK 후보와 현재 선택된 RK의 사용자 계약이 분리되지 않았다

- 분류: 모호성
- 심각도: Critical
- 근거 위치: 1절과 4-2절; PK/UK 중 하나를 엔진이 선택하며 사용자가 직접 수정할 수 없다고 한다.
- 사실/추론 구분: 확인된 사실
- 영향 대상: DBA, 애플리케이션 개발자, 지원 조직

### 문제
문서는 “RK”, “RK 후보”, “하나 이상 존재”를 섞어 쓴다. 후보가 두 개인 경우 실제 선택값, 선택 시점, 재선택 조건과 지속 여부가 사용자 계약에 없다.

### 왜 중요한가
사용자가 삭제 가능한 키를 판단하려면 현재 RK를 알아야 한다. SHOW CREATE TABLE이 ON/OFF만 보여 주고 실제 RK를 숨기면 DDL 결과를 사전에 예측할 수 없다.

### 재현 또는 구체적 예제
`a PRIMARY KEY`, `b NOT NULL UNIQUE`가 있는 테이블에서 PK를 삭제하면 b가 즉시 RK가 되는지, 재시작 후에도 b인지, PK를 다시 만들면 PK로 돌아가는지 알 수 없다.

### 권고안
후보 집합, 선택 RK, 선택 우선순위, 전환 시점, 영속성, 조회 API를 각각 정의하고 `SHOW REPLICATION KEY FROM t` 같은 관찰 방법을 제공한다.

### 검증 방법
키 추가·삭제·재생성·재시작·failover마다 카탈로그와 양 노드의 선택 RK가 같은지 확인한다.

## [PM-10Y-05] 모드 명칭과 적용 범위가 제품 전체 용어 체계와 맞지 않는다

- 분류: 문서 품질
- 심각도: Major
- 근거 위치: 1절, 3절, 9절; `cubrid hb start` 외에는 모두 single이라고 하면서 summary에는 SA를 별도로 쓴다.
- 사실/추론 구분: 확인된 사실
- 영향 대상: 사용자, 기술지원, 문서 작성자

### 문제
single, SA, HA 실행 중, HA 전환 전 상태의 관계가 일관되지 않다. 명령 하나를 실행했다는 사실만으로 모든 서버와 DB가 동일한 HA 상태인지도 불명확하다.

### 왜 중요한가
같은 ALTER가 어느 모드에서는 성공하고 다른 모드에서는 거부되므로 모드 판정은 기능 계약의 일부다. 용어가 흔들리면 사용자가 위험한 변경을 잘못된 절차로 실행한다.

### 재현 또는 구체적 예제
사용자가 SA 모드에서 `REPLICATION=ON`인 무키 테이블을 만든 뒤 서버 모드로 기동만 하고 아직 standby가 연결되지 않은 상황을 생각한다. 문서만으로 어느 검사가 언제 실행되는지 판단할 수 없다.

### 권고안
공식 상태 이름과 전이 다이어그램을 추가하고, 각 SQL 및 HA 검사가 허용되는 상태 표를 제공한다.

### 검증 방법
각 공식 기동 방식에서 동일 SQL 세트를 실행하여 문서의 허용/거부 표와 결과를 대조한다.

## [PM-10Y-06] REPLICATION 기본값 ON은 업그레이드 시 서비스 중단을 만들 수 있다

- 분류: 호환성
- 심각도: Critical
- 근거 위치: 2-1절; 옵션 생략 시 ON이며 무키 테이블은 HA 전환 시 오류가 난다.
- 사실/추론 구분: 문서에서 도출한 추론
- 영향 대상: 기존 사용자, DBA, 배포 관리자

### 문제
기존 DDL에는 새 옵션이 없으므로 모두 ON으로 해석된다. PK/NOT NULL UK가 없는 기존 테이블이 하나라도 있으면 업그레이드 후 HA 시작이 중단될 수 있다.

### 왜 중요한가
안전한 기본값은 신규 객체뿐 아니라 기존 카탈로그와 구버전 dump에도 정의돼야 한다. 기본 ON은 데이터 보호에는 보수적이지만 가용성 측면에서는 파괴적 변경이다.

### 재현 또는 구체적 예제
기존 HA DB에 `CREATE TABLE audit_raw(ts DATETIME, msg STRING)`가 있다고 가정한다. 업그레이드 후 이 객체가 암묵적 ON이면 RK가 없어 `cubrid hb start` 전체가 실패할 수 있다.

### 권고안
업그레이드 전 진단 도구, 자동 생성되는 수정 SQL, 유예/호환 모드, 릴리스 노트의 중단 가능성을 정의한다. 기존 객체의 기본값은 별도 마이그레이션 결정으로 취급한다.

### 검증 방법
여러 구버전 카탈로그와 dump를 새 버전으로 올리고 HA 시작 결과와 진단 메시지 및 되돌리기 절차를 시험한다.

## [PM-10Y-07] 복합 ALTER의 원자성과 실패 계약이 빠졌다

- 분류: 정확성
- 심각도: Blocker
- 근거 위치: 2-2절 예시 7과 4-2절 예시 13; 한 문장에서 기존 키 삭제와 새 키 추가를 허용한다.
- 사실/추론 구분: 확인이 필요한 질문
- 영향 대상: 복제 정합성, DBMS 구현, DBA

### 문제
새 키 추가가 데이터 중복이나 NULL 때문에 실패할 때 기존 키 삭제까지 롤백되는지 설명하지 않는다. 중간에 RK가 없는 상태가 외부에 보이는지도 정의되지 않았다.

### 왜 중요한가
두 동작이 원자적이지 않으면 “항상 RK 후보가 하나 이상”이라는 핵심 불변식이 깨진다. 마스터만 일부 성공하면 슬레이브와 스키마도 달라진다.

### 재현 또는 구체적 예제
`a`가 PK이고 `b`에 중복값이 있는 상태에서 `DROP PK, ADD UNIQUE(b)`를 실행한다. 기대 결과는 전체 실패와 기존 PK/RK 보존이어야 하지만 문서에는 `ERROR` 후 상태가 없다.

### 권고안
복합 ALTER 전체의 검증 순서, 잠금, 커밋 단위, 복제 로그 단위, 실패 시 원상복구를 명시적인 불변식과 함께 규정한다.

### 검증 방법
중복, NULL, 디스크 부족, 강제 종료를 각 단계에 주입하고 양 노드 카탈로그와 RK가 변경 전 상태인지 검사한다.

## [PM-10Y-08] REPLICATION ON/OFF 전환의 데이터 동기화 의미가 정의되지 않았다

- 분류: 정확성
- 심각도: Blocker
- 근거 위치: 2-2절; HA에서 ON→OFF는 허용하고 OFF→ON은 금지한다. single에서는 모두 허용한다고 한다.
- 사실/추론 구분: 문서에서 도출한 추론
- 영향 대상: 데이터 정합성, DBA, failover

### 문제
ON→OFF 시 이미 복제된 슬레이브 데이터가 남는지 삭제되는지, 다시 single에서 ON으로 바꾸면 기존 차이를 어떻게 맞추는지 없다.

### 왜 중요한가
옵션은 미래 DML만 제어할 수도 있고 테이블 전체 상태를 의미할 수도 있다. 이 차이를 정의하지 않으면 같은 `REPLICATION=ON` 테이블인데도 시작 시점에 따라 데이터가 다르다.

### 재현 또는 구체적 예제
100행이 양 노드에 있는 t를 HA에서 OFF로 바꾸고 마스터에 50행을 추가한다. 슬레이브에는 100행이 남는지 0행인지 알 수 없다. single 전환 후 다시 ON으로 하면 50행을 자동 복사하는지도 알 수 없다.

### 권고안
전환별 데이터 수명주기 표를 만들고 OFF→ON에는 full sync 또는 명시적 재구축 절차와 완료 전 쓰기 차단 정책을 정의한다.

### 검증 방법
각 전환 지점에서 행 수·체크섬·복제 로그 위치를 기록하고 재시작과 failover 후 결과를 확인한다.

## [PM-10Y-09] DDL과 선행·후행 DML의 순서 보장이 없다

- 분류: 정확성
- 심각도: Blocker
- 근거 위치: 4절; 모든 DDL은 복제되며 RK 변경 조건만 설명한다.
- 사실/추론 구분: 확인이 필요한 질문
- 영향 대상: 복제 정합성, 애플리케이션

### 문제
RK를 바꾸는 DDL 앞뒤의 DML이 어떤 키 스키마로 인코딩되고 슬레이브에서 어떤 순서로 적용되는지 빠졌다.

### 왜 중요한가
로그 순서가 같더라도 병렬 apply나 트랜잭션 경계 때문에 적용 시점이 달라질 수 있다. 옛 로그를 새 RK로 검색하면 원래 장애가 재현된다.

### 재현 또는 구체적 예제
트랜잭션 A가 `a=1` 행을 갱신하는 동안 트랜잭션 B가 RK를 a에서 b로 바꾸고, A가 나중에 커밋한다. A의 로그가 어느 키를 가져야 하는지 문서에 없다.

### 권고안
DDL 잠금과 동시 트랜잭션 정책, 로그에 포함되는 스키마/RK 버전, apply 직렬화 범위를 사용자 계약 및 구현 요구사항으로 추가한다.

### 검증 방법
DDL과 장시간 DML 트랜잭션의 시작·커밋 순서를 모두 조합하고 병렬 apply 및 지연 상태에서 결과를 비교한다.

## [PM-10Y-10] HA 시작 검사가 전체 클러스터에 대해 원자적인지 불명확하다

- 분류: 운영성
- 심각도: Critical
- 근거 위치: 7절; 위반 시 에러와 파일 리스트를 출력한다고 한다.
- 사실/추론 구분: 확인이 필요한 질문
- 영향 대상: DBA, 서비스 가용성

### 문제
여러 DB 또는 노드 중 일부 검사가 실패했을 때 이미 시작된 프로세스가 남는지, 검사 중 스키마가 바뀌면 스냅샷이 일관적인지 정의하지 않는다. “파일 리스트”도 실제로는 테이블 목록인지 불명확하다.

### 왜 중요한가
부분 기동은 사용자가 HA가 활성화됐다고 오판하게 만들고, 검사 직후 RK가 제거되면 검사 자체가 무효가 된다.

### 재현 또는 구체적 예제
DB A는 유효하고 DB B에는 무키 ON 테이블이 있다. `cubrid hb start`가 A만 기동한 뒤 B에서 실패하면 명령의 최종 상태와 정리 절차가 필요하다.

### 권고안
검사 스냅샷, 잠금 범위, all-or-nothing 여부, 부분 실패 후 프로세스 상태, 재시도 가능성, 구조화된 오류 목록을 정의한다.

### 검증 방법
다중 DB 구성에서 검사 도중 DDL·프로세스 종료를 주입하고 명령 종료 코드와 실제 프로세스·노드 상태를 대조한다.

## [PM-10Y-11] failover 시 허용되는 데이터 차이와 서비스 차단 기준이 없다

- 분류: 누락
- 심각도: Critical
- 근거 위치: 4절과 6절; OFF로 데이터가 다를 수 있으나 failover 자체의 판정 규칙은 없다.
- 사실/추론 구분: 문서에서 도출한 추론
- 영향 대상: 사용자, HA 오케스트레이션, 지원 조직

### 문제
standby에 OFF 데이터가 없고 복제 지연 또는 실패가 있을 때 승격을 계속 허용하는지, 사용자에게 어떤 위험 신호를 주는지 없다.

### 왜 중요한가
HA의 목적은 단순 프로세스 승격이 아니라 예측 가능한 서비스 지속이다. 승격은 성공했지만 데이터 의미가 달라지면 제품 수준에서는 실패일 수 있다.

### 재현 또는 구체적 예제
결제 제한값이 OFF 테이블에 있고 주문은 ON일 때 primary 장애가 난다. standby 승격 후 제한값이 없어 주문이 과승인될 수 있다.

### 권고안
필수 로컬 데이터 여부를 표시하는 정책, 승격 전 위험 검사, 강제 승격 옵션과 감사 로그, 애플리케이션 준비 상태 신호를 정의한다.

### 검증 방법
OFF 의존성이 있는 시스템에서 자동·수동 failover를 각각 실행하고 경고·차단·서비스 상태가 규정대로인지 확인한다.

## [PM-10Y-12] 여러 UK 중 선택 규칙이 비결정적일 수 있다

- 분류: 정확성
- 심각도: Blocker
- 근거 위치: 1절; 여러 UK 중 “예: 테이블 내 명시된 순서 중 가장 빠른 순서”를 엔진이 선택한다고 한다.
- 사실/추론 구분: 확인된 사실
- 영향 대상: 마스터·슬레이브 정합성, 백업·복원

### 문제
예시로만 제시된 순서는 정식 규칙이 아니다. DDL 재작성, unload/load, 카탈로그 OID 차이로 노드별 순서가 달라지면 서로 다른 RK를 선택할 수 있다.

### 왜 중요한가
같은 UPDATE도 마스터는 UK1, 슬레이브는 UK2로 이해할 수 있다. 특히 키 값 변경 로그의 해석이 다르면 누락이나 오적용 위험이 생긴다.

### 재현 또는 구체적 예제
`UNIQUE(email)`과 `UNIQUE(phone)`이 있는 테이블을 dump/load하면서 제약 출력 순서가 바뀐다. 복원된 노드가 phone을 RK로 선택하면 기존 로그와 호환되는지 불명확하다.

### 권고안
안정적인 제약 ID 또는 명시적 RK 카탈로그 값을 영속화하고, 자동 선택의 완전한 정렬 기준 및 노드 간 검증을 정의한다.

### 검증 방법
여러 UK를 다른 순서로 생성·dump/load·rename한 뒤 모든 노드의 RK 식별자와 로그 적용 결과를 비교한다.

## [PM-10Y-13] RK 컬럼 값 자체를 UPDATE하는 계약이 빠졌다

- 분류: 누락
- 심각도: Critical
- 근거 위치: 1절과 4절; 키 제약 DDL만 다루고 키 값 DML은 다루지 않는다.
- 사실/추론 구분: 확인이 필요한 질문
- 영향 대상: 복제 정합성, 애플리케이션 개발자

### 문제
RK가 된 PK/UK 컬럼의 값을 변경할 때 슬레이브 행 검색에 이전 값과 새 값 중 무엇을 쓰는지, 둘 다 로그에 포함되는지 없다.

### 왜 중요한가
새 값으로만 검색하면 슬레이브에는 아직 옛 값만 있어 행을 찾지 못한다. 이전 값이 재사용되거나 여러 변경이 연속되면 순서 보장도 필요하다.

### 재현 또는 구체적 예제
`email NOT NULL UNIQUE`가 RK인 행의 email을 `a@x`에서 `b@x`로 바꾼다. 슬레이브는 `a@x`로 찾은 뒤 `b@x`로 바꿔야 하며, 다른 행에 `b@x`가 있으면 전체 트랜잭션이 동일하게 실패해야 한다.

### 권고안
RK 값 변경 로그의 before/after image, 충돌 처리, 재시도와 멱등성 규칙을 명시한다.

### 검증 방법
단일·복합 RK의 값 변경, 값 교환, 연속 변경, 중복 충돌을 지연 복제와 재적용 조건에서 시험한다.

## [PM-10Y-14] 외래키 정책이 방향·연쇄·전환 조건을 모두 포괄하지 않는다

- 분류: 정확성
- 심각도: Major
- 근거 위치: 5절; ON인 FK 테이블이 참조하는 테이블도 ON이어야 한다고 한다.
- 사실/추론 구분: 문서에서 도출한 추론
- 영향 대상: 데이터 정합성, 스키마 설계자

### 문제
부모 ON/자식 OFF, 부모 OFF/자식 OFF, 다단계 참조, 자기 참조, `ON DELETE CASCADE` 및 기존 FK가 있을 때 ON→OFF 전환의 규칙이 없다.

### 왜 중요한가
FK DDL만 복제되고 데이터는 선택적으로 복제되면 슬레이브 apply가 FK 위반으로 실패할 수 있다. 연쇄 삭제는 어느 테이블에서 DML 로그가 생성되는지에 따라 중복 적용 위험도 있다.

### 재현 또는 구체적 예제
부모 P와 자식 C가 모두 ON이고 `ON DELETE CASCADE`다. P를 OFF로 바꾸는 것이 허용되면 이후 primary의 부모 삭제와 standby의 자식 상태가 달라질 수 있다.

### 권고안
부모/자식 ON/OFF 조합표, 전환 시 기존 의존성 검사, 연쇄 동작의 로그 책임과 오류 정책을 추가한다.

### 검증 방법
모든 조합과 CASCADE/SET NULL/RESTRICT를 생성·변경·failover하며 양 노드 제약과 데이터를 비교한다.

## [PM-10Y-15] fail_count의 의미와 운영 대응이 스펙에서 사라졌다

- 분류: 운영성
- 심각도: Major
- 근거 위치: 문서 전체; 문제 배경의 `fail_count`에 대한 정의·조회·경보·복구 절차가 없다.
- 사실/추론 구분: 확인된 사실
- 영향 대상: DBA, 모니터링, 기술지원

### 문제
변경 이유 중 하나가 `fail_count` 증가인데 성공 기준과 사용자 행동에 이 지표가 포함되지 않는다. 카운터가 테이블별인지 노드별인지, 누적·초기화되는지도 모른다.

### 왜 중요한가
DDL은 성공했지만 복제가 실패하는 상황에서 운영자가 문제를 발견하지 못하면 불일치가 누적된다. 반대로 과거 실패가 남아 있으면 새 기능의 실패로 오판할 수 있다.

### 재현 또는 구체적 예제
RK 변경 전 `fail_count=3`, 변경 후 재시도 성공이라고 가정한다. 값이 3으로 남는지 0으로 되는지, 별도 “last failure”가 있는지에 따라 알람 의미가 달라진다.

### 권고안
정확한 증가 이벤트, 단위, 초기화, 임계값, 오류 상세 연결, 데이터 검증 및 재동기화 runbook을 제품 요구사항에 넣는다.

### 검증 방법
의도적으로 행 미발견·키 충돌·DDL 실패를 발생시키고 카운터와 로그, 경보, 복구 후 상태를 확인한다.

## [PM-10Y-16] 오류 결과가 단순 ERROR/OK라 자동화 계약으로 사용할 수 없다

- 분류: 운영성
- 심각도: Major
- 근거 위치: 2절, 4절, 5절의 예시 대부분이 `ERROR` 또는 `OK`만 표기한다.
- 사실/추론 구분: 확인된 사실
- 영향 대상: DBA, 배포 도구, 애플리케이션, 지원 조직

### 문제
오류 코드, SQLSTATE, 메시지 인자, 실패한 테이블/제약, 수정 방법이 없다. 자동 마이그레이션은 정책 위반과 문법 오류를 구분할 수 없다.

### 왜 중요한가
운영 자동화는 문자열 `ERROR`가 아니라 안정적인 코드가 필요하다. 여러 위반이 있을 때 첫 오류만 나오면 수정과 재시작을 반복해야 한다.

### 재현 또는 구체적 예제
HA 시작 시 무키 테이블 t1과 OFF 부모를 참조하는 t2가 동시에 있다. 기대 출력은 두 객체, 위반 코드, 권장 ALTER를 모두 포함해야 한다.

### 권고안
SQLSTATE/제품 오류 코드 표, 메시지 템플릿, 다중 위반 출력 형식, 명령 종료 코드와 교정 예제를 정의한다.

### 검증 방법
각 금지 동작을 CLI·JDBC·관리 도구로 실행해 동일한 코드와 구조화된 상세가 노출되는지 확인한다.

## [PM-10Y-17] unload/load의 누락 기본값이 본문과 요약에서 정반대다

- 분류: 호환성
- 심각도: Blocker
- 근거 위치: 8절은 변수가 없으면 ON이라고 하고, 9절 5항은 정보가 없으면 OFF라고 한다.
- 사실/추론 구분: 확인된 사실
- 영향 대상: 백업·복원, 업그레이드, 재해 복구

### 문제
동일한 구버전 unload 파일을 로드했을 때 모든 테이블이 복제 대상인지 제외 대상인지 문서가 상충한다.

### 왜 중요한가
ON이면 무키 테이블 때문에 HA가 시작되지 않을 수 있고, OFF이면 사용자가 복제될 것으로 믿은 중요 데이터가 standby에 전달되지 않는다. 어느 쪽도 묵시적으로 결정하면 안 된다.

### 재현 또는 구체적 예제
구버전 dump에 `orders`와 무키 `audit`가 있고 replication 필드가 없다. 8절대로면 둘 다 ON, 9절대로면 둘 다 OFF가 되어 복원 결과가 완전히 달라진다.

### 권고안
하나의 정책으로 통일하고 안전 근거, 경고, 명시적 load 옵션, 객체별 결과 보고서, HA 시작 전 교정 절차를 추가한다.

### 검증 방법
지원하는 각 구버전의 dump fixture를 load하고 카탈로그 값, 경고, HA 시작 및 실제 DML 복제를 확인한다.

## [PM-10Y-18] 혼합 버전 HA와 롤백 정책이 없다

- 분류: 호환성
- 심각도: Critical
- 근거 위치: 8절에서 구버전 파일만 일부 언급하고 노드 간 버전 차이는 다루지 않는다.
- 사실/추론 구분: 확인이 필요한 질문
- 영향 대상: 업그레이드 운영, 가용성, 데이터 정합성

### 문제
새 마스터가 `REPLICATION` 카탈로그/DDL/로그를 보내지만 구버전 슬레이브가 이를 모를 때의 동작과 지원 여부가 없다.

### 왜 중요한가
HA 제품은 흔히 순차 업그레이드가 필요하다. 미지원 문법을 슬레이브가 무시하면 조용한 불일치가 되고, 거부하면 서비스 업그레이드가 중단된다.

### 재현 또는 구체적 예제
새 버전 primary에서 `ALTER TABLE t REPLICATION=OFF`를 실행하고 구버전 standby가 해당 DDL을 받는다. 파싱 실패, 무시, 연결 종료 중 어떤 결과인지 정의돼야 한다.

### 권고안
지원 버전 행렬, DDL capability 협상, 기능 사용 차단 시점, 업그레이드·다운그레이드·롤백 절차를 명시한다.

### 검증 방법
구/신 버전의 primary/standby 조합별로 새 DDL과 RK 로그를 전송하고 명시된 실패 방식과 데이터 보존을 검증한다.

## [PM-10Y-19] 예제에 완전한 사전 상태와 실제 오류 메시지가 없다

- 분류: 문서 품질
- 심각도: Major
- 근거 위치: 2-2절과 4-2절의 예시 5~16; `tbl`, `table_name`, 생략 부호와 단순 결과를 사용한다.
- 사실/추론 구분: 확인된 사실
- 영향 대상: 입문 사용자, QA, 기술 문서 독자

### 문제
예제 13처럼 기존 테이블 정의와 제약 이름이 없고 `DROP CONSTRAINT PRIMARY KEY` 같은 문법이 실제 실행 가능한지 판별하기 어렵다. 예제 16은 UK 제약과 인덱스의 관계도 설명하지 않는다.

### 왜 중요한가
입문자는 예제를 복사하여 학습한다. 실행되지 않는 의사 코드와 설명되지 않은 성공 결과는 기능을 오해하게 하고 테스트 기준으로도 쓸 수 없다.

### 재현 또는 구체적 예제
문서의 `ALTER TABLE table_name DROP CONSTRAINT PRIMARY KEY, ADD CONSTRAINT PRIMARY KEY(a);`를 그대로 실행하면 `table_name`의 기존 컬럼과 제약 이름이 없어 재현할 수 없다.

### 권고안
각 예제를 독립 실행 가능한 CREATE→데이터 입력→ALTER→조회 순서로 바꾸고 실제 오류 코드와 변경 전후 `SHOW CREATE TABLE`을 제공한다.

### 검증 방법
빈 DB에서 문서 코드 블록을 자동 실행하는 doctest를 만들고 예상 결과와 한 줄씩 비교한다.

## [PM-10Y-20] 공개 전 결정을 요구하는 질문과 책임자가 정리되지 않았다

- 분류: 누락
- 심각도: Major
- 근거 위치: 문서 전체; “책임지지 않는다”, “엔진이 선택”, “ERROR” 등 미결 정책이 결정된 요구사항처럼 섞여 있다.
- 사실/추론 구분: 문서에서 도출한 추론
- 영향 대상: PM, 개발, QA, 문서, 지원 조직

### 문제
OFF 데이터 수명, RK 자동 선택, 기존 객체 기본값, 혼합 버전, 오류 코드, full sync 같은 핵심 의사결정의 소유자와 마감 기준이 없다.

### 왜 중요한가
팀마다 다른 가정으로 구현·시험·문서를 만들면 마지막 통합 단계에서 충돌한다. 데이터 정합성 정책은 구현자가 임의로 채울 세부사항이 아니다.

### 재현 또는 구체적 예제
개발팀은 OFF→ON을 single에서 단순 플래그 변경으로 구현하고, QA는 전체 데이터 동기화를 기대하며, 문서팀은 HA에서만 금지라고 적을 수 있다. 세 결과 모두 현재 문구와 양립한다.

### 권고안
미결 질문 표에 선택지, 권고안, 데이터/호환성 영향, 결정권자, 결정 기한, 결정 후 바뀌는 수용 테스트를 기록하고 Blocker가 닫히기 전 구현 완료로 판단하지 않는다.

### 검증 방법
요구사항 추적표에서 모든 Blocker/Critical 질문이 승인된 규칙과 최소 하나의 테스트 케이스에 연결됐는지 검토한다.

## [PM-10Y-21] 복제 정책 변경을 일반 ALTER와 같은 권한으로 취급할지 결정되지 않았다

- 분류: 보안
- 심각도: Critical
- 근거 위치: 2-1절과 2-2절은 사용자가 ON/OFF를 지정·전환한다고만 한다.
- 사실/추론 구분: 확인된 사실
- 영향 대상: 제품 보안, DBA, 감사·규제 조직

### 문제
ON→OFF는 데이터 보호 등급을 낮추지만 별도 권한, 이중 승인, 감사 이벤트가 요구되지 않는다. 일반 schema owner가 조용히 업무 테이블을 OFF로 바꿀 수 있는지 알 수 없다.

### 왜 중요한가
가용성 설정은 데이터 보존 정책이다. 누가 언제 왜 변경했는지 증명하지 못하면 내부 통제와 사고 분석이 어렵다.

### 재현 또는 구체적 예제

```sql
GRANT ALTER ON orders TO app_owner;
-- app_owner 실행
ALTER TABLE orders REPLICATION=OFF;
```

성공 여부와 감사 레코드가 미정이다.

### 권고안
CREATE 지정, ON→OFF, OFF→ON, RK 변경별 권한을 분리하고 중요 테이블에는 policy approval을 지원한다. actor, reason, old/new policy, LSA를 영구 감사한다.

### 검증 방법
역할별 허용·거부 matrix를 시험하고 성공·실패 시도가 audit export에서 변조 방지 형태로 조회되는지 확인한다.

## [PM-10Y-22] ON/OFF 혼합 트랜잭션은 복제 후 원자성 계약을 깨뜨린다

- 분류: 정확성
- 심각도: Blocker
- 근거 위치: 1절·4절은 OFF DML만 제외한다고 하나 transaction 경계는 없다.
- 사실/추론 구분: 문서에서 도출한 추론
- 영향 대상: 애플리케이션 정합성, failover, 제품 보증 범위

### 문제
source의 한 transaction이 ON과 OFF를 함께 바꾸면 replica에는 일부 write만 나타난다. ACID 원자성이 HA 보호 경계에서 달라진다는 중대한 계약이 공개되지 않았다.

### 왜 중요한가
두 테이블에 걸친 업무 불변식은 failover 후 깨진다. 이 현상을 면책만 하면 HA 제품 신뢰가 훼손된다.

### 재현 또는 구체적 예제

```sql
BEGIN;
INSERT INTO invoice(id,total) VALUES (1,100);       -- ON
INSERT INTO tax_evidence(invoice_id,total) VALUES (1,10); -- OFF
COMMIT;
```

새 primary에는 invoice만 있을 수 있다.

### 권고안
혼합 transaction을 지원·경고·금지 중 하나로 명시적으로 결정한다. strict HA profile에서는 commit을 거부하고 사전 schema analyzer로 교차 쓰기를 찾는 방안을 검토한다.

### 검증 방법
commit, rollback, deadlock, crash를 섞은 혼합 transaction에서 source·replica·failover 결과를 수용 규칙과 대조한다.

## [PM-10Y-23] 파티션·상속·샤딩 객체의 지원 범위가 제품 매트릭스에 없다

- 분류: 누락
- 심각도: Critical
- 근거 위치: 문서 전체는 일반 테이블만 다루며 2-3절 출력에 `partitioned` 속성은 보인다.
- 사실/추론 구분: 확인이 필요한 질문
- 영향 대상: 대규모 고객, 제품 포트폴리오, 복제 정합성

### 문제
CUBRID가 실제 지원하는 파티션·상속·분산 객체 각각에서 ON/OFF와 RK를 허용하는지 확인되지 않았다. 부모 정책 상속, 파티션 단위 UK와 전체 유일성, 파티션 교환도 없다.

### 왜 중요한가
대형 고객이 가장 많이 쓰는 데이터 배치 기능이 범위 밖이면 출시 가치가 제한된다. 일부 파티션만 다른 정책을 가지면 기간별 누락도 생긴다.

### 재현 또는 구체적 예제
공식 지원 문법으로 월별 `sales` 파티션을 구성했다고 가정한다.

```sql
SELECT class_name, partitioned, replication
FROM db_class WHERE class_name='sales';
```

부모와 각 파티션의 RK 및 정책 계약이 없다.

### 권고안
실제 지원 객체별 supported/unsupported/roadmap matrix를 공개한다. 지원 시 생성·분할·병합·교환의 상태 전이와 전체 행 식별 조건을 규정한다.

### 검증 방법
각 공식 객체·DDL을 RK 후보 0/1/복수와 조합해 failover까지 시험하고 미지원 경로는 사전에 차단되는지 확인한다.

## [PM-10Y-24] trigger·cascade·프로시저의 내부 DML 책임이 정의되지 않았다

- 분류: 누락
- 심각도: Critical
- 근거 위치: 4절·5절은 직접 DML과 FK만 설명하고 서버 생성 DML은 다루지 않는다.
- 사실/추론 구분: 확인이 필요한 질문
- 영향 대상: 실행 엔진, 애플리케이션, 데이터 정합성

### 문제
trigger나 cascade가 ON/OFF 경계를 넘어 DML을 만들면 source 결과를 row log로 보내는지 replica에서 logic을 다시 실행하는지 없다. 저장 프로시저 지원 범위도 확인이 필요하다.

### 왜 중요한가
결과 로깅과 재실행을 함께 하면 중복되고 둘 다 하지 않으면 누락된다. 제품이 지원하는 모든 자동 DML 기능과 일관된 정책이 필요하다.

### 재현 또는 구체적 예제
orders ON insert가 audit OFF에 trigger write를 만든다고 가정한다.

```sql
INSERT INTO orders(id,status) VALUES (10,'NEW');
SELECT COUNT(*) FROM audit WHERE order_id=10;
```

failover 후 기대 count가 정의되지 않았다.

### 권고안
user/generated DML의 provenance, logging, replica trigger suppression, ON/OFF 판정을 하나의 규범으로 둔다. 안전하지 않은 dependency는 DDL에서 차단한다.

### 검증 방법
trigger, cascade, procedure와 ON/OFF 방향을 조합해 실행 횟수·로그·최종 행을 비교한다.

## [PM-10Y-25] backup·PITR·장기 보관 로그가 RK 세대를 보존하는 정책이 없다

- 분류: 호환성
- 심각도: Blocker
- 근거 위치: 8절은 논리 unload/load만 다루고 물리 backup·PITR는 없다.
- 사실/추론 구분: 확인이 필요한 질문
- 영향 대상: 재해 복구, 장기 지원, 규제 고객

### 문제
백업 snapshot 뒤 RK 변경과 DML 로그를 특정 시점까지 재생할 때 과거 RK 정의를 어디서 얻는지 없다. 보관 기간이 긴 archived log의 미래 버전 호환성도 미정이다.

### 왜 중요한가
재해 복구는 평소보다 오래된 형식과 metadata를 사용한다. 복원은 성공해도 후속 로그가 잘못된 행에 적용되면 치명적이다.

### 재현 또는 구체적 예제

```sql
-- 10:00 backup
-- 10:05 RK id -> email 교체
-- 10:10 DML, 10:11로 PITR
```

두 RK 세대와 비교 규칙을 함께 복구해야 한다.

### 권고안
backup format에 선택 RK identity·epoch history·필수 engine version을 포함한다. 지원 보관 기간, migration converter, 복구 후 HA 재가입 조건을 제품 수명 정책으로 정한다.

### 검증 방법
여러 메이저 버전의 backup과 archived log를 최신 지원 버전에서 PITR하고 checksum·RK history를 원본과 비교한다.

## [PM-10Y-26] RK 구축 작업의 자원 admission control이 제품 요구사항에 없다

- 분류: 성능
- 심각도: Critical
- 근거 위치: 4-2절은 key 후보 추가를 허용하지만 대형 index 구축 비용과 자원 부족은 없다.
- 사실/추론 구분: 확인이 필요한 질문
- 영향 대상: 서비스 가용성, 운영자, 클라우드 비용

### 문제
수십억 행 UK 생성이 disk, temp, CPU, log bandwidth를 고갈시킬 수 있다. 사전 추정, 속도 제한, 우선순위, 취소와 cleanup이 없다.

### 왜 중요한가
안전 기능 도입 과정이 DB 전체 장애를 일으키면 고객은 기능 사용을 피한다. 장기적으로 지원 incident와 운영 비용도 커진다.

```sql
ALTER TABLE event_10b
```

95%에서 disk full이 나도 기존 RK와 서비스가 보존돼야 한다.

### 권고안

### 검증 방법
생산 규모 데이터와 제한 자원에서 build·cancel·crash를 수행해 SLO, cleanup, 기존 복제 안정성을 확인한다.

## [PM-10Y-27] 느린 replica와 로그 보관 한계가 RK 변경 정책에 연결되지 않았다

- 분류: 운영성
- 심각도: Critical
- 근거 위치: 4절은 운영 중 RK 변경을 허용하고 9절은 DML 순서만 문제로 남긴다.
- 사실/추론 구분: 문서에서 도출한 추론
- 영향 대상: 다중 replica, DR, 저장 비용

### 문제
오래 중지된 DR replica 때문에 구 RK epoch와 로그를 얼마나 보관하는지 없다. 무한 보관과 조기 삭제 사이 정책을 정해야 한다.

### 왜 중요한가
무한 보관은 primary disk를 채우고 조기 삭제는 replica를 재생 불능으로 만든다. 토폴로지 규모가 커질수록 비용이 커진다.

### 재현 또는 구체적 예제
DR replica를 7일 중지하고 매일 RK를 교체한 뒤 재개한다고 하자.

```sql
SELECT class_name, replication FROM db_class WHERE class_name='orders';
```

단순 ON 조회로는 replay 가능 여부를 알 수 없다.

### 권고안
지원 최대 lag, epoch/log retention budget, 경고와 강제 재-seed 조건을 정한다. RK DDL은 모든 replica horizon과 예상 보관 비용을 보여 준 뒤 실행한다.

### 검증 방법
여러 replica를 다른 기간 정지하고 retention 경계를 넘나든다. 지원 범위 안은 replay되고 밖은 조용한 실패 없이 재가입 상태로 전환되는지 확인한다.

## [PM-10Y-28] split-brain과 이전 primary 재가입 정책이 없다

- 분류: 정확성
- 심각도: Blocker
- 근거 위치: 4~7절은 정상 primary/standby와 failover만 설명한다.
- 사실/추론 구분: 확인이 필요한 질문
- 영향 대상: HA 오케스트레이션, 데이터 정합성, 지원 조직

### 문제
network partition으로 양 노드가 쓰기를 받으면 같은 RK에 다른 값이나 서로 다른 RK epoch가 생긴다. 재연결 시 자동 병합·격리·재-seed 중 무엇인지 없다.

### 왜 중요한가
RK는 동일 행을 찾을 뿐 업무 충돌을 해결하지 않는다. 임의 last-write-wins는 결제·재고를 손상할 수 있다.

### 재현 또는 구체적 예제

```sql
-- node A
UPDATE account SET balance=900 WHERE id=10;
-- 동시에 node B
UPDATE account SET balance=800 WHERE id=10;
```

네트워크 복구 후 단일 정답을 엔진이 알 수 없다.

### 권고안
term 기반 fencing, stale primary write 차단, divergence 탐지, 권위 노드 승인, old primary 재-seed runbook을 공개한다. 자동 병합은 금지한다.

### 검증 방법
network partition과 fencing service 장애를 함께 주입한다. 단일 writer가 유지되거나 divergence가 격리되어 수동 승인 전 전파되지 않는지 확인한다.

## [PM-10Y-29] 실패 카운터 외 정상 복제 SLO가 없다

- 분류: 운영성
- 심각도: Major
- 근거 위치: 2-3절은 ON/OFF 조회만, 15번 근거인 원문 전체는 `fail_count`조차 정의하지 않는다.
- 사실/추론 구분: 확인된 사실
- 영향 대상: PM, SRE, 고객지원, SLA

### 문제
오류가 없더라도 apply가 멈추거나 느리면 보호되지 않는다. lag, 마지막 성공, replica별 RK epoch, 승격 가능 상태와 제품 SLO가 없다.

### 왜 중요한가
운영자는 “정상”을 측정해야 한다. 출시 후 관련 support case가 줄었는지와 가용성 목표를 달성했는지도 지표 없이는 판단할 수 없다.

### 재현 또는 구체적 예제

```sql
INSERT INTO repl_probe(id,created_at) VALUES (1,CURRENT_DATETIME);
```

standby 적용이 30분 뒤여도 fail_count는 0일 수 있다.

### 권고안
send/apply LSA, seconds/bytes lag, last success, RK epoch agreement, promotability를 제품 지표로 정의한다. 기본 경보와 고객 SLA/SLO를 연결한다.

### 검증 방법
정상·지연·중지·회복 상태에서 지표와 경보를 확인하고 지원 dashboard가 실제 위험을 구분하는지 시험한다.

## [PM-10Y-30] RK 진단 로그의 개인정보·보존 정책이 없다

- 분류: 보안
- 심각도: Critical
- 근거 위치: 7절은 오류 목록, 16번 근거인 원문 예제는 오류 상세가 없으며 RK 값 노출 규칙은 없다.
- 사실/추론 구분: 확인이 필요한 질문
- 영향 대상: 보안·개인정보, 지원 bundle, 감사

### 문제
email·전화번호 같은 UK가 RK이면 apply 실패 진단에 원문 값이 포함될 수 있다. 중앙 로그와 고객 지원 파일은 DB보다 넓게 공유되고 오래 보관된다.

### 왜 중요한가
진단 가능성과 개인정보 최소 수집을 동시에 만족해야 한다. 설계 후반에 마스킹을 붙이면 correlation이 깨지거나 누출 경로가 남는다.

### 재현 또는 구체적 예제

```sql
UPDATE member SET status='ACTIVE' WHERE email='person@example.com';
```

실패 로그와 support bundle의 email 노출 여부가 미정이다.

### 권고안
기본 로그는 keyed hash·constraint ID를 쓰고 원문은 별도 권한·감사 하에 짧게 제공한다. 보존·삭제·지역 이동 정책을 보안 요구사항으로 둔다.

### 검증 방법
민감 RK 오류를 만들고 로그 pipeline, dashboard, bundle, API를 역할별로 점검해 최소 정보 원칙과 진단 가능성을 검증한다.

## [PM-10Y-31] 단계적 공개와 기능 비활성화 경계가 없다

- 분류: 호환성
- 심각도: Critical
- 근거 위치: 원문 전체는 새 동작을 즉시 적용하는 것처럼 보이며 feature flag·edition·backout을 다루지 않는다.
- 사실/추론 구분: 확인이 필요한 질문
- 영향 대상: release management, 기존 고객, 기술지원

### 문제
DB별 opt-in, compatibility mode, canary, emergency disable이 가능한지 없다. 새 catalog/log를 쓴 뒤 flag를 끄거나 downgrade할 수 있는지도 미정이다.

### 왜 중요한가
데이터 형식을 바꾸는 기능은 UI flag처럼 쉽게 되돌릴 수 없다. 공개 전략을 설계와 함께 정하지 않으면 장애 시 안전한 backout이 없다.

### 재현 또는 구체적 예제

```sql
ALTER TABLE cache REPLICATION=OFF;
```

이 record가 생성된 뒤 구 behavior로 돌아갈 수 있는 경계가 필요하다.

### 권고안
shadow validation→opt-in→canary→default-on 단계를 정의하고 feature bit, activation gate, point-of-no-return, emergency policy를 명시한다. edition 차이도 지원표에 둔다.

### 검증 방법
각 공개 단계에서 enable/disable, failover, upgrade rollback을 실행한다. 지원되지 않는 backout은 변경 전에 차단되는지 확인한다.

## [PM-10Y-32] 지원 조합의 폭과 장기 시험 비용이 추정되지 않았다

- 분류: 호환성
- 심각도: Major
- 근거 위치: 원문 1~9절은 mode·키·FK·VIEW·load 규칙을 추가하지만 공식 지원 matrix는 없다.
- 사실/추론 구분: 문서에서 도출한 추론
- 영향 대상: 제품 전략, QA, 유지보수 예산

### 문제
mode × 버전 × RK 종류 × DDL × failover × backup 조합이 폭발한다. 무엇을 지원하고 무엇을 제한할지 없으면 모든 릴리스에서 현실적으로 검증할 수 없다.

### 왜 중요한가
테스트하지 못한 지원 약속은 장기 장애와 비용으로 돌아온다. 10년차 PM은 기능 수보다 유지 가능한 보장 범위를 선택해야 한다.

### 재현 또는 구체적 예제
PK/단일 UK/복합 UK 3종, 노드 버전 4조합, 모드 3종, DDL 10종, 장애 지점 5종만 곱해도 1,800개 조합이다.

```sql
ALTER TABLE t DROP PRIMARY KEY, ADD CONSTRAINT uk_t UNIQUE(b);
```

이 한 SQL도 모든 조합에서 계약이 필요하다.

### 권고안
tier-1 보장 조합, 제한 지원, 비지원 범위를 정하고 risk-based pairwise·model-based test 전략과 릴리스별 실행 예산을 승인한다.

### 검증 방법
지원 matrix의 모든 tier-1 셀이 자동 시험과 owner에 연결되고 미시험 셀이 공개 문서상 지원으로 남지 않는지 감사한다.

## [PM-10Y-33] 관리 도구·드라이버·ORM 생태계 출시 계획이 없다

- 분류: 호환성
- 심각도: Major
- 근거 위치: 2절은 새 SQL과 db_class 필드를 추가하지만 외부 도구 API는 없다.
- 사실/추론 구분: 확인이 필요한 질문
- 영향 대상: 애플리케이션 개발자, 파트너, 제품 채택

### 문제
schema diff가 OFF를 보존하는지, JDBC metadata가 실제 RK를 노출하는지, 관리 UI가 위험을 표시하는지 없다. 서버만 출시하면 도구가 정책을 되돌리거나 숨길 수 있다.

### 왜 중요한가
사용자는 raw SQL보다 ORM·migration·관리 도구를 통해 schema를 바꾼다. 생태계 준비가 늦으면 기능이 있어도 안전하게 채택되지 않는다.

### 재현 또는 구체적 예제

```sql
CREATE TABLE local_cache (id INT PRIMARY KEY) REPLICATION=OFF;
```

schema diff가 옵션을 읽지 못해 재생성 시 기본 ON으로 바꿀 수 있다.

### 권고안
metadata contract, driver version, 주요 도구 지원 일정, fallback behavior와 certification suite를 server release gate에 포함한다.

### 검증 방법
지원 도구별 introspect→diff→migration→restore를 실행해 ON/OFF와 RK identity가 보존되는지 확인한다.

## [PM-10Y-34] OFF 데이터의 법적 보존·삭제 책임이 노드 수명주기와 연결되지 않았다

- 분류: 보안
- 심각도: Major
- 근거 위치: 1절·4절·6절은 OFF 데이터 불일치를 면책하지만 backup, 노드 폐기, 삭제 의무는 없다.
- 사실/추론 구분: 문서에서 도출한 추론
- 영향 대상: 규제 고객, 보안, 데이터 거버넌스

### 문제
OFF는 복제되지 않지만 각 노드의 과거 로컬 데이터와 backup에는 남을 수 있다. failback으로 삭제된 개인정보가 다시 나타날 가능성도 있다.

### 왜 중요한가
“복제 안 됨”은 “보존 안 됨”이나 “삭제 완료”와 다르다. 고객의 삭제 요청과 보존 정책은 모든 복사본을 포함해야 한다.

### 재현 또는 구체적 예제

```sql
DELETE FROM local_profile WHERE user_id=10;
```

현재 primary에서 삭제해도 이전 primary의 OFF 데이터와 backup에 남는지 알 수 없다.

### 권고안
OFF 데이터를 node-local 자산으로 inventory하고 backup 포함 여부, failover/failback, node retirement, 삭제 propagation 책임을 명시한다. 민감 데이터의 OFF 사용을 제한한다.

### 검증 방법
양 노드와 backup에 테스트 개인정보를 만든 뒤 삭제·역할 전환·복원을 수행한다. 정책상 남아서는 안 되는 복사본이 없는지 확인한다.

## [PM-10Y-35] 기능의 장기 지원 종료와 catalog 정리 경로가 없다

- 분류: 호환성
- 심각도: Major
- 근거 위치: 원문 전체는 기능 도입만 다루며 향후 변경·폐기와 metadata cleanup은 없다.
- 사실/추론 구분: 문서에서 도출한 추론
- 영향 대상: 장기 유지보수, upgrade, 고객 자산

### 문제
RK 선택 방식이나 REPLICATION 문법을 미래에 교체할 때 영속 epoch, audit, dump field를 언제 제거할 수 있는지 정책이 없다. 기능을 사용한 DB를 구버전/대체 기능으로 변환하는 exporter도 미정이다.

### 왜 중요한가
영속 형식은 구현보다 오래 산다. 제거 경로 없이 추가하면 모든 미래 버전이 과거 형식을 영구 지원해야 한다.

### 재현 또는 구체적 예제

```sql
CREATE TABLE history (id INT PRIMARY KEY) REPLICATION=OFF;
```

10년 뒤 옵션을 대체해도 이 catalog와 old dump를 읽을 책임이 남는다.

### 권고안
metadata versioning, deprecation notice 기간, read-old/write-new 정책, converter, tombstone cleanup과 지원 종료 기준을 초기 설계에 포함한다.

### 검증 방법
old fixture를 최신 형식으로 변환하고 재변환 없이 여러 upgrade hop을 통과시킨다. deprecated field 제거 전 사용량과 rollback 불가 조건이 보고되는지 확인한다.
