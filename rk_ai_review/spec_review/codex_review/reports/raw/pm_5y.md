## [PM-5Y-01] 문제 원인과 출시 성공 기준이 연결되어 있지 않다

- 분류: 컨셉
- 심각도: Blocker
- 근거 위치: 원문 1절의 RK 필수화 및 9절 요약; 변경 누락, `fail_count`, 기존 데이터 불일치의 예방·해소 기준은 없음
- 사실/추론 구분: 확인된 사실 — 원문은 ON 테이블에 RK를 요구하지만 성공 지표와 기존 불일치 처리 기준을 명시하지 않는다
- 영향 대상: 사용자, DBA, 제품 지원, 복제 정합성, 출시 의사결정자

### 문제
문서가 해결하려는 핵심 장애를 제품 요구사항으로 정의하지 않았다. RK 후보를 항상 남기는 제약은 “키가 아예 없는 상태”를 줄일 수 있지만, 변경 누락과 `fail_count` 증가가 어떤 조건에서 사라져야 하는지, 이미 어긋난 데이터가 어떻게 처리되는지, PK 속성 변경 중 로그가 어느 키를 참조하는지가 없다. 따라서 구현이 문법만 통과해도 기능이 완료됐다고 오판할 수 있다.

### 왜 중요한가
기능의 목적은 새 키워드 추가가 아니라 source/replica의 같은 행에 같은 변경을 적용하는 것이다. 예를 들어 DDL 전에 생성된 UPDATE 로그가 옛 PK를 담고 있는데 replica는 새 PK 정의만 알고 있다면, 새 RK가 존재해도 대상 행을 못 찾을 수 있다. 수용 기준이 없으면 이 실패를 발견하지 못한 채 출시할 수 있고, failover 후 고객이 불일치를 처음 발견하게 된다.

### 재현 또는 구체적 예제
초기에는 양쪽 노드에 `(id=10, email='a@x', balance=500)`이 있고 `id`가 PK/RK라고 가정한다.

```sql
CREATE TABLE account (
  id INT PRIMARY KEY,
  email VARCHAR(100) NOT NULL UNIQUE,
  balance INT NOT NULL
) REPLICATION = ON;

UPDATE account SET balance = 400 WHERE id = 10;
ALTER TABLE account DROP PRIMARY KEY,
  ADD CONSTRAINT pk_account_email PRIMARY KEY (email);
```

복제 적용이 지연되어 UPDATE 로그보다 DDL이 먼저 보이거나, UPDATE 로그가 `id=10`을 기록했는데 적용기가 `email`로만 찾는 경우를 생각할 수 있다. 기대 결과는 DDL/DML 적용 순서와 키 정의가 일치하여 두 노드의 잔액이 모두 400이고 `fail_count`가 증가하지 않는 것이다. 문서는 그 보장을 수용 기준으로 적지 않는다.

### 권고안
문서 첫 절에 측정 가능한 목표를 추가한다. 최소한 “허용된 모든 RK 전환에서 커밋 순서대로 DDL/DML을 적용하고, 적용 후 ON 테이블의 행 집합과 값이 일치하며, 키 정의 변경 때문에 `fail_count`가 증가하지 않는다”를 명시한다. 기존 불일치는 자동 교정 대상인지 사전 차단 대상인지도 구분한다. 각 상태 전이별 정상 결과, 거부 오류, 재시도 정책을 출시 체크리스트로 만든다.

### 검증 방법
PK→PK, PK→UK, UK→PK, UK→UK 전환 각각에 대해 복제 지연을 주고 전환 전후 UPDATE/DELETE 1만 건을 교차 실행한다. 전환 종료 후 양쪽 테이블의 행 수와 행별 해시, 제약 정의, `fail_count` 전후 값을 비교한다. 기존 불일치가 있는 상태로 HA 시작·failover한 시험도 별도로 두고 문서의 정해진 결과와 일치해야 출시를 승인한다.

## [PM-5Y-02] 여러 UK 중 RK 선택 규칙이 결정적이지 않다

- 분류: 정확성
- 심각도: Blocker
- 근거 위치: 원문 1절의 “UK가 여러개 존재한다면 엔진이 선택(ex. 명시된 순서 중 가장 빠른 순서)” 및 4-2절의 엔진 결정
- 사실/추론 구분: 확인된 사실 — `ex.`로 예시만 제시하며 실제 선택·유지 규칙과 조회 방법을 확정하지 않는다
- 영향 대상: 복제 정합성, DBA, 업그레이드 담당자, 엔진 개발자

### 문제
여러 `NOT NULL UNIQUE` 후보 중 무엇이 RK인지 결정하는 규칙이 제품 계약이 아니다. “예를 들어 명시 순서”라는 표현은 구현 선택지를 설명할 뿐이다. source와 replica가 서로 다른 UK를 선택하거나, unload/load 또는 카탈로그 재구성 뒤 선택이 바뀌면 같은 로그를 서로 다른 컬럼으로 해석할 수 있다.

### 왜 중요한가
유일 키는 각각 행을 찾을 수 있지만 로그에 어느 키 값이 담겼는지는 별개다. source가 `email` 값을 기록하고 replica가 `employee_no`를 RK로 생각한다면 값이 우연히 같은 형식이어도 의미가 다르다. 결정성은 “둘 다 아무 UK나 고른다”가 아니라 동일한 스키마 버전에서 반드시 같은 제약 식별자를 선택하고 그 선택을 로그와 함께 보존하는 성질이다.

### 재현 또는 구체적 예제

```sql
CREATE TABLE employee (
  employee_no INT NOT NULL UNIQUE,
  email VARCHAR(100) NOT NULL UNIQUE,
  name VARCHAR(100)
) REPLICATION = ON;
INSERT INTO employee VALUES (101, 'a@corp', 'Kim');
UPDATE employee SET name = 'Lee' WHERE employee_no = 101;
```

노드 A가 `employee_no`를, 노드 B가 `email`을 RK로 고른 상황을 가정한다. UPDATE 로그의 키가 `101`이면 B는 `email='101'`을 찾지 못한다. 기대 결과는 양쪽이 동일한 제약을 선택하며, 백업·복원 뒤에도 선택이 유지되는 것이다. 원문은 어느 결과가 계약인지 결정하지 않는다.

### 권고안
RK 선택 우선순위를 규범 문장으로 확정한다. 예를 들어 PK 우선, 그다음에는 영구적인 제약 ID 또는 명시적으로 정의한 정렬 규칙을 사용하고, 선택된 RK의 제약 이름·컬럼 순서·스키마 버전을 카탈로그와 복제 로그에 기록한다. 후보 추가만으로 현재 RK를 자동 변경하지 않을지, 변경 시점을 언제로 할지도 명시한다. `SHOW CREATE TABLE` 외에 실제 선택 RK를 조회하는 인터페이스를 제공한다.

### 검증 방법
동일한 두 UK를 DDL 순서만 바꾸어 생성, unload/load, 백업 복원, 노드 재시작, 롤링 업그레이드를 수행한다. 각 단계에서 선택 RK가 두 노드에서 같은지 조회하고 UPDATE/DELETE 적용 여부를 확인한다. 선택이 바뀌도록 설계했다면 전환 로그가 존재하며 경계 전후 로그가 모두 올바르게 적용되는지 확인한다.

## [PM-5Y-03] 대안 비교와 REPLICATION=OFF의 제품 책임 경계가 부족하다

- 분류: 컨셉
- 심각도: Critical
- 근거 위치: 원문 1절과 4절의 OFF 데이터 미복제 및 “불일치 책임지지 않는다”, 6절의 VIEW 결과 불일치
- 사실/추론 구분: 문서에서 도출한 추론 — 전 컬럼 식별 방식의 비용을 피하려는 설계로 보이지만 원문은 대안·채택 기준·안전 범위를 설명하지 않는다
- 영향 대상: 사용자, PM, 지원 조직, 데이터 정합성, 애플리케이션

### 문제
원문은 RK가 없는 ON 테이블을 금지하고 OFF 테이블의 불일치는 책임지지 않는다고만 한다. 전 컬럼 비교, 사용자가 RK를 명시하는 방식, surrogate key 자동 추가 등 대안을 어떤 기준으로 제외했는지 없다. 더구나 OFF가 단순 성능 옵션처럼 보이지만 실제로는 failover 후 데이터가 없거나 오래된 상태가 되는 가용성 계약 변경이다.

### 왜 중요한가
제품 옵션의 이름만 보고 사용자는 DDL만 미복제되거나 성능만 달라진다고 오해할 수 있다. 실제 문서대로면 DDL은 복제되지만 DML은 복제되지 않아 빈 테이블 구조가 standby에 생길 수 있다. “책임지지 않는다”는 문구는 위험을 제거하지 않으며, 데이터 분류와 사용 제한 없이 제공하면 장애 시 비즈니스 데이터 손실로 이어진다.

### 재현 또는 구체적 예제

```sql
CREATE TABLE payment_audit (
  event_time DATETIME,
  payload VARCHAR(1000)
) REPLICATION = OFF;
INSERT INTO payment_audit VALUES (CURRENT_DATETIME, 'paid order=77');
```

source에는 감사 기록이 있지만 standby에는 테이블 구조만 있고 행은 없다고 문서에서 추론된다. failover 뒤 감사 조회 결과가 0건이어도 제품 오류가 아닌지, 규제성 데이터에 OFF 사용을 금지할지 명시가 없다. 모든 컬럼을 키로 쓰는 대안은 큰 `payload` 비교 비용이 들 수 있지만, OFF는 행 자체를 잃는 더 큰 의미 변화다.

### 권고안
제품 요구사항에 대안 비교표를 추가하여 정합성, 로그 크기, 검색 비용, 사용자 작업, 지원 범위를 비교한다. OFF는 “standby에서 데이터 가용성을 보장하지 않는 로컬 테이블”로 명명·설명하고, 생성 시 명시 경고와 권한 정책을 검토한다. FK·VIEW·백업·failover에서의 책임 경계를 구체화하고 중요 데이터에는 사용하지 말라는 금지 사례를 제공한다.

### 검증 방법
PM·DBA·지원 조직이 참여해 결제 원장, 임시 캐시, 감사 로그 세 사례를 분류하고 OFF 허용 여부가 동일하게 판단되는지 문서 사용성 시험을 한다. 실제 failover 전후 행 수를 비교해 경고 문구의 예상과 맞는지 확인한다. 대안별 대표 테이블에서 로그량과 적용 시간을 측정해 선택 근거를 제품 결정 기록으로 남긴다.

## [PM-5Y-04] RK 후보와 현재 RK를 구분하는 사용자 계약이 없다

- 분류: 모호성
- 심각도: Major
- 근거 위치: 원문 1절의 PK/UK 선택, 2-3절의 REPLICATION 조회, 4-2절의 “후보가 1개인 경우(=복제키)”
- 사실/추론 구분: 확인된 사실 — 조회 예시는 ON/OFF만 보여 주며 선택된 RK와 후보 목록은 보여 주지 않는다
- 영향 대상: 사용자, DBA, 자동화 도구, 고객 지원

### 문제
문서는 RK 후보와 실제 RK를 혼용한다. 후보가 여러 개면 하나만 실제 로그 식별에 쓰일 텐데, 사용자가 현재 선택을 조회하거나 변경 영향을 사전에 확인할 방법이 없다. `SHOW CREATE TABLE`은 PK/UK 정의와 REPLICATION 값만 보여 주며 “현재 RK”를 표시하지 않는다.

### 왜 중요한가
사용자는 삭제하려는 UK가 단순 후보인지 실제 RK인지 알아야 변경 허용 여부와 위험을 예측할 수 있다. 상태를 볼 수 없으면 같은 SQL이 어떤 환경에서는 성공하고 다른 환경에서는 실패하는 것처럼 보인다. 운영 자동화도 후보 수만으로 실제 사용 키를 추정하게 되어 엔진 규칙 변경에 취약해진다.

### 재현 또는 구체적 예제

```sql
CREATE TABLE member (
  member_no INT NOT NULL UNIQUE,
  email VARCHAR(100) NOT NULL UNIQUE,
  nickname VARCHAR(30)
) REPLICATION = ON;

SHOW CREATE TABLE member;
ALTER TABLE member DROP CONSTRAINT uq_member_email;
```

초기 상태에 UK 두 개가 있다. 출력만으로는 어느 UK가 RK인지 알 수 없다. DROP이 허용되는지, DROP 후 다른 후보로 자동 전환되는지, 선택이 그대로인지 예상할 수 없다. 기대 결과는 DDL 전에 현재 RK와 변경 후 RK를 명확히 확인할 수 있는 것이다.

### 권고안
용어 표에 “RK 후보”와 “활성 RK”를 분리 정의한다. 카탈로그 조회에 `replication=ON`, 활성 제약 이름, 순서가 보존된 컬럼 목록, 선택 이유, 스키마 세대 정보를 제공한다. DDL의 사전 설명 또는 오류에 현재 RK와 대체 후보를 표시한다.

### 검증 방법
PK 1개, UK 1개, UK 2개, 복합 UK가 있는 네 테이블을 만들고 조회 결과만으로 초급 DBA가 활성 RK를 정확히 답할 수 있는지 확인한다. 후보 추가·삭제·PK 추가 후 조회값이 실제 복제 로그가 사용하는 키와 일치하는지 통합 시험한다.

## [PM-5Y-05] 기본 ON과 single·SA·HA 모드의 계약이 안전하지 않다

- 분류: 호환성
- 심각도: Critical
- 근거 위치: 원문 2-1절의 생략 시 ON, 3절의 single, 9절 1-a의 single/SA 사용 가능; 1절은 hb start 이외를 모두 single로 정의
- 사실/추론 구분: 확인된 사실 — 기본값은 ON이지만 SA와 single의 관계 및 나중에 HA로 전환할 때의 생명주기 규칙이 일관되게 정의되지 않는다
- 영향 대상: 기존 사용자, DBA, 설치·업그레이드 담당자, 애플리케이션

### 문제
기존 SQL이 옵션을 생략하면 모두 ON이 된다. single에서는 RK 없는 ON 테이블 생성이 가능하지만 나중에 HA 시작이 막힌다. “single”, “SA”, “HA”가 실행 명령·접속 방식·카탈로그 상태 중 무엇을 뜻하는지도 불분명하다. 기본값이 호환성에는 유리해 보여도 미래의 HA 전환을 지연 실패로 만든다.

### 왜 중요한가
안전한 기본값은 가장 흔한 사용자가 위험을 늦게 발견하지 않게 해야 한다. 개발 환경에서 키 없는 테이블을 정상 생성하고 수개월 뒤 운영 HA 전환 시 전체 시작이 거부되면 장애 창구가 길어진다. SA가 별도 모드라면 동일 SQL의 허용 여부도 표로 설명해야 도구가 예측할 수 있다.

### 재현 또는 구체적 예제

```sql
-- 개발 single/SA 환경
CREATE TABLE staging_event (payload VARCHAR(1000));
INSERT INTO staging_event VALUES ('x');

-- 운영 전환
-- cubrid hb start
```

생략으로 `REPLICATION=ON`이 저장되지만 RK가 없다. 기대 결과 후보는 생성 즉시 경고, HA 전환 사전 검사 도구의 실패, 자동 OFF 중 하나인데 원문은 HA 전환 시 오류만 말한다. SA에서 CREATE가 어떤 규칙을 따르는지도 9절 표현만으로 확정되지 않는다.

### 권고안
single·SA·HA를 명령과 상태로 정확히 정의하고, CREATE/ALTER/LOAD/HA 시작별 허용 행렬을 제공한다. 기본 ON을 유지한다면 RK 없는 ON 테이블 생성 시 지속 경고와 사전 검사 명령을 제공한다. 신규 DB와 업그레이드 DB에 같은 기본값을 적용할지도 결정한다. HA 준비 프로필에서는 RK 없는 CREATE를 즉시 거부하는 선택지도 제공한다.

### 검증 방법
옵션 생략/ON/OFF × single/SA/HA 조합으로 CREATE와 ALTER를 실행해 문서의 상태 행렬과 비교한다. 키 없는 테이블 1천 개가 있는 기존 DB에서 HA 사전 검사가 모든 문제를 시작 전에 발견하고 수정 SQL까지 제공하는지 사용자 시험을 한다.

## [PM-5Y-06] SQL 예제가 실행 가능한 문법과 오류 계약을 제공하지 않는다

- 분류: 문서 품질
- 심각도: Major
- 근거 위치: 원문 2-1~2-2절과 4-2절 예시의 후행 쉼표, `DROP CONSTRAINT ...`, 이름 없는 제약, `ERROR`/`OK`
- 사실/추론 구분: 확인된 사실 — 여러 예제가 완전한 제약 이름과 구체 오류를 생략하고 일부 CREATE 목록에 후행 쉼표가 있다
- 영향 대상: 사용자, QA, 문서 작성자, 드라이버·도구 개발자

### 문제
핵심 기능을 설명하는 SQL이 복사해 실행할 수 없다. 예시 2와 일부 외래키 예시는 마지막 컬럼 뒤 쉼표가 있고, Multiple ALTER는 말줄임표이며, `DROP CONSTRAINT PRIMARY KEY`처럼 제약 이름인지 종류인지 모호한 표현이 있다. 결과도 `ERROR`뿐이어서 제품 오류 계약을 검증할 수 없다.

### 왜 중요한가
사용자 스펙의 예제는 구현팀·QA·문서팀이 같은 기능을 이해하는 공통 기준이다. 구문이 불완전하면 각 팀이 서로 다른 문법을 구현하거나 시험한다. 또한 애플리케이션은 오류 코드로 재시도 또는 사용자 안내를 결정하므로 단순 `ERROR`는 요구사항이 아니다.

### 재현 또는 구체적 예제

```sql
CREATE TABLE repl_table_without_rk (
  a INT,
) REPLICATION = ON;

ALTER TABLE tbl DROP CONSTRAINT ...,
  ADD CONSTRAINT ...;
```

첫 SQL은 후행 쉼표 때문에 RK 정책을 검사하기 전에 파서 오류가 날 수 있다. 둘째는 실제 제약 이름과 컬럼이 없어 PK→PK 전환을 재현하지 못한다. 기대 결과는 구문 자체가 성공적으로 파싱된 뒤 정책상 허용 또는 거부가 명확한 오류 코드로 나타나는 것이다.

### 권고안
모든 예제를 독립 실행 가능한 setup/action/assert 형태로 고친다. 실제 제약 이름을 사용하고 예상 SQLSTATE 또는 CUBRID 오류 코드, 메시지, 실패 후 스키마가 변하지 않았음을 명시한다. 문법 오류를 정책 오류 예제로 사용하지 않는다. 문서 빌드에서 SQL 코드 블록을 추출해 자동 실행한다.

### 검증 방법
빈 DB에서 예시 1~23을 순서 의존 없이 실행하는 문서 테스트를 만든다. 각 예제가 예상 단계까지 파싱되고, 성공/실패 코드와 사후 `SHOW CREATE TABLE` 결과가 명세와 같은지 검사한다. 코드 블록의 `...`와 후행 쉼표를 정적 검사로 금지한다.

## [PM-5Y-07] 하나의 ALTER에서 키 교체가 원자적이라는 보장이 없다

- 분류: 정확성
- 심각도: Blocker
- 근거 위치: 원문 2-2절 예시 7과 4-2절 예시 13의 DROP+ADD 동시 수행
- 사실/추론 구분: 확인이 필요한 질문 — 파싱·검증·카탈로그 변경·복제 로그 적용이 하나의 원자적 작업인지 문서에 없다
- 영향 대상: 복제 정합성, 사용자, DBA, 엔진 개발자

### 문제
문서는 단일 `ALTER TABLE`에 기존 키 삭제와 새 키 추가를 함께 넣으면 키 변경이 가능하다고 안내하지만 원자성 규칙을 정의하지 않는다. 새 제약 검증 실패, 복제 로그 기록 실패, replica 적용 실패 때 DROP만 반영되지 않는지 알 수 없다. 문장상 “항상 하나 이상의 후보”도 명령 중간 상태에 적용되는지 불명확하다.

### 왜 중요한가
원자성은 작업이 전부 성공하거나 전부 취소되는 성질이다. DROP은 성공하고 ADD가 실패하면 ON 테이블이 RK 없이 남을 수 있다. source는 롤백했지만 replica가 부분 적용했다면 양쪽 스키마가 달라진다. 이 기능은 바로 그런 상태를 막기 위한 것이므로 공개 전 보장이 필요하다.

### 재현 또는 구체적 예제

```sql
CREATE TABLE customer (
  id INT CONSTRAINT pk_customer PRIMARY KEY,
  email VARCHAR(100)
) REPLICATION = ON;

INSERT INTO customer VALUES (1, 'dup@x'), (2, 'dup@x');
ALTER TABLE customer
  DROP CONSTRAINT pk_customer,
  ADD CONSTRAINT uq_customer_email UNIQUE (email);
```

새 UK 검증은 중복 때문에 실패해야 한다. 기대 결과는 전체 ALTER가 실패하여 `pk_customer`가 그대로 남고 활성 RK도 `id`이며, replica도 동일한 상태인 것이다. 원문은 DROP이 롤백되는지, 오류 코드가 무엇인지 정하지 않는다.

### 권고안
복합 ALTER의 사전 검증과 커밋을 원자적으로 정의한다. 새 후보의 유일성·NOT NULL·타입 지원을 DROP 전에 검사하고, 어느 노드에서도 중간 스키마가 관찰되지 않게 한다. replica 적용 실패 시 HA를 중단할지 재시도할지 정하고, 부분 적용 불가를 수용 기준으로 둔다.

### 검증 방법
중복 값, NULL 값, 디스크 부족, 복제 프로세스 종료를 ADD 단계에 주입한다. 매 실패 후 source/replica의 PK·UK·활성 RK와 데이터가 시작 전과 같은지 확인한다. 성공 사례에서는 전환 전 로그와 후 로그를 모두 적용해 단 한 건도 누락되지 않는지 검사한다.

## [PM-5Y-08] 키 속성 변경의 상태 전이 표가 없다

- 분류: 누락
- 심각도: Critical
- 근거 위치: 원문 4-2절의 후보 존재 시 “모든 DDL 허용” 및 제한된 PK/UK 추가·삭제 예시
- 사실/추론 구분: 확인된 사실 — 복합 키, 컬럼 이름·타입·NULL 속성 변경 및 실제 RK가 아닌 후보 변경의 규칙이 없다
- 영향 대상: 사용자, DBA, 마이그레이션 도구, 복제 정합성

### 문제
문서는 키 제약 추가·삭제 일부만 다루고 키를 구성하는 컬럼 속성 변경을 포괄하지 않는다. 복합 PK/UK의 일부 컬럼 변경, `NOT NULL` 제거, 컬럼 rename, 정수 폭 또는 문자열 collation 변경, 후보가 두 개일 때 활성 RK 자체를 변경하는 DDL이 모두 빠졌다. “다른 후보가 있으면 모든 DDL 허용”은 안전 조건으로 지나치게 넓다.

### 왜 중요한가
UK는 값 비교 규칙과 NULL 허용 여부까지 포함하여 유일성을 만든다. 문자열 collation이 달라지면 같은 두 값의 동등성 판단이 달라질 수 있고, 복합 키 한 컬럼에 NULL이 허용되면 RK 후보 자격을 잃는다. 다른 후보가 있어도 언제 그 후보로 전환되는지 정하지 않으면 기존 로그 적용이 실패한다.

### 재현 또는 구체적 예제

```sql
CREATE TABLE shipment (
  tenant_id INT NOT NULL,
  tracking_no VARCHAR(30) NOT NULL,
  legacy_id INT NOT NULL UNIQUE,
  CONSTRAINT uq_tracking UNIQUE (tenant_id, tracking_no)
) REPLICATION = ON;

ALTER TABLE shipment ALTER COLUMN tracking_no VARCHAR(200);
ALTER TABLE shipment ALTER COLUMN tenant_id DROP NOT NULL;
ALTER TABLE shipment RENAME COLUMN legacy_id AS old_id;
```

활성 RK가 `uq_tracking`인지 `legacy_id`인지에 따라 각 명령의 영향이 다르다. 기대 결과는 각 DDL이 허용·거부되는 이유와 전환할 RK가 명확한 것이다. 문서대로 “후보가 함께 있으면 모두 허용”만 적용하면 두 번째 명령 뒤 복합 UK는 RK 자격을 잃을 수 있다.

### 권고안
상태 전이 표를 추가한다. 행에는 PK/UK 추가·삭제, 컬럼 추가·삭제·rename, 타입·collation·NOT NULL 변경, 키 컬럼 값 UPDATE를 두고 열에는 활성 RK/비활성 후보/마지막 후보 및 single/HA를 둔다. 각 셀에 허용, 거부, 원자적 RK 전환을 표시하고 오류 코드와 사후 RK를 정의한다.

### 검증 방법
표의 모든 셀을 파라미터화한 DDL 시험으로 만든다. 단일·복합 키, 숫자·문자열 타입을 포함하고 명령 전후 활성 RK와 두 노드 스키마를 비교한다. 문서에 없는 DDL이 발견되면 출시 전에 표와 시험을 함께 갱신하도록 추적한다.

## [PM-5Y-09] DDL과 DML 동시 실행 시 로그 해석 규칙이 없다

- 분류: 정확성
- 심각도: Blocker
- 근거 위치: 원문 4절의 모든 DDL 복제 및 4-2절의 운영 중 키 변경 허용
- 사실/추론 구분: 확인이 필요한 질문 — DDL/DML 직렬화, 로그의 키 스키마 버전, 키 UPDATE 처리 방식이 원문에 없다
- 영향 대상: 복제 정합성, 애플리케이션, DBA, 엔진 개발자

### 문제
HA 운영 중 DDL과 DML이 겹칠 때 어느 키 정의로 변경 행을 찾는지 없다. 키 변경을 허용하려면 전환 전 트랜잭션, 전환 트랜잭션, 전환 후 트랜잭션에 명확한 순서가 있어야 한다. 단순히 DDL도 복제된다는 사실만으로 적용 순서와 스키마 해석이 보장되지 않는다.

### 왜 중요한가
트랜잭션 A가 옛 RK로 행을 읽은 뒤 DDL B가 새 RK로 바꾸고 A가 커밋할 수 있다. replica 적용기가 새 카탈로그만 보고 A의 로그를 해석하면 행을 못 찾는다. 반대로 키 자체가 UPDATE되면 old key로 행을 찾고 new key를 저장해야 할 수 있다. 규칙이 없으면 변경 누락과 `fail_count` 문제를 재현한다.

### 재현 또는 구체적 예제

```sql
-- 초기 RK: id
CREATE TABLE wallet (
  id INT PRIMARY KEY,
  wallet_code VARCHAR(20) NOT NULL UNIQUE,
  amount INT
) REPLICATION = ON;

-- 트랜잭션 A
UPDATE wallet SET amount = amount + 10 WHERE id = 7;
-- A가 아직 커밋하지 않은 동안 트랜잭션 B
ALTER TABLE wallet DROP PRIMARY KEY,
  ADD CONSTRAINT pk_wallet_code PRIMARY KEY (wallet_code);
-- 이후 A COMMIT
```

기대 동작은 B가 A를 기다리거나, A가 B보다 먼저 직렬화되거나, 로그가 스키마 세대를 담아 정확히 적용되는 것 중 하나여야 한다. 현재 문서에서는 성공·대기·거부 여부를 알 수 없다.

### 권고안
DDL/DML 직렬화 모델을 명시한다. 권고는 RK 전환 DDL이 관련 테이블의 선행 쓰기 트랜잭션 종료를 기다리고, DDL 로그에 이전·새 RK와 스키마 세대를 기록하며, 후속 DML은 새 세대만 사용하게 하는 것이다. 잠금 대기 시간 초과와 재시도 가능 오류도 제품 계약에 넣는다.

### 검증 방법
전환 직전·중·직후에 INSERT/UPDATE/DELETE를 각각 실행하고 커밋 순서를 바꾼 동시성 시험을 반복한다. replica 지연과 프로세스 재시작을 조합한다. 최종 데이터, 적용 순서, 키 세대, `fail_count`가 기대와 같은지 확인하고 교착·무한 대기가 없는지 측정한다.

## [PM-5Y-10] HA 시작 전 검증이 원자적이고 실행 가능한 절차가 아니다

- 분류: 운영성
- 심각도: Critical
- 근거 위치: 원문 7절의 HA 실행 시 제약 확인, “에러와 함께 파일 리스트 출력”, single에서 수정 후 재시작
- 사실/추론 구분: 확인된 사실 — 검사 시점·일관된 스냅샷·전체 오류 출력·“파일 리스트” 의미가 정의되지 않는다
- 영향 대상: DBA, 운영 자동화, 가용성, 지원 조직

### 문제
HA 시작 검사가 데이터베이스 전체를 어떤 스냅샷에서 검사하는지 없다. 검사 도중 다른 세션이 테이블이나 FK를 바꾸면 통과 직후 위반 상태가 될 수 있다. “파일 리스트”는 위반 테이블 목록의 오기로 보이지만 사실 여부를 확정할 수 없고, 객체 이름·원인·수정안·종료 코드 형식도 없다.

### 왜 중요한가
사전 검사는 발견과 실제 HA 활성화 사이에 상태가 바뀌지 않아야 의미가 있다. 첫 오류만 출력하면 수천 테이블을 한 번씩 고치고 재시작하는 긴 점검이 된다. 자동화는 안정적인 종료 코드와 구조화된 출력이 있어야 배포를 중단하고 담당자에게 정확한 조치를 안내할 수 있다.

### 재현 또는 구체적 예제

초기 DB에 키 없는 ON 테이블과 OFF 부모를 참조하는 ON 자식이 있다고 한다.

```sql
CREATE TABLE event_log (payload VARCHAR(100)) REPLICATION = ON;
CREATE TABLE local_parent (id INT PRIMARY KEY) REPLICATION = OFF;
CREATE TABLE child (
  id INT PRIMARY KEY,
  parent_id INT,
  FOREIGN KEY (parent_id) REFERENCES local_parent(id)
) REPLICATION = ON;
```

HA 시작은 두 위반을 모두 보고해야 한다. 동시에 다른 세션이 정상 테이블의 마지막 UK를 삭제하려 하면 검사와 전환 중 어느 작업이 차단되는지도 정해야 한다. 기대 결과는 원자적 검증 후에만 HA가 활성화되는 것이다.

### 권고안
읽기 전용 `CHECK HA READINESS` 같은 사전 명령과 시작 시 동일 검사를 정의한다. 안정된 카탈로그 스냅샷 또는 전환 잠금으로 검사와 활성화를 묶고, 모든 위반을 객체 ID·소유자·테이블·제약·원인·수정 예시와 함께 출력한다. 검사 비용, 취소, 권한, 머신 판독 형식과 종료 코드를 명시한다.

### 검증 방법
1만 테이블 규모에서 검사 시간과 잠금 영향을 측정한다. 검사 중 CREATE/ALTER/DROP을 경쟁시켜 통과 후 위반 상태가 생기지 않는지 본다. 복수 위반이 한 번에 모두 출력되고 JSON 또는 정해진 형식으로 자동화가 정확히 파싱하는지 확인한다.

## [PM-5Y-11] failover·failback·재가입에서 OFF 데이터의 생명주기가 없다

- 분류: 누락
- 심각도: Critical
- 근거 위치: 원문 4절의 OFF DML 미복제, 6절의 failover 후 VIEW 불일치, 7절의 HA 전환 검사
- 사실/추론 구분: 문서에서 도출한 추론 — OFF 테이블의 구조는 복제되지만 데이터는 노드별로 달라질 수 있으며 역할 전환 뒤 병합·초기화 규칙이 없다
- 영향 대상: 사용자, DBA, 애플리케이션, 복구 담당자

### 문제
OFF 테이블이 failover 후 새 primary에서 쓰이기 시작하면 이전 primary와 서로 다른 두 데이터 집합이 생긴다. failback 또는 노드 재가입 때 어느 쪽을 보존하는지, 테이블을 비우는지, 로컬 데이터를 계속 유지하는지 문서에 없다. ON으로의 변경이 HA 중 금지된다는 규칙만으로 장기 생명주기를 설명하지 못한다.

### 왜 중요한가
HA는 장애 조치 한 번으로 끝나지 않고 노드 복구와 재가입까지 포함한다. 노드별 로컬 테이블이 캐시라면 비워도 되지만 작업 큐라면 두 노드의 행을 합쳐야 할 수 있다. 제품이 자동으로 판단할 수 없으므로 사용자가 데이터 등급을 정하고 실행할 명확한 절차가 필요하다.

### 재현 또는 구체적 예제

```sql
CREATE TABLE local_job (
  job_id INT PRIMARY KEY,
  state VARCHAR(20)
) REPLICATION = OFF;
```

노드 A가 primary일 때 `(1,'RUNNING')`을 저장하고 A 장애 후 B가 primary가 되어 `(2,'DONE')`을 저장한다. A가 복구되어 재가입할 때 A에는 1번만, B에는 2번만 있다. 기대 결과가 A 데이터 삭제, B 데이터 복사, 그대로 로컬 유지, 수동 병합 중 무엇인지 문서는 말하지 않는다.

### 권고안
OFF 테이블의 노드 로컬 생명주기를 제품 계약으로 정의한다. failover, failback, standby 재구축, 백업 복원 각각에서 보존·초기화 여부를 명시하고 운영 훅 또는 제외 목록을 제공한다. OFF 허용 사례를 재생성 가능한 캐시·임시 통계 등으로 제한하는 가이드와 역할 전환 전후 점검 절차를 넣는다.

### 검증 방법
A→B failover→A 재가입→A failback 순서를 수행하며 각 단계의 OFF 행을 기록한다. 문서의 정책대로 데이터가 보존 또는 정리되는지 확인한다. 캐시, 작업 큐, 감사 로그 샘플로 운영자가 절차를 읽고 데이터 처리 결과를 사전에 정확히 예측하는지 검토한다.

## [PM-5Y-12] FK 규칙이 방향·연쇄 동작·기존 객체 전환을 포괄하지 않는다

- 분류: 정확성
- 심각도: Critical
- 근거 위치: 원문 5절의 ON 외래키 테이블은 참조 테이블도 ON이어야 한다는 규칙과 CREATE/ALTER 예시
- 사실/추론 구분: 확인된 사실 — ON 자식→OFF 부모 한 조합만 주로 다루며 OFF 자식→ON 부모, ON/OFF 전환, 연쇄 동작과 기존 FK는 빠져 있다
- 영향 대상: 데이터 정합성, 사용자, DBA, 애플리케이션

### 문제
문서는 “외래키를 포함하는 복제 테이블”의 부모가 ON이어야 한다고 하지만 나머지 조합과 전환 규칙이 없다. OFF 자식이 ON 부모를 참조할 수 있는지, 부모를 OFF로 바꾸려 할 때 기존 ON 자식 때문에 거부되는지, `ON DELETE CASCADE`가 어느 노드에서 어떤 DML을 만드는지 정의하지 않는다.

### 왜 중요한가
FK는 자식 행이 가리키는 부모 행의 존재를 보장한다. 부모만 복제되고 자식은 로컬이면 standby의 자식 집합은 다르지만 FK 자체는 유효할 수 있다. 반대로 ON 자식의 부모가 OFF면 replica에서 DML 적용이 실패할 수 있다. 연쇄 삭제가 원본 DML인지 파생 DML인지에 따라 OFF 경계를 넘어 예상치 않은 삭제 또는 누락이 발생한다.

### 재현 또는 구체적 예제

```sql
CREATE TABLE parent (id INT PRIMARY KEY) REPLICATION = ON;
CREATE TABLE local_child (
  id INT PRIMARY KEY,
  parent_id INT,
  CONSTRAINT fk_pc FOREIGN KEY (parent_id) REFERENCES parent(id)
    ON DELETE CASCADE
) REPLICATION = OFF;

DELETE FROM parent WHERE id = 1;
ALTER TABLE parent REPLICATION = OFF;
```

source에서는 부모 삭제가 로컬 자식 삭제를 유발할 수 있다. replica에는 local_child 데이터가 없거나 다르다. ALTER는 기존 FK 관계 때문에 거부되어야 하는지 불명확하다. 기대 결과는 네 가지 ON/OFF 조합과 연쇄 동작마다 명확해야 한다.

### 권고안
부모/자식 ON/OFF 2×2 행렬과 CREATE FK, DROP FK, 양쪽 REPLICATION 변경 규칙을 추가한다. `CASCADE`, `SET NULL`, `RESTRICT` 각각의 복제 이벤트 출처와 결과를 명시한다. 상태를 위반하게 만드는 ALTER는 원자적으로 거부하고 관련 제약 이름을 오류에 표시한다.

### 검증 방법
2×2 조합에서 INSERT/UPDATE/DELETE와 모든 referential action을 실행한 뒤 양쪽 노드의 데이터와 오류를 비교한다. 기존 FK를 둔 채 부모·자식을 각각 ON↔OFF 변경하는 시험과 failover 시험을 수행한다. 허용 조합은 FK가 유효하고 금지 조합은 스키마가 전혀 변하지 않아야 한다.

## [PM-5Y-13] OFF 테이블을 포함한 VIEW는 ‘제약 없음’이 아니라 결과 계약 위반이다

- 분류: 정확성
- 심각도: Major
- 근거 위치: 원문 6절의 “Failover 후 뷰 사용에는 제약이 없다”와 노드 간 결과 불일치 면책
- 사실/추론 구분: 확인된 사실 — VIEW DDL은 복제되지만 OFF 데이터 때문에 결과가 다를 수 있음을 인정하면서도 사용 제약이 없다고 서술한다
- 영향 대상: 애플리케이션, 최종 사용자, 데이터 분석, 고객 지원

### 문제
문법적으로 VIEW를 조회할 수 있는 것과 failover 후 같은 비즈니스 결과를 제공하는 것은 다르다. “제약이 없다”는 문장은 가용성과 정합성을 오해하게 한다. ON/OFF 조인, 집계, 보안 필터 VIEW의 위험 수준과 경고·조회 방법이 없다.

### 왜 중요한가
애플리케이션은 테이블이 아니라 VIEW만 조회할 수 있다. OFF 테이블이 권한, 가격, 지역 필터에 쓰이면 failover 후 행이 단순히 줄어드는 것이 아니라 잘못 노출되거나 계산될 수 있다. DDL이 존재한다는 사실은 결과 데이터가 유효하다는 뜻이 아니다.

### 재현 또는 구체적 예제

```sql
CREATE TABLE orders (
  order_id INT PRIMARY KEY,
  region VARCHAR(10)
) REPLICATION = ON;
CREATE TABLE local_region_filter (
  region VARCHAR(10) PRIMARY KEY
) REPLICATION = OFF;
CREATE VIEW visible_orders AS
  SELECT o.* FROM orders o
  JOIN local_region_filter f ON f.region = o.region;
```

source의 필터에 `SEOUL`이 있고 standby에는 없다면 failover 후 같은 VIEW가 0행을 반환한다. 기대 결과가 경고, 생성 금지, 명시적 허용 중 무엇인지 없다. 보안 VIEW라면 빈 결과가 아닌 반대 형태의 조인에서 과다 노출도 가능하다.

### 권고안
“실행 가능하지만 결과 동등성을 보장하지 않는다”로 문구를 고치고 위험 등급을 명시한다. VIEW 의존성에서 OFF 테이블을 조회하는 카탈로그/검사 명령을 제공한다. 보안·정산용 VIEW에는 OFF 참조를 금지하거나 명시적 override를 요구하고, HA 시작 보고서에 영향을 받는 VIEW 목록을 포함한다.

### 검증 방법
INNER/LEFT/NOT EXISTS 조인과 SUM/COUNT 집계를 포함한 VIEW를 만들어 failover 전후 결과를 비교한다. 의존성 검사에서 직접·중첩 VIEW 모두 탐지되는지 확인한다. 사용자 시험에서 “제약 없음” 수정 문구를 읽은 사람이 결과 불일치 가능성을 정확히 설명하는지 평가한다.

## [PM-5Y-14] 키 값 UPDATE와 복합·문자열 키의 비용 및 정합성 규칙이 없다

- 분류: 성능
- 심각도: Critical
- 근거 위치: 원문 1절의 PK/NOT NULL UK 선택과 4-2절의 키 제약 변경 규칙; 키 값 DML과 타입별 비용은 없음
- 사실/추론 구분: 확인이 필요한 질문 — 로그가 old/new 키 중 무엇을 담는지와 RK 크기 제한·성능 기준이 정의되지 않는다
- 영향 대상: 복제 정합성, 성능, 애플리케이션, 용량 계획 담당자

### 문제
RK가 되는 컬럼의 값을 UPDATE할 때 replica가 이전 행을 무엇으로 찾고 새 값을 어떻게 반영하는지 없다. 복합 문자열 UK가 자동 선택될 수 있지만 정수 PK 대비 로그 크기, 인덱스 검색, collation 비교 비용과 제한도 없다. “후보이면 선택 가능”만으로 제품 수준의 성능 계약이 되지 않는다.

### 왜 중요한가
UPDATE 적용은 먼저 기존 행을 찾아야 한다. 로그에 새 키만 있으면 replica에는 아직 새 값이 없으므로 행을 못 찾을 수 있다. old와 new를 모두 담으면 로그가 커진다. 복합 `VARCHAR` 키는 행마다 수백 바이트가 될 수 있어 네트워크와 적용 처리량에 직접 영향을 준다.

### 재현 또는 구체적 예제

```sql
CREATE TABLE catalog_item (
  tenant VARCHAR(100) NOT NULL,
  external_code VARCHAR(500) NOT NULL,
  description VARCHAR(1000),
  CONSTRAINT uq_item UNIQUE (tenant, external_code)
) REPLICATION = ON;

UPDATE catalog_item
SET external_code = 'NEW-CODE'
WHERE tenant = 'A' AND external_code = 'OLD-CODE';
```

PK가 없으므로 복합 UK가 RK다. replica는 `(A, OLD-CODE)`로 찾아 새 값을 써야 할 가능성이 있지만 이는 구현 확인이 필요하다. 기대 결과는 중복 충돌 시 전체 트랜잭션 실패, 성공 시 양쪽에 새 키 하나만 존재하는 것이다.

### 권고안
키 값 UPDATE의 old/new 이미지와 적용 순서를 명세한다. 지원 타입, 최대 RK 바이트, 복합 컬럼 수, collation 일치 조건을 정하고 경고 임계값을 둔다. 여러 UK 중 자동 선택할 때 안정성뿐 아니라 크기를 고려할지 여부를 확정하되 결정성을 훼손하지 않는다. 대표 처리량 목표를 수용 기준에 포함한다.

### 검증 방법
정수 단일 키와 2·4·8개 문자열 복합 키로 동일한 UPDATE/DELETE 부하를 실행해 로그 바이트, 네트워크량, 적용 지연, CPU를 비교한다. RK 값 UPDATE, 값 교환, 중복 충돌, 긴 다국어 문자열을 시험하고 최종 행과 `fail_count`를 검사한다.

## [PM-5Y-15] `fail_count`의 정의와 운영 경보 계약이 빠졌다

- 분류: 운영성
- 심각도: Major
- 근거 위치: 원문 전체; RK·HA 오류는 설명하지만 `fail_count`의 증가·초기화·조회·경보 규칙은 없음
- 사실/추론 구분: 확인된 사실 — 대상 문제의 핵심 지표인 `fail_count`가 사용자 스펙 1~9절에 등장하지 않는다
- 영향 대상: DBA, SRE, 고객 지원, 제품 분석

### 문제
기능 목적과 직접 관련된 `fail_count`를 문서가 사용자 계약으로 다루지 않는다. 어떤 적용 실패가 한 번으로 계산되는지, 재시도마다 증가하는지, 재시작·성공 후 초기화되는지, 테이블과 로그 위치를 식별할 수 있는지 없다. RK 전환 오류가 예방되었는지도 운영자가 확인할 수 없다.

### 왜 중요한가
카운터 하나만 증가해도 원인이 같은 로그의 반복 재시도인지 서로 다른 100개 행 실패인지 의미가 다르다. 누적 카운터가 재시작 때 0이 되면 장애가 숨겨지고, 영구 누적이면 현재 장애 여부를 알기 어렵다. 데이터 정합성 문제는 빠른 탐지와 정확한 원인 위치가 복구 시간을 결정한다.

### 재현 또는 구체적 예제

```sql
CREATE TABLE inventory (
  sku INT PRIMARY KEY,
  qty INT
) REPLICATION = ON;
UPDATE inventory SET qty = qty - 1 WHERE sku = 404;
```

replica에서 해당 행을 의도적으로 제거한 뒤 로그를 적용한다고 가정한다. 같은 로그를 10회 재시도하면 `fail_count`가 1인지 10인지, 성공 로그 하나가 뒤따르면 초기화되는지 알 수 없다. 기대 결과는 오류 건 ID, 테이블, LSA/트랜잭션, 첫·최근 시각과 현재 backlog를 구분해 관찰하는 것이다.

### 권고안
`fail_count`의 단위, 증가 조건, 재시도 중복 처리, 보존·초기화 조건을 명시한다. 누적 실패 수와 현재 미해결 실패 수를 분리하고, 테이블·오류 코드·로그 위치·활성 RK 세대를 조회할 수 있게 한다. 경고/위험 임계값, runbook 연결, 메트릭 이름을 공개한다.

### 검증 방법
행 없음, 중복 키, 스키마 세대 불일치, 일시적 잠금 실패를 각각 주입하고 재시도·재시작 전후 메트릭을 기록한다. 문서 정의대로 카운트되는지, 경보가 한 번 발생하고 해소 상태가 표시되는지, 오류에서 문제 테이블과 로그를 찾을 수 있는지 확인한다.

## [PM-5Y-16] 기존 데이터 불일치의 발견과 복구 절차가 없다

- 분류: 누락
- 심각도: Blocker
- 근거 위치: 원문 4절과 6절의 불일치 허용, 7절의 스키마 조건 검사; 행 데이터 비교·교정은 없음
- 사실/추론 구분: 확인된 사실 — HA 시작 검사는 RK와 FK 상태만 다루며 이미 누락된 행·값의 검사나 복구를 정의하지 않는다
- 영향 대상: 기존 고객, DBA, 복제 정합성, 지원 조직

### 문제
이 변경을 도입하는 이유가 과거 PK 변경에 따른 변경 누락이라면 업그레이드 시 이미 불일치한 고객이 존재할 수 있다. 새 DDL 제약은 미래 오류만 줄일 뿐 과거의 누락을 고치지 않는다. 불일치 상태에서 failover하면 새 primary가 잘못된 값을 정답으로 확정할 위험이 있다.

### 왜 중요한가
스키마가 정상이어도 데이터는 다를 수 있다. RK가 생긴 뒤 새 UPDATE가 잘 적용되어도 누락된 과거 행은 계속 남는다. 고객에게 “업그레이드 후 안전”이라고 알리려면 어느 시점부터 안전한지, 사전 데이터 비교와 재동기화가 필요한지 분명해야 한다.

### 재현 또는 구체적 예제

source에는 `(id=1, qty=9)`, replica에는 과거 누락으로 `(id=1, qty=10)`이 있다고 가정한다.

```sql
CREATE TABLE stock (id INT PRIMARY KEY, qty INT) REPLICATION = ON;
UPDATE stock SET qty = qty - 1 WHERE id = 2;
```

새 기능 설치 후 id=2 변경은 정상 복제되어도 id=1 불일치는 그대로다. 이 상태에서 failover하면 애플리케이션은 qty=10을 본다. 기대 결과는 HA 전환 또는 업그레이드 절차가 기존 차이를 탐지하고 승인 전 교정하는 것이다.

### 권고안
출시 범위에 데이터 정합성 검사 도구와 재동기화 runbook을 포함하거나, 없으면 명시적으로 출시 Blocker로 둔다. 테이블/파티션별 행 수와 RK 범위 해시를 비교하고 차이를 상세 조회할 수 있게 한다. 교정 중 쓰기 처리, 정답 노드 선택, 감사 로그, 실패 롤백을 정의한다.

### 검증 방법
행 누락, 추가 행, 비키 값 차이, 키 값 차이를 의도적으로 만든 뒤 검사 도구의 탐지율을 확인한다. 온라인 쓰기 중 비교의 일관성을 시험하고, 문서 절차로 재동기화한 뒤 전체 해시와 표본 행이 일치하는지 검증한다. 불일치가 남은 경우 failover 승인 절차가 차단되는지도 확인한다.

## [PM-5Y-17] unload/load 기본 처리와 요약이 서로 상충한다

- 분류: 호환성
- 심각도: Critical
- 근거 위치: 원문 8절은 복제 변수 없으면 ON, 9절 5항은 포함하지 않는 테이블은 모두 OFF라고 서술
- 사실/추론 구분: 확인된 사실 — 동일한 “복제 여부 정보가 없는 입력”의 기본값이 ON과 OFF로 상충한다
- 영향 대상: 업그레이드·다운그레이드 사용자, DBA, 데이터 이관, 호환성 시험

### 문제
구버전 unload 파일처럼 REPLICATION 정보가 없을 때 8절은 모두 ON으로 간주한다고 하고, 요약은 모두 OFF라고 한다. 어느 쪽을 구현해도 문서 한 부분을 위반한다. ON이면 RK 없는 테이블 때문에 HA 준비가 실패할 수 있고, OFF면 사용자가 기대한 데이터가 standby로 복제되지 않을 수 있다.

### 왜 중요한가
기본값은 이관 결과를 대량으로 바꾼다. 파일에 1만 테이블이 있으면 사용자가 각각 옵션을 확인하기 어렵다. ON/OFF 중 어느 것도 모든 기존 사용자에게 안전하지 않으므로 모호한 자동 결정 대신 정책과 경고, 명시적 선택이 필요하다.

### 재현 또는 구체적 예제

구버전 unload 파일이 다음 두 테이블을 담지만 REPLICATION 필드는 없다고 한다.

```sql
CREATE TABLE keyed_data (id INT PRIMARY KEY, value VARCHAR(20));
CREATE TABLE heap_data (value VARCHAR(20));
```

8절대로면 둘 다 ON이고 `heap_data` 때문에 HA 시작이 실패한다. 9절대로면 둘 다 OFF여서 `keyed_data`도 복제되지 않는다. 기대 결과를 사용자가 load 전에 선택하고 결과 보고서에서 확인할 수 있어야 한다.

### 권고안
상충 문장을 하나의 정책으로 통일한다. 권고는 파일에 값이 없으면 load 명령의 명시 옵션(`--default-replication=ON|OFF|ERROR`)을 요구하거나 안전 프로필에서는 ERROR로 중단하는 것이다. 테이블별 판정과 RK 유무를 dry-run 보고서로 제공한다. 구버전→신버전, 신버전→구버전 다운그레이드 정책도 추가한다.

### 검증 방법
REPLICATION 필드가 없음/ON/OFF인 세 파일과 RK 있음/없음 조합을 load한다. 명시 옵션별 결과, 경고, 종료 코드, HA readiness를 검증한다. 문서 8절과 9절의 동일 사례가 같은 결과를 말하는지 문서 린트·리뷰 체크리스트로 확인한다.

## [PM-5Y-18] 혼합 버전 HA와 성능 회귀의 출시 기준이 없다

- 분류: 호환성
- 심각도: Blocker
- 근거 위치: 원문 8절의 하위 버전 unload 언급; 1~9절에 롤링 업그레이드, 로그·카탈로그 버전, 부하 기준 없음
- 사실/추론 구분: 확인이 필요한 질문 — 구버전 노드가 REPLICATION/RK 메타데이터와 새 DDL 로그를 이해하는지 확인되지 않았다
- 영향 대상: 기존 HA 고객, DBA, 릴리스 관리자, 지원 조직

### 문제
HA 운영자는 무중단을 위해 노드를 순차 업그레이드할 수 있지만 문서는 신·구 버전 혼합 시 새 DDL과 카탈로그를 어떻게 처리하는지 다루지 않는다. 또한 자동 RK 선택이 복합 UK를 택할 때 로그량과 적용 지연 허용 기준이 없다. 기능이 단일 버전 기능 시험을 통과해도 실제 업그레이드에서 복제가 멈출 수 있다.

### 왜 중요한가
구버전 replica가 새 DDL 로그를 모르면 무시하거나 적용 실패할 수 있다. 그 상태에서 failover하면 새 옵션을 잃거나 OFF 테이블을 잘못 복제할 수 있다. 성능 면에서도 RK가 정수 PK에서 긴 문자열 UK로 바뀌면 네트워크와 인덱스 비교 비용이 커져 지연 목표를 위반할 수 있다.

### 재현 또는 구체적 예제

노드 A는 신버전, B는 구버전인 상태를 가정한다.

```sql
CREATE TABLE session_cache (
  token VARCHAR(512) NOT NULL UNIQUE,
  payload VARCHAR(2000)
) REPLICATION = OFF;
ALTER TABLE existing_table
  ADD CONSTRAINT uq_existing_code UNIQUE (code);
```

B가 `REPLICATION=OFF`와 RK 메타데이터를 모르면 DDL 적용 결과가 다를 수 있다. 동시에 초당 5만 UPDATE를 수행할 때 긴 UK가 RK이면 지연이 급증할 수 있다. 기대 결과는 지원 여부가 명시되고, 비지원이면 새 문법이 혼합 기간에 선제 차단되는 것이다.

### 권고안
버전 N/N-1 조합별 지원 행렬을 정의한다. 로그·카탈로그 capability 협상과 최소 버전을 검사하고, 구버전 노드가 있으면 새 DDL을 명확한 오류로 거부한다. 롤링 업그레이드와 롤백 절차를 제공한다. 대표 키 크기·TPS에서 처리량, p95 적용 지연, 로그 증가율의 허용 회귀율을 출시 기준으로 정한다.

### 검증 방법
N-1 replica→N primary, N replica→N-1 primary 양방향으로 DDL/DML과 failover를 시험한다. 중간 롤백도 수행한다. 정수 PK, 짧은 UK, 긴 복합 UK에서 기준 버전 대비 TPS·로그량·지연을 측정하고 합의한 한계를 넘으면 출시를 차단한다.

## [PM-5Y-19] 예제에 초기 상태·예상 결과·실패 후 상태 설명이 부족하다

- 분류: 문서 품질
- 심각도: Major
- 근거 위치: 원문 2~5절 예시 1~23의 대부분이 SQL과 `OK`/`ERROR`만 제공
- 사실/추론 구분: 확인된 사실 — 예제의 실행 모드, 선행 테이블 정의, 활성 RK, 오류 이유와 사후 상태가 자주 생략된다
- 영향 대상: 입문 사용자, QA, 기술 지원, 문서 독자

### 문제
독자는 예시 12의 `table_name`이 어떤 컬럼과 제약을 갖는지, 예시 14에서 현재 UK가 무엇인지 알 수 없다. 같은 SQL도 초기 RK 후보 수와 HA 상태에 따라 결과가 달라지므로 `OK`/`ERROR`만으로는 학습하거나 시험할 수 없다. 예제가 정책을 설명하기보다 결론을 암기하게 한다.

### 왜 중요한가
입문자는 데이터베이스가 이전 명령의 상태를 기억한다는 점과 PK·UK·RK의 차이를 예제로 배운다. 선행 상태가 없으면 ERROR가 SQL 문법 때문인지 HA 정책 때문인지 구분할 수 없다. 실패 후 기존 제약이 유지되는지도 알아야 안전하게 재시도할 수 있다.

### 재현 또는 구체적 예제

원문의 예시 15는 다음 두 초기 상태에서 결과가 달라질 수 있다.

```sql
-- 상태 A: UK가 하나뿐이어서 활성 RK
CREATE TABLE a (id INT NOT NULL CONSTRAINT uq_a UNIQUE) REPLICATION = ON;

-- 상태 B: PK도 있으므로 문서 우선순위상 UK는 후보
CREATE TABLE b (
  pk INT PRIMARY KEY,
  id INT NOT NULL CONSTRAINT uq_b UNIQUE
) REPLICATION = ON;
```

`DROP CONSTRAINT uq_a`는 마지막 RK 제거라 거부되어야 하지만 `DROP CONSTRAINT uq_b`는 허용될 가능성이 있다. 기대 결과와 이유, 실패 후 제약 목록을 나란히 설명해야 한다.

### 권고안
각 예제를 “목적, 모드, 초기 스키마/데이터, 활성 RK, 실행 SQL, 예상 코드·메시지, 사후 스키마/데이터, 이유” 템플릿으로 다시 쓴다. 동일 SQL이 상태에 따라 달라지는 경우 성공/실패 대조 예제를 제공한다. 용어 첫 등장에는 짧은 정의를 링크한다.

### 검증 방법
컴퓨터공학 입문 수준의 검토자에게 예제만 주고 다음 명령의 결과와 사후 RK를 예측하게 한다. 정답률 목표를 정하고, 오답 원인이 생략된 상태라면 문서를 보완한다. 동시에 예제 자동 실행 결과와 서술 결과가 일치하는지 CI에서 검사한다.

## [PM-5Y-20] 용어·오탈자·상충 표현이 정책 해석을 방해한다

- 분류: 문서 품질
- 심각도: Minor
- 근거 위치: 원문 1절의 hb start 외 모두 single, 5-1절 `CRATE TABLE`, 7절 “파일 리스트”·“재시작해아한다”, 9절 `REPLICATION 를`; master/slave와 HA 전환 표현
- 사실/추론 구분: 확인된 사실 — 다수 오탈자와 모드·전환 표현의 불일치가 있으며, “파일 리스트”가 무엇을 뜻하는지는 확인이 필요하다
- 영향 대상: 모든 문서 독자, 번역·지원·교육 담당자, 자동화 도구 작성자

### 문제
단순 철자 오류뿐 아니라 기능 의미를 바꿀 수 있는 표현이 섞여 있다. `CRATE TABLE`은 검색을 방해하고, “HA 전환”이 HA 시작인지 failover인지 모호하다. `cubrid hb start` 이외를 모두 single이라고 하면 SA 모드와 일반 서버 비-HA 상태의 차이가 사라진다. “파일 리스트”는 테이블 목록인지 실제 파일 목록인지 알 수 없다.

### 왜 중요한가
같은 용어가 두 사건을 가리키면 운영자는 잘못된 시점에 명령을 수행한다. HA 시작 전 single에서 고치라는 절차와 장애 중 failover 절차는 허용 시간과 위험이 완전히 다르다. 오탈자가 많은 정책 문서는 오류 메시지·매뉴얼·UI 용어도 서로 달라질 가능성을 높인다.

### 재현 또는 구체적 예제

```text
상황 1: 비-HA 서버를 `cubrid server start db`로 실행
상황 2: `cubrid hb start`로 HA 클러스터 시작
상황 3: 운영 중 primary 장애로 standby가 승격
상황 4: SA 모드에서 관리 작업 수행
```

원문의 “HA 전환”이 상황 2와 3 중 어디를 뜻하는지 절마다 해석해야 하고, 상황 1과 4는 모두 single로 묶이는 것처럼 보인다. 기대 결과는 네 사건에 서로 다른 표준 용어와 허용 SQL 표가 있는 것이다.

### 권고안
용어집에 server/non-HA, standalone(SA), HA 구동, role failover, failback을 분리 정의하고 문서 전체에서 통일한다. master/slave는 원문 호환 표기 뒤 source/replica 또는 primary/standby를 병기한다. `CRATE`→`CREATE`, “파일 리스트”→의도한 객체 목록, 기타 조사·띄어쓰기를 교정한다. 8절과 9절처럼 의미 상충은 교정이 아니라 정책 결정으로 처리한다.

### 검증 방법
문서 용어 린트를 만들어 금지·권장 용어와 알려진 오탈자를 검사한다. 네 상황을 운영자에게 제시하고 각 절이 어느 상황에 적용되는지 답하게 하여 해석이 일치하는지 확인한다. 번역본에서도 SQL 키워드와 모드 이름이 동일하게 유지되는지 검토한다.

## [PM-5Y-21] 복제 정책을 변경할 권한과 역할 분리가 정의되지 않았다

- 분류: 보안
- 심각도: Critical
- 근거 위치: 원문 2-1~2-2절의 `REPLICATION=ON|OFF` 생성·변경 문법; 실행 권한과 승인 주체는 없음
- 사실/추론 구분: 확인된 사실 — 문서는 “사용자”가 옵션을 쓸 수 있다고만 하며 테이블 소유자, 일반 DDL 권한자, DBA 중 누가 데이터 보호 등급을 바꿀 수 있는지 명시하지 않는다
- 영향 대상: 보안 관리자, DBA, 테이블 소유자, 복제 데이터 보호

### 문제
일반적인 ALTER 권한만 가진 계정이 ON 테이블을 OFF로 바꿀 수 있다면 복제와 장애 조치 보호를 조용히 제거할 수 있다. 반대로 권한을 DBA로만 제한한다면 기존 배포 계정과 마이그레이션 도구의 호환 영향이 생긴다. 이 중요한 권한 계약이 없다.

### 왜 중요한가
ON→OFF는 단순 스키마 변경이 아니라 재해 복구 범위를 바꾸는 작업이다. 실수나 계정 탈취로 설정이 바뀌면 SQL은 성공해도 이후 변경 데이터가 standby에 없어진다. 최소 권한과 역할 분리가 있어야 위험 변경을 승인 가능한 사람만 수행한다.

### 재현 또는 구체적 예제

```sql
-- app_migrator는 orders의 일반 ALTER 권한만 있다고 가정
ALTER TABLE orders REPLICATION = OFF;
INSERT INTO orders VALUES (9001, 10000);
```

첫 SQL이 성공하면 이후 주문이 replica에 없을 수 있다. 기대 결과는 별도의 `ALTER REPLICATION` 권한이 없으면 객체·요청 계정·필요 권한을 포함한 오류가 발생하는 것이다.

### 권고안
CREATE 시 설정, ON→OFF, OFF→ON, RK 제약 변경을 각각 권한 행렬로 정의한다. 데이터 보호를 낮추는 ON→OFF에는 별도 시스템 권한이나 DBA 승인 정책을 요구하고, 권한 위임·회수와 소유권 이전 결과를 명시한다.

### 검증 방법
DBA, owner, ALTER만 가진 계정, DML 전용 계정으로 네 변경을 실행한다. 허용 행렬과 결과가 같고 권한 없는 시도는 설정·로그·데이터를 전혀 변경하지 않는지 확인한다.

## [PM-5Y-22] 복제 정책과 RK 변경의 감사 이력이 없다

- 분류: 운영성
- 심각도: Major
- 근거 위치: 원문 2-2절의 REPLICATION 및 RK 관련 ALTER, 2-3절의 현재 상태 조회
- 사실/추론 구분: 확인된 사실 — 현재 ON/OFF 조회 예시는 있지만 누가 언제 왜 변경했는지 확인하는 이력 계약은 없다
- 영향 대상: 감사 담당자, 보안팀, 고객 지원, 장애 분석

### 문제
현재 상태만으로는 장애 발생 전에 테이블이 잠시 OFF였는지, 어느 DDL이 활성 RK를 바꿨는지 알 수 없다. 사용자 실수, 도구 배포, 엔진 자동 선택을 구분할 증거가 없다.

### 왜 중요한가
복제 누락 범위를 정하려면 설정이 바뀐 시작·종료 시각과 로그 위치를 알아야 한다. 이력이 없으면 전체 테이블을 재동기화해야 하거나 원인을 재현하지 못해 같은 사고가 반복된다.

### 재현 또는 구체적 예제

```sql
ALTER TABLE customer REPLICATION = OFF;
-- 30분 뒤
ALTER TABLE customer REPLICATION = ON;
```

현재 조회에는 ON만 남는다. 기대 결과는 변경 계정, 이전/새 값, 트랜잭션·로그 위치, 시각, 클라이언트 식별자와 영향 경고가 감사 기록에 남는 것이다.

### 권고안
REPLICATION과 활성 RK의 모든 상태 전이에 불변 감사 이벤트를 남긴다. 보존 기간, 조회 권한, 시각 기준, 로그 위치, 성공·실패 시도를 정의하고 변경 티켓 ID 같은 사유 메타데이터를 선택 또는 필수로 받는 정책을 검토한다.

### 검증 방법
성공·실패·롤백된 CREATE/ALTER를 여러 계정으로 실행한다. 감사 이력만으로 상태 타임라인과 잠재 미복제 구간을 재구성할 수 있고 일반 사용자가 기록을 변조하지 못하는지 확인한다.

## [PM-5Y-23] 파티션 테이블의 RK와 REPLICATION 상속 규칙이 없다

- 분류: 누락
- 심각도: Critical
- 근거 위치: 원문 2-3절 `db_class` 예시에 `partitioned` 속성이 보이지만 1~9절에 파티션 상호작용은 없음
- 사실/추론 구분: 확인이 필요한 질문 — 대상 CUBRID 버전의 파티션별 PK/UK 및 DDL 지원 범위와 REPLICATION 저장 단위는 구현 확인이 필요하다
- 영향 대상: 대형 테이블 사용자, DBA, 복제 정합성, 제품 지원

### 문제
부모 테이블과 파티션이 ON/OFF를 따로 가질 수 있는지, RK 유일성이 전체 테이블 기준인지 파티션 내부 기준인지, 파티션 추가·교환·분할 시 활성 RK가 유지되는지 설명이 없다.

### 왜 중요한가
파티션 내부에서만 유일한 키는 전체 테이블에서는 같은 값이 여러 개일 수 있다. 복제 로그가 파티션 ID 없이 RK 값만 담으면 replica가 어느 행을 수정할지 모른다. 파티션 교환은 대량 데이터를 DDL 한 번으로 이동하므로 일반 DML 복제와 의미도 다르다.

### 재현 또는 구체적 예제

```sql
-- 실제 지원 문법은 해당 CUBRID 버전에서 확인 필요
CREATE TABLE sales (
  sale_month INT NOT NULL,
  sale_id INT NOT NULL,
  amount INT,
  UNIQUE (sale_month, sale_id)
) REPLICATION = ON
PARTITION BY RANGE (sale_month) (...);
```

새 파티션 추가와 교환 중 `sale_id`만으로 행을 찾을 수 있는지, 부모 설정이 새 파티션에 상속되는지 불명확하다.

### 권고안
지원 객체를 확인한 뒤 부모/자식 파티션의 설정 저장 단위, 전체 유일성 요구, partition ID 포함 여부, ADD/DROP/SPLIT/MERGE/EXCHANGE별 복제 결과를 제품 범위에 추가한다. 미지원 조합은 생성 시 명확히 거부한다.

### 검증 방법
지원되는 모든 파티션 DDL과 각 경계의 INSERT/UPDATE/DELETE를 실행하고 failover한다. 동일 RK 값이 다른 파티션에 있는 사례에서 정확한 행이 적용되고 설정·행 수·파티션 경계가 양 노드에서 같은지 확인한다.

## [PM-5Y-24] CTAS·LIKE·복제 테이블 복사 시 설정 전파 규칙이 없다

- 분류: 호환성
- 심각도: Major
- 근거 위치: 원문 2-1절은 일반 `CREATE TABLE`만 설명; 생성 계열 SQL의 ON/OFF·제약 복사 범위는 없음
- 사실/추론 구분: 확인이 필요한 질문 — `CREATE TABLE ... AS SELECT`나 `LIKE`의 실제 지원 문법은 버전 확인이 필요하다
- 영향 대상: 데이터 이관 사용자, 분석 작업, 스키마 도구, HA 준비

### 문제
기존 테이블을 복사해 새 테이블을 만드는 경로에서 REPLICATION 기본값과 RK 제약이 함께 복사되는지 없다. 데이터만 복사되고 PK/UK가 빠지는데 기본 ON이면 HA에서 생성 또는 다음 시작이 실패할 수 있다.

### 왜 중요한가
사용자는 복사 SQL을 “원본과 같은 테이블”로 이해하기 쉽다. 실제로 제약이나 옵션이 빠지면 원본은 ON/RK 보유, 사본은 ON/RK 없음 또는 OFF라는 예상 밖 결과가 된다.

### 재현 또는 구체적 예제

```sql
CREATE TABLE customer_copy AS SELECT * FROM customer;
-- 또는 실제 지원 시
CREATE TABLE customer_copy LIKE customer;
```

customer가 ON이고 PK를 가져도 copy가 PK와 ON/OFF를 어떻게 얻는지 문서에 없다. 기대 결과는 각 생성 방식의 제약·데이터·REPLICATION 복사 여부가 표로 정해지는 것이다.

### 권고안
지원되는 모든 생성 계열 SQL을 목록화하고 옵션 생략 시 결과, 원본 설정 상속 여부, RK 없는 ON 결과 처리와 오류를 정의한다. `SHOW CREATE TABLE`로 사후 결과를 확인하는 예제를 제공한다.

### 검증 방법
ON/OFF × PK/UK/키 없음 원본을 각 복사 문법으로 생성한다. 새 객체의 데이터, 제약, 활성 RK와 설정이 명세표와 같고 HA readiness가 예상대로 동작하는지 확인한다.

## [PM-5Y-25] 하나의 트랜잭션에서 ON/OFF 테이블을 함께 변경하는 계약이 없다

- 분류: 정확성
- 심각도: Critical
- 근거 위치: 원문 4절의 ON 데이터만 복제 및 모든 DDL 복제; 혼합 DML 트랜잭션은 없음
- 사실/추론 구분: 문서에서 도출한 추론 — source에서 원자적인 트랜잭션이 replica에서는 ON 변경만 남는 부분 효과를 가질 수 있다
- 영향 대상: 애플리케이션, 트랜잭션 정합성, 장애 조치, 제품 지원

### 문제
한 커밋이 ON 업무 테이블과 OFF 보조 테이블을 함께 바꾸면 replica에는 일부 변경만 존재한다. 이것을 정상적인 부분 복제로 지원하는지, 혼합 트랜잭션을 금지하는지, trigger나 FK에서 간접 발생한 OFF 변경도 같은지 정하지 않았다.

### 왜 중요한가
트랜잭션의 의미는 모든 변경이 함께 성공한다는 것이다. replica에서 절반만 보존되면 failover 후 애플리케이션 불변식이 깨질 수 있다. 단순히 OFF 불일치 면책만으로 혼합 커밋의 업무 의미를 설명할 수 없다.

### 재현 또는 구체적 예제

```sql
-- 한 트랜잭션
UPDATE account SET balance=balance-100 WHERE id=1; -- ON
INSERT INTO local_outbox(id, payload) VALUES (50,'send receipt'); -- OFF
COMMIT;
```

failover 후 잔액은 줄었지만 영수증 작업은 없을 수 있다. 기대 결과가 허용이라면 이 제약을 명확히 경고해야 한다.

### 권고안
혼합 트랜잭션을 지원·금지·경고 중 하나로 결정한다. 허용하면 replica의 원자성 범위가 ON 부분으로 축소됨을 계약화하고 영향 분석 도구를 제공한다. trigger·procedure·연쇄 동작으로 생긴 간접 변경도 같은 분류에 포함한다.

### 검증 방법
직접 DML과 간접 파생 DML로 ON/OFF 혼합 트랜잭션을 commit·rollback·crash한다. source와 replica에서 문서가 약속한 원자성 범위와 failover 후 애플리케이션 결과를 확인한다.

## [PM-5Y-26] 온라인 키 전환의 잠금·진행률·취소 계약이 없다

- 분류: 성능
- 심각도: Critical
- 근거 위치: 원문 4-2절은 HA 운영 중 키 변경을 허용하지만 대형 테이블 제약 검증과 인덱스 구축의 서비스 영향은 없음
- 사실/추론 구분: 확인이 필요한 질문 — 해당 DDL이 온라인인지, 쓰기를 차단하는지와 실제 잠금 구현은 확인 필요하다
- 영향 대상: 운영 사용자, 애플리케이션 SLA, DBA, 고객 지원

### 문제
수억 행에서 새 UK/PK를 추가하려면 중복 검사와 인덱스 구축이 필요할 수 있다. 문서는 작업 중 읽기·쓰기가 가능한지, 진행률·예상 공간·취소 결과·timeout을 제공하지 않는다.

### 왜 중요한가
원자성이 보장돼도 수시간 쓰기가 멈추거나 임시 공간이 가득 차면 운영 장애다. 사용자는 점검 시간을 잡을지 온라인 배포할지 결정할 수 있어야 하고, 취소 시 옛 RK가 안전하게 남아야 한다.

### 재현 또는 구체적 예제

```sql
ALTER TABLE huge_event
  ADD CONSTRAINT uq_event_external UNIQUE (external_id),
  DROP PRIMARY KEY;
```

10억 행과 디스크 여유 15% 환경을 가정한다. 기대 결과는 시작 전 예상 자원, 실행 중 진행률과 차단 범위, 안전 취소 결과가 알려지는 것이다.

### 권고안
지원하는 online/offline 모드, 잠금 수준, 동시 DML 처리, 임시 디스크 추정, 진행률, timeout·cancel·resume 정책을 명시한다. 사전 중복 검사와 영향 예측 명령을 수용 범위에 넣는다.

### 검증 방법
크기별 테이블에서 동시 읽기·쓰기와 키 전환을 수행하고 p95 지연, lock wait, 임시 공간, 복제 lag를 측정한다. 취소·공간 부족 후 옛 RK와 데이터가 완전히 유지되는지 확인한다.

## [PM-5Y-27] 테이블·제약·컬럼 rename 후 객체 정체성 보존이 없다

- 분류: 정확성
- 심각도: Critical
- 근거 위치: 원문 4-2절은 제약 추가·삭제만 다루며 2-3절 조회는 이름 중심; rename 상태 전이는 없음
- 사실/추론 구분: 확인이 필요한 질문 — 복제 로그가 이름 또는 내부 ID 중 무엇을 참조하는지 원문에 없다
- 영향 대상: 스키마 변경 사용자, 복제 정합성, 감사·모니터링

### 문제
활성 RK 제약, 구성 컬럼 또는 테이블 이름을 바꿀 때 과거 로그와 모니터링 이력이 새 객체에 연결되는지 없다. 이름을 identity로 사용하면 rename 전 로그를 적용하지 못할 수 있다.

### 왜 중요한가
이름은 사용자가 바꾸는 표시이고 내부 객체 정체성은 계속 유지돼야 한다. 그렇지 않으면 정상적인 이름 정리만으로 복제가 중단되며 오류 이력이 다른 테이블처럼 분리된다.

### 재현 또는 구체적 예제

```sql
ALTER TABLE customer RENAME COLUMN customer_id AS id;
ALTER TABLE customer RENAME CONSTRAINT pk_customer AS pk_customer_id;
RENAME TABLE customer AS account_holder;
```

각 문법의 실제 지원 여부는 확인 필요하다. 전환 전 UPDATE 로그가 rename 후에도 같은 객체와 컬럼을 찾아야 한다.

### 권고안
지원 rename 문법별로 내부 table/column/constraint ID 보존 여부, schema generation, 과거 로그·감사·경보 표시 이름을 정의한다. ID가 바뀌는 작업은 원자적 RK 전환으로 분류한다.

### 검증 방법
복제 적용을 지연한 상태에서 각 rename을 수행하고 옛·새 이름으로 생성된 DML을 차례로 적용한다. 최종 데이터와 객체 ID, 감사 이력 연결이 유지되는지 확인한다.

## [PM-5Y-28] UNIQUE 제약과 UNIQUE 인덱스의 RK 자격 경계가 모호하다

- 분류: 모호성
- 심각도: Critical
- 근거 위치: 원문 1절은 Not Null Unique Key를 후보로 정의하지만 4-2절 예시 16은 `DROP INDEX`를 RK 후보 제거로 설명
- 사실/추론 구분: 확인된 사실 — UNIQUE constraint와 unique index를 같은 후보로 보는지, 제약이 생성한 backing index를 사용자가 직접 삭제할 수 있는지 구분하지 않는다
- 영향 대상: 사용자, optimizer/인덱스 운영, 복제 정합성

### 문제
문서 용어는 UK 제약을 후보로 말하면서 삭제 예제는 일반 이름의 INDEX를 사용한다. 단순 non-unique index가 RK 후보일 수는 없는지, unique index만으로 후보가 되는지, 인덱스 rebuild가 RK 전환인지 알 수 없다.

### 왜 중요한가
DBA는 성능을 위해 인덱스를 재구축·rename·drop한다. 활성 RK의 물리 인덱스와 논리 UNIQUE 제약 관계가 불명확하면 유지보수 작업이 복제를 중단하거나 불필요하게 거부될 수 있다.

### 재현 또는 구체적 예제

```sql
CREATE TABLE t (id INT NOT NULL, value INT);
CREATE UNIQUE INDEX ux_t_id ON t(id);
ALTER TABLE t REPLICATION = ON;
DROP INDEX ux_t_id ON t;
```

첫 인덱스가 RK 후보인지, ON 전환이 성공하는지, DROP이 제약 오류인지 원문으로 판단할 수 없다.

### 권고안
후보를 논리 제약 기준인지 물리 unique index 기준인지 확정한다. backing index rebuild/rename/drop, 온라인 재구축과 optimizer 통계 갱신이 활성 RK에 미치는 영향을 별도 상태표로 제공한다.

### 검증 방법
PK backing index, UNIQUE constraint index, 독립 unique/non-unique index를 만들고 후보 조회·ON 전환·rebuild/drop을 실행한다. 허용 결과와 활성 RK가 문서 정의와 일치하는지 확인한다.

## [PM-5Y-29] TRUNCATE·대량 적재·INSERT SELECT의 복제 범위가 없다

- 분류: 누락
- 심각도: Critical
- 근거 위치: 원문 1절·4절은 DDL 전체와 “데이터” 복제를 구분하지만 경계 명령을 분류하지 않는다
- 사실/추론 구분: 확인이 필요한 질문 — `TRUNCATE`, bulk load, `INSERT ... SELECT`의 실제 로그·복제 방식은 구현 확인 필요하다
- 영향 대상: 데이터 이관, 배치 사용자, 복제 정합성, 복구 시간

### 문제
TRUNCATE가 DDL로 복제되면 OFF 테이블에서도 replica 로컬 데이터를 지울 수 있고, DML로 필터링되면 지우지 않을 수 있다. 대량 적재가 일반 DML 로그를 우회하는 경로라면 ON 데이터가 누락될 위험도 있다.

### 왜 중요한가
경계 명령 하나가 수억 행에 영향을 준다. 일반 INSERT 예제만 통과해도 bulk 경로가 RK 로그를 만들지 않으면 대규모 불일치가 발생한다. OFF 노드 로컬 데이터가 DDL 때문에 삭제되는 것도 사용자 기대와 충돌한다.

### 재현 또는 구체적 예제

```sql
TRUNCATE TABLE local_cache; -- OFF라고 가정
INSERT INTO target_on SELECT * FROM staging_off;
```

첫 명령이 모든 노드의 local_cache를 지우는지, 둘째 결과 행이 ON target에 정상 복제되는지 명세가 없다.

### 권고안
TRUNCATE, bulk loader, import, `INSERT SELECT`, replace 계열 등 지원 명령을 DDL/DML/특수 로그로 분류하고 ON/OFF별 결과를 표로 제공한다. 고속 경로도 RK·트랜잭션 불변식을 우회하지 못하게 한다.

### 검증 방법
각 대량 경로를 ON/OFF source·target 조합에서 commit·rollback·crash하고 failover한다. 행 수·체크섬과 로컬 데이터 보존 결과가 명세와 같은지 확인한다.

## [PM-5Y-30] PITR 복원 시 RK 세대와 로그 시점의 결합이 없다

- 분류: 호환성
- 심각도: Blocker
- 근거 위치: 원문 8절은 unload/load만 다루며 시점 복구(PITR), 백업 시점과 후속 로그 적용은 없음
- 사실/추론 구분: 확인이 필요한 질문 — CUBRID 대상 버전의 PITR 기능과 RK 메타데이터 보존 방식은 확인 필요하다
- 영향 대상: 재해 복구 사용자, DBA, 데이터 정합성

### 문제
백업은 옛 RK 세대에서 찍히고 복구 목표 시점은 새 RK 전환 이후일 수 있다. 복원 과정이 DDL 로그와 DML 로그를 올바른 순서와 세대로 재생하지 못하면 행을 찾지 못하거나 잘못된 활성 RK로 끝난다.

### 왜 중요한가
복제 기능이 정상이어도 재해 복구에서 과거부터 로그를 재생할 때 모든 키 전환을 다시 통과한다. 이 경로를 정의하지 않으면 가장 필요한 사고 시점에만 복구가 실패할 수 있다.

### 재현 또는 구체적 예제

```text
T1: PK(id) 상태에서 full backup
T2: id 기반 UPDATE 로그
T3: PK(id)→UK(email) 전환
T4: email 기반 UPDATE 로그
T5: 목표 시점 복원
```

복원 결과는 T5의 스키마와 데이터를 정확히 재현해야 한다.

### 권고안
지원 복구 방식별로 백업에 포함되는 REPLICATION·활성 RK·세대 메타데이터와 DDL/DML replay 순서를 정의한다. 복구 목표가 전환 중간을 가리킬 때 허용되는 일관된 시점과 오류를 명시한다.

### 검증 방법
각 T1~T5 경계로 목표 시점을 바꿔 복원한다. 스키마, 활성 RK, 행 체크섬과 로그 적용 위치가 원본 시점과 같은지 확인하고 중간 crash 후 재개도 시험한다.

## [PM-5Y-31] 옛 RK 로그를 위한 보관 한계와 용량 정책이 없다

- 분류: 운영성
- 심각도: Critical
- 근거 위치: 원문 4-2절은 RK 전환을 허용하지만 적용 지연·재적용에 필요한 이전 키 정의의 보존 기간은 없음
- 사실/추론 구분: 문서에서 도출한 추론 — 전환 전 로그가 남아 있는 동안에는 옛 RK 정의 또는 변환 정보가 필요할 수 있으나 보관 조건이 없다
- 영향 대상: 운영자, 로그 저장소, 복제 정합성, 용량 계획

### 문제
replica가 장기간 중단됐거나 재적용이 필요하면 옛 RK 세대 로그가 남는다. 엔진이 현재 키만 보존한다면 적용이 불가능하고, 모든 세대를 무기한 보존하면 카탈로그·로그 용량이 증가한다.

### 왜 중요한가
보관 한계는 장애 허용 시간과 직접 연결된다. 사용자가 replica를 7일 중단할 수 있다고 생각해도 옛 키 정의가 24시간 뒤 정리되면 전체 재구축만 가능할 수 있다.

### 재현 또는 구체적 예제

```text
1. replica B를 72시간 중단
2. A에서 RK를 id→email→external_id로 두 번 변경
3. B 재시작 후 오래된 id 기반 로그부터 적용
```

B가 필요한 세대를 얻는지, 재구축이 필요한지 예측할 수 없다.

### 권고안
세대 메타데이터와 로그의 보관·정리 조건, 최소 지원 lag, 디스크 경고, 재적용 불가 시 재동기화 절차를 정의한다. 현재 backlog가 참조하는 세대는 삭제하지 않는 불변식을 둔다.

### 검증 방법
다양한 중단 기간과 여러 RK 전환을 조합하고 보관 정리를 실행한다. backlog에 필요한 세대가 유지되며 용량 임계값에서는 사전 경고와 안전한 재구축 안내가 나오는지 확인한다.

## [PM-5Y-32] split-brain에서 서로 다른 RK DDL을 병합할 정책이 없다

- 분류: 정확성
- 심각도: Blocker
- 근거 위치: 원문 4절의 master DDL 복제와 6절의 failover; 두 노드가 동시에 primary가 되는 최악 장애는 없음
- 사실/추론 구분: 확인이 필요한 질문 — split-brain 방지와 충돌 DDL 처리 방식은 구현 확인이 필요하다
- 영향 대상: 최악 장애 대응, 복제 정합성, 지원 조직

### 문제
네트워크 분할로 A와 B가 각각 primary가 되어 서로 다른 PK/RK 전환과 DML을 받으면 자동 합칠 수 없다. 문서는 정상적인 한 master만 가정하며 fencing 실패 뒤 어느 노드를 정답으로 선택할지 없다.

### 왜 중요한가
키 정의가 다른 두 데이터 집합은 행 identity 자체가 다르다. 값 충돌만 비교하는 일반 병합으로는 같은 업무 행인지 판단하지 못해 조용한 중복·손실이 생길 수 있다.

### 재현 또는 구체적 예제

```text
분할 중 A: RK id→email, email 기반 UPDATE
분할 중 B: RK id→external_no, external_no 기반 UPDATE
네트워크 복구 후 재가입 시도
```

두 변경을 자동 적용해서는 안 되며 어느 쪽을 authoritative로 택할지 명시적 절차가 필요하다.

### 권고안
fencing과 단일 writer를 전제 조건으로 명시하고 split-brain 감지 시 자동 재가입·로그 병합을 차단한다. 양쪽 RK 세대와 DML 범위를 보존해 데이터 소유자가 정답 노드와 수동 병합을 결정하는 runbook을 제공한다.

### 검증 방법
네트워크 분할과 fencing 실패를 주입해 양쪽에 상충 DDL/DML을 만든다. 재연결 때 자동 덮어쓰기가 없고 진단 보고서가 세대·로그 범위·영향 테이블을 제공하는지 확인한다.

## [PM-5Y-33] 다중 standby와 연쇄 복제의 지원 범위가 없다

- 분류: 누락
- 심각도: Major
- 근거 위치: 원문 전체가 하나의 master와 하나의 slave만 서술
- 사실/추론 구분: 확인이 필요한 질문 — CUBRID 해당 버전이 다중 standby 또는 연쇄 topology를 지원하는지 확인 필요하다
- 영향 대상: 재해 복구 토폴로지 사용자, 원거리 replica, 승격 정책

### 문제
관련 토폴로지가 지원된다면 모든 replica가 동일한 활성 RK 세대와 DDL 순서를 가져야 한다. 지연이 서로 다른 replica 중 하나만 옛 세대일 때 승격 가능 여부와 세대 보관 기준이 없다.

### 왜 중요한가
가장 지연된 replica가 옛 RK 로그를 필요로 하는 동안 빠른 replica 기준으로 세대를 정리하면 복구가 불가능할 수 있다. 원거리 DR 노드가 승격될 때도 최신 세대인지 확인해야 한다.

### 재현 또는 구체적 예제

```text
A primary, B local standby lag 1초, C DR standby lag 2시간
A에서 RK id→email 전환 후 장애
```

B와 C의 승격 조건, C가 옛 로그를 계속 적용할 수 있는지 정의가 필요하다.

### 권고안
지원 topology를 명시하고 replica별 generation ack, 전체 보관 watermark, 승격 eligibility와 topology 변경 절차를 정의한다. 미지원 topology는 문서에서 명확히 제외한다.

### 검증 방법
지원 노드 수와 lag 조합에서 연속 RK 전환·노드 추가/제거·승격을 수행한다. 모든 노드가 같은 스키마·데이터로 수렴하고 옛 세대 조기 정리가 없는지 확인한다.

## [PM-5Y-34] 드라이버·ORM·스키마 diff가 새 메타데이터를 다루는 계약이 없다

- 분류: 호환성
- 심각도: Major
- 근거 위치: 원문 2-3절은 csql 조회 예시만 제공; JDBC/CCI 메타데이터, ORM, migration diff 노출은 없음
- 사실/추론 구분: 확인이 필요한 질문 — 각 드라이버와 도구의 메타데이터 API 확장 가능 여부는 확인 필요하다
- 영향 대상: 애플리케이션 팀, 도구 공급자, 배포 자동화, 제품 채택

### 문제
도구가 REPLICATION을 모르면 `SHOW CREATE TABLE`을 읽고 다시 만들 때 옵션을 삭제하거나 모든 테이블을 기본 ON으로 만들 수 있다. schema diff가 엔진 자동 선택 RK를 매번 다른 변경으로 감지할 가능성도 있다.

### 왜 중요한가
실제 고객은 SQL을 직접 작성하기보다 ORM과 migration 도구를 사용한다. 기능이 csql에서만 보여도 자동 배포 경로가 보존하지 못하면 운영에서 설정 drift가 생긴다.

### 재현 또는 구체적 예제

```text
1. 도구가 OFF 테이블 스키마를 introspect
2. 테스트 DB에 동일 스키마를 생성
3. 도구가 REPLICATION 속성을 모르면 옵션 생략
4. 기본 ON으로 생성
```

두 환경의 데이터 보호 정책이 달라진다.

### 권고안
지원 드라이버/API별 ON/OFF, 활성 RK, 후보 메타데이터 노출과 버전 계획을 정의한다. 주요 schema diff·migration 도구에 round-trip 시험과 미지원 시 경고·문서 우회법을 제공한다.

### 검증 방법
지원 JDBC/CCI 및 대표 migration 경로로 ON/OFF 테이블을 introspect→생성→diff한다. 옵션과 활성 RK 의미가 보존되고 구버전 도구가 조용히 기본값으로 바꾸지 않는지 확인한다.

## [PM-5Y-35] 기능 활성화와 되돌릴 수 없는 카탈로그 변경의 정책이 없다

- 분류: 호환성
- 심각도: Critical
- 근거 위치: 원문 2절의 새 카탈로그 속성 및 8절의 새 unload 정보; 기능 flag·비활성화·downgrade 변환은 없음
- 사실/추론 구분: 확인이 필요한 질문 — 기능이 항상 활성인지, 에디션/라이선스 차이와 카탈로그 downgrade 가능 여부는 확인 필요하다
- 영향 대상: 릴리스 관리자, 기존 사용자, 긴급 롤백, 제품 지원

### 문제
업그레이드 직후 새 필드가 저장되면 구버전 서버로 되돌릴 수 있는지, 기능을 사용하지 않은 DB와 사용한 DB의 롤백 범위가 같은지 없다. 혼합 버전 지원과 별개로 “새 기능을 실제로 활성화한 시점”을 관리할 gate가 필요하다.

### 왜 중요한가
배포 장애 때 가장 빠른 대응은 바이너리 롤백일 수 있다. 새 카탈로그나 로그가 비가역이면 롤백이 데이터베이스를 열지 못하게 할 수 있으므로 활성화 전에 사용자가 알아야 한다.

### 재현 또는 구체적 예제

```text
1. 신버전 설치, 아직 새 DDL 미사용
2. REPLICATION=OFF 테이블 생성 및 RK 전환
3. 애플리케이션 문제로 구버전 바이너리 롤백 요청
```

1과 2 이후의 롤백 가능 조건이 다를 수 있지만 문서에 없다.

### 권고안
기능 capability/version marker, 최초 사용 시점, 비가역 변경 목록, enable/disable 및 downgrade 검사 명령을 정의한다. 에디션·라이선스 차이가 있다면 dump/복원 결과도 명시하고 롤백 불가 시 사전 확인을 요구한다.

### 검증 방법
설치만 한 상태, ON/OFF 생성 후, 여러 RK 전환 후 각각 downgrade dry-run과 실제 롤백을 시험한다. 지원 경계에서는 설정·데이터가 보존되고 비지원 경계에서는 변경 전에 정확히 차단되는지 확인한다.

## [PM-5Y-36] 임시·시스템·세션 범위 객체의 적용 대상이 정의되지 않았다

- 분류: 누락
- 심각도: Major
- 근거 위치: 원문 2절은 “테이블” 전체로 표현하고 2-3절 `db_class`에는 system class 속성이 있으나 객체 종류별 범위는 없음
- 사실/추론 구분: 확인이 필요한 질문 — CUBRID 해당 버전의 temporary/global temporary/system table 지원과 사용자 변경 가능 범위는 확인 필요하다
- 영향 대상: 애플리케이션, 관리 도구, HA readiness, 제품 문서

### 문제
세션 임시 테이블에 REPLICATION 옵션이 허용되는지, 시스템 테이블이 기본 ON 검사에 포함되는지, 세션 종료로 사라지는 객체가 HA 시작을 차단하는지 없다.

### 왜 중요한가
비영구 객체는 일반 업무 테이블과 생명주기가 다르다. 이를 같은 기본 ON 규칙으로 처리하면 불필요한 오류가 생기고, 반대로 영구 관리 테이블을 제외하면 장애 조치 후 도구 상태가 사라질 수 있다.

### 재현 또는 구체적 예제

```sql
-- 실제 임시 테이블 문법은 버전 확인 필요
CREATE TEMPORARY TABLE session_buffer (v INT) REPLICATION=ON;
```

RK 없음 오류가 생성 시 발생하는지, readiness 검사 대상인지, 옵션 자체가 금지되는지 정해야 한다.

### 권고안
일반·파티션·임시·시스템·가상 객체 등 지원 객체 목록과 기본값, 문법 허용 여부, HA 검사·복제 범위를 표로 제공한다. 미지원 객체는 parser/semantic 단계에서 구체 오류를 낸다.

### 검증 방법
지원되는 각 객체 종류에 생략/ON/OFF와 RK 유무를 조합한다. 생성, 세션 종료, HA 시작, failover 후 생명주기가 범위표와 같은지 확인한다.

## [PM-5Y-37] OFF 테이블을 다시 ON으로 편입하는 데이터 초기화 절차가 없다

- 분류: 정확성
- 심각도: Blocker
- 근거 위치: 원문 2-2절은 HA에서 OFF→ON을 금지하지만 single에서는 변경 가능하다고 읽히며 3절은 모든 SQL 허용
- 사실/추론 구분: 확인이 필요한 질문 — single에서 OFF→ON 변경 시 기존 source 데이터가 replica에 어떻게 초기 적재되는지 없다
- 영향 대상: 사용자, DBA, 복제 정합성, 기능 되돌리기

### 문제
OFF 기간 동안 두 노드 데이터가 달라진 뒤 옵션만 ON으로 바꾸면 이후 DML만 복제되고 과거 행 차이는 남을 수 있다. HA를 멈추고 single에서 변경하라는 것만으로 standby 초기화가 이루어지는지 알 수 없다.

### 왜 중요한가
사용자는 ON으로 돌아오면 다시 보호된다고 생각한다. 기준 snapshot 없이 설정만 바꾸면 새 변경은 적용돼도 기존 행이 없어서 UPDATE/DELETE가 실패하고 `fail_count`가 증가할 수 있다.

### 재현 또는 구체적 예제

```sql
-- OFF 기간 source에만 100행 존재
ALTER TABLE local_customer REPLICATION=ON;
-- HA 재시작 뒤
UPDATE local_customer SET status='A' WHERE id=50;
```

replica에 id=50이 없으면 적용 실패한다. 기대 결과는 ON 활성화 전에 전체 기준 데이터를 동기화하고 검증하는 것이다.

### 권고안
OFF→ON을 설정 변경이 아니라 bootstrap 절차로 정의한다. 유효 RK 검사, 일관된 snapshot 복사, DML catch-up, 체크섬, activation barrier와 실패 롤백을 제공한다. 완료 전에는 HA 승격 대상에서 제외한다.

### 검증 방법
OFF 상태에서 양 노드에 서로 다른 행을 만든 뒤 공식 편입 절차 중 동시 DML·중단·재시작을 주입한다. 활성화 후 전체 체크섬이 같고 모든 후속 DML이 오류 없이 적용되는지 확인한다.

## [PM-5Y-38] ON에서 OFF로 전환할 때 복제 backlog의 경계가 없다

- 분류: 정확성
- 심각도: Critical
- 근거 위치: 원문 2-2절과 4절은 HA에서 ON→OFF를 허용하지만 전환 전 미적용 DML 처리 규칙은 없음
- 사실/추론 구분: 확인이 필요한 질문 — 전환 커밋 이전 ON 로그를 모두 적용한 뒤 OFF가 되는지, backlog가 폐기되는지 없다
- 영향 대상: 사용자, 복제 정합성, 장애 조치, 감사

### 문제
replica가 지연된 상태에서 ON→OFF DDL이 적용되면 그 전에 커밋된 ON DML을 끝까지 적용해야 하는지 알 수 없다. 전환 시점이 모호하면 양 노드의 “의도된 불일치 시작점”을 특정할 수 없다.

### 왜 중요한가
OFF 이후 차이는 정책상 허용하더라도 OFF 이전 커밋까지 누락되면 기존 복제 보장을 소급해서 깨뜨린다. 장애 분석과 재편입을 위해 정확한 cutover 로그 위치가 필요하다.

### 재현 또는 구체적 예제

```text
LSA 100: ON 상태 UPDATE
LSA 101: ALTER TABLE t REPLICATION=OFF
LSA 102: OFF 상태 UPDATE
```

replica는 100을 적용하고 101을 적용한 뒤 102만 제외해야 한다는 경계를 명시해야 한다.

### 권고안
ON→OFF 커밋을 cutover barrier로 정의하고 이전 모든 DML 적용, 이후 DML 제외, 로그 위치와 감사 이벤트 기록을 보장한다. backlog가 너무 크면 ALTER 대기·비동기 완료·거부 중 정책과 사용자 상태 조회를 제공한다.

### 검증 방법
큰 backlog에서 전환하고 100/101/102 경계를 중심으로 crash·재시작·failover를 주입한다. OFF 이전 데이터는 양 노드가 같고 이후 데이터만 의도대로 다르며 cutover 위치를 조회할 수 있는지 확인한다.
