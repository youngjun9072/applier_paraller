# CUBRID HA 복제 키 스펙 미결 질문

> **후속 필터링 주의:** 아래 질문은 삭제하지 않은 원래 목록이다. 기능 코드가 이미 답한 전제와 CUBRID 비적용 항목은 [CUBRID_FIT_FILTER_FEATURE.md](CUBRID_FIT_FILTER_FEATURE.md)에 기각·폐기로 표시했으므로, 새 기능 스펙 결정 목록을 만들 때 최신 판정을 우선 적용한다.

이 문서는 `user_spec.html`과 20개 역할·경력 관점에서 작성한 확장 원시 리뷰 691건을 바탕으로, 구현 전에 결정권자가 답해야 할 질문을 모은 것이다. 질문에 답이 없다는 것은 단순한 문서 누락이 아니라 서로 다른 구현이 모두 가능하다는 뜻이다. `Blocker`는 답이 정해지기 전 구현·출시 기준을 확정하면 안 되는 항목이다.

## 읽는 법과 사실 범위

- **원문에서 확인된 사실**: 현재 사용자 스펙에 실제로 적힌 문장만 뜻한다. 실제 CUBRID 구현이 이미 그대로 동작한다는 확인은 아니다.
- **미결 질문**: 원문과 제공된 근거만으로 답할 수 없어 제품·엔진 책임자의 결정 또는 코드 검증이 필요한 사항이다.
- **권고 기본안**: 데이터 정합성을 우선한 제안이며 현재 구현 사실이나 승인된 제품 정책이 아니다.
- `PREPARING`, `epoch`, `barrier` 같은 내부 이름은 개념을 설명하기 위한 제안 명칭이다. 최종 명칭과 구현 방식은 결정권자가 확정해야 한다.

## 1. 행 식별과 RK 수명주기

### Q-01. 복제 로그는 어떤 RK 세대를 사용해 행을 찾는가? — Blocker

- 결정권자: 복제 엔진 설계 책임자
- 질문: DML이 기록될 때의 RK와 적용될 때의 RK가 다르면 로그에 이전 RK 값, 새 RK 값, RK 세대 번호 중 무엇이 저장되는가?
- 예: `id` PK로 기록된 UPDATE 뒤에 PK가 `email`로 바뀌고 standby가 지연 적용한다.
- 권고 기본안: 로그에 영속적인 테이블 ID, RK 논리 ID와 schema/RK epoch를 포함한다. UPDATE/DELETE의 대상 검색에는 생성 당시 old key를 보존하고, RK 값 자체가 바뀌는 UPDATE에는 필요한 new key도 보존한다. 해당 세대는 모든 대상 replica가 소비할 때까지 해석 가능해야 한다.
- 연결 항목: `PM-10Y-01`, `DBDEV-1Y-09`, `엔진개발자-10년차-01`

### Q-02. 여러 NOT NULL UK 중 활성 RK는 어떻게 결정·영속화되는가? — Blocker

- 결정권자: 엔진 아키텍트, SQL 스펙 책임자
- 질문: 제약 생성 순서, 이름, 카탈로그 ID 중 무엇으로 고르며 restart·dump/load·failover 뒤에도 같은 키인가?
- 예: `UNIQUE(email)`과 `UNIQUE(phone)`의 출력 순서가 load 과정에서 바뀐다.
- 권고 기본안: 자동 정렬 결과를 매번 재계산하지 말고 선택된 제약의 안정적인 논리 ID를 카탈로그에 저장한다.
- 연결 항목: `DBA-1년차-06`, `PM-10Y-12`, `DBDEV-1Y-02`

### Q-03. PK가 새로 생기면 UK인 기존 RK를 즉시 교체하는가? — Critical

- 결정권자: SQL 스펙 책임자
- 질문: “PK 우선”은 최초 선택 규칙인지 지속적인 재선택 규칙인지?
- 예: email UK가 RK인 테이블에 `id PRIMARY KEY`를 추가한다.
- 권고 기본안: 명시적인 RK 전환 DDL 없이는 활성 RK를 자동 변경하지 않고 PK는 후보로만 추가한다.
- 원문과의 차이: 원문의 “PK가 존재한다면 PK가 복제 키”는 지속적인 재선택으로도 읽힐 수 있다. 이 권고를 채택하려면 해당 문장을 “최초 선택 규칙”으로 고치거나, 반대로 지속 우선순위를 채택할 경우 자동 전환의 barrier·로그 세대 규칙을 명시해야 한다.
- 연결 항목: `PM-10Y-04`, `DBA-5Y-07`

### Q-04. 어떤 컬럼·타입·collation을 RK로 허용하는가? — Blocker

- 결정권자: 타입 시스템·복제 엔진 책임자
- 질문: 문자열 collation, 시간대, 부동소수, 큰 객체, 생성/표현식 컬럼, 복합 키 크기 제한은 무엇인가?
- 예: 서로 다른 버전의 노드가 대소문자 비구분 문자열을 다르게 비교한다.
- 권고 기본안: canonical encoding과 비교 의미가 버전 간 고정되는 타입만 허용하고 최대 직렬화 크기를 문서화한다.
- 연결 항목: `USER-3Y-27`, `DBDEV-5Y-38`, `엔진개발자-10년차-26`

## 2. SQL과 상태 전이

### Q-05. 복합 ALTER는 전체가 원자적인가? — Blocker

- 결정권자: DDL/트랜잭션 엔진 책임자
- 질문: `DROP old key, ADD new key`의 후반부가 실패하거나 서버가 종료되면 기존 RK가 보존되는가?
- 예: 새 UK 대상 컬럼에 중복값이 있어 ADD가 실패한다.
- 권고 기본안: 전체 사전 검증 후 하나의 카탈로그 커밋으로 공개하며 실패 시 이전 schema/RK epoch로 완전 복귀한다.
- 연결 항목: `PM-10Y-07`, `DBA-3Y-07`, `DBDEV-1Y-07`

### Q-06. RK 관련 DDL과 동시 DML의 잠금·순서 계약은 무엇인가? — Blocker

- 결정권자: 트랜잭션·복제 엔진 책임자
- 질문: 장기 DML이 열린 상태에서 RK 변경 DDL은 대기, 실패, 또는 이전 세대 로그 생성을 허용하는가?
- 예: 트랜잭션 A가 UPDATE를 시작하고 B가 RK를 교체한 뒤 A가 커밋한다.
- 권고 기본안: 명시적 schema barrier와 epoch를 사용하고 사용자에게 대기/timeout/재시도 계약을 공개한다.
- 연결 항목: `PM-10Y-09`, `DBA-5Y-09`, `엔진개발자-3년차-09`

### Q-07. ON→OFF 전환 시 standby의 기존 데이터는 어떻게 되는가? — Blocker

- 결정권자: 제품·복제 책임자
- 질문: 기존 행을 보존, 삭제, 격리 중 무엇을 하며 이후 수정은 어느 노드가 권위 데이터인가?
- 예: 양 노드에 100행이 있을 때 OFF 전환 후 primary에 50행을 추가한다.
- 권고 기본안: 기존 데이터는 자동 삭제하지 않되 `stale/local` 상태로 명시하고 승격 위험을 표시한다.
- 연결 항목: `PM-10Y-08`, `DBA-10년차-06`

### Q-08. OFF→ON은 어떤 초기 동기화를 요구하는가? — Blocker

- 결정권자: 복제·운영 도구 책임자
- 질문: single 모드에서 플래그만 바꾸는가, snapshot/reseed 후 로그를 이어 붙이는가?
- 예: OFF 기간 동안 primary와 standby 데이터가 서로 다르다.
- 권고 기본안: 단순 플래그 변경을 금지하고 full copy + delta catch-up + checksum + atomic cutover 상태 기계를 제공한다.
- 연결 항목: `PM-5Y-37`, `DBA-10년차-07`

### Q-09. ON/OFF 테이블을 함께 변경한 트랜잭션의 원자성은 무엇인가? — Blocker

- 결정권자: 트랜잭션·제품 책임자
- 질문: primary에서는 하나의 원자적 업무였지만 standby에는 ON 테이블 변경만 남는 것을 허용하는가?
- 예: 주문 ON 삽입과 로컬 재고 OFF 감소가 한 트랜잭션에서 커밋된다.
- 권고 기본안: 교차 정책 트랜잭션을 탐지·경고하거나 금지하고, 허용한다면 failover 후 원자성이 축소됨을 API와 감사 로그에 표시한다.
- 연결 항목: `USER-1Y-23`, `DBDEV-5Y-25`

### Q-10. TRUNCATE·bulk load·CTAS·LIKE·INSERT SELECT의 정책은 무엇인가? — Critical

- 결정권자: SQL·복제 책임자
- 질문: 일반 DML/DDL과 다른 빠른 경로가 REPLICATION을 우회하지 않는가?
- 권고 기본안: 명령별 로그 종류, ON/OFF 결과, 원자성, 재시도 규칙을 표로 정의한다.
- 연결 항목: `DBA-3Y-25`, `DBDEV-5Y-24`, `엔진개발자-10년차-22`

## 3. HA, 장애와 복구

### Q-11. RK 전환 중 어느 durable state부터 standby 승격이 가능한가? — Blocker

- 결정권자: HA·복제 책임자
- 질문: PREPARE, BUILDING, SWITCHED, RETIRED 같은 상태 중 승격 가능한 상태는 무엇인가?
- 예: 새 인덱스는 생성됐지만 RK 전환 로그가 모든 standby에 적용되기 전에 primary가 죽는다.
- 권고 기본안: 각 상태의 복구·rollback·승격 가능 여부를 정의하고 불완전 세대의 승격을 차단한다.
- 연결 항목: `DBA-5Y-10`, `USER-10Y-10`, `DBDEV-5Y-11`, `엔진개발자-10년차-11`

### Q-12. split-brain에서 복제 정책 DDL을 어떻게 fencing하는가? — Blocker

- 결정권자: HA 아키텍트
- 질문: 두 primary가 서로 다른 RK 또는 ON/OFF를 커밋한 경우 자동 병합이 가능한가?
- 권고 기본안: quorum/fencing epoch가 없는 노드의 RK·REPLICATION DDL을 거부하고, 분기 후에는 자동 재가입 대신 재구축을 기본으로 한다.
- 연결 항목: `DBA-5Y-30`, `엔진개발자-10년차-10`

### Q-13. 다중 standby와 cascade topology에서 safe point는 어떻게 계산하는가? — Critical

- 결정권자: 복제 아키텍트
- 질문: 느리거나 분리된 replica 때문에 구 RK 세대를 언제까지 보존하는가?
- 권고 기본안: membership epoch와 replica별 적용 위치로 전역 safe point를 계산하고 제거된 replica의 재가입에는 reseed를 요구한다.
- 연결 항목: `DBA-5Y-32`, `엔진개발자-10년차-25`

### Q-14. 기존 불일치를 어떻게 탐지하고 안전하게 수리하는가? — Blocker

- 결정권자: 운영 도구·복제 책임자
- 질문: 새 RK 기능은 과거 누락을 자동 복구하지 않는다. 비교 단위, 권위 노드, 온라인 repair와 동시 쓰기 규칙은 무엇인가?
- 권고 기본안: snapshot 기준 checksum→차이 목록→쓰기 fencing 또는 version check→멱등 repair→재검증 절차를 제공한다.
- 연결 항목: `DBA-1년차-16`, `USER-10Y-16`, `엔진개발자-10년차-16`

### Q-15. `fail_count`의 정확한 상태 모델은 무엇인가? — Critical

- 결정권자: 복제·관측성 책임자
- 질문: 증가·감소·초기화 조건, 범위, 마지막 실패, 영향 행, retry/quarantine와 관계는 무엇인가?
- 권고 기본안: 단일 누적값 외에 오류 코드별 카운터, 첫/마지막 시각, table/RK epoch, lag, quarantine 상태를 제공한다.
- 연결 항목: `PM-10Y-15`, `DBA-3Y-15`, `엔진개발자-10년차-15`

### Q-16. 디스크 full·OOM·로그 손상에서 부분 성공을 어떻게 처리하는가? — Blocker

- 결정권자: 스토리지·복구 책임자
- 질문: DDL, 카탈로그, WAL, 감사 기록 중 일부만 durable할 수 있는가?
- 권고 기본안: 필요한 WAL/인덱스 공간을 admission 단계에서 예약하고 모든 durable 구성요소가 하나의 복구 가능한 상태로 커밋되게 한다.
- 연결 항목: `DBA-1년차-27`, `DBDEV-1Y-27`, `엔진개발자-10년차-30`

## 4. 의존 객체와 데이터 의미

### Q-17. FK의 ON/OFF 허용 행렬과 cascade 규칙은 무엇인가? — Blocker

- 결정권자: SQL·복제 책임자
- 질문: 부모/자식 네 조합, 전환, 자기 참조, 다단계 그래프, CASCADE/SET NULL을 모두 어떻게 처리하는가?
- 권고 기본안: 직접 FK만 보지 말고 전체 의존 그래프를 검사하며 standby apply가 같은 내부 DML을 중복 생성하지 않게 provenance를 기록한다.
- 연결 항목: `PM-10Y-14`, `DBDEV-5Y-13`, `DBDEV-5Y-26`

### Q-18. OFF 의존 VIEW·trigger·procedure를 허용할 것인가? — Critical

- 결정권자: 제품·SQL 책임자
- 질문: failover 후 성공하지만 의미가 다른 결과를 오류로 볼지, 경고로 볼지?
- 권고 기본안: 의존성 목록을 제공하고 중요 객체에는 승격 차단/준비 상태 실패 옵션을 제공한다.
- 연결 항목: `PM-10Y-03`, `사용자-5년차-24`, `DBDEV-5Y-14`, `엔진개발자-10년차-14`

### Q-19. 파티션의 REPLICATION과 RK 소유 단위는 무엇인가? — Critical

- 결정권자: 파티션·복제 책임자
- 질문: 부모에서 상속하는지, 파티션별 설정 가능한지, RK 유일성은 전체 테이블인지 파티션별인지?
- 권고 기본안: 논리 테이블 단위 정책과 전역 행 식별을 기본으로 하고 attach/detach/split/merge 전이를 정의한다.
- 연결 항목: `DBA-10년차-23`, `DBDEV-5Y-22`

### Q-20. 임시·시스템·복사·rename 객체의 정책과 정체성은 무엇인가? — Major

- 결정권자: SQL·도구 책임자
- 질문: CTAS, LIKE, clone은 새 테이블에 어떤 ON/OFF·제약을 복사하는가? rename은 기존 객체 ID와 과거 RK 로그 연결을 보존하는가? temporary/system table은 일반 테이블 규칙의 대상인가?
- 권고 기본안: 새 객체를 만드는 CTAS/LIKE/clone은 새 논리 ID를 발급하고 속성별 복사 여부를 명시한다. rename은 지원되는 경우 기존 논리 ID를 보존한다. temporary/system 객체는 별도 적용 범위표와 정규 metadata API로 구분한다.
- 연결 항목: `USER-10Y-32`, `PM-5Y-24`, `DBA-10년차-25`, `DBA-10년차-31`, `DBDEV-5Y-24`

## 5. 호환성, 백업과 공개 정책

### Q-21. replication 필드가 없는 구버전 dump는 ON인가 OFF인가? — Blocker

- 결정권자: 제품·백업 도구 책임자
- 질문: 8절은 ON, 9절은 OFF라고 하므로 하나를 선택해야 한다.

## 6. 권한, 관측과 사용자 계약

### Q-25. 누가 REPLICATION과 RK 관련 DDL을 변경할 수 있는가? — Critical

- 권고 기본안: 별도 권한, 최소 권한 조회 역할, 선택적 two-person approval/maintenance lock, 원자적 감사 기록을 제공한다.

### Q-26. 현재 활성 RK와 실제 복제 건강 상태를 어떤 API로 조회하는가? — Critical

- 질문: `SHOW CREATE TABLE`의 ON/OFF만으로 충분한가?
- 권고 기본안: 후보, 활성 RK 논리 ID/컬럼, epoch, 전환 상태, replica별 적용 위치, lag, 마지막 성공·오류를 구조화된 카탈로그/API로 제공한다.
