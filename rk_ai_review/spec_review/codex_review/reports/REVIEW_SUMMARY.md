- 대상 문서: `../user_spec/user_spec.html` 1~9절
- 리뷰 관점: 5개 역할 × 4개 경력 = 20개

- 전체 판단: **현재 스펙만으로 구현·출시하면 데이터 정합성과 복구 가능성을 일관되게 보장하기 어렵다. Blocker 규칙을 먼저 확정해야 한다.**

## 1. 결과 개요

691건 중 Blocker와 Critical이 461건으로 66.7%다. 여러 관점이 같은 근본 공백을 독립적으로 발견했기 때문에 이 숫자를 서로 다른 결함 461개로 해석해서는 안 된다. 그러나 핵심 위험이 문구 개선 수준이 아니라 복제 로그, 카탈로그, DDL/DML 순서, failover, 복구 계약에 집중돼 있다는 신호는 분명하다.

가장 중요한 결론은 다음과 같다.

1. **RK가 “존재한다”는 조건만으로 문제는 해결되지 않는다.** 로그를 생성할 때 사용한 RK 정의와 replica가 적용할 때 사용하는 정의를 연결하는 세대 또는 논리 ID, 순서 장벽, 구 정의 보관 규칙이 필요하다.
2. **여러 UK 중 실제 RK 선택이 결정적이고 지속적이어야 한다.** source와 replica, 재시작, 백업·복원, 업그레이드 후에도 같은 키를 선택해야 하며 사용자가 이를 조회할 수 있어야 한다.
3. **`REPLICATION=OFF`는 단순 성능 옵션이 아니다.** failover 시 데이터가 사라지거나 과거 값으로 보일 수 있는 데이터 생명주기 정책이며, OFF→ON 재동기화와 ON→OFF 경계가 정의돼야 한다.
4. **DDL과 DML의 전역 순서 및 failover 차단 조건이 없다.** 복합 ALTER, 장기 트랜잭션, replica 지연, 병렬 apply, 중간 크래시에서 어느 키로 행을 찾는지 결정할 수 없다.
5. **새 기능은 기존 불일치를 자동 복구하지 않는다.** `fail_count` 증가 억제와 이미 누락된 행의 탐지·수리는 별도 문제다.
6. **혼합 버전, backup/PITR, unload/load 계약이 출시 조건으로 정의되지 않았다.** 새 로그·카탈로그를 구버전이 해석하지 못하면 롤링 업그레이드와 되돌리기가 안전하지 않다.

## 4. 핵심 Blocker와 Critical

### 4.1 RK 세대와 행 식별 불변식

`APPDEV-10Y-01`, `DBA-10년차-01`, 다수 엔진 개발자 항목은 “활성 RK가 항상 하나 있다”만으로는 충분하지 않다고 지적한다. 예를 들어 `id` RK로 기록된 UPDATE가 지연된 동안 RK가 `email`로 바뀌면 replica는 옛 로그를 새 키 정의로 해석해서는 안 된다.

출시 전에 로그 레코드가 참조하는 RK 세대 또는 논리 ID, old/new key 저장 규칙, 구 세대 보관 종료 조건을 정해야 한다.

### 4.2 결정적 RK 선택과 관측 가능성

`PM-5Y-02`와 `DBA-5Y-04`는 여러 `NOT NULL UNIQUE` 후보 중 엔진 선택이 결정적이지 않고 실제 선택 결과도 조회할 수 없다는 Blocker를 제기한다. 제약 생성 순서, 내부 ID, 이름, 백업 출력 순서가 달라져도 동일한 RK를 유지할 정책과 카탈로그/API가 필요하다.

### 4.3 ON/OFF 전환의 데이터 의미

`PM-10Y-08`은 ON→OFF 뒤 미적용 backlog의 처리와 OFF→ON 때의 초기 동기화가 정의되지 않았다는 Blocker다. `사용자-5년차-03`은 OFF가 failover 데이터 손실 선택이라는 Critical 사용자 위험을 강조한다. 단순 플래그 변경으로 구현해서는 안 되며, 전환 시점·쓰기 차단·재동기화·취소·복구 상태를 정의해야 한다.

### 4.4 복합 ALTER, DDL/DML 동시성, failover

`DBA-5Y-08`과 `DBA-5Y-09`는 마지막 RK 삭제와 새 RK 추가를 한 ALTER에서 수행할 때의 원자성, 장기 DML과의 직렬화가 없다는 Blocker다. DDL 적용 중 source 장애가 나면 schema와 log 해석이 함께 안전한 replica만 승격돼야 한다. 허용·거부·대기·재시도 중 어느 행동인지 오류 계약까지 필요하다.

### 4.5 split-brain과 승격 fencing

`DBA-5Y-30`과 `USER-10Y-28`은 네트워크 분할 중 양쪽에서 서로 다른 RK/ON-OFF DDL이 수행되면 자동 병합할 수 없다고 지적한다. 단일 writer 보장, DDL fencing token, 승격 전 RK 세대·replica LSA 검증, 이전 primary 재가입 시 재구축 규칙이 출시 전 요구사항이다.

### 4.6 기존 불일치와 `fail_count` 복구 모델

`PM-1Y-16`은 새 RK 정책이 기존 누락 행을 찾아주지 않는다는 Critical 항목이다. `DBA-10년차-15`와 `DBA-10년차-16`은 `fail_count`를 누적 숫자로만 제공하지 말고 최초 실패 LSA, 객체, 오류 종류, 재시도 상태, 수리 결과와 연결해야 한다고 본다. 읽기 전용 비교, 권위 노드 결정, 쓰기 차단 아래 수리, 검증과 감사 증적까지 필요하다.

### 4.7 롤링 업그레이드와 복구 가능성

`DBA-10년차-17`, `APPDEV-10Y-18`, `PM-5Y-30`, `DBA-10년차-18`은 혼합 버전 기능 협상, rollback 경계, backup/PITR의 RK 세대 보존을 Blocker 또는 Critical로 평가한다. 구버전 replica가 새 DDL·로그를 무시하거나 오해하는 것보다 기능 활성화를 차단하는 편이 안전하다.

## 5. 역할별 시각 차이

| 관점 | 주된 질문 | 대표적인 고유 기여 |
|---|---|---|
| PM | 무엇을 지원하며 실패 책임과 출시 기준은 무엇인가 | 기본 ON의 업그레이드 영향, OFF의 제품 책임, 지원 매트릭스, 오류·문서·기능 공개 기준 |
| DB 엔지니어/DBA | 장애를 어떻게 예방·관측·복구하는가 | HA 사전 검사, failover/failback runbook, 실제 RK 조회, lag·fail_count 경보, 비교·수리·감사 절차 |
| 최종 사용자 | SQL 실행 결과와 장애 후 데이터가 예측 가능한가 | ON/OFF 위험 표현, 모드별 오류, 안전한 수정 절차, GUI·국제화 메시지, 개인정보 노출 |
| 애플리케이션 개발자 | 배포·ORM·재시도·연결 전환 계약이 안정적인가 | schema diff 왕복, 동시 배포, prepared statement/cache, CDC event key, retry/idempotency, client routing |
| DBMS 엔진 개발자 | 모든 실행·복구 경로에서 불변식이 유지되는가 | 카탈로그·로그 버전, RK epoch, schema barrier, cache invalidation, crash recovery, 혼합 binary와 장기 유지보수 |

경력 차이도 단순한 지식 수준이 아니라 관찰 범위로 나타났다.

- 1년차는 용어, 기본값, 실행 가능한 예제, 오류 뒤 다음 행동을 주로 지적했다.
- 3년차는 일상적인 migration, 권한, 자동화 도구, 장애 진단과 운영 절차를 확장했다.
- 5년차는 온라인 DDL, 병렬성, 관측성, 성능, 여러 기능의 상호작용을 집중 검토했다.
- 10년차는 장기 불변식, 최악 크래시, PITR, split-brain, 혼합 버전과 되돌릴 수 없는 상태를 중점적으로 다뤘다.

## 6. 추가 심층 조사에서 새로 확장된 범주

초기 400건이 핵심 컨셉과 원문 1~9절을 폭넓게 다뤘다면, 추가 291건은 다음과 같은 구현·운영 경계로 범위를 넓혔다.

- **권한·감사·보안:** 누가 복제 보호 등급을 바꾸는지, 승인 분리, 변경 이력, RK 값이 오류·telemetry에 노출될 때의 개인정보 보호
- **파티션·복사 객체:** 부모/파티션 정책 상속, 전역 유일성, `CREATE LIKE`·CTAS·clone·rename의 ON/OFF와 RK 보존
- **내부·대량 DML:** trigger, cascade, procedure, `TRUNCATE`, bulk load, `INSERT SELECT`가 어느 복제 경로와 원자성에 속하는지
- **온라인 DDL과 병렬 apply:** 대형 UK 구축 진행률·취소·재개, worker drain, schema barrier, 장기 트랜잭션과 구 RK 수명
- **복구와 보관:** backup/PITR 시점, RK 세대와 LSA 결합, 로그 보관 한계, standby 재구축, 다중 standby·원격 DR
- **최악 장애:** 디스크 full, 메모리 부족, 네트워크 분할, 재시작 반복, split-brain과 이전 primary 재가입
- **타입과 비교 의미:** collation, 타입 변환, 복합·가변 길이 키, floating/LOB/JSON 등 후보 타입의 허용 목록과 버전 안정성
- **도구 생태계:** ORM·schema diff·driver metadata·GUI·CDC가 `REPLICATION`과 실제 RK를 보존하고 노출하는 계약
- **논리·물리 객체 분리:** 제약 rename, index rebuild, 통계 갱신, optimizer/cache와 RK 논리 ID의 결합 여부

추가 항목의 분류 분포는 정확성 66, 누락 55, 운영성 53, 호환성 53, 보안 33, 모호성 16, 성능 12, 컨셉 2, 문서 품질 1건이다. 추가 조사가 사소한 문구보다 복구·호환·운영 경계를 발굴했다는 것을 보여 준다.

## 7. 출시 전 우선순위

### P0 — 구현·공개 전에 결정

1. RK 선택·논리 ID·세대·로그 표현과 old/new key 불변식
2. PK↔UK 전환, 복합 ALTER, 컬럼 타입·NULL·collation 변경의 원자적 상태표
3. DDL/DML 직렬화, 병렬 apply schema barrier, 장기 트랜잭션 처리
4. ON/OFF 전환의 backlog·초기 동기화·재전환·failover 데이터 계약
5. 승격 조건, split-brain fencing, 다중 standby와 이전 primary 재가입
6. 혼합 버전 기능 협상, 롤링 upgrade/downgrade, 구버전 로그·카탈로그 처리
7. backup/PITR/unload/load에서 RK 세대와 적용 위치의 보존

### P1 — 출시 후보 승인 전에 제공

1. 활성 RK·후보·세대·변경 이력을 조회하는 카탈로그와 관리 API
2. HA 시작 사전 검사의 일관된 snapshot, 전 객체 오류 목록, 비용·진행률
3. 안정적인 오류 코드/SQLSTATE, 객체·원인·수정 SQL, 국제화 계약
4. `fail_count`, lag, 최초 실패 LSA와 반복 실패를 연결한 관측 모델
5. 기존 불일치 비교·권위 결정·수리·재검증 runbook과 자동화 도구
6. 최소 권한, ON→OFF 승인, 감사·민감 RK 마스킹 정책

### P2 — GA 지원성과 생태계 완성

1. 대형·복합 RK 성능 SLO와 온라인 구축 resource admission
2. ORM, driver, schema diff, GUI, CDC metadata 호환 시험
3. 파티션·trigger·bulk·clone 등 지원 객체 매트릭스
4. 모든 예제의 실행 모드, 초기 상태, 기대 결과, 오류 코드와 사후 상태 보완

P0가 해결되지 않은 상태에서는 `fail_count` 개선만을 성공 기준으로 삼아서는 안 된다. 최소 승인 기준은 동시 DDL/DML, 지연 replica, 중간 크래시, failover, PITR, 혼합 버전에서 데이터와 RK 세대가 일치한다는 자동 시험 결과여야 한다.
