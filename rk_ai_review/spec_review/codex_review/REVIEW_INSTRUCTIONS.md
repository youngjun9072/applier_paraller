# CUBRID HA 복제 키 사용자 스펙 리뷰 작업 지시서

## 1. 작업 목적

리뷰 대상은 `../user_spec/user_spec.html`이다. 이 문서는 CUBRID HA 환경에서 테이블별 복제 여부와 복제 키(Replication Key, RK)를 다루는 사용자 스펙이다.

기존 CUBRID HA 복제는 기본 키(Primary Key, PK)를 행 식별에 사용한다. HA가 실행 중인 상태에서 사용자가 PK 제약 또는 PK 컬럼의 속성을 변경하면, 복제 적용 과정에서 대상 행을 올바르게 찾지 못할 수 있다. 그 결과 다음 문제가 발생할 수 있다.

- 복제 변경 사항이 누락된다.
- 복제 오류가 반복되어 `fail_count`가 증가한다.
- 마스터와 슬레이브의 데이터가 서로 달라진다.
- 장애 조치(failover) 후 애플리케이션이 이전과 다른 데이터 또는 오류를 만날 수 있다.

PK가 없는 테이블의 모든 컬럼을 복제 키처럼 사용하는 MySQL 계열의 접근은 행을 식별할 수 있다는 장점이 있지만, 컬럼 수·데이터 크기·중복 값·`NULL` 처리 등에 따라 비교 비용이 커질 수 있다. 대상 스펙은 이 성능 문제를 피하기 위해 PostgreSQL의 개념 일부를 참고하여 PK 또는 `NOT NULL UNIQUE KEY` 중 하나를 RK로 선택하고, 테이블의 복제 여부를 `REPLICATION={ON|OFF}`로 구분하려는 변경안이다.

이 리뷰의 목적은 제안의 취지를 옹호하는 것이 아니다. 컨셉의 타당성부터 SQL 문법, 상태 전이, 오류 처리, 호환성, 운영 가능성, 설명의 정확성과 누락까지 객관적으로 검토하여 실제 구현 및 사용자 공개 전에 해결해야 할 문제를 찾는 것이다.

## 2. 핵심 용어와 초급 독자를 위한 배경

- **HA(High Availability)**: 한 DB 노드에 장애가 나도 다른 노드가 서비스를 이어받도록 여러 DB 노드를 운용하는 방식이다.
- **마스터와 슬레이브**: 마스터에서 데이터 변경을 수행하고 슬레이브가 그 변경을 받아 적용한다. 문서 원문의 용어를 인용할 때는 그대로 쓰되, 리뷰 본문에서는 가능하면 `primary/standby` 또는 `source/replica`도 함께 표기한다.
- **복제**: 마스터에서 발생한 `INSERT`, `UPDATE`, `DELETE` 같은 변경을 슬레이브에 전달하여 같은 상태로 만드는 과정이다.
- **PK**: 테이블의 각 행을 유일하게 식별하며 `NULL`을 허용하지 않는 키다.
- **UK(Unique Key)**: 값의 중복을 막는 제약이다. RK 후보가 되려면 대상 스펙에 따라 모든 구성 컬럼이 `NOT NULL`이어야 한다.
- **RK(Replication Key)**: 복제된 변경을 슬레이브의 어느 행에 적용할지 찾는 데 사용하는 키다.
- **DDL**: `CREATE TABLE`, `ALTER TABLE`, `DROP TABLE`처럼 스키마 구조를 변경하는 SQL이다.
- **DML**: `INSERT`, `UPDATE`, `DELETE`처럼 테이블 데이터를 변경하는 SQL이다.
- **failover**: 현재 마스터가 서비스를 수행할 수 없을 때 슬레이브가 새 마스터 역할을 맡는 전환이다.
- **`fail_count`**: 복제 적용 실패를 나타내는 카운터로 이해하되, 정확한 증가 조건·초기화 조건·노출 위치는 대상 문서나 구현 근거를 확인하여 리뷰한다.

예를 들어 다음 테이블에서 `id`가 RK라면 `id=10`인 행의 변경은 슬레이브에서도 `id=10`을 검색하여 적용할 수 있다.

```sql
CREATE TABLE customer (
  id INTEGER PRIMARY KEY,
  email VARCHAR(255) NOT NULL UNIQUE,
  name VARCHAR(100)
) REPLICATION = ON;
```

그러나 운영 중 `id`의 PK를 제거하는 DDL과 `id=10` 행을 수정하는 DML의 순서 또는 복제 로그가 참조하는 키 정의가 어긋나면, 슬레이브가 변경할 행을 찾지 못할 수 있다. 이 리뷰에서는 단순히 “PK 제거를 금지한다”는 결론만 확인하지 말고, PK에서 UK로 바꾸는 원자적 DDL, 복합 키, 동시 트랜잭션, 장애 조치 시점까지 검토한다.

## 3. 리뷰 조직

총 20개의 독립된 관점으로 리뷰한다. 역할 5개마다 경력 1년, 3년, 5년, 10년 관점을 각각 둔다.

| 역할 | 1년차 | 3년차 | 5년차 | 10년차 |
|---|---|---|---|---|
| PM | `pm_1y` | `pm_3y` | `pm_5y` | `pm_10y` |
| DB 엔지니어/DBA | `dba_1y` | `dba_3y` | `dba_5y` | `dba_10y` |
| 최종 사용자 | `user_1y` | `user_3y` | `user_5y` | `user_10y` |
| DB를 사용하는 애플리케이션 개발자 | `appdev_1y` | `appdev_3y` | `appdev_5y` | `appdev_10y` |
| DBMS를 개발하는 엔진 개발자 | `dbdev_1y` | `dbdev_3y` | `dbdev_5y` | `dbdev_10y` |

각 관점은 **서로 구별되는 리뷰 항목을 정확히 20개** 작성한다. 따라서 전체 원시 리뷰 항목은 400개다. 같은 문제를 다른 관점에서 다룰 수는 있지만, 문장만 바꾼 중복 항목은 허용하지 않는다. 중복이라면 해당 역할에 고유한 영향, 재현 예제 또는 해결 조건이 있어야 한다.

경력은 지식의 우열을 흉내 내기 위한 장식이 아니라 관찰 범위를 나누는 기준이다.

- **1년차**: 용어를 처음 접하는 사람이 이해할 수 있는지, 기본 사용 흐름과 예제가 실행 가능한지, 모호한 문장이 없는지 중점 검토한다.
- **3년차**: 일반적인 개발·운영 경험을 바탕으로 오류 처리, 마이그레이션, 도구 연동, 일상적인 경계 조건을 검토한다.
- **5년차**: 장애·성능·동시성·호환성·자동화·관측 가능성과 여러 기능 간 상호작용을 검토한다.
- **10년차**: 장기 호환성, 시스템 불변식, 복구 모델, 롤링 업그레이드, 최악의 실패 시나리오, 제품 정책과 유지보수 비용을 검토한다.

경력이 낮은 관점에서도 기술적 오류를 지적할 수 있고, 경력이 높은 관점에서도 문서의 기본적인 오탈자나 이해 가능성을 지적할 수 있다.

## 4. 역할별 중점 사항

### 4.1 PM

- 문제 정의와 변경안 사이의 인과관계가 충분히 설명되는가
- 지원 범위와 비지원 범위, 기본값, 기존 사용자 영향이 명확한가
- `REPLICATION=OFF`로 인한 데이터 불일치를 제품이 어디까지 허용하고 책임지는가
- 업그레이드, 다운그레이드, 기능 공개, 문서화, 오류 메시지 정책이 정의됐는가
- 수용 기준과 성공 지표가 검증 가능한가

### 4.2 DB 엔지니어/DBA

- HA 시작 전 점검, 운영 중 DDL, failover, failback 절차가 안전한가
- RK 선택 결과를 조회하고 감사하며 변경을 계획할 수 있는가
- 백업·복구, `unloaddb`/`loaddb`, 모니터링, 경보, `fail_count` 처리가 충분한가
- 대형 테이블, 복합 키, 온라인 스키마 변경, 잠금과 성능 영향이 설명됐는가
- 데이터 불일치를 탐지·교정하는 운영 절차가 있는가

### 4.3 최종 사용자

- SQL을 처음 사용하는 사용자도 ON/OFF와 RK의 의미를 오해하지 않는가
- 기본값과 실패 시 행동, 에러 메시지, 수정 절차가 이해 가능한가
- 문서 예제가 실제 목적과 결과를 명확히 보여 주는가
- 같은 동작이 single, SA, HA 모드에서 어떻게 다른지 예측 가능한가
- 실수하기 쉬운 설정에 안전장치나 경고가 있는가

### 4.4 DB를 사용하는 애플리케이션 개발자

- ORM과 마이그레이션 도구가 새 문법과 제약을 다룰 수 있는가
- 배포 중 DDL/DML 동시 실행과 트랜잭션 경계가 정의됐는가
- PK/UK 변경, 복합 키, `NULL`, 외래키, 뷰가 애플리케이션에 주는 영향이 명확한가
- failover 후 읽기·쓰기 결과와 오류 계약이 예측 가능한가
- 기존 애플리케이션의 무수정 호환성과 단계적 배포 방법이 있는가

### 4.5 DBMS를 개발하는 엔진 개발자

- RK 선택이 결정적이며 마스터와 슬레이브에서 동일한가
- 카탈로그, 복제 로그, DDL 적용 순서, 캐시 무효화의 불변식이 정의됐는가
- 동시 트랜잭션, 크래시 복구, 로그 재적용, 부분 실패가 안전한가
- PK↔UK 전환과 복합 `ALTER TABLE`이 원자적인가
- 프로토콜/로그/카탈로그 버전 호환성, 테스트 가능성, 성능 비용이 설명됐는가

## 5. 문서 전체에서 반드시 다룰 범위

각 에이전트의 20개 항목은 아래 할당을 모두 충족해야 한다. 숫자의 합은 20이다.

| 리뷰 영역 | 최소/고정 개수 | 예시 질문 |
|---|---:|---|
| 컨셉·문제 정의·대안 | 3 | RK 도입이 원인을 실제로 차단하는가? 모든 컬럼 비교 방식과의 장단점은 정확한가? |
| 용어·기본값·사용자 계약 | 2 | RK 후보와 실제 RK는 어떻게 구분되는가? 기본 ON이 안전한가? |
| SQL 문법과 상태 전이 | 3 | `CREATE/ALTER ... REPLICATION` 문법, 복합 ALTER, 원자성이 명확한가? |
| HA·DDL/DML·failover 시나리오 | 3 | 진행 중인 트랜잭션과 RK 변경의 순서는 어떻게 보장되는가? |
| 데이터 정합성·키·FK·VIEW | 3 | 복합 UK, FK 참조, OFF 테이블을 포함한 VIEW의 결과는 안전한가? |
| 운영·오류·관측 가능성 | 2 | `fail_count`, 오류 코드, 대상 테이블 목록, 복구 절차가 충분한가? |
| 호환성·백업/복원·성능·시험 | 2 | 구버전 unload 파일, 혼합 버전 HA, 회귀/부하 테스트가 정의됐는가? |
| 문서 품질·예제·오탈자 | 2 | 예제가 실행 가능하고 결과 및 이유가 설명됐는가? |

원문 섹션 1~9를 빠짐없이 읽는다. 특히 다음 항목은 어느 한 리뷰에서라도 반드시 구체적으로 검토한다.

- RK 선택 우선순위: PK 우선, 이후 `NOT NULL UK`, 여러 UK 중 엔진 선택
- 여러 UK가 있을 때 선택 기준의 결정성과 지속성
- 기본값 `REPLICATION=ON`
- single/SA/HA 모드 간 허용 동작 차이
- HA 실행 중 RK 후보를 추가·삭제·교체하는 모든 상태 전이
- 하나의 `ALTER TABLE`에서 기존 키 삭제와 새 키 추가를 함께 수행하는 경우
- DDL과 DML이 동시에 실행되거나 복제되는 경우
- 복합 PK/UK, 데이터 타입 변경, 컬럼 이름 변경, `NULL` 가능 여부 변경
- FK가 복제 제외 테이블을 참조하는 경우와 연쇄 동작
- 복제 제외 테이블을 포함하는 VIEW와 failover 후 결과
- HA 시작 전 검증의 원자성, 비용, 오류 출력
- `unloaddb`/`loaddb` 및 구버전 파일의 기본 처리
- 롤링 업그레이드와 서로 다른 버전의 노드
- `fail_count` 증가 방지뿐 아니라 기존 불일치 탐지와 복구
- 오탈자와 상충 문장(예: `CRATE TABLE`, 요약의 load 기본 처리)이 있는지

## 6. 각 리뷰 항목의 필수 형식

각 항목은 아래 형식을 그대로 사용한다. 제목 한 줄만 적거나 근거 없는 의견만 남기지 않는다.

```markdown
## [역할-경력-번호] 짧고 구체적인 제목

- 분류: 컨셉 | 정확성 | 누락 | 모호성 | 호환성 | 운영성 | 성능 | 보안 | 문서 품질
- 심각도: Blocker | Critical | Major | Minor | Suggestion
- 근거 위치: 원문 섹션 번호와 인용 대상의 짧은 요약
- 사실/추론 구분: 확인된 사실 | 문서에서 도출한 추론 | 확인이 필요한 질문
- 영향 대상: 사용자, DBA, 애플리케이션, 복제 정합성 등

### 문제
무엇이 잘못됐거나 빠졌거나 모호한지 설명한다.

### 왜 중요한가
입문 수준 독자도 이해하도록 원인과 결과를 단계별로 설명한다.

### 재현 또는 구체적 예제
실행 전 상태, SQL/이벤트 순서, 기대 결과, 문서상 실제 또는 불명확한 결과를 적는다.

### 권고안
문서 문구, 동작 규칙, 오류 처리 또는 구현 수용 기준을 구체적으로 제안한다.

### 검증 방법
권고안이 충족됐는지 확인할 테스트 또는 관찰 방법을 적는다.
```

심각도는 다음 기준을 사용한다.

- **Blocker**: 데이터 손실·정합성 파괴 가능성이 크거나 핵심 동작을 결정할 수 없어 공개/구현을 중단해야 한다.
- **Critical**: 일반적인 운영에서 장애나 복구 불능을 유발할 가능성이 높다.
- **Major**: 중요한 사용 사례가 실패하거나 호환성·운영성에 큰 공백이 있다.
- **Minor**: 핵심 동작은 가능하지만 문서 정확도, 사용성 또는 제한된 경계 조건에 문제가 있다.
- **Suggestion**: 더 나은 설명이나 설계를 위한 개선 제안이다.

## 7. 예제 작성 기준

모든 20개 리뷰 항목에는 최소 하나의 구체적 예제가 있어야 한다. SQL만 붙여 넣지 말고, 초기 상태와 실행 순서 및 기대 결과를 설명한다.

좋은 예제의 형태는 다음과 같다.

```sql
CREATE TABLE account (
  id INTEGER PRIMARY KEY,
  email VARCHAR(255) NOT NULL UNIQUE,
  balance NUMERIC(15, 2) NOT NULL
) REPLICATION = ON;

-- 트랜잭션 A: 데이터 변경
UPDATE account SET balance = balance - 100 WHERE id = 10;

-- 동시에 또는 복제 지연 중 수행되는 DDL 후보
ALTER TABLE account
  DROP CONSTRAINT pk_account,
  ADD CONSTRAINT pk_account_email PRIMARY KEY (email);
```

이 예제에 대해 최소한 다음을 설명해야 한다.

1. DML 로그가 `id=10`을 RK로 기록했는지 여부
2. DDL 적용 전후 어느 키 정의로 슬레이브의 행을 찾는지
3. DDL과 DML 순서가 마스터 및 슬레이브에서 동일하게 보장되는지
4. 중간 실패나 failover가 발생했을 때 유효한 RK가 항상 하나 이상인지
5. 기대 동작이 “허용”, “거부”, “대기”, “재시도” 중 무엇인지와 오류 코드

초급 독자를 위해 “인덱스가 있으니 무조건 빠르다” 같은 생략된 결론을 피한다. 예를 들어 복합 문자열 UK는 정수 PK보다 로그 크기와 비교 비용이 커질 수 있고, UK 값 자체를 UPDATE하면 이전 키와 새 키 중 무엇으로 행을 찾는지 정의해야 한다는 식으로 원인을 풀어서 쓴다.

## 8. 근거와 비교 제품 사용 규칙

- 대상 문서에 적힌 내용, CUBRID 구현에서 확인한 내용, 일반 DB 이론, 다른 DB 제품의 동작을 섞어 단정하지 않는다.
- 문서의 사실은 섹션 번호를 명시한다.
- 구현을 확인했다면 저장소 파일 경로와 함수/구조체/테스트 이름을 적는다.
- MySQL 또는 PostgreSQL과 비교할 때는 가능하면 해당 버전의 공식 문서 링크와 확인 날짜를 남긴다.
- 외부 근거를 확인하지 못했다면 제품 동작을 사실처럼 쓰지 말고 `검증 필요`로 표시한다.
- “PostgreSQL 컨셉 일부 채용”이라는 표현만으로 동일한 안전성이나 동작을 가정하지 않는다. 어떤 개념을 채용했고 어떤 부분은 다른지 분리한다.
- 에이전트의 내부 지식만을 권위로 사용하지 않는다. 독자가 재현하거나 확인할 수 있는 SQL, 상태 전이, 문서/코드 근거 또는 테스트를 제공한다.
- 원문을 칭찬하는 것이 목적이 아니다. 장점도 근거가 있을 때만 기록하며, 결함과 위험은 완곡하게 숨기지 않는다.

## 9. 에이전트별 산출물

각 관점은 다음 경로에 독립된 Markdown 보고서를 작성한다.

```text
reports/raw/pm_1y.md
reports/raw/pm_3y.md
reports/raw/pm_5y.md
reports/raw/pm_10y.md
reports/raw/dba_1y.md
...
reports/raw/dbdev_10y.md
```

각 파일의 첫 부분에는 다음 메타데이터를 넣는다.

```markdown
# 역할 / 경력 관점 리뷰

- 대상 문서: ../../../user_spec/user_spec.html
- 리뷰 날짜: YYYY-MM-DD
- 리뷰 항목 수: 20
- 검토한 원문 범위: 1~9 전체
- 역할상 중점:
- 확인하지 못한 전제:
```

원시 보고서에는 정확히 20개 항목을 작성한다. 한 항목 안에 독립적인 문제 여러 개를 억지로 묶지 않는다. 반대로 같은 원인의 표현만 바꿔 개수를 채우지 않는다.

## 10. 통합 시 산출물과 중복 처리

20개 원시 보고서가 완성된 뒤 다음 파일을 만든다.

- `reports/REVIEW_SUMMARY.md`: 전체 결과, 심각도별 개수, 핵심 Blocker/Critical, 역할 간 의견 차이
- `reports/CONSOLIDATED_FINDINGS.md`: 동일 원인의 항목을 묶은 통합 결함 목록과 원시 항목 ID 역참조
- `reports/RECOMMENDED_SPEC_CHANGES.md`: 사용자 스펙에 반영할 구체적인 문구·규칙·예제 제안
- `reports/TEST_SCENARIOS.md`: 정상, 오류, 동시성, 장애 조치, 호환성 시험 시나리오
- `reports/OPEN_QUESTIONS.md`: 문서와 구현만으로 답할 수 없는 의사결정 목록과 결정권자

통합 과정에서 원시 400개 항목을 삭제하거나 개수를 줄이지 않는다. 중복은 통합 결함 하나로 연결하되 원시 ID를 모두 보존한다. 다수결로 기술적 위험을 없애지 않으며, 소수 의견이라도 데이터 정합성 위험이 타당하면 별도로 유지한다.

## 12. 작업 제한

- 리뷰 단계에서는 원본 `../user_spec/user_spec.html`을 수정하지 않는다.
- 근거 없이 CUBRID의 현재 구현 동작을 가정하지 않는다.
- 20개 항목 수를 맞추기 위한 문장 분할, 동의어 반복, 역할명만 바꾼 복제를 금지한다.
- 예제 결과가 스펙에 정의되지 않았다면 임의로 결정하지 말고, 가능한 선택지와 권고안을 제시한다.
- 단순 맞춤법 검토에 치우치지 말고 시스템 컨셉, 상태 전이, 정합성 및 복구 가능성을 우선한다.

## 13. 추가 심층 조사 단계

초기 20개 리뷰가 끝난 뒤 각 역할·경력 관점은 **추가로 최대 30개**의 리뷰를 조사한다. 추가 항목 번호는 기존 번호에 이어 `21`부터 `50`까지 사용한다.

추가 조사의 목표는 리뷰 수를 50개로 맞추는 것이 아니다. 기존 20개와 원인이 다르거나, 같은 원인이라도 해당 역할에 고유한 새로운 영향·재현 경로·해결 조건을 제공하는 항목만 추가한다. 다음과 같은 항목은 가치가 낮으므로 추가하지 않는다.

- 기존 항목의 제목이나 표현만 바꾼 내용
- 하나의 문제를 근거 없이 여러 항목으로 잘게 나눈 내용
- 원문이나 검증 가능한 구현 근거 없이 가능성만 반복하는 내용
- 사소한 맞춤법을 여러 건으로 분리한 내용
- 역할 또는 경력 관점의 차이가 없는 복제된 내용
- 구체적 예제, 영향, 권고안 또는 검증 방법을 제시할 수 없는 내용

추가 항목은 초기 항목과 동일한 필수 형식을 사용한다. 추가 조사에서는 특히 초기 검토에서 놓치기 쉬운 다음 주제를 탐색한다.

- 파티션 테이블, 상속·샤딩·분산 객체 등 CUBRID가 실제 지원하는 관련 객체와의 상호작용
- 온라인 DDL, 장기 트랜잭션, 병렬 apply, 로그 압축·보관·재적용
- 키의 collation, 타입 변환, floating/LOB/JSON 등 RK 적합성 및 비교 의미
- 제약 이름 변경, 인덱스 재구축, 통계 갱신, optimizer와 RK의 결합 여부
- 권한, 감사, 보안, 테넌트 분리 및 누가 복제 정책을 변경할 수 있는지
- 백업 시점과 로그 시점, PITR, 복제 슬롯/보관 한계, 재동기화
- 드라이버·ORM·스키마 diff·관리 도구·메타데이터 API 노출
- 국제화된 오류 메시지, 진단 자동화, 대량 객체 검사 결과의 사용성
- 리소스 고갈, 디스크 full, 네트워크 분할, 재시작 반복, split-brain
- 기능 플래그, 라이선스/에디션 차이, downgrade와 되돌릴 수 없는 카탈로그 변경

위 목록의 항목도 대상 제품 또는 원문과 관련이 있을 때만 리뷰한다. CUBRID의 지원 여부를 확인하지 못하면 사실로 단정하지 말고 `확인 필요`로 표시한다.

각 보고서 끝에는 다음 종료 블록을 반드시 추가한다.

```markdown
# 추가 조사 종료 기록

- 추가 조사 목표: 최대 30개
- 실제 추가 항목 수: N개
- 최종 리뷰 항목 수: 20+N개
- 30개를 채우지 않은 경우의 사유: 가치 있는 독립 쟁점을 더 찾지 못했으며, 기존 항목의 반복이나 근거 없는 추측으로 수량을 채우지 않음
- 추가 조사에서 확인하지 못한 영역:
```

추가 항목을 30개 모두 작성한 경우에도 종료 블록과 확인하지 못한 영역을 적는다. 초기 완료 조건의 “각 보고서 정확히 20개, 총 400개”는 초기 단계의 기준으로 보존하며, 최종 통합 단계에서는 각 보고서의 실제 항목 수와 전체 합계를 다시 산출한다.

### 14.4 항목별 판정

각 통합 결함에는 다음 중 하나를 부여한다.

- `확정`: 기능 코드도 문제를 막지 못해 구현 결함 또는 확정 스펙 개정 요구로 승격한다.
- `기각`: 기능 코드가 이미 처리해 원래 전제가 성립하지 않는다.
- `폐기`: 존재하지 않는 기능 또는 다른 DBMS 구조를 전제로 해 CUBRID에 맞지 않는다.
- `판정불가`: 정적 분석으로 결론을 낼 수 없어 구체적인 런타임 시험이 필요하다.
- `코드무관`: 문서 모순, 운영 절차 또는 제품 정책으로 코드 결함 판정 대상이 아니다.

모든 판정에는 코드 파일·심볼 또는 사용자 스펙 문장을 근거로 연결한다. `폐기` 판정에도 원래 항목의 요지를 남기고, 왜 맞지 않는지와 어떤 조건에서 다시 적용될 수 있는지를 기록한다.
