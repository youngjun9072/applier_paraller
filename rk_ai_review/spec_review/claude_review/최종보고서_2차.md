### 1.1 2차에서 나온 양

- **신규 리뷰 총 197건** (20개 리포트, 리포트당 7~12건). 1차의 "20개 × 20건 = 400건"과 달리, 2차는 각 페르소나가 "1차·최종보고서가 다룬 지점을 빼고 새 실패 모드만" 골라 적었기 때문에 리포트당 개수가 줄었다. 이 자체가 정상 신호다 — 1차가 스펙의 정면(正面) 결함을 이미 대부분 덮었다는 뜻이다.
- **1차 40개와 실질 중복이라 걸러낸 것: 약 42건.** 예: "RK가 조용히 바뀌는데 조회할 수 없다"의 이력(history) 각도(1차 C-3), 플래그 전환 중 in-flight DML(1차 C-8), 한 문장 다중 절 원자성 재론(1차 C-7), 국제화 용어(1차 T-6의 확장), 예시 번호·표기 흠(1차 N-1~N-6), 다중 슬레이브·성능/락 재포장(1차 M-9/M-10). 이들은 페르소나 스스로 "조사 종료 선언"에서 제외했거나, 각도만 다르고 뿌리가 같아 신규로 세지 않았다.
- **나머지 ~155건이 30개의 신규 통합 이슈로 수렴**했다(아래 §2). 2차의 특징은 "**스펙이 정면에 쓴 문장의 결함**"(1차)이 아니라 "**스펙이 아예 침묵한 인접 기능과의 충돌**"이라는 점이다. `db_class` 예시(예시 9)에 값만 노출되고 본문이 한 마디도 하지 않은 필드들 — `tde_algorithm`(TDE 암호화), `partitioned`(파티션), `owner_name`(소유자 권한), `collation`, `is_reuse_oid_class` — 이 2차 신규 이슈의 주요 광맥이었다.

### 1.2 1차 판정(NEEDS_FIX)이 바뀌는가 — **아니오. 오히려 강화됨.**

2차는 릴리스 판정을 뒤집을 근거를 하나도 내놓지 않았다. 반대로 **1차가 컨셉 결함으로 지목한 뿌리(RK 비결정성·FK 불변식·복제 로그 정합성)가 스펙이 언급조차 안 한 기능들에서 재발한다**는 것을 보여, "문서만 교정해서는 못 고친다"는 결론을 더 굳혔다. 특히 다음 세 가지가 새로 드러났다.

1. **막으려던 배경 버그(복제 누락 + fail_count 증가)가 이 스펙이 새로 만든 경로로 재현된다.** REPLICATION=OFF 테이블의 DDL 적용 실패(2C-6), loaddb의 단계적 스키마 재현(2C-3), 트리거 기반 참조 무결성(엔진10-22) 모두 스펙의 방어망(§4·§5·§7) 바깥에서 같은 사고를 낸다.
2. **RK 유일성이라는 대전제가 스펙이 침묵한 기능에서 성립하지 않는다.** 파티션-로컬 UNIQUE(2C-1), 부분 NOT NULL 복합 UK(2C-4), 필터/함수 기반 UNIQUE 인덱스(2M-8)가 "RK 값으로 행을 하나로 특정한다"는 전제를 깨뜨린다.
3. **안전장치가 작동하는 시점이 너무 좁다.** §7 검사는 `cubrid hb start`에만 걸리고, 실제로 마스터가 바뀌는 failover·switchover·failback에는 재검증이 없다(2C-2).

**결론: 판정 유지 = 불가(NEEDS_FIX).** 1차 Top 10 + 아래 2차 신규 치명 이슈를 함께 반영해 개정 후 재검토해야 한다.

## 2. 신규 통합 이슈 목록 (1차 40개와 미중복)

> 합의도 = 해당 취지를 지적한 2차 리포트 개수(20 기준, 근사).

### 2.1 치명 (Critical)

#### 2C-1. 파티션 테이블에서 파티션-로컬 UNIQUE가 RK로 뽑히면 행 유일 식별이 깨진다
**합의도: ~13** · 대상: §1, §4 (스펙에 "파티션" 단어 자체가 없음)

파티션 테이블의 UNIQUE 제약은 파티션 키를 포함하지 않으면 "파티션 하나 안에서만 유일"(local)할 수 있다. 즉 같은 값이 서로 다른 파티션에 하나씩 공존한다. RK는 "이 값으로 슬레이브에서 행을 하나로 특정한다"를 전제하는데, 이 전제가 성립하지 않는다. 엔진 개발자 리뷰들이 이를 정합성 파괴(치명)로, 나머지 직군은 "스코프 침묵"(중요)으로 지적했다. 1차는 파티션을 Phase 3 "스코프 명시" 권고로만 스쳤을 뿐, 이 유일성 파괴 메커니즘은 새로 나왔다.

```sql
CREATE TABLE sales (region_id INT, sale_id INT NOT NULL UNIQUE, amount INT)
PARTITION BY RANGE (region_id) (
    PARTITION p1 VALUES LESS THAN (100), PARTITION p2 VALUES LESS THAN (200));
-- PK 없음 → RK = sale_id(UK)
INSERT INTO sales VALUES (10, 555, 1000);   -- p1
INSERT INTO sales VALUES (150, 555, 2000);  -- p2 (파티션-로컬 유일이면 통과)
-- 슬레이브에 "sale_id=555 행 갱신" 로그가 오면 두 행이 걸려 대상을 특정 못 함
```

**예상 시나리오**
1. (전제) HA 두 노드(마스터·슬레이브)가 정상 복제 중이다. sales 테이블은 PK가 없어 NOT NULL UNIQUE인 sale_id가 복제 키로 선택되어 있다. 이 테이블은 region_id 범위로 두 파티션(p1, p2)으로 나뉘고, UNIQUE 제약은 파티션 키(region_id)를 포함하지 않아 파티션 하나 안에서만 유일하다.
2. (조작) 마스터에서 sale_id=555인 행을 서로 다른 파티션에 두 번 INSERT 한다(region_id=10 → p1, region_id=150 → p2). 파티션-로컬 유일성만 검사되므로 두 INSERT 모두 성공한다. 이후 그중 한 행을 UPDATE 한다.
3. (예상 결과) 마스터: 두 행이 정상 공존하고 UPDATE도 정상 수행된다. 슬레이브: 복제 로그에는 "sale_id=555인 행을 갱신하라"만 담기므로, applylogdb가 복제 키로 대상을 찾으면 두 행이 동시에 걸린다. 두 행 모두 갱신되어 마스터에 없는 변경이 슬레이브에 생기거나, 대상이 하나로 특정되지 않아 적용이 실패해 fail_count가 증가한다(둘 중 어느 동작인지는 스펙 미정의라 가정).
4. (사용자 증상) failover 후 슬레이브를 읽는 애플리케이션이 마스터와 다른 데이터를 보게 되거나, fail_count 누적으로 복제가 멈춰 슬레이브가 마스터를 따라가지 못한다. 원인이 "정상적으로 보이던 INSERT 두 건"이라 운영자가 즉시 알아채기 어렵다.

**권고**: "파티션 테이블에서는 파티션 키를 포함하거나 전역 유일성이 보장되는 PK/UK만 RK 후보"라고 §1에 명문화. 파티션 단위 REPLICATION 지정 가부, ADD/DROP PARTITION의 복제 처리도 함께 규정하거나 명시적 out-of-scope 선언.

> **코드 대조 (2026-08-23, feature/CBRD-26246-develop @44468ed73)**: **비적용** — CUBRID는 파티션 테이블의 모든 UNIQUE/PK 제약에 파티션 키 컬럼 포함을 강제하고(미포함 시 ER_SM_INVALID_UNIQUE_IDX_PARTITION), PK는 항상 global이라 RK 후보는 언제나 전역 유일 — '파티션-로컬 UNIQUE로 같은 값이 다른 파티션 공존'이라는 전제가 CUBRID에서 성립하지 않는다. 예시 sales(UNIQUE(sale_id) 파티션키 region_id 미포함)는 애초 생성 자체가 거부됨. (큐브리드에 맞지 않는 내용 — 원문은 이력 보존용으로 유지) (근거: src/object/schema_manager.c:11258-11278 (allocate_unique_constraint), msg/en_US.utf8/cubrid.msg:1242 (err 1169 "Partition key attributes must be present in the index key"))

#### 2C-2. Failover / switchover / failback가 §7 제약 검증을 우회한다
**합의도: ~6 (DBA·엔진·사용자 상위 연차)** · 대상: §7, §1(HA 모드 = `cubrid hb start` 정의)

§7 검사는 "HA 실행 시"(=`cubrid hb start`)에만 걸린다. 그런데 실제로 마스터가 바뀌는 가장 흔한 사건은 재기동이 아니라 **failover**(슬레이브가 마스터로 승격)다. 이는 `hb start`가 아니라 이미 떠 있는 프로세스의 역할 전환이므로 §7 검사가 재실행되지 않는다. 운영 중 어떤 경로로든(예: 1차 C-9의 NOT NULL 해제) RK를 잃은 테이블이 있으면, failover 직후 새 마스터가 검증 없이 그 상태로 쓰기를 받아 배경 버그가 즉시 재현된다. 장애로 복구된 구 마스터가 재합류하는 **failback** 시 x→y→z로 여러 번 바뀐 RK 이력을 순서대로 재생하는지도 미정의(엔진10-29).

```
정상 HA 운영 중 order_items가 RK 후보를 모두 잃음(§7은 시작 시점에만 검사)
→ 마스터 하드웨어 장애 → 슬레이브 승격(hb start 아님, §7 미적용)
→ 새 마스터가 RK 없는 상태로 쓰기 수신 → 복제 누락 + fail_count 재현
```
**권고**: §7 검증 대상을 "마스터 역할을 맡는 모든 시점(failover·switchover·failback 포함)"으로 확장. 승격 전 검증 실패 시 그 노드로의 승격 거부 또는 즉시 경고. failback catch-up 시 스키마(RK 전환) 로그를 중간 상태 건너뛰지 않고 순서대로 재생.

#### 2C-3. loaddb의 "스키마→데이터→인덱스" 단계적 파이프라인이 §4-1과 구조적으로 충돌 (검증 우회 뒷문)
**합의도: ~6 (엔진·응용)** · 대상: §8, §4-1

unloaddb/loaddb는 성능을 위해 (1) 제약 없는 빈 테이블 생성 → (2) 인덱스 없이 대량 적재 → (3) 이후 PK/UK·인덱스 추가 순으로 스키마를 재현한다. (1)단계는 정확히 "RK 후보가 하나도 없는 테이블"이다. §4-1("HA 모드에서 RK 없는 복제 테이블 생성 금지")을 그대로 적용하면 이 표준 복원 절차가 1단계에서 막혀 HA 운영 중 복원 자체가 불가능해진다. 반대로 loaddb가 SQL 파서를 거치지 않는 내부 경로라 §4-1 검증을 건너뛴다면, csql로는 못 만드는 "RK 없는 복제 테이블"을 loaddb로는 살아있는 HA에 심을 수 있는 뒷문이 된다. 어느 쪽이든 문서 교정이 아니라 유틸리티 구현을 바꿔야 하는 사안이다.

**예상 시나리오**
1. (전제) HA 운영 중인 데이터베이스를 unloaddb로 받아 두었다가 loaddb로 복원한다. loaddb는 성능을 위해 (1) 제약 없는 빈 테이블 생성 → (2) 인덱스 없이 대량 적재 → (3) PK/UK·인덱스 추가 순으로 스키마를 재현한다.
2. (조작) HA 모드에서 loaddb를 실행한다. 1단계에서 복제 대상(REPLICATION=ON) 테이블이 아직 복제 키 후보가 하나도 없는 상태로 만들어진다.
3. (예상 결과) 두 갈래가 가능하다(스펙 미정의라 가정). 갈래 A — loaddb가 §4-1의 "HA 모드에서 복제 키 없는 복제 테이블 생성 금지" 검증을 그대로 받으면, 1단계에서 막혀 복원 자체가 실패한다. 갈래 B — loaddb가 SQL 파서를 거치지 않는 내부 경로라 그 검증을 건너뛰면, csql로는 만들 수 없는 "복제 키 없는 복제 테이블"이 살아있는 HA에 그대로 심긴다.
4. (사용자 증상) 갈래 A라면 운영자는 HA를 내리지 않고서는 백업을 복원할 수 없다. 갈래 B라면 복원은 되지만 그 테이블은 복제 키가 없어, 이후 그 테이블의 DML이 슬레이브에 반영되지 못하고 복제 누락·fail_count 증가라는 배경 버그가 다시 나타난다.

**권고**: loaddb가 1단계 CREATE를 항상 REPLICATION=OFF로 내보내고 마지막에 원래 값으로 전환하도록 출력 형식을 바꾸거나, §4-1과 동일 검증 경로를 공유함을 §8에 명시. RK 후보가 없는 ON 테이블을 만났을 때의 처리(실패/경고/OFF 강등)도 규정.

#### 2C-4. 부분 NOT NULL 복합 UK가 RK로 선택되면 행 유일 식별이 불가능
**합의도: ~8** · 대상: §1 "Not Null Unique Key" 정의

스펙의 UK 예시는 모두 단일 컬럼이다. 복합 UNIQUE에서 일부 컬럼만 NOT NULL이면(SQL 관례상 NULL은 서로 다른 값 취급), 같은 값 조합의 행이 여러 개 공존할 수 있어 RK로 쓸 수 없다. "NOT NULL UNIQUE"가 "구성 컬럼 전부 NOT NULL"인지 "하나라도 NOT NULL"인지 스펙에 정의가 없다. 1차 M-1("복제키 후보" 용어 미정의)과는 다른 층위 — 여기는 **후보 자격 판정 기준의 정합성** 문제다.

```sql
CREATE TABLE t3 (x INT NOT NULL, y INT, UNIQUE (x, y));  -- y는 NULL 허용
INSERT INTO t3 VALUES (1, NULL);
INSERT INTO t3 VALUES (1, NULL);  -- 위반 아님 → (x=1,y=NULL) 행이 둘
-- 이 UK가 RK면 "x=1 AND y IS NULL" 조건이 두 행에 매치
```

**예상 시나리오**
1. (전제) 복제 대상 테이블 t3에 PK가 없고 (x, y) 복합 UNIQUE만 있다. x는 NOT NULL이지만 y는 NULL을 허용한다. 복제 키 후보 판정이 "구성 컬럼 전부 NOT NULL"인지 "하나라도 NOT NULL"인지 스펙에 없어, 이 복합 UK가 복제 키로 뽑혔다고 본다(스펙 미정의라 가정).
2. (조작) 마스터에서 (x=1, y=NULL) 행을 두 번 INSERT 한다. SQL 표준상 NULL은 서로 다른 값으로 취급되어 UNIQUE 위반이 아니므로 두 행 모두 들어간다. 이후 이 값 조합을 조건으로 하는 UPDATE 또는 DELETE를 수행한다.
3. (예상 결과) 마스터: 두 행이 공존하고 정상 동작한다. 슬레이브: applylogdb가 "x=1 AND y IS NULL"로 대상 행을 찾으면 두 행이 함께 걸려, 2C-1과 같은 오적용 또는 적용 실패(fail_count 증가)가 일어난다.
4. (사용자 증상) 마스터/슬레이브 데이터가 어긋나거나 복제가 멈춘다. 사용자는 표준 SQL 규칙대로 유효한 데이터를 넣었을 뿐이라, 스펙만 봐서는 이 값 조합이 위험하다는 것을 알 수 없다.

**권고**: "복합 UK가 RK 후보가 되려면 구성 컬럼 전부가 개별적으로 NOT NULL이어야 한다"를 §1에 명시, §4-2 후보 판정에서 부분 NOT NULL 복합 UK를 제외, 복합 UK 예시 최소 1개 추가.

> **코드 대조 (2026-08-23, feature/CBRD-26246-develop @44468ed73)**: **확정** — sm_has_non_null_attribute는 구성 컬럼 중 '하나라도' NOT NULL이면 1을 반환한다. 이를 IS_HA_REPLICATION_KEY_CONSTRAINT가 UNIQUE 계열 판정에 그대로 사용하므로, (x NOT NULL, y NULL) 복합 UK가 RK 자격을 얻는다. '구성 컬럼 전부 NOT NULL' 검사가 없어 부분 NOT NULL 복합 UK가 RK로 뽑혀 행 유일 식별이 깨질 수 있음 — 지적한 구멍이 코드에 그대로 존재. (근거: src/object/schema_manager.c:16114-16130, src/object/class_object.c:95-98)

#### 2C-5. RK 컬럼 값 자체를 바꾸는 순수 UPDATE의 old-key/new-key 로그 처리 미정의
**합의도: ~3 (엔진)** · 대상: 복제 로그 포맷(스펙에 절 없음)

1차 C-8은 RK를 바꾸는 **DDL**의 순서 문제였다. 여기는 DDL이 전혀 없다 — PK/UK 컬럼의 **값**을 평범한 UPDATE로 바꾸는 경우다. 복제 로그가 "변경 후 행 이미지"만 담으면, 슬레이브는 "어떤 행을 찾을지"의 근거(옛 키 값)를 잃는다.

```sql
UPDATE customers SET customer_id = 9001 WHERE customer_id = 5;  -- RK 값 5→9001
-- 슬레이브가 customer_id=9001 행을 찾으려 하면 그런 행은 없음 → 대상 없음/오매칭
```

**예상 시나리오**
1. (전제) 복제 대상 customers 테이블에서 customer_id가 복제 키다. 마스터와 슬레이브에 customer_id=5인 행이 동일하게 존재한다.
2. (조작) 마스터에서 `UPDATE customers SET customer_id = 9001 WHERE customer_id = 5`를 실행해, DDL 없이 복제 키 값 자체를 5에서 9001로 바꾼다.
3. (예상 결과) 마스터: 해당 행의 키가 9001로 정상 변경된다. 슬레이브: 복제 로그가 "변경 후 행 이미지"만 담아 갱신 후 값(9001)으로 대상을 찾으면, 슬레이브에는 아직 5만 있어 대상이 없다. 대상 없음이면 조용히 건너뛰어(무성 skip) 슬레이브에는 여전히 5가 남고, 잘못 매칭되면 엉뚱한 행을 건드린다(둘 중 어느 동작인지는 스펙 미정의라 가정). 어느 쪽이든 마스터=9001, 슬레이브=5로 갈라진다.
4. (사용자 증상) failover 후 슬레이브를 읽는 애플리케이션이 이미 9001로 바뀐 고객을 여전히 5로 보게 되어, 그 키로 연결된 주문·정산이 어긋난다. 조용한 skip이면 fail_count조차 오르지 않아 운영자가 불일치를 감지할 신호가 없다.

**권고**: 복제 로그에 "갱신 전 RK 값(search key)"과 "갱신 후 행 이미지"를 분리 기록. RK 컬럼이 SET 절에 포함되는 케이스를 테스트 케이스로 명시.

> **코드 대조 (2026-08-23, feature/CBRD-26246-develop @44468ed73)**: **비적용** — 이슈 전제('복제 로그가 변경 후 행 이미지만 담아 갱신 후 값으로 대상을 찾는다')가 실제 동작과 다르다. #### 2C-6. REPLICATION=OFF 테이블의 DDL 복제 실패가 배경 버그(fail_count)를 새 경로로 재현
**합의도: ~2 (엔진5, 응용/DBA 일부)** · 대상: §4(DDL은 항상 복제), §1(OFF 데이터 불일치 면책)

§1의 면책은 "데이터 불일치"에 대한 것이고, §4는 "DDL은 REPLICATION 여부와 무관하게 항상 복제·적용되어야 한다"고 한다. 그런데 OFF 테이블은 슬레이브 데이터가 마스터와 다른 것이 허용된 상태이므로, 그 어긋난 데이터 위에서 제약 추가 DDL을 실행하면 마스터에선 성공한 DDL이 슬레이브에선 실패한다 = applylogdb 실패, fail_count 증가, HA 정지. 이 스펙이 새로 만든 OFF 기능 자체가 원래 고치려던 버그의 새 발생 경로다.

```sql
-- customers: REPLICATION=OFF, 슬레이브는 OFF 전환 시점 스냅샷(country 중복 잔존)
ALTER TABLE customers ADD CONSTRAINT UNIQUE(country);  -- 마스터 성공(중복 없음)
-- §4대로 슬레이브 재생 → 슬레이브엔 country 중복 → UNIQUE 위반 실패 → fail_count↑
```
**권고**: OFF 테이블에 대한 DDL 적용 실패 시의 동작을 정의(그 테이블에 한해 DDL 실패를 격리/무시하는 모드 등)하거나, "OFF 테이블도 DDL 실패는 여전히 HA를 정지시킨다"는 위험을 명시하고 운영 가이드 제공.

> **코드 대조 (2026-08-23, feature/CBRD-26246-develop @44468ed73)**: **확정** — 미구현: DML 복제는 heap_is_replication_class로 OFF 테이블을 skip하지만, DDL(SBR) 복제 경로는 테이블 REPLICATION 여부와 무관하게 무조건 복제·재실행한다. §1 면책으로 이미 갈라진 OFF 테이블 슬레이브 데이터 위에서 제약추가 DDL이 재실행되면 마스터 성공·슬레이브 실패가 가능하며, OFF 테이블 DDL 적용 실패를 격리/무시하는 경로가 코드에 존재하지 않아 fail_count 증가·HA 정지를 막지 못함. #### 2C-7. TDE 암호화 테이블 × RK/복제 로그 상호작용 미정의 (정합성 + 보안)
**합의도: ~18 (전 직군)** · 대상: §2-3 예시 9의 `tde_algorithm` 필드, §1

`db_class`에 `tde_algorithm`이 이미 있는데도 본문은 TDE를 한 마디도 안 한다. 두 갈래 위험이 겹친다. **(정합성)** 마스터/슬레이브가 서로 다른 TDE 키를 쓰면 슬레이브가 RK 값으로 행을 찾지 못하거나 적용 실패(→ 또 fail_count). **(보안)** RK 값·복제 로그가 평문으로 실리면, 디스크는 암호화했는데 복제 로그 파일과 네트워크 전송 구간에서 평문이 새어 TDE 도입 취지가 무력화된다. 대부분 중요로 매겼으나 보안+정합성 이중 위험이라 치명으로 승격한다.

```sql
CREATE TABLE payment_cards (card_number CHAR(16) NOT NULL UNIQUE, holder VARCHAR(50))
  /* TDE 적용 */ REPLICATION=ON;   -- RK = card_number(암호화 대상)
-- 복제 로그에 card_number가 평문인가 암호문인가? 슬레이브 키가 다르면 매칭되는가?
```

**예상 시나리오**
1. (전제) 복제 대상 payment_cards 테이블이 TDE로 디스크 암호화되어 있고, NOT NULL UNIQUE인 card_number가 복제 키다. 스펙이 TDE를 다루지 않으므로 마스터·슬레이브의 TDE 키 공유 여부와 복제 로그의 암호화 여부는 미정의다(스펙 미정의라 가정).
2. (조작) 마스터에서 payment_cards에 행을 INSERT/UPDATE 하면 복제 로그가 생성되어 슬레이브로 전송·적용된다.
3. (예상 결과) 두 위험이 겹친다. 정합성 갈래 — 마스터와 슬레이브의 TDE 키가 다르면 슬레이브가 복제 키 값(card_number)으로 행을 찾지 못해 적용이 실패하고 fail_count가 증가한다. 보안 갈래 — 복제 로그가 논리(평문) 레벨로 만들어지면 card_number가 복제 로그 파일과 네트워크 전송 구간에 평문으로 남는다.
4. (사용자 증상) 정합성 갈래면 복제가 멈춰 슬레이브가 뒤처진다. 보안 갈래면 디스크는 암호화했는데 복제 경로에서 카드번호 평문이 새어, 규제 심사에서 TDE 도입 취지가 무력화됐다는 지적을 받는다.

**권고**: 복제 로그가 논리(평문) 레벨에서 생성됨을 명시하고 마스터/슬레이브 TDE 키 공유·로테이션 정책을 규정. 전송 구간 암호화(TLS 등) 강제 여부 명시. 불가하면 "TDE 테이블 복제는 이번 릴리스 검증 범위 밖"이라고 최소한 스코프 선언.

### 2.2 중요 (Major)

#### 2M-1. REPLICATION 변경 권한·감사(audit) 모델이 전무 — 2차 최다 합의
**합의도: ~18 (전 직군·전 연차)** · 대상: §2-2, 예시 9의 `owner_name`

`ALTER TABLE ... REPLICATION=OFF`를 누가 실행할 수 있는지 스펙에 한 줄도 없다. 일반 ALTER 권한(테이블 소유자)만으로 가능하다면, DBA가 아닌 애플리케이션 계정이 승인 없이 DR 보장 범위를 바꾸고 다른 테이블의 FK 무결성(1차 C-2)까지 흔들 수 있다. 부작용이 즉시 안 보이고(다음 failover까지) 변경 이력을 조회할 표준 수단도 없어, 규제 산업(금융·의료) 컴플라이언스 심사에서 바로 걸린다.
```sql
GRANT ALTER ON customers TO app_user;  -- 일반 개발 계정
-- app_user 세션: ALTER TABLE customers REPLICATION=OFF;  성공? 누가 언제 바꿨는지 추적?
```

**예상 시나리오**
1. (전제) DBA가 orders(복제 대상)와 그 FK 부모인 customers(복제 대상)로 HA를 구성했다. 애플리케이션 계정 app_user는 customers에 일반 ALTER 권한을 갖고 있다. REPLICATION 변경에 별도 권한이 필요하다는 규정이 스펙에 없으므로, 일반 ALTER 권한만으로 가능하다고 본다(스펙 미정의라 가정).
2. (조작) app_user가 승인 절차 없이 `ALTER TABLE customers REPLICATION=OFF`를 실행한다.
3. (예상 결과) 마스터: customers가 복제 제외로 바뀌어 이후 customers 데이터가 슬레이브로 가지 않는다. 슬레이브: customers는 전환 시점 스냅샷에서 갱신이 멈춘다. 변경 이력을 남기는 표준 수단이 없어 누가·언제 바꿨는지 카탈로그나 감사 로그에서 확인되지 않는다.
4. (사용자 증상) 부작용이 즉시 보이지 않다가 다음 failover 때 새 마스터의 customers에 최신 데이터가 없어 orders의 FK 참조가 깨진다. 원인을 추적하려 해도 변경 주체·시각을 알 수 없어, 금융·의료 같은 규제 산업의 컴플라이언스 심사에서 바로 걸린다.

**권고**: REPLICATION 변경을 일반 ALTER와 분리된 권한(DBA 또는 신규 `REPLICATION` 권한)으로 제한하거나 최소한 변경 이력(계정·시각·이전/이후 값)을 감사 로그·카탈로그에 기록.

> **코드 대조 (2026-08-23, feature/CBRD-26246-develop @44468ed73)**: **확정** — do_alter_change_replication에는 REPLICATION 전용 권한 검사도, 변경 이력을 남기는 감사 로그도 없다 — 일반 ALTER 권한(소유자/ALTER grant)만으로 SA 모드에서 변경 가능. 이슈의 '전용 권한/감사 부재'는 코드로 확인됨(승격 대상). 단 중요한 완화: !HA_DISABLED() 게이트로 HA 운영 중에는 ER_HA_REPLICATION_OPTION_CHANGE_NOT_ALLOWED로 거부되므로, app_user가 HA 가동 중 즉시 마스터 복제범위를 바꾼다는 시나리오 자체는 온라인에서는 불가. 거버넌스 공백(권한 분리·감사)은 그대로 유효. #### 2M-2. REPLICATION=OFF의 로그 계층(마스터 생성 skip vs 슬레이브 필터) 미정의 → 성능·용량 오판
**합의도: ~5 (DBA·PM)** · 대상: §1, §4

OFF 차단이 (a) 마스터가 애초에 복제 로그를 안 만드는지, (b) 로그는 다 만들되 전송 전 필터인지, (c) 슬레이브 적용 단계에서 버리는지 스펙에 없다. 셋은 사용자에게 보이는 결과(슬레이브에 데이터 없음)는 같지만 네트워크 대역폭·슬레이브 디스크·복제 지연 지표가 100배까지 갈린다. "성능 때문에 MySQL식을 배제했다"는 설계 근거를 내세운 문서인 만큼 이 계층을 밝혀야 한다.
```
audit_log(OFF, 500GB/일) vs orders(ON, 5GB/일)
경로 A(마스터 필터): 복제 트래픽 ~5GB/일 / 경로 B(슬레이브 필터): ~505GB/일, 500GB 버려짐
```
**권고**: OFF 테이블 변경분이 트랜잭션 로그·복제 로그·적용 단계 중 어디서 제외되는지 §1/§4에 명시하고 각 경우의 성능·용량 영향을 표로 정리.

#### 2M-3. §7 검사 blast radius — 전체 vs 부분 기동, DB단위 vs 그룹, 검증 비용
**합의도: ~7 (DBA·엔진)** · 대상: §7

세 가지가 미정의다. (1) 위반 발견 시 클러스터 전체가 안 뜨는지, 위반 테이블만 제외하고 나머지는 뜨는지 — 전자면 테이블 1개가 SPOF, 후자면 "또 다른 조용한 복제 누락". (2) 한 서버의 여러 DB 중 하나만 위반해도 그룹 전체가 막히는지. (3) 수천~수만 테이블 카탈로그 전수 스캔이 위반이 없어도 failover 시간(RTO)에 얼마나 붙는지. 또한 §7 검사 시작~HA 완전 활성화 사이에 싱글 모드 규칙으로 RK를 없애는 레이스(엔진5-26), 노드별 독립 검사 시 마스터 통과·슬레이브 실패의 비대칭 기동(엔진5-27)도 여기 묶인다.
**권고**: §7의 실패 상태·적용 단위(단일 DB/그룹)·성능 특성을 명시. 검사를 배타 잠금 하에 원자적으로 수행하고 통과 즉시 HA 활성화. 노드 간 카탈로그 불일치 자체를 에러로 보고.

#### 2M-4. 물리 백업(backupdb/restoredb)·PITR와 REPLICATION 미정의
**합의도: ~6 (DBA·PM·응용)** · 대상: §8 (unloaddb/loaddb만 다룸)

실무 백업·DR은 논리 백업(§8이 다루는 unloaddb)보다 물리 백업(backupdb/restoredb)이 훨씬 흔한데 스펙이 침묵한다. PITR(시점 복구)은 옛 시점의 REPLICATION 카탈로그 상태를 되살려 현재 클러스터와 어긋날 수 있고(DBA3-21), 슬레이브에서 백업을 뜨면 OFF 테이블은 항상 빈 채로 백업된다(DBA3-22 → §2.4로). 구버전 물리 백업을 신버전에 복원할 때의 카탈로그 마이그레이션도 §8이 다루지 않는다.
**권고**: §8을 "논리 백업 / 물리 백업"으로 나눠 각각의 REPLICATION·RK 저장·복원·마이그레이션 규칙을 명시. PITR 복구 후 REPLICATION 전수 점검을 절차화.

#### 2M-5. 도구 생태계(표준 메타데이터·JDBC·ORM·스키마 diff)에 RK·REPLICATION 미노출 → 조용한 되돌림·드리프트
**합의도: ~6 (응용·PM)** · 대상: §2-3

조회 수단이 CUBRID 전용(`show create table`, `db_class`)뿐이라 표준 경로로는 안 보인다. 결과: (a) Liquibase/Flyway 스키마 diff가 REPLICATION 차이를 못 잡아 환경 드리프트가 사각지대(응용1-22). (b) ORM 자동 스키마 동기화(`hbm2ddl=update`)나 테이블 재생성 경로가 REPLICATION 옵션을 몰라 DBA가 건 OFF를 배포마다 조용히 ON으로 되돌림(응용10-27, 치명). (c) jOOQ/MyBatis Generator가 표준 `DatabaseMetaData`로는 RK를 알 수 없음(응용5-27). (d) 자동 롤백 생성기가 OFF→ON 비대칭(HA 중 금지)을 몰라 롤백 자체가 실패(응용10-29). 1차 C-3(사람이 조회 불가)과 달리 여기는 **도구가 자동으로 소비하는 경로**의 부재다.

**예상 시나리오**
1. (전제) DBA가 customers 테이블을 규제상 슬레이브로 내보내면 안 되어 `REPLICATION=OFF`로 설정해 두었다. 애플리케이션은 ORM(예: Hibernate)의 자동 스키마 동기화(hbm2ddl=update)나 테이블 재생성 경로로 배포되며, ORM은 REPLICATION 옵션의 존재를 알지 못한다.
2. (조작) 다음 배포에서 ORM이 customers를 재생성하거나 동기화하며, REPLICATION 옵션을 생략한 CREATE/ALTER를 낸다. 스펙상 옵션 생략은 기본값 ON이다.
3. (예상 결과) 마스터: customers가 다시 REPLICATION=ON이 된다. 슬레이브: customers 데이터가 다시 복제되기 시작한다. 표준 스키마 diff 도구(Liquibase/Flyway)나 JDBC 표준 메타데이터로는 REPLICATION 차이가 보이지 않아 이 되돌림이 감지되지 않는다.
4. (사용자 증상) DBA가 건 복제 제외 정책이 배포마다 조용히 풀려, 슬레이브로 내보내면 안 되는 데이터가 규제를 위반한 채 복제된다. 아무도 명시적으로 바꾸지 않았기에 원인 파악이 늦어진다.

**권고**: REPLICATION·RK를 표준 메타데이터 뷰/JDBC 확장에 노출. REPLICATION 걸린 테이블은 ORM 자동 동기화·자동 롤백 대상에서 제외하도록 가이드. `show create table` 출력 포맷 변경을 "인터페이스 변경"으로 릴리스 노트에 명시.

#### 2M-6. LIKE / CTAS / RENAME TABLE(그림자 스왑)에서 REPLICATION·RK 상속·승계 미정의 + §5 우회
**합의도: ~7 (사용자·응용·엔진)** · 대상: §2-1, §5

`CREATE TABLE ... LIKE`/`AS SELECT`로 만든 사본이 원본의 REPLICATION을 상속하는지, 옵션 생략으로 간주해 기본값 ON이 되는지 없다. CTAS는 제약이 안 따라와 "RK 없는 복제 대상"이 손쉽게 생긴다. 더 심각한 것은 **RENAME TABLE 기반 그림자 스왑**(무중단 스키마 변경의 표준 기법): OFF로 만든 그림자 테이블을 운영 이름으로 RENAME하면 REPLICATION=OFF가 그대로 승계되어 조용히 복제가 끊기거나(엔진10-25), RENAME이 §5 FK 검증을 재실행하지 않아 "복제 대상이 복제 제외를 참조"하는 1차 C-2 상황이 ALTER 없이 재현된다(엔진1-27).

**예상 시나리오**
1. (전제) 무중단 스키마 변경을 위해 운영 테이블 orders(복제 대상)를 그대로 두고, 새 구조의 그림자 테이블 orders_new를 만들어 데이터를 옮긴 뒤 이름만 바꿔치기하는 기법(그림자 스왑)을 쓴다. 그림자 테이블은 적재 중 복제 부하를 피하려 REPLICATION=OFF로 만들어 두는 일이 흔하다.
2. (조작) orders_new에 데이터를 다 채운 뒤 `RENAME`으로 orders_new를 운영 이름 orders로 바꾼다. RENAME이 §5·§7의 FK·REPLICATION 정합성 재검증을 다시 트리거하는지는 스펙에 없다(스펙 미정의라 가정).
3. (예상 결과) 마스터: 운영 이름 orders가 REPLICATION=OFF 상태를 그대로 승계해 복제가 조용히 끊긴다. 슬레이브: 이름은 orders지만 RENAME 이후의 신규 주문이 더 이상 도착하지 않는다. 재검증이 없으면 "복제 대상이 복제 제외를 참조"하는 FK 위반 상태도 검사 없이 성립한다.
4. (사용자 증상) 애플리케이션은 평소처럼 orders에 쓰지만 슬레이브에는 반영되지 않다가, failover 후 새 마스터에서 스왑 이후의 주문이 통째로 사라진 것을 발견한다.

**권고**: LIKE/CTAS/RENAME의 REPLICATION·RK 승계 규칙을 명문화. RENAME 시 §5·§7과 동일한 FK/REPLICATION 정합성 재검증을 트리거.

#### 2M-7. FK 참조 액션(ON DELETE/UPDATE CASCADE 등)의 복제 처리 미정의

**권고**: 문서 서두에 적용 버전/에디션/타깃 릴리스/성숙도 등급을 명시. 카탈로그 스키마 변경과 다운그레이드 호환성, RK 검증을 한시 완화하는 시스템 파라미터(킬스위치)를 최소 한 릴리스 제공 검토.

> **코드 대조 (2026-08-23, feature/CBRD-26246-develop @44468ed73)**: **코드무관** — 순수 릴리스 거버넌스 메타데이터 이슈로 코드 대조 대상이 아니다. 킬스위치(RK 검증 한시완화 시스템파라미터)는 커밋에 없으나 이는 스펙이 요구한 항목이 아니라 리뷰의 기능 권고이며, 본질은 문서 서두 메타데이터 보강 요청. (근거: 문서 전체 대상 — 적용버전/에디션/성숙도(GA/Beta)/백포트/킬스위치/다운그레이드 메타데이터)

#### 2M-14. "RK 추가"의 실제 비용 — 중복 데이터 정리·대용량 인덱스 락·클라이언트 타임아웃
**합의도: ~4 (사용자·DBA·응용)** · 대상: §3, §7, §9

스펙은 "RK 없으면 ALTER로 추가하면 된다"고 한 줄로 넘긴다. 그러나 PK 없이 오래 운영된 테이블엔 중복값이 쌓여 있어 UNIQUE 추가가 실패하며, 이를 정리하는 것은 비즈니스 로직 판단이 필요한 별도 프로젝트다(사용자3-21). 새 UK를 DEFAULT 상수로 추가하면 두 번째 행부터 중복 위반(사용자3-22). 수천만 건 테이블의 인덱스 생성은 장시간 락 → 다운타임 산정 실패(DBA1-28)와 JDBC socketTimeout 초과 → 재시도가 락 경합을 부름(응용10-28).
**권고**: §7/§9에 "RK 추가는 데이터 정리 선행이 필요할 수 있고 테이블 크기에 비례하는 무거운 DDL"임을 경고. 사전 점검 시 위반 테이블의 행 수 규모를 함께 제공, 온라인(무중단) 인덱스 생성 지원 여부 명시.

> **코드 대조 (2026-08-23, feature/CBRD-26246-develop @44468ed73)**: **코드무관** — §3/§7/§9에 운영 경고 추가를 요구하는 순수 문서·운영 가이드 이슈. 중복 데이터 정리 선행 필요·대용량 인덱스 락·클라이언트 타임아웃은 UNIQUE/PK 추가의 표준 CUBRID DDL 비용으로 본 기능이 새로 만든 동작이 아니다. 권고는 스펙에 비용 경고와 온라인 인덱스 지원 여부를 명시하라는 문서 개정 사안이라 코드 대조 대상 아님. (근거: 코드무관 — §3/§7/§9에 운영 경고 추가를 요구하는 순수 문서·운영 가이드 이슈)

## 3. 1차 이슈의 보강 (새 각도·예제만 간단히)

2차가 신규는 아니지만 1차 이슈에 새 예제/각도를 더한 것:

- **1차 C-1(RK 비결정성) 보강**: unload/load 왕복만으로도(ALTER 없이) RK가 재계산되어 원본과 달라질 수 있음 — 백업/복원 무결성 각도(엔진10-24). RK 자동선택 규칙이 unload 스키마 파일의 제약 나열 순서에 의존하는데 그 순서 보장이 없음.
- **1차 C-2(FK 사후 OFF 미차단) 보강**: 같은 결과를 **RENAME TABLE**(2M-6)과 **트리거 기반 참조 무결성**(엔진10-22)으로도 도달 — §5가 선언적 FOREIGN KEY만 검사하므로 트리거로 구현한 참조는 방어망 밖. 규제(PII 국외반출 제한)로 부모를 OFF로 둬야 하는 요구와 §5 강제가 정면 충돌(PM3-27).
- **1차 C-3(RK 조회 불가) 보강**: "현재 값"뿐 아니라 "변경 이력(언제·무엇에서 무엇으로)"도 없음(사용자1-30). 표준 JDBC/ORM 경로로는 애초에 조회 불가(2M-5).
- **1차 C-4(§7 파일 리스트) 보강**: 실패 후 DB가 어떤 상태로 남는지(DBA1-23), 신규 제약 위반이 클라이언트 화면 밖 서버 에러 로그에도 남는지(DBA10-28), 위반 유형별(RK 없음 vs FK) 해결 절차 구분(사용자5-29)이 없음.
- **1차 C-7(복합 ALTER 원자성) 보강**: 두 개의 독립 트랜잭션이 각자 "다른 후보 있음"으로 통과하지만 합쳐지면 RK 0개가 되는 TOCTOU 경쟁(엔진3-23), 단일 ALTER의 암묵적 다단계 내부 구현이 RK 0개 구간을 거침(엔진5-29).
- **1차 M-5(OFF↔ON 재동기화) 보강**: RK 위반 하나를 고치려 HA 전체를 내려야 하는지, 문제 테이블만 OFF로 임시 격리 가능한지 §7이 대안을 안내하지 않음(DBA1-21).

## 4. 조사 소진 판정

### 4.1 페르소나별 exhausted 선언 현황

20개 리포트 **전부**가 명시적 "조사 종료 선언"을 달았고, 하나도 30건을 채우지 않았다(7~12건). 공통 논리는 동일했다: **(1)** 1차·최종보고서가 스펙 정면을 촘촘히 덮어 남은 것은 인접 기능과의 충돌뿐이다, **(2)** 그중 근거를 코드/문면으로 댈 수 있는 것만 남기고 추측성은 배제했다, **(3)** 개수 채우기용 재포장은 지시가 금지했으므로 하지 않았다.

- 명시적으로 "추가 여지 없음/소진"을 선언: PM 4개, DBA 4개, 사용자 4개, 응용 4개, 엔진 1·5·10년차.
- "코드를 열어봐야 확정되는 영역이 남아있다"고 조건부로 남긴 것: 엔진 3년차(병렬 applylogdb 결합), 엔진10(카탈로그 캐시·TDE를 소스로 검증), DBA1(엔진 내부 락 순서). 이들은 "스펙 문서 리뷰의 범위를 벗어난다"고 스스로 선을 그었다.
- 다수 페르소나가 **의도적으로 제외**한 것이 겹친다: 트리거 간접 DML, SERIAL/AUTO_INCREMENT failover 동기화, REUSE_OID, 멀티 슬레이브 차등 복제, 에러 코드 체계, 성능/락 — 모두 1차 최종보고서(엔진 고유 지적·M-6·M-9·M-10)에 이미 실려 재탕이 되기 때문. collation은 다수가 "무영향"으로 제외했으나 소수가 남겨 2M-11의 이견으로 남았다.

### 4.2 "이 스펙에서 더 짜낼 리뷰가 있는가" — 나의 판단

**문서(스펙 텍스트)만을 대상으로 하는 리뷰는 사실상 소진됐다.** 근거: (1) 2차 197건이 1차 40개와 겹치지 않는 신규를 30개로 수렴시켰는데, 그 30개조차 대부분 "스펙이 침묵한 인접 기능"이라는 **단일 뿌리의 변주**다(권한·TDE·파티션·collation·백업도구·상속·RENAME·loaddb — 전부 "본문에 없다"). (2) 서로 다른 5개 직군이 독립적으로 같은 상위 3개(권한 ~18, TDE ~18, 파티션 ~13)에 수렴한 것은 탐색 공간이 좁아졌다는 신호다. (3) 남은 미탐색은 전부 페르소나들이 "스펙 문서로는 확인 불가, CUBRID 소스를 열어야 한다"고 지목한 구현 검증 영역이다.

**따라서 다음 단계는 3차 리뷰가 아니라 두 갈래다.** (a) 스펙 저자에게 미정의 항목(§8/§9 기본값, RK 확정 알고리즘, 파티션·TDE·권한 스코프)을 확정받아 문서를 개정하고, (b) 개정된 스펙과 실제 CUBRID 카탈로그/복제/loaddb **코드를 대조**하는 코드 분석 라운드로 넘어가는 것. 같은 스펙 텍스트에 리뷰어를 더 투입하는 것은 한계효용이 급감한다.
