## 4. 비적용 목록 — "큐브리드에 맞지 않는 내용"

> 스펙 리뷰가 전제한 상황이 CUBRID의 실제 동작과 달라 애초에 발생할 수 없는 것으로 확인된 3건. 리뷰 이력은 원문 보고서에 그대로 남아 있다.

| ID | 리뷰가 전제한 상황 | CUBRID 실제 동작 |
|---|---|---|
| **2C-1** | 파티션 테이블에서 파티션-로컬 UNIQUE(파티션 키 미포함)로 같은 값이 서로 다른 파티션에 공존해 RK 유일성이 깨짐 | CUBRID는 파티션 테이블의 모든 UNIQUE/PK 제약에 파티션 키 컬럼 포함을 **강제**한다(`schema_manager.c:11258-11278`, 미포함 시 `ER_SM_INVALID_UNIQUE_IDX_PARTITION` 에러 1169). 예시로 든 `sales(UNIQUE(sale_id))` 자체가 테이블 생성 시점에 거부되어 시나리오가 성립하지 않는다. |
| **2C-5** | UPDATE로 RK 컬럼 값을 바꾸면(예: customer_id 5→9001) 복제 로그가 "변경 후 이미지"만 담아 슬레이브가 옛 값(5)으로 대상을 못 찾음 | 복제 로그는 갱신 **전** RK 값(old_key)을 search key로 별도 기록한다(`locator_sr.c:8757-8759`, `:8783`). 슬레이브는 이 옛 키로 행을 찾아 새 이미지를 적용하므로 마스터=슬레이브가 항상 일치한다. |
| **2M-10** | 커넥션 풀의 오래된 세션이 로컬 스키마 캐시(옛 RK)로 DML을 실행해 복제 로그가 비적용된 RK 기준으로 기록될 수 있음(멀티프로세스 캐시 전파 지연) | RK 판정은 클라이언트/CAS 프로세스의 로컬 캐시가 아니라 **서버측 현재 클래스 표현**(heap classrepr)에서만 이뤄진다(`locator_sr.c:8420-8425`). 게다가 RK 변경 DDL은 클래스 X-lock을 잡아 동시 DML을 직렬화한다(`execute_schema.c:11777`). "캐시가 낡아서 옛 RK로 기록된다"는 전제 자체가 CUBRID 아키텍처와 맞지 않는다. |

## 5. 판정불가 목록 — 런타임 테스트 필요 (QA 시나리오 후보)

| ID | 이슈 | 정적 분석으로 확인된 것 | 필요한 런타임 테스트 |
|---|---|---|---|
| **N-11** | DROP TABLE 후 동일명 REPLICATION=ON 재생성으로 "HA중 OFF→ON ALTER 금지" 규칙을 기계적으로 우회 가능 | ALTER 경로는 확실히 차단됨(`execute_schema.c:11740`). 그러나 CREATE는 RK/FK 검사만 통과하면 허용되고, DROP과 연계해 금지를 우회하는 것을 막는 코드가 없음(`:10267-10274`) | HA 2노드에서 REPLICATION=OFF 테이블을 DROP한 뒤 동일 이름으로 REPLICATION=ON 테이블을 재생성 → (1) 슬레이브에 동일한 빈 ON 테이블이 생성되는지, (2) 이후 DML이 정상 복제되는지, (3) 과거 데이터의 복제 공백이 실제로 해를 끼치는지(새 테이블이라 원래 비어있음) 확인 |
| **2C-7** | TDE 암호화 테이블에서 RK/복제 로그 상호작용 미정의 — (a) 정합성: 마스터/슬레이브 TDE 키 불일치 시 행 매칭 실패 가능성, (b) 보안: 복제 로그에 RK 값이 평문 노출 가능성 | 정합성 갈래는 전제가 약함 — TDE는 페이지 단위 암호화이므로 행 매칭은 복호화된 인메모리 값 기준으로 정상 동작할 가능성이 높음. 보안 갈래는 관련 코드(`log_applier.c:1047-1057`)가 정의되지 않은 매크로(`UNSTABLE_TDE_FOR_REPLICATION_LOG`) 뒤에 컴파일아웃되어 있어 정적으로 결론 낼 수 없음 | 2노드 HA + TDE 암호화 REPLICATION=ON 테이블(노드별 TDE 키를 다르게 구성)에서: (a) DML이 정상 복제·매칭되는지(정합성), (b) 슬레이브로 전송/적재된 복제 로그 파일·네트워크 캡처에 RK 값이 평문으로 남는지(보안) 확인 |
