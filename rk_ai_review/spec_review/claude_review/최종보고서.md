## 1. 요약 (릴리스 판정)

### 1.1 스펙의 현재 상태

이 스펙이 풀려는 문제(PK 없는 테이블 때문에 HA 복제가 조용히 깨지고 마스터/슬레이브 데이터가 불일치하는 실제 장애)와 큰 방향(PostgreSQL REPLICA IDENTITY 일부 채용 + REPLICATION 테이블 옵션)은 20개 리뷰 전원이 "타당하다"고 평가했다. 그러나 **문서를 실제 시나리오에 대입하면 컨셉·구현·문서 세 층위 모두에서 릴리스를 막는 결함이 나온다.**

- **내부 모순이 존재한다.** §8과 §9가 "복제 여부 표시가 없는 테이블의 기본값"을 각각 ON과 OFF로 **정반대로** 규정한다. 이 한 곳 때문에 구버전→신버전 업그레이드 결과가 "전부 복제됨" 또는 "전부 복제 안 됨"으로 갈린다 — 둘 다 이 기능이 애초에 막으려던 사고와 같은 종류다.
- **핵심 목표를 스펙 스스로 무력화한다.** FK(외래키) 참조 대상이 복제 제외면 failover 후 참조 데이터가 없어 애플리케이션이 깨진다는 것이 이 기능의 출발점인데, 스펙은 이를 `CREATE TABLE`/FK 추가 시점에만 막는다. 이미 맺어진 관계에서 부모 테이블을 나중에 `ALTER TABLE ... REPLICATION=OFF`로 바꾸는 경로는 아무도 막지 않아, 막으려던 그 장애가 ALTER 한 줄로 그대로 재현된다.
- **핵심 개념이 비결정적이다.** RK 자동 선택 규칙이 "ex.(예를 들어) 테이블 내 명시된 순서 중 가장 빠른 순서"라는 예시 수준으로만 적혀 있다. 확정 알고리즘이 아니라 마스터와 슬레이브가, 혹은 원본과 복원본(unload/load)이 서로 다른 컬럼을 RK로 고를 수 있다.
- **기존 고객 마이그레이션 경로가 통째로 비어 있다.** in-place 업그레이드, 롤링 업그레이드(버전 혼재 구간), 카탈로그 스키마 마이그레이션에 대한 서술이 전혀 없다.

### 1.2 릴리스 가능 여부 — **불가 (NEEDS_FIX)**

20개 리뷰가 매긴 "치명" 등급 지적이 리뷰당 평균 3~5건이며, 그중 상당수가 서로 다른 직군에서 **독립적으로 같은 지점**을 짚었다. 특히 아래 두 가지는 컨셉 차원의 결함이므로 문서 교정만으로는 해소되지 않는다.

1. §8/§9 기본값 모순 (즉시 하나로 확정 필요)
2. FK 참조 대상의 사후 REPLICATION=OFF 전환 미차단 (규칙 자체를 대칭으로 다시 설계해야 함)

**결론: 현재 문서로는 QA 테스트케이스 작성도, 구현 착수도, 사용자 매뉴얼화도 불가능하다. 아래 Top 10을 반영해 개정한 뒤 재검토해야 한다.**

#### C-1. RK 자동 선택 규칙이 비결정적 — "ex. 명시된 순서"

**합의도: ~20/20 (전 직군·전 연차)** · 대상: §1

"UK가 여러개 존재한다면 큐브리드 엔진에 의해 이 중 하나가 선택된다(ex. 테이블내에 명시된 순서 중 가장 빠른 순서)" — `ex.`라는 표현부터 이것이 확정 규칙인지 예시인지 불명확하고, "명시된 순서"가 (a) CREATE TABLE 텍스트 순서, (b) 카탈로그 내부 OID/생성시각 순서, (c) 컬럼 선언 순서 중 무엇인지 정의가 없다. 이 셋은 ALTER로 UK를 추가·삭제·재생성하면 서로 다른 결과를 낸다. 엔진개발자 리뷰들은 여기에 "마스터와 슬레이브가 각자 카탈로그를 보고 재계산하면 두 노드가 서로 다른 RK를 고를 수 있다(split-brain)"는 더 무거운 함의를 붙였다.

**대표 예제** (DB엔지니어·엔진개발자 공통):
```sql
CREATE TABLE t (a INT NOT NULL UNIQUE, b INT NOT NULL UNIQUE);
-- 텍스트 순서 기준이면 RK = a

ALTER TABLE t DROP CONSTRAINT u_t_a;   -- a의 UK 제거
ALTER TABLE t ADD CONSTRAINT UNIQUE(a); -- a의 UK를 다시 생성(카탈로그상 b보다 나중)
-- 이제 RK는 a인가 b인가? 기준 정의에 따라 갈린다. 사용자는 아무것도 "바꾸지" 않았다.
```

**예상 시나리오**
1. (전제) 마스터·슬레이브 2노드 HA 구성. 테이블 t는 PK 없이 NOT NULL UNIQUE 컬럼 a, b 두 개를 가진 복제 테이블이다. 마스터와 슬레이브가 각자 자기 카탈로그를 보고 복제 키를 계산한다(스펙에 "마스터가 정한다"는 규정이 없어 노드별 재계산으로 가정 — 스펙 미정의라 가정).
2. (조작) 운영자가 위 예제처럼 a의 UNIQUE 제약을 지웠다가 다시 추가한다. 마스터는 재계산해도 여전히 a를 복제 키로 고르지만, 슬레이브는 카탈로그상 생성 순번이 뒤바뀌어 b를 복제 키로 고른다.
3. (예상 결과) 이후 마스터에서 `UPDATE t SET c=... WHERE a=1`이 실행되면, 마스터는 a 값을 행 식별자로 삼아 복제 로그를 남긴다. 슬레이브는 자신이 고른 b를 식별자로 기대하므로 로그의 a 값만으로는 갱신할 행을 찾지 못한다. applylogdb는 대상 행을 찾지 못해 조용히 건너뛰거나 fail_count가 올라간다.
4. (사용자 증상) 마스터에 반영된 변경이 슬레이브에는 반영되지 않아 두 노드 데이터가 서서히 어긋난다. Failover 후 애플리케이션이 슬레이브를 읽으면 옛 값이 나온다. 정작 이 스펙이 없애려던 "조용한 복제 누락"이 복제 키 선택 규칙 자체에서 다시 생긴다.

**권고**: 선택 기준을 "제약이 카탈로그에 생성된 순번(단조 증가 ID) 오름차순" 같은 조회 가능한 단일 규칙으로 명문화하고, "한번 선택된 RK는 명시적 DDL 없이는 재선택되지 않는다(sticky)"는 불변식을 추가한다. 마스터가 결정한 RK를 DDL 복제 로그에 실어 슬레이브가 **재계산하지 않고 그대로 사용**하도록 아키텍처를 확정한다.

> **코드 대조 (2026-08-23, feature/CBRD-26246-develop @44468ed73)**: **확정** — RK 선택 규칙이 스펙의 'ex.명시된 순서'가 아니라 '클래스표현 인덱스 배열 순서(PK 패밀리 먼저, 그다음 UNIQUE 프로퍼티 저장순)에서 첫 복제후보'라는 내부 규칙이며, 조회 불가·sticky 불변식 없음. 마스터는 키값만 실어 보내고 슬레이브는 btree_get_rkey_btid로 자기 카탈로그에서 RK를 독립 재계산함(locator_sr.c:6848). object_representation_sr.c:4692 TODO가 '인덱스 의존 방식을 마스터에서 RK 이름을 받는 방식으로 교체 필요'라고 명시 — C-1 권고(마스터가 정한 RK를 슬레이브가 재계산 없이 사용)가 미구현임을 코드가 확인. #### C-2. FK 참조 부모 테이블의 사후 REPLICATION=OFF 전환 미차단

**합의도: ~18/20 (PM·DBA·사용자·응용·엔진 전 직군)** · 대상: §2-2, §4, §5

이 기능의 존재 이유(도입부 다이어그램: orders는 복제되는데 참조 대상 customers가 복제 제외라 failover 후 FK가 깨짐)를 스펙이 스스로 뚫는 가장 심각한 컨셉 결함이다. §5는 FK를 **생성/추가하는 시점**에만 참조 대상이 복제 대상인지 검사한다. 반면 §2-2는 "OFF→ON 전환 금지"라는 한 방향만 규정하고, 반대 방향인 "이미 FK로 참조받는 ON 테이블을 OFF로 내리는 것"은 아무 규칙이 없어 예시 6("ALTER ... REPLICATION=OFF → OK")대로 통과한다. §7 검사는 HA 재시작 시점에만 동작하므로, HA를 계속 켜둔 채 운영하면 다음 재시작 전까지 위반이 감지되지 않는다.

**대표 예제** (거의 모든 리뷰가 동일 형태로 제시):
```sql
-- 예시 17과 동일한 정상 구성 (둘 다 REPLICATION=ON), HA 운영 중
CREATE TABLE customers(customer_id INT PRIMARY KEY, country INT);
CREATE TABLE orders(order_id INT PRIMARY KEY, customer_id INT,
  CONSTRAINT fk FOREIGN KEY(customer_id) REFERENCES customers(customer_id));

ALTER TABLE customers REPLICATION=OFF;   -- 이를 막는 규칙이 스펙에 없음 → OK로 읽힘
-- 이 순간부터 orders(ON)는 복제되지만 customers(OFF)는 복제 안 됨.
-- Failover → 슬레이브에 orders만 있고 customers 데이터 없음 = 도입부 다이어그램 그대로 재현
```

**권고**: `ALTER TABLE ... REPLICATION=OFF` 실행 시, 그 테이블을 참조하는 FK가 있는 복제 대상 테이블이 하나라도 있으면 에러로 차단한다(예시 18의 대칭 규칙). §5의 검사를 "생성 시점"이 아니라 "불변식(항상 유지)"으로 재정의한다.

> **코드 대조 (2026-08-23, feature/CBRD-26246-develop @44468ed73)**: **기각** — ALTER ... REPLICATION 변경은 HA 모드에서 do_alter_change_replication이 !HA_DISABLED()이면 방향 불문 ER_HA_REPLICATION_OPTION_CHANGE_NOT_ALLOWED로 전면 차단 → 이슈가 전제한 'HA 운영 중 ALTER customers REPLICATION=OFF 통과(예시6)'는 성립 불가. reverse-FK 무검사 자체는 사실이나 OFF 전환은 단일모드에서만 가능하고 그 위반은 HA 기동 시 rkcheck가 전 클래스 순회(util_cs.c:3322,3349)로 잡음. (근거: src/query/execute_schema.c:11740-11745)

#### C-3. 현재 RK가 무엇인지 조회할 방법이 없다

**합의도: ~18/20** · 대상: §2-3 (예시 8·9)

`show create table`과 `select * from db_class`는 REPLICATION ON/OFF 여부만 보여줄 뿐, PK/UK가 여러 개일 때 **엔진이 실제로 무엇을 RK로 골랐는지**는 출력하지 않는다. RK는 사용자가 수정할 수 없고(§4-2) 자동으로 바뀔 수도 있는 값인데(C-1), 그 결과를 확인할 수단이 없다. 그 결과 사용자는 §4-2의 제약(RK로 쓰이는 UK는 삭제 불가 등)에 걸릴지 아닐지를 **DDL을 실행해 에러가 나야만** 알게 된다. 장애 디버깅(관측성), 배포 사전검증(응용), 스키마 감사(엔진 리뷰의 규제산업 관점) 모두 이 정보에 의존한다.

**대표 예제**:
```sql
CREATE TABLE t(a INT NOT NULL UNIQUE, b INT NOT NULL UNIQUE);  -- PK 없음, UK 2개
show create table t;      -- 'REPLICATION ON' 만 보임. a와 b 중 무엇이 RK인지 안 나옴
select * from db_class where class_name='t';  -- replication: ON 만 있음
```

**예상 시나리오**
1. (전제) HA 운영 중. 테이블 t는 PK 없이 NOT NULL UNIQUE 컬럼 a, b 두 개. 엔진이 둘 중 하나를 복제 키로 자동 선택했지만(§1), 어느 것을 골랐는지 조회할 수단이 없다.
2. (조작) 운영자가 스키마 정리 작업으로 a 컬럼의 UNIQUE 제약을 지우려 한다. 사전에 `show create table t`와 `db_class`를 확인했지만 `REPLICATION ON`만 보이고 a가 복제 키인지는 나오지 않아, 그냥 삭제 DDL을 실행한다.
3. (예상 결과) 만약 a가 실제 복제 키였다면 이 DDL은 §4-2 예시 15 규칙("복제 키로 쓰는 UNIQUE는 삭제 불가")에 걸려 ERROR로 거부된다. 운영자는 DDL을 실제로 실행해 에러가 나야만 a가 복제 키였음을 뒤늦게 알게 된다.
4. (사용자 증상) 배포 스크립트가 이 지점에서 처음 멈춘다. 사전 점검이나 스키마 감사 단계에서는 위험을 미리 알 방법이 없어, 위험이 항상 운영 반영 시점의 예기치 못한 실패로 나타난다.

**권고**: `db_class`(또는 신규 시스템 뷰 `db_replication_key`)에 RK로 선택된 제약명·컬럼 목록·RK 후보 개수 컬럼을 추가하고, `show create table` 출력에도 `REPLICATION ON (RK: pk_t_a)` 형태로 표기한다.

#### C-4. §7 "파일 리스트"의 정체·포맷·exit code 미정의

**합의도: ~18/20** · 대상: §7

"제약사항 위반 시 에러와함께 파일 리스트를 출력한다" — (1) "파일"이 위반 테이블 목록인지, OS 파일 경로인지, 로그 파일인지 불명확하고(CUBRID에서 위반 단위는 테이블이지 파일이 아님), (2) 출력 매체(표준에러/로그파일), 위반 사유 구분(RK 없음 vs FK 참조 위반), 개수 제한, exit code가 전혀 정의되지 않았다. 신입 운영자는 새벽 장애 시 무엇을 봐야 할지 모르고, 자동화 스크립트는 성공/실패를 문자열 grep으로 추측해야 하며, 대량 위반 시(수백~수천 테이블) 콘솔 한 번 출력으로는 처리 불가능하다.

**대표 예제** (DB엔지니어 3년차):
```bash
$ cubrid hb start testdb
ERROR: replication constraint violation
tbl_a
tbl_b
$ echo $?   # 0인가 1인가? 스펙에 없음 → HA가 안 떴는데도 트래픽이 전환되는 사고 가능
```

**예상 시나리오**
1. (전제) 신버전으로 교체한 HA 클러스터. 복제 테이블 여러 개에 복제 키가 없어 §7 검사에 걸리는 상태다. 장애 대응 자동화 스크립트가 `cubrid hb start`의 성공/실패로 트래픽 전환 여부를 결정한다.
2. (조작) 새벽에 스크립트가 슬레이브를 승격시키려 `cubrid hb start`를 실행하고, 반환된 exit code로 성공 여부를 판정한다.
3. (예상 결과) 제약 위반으로 HA는 실제로는 기동되지 않았지만, exit code 규약이 스펙에 없어(스펙 미정의라 가정) 스크립트가 0(성공)으로 오판할 수 있다. 위반 테이블 목록은 콘솔에 텍스트로만 찍혀 스크립트가 구조적으로 파싱하지 못한다.
4. (사용자 증상) HA가 뜨지 않은 노드로 트래픽이 넘어가 서비스가 중단된다. 운영자는 콘솔 로그의 테이블 이름을 눈으로 훑어야 하고, 위반이 수백 개면 원인 테이블을 추려 내는 데만 한참이 걸린다.

**권고**: "파일 리스트"→"위반 테이블 목록(스키마.테이블명 + 위반 사유 코드)"으로 정정, 기계 판독 가능한 포맷과 실패 시 비정상 exit code를 명시.

#### C-5. §8 vs §9 기본값 정면 모순 (표시 없음 = ON vs OFF)

**합의도: ~10/20 (PM·DBA·사용자·엔진; 문서 대조가 업무인 직군에서 집중 포착)** · 대상: §8, §9

- §8: "복제 여부를 저장하는 변수가 설정되어 있지 않다면 **복제 대상(Default)**으로 간주" + "하위 버전 unload 파일은 load 시 **모두 복제 테이블로** 설정"
- §9: "UNLOADDB 시 ... 이를 포함하지 않는 테이블은 **모두 복제 제외 테이블**이다"

같은 조건에 정반대 결과. §8이 두 번 반복 서술하므로 §9가 오기일 가능성이 높지만, 문서만으로는 확정 불가.

**대표 예제**:

```
구버전 unload 파일(REPLICATION 필드 없음)을 신버전 loaddb

 - §9 적용: orders → REPLICATION=OFF (조용히 복제에서 빠져 마스터/슬레이브 불일치)
```

**권고**: 담당 엔지니어에게 의도 확인 후 한쪽으로 통일. "기본값 정책"을 §1의 표 하나에만 정의하고 §8/§9는 참조만.

#### C-6. 기존 클러스터 업그레이드 / 롤링 업그레이드 / 카탈로그 마이그레이션 경로 부재

#### C-7. 복합 ALTER(예시 13)의 원자성·중간 상태·동시 DML 처리 미정의

**합의도: ~14/20 (사용자·응용·엔진 집중)** · 대상: §2-2 예시 7, §4-2 예시 13

예시 13(`DROP CONSTRAINT PRIMARY KEY, ADD CONSTRAINT PRIMARY KEY(a)`)은 "OK"만 보여준다. 그런데 (1) 이 문장이 원자적으로 처리되는지, 아니면 DROP 후 ADD 사이에 "RK 0개" 상태를 거치는지, (2) 그 찰나에 동시 세션이 DML을 실행하면 복제 로그가 어느 RK 기준으로 기록되는지, (3) ADD가 실패하면 DROP까지 롤백되는지가 전혀 없다. 이는 스펙 내부 모순으로도 이어진다 — 절 단위 순차 검증이라면 DROP 직후 RK 0개가 되어 예시 13은 항상 실패해야 하는데 스펙은 OK라고 한다. 즉 "문장 전체 최종 상태 기준 검증 + 원자성"을 전제해야만 예시 13이 성립하는데, 그 전제가 문서에 없다.

**대표 예제** (엔진 5년차):
```sql
-- table_name.a 컬럼에 이미 중복값이 있는 상태
ALTER TABLE table_name DROP CONSTRAINT PRIMARY KEY, ADD CONSTRAINT PRIMARY KEY(a);
-- ADD 단계 실패 시 DROP은 롤백되는가? 그 사이 복제 로그에 무엇이 남았는가?
```

**예상 시나리오**
1. (전제) HA 운영 중. 복제 테이블 table_name은 복제 키가 PK 하나뿐이고, a 컬럼에는 이미 중복 값이 들어 있다.
2. (조작) 운영자가 예시 13처럼 한 문장으로 PK를 지우고 a로 새 PK를 만든다(`DROP CONSTRAINT PRIMARY KEY, ADD CONSTRAINT PRIMARY KEY(a)`). 동시에 다른 세션이 같은 테이블에 INSERT/UPDATE를 실행하고 있다.
3. (예상 결과) 문장 처리가 절 단위 순차라면 DROP 직후 복제 키가 0개인 순간이 생기고, ADD는 a의 중복 값 때문에 실패한다. 이때 DROP까지 되돌려지는지, 그 찰나에 들어온 동시 DML이 어느 키를 기준으로 복제 로그에 남는지가 스펙에 없다(스펙 미정의라 가정).
4. (사용자 증상) 되돌림이 보장되지 않으면 테이블이 복제 키 없는 상태로 남아 이후 변경이 슬레이브에 반영되지 않거나, 다음 HA 재시작이 §7 검사로 거부된다. 동시 DML이 옛 키 기준으로 기록됐다면 슬레이브가 대상 행을 찾지 못해 마스터와 슬레이브가 어긋난다.

**권고**: "쉼표로 연결된 다중 ALTER 절은 하나의 원자적 트랜잭션·단일 복제 로그 레코드로 처리하며, 최종 상태 기준으로 RK 제약을 검증하고, 일부 절 실패 시 전체 롤백한다. RK 변경 DDL은 테이블 배타 스키마 잠금을 잡아 동시 DML을 대기시킨다"를 §4-2에 명시.

> **코드 대조 (2026-08-23, feature/CBRD-26246-develop @44468ed73)**: **기각** — 다중 절 ALTER는 MULTIPLE_ALTER 세이브포인트로 감싸(1844) 실패 시 error_exit에서 전체 롤백하고(2080), RK 제약 검사는 모든 절 처리가 끝난 뒤 최종 상태 기준으로 1회 수행(2051-2068)하므로 DROP PK+ADD PK(a)는 중간 RK 0개 상태로 실패하지 않고 최종 상태로 검증된다 — 원자성·롤백·최종상태검증이 코드로 구현되어 예시13 모순이 해소됨(스펙 문서만 미기술). (근거: src/query/execute_schema.c:1844,2051-2068,2080)

#### C-8. RK 전환 DDL과 복제 로그의 순서·정합성 미정의

**합의도: ~9/20 (엔진 전 연차 + PM 5년차 + 사용자·DBA 일부)** · 대상: §4-2, 복제 로그 포맷

복제 로그는 커밋 순서(LSA)대로 슬레이브에 적용되는데, RK를 바꾸는 DDL이 커밋되기 전 옛 RK 기준으로 기록된 DML 로그가 슬레이브에 아직 적용되지 않고 큐에 남아 있을 수 있다. DDL이 먼저 적용되어 슬레이브 카탈로그의 RK가 바뀐 뒤 옛 RK 기준 로그가 도착하면, applylogdb가 어떤 컬럼으로 대상 행을 찾을지 정의가 없다. 특히 복제 지연(lag)이 있거나 병렬 적용(사내 논의 중)이면 순서 보장이 더 취약하다. 복제 로그가 RK를 컬럼 참조로만 담는지, 값 스냅샷·스키마 버전 태그를 함께 담는지도 불명확하다.

**대표 예제** (엔진 1년차):
```
T1(마스터): UPDATE tbl SET c=100 WHERE a=5;   -- RK=a 기준으로 로그 기록
T2(마스터): ALTER ... RK를 a→a2로 교체
슬레이브 도착 순서: (1) ALTER 먼저 적용(RK=a2) → (2) "a=5" UPDATE 뒤늦게 도착
→ RK가 a2로 바뀐 슬레이브에서 "a=5" 조건을 어떻게 처리하나?
```

**예상 시나리오**
1. (전제) HA 운영 중이며 슬레이브에 복제 지연이 있어 아직 적용하지 못한 로그가 큐에 쌓여 있다. 테이블 tbl의 복제 키는 a다.
2. (조작) 마스터에서 먼저 `UPDATE tbl SET c=100 WHERE a=5`가 커밋되고(옛 키 a 기준으로 로그 기록), 곧이어 복제 키를 a에서 a2로 바꾸는 ALTER가 커밋된다.
3. (예상 결과) 슬레이브에는 DDL(ALTER)이 먼저 적용되어 카탈로그의 복제 키가 a2로 바뀐 뒤, 뒤늦게 도착한 "a=5" UPDATE 로그가 적용을 시도한다. 슬레이브가 a2를 식별자로 기대하면 a 값만으로는 대상 행을 찾지 못한다. applylogdb가 이를 어떻게 처리할지 스펙에 없어(스펙 미정의라 가정), 대상 행을 못 찾아 조용히 건너뛸 가능성이 크다.
4. (사용자 증상) 마스터의 `c=100` 변경이 슬레이브에서 누락되어 두 노드가 어긋난다. 위반이 조용한 건너뜀이라 로그에도 뚜렷한 에러가 남지 않아, Failover 후에야 값 불일치로 발견된다. 병렬 적용 경로에서는 순서 보장이 더 취약해 재현 빈도가 높아진다.

**권고**: RK 변경 DDL을 배리어(barrier)로 취급 — 그 이전 모든 DML이 슬레이브에 적용 완료된 뒤에만 활성화. 복제 로그 레코드에 RK 스키마 버전을 함께 기록. 병렬 적용 경로에서도 이 순서를 강제.

> **코드 대조 (2026-08-23, feature/CBRD-26246-develop @44468ed73)**: **기각** — 슬레이브는 LOG COMMIT 시점에 커밋(LSA)순으로 단일 스레드 직렬 적용하므로 T2(ALTER, 나중 커밋)가 T1(옛 RK UPDATE, 먼저 커밋)보다 먼저 적용되는 재정렬 자체가 발생하지 않는다. 또한 복제 로그는 RK 컬럼 참조가 아니라 갱신 전 RK 값 스냅샷(repl_old_key=old_key clone)을 담는다. 배리어 우려는 커밋순 직렬 적용으로 이미 충족(병렬 적용은 본 브랜치 밖). #### C-9. NOT NULL 해제·컬럼 타입 변경 등 "열거되지 않은 경로"로 RK 자격 조용히 상실

**합의도: ~7/20 (PM·DBA·응용·엔진; 원래 배경 버그와 직결)** · 대상: §4-2

§4-2는 UK를 RK로 쓸 때 "UNIQUE 제약 삭제"와 "컬럼 삭제"(예시 15)만 막는다. 그런데 RK 자격은 "**NOT NULL** UNIQUE"이므로, UNIQUE는 그대로 두고 `ALTER TABLE ... MODIFY COLUMN a INT NULL`로 NOT NULL만 풀어도 RK 자격이 사라진다. 또 RK 컬럼 타입을 `INT → BIGINT`로 바꾸는 흔한 작업(정작 원래 배경 버그인 "PK 컬럼 속성 변경"과 정확히 같은 유형)도 §4-2에 없다. 열거식 차단이라 우회로가 남고, "HA 복제 대상은 항상 RK를 가진다"는 §1 불변식이 실제로는 보장되지 않는다.

**대표 예제**:
```sql
CREATE TABLE tbl(a INT, b INT NOT NULL UNIQUE);  -- RK = b
ALTER TABLE tbl MODIFY COLUMN b INT NULL;        -- UNIQUE는 유지, NOT NULL만 제거
-- 스펙 어느 규칙에도 안 걸림. b는 이제 RK 자격 상실 → 운영 중 RK 없는 복제 테이블 발생
```

**예상 시나리오**
1. (전제) HA 운영 중. 테이블 tbl은 PK가 없고 b가 NOT NULL UNIQUE라 b가 복제 키다.
2. (조작) 운영자가 UNIQUE 제약은 그대로 둔 채 NOT NULL만 푼다(`ALTER TABLE tbl MODIFY COLUMN b INT NULL`). §4-2는 UNIQUE 삭제와 컬럼 삭제만 막으므로, 이 문장은 어느 규칙에도 걸리지 않고 통과한다.
3. (예상 결과) b는 "NOT NULL UNIQUE"라는 복제 키 자격을 잃는다. 다른 후보가 없으면 복제 키가 0개가 되지만, HA는 이미 켜져 있고 §7 검사는 HA 기동 시점에만 도므로 재시작 전까지는 위반이 감지되지 않는다.
4. (사용자 증상) 이후 이 테이블의 변경이 슬레이브에 제대로 반영되지 않거나(식별자 부재), 다음 HA 재시작에서 갑자기 기동이 거부된다. 배경 장애였던 "PK 컬럼 속성 변경으로 인한 복제 누락"과 사실상 같은 현상이 다른 경로로 재발한다.

**권고**: "RK 자격에 영향을 주는 모든 DDL 경로(제약 삭제·컬럼 삭제·NOT NULL 해제·타입 변경 등)를 전수 조사해 §4-2에 포함하고, 열거되지 않은 경로는 기본 차단"을 원칙으로 선언.

> **코드 대조 (2026-08-23, feature/CBRD-26246-develop @44468ed73)**: **확정** — RK 재검사 게이트 IS_REPL_CONSTRAINT_RELATED_ALTER는 PT_ADD_ATTR_MTHD/PT_DROP_ATTR_MTHD/PT_DROP_CONSTRAINT/PT_DROP_PRIMARY_CLAUSE만 트리거하고, MODIFY/CHANGE COLUMN 경로(PT_CHANGE_ATTR, execute_schema.c:2020)는 목록에 없어 NOT NULL 해제(MODIFY b INT NULL)나 타입 변경 시 check_ha_repl_constraint가 호출되지 않는다. 게다가 게이트가 crt_clause가 아닌 alter->info.alter.code(첫 절)만 보므로 후순위 절의 제약 변경도 누락될 수 있다 — 검사가 있어야 할 자리(2051)에 해당 경로가 빠짐. (근거: src/query/execute_schema.c:109-114(매크로),2051(게이트))

#### M-1. §4-2 "복제키 후보" 용어 미정의 + "모든 DDL 허용(단 기존 제약 유지)"이 예시 12와 모순

**합의도: ~14/20** · 대상: §4-2

§1은 단수 "복제 키"만 설명하다가 §4-2에서 갑자기 "복제키 후보"를 정의 없이 쓴다. "후보 = PK 하나 + 모든 UK"인지, "현재 RK를 제외한 나머지"인지 불명확해 카운팅 로직을 구현할 수 없다. 게다가 본문 "다른 복제키 후보가 함께 존재한다면 모든 DDL은 허용된다"와 예시 12("PK가 복제키면 무조건 삭제 불가")가 PK+UK 공존 테이블에서 정반대 결론(OK vs ERROR)을 낸다. 또 "기존의 제약사항은 유지된다"의 "기존"이 무엇을 가리키는지, 검증 시점이 DDL 실행 전 상태인지 후 상태인지도 없다.

**대표 예제**:
```sql
CREATE TABLE tbl(a INT PRIMARY KEY, b INT NOT NULL UNIQUE, c INT);
ALTER TABLE tbl DROP PRIMARY KEY;
-- 본문("다른 후보 b 있음 → 허용") → OK / 예시12("PK는 삭제 불가") → ERROR. 어느 쪽?
```

**권고**: §1에 "복제키 후보"를 정식 정의하고, "검증은 문장 전체 적용 후 최종 상태 기준"임을 명시, 예시 11~16 각각에 "이 테이블은 후보 N개" 전제를 표기.

> **코드 대조 (2026-08-23, feature/CBRD-26246-develop @44468ed73)**: **코드무관** — '복제키 후보' 용어 미정의·본문vs예시12 모순은 스펙 문서 결함이라 코드 대조로 해소 불가. 참고로 코드는 구체 규칙을 구현(IS_HA_REPLICATION_KEY_CONSTRAINT = PK 또는 NOT NULL UNIQUE 존재)하며, 다른 RK 후보가 있으면 DROP PK를 허용해 본문 해석을 따르므로 예시12('PK 무조건 삭제 불가')와 배치된다 — 문서 개정에서 처리할 사안. #### M-2. 뷰(§6)와 FK(§5)의 검증 강도 불일치 — VIEW는 경고조차 없음

**합의도: ~12/20 (사용자·응용에서 특히 강함)** · 대상: §5, §6

동일한 근본 위험("복제 제외 테이블의 부재 데이터에 의존")인데 FK는 생성 시점 하드 에러(예시 18)로 막고, VIEW는 아무 검사 없이 통과시킨 뒤 "책임지지 않는다"로 끝낸다. VIEW는 SQL 에러도 없이 failover 후 "조용히 축소된 결과"(예: LEFT JOIN에서 country가 전부 NULL)를 반환해 오히려 더 위험하다 — 리포팅·대시보드가 잘못된 숫자를 사용자에게 보여준다.

**대표 예제** (응용 10년차):
```sql
CREATE TABLE customers(...) REPLICATION=OFF;
CREATE VIEW order_summary AS SELECT o.order_id, c.country FROM orders o LEFT JOIN customers c ON ...;
-- CREATE VIEW: 경고 없이 OK. Failover 후 SELECT: 에러 없이 country 전부 NULL
```

**권고**: 최소한 `CREATE/ALTER VIEW` 시 복제 제외 테이블 참조를 감지해 WARNING 출력. FK와 정책 차이가 의도라면 그 근거를 문서화.

> **코드 대조 (2026-08-23, feature/CBRD-26246-develop @44468ed73)**: **확정** — CREATE VIEW(PT_VCLASS) 경로에는 복제 검사 호출이 전혀 없다 — check_ha_repl_constraint는 PT_CLASS 브랜치(10267)에서만 불린다. HA 기동 rkcheck도 util_cs.c:2943에서 vclass(is_vclass>0)를 명시적으로 skip한다(CBRD-26607). 즉 REPLICATION=OFF 테이블을 참조하는 뷰는 생성/기동 어느 시점에도 경고·에러가 없다. 이슈 지적대로 구멍 확인. (근거: src/query/execute_schema.c:10188-10209 (PT_VCLASS branch), :10267-10274 (check_ha_repl_constraint only in PT_CLASS); src/executables/util_cs.c:2943)

#### M-3. PostgreSQL REPLICA IDENTITY 대비 사용자 명시 지정·FULL 폴백 없음 (경쟁·유연성 열위)

**합의도: ~10/20 (PM·엔진·응용 상위 연차)** · 대상: 배경, §1

PostgreSQL은 `DEFAULT`/`USING INDEX`(사용자 지정)/`FULL`(전 컬럼)/`NOTHING` 네 모드를 제공하는데, 이 스펙은 "엔진 자동 선택"만 채용하고 사용자 지정 수단(`USING INDEX` 상당)을 뺐다. UK가 여럿일 때 값이 안 바뀌는 안정적 키를 RK로 강제하고 싶어도 방법이 없다. 또 PK/UK가 없으면 `FULL` 같은 "느려도 복제는 됨" 폴백 없이 오직 "복제 포기(OFF)"뿐이라, MySQL 대비 성능은 얻었지만 유연성은 더 낮아졌다. 엔진·PM 리뷰는 "왜 폴백/명시지정을 뺐는지 근거를 남기지 않으면 향후 재설계 비용이 크다"고 지적.

**대표 예제**:
```sql
-- PostgreSQL: ALTER TABLE t REPLICA IDENTITY USING INDEX t_stable_key;  (명시 지정 가능)
-- 이 스펙: 대응 문법 없음. 순서를 조작하거나 다른 UK를 다 지우는 우회뿐
```

**권고**: 로드맵에 명시 지정 문법(`REPLICATION KEY USING (...)`) 검토를 명기하고, 이번 릴리스에서 폴백을 뺀 설계 근거를 스펙에 한 문단 추가.

> **코드 대조 (2026-08-23, feature/CBRD-26246-develop @44468ed73)**: **코드무관** — 문법상 REPLICATION 옵션은 ON/OFF 두 값뿐이며 REPLICA IDENTITY USING INDEX 상당의 사용자 RK 지정 구문이나 FULL 폴백은 아예 없다(RK는 PK>UK 자동선택). 다만 이는 스펙이 의도적으로 자동선택만 채택한 설계 선택에 대한 로드맵·경쟁포지셔닝 권고로, 코드 결함이 아니라 문서/설계 근거 보강 요청이다. 코드는 이슈의 사실 전제(사용자 지정 구문 부재)를 뒷받침한다. (근거: src/parser/csql_grammar.y:19890-19998 (class_replication_spec / opt_replication_option은 ON|OFF만 파싱))

#### M-4. 개발/스테이징(싱글)에서 통과한 DDL이 운영(HA)에서만 실패 — 사전점검(dry-run) 도구 부재

**합의도: ~10/20 (응용·DBA 집중)** · 대상: §3, §4, §7

§3은 싱글 모드에 RK 제약이 "없다"고 하고, 검사는 §7(HA 기동 시점)에만 걸린다. CI가 싱글 스테이징에서 통과시킨 마이그레이션이 운영 HA 배포 시점에 처음 실패한다(dev/prod parity 붕괴). Flyway/Liquibase 이력 테이블과 실제 스키마가 어긋나는 부분 적용 문제도 파생된다.

**대표 예제** (응용 3년차):
```sql
-- 로컬/스테이징(싱글): ALTER TABLE customers DROP CONSTRAINT u_customers_email;  → OK
-- 운영(HA): 같은 문장 → ERROR (email UK가 유일 RK였다면, 예시 15)
```

**예상 시나리오**
1. (전제) 애플리케이션 팀이 싱글 모드 스테이징에서 스키마 마이그레이션을 검증한다. 대상 테이블 customers는 email UK가 유일한 복제 키이며, 싱글 모드에는 복제 키 제약이 없다(§3).
2. (조작) CI 파이프라인이 스테이징에서 `ALTER TABLE customers DROP CONSTRAINT u_customers_email`을 실행한다. 제약이 없어 통과하고, 파이프라인은 초록불로 운영 배포를 승인한다.
3. (예상 결과) 같은 문장을 운영 HA에 적용하면 email이 유일 복제 키였으므로 §4-2 예시 15 규칙에 걸려 ERROR로 거부된다. 검사가 HA 운영·기동 시점에만 걸리므로(§4·§7) 스테이징에서는 결코 드러나지 않는다.
4. (사용자 증상) 마이그레이션이 운영 배포 도중에야 처음 실패한다. 여러 문장 중 일부만 적용된 채 멈추면 Flyway·Liquibase 같은 도구의 이력과 실제 스키마가 어긋나, 되돌리거나 다시 적용하기가 까다로워진다.

**권고**: `cubrid hb check --dry-run` 또는 싱글 모드용 `--strict-ha` 시뮬레이션 제공. 문서에 "싱글 통과 ≠ HA 통과" 경고 명시.

> **코드 대조 (2026-08-23, feature/CBRD-26246-develop @44468ed73)**: **기각** — 싱글모드가 RK 검사를 건너뛴다는 전제는 코드로 확인됨(HA_DISABLED 가드). 그러나 이슈가 요구한 사전점검(dry-run) 도구는 rkcheck로 존재 — 스테이징 DB에 마이그레이션 적용 후 cubrid rkcheck로 RK 없는 복제테이블을 운영 전에 잡을 수 있음. '도구 부재' 주장이 거짓이라 기각(잔여 parity는 의도된 설계 트레이드오프). #### M-5. REPLICATION=OFF↔ON 전환 시 슬레이브 데이터 처리·재동기화 방침 없음, HA중 OFF→ON 금지 근거 없음

**합의도: ~10/20** · 대상: §2-2, §4

(a) ON→OFF 전환 시 슬레이브에 이미 쌓인 데이터가 삭제되는지 "박제된 옛 스냅샷"으로 남는지 없음(stale read 위험). (b) OFF→ON은 HA 중 아예 금지인데(예시 5), 그렇다면 그동안 마스터에만 쌓인 데이터를 슬레이브에 어떻게 최초 동기화하는지 절차가 없다. (c) OFF→ON 금지의 "근거"(초기 스냅샷 부재로 추정)가 명시되지 않아 의도된 제약인지 불명. 응용 리뷰들은 "일단 OFF로 벌크 적재 후 ON" 및 "점진적 롤아웃" 패턴이 운영 중 봉쇄된다고 지적.

**대표 예제**:
```sql
ALTER TABLE big_orders REPLICATION=OFF;  -- 한 달간 500만건 INSERT (슬레이브 미반영)
ALTER TABLE big_orders REPLICATION=ON;   -- 예시5: HA에서 ERROR. 과거분은 영영 갭으로 남나?
```

**예상 시나리오**
1. (전제) HA 운영 중. big_orders는 복제 테이블(REPLICATION=ON)이다.
2. (조작) 운영자가 대량 적재 성능을 위해 `ALTER TABLE big_orders REPLICATION=OFF`로 복제를 끄고 한 달간 500만 건을 INSERT한 뒤, 다시 `REPLICATION=ON`으로 되돌리려 한다.
3. (예상 결과) OFF 구간 동안 슬레이브에는 이 500만 건이 반영되지 않는다. 되돌리는 `ALTER ... REPLICATION=ON`은 HA 모드에서 금지되어(예시 5) ERROR로 거부된다. OFF→ON 전환 시 그동안 마스터에만 쌓인 데이터를 슬레이브에 처음으로 맞춰 넣는 절차가 스펙에 없다(스펙 미정의라 가정).
4. (사용자 증상) 복제를 다시 켤 방법이 없어 운영 중에는 되돌리지 못한다. 억지로 되돌리더라도 과거 500만 건은 슬레이브에 영영 빈 구간으로 남아, Failover 후 그만큼의 데이터가 사라진 것처럼 보인다.

**권고**: 전환 시 슬레이브 데이터 처리(유지/TRUNCATE)를 명시, OFF→ON 시 재동기화 공식 절차 제공, 금지 근거를 문서화.

> **코드 대조 (2026-08-23, feature/CBRD-26246-develop @44468ed73)**: **코드무관** — 전환 시 데이터 처리 방침·재동기화 절차·금지 근거 문서화 요구는 스펙/운영문서가 채울 사항이라 코드 대조 대상이 아니다. 참고로 코드상 HA 중에는 OFF→ON뿐 아니라 ON→OFF까지 REPLICATION 옵션 변경이 전면 금지되어, '슬레이브 stale/gap' 같은 HA중 전환 시나리오는 이 경로로 발생하지 않음(전환은 HA 해제 상태에서만, 재동기화는 HA 재구성 절차). (근거: src/query/execute_schema.c:11740-11745 (do_alter_change_replication: !HA_DISABLED()면 ER_HA_REPLICATION_OPTION_CHANGE_NOT_ALLOWED로 전면 차단))

#### M-7. 복제 제외 테이블 전수 조회 수단 없음 + 업그레이드 후 대량 위반 일괄정비 도구 없음

#### M-8. 다단계/자기참조/순환 FK, 복합키 RK, FK-UK 겸용 컬럼의 검증 규칙 부재

#### M-9. 멀티 슬레이브·체인 복제 확장성 — 테이블 전역 플래그의 한계

**합의도: ~6/20 (PM·엔진 상위 연차)** · 대상: 컨셉 전체

REPLICATION은 테이블당 값 하나인 전역 속성이라 "슬레이브 A(DR)에는 전체, 슬레이브 B(분석용)에는 PII 제외" 같은 슬레이브별 차등 복제를 표현할 수 없다. RK 계산이 노드별 로컬 재계산이면 체인 복제·지연 구간에서 노드마다 RK가 어긋날 수 있다.

**권고**: 최소한 "이번 범위는 테이블 단위 전역 복제 여부만이며 슬레이브별 차등·컬럼 단위 필터는 out of scope"라고 스코프를 명시.

> **코드 대조 (2026-08-23, feature/CBRD-26246-develop @44468ed73)**: **코드무관** — 복제 여부가 클래스 단위 단일 비트라 슬레이브별 차등 복제를 표현 못 한다는 관찰은 코드상 사실이나(단일 플래그 확인), 스펙이 요구한 기능이 아니며 권고 자체가 'out-of-scope 스코프 명시'라는 문서 조치 — 코드 결함 대조 대상 아님. RK는 노드별로 동일 스키마에서 계산되므로 노드 간 RK 어긋남 전제는 성립 안 함. (근거: src/object/class_object.h:312 (SM_CLASSFLAG_DATA_REPLICATION_OFF = 32, 클래스 단위 단일 플래그))

#### M-10. REPLICATION 옵션 변경의 락·성능 영향, in-place 여부 미정의

**합의도: ~5/20 (PM·엔진)** · 대상: §2-2, §4

`ALTER TABLE ... REPLICATION=OFF`가 메타데이터 전용 O(1) 연산인지, 대용량 테이블에서 락을 얼마나 오래 잡는지 없다. 대량 이관 시 여러 테이블을 일괄 전환하는 스크립트의 서비스 영향을 평가할 수 없다.

**권고**: 옵션 변경이 메타데이터 전용임을 명시(아니면 소요 시간·락 범위 문서화).

> **코드 대조 (2026-08-23, feature/CBRD-26246-develop @44468ed73)**: **코드무관** — 코드가 사실을 확정해준다: 옵션 변경은 dbt_edit_class → sm_set_class_flag(SM_CLASSFLAG_DATA_REPLICATION_OFF) → dbt_finish_class 로 이뤄지는 메타데이터 전용 플래그 플립이며 heap 재구성·행 스캔이 없다(사실상 O(1)). 클래스 배타락(locator_fetch_class DB_FETCH_WRITE)만 잡는다. '대용량 테이블에서 락을 오래 잡을 수 있다'는 함의는 코드상 성립하지 않는다. 남는 것은 스펙에 '메타데이터 전용'임을 명시하라는 문서 보강 요청. (근거: src/query/execute_schema.c:11730-11840 (do_alter_change_replication))

- **N-7. REPLICATION 표기 3종 혼용**(`REPLICATION=ON` / `REPLICATION ON` / `replication : ON`), OFF일 때 `show create table` 예시 없음 (~5).
  - ↳ **코드 대조**: **코드무관** — 실제 show create table 출력은 등호 포함 'REPLICATION=ON'이라, 예시 8의 'REPLICATION ON'(등호 없음)이 오히려 실동작과 불일치. 표기 3종 혼용·OFF 예시 부재는 스펙 문서 정리 사항이며 기능 코드 결함은 아님. (근거: src/object/object_printer.cpp:1138-1144 (show create table 출력 = 'REPLICATION=ON'/'REPLICATION=OFF'))
- **N-8. 컬럼 단위 복제 제외(PII 마스킹) 요구 미지원** (응용 5년차 고유, ~2).
  - ↳ **코드 대조**: **코드무관** — 컬럼 단위 복제 제외(PII 마스킹)는 스펙 요구사항이 아니고 복제 플래그가 테이블 단위라 미지원인 것이 설계상 사실 — 권고가 '스코프 선언'이라 코드 결함이 아닌 문서/범위 이슈. (근거: src/object/class_object.h:312 (복제 on/off가 클래스 단위 플래그, 컬럼 단위 아님))
- **N-9. 읽기/쓰기 분리 아키텍처에서 OFF 테이블이 슬레이브로 라우팅되면 조용히 빈 결과** (응용 5년차 고유, ~1).
  - ↳ **코드 대조**: **코드무관** — OFF 테이블을 읽기 분리 아키텍처가 슬레이브로 라우팅하면 stale/빈 결과가 나오는 것은 OFF의 정의된 동작(데이터 미복제)의 정상 귀결이자 애플리케이션 라우팅 문제 — 엔진이 막거나 검사할 지점이 없고 권고도 운영 가이드/문서 조치라 코드 대조 대상 아님. (근거: src/object/class_object.h:312 (OFF=class data 미복제, schema는 복제))
- **N-10. FK 강제복제가 정적 코드 테이블 OFF 설계를 봉쇄**(무결성 vs 비용 이분법) (응용, ~3).
  - ↳ **코드 대조**: **코드무관** — '복제 대상 FK는 참조 테이블도 복제 대상이어야 함'은 check_ha_repl_fk_ref_all_replicated로 의도적으로 강제되는 설계 제약이며 코드가 그대로 구현. 정적 코드테이블 OFF 봉쇄는 결함이 아니라 무결성 우선 설계 트레이드오프에 대한 개념적 비판 → 코드 리뷰로 승격할 구멍 없음. (근거: src/query/execute_schema.c:9874-9878)
- **N-11. DROP TABLE 후 동일명 재생성으로 OFF→ON 금지 우회** (응용 5년차, ~1).
  - ↳ **코드 대조**: **판정불가** — ALTER OFF→ON은 HA에서 차단되지만 HA 모드에서 CREATE REPLICATION=ON은 RK/FK 검사만 통과하면 허용되고 이전 DROP과 연계하는 코드가 없어 DROP 후 동일명 ON 재생성으로 금지를 기계적 우회 가능은 코드상 확인됨. 다만 새 테이블은 빈 테이블이고 DROP/CREATE DDL이 모두 복제되므로 실제 슬레이브 불일치(해로운 우회)인지 여부는 런타임 확인 필요. (근거: src/query/execute_schema.c:11740; src/query/execute_schema.c:10267-10274) · 필요한 확인: HA 2노드에서 OFF 테이블 DROP 후 동일명 REPLICATION=ON 재생성 → 슬레이브에 동일 빈 ON 테이블이 생성되고 이후 DML이 정상 복제되는지, 슬레이브에 과거 데이터 공백이 생기는지 확인
- **N-12. unload 파일 포맷 미명세**(변수 필드명·위치, 클래스 단위인지, 구버전 파서가 신규 토큰 만나면?) (~6, 엔진·응용).
  - ↳ **코드 대조**: **코드무관** — 스펙이 unload 파일의 REPLICATION 표기 포맷을 명세하지 않은 문서 완결성 이슈. 코드 실체: 포맷은 클래스별 CREATE TABLE의 인라인 `REPLICATION=ON/OFF` DDL 절(위치는 COLLATE 뒤·ENCRYPT 앞), 항상 명시. 다만 신규 문법 토큰에 버전 가드가 없어 구버전 cubrid loaddb가 신버전 unload 파일을 파싱하면 미지의 REPLICATION 토큰에서 구문오류 — 실재하는 다운그레이드/전방호환 갭이니 스펙에 포맷·버전정책 명시 권고. (근거: src/executables/unload_schema.c:1796-1800 (CREATE TABLE 인라인 옵션으로 방출); src/parser/csql_grammar.y:19990-19996 (신규 REPLICATION 토큰, 버전 가드 없음))

### 2.4 사소 (Trivial)

- **T-1. §5-1 제목 오타 "CRATE TABLE" + §7 "재시작해아한다" 등 오탈자** — 합의도 **~8/20**. SQL 키워드 오타는 문서 검색에도 지장.
  - ↳ **코드 대조**: **코드무관** — 제목·본문 오탈자는 순수 스펙 문서 이슈. 코드 대조 무의미(문법 키워드는 CREATE로 정상). (근거: §5-1 제목 'CRATE TABLE', §7 '재시작해아한다' 등은 스펙 산문 오탈자 — 구현 코드와 무관)
- **T-2. §9 "SA" 모드가 정의 없이 처음 등장, §1의 "HA 아니면 싱글" 이분법과 충돌** — 합의도 **~7/20**. HA/CS/SA 관계를 §1에서 정의 필요.
  - ↳ **코드 대조**: **코드무관** — SA는 CUBRID의 standalone(SA_MODE) 실제 빌드/실행 모드를 가리키며(HA_DISABLED() 계열로 replication 변경도 이 모드에서만 허용), 스펙이 §1에서 정의 없이 §9에 등장시킨 것은 용어 일관성 문제다. 코드 결함이 아닌 문서 정의 보강 이슈. (근거: 스펙 §9 'SA' 용어 정의·§1 이분법 충돌 — 순수 문서 서법)
- **T-3. §1 첫 문장 주술 비문**("복제 테이블은 ... HA모드를 실행 할 수 없다"), §4-2 "기존의 연산 결과와 동일한 경우 ..." 비문 (사용자 리뷰).
  - ↳ **코드 대조**: **코드무관** — 주술 비문·문장 다듬기 등 순수 문서 서법 이슈로 코드 대조 대상이 아니다. (근거: user_spec §1 첫 문장·§4-2 문장)
- **T-4. §8 "RK를 할당한다" vs §1 "선택된다" 용어 불일치** — "할당"이 없던 키를 새로 만든다는 오해 유발 (~6).
  - ↳ **코드 대조**: **코드무관** — RK가 '선택'되는지 '할당(신규 생성)'되는지 용어 불일치는 문서 표현 정합성 이슈이며, 코드상 RK는 기존 PK/NOT NULL UNIQUE 중 선택(or_is_replication_candidate_key)이나 이는 T-4 판정과 무관한 문서 용어 통일 대상. (근거: user_spec §8 '할당' vs §1 '선택' 용어)
- **T-5. REPLICATION 예약어 승격 시 기존 `replication` 컬럼명 충돌** (~2).
  - ↳ **코드 대조**: **확정** — lexer가 replication을 전용 REPLICATION 토큰으로 반환하는데, 문법의 비예약(identifier) 목록에 REPLICATION을 추가하지 않음(같이 추가된 이웃 키워드 DISK_SIZE·REVERSE는 목록에 있음). 결과적으로 REPLICATION이 예약어가 되어 기존 replication 컬럼/테이블명을 따옴표 없이 식별자로 못 씀 — T-5 충돌 확인. (근거: src/parser/csql_lexer.l (REPLICATION 토큰 반환), src/parser/csql_grammar.y:20646-20905 (identifier 규칙에 REPLICATION 없음; 동료 키워드 DISK_SIZE=20755, REVERSE=20883 은 있음))
- **T-6. "복제 테이블 / 복제 대상 테이블 / 복제키 후보 / 복제키" 용어 혼용, 용어집 부재** (~6).
  - ↳ **코드 대조**: **코드무관** — '복제 테이블/복제 대상 테이블/복제키 후보/복제키' 용어 혼용과 용어집 부재는 순수 문서 정비 사안으로 코드 대조 대상이 아니다. (근거: user_spec 전반의 용어 혼용)

## 4. 직군별 관점 요약 (그 직군에서 고유하게 나온 지적)

- **PM (요구사항·릴리스 리스크)**: 문서 내부 모순(§8/§9)을 가장 먼저 포착. 마이그레이션 경로 부재, 무중단 롤링 업그레이드, MUST/MAY 서법 미구분, 경쟁 포지셔닝 근거("MySQL이 왜 느린지" 정량 데이터 없음), Oracle GoldenGate 대비 미언급, 파티션 스코프 명시 요구가 PM 고유.

- **DB 엔지니어 (운영/DBA)**: "새벽 3시 장애 대응" 관점. §7 출력의 exit code·파싱 가능성, 신규 슬레이브 조인 시 OFF 테이블 초기 데이터, 스위치오버 전 사전점검 체크리스트, unloaddb가 OFF 테이블 데이터를 백업에 포함하는지(DR의 유일 안전망), 다중 슬레이브 구성, 다운그레이드(신→구 버전) 경로, fail_count 지표와 신규 위반의 관계가 DBA 고유.

- **최종 사용자 (사용성)**: "이 문서만으로 csql 앞에서 따라할 수 있나". 에러 메시지 실물 부재, 예시 12 vs 13의 반직관성("PK 삭제는 되는데 왜 한 문장으로 묶어야 하나"), §1 첫 문장 비문, 예시 3 어순 오류("복제 제외 PK"), "RK 유무와 REPLICATION 여부는 독립 축"이라는 개념이 문서 초반에 강조 안 됨이 사용자 고유.

- **응용 개발자 (ORM/마이그레이션)**: dev/prod parity 붕괴, Flyway/Liquibase가 DROP·ADD를 별도 changeSet으로 쪼개면 예시 13 요구와 충돌, ORM이 `@Column(unique=true)`를 nullable로 만들어 RK 후보 자격 조용히 미달, RK 자동선택이 ORM DDL 생성 순서에 취약, 컬럼 단위 PII 필터 미지원, 읽기/쓰기 분리 라우팅에서 OFF 테이블 빈 결과, `@Id`(PK) 의미와 RK 전환의 무관함 보장 필요가 응용 고유.

- **엔진 개발자 (구현)**: RK를 마스터가 정해 로그로 전파해야 함(노드 재계산 금지), 복제 로그 포맷에 RK 스키마 버전 필요, RK 후보 0개로 떨어지는 동시성 경쟁(TOCTOU) 재검증, 카탈로그에 RK 포인터 명시 저장, 트리거로 인한 간접 DML의 복제 귀속, SERIAL/AUTO_INCREMENT failover 동기화, REUSE_OID와 복제 로그의 독립성, 복합키 RK 성능, in-place 카탈로그 스키마 마이그레이션이 엔진 고유. **가장 깊고 구현 착수를 직접 막는 지적이 이 직군에 집중.**

## 5. 상충 의견 (리뷰어끼리 반대 방향)

1. **REPLICATION 기본값 ON vs OFF**
   - 사용자 3·5년차, PM 10년차: 기본값 ON은 "아무것도 안 하면 나중에 HA에서 터지는" 지뢰 → RK 없는 테이블은 기본 OFF로 하거나 최소한 CREATE 시 경고.
   - 엔진 3년차: 기본값을 OFF로 바꾸면 하위 호환(구버전은 사실상 전부 복제되던 동작)을 깨므로 ON 유지가 맞고, 대신 운영 가이드로 보완.
   - → **미해결 트레이드오프. "안전한 기본값" vs "하위 호환"이 정면 충돌.**

2. **FK-복제 결합을 느슨하게 vs 더 엄격하게**
   - 응용 3·10년차: 정적 코드 테이블을 OFF로 두고도 FK를 걸 수 있도록 예외 옵션(`NOT ENFORCED ON SLAVE` 류)을 달라 — **규칙 완화** 요구.
   - 대다수(PM·DBA·엔진·사용자): 오히려 ALTER OFF 경로까지 막아 FK-복제 불변식을 **강화**하라(C-2).
   - → 같은 §5를 두고 한쪽은 문을 더 열자, 다른 쪽은 더 잠그자.

3. **§8 기본값 중 어느 것이 오기인가**
   - 대다수: §8(ON)이 맞고 §9(OFF)가 오기.
   - DB엔지니어 5년차: "unload 시점 기본 OFF(§9), load 시점 기본 ON(§8)"이라는 비대칭 규칙일 가능성도 배제 못 함(그렇다면 비대칭 근거를 밝혀야).
   - → 다수는 오기로 보나, 소수가 "의도된 비대칭일 수 있다"며 확정을 유보.

4. **MySQL식 전 컬럼 폴백(FULL)을 되살릴 것인가**
   - 엔진 10·DB엔지니어 10·PM 여러: 배경에서 성능으로 배제했지만 "느려도 복제는 됨"이라는 선택지를 로드맵에 남기라 — **부분 복원** 제안.
   - 스펙 배경: 성능상 명시적 배제.
   - → 설계 결정 자체에 대한 재검토 요구(직접 충돌은 아니나 방향 이견).

### Phase 0 — 즉시 (문서 교정, 반나절)

### Phase 1 — 컨셉 확정 (설계 재검토, 릴리스 게이트)
- **RK 선택 규칙을 확정 알고리즘으로 명문화** + "마스터가 정해 로그로 전파, 슬레이브 재계산 금지" + sticky 불변식 (C-1). 이것이 다른 모든 이슈의 뿌리.
- **FK 불변식을 대칭으로 재설계** — ALTER OFF 전환·다단계·자기참조·순환까지 (C-2, M-8). 상충 의견 2를 여기서 결론.
- **복합 ALTER 원자성·검증 시점(문장 최종 상태)·동시성 락** 명시 (C-7, M-1).

- **복제 로그와 RK 전환의 순서 보장(배리어)·로그 포맷** 명시 (C-8).

### Phase 2 — 운영·관측성

### Phase 3 — 마이그레이션·확장성
