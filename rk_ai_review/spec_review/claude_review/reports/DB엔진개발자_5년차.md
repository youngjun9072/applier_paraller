# CUBRID HA 복제 개선 스펙 리뷰 — DB 엔진 개발자(5년차) 관점

## 리뷰어 소개

DBMS 엔진 코어(카탈로그, 복제 로그, applylogdb)를 5년째 개발하고 있는 엔진 개발자다. PK 유무에 따라
복제 여부가 갈리던 기존 구조의 한계와, 복제 로그가 실제로 어떤 값을 기준으로 행(row)을 찾아 갱신하는지를
코드 레벨에서 다뤄 왔다. 이 리뷰에서는 스펙에 쓰인 문장이 "구현 가능한 하나의 알고리즘"으로 명확히
좁혀지는지, 아니면 여러 구현이 모두 "스펙을 만족"하면서도 서로 다른(그리고 잘못된) 동작을 하게 되는지를
중점적으로 따진다.

## 총평

이 스펙은 PostgreSQL의 REPLICA IDENTITY 개념을 빌려와 "PK 또는 NOT NULL UNIQUE 중 하나를 복제 키(RK)로
엔진이 자동 선택한다"는 방향을 잡았는데, 방향 자체는 합리적이다. 그러나 문서는 **"무엇을 할 수 있다/없다"는
규칙은 비교적 촘촘히 나열하면서도, 그 규칙을 구현할 때 반드시 결정해야 하는 하위 질문(무엇을 기준으로
"순서"를 정하는가, 여러 절로 이루어진 ALTER는 원자적인가, 복제 로그는 행을 무엇으로 식별하는가, 두 노드가
독립적으로 같은 결론에 도달함을 어떻게 보장하는가)에는 답하지 않는다.** 특히 RK 자동 선택의 결정성(같은
입력에 대해 항상 같은 출력이 나오는 성질)이 스펙 전체의 정합성을 떠받치는 전제인데, 이 결정성을 실제로
보장하는 구체적 규칙이 없다는 점이 가장 큰 문제다. 예제 코드에도 파싱조차 안 되는 오타가 여러 건 있어
구현 기준 문서로 쓰기엔 다듬을 부분이 많다. 아래 20개 리뷰는 심각도 순으로 정리했다.

### 리뷰 1

**[심각도: 치명] UK가 여러 개일 때 "가장 빠른 순서"의 기준이 정의되지 않아 RK 선택이 비결정적일 수 있다**

**대상**: §1 "UK가 여러개 존재한다면 큐브리드 엔진에 의해 이 중 하나가 선택된다(ex. 테이블내에 명시된
순서 중 가장 빠른 순서)"

**문제 설명**: "결정성(determinism)"이란 같은 입력이 주어지면 언제, 어디서 실행하든 항상 같은 결과가
나오는 성질을 말한다. 복제는 마스터와 슬레이브가 같은 DDL을 각자 실행해서 카탈로그(테이블 구조를 저장하는
메타데이터 저장소) 상태를 독립적으로 맞춰가는 구조이므로, RK 자동 선택 알고리즘이 결정적이지 않으면
두 노드가 서로 다른 컬럼을 RK로 인식하는 사고가 날 수 있다. 그런데 "테이블내에 명시된 순서 중 가장 빠른
순서"라는 문구는 최소 세 가지로 해석 가능하다.

1. CREATE TABLE DDL 문에 UNIQUE 제약이 나타난 텍스트 순서
2. 카탈로그에 저장된 컬럼(attribute) ID 순서
3. 제약이 실제로 생성된 시각(ALTER TABLE로 나중에 추가된 UK 포함) 순서

이 세 기준은 실제로 다른 결과를 낳는다.

**구체 예제**:
```sql
CREATE TABLE t1 (
    a INT,
    b INT,
    UNIQUE (b),   -- DDL 텍스트상 첫 번째로 등장
    UNIQUE (a)    -- DDL 텍스트상 두 번째로 등장, 그러나 컬럼 a는 attribute ID상 b보다 먼저
);
```

**예제 설명**: 컬럼 `a`는 테이블 정의 순서상 첫 번째 컬럼이라 카탈로그의 attribute ID가 `b`보다 작다.
반면 UNIQUE 제약이 선언된 텍스트 순서로 보면 `UNIQUE(b)`가 먼저 나온다. "명시된 순서"를 attribute ID
기준으로 구현하면 RK는 `a`가 되고, DDL 텍스트 등장 순서로 구현하면 RK는 `b`가 된다. 스펙만 보고는 어느
쪽이 맞는지 판단할 수 없다. 이 판단 기준이 구현마다(혹은 같은 구현이라도 버전이 바뀌면서) 달라지면,
과거 unloaddb로 떠 놓은 덤프를 다른 버전에서 loaddb 했을 때 다른 RK가 선택되는 문제로 이어진다(리뷰 2
참조).

**제안**: "명시된 순서"를 카탈로그의 물리적 attribute ID 순서로 고정한다고 명시하고, 복합 UK와 단일
컬럼 UK가 섞여 있을 때의 비교 규칙(리뷰 20)까지 포함한 완전한 알고리즘을 의사코드 수준으로 스펙에
박아 넣어야 한다.

### 리뷰 2

**[심각도: 치명] unloaddb/loaddb로 재구성 시 RK 자동 할당이 노드마다 다르게 나올 위험**

**대상**: §8 "복제 테이블의 경우 큐브리드는 자동으로 RK를 할당한다."

**문제 설명**: §8은 loaddb 시점에 RK를 다시 계산해서 할당한다고만 되어 있다. 그런데 이 재계산이 리뷰 1에서
지적한 "순서" 규칙에 의존한다면, 같은 스키마를 서로 다른 시점에 서로 다른 노드에서 각각 loaddb 했을 때
(예: 슬레이브를 물리 복사가 아니라 논리 덤프로 새로 구성하는 경우, 혹은 재해복구 후 한쪽만 별도로
재적재하는 경우) 두 노드가 서로 다른 UK를 RK로 선택할 수 있다. 복제 로그는 RK 값으로 행을 찾아 갱신하는
구조이므로(리뷰 8), 마스터가 RK=b로 판단해 보낸 UPDATE 로그를 슬레이브가 RK=a로 알고 있는 상태에서
받으면 엉뚱한 행을 갱신하거나 대상 행을 찾지 못하는 오류가 난다.

**구체 예제**:
```
# 마스터에서 백업 대신 논리 덤프로 슬레이브를 재구성한다고 가정
unloaddb -o /backup/dump mydb

# (마스터) 원본 DB는 이미 RK=b(UK)로 운영 중
# (슬레이브) 동일 dump 파일로 새로 loaddb
loaddb -d /backup/dump.schema -u /backup/dump.data slave_db
# loaddb 시점에 "자동으로 RK를 할당"하는데, 이 결과가 반드시 b로 나온다는 보장이 스펙에 없다
```

**예제 설명**: 스키마 파일(.schema)에는 CREATE TABLE 문이 텍스트로 들어있고, loaddb는 이를 다시 파싱해
카탈로그를 만든다. 이 과정에서 UK가 여러 개면 리뷰 1의 "순서" 모호성이 그대로 재현된다. 게다가 마스터의
현재 RK가 이미 b로 확정돼 운영 중이라는 사실은 스키마 텍스트만 봐서는 알 수 없다(RK는 파생 값이라 DDL에
별도로 저장되지 않는다). 즉 loaddb는 "현재 RK가 무엇이었는지"를 전혀 모른 채 처음부터 다시 계산한다.

**제안**: unloaddb 출력에 "이 테이블의 현재 RK가 어떤 제약인지"를 명시적으로 함께 저장하고, loaddb는
그 정보를 우선 사용하도록 해야 한다. 재계산에 의존하는 한 두 노드의 RK 일치를 보장할 방법이 없다.

### 리뷰 3

**[심각도: 치명] 콤마로 여러 절을 묶은 ALTER TABLE의 원자성이 명시되지 않았다**

**대상**: 예시 7 "ALTER TABLE tbl DROP CONSTRAINT ..., ADD CONSTRAINT ...;", 예시 13 (PK를 다른
컬럼으로 변경)

**문제 설명**: "원자성(atomicity)"이란 하나의 작업 단위가 전부 성공하거나 전부 실패하며, 중간 상태가
외부에 노출되지 않는 성질이다. 예시 13은 하나의 ALTER TABLE 문 안에 `DROP CONSTRAINT PRIMARY KEY`와
`ADD CONSTRAINT PRIMARY KEY(a)`를 콤마로 묶어 "OK"라고 결과만 보여준다. 하지만 다음을 전혀 답하지 않는다.

- ADD 단계가 실패하면(예: 새 컬럼에 중복 값 존재) DROP도 함께 롤백되는가?
- 이 문장이 만드는 복제 로그는 DROP과 ADD를 하나로 묶은 단일 레코드인가, 두 개의 개별 레코드인가?
- 두 개의 개별 레코드라면, 슬레이브의 applylogdb가 DROP까지만 반영한 상태에서 프로세스가 죽으면
  슬레이브에는 RK가 하나도 없는 테이블이 남는데, "HA 모드에서 복제 대상 테이블은 반드시 RK가 하나 이상
  존재해야 한다"(§9)는 불변조건이 슬레이브에서 순간적으로 깨지는 것을 허용하는가?

**구체 예제**:
```sql
-- table_name.a 컬럼에 이미 중복값(1, 1, 2)이 들어있는 상태라고 가정
ALTER TABLE table_name
    DROP CONSTRAINT PRIMARY KEY,
    ADD CONSTRAINT PRIMARY KEY(a);
-- ADD 단계에서 "중복 값 존재"로 실패한다.
-- Q1) 이 시점에 DROP CONSTRAINT는 이미 카탈로그에 반영되었다가 롤백되는가?
-- Q2) 트랜잭션 전체가 실패로 기록되어 복제 로그에는 아무것도 안 남는가,
--     아니면 DROP 부분만 담긴 로그가 슬레이브로 이미 전송된 뒤인가?
```

**예제 설명**: 이 시나리오는 "다중 절 ALTER TABLE"이 하나의 트랜잭션·하나의 복제 로그 단위로 다뤄지는지를
검증하는 최소 사례다. 카탈로그 변경은 보통 트랜잭션으로 묶여 롤백이 가능하지만, 스펙 문서 수준에서
"이 문장은 원자적이다"라고 명시하지 않으면 구현자마다 DROP과 ADD를 별개의 하위 단계로 나눠 처리하다가
실패 시 중간 상태를 남기는 구현을 할 수 있다.

**제안**: "쉼표로 연결된 다중 ALTER TABLE 절은 하나의 원자적 트랜잭션이자 하나의 복제 로그 레코드로
취급하며, 일부 절이 실패하면 전체가 롤백되고 복제 로그에도 아무 것도 반영되지 않는다"를 스펙에 명문화한다.

### 리뷰 4

**[심각도: 치명] RK 전환 DDL과 동시에 실행 중인 DML 트랜잭션 간의 경합이 다뤄지지 않았다**

**대상**: §4-2 전반, 예시 13

**문제 설명**: 복제 로그는 트랜잭션 커밋 순서(LSA, Log Sequence Address — 로그가 기록된 물리적 위치를
가리키는 값으로, 슬레이브는 이 순서대로 로그를 재생한다)대로 슬레이브에 전달·재생된다. RK를 바꾸는
ALTER TABLE이 커밋되는 시점과, RK 전환 이전부터 실행 중이던 DML 트랜잭션이 커밋되는 시점의 선후관계가
꼬이면, 슬레이브가 "이 UPDATE 로그는 옛 RK 기준인지 새 RK 기준인지"를 잘못 판단할 여지가 생긴다. 스펙은
ALTER TABLE이 해당 테이블에 대해 어떤 수준의 잠금(진행 중인 DML 트랜잭션의 커밋을 기다리는 배타적
스키마 잠금인지, 아니면 단순 메타데이터 잠금이라 DML과 뒤섞여 실행될 수 있는지)을 거는지 전혀 언급하지
않는다.

**구체 예제**:
```
[마스터]
T1: BEGIN;
T1: UPDATE tbl SET x = 1 WHERE a = 5;      -- 현재 RK는 PK(a)
T2: BEGIN;
T2: ALTER TABLE tbl DROP CONSTRAINT PRIMARY KEY, ADD CONSTRAINT PRIMARY KEY(c);
T1: COMMIT;   -- LSA 100
T2: COMMIT;   -- LSA 105

[슬레이브 applylogdb, LSA 순서대로 재생]
LSA 100: UPDATE 로그 재생 — 이 로그는 "a=5인 행"을 찾으라는 의미인데,
         이 시점 슬레이브의 RK는 아직 a인가, 이미 c로 바뀌었는가?
LSA 105: DDL 반영, RK를 c로 전환
```

**예제 설명**: 만약 CUBRID의 ALTER TABLE이 대상 테이블에 대한 완전한 배타적 잠금을 걸어 T1이 커밋을
마칠 때까지 T2의 커밋을 미룬다면 위 순서(LSA 100 → 105)가 항상 보장되어 문제가 없다. 그러나 스펙에는
그런 잠금 보장이 명시돼 있지 않다. 만약 구현이 메타데이터 수준의 가벼운 잠금만 사용한다면, T1이 오래
걸리는 트랜잭션일 때 T2가 먼저 커밋되어 LSA 순서가 뒤바뀔 수 있고, 이 경우 슬레이브는 이미 RK가 c로
바뀐 상태에서 "a=5" 조건의 UPDATE 로그를 만나게 되어 대상 행을 못 찾거나 잘못된 행을 갱신하게 된다.

**제안**: RK를 변경하는 ALTER TABLE은 해당 테이블에 대한 모든 진행 중인 DML 트랜잭션의 커밋을 기다리는
배타적 스키마 잠금을 반드시 사용한다고 명시하고, 이 잠금 규칙을 복제 로그 순서 보장의 근거로 스펙에
남겨야 한다.

### 리뷰 5

**[심각도: 중요] 이미 FK로 참조되고 있는 ON 테이블을 OFF로 바꾸는 경로가 검증되지 않는다**

**대상**: §4, §5, 예시 17~23

**문제 설명**: 스펙은 "REPLICATION=OFF인 테이블을 새로 참조하는 FK를 추가하는 것"(예시 18, 23)과
"HA 중 OFF→ON 전환"(예시 5, ERROR)은 막지만, **이미 ON 상태이고 다른 테이블의 FK가 참조 중인 테이블을
ON→OFF로 바꾸는 것**을 막는 규칙이 없다. §4는 "HA 환경 복제 제외테이블은 … ON으로 변경하는 것 외의 모든
DDL을 사용할 수 있다"고만 하고, ON 테이블이 OFF로 내려가는 조건에는 FK 참조 여부를 검사하라는 말이
없다. 이 구멍은 스펙이 애초에 해결하려던 배경 문제(참조 테이블이 슬레이브에 없어 FK가 깨지는 상황)를
ALTER 경로로 그대로 재현한다.

**구체 예제**:
```sql
-- 예시 17 상태: customers(ON), orders(ON, FK -> customers) 정상 복제 중
ALTER TABLE customers REPLICATION = OFF;   -- 스펙에 이 케이스에 대한 금지 규정이 없음

-- Failover 발생
-- 슬레이브: orders는 계속 최신, customers는 이 시점부터 갱신 중단
-- 애플리케이션이 orders.customer_id로 customers를 조회 → 최근 추가된 customer_id는 없음
```

**예제 설명**: 이 시나리오는 배경에서 설명한 "FK 참조 테이블이 복제 제외일 때의 문제 상황"(다이어그램)과
동일한 결과를 낳는데, 유일한 차이는 테이블을 OFF로 만든 시점이 CREATE TABLE이 아니라 운영 중 ALTER라는
것뿐이다. §5는 CREATE/ALTER 시점의 FK "추가"만 검사하고, 참조 "대상 테이블 자체의 REPLICATION 변경"은
검사 대상에서 빠져 있다.

**제안**: ALTER TABLE … REPLICATION=OFF 실행 시, 해당 테이블을 참조하는 FK가 존재하는 ON 테이블이 하나라도
있으면 예시 18/23과 동일하게 에러를 내도록 규칙을 대칭적으로 추가해야 한다.

### 리뷰 6

**[심각도: 중요] ON→OFF 전환 시 슬레이브에 이미 있던 데이터의 처리 방침이 없다**

**대상**: §4, §9 "RK가 있는 테이블 역시 복제 제외대상이 될 수 있음"

**문제 설명**: 운영 중(HA 모드)에 ON이던 테이블을 OFF로 바꾸는 것(예시 6, OK) 자체는 허용되지만, 그
순간 슬레이브에 이미 쌓여 있던 해당 테이블의 데이터를 어떻게 할지에 대한 언급이 없다. 삭제(TRUNCATE)
하는지, 그대로 얼려서(freeze) 남겨두는지 스펙이 침묵하고 있다. §1의 "REPLICATION OFF로 인한 데이터
불일치는 책임지지 않는다"는 문장은 향후 발생할 불일치에 대한 면책일 뿐, 전환 시점에 남아 있던 과거
데이터의 취급까지 정의하지는 않는다.

**구체 예제**:
```
[T0] customers: REPLICATION=ON, 마스터/슬레이브 모두 100건 동일
[T1] INSERT INTO customers ...   -- 마스터 101건, 곧 슬레이브도 101건
[T2] ALTER TABLE customers REPLICATION = OFF;   -- DDL은 복제됨
[T3] INSERT INTO customers ...   -- 마스터 200건까지 증가, 슬레이브는 101건에서 멈춤
[Failover]
-- 애플리케이션이 슬레이브의 customers를 조회하면 101건이 나온다.
-- 이 101건이 "OFF 전환 시점의 스냅샷"이라는 사실은 스키마 어디에도 기록되지 않는다.
```

**예제 설명**: 사용자가 실수로 이 테이블을 다시 참조하면(REPLICATION=OFF는 데이터가 없는 게 아니라
"멈춘 옛날 데이터"가 있는 상태다) 완전히 비어 있는 테이블보다 오히려 더 위험할 수 있다. 데이터가 없으면
바로 알아채지만, 그럴듯한 옛날 데이터가 있으면 오류를 늦게 발견한다.

**제안**: ON→OFF 전환 시 슬레이브의 기존 데이터를 TRUNCATE할지, 유지할지 스펙에 명시하고, 유지한다면
"이 데이터가 몇 번째 LSA 시점 것인지"를 db_class 등 카탈로그에 기록해 조회 가능하게 해야 한다.

### 리뷰 7

**[심각도: 중요] db_class 카탈로그 컬럼 추가가 롤링 업그레이드/버전 혼재 구간에 미치는 영향이 없다**

**대상**: §2-3 예시 9 (db_class에 `replication` 컬럼 추가)

**문제 설명**: 카탈로그란 테이블·컬럼·제약 등 스키마 메타데이터를 저장하는 시스템 테이블 집합이다.
db_class는 CUBRID에서 이 메타데이터를 조회하는 대표적인 시스템 뷰이며, 드라이버·관리 도구·모니터링
스크립트가 이 뷰의 컬럼 구성에 의존하는 경우가 많다. 여기 새 컬럼을 추가하면, 마스터와 슬레이브가 서로
다른 버전(구버전 슬레이브에는 REPLICATION 옵션 자체가 없는 상태)으로 운영되는 롤링 업그레이드
구간에서 무슨 일이 벌어지는지가 스펙에 없다.

**구체 예제**:
```
마스터: CUBRID N+1 버전 (REPLICATION 옵션 파서 있음) — 먼저 업그레이드됨
슬레이브: CUBRID N 버전 (REPLICATION 옵션 파서 없음) — 아직 업그레이드 전

마스터: CREATE TABLE t (id INT PRIMARY KEY) REPLICATION=OFF;
-- 이 DDL이 그대로 복제 로그로 슬레이브에 전달된다.
-- 슬레이브의 구버전 SQL 파서는 REPLICATION 옵션을 모른다.
-- 파싱 에러로 applylogdb가 fail_count를 올리며 멈추는가?
-- 옵션을 무시하고 REPLICATION=ON(기본값)으로 처리해버리는가?
```

**예제 설명**: 배경에서 다룬 원래 문제(PK 컬럼 변경으로 인한 복제 누락과 fail_count 증가)와 판박이인
새 실패 유형이 업그레이드 구간에서 재발할 수 있다. 스펙은 신버전-신버전 조합만 상정하고 있고, 버전
혼재 구간의 동작을 전혀 규정하지 않는다.

**제안**: 업그레이드 순서 원칙(예: 슬레이브를 먼저 올린 뒤 마스터를 올린다)과, 구버전 슬레이브가 새
DDL/카탈로그 필드를 만났을 때의 명시적 처리(경고 후 무시/에러 후 정지 등)를 스펙에 추가해야 한다.

### 리뷰 8

**[심각도: 중요] 복제 로그가 RK를 어떻게 인코딩하는지, RK 컬럼 자체가 사라지는 경우 무엇을 참조하는지 정의가 없다**

**대상**: §1, §4-2 전반 (RK 자동 선택·전환), 배경 (REPLICA IDENTITY 차용)

**문제 설명**: PostgreSQL의 REPLICA IDENTITY는 WAL(Write-Ahead Log, 트랜잭션 로그) 레코드에 변경 전
행의 식별 컬럼 값을 함께 남겨 논리 복제가 "어느 행을 바꿀지"를 판단하게 한다. 이 스펙도 같은 개념을
차용한다고 배경에 적혀 있지만, 정작 CUBRID의 복제 로그 레코드가 RK 컬럼을 이름으로 참조하는지, 값만
담아두는지, 스키마 버전 태그를 함께 남기는지에 대한 설명이 전혀 없다. RK가 바뀌는 DDL 직후 옛 RK 기준으로
만들어진 DML 로그가 아직 큐에 남아 있을 때, 슬레이브가 이를 어떤 컬럼 기준으로 해석해야 하는지 답이
없다.

**구체 예제**:
```
-- RK가 a(PK)인 상태에서 만들어진 UPDATE 로그 (LSA 90)
UPDATE tbl SET x = 1 WHERE <RK 컬럼> = 5;

-- 이후 LSA 95에서 RK 전환
ALTER TABLE tbl DROP CONSTRAINT PRIMARY KEY, ADD CONSTRAINT PRIMARY KEY(c);
-- 제약만 제거되고 컬럼 a 자체는 아직 테이블에 남아있다고 가정

-- 그 후 별도 ALTER로 컬럼 a까지 제거 (RK 해제 후에는 §4-2 규칙상 가능)
ALTER TABLE tbl DROP COLUMN a;

-- 이 시점 이후 슬레이브에 도착한, "LSA 90의 로그를 재전송해야 하는" 상황(예: 장애 복구 재동기화)이
-- 생기면 이미 컬럼 a가 없는 슬레이브에서 "a=5"를 어떻게 찾을 것인가?
```

**예제 설명**: 정상 흐름(로그가 실시간으로 순서대로 재생되는 경우)에서는 문제가 드러나지 않을 수 있지만,
재동기화나 로그 재적용처럼 오래된 로그를 나중에 다시 처리해야 하는 복구 경로에서는 "그 시점의 RK가
무엇이었는지"를 로그 자체에 담아두지 않으면 해석이 불가능해진다.

**제안**: 복제 로그 레코드에 RK 컬럼의 스키마 버전(또는 DDL 시퀀스 번호)을 함께 기록해, 어떤 컬럼
집합을 기준으로 값이 인코딩되었는지 로그만 보고 판단할 수 있게 해야 한다.

### 리뷰 9

**[심각도: 중요] 복제키 후보가 2개에서 동시에 0개로 떨어지는 경쟁 조건이 다뤄지지 않았다**

**대상**: §4-2 "테이블에 하나의 복제키만 존재한다면 복제키를 수정하는 DDL이 제한되지만, 다른 복제키
후보가 함께 존재한다면 모든 DDL은 허용된다"

**문제 설명**: 이 규칙은 "정확히 후보가 1개"인 경우만 다루고, "후보가 2개인 테이블에서 두 개의 트랜잭션이
동시에 각각 다른 후보를 지우려는 경우"는 다루지 않는다. 두 트랜잭션이 각자 시작 시점에는 "다른 후보가
있으니 이 DROP은 허용된다"는 조건을 만족한 상태로 실행되지만, 둘 다 커밋되면 결과적으로 후보가 0개가
되어 §9의 불변조건("HA 모드에서 복제 대상 테이블은 반드시 RK가 하나 이상 존재해야한다")이 깨진다.

**구체 예제**:
```sql
-- tbl에 UK 후보가 u_tbl_a, u_tbl_b 두 개 있고 PK는 없는 상태

-- 세션 A
ALTER TABLE tbl DROP CONSTRAINT u_tbl_a;

-- 세션 B (거의 동시에)
ALTER TABLE tbl DROP CONSTRAINT u_tbl_b;

-- 두 세션 모두 "시작 시점엔 다른 후보(u_tbl_b 또는 u_tbl_a)가 있으니 허용된다"는 조건을 만족한다.
-- 둘 다 커밋되면 tbl은 복제키 후보가 0개인 상태가 된다.
```

**예제 설명**: 단일 세션 관점에서 예시 15("복제키로 사용중인 컬럼은 UNIQUE 제약을 삭제할 수 없음")는
후보가 1개일 때만 막는다고 되어 있으므로, 후보가 2개인 상태에서의 DROP은 정의상 허용된다. 문제는 이
"허용 여부 판단"이 트랜잭션 시작 시점의 스냅샷을 기준으로 하는지, 커밋 직전 재검증을 하는지에 대한
언급이 전혀 없다는 것이다. 재검증이 없다면 이 경쟁 조건은 그대로 통과되어 RK가 없는 복제 테이블이
HA 모드에서 만들어질 수 있다.

**제안**: 복제키 후보 개수 검사는 커밋 직전(또는 스키마 변경에 대한 직렬화 가능한 잠금 하)에 재검증하도록
명시하고, 두 번째로 커밋을 시도하는 트랜잭션은 예시 15와 동일한 에러로 실패해야 한다는 규칙을 추가한다.

### 리뷰 10

**[심각도: 중요] 파티션 테이블과 RK/REPLICATION 옵션의 상호작용이 전혀 언급되지 않았다**

**대상**: 스펙 전체 (파티션 관련 절 없음)

**문제 설명**: 파티션 테이블은 하나의 논리적 테이블을 여러 물리적 하위 테이블(파티션)로 나눠 저장하는
기능이다. CUBRID에서 파티션 테이블은 내부적으로 부모 클래스와 자식 파티션 클래스로 구성되며, PK/UK
제약이 파티션 키를 포함해야 하는 등 일반 테이블과 다른 제약 규칙을 갖는다. 이 스펙은 RK 선택과
REPLICATION 옵션을 오직 "테이블" 단위로만 서술할 뿐, 파티션 테이블에 대해서는 한 마디도 하지 않는다.
REPLICATION 옵션이 부모 테이블에만 적용되는지 각 파티션에 개별 적용되는지, 파티션 추가(ADD PARTITION)
시 RK가 자동으로 상속되는지 전혀 알 수 없다.

**구체 예제**:
```sql
CREATE TABLE sales (
    id INT,
    sale_date DATE,
    amount INT
) PARTITION BY RANGE (sale_date) (
    PARTITION p2025 VALUES LESS THAN (DATE'2026-01-01'),
    PARTITION p2026 VALUES LESS THAN (DATE'2027-01-01')
) REPLICATION = ON;
-- id, sale_date 어디에도 PK/UK가 없다.
-- HA 모드라면 예시 10처럼 ERROR가 나야 하는가?
-- 파티션 자식 클래스마다 RK를 개별적으로 요구하는가, 부모 테이블 기준으로만 판단하는가?
```

**예제 설명**: 이 예제는 RK 후보가 아예 없는 흔한 형태의 파티션 테이블이다. 이 스펙의 규칙을 그대로
적용하면 예시 10과 동일하게 에러가 나야 하지만, 파티션 테이블은 내부적으로 여러 개의 물리 클래스로
쪼개지기 때문에 "RK가 없다"는 판정을 부모 기준으로 할지 파티션 각각에 대해 할지에 따라 구현이 완전히
달라진다.

**제안**: 파티션 테이블 전용 절을 추가해 REPLICATION 옵션의 적용 단위(부모/자식)와 RK 자동 선택 시
파티션 키 포함 여부에 대한 규칙을 명시해야 한다.

### 리뷰 11

**[심각도: 중요] 예시 20/23의 ALTER TABLE ADD COLUMN 내 인라인 FOREIGN KEY 문법이 기존 문법과 불일치할 수 있다**

**대상**: 예시 20, 23
```sql
ALTER TABLE new_orders ADD COLUMN
(customer_id INT FOREIGN KEY REFERENCES customers(customer_id));
```

**문제 설명**: 이 예시는 컬럼 정의 안에 `FOREIGN KEY REFERENCES ...`를 그대로 넣어 컬럼과 외래키
제약을 한 번에 추가하려 한다. 그런데 같은 절(§5-2)의 예시 19는 별도의 `ADD CONSTRAINT FOREIGN
KEY(...) REFERENCES ...` 구문을 쓴다. 두 예시가 같은 목적(외래키 추가)을 서로 다른 문법으로 표현하고
있는데, 이 스펙을 위해 컬럼 정의 내부에 `FOREIGN KEY` 키워드를 다시 쓰는 새 문법을 추가하는 것인지,
기존 CUBRID 파서에 이미 있는 문법인지 스펙에서 확인할 수 없다.

**구체 예제**: 위 코드블록 자체가 예제다. 비교를 위해 예시 19를 나란히 두면 차이가 드러난다.
```sql
-- 예시 19 스타일 (CONSTRAINT 절)
ALTER TABLE new_orders ADD CONSTRAINT FOREIGN KEY(customer_id)
REFERENCES customers(customer_id);

-- 예시 20 스타일 (컬럼 정의 내부)
ALTER TABLE new_orders ADD COLUMN
(customer_id INT FOREIGN KEY REFERENCES customers(customer_id));
```

**예제 설명**: 동일한 결과(customer_id 컬럼에 FK 추가)를 얻기 위한 두 문장이 서로 다른 문법 스타일을
쓰고 있다. 문서 하나에서 같은 기능에 두 가지 문법이 섞여 있으면, 구현자가 두 문법을 모두 지원해야
하는지 아니면 예시 20이 단순 오기(誤記)인지 판단할 수 없다.

**제안**: 두 문법 중 실제로 지원할 것을 하나로 통일하고, 다른 하나는 예시에서 제거하거나 "동등한 대체
표현"이라고 명시한다.

### 리뷰 12

**[심각도: 보통] 트리거·시리얼(SERIAL/AUTO_INCREMENT) 등 스펙이 언급하지 않은 객체와의 상호작용이 없다**

**대상**: 스펙 전체, 특히 §4-2 예시 12/15 (RK 컬럼 삭제 제한)

**문제 설명**: RK 컬럼에 걸린 BEFORE/AFTER 트리거가 그 컬럼 값을 조작하는 경우, 트리거가 만든 최종 값과
복제 로그에 기록되는 RK 값의 정합성을 어떻게 보장하는지 언급이 없다. 또한 RK로 쓰이는 PK 컬럼이
AUTO_INCREMENT(내부적으로 SERIAL 객체가 값을 발급)인 경우, RK가 PK에서 UK로 전환된 뒤에도 SERIAL
객체와 컬럼의 연결·복제 순서가 꼬이지 않는지 다루지 않는다.

**구체 예제**:
```sql
CREATE TABLE tbl (
    id INT AUTO_INCREMENT PRIMARY KEY,
    b INT NOT NULL UNIQUE
) REPLICATION = ON;

CREATE TRIGGER trg_before_upd BEFORE UPDATE ON tbl
    -- 트리거 본문에서 id 값을 재계산/조작한다고 가정

-- RK를 id(PK)에서 b(UK)로 전환
ALTER TABLE tbl DROP CONSTRAINT PRIMARY KEY, ADD CONSTRAINT UNIQUE(id);
```

**예제 설명**: 전환 이후에도 트리거는 여전히 id를 조작하지만, 복제 로그의 행 식별 기준은 이제 b다.
트리거가 만드는 id 변경 자체는 더 이상 "이 행을 찾는 열쇠"가 아니게 되는데, 이런 재검토가 필요하다는
안내가 스펙에 없어 사용자가 전환 후에도 예전처럼 id 기반으로 로직을 짜 놓은 트리거를 방치하기 쉽다.

**제안**: RK 전환 시 관련 트리거·시리얼 객체를 재점검하라는 운영 가이드를 최소한 문서 수준에서
언급해야 한다.

### 리뷰 13

**[심각도: 보통] FK CASCADE 삭제 규칙과 RK 보호 규칙 중 어느 것이 우선하는지 불명확하다**

**대상**: 예시 12 (RK 컬럼 DROP 시 ERROR), §5 (FK 참조 제약)

**문제 설명**: 예시 12는 RK로 쓰이는 컬럼을 단독으로 삭제하려는 경우만 다룬다. 그런데 그 컬럼이 동시에
다른 테이블의 FK가 `ON DELETE CASCADE`로 참조하는 상위 키라면, "RK 보호 규칙"과 "FK 참조 규칙" 둘 다
이 DROP을 막을 이유가 있다. 스펙은 어느 검사가 먼저 수행되고 사용자에게 어떤 메시지가 나가는지 말하지
않는다. 예시 12의 결과도 그냥 "ERROR"라고만 되어 있어 원인 구분이 안 된다.

**구체 예제**:
```sql
CREATE TABLE parent (
    id INT PRIMARY KEY
) REPLICATION = ON;

CREATE TABLE child (
    cid INT PRIMARY KEY,
    pid INT,
    CONSTRAINT fk_p FOREIGN KEY(pid) REFERENCES parent(id) ON DELETE CASCADE
) REPLICATION = ON;

ALTER TABLE parent DROP COLUMN id;
-- (1) parent.id는 RK이므로 삭제 불가 -> ERROR
-- (2) child.pid가 참조 중이므로 삭제 불가 -> ERROR
-- 두 사유 중 무엇이 먼저 뜨는지, 혹은 둘 다 알려주는지 스펙에 없다.
```

**예제 설명**: 두 가지 독립적인 제약 위반이 동시에 성립하는 상황에서, 사용자에게 노출되는 에러 메시지가
어느 규칙에서 나온 것인지에 따라 사용자의 다음 행동(FK부터 정리할지, RK부터 바꿀지)이 달라진다.

**제안**: 검사 순서를 명시하거나, 두 사유를 모두 담은 에러 메시지를 내도록 규정한다.

### 리뷰 14

**[심각도: 보통] §7 "파일 리스트" 용어가 모호하고, 전수 검사의 비용이 언급되지 않았다**

**대상**: §7 "제약사항 위반 시 에러와함께 파일 리스트를 출력한다"

**문제 설명**: CUBRID에서 테이블은 볼륨·페이지 단위 내부 파일로 저장되며, 사용자에게 노출되는 단위는
보통 "테이블(클래스)"이다. "파일 리스트"라는 표현이 테이블 이름 목록을 뜻하는 것인지, 실제 OS 파일
경로를 뜻하는 것인지 불명확하다. 또한 HA 시작(`cubrid hb start`)마다 전체 카탈로그를 스캔해 모든
테이블의 RK 존재 여부와 모든 FK 참조 관계를 검사해야 하는데, 테이블 수가 많은 스키마에서 이 전수 검사의
시간 복잡도나 필요한 잠금 수준이 언급되지 않았다. failover가 잦은 상황에서는 HA 재시작 자체가 반복되므로
이 검사가 재시작 지연의 원인이 될 수 있다.

**구체 예제**:
```
$ cubrid hb start mydb
ERROR: 다음 테이블에 복제 키가 없습니다:
  - schema1.tbl_no_rk
  - schema2.legacy_table
  (파일: ??? )
```

**예제 설명**: 실제 CUBRID 사용자가 이 에러를 받았을 때 "파일"이라는 단어를 보고 OS 상의 실제 파일
경로를 찾으러 갈 수도 있는데, 실제로 고쳐야 할 대상은 테이블 스키마다. 용어 하나 때문에 문제 해결
경로가 어긋날 수 있다.

**제안**: "파일 리스트"를 "제약사항을 위반하는 테이블 목록"으로 명확히 바꾸고, 대규모 스키마에서의 검사
시간에 대한 기준(또는 최소한 "이 검사는 O(테이블 수 + FK 수)로 수행된다" 같은 성능 특성)을 명시한다.

### 리뷰 15

**[심각도: 보통] 예시 2/20/23의 CREATE TABLE 구문에 반복되는 트레일링 콤마 오타**

**대상**: 예시 2, 예시 20, 예시 23

**문제 설명**: 트레일링 콤마(trailing comma)란 목록의 마지막 항목 뒤에 불필요하게 남은 콤마를 말한다.
대부분의 SQL 문법은 이를 허용하지 않아 파싱 에러가 난다. 이 스펙의 여러 CREATE TABLE 예시가 이 오타를
그대로 갖고 있다.

**구체 예제**:
```sql
-- 예시 2
CREATE TABLE repl_table_without_rk(
    a INT,
);

-- 예시 20 (일부)
CREATE TABLE new_orders(
    order_id INT PRIMARY KEY
);
-- (이 문장 자체는 문제 없으나 예시 23은 아래처럼 콤마가 남는다)

-- 예시 23
CREATE TABLE new_orders(
    order_id INT PRIMARY KEY,
);
```

**예제 설명**: 예시 2는 "RK 없는 복제 테이블은 싱글 모드에서만 생성 가능"이라는 규칙을 보여주려는
목적인데, SQL 자체가 파싱조차 되지 않으면 이 예시로 규칙을 검증할 수 없다. 구현 기준 문서에 있는
예제가 실행 불가능한 코드라면, 구현자가 이 예제를 그대로 테스트 케이스로 옮겨 쓸 때 엉뚱한 실패를
겪는다.

**제안**: 모든 SQL 예제를 실제로 파싱·실행해 문법 오류가 없는지 확인한 뒤 스펙에 반영해야 한다.

### 리뷰 16

**[심각도: 보통] REPLICATION이 새 예약어가 되는지, 기존 식별자와 충돌하는지 언급이 없다**

**대상**: §2, 예시 8 (SHOW CREATE TABLE 출력의 옵션 나열 순서)

**문제 설명**: 예약어(reserved word)란 SQL 파서가 특별한 의미로 미리 점유해 컬럼명·테이블명 등
일반 식별자로 쓸 수 없게 만드는 단어다. `REPLICATION`을 새 테이블 옵션 키워드로 추가하면서, 이 단어를
예약어로 승격할지 아니면 비예약 식별자(컨텍스트에 따라 옵션으로도, 이름으로도 쓰일 수 있는 단어)로
남겨둘지에 대한 언급이 없다. 이는 하위 호환성(기존에 만들어 둔 스키마가 새 버전에서도 그대로 동작하는지)
문제로 직결된다.

**구체 예제**:
```sql
-- 기존(변경 전 버전)에 이미 존재할 수 있는 스키마
CREATE TABLE replication (
    id INT PRIMARY KEY,
    status VARCHAR(20)
);
-- REPLICATION이 예약어로 승격되면, 새 버전에서 위 CREATE TABLE 자체가
-- 파싱 에러가 날 수 있다.
```

**예제 설명**: 실제로 "replication"이라는 이름의 테이블/컬럼을 쓰던 사용자가 업그레이드 후 스키마를
다시 로드하려다 예약어 충돌로 실패하는 상황을 보여준다.

**제안**: REPLICATION을 비예약 키워드로 처리하도록 문법을 설계하고, 이를 스펙에 명시한다.

### 리뷰 17

**[심각도: 보통] §9 요약과 §2-2/§4 본문 사이의 방향 비대칭이 근거 없이 방치되어 있다**

**대상**: §9 "RK가 있는 테이블 역시 복제 제외대상이 될 수 있음" vs §2-2 "HA 모드에서는 복제 제외
테이블이 복제 테이블로 변경될 수 없다"

**문제 설명**: 두 문장을 합치면 "HA 중엔 ON→OFF는 항상 허용되고 OFF→ON은 항상 금지된다"는 비대칭
규칙이 되는데, 이 비대칭의 근거(왜 한쪽 방향만 막는지)가 스펙 어디에도 설명돼 있지 않다. OFF→ON을
막는 이유는 짐작이 간다(전환 순간 슬레이브에 그 테이블의 과거 데이터가 없어 갑자기 복제가 시작되면
초기 동기화 문제가 생기기 때문일 것이다). 그런데 ON→OFF는 왜 아무 제약 없이 항상 허용되는지에 대한
설명이 없고, 리뷰 5·6에서 지적한 새로운 위험(FK 참조 붕괴, 슬레이브 데이터 고착)을 그대로 열어두는
선택이 의도적인지 누락인지 알 수 없다.

**구체 예제**: (리뷰 5, 6의 예제와 동일한 시나리오가 이 비대칭 규칙의 실제 결과다.)

**예제 설명**: 방향에 따라 안전장치의 유무가 다른데, 그 이유가 스펙에 설명되지 않으면 향후 유지보수자가
"OFF→ON을 막는 이유가 사라졌으니 완화해도 되지 않을까" 같은 잘못된 판단을 내리기 쉽다.

**제안**: 두 방향 각각에 대해 허용/금지의 근거를 명문화하고, ON→OFF에도 리뷰 5의 FK 검사를 대칭적으로
추가할지 여부를 결정해 스펙에 반영한다.

### 리뷰 18

**[심각도: 사소] REPLICATION 옵션 표기 스타일이 문서 내에서 통일되어 있지 않다**

**대상**: 예시 8 (`REPLICATION ON`), CREATE/ALTER TABLE 구문 (`REPLICATION=ON` / `REPLICATION = ON`),
예시 9 db_class 출력 (`replication : ON`)

**문제 설명**: 같은 옵션이 스펙 안에서 최소 세 가지 형태로 등장한다. `=` 유무, 공백 유무가 제각각이다.
SHOW CREATE TABLE의 출력(`REPLICATION ON`, 등호 없음)이 그대로 다시 입력 가능한(round-trip) DDL
문법인지, 순수 출력 전용 표기인지도 불명확하다.

**구체 예제**:
```sql
CREATE TABLE t (a INT PRIMARY KEY) REPLICATION=ON;    -- 예시 1 스타일
CREATE TABLE t (a INT PRIMARY KEY) REPLICATION = ON;   -- 본문 서술 스타일
-- SHOW CREATE TABLE 출력: ... REPLICATION ON   (등호 없음)
```

**예제 설명**: 표기가 통일되지 않으면 문서를 읽는 사람이 "이 셋이 정말 같은 문법인지, 아니면 출력
전용과 입력 전용이 다른 문법인지" 헷갈릴 수 있다.

**제안**: 스펙 전체에서 하나의 표기(`REPLICATION=ON`)로 통일하고, SHOW CREATE TABLE 출력이 재입력
가능한 문법임을 명시한다.

### 리뷰 19

**[심각도: 사소] §3의 "복제 키를 추가하거나"라는 표현이 §4-2의 "RK는 직접 수정 불가" 원칙과 표현상 충돌한다**

**대상**: §3 "싱글 모드에서 생성된 복제 키가 없는 테이블은 HA모드 전환 시 복제 키를 추가하거나 복제
제외 테이블로 변경할 수 있어야한다."

**문제 설명**: §1에 따르면 복제 키(RK)는 사용자가 직접 지정하는 대상이 아니라 PK/UK 존재 여부로부터
엔진이 자동으로 도출하는 파생 개념이다. §4-2도 "복제키는 큐브리드 엔진에 의해 결정되며, 사용자는
복제키를 직접 수정할 수 없다"고 명시한다. 그런데 §3은 "복제 키를 추가"라는 표현을 써서, 마치 RK 자체를
사용자가 지정하는 대상인 것처럼 읽힌다.

**구체 예제**:
```sql
-- §3의 문구를 문자 그대로 읽으면 마치 이런 문법이 있는 것처럼 오해할 수 있다
ALTER TABLE tbl SET REPLICATION_KEY (b);   -- 이런 문법은 스펙 어디에도 없다

-- 실제로 해야 하는 것은 PK/UK 제약을 추가하는 것뿐이다
ALTER TABLE tbl ADD CONSTRAINT UNIQUE(b);
```

**예제 설명**: 이 예제는 §3 문구의 오독 가능성을 보여준다. §4-2를 함께 읽지 않으면 "RK를 직접 지정하는
문법이 있을 것"이라고 잘못 추측할 수 있다.

**제안**: §3의 표현을 "PK 또는 NOT NULL UNIQUE 제약을 추가해 복제 키 후보를 확보하거나"로 바꿔 §1/§4-2와
용어를 일치시킨다.

### 리뷰 20

**[심각도: 사소] 복합 UK와 단일 컬럼 UK 사이의 우선순위가 언급되지 않았다**

**대상**: §1 RK 결정 기준

**문제 설명**: RK 결정 규칙은 "PK 우선, 없으면 UK, UK가 여럿이면 순서상 가장 빠른 것"이라고만 되어
있다. UK는 컬럼 하나짜리 단일 UK와 여러 컬럼을 묶은 복합 UK가 혼재할 수 있는데, 복합 UK가 RK로 선택되면
매 UPDATE/DELETE 복제 로그마다 여러 컬럼 값을 함께 실어 행을 식별해야 하므로 단일 컬럼 RK보다 로그
크기와 비교 비용이 커진다. 스펙은 단일 컬럼 UK를 복합 UK보다 우선할지, 순수하게 "순서"만 볼지 규정하지
않는다.

**구체 예제**:
```sql
CREATE TABLE t2 (
    a INT,
    b INT,
    c INT,
    UNIQUE (b, c),   -- 복합 UK, 먼저 선언됨
    UNIQUE (a)       -- 단일 컬럼 UK, 나중에 선언됨
);
-- "명시된 순서 중 가장 빠른 순서" 규칙을 그대로 적용하면 RK = (b, c) 복합 키가 선택된다.
```

**예제 설명**: 성능·로그 크기 관점에서는 단일 컬럼 `a`가 RK로 더 적합할 수 있지만, 스펙의 규칙을 문자
그대로 따르면 먼저 선언된 복합 UK가 선택되어 매번 두 컬럼 값을 비교해야 하는 상대적으로 무거운 RK가
채택된다.

**제안**: 단일 컬럼 UK를 복합 UK보다 우선하는 규칙을 추가하거나, 최소한 이 트레이드오프를 스펙에서
언급해 구현자가 임의로 정하지 않도록 한다.
