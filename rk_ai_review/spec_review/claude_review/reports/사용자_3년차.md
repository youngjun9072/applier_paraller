# CUBRID HA 복제 개선 스펙 리뷰 — 최종 사용자(3년차) 관점

## 리뷰어 소개

이 리뷰를 작성한 사람은 SQL을 매일 직접 작성해 서비스 DB를 다루는 3년차 실무자다. DBA도
아니고 엔진 개발자도 아니며, 매일 `CREATE TABLE`, `ALTER TABLE`, 마이그레이션 스크립트를
작성하고 장애 시 콘솔에 뜨는 에러 메시지를 보고 즉시 판단을 내려야 하는 입장이다. 복제
아키텍처의 내부 구현보다는 "내가 짠 SQL이 언제 성공하고 언제 실패하는지, 실패하면 무엇을
해야 하는지"가 가장 중요한 관심사다.

## 총평

이 스펙은 복제 키(RK: Replication Key, 복제할 때 마스터와 슬레이브의 로우를 식별하는 데
쓰이는 키)의 선택 기준과 `REPLICATION` 옵션의 동작 규칙 자체는 나쁘지 않게 정리되어 있다.
하지만 실무자가 매일 마주치는 문제인 "언제 내 SQL이 실패하는가"와 "실패했을 때 무엇을 해야
하는가"에 대한 설명이 매우 부족하다. 대부분의 예시가 결과를 그냥 `ERROR` 한 단어로만 표기하고
있어 실제 CUBRID 콘솔에서 어떤 문구가 뜨는지, 그 문구를 보고 사용자가 무엇을 고쳐야 하는지
전혀 알 수 없다. 또한 스펙이 애초에 해결하려던 문제(PK 컬럼 속성 변경 시 복제 누락)의
핵심 시나리오인 "컬럼 타입 변경"이 본문 어디에도 명시적으로 다뤄지지 않고, 예시 SQL 중
일부는 문법 오류를 그대로 포함하고 있다. RK 선택이 엔진에 의해 자동으로 이루어지는데
정작 사용자가 "지금 이 테이블의 RK가 무엇인지" 조회할 방법이 스펙에 없다는 점도, 매일 스키마를
만지는 실무자 입장에서는 상당히 불안한 설계 공백이다.

## 리뷰 1

**[심각도: 치명] `REPLICATION` 생략 시 기본값이 `ON`인 것은 위험한 조용한 기본값이다**

대상: §2-1 "이 옵션은 생략 가능하며 생략시 ON으로 자동으로 복제 테이블로 생성된다."

문제 설명: 옵션을 아예 안 쓰면 무조건 복제 대상(ON)이 된다. 즉 실무자가 이 스펙의 존재를
모르고 예전 방식 그대로 `CREATE TABLE`을 계속 쓰면, 아무 경고 없이 모든 새 테이블이 복제
대상으로 잡힌다. 문제는 그 다음이다 — HA(High Availability, 마스터 장애 시 슬레이브가
자동으로 대신 서비스를 이어받는 이중화 구성) 모드로 전환하는 순간, RK가 없는 테이블은
전환 실패로 이어진다(§7). 즉 "아무것도 안 하면 안전하다"는 통상적인 기본값 설계 원칙과
반대로, "아무것도 안 하면 나중에 HA 전환이 막힌다"는 지뢰가 깔린다.

```sql
-- 개발자가 REPLICATION을 전혀 모른 채 평소처럼 테이블을 만든다
csql> CREATE TABLE audit_log(
    id INT,
    msg VARCHAR(200),
    created_at DATETIME
);
-- 성공. 그런데 이 테이블은 PK도 UK도 없으므로 RK가 없다.
-- REPLICATION을 명시하지 않았으므로 기본값 ON이 적용되어 "복제 대상인데 RK 없음" 상태가 된다.
```

예제 설명: 위 SQL은 지금 당장은 아무 에러도 내지 않고 성공한다. 문제는 몇 주/몇 달 뒤
누군가 이 DB를 HA로 전환하려 할 때 비로소 드러난다(§7, "제약사항 위반 시 에러와 함께 파일
리스트를 출력"). 스키마를 만든 사람과 HA 전환을 시도하는 사람이 다른 조직에서는, 원인
불명의 전환 실패로 이어질 소지가 크다.

제안: 기본값을 ON으로 유지하더라도, RK 후보(PK/UK)가 전혀 없는 테이블을 만들 때는 싱글
모드에서도 경고(WARNING)를 즉시 띄우는 것이 안전하다. 최소한 `CREATE TABLE` 성공 메시지에
"이 테이블은 RK가 없어 HA 전환 시 실패합니다"라는 안내 문구를 포함해야 한다.

## 리뷰 2

**[심각도: 치명] 같은 `CREATE TABLE`이 "지금 성공"하고 "나중에(HA 전환 시)"에야 실패한다 — 실패 시점 지연**

대상: §2-1 예시 2, §4-1 예시 10, §7

문제 설명: 예시 2는 RK 없는 테이블을 싱글 모드에서 `REPLICATION=ON`으로 만드는 것이
성공(`OK` 취급)이라고 설명한다. 반면 예시 10은 똑같은 형태의 테이블을 HA 모드에서 만들면
`ERROR`다. 즉 "복제 키 없는 복제 테이블 생성"이라는 동일한 의도의 SQL이 실행 시점(싱글이냐
HA냐)에 따라 성공/실패가 갈린다. 스펙 자체는 이를 §4-1에서 명시하고 있어 논리적 모순은
아니지만, 사용자 입장에서는 "분명히 저번에 됐던 SQL인데 왜 지금 안 되지?"라는 혼란을 겪게
되는 전형적인 직관 위반 사례다. 더 큰 문제는 §7에 따르면 이 실패가 `CREATE TABLE` 시점이
아니라 "HA 실행 시"(`cubrid hb start`) 시점에 한꺼번에 검사되어 파일 리스트로 통보된다는
점이다. 즉 실패의 원인이 되는 SQL을 실행한 시점과 실패가 드러나는 시점이 완전히 분리된다.

```sql
-- (1) 싱글 모드에서 실행 — 성공
csql> CREATE TABLE staging_import(
    a INT
) REPLICATION = ON;
-- OK

-- (2) 몇 주 뒤, 운영자가 HA 전환을 시도
$ cubrid hb start mydb
-- ERROR: 다음 테이블에 복제 키가 없습니다: staging_import (그리고 다른 N개)
```

예제 설명: (1)에서 스키마를 만든 사람은 아무 이상을 못 느끼고 넘어간다. (2)를 실행하는
사람(대개 운영 담당자)은 스키마 작성자가 아닐 수 있고, 어떤 SQL이 원인인지 즉시 알 수 없다.
실무에서 스키마 변경과 HA 전환 작업은 시점도, 담당자도 분리되어 있는 경우가 많아 이 지연된
실패는 디버깅 비용을 키운다.

제안: `CREATE TABLE ... REPLICATION=ON` 실행 시점에 RK 후보가 없으면 싱글 모드라도 최소
경고를 표시하거나, 아예 `csql`의 `\schema` 류 명령에서 "RK 없음" 테이블 목록을 한 번에 뽑아볼
수 있는 조회 기능을 §2-3에 추가해야 한다.

## 리뷰 3

**[심각도: 치명] 배경 문제의 핵심 시나리오였던 "컬럼 타입 변경"이 본문 어디에도 없다**

대상: 작업지시 배경("HA가 실행 중인 상태에서 사용자가 테이블의 PK 컬럼 속성을 변경하면") vs §4-2 전체

문제 설명: 이 스펙이 만들어진 계기는 "PK 컬럼의 속성(타입 등)을 변경했을 때 복제가 깨진다"는
실제 장애다. 그런데 §4-2에서 다루는 DDL은 전부 "제약 추가/삭제"(`ADD CONSTRAINT`,
`DROP CONSTRAINT`, `DROP COLUMN`)뿐이고, RK로 쓰이는 컬럼의 **타입을 바꾸는**
`ALTER TABLE ... MODIFY`/`CHANGE COLUMN` 류 DDL에 대한 규칙이 전혀 언급되지 않는다. 3년차
실무자가 흔히 겪는 "이 컬럼이 알고 보니 너무 작아서 `INT`를 `BIGINT`로 늘려야 한다" 같은
작업이 정작 이 스펙이 막으려던 원인 시나리오와 정확히 겹치는데, 스펙에는 해당 케이스에 대한
언급이 없다.

```sql
-- customer_id가 RK(PK)인 상태에서, ID 값 범위가 커져 타입을 늘려야 하는 흔한 상황
csql> ALTER TABLE customers MODIFY customer_id BIGINT;
-- 이 SQL은 §4-2의 어느 예시에도 해당하지 않는다. 성공? 실패? 실패라면 메시지는?
```

예제 설명: 이 SQL은 컬럼을 삭제하지도, 제약을 새로 추가/삭제하지도 않는다. 순수하게
타입만 바꾼다. 그런데 이 스펙이 해결하려는 원본 장애가 바로 "PK 컬럼 속성 변경"이었으므로,
이 문장이야말로 스펙이 명시적으로 검증했어야 할 첫 번째 케이스다. §4-2 목록에 없다는 것은
구현이 이를 허용/차단 중 어느 쪽으로 처리할지 문서로는 알 수 없다는 뜻이다.

제안: §4-2에 "RK로 사용 중인 컬럼의 타입 변경" 항목을 별도로 추가하고, PK인 경우/UK인
경우 각각의 허용 여부와 에러 메시지 예시를 명시해야 한다.

## 리뷰 4

**[심각도: 중요] 예시 대부분이 `ERROR`라고만 적혀 있고 실제 에러 메시지가 없다**

대상: 예시 5, 6, 10, 12, 15, 16, 19-패턴의 대응 실패 예시, 22, 23

문제 설명: 작업지시에서 요구한 "에러 메시지의 이해 가능성과 조치 안내"가 스펙 문서에서
가장 부실한 부분이다. 예시 11은 그나마 `ERROR: Primary key "pk_tbl_a" already defined for
class "dba.tbl".`처럼 구체적인 문구를 보여주지만, 대부분의 실패 예시(5, 6이 아니라 6은 OK,
10, 12, 15, 16 등)는 그냥 `ERROR` 한 단어다. 사용자는 실제 콘솔에서 어떤 문구가 뜨는지,
그 문구에 "다른 UK를 RK로 지정하세요" 같은 조치 안내가 포함되는지 전혀 알 수 없다.

```sql
-- 예시 16: 복제키 후보가 없다면 DROP INDEX 불가
csql> DROP INDEX idx_id ON tbl;
-- 스펙: ERROR
-- 실제로 뜰 문구는? "ERROR: cannot drop unique index idx_id, it is the last
--  replication key candidate of table tbl" 같은 안내가 있는지 스펙에 없음
```

예제 설명: 이 예시 하나만 봐서는, 사용자가 왜 인덱스를 못 지우는지 알 방법이 없다. 실제
운영에서는 "인덱스가 느려서 재구성하려는데 갑자기 DROP이 막혔다"는 상황을 마주친 사용자가
원인을 못 찾고 헤맬 수 있다. 에러 메시지에 "이 인덱스는 마지막 남은 복제 키 후보입니다"
같은 문구가 없다면 사용성 관점에서 낙제점이다.

제안: 모든 에러 예시에 실제 출력될 메시지 문구를 명시하고, 메시지 안에 최소한 "왜 막혔는지
(RK 관련임)"와 "무엇을 하면 되는지(대체 RK를 먼저 만들거나 REPLICATION=OFF로 바꾸라)"가
포함되도록 요구사항에 못박아야 한다.

## 리뷰 5

**[심각도: 중요] UK가 여러 개일 때 엔진이 자동으로 하나를 고르는데, 그 결과를 조회할 방법이 없다**

대상: §1 "UK가 여러개 존재한다면 큐브리드 엔진에 의해 이 중 하나가 선택된다(ex. 테이블내에
명시된 순서 중 가장 빠른 순서)"

문제 설명: "가장 빠른 순서"라는 기준 자체가 모호하다("명시된 순서"가 `CREATE TABLE` 문
안의 컬럼 정의 순서인지, 제약 정의 순서인지, 내부 OID 순서인지 불명확하다). 게다가 이
선택은 사용자가 관여할 수 없는 자동 처리인데, 정작 "지금 이 테이블의 RK로 어떤 UK가
선택되어 있는지" 확인할 SQL이 스펙 어디에도 제시되지 않는다. RK가 무엇인지 몰라야 하는데
%4-2에서는 "복제키를 수정하는 DDL이 제한"된다고 하니, 사용자는 자신이 어떤 DDL을 실행하면
막힐지 예측조차 할 수 없다.

```sql
csql> CREATE TABLE product(
    id INT,
    sku VARCHAR(30) NOT NULL UNIQUE,
    barcode VARCHAR(30) NOT NULL UNIQUE
);
-- sku, barcode 둘 다 UK 후보. 스펙상 "가장 빠른 순서"인 sku가 RK가 될 것으로 추정되지만
-- 이를 확인할 SQL이 스펙에 없다.
csql> ALTER TABLE product DROP CONSTRAINT u_product_barcode; -- 되는지 안 되는지 예측 불가
```

예제 설명: barcode를 지우려는 사용자는 sku가 RK로 선택되어 있다면 이 DDL이 성공해야
한다(§4-2: "다른 복제키 후보가 함께 존재한다면 모든 DDL은 허용"). 하지만 사용자가 sku가
RK인지 barcode가 RK인지 미리 알 방법이 없으므로, 결과를 실행 전에 예측할 수 없다.

제안: `show create table` 또는 `db_class` 계열 카탈로그(시스템이 스키마 정보를 저장해
두는 내부 테이블)에 현재 RK로 선택된 제약/컬럼 이름을 명시적으로 노출해야 한다.

## 리뷰 6

**[심각도: 중요] 예시 8, 9의 조회 결과에 RK가 어떤 컬럼/제약인지 나오지 않는다**

대상: §2-3 예시 8("show create table"), 예시 9("select * from db_class")

문제 설명: 예시 8의 결과는 `REPLICATION ON`만 보여줄 뿐, 그 테이블의 RK가 PK인지 UK인지,
어떤 제약 이름인지는 나오지 않는다. 예시 9도 `replication : ON`이라는 필드만 추가되었을
뿐이다. §2-3의 제목은 "REPLICATION 조회"이지 "RK 조회"가 아니어서, 애초에 이 절이 다루는
범위가 REPLICATION 여부로 한정되어 있다는 점 자체가 문제다. RK가 무엇인지는 사용자에게
가장 중요한 정보인데 조회 대상에서 빠져 있다.

```sql
csql> show create table tbl;
-- 'CREATE TABLE [tbl] (... CONSTRAINT [pk_tbl_a] PRIMARY KEY ([a])) ... REPLICATION ON'
-- 이 출력만으로 "지금 RK가 pk_tbl_a"라는 걸 알려면, 사용자가 직접 "PK가 있으면 그게
-- RK다"라는 §1의 규칙을 다시 떠올려 수동으로 판단해야 한다.
-- 만약 PK도 UK도 여러 개라면 이 출력만으로는 RK를 특정할 수 없다.
```

예제 설명: PK가 하나뿐인 단순한 케이스에서는 그나마 유추가 가능하지만, UK가 여러 개
존재하는 테이블에서는 위 SQL 결과만으로 RK를 확정할 수 없다(리뷰 5 참고). 즉 §2-3은
"REPLICATION 여부"는 보여주지만 "RK가 무엇인지"는 보여주지 못하는 반쪽짜리 조회 기능이다.

제안: `show create table` 출력에 `REPLICATION ON (RK: pk_tbl_a)`처럼 RK로 선택된 제약
이름을 함께 표기하고, `db_class`에도 `replication_key` 컬럼을 추가해야 한다.

## 리뷰 7

**[심각도: 중요] 예시 2, 예시 23의 CREATE TABLE 문 자체가 문법 오류(trailing comma)를 담고 있다**

대상: §2-1 예시 2, §5-2 예시 23

문제 설명: 예시 2:

```sql
csql> CREATE TABLE repl_table_without_rk(
    a INT,
);
```

마지막 컬럼 정의 뒤에 콤마가 있고 바로 닫는 괄호가 온다. 표준 SQL이나 CUBRID의 통상적인
DDL 문법에서 이런 트레일링 콤마는 문법 오류로 처리되는 것이 일반적이다. 예시 23도 동일한
문제를 가진다:

```sql
csql> CREATE TABLE new_orders(
    order_id INT PRIMARY KEY,
);
```

예제 설명: 이 문서는 사용자가 그대로 복사해서 실행해볼 것을 전제로 한 예시 모음이다.
그런데 그대로 복붙하면 "복제 키가 없어서 발생하는 에러"가 아니라 "문법 오류"가 먼저
발생할 가능성이 높다. 3년차 실무자가 이 문서를 학습 자료 삼아 따라 하다가 엉뚱한 에러를
만나면, 그것이 복제 스펙 때문인지 자신의 타이핑 실수인지 구분하지 못하고 시간을 낭비하게
된다.

제안: 모든 예시 SQL을 실제로 CUBRID에 태워서 결과를 재검증하고, 트레일링 콤마를
제거하거나 CUBRID가 이를 실제로 허용한다면 "CUBRID는 트레일링 콤마를 허용한다"는 각주를
추가해야 한다.

## 리뷰 8

**[심각도: 중요] 예시 20, 23의 "INT FOREIGN KEY REFERENCES" 인라인 문법이 나머지 예시와 문법 스타일이 다르다**

대상: §5-2 예시 20, 예시 23

문제 설명: 예시 17~19, 21, 22는 전부 `CONSTRAINT fk_xxx FOREIGN KEY (col) REFERENCES
tbl(col)` 형태의 명시적 제약 문법을 쓴다. 그런데 예시 20과 23만 유독
`ADD COLUMN (customer_id INT FOREIGN KEY REFERENCES customers(customer_id))`처럼
컬럼 정의 안에 `FOREIGN KEY REFERENCES`를 인라인으로 붙이는 문법을 쓴다. 이게 CUBRID가
실제로 지원하는 별도 축약 문법인지, 아니면 단순히 스펙 작성자가 실수로 다르게 쓴 것인지
문서만으로는 판단할 수 없다.

```sql
-- 예시 19 스타일 (명시적 CONSTRAINT)
csql> ALTER TABLE new_orders ADD CONSTRAINT FOREIGN KEY(customer_id)
REFERENCES customers(customer_id);

-- 예시 20 스타일 (인라인, 컬럼 추가와 동시)
csql> ALTER TABLE new_orders ADD COLUMN
(customer_id INT FOREIGN KEY REFERENCES customers(customer_id));
```

예제 설명: 두 SQL은 결과적으로 같은 일(외래키 추가)을 하려는 것으로 보이지만 문법 형태가
다르다. 실무자는 "컬럼을 새로 추가하면서 동시에 FK를 걸 때는 인라인 문법을, 기존 컬럼에
FK만 추가할 때는 CONSTRAINT 문법을 쓴다"는 규칙이 있는지, 아니면 둘 다 아무 때나 쓸 수
있는지 알 수 없다. 이 구분이 불명확한 채로 문서화되면 사용자는 어느 쪽을 표준으로 따라야
할지 혼란스럽다.

제안: 두 문법의 관계(둘 다 지원되는 동의어인지, 상황별 필수 문법인지)를 명시하고, 이 스펙
문서가 아니라 기존 CUBRID DDL 매뉴얼과 일치하는지 교차 확인해야 한다.

## 리뷰 9

**[심각도: 중요] "복제키 후보가 1개냐 여러 개냐"로 허용 DDL 전체가 갈리는데 이 개수를 사전에 확인할 방법이 없다**

대상: §4-2 "테이블에 하나의 복제키만 존재한다면 복제키를 수정하는 DDL이 제한되지만, 다른
복제키 후보가 함께 존재한다면 모든 DDL은 허용된다"

문제 설명: 이 문장은 사실상 이 스펙에서 가장 중요한 분기점이다. 그런데 "복제키 후보의
개수"라는, 사용자가 DDL을 실행하기 전에 반드시 알아야 할 값을 확인할 명령어가 스펙 어디에도
없다. 사용자는 결국 DDL을 일단 실행해보고 성공/실패로 역추적해야 한다.

```sql
-- 사용자는 이 테이블에 RK 후보가 몇 개인지 미리 알고 싶다
csql> ALTER TABLE tbl DROP CONSTRAINT u_tbl_b;  -- 성공할까? 실패할까?
-- 성공하면: 이 컬럼은 RK 후보가 아니었거나, 다른 후보가 남아있었다는 뜻
-- 실패하면: 이 UK가 마지막 RK 후보였다는 뜻
-- 결과를 보고 나서야 사전 상태를 역산해야 한다
```

예제 설명: 정상적인 워크플로우라면 사용자는 DDL 실행 전에 "이 컬럼을 지워도 되는지"를
판단할 수 있어야 한다. 그런데 이 스펙 구조에서는 실행해서 에러를 받아야만 판단이 가능하다.
운영 DB에서 이런 "일단 해보고 실패하면 롤백"식 접근은 위험 부담이 크다.

제안: `SHOW REPLICATION KEY CANDIDATES ON tbl` 같은 조회 명령, 혹은 §6(db_class 계열)에
현재 RK 후보 개수와 목록을 노출하는 컬럼을 추가해야 한다.

## 리뷰 10

**[심각도: 중요] 예시 11의 에러 메시지에 등장하는 제약 이름 `pk_tbl_a`가 어떻게 만들어졌는지 스펙에 없다**

대상: §4-2 예시 11 "ERROR: Primary key "pk_tbl_a" already defined for class "dba.tbl"."

문제 설명: 이 예시의 원본 테이블이 `PRIMARY KEY(a)`처럼 이름 없이 정의됐다면, 에러 메시지에
찍힌 `pk_tbl_a`는 CUBRID가 자동으로 생성한 이름일 것이다. 그런데 이 자동 명명 규칙(테이블
이름 + 컬럼 이름 조합으로 추정)이 스펙 어디에도 설명되어 있지 않다. 실무자가 예시 12의
`DROP PRIMARY KEY` 대신 `DROP CONSTRAINT`로 제약을 지정해서 지우고 싶을 때, 제약 이름을
몰라서 못 지우는 상황이 실제로 자주 발생한다.

```sql
csql> CREATE TABLE tbl(a INT PRIMARY KEY, b INT);
-- 이 PK의 제약 이름은 무엇인가? pk_tbl_a로 자동 생성되는가?
csql> ALTER TABLE tbl DROP CONSTRAINT pk_tbl_a;  -- 이 이름을 어떻게 알아냈는가?
```

예제 설명: 사용자가 `CREATE TABLE`에서 제약 이름을 명시하지 않은 경우, 나중에 그 제약을
`DROP CONSTRAINT`로 지목하려면 자동 생성된 이름 규칙을 알아야 한다. 이 규칙이 스펙에
없으므로, 사용자는 매번 `show create table`로 이름을 확인하는 우회 절차를 거쳐야 한다.

제안: RK 관련 제약의 자동 명명 규칙을 §2-3 또는 부록에 명시하고, 가능하면 에러 메시지에
"제약 이름을 모른다면 show create table로 확인하십시오" 같은 조치 안내를 포함해야 한다.

## 리뷰 11

**[심각도: 중요] 이미 운영 중인 FK 관계에서 참조 테이블을 나중에 `REPLICATION=OFF`로 바꾸는 경로가 막혀 있는지 불명확하다**

대상: §5, §4-2

문제 설명: §5는 "복제 대상 테이블이 참조하는 모든 테이블은 복제 대상이어야 한다"고
규정한다. 그런데 이미 FK로 참조되고 있는 테이블에 대해 나중에 누군가
`ALTER TABLE customers REPLICATION=OFF;`를 실행하면 어떻게 되는지 §4-2, §5 어디에도
나오지 않는다. §4의 "복제 제외테이블은 ALTER TABLE … REPLICATION=ON 을 이용한 복제 테이블로
변경하는것 외의 모든 DDL을 사용할 수 있다"는 문장을 그대로 적용하면, 참조되고 있는 테이블도
`REPLICATION=OFF`로 바뀔 수 있다는 뜻이 되어 §5가 막으려던 상황(참조 테이블이 슬레이브에
없음)이 뒷문으로 재현될 수 있다.

```sql
-- 예시 17 상태: orders(REPLICATION 기본 ON)가 customers(REPLICATION ON)를 FK로 참조
csql> ALTER TABLE customers REPLICATION = OFF;
-- 이 SQL은 §4에 따르면 "복제 제외 테이블로 변경하는 것"이므로 허용되는 것처럼 보인다.
-- 그러나 이 순간 orders(복제 대상)가 참조하는 customers는 복제 제외가 되어
-- §5가 경고한 정확히 그 문제 상황(Failover 후 orders는 있는데 customers는 없음)이 발생한다.
```

예제 설명: §5는 "테이블을 만들 때/FK를 추가할 때" 참조 무결성을 검사하는 이야기만 하고
있다. 이미 만들어진 FK 관계의 부모 테이블을 나중에 복제 제외로 바꾸는 경로에 대한 언급이
없다는 것은, 구현에서 이 케이스를 놓쳤을 가능성을 시사한다.

제안: §5에 "이미 FK로 참조되고 있는 복제 대상 테이블을 REPLICATION=OFF로 변경하려는
시도"에 대한 명시적 규칙(허용/차단 여부와 에러 메시지)을 추가해야 한다.

## 리뷰 12

**[심각도: 보통] §6 VIEW 절이 데이터 불일치를 사전 경고 없이 방치한다 — 리포트/집계 뷰 사용자가 소리 없이 틀린 값을 받는다**

대상: §6 "복제 제외테이블이 뷰에 포함되어 있을 경우 ... 이 부분에대해 큐브리드 복제 모듈은 책임지지 않는다"

문제 설명: 3년차 실무자는 흔히 대시보드나 정기 리포트용으로 여러 테이블을 조인한 뷰를
만들어 쓴다. Failover(장애 전환) 후 슬레이브에서 그 뷰를 조회했을 때, 조인에 포함된 테이블
중 하나가 복제 제외 테이블이면 그 결과는 마스터에서 조회했을 때와 다르게 나온다. 문제는
이 상황에서 아무 에러도, 경고도 뜨지 않고 그냥 "다른 값"이 조용히 반환된다는 점이다.

```sql
csql> CREATE VIEW order_summary AS
SELECT o.order_id, o.customer_id, c.country
FROM orders o JOIN non_repl_customers c ON o.customer_id = c.customer_id;
-- non_repl_customers는 REPLICATION=OFF

-- Failover 후 슬레이브에서:
csql> SELECT * FROM order_summary;
-- customers 데이터가 슬레이브에 없으므로 INNER JOIN 결과가 비거나 줄어든다.
-- 에러 없이 "결과가 이상하게 적다"만 관찰된다.
```

예제 설명: 이 SQL은 에러를 내지 않는다. 그래서 사용자는 자신이 조회한 결과가 실제로
불완전하다는 사실을 스스로 눈치채기 전까지는 전혀 알 수 없다. 리포트 값이 실제보다 적게
나와도 시스템이 아무 신호를 주지 않으므로, 잘못된 의사결정으로 이어질 위험이 있다.

제안: 최소한 뷰 생성 시점에 "이 뷰는 복제 제외 테이블을 포함합니다"라는 경고를 출력하거나,
`show create view`에 참조 테이블의 REPLICATION 상태를 표기해야 한다.

## 리뷰 13

**[심각도: 보통] §7 "에러와 함께 파일 리스트를 출력한다"는데 그 형식과 확인 방법이 없다**

대상: §7 "HA 실행시 다음 사항을 제약사항을 확인하며, 제약사항 위반 시 에러와함께 파일 리스트를 출력한다"

문제 설명: "파일 리스트"라는 표현이 구체적으로 무엇을 의미하는지 불명확하다. 로그
파일(`.log`)의 목록인지, 위반한 테이블 이름의 목록을 담은 텍스트 파일인지, 혹은 콘솔에
바로 찍히는 테이블 이름 나열을 "파일"이라고 표현한 것인지 알 수 없다. 실무자가 HA 전환에
실패했을 때 어디를 봐야 원인 테이블 목록을 확인할 수 있는지가 이 스펙만으로는 파악되지
않는다.

```sql
$ cubrid hb start mydb
-- ERROR: (파일 리스트?) ...
-- 실무자는 이 시점에 다음 중 무엇을 해야 하는가?
-- - 화면에 스크롤되어 지나간 출력을 다시 봐야 하나?
-- - 특정 로그 파일 경로를 열어봐야 하나?
-- - cubrid 관리 명령으로 재조회가 가능한가?
```

예제 설명: 위반 테이블이 수십, 수백 개라면 콘솔에 한 번 출력되고 지나가는 형태로는 실무자가
따라가며 하나씩 고치기 어렵다. "파일"이라는 단어를 썼다면 실제로 파일 경로를 제공하는
것인지 스펙에 명시해야, 사용자가 그 경로를 열어 목록을 검토하고 스크립트로 일괄 처리할 수
있다.

제안: 파일 리스트의 실제 형식(파일 경로, 포맷: 텍스트/CSV/JSON), 위치, 그리고 그 파일을
읽는 방법을 §7에 구체적으로 명시해야 한다.

## 리뷰 14

**[심각도: 보통] §8 unload/load 시 "복제 여부를 저장하는 변수"의 이름과 조회/설정 방법이 없다**

대상: §8 "load시 복제 여부를 저장하는 변수에따라 복제 테이블 혹은 복제 제외 테이블로 생성된다"

문제 설명: 이 "변수"가 무엇을 가리키는지(unload된 데이터 파일 내부의 메타데이터 필드인지,
`loaddb` 명령의 옵션 플래그인지) 구체적으로 나와 있지 않다. 데이터 이관 작업은 실무자가
분기별로 자주 겪는 흔한 시나리오(운영 DB를 다른 서버로 옮기거나 백업에서 복원)인데, 이
변수의 실체를 모르면 이관 후 어떤 테이블이 복제 대상으로 잡힐지 예측할 수 없다.

```sh
$ unloaddb -i mydb
# 결과 파일에 REPLICATION 여부가 어떤 형태로 기록되는지 스펙엔 없음
$ loaddb -d mydb_new < mydb.unload
# 이 시점에 각 테이블의 REPLICATION이 언제/어떻게 결정되는지 불명
```

예제 설명: 실무자가 흔히 쓰는 "운영 DB를 스테이징으로 복제해서 테스트한다"는 작업에서,
이관된 스테이징 DB의 REPLICATION 설정이 원본과 다르게 잡히면 스테이징에서의 HA 테스트
결과가 운영과 어긋날 수 있다. 변수의 실체를 몰라서 발생하는 문제다.

제안: unload 파일 포맷에서 REPLICATION 여부가 기록되는 필드명/위치를 §8에 명시하고,
`loaddb` 옵션으로 이 값을 강제 오버라이드할 수 있는지도 함께 문서화해야 한다.

## 리뷰 15

**[심각도: 보통] `REPLICATION=OFF`로 전환할 때 슬레이브에 이미 있던 데이터의 운명이 언급되지 않는다**

대상: §2-2 예시 6, §4

문제 설명: 복제 대상이던 테이블을 `REPLICATION=OFF`로 바꾸면(예시 6), 그 순간까지 이미
슬레이브에 복제되어 있던 데이터는 어떻게 되는지 스펙에 없다. 그대로 남아 마스터와 점점
벌어지는 스냅샷처럼 방치되는 것인지, 삭제되는 것인지 알 수 없다.

```sql
-- customers는 REPLICATION=ON 상태로 1만 건이 슬레이브에 이미 복제되어 있다
csql> ALTER TABLE customers REPLICATION = OFF;
-- OK
-- 이후 마스터에서 customers에 INSERT/UPDATE/DELETE를 계속하면 슬레이브의 기존 1만 건은
-- 더 이상 갱신되지 않는다. 이 "정지된 스냅샷"이 슬레이브에 계속 남아있는가?
```

예제 설명: 슬레이브에 남은 오래된 customers 데이터를 애플리케이션이 실수로 계속 읽는다면,
"복제 제외했으니 당연히 비어있겠지"라는 사용자의 기대와 달리 낡은 데이터가 계속 조회되는
사고로 이어질 수 있다.

제안: `REPLICATION=OFF` 전환 시 슬레이브에 남은 기존 데이터를 그대로 둘지, 정리(TRUNCATE)할지를
명시하고, 어느 쪽이든 사용자에게 알림 메시지로 안내해야 한다.

## 리뷰 16

**[심각도: 보통] 예시 13의 "PK를 다른 컬럼으로 변경" — 다중 ALTER의 원자성(중간 상태)이 불명확하다**

대상: §4-2 예시 13 "ALTER TABLE table_name DROP CONSTRAINT PRIMARY KEY, ADD CONSTRAINT PRIMARY KEY(a);"

문제 설명: 이 SQL은 하나의 `ALTER TABLE` 문 안에 PK 삭제와 새 PK 추가를 함께 넣은
형태다("원자성"이란 여러 동작이 마치 하나의 동작처럼 전부 성공하거나 전부 실패해야 한다는
성질을 말한다). 그런데 이 문장이 하나의 트랜잭션으로 원자적으로 처리되는지, 아니면 내부적으로
DROP을 먼저 커밋한 뒤 ADD를 별도로 처리하는지 스펙에 없다. 만약 원자적이지 않다면, DROP과
ADD 사이의 찰나에 이 테이블은 RK가 하나도 없는 상태가 되고, 그 순간 복제 로그가 어떻게
처리되는지가 §1의 "RK 없으면 HA 실행 불가" 원칙과 충돌할 소지가 있다.

```sql
csql> ALTER TABLE tbl DROP CONSTRAINT PRIMARY KEY,
ADD CONSTRAINT PRIMARY KEY(a);
-- 이 한 문장 실행 도중 DROP 완료~ADD 완료 사이에 tbl은 RK가 없는 순간이 존재하는가?
-- 그 순간 다른 세션이 tbl에 INSERT를 하면 그 로그는 복제되는가, 에러가 나는가?
```

예제 설명: 단일 SQL 문 안에서의 원자성 여부는 동시성 환경에서 실제 서비스 트래픽이 계속
들어오는 운영 DB에 이 DDL을 적용할 때 결정적으로 중요하다. 이 설명이 없으면 실무자는
"이 DDL을 서비스 운영 중에 실행해도 안전한지" 판단할 근거가 없다.

제안: 이런 복합 ALTER 문이 단일 트랜잭션으로 원자 처리됨을 명시하고, 처리 도중 들어오는
동시 DML에 대한 동작(대기/에러)도 함께 설명해야 한다.

## 리뷰 17

**[심각도: 보통] "다른 복제키 후보가 함께 존재한다면 모든 DDL은 허용된다"는 문장이 실제로 무엇을 허용하는지 목록화되어 있지 않다**

대상: §4-2 "다른 복제키 후보가 함께 존재한다면 모든 DDL은 허용된다(단, 기존의 제약사항은 유지된다.)"

문제 설명: "모든 DDL이 허용된다"는 표현이 지나치게 포괄적이다. 예를 들어 RK가 아닌 나머지
UK를 지우는 것도 허용되는지, 컬럼 타입을 바꾸는 것도 허용되는지, 테이블 자체를 DROP하는
것도 "모든 DDL"에 포함되는지 구체적으로 나열되어 있지 않다. "기존의 제약사항은 유지된다"는
단서가 무엇을 가리키는지도 모호하다(예: PK 중복 금지 같은 CUBRID의 원래 제약을 말하는
것으로 추정되지만 명시적이지 않다).

```sql
-- RK 후보가 2개(pk_a, u_b)인 상태라고 가정
csql> ALTER TABLE tbl MODIFY a BIGINT;  -- RK로 쓰이는 컬럼 a의 타입 변경도 "모든 DDL"에 포함되는가?
csql> DROP TABLE tbl;                    -- 테이블 자체 삭제도 "모든 DDL"에 포함되는가?
```

예제 설명: 극단적인 예로 `DROP TABLE`까지 "모든 DDL"에 포함된다고 해석하면 자명해서
문제가 없어 보이지만, 리뷰 3에서 지적한 "타입 변경"처럼 애매한 경계의 DDL은 이 포괄적
문장만으로는 허용 여부가 실무자에게 확신을 주지 못한다.

제안: "모든 DDL"이라는 표현 대신, RK와 무관한 컬럼/제약에 대한 조작이라는 조건을 구체적인
DDL 종류(ADD/DROP/MODIFY COLUMN, ADD/DROP CONSTRAINT 등) 표로 나열해 명시해야 한다.

## 리뷰 18

**[심각도: 사소] §4-2의 "기존의 연산 결과와 동일한 경우 PK, UK를 비교하기위한 예시만 표기한다"는 문장이 어색해 의미 파악이 어렵다**

대상: §4-2 도입부

문제 설명: 이 문장은 아마 "PK를 RK로 쓰는 경우와 UK를 RK로 쓰는 경우 중, 기존 CUBRID
동작과 똑같이 유지되는 부분은 생략하고 비교가 필요한 예시만 보여준다"는 의도로 추정되지만,
실제 문장은 주어와 목적어 관계가 불분명해서 처음 읽는 사람은 몇 번을 다시 읽어야 의미를
파악할 수 있다. 컴퓨터공학과 입문서 수준의 문체를 요구하는 이 리뷰 기준에서 보면, 문서
자체의 문장이 이미 그 기준에 못 미친다.

```
원문: "기존의 연산 결과와 동일한 경우 PK, UK를 비교하기위한 예시만 표기한다."
```

예제 설명: 이 문장 자체는 SQL이 아니지만, 문서를 처음 읽는 3년차 실무자가 이 절 전체의
구성 원칙(왜 어떤 케이스는 예시가 있고 어떤 케이스는 생략됐는지)을 이해하는 데 필요한
핵심 안내문이다. 문장이 불명확하면 뒤에 이어지는 예시 11~16이 "왜 이 조합만 다뤄지는지"에
대한 맥락 없이 툭 던져진 것처럼 읽힌다.

제안: "PK를 RK로 사용하는 경우와 UK를 RK로 사용하는 경우의 동작은 대부분 동일하다. 이하
예시에서는 차이가 나는 부분만 골라 보여준다"처럼 명확한 한국어 문장으로 다시 쓸 것을
제안한다.

## 리뷰 19

**[심각도: 보통] 인덱스 재구성(DROP INDEX 후 CREATE INDEX 재생성)이라는 흔한 운영 패턴이 RK 후보 UK에 적용될 때의 동작이 불명확하다**

대상: §4-2 예시 16, §1

문제 설명: 실무자는 인덱스 성능 문제로 종종 "기존 인덱스를 지우고 새 정렬 옵션/컬럼
조합으로 다시 만든다"는 재구성 작업을 한다. 예시 16은 "복제키 후보가 없다면 DROP INDEX가
안 된다"만 보여줄 뿐, 이 UK를 지우고 나서 곧바로 새 UK를 다시 만들면 어떻게 되는지는
스펙에 없다. 만약 하나의 트랜잭션 안에서 DROP과 CREATE를 순서대로 실행한다면, 리뷰 16과
동일한 "중간 상태에 RK가 없는 순간" 문제가 인덱스 재구성 시나리오에서도 똑같이 발생한다.

```sql
-- tbl의 유일한 RK 후보가 UNIQUE INDEX idx_id 하나뿐인 상황
BEGIN;
csql> DROP INDEX idx_id ON tbl;              -- §1/예시16에 따르면 이 시점에 이미 ERROR?
csql> CREATE UNIQUE INDEX idx_id2 ON tbl(id); -- 도달할 수 있는가?
COMMIT;
```

예제 설명: 예시 16의 규칙을 곧이곧대로 적용하면 첫 줄인 `DROP INDEX`부터 막혀서 두 번째
줄에 도달조차 못 한다. 즉 "RK 후보 UK를 다른 이름/정의의 UK로 교체"하는 흔한 인덱스
재구성 작업 자체가 이 스펙 하에서는 불가능해 보이는데, 이것이 의도된 제약인지 아니면
"DROP과 CREATE를 한 트랜잭션/한 ALTER 문으로 묶으면 허용"되는 별도 경로가 있는지 스펙에
설명이 없다.

제안: 예시 13(PK 교체)처럼 UK도 "DROP CONSTRAINT ..., ADD CONSTRAINT ..." 형태의 단일
ALTER 문으로 교체하는 정식 경로를 제시하고, DROP INDEX + CREATE INDEX의 2단계 방식은
막힌다는 점과 그 이유를 명시해야 한다.

## 리뷰 20

**[심각도: 사소] §9 SUMMARY의 서술 순서가 초심자에게 중요한 사실("RK 있어도 복제 제외 가능")을 뒤쪽에 묻어버린다**

대상: §9 "RK가 있는 테이블 역시 복제 제외대상이 될 수 있음" (세 번째 항목)

문제 설명: 이 스펙을 처음 읽는 사용자는 "복제 제외 테이블 = PK/UK가 없는 테이블"이라고
직관적으로 오해하기 쉽다(실제로 예시 3이 "PK가 존재하지만 복제 제외 테이블로 생성"이라는
반례를 보여주긴 하지만, 절 구성상 이 사실이 SUMMARY의 세 번째 항목으로 다시 나올 때까지
강조되지 않는다). 학습 곡선 관점에서, "RK 유무"와 "REPLICATION 여부"가 서로 독립적인
두 개의 축이라는 점이 문서 초반에 더 강하게 명시되지 않으면 사용자는 계속 두 개념을
섞어서 생각하게 된다.

```sql
-- 흔한 오해: "PK가 있으니까 당연히 복제되겠지"
csql> CREATE TABLE archive_orders(
    order_id INT PRIMARY KEY,
    data TEXT
) REPLICATION = OFF;
-- PK가 멀쩡히 있어도 REPLICATION=OFF이면 복제되지 않는다.
```

예제 설명: 이 테이블은 RK 후보(PK)를 명백히 갖고 있지만 복제되지 않는다. "RK가 있다"와
"복제된다"는 완전히 별개의 두 조건이라는 사실은 이 스펙 전체를 관통하는 가장 기초적인
전제인데, 본문에서는 이 사실이 예시 3에서 지나가듯 등장할 뿐 개념적으로 명시적인 도입
문단이 없다.

제안: §1 도입부 첫 문단에 "RK 존재 여부"와 "REPLICATION 옵션"은 서로 독립적인 두 축이라는
점을 표나 다이어그램으로 명시하고, SUMMARY에 있는 이 문장을 문서 맨 앞으로 끌어올려야
한다.
