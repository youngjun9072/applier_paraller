# CUBRID HA 복제(REPLICATION 옵션/RK) 스펙 리뷰 — 응용 개발자(DB 사용) · 1년차 관점

## 리뷰어 소개

저는 CUBRID를 백엔드 데이터베이스로 사용하는 애플리케이션을 개발한 지 1년 된 응용 개발자입니다. ORM(Object-Relational Mapping, 객체와 테이블을 자동으로 매핑해주는 라이브러리. 예: JPA/Hibernate)과 Flyway/Liquibase 같은 스키마 마이그레이션 도구를 이용해 DDL(Data Definition Language, `CREATE TABLE`/`ALTER TABLE`처럼 스키마 구조를 정의·변경하는 SQL 종류)을 CI/CD 파이프라인으로 자동 배포하는 업무를 맡고 있습니다. DBA(데이터베이스 관리자)만큼 엔진 내부를 알지는 못하지만, 개발-스테이징(싱글 서버)과 운영(HA, High Availability, 마스터 장애 시 슬레이브가 대신 서비스를 이어받는 이중화 구성) 환경 간의 동작 차이가 배포 사고로 이어지는 경우를 자주 겪습니다.

## 총평

이번 스펙은 복제 키(RK) 자동 선택과 `REPLICATION={ON|OFF}` 옵션이라는 컨셉 자체는 이해하기 어렵지 않지만, "이 문서만 보고 마이그레이션 자동화 파이프라인을 안전하게 설계할 수 있는가"라는 기준으로 보면 곳곳에 구멍이 있습니다. 가장 큰 문제는 (1) 제약 위반이 검증되는 시점이 싱글 모드(개발/스테이징)가 아니라 HA 전환·실행 시점(운영)으로 미뤄져 있어 dev/prod parity(개발과 운영 환경의 동작 일치성)가 깨진다는 점, (2) 예시로 제시된 DDL이 실제 마이그레이션 도구가 생성하는 SQL 패턴(제약 하나당 한 문장)과 맞지 않는다는 점, (3) 에러 메시지·에러 코드·카탈로그 조회 방법이 거의 명시되지 않아 자동화 파이프라인이 실패를 프로그래밍적으로 감지할 수 없다는 점입니다. 또한 예제 SQL 자체에 문법 오류(trailing comma)가 있고, 일부 용어("파일 리스트", "Failover")는 정의 없이 사용되어 신입 개발자가 그대로 따라 하기엔 위험합니다. 아래 20개 리뷰에서 구체적인 근거와 재현 시나리오를 제시합니다.

### 리뷰 1

**[심각도: 치명] RK 없는 테이블이 있을 때 HA 시작 실패 범위가 불명확하다**

**대상**: §1(제약 사항) "HA 모드 실행 시 복제 테이블은 ... 복제 키가 존재하지 않으면 HA모드를 실행 할 수 없다" / §4-1(예시 10) / §7(HA 전환)

**문제 설명**: §1은 "HA모드를 실행 할 수 없다"고 말하는데, 이것이 (a) DB 서버 전체가 HA 모드로 못 뜨는 것인지, (b) 문제가 되는 그 테이블 하나만 복제 대상에서 제외되고 나머지는 정상적으로 HA가 도는 것인지 구분이 안 됩니다. §7에서는 "제약사항 위반 시 에러와함께 파일 리스트를 출력한다"고 되어 있어 (a)처럼 보이지만, 만약 운영 DB에 테이블이 수백 개고 그중 하나가 실수로 RK를 잃었다면, 전체 서비스가 HA 전환에 실패해 다운되는 것인지 응용 개발자 입장에서는 매우 중요한 정보인데 스펙에 명시적 문장이 없습니다.

**구체 예제(시나리오)**:
```
-- 운영 DB에 테이블이 200개 있다고 가정
-- 그중 1개(coupon_log)가 실수로 PK/UK를 모두 잃은 상태로 배포됨(개발자 실수)
ALTER TABLE coupon_log DROP CONSTRAINT pk_coupon_log;
-- (싱글 모드/개발 환경에서는 §3에 의해 이 DDL이 문제없이 성공한다)

-- 이후 운영에서 정기 점검 후 HA 재기동
$ cubrid hb start mydb
```

**예제 설명**: 위 시나리오는 실수로 특정 테이블 하나만 RK를 잃은 뒤 `cubrid hb start`로 HA를 재기동하는 상황입니다. 이때 `mydb` 전체가 뜨지 않아 관련 없는 다른 199개 테이블까지 서비스 불가가 되는지, 아니면 `coupon_log`만 복제에서 빠지고 나머지는 정상 기동되는지에 따라 장애 파급 범위가 완전히 달라집니다. 응용 개발자가 배포 전 체크리스트를 만들 때 이 답이 없으면 "전체 장애 가능성이 있다"는 가정하에 과도하게 방어적인 배포 절차를 짜거나, 반대로 안일하게 넘어갔다가 전체 장애를 겪을 수 있습니다.

**제안**: HA 시작 실패의 단위(서버 전체 vs 테이블 단위)를 명시하고, 테이블 단위라면 어떤 상태(복제 제외로 강등되는지, 아예 접근 불가가 되는지)가 되는지 §7에 표로 정리해야 합니다.

### 리뷰 2

**[심각도: 치명] 예시 13의 "DROP CONSTRAINT + ADD CONSTRAINT 한 문장" 요구가 실제 마이그레이션 도구의 SQL 생성 패턴과 맞지 않는다**

**대상**: §4-2 예시 13 (PK를 다른 컬럼으로 변경)

**문제 설명**: 예시 13은 `ALTER TABLE table_name DROP CONSTRAINT PRIMARY KEY, ADD CONSTRAINT PRIMARY KEY(a);`처럼 DROP과 ADD를 **쉼표로 묶어 한 문장**에 넣어야 성공(OK)한다고 보여줍니다. 반면 예시 12는 PK만 단독으로 DROP하면 에러가 납니다("HA 환경에서 PK가 복제키로 사용될 경우 이 PK 혹은 PK 컬럼은 삭제할 수 없다"). 그런데 Flyway, Liquibase, JPA(Hibernate) `ddl-auto` 같은 실무 마이그레이션 도구들은 대부분 제약 하나를 하나의 `ALTER TABLE` 문으로 생성합니다(변경 이력을 단위별로 추적하기 위함). 즉 "DROP과 ADD를 한 문장에 묶어야 한다"는 요구사항 자체가 이런 도구들의 기본 동작 방식과 충돌합니다.

**구체 예제(SQL, Liquibase 스타일 changelog가 생성하는 실제 DDL)**:
```sql
-- Liquibase changelog가 별도 changeSet 두 개로 나눠 생성하는 전형적인 패턴
-- changeSet 1
ALTER TABLE table_name DROP PRIMARY KEY;      -- 예시 12에 의해 ERROR

-- changeSet 2 (changeSet 1이 성공했다고 가정할 때만 실행됨)
ALTER TABLE table_name ADD CONSTRAINT PRIMARY KEY(a);
```

**예제 설명**: 실무에서 스키마 변경 이력을 관리하는 도구는 "PK를 옮긴다"는 의도를 하나의 원자적 SQL 문으로 표현하지 않고, 사람이 검토하기 쉽도록 "제거"와 "추가"를 별개의 변경 단위(changeSet/migration file)로 쪼개는 경우가 매우 흔합니다. 이 스펙대로라면 changeSet 1 단계에서 이미 에러가 나서 마이그레이션 자체가 실패하고, 개발자는 도구가 생성한 코드를 손으로 다시 합쳐야 합니다. 즉 이 컨셉은 "도구를 안 쓰고 손으로 SQL을 짜는 경우"만 상정한 것으로 보이며, 자동화 파이프라인과 정면으로 충돌합니다.

**제안**: 마이그레이션 도구가 생성하는 "분리된 DROP/ADD 두 문장" 패턴을 트랜잭션(하나의 커밋 단위) 안에서 실행하면 허용되는지 여부를 명시하십시오. 만약 반드시 한 SQL 문으로 묶어야만 한다면, 그 이유(중간 상태에서 RK가 0개가 되는 순간을 허용하지 않기 위함으로 추정)를 문서화하고, 트랜잭션 내에서라면 두 문장으로 나눠도 되는지 별도로 규정해야 합니다.

### 리뷰 3

**[심각도: 치명] FK-복제대상 무결성 검증이 싱글 모드에서는 이루어지지 않아 dev/prod parity가 깨진다**

**대상**: §5(외래키), §3(Single 제약사항: "제약은 없으나...")

**문제 설명**: §5는 "HA 모드에서 외래키를 포함한 테이블을 생성한다면 참조 테이블 역시 반드시 복제 대상 테이블이여야한다"고 명시하지만, §3은 싱글 모드에서는 "제약은 없다"고 말합니다. 즉 이 FK-복제상태 정합성 검사는 싱글 모드(대부분의 개발/스테이징 환경)에서는 전혀 작동하지 않고, HA 전환 시점(§7) 혹은 HA에서 직접 DDL을 수행하는 시점(§5-2)에만 걸립니다. 개발자는 로컬/스테이징(싱글 모드)에서 자유롭게 FK를 걸고 테스트를 통과시킨 뒤, 운영(HA) 배포 시점에야 처음으로 이 제약을 만나게 됩니다.

**구체 예제(단계별 시나리오)**:
```sql
-- [1단계] 로컬 개발 환경 (싱글 모드) — §3에 의해 아무 제약 없이 성공
CREATE TABLE audit_customers(
    customer_id INT PRIMARY KEY,
    country INT
) REPLICATION=OFF;   -- "감사용이라 굳이 복제할 필요 없다"는 개발자 판단

CREATE TABLE orders(
    order_id INT PRIMARY KEY,
    customer_id INT,
    CONSTRAINT fk_orders_audit FOREIGN KEY (customer_id) REFERENCES audit_customers(customer_id)
);
-- 싱글 모드에서는 OK. 유닛 테스트/통합 테스트 모두 통과.

-- [2단계] CI/CD 파이프라인이 동일 DDL을 운영 HA 클러스터에 적용
--         (§5-2, 예시 18과 동일한 상황)
-- ERROR (참조 테이블 audit_customers가 REPLICATION=OFF이므로 거부)
```

**예제 설명**: 위 시나리오는 개발자가 로컬에서 정상적으로 개발·테스트를 마친 스키마 변경이, 순전히 "싱글 모드냐 HA 모드냐"라는 실행 환경 차이 때문에 운영 배포 단계에서 처음 실패하는 경우를 보여줍니다. 문제는 이 실패가 코드 리뷰나 로컬 테스트로는 절대 걸러지지 않고, 오직 실제 운영 클러스터에 배포를 시도해야만 드러난다는 점입니다. 이는 "PK 컬럼 속성 변경 시 발생하는 기존 장애"와 근본적으로 같은 유형의 문제(개발 시점과 운영 시점 검증 시점 불일치)를 새 스펙으로도 그대로 재현할 위험이 있습니다.

**제안**: 싱글 모드에서도 (강제 차단은 아니더라도) `WARNING` 수준으로 "이 FK는 REPLICATION=OFF 테이블을 참조합니다"라는 경고를 출력하거나, `csql`/DDL 린트 도구가 이 조합을 사전에 검출할 수 있도록 카탈로그 조회 방법을 제공해야 합니다.

### 리뷰 4

**[심각도: 중요] 복제 키 자동 선택 기준("테이블 내 명시된 순서")이 ORM/마이그레이션 도구가 생성하는 DDL 순서에 의존해 예측 불가능하다**

**대상**: §1 "UK가 여러개 존재한다면 큐브리드 엔진에 의해 이 중 하나가 선택된다(ex. 테이블내에 명시된 순서 중 가장 빠른 순서)"

**문제 설명**: "ex."라는 표현으로 보아 이것이 확정된 규칙인지 예시일 뿐인지도 불분명하지만, 설령 확정 규칙이라 해도 "테이블 내 명시된 순서"는 사람이 손으로 `CREATE TABLE`을 작성할 때는 안정적일 수 있어도, ORM이 엔티티 어노테이션 순서·필드 선언 순서·리플렉션 순서에 따라 자동 생성하는 DDL에서는 실행마다 순서가 달라질 수 있습니다. 결과적으로 어떤 UK가 RK가 될지 애플리케이션 개발자가 전혀 통제할 수 없고 예측도 어렵습니다.

**구체 예제(SQL)**:
```sql
-- JPA 엔티티에 @Table(uniqueConstraints = {...}) 두 개를 선언한 경우
-- Hibernate가 생성하는 DDL의 제약 순서는 JPA 버전/필드 선언 순서에 따라 달라질 수 있음
CREATE TABLE members(
    id INT,
    email VARCHAR(100) NOT NULL,
    phone VARCHAR(20) NOT NULL,
    CONSTRAINT uk_members_email UNIQUE(email),
    CONSTRAINT uk_members_phone UNIQUE(phone)
);
-- 개발자가 "email이 RK가 되겠지"라고 기대해도, 엔진이 phone을 RK로 고를 수도 있음
```

**예제 설명**: `email`과 `phone` 두 개의 NOT NULL UNIQUE 제약이 있는 테이블에서 어느 쪽이 RK가 될지는 스펙상 "테이블 내 명시 순서"에 달려 있는데, 이 순서는 ORM 프레임워크의 버전 업그레이드나 엔티티 클래스 필드 재배치만으로도 바뀔 수 있습니다. RK가 바뀌면 복제 알고리즘 내부 동작(어떤 컬럼으로 UPDATE/DELETE 대상을 식별하는지)이 달라지므로, 애플리케이션 코드는 전혀 바꾸지 않았는데 배포 도구 버전만 올렸다가 복제 동작이 은근히 달라지는 사고가 가능합니다.

**제안**: RK로 어떤 제약이 선택되었는지 정적으로 결정하는 우선순위를 "제약 이름의 사전순" 등 명확하고 재현 가능한 규칙으로 문서화하거나, 사용자가 `CREATE TABLE ... REPLICATION KEY(email)`처럼 명시적으로 지정할 수 있는 옵션을 제공해야 합니다(현재는 "직접 수정할 수 없다"고만 되어 있어 지정 수단이 아예 없음, §4-2).

### 리뷰 5

**[심각도: 중요] REPLICATION OFF→ON 롤백 불가에 대한 마이그레이션 가이드가 없다**

**대상**: §2-2 "단, HA 모드에서는 복제 제외 테이블이 복제 테이블로 변경될 수 없다"

**문제 설명**: 운영 중인 HA 환경에서 한 번 `REPLICATION=OFF`로 바꾼 테이블은 다시 `REPLICATION=ON`으로 되돌릴 수 없습니다(예시 5는 ERROR). 그런데 만약 개발자가 실수로, 혹은 초기 설계 판단 착오로 특정 테이블을 OFF로 잘못 설정했다가 뒤늦게 이를 정정해야 하는 경우 어떻게 해야 하는지 스펙에 절차가 없습니다.

**구체 예제(단계별 시나리오)**:
```sql
-- 운영 HA에서 실수로 로그 테이블을 복제 제외로 전환
ALTER TABLE order_events REPLICATION=OFF;   -- OK (예시 6과 동일 패턴)

-- 한 달 후: order_events 데이터가 슬레이브에도 필요하다는 것을 뒤늦게 발견
ALTER TABLE order_events REPLICATION=ON;    -- ERROR (예시 5와 동일 패턴, §2-2)
```

**예제 설명**: 위 시나리오는 실수로 복제를 끈 테이블을 되돌리려 할 때 정상적인 방법이 막혀 있음을 보여줍니다. 스펙 어디에도 "이럴 때는 테이블을 새로 만들고 데이터를 옮겨라" 같은 대안이 제시되지 않아서, 신입 개발자는 이 상황에 부딪히면 처음부터 해결 방법을 스스로 찾아야 합니다. 이는 실수 복구 비용이 큰 설계로, 최소한 권장 우회 절차(예: 새 테이블 생성 후 데이터 이관 및 이름 교체)를 문서에 명시해야 합니다.

**제안**: OFF→ON 전환이 막힌 이유(슬레이브에 데이터 갭이 생겨 무결성을 보장할 수 없기 때문으로 추정)를 설명하고, 공식적인 우회 절차(예: 신규 테이블 생성 + 데이터 백필 + 테이블 스왑)를 "운영 가이드" 섹션으로 추가해야 합니다.

### 리뷰 6

**[심각도: 중요] REPLICATION ON→OFF 전환 시 슬레이브에 이미 존재하는 데이터의 처리 방침이 없다**

**대상**: §2-2 예시 6 (`ALTER TABLE tbl REPLICATION=OFF;` → OK)

**문제 설명**: 어떤 테이블을 운영 중에 `REPLICATION=OFF`로 바꾸면, 그 순간까지 이미 슬레이브로 복제되어 있던 데이터는 어떻게 되는지 스펙에 없습니다. 슬레이브에서 삭제(TRUNCATE)되는지, 그냥 그 시점의 스냅샷 상태로 방치(더 이상 갱신되지 않음)되는지에 따라 failover(마스터 장애로 슬레이브가 서비스를 이어받는 것) 이후 애플리케이션이 보게 되는 데이터가 완전히 달라집니다.

**구체 예제(단계별 시나리오)**:
```sql
-- [T0] 마스터에서 정상 운영 중, inventory 테이블은 REPLICATION=ON
--      슬레이브에도 최신 재고 데이터가 존재

-- [T1] 운영자가 성능상의 이유로 inventory를 복제 제외로 전환
ALTER TABLE inventory REPLICATION=OFF;   -- OK

-- [T2] 마스터에서 재고 변경이 계속 발생 (슬레이브에는 더 이상 반영 안 됨)
UPDATE inventory SET stock = stock - 1 WHERE product_id = 100;

-- [T3] 마스터 장애로 Failover 발생, 애플리케이션이 슬레이브를 향해 조회
SELECT stock FROM inventory WHERE product_id = 100;
-- T1 시점의 오래된 재고 값이 반환되는가, 아니면 테이블 자체가 빈 상태인가?
```

**예제 설명**: T1에서 복제를 끈 이후 T2까지 마스터에서 발생한 변경분이 슬레이브에 전혀 반영되지 않은 채로 T3에서 failover가 일어나면, 애플리케이션은 "테이블은 존재하지만 오래된 값"을 볼 수도 있고 "완전히 빈 테이블"을 볼 수도 있습니다. 재고처럼 비즈니스 로직이 값에 의존하는 테이블이라면 이 차이는 치명적인 오작동(초과 판매 등)으로 이어질 수 있는데, 스펙은 §1에서 "REPLICATION OFF로 인한 데이터 불일치는 책임지지 않는다"고만 하고 정확히 어떤 상태가 되는지는 설명하지 않습니다.

**제안**: `REPLICATION=OFF` 전환 시점의 슬레이브 데이터 처리(유지/삭제) 동작을 명시하고, 애플리케이션이 failover 후 이 테이블 상태를 사전에 판별할 수 있는 카탈로그 신호(예: "마지막 복제 시각")를 제공해야 합니다.

---

### 리뷰 7

**[심각도: 중요] 카탈로그(db_class 등)에서 실제 RK로 선택된 컬럼/제약을 조회할 방법이 없다**

**대상**: §2-3 예시 8, 예시 9 (show create table / select * from db_class)

**문제 설명**: 예시 8과 9는 `REPLICATION ON` 여부만 보여줄 뿐, 여러 UK 후보 중 실제로 무엇이 RK로 선택되었는지는 출력하지 않습니다. 카탈로그(catalog, DB가 자기 자신의 테이블/컬럼/제약 정보를 저장해두는 메타데이터 저장소)에 이 정보가 없으면, 응용 개발자가 "지금 이 테이블의 복제 키가 뭔지" 알고 싶을 때 확인할 방법이 스펙상 전혀 없습니다.

**구체 예제(SQL)**:
```sql
CREATE TABLE members(
    id INT,
    email VARCHAR(100) NOT NULL UNIQUE,
    phone VARCHAR(20) NOT NULL UNIQUE
);

-- "지금 복제 키로 선택된 건 email인가 phone인가?" 를 확인하고 싶다
show create table members;   -- REPLICATION ON 여부만 보임, RK 컬럼 정보 없음
select * from db_class where class_name = 'members';  -- 예시 9와 동일, replication: ON만 보임
```

**예제 설명**: 위 예제는 UK가 두 개인 테이블을 만든 뒤, 실제로 어떤 컬럼이 RK로 선택됐는지 확인하려는 매우 자연스러운 질문 상황입니다. 그런데 스펙에 제시된 두 조회 수단(show create table, db_class) 모두 이 정보를 주지 않습니다. 장애 상황에서 "왜 이 UPDATE가 복제 안 됐지?"를 디버깅할 때, RK를 모르면 원인 분석 자체가 불가능합니다.

**제안**: `db_class` 혹은 별도 시스템 뷰에 현재 선택된 RK의 제약 이름/컬럼 목록을 노출하는 컬럼을 추가해야 합니다.

### 리뷰 8

**[심각도: 중요] FK-복제 제약 위반 시 에러 메시지/에러 코드가 전혀 명시되지 않아 자동화 파이프라인이 실패를 감지할 수 없다**

**대상**: §5-1 예시 18, §5-2 예시(복제 제외 테이블 참조 외래키 추가), 예시 23 — 모두 결과가 그냥 "ERROR"로만 표기됨

**문제 설명**: CI/CD 파이프라인에서 DDL을 자동 적용할 때는 보통 SQL 실행 결과의 에러 코드(SQLSTATE, 벤더별 에러 번호 등)를 파싱해서 "이건 예상된 실패니 무시" 또는 "이건 심각한 실패니 롤백"을 자동 판단합니다. 그런데 스펙의 모든 에러 예시는 단순히 "ERROR"라고만 적혀 있고 실제 메시지 문자열이나 에러 코드가 하나도 없습니다(예시 5, 10, 12, 15, 16, 18, 23 전부 동일).

**구체 예제(시나리오, 파이프라인 스크립트 관점)**:
```bash
#!/bin/bash
# 배포 파이프라인이 DDL을 적용하고 실패 유형을 구분하려는 시도
csql -u dba mydb < migration_0042_add_fk.sql 2> error.log

if grep -q "ERROR: ????" error.log; then
    echo "복제 제외 테이블 FK 참조 위반 - 알려진 실패, 리뷰 필요"
    exit 2
else
    echo "알 수 없는 실패 - 즉시 롤백 및 알림"
    exit 1
fi
# ????에 채워 넣을 정확한 에러 문자열/코드가 스펙에 없음
```

**예제 설명**: 파이프라인이 "이 실패가 FK-복제상태 위반 때문인지, 아니면 문법 오류나 권한 문제 같은 다른 원인 때문인지"를 구분하려면 정확한 에러 메시지 패턴이나 에러 코드가 필요합니다. 스펙에 이 정보가 없으면 개발자는 실제로 CUBRID를 설치해 에러를 직접 재현해보는 수밖에 없고, 문서만으로는 자동화 코드를 작성할 수 없습니다.

**제안**: 모든 에러 예시에 실제 에러 메시지 전문과 에러 코드(가능하다면 `ER_xxx` 형태의 내부 코드까지)를 명시해야 합니다.

### 리뷰 9

**[심각도: 보통] §7의 "파일 리스트"라는 용어가 무엇을 가리키는지 정의되지 않았다**

**대상**: §7(HA 전환) "제약사항 위반 시 에러와함께 파일 리스트를 출력한다"

**문제 설명**: 여기서 "파일 리스트"가 위반한 "테이블 리스트"를 뜻하는 것으로 추정되지만, 문자 그대로 읽으면 OS 파일 경로 목록(예: 볼륨 파일)을 의미하는 것처럼도 읽힙니다. 입문서 수준의 문체를 지향해야 하는 문서에서 이런 용어는 처음 등장할 때 무엇의 목록인지 한 문장으로 풀어줘야 하는데 이 문서는 그렇게 하지 않았습니다.

**구체 예제(시나리오)**:
```
$ cubrid hb start mydb
ERROR: HA 전환 제약사항 위반
파일 리스트: ???
```

**예제 설명**: 실제 출력이 `테이블: order_events, coupon_log` 같은 테이블 이름 목록일지, 아니면 `/db/mydb/order_events.data` 같은 실제 파일 경로 목록일지에 따라 운영자가 취해야 할 행동(테이블에 ALTER를 걸어야 하는지, 파일 시스템을 확인해야 하는지)이 완전히 달라집니다.

**제안**: "파일 리스트"를 "위반 테이블 목록"처럼 명확한 용어로 교체하고, 실제 출력 포맷 예시를 추가해야 합니다.

### 리뷰 10

**[심각도: 중요] HA 전환 실패 시 "싱글모드에서 재구성"하라는 절차가 이미 다중 노드로 운영 중인 클러스터에 어떻게 적용되는지 설명이 없다**

**대상**: §7 "이 경우 싱글모드에서 ALTER TABLE… 을 이용해 복제 키에 해당하는 제약을 추가하거나 복제 제외 대상으로 변경한 후 HA를 재시작해아한다"

**문제 설명**: "싱글모드에서 재구성"이라는 표현은 이미 마스터·슬레이브 여러 노드로 구성된 운영 HA 클러스터가 있을 때, 구체적으로 어느 노드에서 무엇을 내려야 싱글모드가 되는지(마스터만? 전체 노드를?), 그 사이 서비스 중단은 불가피한지에 대한 절차가 전혀 없습니다. 오탈자도 있습니다("재시작해아한다" → "재시작해야한다").

**구체 예제(단계별 시나리오)**:
```
1) 운영 HA 클러스터(마스터 1대 + 슬레이브 2대)가 이미 서비스 중
2) 신규 배포한 DDL 실수로 order_events 테이블이 RK를 잃음
3) 정기 재기동 중 "cubrid hb start" 실패, 제약 위반 보고
4) "싱글모드에서 재구성" 하라는데:
   - 마스터 1대만 내려서 싱글로 돌리고 ALTER 하면 되는가?
   - 그동안 슬레이브 2대는 어떤 상태가 되는가?
   - 서비스는 완전히 중단되는가, 아니면 무중단 가능한가?
```

**예제 설명**: 이미 서비스 중인 다중 노드 클러스터를 "싱글 모드로 되돌린다"는 것은 사실상 HA 자체를 끄는 것과 다르지 않아 보이는데, 이게 서비스 중단 없이 가능한 절차인지 스펙만으로는 판단할 수 없습니다. 신입 개발자가 장애 대응 런북(runbook, 장애 시 따라야 할 절차서)을 작성하려 해도 이 문장 하나로는 아무것도 쓸 수 없습니다.

**제안**: 운영 중인 다중 노드 클러스터에서의 구체적 복구 절차(노드별 순서, 서비스 영향)를 별도 섹션으로 추가하고, 오탈자를 수정해야 합니다.

### 리뷰 11

**[심각도: 중요] LOADDB 시 RK가 전혀 없는 데이터를 복제 테이블로 적재하면 어떻게 되는지 불명확하다**

**대상**: §8 "복제 테이블의 경우 큐브리드는 자동으로 RK를 할당한다"

**문제 설명**: "자동으로 RK를 할당한다"는 문장은 PK나 UK 후보가 이미 존재하는 컬럼 중에서 고른다는 뜻인지, 아니면 후보가 아예 없을 때 엔진이 새로운 키(예: 내부 OID 기반)를 만들어낸다는 뜻인지 모호합니다. 만약 후보가 없는데 복제 테이블로 로드를 시도하면 로드가 실패하는지, 조용히 RK 없는 상태로 만들어지는지(그러면 §1에 의해 이후 HA를 못 켜게 됨) 알 수 없습니다.

**구체 예제(단계별 시나리오)**:
```
-- 백업 파일에 PK도 UK도 없는 legacy_log 테이블이 포함됨
-- legacy_log는 unload 스키마 파일에 복제 여부 = 복제 대상(ON)으로 기록됨

$ unloaddb -i legacy_log ...   -- (§8, PK/UK 없는 상태로 unload)
$ loaddb -s schema.sql -d data.dat mydb
-- legacy_log를 복제 테이블로 만들려는데 RK 후보 자체가 없다.
-- 결과: 로드가 실패하는가? RK 없이 생성되어 이후 HA 기동 시에만 에러가 나는가?
```

**예제 설명**: 재해 복구(DR, Disaster Recovery) 훈련이나 다른 서버로의 데이터 이관 시 이런 legacy 테이블을 흔히 만나게 됩니다. 이 동작이 명확하지 않으면, 로드 작업 자체는 성공한 것처럼 보였는데 나중에 HA를 켤 때에서야(§1) 실패가 드러나는 식으로, 문제 발견 시점이 계속 뒤로 밀리는 위험한 패턴이 반복됩니다.

**제안**: RK 후보가 전혀 없는 테이블을 복제 대상으로 로드하려 할 때의 정확한 동작(즉시 실패 vs 지연된 실패)을 명시해야 합니다.

### 리뷰 12

**[심각도: 중요] 하위 버전 unload 파일의 load 조건 문장이 중의적이다**

**대상**: §8 "특히 하위 버전에서 unload 한 데이터 파일에는 복제 여부를 저장하는 변수가 설정되어있지 않으므로 (싱글 모드에서) load 시 모두 복제 테이블로 설정된다."

**문제 설명**: 이 문장의 "(싱글 모드에서)"라는 괄호가 "이런 legacy 파일은 오직 싱글 모드로만 load할 수 있다"는 제약을 뜻하는지, 아니면 "싱글 모드로 load하는 경우에 한해 모두 복제 테이블로 강제 설정된다(HA 모드로 로드할 때는 다른 동작)"는 뜻인지 구문만으로는 판단할 수 없습니다. 두 해석은 재해 복구 절차에서 완전히 다른 행동을 요구합니다.

**구체 예제(단계별 시나리오)**:
```
-- 구버전(예: 복제 여부 개념이 없던 버전)에서 unload한 백업 파일 보유
$ unloaddb -i mydb   -- (구버전, 복제 여부 필드 없음)

-- 신버전 HA 클러스터의 마스터에 이 백업을 바로 복원하려 한다
$ loaddb -s old_schema.sql -d old_data.dat new_mydb   -- HA 모드에서 직접 실행 가능한가?
-- 아니면 반드시 싱글 모드 인스턴스에 먼저 load한 뒤 HA로 전환해야 하는가?
```

**예제 설명**: 오래된 버전에서 백업한 데이터를 새 버전의 운영 HA 클러스터로 복원하는 것은 매우 흔한 업그레이드 시나리오입니다. 이 문장이 "HA 모드로는 직접 로드가 아예 안 된다"는 뜻이라면 사전에 싱글 인스턴스를 별도로 준비해야 하는 등 복구 절차와 소요 시간이 크게 달라지므로, 재해 복구 런북을 미리 준비하는 응용팀 입장에서 이 모호함은 실제 장애 상황에서 절차를 즉흥적으로 결정해야 하는 위험으로 이어집니다.

**제안**: "(싱글 모드에서)"가 로드 가능 조건인지 부가 설명인지 명확히 구분해 문장을 다시 쓰고, HA 모드로 직접 legacy 파일을 로드하려 할 때의 동작(허용/거부)을 별도로 명시해야 합니다.

### 리뷰 13

**[심각도: 보통] 뷰(VIEW)는 FK와 달리 복제 제외 테이블 참조를 막지 않는 이유가 설명되지 않는다**

**대상**: §5(외래키, 참조 시 생성을 막음) vs §6(뷰, 참조를 막지 않고 사후 책임만 회피)

**문제 설명**: §5는 복제 제외 테이블을 참조하는 FK 생성 자체를 에러로 막는데(예시 18), §6은 복제 제외 테이블을 포함한 뷰 생성을 막지 않고 "복제 모듈은 책임지지 않는다"고만 합니다. 둘 다 "복제 제외 테이블에 의존하는 객체"라는 점은 동일한데 왜 한쪽은 생성 자체를 차단하고 다른 쪽은 허용하는지 설계 원칙이 스펙에 설명되어 있지 않습니다. 입문자가 당연히 가질 수 있는 "왜 여기는 막고 저기는 안 막는가?"라는 질문에 스펙이 답을 주지 않습니다.

**구체 예제(SQL)**:
```sql
-- FK: 생성 자체가 막힘 (§5, 예시 18과 동일 패턴)
CREATE TABLE orders(
    order_id INT PRIMARY KEY,
    customer_id INT,
    CONSTRAINT fk_c FOREIGN KEY(customer_id) REFERENCES non_repl_customers(customer_id)
);
-- ERROR

-- VIEW: 동일하게 복제 제외 테이블을 참조하지만 생성이 막히지 않음 (§6)
CREATE VIEW v_orders_with_customer AS
SELECT o.order_id, c.country
FROM orders o JOIN non_repl_customers c ON o.customer_id = c.customer_id;
-- OK (스펙상 제약 없음, 단 failover 후 결과 불일치 가능)
```

**예제 설명**: FK는 생성 시점에 참조 무결성을 강제로 검사해 막아주는데, 뷰는 똑같이 복제 제외 테이블에 의존함에도 생성 시점 검사 없이 통과시키고 실행 결과가 달라질 수 있다는 경고만 남깁니다. 신입 개발자 입장에서는 "FK는 안전장치가 있으니 VIEW도 당연히 비슷한 안전장치가 있겠지"라고 오해하기 쉽고, 이 오해가 실제 failover 후 데이터 불일치 사고로 이어질 수 있습니다.

**제안**: FK와 VIEW에 대해 서로 다른 정책을 적용하는 설계 근거(예: 뷰는 조회 전용이라 무결성 강제가 어렵다는 등)를 명시하거나, 최소한 뷰 생성 시에도 복제 제외 테이블 참조에 대한 경고를 출력하도록 일관성을 맞춰야 합니다.

### 리뷰 14

**[심각도: 중요] RK가 엔진에 의해 암묵적으로 재선택될 수 있는데, 이 정보가 ORM 계층에 전혀 노출되지 않는다**

**대상**: §4-2 (PK→UK 전환 시나리오, 예시 13/14) — 컨셉 전반

**문제 설명**: 예시 13/14는 PK를 지우고 다른 컬럼을 RK로 삼는 것이 정상적인 운영 절차로 그려져 있습니다. 그런데 JPA 같은 ORM은 보통 PK(`@Id`)를 엔티티 식별자이자 영속성 컨텍스트의 캐시 키로 사용합니다. RK가 바뀌는 것은 순수하게 "복제 알고리즘이 어떤 컬럼으로 UPDATE/DELETE 대상을 찾는가"의 문제이므로 이론적으로는 애플리케이션 로직과 무관해야 하지만, 스펙에 "이 변경이 애플리케이션에 어떤 영향도 주지 않는다"는 보장 문구가 없어 응용 개발자 입장에서는 불안 요소로 남습니다.

**구체 예제(SQL + 시나리오)**:
```sql
-- DBA가 복제 키 재구성을 위해 PK를 다른 컬럼으로 옮김 (예시 13과 동일 패턴)
ALTER TABLE members DROP CONSTRAINT PRIMARY KEY, ADD CONSTRAINT PRIMARY KEY(email);
-- 기존 PK는 id 컬럼이었고, JPA 엔티티는 @Id private Long id; 로 매핑되어 있음
```

**예제 설명**: DBA/엔진 관점에서는 이 작업이 "복제 키를 id에서 email로 바꾼 것"뿐이지만, 애플리케이션 코드의 `@Id`는 여전히 `id` 컬럼을 엔티티 식별자로 사용합니다. 만약 향후 엔진이 "복제 키가 아닌 PK는 의미가 축소된다"거나 유사한 부작용을 갖게 될 경우(스펙에 배제한다는 보장이 없음) 애플리케이션 계층 코드는 전혀 손대지 않았음에도 예기치 못한 오작동이 생길 수 있습니다.

**제안**: "RK 재선택/변경이 순수 복제 계층 내부 동작이며 애플리케이션이 사용하는 PK 제약의 의미·동작에는 영향이 없다"는 점을 명문화해야 합니다.

### 리뷰 15

**[심각도: 보통] §9 SUMMARY가 §4의 "복제 제외 → 복제 대상 전환 불가" 제약을 누락했다**

**대상**: §9(SUMMARY) 전체 vs §4/§2-2

**문제 설명**: §9는 스펙의 핵심 제약을 7줄로 요약한 체크리스트인데, 여기에 "HA 모드에서는 REPLICATION=OFF 테이블을 ON으로 되돌릴 수 없다"는, 실무적으로 매우 자주 부딪힐 만한 제약(리뷰 5 참고)이 빠져 있습니다. 바쁜 실무자는 본문 전체보다 요약만 참고하고 넘어가는 경우가 많으므로, 요약 누락은 실제 사고로 이어질 수 있습니다.

**구체 예제(시나리오)**:
```
개발자가 배포 전 체크리스트를 §9 SUMMARY만 보고 작성:
[ ] REPLICATION으로 복제 대상/제외 구분 가능
[ ] 싱글/SA에서도 사용 가능
[ ] RK 있는 테이블도 복제 제외 가능
[ ] HA에서 복제 대상은 RK 1개 이상 필요
[ ] FK 테이블의 참조 테이블은 모두 복제 대상이어야 함
[ ] HA 전환 시 RK 없으면 싱글모드에서 재구성
[ ] UNLOADDB 시 복제 대상 여부 출력, 없으면 복제 제외

→ "OFF에서 ON으로 못 돌아간다"는 체크 항목이 없어
  운영 중 실수로 OFF 전환한 테이블을 되돌리려다 실패를 겪음
```

**예제 설명**: 체크리스트에 없는 제약은 곧 "존재하지 않는 제약"처럼 취급되기 쉽습니다. 위 시나리오는 요약만 보고 작업 계획을 세운 개발자가 본문 §2-2에 있는 제약을 놓쳐 뒤늦게 문제를 발견하는 상황을 보여줍니다.

**제안**: §9에 §2-2/§4의 OFF→ON 전환 제약을 추가 항목으로 포함시켜야 합니다.

### 리뷰 16

**[심각도: 보통] 예시 2와 예시 23의 SQL에 trailing comma 문법 오류가 있다**

**대상**: §2-1 예시 2, §5-2 예시 23

**문제 설명**: 예시 2는 `CREATE TABLE repl_table_without_rk(a INT,);`, 예시 23은 `CREATE TABLE new_orders(order_id INT PRIMARY KEY,);`처럼 마지막 컬럼 정의 뒤에 불필요한 쉼표가 붙어 있고 그 뒤에 닫는 괄호가 바로 옵니다. 이는 대부분의 SQL 방언에서 문법 오류(trailing comma)를 유발하는 코드로, 실제로 이 예제를 그대로 복사해 실행하면 스펙이 의도한 결과(RK 없는 테이블 생성 성공/실패)가 아니라 문법 에러가 날 가능성이 있습니다.

**구체 예제(SQL, 원문 그대로)**:
```sql
-- 예시 2 원문
CREATE TABLE repl_table_without_rk(
    a INT,
);

-- 예시 23 원문
CREATE TABLE new_orders(
    order_id INT PRIMARY KEY,
);
```

**예제 설명**: 컬럼 정의가 `a INT`로 끝난 뒤 쉼표가 붙고 바로 `)`가 오는 구조는 "쉼표 다음에 컬럼 정의가 하나 더 있어야 하는데 없다"는 뜻으로 해석되어 문법 오류가 나는 것이 일반적인 SQL 파서 동작입니다. 신입 개발자가 문서를 그대로 복사·붙여넣기 해서 재현 테스트를 하다가 스펙이 설명하려는 것과 무관한 문법 오류를 만나 혼란스러울 수 있습니다.

**제안**: 두 예시에서 trailing comma를 제거해야 합니다(`CREATE TABLE repl_table_without_rk(a INT);`, `CREATE TABLE new_orders(order_id INT PRIMARY KEY);`).

**[심각도: 사소] 예시 21의 제약 이름 "fk_new_orders_customer_id"가 앞선 예시에서 정의된 적이 없다**

-- 예시 19 원문 (제약 이름 없이 추가)
ALTER TABLE new_orders ADD CONSTRAINT FOREIGN KEY(customer_id)

**제안**: 예시 19/20에 실제로 생성되는 제약 이름을 각주로 표기하거나, 엔진의 FK 기본 명명 규칙을 별도로 문서화해야 합니다.

### 리뷰 18

**[심각도: 사소] "Failover" 용어가 정의 없이 사용된다**

**대상**: §5 "Failover 발생"

**문제 설명**: 스펙 본문에서 "Failover"라는 용어가 처음이자 유일하게 등장하는 곳이 §5인데, 이 문서 어디에도 failover가 무엇인지에 대한 설명이 없습니다. 이 문서가 "컴퓨터공학과 전공 입문서 수준"을 지향해야 한다면(작업 지침), HA를 처음 접하는 응용 개발자가 이 단어의 뜻을 몰라 §5 전체 시나리오를 이해하지 못할 수 있습니다.

**구체 예제(원문 발췌)**:
```
HA 실행 시 참조 테이블은 복제 대상이 아니므로 Slave로 복제되지 않고, 오직 외래키 테이블만 복제 됨
Failover 발생
어플리케이션에서 "orders" 데이터 접근
외래키로 참조할 "customers" 가 존재하지 않음
```

**예제 설명**: 위 4줄 흐름은 "Failover 발생"이라는 사건이 왜, 어떤 조건에서 일어나는지 아무 설명 없이 하나의 단계로만 나열되어 있습니다. HA 개념에 익숙하지 않은 신입 개발자는 이 시나리오를 읽어도 "마스터가 죽어서 슬레이브가 새 마스터가 된다"는 배경 지식 없이는 왜 갑자기 애플리케이션이 슬레이브에 접근하게 되는지 이해하기 어렵습니다.

**제안**: 문서 도입부(§1 이전이나 용어 정의 섹션)에 "Failover: 마스터 장애 시 슬레이브가 새로운 마스터 역할을 이어받는 것" 같은 한 줄 정의를 추가해야 합니다.

### 리뷰 19

**[심각도: 보통] FK 체인이 2단 이상일 때 복제 대상 검증이 전이적으로 적용되는지 불명확하다**

**대상**: §5 "외래키 테이블에서 참조하는 모든 테이블은 복제 대상이여야한다"

**문제 설명**: 이 문장은 "외래키 테이블이 직접 참조하는 테이블"만을 말하는 것인지, 참조의 참조까지(전이적으로) 모두 검사한다는 것인지 분명하지 않습니다. 실무 스키마에서는 FK 체인이 2~3단 이어지는 경우가 흔합니다(`order_items → orders → customers`).

**구체 예제(SQL)**:
```sql
CREATE TABLE customers(
    customer_id INT PRIMARY KEY
) REPLICATION=OFF;   -- 복제 제외

CREATE TABLE orders(
    order_id INT PRIMARY KEY,
    customer_id INT,
    CONSTRAINT fk_o_c FOREIGN KEY(customer_id) REFERENCES customers(customer_id)
);
-- §5에 의해 이 시점에서 이미 ERROR가 나야 정상(customers가 REPLICATION=OFF이므로)

-- 만약 customers가 REPLICATION=ON이고, orders도 ON이지만,
-- order_items가 orders를 참조하는 3단 체인이라면?
CREATE TABLE order_items(
    item_id INT PRIMARY KEY,
    order_id INT,
    CONSTRAINT fk_oi_o FOREIGN KEY(order_id) REFERENCES orders(order_id)
);
-- 이 시점에서 orders의 조상인 customers까지 재귀적으로 검사하는가,
-- 아니면 orders 하나만 REPLICATION=ON인지 확인하고 끝나는가?
```

**예제 설명**: 3단 체인 예제는 "직접 참조 테이블만 검사"와 "조상 테이블까지 전부 검사"가 서로 다른 결과를 낼 수 있는 상황을 보여줍니다. 직접 참조만 검사한다면 각 단계의 생성 시점에는 문제가 없어 보여도, 중간에 있는 `customers`가 나중에 `REPLICATION=OFF`로 바뀌면(§2-2, 이는 HA에서 허용됨) 이미 완성된 체인 전체가 리뷰 3과 동일한 FK 참조 문제를 갖게 됩니다.

**제안**: FK 검증이 직접 참조 테이블에 대해서만 이루어지는지, 조상 테이블 전체에 대해 전이적으로 이루어지는지 명시하고, 중간 테이블이 나중에 OFF로 바뀌는 경우의 재검증 시점(즉시 차단 vs HA 재기동 시점)도 규정해야 합니다.

### 리뷰 20

**[심각도: 사소] 파티션 테이블에서 REPLICATION/RK가 어떻게 동작하는지 전혀 언급이 없다**

**대상**: §2-3 예시 9 (`partitioned: NO` 필드가 카탈로그에 존재함)

**문제 설명**: 예시 9의 `db_class` 출력에 `partitioned` 필드가 있는 것으로 보아 파티션 테이블(대량 데이터를 여러 물리적 조각으로 나눠 저장하는 기능)이 이 스펙과 무관하지 않다는 것을 알 수 있는데, 정작 본문 §1~§9 어디에도 파티션 테이블에서 RK/REPLICATION이 부모 테이블 기준으로 적용되는지, 파티션별로 별도 설정이 가능한지에 대한 설명이 없습니다.

**구체 예제(SQL, 시나리오)**:
```sql
CREATE TABLE sales(
    sale_id INT,
    sale_date DATE,
    amount INT,
    PRIMARY KEY(sale_id, sale_date)
) PARTITION BY RANGE (sale_date) (
    PARTITION p2025 VALUES LESS THAN (DATE '2026-01-01'),
    PARTITION p2026 VALUES LESS THAN (DATE '2027-01-01')
) REPLICATION=ON;

-- 개별 파티션(p2025, p2026) 각각에 대해 REPLICATION=OFF를 지정할 수 있는가?
-- RK는 부모 테이블 기준 하나로만 결정되는가, 파티션마다 다를 수 있는가?
```

**예제 설명**: 대용량 로그·매출 테이블은 실무에서 흔히 파티셔닝을 사용합니다. 특정 연도(예: 과거 아카이브 파티션)만 복제에서 빼고 최신 파티션만 복제하고 싶은 요구가 자연스럽게 생기는데, 이 스펙만으로는 그런 세밀한 제어가 가능한지조차 알 수 없습니다.

**제안**: 파티션 테이블에 대한 REPLICATION/RK 적용 단위(테이블 전체 vs 파티션별)를 별도 절로 추가해야 합니다.
