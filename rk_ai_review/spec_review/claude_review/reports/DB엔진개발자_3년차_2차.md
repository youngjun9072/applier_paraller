# CUBRID HA 복제 개선 스펙 리뷰 — DB 엔진 개발자 (3년차) 관점 · 2차 라운드

## 2차 라운드 개요

1차에서는 RK(복제 키) 선택 규칙의 비결정성, 다중 절 ALTER의 원자성, 복제 로그 순서 정합성처럼 스펙 문장 자체에서 바로 드러나는 상위 개념 결함을 다뤘다. 2차에서는 같은 문제를 스펙 문장만으로는 보이지 않는 각도에서 다시 파기 위해, 실제 CUBRID 엔진 소스(스키마 관리 모듈, 복제 모듈, DML 처리 경로, unloaddb/loaddb 유틸리티, SQL 문법 정의)를 직접 확인했다. 그 결과 "PK만 있던 시절에는 거의 발동하지 않던 기존 코드 경로가, RK가 UK일 수도 있게 되는 순간부터 새로 자주 발동하며 문제를 일으키는 지점"과 "파티션·온라인 인덱스·TDE·권한처럼 스펙이 존재 자체를 언급하지 않는 기존 엔진 기능과의 충돌 지점"을 중심으로 조사했다. 1차 리뷰 및 최종보고서에 이미 실린 40개 통합 이슈(RK 비결정성, FK 사후 OFF 전환, §7 파일리스트, §8/§9 모순, 원자성/락, 업그레이드 경로 등)와 겹치는 내용은 모두 제외했다.

## 리뷰 21

**[심각도: 치명] 외래키 캐스케이드 액션과 복제 로그 순서 보존 처리가 PK 전용으로만 존재한다**

**대상**: §1 RK 정의(PK 또는 UK), §5 외래키, 엔진 내부 복제 로그 삽입 경로

**문제 설명**: CUBRID는 이미 오래전부터 외래키가 부모 테이블의 PK뿐 아니라 NOT NULL UNIQUE 키를 참조하는 것을 허용해왔다(표준 SQL 기능). 그런데 부모 테이블의 키 값이 바뀌는 UPDATE에 외래키의 캐스케이드 액션(ON UPDATE CASCADE 같은, 부모 키 변경이 자식 행에 연쇄적으로 반영되는 동작)이 걸려 있을 때, 이 갱신을 복제 로그에 올바른 순서로 기록하기 위해 엔진 내부에는 "캐스케이드 액션이 진행되는 동안 복제 로그 순서 번호(LSA)를 잠깐 보존했다가 되돌려놓는" 특수 처리가 존재한다. 실제로 엔진 코드를 확인해보면 이 특수 처리는 "이 인덱스가 PK 타입일 때"라는 조건에만 묶여 있고, 같은 조건에서 UK 타입 인덱스는 이 특수 처리를 타지 않는다. 지금까지는 PK가 있는 테이블만 복제됐으니 이 특수 처리가 발동할 기회 자체가 "부모 키가 PK인 경우"로 사실상 한정되어 있었지만, 이 스펙대로 PK 없이 UK만으로 RK가 정해지는 테이블이 복제 대상이 되고 그 테이블이 캐스케이드 외래키의 부모가 되는 순간부터, 지금까지 거의 발동한 적 없는 이 취급 없음 경로가 일상적으로 발동하게 된다. 실제로 복제 모듈 코드 안에는 "OLD/NEW PK를 OLD/NEW RK(PK 또는 NOT NULL UNIQUE)로 전환해야 한다"는 미완성 작업 주석이 이미 여러 군데 남아 있어, 구현자들 스스로도 이 지점이 아직 정리되지 않았다는 것을 인지하고 있다. 그런데 정작 스펙 문서에는 이 상호작용에 대한 규정이 한 줄도 없다.

**구체 예제**:
```sql
CREATE TABLE employees (
    emp_id INT NOT NULL UNIQUE,   -- PK 없음, RK = emp_id (UK)
    dept_id INT
);

CREATE TABLE dept_budget (
    dept_id INT,
    manager_emp_id INT,
    CONSTRAINT fk_mgr FOREIGN KEY (manager_emp_id) REFERENCES employees(emp_id)
        ON UPDATE CASCADE
);

-- HA 운영 중, RK 값 자체를 바꾸는 UPDATE
UPDATE employees SET emp_id = 9001 WHERE emp_id = 1001;
-- ON UPDATE CASCADE로 dept_budget.manager_emp_id 도 함께 9001로 갱신되는 연쇄 반응 발생
```

**예제 설명**: employees의 RK는 PK가 아니라 UK다. emp_id를 바꾸는 UPDATE가 dept_budget에 연쇄 갱신을 일으키는 이 시나리오는, PK 기준으로만 짜여 있던 "캐스케이드 도중 복제 로그 순서 보존" 로직이 적용되지 않는 경로를 그대로 통과한다. 이 처리가 원래 왜 필요했는지(캐스케이드 액션이 부모 갱신의 복제 로그 순서 번호를 덮어써버리는 문제를 막기 위해서였다는 것)를 생각하면, UK 기반 RK에서 이 보호 장치가 빠질 경우 부모 UPDATE와 캐스케이드로 발생한 자식 UPDATE의 복제 로그 순서가 뒤바뀌어 슬레이브에 잘못된 순서로 적용될 위험이 있다.

**제안**: RK가 PK든 UK든 관계없이 "이 인덱스가 현재 RK인가"를 판단하는 단일 기준으로 캐스케이드-복제 순서 보존 로직을 일반화해야 한다는 요구사항을 스펙에 명시하고, 이 전환이 완료되기 전까지는 "UK를 RK로 사용하는 테이블은 캐스케이드 외래키의 부모가 될 수 없다"는 임시 제약을 두는 것도 검토해야 한다.

## 리뷰 22

**[심각도: 치명] 파티션 테이블의 UNIQUE 제약은 전역(GLOBAL)이 아니라 파티션별 지역(LOCAL)일 수 있는데, RK 자격 판정이 이를 구분하지 않는다**

**대상**: §1 RK 선택 기준("NOT Null Unique Key"), 스펙 전체(파티션 언급 없음)

**문제 설명**: 파티션 테이블은 하나의 논리 테이블을 여러 물리 조각(파티션)으로 나눠 저장하는 기능이다. CUBRID의 파티션 테이블에서 PK는 항상 전체 파티션에 걸쳐 유일함이 보장되는 전역 제약이지만, UNIQUE 제약은 그 제약에 파티션 기준 컬럼이 포함되어 있지 않으면 "파티션 하나 안에서만 유일함이 보장되는" 지역 제약으로 취급될 수 있다. 즉 같은 값이 서로 다른 파티션에 하나씩 존재하는 것이 허용될 수 있다는 뜻이다. RK는 "슬레이브에서 이 값으로 행을 하나로 특정할 수 있다"는 것을 전제로 하는데, 파티션 기준으로만 유일한 UK를 RK로 선택하면 그 전제 자체가 깨진다. 스펙은 파티션이라는 존재를 §1~§9 어디에서도 언급하지 않으므로, RK 선택 규칙이 "이 UK가 전역 유일인지 파티션 지역 유일인지"를 구분해야 한다는 사실 자체를 반영하지 않는다.

**구체 예제**:
```sql
CREATE TABLE sales (
    region_id INT,
    sale_id INT,
    amount INT,
    CONSTRAINT u_sale UNIQUE (sale_id)   -- 파티션 키(region_id)를 포함하지 않는 UK
)
PARTITION BY RANGE (region_id) (
    PARTITION p1 VALUES LESS THAN (100),
    PARTITION p2 VALUES LESS THAN (200)
);
-- PK가 없으므로 §1 규칙대로면 RK = u_sale(sale_id)

INSERT INTO sales VALUES (10, 555, 1000);   -- p1 파티션에 sale_id=555
INSERT INTO sales VALUES (150, 555, 2000);  -- p2 파티션에도 sale_id=555 저장 가능(파티션별 지역 유일이면)
```

**예제 설명**: u_sale이 파티션 지역 유일 제약으로 처리된다면, sale_id=555인 행이 p1과 p2에 각각 하나씩(서로 다른 실제 데이터) 존재할 수 있다. 이 상태에서 sale_id=555인 행 하나를 UPDATE하면, 복제 로그에는 "sale_id=555인 행을 갱신하라"는 정보만 남는데 슬레이브에는 그 값을 가진 행이 두 개 있어 어느 쪽을 갱신해야 할지 특정할 수 없다. 이는 RK 개념이 전제하는 "이 값으로 행을 유일하게 찾을 수 있다"는 불변식이 파티션 테이블에서는 아예 성립하지 않을 수 있음을 보여준다.

**제안**: RK 후보를 PK/UK 유무만으로 판단하지 말고, 파티션 테이블에 대해서는 "파티션 기준 컬럼을 포함하거나, 전역 유일성이 보장되는 UK만 RK 후보로 인정한다"는 조건을 §1에 추가해야 한다. 파티션 자체를 이번 릴리스 범위에서 제외한다면 그 사실도 명시해야 한다.

## 리뷰 23

**[심각도: 중요] 서로 다른 두 개의 ALTER TABLE 트랜잭션이 각각 개별적으로는 유효성 검사를 통과하지만, 합쳐지면 RK 후보가 0개가 되는 경쟁 상태가 있다**

**대상**: §4-2 "다른 복제키 후보가 함께 존재한다면 모든 DDL은 허용된다"

**문제 설명**: 1차 리뷰(리뷰 2)에서 지적한 원자성 문제는 "한 문장 안에 DROP과 ADD를 같이 쓴 경우"의 중간 상태에 관한 것이었다. 이번 문제는 그와 다르다. 서로 다른 두 개의 독립적인 ALTER TABLE 문(별도 커넥션, 별도 트랜잭션)이 있을 때, 각 문장이 실행되는 순간에는 "다른 후보가 아직 남아 있으니 이 DDL은 허용된다"는 §4-2 서문의 조건을 각각 만족하지만, 두 문장이 모두 커밋되고 나면 후보가 0개로 떨어질 수 있다. 이는 "다른 후보 존재 여부"를 검사하는 시점이 각 트랜잭션이 자신의 스냅샷을 확인하는 순간이지, 두 트랜잭션의 결과를 합쳐서 보는 시점이 아니기 때문에 생기는 전형적인 경쟁 상태(TOCTOU: 확인한 시점과 실제로 사용하는 시점 사이에 상태가 바뀌는 문제)다. 스펙은 "다른 후보가 함께 존재한다면"이라는 조건을 어느 트랜잭션 격리 수준에서, 어느 시점 기준으로 확인하는지 정의하지 않는다.

**구체 예제**:
```sql
-- tbl: PK(a) + UK(b) 두 개의 RK 후보 존재. RK = PK(a)

-- 세션 1 (커넥션 A)                         -- 세션 2 (커넥션 B), 거의 동시에 시작
ALTER TABLE tbl DROP CONSTRAINT PRIMARY KEY;  ALTER TABLE tbl DROP CONSTRAINT u_tbl_b;
-- 검사: "다른 후보 b(UK) 있음" → 통과         -- 검사: "다른 후보 a(PK) 있음" → 통과
-- 세션 1 커밋                                -- 세션 2 커밋
-- 두 커밋이 모두 끝나면 tbl에는 RK 후보가 하나도 남지 않는다.
```

**예제 설명**: 각 세션은 "나 말고 다른 후보가 있으니 내가 지워도 된다"고 판단해 통과했지만, 둘 다 그렇게 판단하고 동시에 실행됐기 때문에 결과적으로 후보가 모두 사라진다. 이 테이블이 HA 운영 중인 복제 대상이었다면, §4-1이 요구하는 "복제 대상 테이블은 RK가 하나 이상 있어야 한다"는 불변식이 두 개의 개별적으로는 정상적인 DDL 조합만으로 깨져버린다. HA를 당장 재시작하지 않는 한 §7의 검사도 이 위반을 잡아내지 못한다.

**제안**: RK 후보 개수를 검사하는 DDL은 해당 테이블에 대해 스키마 배타 잠금을 잡아 직렬화하고, "다른 후보 존재 여부"를 검사할 때 동시에 진행 중인 다른 RK 후보 제거 트랜잭션의 커밋도 함께 고려하도록(즉 낙관적 스냅샷이 아니라 비관적 직렬화로) 스펙에 명시해야 한다.

## 리뷰 24

**[심각도: 보통] REPLICATION 옵션 변경에 필요한 권한 수준이 정의되지 않았다**

**대상**: §2-2 ALTER TABLE ... REPLICATION, 스펙 전체(권한/보안 언급 없음)

**문제 설명**: CUBRID의 권한 체계는 SELECT/INSERT/UPDATE/DELETE/ALTER/INDEX/EXECUTE 정도의 굵직한 단위로만 나뉘어 있고, 이 스펙이 새로 추가하는 REPLICATION 옵션 변경을 위한 별도 권한 항목은 없다. 즉 `ALTER TABLE ... REPLICATION=OFF`는 그 테이블에 대한 일반 ALTER 권한만 있으면 누구나 실행할 수 있는 것으로 보인다. REPLICATION 여부는 단순한 스키마 속성이 아니라 "이 테이블의 데이터가 HA 재해복구/failover 대상에 포함되는가"를 결정하는 클러스터 전체 차원의 운영 정책인데, 테이블 소유자(일반 애플리케이션 계정일 수 있다) 권한만으로 이를 바꿀 수 있다면 DBA가 세운 복제 정책이 조용히 무력화될 수 있다.

**구체 예제**:
```sql
-- DBA가 만든 orders 테이블. 애플리케이션 계정 app_user에게 일반적인 ALTER 권한 부여
GRANT ALTER ON orders TO app_user;

-- app_user 세션에서 (DBA 모르게)
ALTER TABLE orders REPLICATION = OFF;
-- 스펙과 현재 권한 모델대로면 이 문장은 그냥 통과한다.
-- 이후 orders는 HA 복제에서 조용히 빠지고, DBA는 다음 재해복구 훈련에서야 이 사실을 알게 될 수 있다.
```

**예제 설명**: 이 예제는 REPLICATION 여부 변경이 일반 스키마 변경(컬럼 추가/삭제)과 같은 권한 등급으로 취급될 때 생기는 거버넌스 공백을 보여준다. 임의의 ALTER 권한 보유자가 재해복구 정책을 바꿀 수 있다는 것은, 이 기능이 원래 해결하려던 "복제 누락으로 인한 데이터 불일치"를 사람의 실수(혹은 악의) 경로로 재현하는 셈이다.

**제안**: REPLICATION 옵션 변경에 대해서는 일반 ALTER 권한과 별도로 DBA 권한(혹은 새로운 세분화된 권한)을 요구하도록 명시하거나, 최소한 이 변경이 감사 로그에 남아야 한다는 요구사항을 스펙에 추가해야 한다.

## 리뷰 25

**[심각도: 중요] TDE(투명한 데이터 암호화) 테이블의 RK 값이 복제 로그에서 어떻게 취급되는지, 마스터/슬레이브 간 암호화 키가 다를 때 어떻게 되는지 정의되지 않았다**

**대상**: §2-3 예시 9(`db_class` 출력의 `tde_algorithm` 필드), 스펙 전체(TDE 언급 없음)

**문제 설명**: 예시 9의 `db_class` 조회 결과에는 이미 `tde_algorithm : 'NONE'`이라는 필드가 존재한다. 이는 이 스펙이 다루는 테이블들이 TDE(테이블 단위로 저장 데이터를 암호화하는 기능)가 걸릴 수 있는 대상이라는 것을 스펙 스스로 보여주는 셈이다. 그런데 스펙 본문 어디에도 TDE가 적용된 테이블의 RK 선택이나 복제 동작에 대한 언급이 없다. 복제 로그를 다루는 내부 구조에는 이미 "이 복제 로그 레코드가 TDE 대상 클래스의 사용자 데이터를 담고 있는지" 여부를 표시하는 플래그가 존재하는데, 이는 TDE가 걸린 테이블의 복제 로그(그 안에 RK 값도 포함된다)가 암호화된 형태로 다뤄질 수 있음을 뜻한다. 마스터와 슬레이브가 서로 다른 TDE 마스터 키를 사용 중이라면(TDE 키 파일은 일반적으로 노드마다 별도로 관리되며 스키마처럼 자동으로 복제되는 대상이 아니다), 슬레이브가 이 로그를 복호화해 RK 값을 비교하고 대상 행을 찾는 과정 자체가 실패하거나 엉뚱한 결과를 낼 수 있다.

**구체 예제**:
```
[시나리오]
1. 마스터에 tde_algorithm이 NONE이 아닌(TDE가 걸린) 테이블 secure_tbl이 있고,
   REPLICATION=ON, RK=PK(id)로 정상 설정되어 있다.
2. 마스터와 슬레이브는 각자 독립적으로 발급된 TDE 마스터 키를 사용 중이다(키 파일을 수동으로
   맞추지 않는 한 서로 다르다).
3. 마스터에서 INSERT INTO secure_tbl VALUES (1, '123-45-6789'); 실행, 커밋.
4. applylogdb가 이 로그를 슬레이브에 적용하려 한다.
   -> 슬레이브는 이 로그의 RK 값(id=1)을 정상적으로 읽어 행을 식별할 수 있는가?
   -> 마스터 키가 다르면 이 시점에 어떤 에러가 나는가? fail_count가 조용히 증가하는가?
```

**예제 설명**: 이 스펙이 원래 풀려던 문제(작업지시 배경)는 "복제 로그를 잘못 해석해 fail_count가 증가하고 데이터가 불일치하는 것"이었다. TDE 키 불일치로 인한 복호화 실패도 결과적으로 같은 종류의 장애(로그 해석 실패, fail_count 증가, 마스터/슬레이브 불일치)로 이어질 수 있는데, 스펙은 이 경로를 전혀 다루지 않는다.

**제안**: TDE가 적용된 테이블의 RK/REPLICATION 동작을 별도 절로 다루고, 최소한 "TDE 테이블을 복제하려면 마스터와 슬레이브가 동일한 TDE 마스터 키를 공유해야 한다"는 전제 조건과, 키가 다를 때의 에러 처리(구체적인 에러 메시지, HA 기동 거부 여부)를 명시해야 한다.

## 리뷰 26

**[심각도: 치명] loaddb가 스키마-데이터-인덱스를 단계별로 나눠 재현하는 구조 자체가, 최신 버전의 정상적인 덤프에서도 HA 대상 복원 시 자기모순적인 중간 상태를 만든다**

**대상**: §8 UNLOADDB & LOADDB, §4-1(HA 모드에서 RK 없는 복제 테이블 생성 금지)

**문제 설명**: 1차 리뷰(리뷰 6)와 최종보고서(C6)는 "구버전에서 만든 언로드 파일을 신버전으로 로드할 때"의 하위 호환 문제를 지적했다. 이번 문제는 그와 별개로, 버전 문제가 전혀 없는 최신 정상 덤프를 로드하는 경우에도 발생한다. CUBRID의 unloaddb는 대용량 데이터를 빠르게 적재하기 위해 스키마 정의를 여러 단계로 쪼개서 출력한다. 대략적으로 (1) 컬럼만 있는 빈 테이블을 만드는 단계, (2) 대량 데이터를 인덱스 없이 빠르게 적재하는 단계, (3) 그 이후에 PK/UK 같은 제약과 인덱스를 별도로 추가하는 단계로 나뉘는 방식이다(인덱스를 만들고 나서 데이터를 넣는 것보다, 데이터를 다 넣은 뒤에 인덱스를 한 번에 만드는 쪽이 훨씬 빠르기 때문이다). 그런데 이 스펙의 §4-1은 "HA 모드에서는 복제키가 없는 복제 테이블을 생성할 수 없다"고 못박았다. loaddb의 1단계는 정확히 "복제키 후보가 아직 하나도 없는, 컬럼만 있는 테이블"을 만드는 것이므로, loaddb를 이미 HA로 운영 중인 데이터베이스에 대해 실행하면 §8이 아무리 정상적으로 REPLICATION 값을 복원하려 해도, 그 이전에 §4-1이 1단계에서부터 실행 자체를 막아버릴 수 있다.

**구체 예제**:
```
[unloaddb가 만들어내는 스크립트의 대략적인 구조]
1) schema.sql  : CREATE TABLE orders (order_id INT, customer_id INT, status VARCHAR(20));
                 -- 컬럼만 있고 PK/UK가 아직 없음
2) data.data   : (loaddb 유틸리티로 대량 데이터 적재, 인덱스 생성 전이라 더 빠름)
3) indexes.sql : ALTER TABLE orders ADD CONSTRAINT PRIMARY KEY(order_id);
                 -- 이 시점에야 비로소 RK 후보가 생긴다

[시나리오]
신버전 CUBRID를 HA 모드("cubrid hb start")로 이미 기동한 상태에서
위 스크립트를 순서대로 실행해 orders 테이블을 복원한다.
-> 1) 단계의 CREATE TABLE 시점에 REPLICATION 기본값(§8: 없으면 ON)이 적용된다면
   §4-1에 따라 "복제키 없는 복제 테이블 생성"으로 즉시 ERROR가 나야 한다.
-> 그렇다면 이 표준적인 loaddb 재현 순서 자체가 HA 대상 복원과 구조적으로 맞지 않는다.
```

**예제 설명**: 이 예제는 unloaddb/loaddb의 내부 동작 방식(스키마를 단계별로 쪼개 재현)과 §4-1의 제약이 그냥 겹쳐놓기만 해도 충돌한다는 것을 보여준다. §5(2. 변경되거나 추가된 SQL)와 §8을 아무리 정교하게 고쳐도, loaddb 스크립트 자체가 1단계에서 막힌다면 HA로 운영 중인 데이터베이스에 loaddb로 테이블을 복원하는 것 자체가 불가능해진다. 이는 하위 호환성 문제가 아니라 이번 스펙이 새로 추가하는 제약과 기존 유틸리티의 동작 방식이 정면으로 부딪히는 구조적 문제다.

**제안**: loaddb가 1단계 CREATE TABLE을 발행할 때는 항상 REPLICATION=OFF로 만들고, 인덱스/제약을 모두 추가한 마지막 단계에서 원래 저장된 REPLICATION 값으로 전환하는 별도 SQL을 추가로 발행하도록 unloaddb/loaddb의 출력 형식 자체를 바꿔야 한다는 요구사항을 §8에 명시해야 한다. 이는 문서 교정이 아니라 유틸리티 구현을 바꿔야 하는 사안이다.

## 리뷰 27

**[심각도: 중요] 온라인(비차단) 인덱스 빌드 중이거나 비활성(invisible) 상태인 유니크 인덱스가 RK 후보 판정에 그대로 포함될 위험이 있다**

**대상**: §4-2 "복제키 후보" 개수 판정, §1 RK 선택 기준

**문제 설명**: CUBRID는 대용량 테이블에 인덱스를 추가할 때 서비스 중단 없이 백그라운드에서 인덱스를 완성하는 온라인 인덱스 생성 기능과, 인덱스를 만들어두되 실행계획에서는 당장 쓰지 않도록 숨겨두는 비활성(invisible) 인덱스 기능을 함께 제공한다(UNIQUE 인덱스도 온라인 생성이 가능하다). 온라인 생성 중인 유니크 인덱스는 "빌드가 진행 중"이라는 별도 상태를 가지며, 이 상태에서는 기존에 테이블에 있던 모든 행에 대한 유일성 검증이 아직 끝나지 않았을 수 있다. 그런데 이 스펙의 §4-2는 "복제키 후보가 몇 개 있는가"만으로 DDL 허용 여부를 정하면서, 그 후보로 셀 UK가 "완전히 빌드되어 검증까지 끝난 상태"인지 "아직 빌드 중이거나 비활성 상태"인지를 구분하지 않는다. 아직 검증되지 않은 UK를 RK 후보로 셈해버리면, 그 사이에 진짜 RK(PK)를 삭제하는 DDL이 "다른 후보가 있다"는 이유로 허용될 수 있는데, 정작 그 다른 후보는 아직 유일성이 확정되지 않은 상태다.

**구체 예제**:
```sql
-- tbl: PK(a)만 존재. RK = a

-- 세션 1: b 컬럼에 온라인(비차단) 유니크 인덱스 생성 시작 (대용량 테이블이라 시간이 걸림)
ALTER TABLE tbl ADD CONSTRAINT UNIQUE(b) ONLINE;
-- 인덱스가 아직 "빌드 진행 중" 상태 (기존 행 전체의 유일성 검증 미완료)

-- 세션 2: (거의 동시에) 온라인 빌드가 끝나기 전에
ALTER TABLE tbl DROP PRIMARY KEY;
-- "다른 복제키 후보 b(UK)가 있다"는 이유로 통과된다면?
-- 그러나 b는 아직 진짜 유일함이 검증되지 않은 상태다.
```

**예제 설명**: 만약 §4-2의 후보 판정 로직이 인덱스 상태를 확인하지 않고 단순히 "UNIQUE 제약이 카탈로그에 존재하는가"만 본다면, 위 시나리오에서 PK 삭제가 통과된 뒤 온라인 빌드가 실제로는 기존 데이터의 중복 때문에 실패로 끝날 수 있다. 그 순간 테이블은 RK 후보가 하나도 없는 상태로 남는데, 이는 §4-1이 절대 허용하지 않는 상태다. 온라인/비활성 인덱스는 최종 사용자에게는 익숙하지 않은 기능이라 놓치기 쉽지만, 대용량 테이블을 다루는 운영 환경에서는 인덱스 재구성 시 흔히 쓰이는 기능이다.

**제안**: RK 후보 판정 시 "빌드가 완전히 끝나 유일성 검증까지 마친 정상 상태의 UNIQUE 제약만 후보로 인정한다"는 조건을 §4-2에 명시하고, 온라인 빌드 중인 UK를 근거로 다른 RK 후보를 제거하는 DDL은 온라인 빌드가 완료될 때까지 대기하거나 거부하도록 규정해야 한다.

## 조사 종료 선언

리뷰 개수를 30개까지 채우는 대신 7개에서 마무리한다. 판단 근거는 다음과 같다.

- **실제 엔진 소스를 확인해 근거를 잡은 항목만 남겼다.** 스키마 관리 모듈(제약/인덱스 상태), 복제 모듈(로그 삽입 경로, TDE 플래그), DML 처리 경로(외래키 캐스케이드-복제 순서), unloaddb/loaddb 유틸리티, SQL 문법 정의(온라인/비활성 인덱스, 파티션 제약의 전역/지역 구분)를 직접 훑어 스펙과 충돌하는 지점을 찾았고, 근거가 약하거나 코드로 확인되지 않는 추측(예: 콜레이션 기반 유일성과 RK 매칭의 상호작용, 비-RK UNIQUE 제약이 향후 병렬 적용 설계에 미칠 영향)은 확신이 서지 않아 제외했다.
- **1차 리뷰 및 최종보고서와 겹치는 각도는 모두 배제했다.** 트리거·시리얼·REUSE_OID·파티션의 "언급 자체가 없다"는 지적은 이미 1차 리뷰와 최종보고서가 다뤘으므로, 2차에서는 그중 파티션에 대해서만 "전역/지역 유니크 구분"이라는 구체적이고 새로운 실패 모드를 추가했고, 트리거·시리얼·REUSE_OID는 코드 확인 결과 추가로 파고들 만한 새로운 실패 지점을 찾지 못해 그대로 뒀다.
- **더 훑었지만 채택하지 않은 영역**: collation(대소문자 구분 없는 유니크 제약과 RK 매칭)은 유일성 제약 자체가 이미 같은 기준으로 중복을 막기 때문에 실질적 모호성이 없다고 판단해 제외했다. REUSE_OID와 외래키 참조 제한 관계도 코드를 확인했으나 실제로는 OID 타입 참조(객체 컬럼)에만 적용되는 제약이라 이 스펙의 값 기반 외래키와는 무관해 제외했다. 필터/함수 기반 유니크 인덱스는 CUBRID가 애초에 지원하지 않아(엔진이 명시적으로 막아둠) 해당 사항 없음으로 확인했다.

이 관점(엔진 구현, 3년차)에서 스펙 문서와 실제 코드 사이의 명백한 충돌 지점은 이번 7개로 충분히 드러났다고 판단한다. 추가 여지가 있다면 병렬 applylogdb 설계와의 결합 지점(RK 외 UNIQUE 제약의 충돌 감지 역할)이지만, 이는 이번 스펙(단일 노드 순차 적용 기준)의 범위를 넘어서는 별도 프로젝트의 관심사에 가까워 이번 리포트에서는 다루지 않았다.
