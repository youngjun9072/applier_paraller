# CUBRID HA 복제 개선 스펙 리뷰 — DB 엔지니어(DBA/운영) · 10년차 관점 · 2차 라운드

## 2차 라운드 개요

1차 리뷰는 "FK 부모 사후 OFF 전환", "RK 비결정성", "업그레이드 경로 부재" 등 스펙 본문이 직접 다루는 절들의 정합성 문제를 중심으로 봤다. 2차에서는 그 20건과 최종보고서에 이미 통합된 40개 이슈를 모두 피해, 스펙이 아예 언급조차 하지 않는 **인접 기존 기능(TDE, 트리거, 파티션은 제외하고 검토 후 근거 부족으로 배제)과의 상호작용, 클러스터 구성원 변경(failover·재접속) 시점의 검증 공백, 권한·로깅 운영 절차**를 새로 팠다. 파티션·REUSE_OID·collation 등은 검토했으나 CUBRID 내부 동작에 대한 확실한 근거 없이 추측만으로 결함을 단정하기 어려워 이번 리포트에서는 제외했다.

## 리뷰 21

**[심각도: 치명] Failover(역할 승격)가 §7의 HA 전환 제약사항 검사를 우회한다**

**대상**: §7(HA 전환), §1("HA 모드는 'cubrid hb start'로 큐브리드를 실행시킨 상태를 의미")

**문제 설명**: §7은 "HA 실행시 다음 사항을 제약사항을 확인하며..."라고 명시하고, §1은 "HA 모드"를 명시적으로 `cubrid hb start` 명령으로 정의한다. 즉 이 스펙이 정의하는 검증 게이트는 **프로세스를 새로 기동하는 시점**에만 걸린다. 그런데 실제 HA 클러스터에서 가장 빈번하게 일어나는 "마스터가 바뀌는" 이벤트는 `cubrid hb start`를 다시 실행하는 것이 아니라 **failover**다. failover는 이미 떠 있는 슬레이브 프로세스가 heartbeat 판단에 따라 마스터 역할로 승격되는 것이지, 그 슬레이브 프로세스를 재기동(`hb start`)하는 절차가 아니다. 따라서 §7이 정의한 "복제 대상 테이블에 RK가 있는가", "FK 참조 테이블이 복제 대상인가" 같은 검사는 **failover 시점에는 전혀 재실행되지 않는다**. 만약 마스터에서 어떤 경로로든(예: 리뷰1에서 지적한 사후 REPLICATION=OFF 전환처럼, 검사가 뚫린 다른 결함과 결합해) 이미 위반 상태인 테이블이 존재한 채로 클러스터가 돌고 있었다면, 그 위반을 안고 있는 슬레이브가 failover로 새 마스터가 되는 순간 아무 경고 없이 그 상태로 쓰기 트래픽을 받기 시작한다.

**구체 예제**:
```text
[시나리오]
1. 마스터 M, 슬레이브 S1, S2로 구성된 HA 클러스터가 이미 cubrid hb start로 기동되어
   정상 운영 중이다 (즉 §7 검사는 이미 오래 전에 한 번 통과한 상태).
2. 운영 중 어떤 경로로 order_items 테이블이 RK 후보를 모두 잃은 위반 상태가 된다.
   (§7은 "HA 실행시" 즉 시작 시점에만 검사하므로, 운영 중에는 이 위반을
    탐지할 별도 감시가 스펙에 없다 — 다음 재기동 전까지는 조용히 존재한다.)
3. 이 상태에서 마스터 M이 하드웨어 장애로 다운된다.
4. heartbeat 프로세스가 S1을 새 마스터로 승격한다.
   -> 이 승격은 "cubrid hb start"가 아니라 이미 실행 중이던 S1 프로세스의
      역할 전환이므로, §7이 정의한 "HA 실행시 제약사항 확인"의 적용 대상인지
      스펙에 정의가 없다.
5. S1이 새 마스터로서 order_items에 대한 쓰기를 받기 시작한다.
   위반 상태(RK 없음)를 그대로 이어받았으므로, 원래 이 기능이 막으려던
   "복제 누락 + fail_count 증가" 문제가 failover 직후 즉시 재현될 수 있다.
```

**예제 설명**: 이 시나리오의 핵심은 "이 기능의 안전장치가 언제 작동하는가"라는 질문이다. §7의 문구를 문자 그대로 읽으면 안전장치는 `cubrid hb start`라는 **명령 실행**에 결속되어 있지, "이 노드가 마스터 역할을 맡는 모든 순간"에 결속되어 있지 않다. 실무에서는 노드가 재기동되는 일보다 failover가 일어나는 일이 훨씬 잦고, 특히 failover는 장애 상황에서 발생하므로 이때 검증이 빠지면 가장 위험한 순간에 가장 약한 방어만 남는 셈이다.

**제안**: §7의 검사 대상을 "cubrid hb start 명령 실행 시점"뿐 아니라 "슬레이브가 마스터로 승격되는 모든 시점(failover, 수동 switchover 포함)"으로 명시적으로 확장하고, 승격 전 검사에서 위반이 발견되면 해당 노드로의 승격 자체를 거부하거나(다른 정상 슬레이브를 우선 승격) 최소한 즉시 경고를 발생시키는 절차를 §7에 추가해야 한다.

## 리뷰 22

**[심각도: 중요] 트리거로 구현한 참조 무결성은 §5의 FK 보호 대상이 아니어서 완전한 사각지대가 된다**

**대상**: §5(외래키)

**문제 설명**: §5의 모든 보호 로직(예시 17~23)은 `FOREIGN KEY` 제약을 선언적으로(즉 `CONSTRAINT ... FOREIGN KEY ... REFERENCES ...` 문법으로) 정의한 경우만 검사한다. 그런데 실무에서는 네이티브 FK 제약이 요구조건(ON DELETE 정책, 성능, 순환 참조 회피 등)에 맞지 않아 **트리거로 참조 무결성을 직접 구현**하는 패턴이 드물지 않다(예: BEFORE INSERT 트리거에서 참조 테이블에 해당 값이 있는지 SELECT로 확인 후 없으면 에러를 던지는 방식). 이런 트리거는 문법적으로 `FOREIGN KEY`가 전혀 등장하지 않으므로, §5가 말하는 "외래키를 포함하는 복제 테이블의 참조 테이블이 복제 대상이 아닌 경우"라는 검사 대상 자체에 걸리지 않는다. 즉 이 스펙이 존재하는 근본 이유(도입부 다이어그램의 orders/customers 문제)와 정확히 동일한 실패를 재현하면서도, 스펙이 제공하는 유일한 방어선(§5, §7의 FK 검사)을 문법적으로 완전히 비켜간다.

**구체 예제**:
```sql
-- customers 는 REPLICATION=OFF (예: 회원 개인정보라 규정상 슬레이브로 내보내지 않기로 결정)
CREATE TABLE customers(
    customer_id INT PRIMARY KEY,
    country INT
) REPLICATION=OFF;

-- orders 는 REPLICATION=ON, 그러나 참조 무결성은 FK가 아니라 트리거로 구현
CREATE TABLE orders(
    order_id INT PRIMARY KEY,
    customer_id INT
);  -- FOREIGN KEY 없음 -> §5 검사 대상 아님

CREATE TRIGGER trg_orders_check_customer
BEFORE INSERT ON orders
IF (SELECT COUNT(*) FROM customers WHERE customer_id = NEW.customer_id) = 0
EXECUTE '{ RAISE_APPLICATION_ERROR(-20001, "no such customer"); }';
-- 이 CREATE TRIGGER는 §5 어디에도 걸리지 않고 그대로 OK 된다.
-- HA 전환(§7) 검사도 "외래키를 포함하는 복제 테이블"만 훑으므로 orders는 대상에서 빠진다.
```

**예제 설명**: 이 예제는 문법적으로 FK가 없을 뿐, 의미상으로는 예시 18(복제 제외 테이블 참조 예시, ERROR)과 완전히 동일한 상황이다. 그런데도 스펙의 방어 로직이 "FOREIGN KEY 키워드가 카탈로그에 있는가"라는 구문적 조건에 묶여 있어서 통과된다. Failover가 나면 orders는 정상 복제되어 있고, 트리거도 슬레이브의 카탈로그에 DDL로 복제되어 존재하겠지만(§4: "모든 DDL은 슬레이브로 복제") customers 데이터가 없으므로 이 트리거가 슬레이브에서 실행될 경우(혹은 애플리케이션이 직접 customers를 조회할 경우) 원래 막으려던 바로 그 문제가 재현된다.

**제안**: §5의 검사를 "선언적 FOREIGN KEY 제약"으로 한정한다는 점을 스펙에 명시하고, 트리거·애플리케이션 레벨 참조 무결성은 이 기능의 보호 범위 밖(out of scope)임을 문서에 경고 문구로 남길 것을 권고한다. 완전한 해결은 불가능하더라도, "네이티브 FK를 쓰지 않으면 이 안전장치가 적용되지 않는다"는 사실만이라도 명문화해야 트리거 기반 설계를 쓰는 팀이 위험을 인지할 수 있다.

## 리뷰 23

**[심각도: 중요] TDE(투명 데이터 암호화)로 암호화된 복제 대상 테이블이 슬레이브에서 정상 처리되는지에 대한 언급이 없다**

**대상**: §2-3 예시 9(`db_class` 출력에 `tde_algorithm` 필드 존재), 스펙 전체

**문제 설명**: 스펙이 스스로 제시한 예시 9의 `db_class` 출력에는 `tde_algorithm : 'NONE'`이라는 필드가 `replication : ON`과 나란히 표시된다. 이는 CUBRID가 이미 테이블 단위 TDE(Transparent Data Encryption, 저장 데이터를 자동으로 암호화/복호화하는 기능)를 지원하며, 이번 REPLICATION 옵션과 같은 카탈로그 레벨에 공존한다는 뜻이다. 그런데 스펙 어디에도 "TDE로 암호화된 복제 대상 테이블의 데이터가 복제 로그를 통해 슬레이브로 전달될 때, 슬레이브가 이를 복호화하기 위한 키(마스터 키 혹은 볼륨 키)를 이미 갖고 있어야 하는가"에 대한 언급이 없다. CUBRID의 TDE는 통상 서버 기동 시 별도로 키를 언락(unlock)하는 절차(`cubrid tde` 유틸리티 등)를 거치는 것으로 알려져 있는데, 이 언락 상태가 마스터와 슬레이브에 독립적으로 관리된다면, 슬레이브의 키가 언락되어 있지 않은 상태에서 암호화된 테이블의 복제 데이터가 도착했을 때 어떤 일이 벌어지는지 스펙은 침묵한다.

**구체 예제**:
```text
[운영 시나리오]
1. 마스터에서 TDE로 암호화된 테이블(예: customers, 개인정보 컬럼 암호화)이
   REPLICATION=ON 상태로 정상 운영 중이다.
2. 슬레이브 노드를 유지보수 후 재기동했는데, 담당자가 TDE 키 언락 절차를
   빠뜨렸다 (마스터와 슬레이브의 키 언락은 각 노드에서 독립적으로 수행하는
   운영 작업이므로 실수로 누락되기 쉽다).
3. 마스터에서 customers 테이블에 INSERT가 발생 -> 복제 로그가 슬레이브로 전달됨
4. applylogdb가 이 로그를 슬레이브의 customers 테이블에 적용하려 한다.
   - 키가 언락되지 않은 슬레이브는 이 데이터를 어떻게 처리하는가?
     (a) applylogdb가 명확한 에러로 중단되고 fail_count가 오르는가?
     (b) 암호화되지 않은 평문으로 잘못 저장되는가? (보안 사고)
     (c) 애초에 슬레이브가 언락 실패 시 통째로 기동을 거부하는가?
   스펙은 세 가지 중 어느 것도 언급하지 않는다.
```

**예제 설명**: (b)의 경우 원래 암호화로 보호하려던 개인정보가 슬레이브에 평문으로 남는 심각한 보안 사고로 이어질 수 있고, (a)의 경우 이 새 기능이 원래 해결하려던 것과 같은 종류의 "복제 실패로 인한 데이터 불일치"가 TDE라는 다른 원인으로 재발한다. 이 스펙 자체가 REPLICATION 도입을 위해 만든 문서인 만큼, 최소한 자신이 예시로 든 카탈로그 필드(`tde_algorithm`)와의 상호작용 여부는 "확인했고 문제없다" 혹은 "이 조합은 향후 과제"라고 한 줄이라도 밝혀야 한다.

**제안**: TDE가 적용된 테이블에 대해 REPLICATION=ON을 허용하는 조건(슬레이브의 키 언락 상태를 사전에 검증하는지, 검증하지 않는다면 그 이유)을 명시하고, 최소한 §7의 HA 전환 검사 항목에 "TDE 테이블의 경우 슬레이브 키 언락 여부 확인"을 추가할지 검토할 것을 권고한다.

## 리뷰 24

**[심각도: 중요] 슬레이브가 일시 단절 후 재접속할 때, 단절 구간에 RK가 바뀐 트랜잭션의 캐치업 처리가 정의되지 않았다**

**대상**: §4-2(RK 변경), 배경(applylogdb, fail_count)

**문제 설명**: 실 운영에서 슬레이브는 네트워크 순단, OS 패치를 위한 재기동, 디스크 점검 등으로 마스터와 잠시 연결이 끊겼다가 다시 붙는 일이 흔하다(신규 슬레이브를 처음부터 구성하는 것과는 다른, "이미 클러스터의 정식 멤버였던 슬레이브"의 일시 이탈-복귀). 재접속 시 슬레이브는 자신이 마지막으로 적용한 시점 이후의 복제 로그를 순서대로 따라잡는다(catch-up). 그런데 만약 그 단절 구간 동안 마스터에서 RK를 변경하는 DDL(예시 13 유형)이 실행되었다면, 슬레이브는 재접속 후 "옛 RK 기준으로 기록된 DML 로그"와 "RK를 바꾸는 DDL 로그"를 한꺼번에, 그것도 정상 운영 중이었다면 시간차를 두고 순서대로 받았을 로그를 몰아서 받게 된다. 이 몰아 받기(batch catch-up) 상황에서 RK 전환의 순서 보장이 정상 운영 시와 동일하게 유지되는지, 아니면 catch-up 경로가 별도의 최적화(예: 병렬 적용)를 타면서 순서가 흐트러질 위험이 있는지 스펙은 다루지 않는다.

**구체 예제**:
```text
[슬레이브 일시 단절 시나리오]
1. 슬레이브 S가 네트워크 문제로 마스터로부터 5분간 연결이 끊긴다.
2. 그 5분 사이 마스터에서는:
   - UPDATE tbl SET c=1 WHERE a=10;         (RK=a 기준 로그 A)
   - ALTER TABLE tbl DROP CONSTRAINT PRIMARY KEY,
     ADD CONSTRAINT PRIMARY KEY(b);          (RK를 a->b로 전환하는 DDL 로그 D)
   - UPDATE tbl SET c=2 WHERE b=20;         (RK=b 기준 로그 B)
   이 세 로그가 마스터의 트랜잭션 로그에는 A, D, B 순서로 쌓인다.
3. 5분 후 S가 재접속해 밀린 로그를 한 번에 받아 적용을 시작한다(catch-up).
4. catch-up 과정이 실시간 스트리밍 적용과 다른 경로(예: 대량 로그를 묶어서
   처리하는 별도 최적화 루틴)를 탄다면, A, D, B의 순서가 실시간 적용 때와
   동일하게 보장되는지 스펙에 근거가 없다.
```

**예제 설명**: 이 시나리오는 리뷰 대상 최종보고서의 "정상 운영 중 로그 지연(lag)" 문제와는 결이 다르다. 거기서는 실시간으로 조금씩 밀리는 상황을, 여기서는 슬레이브가 완전히 끊겼다가 한꺼번에 몰아서 재생하는 별도의 코드 경로(흔히 실시간 적용과 catch-up 적용은 구현이 다르다)를 문제 삼는다. 순서 보장 로직이 실시간 경로에만 구현되고 catch-up 경로에는 반영되지 않았다면, 이 흔한 운영 이벤트(슬레이브 재기동)만으로 RK 전환 정합성이 깨질 수 있다.

**제안**: RK 전환 DDL의 순서 보장 규칙이 실시간 적용 경로뿐 아니라 catch-up(재접속 후 로그 재생) 경로에도 동일하게 적용됨을 명시하고, 두 경로에 대한 회귀 테스트를 별도로 요구할 것을 권고한다.

## 리뷰 25

**[심각도: 보통] 멀티 데이터베이스를 서비스하는 서버에서 `cubrid hb start`의 실패 범위(전체 서버 vs 개별 DB)가 불명확하다**

**대상**: §7(HA 전환)

**문제 설명**: 리뷰 9(1차)에서 지적한 대로 §7의 출력 형식 자체도 불명확하지만, 여기서는 다른 축을 짚는다. CUBRID 서버 한 대는 보통 여러 개의 데이터베이스를 동시에 서비스할 수 있다. §7의 예시(`cubrid hb start mydb`처럼 특정 DB 이름을 대상으로 하는 형태로 흔히 쓰인다)를 보면 검사가 DB 단위로 도는 것처럼 보이지만, 만약 한 서버가 db_A, db_B, db_C 세 개를 관리하고 그중 db_B에만 RK 위반 테이블이 있다면, 이 서버 프로세스 전체의 HA 기동이 실패하는지 아니면 db_A와 db_C는 정상적으로 HA 모드에 들어가고 db_B만 개별적으로 실패(또는 싱글 모드로 남는지)하는지 스펙에 명시가 없다. 이 차이는 장애 대응 시 "얼마나 많은 서비스가 영향을 받는가"를 결정하는 중요한 정보다.

**구체 예제**:
```text
[운영 시나리오]
서버 노드 1대가 db_orders, db_inventory, db_reporting 세 개의 DB를 서비스한다.
db_reporting에만 최근 스키마 변경으로 RK 위반 테이블이 생겼다.

$ cubrid hb start
-- 이 명령이 노드 전체를 대상으로 하는 것이라면:
--   (a) db_reporting의 위반 때문에 db_orders, db_inventory까지 HA 기동이 막히는가?
--   (b) 아니면 db_reporting만 제외하고 나머지는 정상적으로 HA에 편입되는가?
-- 스펙 §7은 이 중 어느 것인지 답하지 않는다.
```

**예제 설명**: (a)라면 스키마 관리가 느슨한 서브 시스템(db_reporting) 하나의 실수가 핵심 서비스(db_orders)의 HA 전환까지 막는 "blast radius(장애 파급 범위)"가 예상보다 훨씬 커진다. 장애 대응 매뉴얼을 작성하려는 DBA에게는 이 범위 정보가 필수적인데, 스펙은 검사 "내용"만 정의하고 검사의 "적용 단위"는 정의하지 않았다.

**제안**: §7에 "이 검사는 DB 단위로 독립적으로 수행되며, 특정 DB의 위반이 동일 서버의 다른 DB의 HA 전환에 영향을 주지 않는다"(혹은 그 반대라면 그렇게) 한 문장을 명시할 것을 권고한다.

## 리뷰 26

**[심각도: 중요] REPLICATION 옵션 변경에 대한 별도의 권한 통제가 없어, 일반 테이블 소유자가 클러스터 전체의 데이터 정합성에 영향을 주는 조작을 할 수 있다**

**대상**: §2-2(ALTER 옵션), 스펙 전체(보안/권한 관점 서술 없음)

**문제 설명**: 스펙의 모든 예시는 `ALTER TABLE tbl REPLICATION=OFF` 같은 문장을 별다른 권한 조건 없이 실행 가능한 것으로 서술한다. 일반적으로 CUBRID에서 `ALTER TABLE`은 테이블 소유자(혹은 DBA)가 실행할 수 있는 권한 범위 안에 있다. 그런데 이번에 추가되는 `REPLICATION` 옵션은 다른 일반적인 ALTER(컬럼 추가, 인덱스 생성 등)와 성격이 근본적으로 다르다 — 이 옵션 하나의 변경이 **해당 테이블 하나의 스키마**가 아니라 **클러스터 전체의 마스터-슬레이브 데이터 일치 여부**에 영향을 준다(그리고 리뷰 1에서 지적했듯, FK로 얽힌 다른 테이블의 복제 안전성에도 파급된다). 일반 애플리케이션 계정이 소유한 테이블이라면, 그 팀이 "이 테이블은 부하가 많으니 복제를 끄자"는 국소적 판단만으로 클러스터 전체의 FK 무결성이나 failover 시나리오에 영향을 줄 수 있는데, 이를 막거나 최소한 감사(audit)하는 절차가 스펙에 없다.

**구체 예제**:
```sql
-- 애플리케이션 팀 계정 app_user가 소유한 customers 테이블
-- (DBA가 아니라 개발팀이 직접 운영 DB에 배포 권한을 갖는 조직 구조는 드물지 않다)
csql> connect testdb@app_user;
csql> ALTER TABLE customers REPLICATION=OFF;
-- 스펙 예시 6과 동일한 문장. 스펙에는 "DBA 권한 필요" 같은 제약이 없으므로
-- app_user가 ALTER TABLE 권한만 가지고 있으면 그대로 실행된다.
-- 이 한 줄로 orders(다른 팀 소유, FK로 customers 참조)의 failover 안전성까지
-- 함께 깨질 수 있다 (리뷰 1의 시나리오가 DBA 승인 없이 발생).
```

**예제 설명**: 이 예제는 "기술적으로 막을 방법이 없다"는 리뷰 1(1차)의 문제와는 다른 축이다. 리뷰 1은 "규칙 자체가 없다"는 것이었고, 이 리뷰는 설령 규칙이 추가되더라도 "누가 이 옵션을 바꿀 수 있는가"에 대한 접근 통제가 스펙 설계 단계에서부터 고려되지 않았다는 점을 지적한다. 규정 준수(컴플라이언스)가 엄격한 금융권 등에서는 "복제 대상 여부 변경"처럼 재해복구 계획에 직결되는 조작은 반드시 변경 관리 승인을 거치도록 요구하는 경우가 많은데, 이런 요구를 시스템 차원에서 강제할 수 있는 수단(예: DBA 전용 권한으로 분리)이 이번 스펙에는 전혀 반영되어 있지 않다.

**제안**: `REPLICATION` 옵션 변경을 일반 `ALTER TABLE` 권한과 분리된 별도 권한(예: DBA 그룹 전용)으로 제한하는 방안을 검토하고, 최소한 이 옵션이 변경될 때 서버 로그에 "누가, 언제, 어떤 테이블의 REPLICATION을 바꿨는지"가 표준 감사 로그 형태로 남도록 요구할 것을 권고한다.

## 리뷰 27

**[심각도: 보통] REPLICATION=OFF가 정확히 어느 계층에서 동작하는지 불명확해 성능/용량 이득을 사전에 산정할 수 없다**

**대상**: §1, §4(HA 제약사항), 배경(성능 문제로 MySQL 방식 배제)

**문제 설명**: 이 스펙의 배경 설명은 "MySQL처럼 PK 없으면 모든 컬럼을 키로 사용하는 방식은 성능이 느려서 배제했다"고 명시할 만큼 성능을 중요한 설계 기준으로 삼고 있다. 그런데 정작 REPLICATION=OFF 자체가 **어느 계층에서** 비용을 줄이는지는 스펙에 설명이 없다. CUBRID는 원래 자신의 크래시 복구(재시작 시 이전 상태 복원)를 위해 모든 트랜잭션에 대해 REDO/UNDO 로그를 남긴다. REPLICATION=OFF가 (a) 이 트랜잭션 로그 자체의 생성을 건너뛰는 것인지(그렇다면 애초에 크래시 복구용 로그와 복제용 로그가 분리되어 있어야 하는데, 그런 구조 변경이 이번 스펙 범위에 포함되는지 불명), 아니면 (b) 트랜잭션 로그는 평소처럼 다 쌓이지만 그중 복제 대상으로 슬레이브에 **전송/추출**하는 단계에서만 걸러내는 것인지(그렇다면 마스터의 디스크 I/O나 로그 보존 비용은 전혀 줄지 않고, 오직 네트워크 대역폭과 슬레이브 저장 공간만 절약된다)에 따라 운영자가 기대할 수 있는 이득이 완전히 다르다.

**구체 예제**:
```text
[용량 산정 관점]
운영자가 "쓰기 부하가 매우 높은 로그성 테이블 access_log를 REPLICATION=OFF로
돌리면 마스터의 디스크 I/O 부담도 줄어들 것"이라고 기대하고 마이그레이션
계획을 세운다고 하자.

- 만약 (b)라면: 마스터는 여전히 access_log의 모든 쓰기에 대해 REDO 로그를
  100% 기록한다(자체 크래시 복구를 위해 반드시 필요하므로). REPLICATION=OFF는
  오직 "이 로그를 슬레이브로 보낼지 말지"만 결정한다. 이 경우 운영자가
  기대한 마스터 측 I/O 절감은 실제로 일어나지 않는다.
- 스펙 문장만으로는 (a)와 (b) 중 어느 쪽인지 판단할 근거가 없다.
```

**예제 설명**: 이 구분은 단순한 세부 구현 사항이 아니라, 운영자가 이 기능을 "성능 최적화 수단"으로 오인해 잘못된 용량 계획(예: 디스크 증설을 미루는 결정)을 내릴 수 있는 실질적 위험이다. 배경 설명이 성능을 이유로 다른 설계(MySQL 방식)를 명시적으로 배제한 문서인 만큼, 정작 채택한 설계가 어느 계층에서 비용을 줄이는지는 최소한 한 문단으로 밝혀야 균형이 맞는다.

**제안**: REPLICATION=OFF가 마스터의 트랜잭션 로그 생성 자체에 영향을 주는지, 아니면 복제 로그 추출/전송 단계에서만 필터링하는 것인지 명시하고, 각각의 경우 기대할 수 있는 성능/용량 이득의 범위(마스터 I/O, 네트워크 대역폭, 슬레이브 저장공간 중 무엇이 절감되는지)를 §1 또는 별도 성능 절에 표로 정리할 것을 권고한다.

## 리뷰 28

**[심각도: 보통] 신규 제약 위반 에러가 서버 측 에러 로그에도 기록되는지 불명확해, 비대화형 배치 작업에서 발생한 위반을 사후에 추적할 수 없다**

**대상**: §4-2, §5의 각 예시(ERROR 표기), 운영 로깅 절차

**문제 설명**: 스펙의 모든 ERROR 예시(예시 5, 10, 12, 15, 16, 18, 22, 23 등)는 `csql` 대화형 세션에서 사용자가 직접 명령을 치고 즉시 화면으로 에러를 확인하는 상황만 보여준다. 그런데 실제 운영에서 스키마 변경은 대부분 배포 파이프라인이 야간에 스크립트로 `csql -i migration.sql`처럼 비대화형으로 실행한다. 이 경우 화면에 찍힌 에러 메시지는 파이프라인 로그(표준출력/표준에러 리다이렉션 대상)에만 남고, 그 로그가 유실되거나 파이프라인 자체가 별도 처리 없이 넘어가 버리면 그 실패를 아무도 알아채지 못할 수 있다. 이런 위험 때문에 성숙한 DBMS는 클라이언트 세션의 에러와 별개로 **서버 자체의 에러 로그 파일**에도 주요 스키마 변경 실패를 기록해 사후 추적이 가능하게 하는데, 이번 신규 제약(RK/FK 관련 에러)이 이 서버 측 로그에도 남는지 스펙에 언급이 없다.

**구체 예제**:
```bash
# 야간 배포 파이프라인 스크립트 (담당자가 결과를 확인하지 않고 다음 단계로 진행)
$ csql -i nightly_migration.sql -u dba testdb > /tmp/migration.log 2>&1
$ deploy_next_stage.sh   # migration.log의 성공 여부를 검사하지 않고 무조건 실행

# nightly_migration.sql 안에 다음 문장이 포함되어 있었다고 하자
ALTER TABLE order_items DROP CONSTRAINT u_order_items_sku;
-- 예시 15에 해당하는 ERROR (복제키로 쓰이는 UNIQUE 제약 삭제 시도)
-- /tmp/migration.log 에만 에러가 남고, 이 파일은 3일 뒤 로테이션되어 사라진다.
-- 서버 측(예: $CUBRID_DATABASES/testdb/testdb.err 유사 위치)에도
-- 이 실패가 기록되는지 스펙에 근거가 없어, 나중에 "언제부터 order_items의
-- RK가 위반 상태였는지" 조사할 방법이 없다.
```

**예제 설명**: 이 예제는 M-6(최종보고서, 에러 메시지 문구·코드 부재)과는 다른 층위를 짚는다. M-6은 "에러 메시지 내용이 부실하다"는 것이고, 이 리뷰는 "그 메시지가 애초에 클라이언트 화면 밖으로 나가 서버 로그에 영속적으로 남는지"를 묻는다. 메시지 내용이 아무리 좋아져도, 그 메시지를 볼 사람이 아무도 없는 채로 사라진다면 사후 감사나 장애 원인 추적에는 도움이 되지 않는다.

**제안**: RK/FK/REPLICATION 관련 신규 제약 위반이 발생하면 클라이언트 응답과 별도로 서버 측 에러 로그(또는 HA 관련 전용 로그)에도 동일 내용이 기록되도록 요구사항을 명시할 것을 권고한다.

## 조사 종료 선언

이번 2차 라운드에서는 §3(싱글 제약), §6(뷰), §8 세부 절차, 파티션, 트리거, 시리얼, 소유자 권한, TDE, collation, REUSE_OID 등 스펙이 침묵하는 영역과 failover·재접속 같은 클러스터 이벤트 시점의 검증 공백을 훑었다. 이 중 파티션·collation·REUSE_OID·SERIAL은 CUBRID 내부 동작에 대한 확실한 근거 없이는 결함을 단정할 수 없다고 판단해 제외했고(추측성 지적 배제), 시리얼(AUTO_INCREMENT) 동기화는 최종보고서에 엔진 개발자 관점에서 이미 다뤄져 중복으로 제외했다. 나머지 영역에서 8건의 신규 지적(치명 2, 중요 3, 보통 3)을 확보했으며, 그 이상으로 파고들 경우 이미 1차·최종보고서에서 다룬 이슈(RK 비결정성, FK 사후 전환, 롤링 업그레이드, 원자성, 에러 코드 등)의 변주에 그친다고 판단해 여기서 조사를 마친다. 30건을 채우지 못했지만, 이는 미개척 영역이 남아서가 아니라 이미 40개 통합 이슈가 스펙의 대부분의 실패 표면을 촘촘히 덮고 있기 때문이다.
