# CUBRID HA 복제 개선 스펙 리뷰 — DB 사용 개발자(응용 개발) 3년차 관점

## 리뷰어 소개

3년 정도 백엔드 애플리케이션을 개발하며 CUBRID를 포함한 RDBMS를 ORM(Object-Relational
Mapping, 자바/코틀린 등의 객체를 관계형 DB 테이블에 자동으로 매핑해 SQL을 대신 생성해주는
라이브러리) 및 Flyway/Liquibase 같은 스키마 마이그레이션 도구와 함께 다뤄왔다. DB 엔진 내부
구현보다는 "내가 짠 마이그레이션 스크립트가 개발 환경에서 통과했을 때 운영 환경에서도 똑같이
동작하는가", "FK(외래키, Foreign Key — 한 테이블의 컬럼 값이 다른 테이블의 특정 컬럼 값을
참조하도록 강제하는 제약)를 걸어둔 스키마가 장애 상황에서도 애플리케이션 로직을 깨뜨리지
않는가"에 관심이 많다.

## 총평

이번 스펙은 PK(Primary Key)가 없어 복제가 누락되던 기존 문제를 RK(Replication Key) 자동
선택과 REPLICATION 옵션으로 해결하려는 방향 자체는 합리적이다. 그러나 응용 개발자 입장에서
보면 **싱글 모드(HA 없이 단독으로 동작하는 모드)와 HA 모드의 DDL(Data Definition Language,
테이블·인덱스 등 스키마 구조를 정의·변경하는 SQL 명령군) 허용 범위가 서로 다르다는 사실이
스펙 곳곳에 흩어져 있을 뿐, "개발-스테이징에서 검증한 마이그레이션이 운영에서 실패할 수
있다"는 핵심 리스크로 정리되어 있지 않다**. 또한 RK가 사용자 모르게 자동으로 재선택되는
지점, FK 참조 테이블의 REPLICATION 상태를 사후에 바꾸는 경우에 대한 재검증 누락, 그리고
VIEW·FK 사이의 검증 수준 불일치 등 상호 모순이 여러 곳에서 발견된다. 예시 코드 자체에도
문법 오류와 명명 불일치가 있어 문서만 보고 그대로 실습하면 실패하는 경우가 있다. 전체적으로
컨셉은 방향성이 맞지만, "실무자가 매일 하는 작업(컬럼 타입 변경, 인덱스 재구성, 데이터
이관)에 이 스펙을 대입했을 때 무슨 일이 벌어지는가"에 대한 기술이 부족하다.

## 리뷰 1

**[심각도: 치명] 싱글 모드와 HA 모드의 RK 제약 비대칭 — 마이그레이션 스크립트가 개발 환경만 통과하고 운영에서 실패한다**

**대상**: §3(Single 제약사항) "제약은 없으나 … 싱글 모드에서 생성된 복제 키가 없는 테이블은 HA모드 전환 시 복제 키를 추가하거나 복제 제외 테이블로 변경할 수 있어야한다" vs §4-1/§4-2(HA 제약사항)

**문제 설명**: §3은 싱글 모드에서는 RK(복제 키) 관련 제약이 전혀 없다고 명시한다. 반면 §4-1, §4-2는 HA 모드에서 RK가 없는 복제 테이블 생성을 막고(예시 10), RK 컬럼의 삭제·변경도 제한한다(예시 12, 15, 16). 많은 조직의 배포 파이프라인은 "로컬 개발 → 싱글 모드 스테이징 서버에서 마이그레이션 검증 → 운영(HA) 배포" 순서를 따른다. 스테이징이 싱글 모드라면 RK를 깨뜨리는 마이그레이션도 아무 에러 없이 통과하고, 그 스크립트가 그대로 운영 HA 환경에 적용되는 순간 처음으로 에러가 발생한다. 이는 "개발-스테이징(싱글)과 운영(HA)의 동작 차이로 인한 사고"의 전형적인 사례인데, 스펙에는 이 위험을 명시적으로 경고하는 문구가 없다.

**구체 예제**:
```sql
-- (1) 로컬 개발 DB: 싱글 모드. Liquibase/Flyway 마이그레이션 스크립트 V12__drop_legacy_uk.sql
ALTER TABLE customers DROP CONSTRAINT u_customers_email;
-- 싱글 모드에서는 §3에 따라 제약이 없으므로 OK, CI 파이프라인 그린

-- (2) 스테이징 서버도 싱글 모드로 운영 중이라 동일하게 OK

-- (3) 운영 서버는 "cubrid hb start"로 이미 HA 실행 중.
--     customers 테이블의 RK가 u_customers_email(UK) 하나뿐이었다면
ALTER TABLE customers DROP CONSTRAINT u_customers_email;
-- 예시 15에 따라 ERROR: 복제키로 사용중인 UNIQUE 제약은 삭제 불가
```

**예제 설명**: 동일한 마이그레이션 SQL 한 줄이 배포 파이프라인의 앞 두 단계(로컬, 스테이징)에서는 성공하고, 실제 운영 배포 단계에서만 실패한다. 이 시점은 이미 배포 창(deployment window)이 열려 다른 마이그레이션 스텝들이 순차 실행 중일 수 있고, 실패한 스텝 이후의 트랜잭션 처리 방식(롤백? 스킵?)도 스펙에 없다. 결국 "테스트를 통과한 코드가 운영에서만 깨진다"는, 응용 개발자가 가장 두려워하는 유형의 장애가 이 스펙 구조 자체에서 구조적으로 발생한다.

**제안**: (1) 스펙 문서에 "싱글/스테이징에서 검증된 DDL이 HA에서 실패할 수 있다"는 별도 경고 섹션을 추가한다. (2) 싱글 모드에서도 `--strict-ha` 같은 옵션으로 HA 제약을 미리 시뮬레이션해 검증할 수 있는 수단을 제공한다. (3) 마이그레이션 도구(Flyway 등)가 배포 전에 대상 서버의 HA 여부와 RK 후보 개수를 조회해 사전 경고할 수 있도록 카탈로그 조회 인터페이스를 문서화한다.

## 리뷰 2

**[심각도: 치명] HA 모드에서는 REPLICATION=OFF → ON 전환이 아예 불가능 — "일단 OFF로 대량 적재 후 ON 전환"이라는 흔한 데이터 이관 패턴이 운영 중에는 불가능하다**

**대상**: §1 "단, HA 모드에서는 복제 제외 테이블이 복제 테이블로 변경될 수 없다", §2-2 및 예시 5

**문제 설명**: 응용 개발자가 대용량 초기 데이터를 이관(migration)할 때 흔히 쓰는 패턴은 "복제/트리거 등 부가 비용을 잠시 끄고 벌크 적재 → 적재 완료 후 다시 켠다"이다. 이 스펙에 대입하면 "REPLICATION=OFF로 테이블을 만들어 대량 INSERT 후 REPLICATION=ON으로 전환"하는 식이 될 텐데, 예시 5가 명시하듯 **HA가 이미 실행 중이면 이 전환 자체가 원천적으로 에러**다. 즉 이 패턴은 반드시 싱글 모드로 내려가야만 가능하다. 이는 "운영 중 대용량 데이터 이관"을 사실상 다운타임 없이는 할 수 없다는 뜻인데, 스펙 어디에도 이 제약이 "데이터 이관 시 반드시 싱글 모드로 전환해야 한다"는 형태로 명시적으로 안내되어 있지 않다.

**구체 예제**:
```sql
-- 운영 HA 환경에서, 신규 배치 데이터 이관 작업을 하려는 개발자의 시도
csql> CREATE TABLE staging_orders (
    order_id INT PRIMARY KEY,
    payload  VARCHAR(4000)
) REPLICATION=OFF;
-- 벌크 로더로 수백만 건 INSERT (복제 부하 없이 빠르게 적재하려는 의도)

-- 적재 완료 후 정식 테이블로 전환하려는 시도
csql> ALTER TABLE staging_orders REPLICATION=ON;

ERROR   -- §1, 예시5에 의해 HA 모드에서는 절대 허용되지 않음
```

**예제 설명**: 개발자는 "복제 부하 때문에 이관 초반엔 꺼두고 나중에 켠다"는, 다른 DB(예: PostgreSQL의 `ALTER SUBSCRIPTION ... SET (replicate = ...)` 유사 패턴, 또는 MySQL의 binlog 일시 비활성화 후 재개)에서 익숙한 절차를 그대로 시도했다가 막힌다. 이 제약을 모르면 이관 작업 계획을 다 짜놓고 실행 단계에서야 발견하게 되어, 결국 서비스 점검 시간을 새로 잡아야 하는 일정 리스크로 이어진다.

**제안**: (1) §1 요약이나 §9 SUMMARY에 "HA 실행 중에는 OFF→ON 전환이 불가능하므로 대용량 이관은 반드시 싱글 모드에서 수행하라"는 문장을 명시적으로 추가한다. (2) 운영상 불가피하다면 HA 상태에서도 안전하게 OFF→ON 전환을 허용하는 절차(예: 슬레이브에 데이터 동기화 완료를 확인 후 전환)를 검토한다.

## 리뷰 3

**[심각도: 치명] PK를 나중에 추가하면 RK가 사용자 모르게 조용히 재선택된다 — 마이그레이션 스텝 순서에 따라 결과가 달라진다**

**대상**: §1 "PK가 존재한다면 PK가 복제 키가 됨", §4-2 예시 14

**문제 설명**: 스펙은 RK 결정 우선순위를 "PK 있으면 PK, 없으면 UK"로 정의한다. 예시 14는 "UK를 RK로 쓰던 테이블에 PK를 나중에 추가하는 것이 허용된다(OK)"고 말한다. 그런데 이 시점에 우선순위 규칙을 그대로 적용하면, **PK 추가라는 하나의 ALTER 문 실행만으로 RK가 기존 UK에서 새 PK로 자동 전환**되어야 한다. 문제는 이 전환이 사용자가 명시적으로 요청한 동작이 아니라 부수 효과(side effect)라는 점이다. 응용 개발자 입장에서는 "PK만 추가했을 뿐인데 복제 키가 바뀌었다"는 사실을 인지할 방법이 스펙 어디에도 없다(리뷰 11 참고). 더구나 진행 중인 복제 스트림이 있다면, RK 전환 시점 전후로 같은 로우를 서로 다른 키로 식별하게 되는 것 아닌가에 대한 설명이 전혀 없다.

**구체 예제**:
```sql
-- HA 운영 중, orders 테이블은 UK(order_no)를 RK로 사용 중
csql> CREATE TABLE orders(
    order_no INT NOT NULL UNIQUE,
    status   INT
);
-- 이 시점 RK = order_no (UK)

-- 어느 날 팀에서 서러게이트 PK를 도입하기로 결정, 마이그레이션 스텝 실행
csql> ALTER TABLE orders ADD COLUMN id INT AUTO_INCREMENT;
csql> ALTER TABLE orders ADD CONSTRAINT PRIMARY KEY(id);
-- 예시14 기준: OK

-- 이 순간 RK는 §1 우선순위 규칙에 의해 order_no(UK) -> id(PK)로 자동 전환된 것으로 추정되나,
-- 스펙에 이 전환을 알리는 응답/로그/카탈로그 갱신 시점에 대한 언급이 없다.
```

**예제 설명**: 팀 입장에서는 "PK 하나 추가했을 뿐"인데 내부적으로는 복제의 기준 키가 완전히 바뀐다. 애플리케이션이 슬레이브 쪽 데이터 정합성 문제를 디버깅할 때, 이 전환 시점을 모르면 "언제부터 RK가 바뀌었는지" 추적할 방법이 없다. 특히 전환 직전/직후 커밋된 트랜잭션들이 복제 로그에서 서로 다른 키 기준으로 처리된다면 (예: 슬레이브에서 UPDATE 대상 로우를 찾을 때 기준 키가 바뀌는 것) 데이터 불일치가 재발할 수 있다 — 이는 애초에 이 스펙이 해결하려던 문제(§배경) 그 자체다.

**제안**: RK가 자동으로 재선택되는 모든 시점을 카탈로그 변경 이벤트로 남기고, `show create table`이나 별도 명령으로 "직전 RK → 현재 RK" 전환 이력을 조회할 수 있게 한다. 또한 자동 전환이 일어나는 ALTER 문 실행 시 경고 메시지(예: `NOTICE: replication key changed from UK(order_no) to PK(id)`)를 출력해야 한다.

## 리뷰 4

**[심각도: 치명] FK 참조 테이블을 생성 이후에 REPLICATION=OFF로 전환하는 경로에 대한 재검증이 누락되어 있다**

**대상**: §5(외래키), §9 요약 "복제 대상인 외래키 테이블에서 참조하는 모든 테이블이 복제 대상이여야한다"

**문제 설명**: §5와 예시 18, 23은 **CREATE/ALTER로 FK를 새로 만드는 시점**에 참조 테이블이 REPLICATION=OFF이면 에러를 낸다고 명시한다. 그런데 이미 FK 관계가 정상적으로 맺어진 이후, 참조되는 테이블(부모 테이블) 쪽에서 `ALTER TABLE parent REPLICATION=OFF`를 실행하는 시나리오는 스펙에 전혀 다뤄지지 않는다. §4의 "HA 환경 복제 제외테이블은 ALTER TABLE…REPLICATION=ON 을 이용한 복제 테이블로 변경하는것 외의 모든 DDL을 사용할 수 있다"는 문장은 OFF 테이블 쪽 제약만 이야기할 뿐, 반대 방향인 "ON 테이블을 OFF로 바꾸려는데 자신을 참조하는 FK가 있는 경우"는 언급이 없다. 이는 정확히 스펙 배경(§0)에서 그림으로 제시한 "FK 참조 테이블이 복제 제외일 때의 문제 상황"을 CREATE 시점 검증만으로는 막을 수 없다는 뜻이다.

**구체 예제**:
```sql
-- 1단계: 정상적으로 FK 관계 생성 (예시17과 동일)
csql> CREATE TABLE customers(customer_id INT PRIMARY KEY, country INT);
csql> CREATE TABLE orders(
    order_id INT PRIMARY KEY,
    customer_id INT,
    CONSTRAINT fk_customer_id FOREIGN KEY (customer_id) REFERENCES customers(customer_id)
);
-- OK, orders는 REPLICATION=ON(기본값), customers도 ON(기본값)

-- 2단계: 몇 달 후, 다른 팀이 customers를 "우리는 CDC로 별도 동기화하니 복제에서 빼자"며 시도
csql> ALTER TABLE customers REPLICATION=OFF;
-- 스펙에 명시된 검증 규칙이 없어, 이 문장이 OK로 통과할지 ERROR가 날지 불명확.
-- 만약 OK로 통과한다면 orders(ON)가 customers(OFF)를 참조하는,
-- 배경 그림에서 경고한 바로 그 위험 상태가 CREATE 시점 체크를 우회해 만들어진다.
```

**예제 설명**: FK 생성 시점 검증만으로는 "생성 이후 부모 테이블의 REPLICATION 속성이 바뀌는" 경로를 막지 못한다. 실무에서는 스키마가 몇 년에 걸쳐 여러 팀의 손을 거치며 진화하기 때문에, 처음 설계할 때는 올바르게 REPLICATION=ON으로 맺어진 FK 관계도 나중에 누군가 무심코 부모 테이블만 OFF로 바꾸는 순간 깨질 수 있다. 이 취약점은 정확히 스펙이 이미지로 강조한 "failover 후 orders는 있는데 customers가 없다"는 그 장애를 재현한다.

**제안**: `ALTER TABLE ... REPLICATION=OFF` 실행 시, 해당 테이블을 FK로 참조하면서 자신은 REPLICATION=ON인 자식 테이블이 존재하는지 카탈로그를 검사하고, 존재하면 에러로 막아야 한다. §7(HA 전환)의 사전 점검 로직에도 이 케이스(부모가 OFF, 자식이 ON)를 검사 항목으로 추가해야 한다.

## 리뷰 5

**[심각도: 중요] ORM이 기본 생성하는 UNIQUE 제약은 NOT NULL이 아닌 경우가 많아 RK 후보 요건을 조용히 충족하지 못한다**

**대상**: §1 "복제 키는 … Not Null Unique Key(UK)들 중 하나로 선택된다"

**문제 설명**: JPA/Hibernate 같은 ORM에서 엔티티 필드에 `@Column(unique = true)`만 붙이면 기본적으로 `nullable = true`인 UNIQUE 컬럼이 생성된다(대부분의 RDBMS에서 NULL은 UNIQUE 제약과 별개로 취급되어 여러 개의 NULL이 허용됨). 이 UK는 스펙이 요구하는 "NOT NULL UNIQUE"가 아니므로 RK 후보가 될 수 없다. 3년차 응용 개발자가 "이 테이블엔 UNIQUE 인덱스가 있으니 RK 후보가 있겠지"라고 오판하기 쉬운 지점인데, 스펙에는 이 흔한 ORM 매핑 함정에 대한 경고가 전혀 없다.

**구체 예제**:
```java
@Entity
public class Coupon {
    @Id @GeneratedValue
    private Long id; // 이건 못 쓰는 상황을 가정 — 예: AUTO_INCREMENT 미지원 레거시 매핑

    @Column(unique = true) // nullable 기본값 true!
    private String couponCode;
}
```
```sql
-- Hibernate가 실제로 생성하는 DDL
CREATE TABLE coupon (
    id INT,
    coupon_code VARCHAR(50),
    CONSTRAINT uk_coupon_code UNIQUE (coupon_code)  -- NOT NULL 아님
);
-- 이 테이블에는 PK도 없고, UK도 nullable이라 RK 후보가 0개.
-- 싱글 모드에서는 생성되지만 (§3, 제약 없음)
-- HA 전환 시 예시10과 동일하게 ERROR.
```

**예제 설명**: 개발자가 "UNIQUE 제약을 걸었으니 스펙 요건을 충족한다"고 믿고 있다가, HA 전환(§7) 시점에야 비로소 "복제키가 존재하지 않는 경우" 목록에 이 테이블이 올라가는 것을 보고 당황하게 된다. 이는 ORM 코드 한 줄(`nullable = false` 누락)의 차이로 발생하는 문제이며, 코드 리뷰 단계에서 걸러내기 어렵다.

**제안**: 스펙 문서에 "ORM으로 UNIQUE 제약을 생성할 때는 반드시 NOT NULL을 함께 지정해야 RK 후보가 된다"는 안내와, 대표 ORM(Hibernate 등)에서의 올바른 애노테이션 예시(`@Column(unique = true, nullable = false)`)를 부록으로 제공한다.

## 리뷰 6

**[심각도: 중요] RK 후보 개수를 사전에 조회할 표준 방법이 없어 CI/CD 파이프라인에서 정적 검증이 불가능하다**

**대상**: §4-2, 예시 8·9(카탈로그 조회 예시)

**문제 설명**: §4-2는 "복제키 후보가 1개인 경우"와 "여러 개 존재하는 경우"에 따라 허용되는 DDL이 달라진다고 명시한다. 그런데 예시 8(`show create table`)과 예시 9(`select * from db_class`)는 오직 **현재 선택된 RK 하나**만 보여줄 뿐, "이 테이블에 RK 후보가 몇 개 있는지"를 알려주는 조회 수단은 스펙 어디에도 없다. 배포 파이프라인에서 "이 ALTER 문을 실행해도 되는가"를 사전에 정적으로 판단하려면 반드시 후보 개수를 알아야 하는데, 그 방법이 없으니 결국 "일단 실행해보고 에러가 나면 안다"는 시행착오식 배포가 될 수밖에 없다.

**구체 예제**:
```sql
-- 개발자가 CI 파이프라인에서 배포 전 안전성 검사를 하고 싶다.
-- "orders 테이블에 RK 후보가 2개 이상이면 이 ALTER는 안전하다"는 것을 사전에 확인하려는 의도
csql> SELECT ??? FROM db_class WHERE class_name = 'orders';
-- 예시9의 db_class 컬럼 목록(class_name, owner_name, class_type, ..., replication)에는
-- "복제키 후보 개수"나 "현재 RK로 선택된 제약 이름"에 해당하는 컬럼이 없다.
-- 결국 개발자는 사전 검증 스크립트를 작성할 수 없고,
-- ALTER 문을 실제로 실행해 ERROR 여부로만 판단해야 한다.
ALTER TABLE orders DROP CONSTRAINT pk_orders_id; -- 실행해봐야 아는 상태
```

**예제 설명**: 안전한 배포 자동화의 기본 원칙은 "실행하기 전에 실패 여부를 알 수 있어야 한다"는 것이다. 그러나 이 스펙은 카탈로그에 RK 후보 개수나 현재 RK 식별자를 노출하지 않아, 개발자가 짤 수 있는 최선의 사전 검증이 "일단 트랜잭션 안에서 실행하고 실패하면 롤백"하는 수준에 그친다. 이는 온라인 스키마 변경 도구(gh-ost류)와의 통합을 어렵게 만든다.

**제안**: `db_class` 또는 별도 시스템 뷰에 "replication_key_candidate_count", "replication_key_constraint_name" 컬럼을 추가해 사전 조회가 가능하게 한다.

## 리뷰 7

**[심각도: 중요] 여러 UK가 있을 때 RK 자동 선택 기준("테이블 내 명시된 순서 중 가장 빠른 순서")이 마이그레이션 도구의 컬럼 재정렬에 취약하다**

**대상**: §1 "UK가 여러개 존재한다면 큐브리드 엔진에 의해 이 중 하나가 선택된다(ex. 테이블내에 명시된 순서 중 가장 빠른 순서)"

**문제 설명**: "ex."라는 표현 자체가 이것이 확정된 규칙이 아니라 예시일 뿐임을 암시해 모호하다. 설령 "선언 순서가 빠른 UK"가 확정 규칙이라 해도, 많은 마이그레이션 도구나 `ALTER TABLE ... ADD COLUMN`을 반복하며 스키마를 진화시키는 흔한 개발 관행에서는 제약조건의 "선언 순서"가 개발자의 의도와 무관하게 결정된다. 즉 어떤 UK가 RK로 선택되는지가 "테이블을 어떤 순서로 만들었는가"라는, 비즈니스 로직과 무관한 우연에 의해 결정된다.

**구체 예제**:
```sql
-- 초기 테이블: email이 먼저 선언된 UK
csql> CREATE TABLE members(
    id       INT,
    email    VARCHAR(100) NOT NULL UNIQUE,   -- UK1, 선언 순서 1번
    phone    VARCHAR(20)  NOT NULL UNIQUE    -- UK2, 선언 순서 2번
);
-- 스펙 규칙대로면 RK = email(UK1)

-- 6개월 후, 팀에서 "이제부터는 phone을 기준으로 조회 최적화를 하자"며
-- 무심코 테이블을 재생성하는 마이그레이션(예: 컬럼 순서를 바꿔 재생성)을 수행
csql> CREATE TABLE members_v2(
    id       INT,
    phone    VARCHAR(20)  NOT NULL UNIQUE,   -- 이제 선언 순서 1번
    email    VARCHAR(100) NOT NULL UNIQUE    -- 이제 선언 순서 2번
);
-- RK가 email -> phone으로 바뀜. 애플리케이션 코드는 이 변화를 전혀 알 수 없다.
```

**예제 설명**: 테이블을 재생성하거나(무중단 스키마 변경 도구들이 흔히 쓰는 "새 테이블 생성 후 데이터 복사·스왑" 패턴), 컬럼 순서를 바꾸는 마이그레이션을 수행하면, 비즈니스 로직상 아무 변화가 없음에도 RK가 바뀔 수 있다. 이는 "복제 정합성"이라는 매우 민감한 속성이 스키마 선언 순서라는 부수적 요인에 좌우된다는 뜻이며, 응용 개발자가 이를 예측하거나 제어할 방법이 없다.

**제안**: RK 선택 기준을 "ex."가 아니라 확정된 알고리즘으로 명문화하고, 가능하면 사용자가 `PRIMARY KEY`처럼 "이 UK를 RK로 우선한다"고 명시할 수 있는 힌트 구문을 제공한다(PostgreSQL의 `REPLICA IDENTITY USING INDEX idx_name`과 유사한 접근).

## 리뷰 8

**[심각도: 중요] 컬럼 타입 변경(ALTER ... 타입 변경)이 RK 컬럼에 적용될 때의 동작이 스펙에 없다**

**대상**: §4-2 전체 (예시 11~16), 없음(정의 누락)

**문제 설명**: 실무에서 매우 흔한 스키마 변경은 "INT로 만든 PK/UK 컬럼이 자릿수가 부족해져 BIGINT로 확장한다"거나 "VARCHAR(20)이던 코드 컬럼을 VARCHAR(50)으로 늘린다"는 식의 **타입 변경**이다. §4-2는 PK/UK의 추가·삭제(예시 11~16)만 다룰 뿐, RK로 사용 중인 컬럼의 **타입을 변경**하는 `ALTER TABLE ... MODIFY`류 DDL이 허용되는지, 허용된다면 진행 중인 복제에 어떤 영향을 주는지 전혀 언급하지 않는다.

**구체 예제**:
```sql
-- HA 운영 중, orders.order_id(INT PRIMARY KEY, RK로 사용 중)의 값 범위가 한계에 도달
csql> ALTER TABLE orders MODIFY order_id BIGINT;
-- 이 문장이 §4-2의 "복제키를 수정하는 DDL이 제한된다"는 규칙에 해당하는지 불명.
-- - 제약조건 자체(PRIMARY KEY)는 그대로 유지되고 컬럼의 데이터 타입만 바뀌는데,
--   이것도 "복제키 수정"으로 간주해 막아야 하는가?
-- - 만약 허용된다면, 이미 슬레이브로 넘어간 복제 로그의 RK 값(INT로 인코딩된)과
--   앞으로 생성될 로그(BIGINT로 인코딩된)의 정합성은 누가 보장하는가?
```

**예제 설명**: RK 컬럼의 제약조건(PK/UK 여부)은 그대로 두고 타입만 넓히는 것은 이름 그대로는 "복제키를 삭제·변경"하는 것이 아니므로 스펙의 문구만 보면 허용되어야 할 것 같다. 그러나 복제는 바이트 수준 인코딩에 의존하는 저수준 메커니즘이므로, 컬럼 타입이 바뀌면 RK 값의 직렬화 형식도 바뀔 수 있다. 이 경계 케이스가 스펙에 전혀 언급되지 않아 응용 개발자는 "이 흔한 작업을 운영 중에 해도 되는지" 스펙만으로는 판단할 수 없다.

**제안**: §4-2에 "RK 컬럼의 제약조건 변경"과 "RK 컬럼의 데이터 타입 변경"을 별도 항목으로 나눠 각각의 허용 여부와 위험을 명시한다.

## 리뷰 9

**[심각도: 중요] 인덱스 재구성(DROP INDEX 후 CREATE INDEX)이 RK 후보가 순간적으로 0개가 되는 트랜잭션 경계 문제를 일으킬 수 있다**

**대상**: §4-2 예시 16 "DROP INDEX idx_id ON tbl; → 복제키 후보가 없다면 삭제 불가"

**문제 설명**: 인덱스 단편화(fragmentation) 해소나 저장 옵션 변경을 위해 UNIQUE 인덱스를 "삭제 후 재생성"하는 것은 DBA/개발자가 흔히 수행하는 유지보수 작업이다. CUBRID의 DDL은 일반적으로 문장 단위로 자동 커밋(autocommit)되는 것으로 알려져 있는데, 이 경우 "DROP INDEX"와 "CREATE INDEX"가 각각 별도의 DDL 트랜잭션이라면, 그 사이의 짧은 순간 테이블은 RK 후보가 0개인 상태가 된다. 예시 16은 "RK 후보가 없으면 DROP이 거부된다"고만 말할 뿐, 이 케이스처럼 **삭제 직후 곧바로 재생성할 계획이 있는 경우**에도 여전히 거부되는지, 아니면 별도의 원자적 "REBUILD INDEX" 구문이 있는지 언급이 없다.

**구체 예제**:
```sql
-- orders 테이블의 유일한 RK 후보가 UK 인덱스 uk_orders_no 하나뿐인 상황에서
-- 인덱스 재구성을 시도
csql> DROP INDEX uk_orders_no ON orders;

ERROR   -- 예시16: RK 후보가 없어지므로 거부됨

-- 만약 이 테이블에 다른 RK 후보(PK 등)가 있어서 DROP은 성공했다고 가정하면,
csql> DROP INDEX uk_orders_no ON orders;  -- OK (다른 후보 존재 가정)
-- 이 인덱스가 사실은 유일한 UK였는데 §4-2 "다른 복제키 후보가 함께 존재한다면
-- 모든 DDL은 허용된다"는 조항 때문에 통과했다면,
-- 이 순간부터 재생성 전까지 RK는 남은 후보로 이미 전환되어 있다 (리뷰3 참고).
csql> CREATE INDEX uk_orders_no ON orders(order_no);  -- UNIQUE, NOT NULL 재생성
-- 재생성 후 RK가 다시 원래대로 돌아오는지, 아니면 전환된 채로 유지되는지 불명.
```

**예제 설명**: 인덱스 재구성이라는 일상적인 유지보수 작업조차, RK 후보가 하나뿐인 테이블에서는 아예 시도할 수 없고(첫 번째 케이스), 후보가 여럿인 테이블에서는 "재구성 도중 RK가 몰래 바뀌었다가 되돌아오는지 아닌지" 불명확한 상태(두 번째 케이스)에 빠진다. 두 경우 모두 응용 개발자가 "인덱스 재구성 작업 절차서"를 작성할 때 확신을 가지고 쓸 수 없는 부분이다.

**제안**: 원자적으로 인덱스를 교체할 수 있는 `CREATE OR REPLACE INDEX` 류의 구문을 제공하거나, 최소한 "RK 후보가 하나뿐인 UK/PK 인덱스는 재구성 목적이라도 DROP이 불가하니 반드시 새 UK를 먼저 추가한 뒤 이전 것을 제거하라"는 절차를 문서화한다.

## 리뷰 10

**[심각도: 중요] VIEW는 REPLICATION=OFF 테이블 참조에 대해 생성 시점 검증이 전혀 없다 — FK와의 내부 모순**

**대상**: §6(뷰), §5(외래키)와의 비교

**문제 설명**: §5는 FK가 REPLICATION=OFF 테이블을 참조하려 하면 **생성 시점에 에러를 발생**시켜 강하게 막는다(예시 18, 23). 반면 §6은 VIEW가 REPLICATION=OFF 테이블을 포함해도 "Failover 후 뷰 사용에는 제약이 없다"고 하면서 "결과가 두 노드 간 불일치할 수 있으나 책임지지 않는다"는 식으로 **사후 책임 회피**만 할 뿐, 생성 시점 검증은 전혀 하지 않는다. 둘 다 "REPLICATION=OFF 테이블을 참조하는 다른 객체"라는 동일한 근본 문제인데, 하나는 하드 블록(hard block), 다른 하나는 무통보라는 서로 다른 엄격도로 처리되는 것은 설계 일관성이 없다.

**구체 예제**:
```sql
csql> CREATE TABLE non_repl_customers(
    customer_id INT PRIMARY KEY,
    country INT
) REPLICATION=OFF;

-- FK로 참조하면 예시18처럼 즉시 ERROR
csql> CREATE TABLE orders(
    order_id INT PRIMARY KEY,
    customer_id INT,
    CONSTRAINT fk_x FOREIGN KEY (customer_id) REFERENCES non_repl_customers(customer_id)
);
-- ERROR (예시18)

-- 그런데 VIEW로 조인하면 아무 경고 없이 생성된다
csql> CREATE VIEW order_summary AS
    SELECT o.order_id, c.country
    FROM orders o JOIN non_repl_customers c ON o.customer_id = c.customer_id;
-- OK, 아무 경고도 출력되지 않음(§6에는 그런 언급이 없음)
-- Failover 후 슬레이브에서 order_summary를 SELECT하면
-- non_repl_customers에 데이터가 없어 country가 항상 NULL(조인 결과 누락)로 나오는데,
-- 이 사실을 애플리케이션은 뷰 생성 시점에도, 조회 시점에도 통보받지 못한다.
```

**예제 설명**: 애플리케이션 개발자는 흔히 리포팅용 화면이나 API 응답 조립에 VIEW를 적극 사용한다. FK는 막혀서 우회로를 찾다가 "그럼 VIEW로 조인하면 되겠네"라고 생각한 개발자는, 스펙이 정확히 막으려던 문제(참조 데이터가 slave에 없음)를 VIEW라는 뒷문으로 그대로 재현하게 된다. 게다가 이 경우는 에러조차 나지 않으므로 문제를 인지하기까지 더 오래 걸린다.

**제안**: `CREATE VIEW` 시점에 뷰 정의에 사용된 테이블 중 REPLICATION=OFF가 있으면 최소한 경고(WARNING)를 출력하고, 가능하면 뷰에도 "일부 참조 테이블이 복제 제외 상태"라는 메타데이터를 남겨 `show create view` 등으로 조회 가능하게 한다.

## 리뷰 11

**[심각도: 중요] 카탈로그로 "현재 실제 선택된 RK가 어떤 컬럼/제약인지" 조회할 방법이 없어 장애 디버깅 시 관측성이 부족하다**

**대상**: 예시 8·9(REPLICATION 조회)

**문제 설명**: 예시 8(`show create table`)과 예시 9(`select * from db_class`)는 모두 "이 테이블이 REPLICATION ON인가 OFF인가"만 보여줄 뿐, PK/UK가 여러 개 존재할 수 있는 상황에서 **그 중 무엇이 실제 RK로 선택되었는지**는 알려주지 않는다. §1의 RK 결정 규칙이 자동이고, 리뷰 3처럼 시간에 따라 자동으로 바뀔 수도 있는 값이라면, 이를 명시적으로 조회할 수 있는 카탈로그 뷰가 반드시 필요하다.

**구체 예제**:
```sql
-- 장애 상황: 마스터/슬레이브 데이터 불일치가 보고되어 원인 조사 중
-- "혹시 RK가 우리가 생각하는 그 컬럼이 아닌 다른 컬럼으로 바뀐 것 아닌가?"를 확인하고 싶다.
csql> show create table orders;
-- 결과: 'CREATE TABLE [orders] (...) REPLICATION ON' 만 보여줄 뿐
--       PK와 UK가 모두 있는 테이블이라면 "그 중 무엇이 RK인지"는 안 나온다.

csql> select * from db_class where class_name = 'orders';
-- replication: ON 만 나오고, RK로 선택된 제약 이름 컬럼이 없다(예시9 컬럼 목록 참고).
```

**예제 설명**: 정합성 장애의 원인을 조사하는 첫 단계는 보통 "어떤 컬럼을 기준으로 복제가 일어나고 있는가"를 확인하는 것이다. 이 스펙이 제공하는 조회 수단으로는 그 질문에 답할 수 없어, 결국 소스 코드나 내부 디버그 로그를 뒤져야 한다. 이는 응용 개발자뿐 아니라 1차 대응하는 운영 인력에게도 큰 장벽이다.

**제안**: `db_class` 또는 새 시스템 뷰에 `replication_key_name`(현재 RK로 선택된 제약 이름), `replication_key_type`(PK/UK) 컬럼을 추가한다.

## 리뷰 12

**[심각도: 중요] 예시 7 "Multiple ALTER" 구문의 원자성(atomicity)이 불명확하다**

**대상**: §2-2 예시 7 "csql> ALTER TABLE tbl DROP CONSTRAINT ..., ADD CONSTRAINT ...;"

**문제 설명**: 예시 7은 하나의 `ALTER TABLE` 문 안에 DROP CONSTRAINT와 ADD CONSTRAINT를 콤마로 나열한다. 이것이 원자적(atomic, 중간 상태 없이 전부 적용되거나 전부 취소되는 성질)으로 처리되는지, 아니면 DROP이 먼저 실행되고 그 사이에 RK 후보가 0개가 되는 순간이 실제로 존재하는지가 스펙에 없다. 예시 13("DROP CONSTRAINT PRIMARY KEY, ADD CONSTRAINT PRIMARY KEY(a)")도 동일한 구조인데 "OK"라고만 되어 있을 뿐 내부 처리 순서는 설명하지 않는다. 이는 예시 10·16이 "RK 후보가 0개가 되는 것을 막는다"는 규칙과 상충할 수 있는 지점이다: 만약 원자적이지 않다면, DROP 시점에 이미 예시 10과 같은 이유로 에러가 나야 하는데 예시 13은 OK로 표기되어 있어 앞뒤가 안 맞는다. 즉 원자적 처리를 전제해야만 예시 13이 성립하는데, 그 전제가 스펙에 명시돼 있지 않다.

**구체 예제**:
```sql
-- 예시13 재현
csql> ALTER TABLE table_name DROP CONSTRAINT PRIMARY KEY,
      ADD CONSTRAINT PRIMARY KEY(a);
-- OK (스펙 표기)

-- 만약 이것이 "DROP 먼저 즉시 반영, 그 다음 ADD 반영"이라는 순차 처리라면
-- DROP 직후 RK 후보가 0개가 되어 예시10의 규칙("복제 테이블에는 RK 후보가 1개 이상 필요")에
-- 걸려 ERROR가 나야 정합적이다. 그런데 스펙은 OK라고 한다.
-- → 두 규칙이 동시에 참이려면 "한 문장 내 여러 절은 검증 시점에 원자적으로 처리된다"는
--   전제가 필요한데, 이 전제가 문서 어디에도 명시돼 있지 않다.
```

**예제 설명**: 응용 개발자가 마이그레이션 스크립트를 짤 때 "여러 ALTER 절을 한 문장에 몰아써야 하는지, 아니면 나눠 써도 되는지"는 실무적으로 중요한 정보다. 이 스펙만 보고는 "왜 예시 13은 되고 개별 문장으로 나누면 안 되는지"에 대한 근거(원자성 보장)가 설명되지 않아, 개발자가 임의로 절을 분리해 스크립트를 작성했다가 실패를 겪을 수 있다.

**제안**: "RK 후보 유무 검증은 하나의 ALTER TABLE 문 내 모든 절이 적용된 이후의 최종 상태를 기준으로 판단한다"는 원자성 규칙을 §4-2에 명시적으로 추가한다.

## 리뷰 13

**[심각도: 중요] FK 제약으로 인해 "정적 참조/코드 테이블을 REPLICATION=OFF로 둔다"는 흔한 설계 패턴이 봉쇄된다**

**대상**: §5(외래키)

**문제 설명**: 실무에서는 국가 코드, 통화 코드, 상태 코드 등 거의 변하지 않는 참조 테이블을 별도 배포 파이프라인(예: 애플리케이션 초기화 스크립트, 설정 관리 도구)으로 각 노드에 동일하게 심어두고, "굳이 복제할 필요 없다"는 이유로 REPLICATION=OFF로 관리하고 싶어 하는 경우가 있다. 그러나 §5는 REPLICATION=ON 테이블이 이런 참조 테이블을 FK로 참조하는 것을 원천 금지한다. 이는 데이터 무결성(참조 무결성) 관점에서는 안전하지만, "이 테이블은 애플리케이션 로직으로 이미 각 노드에 동일하게 유지되므로 굳이 CUBRID 복제를 통하지 않아도 된다"는 정당한 설계 판단의 여지를 스펙이 아예 차단해버린다는 점에서 애플리케이션 모델링의 자유도를 낮춘다.

**구체 예제**:
```sql
-- 각 노드 배포 시 애플리케이션 초기화 스크립트로 동일하게 심어지는 코드 테이블
csql> CREATE TABLE country_codes(
    code VARCHAR(2) PRIMARY KEY,
    name VARCHAR(50)
) REPLICATION=OFF;   -- 어차피 양쪽 노드에 동일한 정적 데이터

csql> CREATE TABLE customers(
    customer_id INT PRIMARY KEY,
    country_code VARCHAR(2),
    CONSTRAINT fk_country FOREIGN KEY (country_code) REFERENCES country_codes(code)
);
-- 예시18/23과 동일한 이유로 ERROR
-- 결국 country_codes도 REPLICATION=ON으로 바꿔 불필요한 복제 트래픽을 감수하거나,
-- FK 제약 자체를 포기하고 애플리케이션 레벨 검증으로 대체해야 한다.
```

**예제 설명**: FK 제약을 유지하려면 정적 테이블도 강제로 ON이 되어야 하고, ON을 포기하면 데이터베이스 레벨의 참조 무결성 보장을 잃는다(잘못된 country_code가 INSERT되어도 DB가 막아주지 못함). 이 스펙은 이 트레이드오프를 사용자가 선택할 수 있는 옵션으로 제공하지 않고 "무조건 ON"으로 강제한다.

**제안**: FK 참조 대상이 REPLICATION=OFF이더라도, 두 노드에 동일 데이터가 별도 경로로 보장된다는 것을 사용자가 명시적으로 선언할 수 있는 예외 옵션(예: `FOREIGN KEY ... REFERENCES ... /* UNVALIDATED_REPLICATION */`)을 검토한다. 최소한 왜 이 제약이 필요한지, 우회 방법은 없는지를 문서에 설명해 설계자가 대안을 판단할 수 있게 한다.

## 리뷰 14

**[심각도: 보통] 예시 2, 4, 20, 23의 SQL에 트레일링 콤마(trailing comma) 문법 오류가 있어 그대로 실행하면 실패한다**

**대상**: §2-1 예시 2, 예시 4 / §5-2 예시 20, 예시 23

**문제 설명**: 예시 2 `CREATE TABLE repl_table_without_rk( a INT, );` 와 예시 4 `CREATE TABLE non_repl_table_without_rk( a INT )REPLICATION = OFF;`(이건 콤마 없음, 예시2가 문제), 예시 20 `CREATE TABLE new_orders( order_id INT PRIMARY KEY );`(콤마 없음, 정상), 예시 23 `CREATE TABLE new_orders( order_id INT PRIMARY KEY, );`(마지막 컬럼 뒤 콤마) 등에서 컬럼 목록 마지막에 불필요한 콤마가 남아 있는 경우가 있다. SQL 표준 및 CUBRID를 포함한 대부분의 RDBMS에서 컬럼 목록의 마지막 항목 뒤에 콤마가 있으면 문법 오류(syntax error)로 처리된다.

**구체 예제**:
```sql
-- 예시2 원문 그대로
csql> CREATE TABLE repl_table_without_rk(
    a INT,
);
-- 예상 결과: ERROR (문법 오류, 마지막 콤마)
-- 하지만 스펙의 의도는 "PK도 UK도 없는 테이블을 만드는 예시"이므로 결과가 ERROR가 아니어야
-- 문서 취지와 맞다. 즉 이 예시 코드 자체가 스펙이 설명하려는 바를 검증하지 못한다.

-- 올바른 형태
csql> CREATE TABLE repl_table_without_rk(
    a INT
);
```

**예제 설명**: 응용 개발자는 스펙 문서의 SQL 예제를 그대로 복사해 테스트 스크립트를 만드는 경우가 많다. 예제 코드 자체에 문법 오류가 있으면, "이 에러가 스펙이 말하려는 RK 제약 위반 때문인지, 단순 오타 때문인지" 헷갈리게 되어 학습 곡선을 불필요하게 높인다.

**제안**: 모든 SQL 예제를 실제 CUBRID 인스턴스에서 한 번씩 실행해 문법 오류 여부를 검증한 뒤 문서에 반영한다.

## 리뷰 15

**[심각도: 보통] 에러 메시지 제공 수준이 예시마다 달라 자동화 스크립트에서 에러 원인을 판별하기 어렵다**

**대상**: §4-2 예시 11("ERROR: Primary key "pk_tbl_a" already defined for class "dba.tbl".") vs 예시 12, 15, 16, 21 이전 다수("ERROR"만 표기)

**문제 설명**: 예시 11은 구체적인 에러 메시지 문자열을 보여주는 반면, 예시 12·15·16·10 등 다수의 예시는 그냥 "ERROR"라고만 표기한다. 마이그레이션 도구나 배포 자동화 스크립트는 보통 에러 메시지의 SQLSTATE 코드나 텍스트 패턴을 파싱해 "이 실패는 재시도 가능한가, 아니면 즉시 배포를 중단해야 하는가"를 판단한다. 스펙에 구체적 에러 메시지/코드가 없으면 이런 자동화 로직을 미리 설계할 수 없다.

**구체 예제**:
```sql
-- 예시12 (RK로 쓰이는 PK 컬럼 삭제 시도)
csql> ALTER TABLE table_name DROP COLUMN b;
ERROR   -- 메시지 텍스트/코드 없음

-- 배포 스크립트에서 이 실패를 처리하려는 의사코드
if (result.errorCode == "REPL_KEY_IN_USE") {
    // 사용자에게 "이 컬럼은 복제 키로 사용 중이라 삭제할 수 없습니다" 안내
} else {
    // 다른 종류의 실패, 원인 재확인 필요
}
// 그러나 스펙에 명시된 에러 코드가 없어 이 분기 자체를 만들 수 없다.
```

**예제 설명**: 사람이 눈으로 보는 문서라면 "ERROR"만으로도 충분할 수 있지만, CI/CD 파이프라인이나 관리 콘솔이 이 에러를 사용자 친화적 메시지로 변환해 보여주려면 구분 가능한 에러 코드가 필요하다. 지금 상태로는 "RK를 건드려서 실패한 것"과 "단순 문법 오류로 실패한 것"을 프로그램적으로 구분할 수 없다.

**제안**: 모든 RK/FK 관련 제약 위반에 고유한 에러 코드(예: `-71xx` 대역)를 부여하고, 스펙 문서의 모든 "ERROR" 표기를 해당 코드와 메시지 예시로 통일한다.

## 리뷰 16

**[심각도: 보통] §4 "복제 대상의 경우 다음 DDL에 대한 제약 사항이 존재한다"에서 "다음 DDL"의 전체 목록이 나열되어 있지 않다**

**대상**: §4(HA 제약사항)

**문제 설명**: §4는 "복제 대상의 경우 다음 DDL에 대한 제약 사항이 존재한다"고 말한 뒤 §4-1(CREATE TABLE), §4-2(ALTER TABLE) 두 하위 절만 이어진다. 그런데 RENAME TABLE, TRUNCATE TABLE, CREATE INDEX(신규 UNIQUE 인덱스 추가가 아닌 일반 인덱스), 파티셔닝 관련 DDL(ADD/DROP PARTITION) 등 CUBRID가 지원하는 다른 DDL 종류들이 이 "제약 사항"의 대상에 포함되는지 여부가 전혀 언급되지 않는다. "다음 DDL"이라는 표현이 실제로는 CREATE TABLE과 ALTER TABLE(그것도 제약조건 관련 절만) 두 가지로 국한된 것인지, 아니면 나열이 불완전한 것인지 알 수 없다.

**구체 예제**:
```sql
-- RK로 쓰이는 UK가 걸린 컬럼을 포함해 테이블 이름을 바꾸는 경우
csql> RENAME TABLE orders TO orders_archive;
-- §4에 이 DDL에 대한 언급이 전혀 없다. RK 관련 제약이 적용되는지 불명.

-- 파티션 테이블에서 파티션을 드롭하는 경우, RK 컬럼이 파티션 키인 경우
csql> ALTER TABLE orders DROP PARTITION p2023;
-- 이것이 "복제키 후보 감소"에 해당하는지 여부도 언급 없음.
```

**예제 설명**: 응용 개발자가 스펙에 나열되지 않은 DDL을 실행할 때 "이건 제약 대상이 아니니 안전하겠지"라고 판단하는 것은 위험한 추측이다. 스펙이 명시적으로 다루는 DDL 종류를 한정 짓지 않으면, 문서에 없는 DDL을 실행했다가 예상 못한 제약(혹은 반대로 예상했던 제약의 부재)에 부딪힐 수 있다.

**제안**: §4 서두에 "이 절이 다루는 DDL 목록"을 명시적으로 나열하고(CREATE TABLE, ALTER TABLE의 ADD/DROP CONSTRAINT·COLUMN, CREATE/DROP INDEX 등), 목록에 없는 DDL(RENAME, TRUNCATE, 파티션 관련 등)에 대해서는 "제약 없음" 또는 "해당 없음"을 명시적으로 밝힌다.

## 리뷰 17

**[심각도: 보통] 예시 19~22의 FK 제약조건 이름이 서로 대응하지 않아 예제를 그대로 재현할 수 없다**

**대상**: §5-2 예시 19("ADD CONSTRAINT FOREIGN KEY(customer_id) REFERENCES customers(customer_id)", 이름 미지정) vs 예시 21("DROP FOREIGN KEY (fk_new_orders_customer_id)")

**문제 설명**: 예시 19는 `ADD CONSTRAINT FOREIGN KEY(customer_id) REFERENCES customers(customer_id)`로 FK를 추가하면서 제약 이름을 명시하지 않는다(다른 예시들처럼 `CONSTRAINT fk_xxx FOREIGN KEY`형태가 아니다). 그런데 바로 이어지는 예시 21은 "복제 테이블을 참조하는 외래키 제거"로 `DROP FOREIGN KEY (fk_new_orders_customer_id)`를 실행한다. 예시 19에서 이름을 지정한 적이 없는데 예시 21에서 갑자기 `fk_new_orders_customer_id`라는 구체적인 이름이 등장한다. 이는 "예시 19의 결과로 자동 생성된 이름이 fk_new_orders_customer_id다"라는 것을 암묵적으로 가정한 것으로 보이는데, 그 자동 명명 규칙이 스펙 어디에도 설명되어 있지 않다.

**구체 예제**:
```sql
-- 예시19: 이름 없이 FK 추가
csql> ALTER TABLE new_orders ADD CONSTRAINT FOREIGN KEY(customer_id)
      REFERENCES customers(customer_id);
-- OK, 그런데 이 제약의 실제 이름은 무엇인가? 문서에 없음.

-- 예시21: 특정 이름으로 DROP 시도
csql> ALTER TABLE new_orders DROP FOREIGN KEY (fk_new_orders_customer_id);
-- 이 이름이 예시19에서 자동 생성된 이름과 동일하다는 보장이 문서 어디에도 없어,
-- 독자가 그대로 따라 하면 "그런 제약이 없다"는 에러를 만날 수 있다.
```

**예제 설명**: 응용 개발자가 스펙 문서를 실습 삼아 따라 하다가, 자동 생성된 제약 이름 규칙을 모른 채 예시 21을 그대로 실행하면 실패할 가능성이 크다. 이는 문서의 신뢰도를 떨어뜨리고, "이 스펙 문서가 실제로 검증된 것인지" 의심하게 만든다.

**제안**: 예시 19에서도 명시적으로 `CONSTRAINT fk_new_orders_customer_id FOREIGN KEY(...)`처럼 이름을 지정해 이어지는 예시들과 일관되게 만들거나, 자동 명명 규칙(예: `fk_<테이블명>_<컬럼명>`)을 별도로 문서화한다.

## 리뷰 18

**[심각도: 보통] LOADDB/UNLOADDB 기반 환경 복제(clone) 워크플로우에서 애플리케이션 도구가 REPLICATION 상태를 다루는 방법이 문서화되어 있지 않다**

**대상**: §8(UNLOADDB & LOADDB)

**문제 설명**: 많은 팀이 운영 DB를 `unloaddb`로 덤프받아 스테이징/개발 환경에 `loaddb`로 복원해 "운영과 유사한 데이터"로 테스트한다. §8은 "unload 시 복제 테이블 여부를 함께 저장"하고 "load 시 그 변수에 따라 복제/제외 테이블로 생성된다"고 설명하지만, 이 과정이 **응용 개발자가 흔히 쓰는 도구(스크립트, CI 파이프라인의 DB 클론 단계)**에 어떻게 노출되는지는 다루지 않는다. 예를 들어 unload 파일 포맷에 이 변수가 어떤 필드로 들어가는지, 애플리케이션이 이 값을 조작(강제로 모두 ON으로 바꾸는 등)할 수 있는 옵션이 있는지가 불명확하다.

**구체 예제**:
```bash
# 운영 DB를 스테이징으로 복제하는 통상적인 야간 배치 스크립트
unloaddb -o /backup/prod_$(date +%F).unl prod_db
loaddb -d staging_db /backup/prod_$(date +%F).unl
# staging_db는 싱글 모드로 운영되므로 REPLICATION 속성 자체가 의미 없을 수도 있는데,
# §8 규칙에 따라 그대로 복제 테이블 여부가 이관된다면,
# staging에서 다시 HA로 전환해 복제 관련 버그를 재현하려 할 때
# "운영과 동일한 REPLICATION 설정을 유지한 채로 clone 되었는가"를
# 검증할 방법이 스크립트 레벨에 없다.
```

**예제 설명**: DB 클론은 QA/장애 재현 목적으로 매우 자주 쓰이는 작업이다. §8의 규칙이 unload 파일 내부의 저수준 포맷 결정에만 머물러 있고, 그 위에서 동작하는 스크립트/도구가 이 정보를 조회·검증할 수 있는 상위 레벨 인터페이스(예: `loaddb` 실행 결과 요약에 "복제 대상 N개, 복제 제외 M개, 미표기(구버전) K개"를 출력)를 제공하지 않는다.

**제안**: `loaddb` 실행 로그에 REPLICATION 속성별 테이블 개수 요약을 출력하도록 하여, 클론 작업 담당자가 별도 SQL 조회 없이도 결과를 검증할 수 있게 한다.

## 리뷰 19

**[심각도: 사소] REPLICATION 키워드가 기존 예약어·컬럼명과 충돌할 가능성이 검토되어 있지 않다**

**대상**: §2(변경되거나 추가된 SQL) 전체

**문제 설명**: `REPLICATION`을 새 예약어(또는 준예약어)로 도입하면, 기존에 컬럼명이나 테이블명으로 `replication`이라는 단어를 사용해온 애플리케이션의 스키마와 충돌할 가능성이 있다. 특히 예시 9에서 이미 `db_class`의 컬럼명으로 `replication`을 쓰고 있는데, 사용자 테이블에서 우연히 `replication`이라는 컬럼명을 쓰고 있었다면 이번 버전 업그레이드 이후 DDL/DML 파싱에 영향을 받을 수 있는지 스펙에 언급이 없다.

**구체 예제**:
```sql
-- 업그레이드 이전부터 존재하던 레거시 테이블
csql> CREATE TABLE sync_status(
    id INT PRIMARY KEY,
    replication VARCHAR(10)  -- 우연히 이 이름을 컬럼명으로 사용 중이었다면?
);
-- 신버전에서 REPLICATION이 예약어로 승격되었다면 이 DDL/이후 DML이 영향을 받을 수 있는지 불명
```

**예제 설명**: 신규 키워드 도입은 항상 기존 스키마와의 이름 충돌 가능성을 수반한다. 이 스펙에는 하위 호환성 관점에서 이 위험을 검토했다는 언급이 없다.

**제안**: `REPLICATION`을 비예약어(non-reserved keyword)로 처리해 컬럼명/테이블명으로도 계속 사용 가능하도록 설계하거나, 예약어로 승격해야 한다면 업그레이드 가이드에 기존 스키마의 이름 충돌 여부를 점검하는 체크리스트를 포함한다.

## 리뷰 20

**[심각도: 사소] "복제키 후보"와 "복제키"라는 두 용어가 명확히 구분되지 않고 혼용되어 있다**

**대상**: 스펙 전반(§1, §4-2, §7, §9)

**문제 설명**: 스펙은 "복제키(RK)"와 "복제키 후보"라는 두 표현을 사용하는데, 어디에도 두 용어의 정의 차이가 명시적으로 설명되어 있지 않다. 문맥상 "복제키 후보"는 "RK로 선택될 수 있는 PK/UK 제약 전체(현재 선택 여부와 무관)"를, "복제키"는 "그 중 실제로 선택되어 사용 중인 것 하나"를 가리키는 것으로 추측되지만, §4-2의 "복제키 후보가 1개인 경우(= 복제키) 제약사항은 다음과 같다"라는 문장에서 괄호로 "= 복제키"라고 등치시켜버려 오히려 두 용어가 사실상 같은 것처럼 읽히기도 한다. 컴퓨터공학 입문 수준의 독자, 혹은 이제 막 이 기능을 접하는 3년차 응용 개발자에게는 이 용어 구분이 시작부터 혼란을 준다.

**구체 예제**:
```text
스펙 문장: "복제키 후보가 1개인 경우(= 복제키) 제약사항은 다음과 같다."
→ 이 문장만 보면 "복제키 후보 1개 = 복제키"라는 등식으로 읽혀,
  "복제키 후보가 여러 개일 때는 그중 하나만 복제키이고 나머지는 후보일 뿐이다"라는
  더 뒤에 나오는 서술(§4-2 "다른 복제키 후보가 함께 존재한다면 모든 DDL은 허용된다")과
  용어 사용이 매끄럽게 이어지지 않는다.
```

**예제 설명**: 용어 정의가 스펙 서두(§1)에 표로 딱 한 번 정리되어 있지 않아, 읽는 사람이 각 절을 오가며 문맥으로 뜻을 유추해야 한다. 컴퓨터공학과 입문서 수준의 서술을 지향한다면 이런 핵심 용어는 첫 등장 시 명시적 정의가 필요하다.

**제안**: §1 도입부에 "복제키 후보(RK Candidate): PK 또는 NOT NULL UNIQUE 제약으로, RK로 선택될 자격이 있는 것 / 복제키(RK): 복제키 후보 중 엔진이 실제로 선택해 사용 중인 것 하나"라는 용어 정의를 표로 명시하고, 이후 모든 절에서 이 두 용어를 일관되게 구분해 사용한다.
