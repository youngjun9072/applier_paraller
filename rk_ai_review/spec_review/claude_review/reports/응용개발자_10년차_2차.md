# CUBRID HA 복제 개선 스펙 리뷰 — 응용 개발자(10년차) 관점 · 2차 라운드

## 2차 라운드 개요

1차에서는 RK 비결정성, dev/prod parity, FK 사후 전환, 뷰의 조용한 불일치 등 "정면에 보이는" 문제를 다뤘다. 이번 2차에서는 스펙 예시(특히 §2-3 `db_class` 카탈로그 예시 9)에 등장하지만 본문은 침묵하는 필드들 — `tde_algorithm`, `collation`, `partitioned`, `owner_name` — 을 단서 삼아 REPLICATION/RK가 이들과 어떻게 상호작용하는지를 팠고, 응용 개발자가 실제로 배포 자동화에 쓰는 도구(ORM 자동 스키마 동기화, Liquibase 롤백 생성기, JDBC 타임아웃)가 이 스펙의 비대칭 규칙과 부딪히는 지점을 찾았다. 1차·최종보고서에서 이미 합의된 지점(RK 비결정성 자체, FK 사후 OFF 전환, RK 조회 불가, §7 포맷, §8/§9 모순, trailing comma 등)의 재탕은 제외했다.

가치 있는 지적만 남긴 결과 12건으로 마무리한다. 뒤에 "조사 종료 선언" 절에 그 판단 근거를 남긴다.

### 리뷰 21

**[심각도: 치명] Collation(문자열 비교 규칙) 차이가 RK 유일성 전제를 깨뜨릴 수 있다**

**대상**: §1 제약 사항 (RK = PK 또는 NOT NULL UNIQUE), §2-3 예시 8 (`COLLATE utf8_bin`)

**문제 설명**: RK 자격 조건은 "NOT NULL UNIQUE"다. 그런데 UNIQUE 제약이 실제로 "유일하다"고 판정하는 기준은 그 컬럼의 콜레이션(collation, 문자열을 정렬·비교할 때 대소문자·발음 구별 기호 등을 어떻게 취급할지 정하는 규칙 집합)에 따라 달라진다. 예시 8의 `show create table` 결과에 `COLLATE utf8_bin`이 명시된 것을 보면 CUBRID는 대소문자를 구분하는 콜레이션과 구분하지 않는 콜레이션을 모두 지원한다. 마스터 DB가 utf8_bin(대소문자 구분)으로 만들어졌다면 `'User@a.com'`과 `'user@a.com'`은 서로 다른 값이라 UK 위반이 아니다. 그런데 HA 클러스터에서 슬레이브를 별도로 초기화(initdb)할 때 담당자가 다른 콜레이션(대소문자 구분 안 함)을 기본값으로 잡았거나, 컬럼별 `COLLATE` 절을 빠뜨려 세션 기본값에 의존했다면, applylogdb가 RK 값으로 슬레이브에서 대상 행을 찾는 순간 "마스터에서는 서로 다른 두 값이었던 것이 슬레이브에서는 같은 값으로 충돌"하는 상황이 생길 수 있다. 이 스펙은 RK가 "값으로 행을 유일하게 식별할 수 있다"는 전제 위에 설계됐는데, 그 유일성 판정 규칙 자체가 마스터·슬레이브 간에 동일함을 검증하는 절차가 어디에도 없다.

**구체 예제**:
```sql
-- 마스터: DB 기본 콜레이션이 utf8_bin(대소문자 구분)
CREATE TABLE members(
    id     INT,
    email  VARCHAR(100) NOT NULL UNIQUE   -- COLLATE 명시 안 함, DB 기본값 적용
);

-- 마스터에서는 유일성 위반 없이 두 행이 공존 가능(대소문자만 다름)
INSERT INTO members(id, email) VALUES (1, 'User@a.com');
INSERT INTO members(id, email) VALUES (2, 'user@a.com');

-- 슬레이브: DR 사이트 구축 시 담당자가 initdb 파라미터를 다르게 줌
-- (예: 대소문자 구분 안 하는 콜레이션을 기본값으로 설정)
-- applylogdb가 위 두 INSERT를 슬레이브에 그대로 재생하면,
-- 슬레이브 콜레이션 하에서는 'User@a.com' = 'user@a.com'이므로
-- 두 번째 INSERT가 UK(=RK) 위반으로 처리될 위험이 있다
```

**예제 설명**: 이 시나리오는 마스터에서는 정상적으로 커밋된 데이터가 슬레이브에서는 재생 자체가 실패하거나(에러 발생), 혹은 침묵하며 한쪽 행이 유실되는 두 갈래로 흘러갈 수 있다. 둘 다 이 스펙이 원래 막으려던 "마스터/슬레이브 데이터 불일치"와 동일한 유형의 사고인데, 원인이 RK 자체의 결정 로직이 아니라 콜레이션이라는 별도 축이라서 §1~§9 어디를 봐도 이 케이스에 대한 언급이 없다.

**제안**: HA 시작 전 검증 항목(§7)에 "마스터와 슬레이브의 DB/컬럼 콜레이션이 RK 관련 컬럼에서 일치하는지" 확인을 추가하고, RK로 선택되는 UK 컬럼의 콜레이션 일치를 §1에 불변식으로 명문화해야 한다.

### 리뷰 22

**[심각도: 치명] Filtered(부분) UNIQUE INDEX가 "NOT NULL UNIQUE"라는 RK 후보 조건을 형식적으로만 충족시킬 수 있다**

**대상**: §1 제약 사항, §4-2

**문제 설명**: 많은 DBMS(그리고 CUBRID도 인덱스에 WHERE 조건을 붙이는 필터링 인덱스를 지원하는 경우)는 "테이블 전체가 아니라 조건을 만족하는 행 사이에서만" 유일성을 강제하는 부분(필터링) UNIQUE 인덱스를 만들 수 있다. 대표적으로 논리 삭제(soft delete) 패턴에서 "삭제되지 않은 행끼리만 이메일이 유일해야 한다"는 요구가 흔하다. 스펙은 "PK가 없이 UK가 존재한다면 UK가 복제 키가 됨"이라고만 규정할 뿐, 그 UK가 테이블 전체에 대해 무조건 유일성을 강제하는 완전한 제약인지, 특정 조건에서만 유일성을 강제하는 부분 인덱스인지 구분하지 않는다. 만약 엔진이 카탈로그를 조회해 "NOT NULL 컬럼 위의 UNIQUE 인덱스"라는 표면적 조건만으로 RK 후보를 판정한다면, 조건을 벗어난 행들 사이에서는 값이 중복될 수 있는 컬럼이 RK로 뽑혀 복제 로그가 슬레이브에서 어느 행을 갱신할지 특정하지 못하는 사고로 이어진다.

**구체 예제**:
```sql
-- 소프트 삭제 패턴: deleted_at이 NULL인(살아있는) 행에서만 email 유일성을 강제
CREATE TABLE members(
    id         INT,
    email      VARCHAR(100) NOT NULL,
    deleted_at DATETIME
);
CREATE UNIQUE INDEX uk_members_email_active ON members(email) WHERE deleted_at IS NULL;

-- 이 인덱스는 "NOT NULL 컬럼(email) 위의 UNIQUE 인덱스"라는 조건은 만족하지만
-- deleted_at이 채워진(삭제된) 행끼리는 email이 중복될 수 있다.
-- 실제로 탈퇴 후 같은 email로 재가입을 반복하면 삭제된 행이 여러 개 쌓인다.

-- 만약 엔진이 이 인덱스를 RK로 인정한다면:
UPDATE members SET id = 999 WHERE id = 5;   -- 삭제된 행 하나를 수정
-- 복제 로그가 email 값만으로 슬레이브에서 대상 행을 찾으면,
-- 같은 email을 가진 삭제된 행이 여러 개일 때 어느 것을 갱신해야 할지 특정할 수 없다
```

**예제 설명**: 소프트 삭제는 응용 개발에서 매우 흔한 패턴이고, "UNIQUE"라는 표면적 키워드만 보고 RK 후보를 판정하면 이런 부분 인덱스가 조용히 끼어들 여지가 있다. 스펙에 이 케이스가 명시적으로 다뤄지지 않으면, 구현팀이 임의로 "포함/제외" 중 하나를 정하게 되고 그 결정이 문서화되지 않아 사용자가 예측할 수 없다.

**제안**: RK 후보 판정 시 WHERE 조건(필터)이 붙은 부분 UNIQUE 인덱스는 후보에서 제외한다는 규칙을 §1에 명시하고, §4-2에 이 케이스를 다루는 예제를 추가해야 한다.

### 리뷰 23

**[심각도: 중요] TDE(투명한 데이터 암호화) 적용 테이블의 복제 키/복제 로그 암복호화 키 관리가 스펙에 없다**

**대상**: §2-3 예시 9 (`tde_algorithm : 'NONE'`)

**문제 설명**: 예시 9의 `db_class` 조회 결과에 `tde_algorithm`이라는 필드가 존재하는 것으로 보아, CUBRID는 TDE(Transparent Data Encryption — 디스크에 저장된 데이터를 암호화해 저장 매체 자체를 탈취당해도 내용을 보호하는 기능)를 지원한다. TDE가 걸린 테이블이 REPLICATION=ON으로 복제 대상이 될 때 이 스펙은 아무 언급이 없다. 구체적으로 (1) RK로 쓰이는 컬럼 자체가 암호화 대상 컬럼이면 복제 로그에는 평문 RK 값이 실리는지 암호화된 값이 실리는지, (2) 마스터와 슬레이브가 TDE 마스터 키(암호화 키를 다시 보호하는 최상위 키, 통상 별도 키 관리 서버·HSM에 보관)를 공유하는지 각자 관리하는지, (3) failover 후 애플리케이션이 슬레이브에서 TDE 컬럼을 조회할 때 키 배포가 안 되어 있으면 복호화 실패 에러가 나는지, 아니면 값 자체가 다르게 저장되어 있는지가 전혀 규정되지 않았다. 규제 산업(금융, 개인정보 보관 의무가 있는 서비스)은 TDE와 HA를 함께 쓰는 경우가 많으므로 이 공백은 실사용에 바로 부딪힌다.

**구체 예제**:
```sql
CREATE TABLE payment_cards(
    card_token    VARCHAR(64) NOT NULL UNIQUE,  -- RK 후보, TDE 암호화 대상 컬럼
    encrypted_pan VARBIT(2048)
) REPLICATION = ON;
-- (TDE 활성화 구문은 스펙 범위 밖이라 생략)

-- 운영 중 failover 발생. 슬레이브가 마스터와 다른 키 관리 서버(HSM)를 바라보는 구성이라면?
SELECT card_token FROM payment_cards WHERE card_token = 'tok_123';
-- 애플리케이션이 이 조회에서 복호화 실패 예외를 받는가?
-- 아니면 슬레이브에서는 애초에 다른 키로 재암호화되어 값 자체가 마스터와 다른가?
-- 스펙에 규정이 없어 배포 전 키 인프라를 어떻게 준비해야 하는지 판단할 근거가 없다
```

**예제 설명**: TDE와 REPLICATION은 이번 스펙이 침묵하는 CUBRID 고유 기능 간 상호작용의 대표 사례다. "책임지지 않는다"는 식으로도 좋으니 최소한 명시적 스코프 선언이 필요하다.

**제안**: TDE 적용 테이블과 REPLICATION 옵션의 상호작용(키 배포 요구사항, 복제 로그 내 값의 암복호화 여부)을 별도 절로 문서화하거나, 최소한 "이번 릴리스에서는 TDE 적용 테이블의 HA 복제는 검증 범위 밖"이라고 명시해야 한다.

### 리뷰 24

**[심각도: 중요] 파티션 테이블에서 파티션 키와 RK의 관계, ADD/DROP PARTITION의 복제 처리가 스펙에 없다**

**대상**: §2-3 예시 9 (`partitioned : 'NO'`)

**문제 설명**: `db_class` 예시에 `partitioned` 필드가 있는 것으로 보아 CUBRID는 파티셔닝(하나의 논리 테이블을 여러 물리 조각으로 나눠 저장하는 기능으로, 대용량 테이블을 날짜·범위별로 쪼개 관리 비용을 낮추는 데 흔히 쓴다)을 지원한다. 파티션 테이블에서는 통상 파티션 키(어느 조각에 데이터를 넣을지 정하는 기준 컬럼)가 PK/UK에 포함되어야 하는 제약을 두는 DBMS가 많은데, 이 스펙은 파티션 테이블에서 RK를 어떻게 정하는지(파티션 키가 RK 결정에 영향을 주는지), 파티션 단위로 REPLICATION 옵션을 다르게 줄 수 있는지(예: 과거 파티션은 OFF, 최근 파티션만 ON), 그리고 `ALTER TABLE ... DROP PARTITION`(파티션 하나를 통째로 제거하는 연산으로 수백만 건이 한 번에 사라질 수 있음)이 §4의 "복제 대상 DDL 제약"에 어떻게 걸리는지 전혀 다루지 않는다.

**구체 예제**:
```sql
CREATE TABLE orders(
    order_id    INT,
    order_date  DATE,
    customer_id INT,
    PRIMARY KEY(order_id, order_date)
) PARTITION BY RANGE(order_date) (
    PARTITION p2025 VALUES LESS THAN ('2026-01-01'),
    PARTITION p2026 VALUES LESS THAN ('2027-01-01')
);
-- RK는 복합 PK (order_id, order_date)로 정해짐(추정)

ALTER TABLE orders DROP PARTITION p2025;
-- 이 한 문장으로 p2025에 속한 수백만 행이 즉시 사라진다.
-- 이것이 §4의 "DDL"로 취급되어 슬레이브에 동일한 DROP PARTITION 문으로 전파되는지,
-- 아니면 내부적으로 행 단위 DELETE 복제 로그로 변환되는지, 스펙에 규정이 없다
```

**예제 설명**: 파티션은 대용량 운영 테이블에서 실무적으로 매우 흔하게 쓰이는데, 이번 스펙이 침묵하는 대표적인 CUBRID 고유 기능이다. DROP PARTITION처럼 대량 데이터 변화를 일으키는 연산의 복제 방식이 정의되지 않으면, 파티션을 쓰는 테이블에 RK/REPLICATION 규칙을 어떻게 적용해야 할지 사용자가 추측해야 한다.

**제안**: 파티션 테이블의 RK 결정 규칙, 파티션 단위 REPLICATION 세분화 지원 여부, ADD/DROP/REORGANIZE PARTITION의 복제 로그 처리 방식을 §4에 하위 절로 추가하거나 최소한 "지원 범위 밖"임을 명시해야 한다.

### 리뷰 25

**[심각도: 중요] RENAME TABLE / 섀도 테이블 스왑 패턴에서 RK·REPLICATION 속성 승계 규칙 부재**

**대상**: §2-2, §4-1 (스펙 전체에 RENAME TABLE 관련 서술 없음)

**문제 설명**: 무중단으로 대규모 스키마 변경(컬럼 타입 변경, 인덱스 재구성 등)을 할 때 자주 쓰는 패턴은 "원하는 최종 구조로 임시 테이블을 새로 만들고, 데이터를 옮긴 뒤, `RENAME TABLE`로 원래 이름과 자리를 맞바꾸는" 방식이다(MySQL 생태계의 gh-ost, pt-online-schema-change가 이 방식을 자동화한다). 이 스펙은 CREATE/ALTER/DROP에 대한 REPLICATION 규칙은 상세히 다루지만 RENAME TABLE이 REPLICATION 옵션이나 RK 상태에 어떤 영향을 주는지는 전혀 언급하지 않는다. 데이터 적재 작업 동안 슬레이브에 부하를 주지 않으려고 임시 테이블을 REPLICATION=OFF로 만들었다가, 완성 후 원래 운영 테이블 이름으로 RENAME하면 그 순간 이 테이블은 사실상 운영 테이블이 되는데, REPLICATION=OFF 상태가 그대로 유지되는지, RENAME 시점에 자동으로 ON으로 바뀌는지, 아니면 RENAME 자체가 거부되는지 스펙만으로는 알 수 없다.

**구체 예제**:
```sql
-- 무중단 컬럼 타입 변경 패턴(온라인 스키마 변경 도구 흉내)
CREATE TABLE orders_shadow(
    order_id INT PRIMARY KEY,
    amount   BIGINT              -- 기존 orders.amount(INT)를 BIGINT로 바꾸려는 목적
) REPLICATION = OFF;             -- 데이터 이관 중에는 복제 부하를 주지 않으려고 OFF로 생성

-- (트리거 또는 배치 작업으로 orders → orders_shadow 데이터 동기화, 수 시간 소요)

RENAME TABLE orders TO orders_old, orders_shadow TO orders;
-- 이제 orders_shadow였던 테이블이 "orders"라는 이름으로 운영 테이블이 됨
-- 이 테이블의 REPLICATION 값은 여전히 OFF인가?
-- 그렇다면 이 순간부터 신규 orders 테이블은 아무 에러 없이 슬레이브로 복제되지 않는
-- 사고가 발생한다(스펙에 이 경로에 대한 언급이 없음)
```

**예제 설명**: RENAME은 CREATE/ALTER/DROP과 나란히 다뤄져야 할 만큼 흔한 스키마 변경 도구인데, 이 스펙의 어느 절에도 등장하지 않는다. REPLICATION 속성이 "테이블 실체를 따라가는지" 또는 "이름을 따라가는지"조차 정의되어 있지 않다.

**제안**: RENAME TABLE이 REPLICATION 옵션·RK 상태를 테이블 실체 기준으로 그대로 유지함을 명시하고, HA 운영 중 REPLICATION=OFF 테이블을 기존 운영 테이블 이름으로 RENAME하는 시나리오에 경고 또는 차단 규칙을 §2-2에 추가해야 한다.

### 리뷰 26

**[심각도: 중요] REPLICATION 옵션 변경 권한 통제(소유자/DBA 구분)가 스펙에 없다**

**대상**: §2-3 예시 9 (`owner_name : 'DBA'`), §2-2

**문제 설명**: `db_class` 예시는 테이블마다 `owner_name`(소유자)이 기록됨을 보여준다. 그런데 §2-2는 `ALTER TABLE ... REPLICATION`을 실행할 수 있는 권한 주체에 대해 아무 언급이 없다 — 테이블 소유자만 가능한지, 별도로 DBA 권한이 필요한지 불명확하다. 여러 팀이 하나의 물리 DB를 공유하되 스키마(혹은 테이블 그룹)만 나눠 쓰는 조직 구조(마이크로서비스별 DB 접근 계정은 분리하되 물리 인스턴스는 공유하는 흔한 구성)에서, 한 팀의 배포 스크립트가 실수로 다른 팀 소유 테이블에 `REPLICATION=OFF`를 걸 수 있는지가 데이터 무결성에 직결된다. 이 옵션은 "잘못 켜고 끄면 데이터 불일치가 나도 책임지지 않는다"(§1)는 성격을 가지므로 일반 컬럼 추가 ALTER보다 훨씬 신중한 권한 통제가 필요한데, 권한 모델이 전혀 서술되지 않았다.

**구체 예제**:
```sql
-- 팀 A 소유 테이블
CREATE TABLE team_a.critical_orders(order_id INT PRIMARY KEY, amount INT);  -- REPLICATION=ON(기본)

-- 팀 B의 배포 스크립트가 잘못된 접속 정보나 실수로 이 테이블을 대상으로 실행
ALTER TABLE team_a.critical_orders REPLICATION = OFF;
-- 이 실행이 team_a.critical_orders의 소유 여부와 무관하게 성공하는가?
-- 스펙에 권한 규칙이 없어 판단 불가.
-- 성공한다면 팀 A는 자신의 핵심 테이블이 복제에서 빠졌다는 사실을
-- 다음 failover 전까지 알 방법이 없다
```

**예제 설명**: 이 스펙이 도입하는 옵션은 실행 즉시 눈에 보이는 부작용이 없다(에러도, 성능 저하도 즉시 나타나지 않는다)는 점에서 오히려 권한 통제가 더 중요하다. 잘못 실행돼도 그 순간에는 아무도 알아채지 못하기 때문이다.

**제안**: REPLICATION 옵션 변경에 필요한 권한(테이블 소유자 또는 DBA 이상)을 명시하고, 가능하면 이 옵션 변경만 별도 권한으로 분리해 일반 ALTER 권한과 구분해야 한다.

### 리뷰 27

**[심각도: 치명] ORM의 자동 스키마 동기화 기능이 REPLICATION 설정을 인지하지 못해 배포마다 조용히 되돌릴 수 있다**

**대상**: 컨셉 전체, §2-1 (REPLICATION 생략 시 기본값 ON)

**문제 설명**: Hibernate의 `hibernate.hbm2ddl.auto=update`, Django의 자동 마이그레이션, 또는 사내에서 "엔티티 클래스가 스키마의 근원(source of truth)"이라 여기고 배포 때마다 스키마를 엔티티에 맞춰 자동 동기화하는 방식을 쓰는 팀은 실제로 많다. 이런 도구는 표준 SQL 요소(컬럼, 타입, PK/UK, FK)만 인식하도록 만들어져 있어, 이번에 새로 생긴 CUBRID 전용 테이블 옵션인 `REPLICATION`은 인식 대상에 없다. 도구가 "현재 스키마와 엔티티 정의를 비교해 차이만큼 ALTER를 생성"하거나 특정 버전/구현에서 컬럼 변경을 "테이블 재생성"으로 처리하는 경로를 타면, DBA가 의도적으로 `REPLICATION=OFF`로 걸어둔 테이블에 대해 REPLICATION 옵션을 생략한 DDL을 내게 되고, 그 순간 기본값 ON으로 조용히 되돌아간다. 이 문제는 리뷰 20(1차, OFF→ON 전환 봉쇄)과 겹쳐 생각하면 더 심각해진다 — HA 운영 중이라면 §2-2 규칙에 따라 이 되돌림이 에러로 드러나 배포가 막히지만, 도구가 테이블을 완전히 새로 만드는 경로(DROP 후 CREATE, 혹은 싱글 모드 스테이징 DB)를 탄다면 에러 없이 조용히 REPLICATION=ON으로 전환되어 버린다.

**구체 예제**:
```java
// REPLICATION 옵션은 JPA/Hibernate가 표현할 수 있는 개념이 아니므로
// 엔티티 어노테이션 어디에도 나타나지 않는다
@Entity
@Table(name = "audit_events")
public class AuditEvent {
    @Id private Long eventId;
    private String payload;
}
```
```sql
-- DBA가 별도로 실행해 REPLICATION=OFF로 걸어둔 상태
ALTER TABLE audit_events REPLICATION = OFF;

-- 다음 배포에서 hibernate.hbm2ddl.auto=update가 컬럼 추가를 감지해
-- 내부적으로 테이블을 재생성하는 경로를 타면(구현/버전에 따라 다름),
-- 새로 생성되는 audit_events는 REPLICATION 옵션이 없으므로 기본값 ON으로 생성된다
-- → DBA가 명시적으로 꺼둔 설정이 배포 한 번에 조용히 사라진다
```

**예제 설명**: 이 문제의 핵심은 REPLICATION이라는 개념 자체가 ORM의 모델링 어휘(컬럼, 관계, 제약) 바깥에 있어서, 아무리 신중한 개발자라도 엔티티 코드만 보고는 이 설정이 존재한다는 사실 자체를 알기 어렵다는 점이다.

**제안**: REPLICATION 옵션이 걸린 테이블은 ORM 자동 스키마 동기화 대상에서 배제하도록 운영 가이드에 명시하고, 배포 파이프라인이 `show create table` 결과를 실행 전/후로 비교해 REPLICATION 값이 의도치 않게 바뀌었는지 검증하는 절차를 문서에서 권고해야 한다.

### 리뷰 28

**[심각도: 중요] 대용량 테이블에 RK용 제약을 뒤늦게 추가할 때의 장기 락과 클라이언트 타임아웃 충돌**

**대상**: §7, §9 (기존에 RK 없이 운영되던 테이블에 RK 추가를 요구)

**문제 설명**: 이 스펙의 전제 자체가 "지금까지 PK 없이 운영되던 테이블이 존재한다"는 것이다(배경 설명 및 §8의 하위 버전 unload 서술 참고). HA로 전환하려면 이런 테이블에 UNIQUE 제약을 뒤늦게 추가해야 하는데, 이미 대량의 데이터가 쌓인 테이블에 UNIQUE 제약을 추가하는 작업은 대부분의 DBMS에서 기존 데이터 전체를 스캔해 중복 여부를 검증해야 하므로 시간이 오래 걸리고 그동안 테이블 잠금을 오래 유지할 가능성이 높다. 응용 서버의 DB 커넥션 풀/드라이버는 기본적으로 소켓 읽기 타임아웃(짧게는 수십 초, 길어야 수 분)을 갖고 있어, 이 ALTER TABLE 실행이 타임아웃을 넘기면 클라이언트가 연결을 강제 종료하고 재시도할 수 있다. 서버 쪽 작업이 여전히 진행 중인 상태에서 클라이언트가 동일한 DDL을 다시 보내면, 두 개의 장기 ALTER가 경합하거나 "이미 진행 중" 오류가 반복되는 상황이 생길 수 있다. 이 스펙이 §4-1/§7을 통해 요구하는 "RK 추가"는 기존에는 드물던 작업(신규 테이블은 보통 처음부터 PK를 가지므로) — 대용량 레거시 테이블 대상의 온라인 스키마 변경을 갑자기 흔한 배포 작업으로 만든다는 점에서 새로 부각되는 리스크다.

**구체 예제**:
```sql
-- 이미 5천만 건이 쌓인, PK/UK 없이 운영되던 레거시 테이블
-- HA 전환을 위해 §9 규칙에 따라 UK를 추가해야 함
ALTER TABLE legacy_sessions ADD CONSTRAINT UNIQUE(session_token);
-- 5천만 건 전체 스캔 + 중복 검사로 수 분 소요 가능

-- 배포 스크립트(JDBC, 기본 socketTimeout=60000ms)가 이 DDL을 실행하다
-- 60초 안에 응답을 못 받으면 SQLException(타임아웃) 발생 → 배포 스크립트가 "실패"로 처리
-- 하지만 서버는 여전히 ALTER를 백그라운드에서 계속 처리 중일 수 있다
-- 재시도 로직이 있는 배포 스크립트라면 동일 ALTER를 다시 전송 → 중복 실행/락 경합
```

**예제 설명**: 이 문제는 CUBRID만의 문제가 아니라 온라인 스키마 변경 전반의 일반적 함정이지만, 이번 스펙이 "RK 추가"라는 새로운 필수 작업 유형을 (특히 레거시 테이블에 대해) 갑자기 대량으로 요구하게 만든다는 점에서 이 스펙 문서 자체가 그 위험을 짚어줘야 한다.

**제안**: RK용 제약 추가 DDL이 온라인(비차단) 방식으로 처리되는지, 대용량 테이블에서의 예상 소요시간·락 범위를 문서화하고, 배포 가이드에 "이 DDL은 충분히 긴 타임아웃을 설정하고 실행하라"는 권고를 명시해야 한다.

### 리뷰 29

**[심각도: 중요] 자동 롤백(down-migration) 생성 도구가 REPLICATION ON/OFF 전환의 비대칭성을 몰라 장애 대응 롤백이 실패할 수 있다**

**대상**: §2-2 (OFF→ON은 HA 중 금지, ON→OFF는 허용이라는 비대칭 규칙)

**문제 설명**: Liquibase 같은 마이그레이션 도구는 `<rollback>` 태그로 "정방향 변경의 반대"를 생성해두고, 배포 실패 시 자동으로 역방향 DDL을 실행해 이전 상태로 되돌리는 기능을 제공한다. `REPLICATION=ON`에서 `OFF`로 바꾸는 마이그레이션을 작성했다면, 관례상 그 롤백은 "OFF에서 ON으로" 되돌리는 DDL이 된다. 그런데 §2-2 규칙상 HA 운영 중에는 이 되돌리는 방향(OFF→ON) 자체가 금지되어 있다. 즉 "정방향 마이그레이션은 성공했는데 이후 다른 이유로 배포 전체를 롤백해야 하는 상황"이 오면, 자동 생성된 롤백 스크립트가 실행되는 순간 ERROR가 나서 롤백 자체가 막히고, 배포 파이프라인은 "정방향 배포도 문제, 롤백도 실패한" 이중 장애 상태에 놓인다.

**구체 예제**:
```xml
<!-- Liquibase changelog -->
<changeSet id="123" author="dev">
    <sql>ALTER TABLE customers REPLICATION = OFF;</sql>
    <rollback>
        <sql>ALTER TABLE customers REPLICATION = ON;</sql>
    </rollback>
</changeSet>
```
```
-- 배포 파이프라인: changeSet 123 적용 성공 → 이후 changeSet 124가 실패해 전체 배포 롤백 결정
-- 롤백 절차가 changeSet 123의 <rollback>을 실행:
ALTER TABLE customers REPLICATION = ON;
-- ERROR (HA 모드에서 OFF→ON 금지, §2-2)
-- → 배포도 실패, 롤백도 실패. 운영자가 새벽에 수동 개입해야 하는 상황
```

**예제 설명**: 이 문제는 REPLICATION 옵션이 CREATE/DROP처럼 대칭적인 연산이 아니라 "한쪽 방향만 운영 중 허용되는" 비대칭 연산이라는 점을 마이그레이션 도구가 전혀 모른다는 데서 비롯된다. 일반적인 마이그레이션 작성자는 정방향과 역방향이 항상 대칭이라고 가정하고 롤백 스크립트를 기계적으로 작성하기 쉽다.

**제안**: REPLICATION 옵션 변경을 포함한 마이그레이션은 자동 롤백 생성 대상에서 제외하도록 마이그레이션 도구 사용 가이드에 명시하고, "이 옵션 변경은 편도(one-way) 연산이니 롤백 스크립트를 별도로 설계하라"는 경고를 §2-2에 추가해야 한다.

### 리뷰 30

**[심각도: 보통] REPLICATION 옵션이 테이블 단위 전역 속성뿐이라 DB/스키마 레벨 기본값을 지정할 수단이 없다**

**대상**: §2-1 (기본값 ON), 컨셉 전체

**문제 설명**: §2-1은 REPLICATION 옵션을 생략하면 항상 ON이 기본값이라고 규정한다. 이는 데이터베이스 전체 또는 스키마 단위로 "이 스키마의 테이블은 기본적으로 REPLICATION=OFF로 만들어라" 같은 기본값 재정의 수단이 없다는 뜻이다. 하나의 물리 DB에 테넌트별 스키마를 두는 멀티테넌트 SaaS나, 분석/캐시 전용 스키마를 별도로 운영하는 조직에서는 "이 스키마 안의 테이블은 원칙적으로 복제 제외, 예외적으로만 ON"이라는 정책을 세우고 싶을 수 있는데, 이 스펙대로면 스키마 안의 모든 테이블마다 매번 `REPLICATION=OFF`를 명시해야 하고, 하나라도 빠뜨리면 그 테이블만 기본값(ON)으로 생성되어 정책이 깨진다.

**구체 예제**:
```sql
-- 분석 전용 스키마: 원칙적으로 전부 복제 제외하고 싶음
CREATE SCHEMA analytics;
CREATE TABLE analytics.daily_rollup(...) REPLICATION = OFF;   -- 명시함
CREATE TABLE analytics.hourly_cache(...);                      -- REPLICATION 명시를 깜빡함
-- hourly_cache는 기본값 ON으로 생성되어, 분석 스키마 전체를 복제 제외하려던 정책이 깨진다
-- 이 실수는 즉시 에러가 나지 않으므로 복제 트래픽/스토리지가 늘어나야 뒤늦게 발견된다
```

**예제 설명**: 테이블 단위 옵션 자체는 필요하지만, "여러 테이블에 같은 정책을 일관되게 적용"하려는 조직 단위 요구를 이 스펙은 지원하지 않는다.

**제안**: 이번 릴리스 범위는 "테이블 단위 옵션만 지원"으로 명확히 스코프하되, 향후 로드맵에 스키마/DB 레벨 기본값 재정의 기능을 검토 대상으로 남겨야 한다.

### 리뷰 31

**[심각도: 보통] REPLICATION 옵션 변경 이력을 조회할 표준 수단(감사 로그)이 없다**

**대상**: §2-3, 컨셉 전체

**문제 설명**: §2-3은 "현재" REPLICATION 값을 조회하는 방법(`show create table`, `db_class`)만 제공한다. "이 테이블이 언제, 누구에 의해 REPLICATION=OFF로 바뀌었는가"를 추적하는 수단은 스펙에 없다. 이 옵션은 데이터 정합성에 직접 영향을 주는 설정(§1: "REPLICATION OFF로 인한 데이터 불일치는 책임지지 않는다")이므로, 장애 사후 분석(post-mortem)에서 "언제부터 이 테이블이 복제되지 않았는가"를 알아내는 것이 매우 중요한데, 이를 확인할 방법이 카탈로그 현재값 조회 외에는 없다.

**구체 예제**:
```sql
-- 장애 발생: 3개월 전부터 customers 테이블이 복제되지 않고 있었음이 뒤늦게 발견됨
-- "누가 언제 REPLICATION=OFF로 바꿨는가"를 알아내려면?
SELECT * FROM db_class WHERE class_name = 'customers';
-- 현재 값(OFF)만 보여줄 뿐, 변경 이력(시각, 실행자, 이전 값)은 조회할 방법이 없다
-- 결국 별도 DDL 감사 로그가 있다면 그것을 뒤져 REPLICATION 관련 ALTER 문을 찾아야 하는데
-- 그런 감사 로그의 존재 여부 자체가 스펙에 언급되어 있지 않다
```

**예제 설명**: 규제 산업(금융 등)에서는 스키마 변경 이력 자체가 감사 대상이 되는 경우가 흔하고, 이 옵션처럼 "바뀌어도 조용한" 설정일수록 변경 이력 추적의 필요성이 더 크다.

**제안**: REPLICATION 옵션 변경 시 시스템 카탈로그 또는 별도 감사 테이블에 변경 이력(시각, 실행자, 이전/이후 값)을 기록하는 기능을 검토하거나, 기존 DDL 감사 로그 기능이 이 ALTER 문도 포함해 기록하는지 문서에서 확인해줘야 한다.

### 리뷰 32

**[심각도: 사소] `db_class` 시스템 카탈로그에 컬럼이 추가되는 변경이 `SELECT *` 기반 사내 스크립트를 깨뜨릴 위험**

**대상**: §2-3 예시 9

**문제 설명**: 예시 9는 `db_class`에 `replication`이라는 새 컬럼이 추가됨을 보여준다. 많은 조직이 스키마 모니터링, 감사, 문서 자동 생성을 위해 `select * from db_class` 형태로 시스템 카탈로그를 조회하는 내부 스크립트를 운영한다. 컬럼을 이름으로 접근하면 문제가 없지만, 위치 기반(컬럼 번호로 접근)으로 결과를 파싱하는 스크립트라면 새 컬럼이 기존 컬럼들 사이에 끼어드는 위치에 따라 그 뒤 컬럼들의 인덱스가 밀려 파싱이 깨질 수 있다. 이는 이번 스펙 특유의 결함이라기보다 시스템 카탈로그를 확장할 때 일반적으로 지켜야 할 관례(항상 끝에 추가)의 문제이지만, 이번 변경이 그 관례를 지키는지 스펙에 명시가 없다는 점이 아쉽다.

**구체 예제**:
```java
// 사내 스키마 모니터링 스크립트 (안티패턴이지만 실무에 흔함)
ResultSet rs = stmt.executeQuery("select * from db_class where class_name = 'tbl'");
rs.next();
String collation = rs.getString(8);   // 컬럼 순서를 세어서 하드코딩
// db_class에 replication 컬럼이 8번째 이전 위치에 끼워 넣어지면
// 이 스크립트는 collation 대신 replication 값을 엉뚱하게 읽어오게 된다
```

**예제 설명**: 위치 기반 파싱 자체가 안티패턴이지만, 실무에서 완전히 사라지지 않는 관행이므로 릴리스 노트 수준에서라도 이 위험을 짚어줄 필요가 있다.

**제안**: 새 컬럼은 항상 기존 컬럼 목록의 맨 끝에 추가한다는 하위 호환 원칙을 문서에 명시하고, 릴리스 노트에 "db_class 컬럼 목록이 변경되었으니 위치 기반 파싱을 쓰는 도구는 점검하라"는 경고를 포함해야 한다.

## 조사 종료 선언

이번 2차 라운드에서는 다음 영역을 훑었다: (1) §2-3 `db_class` 카탈로그 예시에 등장하는 `tde_algorithm`/`collation`/`partitioned`/`owner_name`/`is_reuse_oid_class` 등 스펙 본문이 침묵하는 필드와 REPLICATION/RK의 상호작용, (2) RENAME TABLE·파티션 연산 등 CREATE/ALTER/DROP 삼종 세트 바깥의 DDL, (3) ORM 자동 스키마 동기화·마이그레이션 도구의 롤백 생성·JDBC 타임아웃 등 응용 개발자가 실제로 쓰는 배포 자동화 도구와 이 스펙의 비대칭 규칙(OFF→ON 금지 등)이 충돌하는 지점, (4) 권한·감사·거버넌스, (5) 시스템 카탈로그 하위 호환.

`REUSE_OID`(OID 재사용 옵션)와 복제의 상호작용, 멀티 슬레이브 브로커 라우팅, 트리거의 간접 DML 복제 귀속, SERIAL 컬럼의 failover 동기화, JPA `@Column(unique=true)`의 nullable 기본값 문제는 조사했으나 최종보고서(§4 직군별 관점 요약, N-8/N-9 등)에 이미 응용 개발자 고유 지적으로 병합되어 있어 신규로 인정하지 않고 제외했다. XA/분산 트랜잭션과 복합 ALTER 배리어의 충돌, optimistic lock 컬럼과 RK의 상호작용은 검토했으나 최종보고서 C-7/C-8의 변주에 가깝거나 실질적 결함으로 보기엔 근거가 얕아 제외했다.

남은 영역(성능 벤치마크 수치, 엔진 내부 잠금 구현 세부)은 응용 개발자 관점에서 검증 가능한 근거가 없어 추측성 리뷰가 될 위험이 커 조사하지 않았다. 이 관점에서 가치 있게 조사할 내용은 소진했다고 판단해 12건으로 마무리한다.
