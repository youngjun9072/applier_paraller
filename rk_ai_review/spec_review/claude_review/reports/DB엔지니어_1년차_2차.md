# CUBRID HA 복제 개선 스펙 리뷰 — DB 엔지니어(운영/DBA) 1년차 관점 — 2차 라운드

## 2차 라운드 개요

1차 리뷰와 최종 통합보고서(치명 9건·중요 10건 등, 특히 RK 비결정성/FK 부모 사후 OFF 전환/RK 조회 불가/§7 파일리스트/§8·§9 모순 등 합의도 높은 이슈)를 먼저 대조해 이미 다뤄진 지점은 배제했다. 이번엔 (1) "HA 클러스터를 켜고 끄는 것" 자체가 하나의 큰 상태 전환이라는 관점에서 부분 유지보수·실패 후 상태·다중 DB 그룹 단위 같은 운영 절차의 공백을 다시 팠고, (2) unloaddb/loaddb 반대편에 있는 물리 백업(backupdb/restoredb) 경로, (3) 스펙이 예시로 보여준 `db_class` 조회 결과에 이미 필드로 등장하지만 본문이 전혀 언급하지 않는 TDE·파티션·소유자 권한 같은 다른 CUBRID 기능과의 상호작용, (4) 복제 로그 용량·대형 테이블 인덱스 생성 비용 같은 용량/성능 운영 관점을 새로 조사했다. 개수를 채우기보다 1차·최종보고서와 확실히 다른 실패 모드로 판단되는 것만 남겼다.

리뷰 21

**[심각도: 치명] RK 위반 하나를 고치기 위해 HA 클러스터 전체를 내려야 하는 것으로 읽힌다 — 문제 테이블만 격리하는 부분 유지보수 경로가 없다**

대상: §1(HA 모드 정의), §3(Single 제약사항), §7(HA 전환)

문제 설명: §1은 HA 모드를 "cubrid hb start로 큐브리드를 실행시킨 상태를 의미하며 나머지는 모두 싱글모드"라고 이분법으로 정의한다. §7은 제약 위반(복제키 없음 등)이 발견되면 "싱글모드에서 ALTER TABLE…을 이용해 복제 키에 해당하는 제약을 추가하거나 복제 제외 대상으로 변경한 후 HA를 재시작해야한다"고 안내한다. 즉 스펙이 제시하는 유일한 수정 절차는 "HA를 끄고(=DB 전체를 싱글모드로 내리고) → 문제 테이블을 고치고 → HA를 다시 켠다"는 것이다. §1의 이분법을 그대로 따르면 이건 문제가 된 테이블 하나만 손보는 게 아니라, 그 순간 정상적으로 복제되고 있던 나머지 수백 개 테이블까지 포함한 DB 전체를 함께 싱글모드로 떨어뜨린다는 뜻이다. 배경에서 지적한 원래 문제(PK 컬럼 변경으로 인한 복제 누락)를 고치려다가, 그보다 훨씬 무거운 대가(전체 서비스의 복제 중단·다운타임)를 치르게 될 위험이 있다. 한 가지 빠져나갈 구멍이 있다면 "문제 테이블만 임시로 REPLICATION=OFF로 돌려서 위기를 넘기고, 나중에 정식 유지보수 시간에 고친다"는 경로인데(§4에 따르면 ON→OFF 전환은 HA 중에도 허용된다), 스펙은 이 경로를 §7에서 대안으로 안내하지 않는다.

구체 예제:
```
[상황]
- HA 클러스터가 6개월째 정상 운영 중. 테이블 200개 중 199개는 문제 없음.
- 배포 실수로 tbl_x 하나가 복제키 자격을 잃었다는 것이 뒤늦게 발견됨
  (예: 1차 리뷰18/최종보고서 C-9가 지적한 "NOT NULL 해제" 같은 우회 경로).

[스펙이 제시하는 유일한 절차]
1) cubrid hb stop        -- HA 전체 중지, 200개 테이블 전부 복제 끊긴 싱글모드로 전환
2) csql> ALTER TABLE tbl_x ADD CONSTRAINT UNIQUE(...);   -- 문제 테이블만 수정
3) cubrid hb start        -- 전체 재기동

-- 이 사이 199개의 정상 테이블도 함께 복제가 끊긴 상태로 서비스된다.
-- "tbl_x 하나만 REPLICATION=OFF로 돌려 HA는 계속 켜둔 채 넘어간다"는 대안이
-- 실제로 가능한지, 이후 §7 검사를 다시 통과하는지는 스펙에 안내가 없다.
```

예제 설명: 1년차 운영자가 새벽에 이런 위반을 발견했을 때, 스펙 문서만 보고 판단하면 "전체를 내려야 하나 보다"고 결론짓고 실제로는 필요 없었을지도 모르는 전체 다운타임을 감수하게 될 수 있다. 반대로 "OFF로 돌려서 넘기면 되지 않을까"라고 스스로 판단해서 시도했다가, 그게 실제로 안전한 절차인지 확신이 없어 불안한 채로 운영 결정을 내리게 된다. 두 경우 모두 문서가 이 갈림길 자체를 언급하지 않아서 생기는 문제다.

제안: §7에 "단일 테이블의 복제키 위반은 REPLICATION=OFF로 임시 전환해 HA를 유지한 채 넘길 수 있다"는 경로를 공식적으로 안내하거나, 그것이 불가능/비권장이라면 그 이유와 함께 "전체 다운이 불가피하다"는 사실을 명시적으로 경고해야 한다.

리뷰 22

**[심각도: 치명] 물리 백업(backupdb/restoredb)에서 REPLICATION 속성이 어떻게 저장·복원되는지 전혀 언급되지 않는다**

대상: §8(제목이 UNLOADDB & LOADDB로, 논리 백업만 다룸)

문제 설명: CUBRID의 백업 방식은 크게 두 가지다. §8이 다루는 unloaddb/loaddb는 "논리 백업"(테이블 구조와 데이터를 덤프해 다시 SQL 형태로 적재하는 방식)이고, 대용량 운영 DB에서 훨씬 흔히 쓰이는 것은 backupdb/restoredb라는 "물리 백업"(데이터베이스 볼륨 파일을 통째로 복사하는 방식)이다. 물리 백업은 볼륨 내부의 카탈로그 페이지를 그대로 복사하므로 REPLICATION 속성이 카탈로그(db_class 등)에 저장되는 값이라면 자연스럽게 함께 보존될 가능성이 높지만, 스펙은 이 경로를 아예 언급하지 않는다. 신입 운영자가 이 스펙만 읽으면 "복제 여부 보존은 unloaddb/loaddb에서만 신경 쓰면 된다"고 오해하기 쉽고, 실제 운영에서 야간 정기 백업이나 DR(재해복구) 사이트 구성에 훨씬 자주 쓰이는 backupdb/restoredb 경로에서 이 속성이 온전히 보존되는지 검증되지 않은 채 넘어갈 위험이 있다. 특히 §8의 "하위 버전에서 unload한 데이터는 load 시 모두 복제 테이블로 설정된다"는 특수 규칙이 물리 백업/복원 경로에도 동일하게 적용되는지, 아니면 애초에 이 경로에는 해당 사항이 없는지조차 알 수 없다.

구체 예제:
```
[일반적인 DR 운영 절차]
1) 매일 새벽 정기 물리 백업
   $ backupdb -d mydb -D /backup mydb

2) 구버전(REPLICATION 미지원)에서 만든 물리 백업을 신버전 CUBRID 바이너리로 복원한다고 가정
   $ restoredb -d mydb -B /backup mydb

3) 이 DB의 각 테이블은 REPLICATION 값이 무엇으로 결정되는가?
   - §8의 "하위 버전 -> load 시 전부 복제 테이블" 규칙이 여기도 적용되는가?
   - 아니면 물리 복사이므로 카탈로그에 애초에 없던 컬럼(replication)이
     복원 후 신버전 기본 스키마에 맞춰 자동으로 채워지는가(그렇다면 그 기본값은?)
   - 스펙 어디에도 답이 없다.
```

예제 설명: 이 시나리오는 DR 훈련이나 실제 재해 복구 상황에서 매우 현실적이다. 물리 백업은 unloaddb보다 빠르고 대형 DB에서 사실상 표준으로 쓰이는 방법인데, 이 경로에 대한 언급이 전혀 없으면 운영자는 자신이 실제로 쓰는 백업 방식이 이 스펙의 규칙을 그대로 따르는지, 완전히 다른 동작을 하는지 실제로 복원해보기 전까지는 알 수 없다. 게다가 하위 버전 물리 백업을 신버전으로 복원하는 것은 카탈로그 스키마 자체가 다른(REPLICATION 컬럼이 아예 없던 버전 vs 있는 버전) 더 근본적인 문제까지 겹친다.

제안: §8을 "UNLOADDB/LOADDB(논리 백업)"과 "BACKUPDB/RESTOREDB(물리 백업)"로 나누어 각각 REPLICATION 속성의 저장·복원 방식을 명시해야 한다. 하위 버전 물리 백업을 신버전으로 복원할 때의 카탈로그 마이그레이션 방식도 함께 다뤄야 한다.

리뷰 23

**[심각도: 치명] HA 전환(hb start)이 제약 위반으로 실패한 직후, DB가 정확히 어떤 상태로 남는지 스펙에 없다**

대상: §7(HA 전환)

문제 설명: §7은 "HA 실행시 다음 사항을 제약사항을 확인하며, 제약사항 위반 시 에러와함께 파일 리스트를 출력한다"고만 되어 있다. 1차 리뷰4와 최종보고서 C-4는 이 출력의 형식·경로가 불명확하다는 점을 지적했는데, 여기서는 다른 질문을 던진다: 이 검사에서 실패하면 그 순간 시도되던 "cubrid hb start"라는 명령 자체는 어떤 결과를 남기는가? 가능성은 최소 세 가지다. (1) hb start가 실패로 끝나고 DB는 시도 이전 상태(예: 정지 상태 혹은 싱글 모드)로 조용히 되돌아간다. (2) hb start가 일부만 진행되어(예: HA 관련 프로세스는 떴지만 실제 복제는 시작되지 않은) 어중간한 상태로 남는다. (3) 이 검사를 통과한 뒤 다른 이유로 기동이 실패하는 경우와 뒤섞여 원인 구분이 안 된다. 이 답이 없으면, 실패한 시도 직후 운영자가 무엇을 해야 하는지(단순 재시도? 프로세스를 강제 종료해야 하나? 지금 DB가 떠 있는 건가 아닌가?) 판단할 근거가 없다.

구체 예제:
```
[새벽 3시, 배포 후 HA 재기동 시도]
$ cubrid hb start mydb
ERROR: replication constraint violation
tbl_a
tbl_b

$ cubrid hb status mydb
-- 이 시점에 mydb는 지금 떠 있는가, 내려가 있는가?
-- 애플리케이션이 이미 mydb에 연결을 시도하고 있다면 그 연결은
-- 성공하는가(싱글모드로 뜬 상태), 실패하는가(완전히 다운),
-- 아니면 복제 없이 반쪽짜리 상태로 연결이 되는가?

$ cubrid hb start mydb   -- 곧바로 재시도해도 안전한지도 불명확
```

예제 설명: "명령이 실패했다"는 사실 하나만으로는 새벽 장애 대응이 끝나지 않는다. 실패 직후의 DB 상태를 모르면 운영자는 무작정 재시도하거나, 최악의 경우 서비스가 실제로는 정상 기동돼 있는데도 로그만 보고 불필요하게 강제 재기동을 시도해 오히려 서비스를 끊어버릴 수 있다.

제안: §7에 "제약 위반으로 hb start가 실패하면 DB는 (기동 전 상태로 되돌아간다 / 이미 싱글 모드로 뜬 상태다 / 등) 어떤 상태로 남으며, 이 상태에서 애플리케이션 연결이 어떻게 처리되는지"를 명시하고, 실패 후 안전하게 재시도할 수 있는 절차를 런북 형태로 제공해야 한다.

리뷰 24

**[심각도: 중요] TDE(투명 데이터 암호화) 테이블과 RK/복제 로그의 상호작용이 전혀 언급되지 않는다**

대상: §2-3 예시 9(`db_class` 조회 결과의 `tde_algorithm` 필드), §1

문제 설명: §2-3 예시 9의 `db_class` 조회 결과에는 `tde_algorithm : 'NONE'`이라는 필드가 그대로 노출된다. 즉 이 스펙이 예시로 보여주는 카탈로그 행에는 TDE(디스크에 저장된 데이터를 투명하게 암호화하는 기능) 여부가 이미 함께 존재하는데, 본문 어디에도 TDE가 걸린 테이블과 REPLICATION/RK 기능이 어떻게 맞물리는지 언급이 없다. 구체적으로 궁금한 것은 두 가지다. (1) TDE로 암호화된 테이블의 변경분이 복제 로그에는 평문으로 실리는가, 암호화된 채로 실리는가? 평문이라면 마스터 디스크에는 암호화되어 저장된 민감 데이터(주민번호, 카드번호 등)가 복제 로그라는 별도 경로로 평문 노출될 위험이 생긴다. (2) 슬레이브가 이 로그를 받아 RK 값으로 대상 행을 찾아 갱신해야 하는데, 슬레이브 쪽 TDE 키 설정이 마스터와 다르면 이 과정이 실패하는지, 아니면 TDE가 원래 복제와 완전히 독립적으로 동작해 이 우려 자체가 기우인지 스펙이 밝히지 않는다.

구체 예제:
```sql
-- TDE가 걸린 복제 테이블이라고 가정
csql> CREATE TABLE customers_secure(
    customer_id INT PRIMARY KEY,
    ssn VARCHAR(20)
) REPLICATION = ON;
-- 이 테이블에 TDE가 적용되어 있다고 가정(tde_algorithm이 NONE이 아닌 값)

csql> UPDATE customers_secure SET ssn = '...' WHERE customer_id = 1;

-- 질문: 이 UPDATE의 복제 로그에 실리는 "customer_id = 1"이라는 RK 조건절과
-- 변경된 ssn 값은 각각 암호화된 형태로 로그에 남는가, 평문인가?
-- 슬레이브의 applylogdb는 이 로그를 어떻게 복호화/재암호화해서
-- 슬레이브의 customers_secure에 반영하는가?
```

예제 설명: 이 질문은 보안 컴플라이언스가 걸린 데이터(주민번호, 카드번호 등)를 다루는 실제 운영에서 반드시 확인해야 한다. TDE를 도입한 이유 자체가 "디스크에 평문으로 남기지 않겠다"는 것인데, 복제 경로에서 이 원칙이 깨진다면 TDE 도입 효과가 사실상 무력화된다. 스펙이 이 관계를 언급하지 않으면, 보안 감사 시점에 "복제 로그 파일도 암호화 대상인가?"라는 질문에 아무도 답하지 못하는 상황이 생긴다.

제안: TDE 테이블의 RK/복제 로그 처리 방식(로그 자체의 암호화 여부, 슬레이브 측 키 요구사항)을 별도로 명시하거나, 최소한 "이번 기능은 TDE와 독립적으로 동작하며 기존 TDE 복제 정책을 그대로 따른다"는 문장을 §1 또는 §8 근처에 추가해야 한다.

리뷰 25

**[심각도: 중요] 파티션 테이블에서 파티션 키 제약이 복제키(RK) 후보 선택에 미치는 영향이 불명확하다**

대상: §1, §2-3 예시 9(`partitioned` 필드)

문제 설명: §2-3 예시 9의 `db_class` 조회 결과에는 `partitioned : 'NO'`라는 필드가 있다. 즉 파티션 테이블(하나의 논리 테이블을 여러 물리 조각으로 나눠 저장하는 기능) 역시 이 카탈로그 행에 이미 존재하는 개념인데, 본문은 파티션 테이블에 대해 한 마디도 하지 않는다. 관계형 DB에서는 흔히 파티션 테이블에 유니크 제약(PK/UK)을 걸려면 그 제약이 파티션을 나누는 기준 컬럼(파티션 키)을 포함해야 한다는 제한이 있다(그렇지 않으면 서로 다른 파티션에 있는 두 행의 유일성을 테이블 전체 차원에서 보장할 수 없기 때문이다). 만약 CUBRID도 이런 제한을 갖고 있다면, RK 후보로 쓸 수 있는 PK/UK 자체가 "파티션 키를 포함하는 것"으로 좁혀질 수 있는데, §1의 RK 선택 규칙("PK가 존재한다면 PK가 복제 키가 됨" 등)은 이런 제한을 전혀 고려하지 않고 서술되어 있다. 파티션 테이블에서 RK 선택이 비파티션 테이블과 완전히 동일한 규칙으로 동작하는지, 아니면 파티션 키가 RK에 강제로 포함되어야 하는 별도 규칙이 있는지 알 수 없다.

구체 예제:
```sql
-- 파티션 테이블 예시 (연도별 파티션이라고 가정)
csql> CREATE TABLE sales(
    sale_id INT,
    sale_year INT,
    amount INT,
    CONSTRAINT pk_sales PRIMARY KEY(sale_id)   -- 파티션 키(sale_year) 미포함
)
PARTITION BY RANGE (sale_year) (
    PARTITION p2025 VALUES LESS THAN (2026),
    PARTITION p2026 VALUES LESS THAN (2027)
);
-- 파티션 키(sale_year)를 포함하지 않는 이 PK 정의를 CUBRID가 허용하는지,
-- 허용한다면 이 PK가 그대로 RK가 되는지, 허용하지 않는다면
-- "RK 후보"라는 개념이 파티션 테이블에서는 애초에 성립하지 않는
-- 케이스가 생기는 것인지 스펙에 답이 없다.
```

예제 설명: 파티션 테이블은 대용량 로그성/이력성 테이블(주문 이력, 접속 로그 등)에서 흔히 쓰이고, 이런 테이블일수록 HA 복제 대상으로 삼고 싶은 경우가 많다. 이 스펙이 파티션과의 상호작용을 다루지 않으면, 파티션을 쓰는 팀은 이 기능을 적용하기 전에 별도로 직접 검증해야 하고, 검증 결과가 기대와 다르면(예: 파티션 테이블은 RK를 가질 수 없어 사실상 HA 전환이 막힌다면) 파티션을 많이 쓰는 서비스일수록 이 기능의 혜택을 전혀 못 받을 수 있다.

제안: 파티션 테이블과 RK/REPLICATION 옵션의 상호작용(파티션 키의 RK 포함 요구 여부, 파티션 단위로 REPLICATION 값을 따로 가질 수 있는지)을 별도로 명시해야 한다.

리뷰 26

**[심각도: 중요] REPLICATION 옵션을 바꿀 수 있는 권한이 누구에게 있는지, 변경 이력을 추적할 수단이 있는지 스펙에 없다**

대상: §2-2, §2-3 예시 9(`owner_name` 필드)

문제 설명: §2-3 예시 9의 `db_class` 조회 결과에는 `owner_name : 'DBA'`처럼 테이블 소유자 정보가 이미 노출된다. 즉 CUBRID에는 이미 테이블 소유자·권한(GRANT/REVOKE) 개념이 존재하는데, `ALTER TABLE ... REPLICATION=ON|OFF`라는 이 새 DDL을 실행할 수 있는 권한이 테이블 소유자에게만 있는지, DBA 권한을 가진 계정만 가능한지, 아니면 일반적인 스키마 변경 권한만 있으면 누구나 실행 가능한지 스펙에 아무 언급이 없다. 이는 사소한 문제가 아니다. 최종보고서 C-2가 지적한 "FK 부모 테이블을 사후에 OFF로 전환해 failover 사고를 재현하는" 시나리오가 실제로 발생하려면 결국 누군가 그 ALTER 문을 실행해야 하는데, 이 명령의 실행 권한이 아무 제한 없이 열려 있다면 사고가 재현될 문턱이 그만큼 낮아진다. 또한 이 옵션을 "언제 누가 바꿨는지"를 사후에 추적할 감사(audit) 수단이 있는지도 불명확하다.

구체 예제:
```sql
-- 일반 애플리케이션 계정(스키마 변경 권한은 있으나 DBA는 아님)으로 접속했다고 가정
csql> connect mydb@app_user;
csql> ALTER TABLE customers REPLICATION=OFF;
-- 이 문장이 성공하는지 여부는 스펙에 없다.
-- 만약 성공한다면, 이후 "누가 이 옵션을 언제 바꿨는지" 확인하려는 DBA는
-- 어떤 카탈로그나 로그를 조회해야 하는가? db_class에는 현재 값만 있을 뿐
-- 변경 이력(history)은 보이지 않는다.
```

예제 설명: 이 시나리오는 사고가 이미 벌어진 뒤 원인을 추적하는 사후 대응(포렌식) 관점을 보여준다. REPLICATION 옵션은 데이터 정합성에 직결되는 민감한 설정인데, 이를 바꾸는 데 특별한 권한이 필요 없고 변경 이력도 안 남는다면, 장애 발생 후 "누가, 왜, 언제 이 테이블을 복제 대상에서 뺐는가"를 규명할 방법이 없다.

제안: REPLICATION 옵션 변경에 필요한 최소 권한(DBA 권한 요구 여부)을 명시하고, 변경 이력을 조회할 수 있는 감사 수단을 §2-2 또는 §2-3에 추가해야 한다.

리뷰 27

**[심각도: 중요] REPLICATION=OFF 테이블의 변경분이 복제 로그 자체에 기록되는지, 그것이 로그 용량·네트워크 대역폭에 어떤 영향을 주는지 불명확하다**

대상: §1, §4

문제 설명: 스펙은 "REPLICATION 옵션은 데이터 복제 여부를 결정한다"고만 서술할 뿐, 이 "결정"이 로그 파이프라인의 어느 단계에서 일어나는지 말하지 않는다. 이는 단순한 구현 디테일이 아니라 운영자가 실제로 체감하는 결과가 완전히 달라지는 문제다. (경로 A) 마스터가 REPLICATION=OFF 테이블의 DML을 애초에 슬레이브로 전송되는 복제 로그에 기록하지 않는다면 로그 용량과 네트워크 대역폭이 절약된다. (경로 B) 반대로 슬레이브로는 모든 테이블의 로그가 동일하게 전송되고, applylogdb(슬레이브가 로그를 받아 실제 반영하는 프로세스)가 적용 단계에서 REPLICATION=OFF인 테이블의 로그만 걸러서 버린다면, 대역폭 절약 효과는 전혀 없고 오히려 슬레이브가 "쓸모없는 로그"를 지속적으로 받고 버리는 낭비가 생긴다. 이 스펙만 읽어서는 어느 경로인지 전혀 알 수 없고, 이는 대용량 REPLICATION=OFF 테이블(예: 로그성 대량 적재 테이블)을 운영하는 팀의 용량 계획(네트워크 대역폭, 슬레이브 디스크의 로그 보관 공간)에 직접 영향을 준다.

구체 예제:
```
[용량 계획 시나리오]
- audit_log 테이블: REPLICATION=OFF, 하루 500GB씩 INSERT되는 대량 로그성 테이블
- orders 테이블: REPLICATION=ON, 하루 5GB 변경

- 경로 A(마스터에서 필터링)라면: 슬레이브로 가는 복제 트래픽은 대략 5GB/일 수준
- 경로 B(슬레이브에서 필터링)라면: 슬레이브로 가는 복제 트래픽은 505GB/일에 달하고
  그중 500GB는 슬레이브에 도착해서 그냥 버려진다

- 네트워크 대역폭과 슬레이브 디스크의 로그 보관 용량을 미리 산정해야 하는
  운영자 입장에서 이 둘은 100배 가까이 차이 나는 완전히 다른 설계다.
```

예제 설명: REPLICATION=OFF는 단순히 "복제 안 함"이라는 논리적 의미를 넘어, 실제 인프라 용량 설계에 수십~수백 배 차이 나는 물리적 결과를 낳을 수 있다. 이 스펙이 배경에서 "MySQL식 전 컬럼 키는 성능이 느려서 배제했다"며 성능을 중요하게 고려한 만큼, REPLICATION=OFF의 로그 처리 방식도 같은 수준의 설명이 필요하다.

제안: REPLICATION=OFF 테이블의 변경분이 (a) 마스터의 트랜잭션 로그 자체에는 항상 기록되는지(크래시 복구를 위해 이건 불가피할 가능성이 높다) (b) 슬레이브로 전송되는 복제 스트림에도 포함되는지, 필터링 시점이 마스터 송신측인지 슬레이브 수신측인지를 §1 또는 §4에 명시해야 한다.

리뷰 28

**[심각도: 중요] 기존 대형 테이블에 복제키 후보(PK/UK)를 신규로 추가하는 작업 자체의 실행 비용이 업그레이드 다운타임 계획에 전혀 반영되지 않았다**

대상: §7, §9

문제 설명: §7과 §9는 "RK가 없는 테이블은 싱글모드에서 ALTER TABLE로 제약을 추가하거나 복제 제외로 바꾼 뒤 HA를 재시작하라"고 안내한다. 그런데 이미 대량의 데이터가 쌓인 기존 테이블에 처음으로 PK나 UNIQUE 제약을 추가하는 작업은 "제약 추가"라는 표현처럼 가벼운 작업이 아니다. 일반적으로 이런 제약을 추가하려면 전체 테이블을 스캔해 기존 데이터가 유일성 조건을 만족하는지 검증하고, 그 컬럼에 대한 인덱스를 새로 생성해야 한다. 수천만~수억 건짜리 테이블이라면 이 작업 자체가 수십 분에서 몇 시간 걸릴 수 있고 그동안 해당 테이블에 장시간 락이 걸릴 수 있다(이는 최종보고서 M-10이 지적한 "REPLICATION 옵션 변경 자체의 락 비용"과는 다른, "제약 추가/인덱스 생성"이라는 별개 작업의 비용이다). 1차 리뷰8이 지적한 "업그레이드 후 RK 없는 테이블이 120개 나올 수 있다"는 시나리오와 결합하면, 이 120개 테이블 각각에 이런 무거운 인덱스 생성 작업을 처리하는 데 걸리는 실제 시간이 업그레이드 다운타임의 대부분을 차지할 수 있는데, 스펙은 이 비용을 전혀 언급하지 않고 "ALTER TABLE로 추가하면 된다"는 한 문장으로 넘어간다.

구체 예제:
```
[업그레이드 런북 시간 산정 실패 시나리오]
1) 사전 점검 결과 RK 없는 테이블 120개 발견(그중 상당수가 각 수천만 건 규모)
2) 런북 작성자가 스펙만 보고 "ALTER TABLE ADD CONSTRAINT는 DDL이니 금방 끝난다"고
   판단해 유지보수 윈도우를 30분으로 잡음
3) 실제로는 대형 테이블 하나에 UNIQUE 인덱스를 새로 만드는 데만 40분이 걸리는
   테이블이 여러 개 있어, 120개를 순서대로 처리하다 유지보수 윈도우를
   몇 시간 초과 -> 서비스 재개 지연
```

예제 설명: 스펙이 제시하는 "해결 방법"(제약 추가)의 문구 자체는 틀리지 않지만, 그 실행 비용에 대한 정보가 없어서 운영 계획(다운타임 산정)이 잘못될 수 있다. 신입 운영자가 이 스펙만 보고 시간을 산정하면 실제 소요 시간을 과소평가하기 쉽다.

제안: §7 또는 §9에 "복제키 후보 추가는 테이블 크기에 비례하는 무거운 DDL이 될 수 있으므로, 사전 점검 시 위반 테이블 목록뿐 아니라 각 테이블의 행 수 규모까지 함께 제공해 다운타임을 예측할 수 있게 해야 한다"는 경고와 함께, 온라인(무중단) 인덱스 생성 지원 여부도 명시해야 한다.

---

리뷰 29

**[심각도: 중요] 하나의 HA 그룹에 여러 데이터베이스가 함께 구성된 경우, §7의 제약 검사가 데이터베이스 단위인지 그룹 전체 단위인지 불명확하다**

대상: §7, §1

문제 설명: 실무에서는 하나의 HA 구성(마스터-슬레이브 페어)에 여러 개의 데이터베이스가 함께 묶여 운영되는 경우가 흔하다. 이런 구성에서 §7의 제약 위반 검사(복제키 없음, FK 참조 문제)가 (1) 지금 기동하려는 데이터베이스 하나에 대해서만 이루어지는지, (2) 같은 HA 그룹에 속한 다른 데이터베이스까지 함께 검사하는지, (3) 만약 여러 DB 중 하나에서만 위반이 발견되면 나머지 정상 DB들의 HA 기동까지 함께 실패하는지 스펙에 언급이 없다. 이는 리뷰21에서 지적한 "부분 유지보수 불가" 문제와 결합하면 더 심각해진다. 만약 위반이 DB 단위가 아니라 그룹 전체에 영향을 준다면, DB A의 사소한 복제키 문제 하나가 같은 그룹의 DB B, C의 HA 기동까지 막을 수 있다.

구체 예제:
```
[가정: 하나의 HA 그룹에 db1, db2, db3 세 개의 DB가 함께 구성됨]
$ cubrid hb start   -- 그룹 전체를 기동하는 형태라고 가정

-- db1에만 RK 위반 테이블이 있고 db2, db3는 문제 없다면:
-- (A) db1만 실패하고 db2, db3는 정상 기동되는가?
-- (B) 그룹 전체 기동이 db1 때문에 실패해 db2, db3도 함께 뜨지 못하는가?
-- 스펙 §7은 이 구분을 전혀 하지 않는다.
```

예제 설명: 여러 서비스가 DB 단위로 나뉘어 하나의 HA 인프라를 공유하는 경우, 이 경계가 어디인지에 따라 장애의 파급 범위가 완전히 달라진다. (B)라면 서로 무관한 서비스 팀들이 다른 팀의 스키마 관리 실수 때문에 함께 장애를 겪는 셈이 된다.

제안: §7에 제약 위반 검사와 그 실패의 영향 범위가 정확히 어느 단위(단일 DB / HA 그룹 전체)인지 명시해야 한다.

리뷰 30

**[심각도: 사소] CUBRID Manager 등 GUI 관리 도구에서 REPLICATION 옵션을 표시·변경할 수 있는지 언급이 없다**

대상: 문서 전체(도구 지원 범위)

문제 설명: 스펙이 제시하는 조회/변경 수단은 전부 csql(명령행 SQL 클라이언트)을 통한 것이다. 실제 운영 현장에서는 CUBRID Manager 같은 GUI 관리 도구로 테이블 속성을 확인하고 스키마를 변경하는 경우도 있다. 이 새로운 REPLICATION 옵션과 RK 정보가 GUI 도구의 테이블 속성 화면에도 노출되는지, GUI를 통해 REPLICATION 값을 변경할 수 있는지에 대한 언급이 전혀 없다.

구체 예제:
```
[시나리오]
GUI로 테이블을 새로 만드는 화면에 REPLICATION 옵션을 지정하는 항목이 없다면,
사용자는 항상 기본값(ON)으로만 테이블을 만들게 되고, RK 없는 테이블을 만들
경우 §4-1("HA 모드에서는 RK 없는 복제 테이블 생성 불가")에 항상 걸리게 될 수 있다.
```

예제 설명: GUI로 스키마를 관리하는 팀은 이 옵션의 존재 자체를 인지하지 못한 채 계속 기본값으로만 테이블을 만들다가, 나중에 HA 전환 시점에서야 무더기로 위반을 겪을 수 있다.

제안: GUI 관리 도구의 지원 범위(최소한 조회라도 가능한지)를 릴리스 노트나 스펙 부록에 명시해야 한다.

## 조사 종료 선언

30개를 채우는 대신 12개를 조사한 시점에서 30개 중 실제로 작성 가치가 있다고 판단한 10개만 남기고 마무리한다. 아래 영역들은 훑어봤지만, 1차 리뷰나 최종보고서가 이미 다룬 지점의 변주이거나 근거 없는 추측에 가까워 제외했다.

- **파티션/트리거/시리얼을 스코프에서 아예 언급 안 한다는 지적 자체**는 최종보고서 Phase 3 권고("파티션·트리거·SERIAL·멀티슬레이브·컬럼 단위 필터를 스코프 명시")에 이미 포함되어 있어, 파티션은 RK 후보 선택이라는 구체적 실패 모드로 좁혀 리뷰25로만 남기고 트리거·SERIAL은 제외했다.
- **다운그레이드(신→구 버전) 경로**와 **fail_count 지표와 신규 위반의 관계**는 최종보고서 4절(직군별 관점 요약)에서 DBA 고유 지적으로 이미 명시돼 있어 재작성하지 않았다.
- **복합키 RK의 로그 크기/성능 영향**은 최종보고서 M-8에 이미 있어 제외했다.
- **VIEW의 집계 함수(COUNT/SUM 등)가 OFF 테이블 때문에 조용히 틀린 값을 낼 수 있다**는 아이디어는 최종보고서 M-2(VIEW가 OFF 테이블 참조 시 경고 없음)의 실패 모드 변주로 판단해 별도 리뷰로 만들지 않았다.
- **cubrid_ha.conf 등 특정 설정 파라미터 이름을 근거로 한 지적**은 정확한 파라미터 존재 여부를 확인할 수 없어 근거 없는 추측이 될 위험이 커서 제외했다.
- **에러 코드 체계 정비**는 최종보고서 M-6에 이미 있어 제외했다.

남은 여지: 엔진 내부 구현(카탈로그 락 순서, 복제 로그 레코드 포맷 세부 필드)에 대한 지적은 DBA 1년차의 직무·연차 범위를 벗어난다고 판단해 의도적으로 배제했으며, 그 영역은 엔진 개발자 리뷰가 이미 더 깊게 다루고 있다(최종보고서 4절). DBA 운영 관점에서는 추가로 조사할 만한 가치 있는 미개척 영역을 찾지 못해 여기서 마무리한다.
