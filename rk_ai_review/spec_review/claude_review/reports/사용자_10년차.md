# CUBRID HA 복제 개선 스펙 리뷰 — 최종 사용자(10년차) 관점

## 리뷰어 소개

SQL을 직접 짜서 서비스 스키마를 설계·운영해 온 지 10년째인 응용 개발자 겸 준(準)DBA다. 특정 벤더에 매여 있지 않고 MySQL, PostgreSQL, Oracle 계열 복제 기능을 실제 운영에서 굴려 본 경험이 있어, 새 기능을 볼 때 "내가 이 옵션을 실수로 잘못 썼을 때 시스템이 나를 얼마나 빨리, 얼마나 친절하게 말려주는가"와 "이 설계가 몇 년 뒤에도 버틸 구조인가"를 함께 본다.

## 총평

이번 스펙은 "PK 없는 테이블 때문에 복제가 조용히 깨진다"는 실제 장애를 해결하려는 방향은 타당하다. 그러나 문서를 실제 SQL 사용자 입장에서 처음부터 끝까지 읽어보면, (1) 실패를 최대한 뒤로 미루는 기본값 설계, (2) "복제 키가 무엇을 식별하는가"와 "이 테이블을 복제할 것인가"라는 서로 다른 두 질문을 하나의 메커니즘에 뭉쳐 놓은 개념적 혼선, (3) 예제 코드 자체의 문법 오류와 §8/§9 사이의 명백한 자기모순이 함께 발견된다. 특히 §8과 §9는 "UNLOADDB 파일에 복제 여부 플래그가 없을 때 기본값을 무엇으로 볼 것인가"를 정반대로 서술하고 있어, 이 스펙만 보고 구현하면 두 팀이 서로 다른 동작을 만들어낼 수 있는 수준이다. PostgreSQL의 REPLICA IDENTITY / PUBLICATION 이원 설계나 Oracle GoldenGate의 KEYCOLS 같은 명시적 오버라이드 수단과 비교하면, 이 스펙은 "엔진이 알아서 고른다"는 편의성 뒤에 사용자가 통제할 수 없는 불투명성을 숨기고 있다. 아래 20건은 심각도 순이 아니라 스펙 절 순서에 가깝게 배치했으며, 개념 자체에 대한 지적과 절별 지적을 고르게 담았다.

### 리뷰 1

**[심각도: 치명] §8과 §9가 "플래그 없는 테이블"의 기본 복제 여부를 정반대로 규정한다**

대상: §8(UNLOADDB & LOADDB) vs §9(SUMMARY)

문제 설명: §8 본문은 "복제 여부를 저장하는 변수가 설정되어 있지 않다면 복제 대상(Default)으로 간주한다"고 명시하고, 바로 다음 문장에서 "하위 버전에서 unload 한 데이터 파일에는 ... 변수가 설정되어있지 않으므로 (싱글 모드에서) load 시 모두 복제 테이블로 설정된다"고 재확인한다. 즉 플래그가 없으면 **복제 대상(ON)**이다. 그런데 §9 SUMMARY는 "UNLOADDB 시 복제 대상 여부를 함께 출력해야하며, **이를 포함하지 않는 테이블은 모두 복제 제외 테이블이다**"라고 적어, 플래그가 없으면 **복제 제외(OFF)**라고 정반대로 말한다. 여기서 "카탈로그"란 테이블·컬럼·제약조건 같은 스키마 메타데이터를 DB 엔진이 내부적으로 보관하는 시스템 테이블 집합을 뜻하는데, unload는 이 카탈로그 내용을 텍스트 파일로 덤프하는 작업이고 load는 그 반대다. 두 절 중 어느 쪽이 진짜 사양인지 이 문서만으로는 결정할 수 없다.

구체 예제:
```
# 시나리오: CUBRID 10.x에서 만든 테이블을 구버전 unloaddb로 백업했다고 가정
$ unloaddb -i mydb   # 구버전 포맷: REPLICATION 플래그 필드 자체가 없음

# 새 버전에서 싱글 모드로 loaddb 실행
$ loaddb -d mydb -s schema.txt -o object.txt

# 결과 확인
csql> select class_name, replication from db_class where class_name='legacy_tbl';
```

예제 설명: §8 규칙을 따르면 위 결과는 `replication : ON`이어야 하고, §9 규칙을 따르면 `replication : OFF`여야 한다. 실제로 이 테이블에 PK도 UK도 없는 레거시 테이블이라면, ON으로 판정될 경우 §7 HA 전환 검사에서 "RK 없음"으로 걸려 HA 기동이 실패하고, OFF로 판정될 경우 조용히 복제 제외 테이블이 되어 페일오버 후 데이터가 통째로 사라진 것처럼 보인다. 즉 이 모순 하나 때문에 업그레이드 결과가 "HA가 아예 안 뜬다" 또는 "말 없이 데이터가 슬레이브에 없다" 둘 중 하나로 갈릴 수 있다.

제안: 둘 중 하나로 확정하고(§8의 서술이 더 상세하므로 §8을 기준으로 삼는 편이 자연스러워 보인다), §9는 §8과 동일한 문장으로 다시 쓰거나 §8을 인용하는 형태로 고쳐야 한다. 또한 실제 구현 시 이 기본값 케이스에 대한 단위 테스트를 반드시 추가해야 한다.

### 리뷰 2

**[심각도: 치명] 복제 대상 테이블이 참조 중인 테이블을 사후에 REPLICATION=OFF로 바꾸는 경로가 막혀 있지 않다**

대상: §2-2(ALTER ... REPLICATION), §5(외래키)

문제 설명: §5는 "외래키 테이블에서 참조하는 모든 테이블은 복제 대상이여야한다"고 **생성 시점**과 **FK를 추가하는 ALTER 시점**(예시 17~23)에 대해서만 검증 예제를 보여준다. 그런데 이미 FK로 참조되고 있는, 이미 REPLICATION=ON인 테이블을 나중에 `ALTER TABLE ... REPLICATION=OFF`로 바꾸는 경로에 대해서는 이 절 어디에도 차단 규칙이 없다. §2-2의 예시 6은 "ALTER TABLE tbl REPLICATION=OFF; → OK"라고만 되어 있어서, 이 tbl이 다른 ON 테이블로부터 FK 참조를 받고 있는 상태여도 OK로 읽힌다.

구체 예제:
```sql
-- HA 모드, 두 테이블 모두 최초에는 REPLICATION=ON
csql> CREATE TABLE customers(
    customer_id INT PRIMARY KEY,
    country INT
);

csql> CREATE TABLE orders(
    order_id INT PRIMARY KEY,
    customer_id INT,
    CONSTRAINT fk_customer_id FOREIGN KEY (customer_id) REFERENCES customers(customer_id)
);
-- 여기까지는 스펙 예시 17과 동일, 정상

-- 문제의 지점: 나중에 누군가 customers만 복제 제외로 바꾼다
csql> ALTER TABLE customers REPLICATION=OFF;
-- 스펙 예시 6의 패턴("ALTER TABLE tbl REPLICATION=OFF" → OK)을 그대로 따르면 이것도 OK로 보인다
```

예제 설명: 이 시퀀스가 실행되면 orders는 여전히 REPLICATION=ON으로 슬레이브에 복제되지만, orders가 참조하는 customers는 더 이상 복제되지 않는다. 이는 스펙 §5가 그림(Application–Master–Slave FK failover 다이어그램)까지 그려가며 경고한 "FK 참조 테이블이 복제 제외일 때의 문제 상황"과 정확히 동일한 상태를, CREATE/FK-ALTER 시점 검증을 모두 통과한 뒤 순수하게 REPLICATION 옵션 변경만으로 재현한 것이다. 즉 입구(생성, FK 추가)는 막아놨는데 뒷문(참조 대상의 옵션 변경)은 열려 있다.

제안: `ALTER TABLE ... REPLICATION=OFF`를 실행하기 전에, 해당 테이블을 참조하는 FK를 가진 REPLICATION=ON 테이블이 하나라도 있는지 검사하고 있으면 에러로 막아야 한다. §5의 "확인해 에러를 출력할 수 있어야한다" 요구사항을 CREATE/ALTER FK 추가 시점뿐 아니라 REPLICATION 값 변경 시점에도 동일하게 적용한다고 §2-2 또는 §5에 명시해야 한다.

### 리뷰 3

**[심각도: 치명] REPLICATION 기본값이 ON이면서 RK 부재 검증은 HA 전환이라는 가장 늦은 시점까지 미뤄진다**

대상: §2-1, §3, §7

문제 설명: §2-1은 "이 옵션은 생략 가능하며 생략시 ON으로 자동으로 복제 테이블로 생성된다"고 하고, 바로 이어서 "복제 키가 없는 테이블은 싱글 모드에서만 생성 가능하고, HA 전환시 에러가 발생한다"고 말한다. 정리하면: 옵션을 아무것도 안 쓰고 PK도 안 붙인 평범한 테이블은 싱글 모드에서 **아무 경고 없이** 생성되고, 그 문제는 몇 주 뒤 실제로 `cubrid hb start`로 HA를 켜는 순간에야 드러난다. 이것은 "가능한 한 빨리 실패하라(fail fast)"는 일반적인 시스템 설계 원칙과 반대로, 실패 시점을 가장 위험한 순간(운영 전환 당일)까지 미루는 설계다.

구체 예제:
```sql
-- 개발자가 싱글 모드 개발 DB에서 무심코 PK 없는 로그 테이블을 만든다
csql> CREATE TABLE access_log(
    ts DATETIME,
    user_id INT,
    action VARCHAR(50)
);
-- REPLICATION 옵션을 안 썼으므로 §2-1 규칙에 따라 REPLICATION=ON, 생성 성공(OK)
-- 이 상태로 몇 주간 개발/스테이징에서 아무 문제 없이 잘 돌아간다

-- 몇 주 뒤, 운영 반영일에 HA를 켠다
$ cubrid hb start mydb
-- §7 규칙: "복제 테이블에 복제키가 존재하지 않는 경우" 위반 → 에러 + 파일(테이블) 리스트 출력, HA 기동 실패
```

예제 설명: access_log는 만드는 시점에는 아무 경고도 받지 않는다. CREATE TABLE 문에는 REPLICATION이라는 단어조차 등장하지 않았는데도, 몇 주 뒤 운영 전환 순간에 처음으로 "이 테이블에 문제가 있다"는 사실을 알게 된다. 게다가 그 시점은 이미 서비스 오픈을 앞둔 시점이라 되돌리기 부담이 가장 큰 때다. 개발자 입장에서는 "내가 REPLICATION을 쓴 적도 없는데 왜 HA 기동이 막히지?"라는 당혹스러운 경험을 하게 된다.

제안: (1) 싱글 모드라도 PK/UK가 전혀 없는 테이블을 REPLICATION=ON(또는 미지정)으로 생성할 때 WARNING을 즉시 출력해 사용자가 그 자리에서 인지하게 한다. (2) `cubrid hb start`가 아니라 별도의 사전 점검 명령(`cubrid hb check` 같은)을 제공해 운영 전환 이전 아무 때나 미리 검증할 수 있게 한다. 실패 시점을 최대한 앞으로 당겨야 한다.

### 리뷰 4

**[심각도: 중요] 복제 키(RK) 자동 선택 기준 "가장 빠른 순서"가 무엇을 기준으로 하는지 정의되어 있지 않고, 사용자가 원하는 키를 지정할 방법이 없다**

대상: §1

문제 설명: §1은 "UK가 여러개 존재한다면 큐브리드 엔진에 의해 이 중 하나가 선택된다(ex. 테이블내에 명시된 순서 중 가장 빠른 순서)"라고 되어 있다. "명시된 순서"가 CREATE TABLE 문 안에서 컬럼이 나열된 순서인지, 제약조건이 선언된 순서인지, 인덱스가 생성된 내부 OID 순서인지 정의가 없다. 게다가 ALTER TABLE로 UK를 추가/삭제하면 이 "순서"가 바뀔 수 있는데, 그 경우 기존에 선택되어 있던 RK가 사용자 모르게 다른 UK로 교체될 수 있는지도 불명확하다. 더 근본적으로, 사용자가 "이 UK 말고 저 UK를 RK로 써 달라"고 직접 지정할 방법이 스펙 어디에도 없다(§4-2: "사용자는 복제키를 직접 수정할 수 없다").

구체 예제:
```sql
csql> CREATE TABLE sessions(
    session_uuid CHAR(36) NOT NULL UNIQUE,   -- UK 후보 1
    numeric_id INT NOT NULL UNIQUE,           -- UK 후보 2
    payload VARCHAR(4000)
);
-- 엔진이 session_uuid를 RK로 선택했다고 가정 (36바이트 문자열)

-- 몇 달 뒤 numeric_id에 성능 이슈가 있어 컬럼 순서를 정리하며 테이블을 재구성
csql> ALTER TABLE sessions DROP CONSTRAINT u_sessions_numeric_id;
csql> ALTER TABLE sessions ADD CONSTRAINT UNIQUE(numeric_id);
-- 이제 numeric_id UK가 "다시 선언"되었으니 순서상 더 나중이 되었나? 아니면
-- session_uuid가 여전히 유일한 후보라서 그대로 RK인가? 스펙만으로는 알 수 없다.
```

예제 설명: 이 예제는 실무에서 흔한 "제약조건 재구성" 작업이 RK 선택에 어떤 영향을 주는지 스펙만으로는 예측이 불가능함을 보여준다. RK는 applylogdb(마스터의 변경 로그를 슬레이브에 적용하는 내부 모듈)가 슬레이브의 어느 로우를 갱신할지 식별하는 데 쓰이는 핵심 값이다. 만약 RK가 조용히 36바이트 문자열 컬럼에서 4바이트 정수 컬럼으로(또는 그 반대로) 바뀐다면 이는 순수한 성능 특성(인덱스 크기, 비교 비용)에 큰 영향을 준다. 그런데 사용자는 `show create table`로 사후 확인하는 것 말고는 이 변경을 예측하거나 통제할 수단이 없다.

제안: (1) "명시된 순서"의 정확한 정의(예: 시스템 카탈로그 내 제약조건 OID 오름차순)를 스펙에 못박는다. (2) PostgreSQL의 `ALTER TABLE ... REPLICA IDENTITY USING INDEX idx_name`처럼, 여러 UK 후보 중 사용자가 명시적으로 RK를 지정할 수 있는 SQL을 추가로 제공하는 것을 검토한다. 최소한 RK가 실제로 바뀌는 ALTER 작업에 대해서는 확인 메시지나 로그를 남겨야 한다.

### 리뷰 5

**[심각도: 중요] "복제 키가 무엇을 식별하는가"와 "이 테이블을 복제할 것인가"라는 서로 다른 두 질문이 하나의 메커니즘에 뒤섞여 있다**

대상: 컨셉 전체(§1, §2), PostgreSQL REPLICA IDENTITY / PUBLICATION 비교

문제 설명: PostgreSQL의 논리적 복제(logical replication, 로우 단위 변경사항을 별도로 추출해 전송하는 복제 방식)는 이 문제를 두 개의 독립된 축으로 나눈다. `REPLICA IDENTITY`는 "UPDATE/DELETE 때 이 로우를 어떻게 식별할 것인가"만 결정하고(DEFAULT=PK, USING INDEX=지정 UK, FULL=전체 컬럼, NOTHING=식별 불가), `PUBLICATION`/`SUBSCRIPTION`은 "어떤 테이블을 복제 대상에 포함할 것인가"를 완전히 별도로 결정한다. 이 두 축은 서로 독립적이라, "PK가 없어서 식별이 불안정한 테이블이지만 그래도 복제는 하고 싶다"(REPLICA IDENTITY FULL + 여전히 publication에 포함) 같은 절충이 가능하다. 반면 이 스펙은 "RK가 있어야 복제 대상이 될 수 있다"(§1, §4-1)는 식으로 두 개념을 사실상 하나로 묶어버려서, "식별은 불안정해도 되니 일단 복제는 하고 싶다"는 요구를 표현할 방법이 없다.

구체 예제:
```
-- PostgreSQL이라면 가능한 표현
ALTER TABLE wide_event_log REPLICA IDENTITY FULL;  -- PK/UK 없어도 전체 로우로 식별
-- 이 테이블은 여전히 publication에 포함되어 복제된다 (느리지만 동작은 한다)

-- CUBRID 스펙에서 동일한 요구를 표현하면?
csql> CREATE TABLE wide_event_log(
    ts DATETIME,
    payload VARCHAR(4000)
)REPLICATION=ON;
-- §4-1 예시 10과 동일한 패턴: RK 후보가 0개이므로 HA 모드에서 ERROR
-- 선택지는 단 두 가지뿐: (a) 인공 UK/PK를 추가한다  (b) REPLICATION=OFF로 아예 복제를 포기한다
```

예제 설명: wide_event_log 같은 append-only 로그성 테이블은 실무에서 흔하지만 자연스러운 유니크 키가 없는 경우가 많다(같은 타임스탬프에 같은 이벤트가 여러 번 들어올 수 있음). PostgreSQL에서는 "느리더라도 전체 컬럼을 비교해서 복제는 계속한다"는 중간 지점을 선택할 수 있는데, 이 스펙은 그 중간 지점 자체를 설계에서 배제했다. 결국 사용자는 이런 테이블마다 인공 서러게이트 키(예: AUTO_INCREMENT PK)를 추가하는 스키마 변경을 강제로 떠안거나, 복제를 아예 포기해야 한다.

제안: RK 후보가 없는 테이블에 대해 "전체 컬럼 비교" 방식의 폴백을 최소 기능으로라도 검토하거나, 최소한 이 설계상의 트레이드오프(성능 vs 유연성)를 스펙 본문에 "왜 REPLICA IDENTITY FULL 같은 폴백을 채택하지 않았는가"라는 형태로 명문화해 향후 논쟁을 줄여야 한다.

### 리뷰 6

**[심각도: 중요] 다단계 FK 체인에서 중간 테이블이 REPLICATION=OFF인 경우가 검증 대상에 포함되는지 불명확하다**

대상: §5, 원본 다이어그램(orders→customers 2단계 예시)

문제 설명: §5와 함께 제공된 다이어그램은 orders(ON) → customers(OFF) 2단계 FK 참조만을 예로 든다. 실무 스키마는 흔히 3단계 이상 체인을 이룬다(주문→고객→국가 코드 테이블 등). "외래키 테이블에서 참조하는 모든 테이블은 복제 대상이여야한다"는 문장이 직접 참조(1단계)만을 말하는 것인지, 참조의 참조(전이적 의존성)까지 포함하는 것인지 스펙에 명시가 없다.

구체 예제:
```sql
csql> CREATE TABLE countries(
    country_code INT PRIMARY KEY
)REPLICATION=OFF;   -- 실수로, 혹은 "국가 코드는 거의 안 바뀌니 굳이 복제 안 해도 된다"는 생각으로 OFF

csql> CREATE TABLE customers(
    customer_id INT PRIMARY KEY,
    country_code INT,
    CONSTRAINT fk_country FOREIGN KEY (country_code) REFERENCES countries(country_code)
)REPLICATION=ON;
-- §5 규칙에 따르면 이 CREATE TABLE 자체가 ERROR여야 한다 (직접 참조 대상이 OFF이므로)

csql> CREATE TABLE orders(
    order_id INT PRIMARY KEY,
    customer_id INT,
    CONSTRAINT fk_customer FOREIGN KEY (customer_id) REFERENCES customers(customer_id)
)REPLICATION=ON;
-- customers는 ON이므로 이 CREATE TABLE은 §5 직접 검사만으로는 통과된다
-- 하지만 customers가 참조하는 countries는 OFF이다 (전이적 문제)
```

예제 설명: 두 번째 CREATE TABLE(customers)이 애초에 §5 규칙으로 막히기 때문에 이 예제 자체는 스펙대로라면 앞단에서 차단된다. 하지만 검증 시점을 CREATE 시점이 아니라 훨씬 나중, 예를 들어 customers를 나중에 `ALTER TABLE customers REPLICATION=OFF`로 바꾸는 경우(리뷰 2와 결합), orders는 여전히 ON인데 orders가 참조하는 customers가 OFF가 되고 그 customers가 참조하던 countries도 OFF인 상황이 얼마든지 파생될 수 있다. 스펙은 "직접 참조"만 언급하므로, 이런 전이적 체인 전체를 검사 범위에 포함하는지 검증 알고리즘 설계자에게 스펙만으로는 답이 나오지 않는다.

제안: FK 참조 검증이 직접 참조 1단계만인지 전이적 폐쇄(transitive closure) 전체인지 명확히 하고, 체인이 3단계 이상인 예제를 최소 1개 추가한다.

### 리뷰 7

**[심각도: 중요] FK는 하드 에러로 차단하면서 VIEW는 동일한 위험을 경고 문구로만 처리해 일관성이 없다**

대상: §5 vs §6(뷰)

문제 설명: §5는 FK가 REPLICATION=OFF 테이블을 참조하면 CREATE/ALTER 시점에 명확히 ERROR를 낸다(예시 18, 23). 반면 §6은 "복제 제외 테이블이 뷰에 포함되어 있을 경우 ... 큐브리드 복제 모듈은 책임지지 않는다"라고만 되어 있어, VIEW 생성 시점에 아무런 에러나 경고도 발생하지 않는다. 두 경우 모두 "슬레이브에 없는 데이터를 참조하게 된다"는 동일한 실패 양상인데, 하나는 엔진이 막아주고 다른 하나는 사용자 책임으로 떠넘긴다.

구체 예제:
```sql
csql> CREATE TABLE customers(
    customer_id INT PRIMARY KEY,
    country INT
)REPLICATION=OFF;

csql> CREATE TABLE orders(
    order_id INT PRIMARY KEY,
    customer_id INT
)REPLICATION=ON;

-- FK로 연결하면 §5에 의해 ERROR (예시 18과 동일 패턴)
-- 하지만 VIEW로 JOIN하면?
csql> CREATE VIEW order_summary AS
    SELECT o.order_id, c.country
    FROM orders o JOIN customers c ON o.customer_id = c.customer_id;
-- §6에 따르면 이건 아무 에러 없이 생성된다(OK로 추정)
```

예제 설명: order_summary 뷰는 생성 시점에 아무 경고도 없이 만들어진다. 그러나 페일오버(마스터 장애 시 슬레이브가 새 마스터로 승격되는 과정) 이후 이 뷰를 SELECT하면 customers 쪽 데이터가 슬레이브에 없으므로 JOIN 결과가 마스터에서와 다르게 나온다(예: 빈 결과, 혹은 매칭 실패). 사용자는 FK를 걸 때는 시스템이 실수를 막아줬으니 VIEW를 만들 때도 비슷한 보호를 기대하게 되는데, 실제로는 정반대로 동작한다. 이는 같은 근본 원인(참조 대상 데이터 부재)에 대해 두 가지 다른 신뢰 수준을 사용자에게 학습시키는 셈이다.

제안: 최소한 VIEW 생성/ALTER 시점에 참조하는 베이스 테이블 중 REPLICATION=OFF가 섞여 있으면 WARNING(하드 ERROR가 부담스럽다면)을 출력해 FK와 유사한 수준의 가시성을 제공한다.

### 리뷰 8

**[심각도: 중요] PK/UK 후보가 전혀 없는 대형 테이블을 복제 대상으로 편입하려면 반드시 스키마 변경(인공 유니크 키 추가)이 필요하며, 이 비용에 대한 언급이 없다**

대상: §1, §4-1, §7

문제 설명: 리뷰 5에서 지적한 "폴백 부재"의 실무적 귀결이다. RK 후보가 없는 테이블은 HA 전환 전에 반드시 PK 또는 NOT NULL UNIQUE 제약을 추가해야 하는데, 수억 건짜리 대형 테이블에 새 유니크 인덱스를 추가하는 작업은 인덱스 전체 재구성과 그에 따른 잠금(lock)을 수반할 수 있다. §7은 이런 테이블을 "싱글모드에서 ALTER TABLE... 을 이용해 복제 키에 해당하는 제약을 추가"하라고만 안내할 뿐, 이 작업이 운영에 미치는 영향(락 범위, 소요 시간, 온라인 DDL 가능 여부)에 대한 언급이 전혀 없다.

구체 예제:
```sql
-- 5억 건짜리 로그 테이블에 PK가 없다고 가정
csql> ALTER TABLE huge_log ADD CONSTRAINT PRIMARY KEY(id);
-- id 컬럼에 대해 처음으로 유니크 인덱스를 구축해야 함
-- 이 작업이 진행되는 동안 huge_log에 대한 쓰기가 얼마나 막히는가?
-- 이 인덱스 구축이 실패(중복 값 발견)하면 어떻게 되는가?
```

예제 설명: 이 예제는 스펙이 "요구사항"만 던지고 "그 요구사항을 충족하는 데 드는 비용"에는 침묵하고 있음을 보여준다. HA 전환을 준비하는 운영팀 입장에서는 "PK를 추가하라"는 한 문장이 실제로는 몇 시간짜리 유지보수 창(maintenance window)을 의미할 수도 있는데, 스펙만 보면 이게 가벼운 작업인지 무거운 작업인지 전혀 가늠할 수 없다.

제안: 필수 요구사항은 아니더라도, 대형 테이블에 RK를 뒤늦게 추가하는 경우의 온라인 DDL 지원 여부(무중단 인덱스 생성 가능 여부)를 이 스펙 또는 연관 문서에서 최소한 언급해야 한다.

### 리뷰 9

**[심각도: 중요] REPLICATION 옵션이 테이블 카탈로그에 전역으로 박혀 있어, 슬레이브마다 다른 복제 대상 집합을 가질 수 없다 — 멀티 슬레이브/체인 복제 확장에 제약**

대상: 컨셉 전체, 향후 확장성

문제 설명: 여기서 "카탈로그"란 스키마 메타데이터를 저장하는 시스템 테이블을 말한다(예시 9의 `db_class`). 이 스펙에서 REPLICATION ON/OFF는 테이블 자체의 카탈로그 속성이고, 모든 DDL은 슬레이브에 그대로 복제되므로(§4) 모든 슬레이브가 정확히 동일한 REPLICATION 설정을 공유하게 된다. 이는 MySQL의 `replicate-do-table`/`replicate-ignore-table`이 복제본(replica) 쪽 설정 파일에 있어서 슬레이브마다 다르게 지정할 수 있는 것과 대비된다. 즉 CUBRID의 이번 설계로는 "슬레이브 A는 전체 미러, 슬레이브 B는 리포팅용으로 일부 테이블만 제외"같은 구성이 원천적으로 불가능하다.

구체 예제:
```
-- 원하는 미래 구성 (MySQL식이라면 replica 설정 파일에서 개별 지정 가능)
Master
 ├─ Slave-A (전체 미러, DR/failover 대상)
 └─ Slave-B (리포팅 전용, 대용량 audit_log 테이블은 굳이 안 받아도 됨)

-- CUBRID 스펙 하에서:
csql> ALTER TABLE audit_log REPLICATION=OFF;
-- 이 설정은 테이블 자체의 속성이므로 Slave-A와 Slave-B 모두에게 동일하게 적용된다
-- Slave-A가 진짜 failover 대상이라면 audit_log도 미러링되길 원할 수 있지만 선택지가 없다
```

예제 설명: REPLICATION 옵션이 "테이블의 속성"으로 설계되어 있어서, 복제 대상 여부가 슬레이브(수신자)가 아니라 마스터 쪽 카탈로그에서 전역으로 결정된다. 이는 지금 당장의 요구사항(단일 슬레이브 기준 PK 없는 테이블 복제 실패 방지)에는 충분하지만, 스펙이 언급하는 미래 방향성(멀티 슬레이브, 체인 복제)과는 설계 축이 어긋난다. 나중에 슬레이브별 차등 복제가 필요해지면 이번 카탈로그 기반 설계를 갈아엎어야 할 가능성이 높다.

제안: 최소한 스펙에 "이번 REPLICATION 옵션은 테이블 전역 속성이며, 슬레이브별 차등 복제는 이번 범위에 포함되지 않는다"는 명시적 스코프 제한 문구를 넣어, 향후 요구사항 충돌 시 참조할 근거를 남겨야 한다.

### 리뷰 10

**[심각도: 중요] 예시 2의 SQL 자체가 문법 오류를 포함하고 있어 "PK 없어도 싱글 모드에서는 생성 가능하다"는 핵심 주장을 증명하지 못한다**

대상: §2-1, 예시 2

문제 설명: 예시 2는 다음과 같다.
```
csql> CREATE TABLE repl_table_without_rk(
    a INT,
);
```
컬럼 정의가 `a INT` 단 하나뿐인데 그 뒤에 쉼표(,)가 붙어 있다. 표준 SQL 문법에서 마지막 컬럼 정의 뒤의 트레일링 콤마(trailing comma)는 문법 오류이며 이 문장은 그대로 실행하면 syntax error가 난다. 이 예시는 "RK 후보 없는 테이블도 REPLICATION 옵션 없이(혹은 ON으로) 싱글 모드에서 만들 수 있다"는, 이 스펙의 핵심 주장 중 하나를 보여주기 위한 예제인데, 정작 그 예제 코드 자체가 실행 불가능하다.

구체 예제:
```sql
-- 스펙 원문 그대로
csql> CREATE TABLE repl_table_without_rk(
    a INT,
);
-- 예상: syntax error (트레일링 콤마)

-- 올바른 형태
csql> CREATE TABLE repl_table_without_rk(
    a INT
);
```

예제 설명: 같은 트레일링 콤마 오류가 예시 23(`order_id INT PRIMARY KEY,` 뒤에 콤마)에도 반복해서 등장한다. 한 번이면 단순 오타지만 두 번 반복되면 이 문서가 실제로 csql에 붙여 넣어 검증되지 않은 채 작성되었다는 정황이 된다. 사용자가 매뉴얼을 보고 그대로 복사-붙여넣기 했다가 문법 오류를 마주치면, "내가 뭘 잘못했나" 하고 시간을 낭비하게 된다.

제안: 모든 예제 SQL을 실제 csql에 붙여넣어 실행 결과를 확인한 뒤 문서에 반영한다. 트레일링 콤마가 있는 모든 예제(예시 2, 23)를 수정한다.

### 리뷰 11

**[심각도: 보통] 예시 5·6은 어떤 모드(싱글/HA)에서 실행한 것인지 SQL 블록 안에 명시되어 있지 않아, 같은 문장이 왜 다른 결과를 내는지 예제만으로는 알 수 없다**

대상: §2-2, 예시 5, 예시 6

문제 설명: 예시 5(`ALTER TABLE tbl REPLICATION=ON;` → ERROR)와 예시 6(`ALTER TABLE tbl REPLICATION=OFF;` → OK)은 앞 문단의 "HA 모드에서는 복제 제외 테이블이 복제 테이블로 변경될 수 없다"는 설명에 기대어서만 이해할 수 있다. 그런데 두 예제 자체에는 지금이 HA 모드인지 싱글 모드인지, tbl이 이전에 무슨 상태였는지(OFF였는지 ON이었는지) 아무 표시가 없다. 초심자가 이 두 블록만 따로 떼어 보면 "왜 ON은 에러이고 OFF는 OK인지" 이해할 수 없다.

구체 예제:
```sql
-- 스펙에 없는, 그러나 있어야 할 정보를 채운 버전
-- 전제: HA 모드(cubrid hb start 로 기동된 상태), tbl은 현재 REPLICATION=OFF

csql> ALTER TABLE tbl REPLICATION=ON;
-- ERROR: HA 모드에서는 복제 제외 테이블을 복제 테이블로 전환할 수 없습니다.
--        싱글 모드로 전환한 뒤 다시 시도하세요.  (예시 문구, 실제 CUBRID 에러 메시지 아님)

csql> ALTER TABLE tbl REPLICATION=OFF;
-- OK  (참고: tbl은 이미 OFF이므로 이 문장은 사실 아무 것도 바꾸지 않는, 자기 자신으로의 전환이다)
```

예제 설명: 원문 예시 6은 애초에 "OFF에서 OFF로" 가는 무의미한 전환일 수도 있고, "ON에서 OFF로" 가는 실제 전환일 수도 있다 — 원문만으로는 어느 쪽인지도 알 수 없다. 이는 사소해 보이지만, 매뉴얼을 읽는 사용자가 시나리오를 재현하려 할 때 반드시 막히는 지점이다.

제안: 모든 ERROR/OK 예제에 "현재 모드: HA / tbl의 이전 REPLICATION 값" 같은 전제 조건을 한 줄이라도 명시한다.

### 리뷰 12

**[심각도: 보통] 예시 7("Multiple ALTER")이 실행 가능한 SQL이 아니라 "..."으로 생략된 의사코드다**

대상: §2-2, 예시 7

문제 설명: 예시 7은 다음과 같다.
```
csql> ALTER TABLE tbl DROP CONSTRAINT ..., ADD CONSTRAINT ...;
```
이 스펙의 작성 규칙(및 상위 작업지시서)은 모든 리뷰/예제가 "구체적인 SQL"을 요구하는데, 이 문서 스스로도 "구체 예제"를 표방하면서 정작 이 예제는 자리표시자(placeholder)만 담고 있어 그대로 실행할 수 없다. 반면 바로 뒤 §4-2의 예시 13은 동일한 개념(PK를 다른 컬럼으로 바꾸는 DROP+ADD)을 완전한 SQL로 보여준다: `ALTER TABLE table_name DROP CONSTRAINT PRIMARY KEY, ADD CONSTRAINT PRIMARY KEY(a);`.

구체 예제:
```sql
-- 예시 7을 예시 13 수준으로 구체화하면 이렇게 되어야 한다
csql> ALTER TABLE tbl DROP CONSTRAINT pk_tbl_a, ADD CONSTRAINT PRIMARY KEY(b);
-- 또는 PK -> UK로 이관하는 경우
csql> ALTER TABLE tbl DROP CONSTRAINT PRIMARY KEY, ADD CONSTRAINT UNIQUE(b);
```

예제 설명: 예시 13이 존재하는 걸 보면 이 스펙 작성자는 완전한 형태의 예제를 쓸 수 있었다. 그런데 예시 7만 생략형으로 남아있다는 것은 검토가 덜 되었거나, 혹은 "DROP과 ADD를 한 문장에 같이 써야 한다"는 것 외에 구체적으로 무엇을 DROP하고 무엇을 ADD하는지가 상황에 따라 달라서 일반화하기 어려웠다는 뜻일 수 있는데, 어느 쪽이든 독자에게는 불친절하다.

제안: 예시 7을 예시 13과 동일한 수준의 완전한 SQL로 다시 쓴다.

### 리뷰 13

**[심각도: 보통] 예시 20·23의 컬럼 레벨 FK 제약 문법("INT FOREIGN KEY REFERENCES ...")이 실제 CUBRID 문법과 일치하는지 의심스럽다**

대상: §5-2, 예시 20, 예시 23

문제 설명: 예시 20은 다음과 같다.
```sql
csql> ALTER TABLE new_orders ADD COLUMN 
(customer_id INT FOREIGN KEY REFERENCES customers(customer_id));
```
표준적인 컬럼 레벨(inline) 참조 제약 문법은 보통 `컬럼명 타입 REFERENCES 테이블(컬럼)`처럼 `FOREIGN KEY` 키워드 없이 `REFERENCES`만 쓴다(`FOREIGN KEY` 키워드는 테이블 레벨 제약에서 참조할 컬럼 목록을 지정할 때 쓰는 것이 일반적이다). `INT FOREIGN KEY REFERENCES ...`처럼 컬럼 레벨에 `FOREIGN KEY` 키워드까지 넣는 조합이 CUBRID에서 실제로 허용되는지 이 문서만으로는 검증되지 않는다.

구체 예제:
```sql
-- 스펙 원문(예시 20)
csql> ALTER TABLE new_orders ADD COLUMN
(customer_id INT FOREIGN KEY REFERENCES customers(customer_id));

-- 일반적으로 통용되는 컬럼 레벨 문법과 비교
csql> ALTER TABLE new_orders ADD COLUMN
(customer_id INT REFERENCES customers(customer_id));
```

예제 설명: 두 문장 중 실제로 CUBRID 파서가 받아들이는 쪽이 어느 것인지가 명확하지 않다는 것 자체가 문제다. 사용자가 매뉴얼 예제를 그대로 썼다가 파서가 이를 거부하면(혹은 반대로 관용적으로 써왔던 REFERENCES 단독 문법을 썼다가 매뉴얼과 다르다고 혼란스러워하면) 학습 곡선에 불필요한 마찰이 생긴다.

제안: 이 문법이 실제 CUBRID 파서에서 검증된 것인지 확인하고, 검증되지 않았다면 이미 널리 알려진 `REFERENCES` 단독 문법으로 교체한다.

### 리뷰 14

**[심각도: 보통] ALTER로 UK 구성을 바꿀 때 RK가 조용히 재선택될 수 있음에도, 이를 감지할 방법(알림/로그)이 스펙에 없다**

대상: §1, §4-2

문제 설명: 리뷰 4에서 지적한 불확정성의 연장선이다. RK는 사용자가 직접 지정할 수 없고 엔진이 PK/UK 상태를 보고 매번 다시 결정하는 값이라면, ALTER TABLE로 제약을 추가/삭제할 때마다 RK가 바뀌었는지 여부를 사용자가 알 방법이 있어야 한다. 그러나 스펙에는 "RK가 변경되었습니다"라는 형태의 알림이나 로그에 대한 언급이 전혀 없다. 사용자는 매번 `show create table`(예시 8)이나 `select * from db_class`(예시 9)를 실행해 수동으로 대조해야 한다.

구체 예제:
```sql
-- 초기 상태: PK가 RK
csql> CREATE TABLE t(a INT PRIMARY KEY, b INT NOT NULL UNIQUE);
csql> show create table t;
-- ... REPLICATION ON, RK = a(PK) ...

-- PK를 UK로 교체 (예시 13 패턴)
csql> ALTER TABLE t DROP CONSTRAINT PRIMARY KEY, ADD CONSTRAINT PRIMARY KEY(a);
-- 위 문장은 재귀적으로 같은 PK를 다시 만드는 예시일 뿐이지만,
-- 실제로 아래처럼 PK를 완전히 제거하면:
csql> ALTER TABLE t DROP CONSTRAINT PRIMARY KEY, ADD CONSTRAINT UNIQUE(a);
-- 이제 RK 후보는 b(기존 UK)와 a(새 UK) 두 개가 됨. 어느 쪽이 RK인가?
-- 스펙 §1의 "가장 빠른 순서" 기준으로는 답이 안 나온다. 별도 알림도 없다.
```

예제 설명: applylogdb는 RK 값을 기준으로 슬레이브의 로우를 찾아 갱신한다. RK가 a에서 b로(혹은 그 반대로) 조용히 바뀌었는데 애플리케이션이나 운영자가 이를 모른 채 있다면, 장애 상황 분석(예: 특정 로우의 복제 지연 추적)에서 "지금 이 테이블의 RK가 뭔지"를 알아내는 데 불필요한 시간을 쓰게 된다.

제안: RK가 실제로 변경되는 ALTER 작업 시 알림 메시지(`NOTICE: replication key changed from (a) to (b)` 형태)를 출력하도록 스펙에 추가한다.

### 리뷰 15

**[심각도: 보통] §7의 "파일 리스트"라는 용어가 실제로 무엇을 의미하는지 불명확하고, 대규모 스키마에서 HA 기동 시점 전수 검사의 비용이 언급되지 않는다**

대상: §7

문제 설명: §7은 "제약사항 위반 시 에러와함께 파일 리스트를 출력한다"고 한다. 여기서 검사 대상은 테이블(스키마 객체)이지 OS 파일이 아니므로 "파일 리스트"라는 표현 자체가 어색하다(오탈자 내지 번역 잔재로 보인다. 문맥상 "위반한 테이블 목록"을 의도한 것으로 추정된다). 또한 이 검사가 `cubrid hb start`를 실행할 때마다 카탈로그 전체를 스캔해 RK 존재 여부와 FK 참조 대상의 REPLICATION 상태를 매번 확인하는 것이라면, 테이블 수가 많은(수천~수만 개) 스키마에서는 HA 기동 자체가 느려질 수 있다. 이는 페일오버 이후 재기동 속도가 중요한 HA 시스템의 목적과 상충될 수 있다.

구체 예제:
```
$ cubrid hb start mydb
ERROR: HA startup constraint violation. Affected files:
  - db_customers.tbl   (예시. "파일"이라는 표현이 실제 출력에도 쓰이는가?)
  - db_orders_v2.tbl
```

예제 설명: 이 가상의 출력 예시처럼, 실제 CUBRID가 테이블 이름 대신 내부 파일 경로 같은 것을 출력한다면 사용자는 이를 다시 테이블 이름으로 역매핑해야 하는 불편을 겪는다. 스펙에 이 출력 형식에 대한 실제 예제(예시 24 정도가 있었어야 할 자리)가 아예 없다는 것도 문제다 — §7은 유일하게 구체 예제가 하나도 없는 절이다.

제안: (1) "파일 리스트"를 "위반 테이블 목록(스키마명.테이블명 형식)"으로 정정한다. (2) 실제 출력 예시를 최소 1개 추가한다(다른 절들처럼 예시 번호를 붙여서). (3) 대규모 스키마에서의 검사 소요 시간에 대한 비고를 추가하거나 최소한 알려진 이슈로 남긴다.

### 리뷰 16

**[심각도: 보통] §8의 "RK를 할당한다"는 표현이 §1의 "선택된다"는 표현과 달라, 마치 없던 키 컬럼을 새로 만드는 것처럼 오해할 수 있다**

대상: §1 vs §8

문제 설명: §1은 RK 결정 방식을 일관되게 "선택된다"(PK가 복제 키가 됨, UK가 복제 키가 됨, 엔진에 의해 이 중 하나가 선택된다)로 서술한다. 그런데 §8은 "복제 테이블의 경우 큐브리드는 자동으로 RK를 **할당**한다"라고 다른 동사를 쓴다. "할당(assign)"이라는 단어는 일반적으로 "새로 부여한다"는 뉘앙스를 가지며, 예컨대 MySQL InnoDB가 PK 없는 테이블에 내부적으로 숨겨진 6바이트 row ID를 자동 생성해 붙이는 동작을 연상시킨다. 그러나 이 스펙의 실제 동작은 "기존에 있던 PK/UK 중 하나를 복제 키 용도로 지정하는 것"(선택)이지 "새 컬럼을 만들어 붙이는 것"(할당/생성)이 아니다.

구체 예제:
```
-- 사용자가 §8 문구만 읽고 오해할 수 있는 시나리오
-- "RK를 자동으로 할당한다"는 문장을 보고, PK도 UK도 없는 테이블을 unload/load해도
-- CUBRID가 알아서 숨겨진 키를 만들어 복제 가능하게 해줄 것이라 기대함

csql> CREATE TABLE t(a INT) REPLICATION=OFF;  -- 원본에 PK/UK 전혀 없음, 구버전 dump에 이 상태로 존재
-- loaddb 이후 "RK를 자동으로 할당"했으니 이제 HA에서 복제 대상으로 전환 가능하다고 오해
csql> ALTER TABLE t REPLICATION=ON;
-- 실제로는 §4-1 규칙대로 RK 후보(PK/UK)가 없으므로 HA 모드에서는 여전히 ERROR
```

예제 설명: "할당"이라는 단어 선택 하나가 사용자로 하여금 "RK 문제는 이제 엔진이 알아서 해결해주는구나"라는 잘못된 기대를 심어줄 수 있다. 실제로는 §8이 말하는 "RK 할당"은 이미 존재하는 PK/UK를 복제 키로 지정하는 것뿐이며,애초에 PK/UK가 없는 테이블에는 여전히 아무 것도 해줄 수 없다.

제안: §8의 "할당한다"를 §1과 동일하게 "(기존 PK/UK 중에서) 선택한다"로 통일하고, "이 동작은 새로운 키 컬럼을 생성하는 것이 아니라 기존 PK/UK 중 하나를 복제 키로 지정하는 것"이라는 설명을 한 줄 덧붙인다.

### 리뷰 17

**[심각도: 보통] show create table 출력 예시(예시 8)가 REPLICATION=ON인 경우만 보여주고, OFF인 경우의 출력 형식은 예시가 없다**

대상: §2-3, 예시 8

문제 설명: 예시 8은 `REUSE_OID, COLLATE utf8_bin, REPLICATION ON` 처럼 REPLICATION 절이 CREATE TABLE 문 끝에 항상 노출되는 형태를 보여준다. 그런데 REPLICATION=OFF일 때도 동일하게 `REPLICATION OFF`라는 절이 출력에 노출되는지, 아니면 OFF는 기본값이 아니므로(§2-1 기본값은 ON이다) 오히려 OFF일 때만 명시적으로 표시되고 ON일 때는 생략되는지 — 혹은 그 반대인지 — 대칭적인 예시가 없어 알 수 없다.

구체 예제:
```sql
csql> CREATE TABLE tbl2(
    a INTEGER PRIMARY KEY
)REPLICATION=OFF;

csql> show create table tbl2;
-- 스펙에 이 출력 예시가 없음. 다음 중 무엇이 맞는가?
-- (A) 'CREATE TABLE [tbl2] (...) REPLICATION OFF'
-- (B) 'CREATE TABLE [tbl2] (...)'   -- OFF는 아예 생략
```

예제 설명: 이는 사소해 보이지만, 스키마를 텍스트로 덤프해서 버전관리(git)에 올려두고 diff로 관리하는 실무 워크플로우에서는 중요하다. REPLICATION 절이 ON/OFF 여부에 따라 출력되었다 안 되었다 하면, 스키마 덤프 diff에 예측 불가능한 변화가 생겨 리뷰가 어려워진다.

제안: OFF인 경우의 `show create table` 출력 예시를 예시 8 옆에 나란히 추가하고, ON/OFF 모두 절이 항상 명시적으로 출력되는 것으로 통일할 것을 권장한다.

### 리뷰 18

**[심각도: 사소] §4-2의 "기존의 연산 결과와 동일한 경우 PK, UK를 비교하기위한 예시만 표기한다"는 문장이 무엇을 뜻하는지 불명확하다**

대상: §4-2

문제 설명: 원문: "기존의 연산 결과와 동일한 경우 PK, UK를 비교하기위한 예시만 표기한다." 이 문장은 주어와 목적어 관계가 불분명해 여러 번 읽어도 정확한 의미를 파악하기 어렵다. "이 절 이하의 예시들은 PK를 RK로 쓰는 경우와 UK를 RK로 쓰는 경우를 나란히 비교하기 위한 것이며, 결과가 기존(PK 단독 시절)과 같은 항목은 예시를 생략한다"는 뜻으로 추정되지만 이는 추정일 뿐이다.

구체 예제:
```
(해당 문장 자체가 SQL이 아니라 스펙 서술문이므로, 예제 대신 재구성 문안을 제시함)

추정 원의도: "이하 예시는 PK를 RK로 쓸 때와 UK를 RK로 쓸 때의 제약을 비교해서 보여준다.
             둘의 동작이 동일한 항목은 중복 표기를 생략한다."
```

예제 설명: 이 문장 하나 때문에 §4-2 전체 예시(11~16)가 "왜 이 항목은 있고 저 항목은 없는지"를 이해하는 기준이 흐릿해진다. 예를 들어 "UK를 복제키로 사용하는 경우"에는 PK 추가(예시 14) 예시만 있고 PK 삭제 예시는 없는데, 이게 "PK가 원래 없으므로 삭제할 PK 자체가 없어서"인지 "PK 사용 시와 결과가 같아서 생략한 것"인지 이 서술만으로는 구분할 수 없다.

제안: 해당 문장을 "이하 예시는 PK를 RK로 사용하는 경우와 UK를 RK로 사용하는 경우의 제약을 비교한다. 두 경우 결과가 동일한 항목은 예시를 생략했다"처럼 명확한 문장으로 재작성한다.

### 리뷰 19

**[심각도: 사소] 예시 23에도 트레일링 콤마 문법 오류가 반복된다**

대상: §5-2, 예시 23

문제 설명: 리뷰 10에서 지적한 것과 동일한 패턴의 오류다.
```
csql> CREATE TABLE new_orders(
    order_id INT PRIMARY KEY,
);
```
컬럼이 `order_id INT PRIMARY KEY` 하나뿐인데 뒤에 콤마가 붙어 있다.

구체 예제:
```sql
-- 원문
csql> CREATE TABLE new_orders(
    order_id INT PRIMARY KEY,
);

-- 수정본
csql> CREATE TABLE new_orders(
    order_id INT PRIMARY KEY
);
```

예제 설명: 리뷰 10과 합쳐서 보면 이 문서 전체에서 "컬럼이 하나뿐인 CREATE TABLE" 패턴에서 트레일링 콤마가 체계적으로 빠짐없이 등장한다(예시 2, 23). 이는 문서 작성 시 여러 예제를 복사해서 컬럼을 하나씩 지우는 식으로 편집하다가 뒤 콤마를 지우지 않은 것으로 추정되며, 검수 과정에서 실행 검증을 거치지 않았음을 시사한다.

제안: 리뷰 10의 제안과 동일하게, 전체 문서의 모든 SQL 예제를 csql로 실행 검증한다.

### 리뷰 20

**[심각도: 보통] 레거시 대량 테이블의 일괄 마이그레이션 절차나 도구가 스펙에 없어, §8에서 예고된 "구버전 dump는 전부 ON으로 로드된다" 상황에 대응할 방법이 막막하다**

대상: §3, §7, §8 (연결된 문제)

문제 설명: §8은 "하위 버전에서 unload 한 데이터 파일 ... load 시 모두 복제 테이블로 설정된다"고 명시한다. 이는 PK가 없는 레거시 테이블이 수백 개 있는 오래된 CUBRID 인스턴스를 업그레이드하는 경우, 그 수백 개 테이블 전부가 REPLICATION=ON으로 로드된다는 뜻이다. §3/§7에 따르면 이후 HA 전환을 시도하면 이 테이블들이 전부 "RK 없음" 위반으로 걸려 HA 기동이 실패한다. 그런데 스펙 어디에도 "이 수백 개 테이블을 어떻게 일괄로 REPLICATION=OFF로 바꾸거나 RK를 부여할 것인가"에 대한 도구나 절차 언급이 없다. §7이 제시하는 해법은 "싱글모드에서 ALTER TABLE... 후 HA 재시작"뿐인데, 이를 테이블 하나하나에 대해 수동으로 반복해야 하는지, 스크립트/유틸리티가 제공되는지 알 수 없다.

구체 예제:
```sql
-- 업그레이드 직후, HA 전환을 시도했다가 실패
$ cubrid hb start mydb
ERROR: 137 tables violate replication constraints (missing replication key)

-- 스펙이 제시하는 유일한 해법: 싱글 모드로 돌아가 테이블마다 수동 처리
csql> ALTER TABLE legacy_tbl_001 REPLICATION=OFF;
csql> ALTER TABLE legacy_tbl_002 ADD CONSTRAINT PRIMARY KEY(id);
-- ... 137개 테이블 각각에 대해 반복 ...
```

예제 설명: 137개(가상의 수치)에 달하는 테이블을 하나씩 검토해서 "이건 진짜 복제해야 하는 테이블인가, PK를 추가할 수 있는가, 아니면 복제 제외로 돌려도 되는가"를 판단하는 작업은 순수 수작업으로는 실수하기 쉽고 시간도 오래 걸린다. 특히 이 판단은 순수 기술적 문제가 아니라 "이 테이블 데이터가 페일오버 후에도 필요한가"라는 비즈니스적 판단을 요구하므로, 최소한 후보 목록을 자동으로 뽑아주는 조회 SQL이나 유틸리티 정도는 스펙에 포함되어야 실용적이다.

제안: HA 전환 전에 "RK 없는 복제 대상 테이블 목록"을 한 번에 뽑아볼 수 있는 조회 뷰나 유틸리티(예: `SELECT class_name FROM db_class WHERE replication='ON' AND <RK 없음>` 형태)를 스펙에 포함시키고, 업그레이드 가이드 문서에서 이 조회 결과를 기반으로 한 일괄 처리 워크플로우를 안내한다.
