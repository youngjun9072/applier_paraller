# CUBRID HA 복제 개선 스펙 리뷰 — PM(10년차) 관점 · 2차 라운드

## 2차 라운드 개요

1차 리뷰(20건)는 RK 선택 규칙의 불확정성, 기존 고객 마이그레이션 경로 부재, §2-1 기본값
정책, 멀티 슬레이브 확장성 등 스펙의 핵심 축을 직접 다뤘다. 이번 2차에서는 1차와
최종보고서(40개 통합 이슈)가 다루지 않은 **주변부 상호작용**을 훑었다 — 스펙이 침묵하고
있는 인접 기능(권한, TDE, REUSE_OID, collation), 기존 CUBRID HA 운영 메커니즘과의 관계,
그리고 "스펙 문서 자체의 완성도"(지원 정책, 버전 식별, 국제화, QA 커버리지 도구로서의
결정 테이블 부재) 쪽으로 시선을 옮겼다. PM 직무 관점(요구사항 완전성·하위 호환·릴리스
리스크·문서 품질·라이선스/지원 정책)과 아키텍처 관점(설계 철학·장기 유지보수·확장성)을
유지하되, 이미 1차·최종보고서가 짚은 지점(RK 비결정성, FK 부모 사후 OFF 전환, RK 조회
불가, §7 파일리스트, §8/§9 모순, trailing comma, fail-late 구조, 다중 절 ALTER 원자성,
업그레이드 경로 부재, 파티션/트리거/시퀀스, 멀티 슬레이브, 에러코드 등)의 재탕은
배제했다.

## 리뷰 21

**[심각도: 중요] REPLICATION 옵션 변경 권한을 누가 갖는지 스펙이 규정하지 않음**

**대상**: §2-2 ALTER 옵션 및 SQL 추가, 스펙 전체(권한/보안 절 부재)

**문제 설명**: 스펙은 `ALTER TABLE ... REPLICATION={ON|OFF}`를 누가 실행할 수 있는지
전혀 언급하지 않는다. 예시 8·9의 `db_class` 결과를 보면 `owner_name`이 테이블마다
다를 수 있음을 알 수 있다 — 즉 CUBRID는 DBA 계정 외에도 스키마 소유자가 자신의
테이블을 독립적으로 관리할 수 있는 구조다. 그런데 REPLICATION 옵션은 단순히 "내
테이블의 속성"이 아니라 **HA 클러스터 전체의 데이터 일관성**에 영향을 주는 설정이다.
§5에 따르면 어떤 테이블을 OFF로 바꾸는 순간, 그 테이블을 참조하는 다른 스키마 소유자의
FK 테이블까지 연쇄적으로 영향을 받을 수 있다(리뷰 대상은 아니지만 최종보고서 C-2가
이미 "부모를 사후에 OFF로 바꾸는 경로가 막혀있지 않다"고 지적했다 — 이 리뷰는 그
*기술적 차단 여부*가 아니라 **누가 그 위험한 조작을 실행할 권한이 있어야 하는지**를
묻는 것으로, 별개의 문제다). 일반적으로 DBMS는 클러스터 전역에 영향을 주는 설정(예:
Oracle의 SUPPLEMENTAL LOGGING, PostgreSQL의 REPLICA IDENTITY도 테이블 소유자 또는
슈퍼유저 권한을 요구)에 대해 명시적인 권한 요구사항을 문서화한다. 이 스펙은 그런
서술이 아예 없다.

**구체 예제**:
```sql
-- 스키마 소유자 alice가 자신의 테이블만 관리한다고 가정
-- (DBA가 아니라 GRANT로 CREATE/ALTER 권한만 받은 일반 사용자)

-- bob 소유의 orders가 alice 소유의 customers를 참조
CREATE TABLE alice.customers(
    customer_id INT PRIMARY KEY,
    country     INT
);

CREATE TABLE bob.orders(
    order_id    INT PRIMARY KEY,
    customer_id INT,
    CONSTRAINT fk_customer_id FOREIGN KEY (customer_id)
        REFERENCES alice.customers(customer_id)
);
-- 둘 다 REPLICATION=ON (기본값)

-- alice가 자신의 테이블에 대한 권한만으로 이 문장을 실행할 수 있는가?
ALTER TABLE alice.customers REPLICATION = OFF;
-- 성공한다면: bob이 전혀 모르는 사이 bob의 orders가 참조하는 부모 데이터가
-- 슬레이브에서 사라지는 상황이 alice의 단독 권한 행사만으로 발생한다.
```

**예제 설명**: alice는 자신의 스키마 안에서 권한상 아무 문제 없는 작업을 했을 뿐이지만,
그 결과는 alice의 스키마 밖에 있는 bob의 테이블과 클러스터 전체의 HA 안전성에 영향을
준다. 이런 "권한 범위(스키마 단위)"와 "영향 범위(클러스터 전체)"의 불일치는 다중
사용자 환경에서 실제로 사고를 만드는 전형적인 패턴이다. 스펙이 이 옵션을 DBA
전용으로 제한할지, 아니면 소유자에게도 허용하되 FK로 얽힌 타 스키마 소유자에게
경고/승인 절차를 요구할지에 대한 정책적 결정을 전혀 하지 않았다.

**제안**: REPLICATION 옵션 변경에 필요한 최소 권한(DBA 전용인지, ALTER 권한 보유자
전체인지)을 명시하고, 만약 소유자에게도 허용한다면 다른 스키마의 FK가 걸린 테이블을
OFF로 전환할 때 별도의 경고 또는 상위 권한 확인 절차를 둘지 결정해 문서화해야 한다.

## 리뷰 22

**[심각도: 중요] TDE(투명한 데이터 암호화) 적용 테이블의 REPLICATION 정책과 키 배포 절차가 언급되지 않음**

**대상**: §2-3 예시 9 (`db_class`의 `tde_algorithm` 필드), 스펙 전체

**문제 설명**: 스펙이 직접 제시한 예시 9의 `db_class` 조회 결과에는 `tde_algorithm :
'NONE'`이라는 필드가 이미 존재한다. 즉 CUBRID는 테이블 단위로 TDE(디스크에 저장된
데이터를 암호화해 파일을 탈취당해도 내용을 읽을 수 없게 하는 기능)를 적용할 수 있는
제품이라는 뜻이다. 그런데 이번 스펙은 REPLICATION=ON인 TDE 적용 테이블이 슬레이브로
복제될 때 (1) 슬레이브 쪽에도 동일한 암호화 키가 미리 배포되어 있어야 하는지, (2)
복제 로그(마스터→슬레이브로 전달되는 논리적 변경분, 이 스펙의 문맥상 "행 단위 변경
내용"을 담는 것으로 보인다) 자체는 평문으로 네트워크를 타는지 암호화된 채로 타는지,
(3) 만약 평문으로 전달된다면 "디스크 파일은 암호화되어 있지만 복제 스트림은 평문"이라는
보안 구멍이 생기는지에 대해 한 마디도 하지 않는다. TDE는 규제 산업(금융·의료·공공)
고객이 컴플라이언스 요건 때문에 도입하는 기능인데, 그 보호 범위에 "복제 경로"가
포함되는지 빠지는지는 감사(audit) 대응 시 반드시 확인받는 항목이다.

**구체 예제**:
```sql
-- TDE가 적용된 개인정보 테이블 (예시 9의 형식을 빌림)
CREATE TABLE customers_secure(
    customer_id INT PRIMARY KEY,
    ssn         VARCHAR(20)
) ENCRYPT=AES REPLICATION=ON;   -- 문법은 가정, TDE 활성화 구문은 CUBRID 문서 별도 참조

-- 질문1: 슬레이브 서버가 이 테이블 파일을 복호화하려면 마스터와 같은 키를
--        어떻게 안전하게 전달받는가? (수동 키 파일 복사? 자동 배포?)
-- 질문2: applylogdb가 이 테이블에 INSERT를 적용할 때, 복제 로그 안의 ssn 값은
--        평문인가 암호문인가? 평문이라면 네트워크 스니핑 시 TDE 보호가 무의미해진다.
```

**예제 설명**: TDE는 "디스크에 놓인 파일"을 보호하는 기술이지 "네트워크로 오가는
데이터"를 보호하는 기술이 아니다. 이 스펙에서 새로 생기는 마스터→슬레이브 복제
경로가 TDE의 보호 범위 밖에 있다면, 고객은 "TDE를 켰으니 개인정보가 안전하다"고
믿었다가 실제로는 복제 스트림을 통해 평문이 오가는 상황을 뒤늦게 발견할 수 있다.
이는 기능 결함이 아니라 **문서가 보안 경계(security boundary)를 명시하지 않은
결함**이다.

**제안**: TDE 적용 테이블의 REPLICATION 정책, 슬레이브 측 키 배포/동기화 절차, 복제
전송 구간의 암호화 여부를 별도 절로 명시해야 한다. 만약 이번 릴리스 범위 밖이라면
"TDE 테이블과 REPLICATION 기능의 상호작용은 검증되지 않았다"는 최소한의 경고 문구를
릴리스 노트에 넣어야 한다.

## 리뷰 23

**[심각도: 보통] REUSE_OID 클래스가 스펙 예시에 등장하지만 RK·FK 규칙과의 상호작용은 언급되지 않음**

**대상**: §2-3 예시 8·9 (`REUSE_OID`, `is_reuse_oid_class: 'YES'`)

**문제 설명**: 예시 8의 `show create table` 결과 문자열에는 `REUSE_OID`라는 키워드가
그대로 포함되어 있고, 예시 9의 `db_class` 결과에도 `is_reuse_oid_class: 'YES'`라는
필드가 나온다(REUSE_OID는 삭제된 행이 쓰던 내부 객체 식별자(OID)를 새 행에 재사용하도록
허용하는 테이블 옵션이다). 스펙 작성자가 이 두 예시를 만들 때 REUSE_OID가 켜진
테이블을 굳이 골라 예시로 쓴 것인지, 아니면 우연히 기본값이 그렇게 나온 것인지는
알 수 없지만, 어느 쪽이든 REUSE_OID와 이번 스펙이 도입하는 RK/FK 규칙이 서로 영향을
주는지 안 주는지는 스펙 어디에도 설명이 없다. RK는 PK/UK라는 "값 기반" 식별자이고
OID는 "내부 위치 기반" 식별자라 원칙적으로는 독립적이어야 하지만, REUSE_OID 테이블은
일반적으로 외래키의 참조 대상이 되는 데 있어 별도 제약을 받는 경우가 있는 것으로
알려져 있다. 이번 스펙이 추가하는 "FK 참조 대상은 반드시 복제 대상이어야 한다"(§5)는
규칙이 REUSE_OID 테이블에 그대로 적용되는지, 아니면 REUSE_OID 자체의 기존 제약과
충돌하는 조합이 있는지 검토한 흔적이 스펙에 없다.

**구체 예제**:
```sql
-- REUSE_OID가 걸린 테이블을 FK의 부모로 사용하려는 시도
CREATE TABLE lookup_codes(
    code_id INT PRIMARY KEY,
    label   VARCHAR(50)
) REUSE_OID REPLICATION = ON;

CREATE TABLE orders(
    order_id INT PRIMARY KEY,
    code_id  INT,
    CONSTRAINT fk_code FOREIGN KEY (code_id) REFERENCES lookup_codes(code_id)
);
-- 질문: REUSE_OID 테이블을 FK 부모로 쓰는 것 자체가 기존 CUBRID 제약과 무관하게
--       가능한가? 가능하다면 이번 스펙의 RK 규칙(§1, §4-2)이 REUSE_OID 테이블에서도
--       동일하게 적용되는지, 예외가 있는지 스펙에 없다.
```

**예제 설명**: 이 예제는 정답을 요구하는 것이 아니라, 스펙이 스스로 제시한 예시
안에 등장하는 옵션(REUSE_OID)에 대해 스펙 본문이 아무 언급도 하지 않는다는 사실
자체를 지적하는 것이다. 리뷰어가 "REUSE_OID와 무관하다"고 확신할 수 없는 이유는,
스펙이 그 무관함을 스스로 진술하지 않았기 때문이다.

**제안**: REUSE_OID 테이블에 대해 RK 선택 규칙과 FK 참조 규칙이 예외 없이 동일하게
적용됨을 한 문장으로 명시하거나, 예시 8·9에서 굳이 REUSE_OID를 노출한 이유(단순
기본값인지 의도적 예시인지)를 각주로 밝혀야 한다.

## 리뷰 24

**[심각도: 중요] Collation 차이에 따라 RK 값의 동일성 판정이 마스터와 슬레이브에서 달라질 위험이 검증되지 않음**

**대상**: §1 (RK는 PK 또는 UK), §2-3 예시 8 (`COLLATE utf8_bin`)

**문제 설명**: 예시 8의 `show create table` 결과에는 `COLLATE utf8_bin`이라는 절이
포함되어 있다. Collation(콜레이션)은 문자열을 비교·정렬할 때 어떤 규칙을 쓸지
정하는 속성으로, 예를 들어 대소문자를 구분하는 `_bin` 계열과 구분하지 않는 계열이
있다. RK가 문자열 타입의 UK 컬럼일 경우, 이 컬럼에 걸린 collation이 대소문자를
구분하지 않는 종류라면 `'ABC'`와 `'abc'`가 "같은 값"으로 취급되어 UNIQUE 제약
자체가 이 둘을 중복으로 판정한다. 문제는 마스터에서 발생한 UPDATE/DELETE의 복제
로그가 슬레이브에 도착했을 때, applylogdb(복제 로그를 슬레이브에 실제로 반영하는
모듈로 추정)가 대상 행을 찾기 위해 RK 값을 비교하는 과정에서 이 collation 규칙을
동일하게 적용하는지, 아니면 단순 바이트 비교를 하는지에 대한 서술이 스펙에 없다는
점이다. 만약 둘의 비교 방식이 어긋나면, 대소문자만 다른 두 값을 서로 다른 행으로
착각해 엉뚱한 행을 갱신하거나, 반대로 원래 갱신해야 할 행을 찾지 못하는 상황이
이론적으로 가능하다.

**구체 예제**:
```sql
-- 대소문자를 구분하지 않는 collation을 UK 컬럼에 적용했다고 가정
CREATE TABLE accounts(
    account_code VARCHAR(20) NOT NULL UNIQUE COLLATE utf8_en_ci,  -- 대소문자 무시 예시
    balance      DECIMAL(15,2)
);
-- RK = account_code (PK 없으므로 UK가 선택됨)

-- 마스터에서 대소문자만 바꾸는 UPDATE
UPDATE accounts SET account_code = 'abc001' WHERE account_code = 'ABC001';
-- collation 규칙상 'ABC001'과 'abc001'은 "같은 값"이므로 UNIQUE 제약 위반이 아니라
-- 정상적으로 값이 바뀐 것으로 마스터는 처리한다.

-- 이 UPDATE의 복제 로그가 슬레이브에 도착했을 때, applylogdb는
-- "RK = 'ABC001'인 행을 찾아 account_code를 'abc001'로 바꿔라"라는 지시를
-- 어떤 비교 규칙으로 수행하는가? 스펙에 규정이 없다.
```

**예제 설명**: 이 시나리오는 극단적으로 드문 경우처럼 보일 수 있지만, RK가 사용자가
직접 지정할 수 없고(§4-2) 엔진이 UK 중 하나를 자동으로 고르는 구조이기 때문에,
사용자가 의도하지 않았는데도 대소문자 비구분 collation이 걸린 컬럼이 RK로 선택될
가능성을 배제할 수 없다. 이 스펙은 "어떤 컬럼이 RK가 되는가"만 다루고, "그 컬럼의
값을 슬레이브에서 어떻게 비교하는가"는 다루지 않는다.

**제안**: RK로 선택된 컬럼의 collation이 복제 로그 적용(applylogdb) 시 어떤 비교
규칙을 따르는지 명시하고, 최소한 대소문자 비구분 등 non-binary collation이 걸린
UK가 RK로 선택될 수 있는지, 선택될 수 있다면 QA 테스트 시나리오에 이를 포함해야
한다는 점을 문서에 남겨야 한다.

## 리뷰 25

**[심각도: 중요] 기존 HA 설정 파일 레벨의 복제 대상 제어 메커니즘과 이번 SQL 옵션의 관계가 불명확함**

**대상**: 컨셉 전체(§1, §2), 기존 CUBRID HA 운영 체계와의 정합성

**문제 설명**: 이번 스펙은 "테이블을 복제 대상에서 제외한다"는 개념을 처음 도입하는
것처럼 서술되어 있다. 그런데 CUBRID HA는 이번 스펙 이전부터 이미 클러스터 전체
운영을 위한 각종 설정 파일(`cubrid_ha.conf` 등)을 통해 복제와 관련된 여러 동작을
제어해왔다. 만약 기존 설정 파일 레벨에 "특정 데이터베이스 전체를 복제 대상에서
제외" 또는 "특정 조건의 테이블을 복제 로그 적용에서 건너뛴다" 같은 유사한 취지의
설정 항목이 이미 존재한다면(있는지 여부 자체가 이 스펙만 봐서는 알 수 없다), 이번에
새로 추가되는 테이블 단위 SQL 옵션(REPLICATION)과 그 기존 설정이 동시에 걸렸을 때
어느 쪽이 우선하는지, 서로 모순되는 값을 가지면 어떻게 되는지에 대한 규정이 전혀
없다. 반대로 그런 기존 메커니즘이 없었다면, "왜 지금까지는 테이블 단위로 복제를
끄는 수단이 전혀 없었는지, 이번에 SQL 레벨로 들어오면서 기존 설정 체계와 계층
구조상 어디에 위치하는지"에 대한 설명이 있어야 운영자가 두 체계를 헷갈리지 않는다.

**구체 예제**:
```
[운영 시나리오 - 두 제어축이 동시에 존재할 가능성]
cubrid_ha.conf (또는 유사 설정 파일)에 데이터베이스 단위 또는
테이블 목록 단위로 복제 관련 설정이 있다고 가정한다.

1. DBA가 SQL로 지정: ALTER TABLE orders REPLICATION = ON;
2. 그러나 설정 파일 쪽에는 (과거 운영 관행으로) orders가
   복제 제외 목록에 이미 등록되어 있다고 가정.
3. 이 상태에서 orders는 실제로 복제되는가, 안 되는가?
   SQL과 설정 파일 중 어느 쪽이 우선인지 스펙에 없다.
```

**예제 설명**: 이 리뷰의 핵심은 "이런 충돌이 실제로 존재한다"고 단정하는 것이 아니라,
**스펙이 기존 HA 설정 체계와 이번 신규 기능의 관계를 한 줄도 언급하지 않는다는 사실
자체**가 문서 완전성의 공백이라는 점이다. 신규 기능이 기존 시스템 위에 얹히는
경우, "기존에 이런 걸 하던 방법이 있었다면 그것과 어떻게 다른가/무엇을 대체하는가"를
설명하지 않으면, 오랜 기간 CUBRID HA를 운영해 온 고객일수록 두 체계를 혼동할
위험이 크다.

**제안**: 기존 HA 설정 파일 체계에 테이블/데이터베이스 단위로 복제를 제어하는 기존
수단이 있는지 여부를 명시하고, 있다면 이번 SQL 옵션과의 우선순위·이관(migration)
계획을, 없다면 "이번이 최초의 테이블 단위 제어 수단"이라는 점을 배경 설명에
명시해야 한다.

## 리뷰 26

**[심각도: 중요] 이 변경이 해결하려는 버그가 유지보수 중인 하위 버전에도 백포트되는지 지원 정책이 불명확함**

**대상**: 작업지시 배경, 스펙 전체(지원 정책 서술 부재)

**문제 설명**: 이 스펙의 출발점은 "PK 컬럼 속성을 변경하면 복제가 누락되고
fail_count가 증가하며 마스터/슬레이브 데이터가 불일치한다"는 **실제로 발생하는
데이터 정합성 버그**다. 이런 종류의 버그는 통상 신규 기능(feature)이 아니라 결함
수정(defect fix)에 가깝게 취급되어, 벤더가 이미 출시해 유지보수 중인 이전 릴리스
라인(LTS 성격의 브랜치)에도 패치를 백포트하는 것이 일반적이다. 그런데 이번 스펙은
`REPLICATION` 옵션과 RK 자동 선택이라는 **새로운 DDL 문법과 카탈로그 스키마 변경을
동반하는 상당히 큰 규모의 기능**으로 설계되어 있다. 이 정도 규모의 변경을 기존
유지보수 브랜치에 그대로 백포트하는 것은 현실적으로 부담이 크다(카탈로그 스키마
변경은 보통 메이저/마이너 버전에서만 허용되고 패치 버전에서는 지양된다). 결국
"이미 이 버그로 데이터 불일치를 겪고 있는, 그러나 최신 메이저 버전으로 당장
업그레이드할 수 없는 기존 고객"은 이번 스펙이 반영되어도 구제받지 못할 가능성이
있는데, 스펙에는 이에 대한 언급이 전혀 없다.

**구체 예제**:
```
[가상 시나리오]
고객 B는 CUBRID N.0 버전(현재 유지보수 지원 중, 그러나 이번 스펙이 반영되는
버전은 N+1.0으로 예정)을 프로덕션에서 운영 중이며, 배경에 서술된 버그
(PK 컬럼 변경 시 복제 누락 + fail_count 증가)를 실제로 겪고 있다.

Q. 고객 B는 N.0 버전의 패치 릴리스(N.0.x)로 이 문제의 완화판을 받을 수 있는가,
   아니면 반드시 N+1.0으로 메이저 업그레이드해야만 하는가?
Q. 메이저 업그레이드가 강제된다면, 이는 "버그 수정"이 아니라 사실상
   "유상/대규모 업그레이드 강제"로 고객에게 받아들여질 수 있다.
```

**예제 설명**: PM 관점에서 이는 지원 정책과 릴리스 노트 작성에 직접 영향을 준다.
버그로 이미 피해를 겪고 있는 고객에게 "다음 메이저 버전으로 오세요"라고 답하는
것과 "현재 버전의 패치로 완화됩니다"라고 답하는 것은 고객 만족도와 지원 티켓
처리 방침이 완전히 다르다. 이 스펙은 기능 설계에만 집중되어 있고, 이 기능이
버그 수정과 신규 기능 중 어느 카테고리로 취급되어 어떤 배포 채널로 나가는지에
대한 판단이 빠져 있다.

**제안**: 이 변경을 (a) 기존 유지보수 브랜치에 축소판으로 백포트할지, (b) 차기
메이저 버전 전용 기능으로만 제공할지 결정하고, 릴리스 노트/지원 정책 문서에
명시해야 한다. 백포트하지 않기로 한다면 그 근거(카탈로그 스키마 변경 규모 등)를
남겨 향후 유사 사례의 선례로 삼아야 한다.

## 리뷰 27

**[심각도: 중요] 이 기능 전체를 일시적으로 끌 수 있는 호환 모드(킬스위치)가 없어, 문제 발생 시 롤백 경로가 바이너리 다운그레이드뿐임**

**대상**: 컨셉 전체, 릴리스 리스크

**문제 설명**: 이번 스펙은 HA 모드 기동 자체를 막는 강한 제약(§4-1, §7)을 도입한다.
이는 데이터 정합성을 지키기 위해 필요한 설계지만, 동시에 "새 버전을 배포했더니
RK 자동 선택 로직에 미처 발견하지 못한 버그가 있어서, 원래 정상적으로 RK를 가지고
있던 테이블까지 HA 기동을 거부당하는" 것과 같은 **이 기능 자체의 결함으로 인한
2차 장애** 가능성을 배제할 수 없다. 이런 상황에서 운영자가 취할 수 있는 완화
조치가 스펙에 전혀 없다. 예를 들어 "이번 릴리스에서 도입된 RK 강제 검증을
한시적으로 비활성화하고 기존(느슨한) 동작으로 되돌리는 시스템 파라미터"
같은 것이 없다면, 배포 직후 예상치 못한 문제가 터졌을 때 유일한 대응은 이전
바이너리로 다운그레이드하는 것뿐이다. 그러나 카탈로그 스키마가 이미 새 버전
형식으로 바뀐 뒤라면(§8이 시사하듯 `db_class`에 `replication` 컬럼이 새로
추가된다) 단순 바이너리 롤백조차 카탈로그 비호환으로 실패할 수 있다 — 이 경우
사실상 롤백 경로 자체가 없다.

**구체 예제**:
```
[릴리스 직후 장애 대응 시나리오]
1. 신버전 배포. RK 자동 선택 로직에 미발견 버그 존재
   (예: 특정 조건에서 정상 PK가 있는데도 "RK 없음"으로 오판)
2. 다수의 정상 테이블이 HA 기동 거부 대상이 됨 (오탐, false positive)
3. 운영자가 원하는 것: "이번 검증 로직을 잠시 끄고 예전처럼 HA를 띄운 뒤,
   버그 수정 패치를 기다리고 싶다"
4. 그런 스위치가 스펙에 없다 -> 선택지는 (a) 전체 서비스 중단 유지,
   (b) 바이너리 다운그레이드 시도(카탈로그 스키마 비호환으로 실패 가능) 뿐
```

**예제 설명**: 이는 이번 기능의 정상 동작을 전제로 한 시나리오들과 달리, "기능
자체에 버그가 있을 때의 대응 수단"을 묻는 것이다. 데이터 정합성을 지키기 위한
엄격한 게이트(§7)를 도입할수록, 그 게이트 자체가 오작동했을 때의 탈출구를 함께
설계해두는 것이 릴리스 리스크 관리의 기본이다.

**제안**: RK 검증을 일시적으로 완화하는 시스템 파라미터(예: 경고만 내고 기동은
허용하는 모드)를 최소 한 릴리스 주기 동안 제공하는 것을 검토하고, 카탈로그 스키마
변경이 바이너리 다운그레이드와 호환되는지(또는 다운그레이드 절차 자체를 별도로
제공하는지) 스펙 또는 운영 매뉴얼에 명시해야 한다.

## 리뷰 28

**[심각도: 보통] 스펙에 QA가 조합 커버리지를 검증할 수 있는 결정 테이블(decision table)이 없음**

**대상**: 스펙 전체의 문서 형식

**문제 설명**: 이 스펙에는 (모드: 싱글/HA) × (RK 존재 여부: PK/UK 1개/UK 여러개/없음)
× (REPLICATION: ON/OFF) × (FK 유무: 있음/없음, 참조 대상의 REPLICATION 상태) 라는
최소 4개 축이 서로 얽혀 있고, 축마다 갈래가 2~4개씩이라 조합의 수가 상당히 많다.
스펙은 이 조합들 중 일부만 예시(예시 1~23)로 골라 보여줄 뿐, "이 조합들을 다
합치면 전체 조합 공간을 얼마나 커버하는가"를 보여주는 표(행렬)를 제공하지 않는다.
QA 입장에서 테스트케이스를 설계할 때 "예시로 주어지지 않은 조합"이 의도적으로
생략된 것인지(그 조합은 자명해서), 아니면 검토 자체가 누락된 것인지 스펙만
봐서는 구분할 수 없다. 이는 개별 조합 하나하나의 결함(1차 리뷰와 최종보고서가
이미 다수 지적)과는 별개로, "테스트 설계의 출발점이 되어야 할 문서가 애초에
조합적으로 완전한지"를 스스로 증명하지 못한다는 **문서 형식 자체의 결함**이다.

**구체 예제**:
```
[결정 테이블이 있었다면 이렇게 보여야 한다 - 현재 스펙에는 없음]

모드   | RK 상태        | REPLICATION | FK 부모 상태     | 예상 결과      | 스펙 근거
-------|---------------|-------------|-----------------|---------------|----------
싱글   | 없음          | ON(기본)    | -               | 생성 OK       | 예시2
싱글   | 없음          | OFF         | -               | 생성 OK       | 예시4
HA     | 없음          | ON(기본)    | -               | 생성 ERROR    | 예시10
HA     | 없음          | OFF         | -               | 생성 OK(?)    | ??? <- 스펙에 명시적 예시 없음
HA     | PK 1개        | ON          | 부모 ON         | 생성 OK       | 예시17
HA     | PK 1개        | ON          | 부모 OFF        | ERROR(?)      | 예시18(생성 시점) / ALTER 시점은 불명(리뷰9, 최종 C-2)
...    | (조합이 이 뒤로도 다수 이어짐, 스펙에는 표 없음)
```

**예제 설명**: 위 표에서 "HA 모드 + RK 없음 + REPLICATION=OFF로 새 테이블을
생성하는" 조합은 논리적으로는 §1("복제 제외 테이블은 복제 키의 유무와 상관없이
생성 가능")에 따라 OK일 것으로 추정되지만, §4-1(HA 모드 CREATE TABLE 절)의
예시는 전부 REPLICATION=ON 케이스만 다뤄 이 조합에 대한 명시적 예시가 없다.
결정 테이블이 있었다면 이런 "논리적으로 추정만 가능하고 예시로 확인되지 않는
칸"이 한눈에 드러났을 것이다.

**제안**: 스펙 부록으로 위와 같은 조합 결정 테이블을 추가하고, 스펙 본문의 예시
번호를 각 칸에 연결해 "이 조합은 예시 N으로 커버됨"과 "이 조합은 예시가 없어
별도 확인 필요"를 구분해야 한다. 이는 QA 테스트케이스 설계의 1차 자료로 그대로
쓰일 수 있다.

## 리뷰 29

**[심각도: 보통] SHOW CREATE TABLE 출력 포맷 변경이 하위 생태계(드라이버·백업·스키마 비교 도구)에 미치는 영향 범위가 정의되지 않음**

**대상**: §2-3 예시 8

**문제 설명**: 예시 8은 `show create table`의 결과 문자열에 `REPLICATION ON`이라는
새 절이 추가된 모습을 보여준다. 이 출력 문자열은 CUBRID 내부에서만 쓰이는 것이
아니라, JDBC/ODBC 드라이버의 메타데이터 API, 서드파티 백업 도구, 스키마 비교
도구(두 데이터베이스의 스키마 차이를 `SHOW CREATE TABLE` 출력을 문자열째로 비교해
찾아내는 방식이 실무에서 흔히 쓰인다), 마이그레이션 도구가 그대로 파싱하거나
저장해두는 대상이다. 이번 스펙은 이 출력 포맷이 바뀐다는 사실만 예시로 보여줄 뿐,
이 변경이 영향을 주는 하위 생태계의 범위(어떤 드라이버 버전부터 새 절을 인식하는지,
구버전 드라이버가 이 새 절을 만나면 무시하는지 파싱 에러를 내는지, 스키마 비교
도구가 "REPLICATION ON"이라는 새 절 때문에 기존에는 "동일 스키마"로 판정하던
두 테이블을 이제 "다른 스키마"로 오판하지는 않는지)를 전혀 검토하지 않는다.

**구체 예제**:
```
[스키마 비교 도구를 사용하는 운영 시나리오]
운영팀이 매주 "스테이징 DB의 SHOW CREATE TABLE 결과"와
"운영 DB의 SHOW CREATE TABLE 결과"를 문자열로 비교해 스키마 드리프트를
감지하는 자동화 스크립트를 오래전부터 사용 중이라고 가정한다.

- 신버전 배포 후: 두 환경의 실제 스키마는 동일한데,
  한쪽만 먼저 업그레이드되어 REPLICATION 절이 붙었다 안 붙었다 하면
  이 스크립트는 "스키마가 달라졌다"는 거짓 경보(false positive)를
  대량으로 쏟아낼 수 있다.
- 이런 도구 생태계 영향에 대한 언급이 스펙에 없어, 운영팀은 배포
  당일에야 이 문제를 처음 발견하게 된다.
```

**예제 설명**: 이 시나리오는 REPLICATION 기능 자체의 정합성과는 무관하게, "출력
텍스트가 바뀐다"는 부수효과만으로 기존에 잘 동작하던 운영 자동화가 깨질 수 있음을
보여준다. 신규 기능이 기존 텍스트 기반 인터페이스에 새 절을 추가할 때는 그 자체가
하위 호환성 이슈로 취급되어야 한다.

**제안**: `SHOW CREATE TABLE` 출력 포맷 변경을 릴리스 노트의 "인터페이스 변경"
항목으로 명시하고, 이 출력을 파싱·저장하는 주요 도구(자체 제공 드라이버, 백업
유틸리티 등)의 호환성을 사전에 점검했는지 여부를 문서에 남겨야 한다.

## 리뷰 30

**[심각도: 사소] "복제 키 후보" 등 신규 용어의 공식 영문 역어가 없어 국제화(번역) 시 문서마다 다르게 옮겨질 위험**

**대상**: 스펙 전체 용어 체계

**문제 설명**: 이 스펙은 전량 한국어로 작성되었고, "복제 키(RK)"라는 약어는 스펙
스스로 "Replication Key"라는 영문 풀네임을 병기해 정의했다. 그러나 "복제 키 후보",
"복제 대상 테이블", "복제 제외 테이블"처럼 스펙 안에서 반복적으로 쓰이는 다른
핵심 용어들은 영문 대응어가 병기되어 있지 않다. CUBRID는 국내뿐 아니라 해외
사용자를 대상으로 하는 영문 레퍼런스 매뉴얼을 함께 제공하는 제품이므로, 이
스펙이 최종적으로 영문 매뉴얼로 옮겨지는 과정에서 "복제 키 후보"가 "replication
key candidate"로 번역될지 "eligible replication key"로 번역될지, "복제 제외
테이블"이 "non-replicated table"인지 "replication-excluded table"인지가 번역자
재량에 맡겨진다. 용어가 문서마다 다르게 번역되면 한국어 원문 스펙과 영문 매뉴얼
사이에서 같은 개념을 가리키는 검색어가 달라져, 다국어 지원팀이 응대할 때 혼선이
생긴다.

**구체 예제**:
```
[스펙에 병기된 용어]         [스펙에 병기되지 않은 용어]
복제 키 -> RK -> Replication Key   복제 키 후보 -> ??? (영문 미정)
                                     복제 대상 테이블 -> ??? (영문 미정)
                                     복제 제외 테이블 -> ??? (영문 미정)

-- 번역자 A: "복제 키 후보" -> "replication key candidate"
-- 번역자 B: "복제 키 후보" -> "eligible key"
-- 두 문서가 동시에 배포되면 영문 사용자는 두 용어가 같은 개념인지 확신할 수 없다.
```

**예제 설명**: 이 문제는 지금 당장 기능 동작에는 영향을 주지 않지만, 스펙이
매뉴얼화·번역되는 다음 단계에서 반드시 드러난다. 핵심 용어의 영문 대응어를 스펙
단계에서 미리 확정해두면, 번역 단계에서 발생하는 재작업과 용어 불일치를 예방할
수 있다.

**제안**: §1 용어 정의 부분(1차 리뷰 6, 최종보고서 T-6이 이미 요구한 "용어집"과
결합해)에 "복제 키 후보(RK candidate)", "복제 대상 테이블(replicated table)",
"복제 제외 테이블(non-replicated table)"처럼 신규 용어마다 공식 영문 역어를
병기해야 한다.

## 조사 종료 선언

2차 라운드에서는 작업지시가 예시한 미개척 영역(소유자 권한, TDE, collation, REUSE_OID,
기존 HA 설정 메커니즘과의 관계, 지원 정책/백포트, 킬스위치, QA 결정 테이블, 생태계
호환성, 국제화)을 각각 실제 스펙 본문의 문구·예시와 대조해가며 훑었다. 이 중
파티션·트리거·시퀀스·에러코드 체계·성능/락·멀티 슬레이브·§8/§9 모순·RK 비결정성·FK
사후 OFF 전환처럼 1차 리뷰 또는 최종보고서가 이미 상당한 합의도로 다룬 영역은
재탕을 피하기 위해 제외했다. 나머지 후보 중 (1) 라이선스/에디션별 적용 범위는
CUBRID의 현재 에디션 체계에 대한 확증 없는 추측이 되어 근거 없이 단정하는 위험이
있어 지원 정책(리뷰 26)으로 대체·흡수했고, (2) DR/RPO 관점의 REPLICATION=OFF 리스크는
결국 "OFF 테이블에 데이터가 없다"는 이미 최종보고서가 여러 각도(C-2, DBA 고유 unloaddb
포함 여부)로 다룬 지점의 변주에 가까워 제외했다. 남은 10건은 모두 스펙 본문의 구체
문구(예시 8·9의 TDE/REUSE_OID/collation 필드, §2-2의 권한 공백, §5의 소유자 교차 영향,
배경 서술의 버그 수정 성격)에 직접 근거해 작성했으며, 추측성 트집이나 1차와 동일 취지의
재포장은 배제했다. 이 관점에서 스펙 본문에 명시적 근거가 있는 추가 지적은 여기까지이며,
더 조사할 가치가 남아 있다면 그것은 CUBRID 내부 구현 코드(카탈로그·복제 모듈)를
직접 열어봐야 확인 가능한 영역(예: 실제 REUSE_OID/FK 제약, 실제 HA 설정 파일 스키마)
이지 PM 관점의 문서 검토만으로는 더 이상 확장하기 어렵다고 판단한다.
