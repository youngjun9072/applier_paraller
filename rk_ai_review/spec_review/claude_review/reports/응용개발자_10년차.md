# CUBRID HA 복제 개선 스펙 리뷰 — 응용 개발자(10년차) 관점

## 리뷰어 소개

10년째 백엔드 서비스를 만들면서 ORM(JPA/Hibernate, TypeORM 등)과 스키마 마이그레이션 도구(Flyway, Liquibase)로 여러 DBMS(MySQL, PostgreSQL, Oracle)를 운영해 온 응용 개발자다. DB 엔진 내부 구현보다는 "이 스펙대로 배포 파이프라인을 짜고 운영했을 때 어디서 사고가 나는가"를 본다. FK로 테이블 관계를 모델링하고, CI/CD로 DDL을 자동 배포하고, failover 이후에도 애플리케이션 코드가 예외 없이 돌아가야 하는 입장에서 이 스펙을 읽었다.

## 총평

이번 스펙은 "PK 없는 테이블 때문에 복제가 깨진다"는 실제 장애를 막기 위해 PostgreSQL의 REPLICA IDENTITY 개념을 절반쯤 들여온 것으로 보인다. 방향 자체는 합리적이지만, 정작 응용 개발자가 매일 부딪히는 세 가지 지점 — ① 개발(싱글)과 운영(HA) 환경의 스키마 검증 규칙이 다르다는 점, ② 복제 키가 사용자가 아니라 엔진이 조용히 자동으로 고른다는 점, ③ FK와 REPLICATION 옵션의 상호작용에서 대칭적으로 다뤄야 할 케이스가 스펙에 빠져 있다는 점 — 이 충분히 다뤄지지 않았다. 이 상태로 나가면 "로컬/스테이징에서는 멀쩡히 배포됐는데 운영 HA에만 올리면 실패한다"는 유형의 장애가 반복될 가능성이 높다. 아래 20개 리뷰는 심각도 순으로 이 문제들을 구체적인 SQL 시나리오와 함께 짚는다.

### 리뷰 1

**[심각도: 치명] RK(복제 키) 자동 선택 규칙이 비결정적이라 ORM 마이그레이션 도구와 정면으로 충돌한다**

**대상**: §1 제약 사항 — "UK가 여러개 존재한다면 큐브리드 엔진에 의해 이 중 하나가 선택된다(ex. 테이블내에 명시된 순서 중 가장 빠른 순서)"

**문제 설명**: "테이블 내 명시된 순서"라는 기준은 사람이 CREATE TABLE 문을 손으로 짤 때는 안정적이지만, ORM 마이그레이션 도구(Flyway, Liquibase, Django migrations 등)가 만들어내는 DDL 순서는 매 배포마다 바뀔 수 있다. 특히 "컬럼/제약을 재정렬해서 새 테이블을 만들고 데이터를 옮긴 뒤 이름을 바꾸는" 패턴(예: SQLite에서 흔하고, 다른 DBMS에서도 컬럼 순서 변경 시 종종 쓰임)을 쓰면 UK의 상대적 순서가 배포할 때마다 달라질 수 있다. 즉 어떤 UK가 RK가 될지는 "테이블 정의를 누가 어떤 도구로 재생성했는가"에 따라 갈리는, 사용자가 통제할 수 없는 값이 된다. 복제 키(Replication Key, RK)는 마스터-슬레이브 간 어느 행을 UPDATE/DELETE할지 찾는 식별자이므로, 이게 배포마다 바뀌면 이전 배포에서 만든 복제 로그와 다음 배포 이후의 복제 로그가 서로 다른 키 기준으로 행을 찾게 되는 위험이 있다.

**구체 예제**:
```sql
-- 마이그레이션 v1 (Flyway V1__init.sql)
CREATE TABLE members(
    id        INT,
    email     VARCHAR(100) NOT NULL UNIQUE,   -- UK #1 (email)
    phone     VARCHAR(20)  NOT NULL UNIQUE     -- UK #2 (phone)
);
-- 이 시점 RK = email (테이블 내 첫 번째 UK)

-- 마이그레이션 v7 (Flyway V7__rebuild_members.sql)
-- ORM/마이그레이션 도구가 "phone 컬럼에 인덱스 힌트를 바꾸기 위해" 테이블을 재생성
CREATE TABLE members_new(
    id        INT,
    phone     VARCHAR(20)  NOT NULL UNIQUE,    -- UK #1 (phone) ← 순서가 바뀜
    email     VARCHAR(100) NOT NULL UNIQUE     -- UK #2 (email)
);
INSERT INTO members_new SELECT id, phone, email FROM members;
DROP TABLE members;
RENAME TABLE members_new TO members;
-- 이 시점 RK = phone (테이블 내 첫 번째 UK) — 배포 담당자는 이 변화를 인지하지 못함
```

**예제 설명**: v1에서는 `email`이 RK였는데, v7에서 컬럼 선언 순서만 바뀐 재생성 DDL을 실행하면 RK가 `phone`으로 조용히 바뀐다. 애플리케이션 코드나 마이그레이션 스크립트 어디에도 "RK가 바뀐다"는 명시적 신호가 없으므로, 배포자는 이 변화를 전혀 모른 채 넘어간다. 만약 이 시점에 슬레이브 쪽에 아직 반영되지 않은 복제 로그가 남아 있다면(applylogdb가 지연 중이라면), 예전 RK(email) 기준으로 만들어진 로그 레코드와 이후 RK(phone) 기준 레코드가 뒤섞여 처리될 가능성을 배제할 수 없다 — 이는 바로 이 스펙이 해결하려는 원래 장애(PK 컬럼 속성 변경 시 복제 누락)와 본질적으로 같은 유형의 문제다.

**제안**: RK 자동 선택 기준에서 "선언 순서"를 배제하고, 제약조건 생성 시각(카탈로그 상 내부 OID)이나 최초 지정된 RK를 명시적으로 카탈로그에 고정값으로 저장해, 이후 테이블이 재생성되어도 동일 논리 키가 유지되도록 하거나, 최소한 `show create table` 결과에 "현재 RK로 선택된 제약조건 이름"을 명시해 배포 파이프라인이 diff로 검증할 수 있게 해야 한다.

### 리뷰 2

**[심각도: 치명] 복제 키 후보가 하나뿐인 상태에서 다른 후보로 전환하는 "멀티플 ALTER"(예시 7, 13) 동안의 원자성이 스펙에 없다**

**대상**: §4-2 예시 7, 예시 13 — `ALTER TABLE tbl DROP CONSTRAINT PRIMARY KEY, ADD CONSTRAINT PRIMARY KEY(a);`

**문제 설명**: 스펙은 "복제키 후보가 1개인 경우" DROP만 하면 에러가 나고, "DROP + ADD를 한 문장에 묶으면" OK라고 설명한다. 이 자체는 배경(§1)에 나온 원래 장애 — "HA 실행 중 PK 컬럼 속성을 변경하면 복제가 누락된다" — 를 그대로 재현할 수 있는 위험 지점이다. 하나의 ALTER 문 안에서 DROP과 ADD가 원자적으로 처리되어 카탈로그 갱신과 복제 로그 기록이 한 트랜잭션으로 묶이는지, 아니면 내부적으로는 여전히 두 단계로 나뉘어 그 사이에 짧게라도 "RK 없음" 상태가 존재하는지 스펙에 아무 설명이 없다. 이 원자성 보장이 없다면, 원래 이 스펙이 고치려던 버그가 "여러 UK를 두고 순서대로 교체"하는 시나리오에서 그대로 재발할 수 있다.

**구체 예제**:
```sql
-- 초기 상태: RK 후보가 PK 하나뿐
CREATE TABLE tbl(
    a INT PRIMARY KEY,
    b INT
) REPLICATION = ON;

-- HA 운영 중 애플리케이션 배포 스크립트가 실행하는 마이그레이션
ALTER TABLE tbl DROP CONSTRAINT PRIMARY KEY,
                ADD CONSTRAINT PRIMARY KEY(b);
-- 이 한 문장이 실행되는 동안, 동시에 다른 커넥션에서
UPDATE tbl SET b = 999 WHERE a = 1;   -- 이 UPDATE는 복제 로그에 어떤 키로 기록되는가?
```

**예제 설명**: `ALTER TABLE ... DROP ..., ADD ...`가 실행되는 그 찰나에 동시성 트랜잭션이 UPDATE를 날리면, 그 UPDATE의 복제 로그가 "옛 PK(a) 기준"으로 남는지 "새 PK(b) 기준"으로 남는지, 혹은 그 경계에서 RK가 일시적으로 없어져 로그가 아예 누락되는지 스펙만으로는 판단할 수 없다. 응용 개발자가 무중단 배포 스크립트를 짤 때 "이 DDL은 트래픽이 있는 상태에서 실행해도 안전한가"를 판단할 근거가 필요한데, 지금 스펙은 그 근거를 주지 않는다.

**제안**: DROP+ADD 복합 ALTER의 원자성(카탈로그 잠금 범위, 그 사이 발생하는 DML의 복제 로그 처리 방식)을 명시적으로 기술하고, 가능하면 동시 트랜잭션 관점의 격리 수준도 문서화해야 한다.

### 리뷰 3

**[심각도: 치명] 개발/스테이징(싱글 모드)에서 통과된 스키마가 운영(HA)에서만 실패하는 구조적 간극**

**대상**: §3 Single 제약사항 — "싱글 모드에서 생성된 복제 키가 없는 테이블은 HA모드 전환 시 복제 키를 추가하거나 복제 제외 테이블로 변경할 수 있어야한다" / §4-1 예시 10

**문제 설명**: 대부분의 조직은 로컬/개발/스테이징을 싱글 모드(비용 절감)로 두고 운영만 HA로 돌린다. 스펙에 따르면 RK 없는 테이블 생성이 싱글 모드에서는 100% 허용되고, HA 모드(또는 HA로의 전환)에서만 에러가 난다. 즉 "테이블 생성이 성공했다"는 사실이 스테이징 환경에서는 아무 의미가 없고, 운영에 배포하는 순간 처음으로 검증이 이뤄진다. CI 파이프라인이 스테이징(싱글) DB에 마이그레이션을 적용해 그린 사인을 받아도, 그 그린 사인은 운영 배포 성공을 전혀 보장하지 않는다.

**구체 예제**:
```sql
-- 1) 로컬/스테이징(싱글 모드) — 개발자가 실행, 성공
CREATE TABLE event_log(
    event_id  INT,
    payload   VARCHAR(1000)
);  -- PK/UK 없음. 싱글 모드라 에러 없이 생성됨.

-- CI: 스테이징 DB에 위 DDL 적용 → 통과 → 배포 승인

-- 2) 운영(HA 모드) 배포 파이프라인이 동일 DDL 실행
CREATE TABLE event_log(
    event_id  INT,
    payload   VARCHAR(1000)
) REPLICATION = ON;  -- 생략해도 기본값 ON
-- ERROR: 복제 키가 없는 복제 테이블은 HA 모드에서 생성 불가 (예시 10과 동일 패턴)
```

**예제 설명**: 개발자 입장에서는 스테이징에서 성공한 DDL이 운영에서 실패하는 것 자체가 "환경 패리티(parity) 붕괴"다. 특히 REPLICATION 옵션을 생략하면 기본값이 ON이므로(§2-1), 개발자가 이 스펙의 존재를 모르고 습관대로 PK 없는 임시 로그성 테이블을 만들면 운영 배포 시점에야 처음 에러를 본다. 배포 자동화 도구(Flyway 등)는 이 시점에 마이그레이션을 "부분 적용" 상태로 남길 수 있어 롤백 처리가 추가로 필요해진다.

**제안**: 싱글 모드에서도 "HA 전환 시 이 테이블은 실패할 것"이라는 경고(WARNING)를 CREATE TABLE 시점에 즉시 출력하거나, `lint` 성격의 검사 도구를 제공해 스테이징 단계에서 미리 걸러낼 수 있게 해야 한다. 최소한 문서에 "싱글에서 통과 ≠ 운영에서 통과"라는 경고 문구를 명확히 넣어야 한다.

### 리뷰 4

**[심각도: 치명] REPLICATION=ON → OFF 전환 시 그 테이블을 참조하는 FK 자식에 대한 검증이 스펙에 없다 (§5의 대칭 케이스 누락)**

**대상**: §5 외래키, §2-2 ALTER 옵션

**문제 설명**: §5는 "FK를 새로 만들 때 참조 테이블이 복제 제외면 에러(예시 18, 22-23)"를 다룬다. 그런데 정반대 방향 — 이미 복제 대상인 부모 테이블(customers)을 FK 자식(orders)이 참조하고 있는 상태에서, 부모 테이블에 `ALTER TABLE customers REPLICATION=OFF`를 실행하면 어떻게 되는지는 스펙 어디에도 없다. §2-2는 "HA 모드에서는 복제 제외 테이블이 복제 테이블로 변경될 수 없다"만 규정할 뿐, "복제 테이블을 복제 제외로 바꿀 때 그것을 참조하는 자식이 있는지"는 검사 대상으로 언급되지 않는다. 이대로면 orders-customers 예시(예시 17)를 만든 뒤 customers만 나중에 OFF로 바꿔서 image.png가 보여주는 정확히 그 장애 상황(FK 참조 대상이 슬레이브에 없음)을 사용자가 스스로 만들어낼 수 있다.

**구체 예제**:
```sql
-- 예시 17 기준 상태 (HA 운영 중)
CREATE TABLE customers(customer_id INT PRIMARY KEY, country INT);           -- REPLICATION=ON(기본)
CREATE TABLE orders(
    order_id INT PRIMARY KEY,
    customer_id INT,
    CONSTRAINT fk_customer_id FOREIGN KEY (customer_id) REFERENCES customers(customer_id)
);  -- REPLICATION=ON(기본)

-- 이후 어떤 개발자가 "customers는 마스터 데이터라 복제 안 해도 된다"고 오판하고 실행
ALTER TABLE customers REPLICATION = OFF;
-- 결과가 OK인가 ERROR인가? 스펙에 명시 없음.

-- 만약 OK로 통과된다면, 이후 failover 발생 시
-- 슬레이브에는 orders만 있고 customers 데이터는 없음 → image.png와 동일한 장애 재현
```

**예제 설명**: §5는 "FK를 만드는 시점"의 검증만 다루지만, 실제 운영에서는 이미 존재하는 부모 테이블의 REPLICATION 속성을 나중에 바꾸는 경우가 더 흔하다(예: 스토리지 절감을 위해 뒤늦게 특정 테이블을 복제 제외로 전환하는 리팩터링). 이 경로가 막혀 있지 않다면 스펙이 막으려는 문제 상황을 스펙 스스로 허용하는 셈이 된다.

**제안**: §2-2에 "복제 대상 테이블을 복제 제외로 변경하려 할 때, 이를 참조하는 FK 자식 테이블이 하나라도 복제 대상이면 ERROR"라는 규칙을 명시적으로 추가해야 한다. §5의 "참조 테이블은 복제 대상이어야 한다"는 제약이 CREATE/ALTER 양방향에서 항상 성립하도록 대칭적으로 정의해야 한다.

### 리뷰 5

**[심각도: 치명] 뷰(VIEW)의 조용한 데이터 불일치 — 애플리케이션에는 에러 없이 틀린 결과만 반환된다**

**대상**: §6 뷰(VIEW) — "복제 제외 테이블이 뷰에 포함되어 있을 경우 ... 수행의 결과는 두 노드가 일치하지 않는다. 이 부분에 대해 큐브리드 복제 모듈은 책임지지 않는다."

**문제 설명**: 이 조항이 응용 개발자에게 특히 위험한 이유는, 뷰 SELECT는 실행 자체가 실패하지 않고 "그럴듯하지만 틀린" 결과를 리턴한다는 점이다. FK 위반이나 DDL 에러는 최소한 예외를 던지므로 애플리케이션 로직이 감지하고 대응할 수 있지만, JOIN 결과가 일부 누락되는 것은 SQL 레벨에서 아무 에러도 나지 않는다. 리포팅/대시보드 기능이 failover 이후 슬레이브를 바라보게 되면, 사용자에게 조용히 축소된 숫자(예: 매출 합계, 주문 건수)를 보여주게 된다.

**구체 예제**:
```sql
-- 마스터에서
CREATE TABLE customers(customer_id INT PRIMARY KEY, country INT) REPLICATION = OFF;  -- 의도적으로 복제 제외
CREATE TABLE orders(order_id INT PRIMARY KEY, customer_id INT, amount INT);          -- REPLICATION=ON

CREATE VIEW order_summary AS
SELECT o.order_id, o.amount, c.country
FROM orders o LEFT JOIN customers c ON o.customer_id = c.customer_id;

-- 애플리케이션 코드 (의사코드)
-- 평상시(마스터 조회): 200건, country 값 정상 채워짐
rows = db.query("SELECT * FROM order_summary");  // 정상 동작, 에러 없음

-- Failover 발생 후 (슬레이브로 자동 라우팅)
rows = db.query("SELECT * FROM order_summary");
// 여전히 에러 없이 200건 반환되지만 c.country 는 전부 NULL
// (customers 데이터가 슬레이브에 없으므로 LEFT JOIN 결과가 비게 됨)
```

**예제 설명**: 애플리케이션은 쿼리가 예외 없이 성공했으므로 정상 응답이라 판단하고 그대로 사용자에게 국가별 통계를 내려준다. 하지만 country 값이 전부 NULL이 되어 집계 로직(GROUP BY country)이 마스터일 때와 슬레이브일 때 완전히 다른 결과를 낸다. 이건 버그 리포트로 이어져도 재현이 어렵다 — "가끔 통계가 이상하다"는 증상만 남고, 원인(failover 전후 차이)을 애플리케이션 로그만으로는 추적하기 힘들다.

**제안**: 최소한 뷰 정의 시점에 복제 제외 테이블이 포함되어 있으면 `CREATE VIEW`에 경고를 내거나, `show create view` 조회 시 "이 뷰는 REPLICATION=OFF 테이블을 참조합니다"라는 메타 정보를 노출해 애플리케이션/모니터링 쪽에서 사전에 인지할 수 있는 최소한의 장치가 필요하다. "책임지지 않는다"로 끝내기엔 실사용 임팩트가 크다.

### 리뷰 6

**[심각도: 보통] §2-1 예시 2의 SQL이 문법 오류로, 예제 자체가 실행 불가능하다**

**대상**: §2-1 예시 2 — `CREATE TABLE repl_table_without_rk(a INT,);`

**문제 설명**: 컬럼 목록 마지막에 콤마(trailing comma)가 붙어 있다. 이는 CUBRID를 포함해 대부분의 SQL 방언에서 문법 오류(syntax error)로 처리된다(문법 오류란 SQL 파서가 명령문의 구조 자체를 이해하지 못해 실행 전에 거부하는 것을 말한다). 이 예제는 "PK/UK가 없는 테이블도 REPLICATION=ON으로 만들 수 있다(싱글 모드 한정)"는 핵심 케이스를 보여주려는 것인데, 정작 그 SQL 자체가 실행되지 않으면 독자(응용 개발자)가 실습하다가 "trailing comma 때문에 나는 에러"와 "RK 관련 규칙 때문에 나는 에러"를 혼동하게 된다.

**구체 예제**:
```sql
-- 스펙 원문 그대로 실행
CREATE TABLE repl_table_without_rk(
    a INT,
);
-- 기대: 성공(싱글 모드, RK 없이 생성)
-- 실제: 대부분 SQL 파서에서 syntax error (trailing comma)
```

**예제 설명**: 이 예제가 통과하려면 콤마를 제거해야 한다. 사소해 보이지만, 스펙 문서는 곧 QA 테스트케이스와 사용자 매뉴얼의 원본이 되므로, 문법 오류가 있는 예제가 그대로 배포 문서에 실리면 실습하는 개발자마다 동일한 삽질을 반복하게 된다.

**제안**: `CREATE TABLE repl_table_without_rk(a INT);`로 수정하고, 전체 문서의 모든 CREATE/ALTER 예제를 한 번 실제 파서에 돌려 문법 검증을 거쳐야 한다(예시 4, 23의 `a INT,)` 등 동일 패턴이 다른 곳에도 있는지 재점검 필요).

### 리뷰 7

**[심각도: 중요] §7 "에러와 함께 파일 리스트를 출력한다"는 문구가 자동화 파이프라인이 소비할 수 있는 형태인지 불명확하다**

**대상**: §7 HA 전환

**문제 설명**: HA 전환 스크립트는 대개 사람이 콘솔에 붙어서 실행하는 게 아니라 배포 자동화 도구(Ansible, 사내 배포 스크립트 등)가 실행한다. 이런 파이프라인은 "실패했다"는 사실뿐 아니라 "무엇 때문에 실패했는지"를 구조화된 형태(JSON, 특정 exit code, 고정 포맷의 텍스트)로 받아야 후속 처리(자동 롤백, 알림에 실패 원인 포함)를 할 수 있다. 스펙의 "에러와 함께 파일 리스트를 출력한다"는 표현은 사람이 읽는 로그 메시지 수준의 서술이라, 이걸 파싱해서 자동화하려는 개발자 입장에서는 출력 포맷·exit code·항목별 실패 사유 구분 방식이 전혀 정의되지 않은 상태다.

**구체 예제**:
```bash
#!/bin/bash
# 배포 자동화 스크립트 일부 (의사코드)
cubrid hb start mydb
if [ $? -ne 0 ]; then
    # 여기서 "복제키 없음"과 "FK 참조 테이블 복제 제외"를 구분해서
    # 서로 다른 후속 조치(자동 RK 추가 vs REPLICATION 옵션 조정)를 하고 싶은데
    # 실패 원인을 프로그램적으로 구분할 방법이 스펙에 없다.
    parse_error_and_decide_action "$(cat cubrid_hb.log)"   # 이 함수를 어떻게 짜야 하나?
fi
```

**예제 설명**: 두 가지 제약 위반(복제키 없음 / FK 참조 테이블이 복제 대상 아님)은 원인이 다르고 권장 조치도 다르다(전자는 UK 추가, 후자는 참조 테이블 REPLICATION 조정). 자동화 스크립트가 이 둘을 구분해서 다른 조치를 취하려면 최소한 에러 코드나 구조화된 필드가 필요한데, 지금 스펙은 "파일 리스트를 출력한다"는 사람 친화적 설명에 머물러 있다.

**제안**: 위반 유형별 에러 코드(예: `ER_HA_NO_RK`, `ER_HA_FK_REF_NOT_REPLICATED`)와 위반 테이블/제약 이름을 포함한 구조화된 출력(JSON 또는 파싱 가능한 고정 필드 포맷)을 exit code와 함께 문서화해야 한다.

### 리뷰 8

**[심각도: 중요] FK 참조 테이블 강제 복제 규칙이 "의도적으로 복제 제외하고 싶은 부모 테이블" 설계를 원천 차단한다**

**대상**: §5 외래키 — "외래키 테이블에서 참조하는 모든 테이블은 복제 대상이여야 한다"

**문제 설명**: 실무에서는 FK로 참조되는 테이블 중 일부를 의도적으로 복제 제외하고 싶은 경우가 있다. 대표적으로 감사 로그성 참조 테이블, 대용량이지만 슬레이브에서는 조회하지 않는 마스터 전용 캐시 테이블 등이다. 이 스펙대로면 "FK로 참조되는 테이블"은 예외 없이 전부 복제 대상이어야 하므로, FK를 걸었다는 이유만으로 그 부모 테이블의 스토리지/대역폭 비용이 강제로 슬레이브 수만큼 배가된다. 이는 FK를 쓸지 말지, 혹은 FK 대신 애플리케이션 레벨 참조 무결성(느슨한 결합)을 쓸지에 대한 설계 판단에 영향을 준다 — 즉 순수히 데이터 무결성 목적으로 FK를 걸고 싶어도 복제 정책 때문에 못 거는 상황이 생긴다.

**구체 예제**:
```sql
-- 의도: audit_events는 매우 커서 슬레이브에 복제하고 싶지 않지만,
-- orders.created_by_event_id가 audit_events를 참조해 무결성을 보장하고 싶음
CREATE TABLE audit_events(
    event_id INT PRIMARY KEY,
    payload  VARCHAR(4000)
) REPLICATION = OFF;   -- 스토리지 절감 목적

CREATE TABLE orders(
    order_id INT PRIMARY KEY,
    created_by_event_id INT,
    CONSTRAINT fk_evt FOREIGN KEY (created_by_event_id) REFERENCES audit_events(event_id)
);
-- ERROR (§5 규칙에 의해 무조건 막힘)

-- 결과적으로 개발자는 무결성 보장을 포기하고 FK 없이 애플리케이션에서만 검증하게 됨
```

**예제 설명**: FK는 데이터베이스가 무결성을 보장해주는 핵심 도구인데, 이 스펙은 "복제하고 싶지 않은 테이블은 FK로 참조당할 수 없다"는 결합을 강제한다. 그 결과 개발자는 무결성(FK 사용)과 비용(복제 제외) 중 하나를 포기해야 하는 이분법에 놓인다.

**제안**: 최소한 "참조 무결성은 마스터에서만 강제하고, 슬레이브 조회 시 이 FK 관계는 보장되지 않는다"는 명시적 옵션(예: `REFERENCES ... NOT ENFORCED ON SLAVE` 류)을 검토하거나, 왜 이 결합이 필수인지(복제 로그 적용 순서 보장 등 엔진 내부 이유가 있다면) 근거를 문서에 남겨야 설계자들이 트레이드오프를 이해하고 받아들일 수 있다.

### 리뷰 9

**[심각도: 중요] 마이그레이션 도구가 여러 DDL을 순차 실행하는 도중 실패했을 때, 마이그레이션 이력 테이블과 실제 스키마 상태가 어긋날 위험**

**대상**: §4 HA 제약사항, §4-1 예시 10, §7

**문제 설명**: Flyway/Liquibase 같은 도구는 하나의 마이그레이션 파일 안에 여러 DDL 문을 순서대로 실행하고, 전부 성공해야 그 마이그레이션을 "적용됨"으로 이력 테이블(`flyway_schema_history` 등)에 기록한다. HA 운영 중 특정 DDL(예: RK 없는 테이블 생성, 또는 마지막 RK 후보 DROP)이 중간에 실패하면, 그 앞의 DDL들은 이미 실행되어 슬레이브까지 복제된 상태(§4 "마스터에서 수행된 DDL은 모두 슬레이브로 복제된다")이지만 마이그레이션 전체는 실패로 기록된다. CUBRID DDL이 트랜잭션으로 묶여 롤백되는지, 아니면 각 DDL이 즉시 커밋(auto-commit) 방식이라 부분 적용 상태가 남는지 스펙에 없다.

**구체 예제**:
```sql
-- 마이그레이션 파일 V12__add_tables.sql (Flyway가 순차 실행)
CREATE TABLE promo_codes(code VARCHAR(20) PRIMARY KEY, discount INT) REPLICATION = ON;  -- (1) 성공, 슬레이브로 복제됨
ALTER TABLE orders ADD COLUMN promo_code VARCHAR(20);                                    -- (2) 성공
CREATE TABLE temp_batch(id INT) REPLICATION = ON;                                        -- (3) ERROR: RK 없음 (예시 10)

-- Flyway는 V12 전체를 실패로 기록하고 "failed migration"으로 표시
-- 하지만 (1),(2)는 이미 마스터/슬레이브 모두 적용된 상태
-- 다음 배포 시 V12를 수정해 재실행하면 (1)의 CREATE TABLE이 "이미 존재함" 에러로 다시 실패
```

**예제 설명**: DDL이 개별 커밋된다면, 마이그레이션 도구가 관리하는 "적용 여부" 상태와 실제 DB 상태가 어긋나는 흔한 함정에 빠진다. 이는 CUBRID만의 문제가 아니라 DDL을 트랜잭션으로 묶기 어려운 DBMS 전반의 문제이지만, 이번 스펙이 "HA 모드에서 새로운 실패 지점(RK 없음, FK 참조 위반)"을 추가하는 만큼, 그 실패가 마이그레이션 파이프라인에 미치는 영향을 문서에서 명시적으로 다뤄야 한다.

**제안**: HA 모드에서 CREATE/ALTER TABLE의 DDL 트랜잭션 원자성 여부(부분 실패 시 앞선 DDL도 롤백되는지)를 명시하고, 마이그레이션 도구 사용 가이드(재실행 시 안전한 패턴, `IF NOT EXISTS` 활용 권장 등)를 부록으로 제공해야 한다.

### 리뷰 10

**[심각도: 보통] §4-2 "다른 복제키 후보가 함께 존재한다면 모든 DDL은 허용된다(단, 기존의 제약사항은 유지된다)"의 "기존의 제약사항"이 정의되지 않았다**

**대상**: §4-2 첫 문단

**문제 설명**: 이 문장은 복제키 후보가 2개 이상일 때는 규칙이 느슨해진다는 뜻인데, 괄호 안의 "기존의 제약사항은 유지된다"가 무엇을 가리키는지 본문에 정의가 없다. HA 이전부터 있던 일반적인 제약(예: "하나의 테이블에 PK는 하나만 존재 가능")을 말하는 것인지, 아니면 §4-2에서 나열하는 개별 규칙(DROP PK 금지 등)이 후보가 여럿이어도 부분적으로 유지된다는 뜻인지 모호하다. 이는 응용 개발자가 "UK를 두 개 만들어두면 뭐든 자유롭게 ALTER해도 되는구나"라고 오해할 위험을 만든다.

**구체 예제**:
```sql
CREATE TABLE tbl(
    a INT PRIMARY KEY,
    b INT NOT NULL UNIQUE   -- RK 후보 2개 (a=PK, b=UK)
) REPLICATION = ON;

-- "복제키 후보가 여럿이면 모든 DDL 허용"이라는 문장만 보면 아래도 될 것 같지만...
ALTER TABLE tbl DROP PRIMARY KEY;   -- OK? 후보가 b(UK) 하나로 줄어드는 이 순간은 안전한가?
ALTER TABLE tbl DROP COLUMN a;      -- PK 컬럼 자체를 지우는 것도 허용되는가?
```

**예제 설명**: "후보가 여럿이면 모든 DDL 허용"이라는 문장만 읽으면 위 두 ALTER 모두 문제없어 보이지만, 실행 결과 남는 테이블은 UK 하나만 남은 "후보 1개" 상태가 된다. 이 전환 과정 자체가 안전한지(원자적으로 새 RK로 넘어가는지), 아니면 이 DDL 자체가 "후보가 1개로 줄어드는 시도"로 간주되어 별도 규칙이 적용되는지 스펙만으로는 알 수 없다.

**제안**: "기존의 제약사항"이 정확히 어떤 규칙 목록을 가리키는지 각주나 표로 명시하고, 후보가 2개에서 1개로 줄어드는 경계 케이스(위 예제)에 대한 명시적 규칙과 예제를 §4-2에 추가해야 한다.

### 리뷰 11

**[심각도: 중요] PostgreSQL REPLICA IDENTITY 대비 "사용자가 RK를 명시적으로 지정할 수 없다"는 점이 채용 취지를 절반만 살렸다**

**대상**: 작업지시 배경(§0), §1 제약 사항 전체 (컨셉 리뷰)

**문제 설명**: 이 스펙은 PostgreSQL의 REPLICA IDENTITY 컨셉을 일부 채용했다고 밝힌다. PostgreSQL의 REPLICA IDENTITY는 `DEFAULT`(PK 사용), `USING INDEX idx_name`(사용자가 지정한 특정 UNIQUE 인덱스를 명시적으로 키로 지정), `FULL`(전체 컬럼을 키로 사용), `NOTHING`(키 없음, UPDATE/DELETE 논리 복제 불가) 네 가지 모드를 제공하며, 핵심은 UK가 여러 개일 때 "DBA/개발자가 어떤 것을 쓸지 직접 고를 수 있다"는 점이다. 반면 이 스펙은 "엔진이 알아서 고른다(순서 기준)"만 있고, 사용자가 원하는 UK를 RK로 지정하는 문법(`USING INDEX` 상당 기능)이 없다. 이는 PostgreSQL 대비 사용자 통제권을 포기한 설계이며, 리뷰 1에서 지적한 비결정성 문제의 근본 원인이기도 하다. 응용 개발자 입장에서 "테이블에 UK가 두 개 있는데 성능/의미상 특정 UK를 RK로 쓰고 싶다"는 요구를 이 스펙은 아예 표현할 방법이 없다.

**구체 예제**:
```sql
-- PostgreSQL이었다면 가능한 것:
-- CREATE TABLE members(id INT, email VARCHAR(100) UNIQUE NOT NULL, ext_uid VARCHAR(64) UNIQUE NOT NULL);
-- ALTER TABLE members REPLICA IDENTITY USING INDEX members_email_key;  -- email을 명시적으로 키로 지정

-- 이 스펙(CUBRID)에서는:
CREATE TABLE members(
    id INT,
    email    VARCHAR(100) NOT NULL UNIQUE,   -- 이걸 RK로 쓰고 싶은데
    ext_uid  VARCHAR(64)  NOT NULL UNIQUE    -- 순서상 이게 먼저 선언되면 이게 RK가 됨
);
-- RK를 email로 강제 지정할 SQL 문법이 스펙에 없음
```

**예제 설명**: 외부 시스템 연동 키(`ext_uid`)보다 내부 검증이 끝난 `email`을 복제 키로 쓰고 싶어도, 이 스펙에는 그런 의사를 표현할 문법이 없다. 결국 컬럼 선언 순서를 바꾸는 식으로 "RK를 유도"해야 하는데, 이는 리뷰 1에서 지적했듯 매우 취약한 방법이다.

**제안**: `ALTER TABLE ... REPLICATION KEY USING (제약조건명)`류의 명시적 RK 지정 문법을 검토해, 최소한 "엔진 자동 선택"과 "사용자 명시 지정" 두 경로를 모두 열어두는 것이 PostgreSQL 컨셉을 채용한 취지에 더 부합한다.

### 리뷰 12

**[심각도: 중요] MySQL RBR / Oracle GoldenGate와 달리 "복제 키를 엔진이 조용히 자동 결정"하는 방식은 감사(audit) 관점에서 예측 가능성을 떨어뜨린다**

**대상**: 컨셉 전체(§1)

**문제 설명**: MySQL의 행 기반 복제(Row-Based Replication, RBR)는 PK가 없으면 성능은 느리지만 "전체 컬럼을 비교 기준으로 쓴다"는 단일하고 예측 가능한 규칙을 따른다. Oracle GoldenGate는 반대로 DBA가 명시적으로 어떤 컬럼 집합에 supplemental logging(복제를 위해 추가로 로그를 남기도록 지정하는 옵션)을 걸지 지정하며, 지정하지 않으면 명확히 에러를 낸다. 두 벤더 모두 "키가 무엇인지 항상 사람이 설명 가능한 규칙"을 따른다. 이 스펙처럼 "UK가 여러 개면 엔진이 알아서 고른다"는 방식은 두 벤더 어디에도 없는 독자 노선이며, 규제 산업(금융권 등)의 스키마 변경 리뷰 프로세스에서 "이 테이블의 복제 키가 무엇인지"를 리뷰어가 DDL 텍스트만 보고 판단할 수 없다는 감사 리스크를 만든다. 리뷰를 통과시키려면 리뷰어가 매번 엔진 내부 선택 규칙("선언 순서")까지 알아야 하는데, 이는 일반적인 코드/스키마 리뷰 프로세스에 맞지 않는 지식 요구다.

**구체 예제**:
```sql
-- 스키마 리뷰 PR에 올라온 DDL
CREATE TABLE payments(
    id            INT,
    txn_ref       VARCHAR(64)  NOT NULL UNIQUE,
    idempotency_key VARCHAR(64) NOT NULL UNIQUE
);
-- 리뷰어 질문: "이 테이블의 복제 키는 뭔가요?"
-- 정답: 두 UNIQUE 제약 중 "테이블 내 선언 순서가 빠른 것" = txn_ref
-- 하지만 리뷰어는 이 규칙을 몰라도 리뷰를 승인할 수 있고, 실제 결정은 배포 시점에 엔진이 함
```

**예제 설명**: 결제(payments) 같은 민감 테이블에서조차 "무엇이 복제 키인가"라는 질문에 DDL 텍스트만으로는 즉답할 수 없고 엔진 문서(선언 순서 규칙)를 따로 찾아봐야 한다. GoldenGate/RBR과 달리 이 스펙은 "명시성"을 포기한 대가로 감사 추적성을 낮췄다.

**제안**: 최소한 `show create table` 출력에 RK로 선택된 제약조건 이름을 항상 표기하도록 하고(현재 예시 8은 PK 하나뿐인 케이스만 보여줘 확인 불가), 스키마 리뷰 체크리스트에 "UK가 2개 이상이면 반드시 RK 확인 절차를 넣으라"는 가이드를 배포해야 한다.

### 리뷰 13

**[심각도: 보통] 멀티 슬레이브/체인 복제 환경에서 RK 계산이 어디서(마스터/각 슬레이브) 이뤄지는지 불명확하다**

**대상**: §1, §8 (확장성/아키텍처 관점)

**문제 설명**: 스펙은 단일 마스터-슬레이브 쌍을 전제로 서술되어 있고, CUBRID HA가 지원하는 멀티 슬레이브 또는 체인 복제(마스터 → 슬레이브1 → 슬레이브2) 구성에서 RK 선택이 어느 노드의 카탈로그를 기준으로 계산되는지 언급이 없다. RK가 "각 노드가 자신의 카탈로그를 보고 독립적으로 계산하는 값"이라면, DDL 복제 타이밍 차이(네트워크 지연, 적용 순서 차이)로 인해 특정 순간 슬레이브1과 슬레이브2가 서로 다른 RK를 사용하는 창이 생길 수 있다. 반대로 "마스터가 계산해서 복제 로그에 값 자체를 실어 보낸다"면 이 문제는 없지만, 그렇다면 그 사실이 §1 어딘가에 명시되어야 아키텍처 리뷰가 가능하다.

**구체 예제**:
```
[Master] --DDL(UK 2개 추가)--> [Slave1] --DDL 전달(체인)--> [Slave2]

t0: Master에서 ALTER TABLE tbl ADD CONSTRAINT UNIQUE(b); 실행 (UK 순서상 RK 후보가 a→b로 재계산될 수 있는 조건)
t1: Slave1이 DDL 수신, 카탈로그 갱신, RK 재계산 완료
t2: Slave2는 아직 DDL 미수신 (체인 복제 지연) — 이 사이 Slave1이 Master로 승격(failover)되면
    Slave2는 잠시 구 RK 기준으로 남아있는 상태에서 새 Master(구 Slave1)의 복제 로그를 받게 됨
```

**예제 설명**: 체인 복제와 failover가 겹치는 경계 조건에서, RK 재계산이 노드별로 독립적이라면 일시적으로 노드 간 RK 인식이 어긋나는 창이 생길 수 있다. 이는 흔치 않은 케이스지만, 멀티 슬레이브를 이미 지원하는 제품에 새 복제 키 체계를 얹는 것이므로 최소한 "RK는 마스터에서 결정되어 로그에 실려 전파된다"는 식의 명시적 아키텍처 선언이 필요하다.

**제안**: RK 계산 주체(마스터 vs 각 노드)를 명시하고, 멀티 슬레이브/체인 복제 구성에서의 동작을 최소 한 문단이라도 스펙에 추가해야 한다. 향후 이 기능 확장(예: 다중 마스터) 논의 때도 이 결정이 전제가 된다.

### 리뷰 14

**[심각도: 보통] 구버전 UNLOADDB 데이터를 신버전으로 승격시킬 때 "전부 복제 테이블"로 자동 지정되는 규칙이 HA 전환 실패를 유발할 수 있다**

**대상**: §8 UNLOADDB & LOADDB — "하위 버전에서 unload 한 데이터 파일에는 복제 여부를 저장하는 변수가 설정되어있지 않으므로 (싱글 모드에서) load 시 모두 복제 테이블로 설정된다"

**문제 설명**: 구버전에서 백업(unload)한 데이터를 신버전으로 복원(load)하면, RK 유무와 무관하게 전부 REPLICATION=ON(복제 테이블)으로 잡힌다. 만약 원본 데이터에 PK/UK가 없는 테이블이 섞여 있었다면(구버전 CUBRID는 PK 없는 테이블도 정상 운영 가능했으므로 실제로 흔했을 것), 신버전으로 옮긴 뒤 HA로 전환하려는 순간 §7의 검사에 걸려 전환이 막힌다. 이는 "DB 버전 업그레이드"라는, 응용 개발자가 배포 계획에 흔히 포함시키는 작업의 실패 지점이 하나 더 늘어난 것이다.

**구체 예제**:
```bash
# 구버전 CUBRID (RK 개념 없음, PK 없는 테이블 다수 존재)
$ unloaddb -o old_backup legacy_db

# 신버전으로 복원
$ loaddb -d new_db old_backup
# 스펙에 따라 legacy_db의 모든 테이블이 REPLICATION=ON 으로 로드됨
# (PK/UK 없는 테이블 포함)

$ cubrid hb start new_db
# ERROR: 다음 테이블에 복제 키가 없습니다: [audit_trail, session_cache, ...]
# → §7에서 예고한 "에러 + 파일 리스트" 발생, HA 전환 실패
```

**예제 설명**: 버전 업그레이드 작업자는 데이터 이관이 끝났다고 안심하고 HA를 켜려다가, 구버전에는 없던 개념(RK) 때문에 다수 테이블을 일일이 REPLICATION=OFF로 바꾸거나 RK를 추가하는 후속 작업을 해야 한다. 이 영향 범위(몇 개 테이블이 걸리는지)를 사전에 파악할 방법이 스펙에 없다.

**제안**: `loaddb` 완료 후 "RK 없이 복제 테이블로 로드된 테이블 목록"을 자동으로 리포트해주는 옵션을 제공해, HA 전환을 시도하기 전에 미리 정리할 수 있게 해야 한다.

### 리뷰 15

**[심각도: 사소] §2-3 예시 8의 `show create table` 출력 포맷이 부자연스럽고, REPLICATION=OFF일 때의 출력 예시가 아예 없다**

**대상**: §2-3 예시 8

**문제 설명**: 예시 8의 결과 문자열 `'CREATE TABLE [tbl] ([a] INTEGER NOT NULL, [b] INTEGER,  CONSTRAINT [pk_tbl_a] PRIMARY KEY  ([a])) REUSE_OID, COLLATE utf8_bin, REPLICATION ON'`에는 `INTEGER,  CONSTRAINT`(공백 두 칸), `PRIMARY KEY  ([a])`(공백 두 칸) 등 불규칙한 공백이 섞여 있다. 오탈자 수준의 문제이지만, 이 출력은 애플리케이션이 스키마를 리버스 엔지니어링하거나 마이그레이션 도구가 파싱할 수도 있는 값이므로 정확한 포맷 명세가 필요하다. 또한 REPLICATION=ON인 경우만 예시로 있고, OFF인 경우 `show create table` 결과에 `REPLICATION OFF`가 명시되는지, 아니면 옵션 자체가 생략되는지 예시가 없다.

**구체 예제**:
```sql
-- REPLICATION=OFF 테이블의 show create table 결과는 어떻게 나오는가? 예시 없음
CREATE TABLE non_repl_table_with_rk(a INT PRIMARY KEY) REPLICATION = OFF;
csql> show create table non_repl_table_with_rk;
-- 기대 출력에 'REPLICATION OFF' 가 명시되는지, 혹은 옵션이 생략(=ON으로 오인 가능)되는지 불명
```

**예제 설명**: REPLICATION 옵션 조회는 §2-3이 명시적으로 다루는 기능인데, ON 케이스만 보여주고 OFF 케이스를 빠뜨린 것은 문서의 균형이 맞지 않는다. 특히 "옵션이 생략되면 ON이 기본값"이라는 규칙(§2-1)이 있으므로, OFF일 때 출력에서 `REPLICATION OFF`가 누락되면 조회 결과만 보고 ON으로 착각할 위험도 있다.

**제안**: 출력 문자열의 공백을 정리하고, REPLICATION=OFF 케이스의 `show create table` / `select * from db_class` 예시를 각각 추가해야 한다.

### 리뷰 16

**[심각도: 사소] 예시 21/22는 정보량이 낮고, 정작 필요한 "부모 테이블을 REPLICATION=OFF로 전환 시도"라는 예시가 빠져 있다**

**대상**: §5-2 예시 21, 22 (참조: 리뷰 4와 연결)

**문제 설명**: 예시 21("복제 테이블을 참조하는 외래키 제거")과 예시 22("외래키 컬럼 제거")는 둘 다 결과가 OK인데, 이는 FK를 없애는 작업이므로 REPLICATION 규칙과 무관하게 원래도 당연히 가능했어야 하는 케이스다. 즉 이 두 예시는 REPLICATION 스펙이 새로 추가한 규칙을 검증하는 데는 거의 기여하지 않는다. 반면 리뷰 4에서 지적한 "부모 테이블을 REPLICATION=OFF로 바꾸려 할 때 자식 FK가 있으면?"이라는, 실제로 헷갈리고 검증이 필요한 케이스는 예시로 존재하지 않는다.

**구체 예제**:
```sql
-- 현재 스펙에 있는 예시 21 (정보량 낮음)
ALTER TABLE new_orders DROP FOREIGN KEY (fk_new_orders_customer_id);  -- OK (당연함)

-- 스펙에 없지만 꼭 필요한 예시
ALTER TABLE customers REPLICATION = OFF;
-- new_orders.fk_new_orders_customer_id 가 customers를 참조 중인 상태에서
-- 결과가 OK인지 ERROR인지 예시가 없음 (리뷰 4 참고)
```

**예제 설명**: 문서에서 예시를 고를 때는 "규칙이 새로 생겨 헷갈리는 지점"을 우선해야 하는데, 지금은 자명한 케이스에 지면을 쓰고 정작 모호한 대칭 케이스는 빠뜨렸다.

**제안**: 예시 21/22를 유지하되, 리뷰 4에서 제시한 "참조당하는 부모 테이블의 REPLICATION 전환 시도" 예시를 §5-2에 반드시 추가해야 한다.

### 리뷰 17

**[심각도: 중요] 에러 메시지/에러 코드 표준화가 없어 배포 스크립트가 실패 원인별로 다른 조치를 자동화할 수 없다**

**대상**: 예시 6, 10, 12, 15, 16, 18, 22, 23 등 "ERROR"로만 표기된 다수 예시 전반

**문제 설명**: 스펙 전체에서 실패 케이스는 거의 전부 그냥 "ERROR"라고만 적혀 있다(예시 6, 10, 12, 15, 16, 18, 22, 23 등). 실제 배포 자동화 스크립트나 애플리케이션의 예외 처리 코드는 에러 메시지 문자열이나 에러 코드를 보고 분기 처리를 해야 하는데(예: "RK 없음" 에러면 자동으로 UK 후보를 제안하고, "FK 참조 테이블 미복제" 에러면 참조 테이블 목록을 알려주는 등), 스펙에 실제 에러 메시지 텍스트나 코드가 전혀 예시되지 않아 이 문서만으로는 예외 처리 코드를 짤 수 없다.

**구체 예제**:
```java
// 애플리케이션/배포 스크립트에서 흔히 필요한 패턴 (의사코드)
try {
    executeDdl("ALTER TABLE customers REPLICATION = OFF;");
} catch (CubridSQLException e) {
    if (e.getErrorCode() == ???) {          // ← 스펙에 코드가 없어 무엇을 넣어야 할지 모름
        // "참조하는 FK 자식이 있어 전환 불가" 케이스 처리
        notifyDeployer("복제 제외 전환 실패: 참조 자식 테이블 확인 필요");
    } else if (e.getErrorCode() == ???) {
        // 다른 원인 처리
    }
}
```

**예제 설명**: 예시 12("ERROR")처럼 원인이 다른 여러 실패(PK 삭제 금지, FK 컬럼 삭제 금지, RK 없음 등)가 전부 "ERROR"라는 한 단어로만 문서화되어 있으면, 실제 구현 시 각기 다른 에러 메시지/코드를 낸다 해도 그 값이 무엇인지 이 문서만으로는 예측할 수 없다. 결국 응용 개발자는 개발 서버에 직접 붙어 하나씩 재현해 메시지를 채집해야 한다.

**제안**: 각 실패 예시에 실제 에러 메시지 문자열(또는 최소한 에러 코드 체계)을 함께 명시하고, 부록으로 "REPLICATION 관련 에러 코드 전체 목록"을 제공해야 한다.

### 리뷰 18

**[심각도: 보통] §8에서 "복제 여부를 저장하는 변수"의 이름/저장 위치가 unload 파일 포맷 문서와 연결되어 있지 않다**

**대상**: §8 UNLOADDB & LOADDB

**문제 설명**: unload/loaddb는 응용 개발자가 데이터 마이그레이션, 테스트 데이터 시딩, 백업 자동화 스크립트에서 자주 다루는 파일 포맷이다. 이번 변경으로 unload 파일에 "복제 여부를 저장하는 변수"가 새로 추가된다고 하는데, 그 변수의 실제 필드명, 스키마 파일(`.schema`) 내 위치, 파서가 이 필드를 어떻게 구분하는지에 대한 정의가 없다. 사내에서 unload 파일을 파싱해 별도 도구(예: 스키마 diff 도구, 테스트 픽스처 생성기)를 만들어 쓰는 경우, 이 필드 추가가 기존 파서를 깨뜨릴 수도 있다는 점을 사전에 알아야 한다.

**구체 예제**:
```
# 현재 .schema 파일 예시(가정)
CREATE TABLE [tbl] ( [a] INTEGER NOT NULL, ... ) REUSE_OID;

# 스펙 변경 후 추가될 것으로 예상되는 형태(문서에 명시 없음)
CREATE TABLE [tbl] ( [a] INTEGER NOT NULL, ... ) REUSE_OID, REPLICATION ON;
-- 위 필드가 실제로 어떤 키워드/토큰으로 나오는지, 커스텀 파서가 이를 무시하고 넘어갈 수 있는지 불명
```

**예제 설명**: 사내 도구가 `.schema` 파일을 정규식이나 간단한 토큰 파서로 읽고 있었다면, `REPLICATION ON` 같은 새 토큰이 추가되는 순간 그 도구가 오작동하거나 그 필드를 무시해 원치 않게 §8의 "변수 없음 = 복제 대상"규칙과 다른 값을 만들어낼 수 있다.

**제안**: `.schema` 파일 포맷 변경 사항(추가되는 정확한 토큰/키워드, 위치)을 unload/load 파일 포맷 문서에 명시적으로 반영하고, 하위 호환을 위해 이 필드가 없는 기존 파서에서도 안전하게 무시될 수 있는 형태인지 검증해야 한다.

### 리뷰 19

**[심각도: 사소] 문서 전반의 오탈자/비문이 실무 레퍼런스로서의 신뢰도를 떨어뜨린다**

**대상**: §5-1 소제목("CRATE TABLE" → CREATE TABLE 오탈자), §7("전환해아한다" → 전환해야 한다), §5 본문("이러한 에러 상황을 막기위해" 띄어쓰기 누락) 등

**문제 설명**: 이 문서는 향후 사용자 매뉴얼/QA 테스트케이스의 원본이 될 문서다. "CRATE TABLE"(§5-1)처럼 SQL 키워드 자체를 잘못 표기한 오탈자는, 문서를 훑어보는 개발자에게 "이 스펙이 충분히 검수되었는가"에 대한 신뢰를 떨어뜨리고, 자동화 도구(용어 검색, grep 기반 문서 색인)에서 누락되는 부작용도 만든다.

**구체 예제**:
```
원문(§5-1 소제목): "5-1. CRATE TABLE 예시"
정정:              "5-1. CREATE TABLE 예시"

원문(§7): "HA를 재시작해아한다"
정정:     "HA를 재시작해야 한다"
```

**예제 설명**: 개별 오탈자는 사소하지만, "CRATE TABLE"처럼 SQL 예약어 자체를 틀린 경우는 문서 내 검색(Ctrl+F로 "CREATE TABLE" 검색 시 해당 절이 안 걸림)에도 실질적 지장을 준다.

**제안**: 배포 전 맞춤법 검사 및 SQL 키워드 표기 일관성 검수를 한 차례 거쳐야 한다.

### 리뷰 20

**[심각도: 중요] "일단 REPLICATION=OFF로 만들고 나중에 ON으로 전환"하는 점진적 롤아웃 패턴이 사실상 봉쇄되어 있다**

**대상**: §2-2 — "HA 모드에서는 복제 제외 테이블이 복제 테이블로 변경될 수 없다"

**문제 설명**: 응용 개발자가 신기능을 배포할 때 흔히 쓰는 패턴은 "일단 새 테이블을 만들어 데이터를 쌓아두되, 안정화되기 전까지는 복제/replication 대상에서 빼두고, 검증이 끝나면 그때 정식으로 복제를 켠다"는 점진적 롤아웃이다. 그런데 이 스펙은 HA 모드에서 REPLICATION=OFF → ON 전환 자체를 원천 금지한다(예시 6 OK는 ON→OFF 방향뿐이고, 반대 방향은 §2-2 본문에서 명시적으로 막혀 있다). 결국 이 패턴을 쓰려면 반드시 싱글 모드로 내려가야 하는데, 운영 중인 HA 클러스터를 이 목적만으로 싱글로 내렸다가 다시 올리는 것은 현실적으로 불가능에 가깝다. 즉 "복제 대상 여부를 나중에 유연하게 켜고 끄기"라는, REPLICATION 옵션이 애초에 제공하려는 유연성 중 절반(OFF→ON 방향)이 운영 중에는 막혀 있는 셈이다.

**구체 예제**:
```sql
-- HA 운영 중, 신규 기능 배포
CREATE TABLE beta_feature_data(
    id     INT PRIMARY KEY,
    payload VARCHAR(1000)
) REPLICATION = OFF;   -- 검증 끝날 때까지는 복제 안 함

-- ... 2주간 안정화 기간 ...

-- 검증 완료, 이제 정식으로 복제를 켜고 싶음
ALTER TABLE beta_feature_data REPLICATION = ON;
-- ERROR (§2-2: HA 모드에서 복제 제외 → 복제 테이블 전환 불가)

-- 결국 선택지는:
--   (a) 처음부터 REPLICATION=ON으로 만들어 검증 기간에도 불필요하게 복제 트래픽/스토리지 부담 (또는)
--   (b) HA를 내리고 싱글로 전환 후 ALTER 실행 후 다시 HA로 전환 (실질적으로 비현실적)
```

**예제 설명**: 점진적 기능 롤아웃은 매우 흔한 배포 전략인데, 이 스펙에서는 "복제를 나중에 켜는" 방향의 전환이 운영 중에는 불가능해 (a)나 (b) 중 하나를 강요받는다. (a)를 택하면 애초에 REPLICATION=OFF 옵션을 도입한 목적(선택적 복제 제외)이 무색해지고, (b)는 운영 중단을 요구하므로 사실상 선택지가 아니다. 이 방향 전환이 왜 막혀 있는지(엔진 내부적으로 기존 데이터의 RK 소급 적용이 어려운 이유가 있다면) 근거가 스펙에 없어, 이것이 의도된 제약인지 누락된 기능인지조차 판단할 수 없다.

**제안**: OFF→ON 전환이 막힌 기술적 근거(예: 기존에 쌓인 데이터에 대한 초기 동기화 스냅샷이 없어 슬레이브가 뒤늦게 켜진 테이블의 과거 데이터를 못 받는 문제 등)를 명시하고, 가능하다면 "전환 시점부터의 변경분만 복제 시작 + 최초 1회 전체 재동기화" 같은 절차를 제공해 이 방향의 전환도 지원해야 한다. 최소한 이 제약이 "설계상 의도"임을 §9 요약에 명확히 못 박아야 한다.
