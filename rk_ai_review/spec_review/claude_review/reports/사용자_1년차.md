# CUBRID HA 복제 개선 스펙 리뷰 — 사용자(최종 사용자) · 1년차

## 리뷰어 소개

저는 CUBRID를 이용해 업무 시스템을 개발·운영하는 1년차 실무자입니다. DB 엔진 내부 구조나 복제 모듈 소스코드는 모르고, csql로 DDL/DML을 짜고 장애가 나면 에러 메시지를 보고 검색부터 하는 입장입니다. 이 리뷰는 "이 문서만 읽고 내가 시키는 대로 따라할 수 있는가", "에러가 나면 무엇을 해야 하는지 이 문서가 알려주는가"를 기준으로 작성했습니다.

## 총평

이 스펙은 REPLICATION 옵션과 복제 키(RK) 자동 선택이라는 핵심 아이디어 자체는 한 번 읽으면 이해할 수 있을 만큼 단순합니다. 그러나 실제로 csql 앞에 앉아 이 문서만 보고 작업해야 하는 1년차 입장에서 보면, (1) 예제 SQL 자체에 문법 오류가 섞여 있어 그대로 따라 치면 스펙이 의도한 것과 다른 에러를 만나게 되고, (2) "ERROR"라고만 적혀 있고 실제 에러 메시지 문구가 거의 제공되지 않아 무엇을 검색해야 할지 알 수 없으며, (3) §8과 §9처럼 서로 다른 절이 같은 상황(복제 여부 미설정)에 대해 정반대의 기본값을 말하는 등 문서 내부 모순이 있습니다. 또한 "복제키 후보"처럼 §1에서 정의되지 않은 채 §4-2에서 갑자기 등장하는 용어, "싱글모드"와 별개로 §9에서만 언급되는 "SA" 모드처럼 신입이 스스로 채울 수 없는 정보 공백이 여럿 있습니다. 컨셉은 나쁘지 않지만, 사용자 매뉴얼로서의 완성도는 아직 부족하다고 판단합니다.

## 리뷰 1

**[심각도: 치명] 모드 용어("싱글모드"/"SA")가 서로 다른 절에서 모순되게 쓰인다**

**대상**: §1 "HA 모드는 'cubrid hb start'로 큐브리드를 실행시킨 상태를 의미하며 나머지는 모두 싱글모드" / §9 "이 키워드는 싱글 이나 SA에서도 사용 가능"

**문제 설명**: §1은 CUBRID의 실행 모드를 "HA 모드"와 "싱글모드" 두 가지로만 나눕니다("나머지는 모두 싱글모드"). 그런데 문서 맨 끝 §9 요약에서는 갑자기 "싱글"과 "SA"를 나란히 언급합니다. SA(Stand-Alone, 다른 클라이언트 접속 없이 서버 프로세스 없이 동작하는 단독 모드를 CUBRID에서 부르는 이름으로 추정됩니다)가 §1의 정의대로라면 "싱글모드"에 포함되는 것인지, 아니면 싱글모드와 별도로 존재하는 제3의 모드인지 이 문서만 봐서는 알 수 없습니다. 1년차 입장에서는 "싱글모드"라는 용어 하나만 외우고 있었는데 마지막 줄에서 "SA"라는 처음 보는 용어가 튀어나오면, 지금까지 읽은 §1~§8의 "싱글모드"가 SA를 포함하는 개념인지 다시 앞으로 돌아가 확인해야 합니다.

**구체 예제(시나리오)**:
```
1) csql -S -u dba mydb   # SA(Stand-Alone) 모드로 접속했다고 가정
2) csql> CREATE TABLE t1 (a INT) REPLICATION=OFF;
3) 질문: 이 SQL은 §1 기준으로 "싱글모드"에서 실행된 것인가,
   아니면 §9가 말하는 "SA"라는 별도 모드에서 실행된 것이라 §1의
   싱글모드 규칙이 그대로 적용되는지 보장할 수 없는가?
```

**예제 설명**: 위 시나리오는 실제로 자주 발생합니다. 운영자가 백업/복구나 스키마 변경을 위해 서버 프로세스 없이 csql -S로 접속하는 경우가 흔한데, 이때 REPLICATION 옵션 관련 규칙(복제키 없는 테이블 생성 가능 여부 등)이 §1~§8이 말하는 "싱글모드" 규칙과 동일하게 적용되는지 문서가 명시하지 않습니다.

**제안**: §1에서 CUBRID가 지원하는 모든 실행 모드(HA, 싱글, SA 등)를 표로 먼저 정의하고, 이후 모든 절에서 "싱글모드"라고 쓸 때 SA를 포함하는지 여부를 일관되게 명시해야 합니다.

## 리뷰 2

**[심각도: 치명] §8과 §9가 "복제 여부 정보가 없을 때의 기본값"을 정반대로 규정한다**

**대상**: §8 "복제 여부를 저장하는 변수가 설정되어 있지 않다면 복제 대상(Default)으로 간주한다" vs §9 "UNLOADDB 시 복제 대상 여부를 함께 출력해야하며, 이를 포함하지 않는 테이블은 모두 복제 제외 테이블이다"

**문제 설명**: 두 절 모두 "unload된 덤프 파일에 복제 여부 정보가 없는 경우"를 다루는데 결론이 정반대입니다. §8은 "정보가 없으면 복제 대상(ON)으로 간주한다"고 하고, §9 요약은 "정보를 포함하지 않는 테이블은 모두 복제 제외(OFF) 테이블"이라고 합니다. 같은 문서 안에서 같은 조건에 대해 서로 다른 답을 주는 것은 신입 입장에서 가장 곤란한 유형의 결함입니다. 어느 쪽을 믿고 마이그레이션 계획을 세워야 할지 판단할 수 없습니다.

**구체 예제(시나리오)**:
```
# 시나리오: 구버전(REPLICATION 옵션이 없던 버전)에서 만든 dump 파일을 이용한 복구
$ unloaddb -u dba old_db          # 구버전 CUBRID, REPLICATION 개념 없음 → 여부 정보 없음
$ (파일을 새 버전 서버로 옮김)
$ loaddb -u dba new_db < old_db.unl

질문: 복구된 테이블은 REPLICATION ON인가 OFF인가?
 - §8을 따르면: ON (복제 대상)
 - §9를 따르면: OFF (복제 제외)
```

**예제 설명**: 이 시나리오는 스펙이 애초에 해결하려는 "구버전 호환" 문제 그 자체입니다. 마이그레이션 후 데이터가 슬레이브로 복제될지 말지가 정확히 예측 가능해야 하는데, 문서 두 곳의 답이 다르므로 실제로 loaddb를 돌려보기 전에는 결과를 알 수 없습니다. 운영 환경에서 이런 불확실성은 데이터 불일치 사고로 직결됩니다(스펙이 애초에 막으려던 문제와 동일한 종류).

**제안**: §8과 §9 중 하나로 통일하고, "REPLICATION 정보가 없는 테이블의 기본값"을 스펙 최상단(§1)에서 단 한 번, 명확히 선언해야 합니다.

## 리뷰 3

**[심각도: 중요] ALTER TABLE ... REPLICATION=OFF가 외래키 참조 무결성 검사 없이 무조건 성공한다 (컨셉 수준 결함)**

**대상**: §2-2 예시 6 (`ALTER TABLE tbl REPLICATION=OFF; → OK`) vs §5 ("외래키 테이블에서 참조하는 모든 테이블은 복제 대상이여야한다")

**문제 설명**: §5는 CREATE TABLE·ALTER TABLE로 외래키를 "추가"할 때는 참조 테이블이 복제 대상인지 검사한다고 설명합니다(예시 18, 22-1 참조 시 ERROR). 그런데 반대 방향, 즉 이미 다른 복제 테이블이 참조하고 있는 테이블을 나중에 `REPLICATION=OFF`로 끄는 경우에 대한 검사는 어디에도 없고, 예시 6은 무조건 `OK`라고만 되어 있습니다. 이 컨셉(REPLICATION ON/OFF를 테이블 단위로 자유롭게 토글)은 "FK 참조 대상은 항상 복제 대상이어야 한다"는 §5의 원칙과 실행 시점이 다를 뿐 똑같이 위반됩니다.

**구체 예제(SQL)**:
```sql
-- 1) 정상적으로 FK 관계의 복제 테이블 두 개를 만든다 (스펙 예시 17과 동일)
csql> CREATE TABLE customers(
    customer_id INT PRIMARY KEY,
    country INT
);
csql> CREATE TABLE orders(
    order_id INT PRIMARY KEY,
    customer_id INT,
    CONSTRAINT fk_customer_id FOREIGN KEY (customer_id) REFERENCES customers(customer_id)
);
-- 지금까지는 §5 예시 17과 동일하게 정상(OK)

-- 2) 그런데 나중에 누군가 customers만 복제 제외로 바꾼다
csql> ALTER TABLE customers REPLICATION=OFF;   -- 스펙 예시 6에 따르면 OK

-- 3) 결과: orders(복제 대상, FK)가 참조하는 customers(복제 제외)가 되어
--    스펙 §5가 그림으로 경고한 "Failover 후 참조 테이블이 슬레이브에 없음" 상황이
--    CREATE TABLE 시점 검사를 모두 통과하고도 그대로 재현된다.
```

**예제 설명**: 위 시나리오는 스펙 서두의 다이어그램(orders가 슬레이브에 있지만 customers가 없어 FK 참조가 깨지는 상황)을 CREATE TABLE 단계 검사만으로는 절대 막을 수 없다는 것을 보여줍니다. §5가 "생성 시점"만 검사하고 "이미 존재하는 FK 관계의 부모 테이블을 나중에 OFF로 바꾸는" 경로를 다루지 않는 한, 스펙이 해결하려던 원래 문제(마스터/슬레이브 불일치)가 REPLICATION 옵션이라는 새 기능을 통해 다시 발생할 수 있습니다.

**제안**: ALTER TABLE ... REPLICATION=OFF 시, 해당 테이블을 참조하는 FK를 가진 복제 대상 테이블이 하나라도 있으면 에러를 내도록 §2-2 규칙에 명시해야 합니다.

## 리뷰 4

**[심각도: 중요] 예시 2의 CREATE TABLE 문에 문법 오류(trailing comma)가 있다**

**대상**: 예시 2 `CREATE TABLE repl_table_without_rk(a INT,);`

**문제 설명**: 마지막 컬럼 정의 뒤에 콤마(`a INT,`)가 붙은 채로 괄호가 닫힙니다. 일반적인 SQL 문법에서는 컬럼 목록의 마지막 항목 뒤에 콤마를 두면 문법 오류입니다. 이 예시는 "복제 키가 없는 테이블은 싱글 모드에서만 생성 가능"이라는 의미론적 규칙을 보여주려는 의도인데, 실제로 이 SQL을 그대로 입력하면 그 규칙과 무관하게 문법 오류부터 발생할 가능성이 큽니다. 1년차가 매뉴얼 예시를 복사해서 실행해보는 것은 아주 흔한 학습 방식인데, 그 첫 시도부터 스펙이 설명하는 것과 다른 종류의 오류를 만나면 "내가 뭘 잘못했나"부터 다시 의심하게 됩니다.

**구체 예제(SQL)**:
```sql
-- 스펙 원문 그대로
csql> CREATE TABLE repl_table_without_rk(
    a INT,
);
```

**예제 설명**: 콤마 뒤에 다음 컬럼 정의가 없는데도 콤마가 남아 있습니다. 즉 "a INT" 다음에 컬럼이 하나 더 있어야 할 자리에 아무것도 없이 괄호가 닫힙니다. 이는 스펙이 보여주려는 "RK 없음" 시나리오와 무관한, 순수한 오타입니다.

**제안**: 마지막 콤마를 제거하거나(`a INT`), 의도적으로 컬럼을 하나 더 추가해 실제로 실행 가능한 SQL로 교정해야 합니다.

## 리뷰 5

**[심각도: 중요] 예시 20, 23도 동일한 trailing comma 오류를 반복한다**

**대상**: 예시 20 `CREATE TABLE new_orders(order_id INT PRIMARY KEY,);`, 예시 23 `CREATE TABLE new_orders(order_id INT PRIMARY KEY,);`

**문제 설명**: 리뷰 4와 같은 유형의 오류가 §5-2 전체에 반복됩니다. 한 곳의 오타라면 단순 실수로 넘어갈 수 있지만, 같은 실수가 문서 전체에 여러 번 반복된다는 것은 예시 SQL이 실제로 한 번도 실행해보지 않은 채 작성되었을 가능성을 시사합니다. 1년차 입장에서는 문서의 예시 코드에 대한 신뢰가 낮아지면, "이 예시가 보여주는 OK/ERROR 결과도 실제로 검증된 것이 맞는지" 전체 문서에 대한 의심으로 번집니다.

**구체 예제(SQL)**:
```sql
-- 예시 20 원문
csql> CREATE TABLE new_orders(
    order_id INT PRIMARY KEY
);
csql> ALTER TABLE new_orders ADD COLUMN
(customer_id INT FOREIGN KEY REFERENCES customers(customer_id));
```
(참고: 예시 20의 첫 CREATE TABLE 자체는 콤마 문제가 없으나, 예시 23의 동일한 형태 CREATE TABLE에는 `order_id INT PRIMARY KEY,` 뒤에 컬럼이 없이 콤마가 남아 있습니다.)

**예제 설명**: 예시 20과 23은 거의 동일한 시나리오(FK 컬럼을 ADD COLUMN으로 추가)를 복제 대상/복제 제외 테이블 각각에 대해 반복 설명하는 구조인데, 복사-붙여넣기 과정에서 예시 23 쪽에만 문법 오류가 남았습니다. 이는 문서 관리(예시 재사용) 과정의 QA 미흡을 보여줍니다.

**제안**: 전체 문서의 SQL 예시를 실제 csql에 한 번씩 실행해보고 문법 오류를 전수 검사할 것을 제안합니다.

## 리뷰 6

**[심각도: 보통] 카탈로그 조회(예시 8, 9)로는 "현재 무엇이 RK인지"를 확인할 방법이 없다**

**대상**: 예시 8 (`show create table`), 예시 9 (`select * from db_class`)

**문제 설명**: §2-3은 "사용자는 REPLICATION 정보를 조회할 수 있어야한다"고 말하고 두 예시를 보여줍니다. 그런데 두 예시 모두 `REPLICATION ON` 또는 `replication : ON`처럼 옵션의 ON/OFF 여부만 보여줄 뿐, 실제로 엔진이 선택한 복제 키(RK)가 어떤 제약(PK인지, 어떤 UK인지, 어떤 컬럼들인지)인지는 조회 결과에 나타나지 않습니다. §1에 따르면 UK가 여러 개면 엔진이 "그 중 하나"를 자동으로 고르는데, 사용자가 그 결과를 확인할 방법이 REPLICATION ON/OFF 여부 외에는 제시되어 있지 않습니다.

**구체 예제(SQL)**:
```sql
csql> CREATE TABLE t(
    a INT,
    b INT NOT NULL UNIQUE,
    c INT NOT NULL UNIQUE
);  -- PK 없음, UK 두 개 → §1 규칙에 따라 엔진이 b, c 중 하나를 RK로 선택

csql> show create table t;
-- REPLICATION ON 이라는 것만 보이고, b와 c 중 무엇이 RK로 선택됐는지는 안 보임

csql> select * from db_class where class_name='t';
-- replication : ON 만 보이고 마찬가지로 어떤 컬럼/제약이 RK인지는 안 보임
```

**예제 설명**: 만약 사용자가 이 상태에서 `c` UNIQUE 제약을 삭제하려고 하면(§4-2 예시 15 규칙에 따라) RK로 선택된 컬럼이면 에러가 나고 아니면 성공합니다. 그런데 사용자는 사전에 `b`와 `c` 중 무엇이 RK인지 조회할 방법이 없으므로, 실제로 DROP을 시도해보고 에러가 나는지 안 나는지로 "역추적"해야 하는 상황이 됩니다. 이는 명백히 비정상적인 운영 워크플로우입니다.

**제안**: `show create table` 또는 `db_class`(혹은 별도 시스템 카탈로그)에 현재 선택된 RK의 제약 이름/컬럼을 명시적으로 표시하는 필드를 추가해야 합니다.

## 리뷰 7

**[심각도: 중요] UK가 여러 개일 때의 선택 기준이 "예시"로만 제시되어 확정된 규칙이 아니다**

**대상**: §1 "UK가 여러개 존재한다면 큐브리드 엔진에 의해 이 중 하나가 선택된다(ex. 테이블내에 명시된 순서 중 가장 빠른 순서)"

**문제 설명**: 괄호 안의 "ex."는 "예를 들어"라는 뜻으로, 이것이 확정된 규칙인지 단지 하나의 가능한 예시인지 불분명합니다. 사용자 매뉴얼에서 엔진 동작의 결정 규칙을 "예시"로만 제시하는 것은 심각한 정보 부족입니다. 특히 이 선택 결과에 따라 어떤 ALTER TABLE이 성공하고 실패하는지가 갈리므로(§4-2), 사용자가 예측 가능성을 가지려면 확정된 규칙이 필요합니다.

**구체 예제(시나리오)**:
```sql
-- 1) 처음에 b가 첫 번째 UK로 선언됨 → RK = b (스펙 규칙에 따르면 추정)
csql> CREATE TABLE t(a INT, b INT NOT NULL UNIQUE, c INT);

-- 2) 이후 c에도 UK를 추가
csql> ALTER TABLE t ADD CONSTRAINT UNIQUE(c);

-- 질문: 이제 RK는 여전히 b인가? 아니면 "테이블에 명시된 순서"가
--       재계산되어 바뀔 수 있는가? 스펙은 "생성 시점" 순서만 예로 들 뿐
--       ALTER로 UK가 추가된 경우의 순서 규칙은 언급하지 않는다.
```

**예제 설명**: RK가 ALTER TABLE 한 번으로 조용히 바뀔 수 있다면, 그 순간부터 이전에는 성공하던 DDL(예: 기존 RK였던 b의 UNIQUE 제약 삭제)이 갑자기 실패하거나, 반대로 실패하던 DDL이 성공하게 됩니다. 사용자는 자신이 아무것도 건드리지 않은 컬럼(b)에 대한 DDL 결과가 달라지는 것을 예측할 수 없습니다.

**제안**: RK 선택 규칙을 "예시"가 아닌 확정된 알고리즘으로 명시하고(예: 생성 순서 고정, 또는 최초 선택 후 불변), ALTER로 새 UK가 추가되어도 기존 RK가 유지되는지 여부를 명확히 기술해야 합니다.

## 리뷰 8

**[심각도: 보통] §1의 첫 문장이 주어-서술어가 맞지 않아 읽기 어렵다**

**대상**: §1 "HA 모드 실행 시 복제 테이블은 복제를 위한 복제 키 (RK: Replication Key) 가 존재하지 않으면 HA모드를 실행 할 수 없다."

**문제 설명**: 이 문장의 주어는 "복제 테이블"인데 서술어는 "HA모드를 실행할 수 없다"입니다. 즉 문장 그대로 읽으면 "복제 테이블이 HA 모드를 실행한다/못한다"는 뜻이 되어 버립니다. 실제 의도는 "복제 테이블에 RK가 없으면 (사용자가) HA 모드를 실행할 수 없다"일 것입니다. 스펙 전체에서 가장 먼저 읽는 문장이 이렇게 문법적으로 꼬여 있으면, 신입 독자는 두세 번 다시 읽어야 의미를 파악하게 됩니다.

**구체 예제(시나리오)**:
```
원문: "HA 모드 실행 시 복제 테이블은 ... RK가 존재하지 않으면 HA모드를 실행 할 수 없다."
읽는 사람의 1차 해석: "복제 테이블"이 무언가를 "실행"한다는 주술 관계로 오독 가능
의도된 해석(추정): "복제 테이블에 RK가 없으면, 사용자는 HA 모드로 전환할 수 없다"
```

**예제 설명**: 특히 이 문장이 스펙 전체의 핵심 제약사항(§1의 첫 문장이자 가장 중요한 규칙)이라는 점에서, 문장 구조의 모호함이 방치되면 안 됩니다.

**제안**: "복제 테이블에 복제 키(RK)가 하나도 없으면, HA 모드로 전환/실행할 수 없다"와 같이 주어를 "사용자" 또는 "시스템"으로 명확히 하여 재작성해야 합니다.

## 리뷰 9

**[심각도: 중요] "복제키 후보"라는 용어가 §1에서 정의되지 않고 §4-2에서 갑자기 등장한다**

**대상**: §4-2 "테이블에 하나의 복제키만 존재한다면 복제키를 수정하는 DDL이 제한되지만, 다른 복제키 후보가 함께 존재한다면..."

**문제 설명**: §1에서는 "복제 키(RK)"라는 단수 개념만 설명합니다(PK 또는 UK 중 엔진이 "하나"를 선택). 그런데 §4-2에 와서 갑자기 "복제키 후보"라는 새 용어가 등장하고, 이후 예시 11~16 전체가 이 "후보"와 "실제 선택된 복제키"의 구분에 의존해서 설명됩니다. 그러나 "후보"가 정확히 무엇인지(PK 하나 + NOT NULL UNIQUE 제약들의 전체 집합인지, RK로 선택되지 않은 나머지 UK들만인지) 명시적으로 정의된 문장이 없습니다. 신입 독자는 §4-2를 읽으면서 스스로 "아마 PK/UK가 여러 개 있으면 그 중 선택 안 된 나머지를 후보라고 부르나보다"라고 추측해야 합니다.

**구체 예제(시나리오)**:
```sql
csql> CREATE TABLE t(
    a INT PRIMARY KEY,
    b INT NOT NULL UNIQUE,
    c INT NOT NULL UNIQUE
);
-- RK는 §1 규칙에 따라 PK인 a로 선택된다고 가정.
-- 이때 "복제키 후보"는 b, c 두 개를 가리키는가?
-- 아니면 a(실제 RK)를 포함해 PK/UK 전부(a, b, c)를 "후보"라고 부르는가?
-- §4-2 예시 11(PK 추가 시도 ERROR)은 "복제키가 1개"라는 표현을 쓰는데
-- 이 테이블은 PK 1개 + UK 2개로 총 3개의 PK/UK 제약이 있다.
-- 그런데 §4-2는 "복제키 후보가 1개인 경우"를 가정하고 규칙을 설명하므로
-- 이 테이블(총 3개)이 어느 규칙에 해당하는지 이 절만 읽어서는 판단이 안 선다.
```

**예제 설명**: 예시 11~16은 모두 "복제키 후보가 1개인 경우"를 전제로 설명되어 있는데, 정작 "후보가 몇 개인가"를 세는 기준(PK/UK를 각각 1개씩 세는지, PK가 있으면 UK는 후보에서 제외하는지 등)이 어디에도 정의되어 있지 않습니다.

**제안**: §1에 "복제키 후보 = RK로 선택될 수 있는 모든 PK/NOT NULL UNIQUE 제약의 집합이며, 이 중 하나가 실제 RK로 선택된다"는 정의 문장을 추가하고, §4-2 예시들이 각각 후보가 몇 개인 테이블을 가정하는지 테이블 스키마를 함께 보여줘야 합니다.

## 리뷰 10

**[심각도: 중요] 예시 12와 예시 13이 겉보기에 같은 동작을 정반대로 처리해 매우 반직관적이다**

**대상**: 예시 12 (`ALTER TABLE table_name DROP PRIMARY KEY; → ERROR`) vs 예시 13 (`ALTER TABLE table_name DROP CONSTRAINT PRIMARY KEY, ADD CONSTRAINT PRIMARY KEY(a); → OK`)

**문제 설명**: 예시 12는 "PK가 복제키로 쓰이는 경우 이 PK는 삭제할 수 없다"고 하면서 `DROP PRIMARY KEY` 단독 실행에 대해 ERROR를 보여줍니다. 그런데 예시 13은 사실상 같은 동작(PK 삭제)을 포함하는 `DROP CONSTRAINT PRIMARY KEY`를 `ADD CONSTRAINT PRIMARY KEY(a)`와 한 문장으로 묶어서 실행하면 OK가 됩니다. 즉 "PK를 지운다"는 연산 자체는 금지되어 있지 않고, "지운 후 대체할 새 RK 후보를 같은 문장 안에서 함께 추가하는지"가 성공/실패를 가릅니다. 이것은 SQL 문법을 배운 지 얼마 안 된 사용자에게는 전혀 직관적이지 않은 규칙입니다. "왜 두 문장으로 나눠 실행하면 안 되고 한 문장으로 묶어야 하는가"에 대한 원리 설명이 스펙에 전혀 없습니다.

**구체 예제(SQL)**:
```sql
-- 시도 A: 두 문장으로 나눠서 실행 (직관적으로 시도하기 쉬운 방식)
csql> ALTER TABLE table_name DROP PRIMARY KEY;
-- ERROR (예시 12)
csql> ALTER TABLE table_name ADD CONSTRAINT PRIMARY KEY(a);
-- 이 문장은 위 DROP이 실패했으므로 애초에 실행할 필요조차 없어짐

-- 시도 B: 한 문장으로 묶어서 실행
csql> ALTER TABLE table_name DROP CONSTRAINT PRIMARY KEY,
      ADD CONSTRAINT PRIMARY KEY(a);
-- OK (예시 13)
```

**예제 설명**: 신입 사용자는 보통 "일단 지우고, 그다음 추가해야지"라는 순차적 사고로 시도 A처럼 두 문장을 따로 실행합니다. 그런데 이 방식은 스펙상 금지되어 있고, 반드시 하나의 ALTER TABLE 문 안에 DROP과 ADD를 함께 나열해야만 허용됩니다(아마도 "복제키가 완전히 사라지는 중간 상태"를 허용하지 않기 위한 원자적 처리로 추정되지만, 스펙에 그런 설명이 없습니다). 이 규칙을 모르는 사용자는 예시 12만 보고 "PK 교체 자체가 아예 불가능하다"고 잘못 결론짓기 쉽습니다.

**제안**: 예시 12 바로 다음에 "RK를 다른 컬럼으로 교체하려면 반드시 예시 13처럼 DROP과 ADD를 한 ALTER TABLE 문 안에 함께 써야 한다"는 명시적 안내와, "왜 두 문장으로 나누면 안 되는지"(RK가 순간적으로 0개가 되는 중간 상태를 막기 위함 등)의 이유를 추가해야 합니다.

## 리뷰 11

**[심각도: 보통] 예시 16의 DROP INDEX 대상이 UNIQUE 인덱스인지 불명확하다**

**대상**: 예시 16 "DROP INDEX: 복제키 후보가 없다면 삭제 불가 `csql> DROP INDEX idx_id ON tbl; → ERROR`"

**문제 설명**: CUBRID에서 `DROP INDEX`는 UNIQUE 인덱스뿐 아니라 일반(비UNIQUE) 인덱스에도 쓸 수 있는 명령입니다. 그런데 이 예시는 `idx_id`가 어떤 종류의 인덱스인지(일반 인덱스인지, UNIQUE 제약과 연결된 인덱스인지) 스키마를 전혀 보여주지 않은 채 "복제키 후보가 없다면 삭제 불가"라는 결과만 제시합니다. 만약 `idx_id`가 단순 비UNIQUE 인덱스라면애초에 RK 후보가 될 수 없으므로(§1: RK는 PK 또는 NOT NULL UNIQUE) 이 예시의 전제 자체가 성립하지 않습니다.

**구체 예제(SQL)**:
```sql
-- 스펙 예시 16 원문 (테이블 정의 없이 인덱스 삭제만 제시됨)
csql> DROP INDEX idx_id ON tbl;
-- ERROR

-- 아래 두 경우 중 스펙이 어느 쪽을 가정하는지 알 수 없다
-- (A) idx_id가 UNIQUE 인덱스이고, 이 UK가 테이블의 유일한 RK 후보인 경우
CREATE TABLE tbl(id INT, CONSTRAINT idx_id UNIQUE(id));

-- (B) idx_id가 단순 비UNIQUE 인덱스인 경우 (RK 후보가 될 수 없음)
CREATE INDEX idx_id ON tbl(id);
```

**예제 설명**: (B)라면 이 인덱스는 애초에 RK와 무관하므로 삭제가 막힐 이유가 없어야 합니다. 스펙 예시가 (A)를 의도했다면 테이블 정의(`CONSTRAINT ... UNIQUE`)를 함께 보여주지 않고서는 신입 독자가 "왜 단순 인덱스 삭제가 막히지?"라고 오해하게 됩니다.

**제안**: 예시 16 앞에 `idx_id`가 어떤 제약과 연결된 인덱스인지 CREATE TABLE 스키마를 함께 제시해야 합니다.

## 리뷰 12

**[심각도: 사소] 예시 3의 설명 문장이 어순 오류로 오해를 유발한다**

**대상**: 예시 3 "CREATE TABLE 을 통한 테이블 생성 예시. 복제 제외 PK가 존재하지만 복제 제외 테이블로 생성 됨."

**문제 설명**: "복제 제외 PK가 존재하지만"이라는 표현은 "복제 제외 PK"라는, 스펙에 정의되지 않은 새로운 개념(PK에도 "복제 제외"라는 속성이 붙는 것)이 있는 것처럼 읽힙니다. 실제 의도는 "PK가 존재하지만 (그와 무관하게) 복제 제외 테이블로 생성됨"일 것입니다. 어순만 바뀌어도 뜻이 크게 달라지는 문장입니다.

**구체 예제(시나리오)**:
```
원문: "복제 제외 PK가 존재하지만 복제 제외 테이블로 생성 됨"
오독 가능성: PK 자체에 "복제 제외"라는 별도 속성이 있다는 뜻으로 읽힘
의도(추정): "PK는 존재하지만, REPLICATION=OFF 옵션 때문에 복제 제외 테이블로 생성됨"
```

**예제 설명**: 실제 예시 3의 SQL(`CREATE TABLE non_repl_table_with_rk(a INT PRIMARY KEY) REPLICATION=OFF;`)을 보면 PK는 정상적인 PK이고, 테이블 자체가 REPLICATION=OFF라서 복제 제외가 된 것뿐입니다. "복제 제외 PK"라는 개념은 존재하지 않습니다.

**제안**: "PK가 존재하지만 REPLICATION=OFF로 지정되어 복제 제외 테이블로 생성됨"과 같이 어순을 교정해야 합니다.

## 리뷰 13

**[심각도: 보통] 예시 7("Multiple ALTER")은 실제로 실행 불가능한 템플릿이며 결과(OK/ERROR)도 없다**

**대상**: §2-2 예시 7 "Multiple ALTER `csql> ALTER TABLE tbl DROP CONSTRAINT ..., ADD CONSTRAINT ...;`"

**문제 설명**: 문서의 다른 모든 예시(1~6, 8~23)는 실제 컬럼명·제약명을 채운 완전한 SQL과 그 실행 결과(OK/ERROR)를 함께 보여줍니다. 그런데 예시 7만 유일하게 `...`(생략 부호)로 채워진 템플릿이고 결과도 없습니다. 입문서 수준의 문서에서 예시 하나만 이렇게 추상적으로 남아 있으면, 신입 독자는 "이 문장을 그대로 실행하면 되는 건가?"라고 오해하거나, 실제 어떤 값을 채워야 하는지 다른 예시(11~16)를 뒤져서 유추해야 합니다.

**구체 예제(SQL)**:
```sql
-- 스펙 원문 (실행 불가능한 템플릿)
csql> ALTER TABLE tbl DROP CONSTRAINT ..., ADD CONSTRAINT ...;

-- 신입이 실제로 채워야 하는 형태 (스펙 예시 13에서 유추)
csql> ALTER TABLE tbl DROP CONSTRAINT pk_tbl_a,
      ADD CONSTRAINT PRIMARY KEY(b);
```

**예제 설명**: 예시 13이 사실상 예시 7의 완전한 버전인데, 두 예시가 서로 다른 절(§2-2, §4-2)에 떨어져 있어 연결 관계가 명시되지 않습니다. 신입 독자는 예시 7만 보고는 실행 가능한 SQL을 얻을 수 없습니다.

**제안**: 예시 7을 실제 실행 가능한 SQL(구체적 컬럼/제약명 포함)과 결과로 교체하거나, "구체적인 예시는 4-2절의 예시 13을 참고"라고 명시적으로 상호 참조를 추가해야 합니다.

## 리뷰 14

**[심각도: 중요] 거의 모든 실패 예시가 "ERROR"라고만 적혀 있고 실제 에러 메시지 문구가 없다**

**대상**: 예시 2, 5, 10, 12, 15, 16, 18, 22-1, 23 등 다수 (예시 11, 12만 일부 메시지 텍스트 포함)

**문제 설명**: 사용자가 실제 운영 중에 에러를 만나면 콘솔에 찍힌 에러 메시지 문구를 그대로 사내 위키나 검색엔진에 검색하거나, 매뉴얼에서 해당 문구를 찾아 원인과 조치법을 확인하는 것이 일반적인 흐름입니다. 그런데 이 스펙은 대부분의 실패 케이스에서 그냥 "ERROR"라고만 적어 놓았습니다(예시 11만 "ERROR: Primary key "pk_tbl_a" already defined for class "dba.tbl"."라는 실제 메시지 형태를 보여줌). 나머지 대다수 예시(5, 10, 12, 15, 16, 18, 22-1, 23)는 실제로 어떤 문구가 뜨는지 전혀 알 수 없습니다. 1년차 입장에서 "ERROR"라는 표기만으로는 실제 운영 중 마주친 에러가 이 스펙이 말하는 그 에러가 맞는지조차 확신할 수 없습니다.

**구체 예제(시나리오)**:
```sql
-- 예시 18과 동일한 상황을 실제로 실행했다고 가정
csql> CREATE TABLE orders(
    order_id INT PRIMARY KEY,
    customer_id INT,
    CONSTRAINT fk_customer_id FOREIGN KEY (customer_id)
    REFERENCES non_repl_customers(customer_id)
);
-- 콘솔에 뜨는 실제 문구는? 스펙은 그냥 "ERROR"라고만 되어 있어 알 수 없다.
-- 아래 중 어느 것과 비슷할지 사용자는 추측만 가능하다:
--   (a) "ERROR: cannot reference a table with REPLICATION=OFF"
--   (b) 기존 CUBRID의 일반적인 FK 생성 실패 메시지 그대로 재사용
--   (c) 새로 추가된 전용 에러 코드/메시지
```

**예제 설명**: 실제 장애 대응 상황에서 사용자는 에러 메시지의 정확한 문구, 에러 코드, 조치 방법(SQLCODE나 CUBRID 에러 번호 등)이 필요합니다. "ERROR"라는 표기만으로는 매뉴얼로서 기능하지 못하고, 실제 제품이 출시된 후 QA/지원팀에 문의가 폭주할 가능성이 높습니다.

**제안**: 모든 실패 예시에 실제 예상 에러 메시지 전문(또는 최소한 에러 코드)을 예시 11 수준으로 채워 넣어야 합니다.

## 리뷰 15

**[심각도: 중요] §7의 "파일 리스트"라는 표현이 정의되지 않아 실제로 무엇이 출력되는지 알 수 없다**

**대상**: §7 "HA 실행시 다음 사항을 제약사항을 확인하며, 제약사항 위반 시 에러와함께 파일 리스트를 출력한다"

**문제 설명**: "파일 리스트"라는 표현이 문서 전체에서 여기 한 번만 등장하며, 정의되어 있지 않습니다. 문맥상 위반 대상 "테이블 리스트"의 오타로 추정되지만, unloaddb/loaddb 절(§8)이 근처에 있는 것을 생각하면 실제로 "위반된 테이블을 포함하는 스키마 파일 목록"일 가능성도 배제할 수 없습니다. 신입 사용자가 HA 전환에 실패했을 때 콘솔에 무엇이 찍힐지(테이블명 목록인지, 파일 경로 목록인지)를 이 문서만으로는 확신할 수 없습니다.

**구체 예제(시나리오)**:
```
$ cubrid hb start mydb
ERROR: HA 전환 제약사항 위반
????   <- 여기에 실제로 무엇이 출력되는가?
       (A) 위반 테이블 이름 목록: tbl1, tbl2, tbl3
       (B) 관련 파일 경로 목록: /path/to/schema1.sql, /path/to/schema2.sql
       (C) 그 밖의 형식
```

**예제 설명**: HA 전환 실패는 운영 중 매우 긴급하게 처리해야 하는 상황입니다(HA가 안 켜지면 이중화가 안 되는 것이므로). 이때 출력되는 정보의 형식을 사전에 알아야 대응 스크립트나 체크리스트를 준비할 수 있는데, "파일 리스트"라는 모호한 표현으로는 사전 준비가 불가능합니다.

**제안**: "파일 리스트"가 정확히 무엇을 가리키는지(테이블명 목록/스키마 파일 경로 등) 명시하고, 실제 출력 예시를 §7에 추가해야 합니다.

## 리뷰 16

**[심각도: 보통] §2-2는 "HA에서 복제 제외→복제 대상 전환 불가"만 말하고 해결 방법을 그 자리에서 안내하지 않는다**

**대상**: §2-2 "단, HA 모드에서는 복제 제외 테이블이 복제 테이블로 변경될 수 없다." (예시 5)

**문제 설명**: 이 문장은 "안 된다"는 제약만 말하고 "그럼 어떻게 해야 하는가"를 §2-2 절 안에서 안내하지 않습니다. 실제 해결 방법(싱글 모드로 내려서 변경 후 다시 HA로 전환)은 훨씬 뒤인 §7에서야 일반론으로 등장합니다("이 경우 싱글모드에서 ALTER TABLE… 을 이용해 ... 후 HA를 재시작해야한다"). 신입 사용자가 §2-2만 읽고 실무에서 이 상황을 마주치면, "복제 제외 테이블을 복제 대상으로 절대 바꿀 수 없다"고 잘못 이해하고 테이블을 새로 만드는 등 불필요하게 무거운 우회를 시도할 위험이 있습니다.

**구체 예제(시나리오)**:
```sql
-- HA 운영 중
csql> ALTER TABLE tbl REPLICATION=ON;
-- ERROR (예시 5)

-- §2-2만 읽은 신입의 오해: "복제 제외 테이블은 영원히 복제 대상으로 바꿀 수 없다"
-- 실제 정답(§7에서야 확인 가능): HA를 잠시 내리고 싱글모드로 전환한 뒤 시도해야 함
$ cubrid hb stop mydb          -- HA 중지, 싱글모드로 전환
csql> ALTER TABLE tbl REPLICATION=ON;   -- 싱글모드에서는 OK
$ cubrid hb start mydb         -- 다시 HA로 전환
```

**예제 설명**: §2-2 절 하나만 읽고 작업하는 사용자는 "복제 제외 → 복제 대상 전환"이 조건부로만 불가능하다는 것(HA를 내리면 가능)을 알 수 없습니다. 관련 정보가 문서 뒤쪽 §7에 흩어져 있어, 절 단위로 문서를 참고하는 실무 습관과 맞지 않습니다.

**제안**: §2-2에도 "HA 모드에서는 불가하며, 싱글 모드로 전환 후 변경할 수 있다(§7 참고)"는 한 문장을 즉시 덧붙여야 합니다.

## 리뷰 17

**[심각도: 중요] §5의 FK 검사가 "실행 시점"에만 국한되어, 운영 중 REPLICATION 변경으로 스펙 서두의 다이어그램 문제가 재발할 수 있다**

**대상**: §5 "또한 HA 모드 실행 시 외래키 테이블에서 참조하는 테이블의 상태도 확인해 복제 제외 테이블을 참조할 경우 에러를 출력할 수 있어야한다."

**문제 설명**: 이 문장은 검사 시점을 "HA 모드 실행 시"(즉 `cubrid hb start` 시점)로 한정합니다. 그런데 HA가 이미 켜져서 운영 중인 상태에서 리뷰 3에서 지적한 것처럼 `ALTER TABLE ... REPLICATION=OFF`로 부모 테이블의 복제를 끄면, 다음 HA 재시작 전까지는 이 위반 상태가 감지되지 않은 채로 방치됩니다. 즉 "HA 실행 시" 검사만으로는 운영 중 발생하는 위반을 실시간으로 막지 못합니다.

**구체 예제(시나리오)**:
```
1) HA 정상 기동 (customers, orders 모두 REPLICATION=ON, FK 정상)
2) 운영 중 DBA가 실수로 customers를 REPLICATION=OFF로 변경
   csql> ALTER TABLE customers REPLICATION=OFF;   -- §2-2 예시 6에 따르면 OK, 즉시 통과
3) 이 시점부터 HA는 재시작되지 않은 채 계속 운영됨
   (§5의 "HA 모드 실행 시" 검사는 다음 재시작 때까지 작동하지 않음)
4) Failover 발생, 애플리케이션이 슬레이브의 orders를 조회
5) orders.customer_id가 참조해야 할 customers 데이터가 슬레이브에 없음
   → 스펙 서두 다이어그램이 설명한 바로 그 장애 상황이 재현됨
```

**예제 설명**: 이 시나리오는 스펙이 해결하고자 했던 원래 문제(FK 참조 테이블이 복제 제외일 때의 Failover 장애)가, 새로 추가되는 REPLICATION 옵션 자체의 허점을 통해 그대로 재발할 수 있음을 보여줍니다. "HA 실행 시"라는 검사 시점 한정이 이 구멍의 원인입니다.

**제안**: FK 무결성 검사를 "HA 실행 시"뿐 아니라 "ALTER TABLE ... REPLICATION=OFF 실행 시"에도 즉시 수행하도록 §2-2/§5를 함께 개정해야 합니다(리뷰 3과 동일한 근본 원인).

## 리뷰 18

**[심각도: 보통] 레거시 덤프를 HA 모드 서버에 직접 load할 때의 동작이 명시되어 있지 않다**

**대상**: §8 "특히 하위 버전에서 unload 한 데이터 파일에는 복제 여부를 저장하는 변수가 설정되어있지 않으므로 (싱글 모드에서) load 시 모두 복제 테이블로 설정된다."

**문제 설명**: 이 문장은 괄호로 "(싱글 모드에서)"라고 명시적으로 조건을 달아 놓았습니다. 그렇다면 만약 사용자가 이 레거시 덤프 파일을 HA 모드로 이미 전환된 서버에 직접 load하려고 시도하면 어떻게 되는지가 자연스러운 다음 질문인데, 이 경우에 대한 설명이 전혀 없습니다. loaddb는 보통 서버가 내려간 상태나 단독 접속 상태에서 수행하는 작업이라 실무에서 흔히 발생할 수 있는 시나리오입니다.

**구체 예제(시나리오)**:
```
$ (구버전에서 만든 legacy.unl 파일 보유, REPLICATION 정보 없음)
$ cubrid hb status   # 이미 HA 모드로 동작 중인 서버 확인
$ loaddb -u dba mydb < legacy.unl
질문: 이 명령이 §8 규칙대로 "복제 대상(ON)"으로 자동 설정되는가?
      아니면 §1의 "복제키 없는 테이블은 HA에서 생성 불가" 규칙에 걸려
      load 자체가 테이블별로 실패하는가?
      (legacy.unl 안에 RK가 없는 테이블이 섞여 있을 수 있음을 감안하면
       이 질문은 실무적으로 중요하다)
```

**예제 설명**: §8은 "싱글 모드에서" load하는 경우만 다루고 있어, HA 모드에서 동일한 파일을 load할 때 RK 없는 테이블에 대해 §1의 제약이 어떻게 상호작용하는지 스펙만으로는 알 수 없습니다. 레거시 마이그레이션은 이 스펙이 존재하는 이유 그 자체와 직결되는 시나리오이므로 반드시 명시되어야 합니다.

**제안**: §8에 "HA 모드에서 레거시 덤프를 load할 경우"에 대한 별도 문단을 추가하고, RK 없는 테이블이 포함된 경우의 처리 방식(에러 발생 여부, 부분 로드 가능 여부 등)을 명시해야 합니다.

## 리뷰 19

**[심각도: 사소] db_class 조회 결과의 필드명 대소문자가 SQL 키워드와 달라 혼란을 줄 수 있다**

**대상**: 예시 9 `replication : ON` (소문자) vs 문서 전반의 SQL 옵션 `REPLICATION={ON|OFF}` (대문자)

**문제 설명**: CUBRID SQL에서 예약어는 보통 대소문자를 구분하지 않으므로 기능적으로는 문제가 없을 수 있지만, 문서 표기 관례상 SQL 키워드로서의 `REPLICATION`(대문자로 일관 표기)과 카탈로그 필드명으로서의 `replication`(소문자)이 같은 예시 묶음 안에서 섞여 나타나면, SQL 문법을 막 배우기 시작한 사용자는 "대문자로 써야 하는 경우와 소문자로 써야 하는 경우가 따로 있나"라고 오해할 수 있습니다.

**구체 예제(시나리오)**:
```sql
-- DDL에서는 대문자 관례
csql> CREATE TABLE tbl(a INT) REPLICATION=OFF;

-- 카탈로그 조회 결과에서는 소문자로 출력됨 (예시 9)
csql> select * from db_class;
...
        replication       : ON
```

**예제 설명**: 다른 db_class 필드들(class_name, owner_name 등)도 전부 소문자이므로 이 자체는 CUBRID 카탈로그의 일반적인 표기 관례일 뿐 버그는 아닙니다. 다만 스펙 문서 내에서 이 차이에 대한 언급이 전혀 없어, 초심자가 "REPLICATION 옵션 이름 자체가 대소문자에 따라 다른 의미를 갖는가"라고 불필요하게 궁금해할 여지가 있습니다.

**제안**: 각주로 "SQL 키워드와 카탈로그 필드명 표기(대/소문자)는 CUBRID의 일반적인 관례를 따른 것으로 REPLICATION 기능과 무관하다"는 안내를 추가하면 좋겠습니다.

## 리뷰 20

**[심각도: 보통] §4-2의 "다른 복제키 후보가 함께 존재한다면 모든 DDL은 허용된다(단, 기존의 제약사항은 유지된다)" 문장이 이중부정적이고 구체 예시가 없다**

**대상**: §4-2 "테이블에 하나의 복제키만 존재한다면 복제키를 수정하는 DDL이 제한되지만, 다른 복제키 후보가 함께 존재한다면 모든 DDL은 허용된다(단, 기존의 제약사항은 유지된다.)"

**문제 설명**: 이 문장에서 "모든 DDL은 허용된다"라고 해놓고 바로 뒤에 "단, 기존의 제약사항은 유지된다"라는 예외를 붙였는데, "기존의 제약사항"이 구체적으로 무엇을 가리키는지(리뷰 9에서 지적한 대로 PK 중복 금지 같은 CUBRID 원래 제약을 말하는지, 아니면 §4-2에서 새로 설명하는 RK 관련 제약 중 일부가 여전히 남는다는 뜻인지) 이 문장만으로는 알 수 없습니다. "모든 DDL이 허용된다"와 "그러나 일부 제약은 유지된다"가 동시에 성립하는 예시가 본문에 제시되지 않았습니다.

**구체 예제(시나리오)**:
```sql
-- 복제키 후보가 2개(a=PK, b=UK)인 테이블
csql> CREATE TABLE t(
    a INT PRIMARY KEY,
    b INT NOT NULL UNIQUE,
    c INT
);
-- RK로 a(PK)가 선택되었다고 가정. §4-2에 따르면 "다른 후보(b)가 있으므로 모든 DDL 허용"

csql> ALTER TABLE t DROP PRIMARY KEY;
-- 스펙 문장 그대로라면 "모든 DDL 허용"이므로 OK여야 할 것 같지만,
-- 상식적으로는 "하나의 테이블에 PK가 없어질 수 있다"는 CUBRID 일반 규칙상
-- 문제 없는 연산이라 OK가 맞을 수도 있음.
-- 그런데 "기존의 제약사항은 유지된다"는 단서가 무엇을 막는지
-- 구체적으로 어떤 DDL이 여전히 실패하는지 예시가 전혀 없어
-- 위 ALTER의 실제 결과를 스펙만으로는 확신할 수 없다.
```

**예제 설명**: "모든 DDL이 허용된다"는 표현은 강력한 일반화인데, 그 직후 붙는 예외 조항이 매우 모호합니다. 신입 사용자가 실제로 어떤 DDL이 이 예외에 걸려 실패하는지 판단할 근거가 본문에 없습니다.

**제안**: "기존의 제약사항"이 가리키는 구체적인 항목을 나열하고(예: "PK는 테이블당 1개만 허용" 같은 CUBRID 기존 규칙), 후보가 2개 이상인 상태에서 실제로 실패하는 DDL 예시를 최소 1개 추가해야 합니다.
