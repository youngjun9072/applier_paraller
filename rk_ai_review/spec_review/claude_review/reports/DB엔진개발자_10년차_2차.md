# CUBRID HA 복제 키(RK) / REPLICATION 옵션 스펙 리뷰 — DB 엔진 개발자(10년차) 관점 · 2차 라운드

## 2차 라운드 개요

1차 리뷰(20건)에서는 RK 선택 비결정성, RK 전환 시 복제 로그 정합성, Multiple ALTER의 원자성, unloaddb 기본값 모순 등 스펙의 핵심 골격 결함을 다뤘다. 최종 종합 보고서 역시 20개 리뷰어가 같은 지점(§8/§9 모순, FK 사후 OFF 전환, RK 조회 불가, §7 파일 리스트 등)을 이미 높은 합의도로 포착해 두었다. 이번 2차 라운드는 그 골격을 다시 건드리지 않고, 스펙이 아예 침묵하고 있는 주변 객체·계층 — TDE(투명 데이터 암호화), collation(문자열 비교 규칙), 카탈로그 캐시를 공유하는 CUBRID의 멀티프로세스 아키텍처, 권한/감사, unload-load 왕복 무결성, 대용량 적재 파이프라인, failback(재합류) — 과 RK/REPLICATION 기능이 만나는 지점에서 아직 아무도 짚지 않은 실패 모드를 찾는 데 집중했다. 그 결과 치명 등급의 새 발견은 없었고(핵심 골격 결함은 1차·최종보고서가 이미 소진했다는 뜻으로 해석한다), "구현에 착수하면 반드시 결정해야 하지만 스펙에 답이 없는" 중요~보통 등급의 항목 9건을 신규로 정리했다.

### 리뷰 21

**[심각도: 중요] TDE 암호화 테이블의 RK 값이 복제 로그에서 평문인지 암호문인지 미정의**

- 대상: §2-3 예시 9의 `db_class` 조회 결과에 등장하는 `tde_algorithm: 'NONE'` 필드, §1 RK 정의 전체

`db_class`에 `tde_algorithm`이라는 필드가 이미 존재한다는 것은 CUBRID가 테이블 단위 투명 데이터 암호화(TDE, Transparent Data Encryption — 디스크에 저장되는 데이터를 암호화해 볼륨을 통째로 탈취당해도 내용을 못 읽게 하는 기능)를 지원한다는 뜻이다. 그런데 이 스펙은 TDE가 걸린 테이블의 PK/UK가 RK로 선택될 수 있는지, 그리고 그 경우 복제 로그(마스터에서 슬레이브로 전달되는 변경분 기록)에 RK 컬럼 값이 어떤 형태로 실리는지 전혀 언급하지 않는다. 저장 엔진 계층에서는 페이지가 암호화되어 있어도, 복제 로그를 만드는 모듈이 이미 복호화된 레코드에서 값을 읽어 로그를 구성한다면 로그 자체에는 평문이 실린다. 반대로 로그 생성이 저장 계층보다 아래(암호화된 페이지 이미지 레벨)에서 이뤄진다면 슬레이브가 복호화 키 없이는 RK 값 자체를 알 수 없어 행 매칭이 불가능하다.

```sql
CREATE TABLE customer_secrets (
    ssn CHAR(13) NOT NULL UNIQUE,   -- TDE 대상 컬럼이자 RK 후보(UK)
    name VARCHAR(50)
) ENCRYPT='AES', REPLICATION = ON;   -- TDE 문법은 예시이며 실제 CUBRID 문법과 다를 수 있음

UPDATE customer_secrets SET name = 'Kim' WHERE ssn = '123-45-6789';

-- 질문:
-- 1) 이 UPDATE의 복제 로그에 실리는 RK 값(ssn)은 평문 '123-45-6789'인가, 암호문 바이트열인가?
-- 2) 마스터와 슬레이브가 서로 다른 TDE 마스터키(키 로테이션, 노드별 개별 키 관리)를 쓴다면
--    슬레이브는 이 RK 값으로 대상 행을 어떻게 찾는가?
```

**예제 설명**: TDE는 "이 컬럼은 디스크에서도 평문으로 보이면 안 된다"는 기밀성 요구사항에서 도입되는 기능이다. 만약 복제 로그가 평문 RK 값을 그대로 담는다면, TDE로 보호하려던 값이 결국 복제 파이프라인 어딘가(로그 파일, 네트워크 버퍼)에는 평문으로 존재하게 되어 TDE 도입 취지가 부분적으로 무력화된다. 반대로 로그가 암호문을 담는다면 키 관리(마스터/슬레이브가 같은 키를 공유해야 하는지, 키 로테이션 시 진행 중인 복제는 어떻게 되는지)라는 완전히 새로운 운영 축이 생기는데, 이 역시 스펙에 없다. 이 문제는 REUSE_OID(1차 리뷰 20)와 마찬가지로 "타 DBMS 사례를 참고할 수 없는 CUBRID 고유 조합"이라 반드시 엔진 구현자가 직접 답을 정해야 한다.

**제안**: 복제 로그 생성 모듈이 TDE 계층보다 상위(논리 레벨, 평문 값)에서 동작함을 명시하고, TDE 테이블을 REPLICATION=ON으로 둘 때 마스터/슬레이브 간 TDE 키 관리 정책(공유 키 필수 여부, 키 로테이션 중 복제 동작)을 별도 절로 규정할 것.

### 리뷰 22

**[심각도: 중요] TDE는 저장 시 암호화를 보장하지만 복제 채널(네트워크 전송 구간)의 기밀성은 스펙에서 다루지 않음**

- 대상: 배경 컨텍스트(PostgreSQL REPLICA IDENTITY 채용) 및 스펙 전체, §2-3 예시 9 `tde_algorithm`

리뷰 21이 "RK 매칭이 되느냐"는 정합성 문제였다면, 이 리뷰는 순수 보안 문제다. TDE는 디스크에 남는 데이터(at rest)를 암호화하는 기능이고, HA 복제는 마스터의 변경분을 네트워크를 통해 슬레이브로 스트리밍하는 것이므로 본질적으로 "in transit"(전송 중) 데이터다. TDE가 at-rest 기밀성만 보장하고 복제 채널 자체는 암호화되지 않는다면, TDE로 보호하려던 민감 컬럼이 REPLICATION=ON으로 설정되는 순간 네트워크 스니핑(패킷 감청)에 완전히 노출된다.

```sql
CREATE TABLE payment_cards (
    card_number CHAR(16) NOT NULL UNIQUE,  -- TDE 적용, RK 후보
    holder VARCHAR(50)
) ENCRYPT='AES', REPLICATION = ON;

-- 마스터의 디스크 파일: card_number는 암호화되어 저장됨 (TDE가 보장하는 부분)
-- 마스터 -> 슬레이브 HA 복제 스트림: card_number가 평문으로 네트워크에 실려 나가는가?
-- 이 스펙과 기존 CUBRID HA 문서 어디에도 "복제 채널 암호화(TLS 등)" 언급이 없다면
-- 결과적으로 TDE를 켠 테이블이 REPLICATION=ON이 되는 순간 오히려 평문 노출 지점이
-- "디스크"에서 "사내망을 지나는 복제 트래픽"으로 옮겨갈 뿐일 수 있다.
```

**예제 설명**: 보안 감사자나 컴플라이언스 담당자는 "이 컬럼에 TDE가 걸려 있다"는 사실만 보고 안전하다고 판단하기 쉽다. 하지만 REPLICATION=ON과 TDE는 서로 독립적인 축이라, 두 기능이 동시에 켜졌을 때 실제 보호 범위가 어디까지인지 스펙이 답하지 않으면 "TDE를 도입했는데 복제 트래픽에서 카드번호가 그대로 흘렀다"는 사고가 감사 시점에야 발견될 수 있다.

**제안**: HA 복제 채널의 전송 구간 암호화 지원 여부(TLS 등 기존 기능이 있다면 그것으로 충분한지)를 명시하고, TDE 테이블을 REPLICATION=ON으로 설정할 때 전송 구간 암호화가 강제되는지, 아니면 사용자가 별도로 켜야 하는지 문서에 못박을 것.

### 리뷰 23

**[심각도: 중요] COLLATE 변경이 RK로 쓰이는 UK의 유일성 가정과 물리적 키 매칭을 흔들 수 있음**

- 대상: §2-3 예시 8 (`show create table` 출력의 `COLLATE utf8_bin`), §1 "NOT NULL UNIQUE"

UNIQUE 제약의 "유일함" 판정은 컬럼의 collation(대소문자·발음 구별 부호 등을 같은 값으로 볼지 다른 값으로 볼지를 정하는 문자열 비교 규칙)에 의존한다. 예시 8은 `COLLATE utf8_bin`(바이트 단위 비교, 대소문자를 다르게 봄)을 보여주는데, 만약 사용자가 나중에 대소문자를 구분하지 않는 collation으로 바꾸면 예전에는 서로 다른 값으로 허용되던 두 행이 새 규칙으로는 같은 값이 되어 유일성 제약을 위반하는 상태가 될 수 있다. 이 컬럼이 RK로 쓰이고 있다면 문제는 한 단계 더 깊어진다 — 복제 로그의 키 값 매칭이 collation을 고려한 논리적 비교로 이뤄지는지, 아니면 바이트 단위 비교로 이뤄지는지가 스펙에 없다.

```sql
CREATE TABLE t (
    email VARCHAR(100) NOT NULL UNIQUE  -- RK 후보(유일한 UK), collate utf8_bin(기본값 가정)
);
INSERT INTO t VALUES ('User@Example.com');
INSERT INTO t VALUES ('user@example.com');   -- utf8_bin 기준으로는 다른 값이므로 OK

-- 이후 이 컬럼의 collation을 대소문자 구분 없는 규칙으로 변경
ALTER TABLE t MODIFY COLUMN email VARCHAR(100) NOT NULL UNIQUE COLLATE utf8_en_ci;
-- (문법은 예시. 실제 CUBRID 구문과 다를 수 있음)

-- 질문 1: 이 ALTER는 기존 데이터('User@Example.com'과 'user@example.com'이 새 규칙으로는
--          같은 값)를 재검증해 실패해야 하는가, 조용히 통과하는가?
-- 질문 2: 통과했다면, 이후 슬레이브에서 "email = 'user@example.com'" 조건으로 행을 찾을 때
--          두 행 중 어느 것을 갱신해야 하는지 판단 기준이 무엇인가?
```

**예제 설명**: 이 시나리오는 RK가 "값이 절대 안 바뀌는 안정적인 키"라는 암묵적 전제를 collation 변경이라는, 컬럼 값 자체는 건드리지 않는 DDL 하나로 깨뜨릴 수 있음을 보여준다. §4-2는 UNIQUE 제약을 직접 DROP하거나 컬럼을 삭제하는 경로만 막을 뿐(1차 리뷰 참고), collation 변경처럼 "제약은 그대로 두고 비교 규칙만 바꾸는" 경로는 §4-2의 논의 대상에 포함되어 있지도 않다.

**제안**: RK로 쓰이는 컬럼(또는 그 컬럼이 속한 UK 전체)의 collation 변경 시 기존 데이터에 대한 유일성 재검증을 강제하도록 §4-2에 추가하고, 복제 로그의 RK 값 매칭이 어느 collation 기준(로그 생성 시점 vs 적용 시점)으로 이뤄지는지 명시할 것.

### 리뷰 24

**[심각도: 중요] unload/load 왕복 시 §8의 "자동으로 RK를 할당한다"가 원본 RK와 다른 결과를 낼 수 있음(백업·복원 무결성)**

- 대상: §8 "복제 테이블의 경우 큐브리드는 자동으로 RK를 할당한다"

이 한 문장은 unload 시점에 "이 테이블의 RK가 구체적으로 무엇이었는지"는 저장하지 않고, load 시점에 §1의 선택 규칙을 처음부터 다시 적용해 RK를 계산한다는 것을 암시한다. 그런데 §1의 선택 기준 자체가 "테이블 내 명시된 순서 중 가장 빠른 순서"처럼 텍스트 직렬화 순서에 의존하는 모호한 규칙이다(1차 리뷰 2에서 지적). unload가 만드는 스키마 파일(.schema)에서 제약조건이 나열되는 순서가 원본 카탈로그에 등록된 순서와 항상 동일하다는 보장이 스펙 어디에도 없다 — unload 유틸리티가 내부적으로 시스템 카탈로그를 순회하는 순서(예: 제약 이름 알파벳순, 내부 ID순)가 원래 CREATE TABLE 문에서 사용자가 선언한 순서와 다를 수 있기 때문이다.

```
# 원본 운영 DB
CREATE TABLE t (
    a INT NOT NULL UNIQUE,   -- 원래 이 순서로 생성되어 RK = a 로 정착(sticky)됨
    b INT NOT NULL UNIQUE
);
-- (오랜 운영 중 여러 ALTER를 거쳐 카탈로그 내부 등록 순서가 이미 뒤섞여 있을 수 있음)

$ cubrid unloaddb -i prod_db backup_output
# backup_output.schema 파일에 UNIQUE(a), UNIQUE(b) 가 어떤 순서로 적히는지는
# "CREATE TABLE 원문 재현"이 목적인 unload 로직의 구현 세부에 달려 있다.

$ cubrid loaddb -d restored_db backup_output.schema
# restore된 restored_db에서 RK가 다시 a로 계산되는가, 아니면 b로 계산되는가?
# 원본 prod_db의 RK와 다르면, 백업에서 복원한 DB로 HA를 새로 구성했을 때
# 복제 동작(어느 컬럼으로 행을 식별하는지)이 원본 운영 환경과 달라진다.
```

**예제 설명**: 백업/복원은 재해복구(DR), 환경 복제(스테이징 구성), 마이그레이션에 광범위하게 쓰이는 핵심 운영 절차다. "복원한 DB가 원본과 똑같이 동작해야 한다"는 것은 백업 유틸리티에 대한 가장 기본적인 기대인데, RK가 unload/load 왕복 과정에서 재계산되고 그 계산 기준 자체가 비결정적이면 이 기대가 깨진다. 이는 1차 리뷰 2(ALTER 시점의 비결정성)와 근본 원인은 같지만, 발생 지점이 완전히 다르다 — ALTER를 한 번도 실행하지 않고 순수하게 백업·복원만 했는데도 RK가 바뀔 수 있다는 것이 이 리뷰의 핵심이다.

**제안**: unload 시 현재 RK로 선택된 제약조건을 스키마 파일에 명시적으로 표기(예: 별도 메타 필드 또는 주석)하고, load 시 이 정보가 있으면 §1 규칙 재계산보다 우선 적용하도록 §8에 규칙을 추가할 것. 최소한 "unload/load 왕복 후 RK가 원본과 달라질 수 있다"는 주의사항을 문서화할 것.

### 리뷰 25

**[심각도: 보통] 대용량 loaddb의 "선 데이터 적재, 후 인덱스 생성" 파이프라인이 §1의 RK 불변식을 일시적으로 위반**

- 대상: §8, §1 "복제 테이블은 RK가 존재해야 한다"는 불변식

대량 데이터를 빠르게 적재해야 하는 상황에서는 흔히 (1) 제약 없이 컬럼만 있는 스키마로 테이블 생성 → (2) 데이터 대량 적재 → (3) 이후 PK/UK 등 제약과 인덱스를 별도로 생성하는 3단계 파이프라인을 쓴다. 인덱스가 있는 상태로 대량 INSERT를 하면 매 행마다 인덱스 갱신 비용이 들지만, 인덱스 없이 적재한 뒤 한 번에 인덱스를 빌드하면 훨씬 빠르기 때문이다. 이 파이프라인의 2단계(데이터 적재 완료, 제약 생성 전) 시점에는 테이블에 RK가 전혀 없는 상태로 데이터가 존재한다.

```
$ cubrid loaddb -d mydb -s schema_no_constraints.txt
  # schema_no_constraints.txt: CREATE TABLE big_orders(order_id INT, customer_id INT, amount INT);
  # REPLICATION 옵션 생략 -> §2-1에 따라 기본 ON으로 생성됨. 이 시점 RK 없음.

$ cubrid loaddb -d mydb -c data_only object_file
  # 수백만 건 적재. 이 순간 "RK 없는 REPLICATION=ON 테이블에 데이터가 존재"하는 상태.

$ csql -c "ALTER TABLE big_orders ADD CONSTRAINT PRIMARY KEY(order_id);" mydb
  # 이제야 RK가 생김.

-- 질문: 2단계와 3단계 사이, 만약 이 작업이 싱글 모드가 아니라 HA 운영 중(§4 상황)이었다면
-- 그 사이에 커밋된 데이터에 대한 복제 로그는 어떻게 처리되는가? RK가 없으므로
-- 배경 문서가 말하는 "복제 누락 + fail_count 증가"가 이 파이프라인 자체에서 재현되지 않는가?
```

**예제 설명**: §3은 "싱글 모드에서 생성된 RK 없는 테이블은 HA 전환 시 조치하면 된다"고 하므로, 이 파이프라인이 싱글 모드에서만 실행된다면 문제가 되지 않는다. 하지만 스펙은 이 파이프라인이 반드시 싱글 모드에서만 허용된다고 명시하지 않았고, 실무에서는 온라인 상태(HA 운영 중)에 대용량 데이터를 추가하면서 인덱스를 나중에 붙이는 최적화가 드물지 않다. 이 경우 이 스펙이 원래 해결하려던 문제(PK 없는 테이블의 복제 누락)가 "느린 온라인 DDL을 피하려는 정상적인 운영 관행" 자체에서 재발할 수 있다.

**제안**: loaddb의 "데이터 우선, 인덱스 후행" 파이프라인이 HA 운영 중에 수행될 경우의 동작(그 기간 동안 해당 테이블을 일시적으로 REPLICATION=OFF로 강제 취급하거나, 혹은 이런 파이프라인 자체를 HA 운영 중에는 거부)을 §8 또는 §4에 명시할 것.

### 리뷰 26

**[심각도: 보통] REPLICATION 플래그 변경 권한 모델과 감사(audit) 추적이 정의되지 않음**

- 대상: §2-2 전체, §2-3 예시 9 (`owner_name` 필드)

예시 9의 `db_class` 조회 결과에 `owner_name: 'DBA'`가 있다는 것은 CUBRID에 테이블 소유자 개념이 명확히 존재한다는 뜻이다. 그런데 `ALTER TABLE ... REPLICATION={ON|OFF}`를 실행할 수 있는 권한이 "테이블 소유자면 누구나"인지, 별도 시스템 권한(DBA 전용)이 필요한지 스펙에 없다. REPLICATION 옵션은 개별 테이블 관점에서는 사소한 속성처럼 보이지만, 실제로는 클러스터 전체의 재해복구(DR) 보장 범위를 결정하는 운영 정책 값이다. 게다가 누가 언제 이 값을 바꿨는지 추적할 수 있는 감사 로그에 대한 언급도 없다.

```sql
-- 일반 애플리케이션 계정(테이블 소유자, DBA 아님)으로 접속
csql> ALTER TABLE regulatory_audit_log REPLICATION = OFF;
-- 이 문장이 성공하는지 실패하는지 스펙에 답이 없다.
-- 성공한다면: 규제 준수를 위해 반드시 DR 사이트에 남아야 하는 테이블이
-- 애플리케이션 계정의 실수 또는 악의적 변경 한 줄로 조용히 복제 대상에서 빠질 수 있다.
-- 그리고 "누가, 언제, 왜 이 값을 바꿨는지"를 사후에 확인할 표준 카탈로그/로그가 없다.
```

**예제 설명**: 금융권 등 규제 산업에서는 "이 테이블은 반드시 DR 사이트에 복제되어야 한다"는 컴플라이언스 요구사항이 흔하다. REPLICATION 옵션이 테이블 소유자 권한만으로 자유롭게 뒤집을 수 있는 값이라면, 이 기능 자체가 규제 우회 경로로 악용되거나 실수로 오남용될 수 있다. §5(외래키)나 §7(HA 전환)이 그 결과(참조 무결성 깨짐, HA 기동 실패)는 다루지만, 애초에 "누가 이 값을 바꿀 자격이 있는가"라는 더 앞단의 질문에는 침묵한다.

**제안**: REPLICATION 옵션 변경에 필요한 최소 권한(테이블 소유자로 충분한지, DBA 전용 GRANT가 필요한지)을 §2-2에 명시하고, 변경 이력(변경 시각·수행 계정·이전 값)을 조회 가능한 형태로 카탈로그나 시스템 로그에 남기도록 요구사항을 추가할 것.

### 리뷰 27

**[심각도: 중요] 이미 연결된 세션의 카탈로그 캐시가 RK 변경 ALTER 커밋 이후에도 갱신되지 않을 위험(캐시 전파 문제)**

- 대상: §4-2 전체, CUBRID의 멀티프로세스 구조(브로커를 통한 다수의 독립 서버 프로세스가 하나의 DB를 공유)

1차 리뷰 4·5는 ALTER 문 자체가 원자적으로 처리되는지와, 동시에 실행되는 두 개의 DDL이 경합할 때의 문제를 다뤘다. 이 리뷰는 그와는 다른 계층 — ALTER가 이미 정상적으로 커밋된 **이후**에 발생하는 전파 지연 문제를 다룬다. CUBRID는 하나의 데이터베이스에 대해 여러 클라이언트 연결이 각자 독립된 서버 프로세스(혹은 그에 준하는 세션 컨텍스트)로 서비스되며, 일반적으로 이런 구조에서는 각 프로세스가 스키마·제약조건 정보를 자신의 로컬 캐시에 들고 있다가 필요 시점에만 갱신한다. RK를 바꾸는 ALTER가 세션 X에서 커밋된 직후, 커넥션 풀에 오래 유지되고 있던 세션 Y가 자신의 캐시된 스키마 정보를 아직 갱신하지 않은 채 DML을 실행하면, 그 DML이 만들어내는 복제 로그가 이미 폐기된 구(舊) RK 기준으로 기록될 위험이 있다.

```
-- 세션 X (신규 연결): RK 변경
ALTER TABLE tbl DROP CONSTRAINT PRIMARY KEY, ADD CONSTRAINT UNIQUE(b);
COMMIT;   -- 카탈로그 상 RK는 이제 UK(b). 이 트랜잭션 자체는 정상적으로 완결됨.

-- 세션 Y (몇 시간째 유지 중인 커넥션 풀의 커넥션, 애플리케이션 서버가 재사용 중)
-- 세션 Y의 로컬 스키마 캐시는 아직 "RK = PK(a)"로 기억하고 있을 수 있음
INSERT INTO tbl (a, b, c) VALUES (10, 20, 30);
-- 이 INSERT가 만드는 복제 로그의 RK 관련 메타데이터가
-- 세션 Y의 캐시된(낡은) 스키마 기준으로 잘못 기록되지는 않는가?
```

**예제 설명**: 이 문제는 ALTER 문 자체의 정확성과 무관하게, 여러 독립 프로세스가 하나의 카탈로그를 나눠보는 구조에서 흔히 발생하는 "캐시 무효화 전파" 클래스의 버그다. 웹 애플리케이션은 보통 커넥션 풀을 오래 유지하며 재사용하므로, ALTER 직후 짧은 시간 안에 이런 낡은 캐시를 가진 세션이 DML을 실행할 가능성은 실무에서 결코 낮지 않다. 스펙은 ALTER 문의 SQL 표면 동작만 다룰 뿐, 이 전파 문제를 다룰 필요성 자체를 인식하지 못한 것으로 보인다.

**제안**: RK를 변경하는 DDL이 커밋될 때 모든 활성 세션의 관련 카탈로그 캐시를 무효화하는 브로드캐스트가 반드시 수반됨을 명시하고(기존 CUBRID의 스키마 변경 알림 체계가 이미 이런 경우를 처리한다면 그 사실을, 처리하지 못한다면 개선이 필요하다는 것을 스펙에 남길 것), 무효화가 완료되기 전까지 해당 테이블에 대한 DML을 지연시키는 등의 안전장치 여부를 §4-2에 규정할 것.

### 리뷰 28

**[심각도: 보통] ADD PRIMARY KEY 한 줄로 인해 사용자가 의도하지 않은 RK가 조용히 승격됨**

- 대상: §4-2 예시 14 "UK를 복제키로 사용하고 있는 테이블은 PK가 없으므로 추가 가능(기존과 동일)", §1 "PK가 존재한다면 PK가 복제 키가 됨"

예시 14는 "UK가 RK인 테이블에 PK를 추가하는 것이 OK"라는 결과만 보여준다. 그런데 §1의 우선순위 규칙("PK가 존재한다면 PK가 복제 키가 됨")을 그대로 적용하면, 이 `ADD CONSTRAINT PRIMARY KEY` 한 줄은 부수효과로 기존 UK 기반 RK를 새로 추가된 PK로 즉시 대체한다. 사용자의 실제 의도는 단순히 "이 테이블에 PK가 없었으니 정석대로 하나 추가하자"는 흔한 스키마 정비 작업일 뿐, RK를 바꾸겠다는 의도가 전혀 없었을 수 있다. 그럼에도 이 ALTER는 조용히 OK로 성공하고 RK를 바꾼다.

```sql
CREATE TABLE t (
    email VARCHAR(100) NOT NULL UNIQUE,   -- RK로 선택됨(유일한 UK)
    a INT, b INT, c INT
);
-- 운영 중 RK = email 로 정착. 복제 로그는 email 값 기준으로 행을 식별.

-- 몇 달 뒤 다른 팀이 "이 테이블에 대리키(surrogate key)가 없다"는 이유로 PK를 추가
ALTER TABLE t ADD CONSTRAINT PRIMARY KEY (a, b, c);   -- 예시 14 기준 OK
-- §1 규칙대로면 RK가 email(단일 인덱스 컬럼) 에서 (a,b,c) 복합 PK로 즉시 전환된다.
-- 이 팀은 "RK를 바꾼다"는 인식 없이 실행했지만, 결과적으로
--  1) 복제 로그에 실리는 키가 좁은 단일 값에서 넓은 복합 값으로 바뀌어 로그 볼륨이 늘고
--  2) 다른 코드/모니터링이 "RK=email"이라고 가정하고 있었다면 그 가정이 조용히 깨진다.
```

**예제 설명**: 이 시나리오는 리뷰 24(unload/load 왕복)나 1차 리뷰 2(ALTER 시점 재정렬)와 달리, 사용자가 RK와 무관한 목적으로 실행한 지극히 정상적인 DDL이 §1의 우선순위 규칙 때문에 부수효과로 RK를 바꾸는 경우다. 스펙 어디에도 이런 부수효과에 대한 경고나 확인 절차가 없다.

**제안**: PK 추가로 인해 기존 RK(UK)가 대체되는 경우, 이를 무경고 OK로 처리하지 말고 "RK가 `<기존 UK명>`에서 `<신규 PK명>`으로 변경됨"이라는 안내(NOTICE/WARNING)를 반환하도록 §4-2에 추가할 것.

### 리뷰 29

**[심각도: 중요] Failback(장애 복구된 구 마스터의 재합류) 시 서로 다른 RK 변경 이력을 가진 두 노드의 재동기화 절차 미정의**

- 대상: 스펙 전체(failover는 §5 배경에서 언급되나 failback은 전혀 언급되지 않음), §4-2

HA 환경에서는 failover(슬레이브가 마스터로 승격)만 일어나는 것이 아니라, 장애가 복구된 구 마스터가 새 마스터의 슬레이브로 재합류하는 failback도 정상적인 운영 시나리오다. 스펙은 배경 다이어그램에서 failover 이후의 FK 문제(§5)만 다룰 뿐, failback 시나리오는 전혀 등장하지 않는다. 그런데 failover가 일어난 뒤 새 마스터에서 RK를 바꾸는 ALTER가 여러 번 발생했다고 가정하면, 재합류하는 구 마스터는 자신이 마스터였던 마지막 순간의 카탈로그(RK 상태)를 그대로 갖고 있다. 재합류 절차(보통 특정 LSA 이후의 로그를 이어받아 따라잡는 catch-up 방식)가 이 사이에 있었던 여러 번의 RK 전환 DDL을 순서대로 재생하지 않고 최신 스냅샷만 한 번에 적용한다면, §4-2가 요구하는 "RK가 0개가 되는 순간이 없어야 한다"는 전제가 catch-up 과정 자체에서 깨질 수 있다.

```
1. Master(A) - Slave(B) 구성, tbl의 RK = PK(x)

2. A 장애 -> B가 마스터로 승격(failover). 이 시점 B의 tbl RK = PK(x)

3. 새 마스터 B에서 운영 중 RK 전환 발생:
   ALTER TABLE tbl DROP CONSTRAINT PRIMARY KEY, ADD CONSTRAINT UNIQUE(y);  -- RK: x -> y
   (이후 한 번 더)
   ALTER TABLE tbl ADD CONSTRAINT PRIMARY KEY(z);  -- RK: y -> z (리뷰 28 패턴)

4. A가 복구되어 B의 슬레이브로 재합류(failback) 시도
   -- A의 카탈로그는 여전히 "RK = PK(x)"인 채로 멈춰 있음
   -- catch-up 로그 재생이 x->y->z 전환을 순서대로 밟는가, 아니면 "최종 상태 z"로 한 번에
   --   스냅샷을 받아오는가? 후자라면 그 사이 x, y 기준으로 기록된 DML 로그를
   --   어떤 RK 문맥으로 해석해 적용해야 하는지가 미정의다.
```

**예제 설명**: 이 시나리오는 1차 리뷰 12(체인 복제·멀티 슬레이브에서 RK 발산)의 사촌 격이지만, 방향이 다르다 — 리뷰 12는 "여러 슬레이브가 지연 때문에 일시적으로 다른 RK를 인지하는" 정상 운영 중의 지연 문제였다면, 이 리뷰는 "한 번 마스터였다가 슬레이브로 강등되어 재합류하는 노드가 자신이 놓친 스키마 이력 전체를 다시 따라잡아야 하는" failback 고유의 문제다. failover는 스펙이 명시적으로 다루지만 failback은 언급조차 없다는 것 자체가, 이 기능이 "정상 운영 중 한 방향 전파"만 가정하고 설계되었다는 신호다.

**제안**: failback(재합류) 절차에서 카탈로그 스키마 변경(RK 전환 포함) 로그도 다른 DML 로그와 동일하게 순서대로 재생되어 중간 상태를 건너뛰지 않음을 보장하고, 재합류가 완료되어 카탈로그가 완전히 따라잡히기 전까지는 해당 테이블에 대한 재합류 노드로의 트래픽 라우팅(혹은 그 노드가 다시 마스터가 되는 것)을 차단하도록 §7 또는 별도의 "재합류" 절에 명시할 것.

## 조사 종료 선언

이번 2차 라운드에서는 1차 리뷰와 최종 종합 보고서가 다루지 않은 다음 영역을 훑었다: TDE(암호화)와 RK/복제 채널의 상호작용, collation 변경과 RK 유일성의 관계, unload/load 왕복 시 RK 재계산 문제, 대용량 적재(loaddb) 파이프라인과 RK 불변식의 충돌, REPLICATION 옵션의 권한/감사 모델, CUBRID 멀티프로세스 구조에서의 카탈로그 캐시 전파, PK 추가로 인한 RK의 부수효과적 변경, failback(재합류) 시나리오. 이 중 실제로 "구현 착수 전에 반드시 답이 필요한" 실패 모드로 좁혀 9건을 남겼다.

다음 영역은 훑어봤지만 신규 항목으로 올리지 않았다: 파티션·트리거·시리얼(AUTO_INCREMENT)·REUSE_OID는 1차 리뷰 9·10·11·20에서 이미 다뤘고, 여기서 떠오른 추가 변형들(파티션별 RK 차등, 트리거 체인 등)은 근본 원인이 1차 리뷰와 동일해 재포장에 그친다고 판단해 제외했다. 에러 코드 체계·멀티 슬레이브 확장성·용어 일관성은 최종 종합 보고서가 이미 M-6·M-9·N-7·T-6으로 높은 합의도를 확보했다. 필터드/부분 인덱스, 계산된(가상) 컬럼, 파티션 익스체인지 같은 항목은 CUBRID가 해당 기능을 실제로 어떤 형태로 지원하는지 스펙과 배경 문서만으로는 근거가 부족해, 확인되지 않은 추측을 지적으로 포장하지 않기 위해 의도적으로 제외했다.

**추가 여지**: 남아 있다면 카탈로그 캐시 무효화(리뷰 27)를 실제 CUBRID 소스(브로커·cub_server 코드)로 검증하는 것, 그리고 TDE 관련 두 건(리뷰 21·22)을 CUBRID의 실제 TDE 구현 문서와 대조하는 것 정도이며, 이는 스펙 리뷰가 아니라 코드 분석 영역이라 이 문서의 범위를 벗어난다고 본다.
