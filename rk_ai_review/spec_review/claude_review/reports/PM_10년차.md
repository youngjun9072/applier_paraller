# CUBRID HA 복제 개선 스펙 리뷰 — PM(10년차) 관점

## 리뷰어 소개

10년차 프로덕트 매니저로서 DBMS 계열 제품의 기능 스펙을 요구사항 완전성, 하위 호환성,
마이그레이션 경로, 릴리스 리스크, 문서 품질, 경쟁 제품 포지셔닝의 축으로 검토해왔다.
코드 레벨 구현 세부사항보다는 "이 기능을 실제 고객이 프로덕션에 적용했을 때 무엇이
깨지는가", "이 스펙만 보고 영업·지원·QA·문서팀이 각자 자기 몫을 해낼 수 있는가"를
기준으로 판단한다. 아키텍처 관점에서는 이번 설계 철학이 장기적으로 유지보수 가능한
구조인지, 타 DBMS(MySQL, PostgreSQL, Oracle)가 이미 해결한 동일 문제와 비교했을 때
CUBRID가 어떤 위치에 서는지, 그리고 멀티 슬레이브·체인 복제 같은 향후 확장 요구와
충돌하지 않는지도 함께 본다.

## 총평

이번 스펙은 "PK가 없으면 HA 복제가 조용히 깨진다"는 실제 장애를 막기 위한 방향 자체는
타당하다. 그러나 문서를 프로덕트 매니저 시각에서 읽으면 세 가지가 눈에 띄게 부족하다.
첫째, **기존 고객의 마이그레이션 경로**가 사실상 기술되어 있지 않다 — 이미 HA를 운영 중인
고객이 이 변경을 적용받는 순간 무슨 일이 일어나는지에 대한 서술이 없다. 둘째, **RK 자동
선택 규칙이 확정된 알고리즘이 아니라 예시("ex.")로만 제시**되어 있어, 이 스펙만으로는
동일 조건에서 항상 같은 RK가 뽑힌다는 보장을 문서가 스스로 하지 못한다. 셋째, **경쟁
제품 대비 포지셔닝과 확장성(멀티 슬레이브·체인 복제) 논의가 전혀 없다** — PostgreSQL의
REPLICA IDENTITY를 "일부 채용"했다고만 적고, 무엇을 채용하지 않았는지, 그로 인해 어떤
기능이 CUBRID에는 없는지에 대한 의도적 트레이드오프 설명이 없다. 여기에 더해 스펙 본문의
SQL 예제 중 최소 2건은 구문 오류를 그대로 포함하고 있어, 이 문서가 QA 테스트케이스나
사용자 매뉴얼의 기초 자료로 그대로 쓰이기에는 손이 더 가야 한다. 아래 20개 리뷰는 이러한
문제를 심각도별로 정리한 것이다.

## 리뷰 1

**[심각도: 치명] RK 자동 선택 알고리즘이 확정된 규칙이 아니라 예시로만 제시됨**

**대상**: §1 제약 사항, "UK가 여러개 존재한다면 큐브리드 엔진에 의해 이 중 하나가
선택된다(ex. 테이블내에 명시된 순서 중 가장 빠른 순서)"

**문제 설명**: 복제 키(RK: Replication Key, 슬레이브에 데이터를 반영할 때 어느 행을
갱신/삭제할지 식별하는 데 쓰이는 키)는 이 스펙 전체의 핵심 개념이다. 그런데 UK(Not Null
Unique Key, NULL을 허용하지 않는 고유 제약)가 여러 개 있을 때 어떤 것이 RK로 선택되는지
설명하면서 "ex."(예시)라는 표현을 썼다. "예시"는 "여러 방법 중 하나를 보여주는 것"이지
"확정된 알고리즘"이 아니다. 즉 이 문장만 읽으면 실제 선택 규칙이 "테이블 내 명시 순서상
가장 빠른 것"인지, 아니면 다른 기준(예: 컬럼 개수가 적은 UK 우선, 인덱스 생성 시각 우선)이
적용될 수도 있는지 문서 자체가 답을 주지 않는다. 이는 단순한 문서 표현 문제가 아니라
제품 계약(behavior contract)의 문제다 — 고객이 어떤 UK가 RK가 될지 예측할 수 있어야
장애 발생 시 "왜 이 UK가 선택됐는지" 지원팀이 설명할 수 있고, 버전 업그레이드 후에도
같은 UK가 계속 선택된다는 보장이 있어야 한다.

**구체 예제**:
```sql
-- 하나의 테이블에 UK 후보가 두 개 존재
CREATE TABLE members(
    id        INT,
    email     VARCHAR(100) NOT NULL,
    ssn       VARCHAR(20)  NOT NULL,
    CONSTRAINT uk_email UNIQUE (email),
    CONSTRAINT uk_ssn   UNIQUE (ssn)
);
-- HA 모드 전환 시 RK로 uk_email이 선택되는가, uk_ssn이 선택되는가?
-- 컬럼 선언 순서(email이 먼저)를 기준으로 하면 uk_email이겠지만,
-- "CONSTRAINT 선언 순서" 기준이면 결과가 달라질 수 있다.
-- 만약 컬럼 순서를 바꿔 재생성하면 (email과 ssn 위치를 스왑) RK도 바뀌는가?
```

**예제 설명**: 위 예제는 UK 후보가 동시에 2개 있는 가장 단순한 상황이다. 스펙이 "명시된
순서 중 가장 빠른 순서"라고 했지만, 이것이 "컬럼 선언 순서"인지 "제약 선언 순서"인지도
불분명하다. 게다가 이 기준이 엔진 버전 업그레이드 후에도 동일하게 유지된다는 보장이
스펙에 없다. 만약 다음 버전에서 내부 구현이 바뀌어 RK 선택 기준이 달라진다면, 업그레이드
직후 슬레이브에 반영되는 행 식별자가 바뀌면서 기존 복제 상태와 충돌할 수 있다.

**제안**: RK 선택 규칙을 "예시"가 아니라 "다음 알고리즘을 따른다"는 확정 명제로 재작성하고,
이 규칙이 하위 호환 계약(향후 버전에서도 변경 시 마이그레이션 가이드 필수)임을 별도
섹션으로 명시해야 한다. 또한 `show create table`이나 `db_class` 조회 결과에 "어떤 제약이
RK로 선택되었는지"를 직접 노출하는 방법(§2-3에서 REPLICATION ON/OFF만 보여주고 RK 자체는
안 보여줌 — 이것도 별도 리뷰 대상)을 함께 제공해야 예측 가능성이 확보된다.

## 리뷰 2

**[심각도: 치명] 기존에 HA를 운영 중인 고객을 위한 마이그레이션 절차가 스펙에 없음**

**대상**: 작업지시 배경, §7 HA 전환, §8 UNLOADDB & LOADDB

**문제 설명**: 이 스펙이 해결하려는 문제 자체가 "이미 HA로 운영 중인 기존 고객"에게서
발생한 장애다(PK 컬럼 변경 시 복제 누락). 그런데 스펙 전체를 읽어봐도 "이미 HA로 돌고
있는 기존 클러스터가 이 버전으로 업그레이드되는 순간 무슨 일이 일어나는지"에 대한 절차가
없다. §7은 "HA 실행 시" 제약사항을 점검한다고 했는데, 이는 신규로 `cubrid hb start`를
호출하는 시점을 가리키는 것으로 읽히지, 이미 떠 있는 HA 프로세스를 무중단으로 업그레이드하는
경로(rolling upgrade)를 다루지 않는다. 릴리스 매니저 입장에서 이는 치명적 공백이다:
기존 고객이 패치를 적용한 뒤 재시작하는 순간 RK가 없는 테이블 때문에 HA가 아예 기동을
거부할 수 있는데, 이를 사전에 감지하고 고객에게 안내할 도구나 절차가 스펙에 없다.

**구체 예제**:
```
[시나리오]
1. 고객 A는 현재 CUBRID 구버전으로 HA 운영 중. 테이블 orders는 PK 없이 운영되고 있었음
   (구버전은 PK 없는 테이블도 일단 생성은 허용했었고, 복제만 누락되는 상태였음).
2. 고객 A가 이번 스펙이 반영된 신버전으로 바이너리만 교체.
3. 기존 HA 프로세스를 재기동(cubrid hb start)한다.
4. 신버전 엔진은 §7 규칙에 따라 orders 테이블에 RK가 없음을 감지하고 HA 기동을 거부한다.
5. 고객은 "에러와 파일 리스트"를 받지만, 이 시점은 이미 서비스가 중단된 이후다.
```

**예제 설명**: 이 시나리오는 스펙이 명시한 §7 규칙을 그대로 따랐을 뿐인데도 실제 운영
중단으로 이어진다. 문제는 "사전에" 이 상황을 점검할 방법이 없다는 것이다. 업그레이드
*전에* 싱글 모드에서 미리 스캔해서 RK 없는 복제 대상 테이블 목록을 뽑아주는 사전 점검
도구나 SQL(`SELECT * FROM db_class WHERE replication = 'ON' AND <RK 없음>` 같은 것)이
스펙에 정의되어 있지 않다. 이는 릴리스 노트에 "업그레이드 전 반드시 이 쿼리를 실행해
점검하라"고 적을 근거 자체가 스펙에 없다는 뜻이다.

**제안**: (1) 업그레이드 전 사전 점검용 조회 SQL 또는 유틸리티를 스펙에 포함시키고,
(2) 기존 HA 클러스터의 무중단 업그레이드 시나리오를 별도 절로 분리해서 다루며,
(3) 최소한 릴리스 노트에 "이 버전 적용 전 반드시 실행할 체크리스트"를 명문화해야 한다.

## 리뷰 3

**[심각도: 치명] REPLICATION 옵션 생략 시 기본값 ON 정책이 기존 배포본과의 하위 호환성을 깨뜨림**

**대상**: §2-1, "이 옵션은 생략 가능하며 생략시 ON으로 자동으로 복제 테이블로 생성된다"

**문제 설명**: 옵션을 생략하면 무조건 ON(복제 대상)이 기본값이다. 언뜻 합리적으로
보이지만, 이는 "기존에 아무 문제 없이 동작하던 스키마 생성 스크립트"의 동작을 조용히
바꾼다. 구버전에서는 `CREATE TABLE t(a INT)`처럼 PK 없는 테이블을 만들어도 단순히
"복제가 안 되는 테이블"로 취급되고 에러가 나지 않았다(배경 설명에 따르면 복제 누락 +
fail_count 증가라는 *결함*이었을 뿐, 생성 자체가 막히지는 않았다). 신버전에서는 동일한
스크립트가 HA 모드에서는 아예 테이블 생성 자체를 거부한다(§4-1, 예시 10). 즉 "복제가
조용히 깨지는" 문제를 "테이블 생성 자체가 실패"로 바꾼 것인데, 이는 개선이긴 하지만
동시에 기존 DDL 스크립트/마이그레이션 도구(Liquibase, Flyway 등)의 재현성을 깨는
행위 변경(behavior change)이다. 스펙 어디에도 이 정책이 "브레이킹 체인지"라는 경고나,
왜 하필 ON을 기본값으로 골랐는지(OFF를 기본값으로 했다면 하위 호환성은 지키면서 옵트인
방식으로 갈 수도 있었다) 대한 트레이드오프 설명이 없다.

**구체 예제**:
```sql
-- 기존에 CI 파이프라인에서 반복 실행되던 스키마 마이그레이션 스크립트 (변경 전 버전 기준으로 작성됨)
CREATE TABLE session_log(
    session_id VARCHAR(64),
    created_at DATETIME,
    payload    VARCHAR(4000)
);
-- 구버전: 생성 성공, 다만 복제가 누락되는 결함이 존재(배경 설명 참조)
-- 신버전 HA 모드: REPLICATION 옵션 생략 -> 기본 ON -> RK 후보 없음 -> 예시10과 동일하게 ERROR
```

**예제 설명**: `session_log`는 로그성 테이블로 원래부터 PK가 필요 없다고 설계된
테이블이다. 이런 테이블은 원래 복제 대상에서 제외되어도 무방한 성격이지만, 스크립트
작성자는 그런 의도를 담아 REPLICATION 옵션을 명시한 적이 없다(과거엔 그런 옵션 자체가
없었으므로). 신버전에서는 이 스크립트가 그대로 HA 모드 배포 파이프라인에서 실패한다.
즉 "기본값 정책 하나" 때문에 기존 배포 자동화가 깨지는 사례다.

**제안**: 릴리스 노트에 이 기본값 정책을 브레이킹 체인지로 명시하고, 업그레이드 가이드에
"PK/UK가 없는 테이블을 생성하는 기존 스크립트가 있다면 REPLICATION=OFF를 명시적으로
추가하라"는 항목을 넣어야 한다. 대안으로 "싱글 모드에서는 생략 시 ON, 향후 HA 전환
시점에 한해 RK 없는 테이블은 경고만 내고 자동으로 OFF로 전환" 같은 완충 정책도 검토
가치가 있다.

## 리뷰 4

**[심각도: 치명] 멀티 슬레이브·체인 복제 구조에서 REPLICATION 옵션이 테이블 단위 전역
플래그라는 점이 향후 확장을 막음**

**대상**: 컨셉 전체(§1, §2), 확장성 관점

**문제 설명**: `REPLICATION={ON|OFF}`는 테이블 하나에 값 하나만 붙는 전역(global)
속성이다. 즉 "이 테이블을 복제할지 말지"는 마스터에 연결된 모든 슬레이브에 대해
동일하게 적용된다. 그런데 CUBRID HA는 멀티 슬레이브(마스터 1대에 슬레이브 여러 대)를
지원하며, 향후 체인 복제(마스터→슬레이브1→슬레이브2로 릴레이하는 구조, 흔히 cascading
replication이라 부름)로 확장될 가능성도 배제할 수 없다. 만약 향후 "슬레이브 A에는
개인정보 테이블을 보내지 않고, 슬레이브 B(분석용)에는 보낸다"처럼 슬레이브별로 다른
복제 대상을 지정하는 요구가 들어오면, 이번 스펙의 테이블 단위 전역 ON/OFF 모델은
근본적으로 확장이 불가능하다 — 옵션 자체를 다시 설계해야 한다(예: 슬레이브별 필터
목록을 별도로 관리하는 구조로 전면 교체). 이는 아키텍처 설계 시점에 고려했어야 할
확장축인데, 스펙에는 "슬레이브가 여러 대인 경우"에 대한 언급이 단 한 줄도 없다.

**구체 예제**:
```
[가상 시나리오 - 향후 요구]
마스터 1대, 슬레이브 2대(슬레이브1=DR용 완전 동기화, 슬레이브2=분석용이며 PII 테이블 제외)

CREATE TABLE customers_pii(
    customer_id INT PRIMARY KEY,
    ssn         VARCHAR(20)
) REPLICATION = ON;   -- 슬레이브1에는 보내야 하지만 슬레이브2에는 보내면 안 됨

-- 현재 스펙의 REPLICATION 옵션은 테이블당 값 하나뿐이므로
-- "슬레이브2만 제외"라는 요구를 표현할 방법이 스펙 안에 없다.
```

**예제 설명**: 이 시나리오는 실제로 규제 산업(금융, 의료)에서 흔히 나오는 요구
패턴이다. 분석용 슬레이브에는 개인정보 테이블을 복제하지 않고 나머지는 모두
복제하고 싶은 경우, 현재 스펙의 테이블 전역 플래그로는 표현이 안 된다. 이런 요구가
들어왔을 때 REPLICATION 옵션의 값 자체를 `ON|OFF`에서 `ON|OFF|슬레이브목록`처럼
확장해야 하는데, 이는 카탈로그 스키마 변경과 기존 고객 데이터 마이그레이션을
동반하는 큰 작업이 된다.

**제안**: 지금 당장 슬레이브별 필터링을 구현하라는 것이 아니라, 최소한 스펙 문서에
"본 설계는 슬레이브 단위가 아닌 테이블 단위 전역 복제 여부만 다루며, 슬레이브별
선택적 복제는 범위 밖(out of scope)"이라고 명시적으로 선을 그어야 한다. 이래야
차후 요구가 들어왔을 때 "완전히 새로운 설계가 필요하다"는 사실을 이해관계자들이
미리 인지하고 로드맵에 반영할 수 있다.

## 리뷰 5

**[심각도: 중요] RK를 사용자가 직접 지정할 수 없음 — PostgreSQL REPLICA IDENTITY 대비 제어권 열위**

**대상**: §4-2, "복제키는 큐브리드 엔진에 의해 결정되며, 사용자는 복제키를 직접
수정할 수 없다"

**문제 설명**: 배경 설명에 "PostgreSQL의 REPLICA IDENTITY 컨셉 일부를 채용했다"고
명시되어 있다. 그런데 PostgreSQL의 REPLICA IDENTITY는 `DEFAULT`(PK 자동 사용),
`USING INDEX idx_name`(사용자가 특정 unique index를 명시적으로 지정), `FULL`(전체
컬럼 사용), `NOTHING`(식별 불가) 네 가지 모드를 제공해서 사용자가 원하는 인덱스를
강제로 지정할 수 있다. 반면 이 스펙은 "일부"만 채용했다고 밝힌 대로, 사용자 지정
기능(`USING INDEX`에 해당하는 기능)을 아예 빼고 엔진 자동 선택만 남겼다. 이는 UK가
여러 개 있을 때 사용자가 "비즈니스적으로 더 안정적인 키"를 RK로 강제하고 싶어도
불가능하다는 뜻이다. PM 관점에서 이것은 "PostgreSQL 대비 열위 기능"으로 competitive
battlecard에 그대로 올라갈 항목이며, 스펙 문서 자체에 이 트레이드오프에 대한 근거나
향후 계획이 없다는 것이 문제다.

**구체 예제**:
```sql
CREATE TABLE accounts(
    internal_seq  INT           NOT NULL UNIQUE,  -- 시스템 내부용, 자주 안 바뀜
    account_no    VARCHAR(30)   NOT NULL UNIQUE,   -- 업무적으로 의미 있는 키, 조회에 주로 사용
    balance       DECIMAL(15,2)
);
-- 스펙 §1 규칙: "테이블내에 명시된 순서 중 가장 빠른 순서" -> internal_seq가 RK로 선택됨
-- 그러나 운영팀은 장애 시 로그를 보면서 account_no 기준으로 슬레이브 데이터를 대조하고 싶어함
-- PostgreSQL이었다면: ALTER TABLE accounts REPLICA IDENTITY USING INDEX uk_account_no; 로 강제 가능
-- CUBRID 신버전: 이런 지정 수단이 없음
```

**예제 설명**: 운영 관점에서 RK는 단순히 "슬레이브 행 식별자"가 아니라 장애 분석 시
로그와 대조하는 기준값이기도 하다. 사람이 다루기 쉬운 키(account_no)가 아니라 내부용
시퀀스(internal_seq)가 자동으로 선택되면, 장애 대응 시 운영자가 로그의 account_no를
가지고 슬레이브 데이터를 대조하기 번거로워진다. 이런 요구는 실제로 자주 나오는데,
현재 스펙에는 이를 해결할 방법이 없다.

**제안**: 최소한 로드맵 상에 "향후 사용자 지정 RK(USING INDEX 방식)를 지원할 계획이
있는지"를 명시하고, 이번 릴리스에서는 왜 자동 선택만 지원하는지(성능/복잡도 트레이드오프)
근거를 스펙 서두에 한 문단으로 남겨야 한다.

## 리뷰 6

**[심각도: 중요] "복제키 후보"라는 핵심 용어가 정의 없이 등장함**

**대상**: §4-2, "복제키 후보가 1개인 경우", 예시 16 "복제키 후보가 없다면 삭제 불가"

**문제 설명**: §1과 §2에서는 줄곧 "복제 키(RK)"라는 단수 개념만 설명한다 — "PK가 있으면
PK가 RK, 없으면 UK 중 하나가 RK"라는 식으로, 테이블에는 RK가 하나만 존재하는 것처럼
읽힌다. 그런데 §4-2에 가서 갑자기 "복제키 후보"라는 새 용어가 등장하고, "후보가 여러 개
있으면 모든 DDL이 허용된다"는 규칙이 나온다. 이는 실제로는 "RK로 선택될 자격이 있는
PK/UK 제약의 집합"을 가리키는 것으로 추정되지만, 이 용어가 §1에서 미리 정의되지 않았기
때문에 독자는 "RK"와 "RK 후보"가 같은 것인지 다른 것인지 §4-2를 읽는 순간까지 알 수
없다. 스펙 문서에서 핵심 개념의 정의가 사용 시점보다 한참 뒤에, 그것도 정의문 없이
등장하는 것은 명백한 문서 결함이다.

**구체 예제**:
```sql
CREATE TABLE tbl(
    a INT PRIMARY KEY,
    b INT NOT NULL UNIQUE,
    c INT
);
-- RK는 a(PK)로 선택됨. 그렇다면 b(UK)는 "RK"인가, "RK 후보"인가?
-- 예시16 "복제키 후보가 없다면 삭제 불가"라는 규칙을 적용하면:
DROP INDEX idx_b ON tbl;  -- b의 UK 인덱스를 지우는 상황
-- a(PK)가 여전히 있으므로 "복제키 후보"는 a 하나 남는데, 이 DROP은 허용되는가 금지되는가?
-- "복제키 후보가 없다면 삭제 불가"라는 문장만으로는 이 케이스가 허용인지 판단 불가
```

**예제 설명**: 이 예제는 "RK 후보"가 "현재 RK로 선택된 것"만을 가리키는지, 아니면
"RK가 될 자격이 있는 모든 제약(PK + 모든 UK)"을 가리키는지에 따라 결과가 완전히
달라지는 상황을 보여준다. 전자라면 b는 RK 후보가 아니므로 DROP이 허용되어야 하고,
후자라면 b도 후보 중 하나이므로 규칙 적용 대상이 될 수 있다. 스펙 문장만으로는 어느
쪽인지 결정할 수 없다.

**제안**: §1에 "RK 후보(replication key candidate)"라는 용어를 명시적으로 정의하는
문장을 추가하고, "RK 후보 = PK 하나 + 모든 UK"인지 "RK 후보 = 현재 선택되지 않은
대체 가능 제약들"인지 정확히 규정해야 한다.

## 리뷰 7

**[심각도: 중요] §2-1 예시 2의 SQL이 구문 오류를 포함하면서, 서술 내용과도 모순됨**

**대상**: §2-1, 예시 2 "복제 키가 존재하지 않는 복제 테이블. 오직 싱글모드에서만 생성 가능"

**문제 설명**: 예시 2의 SQL은 다음과 같이 되어 있다.
```sql
CREATE TABLE repl_table_without_rk(
    a INT,
);
```
컬럼 목록의 마지막 항목 뒤에 쉼표(trailing comma)가 있다. 이는 CUBRID를 포함한 대부분의
SQL 방언에서 구문 오류(syntax error)로 처리된다(즉 파서가 쉼표 뒤에 다음 컬럼 정의가
와야 하는데 바로 닫는 괄호가 오므로 문법 오류). 사용자 매뉴얼이나 QA 테스트케이스가 이
스펙 문서의 예제를 그대로 복사해서 쓴다면 실행 자체가 실패하는 문서 결함이다. 더 큰
문제는, 이 예제가 "PK/UK가 없는 테이블도 REPLICATION 옵션 없이(또는 명시적으로 ON을
붙여도) 만들 수 있다"는 것을 보여주려는 의도인데, 정작 §4-1 예시 10에서는 "HA 모드에서는
복제키가 없는 복제 테이블을 생성할 수 없다(ERROR)"고 정반대 결과를 보여준다. 두 예시
모두 "REPLICATION 옵션 생략/ON, RK 없음"이라는 동일 조건인데 결과가 다른 이유는 "싱글
모드냐 HA 모드냐"의 차이이지만, 예시 2 자체에는 "이것이 싱글 모드에서 실행된 것"이라는
표시(프롬프트, 주석 등)가 SQL 코드 안에는 전혀 없다. 본문 설명을 읽어야만 알 수 있어,
예제만 따로 떼어서 인용하면 오해를 낳는다.

**구체 예제**:
```sql
-- 스펙 원문 그대로 (문제 있는 버전)
CREATE TABLE repl_table_without_rk(
    a INT,
);
-- 실행 결과: 구문 오류 (trailing comma)

-- 올바르게 고친 버전 + 모드 명시
-- (싱글 모드에서 실행)
CREATE TABLE repl_table_without_rk(
    a INT
) REPLICATION = ON;
```

**예제 설명**: 위쪽은 스펙 원문을 그대로 재현한 것으로, 이 상태로는 애초에 실행이
안 되므로 "RK 없는 복제 테이블이 싱글 모드에서 생성된다"는 스펙의 주장을 검증할 수조차
없다. 아래쪽은 구문 오류를 제거하고 실행 모드를 주석으로 명시한 정정본이다. 이렇게
고쳐야만 비로소 예시 2와 예시 10(HA 모드에서는 동일 SQL이 ERROR)의 대비가 명확해진다.

**제안**: 모든 SQL 예제에 대해 실제로 실행해 문법 검증을 거치고, 각 예제 코드 블록
안에 모드(싱글/HA)를 주석으로 명시해야 한다. trailing comma 오류는 예시 23에도
동일하게 나타나므로(리뷰 19 참조) 문서 전체를 일괄 재검토할 필요가 있다.

## 리뷰 8

**[심각도: 중요] 예시 10의 테이블 이름이 예시가 보여주려는 내용과 반대로 붙어 있음**

**대상**: §4-1, 예시 10 "복제 테이블에는 반드시 복제 키 후보가 1개 이상 필요하다"

**문제 설명**: 예시 10의 SQL은 다음과 같다.
```sql
CREATE TABLE repl_table_with_rk(
    a INT
);
```
테이블 이름이 `repl_table_with_rk`("RK가 있는 복제 테이블")인데, 정작 컬럼 정의에는
PK도 UK도 없다 — 즉 이 예시가 보여주려는 것은 "RK가 *없는* 테이블을 HA 모드에서
만들려다 에러가 난다"는 상황이다. §2-1의 예시 1/2에서는 각각 `repl_table_with_rk`(RK
있음, 정상)와 `repl_table_without_rk`(RK 없음)로 이름을 구분해 붙여 놓고서, §4-1의
예시 10에서는 "RK가 없는" 상황인데도 앞서 "RK가 있는" 용도로 썼던 이름을 재사용했다.
이는 단순 오탈자 수준을 넘어, 매뉴얼 작성자나 QA가 이 문서를 참고 자료로 삼아 테스트
케이스 이름을 붙일 때 실제 테스트 의도와 반대되는 이름을 붙이게 만들 수 있는 실질적인
혼란 요인이다.

**구체 예제**:
```sql
-- 스펙 원문 (이름이 잘못 붙음)
CREATE TABLE repl_table_with_rk(   -- 이름은 "RK 있음"인데
    a INT                          -- 실제로는 PK/UK가 전혀 없음
);
-- ERROR (HA 모드, 예시10)

-- 올바른 명명
CREATE TABLE repl_table_without_rk(
    a INT
);
-- ERROR (HA 모드)
```

**예제 설명**: 이름과 실제 내용이 어긋난 예제를 그대로 QA 테스트케이스 관리 시스템에
등록하면, 예를 들어 "TC_repl_table_with_rk_should_succeed"라는 케이스 이름이 실제로는
"RK 없는 테이블 생성 실패를 검증하는" 케이스가 되어버려 회귀 테스트 로그를 나중에
검토하는 사람에게 혼선을 준다.

**제안**: 예시 10의 테이블명을 `repl_table_without_rk`로 정정하거나, 최소한 §2-1의
동명 테이블과 구분되도록 이름을 바꿔야 한다.

## 리뷰 9

**[심각도: 중요] §5 외래키 정책이 "부모가 OFF면 안 됨"만 규정하고, 자식 테이블의
REPLICATION 전환 시나리오는 다루지 않음**

**대상**: §5 외래키, "외래키 테이블에서 참조하는 모든 테이블은 복제 대상이여야한다"

**문제 설명**: §5는 자식(FK를 가진) 테이블이 복제 대상(ON)일 때 부모(참조 대상) 테이블도
반드시 ON이어야 한다는 규칙만 다룬다. 그런데 반대 방향, 즉 "이미 존재하는 자식 테이블을
REPLICATION=OFF에서 ON으로 전환하려는데, 그 부모가 OFF인 경우"에 대한 규칙이 없다.
§2-2에는 "HA 모드에서는 복제 제외 테이블이 복제 테이블로 변경될 수 없다"는 규칙이
있지만, 이는 HA 모드라는 조건에서만 적용되고, 싱글 모드에서 자식을 ON으로 바꿀 때
부모의 REPLICATION 상태를 검사하는지에 대한 언급이 없다. 만약 검사하지 않는다면,
싱글 모드에서 "부모 OFF, 자식 ON"이라는 §5가 금지하는 상태 조합이 ALTER TABLE 경로를
통해 만들어질 수 있고, 이 상태로 HA를 시작하면 §7의 검증에 걸릴지, 아니면 조용히
통과될지도 불명확하다(§7은 "외래키를 포함하는 복제 테이블의 참조 테이블이 복제 대상이
아닌경우"를 점검한다고 했으므로 아마 걸릴 것으로 추정되지만, ALTER 시점에 막지 않고
HA 시작 시점에야 걸리는 것이라면 사용자 경험상 실패 시점이 너무 늦다).

**구체 예제**:
```sql
-- 1) 싱글 모드에서 두 테이블을 REPLICATION=OFF로 생성
CREATE TABLE customers(
    customer_id INT PRIMARY KEY
) REPLICATION = OFF;

CREATE TABLE orders(
    order_id    INT PRIMARY KEY,
    customer_id INT,
    CONSTRAINT fk_customer_id FOREIGN KEY (customer_id) REFERENCES customers(customer_id)
) REPLICATION = OFF;

-- 2) 이후 orders만 복제 대상으로 전환 시도 (싱글 모드)
ALTER TABLE orders REPLICATION = ON;
-- 이 시점에 customers가 여전히 OFF임을 검사해서 막아주는가?
-- 스펙 §2-2/§5 어디에도 이 케이스에 대한 명시적 답이 없다.
```

**예제 설명**: 이 시나리오는 §5가 금지하려는 최종 상태("자식은 ON, 부모는 OFF")를
CREATE TABLE이 아니라 ALTER TABLE 경로로 만들어내는 경우다. §5의 예시 17~23은 모두
CREATE TABLE 또는 FK 추가 시점의 검사만 다루고, "이미 있는 자식을 ON으로 전환하는"
방향의 검사는 다루지 않는다. 이 갭이 방치되면 사용자는 ALTER 시점에는 성공 응답을
받았다가, 정작 HA를 시작하는 시점에 가서야(§7) 실패를 통보받게 되어 문제 발견이
지연된다.

**제안**: `ALTER TABLE ... REPLICATION=ON` 실행 시 해당 테이블이 참조하는 모든 부모
테이블의 REPLICATION 상태를 함께 검사하는 규칙을 §2-2 또는 §5에 명시적으로 추가하고,
대응하는 예제(부모 OFF일 때 자식을 ON으로 전환 시도 → ERROR)를 §5에 넣어야 한다.

## 리뷰 10

**[심각도: 중요] §7 "에러와 함께 파일 리스트를 출력한다"의 출력 형식이 정의되어 있지 않음**

**대상**: §7 HA 전환, "제약사항 위반 시 에러와함께 파일 리스트를 출력한다"

**문제 설명**: HA 전환 검증에 실패했을 때 "파일 리스트"를 출력한다고만 되어 있다.
이 "파일"이 무엇을 가리키는지가 불명확하다 — 위반 사항이 있는 테이블/클래스 이름의
목록인지, 실제 OS 파일 경로(예: 특정 볼륨 파일)인지, 아니면 별도로 생성되는 보고서
파일의 경로인지 알 수 없다. 문맥상 "테이블 목록"을 의도했을 가능성이 높지만, 굳이
"파일 리스트"라는 표현을 쓴 이유가 설명되지 않는다. 이는 운영(DBA)팀이 이 기능을
자동화 스크립트(예: 실패 시 알림을 보내거나, 실패한 테이블 목록을 파싱해서 자동으로
ALTER 문을 생성하는 스크립트)에 통합하려 할 때 치명적인 공백이다 — 출력 형식(표준
출력인지 로그 파일인지, 구분자가 무엇인지, 테이블당 한 줄인지)이 하나도 정의되어
있지 않으면 어떤 자동화 도구도 이 출력을 파싱하도록 만들 수 없다.

**구체 예제**:
```
[운영 시나리오]
$ cubrid hb start mydb
ERROR: HA 전환 제약사항 위반
파일 리스트:
  ???  <- 이 자리에 실제로 무엇이 출력되는지 스펙에 규정이 없음
       (테이블명? 전체 경로? 오류 코드? 위반 사유까지 포함?)

# 운영팀이 원하는 자동화 예시
$ cubrid hb start mydb --check-only --format=json > violations.json
$ python fix_violations.py violations.json   # 이런 자동화가 가능하려면
                                              # 출력 포맷이 스펙에 명시되어 있어야 함
```

**예제 설명**: 위 시나리오는 운영팀이 HA 전환 실패를 자동으로 감지하고 후속 조치를
스크립트로 처리하고 싶어하는 매우 현실적인 요구다. 그러나 "파일 리스트를 출력한다"는
한 문장만으로는 이 출력을 프로그램이 파싱할 수 있는 형태로 설계할 근거가 없다. 출력이
버전마다 바뀔 수도 있고(포맷이 계약이 아니므로), 로그 레벨에 따라 나오거나 안 나올
수도 있다.

**제안**: 출력 대상이 테이블명인지 파일 경로인지 명확히 하고, 각 위반 항목에 최소한
"테이블명 + 위반 사유 코드"가 포함된 구조화된 포맷(가능하면 기계 판독 가능한 형태)을
정의해야 한다. 이는 §7뿐 아니라 릴리스 노트/운영 매뉴얼 작성에도 직접 영향을 준다.

## 리뷰 11

**[심각도: 중요] 파티션 테이블과 REPLICATION/RK의 상호작용이 스펙에 전혀 언급되지 않음**

**대상**: 스펙 전체 (특히 §1, §2, §4)

**문제 설명**: CUBRID는 파티션 테이블(하나의 논리 테이블을 여러 물리 파티션으로 나누는
기능)을 지원하는 제품이다. 이번 스펙은 REPLICATION 옵션과 RK 선택 규칙을 설명하면서
파티션 테이블에 대한 언급을 한 줄도 하지 않는다. 파티션 테이블에서는 통상 파티션 키
컬럼이 PK/UK에 포함되어야 하는 제약(파티셔닝 엔진의 일반적 제약)이 있는 경우가 많은데,
이것이 RK 선택과 충돌하지는 않는지, 파티션별로 REPLICATION 값을 다르게 줄 수 있는지
(예: 오래된 파티션은 OFF로 바꿔서 복제 부하를 줄이는 운영 패턴은 실제로 자주 요구된다),
아니면 부모 테이블 레벨에서만 설정하고 모든 파티션에 강제로 상속되는지에 대한 규정이
없다.

**구체 예제**:
```sql
-- 파티션 테이블 예시 (연도별 파티셔닝)
CREATE TABLE sales(
    sale_id   INT NOT NULL,
    sale_date DATE NOT NULL,
    amount    DECIMAL(10,2),
    PRIMARY KEY (sale_id, sale_date)
) PARTITION BY RANGE (sale_date) (
    PARTITION p2024 VALUES LESS THAN ('2025-01-01'),
    PARTITION p2025 VALUES LESS THAN ('2026-01-01')
);
-- 질문1: REPLICATION 옵션은 sales 테이블 전체에만 붙는가, 파티션별로도 붙일 수 있는가?
-- 질문2: p2024처럼 오래된 파티션만 REPLICATION=OFF로 바꿔서 복제 트래픽을 줄이는 것이 가능한가?
ALTER TABLE sales REPLICATION = OFF;  -- 이게 부모 전체에 적용된다면 p2025(최신 데이터)까지 복제 중단됨
```

**예제 설명**: 파티션 테이블은 시계열 데이터에서 흔히 쓰이며, "오래된 파티션은 복제
제외, 최신 파티션만 복제"라는 요구가 실제로 자주 나온다. 스펙이 파티션 단위 설정을
언급하지 않는다는 것은 이런 요구를 지원하지 않는다는 뜻일 수도 있고, 단순히 검토
누락일 수도 있다 — 어느 쪽이든 문서에 명시가 없으면 영업/지원팀이 고객 문의에 답할
근거가 없다.

**제안**: 파티션 테이블에서 REPLICATION 옵션의 적용 단위(부모 전체 vs 파티션별)와
RK 선택 규칙이 파티션 키와 어떻게 상호작용하는지를 최소 한 문단으로 명시해야 한다.
지원하지 않는다면 "지원하지 않음"이라고 명시적으로 적어야 한다.

## 리뷰 12

**[심각도: 중요] 경쟁 제품(Oracle GoldenGate, MySQL GTID/RBR) 대비 포지셔닝 근거가
스펙에 없음**

**대상**: 배경 설명 전체, 컨셉

**문제 설명**: 배경 설명은 "MySQL식은 성능 문제로 배제, PostgreSQL REPLICA IDENTITY
컨셉 일부 채용"이라고만 되어 있다. PM 관점에서 이는 근거가 매우 얇다. 첫째, "MySQL식이
느리다"는 주장에 대한 정량적 근거(벤치마크, 논문, 벤더 문서 인용 등)가 스펙에 없다 —
그냥 "느려서 배제"라고만 적혀 있어 향후 "왜 MySQL처럼 안 했나"라는 고객/영업 질문에
근거를 댈 문서가 없다. 둘째, Oracle GoldenGate(로그 기반 이기종 복제 솔루션)나 MySQL의
GTID(Global Transaction Identifier, 트랜잭션에 전역 고유 ID를 부여해 복제 위치를
추적하는 방식) 같은, RK 문제와 인접한 다른 벤더의 해법과 CUBRID의 접근이 어떻게
다른지에 대한 비교가 전혀 없다. 셋째 "PostgreSQL 컨셉 일부 채용"이라고 했지만 정확히
무엇을 채용하고 무엇을 채용하지 않았는지(리뷰 5에서 지적한 USING INDEX 미지원 등)를
표로 정리한 자료가 없어, 세일즈 엔지니어가 고객 앞에서 "PostgreSQL과 뭐가 다른가요"라는
질문에 스펙만 보고는 답할 수 없다.

**구체 예제**:
```
[가상 고객 질의 - 실제로 나올 법한 질문]
Q1. "MySQL은 PK 없으면 전 컬럼을 키로 쓴다던데, 그게 왜 느린가요? 우리 워크로드는
     테이블이 작은데도 그게 문제가 되나요?"
Q2. "PostgreSQL REPLICA IDENTITY처럼 특정 인덱스를 강제로 지정할 수 있나요?"
Q3. "Oracle GoldenGate는 PK 없는 테이블도 로그 기반으로 다 처리한다던데,
     CUBRID는 왜 RK가 필수인가요?"

-> 현재 스펙 문서만으로는 세일즈/지원 엔지니어가 이 세 질문 중 어느 것도
   구체적 수치나 비교표 없이 답변할 수 없다.
```

**예제 설명**: 이 세 질문은 경쟁 제품을 써본 고객이라면 자연스럽게 던질 질문들이다.
스펙에 "느려서 배제했다"는 결론만 있고 "왜, 얼마나 느린지, 어떤 조건에서 느린지"에
대한 근거 자료가 없으면, 이 기능의 가치를 고객에게 설득하는 자료(FAQ, 경쟁 비교
문서)를 만들 때마다 매번 새로 조사해야 한다.

**제안**: 별도 부록으로 "MySQL 전체 컬럼 키 방식 vs UK/PK 기반 RK 방식" 성능
비교표(가능하면 실측치), "PostgreSQL REPLICA IDENTITY 대비 CUBRID RK 기능 비교표"를
추가하고, Oracle GoldenGate류의 로그 기반 방식과 CUBRID의 논리적 복제 방식이 애초에
다른 카테고리(로그 마이닝 기반 이기종 복제 vs 동종 엔진 내장 복제)임을 명확히 구분해
설명하는 절을 신설해야 한다.

## 리뷰 13

**[심각도: 중요] REPLICATION=OFF 테이블의 unload/load 시 FK 참조 무결성 처리 방식이
불명확함**

**대상**: §8 UNLOADDB & LOADDB, §5 외래키

**문제 설명**: §8은 "unload 시 복제 테이블의 여부를 함께 저장한다"고만 설명하고,
FK 관계와의 상호작용은 언급하지 않는다. §5에 따르면 "복제 대상인 외래키 테이블이
참조하는 모든 테이블은 복제 대상이어야 한다"는 제약이 있는데, 만약 unloaddb/loaddb
과정(예: 슬레이브를 새로 구성하기 위한 백업/복구, 혹은 버전 업그레이드 시의 덤프-리로드)
에서 부모 테이블과 자식 테이블이 서로 다른 시점에 언로드되거나, 서로 다른 배치로
로드된다면 §5의 제약이 로드 과정 중간 상태에서 일시적으로 깨질 수 있다. 이때 loaddb가
이 제약을 로드 완료 후에 검증하는지, 아니면 개별 파일 로드 시점마다 검증해서 실패하는지
스펙에 규정이 없다. 특히 "unloaddb를 이용한 대량 초기 슬레이브 구성"은 CUBRID HA의
실제 운영 관행 중 하나이므로, 이 경로가 막히면 신규 슬레이브 추가 작업 자체가 영향을
받는다.

**구체 예제**:
```
[운영 시나리오 - unloaddb/loaddb를 이용한 신규 슬레이브 구성]
1. 마스터에서 unloaddb 실행 -> customers.data, customers.schema,
   orders.data, orders.schema 등 파일 생성
   (customers: REPLICATION=ON, orders: REPLICATION=ON, FK orders->customers)
2. 신규 슬레이브 서버에서 loaddb 실행 시, 파일 로드 순서가
   orders -> customers 순서라면?
   (loaddb는 통상 스키마 의존성을 고려해 순서를 잡지만, 명시적 보장이 스펙에 없음)
3. orders 로드 시점에는 customers가 아직 존재하지 않는데,
   FK 제약(§5) 검사가 이 시점에 걸리는가?
```

**예제 설명**: unloaddb/loaddb는 파일 단위 작업이라 로드 순서에 따라 일시적으로
참조 무결성이 깨진 상태를 거칠 수 있다. 기존 CUBRID의 loaddb는 이런 상황을 지연
제약 검사(deferred constraint check)나 순서 정렬로 처리했을 가능성이 높지만, 이번
스펙에서 새로 추가된 "복제 대상 여부" 규칙(§5의 "참조 테이블도 복제 대상이어야
한다")이 기존 FK 로드 로직과 충돌 없이 맞물리는지 검증한 내용이 스펙에 없다.

**제안**: unloaddb/loaddb 절차에서 REPLICATION 관련 제약(§5 포함)이 언제 검증되는지
(로드 도중 각 파일 단위 vs 전체 로드 완료 후 일괄 검증)를 명시하고, 순서에 의존하지
않는 지연 검증 방식을 권장 사항으로 추가해야 한다.

## 리뷰 14

**[심각도: 보통] §3과 §7의 "HA 전환 시점" 절차 서술이 서로 다른 그림을 그림**

**대상**: §3 Single 제약사항, §7 HA 전환

**문제 설명**: §3은 "싱글 모드에서 생성된 복제 키가 없는 테이블은 HA모드 전환 시 복제
키를 추가하거나 복제 제외 테이블로 변경할 수 있어야한다"고 적었다. 이 문장은 "HA 모드로
전환하는 그 시점에" 수정이 가능한 것처럼 읽힌다. 그런데 §7은 "HA 실행시 제약사항을
확인하며, 위반 시 에러... 이 경우 싱글모드에서 ALTER TABLE...을 이용해 ... 변경한 후
HA를 재시작해야한다"고 적어, 실제 절차는 "HA 시작 시도 → 실패 → 싱글 모드로 돌아가서
수정 → 재시도"의 반복임을 보여준다. 즉 §3의 "전환 시" 수정이 가능하다는 표현과, §7의
"전환을 먼저 시도했다가 실패하면 싱글 모드로 되돌아가 수정한다"는 실제 절차 사이에는
뉘앙스 차이가 있다 — §3만 읽은 독자는 "HA로 전환되는 도중에 온라인으로 수정할 수
있다"고 오해할 수 있다.

**구체 예제**:
```
[§3만 읽었을 때 예상하는 절차]
$ cubrid hb start mydb
-> (전환 도중 RK 없는 테이블 발견) -> 그 자리에서 ALTER TABLE로 수정 가능? -> 전환 계속 진행?

[§7이 실제로 서술하는 절차]
$ cubrid hb start mydb
-> ERROR + 파일 리스트 출력 (HA 시작 자체가 실패, 프로세스는 싱글 모드로 남음)
$ csql -u dba mydb
csql> ALTER TABLE tbl ADD CONSTRAINT PRIMARY KEY(a);
$ cubrid hb start mydb   -- 재시도
```

**예제 설명**: 두 절 모두 최종적으로 "싱글 모드에서 고치고 다시 HA를 시작한다"는
결론은 같지만, §3의 문장은 "전환 시"라는 표현 때문에 마치 전환 과정 중간에 개입할
여지가 있는 것처럼 오독될 소지가 있다. 매뉴얼 작성자가 §3만 보고 사용자 가이드를
쓰면 실제 동작과 다른 설명을 배포하게 된다.

**제안**: §3의 "HA모드 전환 시"라는 표현을 "HA모드로 전환을 시도하기 전, 싱글
모드에서 미리"로 명확히 바꾸거나, §7과 동일한 절차 설명(실패→롤백→수정→재시도)을
§3에도 동일하게 반복 기술해 두 절 간 서술을 통일해야 한다.

## 리뷰 15

**[심각도: 보통] 뷰(VIEW)에 REPLICATION 속성이 상속되는지, 조회 시 어떻게 표시되는지
규정이 없음**

**대상**: §6 뷰(VIEW)

**문제 설명**: §6은 "복제 제외 테이블이 뷰에 포함되어 있을 경우 두 노드의 결과가
일치하지 않을 수 있으며 이는 책임지지 않는다"는 면책 조항만 담고 있다. 그런데 뷰
자체에도 REPLICATION 옵션을 줄 수 있는지, 아니면 뷰는 애초에 데이터를 갖지 않으므로
이 옵션 자체가 무의미한 것인지 스펙이 밝히지 않는다. 또한 `show create table`이나
`db_class` 조회(§2-3)에서 뷰를 조회했을 때 REPLICATION 필드가 어떻게 표시되는지도
예제가 없다. 사용자 입장에서는 "뷰도 REPLICATION=OFF로 설정해서 실수로 뷰를 통해
불일치 데이터가 조회되는 것을 막을 수 있는가"라는 질문이 자연스럽게 나올 수 있는데,
스펙은 이 질문에 답하지 않는다.

**구체 예제**:
```sql
CREATE TABLE non_repl_customers(
    customer_id INT PRIMARY KEY,
    country     INT
) REPLICATION = OFF;

CREATE VIEW customer_summary AS
    SELECT customer_id, country FROM non_repl_customers;

-- 질문1: customer_summary에 REPLICATION 옵션을 붙일 수 있는가?
--        (CREATE VIEW ... REPLICATION = OFF; 같은 문법이 있는가?)
-- 질문2: show create table customer_summary; 를 실행하면
--        REPLICATION 필드가 어떻게 나오는가? (뷰이므로 NULL? 혹은 항상 ON?)
SHOW CREATE TABLE customer_summary;
```

**예제 설명**: 뷰는 실제 데이터를 저장하지 않고 하부 테이블을 참조하는 논리적
객체이므로 REPLICATION 옵션이 있어도 의미가 없다고 볼 수도 있지만, 그렇다면 왜
§6이 별도 절로 존재하는지, 그리고 뷰의 조회 결과에 이 상태가 어떻게 드러나는지에
대한 최소한의 설명이 있어야 사용자가 혼란을 겪지 않는다.

**제안**: 뷰에는 REPLICATION 옵션 자체가 적용되지 않는다는 점(혹은 적용된다면 그
문법)을 §6에 명시하고, `show create table`/`db_class` 조회 시 뷰의 REPLICATION
필드가 어떻게 나오는지 예제를 추가해야 한다.

## 리뷰 16

**[심각도: 보통] FK 제약의 자동 명명 규칙이 문서화되지 않아 예시 19와 예시 21이
서로 안 맞물림**

**대상**: §5-2, 예시 19 "외래키 추가", 예시 21 "복제 테이블을 참조하는 외래키 제거"

**문제 설명**: 예시 19는 다음과 같이 이름 없이 FK를 추가한다.
```sql
ALTER TABLE new_orders ADD CONSTRAINT FOREIGN KEY(customer_id)
REFERENCES customers(customer_id);
```
그런데 바로 다음에 이어지는 예시 21은 이렇게 이름을 지정해 삭제한다.
```sql
ALTER TABLE new_orders DROP FOREIGN KEY (fk_new_orders_customer_id);
```
`fk_new_orders_customer_id`라는 이름이 어디서 나왔는지 스펙 어디에도 설명이 없다.
CUBRID가 이름을 생략하면 `fk_<테이블명>_<컬럼명>` 같은 규칙으로 자동 명명한다는
것을 암묵적으로 전제하고 있는 것으로 보이지만, 이 규칙 자체가 이번 스펙의 범위는
아니라 하더라도 최소한 예시에서 "자동 생성된 이름은 fk_new_orders_customer_id이다"라는
각주 한 줄 정도는 있어야 독자가 예시 19와 21을 연결해서 읽을 수 있다. 지금 상태로는
두 예시가 마치 서로 무관한 이름을 쓰는 것처럼 보여 혼란스럽다.

**구체 예제**:
```sql
-- 예시19: 이름 없이 FK 추가
ALTER TABLE new_orders ADD CONSTRAINT FOREIGN KEY(customer_id)
REFERENCES customers(customer_id);
-- OK  (제약 이름이 자동 생성됨 -- 그 이름이 무엇인지 스펙에 명시 안 됨)

-- 예시21: 이름을 지정해서 삭제 (이름이 어디서 왔는지 불명)
ALTER TABLE new_orders DROP FOREIGN KEY (fk_new_orders_customer_id);
-- OK
```

**예제 설명**: 독자가 예시 19를 실행한 뒤 실제로 생성된 제약 이름을 조회해보지
않고서는 예시 21의 `fk_new_orders_customer_id`라는 이름을 어떻게 알아냈는지 알 수
없다. 문서만 순서대로 읽는 독자 입장에서는 마치 별도로 존재하던 제약을 지우는
것처럼 오해할 수 있다.

**제안**: 예시 19 뒤에 "이름을 생략하면 `fk_<테이블>_<컬럼>` 규칙으로 자동 생성되며,
예시 21은 이렇게 생성된 이름을 그대로 사용한다"는 각주를 추가해야 한다.

## 리뷰 17

**[심각도: 보통] 복합 UNIQUE 키의 일부 컬럼이 NULL 허용으로 바뀌는 ALTER 시나리오가
다뤄지지 않음**

**대상**: §4-2, 예시 15 DROP CONSTRAINT/DROP COLUMN 규칙

**문제 설명**: RK로 쓰이는 UK는 "Not Null Unique"여야 한다(§1). 예시 15는 "UK 자체를
삭제"하거나 "UK를 구성하는 컬럼 자체를 삭제"하는 경우만 다룬다. 그런데 컬럼을 삭제하지
않고 `ALTER TABLE ... MODIFY` 류의 문장으로 해당 컬럼의 NOT NULL 제약만 제거해서
NULL을 허용하도록 바꾸는 경우는 다루지 않는다. UK는 그대로 남아 있지만, 컬럼이
NULL을 허용하게 되면 "Not Null Unique"라는 RK의 자격 요건 자체가 깨지는 것 아닌가?
이 경우 UK 인덱스 구조는 그대로인데 RK로서의 자격만 잃는 애매한 상태가 될 수 있는데,
스펙은 이 경로를 언급하지 않는다.

**구체 예제**:
```sql
CREATE TABLE tbl2(
    a INT,
    b INT NOT NULL,
    CONSTRAINT u_tbl2_b UNIQUE(b)
);
-- b: NOT NULL UNIQUE -> RK로 선택됨 (PK 없으므로)

-- b의 NOT NULL 제약만 제거 시도
ALTER TABLE tbl2 MODIFY b INT NULL;
-- 이 시점에 RK 자격이 깨지는데, 이 ALTER 자체가 예시15(UNIQUE 삭제 금지)처럼
-- 막혀야 하는가? 스펙에 명시가 없다.
```

**예제 설명**: 이 시나리오는 "UNIQUE 제약 자체를 지우지도 않았고 컬럼을 지우지도
않았지만, RK의 필수 조건인 NOT NULL을 우회적으로 제거하는" 경로다. 예시 15의 규칙이
"UNIQUE 제약/컬럼 삭제"만 명시적으로 막고 있으므로, 이 경로가 막혀 있는지 스펙 문면만
봐서는 확신할 수 없다. 만약 막혀 있지 않다면 RK 자격이 깨진 채로 방치되는 우회로가
된다.

**제안**: RK로 사용 중인 UK 컬럼에 대해 NOT NULL 제약을 제거하는 ALTER 역시 예시
15와 동일하게 금지 대상임을 명시적으로 추가해야 한다.

## 리뷰 18

**[심각도: 보통] 트리거·시퀀스 등 종속 객체와 REPLICATION 옵션의 관계가 정의되지 않음**

**대상**: 스펙 전체

**문제 설명**: CUBRID는 트리거(TRIGGER, 특정 DML 이벤트 발생 시 자동 실행되는
프로시저)와 시퀀스(SERIAL, 자동 증가 값을 관리하는 객체) 기능을 제공한다. 이번
스펙은 REPLICATION 옵션을 테이블에만 적용하는 것으로 서술하는데, 복제 제외
테이블(REPLICATION=OFF)에 걸린 트리거가 마스터에서만 실행되고 슬레이브에서는 아예
실행되지 않는 것인지(데이터가 없으니 당연히 실행 안 될 것 같지만), 혹은 시퀀스 값이
마스터/슬레이브 간에 어떻게 동기화되는지(복제 제외 테이블이 시퀀스를 공유하는 다른
복제 대상 테이블과 얽혀 있다면 시퀀스 값이 어긋날 수 있음)에 대한 언급이 전혀 없다.

**구체 예제**:
```sql
CREATE TABLE audit_log(
    log_id  INT,
    message VARCHAR(200)
) REPLICATION = OFF;

CREATE TABLE orders(
    order_id INT PRIMARY KEY,
    amount   DECIMAL(10,2)
) REPLICATION = ON;

-- orders에 INSERT/UPDATE 시 audit_log에 기록을 남기는 트리거
CREATE TRIGGER trg_orders_audit
AFTER INSERT ON orders
EXECUTE INSERT INTO audit_log VALUES (audit_log_seq.NEXT_VALUE, 'order inserted');

-- 마스터에서 orders에 INSERT 발생 -> 트리거가 audit_log에도 INSERT
-- 슬레이브에는 orders INSERT만 복제되는가, 트리거로 인해 발생한
-- audit_log INSERT까지 복제 시도되었다가 대상 테이블이 OFF라서 버려지는가?
-- 그 과정에서 시퀀스(audit_log_seq)의 NEXT_VALUE 호출은 마스터에서만
-- 일어나므로 슬레이브와 시퀀스 현재값이 어긋나기 시작한다.
```

**예제 설명**: 이 예제는 REPLICATION=OFF 테이블이 트리거를 통해 간접적으로
갱신되는 경우, 그리고 그 과정에서 시퀀스 값이 소모되는 경우를 보여준다. 트리거
자체는 복제되는 DDL(§4)에 포함되어 슬레이브에도 존재하겠지만, 트리거가 실행되며
소모하는 시퀀스 값이 마스터와 슬레이브에서 어떻게 다뤄지는지는 이번 스펙의 관심사
밖에 있다. 그러나 이 문제는 REPLICATION=OFF 옵션이 도입되면서 처음 생기는 문제이므로,
최소한 "트리거/시퀀스는 이 스펙의 범위 밖"이라는 명시가 필요하다.

**제안**: 트리거·시퀀스와 REPLICATION 옵션의 상호작용을 이번 릴리스의 범위 밖(known
limitation)으로 명시하거나, 향후 검토 항목으로 별도 문서화해야 한다.

## 리뷰 19

**[심각도: 사소] 예시 23에도 trailing comma 구문 오류가 반복됨**

**대상**: §5-2, 예시 23 "외래키 컬럼 추가"

**문제 설명**: 리뷰 7에서 지적한 예시 2와 동일한 유형의 오류가 예시 23에도 있다.
```sql
CREATE TABLE new_orders(
    order_id INT PRIMARY KEY,
);
```
`order_id INT PRIMARY KEY,` 뒤에 바로 닫는 괄호가 와서 trailing comma 구문 오류가
발생한다. 같은 유형의 오류가 문서 내 최소 2곳(예시 2, 예시 23)에서 반복된다는 것은
이 문서가 실제 SQL 실행 검증 없이 손으로 작성/복사되었을 가능성을 시사하며, 문서
전체의 신뢰도에 의문을 남긴다.

**구체 예제**:
```sql
-- 스펙 원문 (오류)
CREATE TABLE new_orders(
    order_id INT PRIMARY KEY,
);

-- 수정본
CREATE TABLE new_orders(
    order_id INT PRIMARY KEY
);
```

**예제 설명**: 단일 컬럼 테이블을 만드는 가장 단순한 문장에서조차 trailing comma
오류가 나는 것은, 이 스펙의 SQL 예제들이 실행 검증 없이 작성되었을 가능성을 보여주는
방증이다. 다른 예제에도 유사한 오류가 남아있지 않은지 전수 점검이 필요하다.

**제안**: 문서에 포함된 모든 SQL 예제를 실제 CUBRID 인스턴스에 순서대로 실행해
문법 오류가 없는지 자동화된 방식으로 검증(예: 문서에서 코드 블록을 추출해 실행하는
스크립트)한 뒤 배포해야 한다.

## 리뷰 20

**[심각도: 사소] §9 요약에서 "SA"라는 용어가 처음이자 유일하게 등장하며 본문의
"싱글모드"와의 관계가 설명되지 않음**

**대상**: §9 SUMMARY, "이 키워드는 싱글 이나 SA에서도 사용 가능"

**문제 설명**: 스펙 본문(§1~§8)에서는 "HA 모드"와 "싱글 모드"라는 두 축으로만 서술이
이루어진다. §3의 제목조차 "Single 제약사항"이다. 그런데 마지막 요약 절인 §9에 가서
갑자기 "SA"라는 약어가 등장한다. CUBRID 제품에는 실제로 CS(Client-Server) 모드와
SA(Stand-Alone) 모드라는, HA 여부와는 다른 별개의 축이 존재하는 것으로 알려져 있다.
만약 §9의 "SA"가 이 Stand-Alone 모드를 가리키는 것이라면, 본문 전체에서 말하던
"싱글 모드"(아마도 HA가 아닌 CS 모드를 가리키는 것으로 추정)와 "SA 모드"가 같은
것인지 다른 것인지 스펙이 한 번도 구분해서 설명하지 않은 채 요약에서만 별도 언급을
한 셈이다. 이는 작성자 스스로도 "싱글 모드"와 "SA 모드"라는 두 축을 명확히 구분하지
않고 섞어 쓰고 있을 가능성을 시사하며, 독자에게는 "본문에서 말한 싱글 모드가 SA
모드까지 포함하는 개념인지" 의문을 남긴다.

**구체 예제**:
```
[본문 전체에서 쓰인 용어]
§1: "HA 모드는 cubrid hb start 로 실행시킨 상태, 나머지는 모두 싱글모드"
§3: "Single 제약사항"
§9: "이 키워드는 싱글 이나 SA에서도 사용 가능"  <- 여기서만 "SA" 등장

질문: §1의 정의("HA가 아니면 모두 싱글모드")를 그대로 따르면 SA 모드도
      이미 "싱글모드"에 포함되는 것 아닌가? 그렇다면 §9에서 "싱글 이나 SA"라고
      굳이 병렬로 나열한 이유는 무엇인가? (동어반복이거나, 혹은 실제로는
      "싱글모드=CS 모드 중 HA 아닌 것"이라는 제3의 정의가 숨어 있는 것인가?)
```

**예제 설명**: §1의 정의를 문자 그대로 받아들이면 "HA가 아닌 모든 상태"가 싱글
모드이므로 SA 모드도 이미 포함되어야 하는데, §9는 굳이 "싱글 이나 SA"라고 나눠
썼다. 이는 §1의 정의가 실제로는 완전하지 않거나(즉 "싱글모드"가 HA 아닌 CS 모드만을
암묵적으로 가리키고 SA는 별도 취급), 혹은 §9의 표현이 그냥 불필요한 중복이거나 둘 중
하나다. 어느 쪽이든 용어 정의의 정합성 문제다.

**제안**: §1에서 "싱글모드"의 정의를 CS/SA 모드 축까지 포함해 명확히 하고, §9의
"SA"라는 표현이 정말 필요한 별도 언급인지, 아니면 §1 정의에 이미 포함되는 중복
표현인지 정리해야 한다.
