# CUBRID HA 복제 개선 스펙 리뷰 — PM 3년차 관점

## 리뷰어 소개

3년차 프로덕트 매니저로서 DB 엔진/미들웨어 제품의 스펙 검토와 릴리스 관리를 담당하고 있다. 코드를 직접 짜지는 않지만 스펙 문서만 보고 개발자·QA·기존 고객이 어떤 순서로 이 기능을 마주치는지 시뮬레이션하는 것이 주 업무다. 이번 리뷰는 "요구사항이 빠짐없이 정의되어 있는가", "기존 사용자가 업그레이드했을 때 무엇이 깨지는가", "문서 자체가 구현팀·QA팀에게 애매함 없이 읽히는가"에 집중했다.

## 총평

이번 스펙은 PK(Primary Key, 테이블에서 각 행을 유일하게 식별하는 제약 조건)가 없는 테이블도 HA(High Availability, 마스터 장애 시 슬레이브가 대신 서비스를 이어받는 이중화 구성) 복제 대상에 포함시키기 위해 복제 키(RK) 자동 선택과 `REPLICATION` 옵션이라는 두 가지 장치를 도입한다. 문제 인식과 방향성 자체는 합리적이지만, 문서를 실제 운영 시나리오에 대입해보면 **RK 자동 선택 결과를 사용자가 조회할 방법이 없고, REPLICATION=OFF 테이블과 FK(외래키)가 얽힌 경우의 데이터 무결성 문제를 "책임지지 않는다"는 문구로 회피하고 있으며, 하위 버전 업그레이드·기존 클러스터 마이그레이션 경로가 전혀 서술되어 있지 않다**는 세 가지 큰 공백이 발견된다. 또한 §4, §7, §8 사이에 서로 다른 조건을 전제로 한 문장들이 섞여 있어 상호 모순처럼 읽히는 부분이 여럿 있고, 예제 코드에도 문법 오류·명명 불일치가 다수 있어 이 상태로는 QA 시나리오 작성이나 사용자 매뉴얼화가 어렵다. 컨셉 방향은 유지하되, 아래 20건을 반영해 "엔진이 무엇을 결정했는지 사용자가 확인할 수 있는 수단"과 "전환 경계에서의 명시적 동작 정의"를 먼저 채워 넣을 것을 권고한다.

## 리뷰 1

**[심각도: 치명] REPLICATION=OFF와 FK가 결합될 때의 데이터 무결성 문제를 해결책 없이 "책임지지 않는다"로 종결**

**대상**: §5(외래키), §6(뷰), 원본 다이어그램 설명(orders/customers 시나리오)

**문제 설명**: FK(Foreign Key, 한 테이블의 컬럼 값이 다른 테이블의 특정 컬럼에 실제로 존재하는 값이어야 한다는 참조 무결성 제약)를 가진 테이블이 REPLICATION=OFF인 테이블을 참조하는 것은 CREATE/ALTER 시점에 에러로 막는다고 되어 있다(예시 18, 23). 그런데 스펙은 동시에 "복제 대상인 orders가 참조하는 customers도 반드시 복제 대상이어야 한다"는 규칙을 **생성 시점 강제**로만 걸어두고, **운영 중 REPLICATION 속성 변경이나 뷰(VIEW)를 통한 우회 경로**는 "책임지지 않는다"(§6)는 문장으로 넘어간다. 즉 생성 시점 검사는 있는데 지속적 보장(invariant)이 없다. 이는 컨셉 자체의 구멍이지 문서 표현 문제가 아니다.

**구체 예제**:
```sql
-- 1) 정상적으로 FK 관계를 맺은 두 복제 대상 테이블
csql> CREATE TABLE customers(
    customer_id INT PRIMARY KEY,
    country INT
);  -- REPLICATION 옵션 생략 -> 기본값 ON

csql> CREATE TABLE orders(
    order_id INT PRIMARY KEY,
    customer_id INT,
    CONSTRAINT fk_customer_id FOREIGN KEY (customer_id) REFERENCES customers(customer_id)
);  -- REPLICATION 옵션 생략 -> 기본값 ON

-- 2) 운영 중 누군가 customers를 복제 제외로 전환한다
csql> ALTER TABLE customers REPLICATION=OFF;
-- 스펙 §4에 따르면 "복제 제외테이블은 ALTER TABLE...REPLICATION=ON 으로 변경하는 것 외의
--  모든 DDL을 사용할 수 있다"는 문장은 orders 쪽 제약이지, customers 자신을 OFF로 만드는
--  이 시점에 FK 참조 무결성을 검사한다는 규정이 스펙 어디에도 없다.
```

**예제 설명**: 예시 17에서는 CREATE TABLE 시점에 참조 테이블이 REPLICATION=OFF이면 에러를 낸다고 명시했지만, 이미 REPLICATION=ON으로 맺어진 FK 관계에서 **참조되는 쪽(customers)을 나중에 OFF로 바꾸는 경로**는 스펙에 검사 규칙이 없다. 이 SQL이 성공한다면 원본 문서가 그린 다이어그램(failover 이후 orders는 있는데 customers 데이터가 없어 FK를 만족시키지 못하는 상황)이 "생성 시점에는 막았지만 운영 중에는 다시 뚫리는" 결과로 재현된다.

**제안**: `ALTER TABLE customers REPLICATION=OFF`를 실행할 때 그 테이블을 참조하는 복제 대상 FK 자식 테이블이 존재하면 에러로 막거나, 최소한 §5의 "HA 모드 실행 시 참조하는 테이블의 상태를 확인해 에러를 출력"하는 검사가 **ALTER 시점에도** 동일하게 적용됨을 명시해야 한다.

## 리뷰 2

**[심각도: 치명] RK 자동 선택 알고리즘이 비결정적(non-deterministic)이며 조회 수단이 없다**

**대상**: §1 "UK가 여러개 존재한다면 큐브리드 엔진에 의해 이 중 하나가 선택된다(ex. 테이블내에 명시된 순서 중 가장 빠른 순서)"

**문제 설명**: "ex."라는 표현 자체가 이것이 확정된 규칙이 아니라 하나의 예시일 뿐임을 암시한다. 즉 **RK 선택 규칙이 확정되어 있지 않다.** 게다가 "테이블 내 명시된 순서"라는 기준은 컬럼/제약 추가·삭제(ALTER)가 반복되는 실제 운영 환경에서는 시간에 따라 바뀔 수 있는 값이다. 카탈로그(catalog, 테이블·컬럼·제약조건 등 메타데이터를 저장하는 시스템 내부 저장소)에 저장된 순서가 스토리지 재구성이나 버전 업그레이드로 바뀌면 RK 자체가 사용자 모르게 바뀔 수 있다.

**구체 예제**:
```sql
csql> CREATE TABLE t(
    a INT NOT NULL UNIQUE,
    b INT NOT NULL UNIQUE,
    c INT
);
-- PK가 없으므로 스펙 규칙에 따라 a, b 중 하나가 RK가 된다. "명시된 순서 중 가장 빠른 순서"라면
-- a가 RK로 선택될 것이다.

-- 이후 운영 중 DBA가 UK(a)를 재구성하기 위해 아래처럼 재생성한다.
csql> ALTER TABLE t DROP CONSTRAINT u_t_a;
csql> ALTER TABLE t ADD CONSTRAINT UNIQUE(a);
-- a에 대한 UK가 새로 만들어졌다. 이 새 UK가 카탈로그에서 "b보다 나중에 정의된 것"으로
-- 취급된다면, 이제 RK는 b로 바뀔 수 있다 — 스펙에 이를 막는 규정이 없다.
```

**예제 설명**: DROP 후 ADD로 제약을 재구성하는 것은 인덱스 재구성이나 스키마 리팩터링 시 흔한 패턴이다. 이 패턴만으로 RK가 a에서 b로 조용히 바뀔 수 있다면, 복제 엔진 입장에서는 이전에 a를 키로 삼아 전송하던 로그와 이후 b를 키로 삼는 로그가 섞이는 상황이 발생할 수 있고, 사용자는 자신이 RK를 바꿨다는 사실조차 알 수 없다.

**제안**: (1) RK 선택 규칙을 "ex."가 아닌 확정 규칙으로 명문화한다(예: 제약 생성 시각 오름차순, 또는 내부 constraint OID 오름차순). (2) 위 예시처럼 RK로 사용 중인 제약을 DROP했다가 다시 ADD하는 것이 RK 재선택을 유발하는지 여부를 명시한다. (3) 아래 리뷰 7과 연결되지만, 현재 RK가 어느 컬럼인지 조회하는 명령/카탈로그 뷰를 반드시 제공해야 한다.

## 리뷰 3

**[심각도: 치명] "복제키 없는 복제 테이블"을 둘러싼 §2-1/§4-1/§7의 서술이 서로 다른 시점 기준을 섞어 모순처럼 읽힌다**

**대상**: §2-1 예시 2, §4-1 예시 10, §7

**문제 설명**: §2-1은 "복제 키가 없는 테이블은 싱글 모드에서만 생성 가능하고, HA 전환 시 에러가 발생한다"고 말한다. §4-1은 "HA 모드에서는 CREATE TABLE 시 복제키가 없는 복제 테이블을 생성할 수 없다"고 말한다(즉 생성 자체를 막음, 에러는 HA 전환 때가 아니라 CREATE 시점). §7은 "HA 실행 시 제약사항을 확인하며 위반 시 에러와 함께 파일 리스트를 출력한다"고 말한다. 세 문장을 합치면: 싱글 모드에서 RK 없는 테이블을 만든 뒤 `cubrid hb start`로 HA를 켜는 시점에 에러가 나는 것(§2-1, §7)과, HA가 이미 켜진 상태에서 CREATE TABLE 자체가 거부되는 것(§4-1)은 서로 다른 시점의 이야기인데, 문서는 이를 마치 "복제키 없으면 에러"라는 하나의 규칙처럼 뭉뚱그려 쓰고 있어 독자가 "언제 에러가 나는지"를 정확히 재구성하기 어렵다.

**구체 예제**:
```
시나리오 A (싱글 모드에서 생성 후 HA 전환)
  1) 싱글 모드: CREATE TABLE t(a INT); -- RK 없음, REPLICATION 생략(ON)  => 성공 (§2-1)
  2) cubrid hb start                                                    => 에러 + 파일 리스트 (§7)

시나리오 B (HA 모드에서 직접 생성 시도)
  1) HA 모드: CREATE TABLE t(a INT); -- RK 없음, REPLICATION 생략(ON)  => 에러 (§4-1, 예시 10)
```

**예제 설명**: 두 시나리오 모두 "에러가 난다"는 결론은 같지만 실패 시점(hb start 시점 vs CREATE 시점)과 실패 형태(파일 리스트 출력 vs 단순 SQL 에러)가 다르다. 스펙만 읽고 QA 테스트케이스를 짠다면 두 시나리오를 같은 것으로 착각해 시나리오 B의 "파일 리스트 출력" 여부를 검증 누락할 위험이 크다.

**제안**: §2-1, §4-1, §7을 하나의 상태 전이표로 통합해 "싱글 모드에서 생성 / HA 모드에서 생성 / 싱글에서 만든 뒤 HA 전환" 세 케이스별로 실패 시점과 에러 형태(단순 에러 vs 파일 리스트)를 표로 명시할 것을 권고한다.

## 리뷰 4

**[심각도: 치명] 기존 운영 중인 HA 클러스터에 대한 업그레이드/마이그레이션 경로가 스펙에 전혀 없다**

**대상**: 스펙 전체(특히 §8, §9), 작업지시 배경(기존 CUBRID는 PK 있는 테이블만 복제)

**문제 설명**: 이 스펙은 신규 기능이 배포된 이후의 "새 세계"만 기술하고 있다. 그러나 PM 관점에서 가장 중요한 질문은 "이미 운영 중인 고객이 이 버전으로 업그레이드하면 무슨 일이 일어나는가"이다. 기존 버전은 PK 없는 테이블은 애초에 HA 복제가 불가능했으므로, 기존에 운영 중인 모든 테이블에는 PK가 있었을 것이다(그렇지 않으면 원래도 복제가 안 됐을 것이므로). 새 버전으로 업그레이드하면 이 기존 테이블들에 `REPLICATION` 카탈로그 컬럼(예시 9의 `replication` 필드)이 새로 생기는데, **in-place 업그레이드(기존 DB 볼륨을 그대로 새 바이너리로 띄우는 방식) 시 이 컬럼의 기본값을 무엇으로 채우는지**가 스펙에 없다. §8은 unloaddb/loaddb라는 별도 도구를 통한 이관만 다루고 있어 "재기동만으로 업그레이드"하는 훨씬 흔한 경로가 누락되어 있다.

**구체 예제**:
```
[업그레이드 전: 구버전, PK 있는 테이블만 존재]
  customers(customer_id PK, country)   -- 원래부터 복제되고 있었음
  orders(order_id PK, customer_id, FK->customers)  -- 원래부터 복제되고 있었음

[바이너리만 새 버전으로 교체, DB 볼륨은 그대로 재기동]
  -> 카탈로그에 REPLICATION 컬럼이 새로 추가되어야 하는데, 값이 ON인지 OFF인지 스펙에 없음
  -> customers, orders 모두 PK가 있으므로 RK 선택에는 문제 없지만,
     REPLICATION 값이 예상과 다르게 초기화되면 복제가 갑자기 멈추는 회귀(regression)가 발생할 수 있음
```

**예제 설명**: unloaddb/loaddb라는 명시적 도구를 거치지 않고 단순히 서버 바이너리를 올려서 재기동하는 것이 실무에서 훨씬 흔한 패치 업그레이드 방식이다. 이 경로에서 REPLICATION 값의 기본 초기화 규칙이 없으면, 기존 고객이 패치만 했는데 특정 테이블의 복제가 조용히 꺼지는 릴리스 리스크가 생긴다.

**제안**: "기존 카탈로그에 REPLICATION 컬럼이 없는 기존 테이블은 in-place 업그레이드 시 전부 ON으로 간주한다"는 문장을 §8과 별도로, 업그레이드 전용 섹션에 명시해야 한다. 또한 이 전환을 검증하는 업그레이드 회귀 테스트 항목을 릴리스 체크리스트에 포함해야 한다.

## 리뷰 5

**[심각도: 치명] §8 unloaddb/loaddb 규칙 두 문장이 서로 다른 기본값을 암시해 모순으로 읽힌다**

**대상**: §8 "복제 여부를 저장하는 변수가 설정되어 있지 않다면 복제 대상(Default)으로 간주한다" vs "하위 버전에서 unload 한 데이터 파일에는 ... 설정되어있지 않으므로 (싱글 모드에서) load 시 모두 복제 테이블로 설정된다"

**문제 설명**: 첫 문장만 보면 "변수 없음 = 복제 대상(ON)"이라는 일반 규칙처럼 읽힌다. 그런데 두 번째 문장은 굳이 "(싱글 모드에서)"라는 조건을 괄호로 덧붙여 같은 결론(모두 복제 테이블)을 다시 말하고 있다. 이 괄호가 왜 필요한지, 즉 **HA 모드에서 하위 버전 파일을 load하면 다른 동작을 하는지**가 암시만 되고 명시되지 않는다. 만약 HA 모드에서 load할 때도 동일하게 ON으로 간주한다면, RK가 없는 테이블이 복제 대상(ON)으로 만들어지는 셈이 되어 §4-1("HA 모드에서는 RK 없는 복제 테이블 생성 불가")과 정면으로 충돌한다.

**구체 예제**:
```
[하위 버전에서 만든 언로드 파일]
  테이블 old_tbl(id INT, name VARCHAR(50))  -- PK/UK 없음 (구버전은 PK 있는 테이블만 HA
  복제했으므로 이 테이블은애초에 복제 대상이 아니었을 가능성이 큼. 그러나 unload 포맷 자체에는
  "복제 여부" 변수가 없으므로 이 정보가 소실된 채로 파일만 존재.

[신버전에서 HA 모드로 이 파일을 loaddb]
  §8 첫 문장 규칙(변수 없으면 Default=복제 대상)을 그대로 적용하면 -> REPLICATION ON으로 생성 시도
  §4-1 규칙(HA 모드에서 RK 없는 복제 테이블 생성 불가)을 적용하면                -> 에러

  두 규칙이 동시에 적용 대상이 되는 이 케이스에 대해 스펙은 답을 주지 않는다.
```

**예제 설명**: old_tbl은 PK/UK가 없어 RK 후보가 없는 테이블이다. §8의 "변수 없으면 Default=복제 대상"을 곧이곧대로 따르면 HA 모드에서 RK 없는 복제 테이블을 만들려는 시도가 되어 §4-1과 충돌한다. 문서가 "(싱글 모드에서)"라는 조건을 괄호로만 처리하고 HA 모드 케이스를 침묵한 것은, 작성자도 이 충돌을 인지하고 회피한 것으로 보인다.

**제안**: HA 모드에서 이런 파일을 loaddb할 때의 동작(에러로 거부 / 자동으로 REPLICATION=OFF로 강등 / RK 자동 생성 시도)을 명시적으로 정의하고, 두 문장을 하나의 조건부 표(싱글 모드 vs HA 모드 × 변수 있음 vs 없음)로 재작성해야 한다.

## 리뷰 6

**[심각도: 중요] §7 "에러와 함께 파일 리스트를 출력"에서 "파일"의 정체가 정의되지 않았다**

**대상**: §7

**문제 설명**: HA 전환 시 제약 위반이 있으면 "파일 리스트"를 출력한다고 되어 있는데, 위반 대상은 테이블(그리고 그 테이블이 속한 DB 볼륨 파일들)이지 사용자가 일반적으로 다루는 "파일"이라는 단위와 자연스럽게 대응하지 않는다. 사용자가 실제로 마주치는 화면에 어떤 문자열이 찍히는지(테이블명 목록인지, 실제 OS 파일 경로인지, 로그 파일 위치인지) 알 수 없어 에러 메시지 설계도, QA 검증도 불가능하다.

**구체 예제**:
```
csql> cubrid hb start mydb
ERROR: HA 모드 전환 제약 위반
파일 리스트:
  ????   <- 여기에 실제로 무엇이 출력되는지 스펙에 없음
```

**예제 설명**: 위 의사코드(pseudo-code)처럼, "파일 리스트"라는 한 단어만으로는 QA가 "정상적으로 위반 테이블 이름이 나열되는가"를 검증할 재현 절차조차 만들 수 없다. 테이블이 100개 있는 스키마에서 이 중 3개가 RK 없이 REPLICATION=ON으로 남아있다면, 그 3개의 이름이 어떤 형식(테이블명 / 스키마.테이블명 / 파일 경로)으로 나오는지가 사용자 경험을 좌우한다.

**제안**: "파일"이라는 단어를 "위반한 테이블 목록(스키마.테이블명 형식)"으로 구체화하고, 출력 예시(실제 문자열 포맷)를 스펙에 추가한다.

## 리뷰 7

**[심각도: 중요] RK가 실제로 무엇으로 선택되었는지 조회할 카탈로그 수단이 없다**

**대상**: §2-3, 예시 8/9

**문제 설명**: 예시 8(`show create table`)과 예시 9(`select * from db_class`)는 모두 REPLICATION이 ON/OFF인지만 보여줄 뿐, **실제로 어떤 제약(PK인지, 혹은 어느 UK인지)이 RK로 선택되었는지는 보여주지 않는다.** 리뷰 2에서 지적했듯 RK 선택은 엔진이 자동으로 하고 사용자가 관여할 수 없는데, 그 선택 결과를 확인할 방법조차 없다면 운영자는 자신이 지금 어떤 컬럼을 함부로 건드리면 안 되는지(§4-2의 "복제키 후보가 1개인 경우" 제약과 직결) 알 방법이 없다.

**구체 예제**:
```sql
csql> CREATE TABLE t(
    a INT NOT NULL UNIQUE,
    b INT NOT NULL UNIQUE
);
-- RK 후보가 a, b 둘. 스펙 규칙상 "테이블내 명시된 순서 중 가장 빠른 순서"이므로 a가 RK로 추정.

csql> show create table t;
-- 예시 8 형식대로라면 REPLICATION ON만 보이고, "RK는 a의 UK다"라는 정보는 안 보인다.

csql> ALTER TABLE t DROP CONSTRAINT u_t_a;
-- 만약 a가 진짜 RK였다면 §4-2 규칙상 "복제키 후보가 1개(b)로 줄어드는 게 아니라
-- RK 자체(a)가 삭제되는" 상황인데, 이게 허용되는지(§4-2는 "복제키 후보가 1개인 경우"의
-- 제약만 정의하고 있고 "복제키 후보가 2개에서 1개로 줄어드는 DROP" 자체는 다루지 않음)
-- 사용자는 사전에 a가 RK인지 몰랐으므로 결과를 예측할 수 없다.
```

**예제 설명**: 이 예제는 두 가지를 동시에 보여준다. 첫째, 사용자는 `show create table`이나 `db_class`를 아무리 조회해도 a가 RK인지 b가 RK인지 알 수 없다. 둘째, RK 정보를 모른 채로 DROP CONSTRAINT를 실행하면 그 결과(성공/실패, 그리고 실패라면 왜 실패했는지)를 사전에 예측할 수 없어 운영자가 사고를 회피할 수단이 없다.

**제안**: `show create table`, `db_class`에 RK로 선택된 컬럼/제약명을 명시적으로 출력하는 필드를 추가해야 한다. 최소한 별도 카탈로그 뷰(예: `db_replication_key`)를 신설해 "테이블명, RK 제약명, RK 컬럼 목록"을 조회할 수 있게 해야 한다.

## 리뷰 8

**[심각도: 중요] REPLICATION 옵션 변경 시 대량 테이블/대용량 데이터에 대한 성능·락 영향이 기술되어 있지 않다**

**대상**: §2-2, §4

**문제 설명**: `ALTER TABLE tbl REPLICATION=OFF`처럼 보이는 것은 단순 메타데이터 변경 같지만, DDL(Data Definition Language, 테이블 구조 자체를 바꾸는 SQL 명령군)은 대상 테이블에 락(lock, 다른 트랜잭션의 동시 접근을 막는 잠금)을 거는 것이 일반적이다. 이 옵션 전환이 테이블 전체에 스키마 락을 거는지, 대용량 테이블에서 얼마나 걸리는지, 운영 중인 서비스에 영향을 주는지에 대한 언급이 전혀 없다. 마이그레이션(대량 데이터 이관) 작업 중 흔히 여러 테이블의 REPLICATION 속성을 일괄 변경하는 스크립트를 돌릴 텐데, 이때의 락 경합에 대한 정보가 없으면 릴리스 리스크 평가가 불가능하다.

**구체 예제**:
```sql
-- 데이터 이관 작업 중 배치 스크립트로 100개 테이블을 한 번에 복제 제외로 돌리는 흔한 시나리오
csql> ALTER TABLE huge_log_table_2023 REPLICATION=OFF;  -- 행 수 5억 건
csql> ALTER TABLE huge_log_table_2024 REPLICATION=OFF;  -- 행 수 5억 건
-- ... 반복 ...
```

**예제 설명**: 로그성 대용량 테이블을 복제 대상에서 빼는 것은 스토리지 절감을 위해 실무에서 흔히 벌어지는 작업이다. 이 ALTER가 테이블의 행 수에 비례해 시간이 걸리는 연산(예: RK 재계산이 필요한 연산)인지, 아니면 카탈로그 메타데이터만 바꾸는 즉시 완료 연산인지에 따라 서비스 영향이 완전히 다르다. 스펙에 이 정보가 없으면 운영팀은 이 작업을 점검 시간에 해야 하는지 언제든 해도 되는지 판단할 수 없다.

**제안**: REPLICATION 옵션 변경이 메타데이터 전용 연산이며 O(1)(테이블 크기와 무관하게 일정 시간)임을 명시하거나, 만약 그렇지 않다면 예상 소요 시간과 락 범위를 문서화해야 한다.

## 리뷰 9

**[심각도: 중요] REPLICATION=OFF 전환 후 슬레이브에 남아있던 기존 데이터의 처리 방침이 없다**

**대상**: §2-2 예시 6, §4

**문제 설명**: 예시 6은 `ALTER TABLE tbl REPLICATION=OFF`가 "OK"로 성공한다고만 보여준다. 그런데 이 테이블은 이전까지 REPLICATION=ON으로 정상 운영되며 슬레이브에도 데이터가 쌓여 있었을 것이다. OFF로 전환한 이후 마스터에서 발생하는 변경분은 더 이상 슬레이브로 전달되지 않겠지만, **슬레이브에 이미 쌓여 있던 데이터는 그대로 남는지, 삭제되는지, 아니면 그대로 "박제된 채" 남아 이후 조회 시 stale(오래되어 신뢰할 수 없는) 데이터를 보여주게 되는지**가 전혀 언급되지 않았다.

**구체 예제**:
```sql
-- 1) 정상 운영: tbl은 REPLICATION=ON, 마스터/슬레이브 모두 100만 건 동기화된 상태
-- 2) 운영자가 스토리지 절감을 위해 복제 중단 결정
csql> ALTER TABLE tbl REPLICATION=OFF;   -- OK (예시 6)
-- 3) 이후 마스터에서 계속 INSERT/UPDATE/DELETE 발생 -> 슬레이브로 전파 안 됨 (의도한 동작)
-- 4) 그런데 슬레이브의 tbl에는 여전히 2번 시점의 100만 건 스냅샷이 남아있다.
csql> -- 슬레이브에서:
csql> SELECT COUNT(*) FROM tbl;  -- 결과: 여전히 100만 건 근처 (마스터와는 이미 괴리됨)
```

**예제 설명**: 이 시나리오는 "복제를 껐다"는 사용자의 의도와 "슬레이브에 남은 데이터를 어떻게 취급할 것인가"라는 별개의 질문을 보여준다. 사용자가 REPLICATION=OFF를 실행한 이유가 "이 테이블은 더 이상 슬레이브에서 볼 필요 없다"는 것이라면, 슬레이브에 낡은 스냅샷이 계속 남아있는 것은 §6에서 이미 경고한 "두 노드 데이터 불일치"를 사용자가 직접 만들어내는 상황이 되어 매우 헷갈리는 사용자 경험을 낳는다.

**제안**: REPLICATION=OFF 전환 시 슬레이브에 남은 기존 데이터를 (a) 그대로 둘지 (b) TRUNCATE할지 (c) 사용자가 별도 명령으로 정리하게 할지 방침을 정하고, 최소한 "그대로 남는다"는 사실만이라도 §4나 §6에 명시해야 한다.

## 리뷰 10

**[심각도: 중요] REPLICATION=OFF → ON 전환 시 초기 데이터 동기화 방법이 없다**

**대상**: §2-2 예시 5(HA에서는 ERROR), §3(싱글/SA에서는 가능)

**문제 설명**: 예시 5에 따르면 HA 모드에서는 OFF→ON 전환이 막혀 있고, §3에 따르면 싱글/SA 모드에서는 REPLICATION 옵션 사용이 가능하다고 되어 있다. 그렇다면 사용자는 "HA를 잠깐 내리고 싱글 모드로 전환한 뒤 OFF였던 테이블을 ON으로 바꾸고 다시 HA를 켜는" 경로를 밟아야 하는데, 이 경우 **그동안 마스터에만 쌓여 있던 데이터를 슬레이브로 어떻게 최초 동기화하는지**가 스펙에 없다. 기존 CUBRID에는 이런 목적의 복제 재구성 도구(예: DB 전체 재구성/리로드)가 있지만, 이 스펙은 그 절차를 언급하지 않고 "가능하다"고만 말해 사용자가 실제로 실행 가능한 절차를 재구성할 수 없다.

**구체 예제**:
```
[운영 시나리오]
1) HA 운영 중, archive_2023 테이블은 REPLICATION=OFF (슬레이브에 데이터 없음)
2) 비즈니스 요구 변경으로 archive_2023도 이제 슬레이브에서 조회 가능해야 함
3) csql> ALTER TABLE archive_2023 REPLICATION=ON;  -- HA 모드이므로 예시 5에 따라 ERROR
4) 사용자가 택할 수 있는 경로가 스펙에 없음:
   - HA를 내리고 싱글 모드로 바꾼 뒤 ALTER? 그 경우 슬레이브의 archive_2023에는
     여전히 데이터가 0건인 채로 남아있을 텐데, HA 재시작 후 이 차이는 어떻게 메워지는가?
```

**예제 설명**: "옵션 값을 바꾸는 것"과 "그 옵션 값이 요구하는 데이터 상태를 실제로 맞추는 것"은 다른 작업이다. 스펙은 전자만 다루고 후자(최초 동기화)를 완전히 비워뒀다. 이 공백은 실제 운영자가 매뉴얼을 따라도 목표 상태에 도달할 수 없게 만든다.

**제안**: OFF→ON 전환 후 슬레이브 데이터를 채우는 공식 절차(예: 해당 테이블만 재언로드/재로드, 혹은 DB 전체 리빌드가 유일한 방법이라는 사실)를 §2-2 또는 별도 섹션에 명시해야 한다.

## 리뷰 11

**[심각도: 중요] PostgreSQL REPLICA IDENTITY 대비 사용자 지정 옵션이 없어 경쟁력이 뒤처진다**

**대상**: 컨셉 자체(작업지시 배경의 "PostgreSQL REPLICA IDENTITY 컨셉 일부 채용" 언급)

**문제 설명**: PostgreSQL의 REPLICA IDENTITY는 `DEFAULT`(PK 사용), `USING INDEX idx_name`(특정 UNIQUE 인덱스를 사용자가 직접 지정), `FULL`(모든 컬럼 사용), `NOTHING`(키 없음) 네 가지 모드를 제공해 **사용자가 어떤 인덱스를 키로 쓸지 직접 선택**할 수 있다. 반면 이 스펙은 "엔진이 알아서 UK 중 하나를 고른다"는 자동 선택만 제공하고 사용자 지정 경로가 없다. UK가 여러 개인 테이블에서 특정 UK가 자주 NULL이 되거나(주의: NOT NULL UNIQUE라 NULL은 없지만, 값이 자주 변경되는 컬럼일 수 있음) 성능상 부적합한 경우에도 사용자는 원하는 UK를 RK로 지정할 방법이 없다. "일부만 채용"했다고 명시했지만, 정작 REPLICA IDENTITY 컨셉의 핵심 가치인 "운영자의 명시적 선택권"이 빠진 채 자동화만 가져온 셈이다.

**구체 예제**:
```sql
csql> CREATE TABLE t(
    a INT NOT NULL UNIQUE,   -- 값이 자주 변경되는 자연키(natural key), 예: 이메일
    b INT NOT NULL UNIQUE,   -- 값이 절대 변경되지 않는 대체키(surrogate key), 예: 내부 발급 코드
    c INT
);
-- 운영자는 값이 안 바뀌는 b를 RK로 쓰고 싶지만, 스펙 규칙(정의 순서상 가장 빠른 것)대로면
-- a가 RK로 선택된다. 사용자가 이를 뒤집을 방법이 없다.
```
PostgreSQL이라면:
```sql
ALTER TABLE t REPLICA IDENTITY USING INDEX t_b_key;  -- 사용자가 b를 명시적으로 지정 가능
```

**예제 설명**: 자연키(비즈니스 의미가 있어 값이 바뀔 수 있는 키)를 RK로 삼으면 리뷰 2에서 지적한 것처럼 컬럼 값 변경 시 복제 키 관리가 까다로워진다. 값이 절대 바뀌지 않는 대체키를 RK로 쓰는 것이 운영상 훨씬 안전한데, 이 스펙은 그 선택권을 사용자에게 주지 않는다.

**제안**: 최소 기능(MVP)으로 자동 선택만 먼저 내놓더라도, 로드맵 상에 "사용자 지정 RK" 옵션(예: `REPLICATION KEY USING INDEX idx_name`)을 후속 과제로 명시해 두어야 경쟁 제품과의 격차를 줄일 수 있다.

## 리뷰 12

**[심각도: 중요] §4-2 "다른 복제키 후보가 함께 존재한다면 모든 DDL은 허용된다(단, 기존의 제약사항은 유지된다)"에서 "기존의 제약사항"이 무엇을 가리키는지 불명확**

**대상**: §4-2 도입부

**문제 설명**: 이 문장은 복제키 후보가 2개 이상일 때는 자유롭게 DDL이 가능하다고 하면서 괄호로 "기존의 제약사항은 유지된다"는 예외를 덧붙인다. 그런데 "기존의 제약사항"이 (a) CUBRID가 원래부터 갖고 있던 일반 SQL 제약(예: PK 중복 불가)을 말하는 것인지, (b) 바로 위 문단에서 말한 "복제키 후보가 1개인 경우"의 제약을 가리키는 것인지, (c) 구버전 HA의 "PK 있는 테이블만 복제"라는 옛 제약을 가리키는 것인지 문맥상 셋 다 가능하게 읽힌다.

**구체 예제**:
```sql
csql> CREATE TABLE t(
    a INT PRIMARY KEY,
    b INT NOT NULL UNIQUE,   -- RK 후보 2개(PK, UK) 존재 -> "모든 DDL 허용" 규칙 적용 대상
    c INT
);

-- "모든 DDL이 허용된다"면 아래도 되어야 하는데:
csql> ALTER TABLE t DROP PRIMARY KEY;
-- 이것이 §4-2 첫 문단이 말하는 "PK가 복제키로 사용될 경우 삭제 불가"(예시 12)에 걸리는지,
-- 아니면 "후보가 2개이므로 모든 DDL 허용"에 해당해 성공하는지 스펙 문장만으로는 결정 불가.
```

**예제 설명**: 이 테이블은 PK(a)와 UK(b) 두 개의 RK 후보를 갖고 있다. RK는 규칙상 PK인 a로 확정된다. 이 상태에서 "다른 후보(b)가 함께 존재하므로 모든 DDL이 허용된다"는 문장을 그대로 적용하면 DROP PRIMARY KEY도 허용되어야 할 것 같지만, 예시 12는 "PK가 복제키로 사용될 경우 삭제할 수 없다"고 명시하고 있어 정반대 결론이 나온다. 두 규칙 중 어느 것이 우선하는지 스펙 문장 순서만으로는 판단할 수 없다.

**제안**: "모든 DDL이 허용된다"는 표현을 "RK 자체를 제거하는 DDL을 제외한 모든 DDL이 허용된다"처럼 구체화하고, "기존의 제약사항"이 정확히 어떤 규칙 집합을 가리키는지 각주나 상호 참조로 명시해야 한다.

## 리뷰 13

**[심각도: 중요] 예시 13(PK를 다른 컬럼으로 교체하는 복합 ALTER)의 원자성(atomicity)이 불명확**

**대상**: §4-2 예시 13

**문제 설명**: `ALTER TABLE table_name DROP CONSTRAINT PRIMARY KEY, ADD CONSTRAINT PRIMARY KEY(a)`처럼 하나의 문장 안에서 기존 PK를 지우고 새 PK를 추가하는 복합 DDL을 "OK"로 허용한다고 되어 있다. 그런데 이 두 동작(DROP, ADD)이 하나의 트랜잭션으로 원자적으로 처리되는지, 아니면 순차적으로 처리되어 그 "중간 순간"에 테이블이 RK 후보 0개 상태(즉 §1의 "RK가 없으면 HA를 실행할 수 없다"는 제약을 순간적으로 위반하는 상태)를 거치는지가 불명확하다. 만약 순차 처리라면, 그 찰나에 복제 로그를 만드는 다른 트랜잭션이 끼어들 경우 어떻게 처리되는지도 정의되어야 한다.

**구체 예제**:
```sql
-- HA 운영 중, RK 후보가 PK(a) 하나뿐인 테이블
csql> CREATE TABLE t(a INT PRIMARY KEY, b INT NOT NULL);

-- 예시 13대로 PK를 a에서 b로 옮기고 싶다면 b를 UNIQUE로 먼저 만들어야 하지만
-- (b는 현재 NOT NULL이지만 UNIQUE는 아님) 예시 13 원문은 이 전제조건조차 언급하지 않고
-- 바로 DROP/ADD PRIMARY KEY(a->b 아님, 여기선 동일 컬럼 예시지만 실제 컬럼 교체 시):
csql> ALTER TABLE t DROP CONSTRAINT PRIMARY KEY, ADD CONSTRAINT PRIMARY KEY(b);
-- Q1. 이 한 문장 실행 도중 동시에 다른 세션이 t에 INSERT를 실행하면 어느 시점의 RK로
--     복제 로그가 기록되는가?
-- Q2. b에 UNIQUE 제약도 NOT NULL도 없다면(값 중복 가능) 이 ADD CONSTRAINT는 그 자체로
--     실패해야 하는데, 실패 시 DROP은 이미 반영된 상태로 롤백되지 않는 것은 아닌가?
```

**예제 설명**: 이 예제는 "하나의 SQL 문장처럼 보이는 것이 실제로 원자적 트랜잭션인지"를 확인하려는 질문이다. RK가 순간적으로 사라지는 창(window)이 존재한다면, 그 사이 발생한 복제 대상 DML(데이터 조작 명령)은 applylogdb(슬레이브 쪽에서 복제 로그를 실제로 적용하는 모듈) 입장에서 키를 찾을 수 없어 에러가 날 위험이 있다 — 이는 정확히 이 스펙이 해결하려는 원래 문제(작업지시 배경의 "복제 누락 + fail_count 증가")를 예시 13이 스스로 재현할 위험이 있다는 뜻이다.

**제안**: 예시 13과 같은 복합 ALTER는 단일 트랜잭션/단일 카탈로그 갱신으로 원자적으로 처리됨을 명시하고, 중간 상태가 외부(다른 세션, 복제 로그)에 노출되지 않음을 스펙에 보증 문구로 추가해야 한다.

## 리뷰 14

**[심각도: 보통] 예시 8과 예시 11의 제약명이 우연히 일치하지만 문서 전체에서 하나의 연속된 시나리오로 관리되지 않아 추적이 어렵다**

**대상**: 예시 8(`pk_tbl_a`), 예시 11(`Primary key "pk_tbl_a" already defined for class "dba.tbl"`)

**문제 설명**: 두 예시에 같은 제약명(`pk_tbl_a`)과 테이블명(`tbl`)이 등장하지만, 그 사이(예시 9, 10)에는 전혀 다른 테이블(`db_class` 조회 결과, `repl_table_with_rk`)이 끼어 있어 이것이 "같은 테이블을 이어서 설명하는 것"인지 "우연히 이름이 겹친 별개 예시"인지 독자가 매번 다시 판단해야 한다. 스펙 문서 전체에 걸쳐 예시 번호와 등장 테이블명의 대응 관계를 관리하는 원칙이 없다.

**구체 예제**:
```
예시 8: tbl (PK: pk_tbl_a, 컬럼 a, b)
예시 9: tbl (db_class 조회 - 예시 8과 같은 테이블로 추정되나 명시 안 됨)
예시 10: repl_table_with_rk (별개 테이블, RK 없어서 에러)
예시 11: tbl (PK: pk_tbl_a - 예시 8과 같은 이름이 다시 등장)
```

**예제 설명**: 문서를 순서대로 읽는 독자는 예시 10에서 잠깐 다른 테이블 이름을 봤다가 예시 11에서 다시 `tbl`을 마주치면, 이것이 예시 8/9의 연장인지 아닌지 헷갈리게 된다. 스펙 문서가 QA 테스트케이스의 기반이 된다는 점을 고려하면, 예시별로 독립된 테이블명을 쓰거나 "이하 tbl은 예시 8과 동일한 테이블"이라는 각주가 필요하다.

**제안**: 예시마다 테이블을 새로 정의하거나(권장), 동일 테이블을 재사용할 경우 "예시 N과 동일한 테이블"이라는 명시적 각주를 추가해 문서 가독성과 QA 재현성을 높인다.

## 리뷰 15

**[심각도: 보통] 예시 19~22에서 FK 제약명이 어디서 생겼는지 설명 없이 등장한다**

**대상**: 예시 19("OK"만 표시, 제약명 없음), 예시 21(`fk_new_orders_customer_id`로 DROP)

**문제 설명**: 예시 19는 `ALTER TABLE new_orders ADD CONSTRAINT FOREIGN KEY(customer_id) REFERENCES customers(customer_id)`를 실행하면서 제약 이름을 지정하지 않았다. 그런데 예시 21은 이 제약을 `fk_new_orders_customer_id`라는 이름으로 DROP한다. CUBRID가 이름 없는 제약에 자동으로 이름을 부여하는 규칙(예: `fk_<테이블명>_<컬럼명>`)이 존재한다는 뜻인데, 이 자동 명명 규칙이 스펙 어디에도 설명되어 있지 않다.

**구체 예제**:
```sql
csql> CREATE TABLE new_orders(
    order_id INT PRIMARY KEY,
    customer_id INT
);

csql> ALTER TABLE new_orders ADD CONSTRAINT FOREIGN KEY(customer_id)
REFERENCES customers(customer_id);
-- OK  (제약 이름을 지정하지 않았음)

-- ...나중에...
csql> ALTER TABLE new_orders DROP FOREIGN KEY (fk_new_orders_customer_id);
-- 이 이름이 어떻게 자동 부여됐는지 스펙에 없음. 사용자가 실제로 이 이름을 알고
-- DROP 문을 쓰려면 별도로 조회(show create table)를 먼저 해봐야 하는데, 이는
-- 사용성 관점에서 "예측 불가능한 이름을 외워서 지워야 하는" 마찰을 유발한다.
```

**예제 설명**: 이름을 지정하지 않고 만든 제약을 나중에 특정 이름으로 지워야 한다면, 그 자동 생성 규칙이 문서화되어 있지 않은 이상 사용자는 매번 `show create table`로 이름을 다시 확인해야 한다. 이는 이 스펙이 신규로 만드는 문제는 아니지만, FK 예제 전체가 이 패턴을 반복하고 있어 문서 품질 문제로 지적할 가치가 있다.

**제안**: 자동 명명 규칙을 스펙 어딘가(부록 등)에 명시하거나, 최소한 예시 19에서 실제로 자동 부여된 이름이 `fk_new_orders_customer_id`임을 예시 출력에 포함해 예시 21과의 연결을 분명히 해야 한다.

## 리뷰 16

**[심각도: 보통] 여러 CREATE TABLE 예시에 트레일링 콤마(trailing comma) 문법 오류가 반복된다**

**대상**: 예시 2, 예시 20, 예시 23

**문제 설명**: 예시 2는 `CREATE TABLE repl_table_without_rk(a INT,);`처럼 마지막 컬럼 정의 뒤에 콤마가 남아있다. 예시 23도 `CREATE TABLE new_orders(order_id INT PRIMARY KEY,);`로 동일한 패턴이다. 표준 SQL 및 CUBRID 문법에서 컬럼 목록 마지막에 콤마를 남기는 것은 보통 문법 오류다. 이 오류가 (a) 단순 오탈자인지, (b) CUBRID가 실제로 트레일링 콤마를 허용하는 관대한 파서를 갖고 있어서 의도적으로 그렇게 쓴 것인지 스펙만으로는 판단할 수 없다.

**구체 예제**:
```sql
-- 예시 2 원문 그대로
csql> CREATE TABLE repl_table_without_rk(
    a INT,
);
-- 콤마 뒤에 컬럼 정의가 없다. 대부분의 SQL 파서는 이를 syntax error로 처리한다.
```

**예제 설명**: 이 예시가 보여주려는 핵심은 "RK가 없는 테이블도 싱글 모드에서는 생성 가능하다"는 것인데, 정작 예제 SQL 자체가 문법 오류를 담고 있다면 신규 사용자나 QA가 그대로 복사해서 실행했을 때 "RK 없음" 때문에 실패한 것인지 "문법 오류" 때문에 실패한 것인지 구분할 수 없어 예제의 설득력이 떨어진다.

**제안**: 모든 예제 SQL을 실제 CUBRID 인스턴스에 한 번씩 실행해 검증한 뒤 스펙에 반영하는 교정 절차를 릴리스 전 문서 체크리스트에 추가해야 한다.

## 리뷰 17

**[심각도: 보통] "HA 모드"/"싱글 모드"/"SA 모드" 세 용어의 관계가 §1과 §3/§9에서 다르게 서술된다**

**대상**: §1("HA 모드는 cubrid hb start로 실행시킨 상태를 의미하며 나머지는 모두 싱글모드"), §3("싱글 모드에서 생성된..."), §9("이 키워드는 싱글 이나 SA에서도 사용 가능")

**문제 설명**: §1은 이분법(HA vs 싱글)으로 모드를 정의한다("나머지는 모두 싱글모드"). 그런데 §9는 "싱글 이나 SA"라는 표현으로 싱글과 SA(Standalone, 단독 실행 모드로 CUBRID에서 별도로 존재하는 서버 기동 방식)를 별개 항목처럼 나열한다. §1의 정의대로라면 SA도 "나머지"에 속해 싱글 모드에 포함되어야 하는데, §9는 왜 굳이 나눠 썼는지 설명이 없다. 초심자 입장에서는 SA가 싱글 모드의 부분집합인지, 아니면 완전히 다른 제3의 모드인지 판단할 수 없다.

**구체 예제**:
```
§1의 정의를 따르면:
  모드 = { HA 모드, 싱글 모드(그 외 전부) }   -- SA는 싱글 모드에 포함되어야 함

§9의 표현을 따르면:
  모드 = { HA, 싱글, SA }   -- SA가 독립 항목으로 나열됨

사용자가 실제로 궁금한 질문:
  csql> -- SA 모드로 기동한 서버에서
  csql> CREATE TABLE t(a INT) REPLICATION=OFF;
  -- 이게 되는지 여부는 §1 정의로는 "싱글 모드에 포함"이므로 가능해야 하고,
  -- §9 표현으로도 "싱글 이나 SA에서 가능"이라 하니 결론은 같지만,
  -- 두 서술이 왜 다른 분류 체계를 쓰는지는 여전히 불명확하다.
```

**예제 설명**: 결론(SA에서도 REPLICATION 옵션 사용 가능)은 다행히 일치하지만, 정의 방식이 문서 내에서 두 번 다르게 등장하는 것은 독자에게 "내가 뭔가 놓친 제3의 규칙이 있나"하는 불필요한 의심을 심는다. 특히 이 스펙은 모드 전환(싱글→HA)이 핵심 주제이므로 모드 용어 정의는 가장 먼저, 가장 명확하게 고정되어야 한다.

**제안**: §1 도입부에서 HA/싱글/SA 세 모드의 관계를 벤 다이어그램이나 명시적 문장("SA는 싱글 모드의 한 실행 방식이다" 등)으로 한 번에 정의하고, 이후 섹션은 이 정의를 재사용한다.

## 리뷰 18

**[심각도: 보통] "복제 대상인 FK 자식 테이블이 참조하는 부모 테이블은 복제 대상이어야 한다"는 규칙이 부모→자식 방향의 캐스케이드(다단계 참조) 케이스를 다루지 않는다**

**대상**: §5

**문제 설명**: §5의 규칙과 예시들은 모두 "자식 테이블 1개 → 부모 테이블 1개"의 단순한 2단 구조만 다룬다. 실무에서는 A→B→C처럼 여러 단계로 FK가 이어지는 경우가 흔한데, 이런 다단계 참조 사슬에서 중간 테이블(B)이 REPLICATION=OFF가 되려는 시도를 언제 막는지(B를 참조하는 A가 있을 때 vs B가 참조하는 C가 없을 때) 스펙이 명확히 다루지 않는다.

**구체 예제**:
```sql
csql> CREATE TABLE countries(
    country_id INT PRIMARY KEY
);  -- REPLICATION 기본 ON

csql> CREATE TABLE customers(
    customer_id INT PRIMARY KEY,
    country_id INT,
    FOREIGN KEY(country_id) REFERENCES countries(country_id)
);  -- REPLICATION 기본 ON, countries를 참조

csql> CREATE TABLE orders(
    order_id INT PRIMARY KEY,
    customer_id INT,
    FOREIGN KEY(customer_id) REFERENCES customers(customer_id)
);  -- REPLICATION 기본 ON, customers를 참조

-- 여기서 customers를 복제 제외로 바꾸려 하면?
csql> ALTER TABLE customers REPLICATION=OFF;
-- customers는 orders의 부모이면서 동시에 countries를 참조하는 자식이기도 하다.
-- §5는 "참조하는 모든 테이블이 복제 대상이어야 한다"고만 하지, customers 자신을
-- 참조하는 orders(자식) 쪽 검사를 요구하는지는 리뷰 1에서 지적한 대로 불명확하고,
-- 이 3단 체인 전체를 검사 범위로 두는지도 스펙에 없다.
```

**예제 설명**: countries-customers-orders 3단 체인은 실무 스키마에서 매우 흔한 구조다. §5는 "직접 참조하는 부모가 복제 대상인지"만 검사 대상으로 언급하고 있어, 이 체인 전체를 재귀적으로 검사해야 하는지(중간 단계인 customers가 자신의 부모 countries 상태까지 신경 써야 하는지) 판단할 근거가 없다.

**제안**: FK 참조 사슬이 다단계일 때 검사가 직접 부모 1단계에만 적용되는지 전체 사슬에 재귀적으로 적용되는지를 §5에 명시하고, 3단 이상 체인 예제를 추가한다.

## 리뷰 19

**[심각도: 보통] 이 기능이 신규 생성 DB에만 적용되는지, 기존 DB에도 무중단으로 적용 가능한지에 대한 릴리스 범위가 불명확하다**

**대상**: 스펙 전체, 특히 §8과의 관계

**문제 설명**: §8은 unloaddb/loaddb를 통한 이관 시나리오만 다루고 있어, 이 기능이 "새로 만드는 DB부터 적용되는 기능"인지 "기존에 돌고 있는 DB에도 패치만으로 즉시 적용되는 기능"인지 구분이 안 된다. 릴리스 노트/마이그레이션 가이드 작성 관점에서 이는 결정적인 차이다. 전자라면 기존 고객은 이 기능을 쓰려면 unloaddb/loaddb라는 무거운 작업을 거쳐야 하고, 후자라면 그냥 패치만 하면 된다.

**구체 예제**:
```
시나리오 X: "패치 적용만으로 기존 DB에 REPLICATION 옵션 사용 가능"이 맞다면
  1) 기존 운영 DB에 신버전 패치 적용, 재기동
  2) 바로 csql> ALTER TABLE existing_tbl REPLICATION=OFF;  실행 가능해야 함

시나리오 Y: "unloaddb/loaddb를 거쳐야만 새 기능 사용 가능"이 맞다면
  1) 기존 운영 DB를 unloaddb
  2) 신버전으로 loaddb (§8 규칙에 따라 복제 대상 여부 재구성)
  3) 이후에야 REPLICATION 옵션 사용 가능

두 시나리오 중 어느 쪽이 맞는지 스펙에 근거가 없다.
```

**예제 설명**: 이 두 시나리오는 릴리스 작업량이 완전히 다르다. 시나리오 X는 일반적인 마이너 패치이고, 시나리오 Y는 다운타임을 동반하는 대규모 마이그레이션 작업이다. PM 입장에서 릴리스 리스크와 고객 커뮤니케이션 방식이 완전히 달라지므로 이 구분이 스펙에 명시되지 않은 것은 릴리스 계획 수립을 불가능하게 만드는 공백이다.

**제안**: "이 기능은 in-place 패치로 기존 DB에도 즉시 적용 가능하다" 또는 "unloaddb/loaddb 마이그레이션이 필요하다" 중 하나를 명확히 선언하는 섹션을 스펙 서두에 추가해야 한다. (리뷰 4에서 지적한 카탈로그 초기화 문제와도 직결된다.)

## 리뷰 20

**[심각도: 사소] 오탈자 및 문서 다듬기 미비로 전문 문서로서의 신뢰도가 떨어진다**

**대상**: §5-1 제목("CRATE TABLE" → "CREATE TABLE" 오타), 전반적인 띄어쓰기·조사 오류, 일부 예시의 결과 출력 형식 불일치(예시 5/6/10/12는 "ERROR"/"OK"만 표기, 예시 8/9/11은 실제 출력 전문을 표기 — 어느 예시가 실제 화면 캡처이고 어느 예시가 요약인지 표기 규칙이 없음)

**문제 설명**: §5-1의 소제목 "CRATE TABLE 예시"는 "CREATE"의 단순 오타다. 이 자체는 사소하지만, 스펙 문서 전반에 걸쳐 이런 오탈자와 서식 불일치가 누적되어 있으면(리뷰 16의 SQL 문법 오류까지 포함) 이 문서가 충분히 검토(review)되지 않은 초안 수준으로 비칠 위험이 있고, 실제로 앞선 19건의 리뷰에서 지적한 여러 모호함·모순이 "의도된 생략"이 아니라 "단순 누락"일 가능성에 무게를 싣는 정황 증거가 된다.

**구체 예제**:
```
§5-1 원문 소제목: "5-1. CRATE TABLE 예시"
                        ^^^^^ CREATE의 오타

또한 예시 결과 표기 방식 비교:
  예시 5, 6, 10, 12, 13, 14, 15, 16 등: "ERROR" 또는 "OK" 한 단어만 표기
  예시 8, 9, 11: 실제 콘솔 출력 전체(구분선, 필드명 포함)를 표기

  -> 왜 어떤 예시는 축약하고 어떤 예시는 전체를 보여주는지 기준이 없다.
```

**예제 설명**: 오타 자체보다 중요한 것은 이런 사소한 흠들이 반복되는 패턴이다. 하나의 스펙 문서 안에서 결과 표기 방식이 예시마다 다른 것은, 이 문서가 여러 차례에 걸쳐 부분적으로 수정되었고 전체 통일 편집(교정쇄 검토) 단계를 거치지 않았음을 시사한다. 문서 품질에 대한 신뢰가 낮아지면 리뷰어와 구현자 모두 "이 문장이 의도된 것인지 실수인지"를 매번 재확인해야 하는 비용이 발생한다.

**제안**: 릴리스 전 최종 교정(proofreading) 패스를 한 번 거치고, 모든 예시의 결과 표기를 "실제 콘솔 출력 전문" 형식으로 통일할 것을 권고한다.
