# CUBRID HA 복제 키(RK) / REPLICATION 옵션 스펙 리뷰 — DB 엔진 개발자(10년차) 관점

## 리뷰어 소개

DBMS 엔진 코어(스토리지, 복제, 카탈로그 매니저)를 10년째 개발하고 있는 엔진 개발자다. 카탈로그(catalog, DBMS가 테이블·컬럼·제약조건 등 스키마 정보를 저장해두는 내부 메타데이터 저장소) 스키마 변경, 복제 로그 포맷, 트랜잭션 원자성(atomicity, 하나의 작업 단위가 "전부 성공" 아니면 "전부 실패"로만 끝나야 한다는 성질) 같은 구현 세부사항과, 그 구현이 장기적으로 유지보수 가능한 아키텍처인지를 함께 본다.

## 총평

이 스펙은 "PK 없는 테이블은 복제가 안 된다"는 기존 문제를 사용자 관점 SQL 옵션(REPLICATION, RK 자동 선택)으로 풀어내는 데는 성공했지만, 그 SQL이 엔진 내부에서 **언제, 어떤 순서로, 얼마나 원자적으로** 처리되는지에 대한 설명이 통째로 빠져 있다. RK가 자동으로 선택·재선택되는 로직의 결정성(determinism, 같은 입력이면 항상 같은 출력이 나온다는 성질)이 불명확하고, RK가 바뀌는 순간의 복제 로그 정합성, 카탈로그 스키마 자체의 변경 범위, unloaddb/loaddb 파일 포맷의 하위 호환성, 파티션·트리거·시리얼 같은 스펙이 아예 언급조차 하지 않은 객체들과의 상호작용이 전부 미정의 상태다. 더 심각한 건 스펙 §8과 §9 사이에 "unloaddb 변수가 없을 때의 기본값"이 정반대로 적혀 있다는 점인데, 이는 문서 오류를 넘어서 구현자가 어느 쪽을 정답으로 삼아야 할지조차 알 수 없게 만드는 치명적 결함이다. 컨셉 자체(PostgreSQL REPLICA IDENTITY 부분 채용)는 방향은 맞지만, PG가 제공하는 폴백(FULL identity)이나 명시적 지정(REPLICA IDENTITY USING INDEX) 같은 안전장치 없이 "엔진이 알아서 고른다"만 남겨둔 것은 장기적으로 디버깅 불가능한 복제 불일치를 낳을 소지가 크다. 아래 20개 항목에서 구체적으로 짚는다.

### 리뷰 1

**[심각도: 치명] unloaddb 기본값이 §8과 §9에서 정반대로 기술됨**

- 대상: §8 "UNLOADDB & LOADDB" 4번째 항목 vs §9 "SUMMARY" 마지막 항목

§8은 "복제 여부를 저장하는 변수가 설정되어 있지 않다면 **복제 대상(Default)**으로 간주한다"고 말한다. 반면 §9 SUMMARY 마지막 줄은 "UNLOADDB 시 복제 대상 여부를 함께 출력해야하며, **이를 포함하지 않는 테이블은 모두 복제 제외 테이블**이다"라고 말한다. 정확히 반대다. 하나는 "값 없음 → ON", 다른 하나는 "값 없음 → OFF"다.

```
# 시나리오: 구버전(REPLICATION 개념 도입 이전) unload 파일을 신버전 loaddb로 적재
$ cubrid unloaddb -i legacy_db legacy_output   # REPLICATION 필드 없는 구버전 포맷
$ cubrid loaddb   -d new_db legacy_output.unload  # 신버전 엔진

# §8 규칙 적용 시: 모든 테이블 REPLICATION=ON 으로 생성
# §9 규칙 적용 시: 모든 테이블 REPLICATION=OFF 으로 생성
# → 구현자가 어느 문서를 참조했는지에 따라 완전히 다른 DB가 만들어진다
```

**예제 설명**: 같은 입력 파일을 같은 loaddb 커맨드로 적재해도, 구현이 §8을 따르면 하위 호환 목적(기존 데이터가 전부 복제되던 구버전 동작 유지)에 부합하지만, §9를 따르면 정반대로 아무것도 복제되지 않는 DB가 만들어진다. 이는 단순 오탈자가 아니라 "구버전 마이그레이션 시 데이터가 새는가 안 새는가"를 결정하는 핵심 분기점이다. 실제로 §8 본문 바로 다음 줄에 "특히 하위 버전에서 unload 한 데이터 파일에는 ... load 시 모두 복제 테이블로 설정된다"라는 명시적 문장이 있어 §8 쪽이 의도된 값으로 보이지만, 요약본(§9)이 반대로 적혀 있다는 것 자체가 검토 과정에서 아무도 두 절을 대조하지 않았다는 신호다.

**제안**: 스펙 저자에게 어느 쪽이 맞는지 확인받고, 하나의 정본만 남긴 뒤 나머지는 삭제하거나 "§9는 §8의 요약이며 상세 규칙은 §8을 따른다"라고 명시. 구현 시 unload 파일 포맷에 버전 태그를 두어 "필드 없음"과 "필드 있음+OFF"를 구분할 수 있게 할 것(리뷰 8 참고).

### 리뷰 2

**[심각도: 치명] RK 자동 선택 기준 "가장 빠른 순서"의 정의 부재로 비결정적 동작 위험**

- 대상: §1 "UK가 여러개 존재한다면 큐브리드 엔진에 의해 이 중 하나가 선택된다(ex. 테이블내에 명시된 순서 중 가장 빠른 순서)"

"명시된 순서"가 (a) CREATE TABLE 문에서 컬럼/제약조건이 나열된 텍스트 순서인지, (b) 카탈로그에 INSERT된 내부 OID(Object ID, 카탈로그 내부에서 각 객체를 구분하는 고유 식별자) 순서인지, (c) 인덱스 생성 시각 순서인지 전혀 정의되지 않았다. 이 셋은 ALTER TABLE로 UK를 추가/삭제/재생성하는 시나리오에서 서로 다른 결과를 낸다.

```sql
-- 초기 생성: UK가 b, c 순서로 명시됨
CREATE TABLE t (
    a INT,
    b INT NOT NULL UNIQUE,   -- UK_1
    c INT NOT NULL UNIQUE    -- UK_2
);
-- 텍스트 순서 기준 RK = UK_1(b)

-- 이후 운영 중 컬럼 b의 UNIQUE 제약을 지웠다가 다시 만듦
ALTER TABLE t DROP CONSTRAINT u_t_b;
ALTER TABLE t ADD CONSTRAINT UNIQUE (b);   -- 새로운 UK, 카탈로그 상 c보다 늦게 생성됨

-- 질문: 이제 RK는 b인가 c인가?
--  - "텍스트 순서(컬럼 선언 순서)" 기준이면 여전히 b
--  - "카탈로그 등록 순서(생성 시각)" 기준이면 c로 바뀜
```

**예제 설명**: 위 시나리오는 컬럼 선언 순서와 제약조건 생성 시각 순서가 어긋나는 흔한 운영 패턴(제약을 지웠다 다시 만드는 스키마 리팩터링)을 보여준다. 스펙이 "어느 기준"인지 못박지 않으면, 엔진 구현에 따라 RK가 b로 유지될 수도 c로 바뀔 수도 있다. RK가 바뀌면 복제 로그에 실리는 키 컬럼이 바뀌는 것이므로, 슬레이브가 적용하는 UPDATE/DELETE 문의 WHERE 절 대상 컬럼도 바뀐다 — 이 재계산이 마스터와 슬레이브에서 독립적으로 일어난다면(즉 RK 자체는 복제되지 않고 각 노드가 로컬 카탈로그 상태로 재계산한다면) 마스터와 슬레이브가 서로 다른 RK를 갖게 되는 스플릿 브레인적 상황이 발생할 수 있다.

**제안**: RK 선택 규칙을 "카탈로그 내부 UK 등록 순서(생성 시각, 즉 시스템 컬럼 예: `unique_btid` 오름차순)"처럼 구현 가능한 단일 기준으로 명문화하고, 이 값 자체를 카탈로그에 영속화해서 마스터가 결정한 RK를 DDL 복제 로그에 실어 슬레이브에 그대로 전파해야 한다(슬레이브가 재계산하면 안 됨).

### 리뷰 3

**[심각도: 치명] RK가 PK→UK로 전환되는 순간의 복제 로그 정합성 미정의**

- 대상: §4-2 예시 13 "PK 를 다른 컬럼으로 변경" (`DROP CONSTRAINT PRIMARY KEY, ADD CONSTRAINT PRIMARY KEY(a)`), 그리고 그 아래 "복제키를 PK에서 UK로 변경하는 경우 ... UK 추가, PK 제거로 가이드됨"

RK 전환은 단일 ALTER 문 안에서 일어나지만, 그 ALTER가 처리되는 도중 이미 진행 중인 다른 트랜잭션의 DML이 복제 로그를 만들고 있을 수 있다. RK가 바뀌기 전에 커밋된 로그는 구 RK(예: 옛 PK 컬럼) 기준으로 키가 인코딩되고, ALTER 이후 커밋된 로그는 신 RK 기준으로 인코딩된다. applylogdb(슬레이브에서 복제 로그를 순서대로 적용하는 프로세스)가 이 경계를 어떻게 인식하는지가 스펙에 없다.

```sql
-- 세션 A: 긴 트랜잭션이 진행 중
-- (A) BEGIN;
-- (A) UPDATE tbl SET c = c + 1 WHERE old_pk_col = 100;   -- 아직 커밋 안 함

-- 세션 B: 그 사이 RK를 old_pk_col(PK)에서 uk_col(UK)로 변경
-- (B) ALTER TABLE tbl DROP CONSTRAINT PRIMARY KEY, ADD CONSTRAINT UNIQUE(uk_col);
-- (B) COMMIT;

-- 세션 A 커밋
-- (A) COMMIT;

-- applylogdb가 세션 A의 UPDATE 로그를 슬레이브에 적용하려는 시점:
--   - 로그 레코드가 만들어진 시점(구 RK=old_pk_col) 기준으로 적용해야 하는가?
--   - 아니면 적용 시점의 슬레이브 카탈로그(신 RK=uk_col) 기준으로 재해석해야 하는가?
```

**예제 설명**: 이 시나리오는 "복제 로그가 만들어진 시점의 스키마"와 "복제 로그가 적용되는 시점의 스키마"가 달라질 수 있음을 보여준다. RDBMS 복제에서 이런 스키마-데이터 시점 불일치는 전형적으로 데이터 손상을 유발하는 원인이다. 예를 들어 PostgreSQL 논리 복제는 REPLICA IDENTITY가 트랜잭션 커밋 시점 기준으로 WAL(Write-Ahead Log)에 이미 구체적인 튜플 형태로 박혀 있어 이런 문제가 원천적으로 없는데, 이 스펙에서는 RK가 "컬럼 참조"로만 다뤄지고 로그 레코드에 RK 스냅샷이 함께 실리는지 여부가 전혀 언급되지 않는다.

**제안**: 복제 로그 레코드 자체에 "이 레코드가 만들어질 때 사용된 RK 컬럼 식별자(또는 값)"를 함께 기록하도록 로그 포맷을 확장하고, RK 변경 DDL은 그 이전에 커밋된 모든 트랜잭션의 로그가 슬레이브에 완전히 적용된 뒤에만 슬레이브 측에서 활성화되도록 순서를 강제해야 한다.

### 리뷰 4

**[심각도: 치명] Multiple ALTER(예시 7, 13)의 원자성 및 중간 상태 노출 여부 불명**

- 대상: §2-2 예시 7 `ALTER TABLE tbl DROP CONSTRAINT ..., ADD CONSTRAINT ...;`, §4-2 예시 13 `DROP CONSTRAINT PRIMARY KEY, ADD CONSTRAINT PRIMARY KEY(a)`

이 예시들은 "하나의 ALTER 문에 DROP과 ADD를 같이 써서 RK 없는 순간을 안 만든다"는 의도로 보인다. 그런데 CUBRID의 ALTER TABLE이 여러 절(clause)을 원자적 단일 카탈로그 트랜잭션으로 처리하는지, 아니면 절 단위로 순차 적용(그 사이 순간적으로 RK가 0개인 상태가 카탈로그에 존재)하는지가 스펙에 없다. 절 단위 순차 적용이라면 "복제 대상 테이블은 RK가 반드시 있어야 한다"(§1, §9)는 불변조건이 트랜잭션 내부에서 일시적으로 깨지는데, 그 순간 동시에 실행되는 DML이 있다면 어떤 RK로 로그를 남겨야 하는지 정의가 없다.

```sql
-- 세션 A: RK 교체
ALTER TABLE tbl DROP CONSTRAINT PRIMARY KEY, ADD CONSTRAINT PRIMARY KEY(a);

-- 세션 A의 ALTER 처리 도중 절 단위로 커밋 가시성이 열린다고 가정하면
-- (구현에 따라 카탈로그 락 해제 시점이 절 사이일 수 있음)
-- 세션 B: 그 찰나에 끼어드는 INSERT
INSERT INTO tbl (old_pk, a, c) VALUES (1, 2, 3);
-- 이 INSERT의 복제 로그는 RK=old_pk 기준인가, RK=a 기준인가?
-- old_pk 제약이 이미 DROP된 시점이면 RK 자체가 없는 상태에서 만들어진 로그가 생긴다
```

**예제 설명**: 예시가 "여러 절을 한 ALTER 문으로 묶으면 안전하다"는 인상을 주지만, 실제로 안전하려면 그 ALTER 문 처리 전체가 다른 트랜잭션에서 원자적으로(all-or-nothing) 보이도록 카탈로그 락과 복제 로그 생성 로직이 함께 설계되어야 한다. 스펙은 SQL 표면 문법만 보여줄 뿐 "이 문장이 내부적으로 원자적으로 처리된다"는 보장을 명시하지 않았다.

**제안**: ALTER TABLE의 다중 절 처리가 카탈로그 스키마 버전 번호를 한 번에 원자적으로 증가시키는 단일 트랜잭션임을 명문화하고, 그 트랜잭션이 커밋되기 전까지는 동시 DML이 구 스키마(구 RK) 기준으로만 로그를 생성하도록 락 프로토콜(2단계 잠금 등)을 스펙에 추가해야 한다.

### 리뷰 5

**[심각도: 중요] RK 변경 DDL과 동시 DML 간의 락 범위/격리 수준 미정의**

- 대상: §4-2 전체 (복제키 후보 1개/여러개에 따른 제약)

"테이블에 하나의 복제키만 존재한다면 복제키를 수정하는 DDL이 제한되지만, 다른 복제키 후보가 함께 존재한다면 모든 DDL은 허용된다"는 규칙은 판정 시점을 스키마 스냅샷 하나로 가정하고 있다. 하지만 동시에 두 개의 ALTER 세션이 "복제키 후보가 2개"인 상태를 보고 각각 하나씩 지우려 든다면 최종적으로 후보가 0개가 되는 경합이 가능하다.

```sql
-- 초기 상태: PK(a), UK(b) 두 개의 RK 후보 존재. 현재 RK = PK(a)
-- 세션 A와 세션 B가 거의 동시에 실행
-- 세션 A:
ALTER TABLE tbl DROP CONSTRAINT PRIMARY KEY;   -- "후보가 2개니까 허용된다"고 판단
-- 세션 B (A와 동시, 서로의 커밋을 아직 못 봄):
ALTER TABLE tbl DROP CONSTRAINT u_tbl_b;       -- "후보가 2개니까 허용된다"고 판단

-- 두 세션 모두 커밋되면: RK 후보가 0개인 복제 테이블이 만들어짐
-- → §1의 불변조건("HA 모드 복제 테이블은 RK가 반드시 존재") 위반
```

**예제 설명**: 이 시나리오는 "판정 시점에는 후보가 2개였다"는 이유로 두 DDL이 모두 개별적으로는 규칙을 통과하지만, 둘 다 커밋되면 후보가 0개로 떨어지는 전형적인 TOCTOU(Time-Of-Check to Time-Of-Use, 검사 시점과 사용 시점 사이의 간극을 이용한 경쟁 조건) 문제다. 카탈로그 DDL은 보통 배타적 스키마 락으로 직렬화되긴 하지만, 스펙에 "이 두 ALTER는 반드시 직렬화되어야 하며 두 번째 것은 재검증 후 거부되어야 한다"는 요구사항이 명시되어 있지 않으면 구현자가 락 범위를 좁게 잡아 이 케이스를 놓칠 수 있다.

**제안**: RK 후보 개수 검증을 "낙관적 스냅샷 체크"가 아니라 스키마 변경 트랜잭션 커밋 직전 재검증(validate on commit)으로 명시하고, 두 번째 커밋 시도는 "복제키 후보가 0개가 됨" 에러로 거부되도록 스펙에 추가.

### 리뷰 6

**[심각도: 중요] 카탈로그 스키마 자체의 변경 범위(REPLICATION 플래그·RK 포인터 저장 위치)가 스펙에 없음**

- 대상: §2-3 예시 9 (db_class 조회 결과에 `replication: ON` 필드 등장)

예시 9는 `db_class`에 `replication` 컬럼이 추가된다는 것만 보여줄 뿐, "현재 RK가 어떤 제약조건/인덱스인지"를 가리키는 메타데이터가 카탈로그 어디에 저장되는지는 전혀 언급이 없다. RK는 컬럼 자체가 아니라 "PK 또는 UK 제약조건 중 하나"를 가리키는 참조이므로, 이 참조가 `db_constraint`나 `db_index` 시스템 카탈로그에 새 플래그(예: `is_replication_key`)로 저장되는지, 아니면 매번 규칙(§1의 우선순위)을 재계산해서 구하는지에 따라 구현 복잡도와 정합성 리스크가 완전히 달라진다.

```sql
-- RK를 조회하고 싶은 DBA/개발자가 쓸 수 있는 표준 방법이 스펙에 없다
-- 예시 9는 replication ON/OFF만 보여줄 뿐, 아래 질문에 답을 주지 않는다:
SELECT * FROM db_class WHERE class_name = 'tbl';   -- replication: ON 만 보임, RK 컬럼명은 안 보임

-- 반면 PostgreSQL은 다음으로 즉시 확인 가능:
-- SELECT relreplident FROM pg_class WHERE relname = 'tbl';
-- (d=default(PK), n=nothing, f=full, i=특정 인덱스)
```

**예제 설명**: 이 비교는 RK를 저장 없이 매번 재계산하는 방식(암묵적, 사용자가 조회 불가)과, PostgreSQL처럼 플래그로 명시 저장하는 방식(조회 가능, 감사 가능)의 차이를 보여준다. 재계산 방식은 카탈로그 스키마 변경이 적다는 장점이 있지만, 리뷰 2에서 지적한 비결정성 문제와 결합하면 "지금 RK가 무엇인지 아무도 확신할 수 없는" 운영 리스크로 이어진다.

**제안**: RK를 가리키는 명시적 포인터 컬럼(예: `db_class.replication_key_constraint_id`)을 카탈로그에 추가하고, ALTER TABLE 처리 시 이 값을 명시적으로 갱신하도록 구현 요구사항에 못박을 것. 아울러 사용자가 RK를 직접 조회할 수 있는 카탈로그 뷰나 `show create table` 확장을 §2-3에 추가할 것(리뷰 19와 연계).

### 리뷰 7

**[심각도: 중요] 복제 로그 포맷 변경과 롤링 업그레이드(마스터/슬레이브 버전 불일치) 호환성 미검토**

- 대상: 전체 스펙 (특히 §1, §4)이 "복제 로그에 RK 정보가 어떻게 실리는가"를 언급하지 않음

기존 CUBRID 복제 로그는 PK 컬럼 값으로 UPDATE/DELETE 대상 행을 식별했을 것으로 추정되는데, 이제는 RK가 PK일 수도 UK일 수도 있고 테이블마다 다르며 시간에 따라 바뀔 수도 있다. HA 업그레이드는 보통 슬레이브부터 순차적으로 새 버전으로 교체하는 롤링 업그레이드 방식을 쓰는데, 이 기간 동안 신버전 마스터가 신규 로그 포맷(RK 기반)을 만들고 구버전 슬레이브(PK 기반 가정)가 그걸 받는 구간이 반드시 존재한다.

```
# 롤링 업그레이드 시나리오
1. 마스터: 구버전 → 신버전 교체, RK 기반 REPLICATION 기능 사용 시작
2. 이 시점 슬레이브 1대는 아직 구버전 (RK 개념 없음, PK 컬럼만 이해)
3. 마스터에서: ALTER TABLE tbl DROP CONSTRAINT PRIMARY KEY, ADD CONSTRAINT UNIQUE(b);
   -- RK가 PK(a)에서 UK(b)로 바뀜, 이후 UPDATE 로그는 b 값으로 행을 식별
4. 구버전 슬레이브의 applylogdb는 여전히 "PK=a"로 행을 찾으려 시도
   -- 로그 레코드 해석 실패 또는 엉뚱한 행 갱신
```

**예제 설명**: 이 시나리오는 스펙이 순수하게 "단일 버전 클러스터"만 가정하고 있어서, 실제 운영에서 거의 항상 발생하는 혼합 버전 구간을 다루지 못한다는 점을 보여준다. MySQL의 행 기반 복제(RBR, Row-Based Replication)는 바이너리 로그 이벤트에 포맷 버전 필드를 두어 이런 호환성 문제를 명시적으로 다루고, PostgreSQL 논리 복제는 프로토콜 버전 협상을 한다. 이 스펙에는 그런 버전 협상/폴백 메커니즘이 전혀 없다.

**제안**: 복제 로그 레코드에 RK 관련 필드(어느 제약조건 기반인지)를 실을 때 포맷 버전을 함께 명시하고, 구버전 슬레이브가 신버전 로그를 만나면 명확히 에러를 내고 replication을 중단하도록(잘못된 행을 갱신하는 사일런트 실패보다 안전) 스펙에 규정할 것. 최소한 "이 기능은 마스터/슬레이브 버전이 동일해야만 지원된다"는 제약이라도 명시해야 한다.

### 리뷰 8

**[심각도: 중요] unloaddb 파일 포맷의 하위 호환성 설계 부재**

- 대상: §8 UNLOADDB & LOADDB 전체

§8은 "unload 시 복제 테이블의 여부를 함께 저장한다"고만 말할 뿐, 이 값이 파일의 어느 위치에 어떤 포맷으로 저장되는지, 그리고 **신버전에서 만든 unload 파일을 구버전 CUBRID의 loaddb로 읽으려 할 때** 무슨 일이 벌어지는지는 언급이 없다(리뷰 1은 반대 방향인 구버전→신버전을 다뤘다).

```
# 시나리오: 신버전에서 unload한 파일을 구버전으로 되돌려 적재(다운그레이드/백업 이관)
$ cubrid unloaddb -i new_db output_v2   # REPLICATION 필드 포함된 신버전 스키마 파일(.schema)

$ cubrid_old loaddb -d target_db output_v2.schema
# 구버전 loaddb 파서는 REPLICATION 이라는 토큰을 모른다.
# 파싱 에러로 전체 로드가 중단되는가? 아니면 알 수 없는 토큰을 무시하고 계속 진행하는가?
# 스펙에 답이 없다.
```

**예제 설명**: 스키마 파일(.schema)은 텍스트 기반 DDL이므로 신버전 전용 문법(REPLICATION 옵션)이 섞여 있으면 구버전 파서가 이를 이해하지 못한다. 이는 단순 "필드 없을 때 기본값" 문제(리뷰 1)와 달리 "알 수 없는 신규 문법을 만났을 때의 파서 동작"이라는 별개의 하위 호환성 문제다. 실무에서 unload/load는 백업, 버전 다운그레이드, DB 이관에 광범위하게 쓰이므로 이 경로가 막히면 파급이 크다.

**제안**: unloaddb 스키마 파일 포맷에 버전 헤더를 추가하고, loaddb가 자신이 모르는 옵션 토큰을 만났을 때의 동작(무시하고 경고 vs 즉시 에러)을 명시적으로 정의해 §8에 추가할 것.

### 리뷰 9

**[심각도: 중요] 파티션 테이블과의 상호작용이 스펙에서 전혀 다뤄지지 않음**

- 대상: 스펙 전체(파티션 관련 언급 없음), §4-1/4-2의 CREATE/ALTER 제약과 충돌 가능

CUBRID는 파티션 테이블(하나의 논리 테이블을 여러 물리 파티션으로 나누는 기능)을 지원하는데, RK와 REPLICATION 옵션이 파티션 단위로 개별 설정 가능한지, 아니면 부모 테이블에만 적용되고 모든 파티션이 상속받는지가 전혀 언급되지 않았다.

```sql
-- 파티션 테이블 생성 시 RK/REPLICATION 이 어떻게 적용되는가?
CREATE TABLE sales (
    sale_id INT,
    sale_date DATE,
    amount INT,
    UNIQUE (sale_id, sale_date)   -- 파티션 키를 포함해야 UNIQUE가 성립하는 CUBRID 파티션 제약
) REPLICATION = ON
PARTITION BY RANGE (sale_date) (
    PARTITION p2025 VALUES LESS THAN (DATE '2026-01-01'),
    PARTITION p2026 VALUES LESS THAN (DATE '2027-01-01')
);

-- 질문1: RK는 부모 테이블 레벨에서 하나로 결정되는가, 파티션마다 별도로 결정되는가?
-- 질문2: 파티션 단위로 REPLICATION=OFF를 걸어 "2025년치는 복제 제외"처럼 부분 제외가 가능한가?
-- 질문3: ALTER TABLE ... ADD PARTITION 으로 새 파티션이 생기면 RK 재검증이 다시 일어나는가?
```

**예제 설명**: 파티션은 대용량 이력 테이블에서 흔히 쓰이고, "오래된 파티션은 복제 안 하고 최근 파티션만 복제"하고 싶은 요구가 실제로 나올 법한 시나리오다. 스펙이 이를 언급하지 않으면 구현자는 임의로 "부모만 REPLICATION 옵션을 가지고 전체 파티션에 획일 적용"으로 결정하게 될 텐데, 이게 사용자 기대와 다를 경우 릴리스 후 요구사항 변경으로 되돌아온다.

**제안**: 최소한 "REPLICATION/RK는 파티션 테이블에서 부모 테이블 단위로만 설정 가능하며 개별 파티션 단위 설정은 지원하지 않는다"는 명시적 제약이라도 §1 또는 별도 절에 추가할 것.

### 리뷰 10

**[심각도: 중요] 트리거가 REPLICATION 경계를 넘나들 때의 복제 로그 귀속 규칙 부재**

- 대상: 스펙 전체(트리거 언급 없음), §1의 "REPLICATION 옵션은 데이터 복제 여부를 결정한다"와 충돌 가능

CUBRID는 BEFORE/AFTER INSERT/UPDATE/DELETE 트리거를 지원한다. REPLICATION=OFF 테이블에 대한 DML이 트리거를 통해 REPLICATION=ON 테이블을 변경하는 경우(또는 그 반대), 그 파생 변경이 복제되어야 하는지가 전혀 정의되지 않았다.

```sql
CREATE TABLE audit_log (id INT PRIMARY KEY, msg VARCHAR(200)) REPLICATION = OFF;
CREATE TABLE orders (order_id INT PRIMARY KEY, amount INT) REPLICATION = ON;

CREATE TRIGGER trg_order_audit
AFTER INSERT ON orders
EXECUTE INSERT INTO audit_log VALUES (..., 'order created');

-- orders에 INSERT 하면 트리거가 audit_log에도 INSERT 한다.
INSERT INTO orders VALUES (1, 100);

-- orders.INSERT 는 REPLICATION=ON 이므로 복제된다.
-- audit_log.INSERT 는 트리거로 유발된 것인데, audit_log 자체가 REPLICATION=OFF다.
-- 이 파생 INSERT는 (a) 원본 트랜잭션을 따라 무조건 복제되는가,
--                  (b) audit_log 테이블 옵션에 따라 복제 안 되는가?
```

**예제 설명**: 트리거로 발생한 DML은 원래 트랜잭션의 일부로 커밋되므로, "테이블 단위 REPLICATION 옵션"이라는 원칙과 "트리거는 임의의 테이블을 건드릴 수 있다"는 CUBRID의 기존 기능이 충돌하는 지점이다. §1의 원칙을 그대로 적용하면 (b)가 맞아 보이지만, 그렇다면 마스터에서는 트리거가 감사 로그를 남기는데 슬레이브에서는 그 감사 로그가 비어있는 채로 failover가 일어날 수 있다 — 이는 §6(VIEW)에서 이미 인정한 "REPLICATION=OFF로 인한 불일치는 책임지지 않는다"는 면책 조항의 범위를 트리거까지 확장해야 하는지 여부의 문제이기도 하다.

**제안**: 트리거로 발생한 DML은 "트리거가 실행된 테이블의 REPLICATION 옵션이 아니라, 실제로 INSERT/UPDATE/DELETE 되는 대상 테이블 자체의 REPLICATION 옵션을 그대로 따른다"는 원칙을 명시하고, §5(외래키)처럼 트리거를 통한 간접 참조에도 동일한 무결성 검사(대상 테이블이 REPLICATION=OFF면 경고)를 적용할지 결정해 스펙에 추가할 것.

### 리뷰 11

**[심각도: 중요] RK가 AUTO_INCREMENT(시리얼) 컬럼일 때 마스터/슬레이브 시리얼 상태 불일치 위험**

- 대상: 스펙 전체(시리얼/AUTO_INCREMENT 언급 없음), §4-2 PK/UK 관련 규칙과 결합

CUBRID는 PK나 UK 컬럼에 AUTO_INCREMENT(자동 증가값, 내부적으로 시리얼 객체가 다음 값을 관리)를 흔히 함께 쓴다. RK가 UK로 승격되는 경우 그 UK 컬럼이 AUTO_INCREMENT라면, 시리얼의 현재 값(current_val)과 캐시된 값 범위가 마스터에만 존재하고 슬레이브에는 복제 로그를 통해 간접적으로만 반영되는 기존 구조에서, RK 재계산과 시리얼 상태가 서로 다른 이벤트로 취급될 때의 정합성이 스펙에서 다뤄지지 않는다.

```sql
CREATE TABLE t (
    id INT AUTO_INCREMENT NOT NULL UNIQUE,   -- UK, RK 후보
    a INT PRIMARY KEY
);
-- 현재 RK = PK(a)

ALTER TABLE t DROP CONSTRAINT PRIMARY KEY;
-- RK가 UK(id, AUTO_INCREMENT)로 전환됨

-- 이후 INSERT 시 id는 시리얼에서 자동 채번됨
INSERT INTO t (a) VALUES (100);   -- id = 시리얼.nextval

-- 슬레이브의 applylogdb가 이 INSERT를 RK=id 기준으로 적용해야 하는데,
-- id 값 자체는 로그에 실려 오므로 문제 없어 보이지만,
-- 만약 이후 슬레이브가 마스터로 승격(failover)된 뒤 새 INSERT가 발생하면
-- 슬레이브 로컬 시리얼 캐시 값이 마스터가 실제로 사용한 마지막 id 값을 못 따라잡아
-- 중복 id(=RK 값 충돌)를 발급할 위험이 있다
```

**예제 설명**: 이 문제 자체는 AUTO_INCREMENT 복제 일반의 오래된 이슈이지만, 기존에는 PK가 곧 시리얼 컬럼인 경우가 많아 이미 알려진 리스크였다면, 이번 스펙으로 UK 기반 RK가 새로 허용되면서 "RK=UK=AUTO_INCREMENT" 조합이 새로운 표면적으로 추가된다. RK가 유일해야 한다는 요구사항과 시리얼의 failover 후 채번 정합성이 어떻게 맞물리는지 스펙에 한 줄도 없다.

**제안**: RK 후보가 AUTO_INCREMENT 컬럼을 포함하는 UK일 경우 시리얼 failover 동기화 요구사항(슬레이브가 마스터로 승격되기 전 시리얼 캐시를 최신화하는 절차)을 별도 절로 명시하거나, 최소한 "이 조합은 알려진 제약"이라고 문서화할 것.

### 리뷰 12

**[심각도: 중요] 멀티 슬레이브/체인 복제 확장성 — RK가 마스터 로컬 판단으로 결정되는 구조의 발산 위험**

- 대상: §1 "복제키는 큐브리드 엔진에 의해 결정된다"는 표현이 "어느 노드의 엔진"인지 불명

스펙은 단일 마스터-단일(혹은 다중) 슬레이브 구성만 암묵적으로 가정한다. 그러나 CUBRID HA는 다중 슬레이브를 지원하고, 향후 체인 복제(슬레이브가 다시 다른 슬레이브의 소스가 되는 계층 구조)나 다중 마스터 확장을 고려할 수 있다. RK 결정이 "각 노드가 로컬 카탈로그를 보고 §1 규칙을 재계산하는" 방식이라면(리뷰 2에서 지적한 대로 이 여부조차 불명확), 서로 다른 노드가 서로 다른 시점에 DDL을 적용받아 일시적으로 다른 RK를 계산해내는 창구가 생긴다.

```
# 체인 복제 가정: Master -> Slave1 -> Slave2 (Slave1이 Slave2의 업스트림)

1. Master: ALTER TABLE t DROP CONSTRAINT PRIMARY KEY, ADD CONSTRAINT UNIQUE(b);
   -- Master, RK: PK(a) -> UK(b)로 즉시 전환, 로그 생성 시작

2. Slave1: 위 DDL 로그를 아직 적용 전. 여전히 로컬 카탈로그 상 RK=PK(a)로 인지
   -- Slave1이 Slave2에게 전달할 로그를 만드는 시점의 RK 인식이 Master와 다름

3. Slave2: Slave1보다 더 지연되어 있다면 3중으로 다른 상태
```

**예제 설명**: 체인 복제나 다중 슬레이브 환경에서는 각 노드가 DDL을 반영하는 시점에 편차(replication lag)가 존재하는 것이 정상이다. RK가 "각 노드의 로컬 재계산"이라면 이 편차 구간에서 각 노드가 서로 다른 RK를 사용하게 되고, 이는 단순 지연이 아니라 "행 식별 기준 자체가 다름"이라는 더 심각한 문제로 이어진다. 이는 스펙이 다중 슬레이브 확장성을 전혀 고려하지 않고 설계되었다는 방증이다.

**제안**: RK는 마스터에서 결정된 값을 DDL 복제 로그의 일부로 명시적으로 실어 전파하고, 슬레이브(및 체인의 하위 슬레이브)는 이를 재계산하지 않고 그대로 적용하도록 아키텍처를 확정할 것. 이렇게 하면 지연은 있어도 최종적으로 모든 노드가 동일한 RK 이력을 순서대로 따라가게 되어 발산이 방지된다.

### 리뷰 13

**[심각도: 중요] 설계 철학 재검토 — PostgreSQL REPLICA IDENTITY의 폴백(FULL/명시 지정) 없이 "엔진이 알아서 고른다"만 채택**

- 대상: 작업지시 배경("PostgreSQL의 REPLICA IDENTITY 컨셉 일부를 채용"), §1 전체

PostgreSQL의 REPLICA IDENTITY는 네 가지 모드를 제공한다: `DEFAULT`(PK 사용), `USING INDEX idx_name`(사용자가 특정 UNIQUE 인덱스를 명시적으로 지정), `FULL`(키가 없으면 모든 컬럼을 비교해 행을 식별 — 이 스펙이 배제한 MySQL 방식과 유사), `NOTHING`(복제에서 UPDATE/DELETE 대상 식별을 포기). 이 스펙은 PK/UK 자동 선택만 채용하고 나머지 세 가지 폴백/명시 옵션을 전부 배제했다.

```sql
-- PostgreSQL: 사용자가 "이 UNIQUE 인덱스를 복제 키로 써라"고 명시할 수 있다
ALTER TABLE tbl REPLICA IDENTITY USING INDEX idx_tbl_b;

-- 이 스펙(CUBRID)에는 대응하는 구문이 없다.
-- 사용자가 "b가 아니라 c를 RK로 쓰고 싶다"고 하려면?
-- §4-2: "복제키는 큐브리드 엔진에 의해 결정되며, 사용자는 복제키를 직접 수정할 수 없다"
-- → 방법이 없다. UK를 하나만 남기고 나머지를 다 지우는 우회밖에 없다.
```

**예제 설명**: 이 비교는 "엔진이 결정한다"는 설계가 사용자 통제권을 완전히 박탈한다는 것을 보여준다. 예를 들어 UK가 세 개 있고 그 중 인덱스 크기가 가장 작아 복제 성능에 유리한 것을 사용자가 알고 있어도, 이 스펙 하에서는 "테이블 내 명시된 순서"라는 불투명한 규칙에 종속될 뿐 사용자가 개입할 수단이 없다. 또한 "PK/UK가 전혀 없는 테이블은 복제 불가"만 있고 PG의 `FULL`처럼 최후의 수단(느리더라도 전체 컬럼 비교로라도 복제)을 선택할 옵션이 없어, MySQL 방식을 성능상 배제한 대가로 "복제 자체가 아예 안 됨"이라는 더 강한 제약을 사용자에게 떠넘기고 있다.

**제안**: 최소 기능으로 `ALTER TABLE ... REPLICATION KEY USING (col_list)`처럼 사용자가 명시적으로 RK 후보를 지정할 수 있는 구문을 장기 로드맵에 추가 검토할 것. 최소한 이번 릴리스에서 안 넣더라도, 스펙 문서에 "왜 명시 지정/FULL 폴백을 채용하지 않았는지"에 대한 설계 근거를 남겨 향후 요구사항이 들어왔을 때 재설계 비용을 줄여야 한다.

### 리뷰 14

**[심각도: 중요] FK 참조 무결성 검사가 CREATE TABLE 시점에만 작동, 참조 테이블을 사후에 REPLICATION=OFF로 바꾸는 경로가 막혀있지 않음**

- 대상: §5 "외래키" 전체, 특히 §2-2 예시 6과의 상호작용

§5는 "외래키 테이블에서 참조하는 모든 테이블은 복제 대상이어야 한다"고 규정하고, 이를 CREATE TABLE(예시 17/18)과 ALTER TABLE ADD FOREIGN KEY(예시 19~23) 시점에 검사한다. 그런데 §2-2 예시 6은 `ALTER TABLE tbl REPLICATION=OFF`가 무조건 `OK`로 성공한다고 보여줄 뿐, `tbl`을 참조하는 FK가 이미 존재하는지는 전혀 검사하지 않는다.

```sql
CREATE TABLE customers (customer_id INT PRIMARY KEY, country INT) REPLICATION = ON;
CREATE TABLE orders (
    order_id INT PRIMARY KEY,
    customer_id INT,
    CONSTRAINT fk_customer_id FOREIGN KEY (customer_id) REFERENCES customers(customer_id)
);  -- OK, 예시 17과 동일

-- 이제 customers를 복제 제외로 바꿔본다 (§2-2 예시 6 그대로)
ALTER TABLE customers REPLICATION = OFF;
-- 스펙 §2-2에 따르면 이 문장은 무조건 OK로 나온다 (예시 6 참고).
-- 하지만 orders가 customers를 FK로 참조하고 있으므로,
-- 이 순간 §5가 막으려던 "FK 테이블은 복제되는데 참조 테이블은 복제 안 되는" 상황이
-- ALTER 한 줄로 재현되어 버린다.
```

**예제 설명**: §5는 배경 문서에 있는 image.png 다이어그램(orders는 복제되는데 customers는 복제 안 돼서 failover 후 FK 참조 무결성이 깨지는 문제)을 막기 위한 절인데, 정작 그 문제를 CREATE/ALTER FK 시점에만 막고 "참조 테이블 자체의 REPLICATION을 나중에 끄는" 경로는 전혀 막지 않는다. §5 후반부에 "HA 모드 실행 시 외래키 테이블에서 참조하는 테이블의 상태도 확인해 ... 에러를 출력할 수 있어야한다"는 문장이 있지만, 이는 "HA 실행 시(즉 §7 HA 전환 시점)"에 한정된 사후 검사로 읽히고, ALTER 시점 즉시 차단인지 아닌지 모호하다. 즉 §5의 목표를 §2-2의 예시가 스스로 무력화하고 있다.

**제안**: `ALTER TABLE ... REPLICATION=OFF`를 실행할 때, 해당 테이블을 참조하는 FK가 존재하고 그 FK를 가진 테이블이 REPLICATION=ON이면 에러를 내도록 §2-2에 명시적으로 예외 규칙을 추가할 것(예시 6을 무조건 OK 사례로만 두지 말고, "단 참조하는 복제 테이블이 없을 때"라는 조건을 붙일 것).

### 리뷰 15

**[심각도: 보통] "복제키 후보 1개/여러개"의 판정 기준과 격리 수준이 §4-2 본문에 정의되지 않음**

- 대상: §4-2 "테이블에 하나의 복제키만 존재한다면 ... 다른 복제키 후보가 함께 존재한다면 모든 DDL은 허용된다"

이 규칙 자체는 합리적이지만, "복제키 후보"의 정의가 §1의 RK 정의(PK 또는 NOT NULL UNIQUE)와 완전히 같은지, 아니면 RK로 선택되지 않은 나머지 UK까지 포함하는지 문구상 약간의 해석 차이가 있다. 또한 이 판정이 DDL 실행 시점의 커밋된 카탈로그 상태를 보는지, 세션 내 미커밋 변경까지 반영하는지도 불명확하다(리뷰 5의 동시성 문제와 별개로, 단일 세션 내에서도 모호함이 있다).

```sql
-- 세션(트랜잭션) 내에서 순차 실행, 아직 커밋 안 함
BEGIN;
ALTER TABLE tbl ADD CONSTRAINT UNIQUE (c);   -- 후보 2개(PK a, UK c)가 됨
ALTER TABLE tbl DROP PRIMARY KEY;            -- "후보가 2개니까 허용"? 아니면
                                              -- "같은 트랜잭션 내 아직 미확정 변경은 후보로 안 침"?
COMMIT;
```

**예제 설명**: 이 예제는 같은 트랜잭션 안에서 후보 개수를 늘렸다가 바로 줄이는 극단적 케이스를 보여준다. 스펙 문면만으로는 이게 허용되는지 판단할 수 없다. CUBRID의 DDL이 트랜잭션 단위로 묶이는지(즉 세션 내 여러 ALTER를 커밋 전까지 보류할 수 있는지) 자체도 버전에 따라 다를 수 있어, 이 부분이 정의되지 않으면 QA에서 재현 불가능한 버그로 보고될 가능성이 높다.

**제안**: "복제키 후보 개수"는 직전에 커밋된 카탈로그 상태 기준으로 판정하며, 같은 트랜잭션 내 여러 DDL을 조합해 우회할 수 없다는 것을 명시할 것(즉 여러 ALTER를 하나의 트랜잭션에 넣어도 각 단계는 이전 단계의 커밋 여부와 무관하게 논리적으로 순차 검증됨을 못박을 것).

### 리뷰 16

**[심각도: 보통] DROP INDEX 규칙(예시 16)이 "RK가 아닌 여분의 UK 인덱스" 삭제 가능 여부를 명시하지 않음**

- 대상: §4-2 예시 16 "DROP INDEX: 복제키 후보가 없다면 삭제 불가"

예시 16은 `DROP INDEX idx_id ON tbl;`이 "복제키 후보가 없다면" ERROR라고만 말한다. 그런데 UK가 여러 개 존재하고 그중 하나만 RK로 선택된 상태에서, RK로 선택되지 않은 다른 UK의 인덱스를 지우는 경우는 다뤄지지 않는다.

```sql
CREATE TABLE tbl (
    a INT,
    b INT NOT NULL UNIQUE,   -- RK로 선택됨 (더 빠른 순서, 리뷰 2 참고)
    c INT NOT NULL UNIQUE    -- RK 후보지만 현재는 선택 안 됨
);

-- c에 대한 UNIQUE 인덱스를 지운다. RK인 b는 그대로 남는다.
DROP INDEX u_tbl_c ON tbl;
-- RK 후보는 여전히 1개(b) 남아있으므로 예시16 문구상 "후보가 있으니 허용"으로 읽히지만,
-- §4-2 앞부분 "복제키 후보가 1개인 경우(=복제키) 제약사항"과의 경계가 뒤섞여
-- "RK가 아닌 잉여 UK 삭제는 자유롭다"는 것이 명문화되어 있지 않다
```

**예제 설명**: 실무에서는 사용 안 하는 인덱스를 정리하는 작업(성능 튜닝)이 흔한데, 그 인덱스가 "RK 후보였지만 선택되지는 않은 UK"일 경우 삭제가 허용되는지 스펙만 봐서는 확신할 수 없다. 규칙이 "RK 자체" 기준인지 "RK를 포함해 후보군 전체 개수" 기준인지 예시 16의 문구가 §4-2 서두 규칙과 정확히 같은 표현을 쓰지 않아 혼동을 준다.

**제안**: 예시 16 문구를 "RK가 아닌 다른 UK/인덱스는 자유롭게 DROP 가능하며, DROP 대상이 현재 RK이거나 RK 후보가 이 DROP으로 인해 0개가 되는 경우에만 에러"로 명확히 다시 쓸 것.

### 리뷰 17

**[심각도: 보통] §7 HA 전환 시 에러 파일 리스트 출력의 포맷/규모가 정의되지 않음**

- 대상: §7 "HA 전환" — "제약사항 위반 시 에러와함께 파일 리스트를 출력한다"

대형 스키마(수천 개 테이블)를 가진 운영 DB에서 RK 없는 복제 테이블이 다수 존재할 경우, 이 "파일 리스트"가 콘솔에 전부 쏟아지는지, 파일로 저장되는지, 개수 제한(truncate)이 있는지 전혀 정의가 없다. 또한 "파일 리스트"라는 표현 자체가 애매한데, 실제로 위반하는 것은 "테이블"이지 "파일"이 아니다(CUBRID는 테이블마다 별도 볼륨 파일을 두지 않으므로 "파일"이 정확히 무엇을 가리키는지도 불분명).

```
$ cubrid hb start mydb
ERROR: HA 전환 제약사항 위반
파일 리스트:
  - tbl_001 (RK 없음)
  - tbl_002 (RK 없음)
  - tbl_003 (FK 참조 테이블이 REPLICATION=OFF)
  ... (테이블이 5,000개 있고 이 중 3,000개가 위반이라면?)
```

**예제 설명**: 이 예제는 "위반 목록 출력"이라는 요구사항이 실제 대규모 운영 환경에서 사용성/성능 문제로 이어질 수 있음을 보여준다. 목록이 너무 길면 콘솔 스크롤로는 확인이 불가능하고, 자동화 스크립트가 이 출력을 파싱해 일괄 수정하려 해도 포맷이 정의되어 있지 않으면 파싱 규칙을 매 버전 업그레이드 때마다 재작성해야 한다.

**제안**: "파일"이라는 표현을 "테이블"로 정정하고, 출력 포맷(예: CSV 또는 한 줄에 하나씩, 위반 사유 코드 포함)과 개수 제한/전체 파일 저장 옵션(`--report-file=...`)을 §7에 구체적으로 명시할 것.

### 리뷰 18

**[심각도: 보통] 예시 7의 Multiple ALTER 구문이 자리표시자(`...`)로만 표기되어 실제 유효 문법인지 검증 불가**

- 대상: §2-2 예시 7 `ALTER TABLE tbl DROP CONSTRAINT ..., ADD CONSTRAINT ...;`

이 예시는 "PK를 다른 컬럼으로 변경할 때 이런 SQL을 쓴다"는 것을 보여주려는 의도인데, `DROP CONSTRAINT ...`와 `ADD CONSTRAINT ...`의 `...` 부분이 실제 제약조건 이름/정의로 채워지지 않아 이 문장이 CUBRID 파서가 실제로 받아들이는 문법인지 독자가 검증할 수 없다. 반면 바로 이어지는 §4-2 예시 13은 구체적인 값을 채운 `DROP CONSTRAINT PRIMARY KEY, ADD CONSTRAINT PRIMARY KEY(a)`를 보여주는데, 두 예시가 사실상 같은 내용(다중 절 ALTER)을 다루면서 하나는 추상적이고 하나는 구체적이어서 스펙 문서 내 일관성이 떨어진다.

```sql
-- 예시 7 (§2-2, 자리표시자):
ALTER TABLE tbl DROP CONSTRAINT ..., ADD CONSTRAINT ...;

-- 예시 13 (§4-2, 구체적 값):
ALTER TABLE table_name DROP CONSTRAINT PRIMARY KEY,
ADD CONSTRAINT PRIMARY KEY(a);

-- 예시 7의 "..."을 예시 13처럼 채워 실행 가능한 SQL로 만들면 정말 같은 결과인가?
-- 또한 예시 7과 예시 13은 테이블명도 tbl / table_name 으로 서로 다르게 표기되어 있다
```

**예제 설명**: 스펙 문서에서 "예시"는 독자(개발자, QA, 문서 작성자)가 그대로 복사해 실행해볼 수 있어야 신뢰할 수 있는 레퍼런스가 된다. 자리표시자만 있는 예시 7은 검증이 불가능하고, 같은 개념을 나중에 예시 13이 구체값으로 다시 설명하면서 앞선 예시 7의 존재 의의(무엇을 보여주려 했는지)가 모호해진다.

**제안**: 예시 7을 삭제하고 §2-2에서 §4-2의 예시 13을 참조하도록 링크하거나, 예시 7 자체를 실행 가능한 완전한 SQL(구체적 제약조건 이름 포함)로 채워 넣을 것. 테이블명 표기(`tbl` vs `table_name`)도 스펙 전체에서 통일할 것.

### 리뷰 19

**[심각도: 사소] RK 자체를 직접 조회하는 표준 카탈로그 뷰/명령이 스펙에 없음**

- 대상: §2-3 예시 8, 9 (REPLICATION ON/OFF만 조회 가능, RK가 어느 컬럼/제약인지는 조회 불가)

예시 8(`show create table`)과 예시 9(`select * from db_class`)는 모두 REPLICATION 옵션 값만 노출하고, "현재 이 테이블의 RK가 어떤 제약조건인지"는 별도로 조회할 방법을 제공하지 않는다. RK는 PK가 아닐 수도 있고(UK로 승격된 경우) 여러 UK 중 엔진이 내부적으로 고른 것일 수도 있으므로(리뷰 2), 사용자가 이를 알아내려면 모든 UK를 나열하고 §1의 규칙을 직접 손으로 재현해봐야 한다.

```sql
-- 사용자가 "지금 RK가 뭔지" 알고 싶을 때 쓸 수 있는 공식적인 방법이 없다
show create table tbl;   -- REPLICATION ON 만 보이고, RK가 PK인지 UK인지, 어느 UK인지는 안 보임
select * from db_class where class_name = 'tbl';   -- 위와 동일하게 replication: ON 만 있음

-- 사용자가 할 수 있는 유일한 대안: db_constraint 등을 뒤져서 PK/UK를 모두 나열하고
-- 스펙 §1의 "PK 우선, 없으면 UK 중 가장 빠른 순서" 규칙을 스스로 적용해봐야 함
-- (게다가 "가장 빠른 순서"의 정의 자체가 불명 — 리뷰 2)
```

**예제 설명**: 이 문제는 리뷰 6(카탈로그에 RK를 명시 저장해야 한다)과 직결된다. RK가 카탈로그에 명시적으로 저장되지 않는 한 이를 노출하는 조회 기능 자체를 만들 수 없으므로, 두 리뷰는 사실상 하나의 근본 원인(RK가 1급 카탈로그 객체로 취급되지 않음)에서 나온 서로 다른 증상이다.

**제안**: `show create table`과 `db_class`(또는 신규 시스템 뷰)에 현재 RK로 선택된 제약조건 이름을 명시적으로 노출하도록 §2-3에 추가할 것.

### 리뷰 20

**[심각도: 사소] REUSE_OID 옵션과 RK/복제 간 상호작용이 언급되지 않음**

- 대상: §2-3 예시 8 (`... ) REUSE_OID, COLLATE utf8_bin, REPLICATION ON`)

예시 8의 `show create table` 출력에 `REUSE_OID`(OID 슬롯을 재사용해 저장공간을 절약하는 CUBRID 고유 옵션)가 REPLICATION과 나란히 등장하지만, 본문 어디에도 이 둘의 상호작용은 설명되지 않는다. REUSE_OID 클래스는 삭제된 행의 OID를 새 행에 재할당하는데, 복제 로그가 OID 기반이 아니라 RK(컬럼 값) 기반으로 행을 식별한다면 이 자체는 문제가 안 될 수도 있지만, 그 전제(복제 로그가 순수 RK 값 기반이며 OID를 전혀 참조하지 않는다)가 스펙 어디에도 명시적으로 확인되지 않는다.

```sql
CREATE TABLE tbl (
    a INT PRIMARY KEY,
    b INT
) REUSE_OID, REPLICATION = ON;

DELETE FROM tbl WHERE a = 1;   -- OID 슬롯 반환
INSERT INTO tbl VALUES (2, 20);  -- 반환된 OID 슬롯을 재사용할 수 있음(REUSE_OID 특성)

-- 만약 복제 로그 내부 구현이 (RK 값과 별개로) OID를 힌트로 사용하는 경로가 조금이라도 있다면
-- DELETE 로그와 INSERT 로그가 슬레이브에 적용되는 순서/타이밍에 따라
-- OID 슬롯 재사용 특성이 예기치 않은 방식으로 행 매칭에 끼어들 여지가 있다
```

**예제 설명**: 이 항목은 "실제로 버그가 있다"는 증명이 아니라 "스펙이 이 조합을 검토했다는 증거가 전혀 없다"는 지적이다. REUSE_OID는 CUBRID 고유 기능이라 타 DBMS 사례를 참고할 수도 없으므로, 반드시 CUBRID 엔진 내부 구현자가 직접 "복제 로그 적용 경로가 OID를 전혀 사용하지 않고 오직 RK 컬럼 값만 사용한다"는 것을 명시적으로 확인하고 문서화해야 한다.

**제안**: §1 또는 별도 부록에 "REUSE_OID와 RK/복제 로그는 독립적이며 서로 영향을 주지 않는다"는 확인 문장을 명시하거나, 만약 영향이 있다면 그 상호작용을 구체적으로 기술할 것.
