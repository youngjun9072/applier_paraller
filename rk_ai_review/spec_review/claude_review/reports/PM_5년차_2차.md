# CUBRID HA 복제 개선 스펙 리뷰 — PM(5년차) 관점 2차 라운드

## 2차 라운드 개요

1차 리뷰(20건)와 40개 통합 이슈(최종보고서)가 이미 다룬 RK 비결정성·FK 사후 OFF 전환·RK 조회 불가·§7 파일리스트·§8/§9 모순·trailing comma·복합 ALTER 원자성·업그레이드 경로 등은 모두 제외하고, 이번에는 스펙이 **아예 언급조차 하지 않은 객체·생태계·정책 축**을 팠다. 구체적으로 (1) 파티션 테이블과의 상호작용, (2) 권한·감사(거버넌스) 공백, (3) 다중 스키마 환경, (4) CUBRID Manager·마이그레이션 툴·드라이버 같은 클라이언트 생태계, (5) 지원/버전 정책, (6) 선택적 unload/load, (7) 문서 국제화, (8) REPLICATION=OFF의 실제 성능 이점이 실현되는 단계를 조사했다. 개수를 채우기보다 실제로 릴리스 판단에 영향을 줄 만한 지점만 남겼다.

### 리뷰 21

**[심각도: 중요] 파티션 테이블에서 REPLICATION 옵션의 적용 범위(부모 단위인지, 파티션 단위인지)가 정의되어 있지 않다**

**대상**: 스펙 전체(파티션에 대한 언급이 단 한 번도 없음), §1, §2-1

**문제 설명**: CUBRID는 RANGE/HASH/LIST 파티션 테이블을 지원하며, 파티션 테이블은 논리적으로는 하나의 테이블이지만 물리적으로는 각 파티션이 별도의 하위 클래스(서브테이블)로 저장된다. 이 스펙은 `CREATE TABLE ... REPLICATION={ON|OFF}` 옵션을 순수 비파티션 테이블 예제로만 설명하고, 파티션 테이블에 이 옵션을 어떻게 적용할지는 전혀 다루지 않는다. 구체적으로 다음이 불명확하다.
- `REPLICATION` 옵션은 부모(논리) 테이블에만 붙는가, 아니면 파티션마다 개별로 지정할 수 있는가?
- 개별 지정이 가능하다면 "특정 파티션만 복제 제외"라는 부분 복제가 이 스펙의 §1 "테이블의 REPLICATION 옵션은 데이터 복제 여부를 결정한다"는 문장과 어떻게 양립하는가(파티션은 "테이블"인가 "테이블의 일부"인가)?
- 개별 지정이 불가능하다면(부모에만 적용), `ALTER TABLE ... ADD PARTITION`으로 새 파티션을 추가할 때 부모의 REPLICATION 값을 자동으로 상속하는가?

**구체 예제(SQL)**:
```sql
-- 매출 데이터를 월별로 파티셔닝한 복제 대상 테이블
CREATE TABLE sales (
    sale_id INT PRIMARY KEY,
    sale_date DATE NOT NULL,
    amount INT
) REPLICATION = ON
PARTITION BY RANGE (sale_date) (
    PARTITION p2026_01 VALUES LESS THAN (DATE'2026-02-01'),
    PARTITION p2026_02 VALUES LESS THAN (DATE'2026-03-01')
);

-- 질문 1: 이 스펙 하에서 아래 문장이 문법적으로 허용되는가?
--        (파티션 단위 REPLICATION 지정 시도)
ALTER TABLE sales REPLICATION = OFF PARTITION p2026_01;

-- 질문 2: 허용되지 않는다면(부모 단위만 존재), 3월 파티션을 새로 추가할 때
ALTER TABLE sales ADD PARTITION p2026_03 VALUES LESS THAN (DATE'2026-04-01');
-- 새로 생긴 p2026_03은 자동으로 REPLICATION=ON을 상속하는가?
-- 상속 여부가 §2-1의 "생략시 ON으로 자동 생성" 규칙과 같은 규칙인지,
-- 별도 규칙인지 스펙은 답하지 않는다.
```

**예제 설명**: 파티션 테이블은 오래된 파티션은 복제 대상에서 빼고(예: 아카이브성 데이터라 슬레이브에 부담만 준다), 최근 파티션만 복제하고 싶은 실무 요구가 흔하다. 이 요구를 이 스펙의 테이블 단위 `REPLICATION` 옵션이 애초에 표현할 수 있는 구조인지조차 스펙에서 알 수 없다. 만약 부모 단위로만 결정된다면 이는 "이번 릴리스는 파티션 세분화 복제를 지원하지 않는다"는 명시적 스코프 결정이 필요하고, 그 결정이 §9 SUMMARY에 한 줄이라도 남아야 QA가 "파티션 테이블에 이 옵션 안 먹는 게 정상"이라고 판단할 수 있다.

**제안**: §1 또는 §9에 "REPLICATION 옵션은 파티션 테이블에서는 부모(논리) 테이블 단위로만 적용되며, 개별 파티션 단위 지정은 이번 범위에서 지원하지 않는다" 같은 명시적 스코프 문장을 추가할 것을 요청한다. 파티션 추가 시 REPLICATION 상속 규칙도 §2-2에 명문화해야 한다.

### 리뷰 22

**[심각도: 중요] 파티션 키 컬럼과 RK(PK/UK) 후보 컬럼의 관계가 스펙에 없어, 파티션 테이블에서 RK 선택이 무의미해지거나 실패할 수 있다**

**대상**: §1(RK 결정 기준), §4-2(RK 후보 제약)

**문제 설명**: 많은 관계형 DB에서는 파티션 테이블의 UNIQUE 제약(PK 포함)이 파티션 키 컬럼을 포함해야 한다는 제약을 두는 경우가 흔하다(그렇지 않으면 같은 값이 서로 다른 파티션에 중복 존재할 수 있어 "유일성"이 파티션 경계를 넘어 보장되지 않기 때문이다). 이 스펙은 §1에서 "PK가 없이 UK가 존재한다면 UK가 복제 키가 됨"이라고만 말할 뿐, **파티션 테이블에서 RK 후보가 되려면 파티션 키 컬럼을 포함해야 하는지**를 전혀 언급하지 않는다. CUBRID의 실제 파티션 제약이 정확히 어떤지는 이 리뷰의 범위(엔진 코드 확인)를 벗어나지만, PM 관점에서 지적해야 할 것은 **이 상호작용 자체가 스펙에서 검토된 흔적이 없다**는 점이다.

**구체 예제(시나리오)**:
```sql
-- 파티션 키는 sale_date, RK 후보로 쓰일 수 있는 UK는 sale_date를 포함하지 않음
CREATE TABLE sales (
    sale_id INT NOT NULL UNIQUE,   -- 파티션 키(sale_date)를 포함하지 않는 UK
    sale_date DATE NOT NULL,
    amount INT
) REPLICATION = ON
PARTITION BY RANGE (sale_date) (
    PARTITION p1 VALUES LESS THAN (DATE'2026-02-01'),
    PARTITION p2 VALUES LESS THAN (DATE'2026-03-01')
);

-- 만약 CUBRID가 "파티션 테이블의 UK는 파티션 키를 포함해야 한다"는
-- 제약을 이미 갖고 있다면, 이 CREATE TABLE은 파티셔닝 규칙 위반으로
-- 애초에 거부되어야 하는데, 그 경우 이 테이블은 §1 관점에서
-- "RK 후보가 하나도 없는 복제 테이블"이 되어 HA 모드에서 생성 불가(§4-1)와
-- "sale_id에 UK를 걸 수 없다"는 파티셔닝 제약이 충돌한다.
-- 즉 사용자는 "파티션 키를 포함하는 컬럼 조합으로만 UK를 만들라"는
-- 안내를 스펙 어디에서도 받지 못한 채 원인 불명의 에러를 마주치게 된다.
```

**예제 설명**: 이 시나리오가 보여주려는 것은 "파티션 제약"과 "RK 자격 요건"이라는 두 개의 서로 다른 제약 체계가 겹칠 때 사용자가 받는 에러 메시지가 어느 쪽 규칙 위반인지조차 구분하기 어려울 수 있다는 점이다. 스펙에 이 상호작용이 문서화되어 있지 않으면, 파티션 테이블을 HA 복제 대상으로 설계하려는 사용자는 시행착오로 이 제약을 알아내야 한다.

**제안**: 파티션 테이블에서 RK 후보로 쓰일 수 있는 PK/UK 조건(파티션 키 포함 여부)을 §4-2에 명시하고, 위반 시 나오는 에러 메시지가 "파티셔닝 제약 위반"과 "RK 자격 미달" 중 무엇인지 구분해서 안내하도록 요구사항에 추가해야 한다.

### 리뷰 23

**[심각도: 중요] REPLICATION 옵션을 변경/조회할 수 있는 권한 모델이 스펙에 없다**

**대상**: §2-2(ALTER 옵션), §2-3(조회)

**문제 설명**: 스펙의 모든 예제는 `csql>` 프롬프트로만 실행되며 실행 주체의 권한 수준이 명시되지 않는다. `ALTER TABLE ... REPLICATION={ON|OFF}`는 단순한 스키마 변경처럼 보이지만, 실제로는 "이 테이블의 데이터가 재해복구(DR) 슬레이브에 존재하는지 여부"를 결정하는 **운영 정책 성격의 옵션**이다. 일반적인 스키마 변경 권한(테이블 소유자의 ALTER 권한)만으로 이 옵션까지 바꿀 수 있다면, 테이블 소유자(꼭 DBA가 아닐 수 있는 애플리케이션 계정)가 별도 승인 없이 재해복구 범위를 축소시킬 수 있다는 뜻이 된다. 반대로 DBA 전용 권한이 필요하다면 이를 강제하는 권한 체크 로직과 에러 메시지가 필요한데, 스펙은 이에 대해 아무 말도 하지 않는다.

**구체 예제(시나리오)**:
```sql
-- 테이블 소유자(DBA가 아닌 애플리케이션 계정)로 로그인
csql> ALTER TABLE app_user.critical_orders REPLICATION = OFF;
-- 이 문장이 성공하는가? 성공한다면, 이 테이블이 갑자기 DR 대상에서
-- 빠졌다는 사실을 DBA/운영팀은 어떻게 알게 되는가(§24 참고)?
-- 실패한다면, "권한 부족"이라는 에러가 나와야 하는데
-- 스펙의 모든 예시(5,6)는 권한 문제 없이 바로 OK/ERROR만 보여준다.

csql> select replication from db_class where class_name = 'critical_orders';
-- 이 조회 역시 아무나(SELECT 권한만 있으면) 할 수 있는지,
-- REPLICATION 상태 자체가 민감 정보로 취급되어야 하는지 불명확.
```

**예제 설명**: 이 시나리오는 "테이블 구조를 바꿀 권한"과 "재해복구 범위를 바꿀 권한"이 실질적으로 다른 위험 수준을 갖는데도 스펙이 이를 구분하지 않는다는 점을 보여준다. 만약 구현이 기존 ALTER TABLE 권한 체계를 그대로 재사용한다면(가장 손쉬운 구현), 이는 컴플라이언스 관점에서 "재해복구 정책 변경에 대한 승인 절차가 없다"는 감사 지적 사항이 될 수 있다.

**제안**: `REPLICATION` 옵션 변경에 필요한 권한 수준(테이블 소유자로 충분한지, DBA 권한이 별도로 필요한지)을 §2-2에 명시하고, 조회(§2-3) 시에도 이 값을 볼 수 있는 권한 범위를 규정해야 한다.

### 리뷰 24

**[심각도: 보통] REPLICATION 옵션 변경 이력에 대한 감사(audit) 추적 요구사항이 없다**

**대상**: §2-2(연장), 배경 설명

**문제 설명**: 리뷰 23과 이어지는 문제다. `REPLICATION=OFF`로의 전환은 데이터 유실처럼 보이는 상황(마스터/슬레이브 불일치)을 의도적으로 허용하는 조작이다. 장애 사후 분석(post-mortem)에서 "언제, 누가, 왜 이 테이블을 복제 제외로 바꿨는가"를 추적할 수 있어야 하는데, 스펙에는 이 변경을 별도로 로깅하거나 `db_class`류 카탈로그에 변경 이력(변경자, 변경 시각)을 남기는 요구사항이 없다. 현재로서는 일반 DDL 로그(있다면)에 섞여 다른 스키마 변경과 구분되지 않을 가능성이 크다.

**구체 예제(시나리오)**:
```text
[장애 상황] 
분기 결산 리포트가 failover 이후 매출 데이터 일부를 누락해서 나왔다.
원인 조사: orders 테이블이 어느 시점부터 REPLICATION=OFF였던 것으로 드러남.

조사팀의 질문:
  - 언제 OFF로 바뀌었는가? (failover 발생 몇 시간/며칠 전인가?)
  - 누가 실행했는가? (배포 스크립트의 실수인가, 운영자의 의도적 조치인가?)
  - 이 변경이 승인/리뷰를 거쳤는가?

스펙이 제공하는 것: db_class.replication = 'OFF'라는 "현재 상태"뿐.
변경 이력(누가/언제)을 조회할 표준 수단이 스펙에 없다.
```

**예제 설명**: 이 시나리오는 실제로 벌어질 법한 사후 감사 요청을 가정한 것이다. 일반 DDL 감사 로그가 CUBRID에 이미 있다면 이 문제는 이미 해결된 것일 수 있으나, 그렇다 하더라도 "REPLICATION 옵션 변경은 반드시 감사 로그에 남는다"는 문장이 이 스펙에 명시적으로 있어야, QA가 이 요구사항을 테스트 케이스로 검증할 수 있다.

**제안**: REPLICATION 옵션 변경이 기존 DDL 감사 체계에 포함됨을 명시하거나, 포함되지 않는다면 이 스펙의 범위에서 감사 로깅을 추가할지 여부를 결정해 문서화해야 한다.

### 리뷰 25

**[심각도: 중요] 다중 스키마(소유자) 환경에서 FK 참조 검증(§5)이 스키마 한정자까지 명확히 다루는지 예시로 확인할 수 없다**

**대상**: §5, 예시 17~23

**문제 설명**: §5의 모든 예제는 `customers`, `orders`, `new_orders`처럼 스키마 접두사 없이 테이블명만 등장한다(실제로는 모두 동일 소유자, 즉 `dba` 스키마로 보인다). CUBRID는 사용자(소유자)별로 스키마가 분리되고, 같은 이름의 테이블이 서로 다른 소유자 아래 동시에 존재할 수 있다. 이 스펙의 FK 검증 규칙("참조 테이블은 반드시 복제 대상")이 **다른 소유자의 동명 테이블을 혼동하지 않고 정확한 FK 대상(스키마 한정 테이블)의 REPLICATION 값을 검사하는지**가 예시로 검증되지 않는다.

**구체 예제(SQL)**:
```sql
-- 소유자 alice 아래: 복제 대상
CREATE TABLE alice.customers(customer_id INT PRIMARY KEY) REPLICATION = ON;

-- 소유자 bob 아래: 동명이지만 복제 제외 테이블 (알파벳 우연히 같은 이름)
CREATE TABLE bob.customers(customer_id INT PRIMARY KEY) REPLICATION = OFF;

-- bob 소유의 orders가 bob.customers를 참조
CREATE TABLE bob.orders(
    order_id INT PRIMARY KEY,
    customer_id INT,
    CONSTRAINT fk_c FOREIGN KEY (customer_id) REFERENCES bob.customers(customer_id)
);
-- 이 문장은 §5 규칙대로 ERROR가 나야 한다(bob.customers가 OFF이므로).
-- 그런데 검증 로직이 "customers"라는 이름만으로 참조 대상을 찾다가
-- alice.customers(ON)를 잘못 매칭해 통과시켜버릴 위험은 없는가?
-- 스펙의 모든 예시가 단일 소유자 기준이라 이 케이스를 배제하지 못한다.
```

**예제 설명**: 이 예제는 이름 충돌 자체가 목적이 아니라, "FK 검증이 정확한 정규화된(스키마 한정) 이름을 기준으로 동작한다"는 당연해 보이는 전제가 스펙에서 한 번도 명시적으로 검증되지 않았다는 것을 보여주기 위한 것이다. FK 구문 자체는 표준적으로 스키마를 정확히 특정하므로 실제 구현에서 문제가 될 가능성은 낮을 수 있지만, **문서에 이 전제가 없다는 것 자체가 리뷰 대상**이다. 특히 QA 입장에서는 "다중 스키마 환경에서의 FK-REPLICATION 검증"이 테스트 매트릭스에 아예 들어갈 근거를 스펙에서 찾을 수 없다.

**제안**: §5 예시 중 최소 1개를 스키마가 다른 두 사용자 간 FK 관계로 바꿔, 검증이 스키마 한정 이름 기준으로 동작함을 명시적으로 보여줄 것을 제안한다.

### 리뷰 26

**[심각도: 중요] CUBRID Manager, 마이그레이션 도구, 드라이버 등 클라이언트 생태계에 REPLICATION 정보를 노출할 계획이 스펙에 없다**

**대상**: 스펙 전체, §2-3(조회)

**문제 설명**: §2-3은 `csql`(커맨드라인 SQL 클라이언트)에서 `show create table`과 `select * from db_class`로 조회하는 방법만 제시한다. 그러나 실제 CUBRID 사용자 중 상당수는 GUI 관리 도구(CUBRID Manager류의 스키마 브라우저)나 JDBC/ODBC 드라이버를 통해 메타데이터를 조회한다. 이 스펙에는 (a) GUI 스키마 브라우저의 테이블 속성 화면에 REPLICATION ON/OFF 표시가 추가되어야 하는지, (b) JDBC의 `DatabaseMetaData` 계열 API에 이 정보가 새로 노출되어야 하는지, (c) 타 DB(MySQL/Oracle 등)에서 CUBRID로 스키마를 이관하는 마이그레이션 도구가 이 옵션을 생성 스크립트에 반영해야 하는지에 대한 언급이 전혀 없다. 이 스펙만 읽은 각 도구 개발팀은 "이 기능이 우리 도구에 영향을 주는지"조차 판단할 근거가 없다.

**구체 예제(시나리오)**:
```text
[GA(정식 출시) 체크리스트 담당자의 입장]

"당신 팀 산출물에 이 변경이 영향을 주는가?"를 물어야 출시할 수 있다.

  - GUI 관리 도구 팀: "테이블 생성/수정 다이얼로그에 REPLICATION

세 팀 모두 이 스펙 문서 하나로는 자신의 작업 범위를 결정할 수 없다.
```

**예제 설명**: 이 시나리오는 엔진 스펙 하나가 승인되었다고 해서 제품 전체의 출시 준비가 끝나는 것이 아니라는, PM이 흔히 놓치는 지점을 보여준다. 엔진 기능은 사용자에게 `csql`이라는 하나의 인터페이스로만 도달하지 않는다.

**제안**: 스펙 말미에 "영향 받는 컴포넌트" 절을 추가해 GUI 도구/드라이버/마이그레이션 도구 각각에 대해 "영향 있음(구체 내용)" 또는 "영향 없음(이유)"을 명시할 것을 요청한다.

### 리뷰 27

**[심각도: 보통] 이 기능이 적용되는 최소 버전과 기존 유지보수 고객 대상 지원/백포트 정책이 스펙에 없다**

**대상**: 스펙 전체(배경 설명 포함)

**문제 설명**: 이 스펙은 어떤 CUBRID 버전부터 이 기능이 포함되는지, 이미 이전 버전으로 HA를 운영 중인 고객이 이 문제(§4-1의 원인이 된 PK 컬럼 속성 변경 버그)를 이번 버전으로 업그레이드해야만 해결할 수 있는지, 아니면 유지보수 계약을 맺은 고객에게는 패치 형태로 이전 버전에도 백포트(backport, 최신 기능을 하위 버전에 이식하는 것)되는지에 대한 언급이 없다. 이는 구현 세부사항이 아니라 **이 기능의 출시 형태 자체를 결정하는 제품 정책**이며, 릴리스 노트와 고객 공지, 지원팀 응대 스크립트를 작성하기 전에 반드시 확정되어야 한다.

**구체 예제(시나리오)**:
```text
[지원팀에 접수된 문의]

고객: "저희는 N-1 버전을 쓰고 있고 지금 이 PK 변경 버그로
      데이터 불일치가 발생했습니다. 이번에 나온다는 RK 개선이
      저희 버전에도 패치로 오나요, 아니면 메이저 업그레이드를
      해야 하나요?"

지원팀이 이 스펙 문서에서 찾을 수 있는 답: 없음.
스펙은 "무엇을 고칠 것인가"만 다루고 "누구에게 언제 줄 것인가"는
다루지 않는다.
```

**예제 설명**: 이 시나리오는 스펙의 기술적 완성도와 별개로, 이 문서만으로는 영업/지원 조직이 고객 응대를 할 수 없다는 점을 보여준다. 특히 이 스펙이 해결하는 버그가 이미 실제 장애로 보고된 것(작업지시 배경 참고)이라면, 기존 고객에게 이 수정이 언제 어떤 형태로 도달하는지는 기술 스펙과 별개로 반드시 문서화되어야 하는 정보다.

**제안**: 이 스펙과는 별도 문서일지라도, 릴리스 계획에 "적용 최소 버전", "이전 버전 백포트 여부/일정"을 명시한 지원 정책 문서를 함께 준비할 것을 요청한다. 최소한 이 스펙 서두에 "대상 버전: vX.Y 이상" 한 줄이라도 있어야 한다.

### 리뷰 28

**[심각도: 중요] 선택적(-t 옵션 등) unloaddb/loaddb로 일부 테이블만 이관할 때 FK-REPLICATION 불변식이 로드 순서/선택 범위에 의해 깨질 수 있다**

**대상**: §8

**문제 설명**: §8은 "unload 시 복제 테이블의 여부를 함께 저장한다"고만 말하며, 데이터베이스 전체를 통째로 unload/load하는 것을 전제로 서술한다. 그러나 `unloaddb`는 실무에서 특정 테이블만 골라 이관하는 용도(`-t` 류 옵션으로 테이블 목록을 지정하는 부분 unload)로도 흔히 쓰인다. 이 스펙은 **부분 unload/load 시 FK로 얽힌 두 테이블 중 하나만 이관 대상에서 빠지는 경우**를 전혀 다루지 않는다. §5의 "복제 대상 테이블이 참조하는 모든 테이블은 복제 대상이어야 한다"는 불변식은 `CREATE TABLE`/`ALTER TABLE` 경로에서만 검증되도록 서술되어 있는데, `loaddb`가 이 불변식을 우회하는 제3의 경로가 될 수 있다.

**구체 예제(시나리오)**:
```text
[운영자가 orders 테이블만 다른 서버로 이관하려는 상황]

원본 DB: customers(REPLICATION=ON, PK customer_id), 
         orders(REPLICATION=ON, FK -> customers)

unloaddb -t orders mydb   -- orders만 선택적으로 unload
-- 이 unload 파일에는 customers에 대한 정보가 전혀 없다.

(새 서버에서) loaddb -d newdb orders.unl
-- orders는 §8 규칙대로 REPLICATION=ON, RK 자동 선택(PK)으로 생성된다.
-- 그런데 orders의 FK가 참조하는 customers 테이블은 newdb에 아예
-- 존재하지 않는다. §5는 "CREATE TABLE/ALTER TABLE 시점"의 검증만
-- 규정하는데, loaddb가 만드는 CREATE TABLE(내부적으로 생성됨)이
-- 이 검증을 거치는지, 아니면 loaddb 특유의 별도 경로라 검증을
-- 건너뛰는지 스펙에 없다.
-- 만약 검증을 안 거친다면, orders는 존재하지도 않는 customers를
-- 참조하는 FK를 가진 채로 HA 모드에 진입할 수 있다(§7 검증에서야
-- 뒤늦게 걸릴 수도, 혹은 FK 자체가 무결성 위반으로 아예 로드 실패할 수도 있다).
```

**예제 설명**: 이 시나리오는 배경 설명의 원래 버그(FK 참조 대상 미복제)가 `unloaddb`/`loaddb`라는 완전히 다른 경로로도 재현될 수 있음을 보여준다. `unloaddb -t`는 실제로 대용량 DB에서 특정 테이블만 다른 클러스터로 옮기거나 샘플링할 때 자주 쓰이는 기능이라, 이 경로가 검증되지 않은 채 남아 있으면 실사용에서 부딪힐 가능성이 낮지 않다.

**제안**: §8에 "부분 unload/load 시에도 FK 참조 무결성과 REPLICATION 불변식이 §5와 동일하게 검증된다"는 문장을 추가하거나, 부분 unload가 이 스펙의 범위 밖이라면 명시적으로 "부분 이관은 사용자가 FK 무결성을 직접 보장해야 한다"는 경고를 §8에 남겨야 한다.

### 리뷰 29

**[심각도: 보통] 영어 공식 문서·API 참조에 대한 반영 계획과 용어 번역 매핑이 스펙에 없다**

**대상**: 스펙 전체(국제화)

**문제 설명**: 이 스펙 문서는 한국어로 작성되어 있고, `REPLICATION`, `Replication Key(RK)`처럼 영문 키워드는 코드/SQL 문법 차원에서만 등장한다. CUBRID는 국내뿐 아니라 해외 사용자도 있는 오픈소스 프로�트이며 공식 문서 사이트도 영어를 포함한다. 이 스펙에는 "복제 대상 테이블", "복제 제외 테이블", "복제키 후보"처럼 한국어로만 정의된 개념을 영문 매뉴얼에서 어떤 용어로 번역할지에 대한 매핑이 없다. 작은 문제로 보일 수 있지만, 번역자가 "복제 대상 테이블"을 "replicated table"로, "복제 제외 테이블"을 어떤 문서에서는 "excluded table"로 다른 문서에서는 "non-replicated table"로 제각각 옮기면, 영문 사용자 커뮤니티에서 같은 개념이 다른 이름으로 불려 혼란이 생긴다.

**구체 예제(시나리오)**:
```text
[영문 매뉴얼 작성자의 입장]

한국어 스펙 용어           -> 영문 문서에서 실제로 쓰일 이름은?
"복제 대상 테이블"         -> "replicated table"? "replication-enabled table"?
"복제 제외 테이블"         -> "non-replicated table"? "replication-excluded table"?
"복제키 후보"              -> "replication key candidate"? 스펙에 대응 영문 없음

이 매핑이 스펙에 없으므로, 영문 매뉴얼 작성자는 자체적으로 용어를
정해야 하고, 이후 이 스펙을 기반으로 나온 에러 메시지 문자열
(영문 locale)이 매뉴얼 용어와 다시 어긋날 위험이 있다.
```

**예제 설명**: 이 시나리오는 문서 품질 문제가 단일 언어 안에서의 일관성(리뷰 17에서 지적한 "복제 테이블"/"복제 대상 테이블" 혼용)에 그치지 않고, 번역 과정에서 다시 한번 증폭될 수 있음을 보여준다.

**제안**: 스펙에 짧은 용어 대조표(한국어 용어 - 영문 대응 용어)를 추가해, 이후 매뉴얼·에러 메시지·API 문서가 동일한 영문 용어를 쓰도록 기준점을 제공할 것을 제안한다.

### 리뷰 30

**[심각도: 중요] REPLICATION=OFF의 성능 이점이 마스터의 로그 생성 단계에서 실현되는지, 슬레이브의 필터링 단계에서만 실현되는지 스펙이 침묵한다**

**대상**: 배경 설명("MySQL처럼 모든 컬럼을 키로 사용하는 방식은 성능이 느려서 배제"), §1, §4

**문제 설명**: 이 기능 전체의 출발점은 "PK 없는 테이블도 복제를 안전하게 하되, 성능 저하는 피한다"는 목표다. `REPLICATION=OFF`라는 옵션이 존재하는 이유 중 하나도 "굳이 슬레이브로 보낼 필요 없는 테이블(예: 세션 캐시, 임시 통계 테이블처럼 쓰기가 잦지만 재해복구 가치가 낮은 테이블)의 복제 부담을 없앤다"는 성능/운영 목적으로 읽힌다. 그런데 스펙은 이 옵션이 실제로 **마스터 쪽 트랜잭션 로그 생성 자체를 건너뛰어 마스터의 쓰기 경로 부하(디스크 I/O, 로그 볼륨)를 줄이는지**, 아니면 **로그는 평소처럼 다 만들되 슬레이브에 전송/적용하는 단계에서만 걸러내는지**를 전혀 구분해서 말하지 않는다. 후자라면 "성능이 느려서 MySQL 방식을 배제했다"는 이 기능의 핵심 근거와 달리, `REPLICATION=OFF`로 지정해도 마스터 쪽 로그 생성 오버헤드는 그대로 남아 고빈도 쓰기 테이블을 복제에서 뺐을 때 기대하는 성능 이득이 실현되지 않는다.

**구체 예제(시나리오)**:
```sql
-- 초당 수만 건씩 INSERT되는 로그성 테이블을 복제에서 제외해
-- 마스터 부하를 줄이려는 의도
CREATE TABLE access_log (
    id BIGINT PRIMARY KEY,
    payload VARCHAR(4000)
) REPLICATION = OFF;

-- 운영자의 기대: "이 테이블은 복제 제외니까 트랜잭션 로그에도
--                 최소한만 기록되고, 그만큼 마스터 쓰기 성능이 좋아지겠지"
--
-- 실제로 검증해야 할 질문:
--   1) access_log에 대한 INSERT가 여전히 풀(full) 트랜잭션 로그
--      레코드를 만드는가? (RECOVERY용 로그와 REPLICATION용 로그가
--      분리되어 있는지, 아니면 하나의 로그를 나중에 필터링하는지)
--   2) 만약 하나의 로그를 필터링만 한다면, REPLICATION=OFF는
--      "슬레이브 디스크/네트워크만 아낄 뿐 마스터 성능에는
--      영향이 없다"는 것인데, 이는 배경 설명의 "성능이 느려서"
--      라는 설계 근거가 정확히 무엇을 겨냥한 것인지와 어긋난다.
```

**예제 설명**: 이 시나리오는 사용자가 `REPLICATION=OFF`를 순수 성능 목적(마스터 부하 절감)으로 사용하려 할 때, 실제로 얻는 이득이 스펙 문서만으로는 가늠되지 않는다는 점을 보여준다. PM 입장에서 이는 두 가지로 이어진다. (1) 영업/마케팅 자료에 "REPLICATION=OFF로 쓰기 성능을 개선하세요"라는 문구를 넣을 수 있는지 결정할 근거가 없고, (2) 성능 테스트 계획(QA)이 "마스터 쓰기 처리량"을 측정 지표에 넣어야 하는지조차 스펙에서 알 수 없다.

**제안**: REPLICATION=OFF가 마스터의 로그 생성 단계에 미치는 영향(로그를 아예 안 만드는지, 만들되 전송 전에 필터링하는지)을 §1 또는 §4에 명시하고, 두 방식 중 무엇을 택했는지에 따라 배경 설명의 "성능" 근거 문장도 그에 맞게 다시 쓸 것을 제안한다.

## 조사 종료 선언

이번 2차 라운드에서는 작업 지시가 지목한 미개척 영역(파티션, 트리거, 시리얼, 소유자 권한, TDE, collation, REUSE_OID, 에러코드 체계, 성능/락, 보안, 멀티 슬레이브, 문서 국제화)을 각각 훑었다. 이 중 트리거·REUSE_OID·시리얼(AUTO_INCREMENT)·멀티 슬레이브 차등 복제는 최종보고서 4절("직군별 관점")에 이미 엔진/PM 관점 지적으로 명명되어 있어 같은 지점의 재포장이 될 위험이 커서 제외했다. TDE와 collation은 RK/복제 정합성과 결합해 봐도 근거 있는 구체적 실패 시나리오를 세우기 어려워(추측 수준에 머물러) 제외했다.

남은 것 중 실제로 릴리스 판단·문서 작성·QA 계획에 영향을 줄 만큼 구체적인 지점만 10건으로 추렸다: 파티션 스코프/제약 상호작용(2건), 권한·감사 거버넌스(2건), 다중 스키마 FK 검증(1건), 클라이언트 생태계 노출(1건), 지원·버전 정책(1건), 선택적 unload의 FK 우회(1건), 문서 국제화(1건), REPLICATION=OFF의 실제 성능 이득 위치(1건). 이 이상으로 개수를 채우려면 이미 나온 지적을 다른 각도로 포장하거나 근거 없는 추측을 늘어놓아야 했으므로, 여기서 조사를 마친다.

추가 여지: 있음(파티션·권한 영역은 구현 세부가 공개되면 후속 리뷰 가치가 더 있음). 다만 현재 스펙 문서 자체를 대상으로 한 1차 조사로는 이 10건이 한계선이라고 판단한다.
