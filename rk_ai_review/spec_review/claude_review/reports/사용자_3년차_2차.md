# CUBRID HA 복제 개선 스펙 리뷰 — 최종 사용자(3년차) 2차 라운드

## 2차 라운드 개요

1차 리뷰에서는 "에러 메시지가 `ERROR` 한 단어뿐이다", "RK(복제 키)를 조회할 방법이 없다",
"REPLICATION 기본값이 위험하다" 같은 사용성 정면 문제를 다뤘다. 이번 2차에서는 1차와
최종 통합 보고서(20개 리뷰 병합본)가 이미 다룬 영역 — RK 선택 비결정성, FK 부모 사후
전환, 복합 ALTER 원자성, §8/§9 기본값 모순, trailing comma 등 — 을 의도적으로 피하고,
아직 아무도 짚지 않은 지점을 찾는 데 집중했다. 구체적으로는 (1) "RK를 만들라"는 요구를
실제로 만족시키려 할 때 실무자가 겪는 데이터 정리 노동, (2) 사용자가 알아채지 못하는
사이에 RK가 바뀌는 숨은 경로, (3) 권한·보안·도구 생태계처럼 스펙이 아예 침묵하는 주변
영역을 훑었다. 파티션·트리거·멀티슬레이브처럼 통합 보고서가 이미 "스코프 불명"으로
짚은 영역은 같은 실패 모드의 변주가 되기 쉬워 의도적으로 제외했다.

## 리뷰 21

**[심각도: 중요] "RK를 추가하라"는 요구가 실제로는 기존 데이터의 중복값 제거라는 별도 프로젝트로 이어질 수 있는데, 이 노동이 스펙 어디에도 언급되지 않는다**

대상: §3 "싱글 모드에서 생성된 복제 키가 없는 테이블은 HA모드 전환 시 복제 키를 추가하거나
복제 제외 테이블로 변경할 수 있어야한다."

문제 설명: 이 문장은 마치 "RK 추가"가 `ALTER TABLE ... ADD CONSTRAINT UNIQUE(col)` 한 줄이면
끝나는 가벼운 작업인 것처럼 서술한다. 그러나 실무에서 PK/UK 없이 오랫동안 운영된 테이블은
십중팔구 중복값을 포함하고 있다. `ADD CONSTRAINT UNIQUE`는 기존 데이터 전체를 스캔해
중복이 있으면 실패하므로, RK를 만들려면 먼저 중복값을 찾아 정리(삭제/병합/컬럼 추가로
구분)하는 별도의 데이터 정리 작업이 선행되어야 한다. 더 나쁜 경우는 §5(외래키) 때문에
"복제 제외 테이블로 변경"이라는 도피처조차 막혀 있는 테이블이다 — 이 테이블을 다른 복제
테이블이 FK로 참조하고 있다면 REPLICATION=OFF로 뺄 수 없으므로(예시 18), 사용자는 반드시
중복값을 정리해서 RK를 만들어야만 HA 전환이 가능하다. 이 강제적 데이터 정리 작업의 존재
자체가 스펙에 한 줄도 없다.

```sql
-- HA 전환 대상이 된 레거시 테이블. PK/UK 없이 3년간 운영되어 email에 중복이 쌓여 있다
csql> ALTER TABLE legacy_customers ADD CONSTRAINT UNIQUE(email);

ERROR: Unique constraint violation... (예: 'a@test.com' 이 12건 중복)

-- 이 테이블은 orders.customer_id가 FK로 참조하므로(§5) REPLICATION=OFF로 뺄 수도 없다.
-- 결국 개발자는 아래와 같은 중복 제거 스크립트를 별도로 작성해야 한다.
csql> DELETE FROM legacy_customers a
      WHERE a.id NOT IN (
        SELECT MIN(id) FROM legacy_customers b WHERE b.email = a.email
        GROUP BY b.email
      );
-- 어떤 행을 남기고 어떤 행을 지울지(가장 최근 행? 가장 오래된 행?)는 순전히 애플리케이션
-- 로직에 달려 있는데, 스펙은 이 선택이 필요하다는 사실조차 알려주지 않는다.
```

예제 설명: 3년차 실무자가 이 스펙만 읽고 "RK 없는 테이블은 ALTER 한 줄로 고치면 되는구나"
라고 오해하면, 실제 작업에 들어가서야 중복 데이터 정리라는 훨씬 큰 작업량과 마주치게 된다.
특히 어떤 행을 "정답"으로 남길지는 순수한 SQL 문제가 아니라 비즈니스 로직 판단이 필요한
경우가 많아, HA 전환 일정에 이 작업 시간이 반영되지 않으면 프로젝트 지연으로 이어진다.

제안: §3 또는 §7에 "RK 후보가 없는 테이블에 UK를 추가하려면 기존 데이터에 중복값이 없어야
하며, 중복이 있다면 사전에 정리해야 한다"는 경고 문장과 함께, 중복값을 미리 찾아볼 수 있는
조회 SQL 예시(`GROUP BY ... HAVING COUNT(*) > 1`)를 안내 예제로 추가해야 한다.

## 리뷰 22

**[심각도: 보통] RK 후보를 늘리려고 `NOT NULL UNIQUE` 컬럼을 새로 추가하면 DEFAULT 값 때문에 구조적으로 실패하는데, 이 에러가 RK 문제인지 일반 제약 위반인지 스펙이 구분해주지 않는다**

대상: §4-2 "다른 복제키 후보가 함께 존재한다면 모든 DDL은 허용된다" / 리뷰 9(1차)에서
지적한 "RK 후보 개수 확인 불가" 문제의 연장선

문제 설명: RK 후보가 하나뿐이라 DDL이 막힌 사용자가 취할 수 있는 자연스러운 대응은
"그럼 UK 후보를 하나 더 만들어서 여유를 두자"는 것이다. 그런데 컬럼이 이미 데이터로
채워진 테이블에 `NOT NULL UNIQUE` 컬럼을 새로 추가하려면 `DEFAULT` 상수값을 지정해야
하는 경우가 많고, 그 상수값은 기존의 모든 행에 동일하게 채워지므로 두 번째 행부터 곧바로
UNIQUE 위반이 난다. 즉 "RK 후보를 늘려서 제약을 피해가자"는 가장 직관적인 해법 자체가
구조적으로 막혀 있다. 게다가 이 에러는 문법적으로는 리뷰 4(1차)에서 지적한 "RK라서 막힌
DDL"과 똑같이 `ERROR`로만 보일 가능성이 높아, 사용자는 "RK 후보 규칙 때문에 막혔나,
아니면 그냥 평범한 UNIQUE 제약 위반인가"를 구분할 단서가 없다.

```sql
csql> CREATE TABLE product(id INT PRIMARY KEY, sku VARCHAR(30));
-- 이미 10만 건이 있고 sku는 지금까지 UK가 아니었다

csql> ALTER TABLE product ADD COLUMN (barcode VARCHAR(30) NOT NULL UNIQUE DEFAULT 'N/A');
-- 첫 번째 행은 성공하지만, 두 번째 행부터 barcode='N/A' 값이 중복되어 즉시 실패한다
ERROR: Unique constraint violation on column "barcode"
-- 이 ERROR는 RK 후보 관련 규칙 때문인가, 아니면 그냥 평범한 UNIQUE 위반인가?
-- 문면만으로는 완전히 동일하게 보인다.
```

예제 설명: 사용자는 "RK 후보를 하나 더 만들어 여유를 확보하겠다"는 나름 신중한 대응을
했는데도 실패하고, 그 실패 원인도 이 스펙이 새로 만든 규칙 때문인지 원래 있던 일반적인
제약 규칙 때문인지 판단할 수 없다. 결국 "RK 후보를 늘리려면 값이 이미 고유한 기존 컬럼을
재활용하거나, 일련번호를 새로 채워 넣는 별도 마이그레이션이 필요하다"는 사실을 스스로
경험으로 터득해야 한다.

제안: §4-2에 "RK 후보를 늘리기 위해 새 UK 컬럼을 추가할 때는 DEFAULT 상수만으로는 대개
불가능하며, 값이 고유하도록 채우는 마이그레이션이 별도로 필요하다"는 실무 안내 문단을
추가하고, 최소한 에러 메시지에서 "일반 UNIQUE 위반"과 "RK 후보 관련 제약"을 구분해
표기해야 한다.

## 리뷰 23

**[심각도: 치명] `ADD CONSTRAINT PRIMARY KEY` 한 줄이 기존에 RK로 쓰이던 UK를 아무 경고 없이 갈아치운다 — "사용자는 복제키를 직접 수정할 수 없다"는 원칙이 지켜지지 않는 구멍**

대상: §1 "복제키는 큐브리드 엔진에 의해 Primary Key ... 혹은 Not Null Unique Key ... 들
중 하나로 선택된다", §4-2 "복제키는 큐브리드 엔진에 의해 결정되며, 사용자는 복제키를
직접 수정할 수 없다.", §4-2 예시 14

문제 설명: §1의 RK 선택 규칙은 "PK가 존재한다면 PK가 복제 키가 됨"을 최우선으로 둔다.
그런데 §4-2 예시 14는 "UK를 복제키로 사용하고 있는 테이블은 PK가 없으므로 (PK) 추가
가능(기존과 동일)"이라고만 설명한다. 이 두 문장을 합치면, 지금 UK가 RK로 쓰이고 있는
테이블에 아무 관계 없어 보이는 컬럼으로 `ADD CONSTRAINT PRIMARY KEY`를 실행하는 순간,
그 PK가 자동으로 새 RK가 되고 지금까지 RK였던 UK는 조용히 "그냥 UK"로 강등된다. 이는
명백히 "복제키를 직접 수정"한 것과 동일한 결과인데, 스펙은 이 조작을 "PK 추가는 원래
되던 대로 된다(기존과 동일)"는 문구로 태연하게 허용한다. 즉 "사용자는 RK를 직접 수정할
수 없다"는 원칙은 `DROP CONSTRAINT`/`ADD CONSTRAINT` 같은 RK 관련 DDL에만 적용되고,
"RK보다 우선순위가 높은 새 제약을 추가"하는 방식으로는 사용자가 RK를 사실상 마음대로
바꿀 수 있다는 뜻이 된다. 게다가 이 재할당은 아무 확인 절차나 경고 메시지 없이 `OK` 한
줄로 끝난다.

```sql
-- product 테이블: PK 없음, sku가 유일한 UK → §1 규칙에 의해 RK = sku
csql> CREATE TABLE product(
    id INT,
    sku VARCHAR(30) NOT NULL UNIQUE,
    stock INT
);

-- 재고 관리 담당자가 "id를 기본키로 지정하자"는, RK와 무관해 보이는 리팩터링을 실행
csql> ALTER TABLE product ADD CONSTRAINT PRIMARY KEY(id);
-- OK (예시 14의 규칙: "PK가 없으므로 추가 가능")

-- 그런데 이 순간 §1 규칙("PK가 존재한다면 PK가 복제 키가 됨")이 적용되어
-- RK가 sku(UK)에서 id(PK)로 조용히 넘어간다. sku는 더 이상 RK가 아니다.
-- 담당자는 "PK를 하나 추가했을 뿐"이라고 생각하지, "복제 키를 바꿨다"고는 생각하지 못한다.
```

예제 설명: 이 시나리오가 위험한 이유는 두 가지다. 첫째, sku를 기준으로 이미 슬레이브에
적용 중이거나 대기 중인 복제 로그가 있다면, RK가 갑자기 id로 바뀐 시점 전후로 어떤
기준으로 행을 찾아 적용해야 하는지 불분명해진다(이 점은 최종 통합 보고서의 RK 로그 순서
이슈와 맞닿아 있지만, 여기서 지적하려는 핵심은 그 이전 단계 — "사용자가 자신이 RK를
바꾸고 있다는 사실 자체를 인지하지 못한다"는 것이다). 둘째, "직접 수정 불가"라는 스펙의
표면적 안전장치가 실제로는 우회 가능하다는 점에서, 이 스펙이 스스로 내세운 안전 원칙에
대한 사용자의 신뢰를 무너뜨린다.

제안: PK 추가로 인해 기존 RK(UK)가 다른 제약으로 교체되는 경우, `ADD CONSTRAINT PRIMARY
KEY` 실행 시 "이 작업으로 복제 키가 sku에서 id로 변경됩니다"라는 명시적 안내 메시지를
출력하도록 요구사항에 못박아야 한다. 또한 §4-2의 "사용자는 복제키를 직접 수정할 수
없다"는 문장 바로 아래에, "단, RK보다 우선순위가 높은 제약(PK)을 추가하면 RK가 자동으로
재할당되며 이는 예외가 아니라 §1 규칙의 정상 적용 결과"라는 각주를 반드시 추가해야 한다.

## 리뷰 24

**[심각도: 중요] `REPLICATION` 옵션을 바꿀 수 있는 권한이 누구에게 있는지 스펙에 전혀 없다**

대상: §2-2 전체

문제 설명: 이 스펙 전체를 관통하는 전제는 "REPLICATION=OFF는 데이터 불일치를 스스로
감수하는 명시적 선택"이라는 것이다(§1: "REPLICATION OFF 로 인한 데이터 불일치는 책임지지
않는다"). 그런데 정작 `ALTER TABLE ... REPLICATION=OFF`를 누가 실행할 수 있는지 —
DBA만 가능한지, 테이블 소유자면 누구나 가능한지 — 에 대한 언급이 스펙 어디에도 없다.
CUBRID의 일반적인 `ALTER TABLE` 권한 규칙을 그대로 물려받는다면, 테이블을 소유한 일반
애플리케이션 계정도 이 옵션을 마음대로 바꿀 수 있다는 뜻이 된다. 최종 통합 보고서가
지적했듯 이 옵션 하나가 FK 무결성(§5)까지 깨뜨릴 수 있는 파급력을 가진 설정인데,
파급력에 걸맞은 권한 통제가 없다면 실수(또는 악의적 조작)로 인한 사고를 막을 수단이
없다.

```sql
-- app_user는 orders 테이블의 소유자일 뿐 DBA 권한은 없다고 가정
csql> connect app_user;
csql> ALTER TABLE orders REPLICATION = OFF;
-- 이 SQL이 성공하는가, 아니면 DBA 권한이 필요하다는 에러가 나는가?
-- 스펙에는 이 질문에 대한 답이 없다.
```

예제 설명: 실무에서는 애플리케이션 배포 파이프라인이 자동으로 `ALTER TABLE` 마이그레이션
스크립트를 실행하는 경우가 흔하다. 이 파이프라인 계정에 REPLICATION 옵션까지 변경할
권한이 함께 부여되어 있다면, 마이그레이션 스크립트의 사소한 실수 하나로 운영 중인 HA
복제 대상 테이블이 조용히 복제 제외로 바뀔 수 있다. 이는 §5가 막으려던 FK 참조 무결성
문제(도입부 다이어그램의 orders/customers 시나리오)를 애플리케이션 계정의 실수 한 번으로
재현시킬 수 있는 경로다.

제안: REPLICATION 옵션 변경에 DBA 권한 또는 별도의 명시적 권한(GRANT)을 요구하도록
정책을 정하고, 최소한 변경 이력을 감사 로그(누가 언제 어떤 테이블의 REPLICATION을
바꿨는지)로 남기도록 요구사항에 추가해야 한다.

## 리뷰 25

**[심각도: 보통] TDE(투명한 데이터 암호화)로 암호화된 테이블을 `REPLICATION=ON`으로 복제할 때, 슬레이브가 같은 암호화 키를 가져야 하는지에 대한 언급이 없다**

대상: §2-3 예시 9 (db_class 조회 결과에 `tde_algorithm`과 `replication` 필드가 나란히 존재)

문제 설명: 예시 9의 `db_class` 조회 결과를 보면 `tde_algorithm : 'NONE'`과
`replication : ON`이 같은 테이블 행에 나란히 출력된다. 즉 TDE(디스크에 저장된 데이터를
암호화해, 파일을 직접 열어봐도 내용을 알 수 없게 하는 CUBRID의 보안 기능) 여부와
REPLICATION 여부는 완전히 독립적인 두 속성으로 카탈로그에 공존한다. 그런데 이 둘이
동시에 켜졌을 때 — 즉 TDE로 암호화된 민감 테이블(예: 주민등록번호, 카드번호가 담긴
테이블)을 `REPLICATION=ON`으로 복제할 때 — 슬레이브가 마스터와 동일한 암호화 키를
갖고 있어야 정상적으로 데이터를 읽고 쓸 수 있는지, 아니면 복제 로그 자체가 암호화되지
않은 평문으로 전달되어 네트워크 구간에서 노출되는지에 대한 설명이 스펙에 전혀 없다.
보안을 이유로 TDE를 켠 테이블일수록 이런 세부사항이 문서화되지 않으면 실무자가 규정
준수(컴플라이언스) 심사에서 답변할 수 없는 질문이 된다.

```sql
csql> CREATE TABLE customer_ssn(
    customer_id INT PRIMARY KEY,
    ssn VARCHAR(20)
) ENCRYPT='AES';  -- TDE 암호화 지정 (실제 CUBRID 문법은 다를 수 있음)

-- 이 테이블은 REPLICATION 기본값(ON)에 따라 복제 대상이 된다.
-- 슬레이브 서버는 마스터와 같은 암호화 키를 보유하고 있는가?
-- 복제 로그(마스터→슬레이브 전송 구간)에서 ssn 컬럼 값은 암호화된 채로 전달되는가?
-- 이 스펙과 기존 TDE 문서 어디에도 두 기능의 접점에 대한 설명이 없다.
```

예제 설명: 이 예제는 극단적으로 보일 수 있지만, TDE를 쓰는 조직일수록 민감 데이터
보호가 업무상 중요하기 때문에 이 접점의 공백은 실제 배포 전에 반드시 확인해야 할
질문이다. 확인 안 된 채로 방치하면, "암호화했으니 안전하다"고 믿었던 데이터가 복제
경로를 통해 평문으로 새어나가는 사고로 이어질 수 있다.

제안: TDE 암호화 테이블과 REPLICATION 옵션의 상호작용(키 전파 방식, 복제 로그 내
데이터의 암호화 여부)을 별도 절로 명시하거나, 최소한 "이번 릴리스에서는 다루지 않으며
TDE 테이블의 복제는 권장하지 않는다"는 식으로 범위를 명확히 선언해야 한다.

## 리뷰 26

**[심각도: 보통] `CREATE TABLE ... LIKE`나 `CREATE TABLE ... AS SELECT`로 테이블을 복제할 때 REPLICATION 옵션과 RK 후보가 원본에서 그대로 이어지는지 스펙이 침묵한다**

대상: 스펙 전체(§2-1에 해당 문법 자체가 언급되지 않음)

문제 설명: 3년차 실무자가 "기존 테이블과 똑같은 구조의 테이블을 하나 더 만들고 싶다"고
할 때 가장 먼저 떠올리는 방법은 컬럼을 하나하나 다시 타이핑하는 것이 아니라 기존 테이블
구조를 복사하는 SQL(예: `LIKE` 절 또는 `AS SELECT`)이다. 이 스펙은 `CREATE TABLE`의
`REPLICATION` 옵션을 §2-1에서 다루지만, "구조를 복사해서 만드는 CREATE TABLE"에서
REPLICATION 옵션과 PK/UK 제약(RK 후보)이 원본으로부터 그대로 상속되는지, 아니면
새 테이블은 무조건 옵션을 생략한 것으로 간주되어 기본값(§2-1: "생략시 ON")이 적용되는지
언급이 없다. 게다가 `AS SELECT`로 만든 테이블은 애초에 PK/UK 제약 자체가 함께 복사되지
않는 것이 일반적인 SQL 관행이므로, 원본이 아무리 RK를 잘 갖추고 있어도 복사본은 RK가
전혀 없는 테이블로 만들어질 가능성이 높다 — 그런데 REPLICATION 여부는 기본값 ON이 그대로
적용된다면, "RK 없이 복제 대상인 테이블"이 손쉽게 하나 더 생겨나는 셈이다.

```sql
-- customers는 예시 17의 테이블: RK(PK)를 갖춘 정상적인 복제 대상 테이블
csql> CREATE TABLE customers_backup LIKE customers;
-- REPLICATION 옵션과 PK 제약이 그대로 복사되는가?

csql> CREATE TABLE customers_snapshot AS SELECT * FROM customers;
-- 이 문법은 통상 컬럼 데이터 타입만 복사하고 PK/UK 제약은 복사하지 않는다.
-- customers_snapshot은 REPLICATION 기본값(ON)이 적용되면서 RK는 없는,
-- 리뷰 1(1차)에서 지적한 "지뢰" 상태의 테이블로 태어날 가능성이 높다.
```

예제 설명: 백업용 테이블이나 스냅샷 테이블을 만드는 작업은 실무에서 흔하지만, 대개
운영 DB의 RK 규칙에 신경 쓰지 않고 습관적으로 실행하는 명령이다. 이런 명령으로 생성된
테이블이 아무 경고 없이 "RK 없는 복제 대상"으로 쌓이면, 몇 달 뒤 HA 전환이나 재시작
시점에 §7의 위반 목록에 원인 모를 테이블들이 무더기로 나타날 수 있다.

제안: `LIKE`/`AS SELECT` 계열 `CREATE TABLE`에서 REPLICATION 옵션과 RK 후보 제약의
상속 규칙을 §2-1에 명시하고, `AS SELECT`처럼 제약이 복사되지 않는 것이 기존 CUBRID
동작이라면 최소한 "복사된 테이블은 RK가 없을 수 있으니 확인하라"는 경고를 CREATE 성공
메시지에 포함해야 한다.

## 리뷰 27

**[심각도: 중요] `ALTER TABLE`에서 `REPLICATION` 절을 아예 언급하지 않으면 "현재 값 유지"인지 "생략 시 기본값(ON) 재적용"인지 불명확하다**

대상: §2-1 "이 옵션은 생략 가능하며 생략시 ON으로 자동으로 복제 테이블로 생성된다."
(CREATE TABLE 기준) vs §2-2 전체(ALTER TABLE에는 이런 문장이 없음)

문제 설명: §2-1은 `CREATE TABLE`에서 REPLICATION을 생략하면 무조건 ON이 된다고 명시적으로
못박는다. 그런데 §2-2(ALTER TABLE 관련 절)에는 "REPLICATION 절을 포함하지 않은 일반적인
ALTER TABLE 문(예: 컬럼 추가, 인덱스 생성 등)을 실행했을 때 REPLICATION 상태가 어떻게
되는가"에 대한 언급이 전혀 없다. 통상적인 SQL 관례라면 "언급하지 않은 옵션은 그대로
유지된다"고 짐작하는 것이 합리적이지만, 이 스펙이 CREATE TABLE에서는 "생략 = 기본값
적용"이라는 특이한 규칙을 정해둔 전례가 있기 때문에, ALTER TABLE에서도 혹시 같은 규칙이
적용되어 REPLICATION=OFF로 신중하게 설정해 둔 테이블이 무관한 스키마 변경 한 번에
REPLICATION=ON으로 되돌아가는 것은 아닌지 문서만으로는 확신할 수 없다.

```sql
-- 이 테이블은 의도적으로 REPLICATION=OFF로 운영 중이다 (예: 대용량 로그 테이블)
csql> ALTER TABLE audit_log REPLICATION = OFF;  -- 과거에 실행됨, 현재 OFF 상태

-- 몇 달 뒤, 컬럼을 하나 추가하는 평범한 스키마 변경을 수행한다
csql> ALTER TABLE audit_log ADD COLUMN (extra_info VARCHAR(100));
-- 이 ALTER TABLE 문에는 REPLICATION 절이 없다.
-- audit_log는 여전히 REPLICATION=OFF인가, 아니면 §2-1의 "생략시 ON" 규칙이
-- ALTER TABLE에도 똑같이 적용되어 REPLICATION=ON으로 되돌아가는가?
```

예제 설명: 만약 후자(생략 시 ON으로 리셋)라면, 의도적으로 복제에서 제외해 둔 테이블이
아무 상관 없는 컬럼 추가 작업 하나로 조용히 복제 대상에 편입되는 대형 사고가 된다.
그리고 그 테이블이 RK가 없는 상태라면 §7의 HA 전환 검사에서야 뒤늦게 발각된다.
CREATE TABLE에서 이미 "생략 시 기본값 적용"이라는 이례적인 규칙을 만들어 둔 이상, 이
문서는 ALTER TABLE에도 같은 규칙이 적용되는지 아닌지를 명시적으로 밝혀야 하는데 지금은
아무 말이 없다.

제안: §2-2에 "REPLICATION 절을 포함하지 않은 ALTER TABLE 문은 기존 REPLICATION 설정에
영향을 주지 않는다"는 문장을 명시적으로 추가해야 한다. (반대로 정말 리셋되는 설계라면
그 사실과 이유를 훨씬 더 크게 경고해야 한다.)

## 리뷰 28

**[심각도: 보통] 스키마 버전관리에 흔히 쓰이는 `cubrid dumpdb`류 스키마 추출 결과에 REPLICATION 절이 포함되는지 언급이 없어, 환경 간 스키마 비교 도구가 이 속성의 차이를 놓칠 수 있다**

대상: §8 (unloaddb/loaddb만 다루며, 스키마 전용 추출 도구는 언급되지 않음)

문제 설명: §8은 데이터까지 포함한 `unloaddb`/`loaddb`의 REPLICATION 처리만 다룬다.
그런데 실무에서 스테이징과 운영 환경의 스키마가 서로 어긋나지 않았는지 확인할 때는
데이터 없이 스키마(테이블 구조 DDL)만 뽑아 비교하는 방식을 훨씬 자주 쓴다(예: git으로
버전 관리되는 DDL 스크립트, 또는 스키마 전용 덤프 도구의 출력을 diff). 이런 스키마 전용
추출 결과에 REPLICATION 옵션이 포함되는지, 즉 `show create table`처럼 REPLICATION 절이
DDL 텍스트에 함께 나오는지에 대한 보장이 §8에는 없다(§8은 데이터 이관 시나리오만
다룬다). 만약 스키마 전용 추출 도구가 이 새 옵션을 놓친다면, "스테이징은 REPLICATION=OFF
인데 운영은 ON"처럼 실제로는 다른 두 환경의 스키마가 diff 도구상으로는 "동일함"으로
표시되는 맹점이 생긴다.

```sh
# 스테이징 DB
$ show_schema staging_db customers   # REPLICATION=OFF (테스트 데이터라 복제 안 함)

# 운영 DB
$ show_schema prod_db customers      # REPLICATION=ON

$ diff <(show_schema staging_db customers) <(show_schema prod_db customers)
# 만약 스키마 추출 도구가 REPLICATION 절을 표시하지 않는다면, 이 diff는 "차이 없음"으로
# 나온다. 그런데 두 환경의 실제 복제 동작은 완전히 다르다.
```

예제 설명: 스키마 버전관리는 3년차 실무자가 릴리스 전에 반드시 거치는 점검 단계다.
이 단계에서 사용하는 도구가 REPLICATION 속성을 표시하지 않는다면, 환경 간 설정 드리프트
(설정이 서서히 어긋나는 현상)를 발견할 유일한 안전망이 뚫리는 셈이다. §2-3이 다루는
`show create table`은 이미 REPLICATION을 포함하고 있으니(예시 8), 이 정보가 스키마
비교/버전관리에 흔히 쓰이는 다른 도구 경로에도 일관되게 노출되는지를 스펙이 확인해줘야
한다.

제안: §2-3 또는 §8에 "REPLICATION 옵션은 `show create table` 뿐 아니라 스키마 추출을
목적으로 하는 모든 인터페이스(스키마 전용 dump 유틸리티 등)의 출력에도 동일하게 포함된다"는
문장을 명시해야 한다.

## 리뷰 29

**[심각도: 사소] 스펙 내 한국어 용어("복제 테이블", "복제 대상", "복제 제외")가 영문 매뉴얼로 번역될 때 어떤 용어로 고정될지 정해져 있지 않다**

대상: 스펙 전체 (§1, §2, §9에서 "복제 테이블"/"복제 대상 테이블"/"복제 제외 테이블"이
혼용됨)

문제 설명: CUBRID는 한국어와 영어 매뉴얼을 함께 제공하는 프로젝트다. 이 스펙 문서 안에서
이미 "복제 테이블", "복제 대상 테이블", "복제 대상"이 서로 바꿔가며 쓰이고 있는데(최종
통합 보고서도 이를 용어 혼용 문제로 지적했다), 이 상태로 영문 매뉴얼 작업이 진행되면
번역자가 "replicated table", "replication target table", "table subject to
replication" 등 서로 다른 영어 표현을 상황마다 다르게 골라 쓸 위험이 있다. 그렇게 되면
영문 매뉴얼 독자는 한국어 원문 독자보다 더 심하게 "이게 같은 개념을 가리키는 다른 단어인지,
아니면 실제로 다른 개념인지" 혼란을 겪는다. 특히 온라인 매뉴얼에서 용어로 검색하는 사용자
입장에서는 번역어가 페이지마다 다르면 검색 결과 자체가 누락된다.

```
한국어 원문 혼용 예:
- §1: "복제 테이블은 ... 존재하지 않으면"
- §2-1: "복제 테이블 생성 여부를 설정한다"
- §4: "복제 대상의 경우 다음 DDL에 대한 제약 사항이 존재한다"
- §9: "RK가 있는 테이블 역시 복제 제외대상이 될 수 있음"

영문 매뉴얼화 시 예상되는 위험:
- "replicated table" / "replication table" / "replication target table" 중
  번역자마다 다른 용어를 고를 수 있다.
```

예제 설명: 이 항목은 SQL 예제가 아니라 문서화 프로세스에 대한 지적이다. 그러나
"매뉴얼화 가능성"이 이 리뷰의 평가 기준 중 하나이므로, 번역 단계에서 용어가 갈라질 여지를
원천 차단하지 않으면 한국어 스펙 문서의 모호함이 영문 매뉴얼에서 그대로, 혹은 더 심하게
재현된다는 점을 짚어둔다.

제안: 스펙을 확정하기 전에 "복제 대상 테이블(replicated table)" / "복제 제외 테이블
(non-replicated table)"처럼 한국어-영어 용어를 1:1로 고정한 용어집을 만들어 문서 서두에
배치하고, 이후 모든 매뉴얼·문서·에러 메시지가 이 용어집만 참조하도록 해야 한다.

## 조사 종료 선언

이번 2차 라운드에서는 §3(싱글 제약), §2-2(ALTER 생략 시 동작), §8(스키마 도구 연계),
그리고 스펙이 아예 침묵하는 주변 영역(권한 통제, TDE, LIKE/AS SELECT 상속, 문서 번역
일관성)을 훑어 9건의 신규 리뷰를 작성했다. 이 외에 검토했으나 최종적으로 제외한 영역은
다음과 같다.

- **파티션 테이블·트리거·멀티 슬레이브·컬럼 단위 필터**: 최종 통합 보고서가 이미 "스코프
  불명" 또는 "엔진 개발자 고유 지적"으로 짚어 놓은 영역이라, 구체적인 예제를 새로 만들어도
  근본적으로 같은 실패 모드("이 스펙은 이 객체/구성을 다루지 않는다")의 변주가 될 뿐이라
  판단해 제외했다.
- **REPLICATION 예약어 충돌, DROP TABLE 재생성 우회, SERIAL/AUTO_INCREMENT 동기화**:
  1차 리뷰 또는 최종 통합 보고서에 이미 등장한 지적과 메커니즘이 동일해 신규성이 없다고
  판단했다.
- **GUI 관리 도구(스키마 편집기 등)에서의 REPLICATION 지원 여부**: 초안에서 검토했으나,
  이 스펙 자체가 SQL 계층만을 다루는 문서이고 GUI 도구 지원은 별도 프로젝트 범위일
  가능성이 높아 근거 없는 추측에 가깝다고 판단해 제외했다.
- **CASCADE(연쇄 삭제/갱신) FK 액션과 RK 재계산의 상호작용**: 최종 통합 보고서의 "다단계
  FK" 지적(M-8)과 본질적으로 같은 실패 모드(FK 관계에서 참조 무결성이 복제 경계를 넘어
  깨지는 것)로 수렴한다고 판단해 별도 항목으로 올리지 않았다.

3년차 최종 사용자 관점("내가 짠 SQL이 언제 성공/실패하고, 실패하면 무엇을 해야 하는가")에서
더 파볼 만한 새로운 영역은 현재로서는 소진되었다고 판단한다. 개수를 채우기보다 실제로
겪을 법한 시나리오에 근거를 둔 지적만 남겼다.
