# CUBRID HA 복제 키(RK) / REPLICATION 옵션 스펙 리뷰 — 2차 라운드
### 리뷰어: DB 엔지니어(DBA·운영자) 3년차 관점

## 2차 라운드 개요

1차는 RK 선택 규칙의 비결정성, HA 전환 실패 출력 포맷, 데이터 재동기화, DDL 원자성, FK
사후 전환 미차단 등 스펙 본문이 직접 다루는 절차 중심으로 짚었다. 이번 2차는 1차와
최종보고서(40개 통합 이슈)가 다루지 않은 **스펙이 아예 침묵하는 주변 객체·도구와의
상호작용**을 팠다 — 물리 백업(backupdb/restoredb), 백업을 수행하는 위치(마스터냐
슬레이브냐), 권한·감사 체계, 파티션 테이블, 인덱스 생성 문법(CONSTRAINT vs INDEX),
대량 데이터 적재 도구(cubrid loader), TDE(투명 데이터 암호화), 복제 로그 용량 문제,
운영 중 단일 테이블 부분 복원(loaddb)이 그것이다. 개수를 채우기보다 실제로 운영자가
현장에서 밟을 법한 절차 중 스펙이 답을 주지 않는 지점만 추렸다.

## 리뷰 21

**[심각도: 치명] 물리 백업/시점 복구(backupdb·restoredb)가 스펙에서 완전히 누락 — PITR 시 REPLICATION 상태가 과거로 되돌아갈 위험**

- 대상: §8 (UNLOADDB & LOADDB 절 전체)

**문제 설명**

§8은 오직 `unloaddb`/`loaddb`(테이블을 텍스트/바이너리 덤프로 뽑아 논리적으로
복원하는 도구)만 다룬다. 그런데 실제 운영 현장에서 CUBRID DBA가 매일 밤 돌리는
백업은 대부분 `backupdb`(데이터베이스 볼륨을 통째로 뜨는 물리 백업, 증분 레벨
0/1/2 지원)이고, 장애 복구는 `restoredb -r`(특정 시점까지 트랜잭션 로그를 재생하는
PITR, Point-In-Time Recovery)으로 한다. 스펙은 이 두 명령을 한 번도 언급하지
않는다. 물리 백업 자체는 볼륨을 그대로 복사하므로 REPLICATION 옵션 같은 카탈로그
값도 당연히 함께 백업되겠지만, 문제는 "그 시점의" 값이 함께 백업된다는 점이다.
REPLICATION 옵션은 시간에 따라 바뀌는 값이므로, 옛 백업 + 로그 재생 조합인 PITR은
"현재 클러스터가 합의한 REPLICATION 상태"와 다른 과거 상태를 되살릴 수 있다.

**구체 예제**

```bash
# 1일차: customers 테이블 REPLICATION=ON, 정상 운영
# 5일차 00:00: backupdb (레벨 0 전체 백업)

# 10일차: 개인정보 이슈로 전환
ALTER TABLE customers REPLICATION=OFF;
# 이 시점부터 슬레이브의 customers는 텅 비게 됨 (§1의 명시된 동작)

# 20일차: 마스터 디스크 장애 발생, DBA가 PITR 결정
# "10일차 REPLICATION=OFF 전환 직전 시점"까지만 복구하기로 함
$ restoredb -r "2026-08-15 23:59:00" -B backup_vol testdb
```

**예제 설명**

복구된 DB는 10일차 이전 상태이므로 customers는 다시 REPLICATION=ON이고 데이터도
가득 차 있다. 그런데 이 시점 이후 슬레이브는 이미 "customers는 OFF" 라는 카탈로그
상태로 계속 운영되어 왔다. 복구된 마스터를 그대로 클러스터에 재편입시키면, 마스터는
customers를 복제 대상으로 인식해 DML을 슬레이브로 계속 보내려 하는데 슬레이브
카탈로그는 그 사이 REPLICATION=OFF로 굳어 있던 상태다(혹은 그 반대로 애초에
DDL이 다시 흘러가 다시 OFF로 맞춰질 수도 있음). 어느 쪽이든 "복구 시점 선택에 따라
REPLICATION 상태가 시간을 되짚어 요동칠 수 있다"는 위험은 스펙 어디에도 경고가
없다. 이는 unloaddb만 다루는 §8의 범위를 완전히 벗어나는, DBA가 실제로 훨씬 자주
쓰는 도구의 사각지대다.

**제안**

§8을 "논리 백업(unloaddb/loaddb)"과 "물리 백업(backupdb/restoredb)"으로 구분해
각각의 절을 신설하고, 특히 PITR 시나리오에서 복구된 REPLICATION 카탈로그 상태와
현재 클러스터의 상태가 어긋날 수 있음을 명시하며, 복구 후 반드시 REPLICATION
전수 점검을 거치도록 운영 절차를 규정해야 한다.

## 리뷰 22

**[심각도: 중요] 백업을 슬레이브에서 수행하는 흔한 관행과 결합하면 REPLICATION=OFF 테이블은 구조적으로 백업 자체가 불가능**

- 대상: §8, §1 ("REPLICATION OFF 로 인한 데이터 불일치는 책임지지 않는다")

**문제 설명**

마스터의 부하를 줄이기 위해 백업(`unloaddb`든 `backupdb`든)을 슬레이브에서
수행하는 것은 HA 구성에서 흔한 운영 관행이다. 그런데 REPLICATION=OFF 테이블은
정의상 슬레이브에 데이터가 아예 존재하지 않는다. 즉 리뷰 18(1차)에서 지적한
"unloaddb가 OFF 테이블 데이터를 백업에 포함하는가"라는 질문에 설령 "포함한다"는
답이 나오더라도, 그 백업을 **슬레이브에서** 수행하는 순간 답과 무관하게 OFF
테이블은 항상 빈 채로 백업된다. 이는 도구의 정책 문제가 아니라 슬레이브라는
장소 자체의 구조적 한계이므로, "unloaddb 정책을 명시하라"는 제안만으로는
해결되지 않는다.

**구체 예제**

```bash
# 운영 관행: 매일 새벽 2시, 마스터 부하를 피해 슬레이브에서 백업
$ ssh slave_host
$ unloaddb -o /backup/daily_$(date +%F) testdb   # 슬레이브에서 실행

# non_repl_customers 는 REPLICATION=OFF
# 슬레이브에는 이 테이블의 행이 0건 → 백업 파일에도 스키마만 있고 데이터는 0건
```

**예제 설명**

담당자가 매일 백업 로그의 "성공" 여부만 확인한다면, non_repl_customers가 사실상
한 번도 제대로 백업된 적이 없다는 사실을 몇 달간 눈치채지 못할 수 있다. 마스터
장애 시 마지막 안전망이라고 믿었던 백업이 정작 REPLICATION=OFF 테이블에 대해서는
아무 역할도 하지 못하는 상황이 이 시점에야 드러난다. 이 문제는 REPLICATION 옵션을
도입하는 순간 "백업 위치는 반드시 마스터여야 한다"는 새로운 제약이 암묵적으로
생긴다는 뜻인데, 스펙은 이를 한 마디도 언급하지 않는다.

**제안**

§8 또는 운영 매뉴얼에 "REPLICATION=OFF 테이블이 존재하는 클러스터에서는 데이터
백업(unloaddb/backupdb 불문)을 반드시 마스터에서 수행해야 한다"는 제약을 명문화하고,
슬레이브에서 백업 명령을 실행할 경우 OFF 테이블 목록과 함께 경고를 출력하도록
해야 한다.

## 리뷰 23

**[심각도: 중요] REPLICATION 옵션 변경에 대한 별도 권한·감사(audit) 체계가 없어 스키마 소유자 혼자 HA 안전성을 깰 수 있음**

- 대상: §2-2 (ALTER TABLE ... REPLICATION), 스펙 전체

**문제 설명**

`ALTER TABLE ... REPLICATION=OFF`는 문법상 일반 `ALTER TABLE` 옵션 변경과
동일해 보인다. 즉 해당 테이블에 대한 통상적인 ALTER 권한(테이블 소유자이거나
DBA 그룹)만 있으면 실행할 수 있을 가능성이 높다. 그런데 이 한 문장의 파급力은
일반 컬럼 추가/삭제와 차원이 다르다 — 리뷰 6(1차)·최종보고서 C-2가 지적했듯,
이 문장 하나로 그 테이블을 참조하는 다른 복제 테이블의 FK 무결성이 슬레이브에서
깨질 수 있고, failover 시 애플리케이션 장애로 직결된다. 그런데 스펙에는 이 위험한
작업에 대해 더 높은 권한 등급을 요구하거나, 실행 사실을 별도로 기록(감사 로그)
하겠다는 언급이 전혀 없다.

**구체 예제**

```sql
-- 애플리케이션 개발자 계정 (자신이 만든 테이블에 대해 ALTER 권한 보유)
-- customers는 orders(다른 개발자 소유, 복제 대상)가 참조 중임을 이 개발자는 모름
ALTER TABLE customers REPLICATION=OFF;   -- 배치 처리 성능 때문에 임시로 껐다가 깜빡 잊음

OK
```

**예제 설명**

이 문장은 일반 스키마 권한만으로 실행되며, 실행 즉시 로그에 "누가, 왜" 이 옵션을
바꿨는지 남긴다는 보장이 스펙에 없다. 몇 주 뒤 failover가 발생해 orders의 FK
참조가 깨졌을 때, 운영자는 "언제부터, 누가 이 옵션을 바꿨는지"를 감사 로그에서
찾아야 하는데 이를 위한 표준 절차가 없다. DBA가 아닌 개발자 계정이 클러스터
전체의 HA 안전성에 영향을 주는 조작을 아무 승인 절차 없이 단독으로 실행할 수
있다는 것 자체가 운영 관점에서는 권한 최소화 원칙에 어긋난다.

**제안**

`ALTER TABLE ... REPLICATION` 변경에는 테이블 소유자 권한과 별개로 DBA 권한(또는
신설되는 별도 권한, 예: `REPLICATION ADMIN`)을 요구하도록 스펙에 명시하고, 이
옵션이 변경될 때마다 실행 계정·시각·이전 값/이후 값을 서버 로그(또는 `db_class`
이력 테이블)에 남기도록 감사 요구사항을 추가해야 한다.

## 리뷰 24

**[심각도: 중요] 파티션 테이블에서 REPLICATION 옵션·RK가 파티션 단위인지 부모 테이블 단위인지 불명**

- 대상: 스펙 전체 (파티션 관련 언급 전무)

**문제 설명**

스펙은 파티션 테이블(하나의 논리 테이블을 물리적으로 여러 조각으로 나눠 저장하는
기능, 보통 날짜·범위 기준)을 한 번도 언급하지 않는다. CUBRID의 파티션 테이블은
파티션 키가 PK/UK에 포함되어야 하는 등 일반 테이블과 제약이 다르다. 그런데
REPLICATION 옵션과 RK 후보 판정이 부모 테이블 단위로만 적용되는지, 아니면 개별
파티션 단위로 서로 다르게 지정할 수 있는지(예: 오래된 월별 로그 파티션만 복제
제외로 돌려 슬레이브 저장 공간을 절약하는 흔한 운영 패턴) 전혀 알 수 없다. 대용량
로그성 테이블을 파티션으로 운영하는 DBA에게는 실무적으로 매우 중요한 질문이다.

**구체 예제**

```sql
CREATE TABLE access_log (
    log_id BIGINT,
    log_date DATE,
    msg VARCHAR(200),
    PRIMARY KEY (log_id, log_date)
)
PARTITION BY RANGE (log_date) (
    PARTITION p202606 VALUES LESS THAN ('2026-07-01'),
    PARTITION p202607 VALUES LESS THAN ('2026-08-01'),
    PARTITION p202608 VALUES LESS THAN ('2026-09-01')
);

-- DBA가 원하는 것: 6월 파티션(p202606)은 이미 분석 완료, 조회 안 함
-- -> 슬레이브 저장 공간 절약을 위해 이 파티션만 복제 제외로 돌리고 싶음
ALTER TABLE access_log ??? -- 파티션 단위 REPLICATION 지정 문법이 스펙에 없음
```

**예제 설명**

일반 테이블 기준으로는 REPLICATION은 테이블 전체에 대해 하나의 값이다(§2-1).
파티션은 내부적으로 여러 개의 물리 테이블처럼 동작하지만 사용자에게는 논리적으로
하나의 테이블로 보이므로, "파티션 단위 REPLICATION"이 애초에 설계 범위 밖인지,
아니면 구현하다 보니 자연스럽게 지원되는지조차 스펙이 답하지 않는다. 이 답에
따라 대용량 파티션 테이블을 운영하는 방식 자체가 달라지므로, 최소한 "이번 스펙은
파티션 단위 세분화를 지원하지 않으며 REPLICATION은 항상 파티션드 테이블 전체에
적용된다"는 스코프 확정 문장이라도 필요하다.

**제안**

파티션 테이블에서 REPLICATION 옵션과 RK 후보 판정이 부모 테이블 전체 단위로만
적용됨을 명시하거나, 파티션 단위 지원 여부를 로드맵으로 분리해 명확히 선언해야
한다. 또한 파티션 키가 RK 후보 판정에 어떤 영향을 주는지(예: PK가 파티션 키를
포함해야 하는 기존 제약과 RK 선택 규칙의 상호작용)도 예시로 추가해야 한다.

## 리뷰 25

**[심각도: 보통] CREATE INDEX / CREATE UNIQUE INDEX 로 만든 유니크 키가 RK 후보로 인정되는지 스펙에 예시가 없음**

- 대상: §4-2 (예시 11~16이 전부 `ADD CONSTRAINT` / `DROP CONSTRAINT` 문법)

**문제 설명**

§4-2의 모든 예시는 `ALTER TABLE ... ADD CONSTRAINT` / `DROP CONSTRAINT` 문법만
사용한다. 그런데 CUBRID를 포함한 대부분의 RDBMS는 유니크 제약을 만드는 또 다른
경로로 `CREATE UNIQUE INDEX idx_name ON tbl(col)` 문법을 지원한다. 인덱스
재구성(재생성, 재정렬) 작업을 할 때 DBA는 관례적으로 `ALTER TABLE ADD
CONSTRAINT`보다 `CREATE INDEX`/`DROP INDEX`류 명령을 더 자주 쓴다(인덱스 이름을
직접 관리하기 편하고, 온라인 도구들이 이 문법을 전제로 스크립트를 생성하는 경우가
많기 때문). §1은 "PK 혹은 Not Null Unique Key"라고만 정의할 뿐, 이 UK가 반드시
`CONSTRAINT`로 선언되어야 하는지, `CREATE UNIQUE INDEX`로 만든 것도 동등하게
인정되는지 구분하지 않는다.

**구체 예제**

```sql
CREATE TABLE tbl (a INT, b INT, c INT);

-- 경로 1: 제약으로 선언 (스펙 예시와 동일한 문법)
ALTER TABLE tbl ADD CONSTRAINT UNIQUE (a);

-- 경로 2: 인덱스로 선언 (스펙에 예시 없음, 그러나 실무에서 흔히 쓰는 문법)
CREATE UNIQUE INDEX idx_tbl_b ON tbl(b);
ALTER TABLE tbl MODIFY b INT NOT NULL;   -- NOT NULL UNIQUE 요건 충족 시도

-- 이 상태에서 tbl의 RK 후보는 a 뿐인가, a와 b 둘 다인가?
```

**예제 설명**

만약 `CREATE UNIQUE INDEX`로 만든 UK가 RK 후보로 인정되지 않는다면, DBA가
평소 쓰던 인덱스 관리 방식으로는 절대 RK 후보를 만들 수 없고 반드시
`ADD CONSTRAINT` 문법으로 다시 작성해야 한다는 뜻인데 이는 실무 관행과 충돌한다.
반대로 인정된다면, 이번엔 예시 16("DROP INDEX 는 복제키 후보가 없다면 삭제
불가")과의 관계도 재정리해야 한다 — `DROP INDEX`가 제약 기반 UK에는 애초에 쓸 수
없는 명령인지(제약은 `DROP CONSTRAINT`로만 지운다는 것이 CUBRID의 일반 규칙이라면),
아니면 인덱스 기반 UK에도 쓸 수 있는 것인지 이 둘의 관계가 스펙 전체에서 한 번도
명시적으로 정리되지 않는다.

**제안**

§1 또는 §4-2에 "RK 후보가 될 수 있는 UK는 제약(CONSTRAINT)으로 선언된 것만
해당하며, 인덱스로만 선언된 UNIQUE 인덱스는 (해당/비해당)이다"라는 문장을 명시하고,
`CREATE UNIQUE INDEX` 문법을 사용한 예시를 최소 하나 추가해야 한다.

## 리뷰 26

**[심각도: 치명] 대량 데이터 이관에 쓰는 벌크 적재 도구(cubrid loader)가 복제 로그를 생성하는지 불명**

- 대상: 스펙 전체 (unloaddb/loaddb 외의 데이터 이관 경로 미언급)

**문제 설명**

§8이 다루는 `unloaddb`/`loaddb`는 데이터베이스 전체(혹은 지정 클래스 전체)를
논리적으로 통째로 옮기는 도구다. 그런데 실무에서 "데이터 이관"이라 하면 이보다
훨씬 자주 쓰는 것은 `cubrid loader`(CSV/텍스트 파일을 특정 테이블에 대량
적재하는 유틸리티, 인덱스 비활성화·병렬 적재 등 성능 최적화 옵션을 가진 별도
도구)나 `csql`의 `.import` 류 명령이다. 이런 벌크 적재 도구들은 일반 INSERT
문과 다른 저수준 경로(예: 인덱스를 잠시 끄고 마지막에 재구성, WAL/로그 우회
최적화)를 쓰는 경우가 흔하다. 이 스펙은 HA 운영 중 REPLICATION=ON 테이블에
`cubrid loader`로 대량 데이터를 적재했을 때, 그 적재분이 일반 DML과 동일하게
복제 로그에 기록되어 슬레이브로 전파되는지 전혀 언급하지 않는다.

**구체 예제**

```bash
# HA 운영 중, orders(REPLICATION=ON) 테이블에 대량 이관
# 다른 시스템에서 뽑은 CSV 500만 건을 벌크 적재
$ cubrid loader -u dba -c load.ldf --no-log -t orders new_data.txt
# --no-log 류 옵션(성능을 위해 로깅을 최소화하는 옵션)이 실제로 존재한다면,
# 이 500만 건이 슬레이브로 복제되는가?
```

**예제 설명**

이번 개선의 출발점이 된 문제가 정확히 "복제가 조용히 누락되는 것"이었다는 점을
생각하면, 벌크 적재 도구가 성능을 위해 일반 로깅 경로를 우회하는 옵션을 제공하고
있다면(다른 DBMS의 벌크 로더들이 흔히 그렇듯), 그 우회 경로로 들어간 데이터는
RK 유무나 REPLICATION 옵션과 무관하게 애초에 복제 로그 자체를 안 만들 수 있다.
이 경우 마스터에는 500만 건이 있는데 슬레이브에는 하나도 없는 상황이 "RK가 없어서"도
아니고 "REPLICATION=OFF라서"도 아닌, 순전히 이관 도구의 경로 때문에 재현된다. 이는
이번 스펙이 다루는 문제 영역과 근본적으로 같은 유형의 사고이지만 스펙의 방어망
(§1, §4, §7) 밖에 있다.

**제안**

`cubrid loader` 등 unloaddb/loaddb·일반 DML 이외의 데이터 적재 경로가 복제 로그를
생성하는지 여부를 명시하고, 만약 로깅을 우회하는 고성능 모드가 존재한다면 HA
운영 중에는 그 모드의 사용을 제한하거나 최소한 경고를 출력하도록 스펙 범위에
포함해야 한다.

## 리뷰 27

**[심각도: 중요] TDE(투명 데이터 암호화) 적용 테이블과 REPLICATION의 상호작용 — 슬레이브에 암호화 키가 없을 때 동작 불명**

- 대상: §2-3 예시 9 (`tde_algorithm : 'NONE'` 필드가 이미 노출됨)

**문제 설명**

예시 9의 `db_class` 조회 결과에는 `replication` 바로 옆에 `tde_algorithm`(TDE,
Transparent Data Encryption: 저장된 데이터를 투명하게 암호화하는 기능) 필드가
함께 표시된다. 즉 이 두 속성이 같은 카탈로그에 공존한다는 사실은 스펙 자체가
보여주고 있는데, 정작 본문에는 이 둘의 상호작용에 대한 언급이 전혀 없다. TDE가
적용된 테이블은 암호화 키(볼트/키스토어에 보관)가 있어야 데이터를 읽고 쓸 수
있는데, 이 키가 마스터와 슬레이브에 별도로 배포·관리되는 것이라면, 복제 대상
(REPLICATION=ON)이면서 TDE가 걸린 테이블의 변경분을 슬레이브의 applylogdb가
적용하려 할 때 슬레이브 쪽에 해당 키가 없거나 다르면 어떤 일이 벌어지는지가
궁금해진다.

**구체 예제**

```sql
-- 마스터: TDE 적용 + 복제 대상 테이블
CREATE TABLE sensitive_orders (
    order_id INT PRIMARY KEY,
    card_no VARCHAR(20)
) ENCRYPT='AES' REPLICATION=ON;

-- 운영자가 슬레이브 서버의 키스토어 설정을 깜빡하고 마스터만 설정한 상태
INSERT INTO sensitive_orders VALUES (1, '1234-5678-...');
```

**예제 설명**

마스터에서의 INSERT는 문제없이 성공한다. 이 변경분이 슬레이브로 전달되어
applylogdb가 반영을 시도할 때, 슬레이브에 해당 테이블의 암호화 키가 없다면
반영이 실패해 기존 문제(applylogdb 에러 → fail_count 증가)가 재현될 수도 있고,
혹은 암호화 관련 처리가 애초에 복제 로그 레이어와 무관하게(로그 자체는 암호화
이전 평문 단계에서 기록되는 등) 동작해서 문제가 없을 수도 있다. 어느 쪽이든
스펙이 침묵하고 있어 TDE를 쓰는 보안 규제 환경(금융권 등 카드번호·주민번호를
다루는 테이블)의 운영자는 이 조합을 검증 없이 그냥 신뢰해야 하는 처지다.

**제안**

REPLICATION=ON이면서 TDE가 적용된 테이블의 복제 동작(키 배포 요구사항, 슬레이브
키 부재 시 에러 처리)을 스펙에 명시하고, 최소한 "TDE와 REPLICATION은 독립적으로
동작하며 슬레이브도 동일한 키를 보유해야 한다"는 운영 전제 문장이라도 추가해야
한다.

## 리뷰 28

**[심각도: 중요] REPLICATION=OFF 테이블의 DML도 트랜잭션 로그에 기록되는지 불명 — 로그 용량·아카이브 보존·복제 지연 지표 왜곡 가능성**

- 대상: §1, §4 (REPLICATION 옵션이 "무엇을 걸러내는지"의 계층이 불명)

**문제 설명**

REPLICATION=OFF는 "슬레이브로 데이터가 복제되지 않는다"는 것만 규정한다. 그런데
이 차단이 어느 계층에서 일어나는지가 스펙에 없다 — (a) 마스터의 트랜잭션
로그(WAL 성격의 로그, 장애 복구·PITR의 기반이 되는 로그) 자체에 OFF 테이블의
변경 레코드가 아예 안 남는지, 아니면 (b) 트랜잭션 로그에는 다른 테이블과 동일하게
기록되고 복제 전용 로그(replication log)로 걸러 담는 단계에서만 제외되는지, 그도
아니면 (c) 복제 로그에는 담기지만 슬레이브의 applylogdb가 적용 직전에 스킵하는지.
이 세 가지는 사용자에게 보이는 결과(슬레이브에 데이터 없음)는 같지만, 운영자가
용량을 계획하고 지표를 해석하는 방식은 완전히 달라진다.

**구체 예제**

```
[용량 계획 시나리오]
- non_repl_audit_log (REPLICATION=OFF) 테이블에 초당 수백 건 INSERT (감사 로그성 테이블)
- 이 테이블을 굳이 REPLICATION=OFF로 둔 이유: "어차피 슬레이브에 안 보낼 거라
  로그 트래픽도 아낄 수 있겠지" 라는 기대

[의문]
1. 이 INSERT들이 replication log(아카이브 로그 중 슬레이브 전송용 부분)에
   여전히 다 쌓이는가?
2. 만약 (c)처럼 슬레이브의 applylogdb 단계에서만 걸러진다면, 네트워크 대역폭과
   슬레이브의 로그 재생 CPU는 절약되지 않고 오히려 "쓸모없는 로그를 계속 받아서
   버리는" 낭비가 생기는가?
3. 복제 지연(lag)을 "마스터-슬레이브 LSA(로그 위치) 차이"로 측정한다면, OFF
   테이블의 대량 쓰기가 실제 데이터 지연과 무관하게 지연 수치를 부풀리는가?
```

**예제 설명**

운영자가 REPLICATION=OFF를 택하는 실무적 동기 중 하나는 "이 테이블은 트래픽이
너무 많아서 복제 대역폭을 아끼려는 것"(예: 감사 로그, 세션 테이블)이다. 만약
실제로는 (b)나 (c)처럼 로그가 만들어진 뒤에야 걸러진다면, 이 최적화 의도 자체가
성립하지 않는다. 반대로 (a)처럼 트랜잭션 로그 단계에서부터 아예 기록을 안
한다면, 이는 PITR(리뷰 21)의 복구 정밀도에도 영향을 준다 — 그 시점 그 테이블의
변경 이력 자체가 로그에 없으므로 복구할 방법이 없다는 뜻이 되기 때문이다. 이
계층 구분이 스펙에 없으면 용량 산정도, 지연 모니터링 해석도, 복구 범위 판단도
전부 추측에 의존하게 된다.

**제안**

REPLICATION=OFF 테이블의 변경 사항이 (1) 트랜잭션 로그, (2) 복제(전송) 로그,
(3) 슬레이브 적용 단계 중 정확히 어느 단계에서 제외되는지 명시하고, 이것이 로그
용량·네트워크 대역폭·복제 지연 지표에 미치는 영향을 §4 또는 별도 "운영 지표" 절에
서술해야 한다.

## 리뷰 29

**[심각도: 중요] HA 운영 중 단일 테이블 부분 복원(loaddb)이 가능한지, 가능하다면 RK가 안전하게 재할당되는지 불명**

- 대상: §8

**문제 설명**

§8은 "load시 ... (싱글 모드에서) load 시 모두 복제 테이블로 설정된다"처럼
`loaddb`가 싱글 모드에서 DB 전체를 이관하는 상황만 전제한다. 그런데 실무에서
`loaddb`는 전체 DB 이관 목적 외에도, 특정 테이블 하나가 논리적으로 손상되었거나
실수로 대량 삭제된 경우 "그 테이블만" 별도 백업 파일에서 복원하는 부분 복구
용도로도 쓰인다. 이런 부분 복구가 **HA가 이미 운영 중인 상태**에서 가능한지,
가능하다면 새로 로드된 테이블에 RK가 어떻게 재할당되고 그 순간부터 슬레이브
복제가 어떻게 재개되는지 스펙에 전혀 없다.

**구체 예제**

```bash
# HA 운영 중, orders 테이블에서 애플리케이션 버그로 대량 오삭제 발생
# 어젯밤 백업에서 orders 테이블만 복원하기로 결정

# 1. 마스터에서 손상된 테이블 제거 후 재생성 시도
csql> DROP TABLE orders;              -- 이 시점 orders를 참조하는 FK(§5)는?
csql> loaddb -d testdb -u dba --input-file=orders_only.backup

# 2. HA가 켜진 채로 이 작업이 허용되는가?
# 3. 복원된 orders의 RK는 원래 order_id(PK)로 다시 잡히는가?
# 4. 복원 직후부터 슬레이브 복제가 재개되는가, 아니면 전체 재동기화가 필요한가?
```

**예제 설명**

이 시나리오는 장애 복구 중 가장 시간이 급한 순간에 발생한다. `DROP TABLE`
자체가 §1에 따라 DDL이므로 슬레이브에도 전파될 텐데, 그렇다면 이 짧은 순간
orders를 참조하는 다른 복제 테이블의 FK(§5)는 일시적으로 참조 대상이 없는
상태가 된다. 이어지는 `loaddb`가 HA 운영 중에 허용되는 명령인지조차 스펙에
없으므로(§8의 예시는 전부 싱글 모드), 운영자는 이 복구 작업을 위해 일시적으로
HA를 내려야 하는지, 아니면 마스터에서 바로 실행해도 되는지 매뉴얼만으로는
판단할 수 없다. 새벽 장애 대응 중 이런 불확실성은 복구 시간(RTO)을 직접
늘리는 요인이다.

**제안**

§8에 "HA 운영 중 단일 테이블 부분 복원" 절차를 별도로 추가하고, DROP TABLE →
loaddb 과정에서 FK 참조 무결성 검증 시점, RK 재할당 규칙, 슬레이브 복제 재개
방식(자동 재동기화 여부)을 명시해야 한다. 최소한 "HA 운영 중 loaddb는 지원하지
않으며 반드시 싱글 모드로 전환 후 수행해야 한다"는 제약이라도 명확히 선언해야
한다.

## 조사 종료 선언

이번 2차 라운드는 스펙이 명시적으로 다루는 절차(§1~§9 본문)를 벗어나 **스펙이
침묵하는 주변 도구·객체와의 상호작용**을 중심으로 팠다 — 물리 백업/PITR,
백업 수행 위치, 권한·감사, 파티션, 인덱스 생성 문법, 벌크 적재 도구, TDE, 로그
