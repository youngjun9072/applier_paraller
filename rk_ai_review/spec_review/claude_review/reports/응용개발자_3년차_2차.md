# CUBRID HA 복제 개선 스펙 리뷰 — DB 사용 개발자(응용 개발) 3년차 관점 · 2차 라운드

## 2차 라운드 개요

1차 리포트와 이를 종합한 최종보고서가 이미 다룬 RK 비결정성, FK 부모 사후 OFF 전환, RK 조회 불가,
§7 파일 리스트 미정의, §8/§9 기본값 모순, trailing comma, fail-late 구조, 다중 절 ALTER 원자성,
업그레이드 경로 부재 등은 그 변주까지 포함해 모두 제외했다. 대신 이번 라운드에서는 스펙이 완전히
침묵하고 있는 **다른 DB 객체·인프라 요소와의 상호작용**(파티셔닝, TDE 암호화, COLLATE, 복합
UNIQUE의 부분 NULL 허용, REPLICATION DDL의 권한 모델)과, 응용 개발자가 실제로 부딪히는
**배포 자동화·테스트 환경 구성 관점의 사각지대**(무중단 스키마 변경 패턴, 다중 문장 배치 실행 중
부분 실패, 카탈로그 스키마 변경에 따른 도구 호환성, CI/서버 버전 스큐)를 위주로 훑었다.

10건 모두 최종보고서의 통합 이슈(C-1~C-9, M-1~M-10)와 겹치지 않는 새 실패 모드로 판단했다.
개수를 채우기 위한 사소한 트집이나 이미 지적된 논점의 재포장은 배제했다.

## 리뷰 21

**[심각도: 중요] 파티션 테이블에서 UK의 유일성 범위(테이블 전체 vs 파티션 로컬)가 정의되지 않아 RK 무결성 전제가 흔들릴 수 있다**

**대상**: §1(RK 정의), §4(HA 제약사항 — 파티션 관련 DDL 자체가 언급되지 않음)

**문제 설명**: 파티셔닝(테이블을 특정 컬럼 값 범위·해시 기준으로 여러 물리적 조각으로 나눠 저장하는 기능)된 테이블에서는, DB 엔진에 따라 UNIQUE 제약이 "테이블 전체를 통틀어" 유일함을 보장하는 경우도 있고, "각 파티션 내부에서만" 유일함을 보장하는 경우도 있다(예를 들어 일부 DB는 파티션 키가 UNIQUE 제약에 포함되지 않으면 전역 유일성 검사 자체가 불가능해 파티션 키를 반드시 UNIQUE에 포함하도록 강제한다). 이 스펙은 파티션 테이블을 한 번도 언급하지 않으면서 RK 후보(PK/UK)의 유일성 범위를 "테이블 전체"라고 전제하고 있다. 만약 CUBRID의 파티션 테이블에서 UK가 파티션 로컬 유일성만 보장한다면, 서로 다른 파티션에 같은 RK 값을 가진 행이 동시에 존재할 수 있어 "RK 값으로 슬레이브에서 갱신 대상 행을 하나로 특정한다"는 복제의 근본 전제가 깨진다.

**구체 예제**:
```sql
-- region_id 기준으로 범위 파티셔닝된 주문 테이블
CREATE TABLE orders_part(
    region_id INT NOT NULL,
    order_no  INT NOT NULL UNIQUE,   -- 파티션 키(region_id)를 포함하지 않는 UK
    amount    INT
) PARTITION BY RANGE (region_id) (
    PARTITION p_kr VALUES LESS THAN (100),
    PARTITION p_us VALUES LESS THAN (200)
);

-- 만약 UNIQUE(order_no)가 파티션별로만 검사된다면
INSERT INTO orders_part VALUES (10, 5001, 100);   -- p_kr 파티션에 저장
INSERT INTO orders_part VALUES (150, 5001, 200);  -- p_us 파티션에도 order_no=5001 저장 가능?
-- 두 행 모두 성공한다면, order_no(=RK 후보)만으로는 두 행을 구분할 수 없다.
-- 복제 로그에 "order_no=5001인 행을 UPDATE하라"는 명령이 오면 슬레이브는 어느 파티션의
-- 행을 갱신해야 하는지 알 수 없다.
```

**예제 설명**: 파티셔닝은 대용량 이력·로그성 테이블에서 응용팀이 조회 성능·보관 주기 관리를 위해 흔히 도입하는 기법이다. 이 스펙이 파티션 테이블을 전혀 다루지 않는다는 것은, 파티셔닝을 쓰는 팀이 RK 규칙을 어떻게 적용해야 할지 스스로 알아내야 한다는 뜻이다. 최악의 경우 "UK가 있으니 RK 후보가 되어 HA 전환이 통과된다"고 안심했다가, 실제로는 파티션 간 중복 값 때문에 복제가 잘못된 행을 갱신하는 조용한 데이터 오염이 발생할 수 있다.

**제안**: 파티션 테이블에 대한 RK 후보 규칙을 별도 절로 명시한다. "파티션 테이블의 UK/PK는 반드시 파티션 키를 포함해 테이블 전체에 걸친 유일성을 보장해야 RK 후보가 될 수 있다"는 원칙을 §1에 추가하고, 파티션 키가 빠진 UK를 가진 테이블이 HA로 전환될 때 §7 검사에서 이를 별도로 식별해 경고하도록 한다.

## 리뷰 22

**[심각도: 중요] 무중단 스키마 변경(shadow table + rename) 패턴에서 REPLICATION/RK가 그대로 이어지는지, 복제 부하가 이중으로 발생하는지 불명이다**

**대상**: §2-1, §2-2, §4 전체

**문제 설명**: 대용량 테이블에 컬럼 추가나 인덱스 재구성을 다운타임 없이 수행하기 위해, 전용 온라인 DDL 도구가 없는 환경의 응용팀은 "새 스키마로 shadow(그림자) 테이블을 만들고, 백그라운드에서 데이터를 복사한 뒤, 이름을 맞바꾸는(rename swap)" 절차를 직접 구현해 쓰는 경우가 많다. 이 절차를 REPLICATION=ON 테이블에 적용하면 세 가지가 불명확해진다. 첫째, shadow 테이블은 새로 `CREATE TABLE`되므로 기본값에 따라 REPLICATION=ON으로 생성되는데, 그러면 데이터 복사 단계의 대량 INSERT 자체가 복제 스트림에 실려, 원본 테이블에 대한 정상 트래픽 복제와 별도로 이중 부하가 걸리는 것 아닌가. 둘째, `RENAME TABLE`로 이름을 맞바꾼 뒤 슬레이브 입장에서 이것이 "기존 테이블 삭제 + 새 테이블 생성"으로 보이는지, 아니면 매끄럽게 컬럼만 바뀐 연속된 테이블로 보이는지. 셋째, 스왑 전후로 RK가 동일한 논리적 컬럼을 계속 가리키는 것이 보장되는지가 스펙에 전혀 없다.

**구체 예제**:
```sql
-- orders 테이블에 컬럼을 추가하되 잠금 시간을 최소화하려는 시도
CREATE TABLE orders_new(
    order_id   INT PRIMARY KEY,
    customer_id INT,
    status     VARCHAR(20),
    priority   INT DEFAULT 0        -- 새로 추가하려는 컬럼
);  -- REPLICATION 옵션 생략 → 기본값 ON으로 생성

-- 대량 백필 (수백만 건)
INSERT INTO orders_new (order_id, customer_id, status)
    SELECT order_id, customer_id, status FROM orders;
-- 이 INSERT가 REPLICATION=ON인 orders_new에 대해 그대로 슬레이브로 복제된다면,
-- 원본 orders 테이블에 대한 실시간 DML 복제와 동시에 수백만 건짜리 복제가 겹쳐 부하가 급증한다.

RENAME TABLE orders TO orders_old, orders_new TO orders;
-- 스왑 이후 슬레이브의 "orders"는 새 물리 테이블인데,
-- 이것이 복제 연속성을 유지한 채 이어지는지, RK가 재계산되는지 불명.
```

**예제 설명**: 이 패턴은 온라인 스키마 변경 도구(gh-ost, pt-online-schema-change류)가 없는 CUBRID 환경에서 응용팀이 실제로 손수 구현할 가능성이 높은 절차다. 스펙이 이를 다루지 않으면, 각 팀이 서로 다른 가정으로 절차를 설계하다가 일부는 복제 폭주로 슬레이브 지연을 유발하고, 일부는 스왑 이후 RK 불일치로 데이터 정합성 사고를 낼 수 있다.

**제안**: `RENAME TABLE`의 복제 시맨틱(구 테이블명으로 슬레이브에 쌓인 데이터의 운명, 새 이름에 대한 RK 재계산 여부)을 명시한다. 대량 백필을 복제 부하 없이 수행할 수 있는 권장 절차(예: 백필 단계에서는 REPLICATION=OFF로 생성했다가 스왑 직전에만 ON으로 바꾸는 방법이 가능한지, 가능하지 않다면 대안)를 별도 가이드로 문서화한다.

## 리뷰 23

**[심각도: 중요] REPLICATION 옵션을 다루는 DDL에 필요한 권한(privilege) 모델이 정의되어 있지 않다**

**대상**: §2-1, §2-2 전체

**문제 설명**: 많은 조직은 배포 자동화 도구(Flyway, Liquibase 등)를 DBA 계정이 아니라 최소 권한만 가진 애플리케이션 서비스 계정으로 실행한다. 이 스펙은 `REPLICATION={ON|OFF}` 옵션이 붙은 CREATE/ALTER TABLE을 실행하는 데 어떤 권한이 필요한지 전혀 언급하지 않는다. REPLICATION 옵션은 개별 테이블의 컬럼 구조가 아니라 클러스터 전체의 마스터-슬레이브 데이터 정합성에 영향을 미치는, 일반 컬럼 추가보다 운영 성격이 강한 설정이다. 그런데도 일반 테이블 소유자 권한만으로 자유롭게 바꿀 수 있다면 위험 반경이 넓고, 반대로 DBA 권한을 별도로 요구한다면 자동화 파이프라인이 매번 사람 승인을 거쳐야 해 "배포 자동화"라는 목표 자체가 흔들린다.

**구체 예제**:
```sql
-- app_deploy 계정: orders 테이블의 소유자이지만 DBA 권한은 없음
-- CI/CD 파이프라인이 이 계정으로 마이그레이션을 실행

csql> ALTER TABLE orders REPLICATION=OFF;
-- (A) 소유자 권한만으로 통과한다면:
--     실수로 이 한 줄이 포함된 마이그레이션이 리뷰 없이 병합되어도 즉시 반영되어,
--     한 팀의 실수가 전사 HA 복제 정합성에 영향을 준다.
-- (B) DBA 권한이 필요해 거부된다면:
--     이 마이그레이션 파일 하나 때문에 매번 DBA를 호출해 수동 실행해야 하고,
--     CI/CD 파이프라인은 이 한 줄만 걸러내는 예외 처리를 별도로 만들어야 한다.
-- 스펙에는 (A)/(B) 중 무엇인지, 혹은 제3의 권한 체계가 있는지 언급이 없다.
```

**예제 설명**: 응용 개발자가 마이그레이션 도구로 배포 파이프라인을 설계할 때, "이 DDL 종류는 누가 실행할 수 있는가"는 파이프라인 구조(승인 단계 삽입 여부, 계정 분리 여부)를 결정하는 핵심 정보다. 이 정보가 없으면 조직마다 임의로 가정하고 설계하게 되어, 어떤 곳은 과도하게 열려 있고 어떤 곳은 과도하게 막혀 배포 지연을 겪는다.

**제안**: REPLICATION 옵션 변경에 필요한 최소 권한 수준을 명시한다(예: 테이블 소유자 + ALTER 권한으로 충분한지). 더 엄격한 통제가 필요한 조직을 위해서는 별도의 세분화된 권한(`GRANT REPLICATION_CONTROL ON tbl TO role` 류)을 선택적으로 도입하는 방안을 검토한다.

## 리뷰 24

**[심각도: 보통] 복합 UNIQUE 키에서 일부 컬럼만 NOT NULL이고 나머지는 NULL을 허용하는 경우, 이 UK 전체가 RK 후보 자격을 얻는지 불명이다**

**대상**: §1 "Not Null Unique Key(UK)"

**문제 설명**: 스펙은 "NOT NULL UNIQUE"라는 조합만 언급할 뿐, 두 개 이상의 컬럼으로 이루어진 복합(composite) UNIQUE 제약에서 이 요건을 어떻게 적용하는지는 규정하지 않는다. 즉 "구성 컬럼 전부가 NOT NULL이어야 하는지"와 "구성 컬럼 중 하나라도 NOT NULL이면 충분한지"가 구분되어 있지 않다. 표준 SQL의 일반적인 UNIQUE 제약 동작에서는, 여러 컬럼으로 이루어진 UNIQUE 제약이라도 그 중 한 컬럼이라도 NULL 허용이면 그 컬럼 값이 NULL인 조합은 여러 번 등장할 수 있다(NULL은 서로 다른 값으로 취급되는 경우가 흔하다). 이런 UK는 "모든 행을 하나로 식별한다"는 RK의 목적에 부합하지 않을 수 있다.

**구체 예제**:
```sql
CREATE TABLE inventory(
    warehouse_id INT NOT NULL,
    sku          VARCHAR(30),          -- NULL 허용
    qty          INT,
    CONSTRAINT uk_inv UNIQUE (warehouse_id, sku)
);
-- warehouse_id는 NOT NULL이지만 sku는 NULL 허용.
-- 표준적인 UNIQUE 동작이라면 sku가 NULL인 행은 warehouse_id 값이 같아도 여러 개 존재 가능.

INSERT INTO inventory VALUES (1, NULL, 10);
INSERT INTO inventory VALUES (1, NULL, 20);   -- uk_inv 위반 없이 두 번째 행도 들어갈 수 있는가?
-- 만약 두 INSERT가 모두 성공한다면, uk_inv를 RK로 선택했을 때
-- 두 행이 복제 로그에서 서로 구분되지 않는다.
```

**예제 설명**: 응용 개발자는 "복합 UNIQUE에 NOT NULL이 하나라도 붙어 있으니 스펙의 RK 후보 요건(NOT NULL UNIQUE)을 충족한다"고 오판하기 쉽다. HA 전환 시점에 이 판단이 잘못됐음이 드러나거나(예시10과 같은 형태의 에러), 더 나쁜 경우 아예 걸러지지 않고 통과되어 조용한 데이터 오염으로 이어질 수 있다.

**제안**: §1에 "복합 UK가 RK 후보가 되려면 구성 컬럼 전부가 NOT NULL이어야 한다"는 규칙을 명시적으로 추가하고, §7의 HA 전환 검사도 이 기준으로 판정하도록 한다.

## 리뷰 25

**[심각도: 보통] TDE로 암호화된 컬럼이 RK로 선택될 때, 복제 로그에 실리는 RK 값의 상태와 마스터-슬레이브 간 키 관리 방식이 불명이다**

**대상**: 예시 9(db_class의 `tde_algorithm` 컬럼 노출), §1

**문제 설명**: 예시 9의 `db_class` 조회 결과에 `tde_algorithm: NONE`이라는 컬럼이 등장하는 것으로 보아, CUBRID는 테이블(또는 컬럼) 단위의 투명 데이터 암호화(TDE: Transparent Data Encryption, 저장된 데이터를 디스크 레벨에서 암호화해 파일이 유출돼도 내용을 알 수 없게 하는 기능)를 지원한다. 개인정보보호 규정 때문에 응용팀은 이메일, 전화번호 같은 컬럼에 UNIQUE 제약과 TDE 암호화를 동시에 걸어두는 경우가 드물지 않다. 이런 컬럼이 PK 없이 RK 후보(UK)로 선택되는 상황에서, 복제 로그에 실리는 RK 값이 암호화된 바이트열인지 마스터가 복호화한 평문인지, 그리고 마스터와 슬레이브가 서로 다른 TDE 마스터 키를 사용하는 구성이라면 슬레이브가 이 값을 올바르게 비교해 대상 행을 찾을 수 있는지가 스펙에 없다.

**구체 예제**:
```sql
CREATE TABLE customers(
    customer_id INT,
    ssn VARCHAR(20) NOT NULL UNIQUE   -- TDE로 암호화하려는 개인정보 컬럼, PK 없음
);
-- ssn이 유일한 RK 후보라면 RK = ssn(UK)이 된다.
-- 복제 로그에 담기는 "ssn = ?" 형태의 식별 조건이
--  (a) 마스터가 암호화한 바이트열 그대로인지,
--  (b) 마스터가 복호화한 평문인지에 따라
-- 슬레이브가 서로 다른 TDE 키를 쓰는 구성(노드별 키 로테이션 정책이 다른 경우 등)에서
-- 결과가 달라질 수 있는데, 이에 대한 설명이 전혀 없다.
```

**예제 설명**: 이 문제는 "RK로 어떤 컬럼이 선택되는가"라는 스펙의 핵심 주제가 TDE라는 이미 존재하는 CUBRID 기능과 처음으로 맞물리는 지점인데, 두 기능의 상호작용이 스펙 어디에도 검토되어 있지 않다. 규제 산업(금융, 의료)의 스키마를 다루는 응용팀에게는 이 공백이 실제 채택 여부를 좌우할 수 있다.

**제안**: TDE 암호화 컬럼이 RK 후보가 될 수 있는지 여부를 명시한다(허용하지 않거나, 허용한다면 마스터-슬레이브 간 키 공유 요건을 규정한다). 최소한 §1이나 부록에 TDE와 RK의 상호작용 원칙을 한 문단 추가한다.

## 리뷰 26

**[심각도: 보통] COLLATE 변경이 사후에 기존 UK(RK)의 "논리적 유일성" 전제를 깨뜨릴 수 있는 경로가 §4-2의 제약 목록에 없다**

**대상**: 예시 8(`show create table` 출력의 `COLLATE utf8_bin` 노출), §4-2

**문제 설명**: 예시 8의 결과에 `COLLATE utf8_bin`이 등장하는 데서 알 수 있듯, CUBRID는 문자열 컬럼에 collation(문자열 비교·정렬 규칙, 예를 들어 대소문자를 구분할지 여부)을 지정할 수 있다. VARCHAR 컬럼에 UNIQUE 제약이 걸려 있고 이 컬럼이 RK로 쓰이는 상황에서 `ALTER TABLE ... MODIFY ... COLLATE`로 대소문자를 구분하지 않는 collation으로 바꾸면, 바뀌는 시점에 이미 저장돼 있던 데이터 중 예전 collation에서는 서로 다른 값으로 UNIQUE를 통과했던 값들이 새 collation 기준으로는 논리적으로 같은 값이 될 수 있다. §4-2는 제약 추가·삭제·컬럼 삭제만 다룰 뿐, "제약 자체는 그대로 두고 값 비교 규칙만 바꾸는" 이런 DDL이 RK의 유일성 전제에 미치는 영향은 전혀 언급하지 않는다.

**구체 예제**:
```sql
CREATE TABLE members(
    code VARCHAR(10) NOT NULL UNIQUE     -- RK 후보(PK 없음). 기본 COLLATE utf8_bin(대소문자 구분)
);
-- 기존 데이터: 'ABC'와 'abc'가 서로 다른 값으로 이미 저장되어 있음(bin collation에서는 다른 값)

ALTER TABLE members MODIFY code VARCHAR(10) COLLATE utf8_en_ci;  -- 대소문자 무시로 변경
-- 이 시점부터 'ABC'와 'abc'는 논리적으로 "같은 키"가 되었지만
-- 기존 두 행은 그대로 남아 있다. code가 RK라면,
-- 슬레이브가 이후 "code='abc'" 조건의 복제 로그를 받았을 때
-- 원래 'ABC'였던 행과 'abc'였던 행 중 어느 쪽을 대상으로 삼아야 하는지 모호해진다.
```

**예제 설명**: collation 변경은 다국어 지원 추가나 검색 요구사항 변화에 따라 응용팀이 실제로 수행하는 스키마 변경이다. RK로 쓰이는 컬럼에 이런 변경을 가하는 것이 "제약을 건드리지 않았으니 안전하다"는 §4-2의 표현만으로는 안전하지 않을 수 있는데, 스펙은 이 경계를 다루지 않는다.

**제안**: RK로 사용 중인 컬럼의 COLLATE 변경을 §4-2의 "복제키 수정 제한" 대상에 명시적으로 포함시키거나, 최소한 COLLATE 변경 시 새 collation 기준으로 기존 데이터의 중복 여부를 재검사하도록 규정한다.

## 리뷰 27

**[심각도: 사소] 싱글/개발 모드에서 REPLICATION 옵션이 완전히 무효과(no-op)라는 사실이 명시되지 않아, 실수로 넣은 설정이 검증 없이 운영까지 전파될 수 있다**

**대상**: §3

**문제 설명**: §3은 "REPLICATION 옵션 사용은 싱글 모드에서도 가능하다"고만 말할 뿐, 싱글 모드에서 이 옵션이 카탈로그에 값은 저장되지만 런타임 동작에는 아무 영향도 주지 않는(HA가 아예 없으니 복제할 대상 자체가 없는) 순수 메타데이터라는 점을 명시적으로 언급하지 않는다. 개발 DB와 CI가 항상 싱글 모드로 도는 조직에서는, 누군가 오래된 예제를 그대로 복사하다가 실수로 `REPLICATION=OFF`가 붙은 CREATE TABLE 스크립트를 커밋해도 개발 환경에서는 아무 이상 징후가 나타나지 않는다.

**구체 예제**:
```sql
-- 로컬 개발(싱글 모드): 예전 예제를 복붙하다가 실수로 OFF가 딸려 옴
CREATE TABLE promotions(
    promo_id INT PRIMARY KEY,
    name VARCHAR(50)
) REPLICATION=OFF;
-- 싱글 모드라 이 옵션의 존재 자체가 개발자에게 아무런 신호를 주지 않는다.
-- 코드 리뷰에서도 "왜 이 테이블만 OFF인지" 묻지 않으면 그대로 통과된다.

-- 이 마이그레이션이 그대로 운영 HA에 반영됨.
-- promo_id에 PK가 있어 RK도 존재하므로 §4·§5·§7 어느 검사에도 걸리지 않는다.
-- 결과: promotions는 마스터에서만 갱신되고 슬레이브에는 영원히 비어 있다가,
-- 몇 달 뒤 failover 이후 "프로모션 목록이 텅 비었다"는 장애로 처음 발견된다.
```

**예제 설명**: RK 유무 위반은 에러로 걸러지지만, "의도치 않은 REPLICATION=OFF"는 문법적으로나 제약상으로나 완전히 유효한 상태라 아무 도구도 걸러주지 않는다. 이 사고는 스펙의 규칙을 어긴 게 아니라 정확히 규칙대로 동작한 결과이기 때문에 더 찾기 어렵다.

**제안**: 문서에 "REPLICATION 옵션은 싱글/SA 모드에서 문법적으로 허용되나 런타임에는 효과가 없으며 값만 카탈로그에 저장된다"는 문장을 명시한다. 아울러 신규 REPLICATION=OFF 테이블이 포함된 마이그레이션을 배포 전에 눈에 띄게 표시하는 CI 린트 규칙을 권장 관행으로 제시한다.

## 리뷰 28

**[심각도: 보통] 여러 DDL 문장으로 이루어진 스크립트/배치 실행 중 한 문장이 RK 위반으로 실패하면, 이미 실행된 앞선 문장들의 처리 상태와 이후 실행 여부가 불명이다 (단일 ALTER 문 내부 절의 원자성과는 다른 층위)**

**대상**: §4-2(예시 7, 13은 "하나의 ALTER TABLE 문 안에 콤마로 묶인 여러 절"만 다룸), 스크립트/배치 단위 언급 부재

**문제 설명**: 예시 7·13이 다루는 원자성은 "한 ALTER TABLE 문 안에 있는 여러 절"에 국한된다. 그런데 실무 마이그레이션 파일은 보통 서로 다른 DDL "문장" 여러 개를 세미콜론으로 이어 하나의 파일로 만들고, JDBC의 배치 실행이나 csql 스크립트 실행기, Flyway/Liquibase의 changeSet을 통해 순차 실행한다. 이 경우 세 번째 문장이 RK 위반으로 실패했을 때, 앞서 성공한 문장들의 변경이 그대로 남는지, 이후 문장이 계속 실행되는지는 이 스펙의 범위(하나의 문장 내부) 밖이라 다뤄지지 않는다.

**구체 예제**:
```sql
-- 하나의 마이그레이션 파일(V15__refactor_orders_key.sql)에 여러 DDL을 순서대로 나열
ALTER TABLE orders ADD COLUMN order_uuid CHAR(36);
ALTER TABLE orders ADD CONSTRAINT UNIQUE (order_uuid);   -- (1) 성공, 새 RK 후보 추가
ALTER TABLE orders DROP CONSTRAINT PRIMARY KEY;          -- (2) 성공, order_uuid의 UK가 RK로 승격
ALTER TABLE orders DROP COLUMN order_id;                 -- (3) 실패: 다른 곳에서 FK로 참조 중이라 등

-- Flyway는 이 changeSet 전체를 "실패"로 기록하지만,
-- 실제 DB에는 (1), (2)가 이미 반영되어 order_uuid가 새 RK로 바뀐 상태로 남는다.
-- 다음 배포에서 이 파일을 그대로 재시도하면 (1), (2)가 "이미 존재한다"는 에러로 다시 실패하고,
-- Flyway/Liquibase의 표준 복구 절차("실패한 changeSet을 정정 후 재실행")가 꼬인다.
```

**예제 설명**: 배포 자동화 도구는 "changeSet 하나 = 전부 성공 또는 전부 실패"라는 원자성을 전제로 이력을 관리한다. 이 스펙이 여러 DDL 문장에 걸친 부분 실패 처리를 명시하지 않으면, 도구가 기록하는 상태(실패)와 실제 DB 상태(일부 반영됨)가 어긋나는, 마이그레이션 이력 관리에서 가장 다루기 까다로운 종류의 불일치가 발생한다.

**제안**: §4-2에 "여러 DDL 문장으로 나뉜 스크립트는 문장 단위로 개별 커밋되며, 실패한 문장 이전의 변경은 롤백되지 않는다"는 원칙을 명시하고, 마이그레이션 도구가 부분 실패를 감지·복구할 수 있도록 이 특성을 운영 가이드에 별도로 안내한다.

## 리뷰 29

**[심각도: 사소] 신규 카탈로그 컬럼(`db_class.replication`) 추가가 `SELECT *` 기반 레거시 조회나 구버전 드라이버의 메타데이터 조회 가정을 깨뜨릴 수 있다**

**대상**: 예시 9(`db_class` 컬럼 목록에 `replication` 신규 추가)

**문제 설명**: 예시 9는 `db_class`에 `replication`이라는 컬럼이 새로 추가된 결과를 보여준다. 권장되는 방식은 아니지만, 오래된 사내 스크립트나 DB 익스플로러 도구 중에는 `SELECT * FROM db_class`처럼 전체 컬럼을 조회한 뒤 결과를 컬럼명이 아니라 순번(인덱스)으로 접근하는 코드가 남아 있는 경우가 실무에서 드물지 않다. 이런 코드는 새 컬럼이 기존 컬럼 목록 중간에 끼어들면 그 뒤 컬럼들의 순번이 밀려 오동작할 수 있는데, 이 스펙에는 새 컬럼이 어느 위치에 추가되는지(항상 끝에 append되는지) 언급이 없다.

**구체 예제**:
```sql
-- 레거시 사내 스크립트가 컬럼명이 아니라 순번으로 값을 꺼낸다고 가정
SELECT * FROM db_class WHERE class_name = 'orders';
-- 신버전에서 replication 컬럼이 owner_name과 class_type 사이 같은 중간 위치에 추가된다면,
-- 이후 컬럼(comment 등)을 읽던 로직이 하나씩 밀린 값을 읽게 되어
-- 화면에 엉뚱한 정보가 표시되거나 조건문이 잘못된 값을 비교하게 된다.
```

**예제 설명**: 카탈로그 스키마 변경은 서버 업그레이드마다 늘 존재할 수 있는 위험이지만, 이번처럼 사용자에게 새로 노출되는 컬럼이 생기는 변경은 특히 레거시 코드의 암묵적 가정을 건드릴 가능성이 크다. 스펙에 위치 보장이 없으면 이 위험을 사전에 점검할 근거가 없다.

**제안**: 신규 카탈로그 컬럼은 항상 기존 컬럼 목록의 끝에 추가됨을 명시하고, 릴리스 노트에 "`SELECT *` 대신 명시적 컬럼 나열을 사용하라"는 권고를 포함한다.

## 리뷰 30

**[심각도: 보통] REPLICATION 신규 문법을 지원하지 않는 구버전 엔진과의 버전 스큐를 감지할 표준 방법이 없어, 마이그레이션 실패의 원인을 오판하기 쉽다**

**대상**: §2 전체(신규 문법 도입에 따른 버전 호환성 안내 부재)

**문제 설명**: 새 SQL 문법(`REPLICATION={ON|OFF}`)이 도입되면, 이를 지원하지 않는 이전 버전 서버는 이 구문을 파싱하지 못해 일반적인 문법 오류로 실패한다. 많은 조직에서 CI/스테이징 환경의 DB 엔진 버전(예: 고정된 Docker 이미지 태그)이 프로덕션보다 뒤처져 있는 경우가 흔하다. 이 스펙에는 이 문법이 도입된 최소 버전이 무엇인지, 구버전 서버가 이 문법을 만났을 때의 에러가 일반 문법 오류와 구분되는지, 애플리케이션이 사전에 버전 지원 여부를 조회할 표준 방법이 있는지에 대한 언급이 전혀 없다.

**구체 예제**:
```bash
# CI 파이프라인의 docker-compose.yml에 오래전부터 고정된 CUBRID 이미지 태그
image: cubrid/cubrid:11.2   # REPLICATION 옵션 도입 이전 버전이라고 가정

# 마이그레이션 스크립트는 최신 문법을 사용
ALTER TABLE orders REPLICATION=OFF;
```
```
CI 로그: ERROR: syntax error near 'REPLICATION'
```
개발자는 이 메시지만 보고 "SQL을 잘못 썼나?"부터 의심하며 시간을 쓰다가, 한참 뒤에야 CI 이미지 자체가 이 기능이 추가되기 전 버전이었음을 깨닫는다.

**예제 설명**: 새 예약어/옵션 도입은 항상 이런 버전 스큐 문제를 동반하는데, 에러 메시지가 일반 문법 오류와 구분되지 않으면 원인 파악에 불필요한 시간이 든다. 이는 다수의 서비스가 동일 CUBRID 클러스터를 서로 다른 배포 주기로 쓰는 조직에서 반복적으로 발생할 수 있는 마찰이다.

**제안**: 이 옵션이 도입된 최소 버전을 릴리스 노트와 스펙 문서에 명시하고, 가능하다면 구버전 서버가 이 신규 키워드를 만났을 때 "현재 서버 버전이 이 옵션을 지원하지 않습니다"처럼 버전 관련임을 알 수 있는 에러 메시지를 제공하도록 권고한다.

## 조사 종료 선언

이번 2차 라운드에서는 §3(싱글 제약), §6(뷰)과의 재비교, §8 세부 절차, 파티션·시리얼·소유자
권한·TDE·collation·REUSE_OID 등 스펙이 침묵하는 객체와의 상호작용, 에러 코드 체계, 성능/락,
멀티 슬레이브, 용어 일관성 영역을 응용 개발자(ORM/마이그레이션 도구, dev/prod parity, FK 설계,
DDL 배포 자동화, 커넥션/드라이버, 테스트 환경 구성) 관점에서 훑었다. 그 결과 10건은 최종보고서의
40개 통합 이슈와 명확히 구분되는 새 실패 모드로 확인했으나, 이 이상으로는 다음 두 가지 이유로
추가 조사의 한계효용이 낮다고 판단했다.

1. 트리거·SERIAL/AUTO_INCREMENT·REUSE_OID·다단계 FK·복합키 RK 성능 등 나머지 미개척 영역은
   최종보고서의 "직군별 관점 요약" 절에서 이미 엔진 개발자 직군의 고유 지적으로 계통이 잡혀 있어,
   같은 항목을 응용 개발자 관점으로 다시 써도 관찰 대상(엔진 내부 동작)이 같아 실질적으로 변주에
   그친다.
2. 남은 항목들(§9 요약 문장 재검토, 오탈자, 표기 혼용 등)은 이미 1차 리포트와 최종보고서에서
   사소/보통 등급으로 충분히 다뤄졌고, 이를 다른 SQL 예제로 바꿔 다시 제출하는 것은 지시사항이
   금지한 "재탕·변주"에 해당한다.

따라서 30개를 채우기보다 10개의 확실히 새로운 지적으로 마무리한다.
