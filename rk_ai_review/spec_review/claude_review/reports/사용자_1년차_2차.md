# CUBRID HA 복제 개선 스펙 리뷰 — 사용자(최종 사용자) · 1년차 · 2차 라운드

## 2차 라운드 개요

1차에서는 스펙 본문(§1~§9)을 순서대로 읽으며 예제 문법 오류, 용어 정의 공백, 절 사이의 모순을 주로 짚었습니다. 2차에서는 1차와 최종보고서가 이미 다룬 지점(RK 비결정성, FK 부모 사후 OFF 전환, RK 조회 불가, §7 파일 리스트, §8/§9 모순, trailing comma, 다중 절 ALTER 원자성, 업그레이드 경로 부재 등)을 피하고, 스펙이 아예 침묵하고 있는 객체·상황 — CTAS/LIKE, 권한, 파티션, TDE, 트랜잭션 원자성, RK 재배정 이벤트, 표기 규칙 — 을 1년차 실무자가 실제로 마주칠 법한 순서로 훑었습니다. 개수를 채우는 것보다 실제로 "이 문서만 보고 작업하다가 막히는 지점"인지를 기준으로 추렸습니다.

## 리뷰 21

**[심각도: 중요] CREATE TABLE ... AS SELECT(CTAS)와 CREATE TABLE ... LIKE 에서 REPLICATION 옵션이 어떻게 정해지는지 스펙이 전혀 말하지 않는다**

**대상**: §2-1 (CREATE TABLE 옵션 추가) 전체

**문제 설명**: §2-1은 REPLICATION 옵션의 기본값 규칙("생략시 ON으로 자동 생성")을 오직 컬럼을 직접 나열하는 일반 `CREATE TABLE(...)` 형태로만 설명합니다. 그런데 실무에서 테이블을 복제하는 또 다른 흔한 방법으로 기존 테이블 구조를 그대로 복사하는 `CREATE TABLE ... LIKE`나, 조회 결과로 새 테이블을 만드는 `CREATE TABLE ... AS SELECT`(흔히 CTAS라고 부릅니다)가 있습니다. 이 두 방식으로 만든 새 테이블의 REPLICATION 값이 (a) 원본 테이블의 값을 그대로 물려받는지, (b) 옵션이 생략된 것으로 취급되어 무조건 기본값 ON이 되는지 스펙 어디에도 언급이 없습니다. 원본이 REPLICATION=OFF인 테이블을 복사했는데 새 테이블이 조용히 ON으로 생성된다면, 1차 리뷰 3/17이 지적한 "FK 부모가 나중에 OFF로 바뀌는" 문제와는 반대 방향으로, 사용자가 의도적으로 제외했던 테이블의 "사본"이 의도치 않게 복제 대상이 되어버리는 상황이 생깁니다.

**구체 예제(SQL)**:
```sql
-- 원본: 로그성 테이블이라 의도적으로 복제 제외
csql> CREATE TABLE access_log(
    id INT PRIMARY KEY,
    msg VARCHAR(200)
) REPLICATION=OFF;

-- 1) 구조만 복사 (LIKE)
csql> CREATE TABLE access_log_bak LIKE access_log;

-- 2) 데이터까지 복사 (CTAS)
csql> CREATE TABLE access_log_2026 AS SELECT * FROM access_log;

-- 질문: access_log_bak, access_log_2026 은 REPLICATION=OFF를 물려받는가,
-- 아니면 옵션을 안 썼으니 §2-1 기본값 규칙대로 ON이 되는가?
-- 스펙은 "REPLICATION 옵션을 생략하면 ON"이라고만 했지,
-- "무엇을 기준으로 생략 여부를 판단하는지"(LIKE/CTAS 포함 여부)를 정의하지 않았다.
```

**예제 설명**: LIKE와 CTAS는 스키마 마이그레이션 도구나 백업 스크립트, 혹은 단순히 "테스트용으로 원본과 똑같은 테이블 하나 더 만들자"는 실무자가 매일 쓰는 명령입니다. 이 경로에서 REPLICATION 값이 무엇으로 정해지는지 스펙에 없으므로, 사용자는 매번 실제로 만들어보고 `show create table`로 확인해야만 알 수 있습니다.

**제안**: §2-1에 "LIKE/CTAS로 생성된 테이블의 REPLICATION 값은 원본을 상속하는지, 옵션 생략으로 간주해 기본값(ON)을 적용하는지"를 명시하는 한 문단을 추가해야 합니다.

## 리뷰 22

**[심각도: 중요] ALTER TABLE ... REPLICATION 을 실행할 수 있는 권한이 누구에게 있는지 스펙에 전혀 없다**

**대상**: §2-2 전체

**문제 설명**: `REPLICATION={ON|OFF}`는 테이블 단위로 마스터-슬레이브 데이터 일치 여부를 결정하는, 사실상 "이 테이블은 장애 시 데이터가 사라져도 책임지지 않는다"는 선언에 가까운 옵션입니다(§1의 면책 문구 참고). 그런데 이 값을 바꾸는 `ALTER TABLE ... REPLICATION=ON/OFF`를 실행하는 데 특별한 권한(DBA 권한, 또는 테이블 소유자 권한)이 필요한지, 아니면 해당 테이블에 ALTER 권한만 있으면 누구나 실행할 수 있는지가 문서 어디에도 나오지 않습니다. CUBRID는 일반적으로 테이블 소유자나 DBA가 아니어도 부여받은 권한에 따라 ALTER TABLE을 실행할 수 있는데, 만약 REPLICATION 옵션 변경에 별도 권한 체크가 없다면, 여러 명이 같은 DB에 접근하는 조직에서 DBA도 모르는 사이에 중요한 테이블이 REPLICATION=OFF로 바뀌어 있는 상황이 발생할 수 있습니다.

**구체 예제(시나리오)**:
```sql
-- DBA가 아닌 개발 계정 dev_user 로 접속, orders 테이블에 ALTER 권한만 부여받은 상태
csql> ALTER TABLE orders REPLICATION=OFF;

-- 질문: 이 SQL은 성공하는가?
-- 성공한다면, DBA는 이 변경을 무엇으로 알아챌 수 있는가?
--   (권한 체크 규칙도, 변경 시 알림/로그 규칙도 스펙에 없음)
```

**예제 설명**: 1년차 실무자 입장에서 가장 무서운 시나리오는 "내가 실행 권한이 있길래 실행했는데, 그게 이렇게 큰 파급력을 가진 옵션인 줄 몰랐다"는 상황입니다. REPLICATION 옵션은 일반 컬럼 추가/삭제와 달리 장애 상황에서의 데이터 존재 여부를 결정하므로, 최소한 "누가 이 옵션을 바꿀 수 있는가"에 대한 명시적 정책이 필요합니다.

**제안**: §2-2에 "REPLICATION 옵션 변경에 필요한 권한 수준(DBA 전용인지, 테이블 소유자 이상인지)"을 명시하고, 가능하다면 변경 이력이 남는지도 함께 기술해야 합니다.

## 리뷰 23

**[심각도: 중요] 파티션 테이블에 REPLICATION/RK 규칙이 어떻게 적용되는지 스펙이 다루지 않는다**

**대상**: 스펙 전체 (파티션 관련 언급 전무). 참고: 예시 9의 `db_class` 출력에는 `partitioned` 필드가 있어 CUBRID가 파티션 테이블을 지원함을 알 수 있음

**문제 설명**: 예시 9의 카탈로그 조회 결과에는 `partitioned : 'NO'`라는 필드가 replication 필드와 나란히 나옵니다. 즉 CUBRID에는 파티션 테이블이라는 기능이 이미 존재하는데, 스펙 어디에도 "파티션 테이블에 REPLICATION 옵션을 어떻게 지정하는지", "복제 키(RK)가 파티션마다 따로 있는 것인지 아니면 전체 파티션 테이블에 하나만 있는 것인지"를 설명하지 않습니다. 파티션 테이블은 보통 여러 개의 물리적 파티션이 하나의 논리적 테이블처럼 보이는 구조이므로, 파티션별로 REPLICATION을 다르게 줄 수 있는지(예: 오래된 연도 파티션은 OFF, 최근 파티션만 ON), 아니면 파티션 테이블 전체가 하나의 REPLICATION 값을 공유하는지는 사용자가 반드시 알아야 할 정보입니다.

**구체 예제(SQL)**:
```sql
-- 연도별 파티션 테이블 (가정)
csql> CREATE TABLE sales(
    sale_id INT,
    sale_date DATE,
    amount INT,
    PRIMARY KEY(sale_id, sale_date)
) PARTITION BY RANGE (sale_date) (
    PARTITION p2024 VALUES LESS THAN ('2025-01-01'),
    PARTITION p2025 VALUES LESS THAN ('2026-01-01')
);

-- 질문 1: REPLICATION 옵션은 sales 테이블 전체에만 붙일 수 있는가,
--         아니면 PARTITION p2024 REPLICATION=OFF 처럼 파티션 단위로도 가능한가?
-- 질문 2: RK(위 예시에서는 복합 PK sale_id+sale_date)가
--         파티션 간에 항상 동일하게 유지된다는 보장은 스펙 어디서 확인할 수 있는가?
```

**예제 설명**: 파티션 테이블은 데이터량이 많은 테이블에 주로 쓰이고, 이런 테이블일수록 "오래된 데이터는 굳이 슬레이브까지 복제할 필요 없다"는 요구가 실무에서 자주 나옵니다. 그런데 이 요구를 이번 REPLICATION 옵션으로 해결할 수 있는지조차 스펙만 봐서는 판단할 수 없습니다.

**제안**: 파티션 테이블에 대한 REPLICATION/RK 규칙을 최소한 한 문단으로 명시하고("파티션 단위 지정 불가, 테이블 전체 단위로만 적용됨" 등), 지원하지 않는다면 명시적으로 범위 밖(out of scope)이라고 밝혀야 합니다.

## 리뷰 24

**[심각도: 보통] TDE(투명한 데이터 암호화)가 적용된 테이블의 복제 로그도 암호화되는지 언급이 없다**

**대상**: 예시 9의 `db_class` 출력 `tde_algorithm : 'NONE'` 필드와 `replication : ON` 필드가 나란히 나오지만 관계 설명 없음

**문제 설명**: 예시 9는 `tde_algorithm`(TDE: Transparent Data Encryption, 데이터를 디스크에 저장할 때 자동으로 암호화하는 기능의 알고리즘 설정)이라는 필드를 보여주는데, 이 값이 `NONE`이 아니라 실제 암호화 알고리즘으로 설정된 테이블에 REPLICATION=ON을 걸면, 마스터에서 슬레이브로 전송되는 복제 로그 안의 실제 데이터 값도 암호화된 상태로 전달되는지, 아니면 복제 로그 자체는 평문으로 만들어져 전송 구간에서 암호화 정책이 무력화되는지에 대한 설명이 전혀 없습니다. 보안 요구사항 때문에 TDE를 켠 테이블일수록 오히려 이 정보가 더 중요합니다.

**구체 예제(시나리오)**:
```sql
csql> CREATE TABLE customers_secure(
    customer_id INT PRIMARY KEY,
    ssn VARCHAR(20)   -- 주민번호 등 민감정보, TDE로 암호화해서 저장 중이라 가정
) REPLICATION=ON;
-- (TDE 알고리즘 설정은 별도 DDL/설정으로 가정)

-- 질문: 이 테이블이 슬레이브로 복제될 때,
-- 복제 로그 안의 ssn 값은 암호화된 채로 전송/저장되는가?
-- 슬레이브의 물리적 로그 파일을 열어보면 평문 ssn이 보이는가?
```

**예제 설명**: 이 스펙이 새로 만드는 "복제 로그"라는 전송 경로가 기존 TDE의 보호 범위(디스크에 저장된 파일) 안에 포함되는지, 새로 뚫리는 구멍인지는 보안 감사 시 반드시 확인해야 하는 사항인데, 스펙에 이에 대한 언급이 전혀 없어 사용자가 스스로 실험해보거나 별도로 문의해야 합니다.

**제안**: TDE가 설정된 테이블의 REPLICATION 동작(복제 로그의 암호화 여부)을 명시하거나, 최소한 "이번 기능은 TDE와 독립적이며 별도 검토가 필요하다"는 주의 문구를 추가해야 합니다.

## 리뷰 25

**[심각도: 중요] 하나의 트랜잭션 안에서 REPLICATION=ON 테이블과 OFF 테이블을 함께 변경하면, "커밋 = 전부 반영"이라는 트랜잭션의 기본 개념이 슬레이브 쪽에서는 깨진다**

**대상**: §1 "REPLICATION OFF 로 인한 데이터 불일치는 책임지지 않는다"는 문구는 있으나, 이것이 "트랜잭션 원자성" 자체가 깨진다는 의미까지 포함하는지 구체적으로 설명하지 않음

**문제 설명**: SQL을 배우는 사람이 가장 먼저 배우는 개념 중 하나가 "트랜잭션은 COMMIT을 하면 그 안의 모든 변경사항이 전부 반영되거나, 하나도 반영되지 않는다"(원자성)입니다. 그런데 이 스펙에서는 하나의 트랜잭션 안에 REPLICATION=ON 테이블에 대한 변경과 REPLICATION=OFF 테이블에 대한 변경이 함께 들어 있어도 마스터에서는 정상적으로 원자적으로 커밋됩니다. 문제는 슬레이브 쪽입니다. 슬레이브는 ON 테이블의 변경분만 받으므로, 사용자가 "하나의 트랜잭션으로 묶어서 안전하게 처리했다"고 믿었던 작업이 슬레이브 관점에서는 "절반만 반영된 트랜잭션"이 되어버립니다. §1의 면책 문구는 "데이터 불일치"라고만 되어 있어, 이것이 단순히 "두 테이블이 서로 다른 시점의 값을 갖는다"는 뜻인지 "같은 트랜잭션으로 묶은 작업이 반쪽만 반영된다"는 더 근본적인 문제인지 1년차 독자가 스스로 알아채기 어렵습니다.

**구체 예제(SQL)**:
```sql
-- ledger: 실제 잔액 변화 (복제 대상)
csql> CREATE TABLE ledger(
    id INT PRIMARY KEY,
    account_id INT,
    amount INT
);  -- REPLICATION 생략 -> 기본 ON

-- ledger_audit: 감사용 로그, 용량 부담 때문에 복제 제외로 설계
csql> CREATE TABLE ledger_audit(
    id INT PRIMARY KEY,
    ledger_id INT,
    memo VARCHAR(500)
) REPLICATION=OFF;

-- 애플리케이션은 "잔액 변경 + 감사로그 기록"을 하나의 트랜잭션으로 묶어 안전하다고 믿음
csql> START TRANSACTION;
csql> INSERT INTO ledger VALUES (1, 100, 5000);
csql> INSERT INTO ledger_audit VALUES (1, 1, '입금 5000원 처리');
csql> COMMIT;

-- 마스터: 두 INSERT 모두 반영됨 (정상적인 원자적 커밋)
-- 슬레이브: ledger 행만 존재, ledger_audit 행은 존재하지 않음
-- Failover 후: "잔액은 바뀌었는데 그 잔액 변경에 대한 감사 기록은 어디에도 없다"
--             는 상태가, 애플리케이션 입장에서는 트랜잭션이 절반만 커밋된 것처럼 보임
```

**예제 설명**: 이 예제에서 애플리케이션 개발자는 잘못한 것이 하나도 없습니다. 트랜잭션으로 묶었으니 원자성이 보장된다고 믿는 것은 SQL의 기본 전제이기 때문입니다. 그런데 REPLICATION 옵션이라는, 트랜잭션과는 별개 차원의 테이블 속성 하나 때문에 이 전제가 슬레이브에서는 소리 없이 깨집니다. §1의 "데이터 불일치는 책임지지 않는다"는 문구만으로는 이 정도로 근본적인 개념(트랜잭션 원자성)까지 영향을 받는다는 것을 1년차가 짐작하기 어렵습니다.

**제안**: §1 또는 별도 절에 "REPLICATION=OFF 테이블과 ON 테이블을 같은 트랜잭션에서 함께 변경하면, 슬레이브에서는 그 트랜잭션이 원자적으로 반영되지 않는다"는 문장을 명시적으로 추가하고, 이런 조합을 설계 단계에서 피해야 한다는 가이드(또는 최소한 경고)를 제공해야 합니다.

## 리뷰 26

**[심각도: 치명] UK가 복제키로 쓰이는 테이블에 새 PK를 추가하면, 사용자가 그 사실을 알아챌 방법 없이 복제키가 조용히 PK로 넘어간다**

**대상**: §4-2 예시 14 ("UK를 복제키로 사용하고 있는 테이블은 PK가 없으므로 추가 가능") + §1 ("PK가 존재한다면 PK가 복제 키가 됨")

**문제 설명**: §1의 RK 선택 규칙은 "PK가 있으면 무조건 PK가 RK"입니다. 그런데 §4-2 예시 14는 "UK가 RK로 쓰이는 테이블에 새 PK를 추가하는 것"을 아무 제약 없이 허용합니다(OK). 두 규칙을 합치면, UK가 RK였던 테이블에 누군가 (전혀 다른 목적으로, 예를 들어 ORM 프레임워크가 관례적으로 요구해서) PK를 하나 추가하는 순간, RK는 그 즉시 기존 UK에서 새 PK로 자동 전환됩니다. 이 전환은 어떤 에러도, 경고도, 로그도 없이 §1 규칙에 따라 "자동으로" 일어나며, 리뷰 6/최종보고서 C-3이 지적한 대로 사용자는 애초에 지금 RK가 무엇인지 조회할 방법조차 없으므로 이 전환이 일어났다는 사실 자체를 알 방법이 없습니다.

**구체 예제(SQL)**:
```sql
-- 1) 외부 연동 시스템과의 계약상 email이 "행을 식별하는 유일한 키"로 쓰이고 있어
--    RK로 email의 UK를 의도적으로 선택되게 설계함 (PK 없음)
csql> CREATE TABLE members(
    member_id INT,
    email VARCHAR(100) NOT NULL UNIQUE,
    name VARCHAR(50)
);
-- RK = email의 UK (PK가 없으므로 §1 규칙에 따라)

-- 2) 몇 달 뒤, 신규 입사자가 "테이블에는 PK가 있어야 한다"는 사내 컨벤션에 따라
--    member_id에 PK를 추가함 (RK와는 전혀 무관한 의도)
csql> ALTER TABLE members ADD CONSTRAINT PRIMARY KEY(member_id);
-- OK (예시 14 그대로)

-- 3) 이 순간부터 RK는 email의 UK가 아니라 member_id의 PK로 조용히 바뀐다.
--    외부 연동 시스템이 "email 기준으로 슬레이브 데이터를 조회"하도록 만들어져 있었다면,
--    이제 슬레이브 쪽 갱신/삭제 판단 기준이 email이 아니라는 사실이
--    아무 통보 없이 이미 벌어져 있다.
```

**예제 설명**: 신규 입사자는 자신이 "PK를 하나 추가했을 뿐"이라고 생각하지만, 실제로는 이 테이블의 복제 정합성을 좌우하는 핵심 값(RK)을 완전히 바꿔버린 것입니다. 더 심각한 점은, 이 변경이 성공(OK)으로 처리되기 때문에 아무도 이상함을 느끼지 못하고, 문제는 한참 뒤 무언가 email 기준 로직이 예상과 다르게 동작할 때에야 발견된다는 것입니다.

**제안**: RK가 실제로 전환되는 모든 DDL(이 경우 PK 추가)에 대해 최소한 경고 메시지를 출력하도록 하거나, RK 전환이 일어나는 시점을 사용자가 조회/로그로 확인할 수 있는 수단(리뷰 30 참고)을 함께 제공해야 합니다.

## 리뷰 27

**[심각도: 보통] "DROP CONSTRAINT PRIMARY KEY"라는 구문이 "PRIMARY KEY"를 제약 이름처럼 쓰는 것인지 특수 키워드인지 예시들 사이에서 일관성이 없다**

**대상**: 예시 12 `ALTER TABLE table_name DROP PRIMARY KEY;` vs 예시 13 `ALTER TABLE table_name DROP CONSTRAINT PRIMARY KEY, ADD CONSTRAINT PRIMARY KEY(a);` vs 예시 15 `ALTER TABLE table_name DROP CONSTRAINT u_tbl_a;`

**문제 설명**: 예시 15에서 `DROP CONSTRAINT` 뒤에는 `u_tbl_a`라는, 사용자가 지정했거나 시스템이 자동 생성한 실제 제약 이름이 옵니다. 반면 예시 13에서는 `DROP CONSTRAINT` 뒤에 `PRIMARY KEY`라는, 앞서 예시 11에서 본 자동 생성 이름("pk_tbl_a")과 전혀 다른 문자열이 옵니다. 1년차 사용자는 이 둘을 보고 다음 중 무엇이 맞는지 판단할 근거가 없습니다: (a) `PRIMARY KEY`는 실제 제약 이름과 무관하게 "현재 PK인 제약"을 가리키는 특수 키워드다, (b) 이 예시의 테이블은 우연히 제약 이름이 문자 그대로 `PRIMARY KEY`로 지정되어 있다, (c) 사실 이 두 표현(`DROP PRIMARY KEY`와 `DROP CONSTRAINT PRIMARY KEY`)은 완전히 동의어다. 자신의 실제 테이블에 이 구문을 적용하려는 사용자는 "내 PK의 실제 이름"을 몰라도 `DROP CONSTRAINT PRIMARY KEY`라고 그대로 타이핑하면 되는지, 아니면 반드시 `pk_tbl_xxx` 형태의 진짜 이름을 알아내서 넣어야 하는지 확신할 수 없습니다.

**구체 예제(SQL)**:
```sql
-- 예시 11에서 본 자동 생성 이름 형태
-- ERROR: Primary key "pk_tbl_a" already defined for class "dba.tbl".
-- 즉 이 테이블의 실제 PK 제약 이름은 "pk_tbl_a" 이다.

-- 그런데 예시 13은:
csql> ALTER TABLE table_name DROP CONSTRAINT PRIMARY KEY,
      ADD CONSTRAINT PRIMARY KEY(a);
-- "PRIMARY KEY"라고만 썼다. 실제 이름인 "pk_tbl_a"를 쓴 게 아니다.

-- 신입 사용자가 자신의 테이블에 그대로 적용해도 되는지 확신할 수 없다:
csql> ALTER TABLE my_table DROP CONSTRAINT PRIMARY KEY,
      ADD CONSTRAINT PRIMARY KEY(new_col);
-- 이게 정말 동작하는 문법인지, my_table의 PK 제약 이름을 먼저
-- show create table 등으로 조회해서 그 이름을 넣어야 하는지 알 수 없다.
```

**예제 설명**: 문법서에 나오는 예시는 그대로 복사해서 자신의 테이블 이름만 바꿔 써도 동작해야 한다는 것이 1년차가 매뉴얼에 갖는 기본적인 기대입니다. 그런데 이 세 예시(12, 13, 15)는 같은 종류의 명령(`DROP CONSTRAINT`)에 서로 다른 형태의 인자를 써서, 어느 것이 일반화 가능한 문법이고 어느 것이 해당 예시에서만 우연히 성립하는 표기인지 구분할 수 없게 만듭니다.

**제안**: `PRIMARY KEY`가 `DROP CONSTRAINT` 뒤에 올 수 있는 예약된 표현(동의어)이라면 그렇다고 명시하고, 아니라면 예시 13을 실제 제약 이름을 사용하는 형태로 고쳐야 합니다.

## 리뷰 28

**[심각도: 사소] "REPLICATION={ON|OFF}"라는 표기가 실제 SQL 문법이 아니라 문법을 설명하는 표기법(BNF 스타일)이라는 점이 안내되지 않는다**

**대상**: §2 "다음 옵션을 제공한다. `REPLICATION={ON|OFF}`"

**문제 설명**: 이 표기에서 중괄호(`{}`)와 세로줄(`|`)은 "둘 중 하나를 선택하라"는 뜻을 나타내는 문법 설명용 기호(BNF 표기법과 유사)이지, 실제 SQL 문장에 그대로 입력하는 문자가 아닙니다. 그런데 스펙 어디에도 이 표기법 자체에 대한 설명이 없습니다. 이후 실제 예시들(`REPLICATION = ON`, `REPLICATION=OFF`)을 보면 문맥상 유추할 수는 있지만, SQL을 막 배우기 시작한 독자, 특히 이 문서를 다른 BNF 표기 관례를 접해본 적 없는 상태로 처음 읽는 독자에게는 "정말로 중괄호와 파이프 문자를 그대로 입력해야 하는가"라는 의문이 스쳐 지나갈 수 있습니다. 사소하지만, 이런 표기법에 대한 각주 한 줄이 없다는 것은 이 문서가 "전문 지식을 아는 사람만 이해할 수 있게 쓰지 말라"는 이 스펙 자체의 서술 목표와 어긋납니다.

**구체 예제(시나리오)**:
```
문서 표기:  REPLICATION={ON|OFF}
1년차의 최초 오독 가능성: 아래처럼 문자 그대로 입력해야 하는 줄 알고 시도
csql> CREATE TABLE t(a INT) REPLICATION={ON|OFF};
-- (물론 몇 줄 아래 실제 예시를 보면 아니라는 것을 알 수 있지만,
--  표기법 자체에 대한 설명이 없어 첫 인상에서 혼란을 줄 여지가 있다)
```

**예제 설명**: 뒤이어 나오는 구체 예시들(예시 1~4)이 실제로는 `REPLICATION = ON` 또는 `REPLICATION = OFF`처럼 값 하나만 쓴다는 것을 보여주므로 실질적인 피해는 크지 않지만, 표기 규칙에 대한 명시적 언급이 없다는 것 자체가 "전공 입문서 수준"을 표방하는 문서로서는 사소한 결함입니다.

**제안**: `{ON|OFF}` 표기 옆에 "중괄호와 세로줄은 둘 중 하나를 선택한다는 뜻의 표기법이며 실제로 입력하는 문자가 아니다"라는 각주를 추가하면 좋겠습니다.

## 리뷰 29

**[심각도: 사소] 이 스펙이 어느 CUBRID 버전부터 적용되는지 문서 어디에도 명시되어 있지 않다**

**대상**: 스펙 전체 (버전 정보 없음)

**문제 설명**: 이 스펙 자체는 "지금까지의 CUBRID HA는 PK 있는 테이블만 복제 가능했다"는 기존 동작을 전제로, REPLICATION 옵션과 RK 자동 선택이라는 새 기능을 추가하는 변경입니다. 그런데 이 새 기능이 몇 버전부터 적용되는지, 사용자가 지금 쓰고 있는 CUBRID가 이 기능을 지원하는지 확인하려면 어떻게 해야 하는지에 대한 정보가 문서 어디에도 없습니다. 1년차 사용자가 사내 매뉴얼이나 검색으로 이 문서를 접했을 때, 가장 먼저 확인해야 할 것은 "내가 쓰는 버전에 이 내용이 해당하는가"인데 이 질문에 답할 수 있는 단서가 문서 자체에는 없습니다.

**구체 예제(시나리오)**:
```
$ cubrid --version
CUBRID 11.x.x

질문: 이 문서(REPLICATION 옵션, RK 자동 선택)가 이 버전에 적용되는가?
-> 문서 자체에는 버전 번호가 전혀 언급되어 있지 않아 판단 불가.
   결국 별도로 릴리스 노트나 변경 이력을 찾아봐야 한다.
```

**예제 설명**: 다른 벤더의 기능 문서(예: PostgreSQL의 REPLICA IDENTITY 문서)는 대개 "PostgreSQL 9.4부터 지원"처럼 최소 지원 버전을 명시합니다. 이 스펙에는 그런 버전 고정 정보가 없어, 문서만 따로 떼어놓고 보면 "언제부터, 어떤 버전에 이 내용이 유효한지" 알 수 없습니다.

**제안**: 문서 상단에 적용 버전(예: "CUBRID X.Y 이상에 적용")을 명시해야 합니다.

## 리뷰 30

**[심각도: 보통] 현재 RK를 조회할 방법이 없는 것과 별개로, RK가 "언제, 무엇에서 무엇으로 바뀌었는지" 이력을 확인할 방법도 없다**

**대상**: §2-3 (REPLICATION 조회), §4-2 (RK 자동 재선택 관련 규칙 전반)

**문제 설명**: 1차 리뷰와 최종보고서는 "지금 이 순간의 RK가 무엇인지"를 조회할 방법이 없다는 점을 지적했습니다. 여기서는 그와는 다른 축의 문제, 즉 "RK가 과거에 바뀐 적이 있는지, 있다면 언제 무엇 때문에 바뀌었는지"를 확인할 방법이 전혀 없다는 점을 지적합니다. 리뷰 26에서 보인 것처럼 RK는 PK 추가처럼 RK 전환을 의도하지 않은 DDL로도 조용히 바뀔 수 있습니다. 장애가 발생한 뒤 원인을 분석하는 실무자는 "지금 RK가 무엇인가"뿐 아니라 "장애 당시 RK가 무엇이었는가", "그 RK가 언제부터 그 값이었는가"를 알아야 하는 경우가 많은데, 이런 이력 정보를 남기거나 조회하는 방법이 스펙에 전혀 없습니다.

**구체 예제(시나리오)**:
```
1) 2026-08-01: members 테이블 RK = email(UK)
2) 2026-08-15: 누군가 PK 추가, RK가 조용히 member_id(PK)로 전환 (리뷰 26 시나리오)
3) 2026-08-22: Failover 발생, 이후 email 기준 외부 연동에서 데이터 불일치 신고 접수

질문: 담당자가 장애 원인을 조사하려 할 때,
"RK가 8월 15일에 email에서 member_id로 바뀌었다"는 사실을
CUBRID의 어떤 명령/카탈로그로 확인할 수 있는가?
-> 스펙에는 현재 값 조회 수단조차 없으므로(리뷰 6/최종보고서 C-3),
   과거 이력은 더더욱 확인할 방법이 없다.
```

**예제 설명**: 장애 조사는 "지금 상태"만으로는 원인을 알 수 없는 경우가 대부분이며, "언제부터 그랬는가"를 추적하는 것이 핵심입니다. RK 조회 기능이 나중에 추가되더라도, 그것이 "현재 값"만 보여주는지 "변경 이력"까지 보여주는지는 별개의 설계 결정이므로 이번 스펙 단계에서부터 구분해서 논의되어야 합니다.

**제안**: RK 조회 기능을 설계할 때 현재 값뿐 아니라 변경 이력(또는 최소한 마지막 변경 시각)까지 남기는 것을 검토 항목에 포함해야 합니다.

## 리뷰 31

**[심각도: 중요] 복합 UNIQUE 키의 일부 컬럼만 NOT NULL이고 나머지는 NULL 허용일 때, 이 UK가 RK 후보가 되는지 정의가 없다**

**대상**: §1 "복제 키는 큐브리드 엔진에 의해 Primary Key(PK) 혹은 Not Null Unique Key(UK)들 중 하나로 선택된다"

**문제 설명**: §1은 RK 후보 자격을 "Not Null Unique Key"라고 정의합니다. 이 표현은 컬럼이 하나뿐인 UNIQUE 제약을 염두에 둔 것으로 보이는데, CUBRID의 UNIQUE 제약은 여러 컬럼을 묶은 복합 키로도 만들 수 있습니다. 복합 UNIQUE 키를 구성하는 컬럼 중 일부만 `NOT NULL`이고 나머지는 `NULL`을 허용한다면, 이 복합 키 전체가 "Not Null Unique Key"에 해당하는지(=RK 후보가 되는지) 아니면 구성 컬럼 전부가 `NOT NULL`이어야만 후보가 되는지에 대한 정의가 없습니다. 이는 앞선 1차 리뷰 9가 지적한 "복제키 후보 정의 공백"과는 다른, 더 구체적인 하위 질문(복합 키의 NULL 허용 범위 판정 기준)입니다.

**구체 예제(SQL)**:
```sql
csql> CREATE TABLE order_items(
    order_id INT NOT NULL,
    line_no INT,                 -- NOT NULL 아님
    product_id INT,
    CONSTRAINT uk_order_line UNIQUE(order_id, line_no)
);
-- order_id는 NOT NULL, line_no는 NULL 허용.
-- 두 컬럼을 합친 복합 UNIQUE 제약 uk_order_line은
-- "Not Null Unique Key"인가, 아닌가?

-- 만약 이 테이블에 PK가 없다면, uk_order_line이 RK 후보가 되어
-- HA 모드 전환이 가능한 테이블인가, 아니면 §1의 "복제키 없음"으로 처리되어
-- HA 전환 시 에러가 나는 테이블인가?
```

**예제 설명**: 이 질문에 대한 답은 실제로 서비스 영향이 큽니다. 만약 이 판정 기준을 몰라 "이 복합 UK가 RK 후보가 될 것"이라고 잘못 가정한 채 HA 전환을 시도하면, 이 테이블이 RK 없는 테이블로 취급되어 §7 규칙에 따라 HA 전환 자체가 거부될 수 있습니다. 반대로 실제로는 RK 후보로 인정되는데 사용자가 "부분 NULL 허용이니 안 될 것"이라 지레짐작해 불필요하게 스키마를 변경할 수도 있습니다.

**제안**: §1에 복합 UNIQUE 키의 경우 "구성 컬럼 전체가 NOT NULL이어야 RK 후보가 된다"는 식으로 명확한 판정 기준을 추가하고, 복합 키 예시를 §1 또는 §4-2에 최소 하나 포함해야 합니다.

## 리뷰 32

**[심각도: 사소] 테이블마다 REPLICATION 옵션을 일일이 명시해야 하며, 데이터베이스/세션 단위로 기본값을 바꾸는 방법이 없다**

**대상**: §2-1 "이 옵션은 생략 가능하며 생략시 ON으로 자동으로 복제 테이블로 생성된다"

**문제 설명**: 이 규칙은 테이블 단위 기본값(옵션을 생략하면 ON)만 정의할 뿐, 데이터베이스 전체나 현재 접속 세션 단위로 기본값을 OFF로 바꿔두는 방법은 제공하지 않습니다. 예를 들어 로그성 테이블을 대량으로 만드는 스테이징/분석용 데이터베이스에서는 "이 DB에 새로 만드는 테이블은 기본적으로 REPLICATION=OFF였으면 좋겠다"는 요구가 자연스러운데, 이런 DB에서도 사용자는 테이블을 만들 때마다 `REPLICATION=OFF`를 빠짐없이 타이핑해야 하고, 한 번이라도 빠뜨리면(§2-1 기본값이 ON이므로) 그 테이블만 조용히 복제 대상으로 생성됩니다.

**구체 예제(SQL)**:
```sql
-- 분석용 스테이징 DB. 이 DB의 테이블은 전부 복제 제외로 두고 싶다고 가정
csql> CREATE TABLE stg_orders(...) REPLICATION=OFF;
csql> CREATE TABLE stg_customers(...) REPLICATION=OFF;
csql> CREATE TABLE stg_events(...);   -- 실수로 옵션을 빠뜨림
-- stg_events만 REPLICATION=ON(기본값)으로 생성되어,
-- 의도와 다르게 복제 대상에 섞여 들어간다.
```

**예제 설명**: 이런 종류의 "매번 명시해야 하는 옵션, 빠뜨리면 조용히 반대 값이 적용됨" 패턴은 실무에서 반복 작업 중 실수가 누적되는 전형적인 원인입니다. 데이터베이스나 세션 단위로 기본값을 설정하는 수단이 있다면 이런 실수를 원천적으로 줄일 수 있습니다.

**제안**: 데이터베이스 생성 시 또는 세션 옵션으로 "이후 생성되는 테이블의 REPLICATION 기본값"을 지정할 수 있는 수단을 검토 항목에 추가하면 좋겠습니다.

## 조사 종료 선언

이번 2차 라운드에서는 1차/최종보고서가 다루지 않은 아래 영역을 훑었습니다: CTAS/LIKE를 통한 테이블 생성 경로, REPLICATION 옵션 변경 권한/소유자, 파티션 테이블과의 상호작용, TDE 암호화와의 관계, 트랜잭션 원자성, RK가 조용히 재배정되는 이벤트, 예시 문장들 사이의 구문 표기 불일치, 표기법(BNF) 설명 부재, 문서의 적용 버전 명시 여부, RK 변경 이력 조회, 복합 UNIQUE 키의 NULL 허용 범위, DB/세션 단위 기본값 설정 부재. 이 중 12건을 실제로 "1년차가 이 문서만 보고 작업하다가 막히거나 사고를 낼 수 있는 지점"으로 판단해 리뷰로 남겼습니다.

추가로 트리거를 통한 간접 DML의 복제 처리, SERIAL/AUTO_INCREMENT와 failover의 관계, 컬레이션(collation) 차이에 따른 RK 값 비교, REUSE_OID/멀티 슬레이브 관련 사항도 검토했으나, 이들은 최종보고서 4절(직군별 고유 지적)에서 엔진 개발자 관점으로 이미 언급되어 있거나, 1년차 최종 사용자가 SQL을 직접 다루는 업무 범위를 벗어나 실질적으로 새로운 지적이라 보기 어려워 제외했습니다. 이 이상으로 "사용성/에러 메시지/학습 곡선/직관성" 관점에서 1차·최종보고서와 뚜렷하게 구분되는 새로운 결함을 찾기는 어렵다고 판단해 12건에서 조사를 마칩니다.
