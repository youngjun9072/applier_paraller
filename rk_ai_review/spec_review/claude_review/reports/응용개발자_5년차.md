# CUBRID HA 복제 개선 스펙 리뷰 — 응용 개발자(5년차) 관점

## 리뷰어 소개

저는 5년차 백엔드 애플리케이션 개발자로, 주로 ORM(Object-Relational Mapping, 객체와 관계형 DB 테이블을 자동으로 매핑해주는 프레임워크. 예: JPA/Hibernate)과 스키마 마이그레이션 도구(Flyway, Liquibase 등 DB 스키마 변경 이력을 버전 관리하고 자동 적용하는 도구)를 이용해 서비스를 개발·배포해왔습니다. DB 엔진 내부 구현보다는 "이 스펙대로 동작하는 DB 위에서 내가 짠 애플리케이션 코드와 배포 파이프라인이 실제로 어떻게 움직이는가"를 중심으로 검토했습니다.

## 총평

이번 스펙은 PK(Primary Key, 테이블에서 각 행을 유일하게 식별하는 기본 키) 컬럼을 변경했을 때 복제가 깨지던 기존 결함을, 복제 키(RK)를 PK 또는 NOT NULL UNIQUE 키(이하 UK) 중에서 엔진이 자동으로 고르고 `REPLICATION={ON|OFF}` 옵션으로 복제 대상을 통제하는 방식으로 해결하려 합니다. 방향 자체는 합리적이지만, 응용 개발자 시점에서 보면 두 가지 구조적 우려가 있습니다. 첫째, 개발/스테이징(대개 싱글 모드)과 운영(HA 모드)에서 동일한 DDL이 다르게 동작하도록 설계되어 있어, 로컬에서 검증된 마이그레이션 스크립트가 운영 배포 시점에야 실패하는 시나리오가 여러 곳에 잠재해 있습니다. 둘째, 스펙이 "정상 경로"의 성공/실패 예시는 비교적 촘촘히 다루지만, 여러 규칙이 동시에 걸리는 경계 조건(복제키 후보가 여럿일 때의 전환 순서, ALTER 문 내부 절 단위 검증 시점, REPLICATION 상태가 나중에 바뀌는 경로)에 대해서는 침묵하는 부분이 많습니다. 이런 침묵은 엔진 개발자에게는 "구현하기 나름"이겠지만, 그 위에서 자동화된 배포 파이프라인을 짜는 응용 개발자에게는 "언제 터질지 모르는 지뢰"로 다가옵니다. 아래 20개 리뷰는 이 두 축을 중심으로 정리했습니다.

### 리뷰 1

**[심각도: 치명] REPLICATION=OFF 테이블과 읽기/쓰기 분리(Read-Write Splitting) 아키텍처가 만나면 조용히 데이터가 사라진다**

**대상**: §1 "REPLICATION OFF 로 인한 데이터 불일치는 책임지지 않는다(6. 뷰(VIEW))", §4 HA 제약사항

**문제 설명**: 실무에서 많은 애플리케이션은 성능을 위해 쓰기는 마스터로, 읽기 전용 트랜잭션은 슬레이브로 자동 라우팅하는 구조(Spring의 `@Transactional(readOnly=true)` + 라우팅 데이터소스, 혹은 JDBC 드라이버의 로드밸런싱 커넥션 등)를 씁니다. 이때 REPLICATION=OFF 테이블에 대한 SELECT가 슬레이브로 라우팅되면, 에러 없이 "빈 결과" 또는 "오래된 결과"가 반환됩니다. 스펙은 이 상황에 대해 "책임지지 않는다"고만 명시할 뿐, DB 드라이버나 SQL 실행 계층에서 이를 감지해 경고하거나 차단할 수단을 전혀 제공하지 않습니다.

**구체 예제**:
```sql
-- 마스터에서
csql> CREATE TABLE session_cache(
    session_id VARCHAR(64) PRIMARY KEY,
    payload VARCHAR(4096)
) REPLICATION = OFF;

csql> INSERT INTO session_cache VALUES ('abc123', '{...}');
-- 마스터에서는 정상 조회됨
csql> SELECT * FROM session_cache WHERE session_id = 'abc123';
```
```java
// 애플리케이션 계층: 읽기 전용 트랜잭션은 슬레이브로 라우팅되는 흔한 패턴
@Transactional(readOnly = true)
public SessionPayload getSession(String id) {
    // 이 SELECT는 라우팅 데이터소스에 의해 슬레이브 커넥션으로 실행됨
    return sessionRepository.findById(id); // -> 결과 없음 (에러도 아님, 그냥 empty)
}
```

**예제 설명**: 애플리케이션 개발자는 `session_cache`가 REPLICATION=OFF라는 사실을 DAO나 Repository 코드에서 알 수 있는 방법이 없습니다. ORM 매핑에는 그런 정보가 노출되지 않기 때문입니다. 그 결과 마스터에 방금 쓴 데이터를 슬레이브에서 못 찾는 현상이 "버그"처럼 보이지만 실제로는 스펙이 의도한 정상 동작입니다. 문제는 이게 예외를 던지지 않고 조용히 틀린 결과를 준다는 점입니다.

**제안**: 최소한 JDBC 드라이버나 카탈로그 뷰 수준에서 "이 커넥션이 슬레이브인지"와 "이 테이블이 REPLICATION=OFF인지"를 조합해 SELECT 시 경고를 로그로 남기거나, 세션 힌트(예: `SET REPL_OFF_READ_POLICY=WARN|ERROR`)를 제공하는 것을 검토해야 합니다. 최소한 문서에는 "읽기/쓰기 분리 아키텍처에서는 REPLICATION=OFF 테이블에 대한 읽기를 반드시 마스터로 강제하라"는 경고 문구가 필요합니다.

### 리뷰 2

**[심각도: 치명] RK 자동 선택 기준 "테이블 내 명시된 순서 중 가장 빠른 순서"가 비결정적이어서 스키마 검증 도구와 충돌한다**

**대상**: §1 "UK가 여러개 존재한다면 큐브리드 엔진에 의해 이 중 하나가 선택된다(ex. 테이블내에 명시된 순서 중 가장 빠른 순서)"

**문제 설명**: "명시된 순서"가 CREATE TABLE 문에 나열한 컬럼 순서인지, UK 제약을 추가한 시간 순서(카탈로그 저장 순서)인지 스펙이 명확히 정의하지 않습니다. `ex.`(예를 들어)라는 표현 자체가 "이건 참고 예시고 확정 규칙이 아닐 수도 있다"는 인상을 줍니다. 그런데 Hibernate의 `hbm2ddl.auto=validate`처럼, 애플리케이션이 기동 시점에 엔티티 매핑과 실제 DB 스키마를 대조 검증하는 도구를 쓴다면, "어떤 UK가 RK인가"가 배포마다 달라질 경우 검증 실패가 재현 불가능한 방식으로 발생할 수 있습니다.

**구체 예제**:
```sql
csql> CREATE TABLE product(
    id INT,
    sku VARCHAR(32) NOT NULL,
    barcode VARCHAR(32) NOT NULL,
    UNIQUE(barcode),
    UNIQUE(sku)
);
-- PK가 없으므로 UK 중 하나가 RK. barcode가 먼저 선언되었으므로 barcode가 RK인가?
-- 아니면 카탈로그 내부 OID(Object ID) 생성 순서가 기준인가?
```
```
-- 이후 애플리케이션 마이그레이션 스크립트가 sku UK를 DROP 후 재생성했다면
csql> ALTER TABLE product DROP CONSTRAINT u_product_sku;
csql> ALTER TABLE product ADD CONSTRAINT UNIQUE(sku);
-- 재생성된 sku UK가 이제 "가장 나중에 명시된" 것이 되어 RK 후보 우선순위가 바뀌는가?
```

**예제 설명**: 두 번째 스크립트는 겉보기엔 "같은 제약을 지웠다가 다시 만든 것"뿐이라 애플리케이션 개발자는 아무 영향이 없을 거라고 생각하기 쉽습니다. 하지만 "명시된 순서"의 정의에 따라 RK가 barcode에서 sku로 바뀔 수도 있고, RK가 바뀌면 §4-2의 ALTER 제약(어떤 컬럼을 못 건드리는지)도 함께 바뀝니다. 즉 겉으로 동일해 보이는 리팩터링이 내부적으로 전혀 다른 제약 상태를 만들 수 있습니다.

**제안**: RK 선택 기준을 "생성 시각 기준 카탈로그 순서(내부 index id)"처럼 관찰 가능하고 재현 가능한 정의로 못박고, `show create table`이나 `select * from db_class`에 현재 RK로 선택된 제약의 이름을 명시적으로 노출해야 합니다(현재 예시 8/9에는 REPLICATION ON/OFF만 나오고 RK가 어떤 제약인지는 안 나옵니다).

### 리뷰 3

**[심각도: 중요] 로컬(싱글 모드) 개발 → 스테이징/운영(HA) 승격 경로에서 RK 누락이 배포 시점에야 발견된다**

**대상**: §3 Single 제약사항, §7 HA 전환

**문제 설명**: 많은 팀의 실제 워크플로우는 "로컬/CI에서는 싱글 모드 DB로 테스트 → 스테이징/운영은 HA"입니다. §3에 따르면 싱글 모드에서는 RK 없는 테이블도 자유롭게 만들 수 있고, 스펙은 이게 §7 단계(HA 전환)에서만 에러로 걸린다고 말합니다. 즉 CI 파이프라인에서 마이그레이션 스크립트가 문제없이 통과했더라도, 그 스크립트가 실제로 HA 환경에 안전한지는 별도 검증 없이는 알 수 없습니다.

**구체 예제**:
```sql
-- Flyway 마이그레이션 파일 V12__add_audit_log.sql (CI에서 싱글모드 DB에 대해 성공)
CREATE TABLE audit_log(
    actor VARCHAR(64),
    action VARCHAR(64),
    ts DATETIME
);
-- PK/UK가 전혀 없음. 싱글 모드에서는 이 파일이 그대로 통과한다.
```
```
# 이후 운영 HA 클러스터에 같은 마이그레이션을 적용
$ flyway migrate
# -> 마이그레이션 자체는 "적용됨"으로 기록되지만,
#    실제로는 이 테이블이 복제 대상에서 빠지거나(REPLICATION 옵션이 없어 기본 ON으로 시도되어 에러),
#    HA 재시작 시점에야 §7의 "파일 리스트" 에러로 뒤늦게 발각된다.
```

**예제 설명**: Flyway/Liquibase 같은 도구는 "한 번 성공한 마이그레이션은 다시 실행하지 않는다"는 원칙으로 동작합니다. CI에서 싱글 모드로 검증하고 통과한 스크립트를 운영에 그대로 밀어넣었을 때, 운영이 HA로 떠 있는 상태라면 §4-1에 따라 이 CREATE TABLE 자체가 즉시 에러가 나서 마이그레이션이 실패합니다(그나마 나은 경우). 더 나쁜 경우는 HA가 아직 기동 전(싱글로 전환된 상태에서 배포)이라 CREATE는 성공하고, 이후 HA 재시작 시점에야 §7 에러가 튀어나오는 경우인데, 이때는 이미 애플리케이션 코드가 배포되어 이 테이블에 의존하는 트래픽이 흐르고 있을 수 있습니다.

**제안**: CI/CD 파이프라인이 사용할 수 있는 "HA 호환성 정적 검사" 모드(`csql --check-ha-compat`류)를 제공해, 싱글 모드에서도 "이 DDL이 HA 환경이었다면 통과했을지"를 미리 판정할 수 있게 해야 합니다. 스펙에 이 도구/모드에 대한 언급이 전혀 없습니다.

### 리뷰 4

**[심각도: 중요] 예시 2와 예시 4의 CREATE TABLE 구문에 트레일링 콤마 오류가 있어 예제 자체가 재현 불가능하다**

**대상**: 예시 2 `CREATE TABLE repl_table_without_rk(a INT,);`, 예시 4 `CREATE TABLE non_repl_table_without_rk(a INT)` 바로 아래 반복되는 유사 패턴

**문제 설명**: 예시 2의 `a INT,` 뒤에 바로 닫는 괄호가 오는 것은 대부분의 SQL 방언에서 문법 오류(trailing comma, 마지막 항목 뒤에 불필요한 쉼표가 남는 오류)입니다. 이 스펙은 "복잡한 지식을 아는 사람만 이해하게 쓰지 말라"는 원칙의 문서인데, 정작 핵심 예제의 SQL이 그대로 실행하면 파싱 에러가 나는 문장이라면 독자(응용 개발자)는 "이게 RK 관련 의도된 에러인지, 그냥 오타인지"를 구분할 수 없습니다.

**구체 예제**:
```sql
-- 스펙 원문 그대로
csql> CREATE TABLE repl_table_without_rk(
    a INT,
);
```

**예제 설명**: 이 문장을 그대로 CUBRID csql에 입력하면, 의도한 "RK가 없어서 발생하는 의미론적 에러"가 아니라 "구문 자체가 틀려서 발생하는 파서 에러"가 날 가능성이 높습니다. 즉 예제가 보여주려는 핵심 포인트(RK 없는 테이블도 싱글 모드에서는 생성 가능하다)를 증명하지 못하는 예제가 되어버립니다. 실제로 CUBRID가 trailing comma를 허용하는지 확인이 안 된 상태로 문서에 실렸다면, 이는 예제 신뢰성의 문제입니다.

**제안**: 모든 예제 SQL을 실제 csql에 돌려보고 캡처한 결과로 교체해야 합니다. 최소한 `a INT,` → `a INT` 로 트레일링 콤마를 제거해야 합니다.

### 리뷰 5

**[심각도: 중요] 예시 12(DROP PK 단독 → 에러)와 예시 13(DROP+ADD PK 한 문장 → OK)이 "검증 시점"에 대해 서로 다른 모델을 암시한다**

**대상**: §4-2, 예시 12, 예시 13

**문제 설명**: 예시 12는 `ALTER TABLE ... DROP PRIMARY KEY`를 단독으로 실행하면 에러가 난다고 말합니다(RK 후보가 0개가 되므로). 그런데 예시 13은 `ALTER TABLE table_name DROP CONSTRAINT PRIMARY KEY, ADD CONSTRAINT PRIMARY KEY(a)`처럼 DROP과 ADD를 한 문장(콤마로 연결된 복수 절)에 넣으면 OK라고 말합니다. 이 둘을 같이 보면, 검증이 "각 절을 순서대로 적용하면서 매 순간 RK가 있는지 확인"하는 것이 아니라 "문장 전체를 적용한 최종 상태만 확인"하는 방식임을 암시합니다. 그런데 이 평가 모델(절 단위 vs 문장 단위)이 스펙 어디에도 명시적으로 정의되어 있지 않습니다.

**구체 예제**:
```sql
-- 예시 12: 단독 DROP -> 에러 (중간 상태가 곧 최종 상태이므로 RK 0개)
csql> ALTER TABLE tbl DROP PRIMARY KEY;
-- ERROR

-- 예시 13: DROP+ADD 한 문장 -> OK (최종 상태에는 RK가 있으므로)
csql> ALTER TABLE tbl DROP CONSTRAINT PRIMARY KEY, ADD CONSTRAINT PRIMARY KEY(a);
-- OK

-- 그렇다면 이건 어떻게 되는가? 스펙 침묵.
csql> ALTER TABLE tbl DROP CONSTRAINT PRIMARY KEY, ADD COLUMN d INT, ADD CONSTRAINT PRIMARY KEY(a, d);
```

**예제 설명**: 마지막 문장은 "PK를 지우고, 새 컬럼을 만들고, 그 새 컬럼을 포함해 새 PK를 건다"는 흔한 스키마 확장 패턴(복합키로 전환)입니다. 이게 허용되는지 스펙만으로는 판단할 수 없습니다. 마이그레이션 도구(Liquibase의 `addColumn` + `addPrimaryKey` changeSet 조합)는 이런 다단계 변경을 자동 생성하는데, 검증 모델이 "문장 단위 최종 상태"라는 게 확정되지 않으면 어떤 조합의 ALTER가 안전한지 예측할 수 없습니다.

**제안**: "RK 제약 검증은 하나의 ALTER TABLE 문에 포함된 모든 절을 적용한 이후의 최종 카탈로그 상태를 기준으로 한다"는 문장을 §4-2에 명시적으로 추가해야 합니다. 아울러 이 규칙이 트랜잭션 여러 개(멀티 스테이트먼트)에는 적용되지 않는다는 점(즉 별도 ALTER 문으로 나누면 중간 상태에서 에러가 날 수 있다는 점)도 명시해야 합니다.

### 리뷰 6

**[심각도: 보통] PK→UK 전환 시 "UK 먼저 추가, PK 나중에 제거"라는 순서가 권고일 뿐 강제되지 않는다**

**대상**: §4-2 "복제키를 PK에서 UK로 변경하는 경우... UK 추가, PK 제거 로 가이드 됨"

**문제 설명**: 스펙은 "가이드 됨"이라고만 적었을 뿐, 반대 순서(PK를 먼저 지우고 UK를 나중에 추가)로 실행했을 때 무슨 일이 일어나는지 다루지 않습니다. 리뷰 5에서 지적한 것처럼 검증이 문장 단위라면 한 문장 안에서 순서를 바꿔도 결과는 같을 수 있지만, 별도의 두 ALTER 문(전형적인 마이그레이션 스크립트 2단계 배포)으로 나눠 실행하면 순서에 따라 중간 상태에서 RK가 0개가 되는 시점이 생길 수 있습니다.

**구체 예제**:
```sql
-- 마이그레이션 스크립트 V20 (개발자가 "가이드"를 못 보고 반대 순서로 작성)
-- Step 1
csql> ALTER TABLE tbl DROP CONSTRAINT PRIMARY KEY;
-- 이 시점에 RK 후보가 0개가 되어 에러가 나야 정상(예시 12와 동일 상황)이지만
-- 만약 엔진이 "이 트랜잭션이 커밋되기 전까지는 아직 유예"하는 식으로 구현되어 있다면?

-- Step 2 (별도 배포, 별도 트랜잭션)
csql> ALTER TABLE tbl ADD CONSTRAINT UNIQUE(b);
```

**예제 설명**: 이 두 단계가 서로 다른 배포(다른 Flyway 버전 파일)로 나뉘어 있다면, Step 1만 배포된 상태로 애플리케이션이 한동안(다음 배포 전까지) 운영되는 구간이 반드시 생깁니다. 이 구간에서 테이블에 RK가 없는 상태로 HA가 계속 돌고 있다면, 배경 설명에 나온 원래 버그(복제 누락 + fail_count 증가)가 새 스펙에서도 형태를 바꿔 재현될 수 있습니다. 즉 "가이드"라는 표현은 순서를 지키지 않은 사용자에게 안전망이 되지 못합니다.

**제안**: 순서를 어겼을 때(PK 먼저 제거)의 동작을 예시 12와 동일하게 "에러로 즉시 차단"한다고 명시하거나, 혹은 엔진이 두 ALTER 사이의 과도기를 허용하지 않는다는 점(즉 매 DDL 커밋마다 RK가 반드시 1개 이상 있어야 한다는 불변조건)을 §4-2 서두에 원칙으로 못박아야 합니다.

### 리뷰 7

**[심각도: 보통] 예시 7 "Multiple ALTER"는 실제 컬럼명 없이 "..."로만 표기되어 그대로 실행할 수 없다**

**대상**: 예시 7 `ALTER TABLE tbl DROP CONSTRAINT ..., ADD CONSTRAINT ...;`

**문제 설명**: 스펙의 다른 모든 예시(11~16 등)는 실제 컬럼명과 제약 이름을 명시해 그대로 복사해서 실행할 수 있는 반면, 예시 7만 유일하게 자리표시자("...")로 남아 있습니다. "HA 환경에서 PK를 복제키로 사용하던 중 다른 컬럼으로 변경해야한다면"이라는 가장 중요한 시나리오를 보여주는 예제인데, 정작 이 예제만 추상적이라 응용 개발자가 실제 마이그레이션 스크립트를 작성할 때 참고할 수 없습니다.

**구체 예제**:
```sql
-- 스펙 원문 (실행 불가능한 자리표시자)
csql> ALTER TABLE tbl DROP CONSTRAINT ..., ADD CONSTRAINT ...;

-- 응용 개발자가 실제로 필요한 형태 (예시 13과 사실상 동일해 보이는데, 왜 별도 예시로 존재하는지도 불명확)
csql> ALTER TABLE tbl DROP CONSTRAINT pk_tbl_a, ADD CONSTRAINT PRIMARY KEY(c);
```

**예제 설명**: 예시 7과 예시 13은 문면상 거의 같은 시나리오(PK를 다른 컬럼으로 바꾸는 것)를 다루는 것처럼 보이는데, 예시 7은 §2-2(일반 ALTER 옵션 설명 절)에, 예시 13은 §4-2(HA 제약사항 절)에 중복해서 등장합니다. 이게 의도적으로 같은 것을 두 번 보여주는 것인지, 아니면 §2-2 예시 7이 더 일반적인 "임의의 제약 교체"이고 §4-2 예시 13이 "PK 한정" 특수 케이스인지 스펙만으로는 구분할 수 없습니다.

**제안**: 예시 7에 실제 컬럼명을 채우고, 예시 13과의 관계(둘이 같은 것을 가리키는지, 아니면 범위가 다른지)를 각주로 명시해야 합니다.

### 리뷰 8

**[심각도: 치명] FK 참조 무결성 검사가 CREATE/ALTER FK 시점에만 있고, 참조 테이블을 나중에 REPLICATION=OFF로 내리는 경로는 검증하지 않는다**

**대상**: §5 외래키, 예시 18(생성 시점 차단), §4 "HA 환경 복제 제외테이블은 ALTER TABLE … REPLICATION=ON 을 이용한 복제 테이블로 변경하는것 외의 모든 DDL을 사용할 수 있다"

**문제 설명**: 예시 18은 FK를 REPLICATION=OFF 테이블에 걸려고 하면 CREATE 시점에 에러를 낸다고 명시합니다. 그런데 §4를 보면 "복제 제외 테이블은 ON으로 바꾸는 것 외 모든 DDL 허용"이라고 되어 있을 뿐, "복제 테이블(ON)을 OFF로 바꾸는 ALTER"에 대한 제약은 전혀 언급되지 않습니다. 즉 FK로 참조당하고 있는 정상적인 복제 테이블을 운영 도중 `ALTER TABLE ... REPLICATION=OFF`로 내리는 것이 막혀 있지 않다면, CREATE 시점에 그렇게 힘들게 차단한 "다이어그램의 그 문제 상황"(FK 참조 테이블이 슬레이브에 없어 failover 후 애플리케이션이 접근 실패)이 ALTER 경로로 그대로 재현됩니다.

**구체 예제**:
```sql
-- 예시 17의 정상 구성 (customers는 REPLICATION=ON, orders가 FK로 참조)
csql> CREATE TABLE customers(
    customer_id INT PRIMARY KEY,
    country INT
);
csql> CREATE TABLE orders(
    order_id INT PRIMARY KEY,
    customer_id INT,
    CONSTRAINT fk_customer_id FOREIGN KEY (customer_id) REFERENCES customers(customer_id)
);
-- 여기까지는 스펙 예시 17 그대로, OK

-- 이후 운영 중 누군가(혹은 자동화 스크립트)가 customers를 복제 제외로 전환
csql> ALTER TABLE customers REPLICATION = OFF;
-- 스펙 §4/§5 어디에도 이 문장을 막는다는 규정이 없음. 성공한다고 가정하면:

-- Failover 발생 -> 애플리케이션이 슬레이브의 orders에 접근
-- -> orders.customer_id가 참조해야 할 customers 데이터가 슬레이브에 없음
-- -> 원본 다이어그램이 경고하던 바로 그 상황이 재현됨
```

**예제 설명**: 예시 18이 막으려던 것은 "처음부터 잘못 만드는 것"인데, 이 예제는 "처음엔 맞게 만들었다가 나중에 잘못된 상태로 바꾸는 것"입니다. FK 제약이 카탈로그에 존재하는 한, 참조 테이블의 REPLICATION 속성 변경도 FK 무결성 검사의 대상이 되어야 논리적으로 일관됩니다. 스펙이 CREATE 시점 검사만 명시하고 ALTER 경로를 침묵한 것은, 어렵게 도입한 안전장치에 구멍을 남긴 것입니다.

**제안**: §4 규칙에 "다른 복제 테이블이 FK로 참조하고 있는 복제 테이블은 REPLICATION=OFF로 전환할 수 없다"는 제약을 추가하고, 이를 예시로도 보여줘야 합니다(예시 18과 대칭되는 "ALTER 버전" 예시가 필요).

### 리뷰 9

**[심각도: 중요] VIEW는 복제 제외 테이블 참조를 에러 없이 허용하는데, FK는 동일 상황에서 에러를 낸다 — 검증 정책이 일관되지 않는다**

**대상**: §5(FK, 예시 18 ERROR) vs §6 뷰(VIEW) ("Failover 후 뷰 사용에는 제약이 없다... 결과는 두 노드가 일치하지 않는다... 책임지지 않는다")

**문제 설명**: 같은 문제 상황(복제 제외 테이블을 다른 객체가 참조)에 대해 FK는 생성 시점에 강하게 막고(예시 18), VIEW는 생성 시점에 아무 제약 없이 허용한 뒤 "책임지지 않는다"고만 합니다. 애플리케이션 개발자 입장에서는 두 메커니즘 다 "복제 제외 테이블을 참조하는 다른 스키마 객체"라는 점에서 본질이 같은데, 왜 한쪽은 강한 보증(에러)을 주고 다른 쪽은 약한 보증(사후 책임 회피)만 주는지 설계 근거가 스펙에 없습니다.

**구체 예제**:
```sql
csql> CREATE TABLE non_repl_customers(
    customer_id INT PRIMARY KEY,
    country INT
) REPLICATION = OFF;

-- FK로 참조하면 CREATE 시점에 에러 (스펙 예시 18)
csql> CREATE TABLE orders(
    order_id INT PRIMARY KEY,
    customer_id INT,
    CONSTRAINT fk_c FOREIGN KEY (customer_id) REFERENCES non_repl_customers(customer_id)
);
-- ERROR

-- 그런데 VIEW로 참조하면 에러 없이 통과
csql> CREATE VIEW order_summary AS
    SELECT o.order_id, c.country
    FROM orders o JOIN non_repl_customers c ON o.customer_id = c.customer_id;
-- OK (스펙 §6에 따르면 아무 제약 없음)
```

**예제 설명**: `order_summary` 뷰는 마스터에서는 정상 작동하지만, failover 후 슬레이브에서는 `non_repl_customers`가 비어 있어 JOIN 결과가 항상 빈 집합이거나 부분적으로만 채워집니다. FK는 이런 상황을 아예 원천 차단하면서, 논리적으로 거의 동일한 위험을 가진 VIEW는 방치하는 것은 애플리케이션 개발자에게 "어디까지가 안전장치의 보호범위인지" 예측 불가능하게 만듭니다. VIEW가 FK보다 검사가 어렵다는 기술적 이유(뷰 정의는 임의의 JOIN/서브쿼리를 포함할 수 있어 정적 분석이 복잡함)는 이해되지만, 그렇다면 최소한 "이 뷰는 복제 제외 테이블을 참조합니다"라는 경고를 CREATE VIEW 시점에 출력하는 정도는 가능할 것입니다.

**제안**: 최소 요구사항으로 CREATE/ALTER VIEW 시점에 복제 제외 테이블 참조 여부를 카탈로그 조회로 검사해 경고(에러는 아니더라도)를 내도록 하고, 이 비일관성에 대한 설계 근거를 문서에 남겨야 합니다.

### 리뷰 10

**[심각도: 보통] FK 예제가 전부 단일 컬럼·비순환 참조만 다루어 복합키/자기참조/순환참조 FK의 RK-REPLICATION 검증 순서가 정의되지 않았다**

**대상**: §5 외래키, 예시 17~23

**문제 설명**: JPA/Hibernate로 도메인 모델을 설계할 때 자기참조(예: `Employee.managerId -> Employee.id`, 조직도 트리 구조)나 두 테이블이 서로를 참조하는 순환 FK(예: `orders.latest_invoice_id -> invoices.id`이면서 `invoices.order_id -> orders.id`)는 드물지 않은 패턴입니다. 스펙의 모든 FK 예시는 `orders -> customers`처럼 한 방향, 단일 컬럼짜리만 다루고 있어, 다음과 같은 질문에 답이 없습니다: 자기참조 FK가 걸린 테이블이 REPLICATION=OFF이면 이건 "자기 자신을 참조하므로 자기 자신이 복제 대상이어야 한다"는 규칙을 자명하게 통과하는가, 아니면 별도 처리가 필요한가? 순환 FK에서 두 테이블 중 하나만 나중에 OFF로 전환하려 하면 어느 쪽이 막히는가?

**구체 예제**:
```sql
-- 자기참조 FK
csql> CREATE TABLE employee(
    emp_id INT PRIMARY KEY,
    manager_id INT,
    CONSTRAINT fk_manager FOREIGN KEY (manager_id) REFERENCES employee(emp_id)
) REPLICATION = OFF;
-- REPLICATION=OFF인 테이블이 자기 자신을 참조. §5 규칙("참조 테이블은 복제 대상이어야 한다")을
-- 문자 그대로 적용하면 employee 자신이 복제 대상이 아니므로 위반인가?
-- 아니면 자기참조는 예외인가? 스펙 침묵.
```

**예제 설명**: 이 CREATE TABLE 문이 성공해야 하는지 실패해야 하는지 스펙만으로는 판단할 수 없습니다. 만약 "참조 테이블 ≠ 자기 자신일 때만 검사"라는 암묵적 예외가 있다면 명시해야 하고, 없다면 자기참조 FK를 가진 테이블은 원천적으로 REPLICATION=OFF가 불가능하다는 부작용이 생기는데 이 역시 문서화되어야 합니다.

**제안**: 자기참조 FK와 순환 FK 케이스를 예시에 최소 1개씩 추가하고, 검사 로직이 "참조 테이블 self 여부"를 어떻게 다루는지 명시해야 합니다.

### 리뷰 11

**[심각도: 보통] FK 컬럼이 동시에 UK(RK 후보)인 경우, FK 삭제와 RK 규칙이 교차하는 지점이 스펙에 없다**

**대상**: 예시 21/22 "복제 테이블을 참조하는 외래키(컬럼) 제거", §4-2 RK 후보 제약

**문제 설명**: 예시 21/22는 FK나 FK 컬럼을 삭제하는 것이 "항상 OK"라고 보여줍니다. 그런데 만약 그 FK 컬럼이 동시에 해당 테이블의 UK(즉 RK 후보)이기도 하다면 어떻게 될까요? FK 삭제 규칙만 보면 OK이지만, §4-2의 "복제키로 사용중인 컬럼은 UNIQUE 제약을 삭제할 수 없음"(예시 15) 규칙과 충돌할 수 있습니다.

**구체 예제**:
```sql
-- customer_id가 FK이면서 동시에 UK(즉 이 테이블의 유일한 RK 후보)인 케이스
csql> CREATE TABLE orders(
    order_id INT,
    customer_id INT NOT NULL UNIQUE,   -- RK 후보 (PK가 없으므로 이 UK가 RK)
    CONSTRAINT fk_c FOREIGN KEY (customer_id) REFERENCES customers(customer_id)
);

-- FK 컬럼이자 RK인 customer_id 컬럼을 삭제 시도
csql> ALTER TABLE orders DROP COLUMN customer_id;
-- 예시 22 규칙("FK 컬럼 제거는 OK")을 적용하면 OK?
-- 예시 15 규칙("RK로 쓰이는 컬럼의 UNIQUE는 삭제 불가")을 적용하면 ERROR?
-- 두 규칙이 동시에 적용 대상인 컬럼에 대해 스펙은 우선순위를 정하지 않았다.
```

**예제 설명**: 이 컬럼은 "FK 컬럼"이자 "RK로 쓰이는 UK 컬럼"이라는 두 정체성을 동시에 가지고 있습니다. 예시 22는 FK 관점에서 삭제를 허용하지만, 예시 15는 RK 관점에서 삭제를 금지합니다. 두 규칙 중 어느 것이 우선하는지 스펙에 명시되어 있지 않으므로, 이 ALTER 문의 실제 결과를 예측할 방법이 없습니다. 실무에서는 FK 컬럼에 UNIQUE를 거는 1:1 관계 매핑(JPA `@OneToOne`)이 흔하기 때문에 이 조합은 드문 경우가 아닙니다.

**제안**: "한 컬럼이 여러 역할(FK, RK 후보)을 겸할 때는 더 강한 제약(RK 보호)이 우선한다"는 우선순위 규칙을 §4-2 또는 §5에 명시하고, 이 조합의 예시를 추가해야 합니다.

### 리뷰 12

**[심각도: 중요] §7의 "에러와 함께 파일 리스트를 출력"이 자동화 파이프라인이 파싱할 수 있는 형식으로 정의되어 있지 않다**

**대상**: §7 HA 전환

**문제 설명**: "제약사항 위반 시 에러와함께 파일 리스트를 출력한다"는 문장에서 "파일 리스트"가 정확히 무엇인지 정의가 없습니다. 위반한 테이블 이름의 목록을 담은 텍스트 파일인지, 로그 파일 경로 목록인지, 혹은 unloaddb 스타일의 스키마 파일 목록인지 알 수 없습니다. 운영에서 HA 기동/재기동은 대개 자동화된 오케스트레이션 스크립트(예: Kubernetes Operator, Ansible playbook, 사내 배포 도구)로 수행되는데, 이 스크립트가 "왜 실패했는지"를 판단하려면 에러 출력이 기계가 파싱 가능한 정형 포맷(JSON, 혹은 최소한 고정된 grep 가능 포맷)이어야 합니다.

**구체 예제**:
```
# HA 기동 스크립트 (배포 자동화 도구가 실행)
$ cubrid hb start
ERROR: HA 전환 제약사항 위반
파일 리스트:
  - tbl_orders_v2
  - tbl_legacy_sessions
```
```bash
# 자동화 스크립트가 실패 원인을 파싱해서 알림을 보내려 한다
if cubrid hb start 2>&1 | grep -q "제약사항 위반"; then
    # 그런데 "파일 리스트"의 각 항목이 테이블명인지, 파일 경로인지,
    # 한 줄에 몇 개씩 나오는지, 구분자가 무엇인지 스펙에 없어
    # 이 이후의 파싱 로직을 안정적으로 작성할 수 없다.
    send_alert "HA 전환 실패: 원인 불명확한 포맷"
fi
```

**예제 설명**: 사람이 콘솔에서 직접 읽는다면 "파일 리스트"가 대충 무엇을 뜻하는지 짐작할 수 있지만, 자동화된 CI/CD나 오케스트레이션 도구는 출력 포맷이 문서로 확정되어 있지 않으면 파싱 로직을 짤 수 없고, 짜더라도 다음 버전에서 출력 형식이 바뀌면 조용히 깨집니다.

**제안**: 에러 출력 포맷을 스펙에 명시(예: 위반 테이블명, 위반 사유 코드, 총 개수를 포함한 JSON 또는 고정 포맷)하고, 종료 코드(exit code)도 위반 종류별로 구분해야 자동화 스크립트가 안정적으로 원인을 분기 처리할 수 있습니다.

### 리뷰 13

**[심각도: 중요] UNLOADDB의 "복제 여부 저장 변수"가 테이블(클래스) 단위인지 파일 전체 단위인지 불명확해 스테이징 리프레시 워크플로우가 위험하다**

**대상**: §8 UNLOADDB & LOADDB

**문제 설명**: "복제 여부를 저장하는 변수가 설정되어 있지 않다면 복제 대상(Default)으로 간주한다"는 문장에서 이 "변수"가 unload 파일 하나 전체에 대한 것인지, 파일 내부의 각 클래스(테이블) 스키마 정의마다 개별로 존재하는 것인지 알 수 없습니다. 실무에서 스테이징 환경을 운영 데이터로 주기적으로 리프레시하는 작업은 흔한데, 이 작업이 unloaddb/loaddb를 그대로 쓰는지, 혹은 unload 결과를 사람이나 스크립트가 부분 편집(특정 민감 테이블만 제외하고 로드)해서 쓰는지에 따라 결과가 달라질 수 있습니다.

**구체 예제**:
```
# 운영에서 unload (신버전, 클래스별로 복제 여부 기록됨)
$ unloaddb -o schema.unload -i indexes.unload -c customers,orders,session_cache mydb

# 스테이징팀이 개인정보 컴플라이언스 때문에 session_cache 관련 정의만
# 스크립트로 잘라내서 손으로 스키마 파일을 재조립한 뒤 loaddb 수행
$ loaddb -s modified_schema.unload -d ... stagingdb
```

**예제 설명**: 만약 "복제 여부 변수"가 파일 전체 단위(예: 파일 헤더에 한 번만 기록)라면, 손으로 특정 클래스 정의를 잘라내거나 순서를 바꾸는 순간 이 변수가 어느 클래스에 적용되는지 알 수 없게 됩니다. 반대로 클래스별 변수라면 이런 편집에는 안전하지만, 스펙에 어느 쪽인지 나와 있지 않으므로 스테이징 자동화 스크립트를 작성하는 개발자는 "일단 되는 것 같으니 넘어간다"는 식으로 넘어가기 쉽고, 이는 나중에 스테이징에서만 재현되는 복제 관련 버그의 원인이 됩니다.

**제안**: 이 변수가 클래스(테이블) 단위로 스키마 정의 블록 안에 저장된다는 것을 명시하고, unload 파일 포맷 문서에 실제 필드 위치·이름을 기재해야 합니다(§8은 개념만 있고 파일 포맷 언급이 전혀 없습니다).

### 리뷰 14

**[심각도: 보통] LOADDB 시 자동 할당되는 RK가 원본(UNLOAD 시점) 마스터의 RK 선택과 동일함을 보장하는지 스펙이 침묵한다**

**대상**: §8 "복제 테이블의 경우 큐브리드는 자동으로 RK를 할당한다"

**문제 설명**: RK 후보(PK/UK)가 여러 개인 테이블을 unload한 뒤 다른(혹은 재구성된) DB에 load하면, load 시점에 §1의 선택 규칙("PK 우선, 그다음 UK 중 순서상 첫번째")이 다시 적용됩니다. 원본에서 이미 특정 UK가 RK로 확정되어 있었더라도, unload 파일에 "RK로 선택되었던 제약이 어떤 것인지"까지 기록되지 않는다면, load 후 재선택된 RK가 원본과 다를 수 있습니다.

**구체 예제**:
```sql
-- 원본 DB: UK가 2개, barcode가 먼저 선언되어 RK로 선택되어 있던 상태
CREATE TABLE product(
    id INT,
    barcode VARCHAR(32) NOT NULL UNIQUE,  -- 원본에서 RK로 선택됨
    sku VARCHAR(32) NOT NULL UNIQUE
);
```
```
$ unloaddb -c product mydb
# unload 파일에는 barcode/sku가 둘 다 UK라는 스키마 정보만 남고,
# "barcode가 RK로 선택되어 있었다"는 사실 자체는 §1 규칙으로 재계산 가능하므로 저장 안 해도 될 것 같지만,
# 만약 unload/load 사이에 컬럼 선언 순서가 재정렬되거나 병합 스크립트로 컬럼 순서가 바뀌면?

$ loaddb -s reordered_schema.unload targetdb
-- 이제 sku가 먼저 선언되어 sku가 RK로 재선택될 수 있음
```

**예제 설명**: 스키마 정의 파일을 텍스트로 다루다 보면 컬럼/제약 선언 순서가 도구(diff 병합, 포맷터)에 의해 바뀌는 일이 종종 있습니다. RK 선택이 "선언 순서"에 의존하는 한, unload/load 파이프라인 중간에 순서가 재배열되면 원본과 다른 RK가 선택될 수 있고, 이는 다시 §4-2의 ALTER 제약(어느 컬럼을 못 건드리는지)이 원본과 대상 DB에서 서로 달라지는 결과로 이어집니다.

**제안**: unload 파일에 "이 시점에 RK였던 제약 이름"을 명시적으로 기록하고, load 시 가능하면 이를 우선 적용하도록 해야 합니다. 최소한 문서에는 "load 후 RK가 원본과 달라질 수 있다"는 주의사항을 명기해야 합니다.

### 리뷰 15

**[심각도: 치명] ORM의 자동 스키마 생성(auto-DDL)이 운영 HA에 직접 연결된 상태에서 RK 없는 CREATE TABLE을 시도할 때, 트랜잭션 범위와 나머지 엔티티 처리 결과가 정의되지 않았다**

**대상**: §4-1 CREATE TABLE, 예시 10

**문제 설명**: Hibernate의 `hbm2ddl.auto=update`나 `create`처럼, 애플리케이션 기동 시점에 엔티티 클래스들을 스캔해 여러 개의 CREATE TABLE을 순차 실행하는 기능이 실무에서 여전히 종종 쓰입니다(권장되진 않지만 소규모 서비스나 초기 스타트업 단계에서는 흔합니다). 이때 엔티티 매핑 실수로 `@Id` 애노테이션이 빠진 엔티티가 섞여 있으면, 예시 10처럼 HA 모드에서 해당 CREATE TABLE만 에러가 납니다. 문제는 이 실패가 애플리케이션 부팅 시퀀스 전체에 어떤 영향을 주는지(부팅 실패로 애플리케이션이 죽는지, 그 테이블만 스킵하고 나머지는 정상 기동하는지, 이미 만들어진 다른 테이블들은 롤백되는지) 스펙이 전혀 언급하지 않는다는 점입니다. 이건 엔진이 "DDL은 원자적(atomic)으로 처리하는지, 각 CREATE TABLE 문 단위로 독립인지"에 대한 기본 정보인데, 응용 개발자가 배포 실패 시나리오를 설계하려면 반드시 알아야 하는 정보입니다.

**구체 예제**:
```java
// 매핑 실수: @Id 누락 (실무에서 실제로 발생하는 흔한 실수)
@Entity
@Table(name = "audit_trail")
public class AuditTrail {
    // @Id 애노테이션을 빠뜨림
    private String actor;
    private String action;
}
```
```sql
-- Hibernate가 생성하는 DDL (HA 운영 DB에 직접 연결된 상태)
CREATE TABLE audit_trail(actor VARCHAR(255), action VARCHAR(255));
-- 예시 10과 동일한 상황: RK 후보 없음 -> ERROR (HA 모드이므로)
```

**예제 설명**: 이 CREATE TABLE 하나만 실패하는 것인지, 아니면 같은 Hibernate 세션에서 순서상 이후에 생성될 다른(정상적인) 엔티티 테이블들까지 생성이 중단되는지가 스펙에 없습니다. 애플리케이션이 "일부 테이블만 없는 상태"로 기동을 계속한다면 런타임에 예측 불가능한 2차 장애(그 테이블을 쓰는 기능만 죽거나, 아예 그 기능 호출 시 매번 에러)로 이어집니다.

**제안**: 스펙 범위를 벗어나는 ORM 세부사항까지 다룰 필요는 없지만, 최소한 "각 CREATE/ALTER TABLE 문은 독립적인 단위로 성공/실패하며, 하나의 실패가 세션 내 이전에 이미 커밋된 다른 DDL에 영향을 주지 않는다"는 원자성 범위를 §4-1 또는 §2-1에 명시해야 합니다. 이는 ORM 자동 DDL뿐 아니라 Flyway/Liquibase가 여러 CREATE TABLE을 한 마이그레이션 파일에 담을 때도 동일하게 중요한 정보입니다.

### 리뷰 16

**[심각도: 사소] FK 관련 예시(17~23)는 에러 메시지 내용을 전혀 보여주지 않아, 예시 11(메시지 텍스트 제공)과 문서화 깊이가 들쭉날쭉하다**

**대상**: 예시 11 vs 예시 18/20/23 등

**문제 설명**: 예시 11은 `ERROR: Primary key "pk_tbl_a" already defined for class "dba.tbl".`처럼 실제 에러 메시지 텍스트를 보여줍니다. 반면 FK 관련 예시들은 전부 그냥 "ERROR"라고만 적혀 있습니다. 애플리케이션에서 DB 예외를 잡아 사용자 친화적 메시지로 변환하는 로직(예: JPA `ConstraintViolationException` 매핑)을 작성할 때는 정확한 에러 메시지 포맷이나 SQLSTATE 코드가 필요한데, FK 관련 부분은 이 정보가 아예 없습니다.

**구체 예제**:
```sql
csql> CREATE TABLE orders(
    order_id INT PRIMARY KEY,
    customer_id INT,
    CONSTRAINT fk_customer_id FOREIGN KEY (customer_id)
    REFERENCES non_repl_customers(customer_id)
);
-- ERROR   <- 이게 전부. 실제 메시지, 에러 코드 없음
```

**예제 설명**: 응용 개발자가 "이 특정 에러(FK 참조 테이블이 REPLICATION=OFF)"를 잡아서 "관리자에게 문의하세요" 같은 구체적 안내로 바꾸려면 에러 코드나 메시지 패턴이 필요합니다. 지금 상태로는 다른 종류의 FK 에러(예: 참조 테이블 자체가 없음)와 구분할 방법이 문서상 없습니다.

**제안**: 모든 ERROR 예시에 실제 에러 메시지 텍스트(혹은 최소한 에러 코드)를 일관되게 채워야 합니다.

### 리뷰 17

**[심각도: 보통] §1의 HA/싱글 이분법 정의와 §9의 "SA에서도 사용 가능"이 서로 충돌한다**

**대상**: §1 "HA 모드는 'cubrid hb start' 로 큐브리드를 실행시킨 상태를 의미하며 나머지는 모두 싱글모드", §9 "이 키워드는 싱글 이나 SA에서도 사용 가능"

**문제 설명**: §1은 "HA다 아니다"의 이분법만 정의하면서 "나머지는 모두 싱글모드"라고 못박습니다. 그런데 §9 요약에서 갑자기 "SA"(Stand-Alone, 단일 프로세스로 동작하는 모드로 알려진 CUBRID의 또 다른 실행 모드)가 싱글모드와 별개의 것처럼 언급됩니다. CUBRID를 매일 다루지 않는 응용 개발자 입장에서는 "SA가 싱글모드에 포함되는 것인지, 아니면 셋(HA/싱글/SA)으로 나뉘는 것인지"를 스펙 앞부분만 읽고는 알 수 없다가, 맨 끝 요약에서야 다른 용어가 튀어나오는 구성입니다.

**구체 예제**:
```
§1: "HA 모드... 나머지는 모두 싱글모드"  -> 세상은 {HA, 싱글} 두 가지로만 나뉜다고 읽힘

...

§9: "이 키워드는 싱글 이나 SA에서도 사용 가능" -> 갑자기 {싱글, SA}가 별개 항목으로 나열됨
```

**예제 설명**: 배포 자동화 스크립트를 짤 때 "현재 이 서버가 HA인지 아닌지"만 체크하면 되는지, 아니면 SA라는 제3의 상태를 별도로 감지해야 하는지가 이 두 문장만으로는 결정되지 않습니다. CUBRID를 잘 아는 엔진 개발자에게는 자명할 수 있지만, 이 스펙은 "전공 입문서 수준"으로 읽는 응용 개발자도 대상으로 삼아야 하므로 이 용어 불일치는 실제 혼란을 유발합니다.

**제안**: §1에서 실행 모드를 처음 정의할 때 HA/싱글/SA(혹은 SA가 싱글의 부분집합이라면 그 관계)를 한 번에 명확히 나열하고, 이후 절에서는 이 정의를 일관되게 재사용해야 합니다.

### 리뷰 18

**[심각도: 사소] `show create table`(예시 8) 출력이 그대로 재실행했을 때 동일한 테이블을 재현하는지(멱등성) 언급이 없다**

**대상**: 예시 8

**문제 설명**: 스키마 마이그레이션 도구나 백업 스크립트 중에는 `show create table`의 출력을 그대로 저장해두었다가 재해복구(disaster recovery) 시 재실행하는 방식을 쓰는 경우가 있습니다. 예시 8의 출력에는 `REUSE_OID, COLLATE utf8_bin, REPLICATION ON`처럼 여러 옵션이 나열되는데, 이 출력 문자열을 그대로 다시 실행했을 때 완전히 동일한 테이블(제약 이름 포함)이 재현되는지, 아니면 일부 속성(예: 내부적으로 생성된 제약 이름 `pk_tbl_a`)이 재현 과정에서 달라질 수 있는지 스펙이 언급하지 않습니다.

**구체 예제**:
```sql
csql> show create table tbl;
-- 'CREATE TABLE [tbl] ([a] INTEGER NOT NULL, [b] INTEGER,
--  CONSTRAINT [pk_tbl_a] PRIMARY KEY ([a])) REUSE_OID, COLLATE utf8_bin, REPLICATION ON'
```
```sql
-- 이 출력을 그대로 복사해서 다른 DB(혹은 같은 DB의 다른 이름)에 재실행
csql> CREATE TABLE tbl2 ([a] INTEGER NOT NULL, [b] INTEGER,
    CONSTRAINT [pk_tbl_a] PRIMARY KEY ([a])) REUSE_OID, COLLATE utf8_bin, REPLICATION ON;
-- REPLICATION ON이 그대로 재현되는가? RK도 동일하게 PRIMARY KEY(a)로 재현되는가?
```

**예제 설명**: 이 부분 자체가 크게 문제될 가능성은 낮지만("REPLICATION ON"이 명시적으로 출력에 포함되므로 재현될 가능성이 높습니다), 스펙이 명시적으로 "이 출력은 멱등적으로 재실행 가능함을 보장한다"고 선언하지 않으면 도구 개발자는 가정에 의존해야 합니다.

**제안**: `show create table` 출력이 그대로 재실행 가능함(멱등성)을 보장한다는 문장을 §2-3에 한 줄 추가하면 충분합니다.

### 리뷰 19

**[심각도: 중요] REPLICATION 옵션이 테이블 전체 단위로만 존재해, 컬럼 단위 복제 제외(PII 마스킹 등) 요구를 지원하지 못하는 것이 컨셉 자체의 한계다**

**대상**: 컨셉 전체 — §1, §2 REPLICATION 옵션

**문제 설명**: 이번 스펙이 채택한 접근(REPLICATION=ON/OFF를 테이블 단위로만 지정)은 "복제하거나 안 하거나" 둘 중 하나만 고를 수 있습니다. 그런데 실무에서 자주 마주치는 요구는 "이 테이블은 복제하되, 주민등록번호나 카드번호 같은 특정 컬럼만 슬레이브에는 안 두고 싶다(GDPR, 개인정보보호법 등 컴플라이언스 대응, 혹은 슬레이브를 조회 전용 분석 노드로 열어줄 때의 접근 통제)"는 컬럼 단위 요구입니다. 스펙에 채택 배경으로 언급된 PostgreSQL의 REPLICA IDENTITY도 사실 이 문제(RK 선택)만 해결하는 개념이고 컬럼 단위 필터링은 별도 메커니즘(논리 복제 publication의 컬럼 필터 등)으로 제공되는데, 이번 스펙은 그 부분을 아예 다루지 않습니다.

**구체 예제**:
```sql
-- 원하는 것: 테이블 전체는 복제하되 주민등록번호 컬럼만 제외
csql> CREATE TABLE customers(
    customer_id INT PRIMARY KEY,
    name VARCHAR(64),
    resident_reg_no VARCHAR(20)  -- 이 컬럼만 슬레이브에 두고 싶지 않음
) REPLICATION = ON;  -- 하지만 이 옵션은 테이블 전체에만 적용된다

-- 현재 스펙으로 가능한 유일한 우회: 테이블을 쪼개는 것
csql> CREATE TABLE customers_public(
    customer_id INT PRIMARY KEY,
    name VARCHAR(64)
) REPLICATION = ON;

csql> CREATE TABLE customers_sensitive(
    customer_id INT PRIMARY KEY,
    resident_reg_no VARCHAR(20),
    FOREIGN KEY (customer_id) REFERENCES customers_public(customer_id)
) REPLICATION = OFF;
```

**예제 설명**: 테이블을 쪼개는 우회 방법은 스키마 정규화를 컴플라이언스 요구에 맞춰 억지로 재설계하게 만들고, 애플리케이션의 도메인 모델(하나의 `Customer` 엔티티)과 물리 스키마(두 테이블) 사이에 불필요한 괴리를 만듭니다. 또한 JOIN 비용도 추가됩니다. 이는 "성능 때문에 MySQL 방식(모든 컬럼 키)을 배제했다"는 이번 스펙의 설계 철학과는 별개로, 컬럼 단위 요구를 지원하지 않는 것 자체가 향후 컴플라이언스 요구가 들어오면 이번 스펙 전체를 다시 설계해야 할 수도 있다는 리스크입니다.

**제안**: 지금 당장 컬럼 단위 필터링을 구현하라는 것은 아니지만, 스펙 문서에 "이번 버전은 테이블 단위 복제 제어만 지원하며, 컬럼 단위 필터링은 범위 밖"이라고 명시적으로 스코프를 한정해, 향후 요구사항이 들어왔을 때 "이미 알고 있었던 제약"인지 "설계 당시 놓친 부분"인지 구분할 수 있게 해야 합니다.

### 리뷰 20

**[심각도: 보통] "복제 제외 테이블은 REPLICATION=ON 외 모든 DDL 허용"이라는 문구가 DROP TABLE + 동일 이름 재생성 같은 우회 경로를 배제하지 않는다**

**대상**: §4 "HA 환경 복제 제외테이블은 'ALTER TABLE … REPLICATION=ON' 을 이용한 복제 테이블로 변경하는것 외의 모든 DDL을 사용할 수 있다"

**문제 설명**: 이 문장은 ALTER를 통한 전환만 제한할 뿐, DROP TABLE로 복제 제외 테이블을 완전히 지운 뒤 같은 이름으로 REPLICATION=ON 테이블을 새로 CREATE하는 것까지 막지는 않습니다. §4-1에 따르면 HA 모드에서 RK가 있는 CREATE TABLE은 허용되므로, 이 우회 경로를 쓰면 사실상 "복제 제외 → 복제 대상" 전환을 ALTER 없이 이뤄낼 수 있습니다. "모든 DDL 허용"이라는 표현이 이런 우회를 의도한 것인지, 아니면 단순히 서술이 허술한 것인지 불명확합니다.

**구체 예제**:
```sql
-- non_repl_customers는 REPLICATION=OFF (예시 18과 동일 구성), HA 운영 중
csql> DROP TABLE non_repl_customers;
-- §4 문구상 "REPLICATION=ON으로 바꾸는 ALTER"가 아니므로 허용되는 DDL로 보임

csql> CREATE TABLE non_repl_customers(
    customer_id INT PRIMARY KEY,
    country INT
);  -- REPLICATION 옵션 생략 -> 기본값 ON
-- 결과적으로 ALTER REPLICATION=ON을 거치지 않고도 "같은 이름, 같은 데이터 구조"의
-- 테이블이 복제 대상으로 전환된 것과 사실상 동일한 효과
```

**예제 설명**: DROP 시점에는 기존 데이터가 전부 사라지므로 ALTER로 옵션만 바꾸는 것과 완전히 같은 결과는 아니지만(데이터 유실이 발생), 만약 이 DROP+CREATE 직후 애플리케이션이 즉시 데이터를 다시 채워 넣는 배치 작업을 실행한다면, 최종적으로 "복제 제외였던 테이블이 사실상 복제 대상으로 승격"되는 효과를 ALTER 제약을 우회해서 만들어낼 수 있습니다. §4가 ALTER 경로만 막아둔 의도가 "실수로 되돌리기 어려운 대량 데이터 복제 유발을 막기 위함"이라면, 이 우회 경로도 동일한 결과를 낳으므로 규칙의 실효성이 떨어집니다.

**제안**: §4의 제약이 "ALTER 문에만" 적용되는 것인지, 아니면 "DROP 후 재생성을 포함한 모든 우회 경로"까지 포괄하는 의도인지 명시해야 합니다. 후자라면 DROP TABLE 자체에 대한 별도 규칙(예: 복제 제외 테이블 DROP 후 같은 이름으로 즉시 복제 대상 재생성 시 경고)이 필요합니다.
