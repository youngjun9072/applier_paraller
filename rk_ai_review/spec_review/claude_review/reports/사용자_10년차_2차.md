# CUBRID HA 복제 개선 스펙 리뷰 — 최종 사용자(10년차) 관점 · 2차 라운드

## 2차 라운드 개요

1차에서는 스펙 본문이 명시적으로 다루는 §1~§9의 논리적 결함(모순, 비결정성, 예제 오류)을 위주로 훑었다. 2차에서는 스펙이 **아예 언급조차 하지 않는 CUBRID 특유의 다른 객체·기능들**(파티션, 클래스 상속, TDE, collation, 클라이언트 드라이버, 브로커, 권한 체계, failover 승격 이벤트)과의 상호작용, 그리고 문서 자체의 이름짓기·버전 표기 같은 메타적 품질을 중심으로 조사했다. 최종보고서(40개 통합 이슈)에 실린 지점의 재탕은 모두 제외했으며, 통합 이슈가 한 줄로만 스코프 문제를 언급하고 지나간 항목(예: 파티션)은 구체적인 실패 시나리오를 새로 만들어 제시했다.

### 리뷰 21

**[심각도: 중요] REPLICATION 옵션을 변경할 수 있는 권한 수준이 스펙에 정의되어 있지 않다**

대상: §2-2(ALTER TABLE … REPLICATION), 컨셉 전체(권한/보안)

문제 설명: 스펙 전체에 걸쳐 `ALTER TABLE ... REPLICATION=OFF/ON`을 **누가** 실행할 수 있는지에 대한 언급이 전혀 없다. 일반적으로 CUBRID는 테이블 소유자(owner) 또는 DBA 권한을 가진 사용자가 ALTER TABLE을 실행할 수 있는 권한 모델을 갖는다. 그런데 REPLICATION 옵션은 컬럼 추가/삭제 같은 일반 스키마 변경과 성격이 다르다 — 이 스위치 하나가 "이 테이블 데이터가 재해복구(DR, Disaster Recovery: 장애 시 데이터를 잃지 않고 복구하는 체계) 상황에서 살아남는가"를 결정한다. 스펙은 이를 순수한 ALTER TABLE 문법 확장으로만 다루고 있어, 테이블 소유권만 있으면 별도의 승인 절차나 감사(audit, 누가 무엇을 언제 바꿨는지 기록) 없이 누구나 이 스위치를 끌 수 있는 것으로 읽힌다.

구체 예제:
```sql
-- 애플리케이션 서비스 계정(테이블 소유자)이 스키마 정리 스크립트를 돌리다가
-- 실수로 orders 대신 orders_backup을 지정해야 할 것을, orders 자체에 실행
csql> ALTER TABLE orders REPLICATION=OFF;
-- §2-2 예시 6 패턴대로 OK. DBA는 이 변경을 알지 못한 채 몇 주가 지난다.

-- 몇 주 뒤 마스터 장애로 failover 발생
-- 슬레이브에는 이 기간 동안의 orders 데이터가 전혀 없음이 뒤늦게 발견됨
```

예제 설명: 이 시나리오에서 문제가 되는 것은 기술적 결함이 아니라 통제(control)의 부재다. 일반 컬럼 변경 실수는 대체로 즉시 눈에 띄는 에러(타입 불일치, 제약 위반 등)로 나타나지만, REPLICATION=OFF는 SQL 차원에서는 아무 부작용 없이 조용히 성공하고, 그 결과는 몇 주 뒤 failover가 실제로 발생해야만 드러난다. DBA 입장에서는 "이 회사 스키마의 어떤 테이블이 언제 복제 대상에서 빠졌는지" 이력을 추적할 수단조차 없다.

제안: (1) REPLICATION 옵션 변경에 DBA 권한 또는 별도 승인을 요구하는 방안을 검토한다. (2) 최소한 이 옵션이 변경될 때 서버 로그에 "누가, 언제, 어떤 테이블의 REPLICATION을 무엇에서 무엇으로 바꿨는지"를 기록하도록 스펙에 명시한다.

### 리뷰 22

**[심각도: 보통] TDE로 암호화된 테이블의 RK가 마스터/슬레이브 간 키 불일치 상황에서 어떻게 동작하는지 스펙이 침묵한다**

대상: 예시 9(`db_class`의 `tde_algorithm` 필드), 컨셉 전체

문제 설명: 예시 9의 `db_class` 출력에는 `replication` 필드 바로 옆에 `tde_algorithm` 필드가 나란히 존재한다. 이는 CUBRID가 TDE(Transparent Data Encryption: 테이블 데이터를 디스크에 저장할 때 애플리케이션이 알아채지 못하게 자동으로 암호화하는 기능)를 테이블 단위로 지원한다는 뜻이다. 이 스펙은 RK라는 새로운 개념을 도입하면서, 그 RK 컬럼이 TDE로 암호화된 테이블에 속할 경우의 동작을 전혀 다루지 않는다. TDE는 보통 암호화 키를 노드(또는 볼륨) 단위로 관리하므로, 마스터와 슬레이브가 물리적으로 별도 구성된 환경에서 두 노드가 서로 다른 키 관리 체계를 쓸 가능성을 배제할 수 없는데, 이 경우 RK 매칭에 어떤 영향이 있는지 언급이 없다.

구체 예제:
```
-- TDE 적용 테이블: payments(account_no를 RK로 사용, TDE로 account_no 컬럼 자체가 암호화)
-- 슬레이브를 새로 프로비저닝하면서 TDE 키 관리 시스템(KMS)을 마스터와 별도로 구성했다고 가정

마스터: UPDATE payments SET balance = 900 WHERE account_no = 'A-1001';
-- 복제 로그에는 RK 값 'A-1001'이 (암호화된 형태로? 평문으로?) 실려 슬레이브로 전달됨
-- 슬레이브가 이 값으로 자신의 암호화된 컬럼에서 대상 로우를 찾을 수 있는가?
```

예제 설명: 이 질문에 대한 답은 스펙 밖의 구현 디테일(복제 로그가 암호화 이전 값을 담는지, 이후 값을 담는지)에 달려 있지만, 정작 스펙은 TDE의 존재 자체를 언급하지 않는다. 최소한 "TDE와 이번 기능은 서로 독립적으로 동작하며 마스터/슬레이브가 동일한 키 구성을 전제로 한다"는 확인이라도 있어야, TDE를 도입한 고객이 이번 기능을 함께 켤 때 안심할 수 있다.

제안: TDE 적용 테이블이 이번 RK/REPLICATION 기능의 지원 범위에 포함되는지, 포함된다면 마스터/슬레이브 키 구성에 대한 전제조건이 무엇인지 스펙 또는 관련 문서에 한 문단으로 명시한다.

### 리뷰 23

**[심각도: 보통] Collation에 따라 "유일하다"고 판정되는 두 값이 바이트 단위로는 다를 수 있는데, RK가 로우를 찾는 연산이 이를 인식하는지 불명확하다**

대상: §1, 예시 8(`COLLATE utf8_bin`)

문제 설명: collation(콜레이션)은 문자열을 비교·정렬할 때 사용하는 규칙 집합으로, 대소문자를 구분하지 않거나(case-insensitive) 문자열 끝의 공백 유무를 무시하는(PAD SPACE) 등 다양한 비교 방식을 정의한다. UNIQUE 제약은 이 collation 규칙을 기준으로 "같다"고 판단되는 값의 중복을 막는데, 이는 "같다고 판단되는 두 값이 바이트 단위로는 서로 다를 수 있다"는 뜻이기도 하다. 이 스펙은 RK로 선택된 UK 컬럼의 값을 applylogdb(마스터의 변경 로그를 슬레이브에 적용하는 내부 모듈)가 슬레이브에서 대상 로우를 찾는 데 쓴다고 설명하는데, 그 "찾는" 연산이 컬럼의 collation을 그대로 따르는지 아니면 저장된 바이트를 그대로 비교하는지에 대한 언급이 전혀 없다.

구체 예제:
```sql
csql> CREATE TABLE users(
    login_name VARCHAR(30) NOT NULL UNIQUE,  -- collation이 대소문자 무시라고 가정
    display_name VARCHAR(30)
);
-- RK = login_name

-- 마스터에서 표기만 바꾸는 갱신 (collation상 동일값이므로 UNIQUE 위반 아님)
csql> UPDATE users SET login_name = 'ALICE' WHERE login_name = 'Alice';
```

예제 설명: 대소문자를 구분하지 않는 collation에서는 'Alice'와 'ALICE'가 유일성 검사상 "같은 값"이므로 이 UPDATE는 정상적으로 허용된다. 그런데 이 갱신은 RK 컬럼 자체의 값을 바꾸는 것이기도 하다. applylogdb가 슬레이브에서 이전 값 'Alice'를 가진 로우를 찾는 연산이 collation을 인식한 비교라면 문제가 없지만, 만약 내부적으로 정확한 바이트 매치를 쓴다면 이런 "표기만 바뀌는 갱신"이 몰리는 경우(대량 데이터 정규화 배치 등)에 예상치 못한 동작을 할 위험을 배제할 수 없다. 이는 흔한 사례는 아니지만, 스펙이 이 비교 방식 자체를 아예 언급하지 않는다는 점이 문제다.

제안: RK를 이용한 로우 검색 연산이 해당 컬럼에 정의된 collation을 그대로 따른다는 것을 스펙에 명시적으로 못박는다.

### 리뷰 24

**[심각도: 중요] 파티션 테이블에서 파티션을 추가/편입할 때 REPLICATION 옵션의 상속 규칙이 없다**

대상: 컨셉 전체(파티션과의 상호작용), §2-1

문제 설명: CUBRID는 파티션 테이블(하나의 논리적 테이블을 여러 물리적 파티션으로 나눠 저장하는 기능으로, 대용량 시계열 데이터 관리에 흔히 쓰인다)을 지원한다. 이 스펙은 REPLICATION 옵션을 처음부터 끝까지 "테이블" 단위로만 서술하며 파티션이라는 단어 자체가 문서 어디에도 등장하지 않는다. 파티션된 테이블에 새 파티션을 추가하는 것은 일상적인 운영 작업인데, 새로 생기는 파티션이 상위(마스터) 테이블의 REPLICATION 설정을 자동으로 상속하는지, 아니면 §2-1의 기본값 규칙("생략하면 ON")이 파티션 추가 시점에도 독립적으로 다시 적용되는지 스펙만으로는 알 수 없다.

구체 예제:
```sql
-- 마스터 테이블은 REPLICATION=ON, RK=order_id
csql> CREATE TABLE orders(
    order_id INT PRIMARY KEY,
    order_date DATE
)REPLICATION=ON PARTITION BY RANGE (order_date) (
    PARTITION p2025 VALUES LESS THAN ('2026-01-01'),
    PARTITION p2026 VALUES LESS THAN ('2027-01-01')
);

-- 연말에 새 연도 파티션을 추가하는, 매년 반복되는 운영 작업
csql> ALTER TABLE orders ADD PARTITION p2027 VALUES LESS THAN ('2028-01-01');
-- 새로 생기는 p2027 파티션(혹은 그 파티션에 들어가는 데이터)은
-- orders 전체와 동일하게 REPLICATION=ON으로 취급되는가?
-- 스펙 어디에도 파티션이라는 단어가 없으므로 답을 알 수 없다.
```

예제 설명: 파티션 테이블은 대용량 로그·주문 이력 테이블에 흔히 쓰이는데, 이런 테이블이야말로 HA 복제가 절실한 대상이다. "파티션 추가"라는, 스크립트로 자동화되어 매달·매년 반복 실행되는 흔한 운영 작업이 REPLICATION 설정을 놓치는 경로가 될 수 있는지, 아니면 안전하게 상속되는지 스펙만으로는 실무자가 판단할 수 없다.

제안: 파티션 테이블에서 REPLICATION 옵션은 마스터(파티션되지 않은 논리적 테이블) 레벨에서 단일하게 관리되며 모든 파티션에 균일하게 적용된다는 것(혹은 그 반대의 설계)을 명시하고, 파티션 추가/편입 시나리오에 대한 예제를 최소 1개 추가한다.

### 리뷰 25

**[심각도: 중요] Failover로 슬레이브가 새 마스터로 승격될 때 §7의 제약사항이 재검증되는지 불명확하다**

대상: §7, failover 컨셉

문제 설명: §7은 "HA 실행시" 제약사항을 검사한다고 되어 있는데, 이는 문맥상 `cubrid hb start`(§1이 정의한 HA 모드 진입) 시점을 가리키는 것으로 보인다. 그런데 HA 운영 중 발생하는 failover(마스터 장애로 슬레이브가 새 마스터로 승격되는 이벤트)는 최초의 `hb start`와는 다른 이벤트다. 슬레이브가 새 마스터로 승격되는 순간, 그 슬레이브의 카탈로그 상태(RK 존재 여부, FK 참조 대상의 REPLICATION 상태)가 §7이 요구하는 제약을 만족하는지 다시 검증하는지, 아니면 "이미 예전에 hb start를 통과한 적이 있으니" 재검증 없이 그대로 승격이 완료되는지가 스펙에 없다.

구체 예제:
```
1. 마스터 M, 슬레이브 S로 정상 HA 운영 중 (최초 hb start 시 §7 검증을 통과한 상태)
2. 복제 지연(lag)이 있는 상황에서 M에서 RK 관련 ALTER(예시 13 패턴의 DROP+ADD)가
   커밋되었으나, 그 DDL 로그가 아직 S에 도달하기 전에 M이 다운됨
3. S가 새 마스터로 승격(failover) — 이 순간 S의 카탈로그는 여전히 ALTER 이전 상태
4. 승격된 S는 이제 자신이 새 슬레이브(복구된 옛 M 등)를 거느리는 새 마스터가 되어
   HA 운영을 계속한다 — 이때 S 자신이 hb start를 다시 실행하는지는 불명확하다
```

예제 설명: 이 시나리오는 승격된 새 마스터가 hb start 시점에는 존재하지 않았던 상태(복제 지연으로 인해 놓친 DDL 등)를 그대로 안은 채 계속 마스터 역할을 이어갈 수 있음을 보여준다. §7의 검증이 "최초 기동 시 1회"로 한정된다면, failover는 검증이 전혀 이뤄지지 않는 사각지대가 된다. 이는 이 스펙이 원래 막으려던 장애(마스터/슬레이브 데이터 불일치)가 가장 취약한 순간인 failover 직후에 검증 공백을 통해 재발할 수 있다는 뜻이다.

제안: failover(승격) 이벤트 시에도 §7과 동일한 제약사항 검증을 수행하도록 명시하거나, "승격 시에는 재검증하지 않는다"가 의도된 설계라면 그 이유(예: 성능상 재검증이 부담스럽다)를 문서에 밝힌다.

### 리뷰 26

**[심각도: 보통] 새 REPLICATION 관련 에러가 클라이언트 드라이버의 자동 재시도 로직에 의해 일시적 오류로 오인될 위험이 있다**

대상: §4-2, §5(에러가 발생하는 여러 지점), 클라이언트 드라이버 상호작용

문제 설명: 이 스펙이 새로 정의하는 에러들(RK로 쓰이는 제약 삭제 불가, FK 참조 대상이 REPLICATION=OFF 등)은 모두 "영구적인" 에러다 — 몇 번을 재시도해도 스키마를 고치지 않는 한 절대 성공하지 않는다. 반면 HA 환경에서 흔히 발생하는 다른 에러들(failover 진행 중 일시적 연결 끊김, 새 마스터를 찾는 중 등)은 "일시적인" 에러로, 잠시 후 재시도하면 성공한다. 많은 CUBRID 애플리케이션과 배포 자동화 도구는 드라이버 레벨에서 HA 관련 일시적 에러를 자동으로 감지해 재연결·재시도하는 로직을 이미 갖추고 있다. 이 스펙은 새로 추가되는 에러들이 기존의 "일시적 에러" 그룹과 명확히 구분되는 전용 에러 코드를 갖는지 전혀 언급하지 않는다.

구체 예제:
```sql
-- 자동화된 스키마 마이그레이션 파이프라인이 다음 DDL을 실행
csql> ALTER TABLE table_name DROP CONSTRAINT PRIMARY KEY;
-- ERROR (해당 PK가 RK로 사용 중이므로 삭제 불가 — 영구적 실패, 재시도해도 무의미)

-- 만약 이 에러가 기존의 일반 제약조건 위반이나 HA 일시 오류와 같은 코드 범주를 공유한다면,
-- 파이프라인의 "일시 오류 시 재시도" 로직이 이를 곧 해결될 문제로 오판할 수 있다
```

예제 설명: 자동 배포 파이프라인이나 스키마 마이그레이션 툴은 보통 에러 코드를 보고 "이 에러는 재시도할 가치가 있는가"를 기계적으로 판단한다. 새 RK/REPLICATION 관련 에러가 기존 범용 에러 코드를 그대로 재사용한다면 이 판단 자체가 불가능해지고, 최악의 경우 영구히 실패할 스크립트가 타임아웃까지 반복 재시도하면서 다른 정상 트랜잭션이 필요로 하는 스키마 락까지 붙잡고 있는 부수 피해로 이어질 수 있다.

제안: 이 스펙이 도입하는 모든 신규 에러에 "영구적 실패(재시도 무의미)"임을 클라이언트가 식별할 수 있는 전용 에러 코드를 배정하고, 기존 HA 일시 오류 코드 그룹과 명확히 구분한다.

### 리뷰 27

**[심각도: 보통] 동일한 컬럼 집합의 복합 UK를 다른 컬럼 순서로 재선언하면 RK의 내부 처리가 달라지는지 불명확하다**

대상: §1, §4-2

문제 설명: RK가 복합(2개 이상 컬럼) UK일 수 있다는 것은 스펙에 암시되어 있다(§1이 UK의 단수/복수를 구분하지 않고 서술한다). 그런데 동일한 컬럼 집합 (a, b)로 이루어진 UK라도 `UNIQUE(a, b)`로 선언하는 것과 `UNIQUE(b, a)`로 선언하는 것은 논리적 유일성 제약으로는 같지만, 내부적으로는 컬럼 순서가 다른 별개의 복합 인덱스로 취급될 수 있다. 이 스펙은 "같은 컬럼 집합, 다른 선언 순서"의 UK를 DROP 후 재선언하는 경우, RK로 쓰이는 값의 처리(복제 로그에 값이 기록·매칭되는 순서 등)가 영향을 받는지 다루지 않는다.

구체 예제:
```sql
csql> CREATE TABLE t(a INT NOT NULL, b INT NOT NULL, UNIQUE(a, b));  -- RK 후보 = (a,b)

-- 몇 달 뒤 쿼리 성능 튜닝을 위해 선두 컬럼을 바꿔 재구성
-- (복합 인덱스는 흔히 선택도가 높은 컬럼을 앞에 둘수록 효율이 좋아진다)
csql> ALTER TABLE t DROP CONSTRAINT u_t_a_b;
csql> ALTER TABLE t ADD CONSTRAINT UNIQUE(b, a);   -- 같은 컬럼 집합, 순서만 반대
-- 이 재구성이 RK 관점에서 "같은 RK를 유지한 것"인가, "새 RK로 교체된 것"인가?
```

예제 설명: 실무에서 복합 인덱스의 컬럼 순서를 바꾸는 것은 흔한 성능 튜닝 기법이다. 이런 순수 성능 목적의 재구성이 논리적으로는 같은 제약을 다시 선언한 것뿐인데도 RK 입장에서 뭔가 다르게 취급된다면, 사용자는 자신의 튜닝 작업이 복제 안정성에 어떤 영향을 주는지 예측할 수 없게 된다.

제안: 복합 RK의 컬럼 선언 순서가 복제 로그 처리나 매칭 로직에 실질적인 영향을 주는지 여부를 명시하고, 영향을 준다면 이런 재구성 시 경고를 출력하도록 한다.

### 리뷰 28

**[심각도: 중요] CUBRID 고유의 클래스 상속(UNDER) 계층에서 REPLICATION/RK가 어떻게 적용되는지 스펙이 전혀 다루지 않는다**

대상: 컨셉 전체(CUBRID 고유 객체지향 기능과의 상호작용)

문제 설명: CUBRID는 다른 주류 관계형 DBMS와 달리 객체지향 데이터베이스에서 유래한 클래스 상속 기능을 지원한다(`CREATE TABLE ... UNDER 상위테이블` 형태로 서브클래스를 정의하면, 서브클래스는 상위 클래스의 컬럼과 일부 특성을 물려받는다). 이 스펙은 REPLICATION 옵션과 RK 개념을 순수하게 독립적인 "테이블" 단위로만 설명하고 있어, 상속 계층에 있는 서브클래스/수퍼클래스 사이에서 이 두 개념이 어떻게 상호작용하는지에 대한 언급이 전혀 없다.

구체 예제:
```sql
csql> CREATE TABLE vehicle(
    vehicle_id INT PRIMARY KEY,
    brand VARCHAR(30)
) REPLICATION = ON;

csql> CREATE TABLE car(
    trunk_capacity INT
) UNDER vehicle;
-- car는 vehicle의 컬럼(및 PK)을 상속받는다고 가정.
-- car 자체는 REPLICATION 옵션을 지정하지 않았다.
-- (1) car는 vehicle과 동일하게 REPLICATION=ON으로 취급되는가,
--     아니면 §2-1 기본값 규칙이 독립적으로 다시 적용되어 별도로 결정되는가?
-- (2) car의 RK는 상속받은 vehicle_id인가?

csql> ALTER TABLE vehicle REPLICATION=OFF;
-- 상위 클래스가 OFF로 바뀌면 이를 상속한 car도 함께 OFF가 되는가?
```

예제 설명: 이 시나리오는 스펙에 등장하는 어떤 예시로도 답이 나오지 않는다. 상속은 CUBRID의 정체성과도 같은 기능이며, 오래전부터 CUBRID를 도입한 고객일수록 이런 객체지향적 스키마 설계를 실제로 사용하고 있을 가능성이 있다. 이 스펙이 상속 계층을 아예 고려하지 않고 작성되었다면, 그런 기존 고객이 이번 기능을 도입할 때 문서에 없는 사각지대에 부딪히게 된다.

제안: 상속 계층에서 REPLICATION 옵션과 RK 결정 규칙을 명시하거나, 최소한 "상속 계층을 사용하는 테이블은 이번 기능의 지원 범위에서 제외한다"는 스코프 제한을 명문화한다.

### 리뷰 29

**[심각도: 사소] "REPLICATION"이라는 옵션 이름이 HA 복제 기능 전체를 가리키는 이름과 겹쳐, 문서·에러 로그·커뮤니티 검색에서 모호함을 유발한다**

대상: 컨셉 전체, 용어 설계

문제 설명: 이 스펙이 도입하는 것은 "테이블 단위로 복제 대상 여부를 껐다 켰다 하는 옵션"인데, 그 옵션의 이름으로 CUBRID HA 기능 전체를 가리키는 데 이미 쓰이고 있는 일반명사 "복제(replication)"를 그대로 재사용했다. PostgreSQL이 논리적 복제라는 기능 자체와, 그 안에서 로우 식별 방식을 정하는 테이블 옵션을 각각 "logical replication"과 "REPLICA IDENTITY"로 이름을 다르게 붙인 것과 대비된다. 상위 개념(기능 전체)과 하위 개념(테이블 옵션)이 같은 단어를 공유하면, 사용자가 커뮤니티나 이슈 트래커에서 "복제가 안 돼요"라고 검색·질문할 때 그것이 "HA 복제 기능 자체의 장애"인지 "특정 테이블의 REPLICATION 옵션이 OFF라서 그 테이블만 복제가 안 되는 정상 동작"인지 글만 봐서는 구분되지 않는다.

구체 예제:
```
사용자 질문: "cubrid HA에서 replication이 안 돼요. 마스터에 넣은 데이터가 슬레이브에 없어요."
답변자 A(HA 인프라 장애로 이해): "hb list로 노드 상태부터 확인해보세요. 네트워크는 정상인가요?"
답변자 B(REPLICATION=OFF 테이블로 이해): "혹시 그 테이블 REPLICATION 옵션이 OFF 아닌가요?"
-- 질문 자체에 두 원인 중 어느 쪽인지 구분할 단서가 없어 진단이 늦어진다
```

예제 설명: 이 문제는 기능 결함이 아니라 순수한 이름짓기(naming)의 문제이지만, 매뉴얼·에러 메시지·로그·지원 티켓 전반에서 반복적으로 검색 가능성과 진단 속도를 떨어뜨리는 장기적 비용을 유발한다.

제안: 테이블 옵션의 이름을 "REPLICATION" 대신 상위 개념과 시각적으로 구분되는 이름(예: `REPLICATE` 동사형, `REPL_TARGET` 등)으로 검토하거나, 최소한 매뉴얼 전반에서 "HA 복제"와 "REPLICATION 옵션"처럼 항상 수식어를 붙여 구분해 표기하는 문서 작성 규칙을 정한다.

### 리뷰 30

**[심각도: 사소] 이 기능이 적용되는 CUBRID 버전이 스펙 어디에도 명시되어 있지 않아 호환성 매트릭스를 작성할 수 없다**

대상: §8(하위 버전 언급), 문서 메타데이터

문제 설명: §8은 "하위 버전에서 unload 한 데이터 파일"이라는 표현을 두 번 사용해 이 기능이 특정 시점 이후의 신버전에만 존재한다는 것을 암시한다. 그러나 스펙 어디에도 이 기능이 정확히 어느 CUBRID 버전부터 도입되는지 버전 번호가 명시되어 있지 않다. 실무에서 DBA나 응용 개발자는 "우리 회사가 쓰는 CUBRID 버전에도 이 기능이 있는가, 없다면 어느 버전으로 올려야 하는가"를 확인해야 업그레이드 계획과 호환성 매트릭스(여러 컴포넌트가 어떤 버전 조합에서 함께 동작하는지 정리한 표)를 작성할 수 있는데, 이 스펙만으로는 그 기준점을 알 수 없다.

구체 예제:
```
운영팀 체크리스트에 넣고 싶은 항목:
"CUBRID 버전 X.Y.Z 이상 → REPLICATION 옵션 지원, 미만 → 미지원"
-- 이 문서에는 X.Y.Z에 해당하는 값이 어디에도 없다.
-- §8의 "하위 버전"이 정확히 어느 버전 이하를 가리키는지도 알 수 없다.
```

예제 설명: 버전 번호가 없으면 릴리스 노트 작성자, 업그레이드 가이드 작성자, 그리고 이 문서를 읽고 QA 테스트 계획을 짜야 하는 팀이 각자 다른 가정을 하게 된다. 사소해 보이지만, 사용자 매뉴얼화의 첫 단계(이 내용을 어느 버전 챕터에 넣을 것인가)조차 막는 실무적 공백이다.

제안: 스펙 서두 또는 §8에 이 기능이 적용되는 최소 CUBRID 버전을 명시한다.

## 조사 종료 선언

작업지시가 미개척 영역으로 제시한 항목(파티션, 트리거, 시리얼, 소유자 권한, TDE, collation, REUSE_OID, 에러 코드/메시지 체계, 성능·락, 보안, 멀티 슬레이브, 문서 국제화·용어 일관성)을 각각 실제 CUBRID 기능과 대조하며 훑었다. 그 결과:

- **파티션·TDE·collation·클래스 상속(UNDER)**: 스펙이 전혀 언급하지 않는 CUBRID 고유 객체/기능이라 구체적인 실패 시나리오를 새로 구성해 리뷰 21·22·23·24·28에 반영했다.
- **권한/보안, 클라이언트 드라이버 재시도, failover 승격 재검증, 이름짓기, 버전 표기**: 최종보고서의 40개 통합 이슈 어디에도 없는 각도라 신규로 인정해 리뷰 21·25·26·29·30에 반영했다.
- **트리거**: "트리거가 유발한 간접 DML의 복제 귀속" 문제를 검토했으나, 이는 최종보고서 M-8 영역에서 엔진 개발자 직군의 고유 지적으로 이미 명시되어 있어 어떤 각도로 재구성해도 동일한 실패 모드의 변주에 그쳤다. 신규로 인정하지 않았다.
- **시리얼(SERIAL/AUTO_INCREMENT) failover 동기화, 성능·락, 멀티 슬레이브 확장성**: 최종보고서가 이미 엔진 개발자 고유 지적 및 C-1/C-8/M-9/M-10으로 상세히 다루고 있어, 남은 변형은 표현만 다른 재탕이었다. 신규로 인정하지 않았다.
- **REUSE_OID**: CUBRID 내부 OID 재사용 메커니즘과 RK 매칭의 상호작용을 검토했으나, 이 스펙이 명시한 정보(REUSE_OID는 예시에 등장만 하고 RK와의 관계는 서술이 없음)만으로는 구체적 실패 시나리오를 확신 있게 구성할 근거가 부족했다. 근거 없는 추측을 배제하라는 규칙에 따라 이 항목은 리뷰로 올리지 않았다.

위 근거로, 10건 모두 최종보고서 및 1차 리포트와 겹치지 않는 새로운 실패 모드/각도라고 판단한다. 30개를 채우기 위한 추가 조사는 사소한 표현 트집이나 이미 지적된 이슈의 재포장으로 이어질 것으로 판단해 여기서 조사를 종료한다.
