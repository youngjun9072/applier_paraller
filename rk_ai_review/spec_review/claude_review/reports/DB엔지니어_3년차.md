# CUBRID HA 복제 키(RK) / REPLICATION 옵션 스펙 리뷰
### 리뷰어: DB 엔지니어(DBA·운영자) 3년차 관점

## 리뷰어 소개

CUBRID를 포함한 관계형 DBMS 운영을 3년째 담당하고 있는 DBA다. 주 업무는 HA(High
Availability, 마스터 장애 시 슬레이브가 서비스를 이어받는 고가용성 구성) 클러스터의
일상 모니터링, 정기 업그레이드, 스키마 변경 반영, 장애 시 failover(마스터 장애 시
슬레이브를 새 마스터로 승격시키는 절차) 대응이다. 신규 기능 설계보다는 "이 기능이
운영 중에 실제로 어떻게 동작하고, 새벽에 알람이 울렸을 때 내가 뭘 봐야 하는가"의
관점에서 스펙을 읽는다.

## 총평

이번 스펙은 "PK가 없으면 HA 복제가 깨진다"는 실제 장애 원인을 없애기 위한 방향(복제
키 자동 선택, REPLICATION 옵션 도입) 자체는 합리적이다. 그러나 운영자 관점에서 보면
스펙 대부분이 **정상 경로(happy path)의 SQL 성공/실패 예시**에 집중되어 있고, 운영
중 실제로 문제가 되는 지점 — 장애 중간에 걸린 DDL, 옵션 전환 시 데이터 재동기화,
자동화 스크립트가 파싱해야 할 에러 출력 포맷, 다중 슬레이브 구성, 백업/복원 절차와의
연동 — 은 거의 다뤄지지 않는다. 특히 이번 개선의 출발점이 된 문제(복제 누락 →
fail_count 증가 → 데이터 불일치)가 REPLICATION 옵션 전환이라는 새로운 경로를 통해
그대로 재현될 수 있는 지점을 여러 곳에서 발견했다. 아래 20개 리뷰로 정리한다.

## 리뷰 1

**[심각도: 치명] RK 자동 선택 규칙이 "예시"로만 제시되어 재현 불가능**

- 대상: §1 "UK가 여러개 존재한다면 큐브리드 엔진에 의해 이 중 하나가 선택된다(ex. 테이블내에 명시된 순서 중 가장 빠른 순서)"

**문제 설명**

`ex.`(예를 들어)라는 표현은 이것이 확정된 규칙인지, 아니면 구현체가 실제로는 다른
기준(예: 시스템 카탈로그 내부 OID 순서)을 쓸 수도 있다는 뜻인지 구분이 안 된다.
운영자에게 RK(Replication Key, 슬레이브로 복제할 때 각 행을 식별하는 데 쓰이는 키)가
무엇인지는 단순한 참고 정보가 아니다. 장애 시 "이 테이블이 지금 어떤 컬럼 기준으로
복제되고 있는가"를 알아야 데이터 불일치 여부를 판단할 수 있다. 규칙이 예시 수준으로만
쓰여 있으면, 매뉴얼만 보고는 실제 엔진 동작을 신뢰할 수 없고 반드시 매번 조회
(예시 8, 9)해서 확인해야 하는데, 그마저도 "언제 재계산되는지"가 불명확하면 조회
시점과 실제 적용 시점 사이에 갭이 생긴다.

**구체 예제**

```sql
CREATE TABLE t1 (
    a INT NOT NULL UNIQUE,
    b INT NOT NULL UNIQUE,
    c INT
);
-- 스펙대로라면 "명시된 순서 중 가장 빠른 순서"이므로 a가 RK

-- 몇 주 후, 컬럼 a의 UNIQUE 제약을 재구성 (실무에서 흔한 인덱스 정리 작업)
ALTER TABLE t1 DROP CONSTRAINT u_t1_a;
ALTER TABLE t1 ADD CONSTRAINT UNIQUE (a);

-- 이 시점 RK는 a인가, 아니면 그 사이 b로 넘어갔다가 다시 a로 돌아온 것인가?
```

**예제 설명**

`DROP CONSTRAINT` 로 a의 UK를 지웠다가 다시 만드는 것은 컬럼 정의를 바꾸지 않고
인덱스만 재구성하려는 실무에서 흔히 하는 조작이다. 이 순간 "명시된 순서"가
카탈로그 저장 순서를 의미한다면 a는 이제 b보다 나중에 추가된 UK가 되어 RK가 b로
넘어갈 수도 있다. 반대로 컬럼 정의 순서를 의미한다면 그대로 a가 유지될 수도 있다.
운영자는 이 차이를 미리 알아야, 이후 이 DDL이 §4-2의 "복제키 후보가 1개일 때의
제약사항"에 걸리는지 아닌지를 예측할 수 있다. 규칙이 재현 불가능하면 이 예측 자체가
불가능해진다.

**제안**

RK 결정 규칙을 "테이블 생성 또는 제약 추가 시점의 시스템 카탈로그 순번(예:
`db_constraint` 의 등록 순서)" 처럼 조회 가능한 값으로 명문화하고, 이 순번을
`show create table` / `db_class` 조회 결과에서 확인할 수 있게 해야 한다. "ex." 같은
비확정적 표현은 스펙에서 제거해야 한다.

## 리뷰 2

**[심각도: 치명] HA 전환 실패 시 출력 포맷·종료 코드가 정의되지 않아 자동화 불가**

- 대상: §7 "HA 실행시 다음 사항을 제약사항을 확인하며, 제약사항 위반 시 에러와함께 파일 리스트를 출력한다"

**문제 설명**

운영자는 보통 `cubrid hb start` 를 사람이 손으로 치지 않는다. systemd 유닛이나
배포 스크립트, 모니터링 도구가 감싸서 실행하고, 종료 코드(exit code)와 표준
출력/표준 에러의 형식을 보고 성공/실패를 자동 판정한다. 스펙은 "에러와 함께 파일
리스트를 출력한다"고만 되어 있고, 그 "파일 리스트"가 위반 테이블 이름 목록인지
실제 파일 경로인지조차 불분명하다. 출력 포맷·종료 코드·로그 파일 위치가 정의되지
않으면 자동화 스크립트는 성공/실패를 문자열 그렙(grep)으로 추측해야 하고, 신버전에서
메시지 문구가 바뀌면 그 즉시 감지 로직이 깨진다.

**구체 예제**

```bash
# 배포 스크립트 안에서
$ cubrid hb start testdb
ERROR: replication constraint violation
tbl_a
tbl_b
non_repl_customers

$ echo $?
# 이 값이 0인지 1인지, 위반 건수에 따라 달라지는지 스펙에 없음
```

**예제 설명**

위 예제에서 스크립트가 `cubrid hb start` 실행 후 다음 단계(예: 로드밸런서에 노드
등록, 애플리케이션 트래픽 전환)로 넘어가려면 종료 코드를 봐야 한다. 종료 코드가
0으로 나온다면(스펙에 명시가 없으니 구현이 그렇게 되어 있을 가능성을 배제 못함)
HA가 실제로는 뜨지 않았는데도 트래픽이 전환되는 사고가 날 수 있다. "제약사항 위반
시 에러를 출력한다"는 서술만으로는 이 위험을 배제할 수 없다.

**제안**

실패 시 비정상 종료 코드(0이 아닌 값)를 보장하고, 위반 테이블명·위반 사유
코드·해결 커맨드 예시를 한 줄에 하나씩, 파싱 가능한 고정 포맷(예: 탭 구분 또는
JSON)으로 표준 에러에 출력하도록 스펙에 명시해야 한다.

## 리뷰 3

**[심각도: 치명] REPLICATION=OFF → ON 전환 시 그동안 쌓인 데이터의 재동기화 절차가 없음**

- 대상: §2-2 예시 5, 예시 6, §4-1

**문제 설명**

예시 5는 `ALTER TABLE tbl REPLICATION=ON;` 이 `OK`로 끝난다는 것만 보여준다. 그런데
이 테이블이 그 이전에 `REPLICATION=OFF` 상태로 오랫동안 운영되며 마스터에만 데이터가
쌓였다면, ON으로 전환하는 순간 슬레이브에 과거 데이터가 채워지는지, 아니면 전환
시점 이후의 변경분만 복제되기 시작하는지 스펙에 아무 언급이 없다. 이는 이번 개선의
출발점이 된 문제(복제 누락으로 인한 마스터/슬레이브 불일치)를 REPLICATION 옵션이라는
새 경로로 그대로 재현할 수 있는 지점이다.

**구체 예제**

```sql
-- 마스터, 한 달 전
ALTER TABLE big_orders REPLICATION=OFF;   -- 배치 작업 때문에 임시로 복제 제외

-- 이후 한 달간 500만 건 INSERT 발생 (슬레이브에는 전혀 반영 안 됨)

-- 오늘, 다시 복제 대상으로 전환
ALTER TABLE big_orders REPLICATION=ON;    -- OK (예시 5와 동일 패턴)

-- 슬레이브에서 확인
csql> SELECT COUNT(*) FROM big_orders;
```

**예제 설명**

운영자가 기대하는 결과는 슬레이브에서도 500만 건이 조회되는 것이다. 그러나 §1의
"REPLICATION OFF로 인한 데이터 불일치는 책임지지 않는다"는 면책 조항이 ON으로
되돌린 뒤에도 계속 유효한지, 즉 과거분 갭이 영구히 남는지 알 수 없다. `ALTER TABLE
... REPLICATION=ON` 자체는 §1에 따라 DDL로서 슬레이브에 전달되겠지만, DDL 전달과
데이터 재적재는 별개의 문제다. 이 갭을 인지하지 못한 운영자가 "ON으로 바꿨으니
이제 동기화되겠지"라고 판단하면, 실제로는 슬레이브가 여전히 비어 있는 상태로
failover를 맞이할 수 있다.

**제안**

`REPLICATION=OFF → ON` 전환은 향후 변경분만 복제하며 기존 데이터는 복제되지
않는다는 점을 명문화하거나, 반대로 엔진이 자동으로 풀 재동기화를 수행한다면 그
방법(예: 내부적으로 unloaddb/loaddb를 트리거하는지, 얼마나 오래 걸리는지, 그동안
락이 걸리는지)을 §2-2에 구체적으로 서술해야 한다.

## 리뷰 4

**[심각도: 치명] 복제키 교체 DDL 도중 마스터 장애가 나면 원자성이 보장되는지 불명**

- 대상: §4-2 예시 7, 예시 13, §7

**문제 설명**

예시 13 `ALTER TABLE table_name DROP CONSTRAINT PRIMARY KEY, ADD CONSTRAINT PRIMARY
KEY(a);` 는 DROP과 ADD를 한 문장에 묶어 RK가 없는 순간을 없애는 패턴이다. 그런데
이 한 문장이 마스터의 트랜잭션 로그에서도 하나의 원자적(atomic, 전부 반영되거나
전부 반영되지 않는 성질) 단위로 슬레이브에 전달되는지는 스펙 어디에도 없다. 만약
전달 도중 마스터가 강제 종료되면, 슬레이브는 DROP만 반영하고 ADD는 받지 못한 상태로
남을 수 있다. 이 상태에서 슬레이브가 failover로 승격되면, 승격된 새 마스터에는
§1이 절대 허용하지 않는다고 한 "RK 없는 상태로 HA 운영 중"인 테이블이 실제로
존재하게 된다.

**구체 예제**

```sql
-- 마스터, HA 운영 중
ALTER TABLE tbl DROP CONSTRAINT PRIMARY KEY, ADD CONSTRAINT PRIMARY KEY(a);
-- 이 문장이 슬레이브로 전송되는 도중 마스터 프로세스가 강제 종료(kill -9)됨
```

```
[운영자 조치 순서]
1. 슬레이브를 새 마스터로 승격 (failover)
2. 애플리케이션 트래픽을 새 마스터로 전환
3. csql> SELECT * FROM db_class WHERE class_name='tbl';
   -> 이 시점 tbl에 PK가 있는가, 없는가?
```

**예제 설명**

이 시나리오는 "복제 로그 전송 단위가 SQL 문장 단위보다 작을 수 있는가"라는 구현
디테일에 달려 있는데, 스펙은 이를 전혀 언급하지 않는다. 운영자는 failover 직후 이
불일치를 알아챌 방법도 없다. §1은 "RK가 없으면 HA 모드를 실행할 수 없다"고 했지만
이건 어디까지나 신규 실행(`cubrid hb start`) 시점의 체크이지, 이미 떠 있는 HA
클러스터가 런타임에 RK 없는 상태에 빠지는 것까지 막아주지는 못한다.

**제안**

복제키를 변경하는 DDL은 반드시 단일 복제 로그 레코드(원자적 단위)로 전송되도록
보장하고, failover 직후 승격된 노드가 모든 복제 대상 테이블의 RK 존재 여부를
자동으로 재검증하는 헬스체크 절차를 §7에 추가해야 한다.

## 리뷰 5

**[심각도: 치명] RK 교체를 두 문장으로 나누면 즉시 에러 — 실무 마이그레이션 툴 패턴과 충돌**

- 대상: §4-2 예시 7·13 vs 예시 16

**문제 설명**

예시 7과 예시 13은 `DROP CONSTRAINT ..., ADD CONSTRAINT ...` 를 **하나의 ALTER TABLE
문장**으로 묶어서 성공하는 모습만 보여준다. 반면 예시 16은 "복제키 후보가 없다면
DROP INDEX 는 실패한다"고 명시한다. 이 두 규칙을 합치면, RK 교체를 두 개의 별도
문장으로 나눠 실행하면 반드시 첫 문장에서 에러가 난다는 뜻이 된다. 그런데 실무에서
스키마 변경은 사람이 손으로 한 줄씩 치는 것이 아니라 Liquibase, Flyway 같은
마이그레이션 도구나 DBA의 배치 스크립트로 실행되며, 이런 도구들은 관례적으로 제약
조건 변경을 "옛 제약 제거 → 새 제약 추가"의 별도 단계로 쪼개어 기록한다. 스펙 어디에도
"RK 변경은 반드시 단일 문장이어야 한다"는 경고가 본문에 명시되어 있지 않고, 예시가
우연히 그렇게 짜여 있을 뿐이다.

**구체 예제**

```sql
-- 마이그레이션 툴이 흔히 생성하는 형태 (두 단계로 분리)
-- Step 1
ALTER TABLE tbl DROP CONSTRAINT pk_tbl_a;
-- Step 2
ALTER TABLE tbl ADD CONSTRAINT PRIMARY KEY (b);
```

**예제 설명**

tbl에 PK(a) 하나만 있고 다른 UK 후보가 없는 상태라고 하자. Step 1 실행 순간 tbl은
RK 후보가 0개가 되므로, 예시 16의 규칙("복제키 후보가 없다면 삭제 불가")에 따라 이
`DROP CONSTRAINT` 자체가 ERROR로 거부되어야 정합적이다. 즉 이 패턴을 그대로 마이그
레이션 스크립트에 넣으면 Step 1에서 바로 실패한다. 문제는 이 사실이 본문 규칙
문장이 아니라 예시들 사이의 "행간"으로만 추론 가능하다는 점이다. 3년차 실무자가
매뉴얼의 본문 규칙만 읽고 스크립트를 짰다면 운영 반영 직전에야 이 실패를
발견하게 된다.

**제안**

§4-2 본문에 "복제키를 다른 후보로 교체하는 작업은 반드시 하나의 ALTER TABLE 문
안에서 DROP과 ADD를 동시에 수행해야 하며, 별도 문장으로 나누면 중간 상태에서 실패
한다"는 문장을 명시적으로 추가해야 한다. 또한 대중적인 마이그레이션 도구가 이
제약을 지킬 수 있는지에 대한 가이드(운영 매뉴얼)도 함께 필요하다.

## 리뷰 6

**[심각도: 치명] REPLICATION=OFF로 전환할 때 그 테이블을 참조 중인 FK 관계를 검증하지 않음**

- 대상: §2-2 vs §5

**문제 설명**

§5는 `CREATE TABLE` 시점(예시 18)과 `ALTER TABLE ... ADD CONSTRAINT FOREIGN KEY`
시점(예시 22 다음 문단)에서만 "참조 테이블이 복제 제외면 에러"를 규정한다. 그런데
정상적으로 두 테이블 모두 복제 대상(ON)으로 만들어진 뒤, 나중에 참조되는 쪽
테이블만 `REPLICATION=OFF`로 전환하는 경우는 §2-2 어디에도 검증 로직이 없다. 이는
image.png가 경고하는 "FK 참조 테이블이 슬레이브에 없어 failover 후 애플리케이션이
깨지는" 문제를 그대로, 그것도 CREATE TABLE 단계의 방어를 다 통과한 뒤에 재현하는
경로다.

**구체 예제**

```sql
CREATE TABLE customers(customer_id INT PRIMARY KEY, country INT);
CREATE TABLE orders(
    order_id INT PRIMARY KEY,
    customer_id INT,
    CONSTRAINT fk_customer_id FOREIGN KEY (customer_id) REFERENCES customers(customer_id)
);
-- 예시 17과 동일: 둘 다 REPLICATION 기본값 ON, 문제 없이 생성됨

-- 몇 달 후, 개인정보 이슈로 customers를 슬레이브에 두지 않기로 결정
ALTER TABLE customers REPLICATION=OFF;   -- 이 시점 orders가 customers를 여전히 참조 중
```

**예제 설명**

이 ALTER 문은 §2-2의 "REPLICATION OFF" 규칙(예시 6, "OK")만 놓고 보면 성공해야
한다. 그런데 이 순간부터 `orders`(복제 대상)가 참조하는 `customers`(복제 제외)는
슬레이브에 존재하지 않게 되어, §5가 막으려던 정확히 그 상황이 재현된다. §7의 HA
재시작 체크리스트에는 이 항목이 있지만, HA 클러스터를 무중단으로 계속 띄워둔 채
운영하는 것이 일반적이므로 재시작 없이는 이 위반이 영원히 감지되지 않을 수 있다.

**제안**

`ALTER TABLE ... REPLICATION=OFF` 실행 시, 해당 테이블을 참조하는 FK를 가진
복제 대상 테이블이 하나라도 있으면 실행을 거부하거나 최소한 경고를 출력하도록
§5의 검증 범위를 CREATE 시점뿐 아니라 ALTER 시점까지 확장해야 한다.

## 리뷰 7

**[심각도: 중요] 컬럼 타입/길이 변경이 "복제키를 수정하는 DDL"에 해당하는지 불명**

- 대상: §4-2

**문제 설명**

§4-2가 나열한 예시(11~16)는 전부 제약 추가/삭제, 컬럼 추가/삭제, 인덱스 삭제만
다룬다. RK로 쓰이는 컬럼 자체의 타입이나 길이를 바꾸는 `ALTER TABLE ... MODIFY`
류의 DDL은 예시에 없다. 그런데 이런 변경은 운영 현장에서 매우 흔하다 — 특히 서비스
초기에 INT로 만든 PK가 값 범위를 초과할 것 같아 BIGINT로 넓히는 작업은 3년차
DBA가 자주 마주치는 일이다.

**구체 예제**

```sql
CREATE TABLE tbl (a INT PRIMARY KEY, b VARCHAR(10));
-- HA 운영 중, a가 유일한 RK 후보이자 실제 RK

ALTER TABLE tbl MODIFY a BIGINT;   -- PK 자체는 그대로 두고 타입만 확장
```

**예제 설명**

이 DDL은 PK 제약을 DROP/ADD 하지 않는다. "RK를 수정하는 DDL"의 정의가 제약
자체의 존재 여부(있다/없다)만을 가리키는 것인지, 아니면 RK로 지정된 컬럼의 값
표현 방식(타입)까지 포함하는 것인지 스펙에 정의가 없다. 만약 허용된다면 이 타입
변경이 마스터에서 슬레이브로 전파되는 순서와, 그사이 복제 스트림에 이미 들어와
있는 이전 타입 기준 로그 레코드를 슬레이브가 어떻게 해석하는지도 불명확하다.

**제안**

RK로 사용 중인 컬럼의 타입/길이/정밀도 변경 허용 여부를 §4-2에 명시적인 예시로
추가하고, 허용한다면 복제 로그 적용 순서에 대한 보장 사항도 함께 기술해야 한다.

## 리뷰 8

**[심각도: 중요] fail_count 지표와 이번 스펙이 만드는 새 에러 경로의 관계가 불명**

- 대상: 배경(작업지시), §4

**문제 설명**

이번 개선의 출발점은 "PK 컬럼 변경 시 복제 누락 + applylogdb 에러로 fail_count
증가"였다. 스펙은 §7에서 "HA 실행 시" 제약 위반을 미리 걸러낸다고 했지만, 리뷰 4·6
에서 지적했듯 런타임 중에도 RK 부재나 FK 위반 상태에 빠질 수 있는 경로가 남아
있다. 이런 런타임 위반이 발생했을 때 기존처럼 applylogdb 에러로 fail_count가
올라가는 것인지, 아니면 조용히 스킵되고 아무 지표도 안 오르는 것인지 스펙에 없다.
운영자는 이 지표를 기준으로 알람을 걸어두는데, 새 에러 경로가 기존 지표에
반영되지 않으면 장애를 놓친다.

**구체 예제**

```
[모니터링 시나리오]
- Zabbix/Prometheus에서 cubrid HA의 fail_count를 5분마다 스크레이핑
- 임계치 초과 시 Slack 알람

[의문]
- 리뷰 4의 "RK 교체 도중 failover" 상황에서 fail_count가 오르는가?
- 리뷰 6의 "참조 테이블을 나중에 REPLICATION=OFF로 바꾼" 상황은
  fail_count로 잡히는가, 아니면 그냥 데이터가 조용히 비게 되는가?
```

**예제 설명**

두 시나리오 모두 데이터 불일치를 유발하지만, 발생 경로가 §7의 "HA 시작 시 검증"
범위 밖에 있다. 기존 지표(fail_count)가 이 경로들까지 커버하는지 스펙에 답이
없으므로, 운영자는 "새 기능이 도입된 뒤에도 여전히 조용한 데이터 불일치가
가능한가"라는 가장 중요한 질문에 답할 수 없다.

**제안**

새로 도입되는 위반 상황(런타임 RK 소실, 런타임 FK-REPLICATION 불일치) 각각에
대해 어떤 지표/로그로 관측 가능한지 표로 명시해야 한다. 최소한 별도의 카운터를
신설하거나 기존 fail_count에 통합한다고 명문화해야 한다.

## 리뷰 9

**[심각도: 중요] §5와 §7의 검증 강제성 표현이 서로 달라 필수 요구사항인지 불분명**

- 대상: §5 "확인해 에러를 출력할 수 있어야한다" vs §7 "확인하며 ... 출력한다"

**문제 설명**

§5는 "~할 수 있어야한다"는 능력(capability) 표현을 쓰고, §7은 "~하며 ... 출력한다"는
단정(assertion) 표현을 쓴다. 둘 다 사실상 같은 FK 관련 검증을 설명하는 것처럼
보이는데, 표현이 다르다 보니 이게 하나의 기능을 두 절에서 다르게 서술한 것인지,
아니면 §5는 "향후 추가될 수도 있는 기능"이고 §7만 "이번에 확정 구현되는 기능"인지
구분이 안 된다. 스펙 문서에서 요구사항의 강제성이 애매하면, 구현 완료 여부를
검수(QA)할 기준 자체가 없다는 뜻이고, 운영자는 이 보호장치가 이번 릴리스에 실제로
들어있는지 신뢰할 수 없다.

**구체 예제**

```
§5 원문: "HA 모드 실행 시 외래키 테이블에서 참조하는 테이블의 상태도 확인해
          복제 제외 테이블을 참조할 경우 에러를 출력할 수 있어야한다."
§7 원문: "HA 실행시 다음 사항을 제약사항을 확인하며, 제약사항 위반 시 에러와
          함께 파일 리스트를 출력한다."
         - 외래키를 포함하는 복제 테이블의 참조 테이블이 복제 대상이 아닌경우
```

**예제 설명**

두 문장을 나란히 놓고 보면 검증 대상(참조 테이블의 REPLICATION 상태)은 동일하다.
그런데 §5는 조동사 "~수 있어야한다"로 다소 느슨하게, §7은 "출력한다"로 확정적으로
쓰여 있다. QA 담당자가 테스트 케이스를 작성할 때 §5만 보고 "이건 선택 구현
사항"이라 판단해 테스트를 생략할 위험이 있다.

**제안**

§5와 §7이 같은 요구사항을 가리킨다면 §5의 표현을 §7과 동일한 확정형으로 통일하고,
"이 검증은 §7의 HA 전환 체크에 포함된다"는 상호 참조를 명시해야 한다.

## 리뷰 10

**[심각도: 중요] 예시 12는 에러 메시지 텍스트가 없어 예시 11과 형식이 다름**

- 대상: §4-2 예시 11, 12

**문제 설명**

예시 11은 `ERROR: Primary key "pk_tbl_a" already defined for class "dba.tbl".` 처럼
구체적인 메시지 문자열을 보여준다. 반면 바로 다음의 예시 12(`DROP PRIMARY KEY`,
`DROP COLUMN b`)는 그냥 `ERROR` 라고만 되어 있다. 운영자는 애플리케이션 로그나
`cubrid broker` 로그에서 에러 문자열을 grep해서 원인을 분류하는 자동 알람 규칙을
많이 쓴다. 같은 절 안에서 어떤 예시는 메시지가 있고 어떤 예시는 없으면, 실제
구현체가 이 케이스에 대해 사람이 읽을 수 있는 메시지를 주는지조차 스펙만으로는
확신할 수 없다.

**구체 예제**

```sql
-- 예시 11 (메시지 있음)
csql> ALTER TABLE table_name ADD CONSTRAINT PRIMARY KEY(b);
ERROR: Primary key "pk_tbl_a" already defined for class "dba.tbl".

-- 예시 12 (메시지 없음)
csql> ALTER TABLE table_name DROP PRIMARY KEY;
ERROR
```

**예제 설명**

두 에러가 원인이 완전히 다름에도(하나는 "이미 PK가 있어서 못 만듦", 다른 하나는
"RK로 쓰이고 있어서 못 지움") 후자는 사람이 읽고 원인을 구분할 문구가 스펙에
없다. 운영 스크립트가 "PK already defined"와 "cannot drop replication key"를
서로 다른 알람으로 분류하려면 각 에러마다 고유한 메시지가 필요하다.

**제안**

모든 ERROR 예시에 실제 출력될 메시지 문자열을 채워 넣고, 에러마다 고유한
식별자(에러 코드)를 부여해 운영 스크립트가 원인별로 분기할 수 있게 해야 한다.

## 리뷰 11

**[심각도: 중요] REPLICATION 상태를 테이블 단위로만 조회 가능, 전체 목록을 뽑는 방법이 없음**

- 대상: §2-3 예시 8, 9

**문제 설명**

예시 8(`show create table`)과 예시 9(`select * from db_class`)는 모두 테이블
이름을 하나 지정해서 조회하는 방식이다. 그런데 운영자가 실제로 자주 필요로 하는
질문은 "지금 이 DB에 복제 제외 테이블이 몇 개, 어떤 것들이 있는가"다. 특히
failover나 HA 전환 전 사전 점검, 정기 감사(audit) 시 전체 스키마를 훑어야 하는데,
스펙에는 이를 위한 집계 조회 방법(예: `db_class` 전체를 REPLICATION 컬럼으로
필터링하는 표준 조회문)이 예시로 제공되지 않는다.

**구체 예제**

```sql
-- 스펙이 제공하는 예시 (테이블 하나만)
csql> select * from db_class where class_name = 'tbl';

-- 운영자가 실제로 필요로 하는 조회 (스펙에 없음)
csql> select class_name, replication from db_class
      where is_system_class = 'NO' and replication = 'OFF';
```

**예제 설명**

`db_class`에 `replication` 컬럼이 있다는 것 자체는 예시 9로 알 수 있지만, 이
컬럼을 조건절에서 그대로 필터링할 수 있는지(문자열 'OFF'로 비교하는지, enum
값인지) 스펙에 나와 있지 않다. 운영 매뉴얼에 "복제 제외 테이블 전체 목록 뽑는
법"이 표준 조회문으로 제공되지 않으면, 각 현장마다 다른 방식으로 임시 조회문을
짜게 되고 실수가 발생하기 쉽다.

**제안**

§2-3에 "복제 제외 테이블 전체 목록 조회" 예시를 하나 추가하고, `replication`
컬럼의 정확한 타입과 비교 가능한 리터럴 값을 명시해야 한다.

## 리뷰 12

**[심각도: 중요] 하위 버전 unload 파일을 올릴 때 RK 없는 테이블이 무더기로 생길 위험, 사전 점검 도구 없음**

- 대상: §8

**문제 설명**

§8은 "하위 버전에서 unload 한 데이터 파일에는 복제 여부를 저장하는 변수가
설정되어있지 않으므로 (싱글 모드에서) load 시 모두 복제 테이블로 설정된다"고
한다. 즉 구버전 백업을 신버전으로 복원하면 PK도 UK도 없는 테이블까지 전부
"복제 대상(ON)"으로 잡힌다는 뜻이다. 이런 상태로 그대로 HA를 켜면 §7의 체크에
걸려 무더기로 에러가 날 텐데, load 직후 "이 DB에서 HA 전환을 막을 테이블이
몇 개인지"를 미리 스캔할 도구나 명령이 스펙에 없다. 대량 마이그레이션(예: 구버전
운영 DB를 신버전으로 통째로 이관) 시나리오에서 이는 실무자가 가장 먼저 부딪히는
벽이 될 것이다.

**구체 예제**

```bash
# 구버전(HA 개선 이전)에서 백업
$ unloaddb -o old_backup legacy_db

# 신버전으로 이관, 싱글 모드에서 복원
$ loaddb -d new_db old_backup
# §8에 따르면 old_backup 안의 모든 테이블이 REPLICATION=ON으로 생성됨

# 이 DB를 HA로 전환
$ cubrid hb start new_db
# RK 없는 테이블이 몇 개나 걸릴지 사전에 알 방법이 없음
```

**예제 설명**

레거시 DB에는 PK도 UK도 없는 테이블이 흔히 존재한다(로그성 테이블, 스테이징
테이블 등). 이런 테이블이 load 시 자동으로 복제 대상으로 잡히면, HA 전환
시점에서야 §7의 "제약사항 위반 파일 리스트"로 한꺼번에 쏟아져 나올 수 있다.
수십~수백 개 테이블 규모의 레거시 DB라면 이걸 하나하나 REPLICATION=OFF로
바꾸거나 RK를 추가하는 작업이 이관 작업 전체를 지연시키는 병목이 된다.

**제안**

`loaddb` 완료 직후 또는 별도 유틸리티로 "RK 없는 테이블 목록"을 뽑아주는 사전
점검 명령을 제공해야 한다. 대량 이관 시나리오를 고려해 "RK가 없는 테이블은
로드 시 기본적으로 REPLICATION=OFF로 생성"하는 옵션(현재는 무조건 ON)도
검토할 필요가 있다.

## 리뷰 13

**[심각도: 중요] 다중 슬레이브 구성에 대한 언급이 전혀 없음**

- 대상: 스펙 전체 (특히 §1, §7)

**문제 설명**

스펙 전체가 마스터 1대, 슬레이브 1대를 암묵적으로 가정하고 서술되어 있다("슬레이브로
복제된다", "슬레이브에는 데이터가 존재하지 않아" 등, 항상 단수형). 그런데 CUBRID
HA는 실제로 마스터 1대에 슬레이브 여러 대(replica 포함) 구성을 지원한다. REPLICATION
옵션이나 RK 선택이 슬레이브별로 다르게 적용될 수 있는지(예: 슬레이브 A에는
REPLICATION=ON 테이블만, 슬레이브 B에는 전체를 복제) 아니면 항상 클러스터 전체에
동일하게 적용되는 것인지 스펙에 명시가 없다.

**구체 예제**

```
[운영 구성 예시]
Master
 ├── Slave1 (동일 데이터센터, 즉시 failover 대상)
 └── Slave2 (원격 DR 사이트, 읽기 전용 replica)

customers 테이블을 REPLICATION=OFF로 설정했을 때
-> Slave1과 Slave2 모두에서 customers가 비어있는가?
   아니면 슬레이브별로 다르게 설정할 수 있는 여지가 있는가?
```

**예제 설명**

다중 슬레이브 구성에서는 슬레이브마다 용도가 다른 경우가 흔하다(즉시 failover용
vs 분석/리포팅용 vs 원격 DR용). REPLICATION 옵션이 테이블 전역 속성이라면, 특정
슬레이브에서만 데이터를 제외하고 싶은 요구(예: 원격 DR에는 개인정보 테이블을
아예 안 보내고 싶다)를 이 스펙으로는 만족시킬 수 없다는 뜻인데, 이게 설계상
의도된 제약인지 그냥 언급이 누락된 것인지 알 수 없다.

**제안**

REPLICATION 옵션이 클러스터 전역 속성임을 명시하고, 다중 슬레이브·replica
구성에서의 동작(모든 슬레이브에 동일 적용됨)을 §1 또는 §4에 별도 문장으로
확인해줘야 한다.

## 리뷰 14

**[심각도: 중요] 스위치오버·failover 전 운영자가 실행할 사전 점검 체크리스트/명령이 없음**

- 대상: §5, §7 (image.png 시나리오)

**문제 설명**

image.png가 보여주는 문제(FK 참조 테이블이 복제 제외라 failover 후
애플리케이션이 깨지는 상황)는 스펙이 해결하려는 핵심 시나리오 중 하나다. 그런데
스펙은 이 문제를 "생성 시점에 막는다"(§5)와 "HA 재시작 시 확인한다"(§7)는
두 시점만 다룰 뿐, 정기적으로 예정된 스위치오버(계획된 마스터 교체, downtime
없이 마스터/슬레이브 역할을 바꾸는 운영 절차) 직전에 운영자가 수동으로 돌려볼
수 있는 사전 점검 명령이나 체크리스트를 제공하지 않는다. HA 클러스터는 대개
재시작 없이 몇 달씩 떠 있으므로, "HA 실행 시" 체크만으로는 그 사이에 누적된
위반(리뷰 6 참고)을 스위치오버 직전에 잡아낼 수 없다.

**구체 예제**

```
[운영자가 원하는 절차]
1. 계획된 스위치오버 1시간 전
2. $ cubrid ha_check_replication_consistency new_db   <- 이런 명령이 없음
3. 결과: "customers 테이블이 REPLICATION=OFF인데 orders(ON)가 참조 중" 같은
   사전 경고를 받고 싶음
4. 문제 없으면 스위치오버 진행
```

**예제 설명**

이 시나리오는 실제 있는 명령이 아니라 운영자가 기대하는 이상적인 절차를
예시로 든 것이다. 스펙에는 이런 사전 점검 도구가 전혀 등장하지 않는다. 결과적으로
운영자가 image.png의 사고를 피하려면 스위치오버 때마다 수작업으로 `db_class`와
FK 카탈로그를 조인해서 직접 스크립트를 짜야 하는데, 이는 사람이 실수하기 쉬운
작업이다.

**제안**

"복제 대상 테이블 중 REPLICATION=OFF 테이블을 참조하는 FK가 있는지"를 한 번에
검사하는 관리 명령 또는 시스템 뷰를 제공하고, 계획된 스위치오버 운영 매뉴얼에
이 점검을 필수 절차로 포함해야 한다.

## 리뷰 15

**[심각도: 중요] RK가 PK→UK로 바뀌는 순간, 슬레이브 catch-up 지연 중이면 어느 시점 기준으로 적용되는지 불명**

- 대상: §4-2

**문제 설명**

슬레이브가 마스터를 실시간으로 따라가지 못하고 지연(lag)되어 있는 상황은 운영
중 드물지 않다(대량 배치, 네트워크 지연 등). 이 지연 구간 동안 마스터에서 RK를
PK에서 UK로 교체하는 DDL(예시 13과 유사한 패턴)이 실행되고, 뒤이어 그 사이에
쌓인 데이터 변경 로그가 슬레이브로 순차 적용된다고 하자. 이 로그들 각각이 "RK
교체 이전 시점의 PK 기준"으로 기록된 것인지 "이후 UK 기준"으로 기록된 것인지,
그리고 슬레이브의 applylogdb가 이 전환 경계를 어떻게 인식하는지 스펙에 설명이
없다.

**구체 예제**

```sql
-- 마스터, 슬레이브가 5분 지연 중인 상태
ALTER TABLE tbl DROP CONSTRAINT PRIMARY KEY, ADD CONSTRAINT PRIMARY KEY(new_col);
-- (실질적으로는 PK 컬럼 자체를 바꾸는 것과 유사한 효과, RK가 old PK -> new_col 기준으로 변경)

UPDATE tbl SET x = 1 WHERE old_pk_col = 100;   -- DDL 직후 발생한 UPDATE
```

**예제 설명**

슬레이브가 지연되어 있다면, 이 `UPDATE`에 대한 복제 로그가 슬레이브에 도착할
시점에 슬레이브는 아직 DDL을 반영하기 전일 수도, 반영한 후일 수도 있다. RK 기준
행 식별이 로그 적용 시점의 카탈로그 상태에 의존한다면, DDL과 데이터 변경의
적용 순서가 어긋날 때 엉뚱한 행이 갱신되거나 적용이 실패할 위험이 있다. 이는
운영자가 지연된 슬레이브를 catch-up 시킬 때 실제로 겪을 수 있는 문제인데
스펙에 순서 보장에 대한 언급이 없다.

**제안**

RK 교체 DDL과 후속 데이터 변경 로그가 슬레이브에 반드시 순서대로(DDL 먼저,
그 다음 데이터) 적용됨을 보장한다는 문장을 명시하고, 지연된 슬레이브의
catch-up 중 이 순서가 깨지지 않음을 §4-2 또는 별도 절에 기술해야 한다.

## 리뷰 16

**[심각도: 보통] DROP INDEX 에러 시 어떤 인덱스가 원인인지 식별할 방법이 없음**

- 대상: §4-2 예시 16

**문제 설명**

예시 16은 `DROP INDEX idx_id ON tbl;` 이 "복제키 후보가 없다면" 에러가 난다는
것만 보여준다. 그런데 테이블에 인덱스가 여러 개 있는 실무 상황에서, 어떤
`DROP INDEX` 가 "이게 마지막 RK 후보라서" 막힌 것인지, 아니면 단순 문법 오류나
존재하지 않는 인덱스 이름 때문인지 메시지만으로 구분할 수 없다(메시지 텍스트
자체가 `ERROR` 뿐이라 리뷰 10과 동일한 문제도 겹친다).

**구체 예제**

```sql
CREATE TABLE tbl (
    a INT NOT NULL UNIQUE,
    b INT,
    INDEX idx_b (b)
);
-- RK 후보: a (UK) 하나뿐. idx_b는 일반 인덱스로 RK와 무관.

DROP INDEX idx_b ON tbl;   -- 이건 성공해야 함 (RK와 무관한 인덱스)
DROP INDEX u_tbl_a ON tbl; -- 이건 실패해야 함 (마지막 RK 후보)
```

**예제 설명**

두 `DROP INDEX` 문의 실패/성공 여부가 완전히 다름에도 스펙은 이 구분을 명시적
으로 다루지 않는다. 운영자가 야간 배치로 여러 인덱스를 정리하는 스크립트를
돌리다 하나가 실패했을 때, 로그에 `ERROR` 한 줄만 있으면 "인덱스 이름 오타"와
"RK 후보 소실"을 구분하지 못해 원인 파악에 시간이 걸린다.

**제안**

RK 후보 소실로 인한 DROP INDEX 실패에는 "이 인덱스는 마지막 남은 복제키
후보이므로 삭제할 수 없습니다"처럼 원인을 특정하는 메시지를 부여해야 한다.

## 리뷰 17

**[심각도: 보통] show create table과 db_class의 REPLICATION 표기 형식이 서로 다름**

- 대상: §2-3 예시 8, 9

**문제 설명**

예시 8의 `show create table` 결과는 `REPLICATION ON`(공백 구분, 대문자, 등호
없음)으로 표시되고, 예시 9의 `db_class` 조회 결과는 `replication : ON`(콜론
구분, 컬럼명 소문자)으로 표시된다. 값 자체(`ON`)는 같지만 표시 컨텍스트가 다르다.
사소해 보이지만, 이 스펙의 다른 예시들(예시 5, 6)에서는 `REPLICATION=ON` 처럼
등호를 쓰는 SQL 구문 표기도 섞여 있어, 총 세 가지 표기(`REPLICATION=ON`,
`REPLICATION ON`, `replication : ON`)가 문서 안에 공존한다.

**구체 예제**

```
SQL 구문:        REPLICATION=ON
show create table 출력: ... REPLICATION ON'
db_class 조회 출력:      replication       : 'ON'
```

**예제 설명**

운영 스크립트가 `show create table` 출력을 파싱해서 REPLICATION 값을 뽑아낼 때,
어떤 정규식을 써야 할지가 예시마다 다르게 생겨서 헷갈릴 수 있다. 이 자체가
심각한 결함은 아니지만, 스펙 문서 하나 안에서 표기 일관성이 없다는 것은 문서의
신뢰도를 떨어뜨리고, 실제 구현체의 출력이 어느 쪽을 따를지 예측을 어렵게 한다.

**제안**

SQL 구문 표기(`REPLICATION=ON`)와 조회 결과 표기를 통일된 스타일 가이드에 따라
정리하고, 예시 8·9 표기를 재검토해야 한다.

## 리뷰 18

**[심각도: 보통] 복제 제외 테이블의 백업/재해복구(DR) 정책이 §8에 없음**

- 대상: §8

**문제 설명**

§8은 unload 시 "복제 테이블의 여부를 함께 저장한다"고만 하고, `REPLICATION=OFF`
테이블 자체를 unloaddb가 데이터까지 포함해서 백업하는지, 스키마만 백업하는지는
언급하지 않는다(문맥상 데이터까지 백업하는 것으로 보이지만 명시적이지 않다).
운영자 입장에서는 "복제 제외 테이블 = 슬레이브에 없는 데이터"이므로, 마스터의
정기 백업(unloaddb)이 이 테이블을 확실히 포함하는지가 재해복구 계획의 핵심
전제가 된다. 슬레이브가 데이터 안전망 역할을 못 해주는 테이블이기 때문에
백업이 유일한 안전망인데, 이 부분이 명시적으로 확인되지 않는다.

**구체 예제**

```
[DR 시나리오]
1. non_repl_customers (REPLICATION=OFF) 에 중요 데이터 존재
2. 마스터 디스크 장애로 마스터 자체가 소실
3. 슬레이브를 승격 -> non_repl_customers는 원래부터 슬레이브에 없었으므로 데이터 없음
4. 남은 유일한 복구 수단은 가장 최근 unloaddb 백업

질문: unloaddb는 REPLICATION=OFF 테이블의 데이터를 항상 포함하는가?
      운영자가 백업 정책에서 이를 별도로 신경 써야 하는가?
```

**예제 설명**

이 시나리오는 REPLICATION=OFF 테이블에 대해 "슬레이브도 없고 백업도 안 됐다면"
데이터가 완전히 소실되는 최악의 경우를 보여준다. §8이 unload 대상에서 REPLICATION
옵션과 무관하게 전체 테이블을 항상 백업한다고 명확히 말해주지 않으면, 운영자는
불안한 채로 별도 검증을 해야 한다.

**제안**

§8에 "unloaddb는 REPLICATION 옵션과 무관하게 모든 테이블의 데이터를 백업 대상에
포함한다"는 문장을 명시적으로 추가해, 복제 제외 테이블의 유일한 안전망이 백업임을
운영 매뉴얼에도 강조해야 한다.

## 리뷰 19

**[심각도: 보통] "기존의 제약사항은 유지된다"는 문구가 무엇을 가리키는지 정의가 없음**

- 대상: §4-2 "다른 복제키 후보가 함께 존재한다면 모든 DDL은 허용된다(단, 기존의 제약사항은 유지된다.)"

**문제 설명**

이 문장은 "RK 후보가 2개 이상이면 DDL 제약이 완화된다"는 규칙 뒤에 예외를
붙인 것인데, "기존의 제약사항"이 구체적으로 무엇을 가리키는지 스펙 어디에도
정의되어 있지 않다. §4-2 앞부분에서 이미 나열한 "복제키 후보 1개일 때의
제약사항(예시 11~16)"을 말하는 것인지, 아니면 이번 스펙과 무관한 CUBRID의
기존 DDL 제약(예: PK는 테이블당 1개) 전체를 말하는 것인지 모호하다.

**구체 예제**

```sql
CREATE TABLE tbl (
    a INT PRIMARY KEY,
    b INT NOT NULL UNIQUE,   -- RK 후보 2개: PK(a), UK(b)
    c INT
);

-- RK 후보가 2개이므로 "모든 DDL 허용"에 해당
ALTER TABLE tbl DROP COLUMN a;   -- PK 컬럼을 지운다 -> 허용되는가?
```

**예제 설명**

RK 후보가 2개(PK a, UK b)이므로 규칙상 "모든 DDL은 허용된다"에 해당하지만,
`DROP COLUMN a`는 PK 자체를 삭제하는 조작이다. "기존의 제약사항"이 "테이블에
PK가 있으면 무조건 못 지운다"는 CUBRID 일반 규칙을 의미한다면 이 문장은 여전히
막혀야 하고, 반대로 "RK 유지 제약만"을 의미한다면 통과되어야 한다. 실무자가
사전에 어느 쪽인지 판단할 근거가 스펙에 없다.

**제안**

"기존의 제약사항"이 정확히 어떤 규칙 집합을 가리키는지 각주나 참조 절 번호로
명시하고, 리뷰의 예제와 같은 경계 사례(RK 후보 2개 상태에서 그중 하나를 지우는
DDL)에 대한 예시를 §4-2에 추가해야 한다.

## 리뷰 20

**[심각도: 사소] 신버전 메타데이터를 구버전으로 내리는 다운그레이드 경로가 §8에 없음**

- 대상: §8

**문제 설명**

§8은 "하위 버전에서 unload한 파일을 신버전으로 올리는" 업그레이드 방향만
다룬다. 반대 방향, 즉 신버전에서 REPLICATION 옵션과 RK 메타데이터를 가진
채로 unload한 파일을 구버전(이번 개선이 없는 버전)으로 내려서 복원해야 하는
다운그레이드 상황은 언급이 없다. 릴리스 초기에 신버전에 문제가 발견되어
긴급 롤백해야 하는 경우, 운영자는 이 경로가 안전한지 알아야 한다.

**구체 예제**

```bash
# 신버전(이번 스펙 적용됨)에서 백업
$ unloaddb -o new_backup mydb
# new_backup 안에는 REPLICATION 옵션 값이 테이블별로 저장되어 있음

# 긴급 롤백: 구버전으로 복원 시도
$ loaddb -d mydb_old new_backup   # 구버전 CUBRID 바이너리
```

**예제 설명**

구버전 `loaddb`가 REPLICATION 옵션이라는 새 메타데이터 필드를 이해하지 못하면
로드 자체가 실패할 수도 있고, 조용히 무시하고 진행될 수도 있다. 어느 쪽이든
운영자에게는 "롤백이 가능한가"를 사전에 알아야 하는 중요한 정보인데 스펙에
없다.

**제안**

§8에 신버전 unload 파일을 구버전으로 내리는 다운그레이드 시나리오의 동작(실패/
무시/부분 지원)을 명시하고, 지원하지 않는다면 그 사실을 운영 매뉴얼과 릴리스
노트에 명확히 경고해야 한다.
