# CUBRID HA 복제(REPLICATION 옵션 / RK 자동 선택) 스펙 리뷰
### 리뷰어: DB 엔지니어(DBA/운영), 경력 5년차

저는 CUBRID를 포함한 관계형 DB의 HA(High Availability, 마스터 장애 시 서비스가 끊기지 않도록 슬레이브가 대신 서비스를 이어받는 이중화 구성) 클러스터를 운영하며, failover(장애 조치 — 마스터가 죽었을 때 슬레이브를 새 마스터로 승격시키는 절차)와 스위치오버(계획된 마스터/슬레이브 역할 교체), 백업/복원, 업그레이드를 실무로 처리해온 5년차 엔지니어입니다. 코드 구현보다는 "이 기능이 새벽 3시 장애 상황에서 나를 어떻게 도와주거나 괴롭힐 것인가"를 기준으로 스펙을 읽습니다.

**총평**: 이번 스펙은 PK(Primary Key, 테이블에서 각 행을 유일하게 식별하는 제약)가 없는 테이블 때문에 복제가 조용히 깨지던 기존 문제를 구조적으로 막으려는 시도로서 방향 자체는 타당합니다. 그러나 운영자 관점에서 보면 "정상 경로"에 대한 설명은 상세한 반면, 장애·전환·중간 상태·모니터링처럼 실제로 사고가 나는 지점에 대한 규정이 비어 있습니다. 특히 §8과 §9 사이에서 발견되는 정면 모순(리뷰 1)은 백업/복원 운영자가 어느 쪽을 믿어야 할지조차 알 수 없게 만드는 수준의 결함이며, HA 전환 실패 시 나온다는 "파일 리스트"가 무엇인지, RK(복제 키) 후보가 여러 개에서 0개로 줄어드는 경계 조건에서 언제 검사가 걸리는지 등 다수의 항목이 스펙에 정의되지 않은 채 "엔진이 알아서 판단"한다는 식으로 남아 있습니다. 아래 20개 리뷰는 심각도 순으로 정리했습니다.

---

## 리뷰 1

**[심각도: 치명] §8과 §9가 "복제 여부 미저장 시 기본값"을 정반대로 규정한다**

- **대상**: §8 UNLOADDB & LOADDB 4번째 항목, §9 SUMMARY 7번째 항목

**문제 설명**

unloaddb(데이터베이스 전체를 파일로 내보내는 백업 도구)와 loaddb(그 파일을 다시 적재하는 복원 도구)는 DBA가 정기 백업, 슬레이브 재구성, 다른 서버로의 마이그레이션에 상시로 쓰는 핵심 운영 도구입니다. 그런데 스펙 본문의 두 절이 "복제 여부를 저장하는 변수가 없을 때 어떤 값으로 간주하는가"에 대해 서로 반대로 말하고 있습니다.

- §8: "복제 여부를 저장하는 변수가 설정되어 있지 않다면 **복제 대상(Default)으로 간주**한다."
- §9: "UNLOADDB 시 복제 대상 여부를 함께 출력해야 하며, **이를 포함하지 않는 테이블은 모두 복제 제외 테이블이다.**"

전자는 "변수 없음 → REPLICATION ON", 후자는 "변수 없음 → REPLICATION OFF"로, 정확히 반대입니다.

**구체 예제**

```text
[시나리오]
1. 구버전(이 기능 이전) CUBRID 마스터에서 orders 테이블을 unloaddb 로 백업.
   -> 이 백업 파일에는 복제 여부 변수가 아예 없음(§8/§9 모두 인정하는 전제).

2. 신버전 CUBRID로 업그레이드된 슬레이브 장비에 이 백업 파일을 loaddb 로 복원.

3. 복원된 orders 테이블의 REPLICATION 값은?
   - §8 규정을 따르면: REPLICATION = ON  (복제 대상)
   - §9 규정을 따르면: REPLICATION = OFF (복제 제외 대상)
```

**예제 설명**

같은 입력(변수 없는 구버전 백업 파일)에 대해 스펙 본문 두 곳이 서로 다른 출력(ON vs OFF)을 명시하고 있습니다. 이는 단순 오타 수준이 아니라, 실제로 DBA가 대규모 데이터센터 마이그레이션이나 재해복구 리허설에서 "이 테이블이 복제되는가"를 미리 계산해서 다운타임을 산정해야 할 때, 어느 절을 근거로 삼느냐에 따라 결론이 완전히 달라지는 치명적 모순입니다. 더구나 §8 본문 바로 다음 문장은 "하위 버전에서 unload한 파일은 (싱글 모드에서) load 시 모두 복제 테이블로 설정된다"고 다시 한 번 ON 쪽을 명시하고 있어, §9만 유독 반대 방향으로 적혀 있는 모양새입니다.

**제안**

둘 중 하나가 오타인지, 아니면 "unload 시점의 기본값(§9, OFF)"과 "load 시점의 기본값(§8, ON)"이 서로 다른 별개 규칙인지를 명확히 구분해서 재기술해야 합니다. 후자라면 "unload는 기본 OFF로 표시하지만 load는 변수가 없으면 ON으로 복원한다"는 비대칭 자체가 매우 직관에 반하므로, 왜 그런 비대칭이 필요한지 근거를 스펙에 남겨야 합니다.

## 리뷰 2

**[심각도: 치명] HA 운영 중에는 복제 제외 테이블을 복제 대상으로 편입할 방법이 없다**

- **대상**: §2-2, 예시 5

**문제 설명**

§2-2는 "HA 모드에서는 복제 제외 테이블이 복제 테이블로 변경될 수 없다"고 명시하고, 예시 5(`ALTER TABLE tbl REPLICATION=ON;` → ERROR)로 이를 뒷받침합니다. 즉 운영 중인 HA 클러스터에서 실수로, 혹은 초기 설계상 REPLICATION=OFF로 만들어둔 테이블을 나중에 다시 복제 대상으로 되돌리려면 무조건 싱글 모드로 전환(=HA 중단)해야 한다는 뜻입니다. 이것은 무중단 스키마 변경(온라인 DDL)을 지향하는 현대적 운영 관행과 정면으로 충돌하는 제약입니다.

**구체 예제**

```sql
-- 운영 중인 HA 클러스터, 마스터에서 실행

-- 1) 배치 작업 테이블을 급하게 복제 제외로 만들었다가
csql> ALTER TABLE batch_staging REPLICATION=OFF;
OK

-- 2) 다음날 요구사항이 바뀌어 다시 복제가 필요해졌다
csql> ALTER TABLE batch_staging REPLICATION=ON;
ERROR   -- §2-2에 의해 HA 모드에서는 거부됨
```

**예제 설명**

한 번 REPLICATION=OFF로 내려간 테이블은 HA를 유지한 채로는 되돌릴 방법이 스펙에 없습니다. 결국 운영자가 선택할 수 있는 길은 "전체 클러스터를 싱글 모드로 내렸다가 다시 HA로 올리는" 계획 정지뿐입니다. 이는 서비스 규모가 커질수록(테이블 수백 개, 트래픽 상시 발생) 실질적으로 불가능에 가까운 운영 비용을 요구합니다.

**제안**

REPLICATION=OFF → ON 전환이 왜 HA 중에 위험한지(아마도 슬레이브에 데이터가 없는 상태에서 갑자기 복제를 시작하면 초기 데이터 동기화 문제가 생기기 때문으로 추정됩니다) 이유를 스펙에 명시하고, 대신 "슬레이브에 해당 테이블 데이터를 먼저 수동 동기화한 뒤 ON으로 전환"하는 것과 같은 온라인 절차를 대안으로 제공해야 합니다. 최소한 이 제약이 영구적인지, 향후 버전에서 완화될 계획인지 정도는 언급이 필요합니다.

## 리뷰 3

**[심각도: 치명] 복제키 후보가 2개 이상일 때 한 번의 DDL로 모두 제거하는 경계 조건이 스펙에 없다**

- **대상**: §4-2, 예시 15

**문제 설명**

§4-2는 "복제키 후보가 1개인 경우"에만 삭제 제약을 규정합니다("복제 키로 사용중인 컬럼은 UNIQUE 제약을 삭제할 수 없음"). 그리고 "다른 복제키 후보가 함께 존재한다면 모든 DDL은 허용된다"고 되어 있습니다. 그런데 이 "모든 DDL 허용"이 후보 2개 중 1개만 지우는 경우를 말하는 것인지, 한 문장(ALTER TABLE 하나) 안에서 후보 2개를 동시에 지워 결과적으로 RK 후보 0개 상태로 직행하는 경우까지 포함하는지 스펙이 침묵합니다. CUBRID의 ALTER TABLE은 콤마로 여러 제약 변경을 한 문장에 묶을 수 있으므로(예시 13, 예시 7 참고) 이 조합은 실제로 실행 가능한 문장입니다.

**구체 예제**

```sql
-- 사전 상태: HA 운영 중, PK 없음, UK 2개(u1, u2)가 복제키 후보
csql> CREATE TABLE t (
    a INT NOT NULL UNIQUE,   -- 제약명 u1
    b INT NOT NULL UNIQUE,   -- 제약명 u2
    c INT
) REPLICATION=ON;

-- 현재 RK는 엔진이 "가장 빠른 순서"로 고른 u1 이라고 가정

-- 후보가 2개이므로 "모든 DDL 허용"에 해당 -> 아래 문장은 허용되는가?
csql> ALTER TABLE t DROP CONSTRAINT u1, DROP CONSTRAINT u2;
-- 결과: OK? ERROR? -- 스펙에 명시 없음
```

**예제 설명**

이 한 문장이 성공한다면 실행 직후 테이블 t는 RK 후보가 0개인 채로 HA 복제 대상에 남게 되어, §1의 "복제 키가 없으면 HA 모드를 실행할 수 없다"는 대원칙과 정면으로 충돌하는 상태가 됩니다(이미 HA가 실행 중이므로 "실행할 수 없다"가 아니라 "실행 중인데 위반 상태가 된다"는 더 심각한 문제입니다). 반대로 이 문장이 거부된다면 "복제키 후보가 1개일 때만 제약"이라는 §4-2의 문언과 어긋납니다. 즉 문언 그대로 읽으면 허용되어야 하는데, 허용되면 시스템 불변식이 깨지는 모순 상태입니다. 이런 "복수 제약을 한 문장에서 동시에 제거"하는 경우는 실무 마이그레이션 스크립트에서 흔히 쓰는 패턴이라 반드시 정의가 필요합니다.

**제안**

검사 시점을 명확히 규정해야 합니다. 즉 "ALTER TABLE 문장이 여러 개의 제약 변경을 포함하더라도, 검사는 개별 하위 절 단위가 아니라 문장 전체가 커밋되는 시점의 최종 상태를 기준으로 한다"는 원칙을 §4-2에 추가하고, 최종 상태에서 RK 후보가 0이 되면 전체 문장을 에러로 롤백해야 합니다.

## 리뷰 4

**[심각도: 중요] §7 "에러와 함께 파일 리스트를 출력한다"의 "파일 리스트"가 무엇인지 정의되어 있지 않다**

- **대상**: §7 HA 전환

**문제 설명**

§7은 HA 시작 시 제약 위반이 있으면 "에러와 함께 파일 리스트를 출력한다"고만 되어 있습니다. 이 "파일"이 무엇을 가리키는지(위반 테이블 목록을 담은 임시 텍스트 파일인지, DB 볼륨/스키마 파일 경로인지, 로그 파일 경로인지) 전혀 설명이 없습니다. 장애 대응 매뉴얼(runbook)은 정확한 출력 형식과 파일 위치를 전제로 작성되는데, 이 부분이 비어 있으면 실제 장애 시 운영자가 무엇을 열어봐야 하는지 알 수 없습니다.

**구체 예제**

```text
[장애 대응 시나리오]
새벽 3시, 스위치오버 작업 중 cubrid hb start 실행

$ cubrid hb start mydb
ERROR: HA startup constraint violation.
파일 리스트: ??? <- 이 부분이 실제로 어떤 형태로 출력되는지 스펙에 없음

운영자가 다음 중 무엇을 해야 하는지 스펙만으로는 판단 불가:
(a) 화면에 출력된 텍스트에서 테이블명을 눈으로 읽고 대응
(b) 특정 경로의 파일을 열어서 위반 테이블 목록을 확인
(c) 위반 "테이블"이 아니라 위반 "스키마 파일(.schema)" 경로가 나오는 것이므로
    unloaddb 파일 자체를 열어봐야 함
```

**예제 설명**

새벽 시간대 장애 대응은 시간이 곧 서비스 다운타임이므로, 스크립트로 자동 파싱해서 알림을 보내거나 다음 조치를 자동화하고 싶은 것이 실제 운영 요구입니다. "파일 리스트"라는 표현이 사람이 읽는 콘솔 메시지인지, 별도 저장되는 파일 경로인지조차 불명확하면 자동화가 불가능합니다.

**제안**

출력 형식(예: 표준 에러로 테이블명 목록을 한 줄씩 출력, 혹은 `$CUBRID/log/ha_violation_<db>.log` 같은 고정 경로에 저장)과 그 안에 담기는 항목(테이블명, 위반 사유 코드, 참조 테이블명 등)을 스펙에 명시해야 합니다.

## 리뷰 5

**[심각도: 중요] 복제 제외 테이블·무RK 테이블을 한눈에 파악할 카탈로그 조회 수단이 없다**

- **대상**: §2-3, 예시 8, 예시 9

**문제 설명**

REPLICATION 정보 조회 예시는 `show create table`과 `select * from db_class`뿐이며, 둘 다 테이블 1개씩 확인하는 방식입니다. 테이블이 수십~수백 개인 실 운영 환경에서 "지금 복제 제외로 설정된 테이블이 몇 개이고 무엇인지", "복제 대상인데 RK가 위태롭게 후보 1개만 남은 테이블이 무엇인지"를 한 번에 뽑는 시스템 카탈로그 뷰가 스펙에 전혀 언급되지 않습니다.

**구체 예제**

```sql
-- 운영자가 실제로 원하는 질의(현재 스펙 기준으로는 불가능):
SELECT class_name, replication
FROM db_class
WHERE replication = 'OFF';

-- 또는 RK 후보 개수까지 함께 보고 싶은 질의(더 어려움):
SELECT class_name,
       (SELECT COUNT(*) FROM db_index_key ... ) AS rk_candidate_count
FROM db_class
WHERE replication = 'ON'
  AND rk_candidate_count <= 1;   -- 위태로운 테이블 사전 경보
```

**예제 설명**

db_class에 replication 컬럼이 추가된 것(예시 9)은 확인했지만, 이것만으로는 "전체 스캔"을 사용자가 직접 짜야 합니다. 특히 RK 후보 수를 계산하는 표준 방법이 스펙 어디에도 없어서, "복제 대상인데 후보가 1개만 남아 위험한 테이블"을 사전에 찾아 경고하는 모니터링 스크립트를 만들 근거 자체가 없습니다. 이는 §4-2에서 다루는 위험한 경계(후보 1개 → 삭제 시도 시 에러)에 도달하기 *전에* 운영자가 미리 알아챌 수 있는 유일한 방법인데, 그 재료가 스펙에 없다는 뜻입니다.

**제안**

`db_class`에 RK로 선택된 제약명과 RK 후보 총 개수를 함께 노출하는 컬럼을 추가하거나, `db_replication_status` 같은 전용 시스템 뷰를 신설해서 복제 대상 여부·RK 존재 여부·RK 후보 수를 한 번에 조회할 수 있게 해야 합니다.

## 리뷰 6

**[심각도: 중요] loaddb 시 자동 RK 재할당이 마스터와 다른 결과를 낼 수 있다 — 슬레이브 리빌드 시나리오**

- **대상**: §8 UNLOADDB & LOADDB, 3번째 항목

**문제 설명**

§8은 "복제 테이블의 경우 큐브리드는 자동으로 RK를 할당한다"고 되어 있습니다. RK 선택 규칙(§1)은 "PK 우선, 없으면 UK 중 테이블 내 명시된 순서가 가장 빠른 것"입니다. 그런데 unloaddb 파일에는 데이터와 스키마(제약 정의)가 담기지만, 이 "명시된 순서"라는 것이 재구성 과정에서 원본과 동일하게 보존된다는 보장이 스펙에 없습니다. DBA가 슬레이브를 통째로 새로 만들 때 흔히 쓰는 절차가 "마스터를 unloaddb로 백업 → 새 장비에 loaddb로 복원 → HA 슬레이브로 편입"이므로, 이 재할당 로직은 실무에서 매우 자주 발동합니다.

**구체 예제**

```sql
-- 마스터의 원본 테이블 (u_a가 u_b보다 먼저 선언됨 -> RK = u_a)
CREATE TABLE t (
    a INT NOT NULL UNIQUE,   -- 제약명 u_a, 먼저 선언
    b INT NOT NULL UNIQUE,   -- 제약명 u_b
    c INT
);

-- 1) 마스터: unloaddb -o backup.unl mydb
-- 2) 새 슬레이브 장비: loaddb -d newdb backup.unl
-- 3) loaddb 내부에서 스키마 파일(.schema)의 CONSTRAINT 선언 순서가
--    (예: 알파벳 정렬, 해시맵 순회 등 구현 디테일로 인해) 뒤바뀐다면
--    새 슬레이브에서는 u_b 가 RK로 선택될 수 있음
```

**예제 설명**

만약 마스터는 u_a를 RK로 쓰고 새로 복원된 슬레이브는 u_b를 RK로 쓴다면, 복제 스트림에서 오는 UPDATE/DELETE 레코드가 어떤 키로 슬레이브의 행을 찾아야 하는지에 대해 마스터와 슬레이브의 "합의"가 깨집니다. 이는 곧바로 데이터 불일치 또는 applylogdb(슬레이브에서 복제 로그를 실제 데이터에 반영하는 프로세스) 에러로 이어질 수 있는, 백업/복원이라는 지극히 일상적인 운영 작업에서 발생하는 잠재 결함입니다.

**제안**

unloaddb 파일에 "복제 여부"뿐 아니라 "현재 선택된 RK의 제약명"까지 함께 저장하고, loaddb 시 가능하면 그 제약을 그대로 RK로 재사용하도록 규정해야 합니다. 최소한 "loaddb 후 RK 재계산 결과가 원본과 동일함을 보장한다/보장하지 않는다"를 스펙에 명시해야 합니다.

## 리뷰 7

**[심각도: 중요] 하위 버전 백업을 HA 모드에서 복원하는 경로가 정의되지 않았다**

- **대상**: §8, 마지막 항목

**문제 설명**

§8은 "하위 버전에서 unload한 데이터 파일은 (싱글 모드에서) load 시 모두 복제 테이블로 설정된다"고 명시합니다. 괄호로 "싱글 모드에서"라는 조건을 굳이 붙인 것은 곧 HA 모드에서 이 작업을 하면 다른 결과(혹은 에러)가 난다는 암시로 읽히는데, 그 다른 결과가 무엇인지는 전혀 서술되어 있지 않습니다. 재해복구(DR) 훈련이나 오래된 백업으로부터의 데이터 일부 복구는 HA가 켜진 상태의 운영 DB 옆에서 별도 인스턴스로 수행되는 경우가 흔하지만, "동일 DB를 HA 모드인 채로 하위 버전 백업으로 loaddb"하는 케이스도 실무에서는 발생할 수 있습니다(예: 특정 테이블만 과거 백업에서 복구).

**구체 예제**

```text
[시나리오: 다운그레이드 직후 재해복구]
1. 신버전으로 업그레이드했다가 문제가 생겨 롤백하기로 결정
2. 롤백 전 유지하던 구버전 시절 unloaddb 백업 파일이 있음
3. 신버전 HA 클러스터가 이미 hb start 로 켜진 상태에서
   특정 손상된 테이블만 그 구버전 백업으로 loaddb 시도

$ loaddb -d proddb -u dba old_backup_v1.unl
-- HA 모드인데 "싱글 모드에서"라는 전제 조건을 만족 못 함
-- 결과가 에러인지, ON으로 처리되는지, 다른 동작인지 스펙에 없음
```

**예제 설명**

스펙의 문언이 "싱글 모드에서 load 시"라는 조건절을 굳이 넣었다는 것은 HA 모드에서의 동작이 다르다는 뜻인데 그 내용이 없으므로, 운영자는 이 경로를 시도하기 전에 사전 검증할 방법이 없고, 실제로 겪어보기 전까지는 위험을 예측할 수 없습니다.

**제안**

HA 모드에서 복제 여부 변수가 없는 구버전 백업을 loaddb 할 때의 동작(예: "HA 모드에서는 이 작업 자체를 거부한다" 또는 "역시 ON으로 간주하되 RK가 없으면 §1 규칙에 따라 에러")을 명시적으로 추가해야 합니다.

## 리뷰 8

**[심각도: 중요] PK 교체(예시 13) 도중 DROP과 ADD 사이의 순간, 동시 트랜잭션의 복제 로그 처리가 불명확하다**

- **대상**: 예시 13, §4-2

**문제 설명**

예시 13은 `ALTER TABLE table_name DROP CONSTRAINT PRIMARY KEY, ADD CONSTRAINT PRIMARY KEY(a);` 한 문장이 OK로 성공한다고 서술합니다. 이 문장이 한 트랜잭션으로 원자적(문장 전체가 성공하거나 전체가 실패하는 성질)으로 처리된다면 논리적으로는 문제가 없어 보입니다. 그러나 DBMS 내부적으로 DROP과 ADD가 순차 실행되는 구간 동안, 같은 테이블에 대해 동시에 들어오는 다른 트랜잭션의 INSERT/UPDATE가 어떤 락(lock, 다른 트랜잭션의 동시 접근을 막는 잠금) 레벨로 대기하는지, 그리고 그 동시 트랜잭션이 먼저 커밋되어 복제 로그에 기록될 경우 "구 PK"와 "신 PK" 중 어느 것을 기준으로 레코드가 만들어지는지가 스펙에 없습니다.

**구체 예제**

```sql
-- 세션 1 (DDL 담당자)
csql> ALTER TABLE t DROP CONSTRAINT PRIMARY KEY, ADD CONSTRAINT PRIMARY KEY(b);

-- 세션 2 (동시에 실행되는 애플리케이션 트랜잭션, 세션 1과 겹치는 타이밍)
csql> UPDATE t SET c = c + 1 WHERE a = 100;
csql> COMMIT;

-- 질문: 세션 2의 UPDATE가 복제 로그에 기록될 때
-- 기준 키는 구 PK(a) 인가, 신 PK(b) 인가?
-- 만약 ALTER 문이 아직 커밋 전이라 세션 2가 블로킹된다면
-- 그 대기 시간(DDL 락) 동안의 서비스 영향은 어느 정도인가?
```

**예제 설명**

일반적인 RDBMS에서 스키마 변경 DDL은 대상 테이블에 강한 잠금을 걸어 동시 DML(데이터 조작 언어, INSERT/UPDATE/DELETE)을 차단하는 경우가 많습니다. 그렇다면 이 문장 자체는 원자적으로 처리되어 큰 문제가 없을 수 있지만, "그렇다"는 보장이 스펙에 한 줄도 없습니다. 대형 테이블에서 PK 교체는 드물지 않은 마이그레이션 작업이므로, 이 DDL이 서비스에 미치는 락 영향과 복제 일관성 보장 여부를 운영자가 사전에 알아야 배포 시간대를 정할 수 있습니다.

**제안**

§4-2에 "복제키를 변경하는 DDL은 테이블 전체 잠금 하에 원자적으로 처리되며, 변경 트랜잭션이 커밋되기 전까지 해당 테이블의 DML은 대기한다"는 식으로 동시성 보장 범위를 명시해야 합니다. 대형 테이블에서 이 DDL의 예상 소요 시간과 락 범위에 대한 안내도 필요합니다.

## 리뷰 9

**[심각도: 중요] 기존 클러스터의 업그레이드/롤링 업그레이드 경로가 전혀 기술되어 있지 않다**

- **대상**: 스펙 전체 (특히 §1, §8)

**문제 설명**

이 기능은 기존에 "PK만 있으면 복제됨" 이었던 클러스터를 "REPLICATION 옵션 + RK 자동 선택" 체계로 바꾸는 것입니다. 그런데 이미 운영 중인 구버전 HA 클러스터를 이 기능이 포함된 신버전으로 업그레이드하는 절차, 특히 마스터와 슬레이브의 버전이 잠시 혼재하는 롤링 업그레이드 구간(다운타임을 최소화하기 위해 슬레이브부터 순차적으로 업그레이드하는 일반적인 방식)에 대한 언급이 스펙에 없습니다.

**구체 예제**

```text
[롤링 업그레이드 시나리오]
1. 슬레이브를 먼저 신버전으로 업그레이드 (마스터는 아직 구버전)
2. 마스터는 구버전이므로 REPLICATION 옵션이라는 개념 자체가 없음
   -> 이 상태는 문제 없음 (마스터가 새 DDL을 만들지 않으므로)

3. 마스터를 신버전으로 업그레이드 완료. 이제 기존 PK 테이블들은
   REPLICATION=? RK=? 로 자동 인식되는가?
   -> 기존 테이블에는애초에 REPLICATION 컬럼값이 카탈로그에 없었을 텐데
      업그레이드 스크립트가 이를 어떻게 채우는지 스펙에 없음

4. 마스터가 신버전 문법(REPLICATION 옵션 포함 DDL)을 복제 로그로 내려보내는데
   슬레이브가 아직 구버전이면 파싱에 실패하지 않는가?
   (2번과 반대로, 슬레이브가 늦게 올라가는 순서라면 발생 가능)
```

**예제 설명**

카탈로그 스키마 자체가 바뀌는 기능(REPLICATION 컬럼 신설, RK 개념 도입)은 업그레이드 시점에 기존 메타데이터를 마이그레이션하는 단계가 반드시 필요합니다. 이 단계가 실패하거나 정의되지 않으면, 업그레이드 직후 모든 기존 테이블이 어떤 RK/REPLICATION 값을 갖는지 예측할 수 없어 즉시 §1의 "RK 없으면 HA 실행 불가" 규칙에 걸려 서비스 전체가 기동 실패할 위험이 있습니다.

**제안**

업그레이드 시 기존 테이블은 "PK가 있으면 RK=PK, REPLICATION=ON"으로 자동 마이그레이션한다는 규칙과, 마스터/슬레이브 버전이 혼재하는 구간에서의 호환성 정책(예: 신버전 마스터는 구버전 슬레이브가 남아있는 동안 REPLICATION 옵션이 포함된 DDL 복제를 보류한다)을 명시해야 합니다.

## 리뷰 10

**[심각도: 중요] FK 참조 무결성 검사가 "생성/전환 시점"에만 있고 "운영 중 참조 테이블을 나중에 OFF로 바꾸는 경로"에 대한 방지책이 없다**

- **대상**: §5, §7, 예시 18

**문제 설명**

§5와 예시 18은 REPLICATION=OFF 테이블을 참조하는 FK를 "생성 시점"에 막습니다. §7은 "HA 실행 시" 이 제약을 재검사합니다. 그런데 "이미 정상적으로 생성된 FK 관계(양쪽 다 REPLICATION=ON)"에서, 운영 중에 참조되는 쪽(부모 테이블)만 나중에 `REPLICATION=OFF`로 바꾸는 것을 막는 규칙이 스펙 어디에도 없습니다. §4에 언급된 "복제 제외 → 복제 대상"으로의 전환 제약(리뷰 2)은 있지만, 반대 방향인 "복제 대상 → 복제 제외" 전환에는 FK 참조 여부에 따른 제약이 언급되지 않습니다.

**구체 예제**

```sql
-- 예시 17의 정상 상태: customers(ON) <- orders(ON, FK)
-- HA 운영 중, 여기서 부모 테이블만 복제 제외로 전환 시도

csql> ALTER TABLE customers REPLICATION=OFF;
-- 결과가 OK인가 ERROR인가? 스펙에 없음.
-- §4 문언상 "복제 제외 테이블이 복제 테이블로 변경될 수 없다"는
-- 반대 방향만 규정하므로, 문언 그대로라면 이 문장은 허용되는 것으로 읽힘

-- 만약 OK라면:
-- 이제 orders(ON, FK customer_id -> customers) 인데 customers는 OFF.
-- 이는 정확히 스펙 §5가 애초에 막으려던 "FK 참조 테이블이 복제 제외"
-- 상황과 동일한 결과에 도달함 (경로만 다를 뿐)
```

**예제 설명**

§5가 그렇게 공들여 막으려던 문제(참조 테이블이 복제 제외라서 failover 후 애플리케이션이 존재하지 않는 데이터를 참조)를, "생성 시점 차단"이라는 정문은 잠가두고 "운영 중 ALTER"라는 뒷문은 열어둔 채로 재현할 수 있다는 뜻입니다. HA가 이미 실행 중인 상태이므로 §7의 시작 시점 검사는 이 케이스를 잡아내지 못합니다(HA를 재시작하지 않는 한).

**제안**

"복제 대상 테이블을 REPLICATION=OFF로 전환하려 할 때, 그 테이블을 참조하는 FK를 가진 다른 복제 대상 테이블이 존재하면 에러를 낸다"는 규칙을 §4 또는 §5에 명시적으로 추가해야 합니다.

## 리뷰 11

**[심각도: 중요] FK는 강제로 막고 VIEW는 책임을 회피하는 비일관적 정책**

- **대상**: §5, §6

**문제 설명**

동일하게 "복제 제외 테이블의 데이터가 슬레이브에 없어서 발생하는 문제"를 다루면서, §5(외래키)는 생성 시점에 명시적으로 ERROR를 내는 강한 정책을 취하는 반면, §6(뷰)은 "책임지지 않는다"는 문구만으로 끝내고 아무런 사전 방지 장치를 제공하지 않습니다. 같은 근본 원인에 대해 대응 강도가 정책적으로 다른 이유가 설명되어 있지 않습니다.

**구체 예제**

```sql
-- FK 케이스: 생성 시점에 강제 차단 (예시 18)
csql> CREATE TABLE orders(
    order_id INT PRIMARY KEY,
    customer_id INT,
    CONSTRAINT fk_customer_id FOREIGN KEY (customer_id)
    REFERENCES non_repl_customers(customer_id)  -- REPLICATION=OFF
);
ERROR

-- VIEW 케이스: 동일한 근본 문제인데도 생성이 그대로 허용됨
csql> CREATE TABLE non_repl_customers(
    customer_id INT PRIMARY KEY, country INT
) REPLICATION=OFF;

csql> CREATE VIEW customer_orders AS
    SELECT o.order_id, c.country
    FROM orders o JOIN non_repl_customers c
      ON o.customer_id = c.customer_id;
-- §6에 의하면: OK (생성은 막지 않고, 실행 결과 불일치를 "책임지지 않는다"고만 함)
```

**예제 설명**

FK와 VIEW 모두 "복제 제외 테이블의 부재 데이터에 의존하는 객체를 슬레이브에서 잘못 사용하게 될 위험"이라는 동일한 리스크를 갖습니다. 그런데 FK는 아예 만들 수 없게 막고, VIEW는 만드는 것도 허용하고 조용히 틀린 결과를 내도록 방치합니다. 운영자 입장에서는 VIEW야말로 애플리케이션 개발자가 무심코 만들기 쉬운 객체이기 때문에, 사전 경고 없이 방치되는 쪽이 더 위험할 수 있습니다.

**제안**

최소한 CREATE VIEW 시점에 복제 제외 테이블을 참조하는 것을 감지해 WARNING을 내는 기능을 추가하거나, 왜 VIEW에 대해서는 FK와 다른 수준의 관용을 두는지 설계 근거를 스펙에 남겨야 합니다.

## 리뷰 12

**[심각도: 중요] 이 기능으로 인한 위반/에러가 fail_count(운영 배경에서 언급된 지표)와 어떤 관계인지 스펙 본문에 없다**

- **대상**: 작업지시 배경 vs 스펙 §4, §7 (스펙 자체에는 fail_count 언급 없음)

**문제 설명**

이 스펙을 만들게 된 배경 자체가 "PK 변경 시 fail_count가 증가하고 데이터가 불일치하는 문제"였습니다. 그런데 정작 스펙 본문에는 fail_count라는 단어가 한 번도 등장하지 않습니다. 신규 제약을 통해 사전에 DDL을 막는 경우(§4-2 에러들)는 fail_count와 무관해 보이지만, §4의 "REPLICATION OFF로 인한 데이터 불일치는 책임지지 않는다"거나 §6 VIEW의 불일치 상황은 여전히 존재하는데, 이런 상황이 운영자가 모니터링하는 fail_count 지표에 잡히는지 안 잡히는지가 불명확합니다.

**구체 예제**

```text
[운영자가 대시보드에서 보는 지표]
fail_count: applylogdb 가 복제 로그를 슬레이브에 적용하다 실패한 횟수

[질문 시나리오]
1. REPLICATION=OFF 테이블에 대한 변경이 마스터에서 발생
   -> 슬레이브로는 애초에 전송되지 않음(§1: "REPLICATION 옵션은 데이터 복제 여부를 결정")
   -> 이 경우 fail_count는 증가하지 않는가? (전송 자체를 안 하므로 "실패"가 아님)

2. FK 참조 무결성이 깨진 상태에서 슬레이브에 없는 데이터를 참조하는
   DML 로그가 실수로 슬레이브에 전달된다면
   -> applylogdb 가 참조 무결성 에러를 내며 fail_count 증가?
   -> 아니면 이 스펙의 생성 시점 차단 덕분에 원천적으로 발생 불가능?
```

**예제 설명**

이 스펙이 실제로 배경 문제(fail_count 증가)를 얼마나 줄이는지, 혹은 어떤 잔존 시나리오에서는 여전히 fail_count가 증가할 수 있는지를 운영자가 판단하려면 이 연결고리가 스펙에 있어야 합니다. 지금 상태로는 "이 기능이 배포되면 fail_count 관련 알림 임계치를 조정해야 하는가"라는 실무 질문에 답할 근거가 없습니다.

**제안**

§4 혹은 §7에 "이 스펙에서 다루는 제약 위반은 사전에 DDL 단계에서 차단되므로 fail_count 증가와는 무관하다" 또는 "다음과 같은 잔존 시나리오에서는 여전히 fail_count가 증가할 수 있다"는 형태로 명시적 연결을 추가해야 합니다.

## 리뷰 13

**[심각도: 중요] §7 HA 시작 실패에 대한 사전 검증(dry-run) 도구가 없다**

- **대상**: §7 HA 전환

**문제 설명**

§7의 제약 검사는 "HA 실행 시" 수행됩니다. 즉 `cubrid hb start`를 실제로 실행해봐야 위반 여부를 알 수 있습니다. 계획된 유지보수 창(maintenance window)에 HA를 재기동했다가 이 시점에야 위반 테이블을 발견하면, 이미 서비스 다운타임이 시작된 상태에서 "싱글모드로 되돌려 스키마를 고치고 다시 HA 재시작"이라는 추가 다운타임이 필요합니다. 사전에 검증할 수 있는 명령이 없다는 것은 예방 가능한 다운타임을 방치하는 것입니다.

**구체 예제**

```text
[현재 스펙이 강제하는 절차]
1. 유지보수 창 시작, 서비스 중단 공지
2. cubrid hb start 실행
3. 이 시점에야 위반 테이블 발견 (§7 에러 + 파일 리스트)
4. 다시 싱글 모드로 내려서 ALTER TABLE로 RK 추가/REPLICATION=OFF 처리
5. cubrid hb start 재실행
6. (운 좋으면) 성공

[바람직한 절차 - 스펙에 없음]
1. 유지보수 창 시작 전, 미리
   $ cubrid hb check --dry-run mydb
   위반 테이블 목록 사전 확인
2. 문제 있는 테이블만 미리 싱글 모드에서(혹은 별도 창구로) 수정
3. 실제 유지보수 창에서는 바로 hb start 실행 -> 다운타임 최소화
```

**예제 설명**

사전 검증 명령이 있고 없고의 차이는 "다운타임 중에 문제를 발견"하느냐 "다운타임 시작 전에 문제를 예방"하느냐의 차이입니다. 운영 규모가 커질수록(수백 개 테이블) 이 차이는 몇 분과 몇 시간의 차이로 벌어질 수 있습니다.

**제안**

HA를 실제로 시작하지 않고도 §7의 제약(RK 존재 여부, FK 참조 테이블의 복제 대상 여부)을 검사만 하는 별도 명령이나 SQL 함수(`SELECT check_ha_readiness();` 류)를 추가해야 합니다.

## 리뷰 14

**[심각도: 보통] 싱글 모드에서 수백 개 테이블을 일괄 정비해야 하는 운영 부담에 대한 도구가 없다**

- **대상**: §3, §7

**문제 설명**

§3과 §7은 "싱글 모드에서 ALTER TABLE로 하나씩 복제 키를 추가하거나 복제 제외로 바꾼 뒤 HA를 재시작해야 한다"고 되어 있습니다. 이미 오랫동안 PK 없이 운영되던 테이블이 스키마에 다수 존재하는 실서비스(로그성 테이블, 임시 테이블 등)에서는 이 작업이 테이블 1개가 아니라 수십~수백 개 단위일 수 있습니다. 이를 일괄로 처리하는 절차나 도구(예: 위반 테이블 목록을 받아 일괄로 REPLICATION=OFF를 적용하는 스크립트, 혹은 그런 기능을 내장한 유틸리티)에 대한 언급이 없습니다.

**구체 예제**

```sql
-- 현재 스펙 기준: 운영자가 수작업으로 반복
ALTER TABLE log_2024_01 REPLICATION=OFF;
ALTER TABLE log_2024_02 REPLICATION=OFF;
ALTER TABLE log_2024_03 REPLICATION=OFF;
-- ... 위반 테이블 수만큼 반복 (수백 개일 수 있음)
```

**예제 설명**

이런 반복 작업은 스크립트로 자동화할 수 있지만, 그 근거가 되는 "위반 테이블 목록"을 기계가 읽을 수 있는 형태로 얻을 방법이 리뷰 4에서 지적한 대로 불명확하기 때문에, 결국 사람이 §7의 콘솔 출력을 눈으로 읽고 한 줄씩 스크립트를 작성해야 하는 상황이 됩니다.

**제안**

일괄 처리를 지원하는 배치용 유틸리티나, 최소한 위반 테이블 목록을 SQL/CSV 형태로 뽑아 스크립트에 바로 먹일 수 있는 출력 옵션을 제공해야 합니다.

## 리뷰 15

**[심각도: 보통] 예시 2의 SQL 자체에 문법 오류(trailing comma)가 있다**

- **대상**: 예시 2

**문제 설명**

```sql
csql> CREATE TABLE repl_table_without_rk(
    a INT,
);
```

컬럼 정의가 `a INT` 하나뿐인데 그 뒤에 콤마(,)가 붙어 있습니다. 대부분의 SQL 파서는 이런 trailing comma를 허용하지 않으므로, RK 유무 문제 이전에 이 문장 자체가 구문 오류로 실패할 가능성이 있습니다.

**구체 예제**

```sql
-- 스펙 원문 그대로
CREATE TABLE repl_table_without_rk(
    a INT,
);

-- 문법적으로 올바른 형태 (아마도 의도한 것)
CREATE TABLE repl_table_without_rk(
    a INT
);
```

**예제 설명**

이 예시는 "RK 없는 테이블은 싱글 모드에서만 생성 가능하다"는 규칙을 보여주기 위한 예제인데, 정작 예제 SQL이 문법 오류로 실패한다면 독자(특히 이 스펙을 처음 보는 신입 개발자나 QA 담당자)는 "RK가 없어서 실패한 것"과 "trailing comma 때문에 실패한 것"을 구분하지 못하고 혼란을 겪을 수 있습니다. 스펙 문서에 실리는 예제는 실제로 그대로 실행 가능해야 신뢰할 수 있습니다.

**제안**

trailing comma를 제거하고, 가능하면 이 스펙을 확정하기 전에 모든 예제 SQL을 실제 csql에 돌려서 원문 그대로 재현되는지 검증하는 절차를 거쳐야 합니다.

## 리뷰 16

**[심각도: 보통] 예시 20/23의 인라인 FOREIGN KEY 컬럼 속성 문법이 실제로 지원되는지 의문스럽다**

- **대상**: 예시 20, 예시 23

**문제 설명**

```sql
csql> ALTER TABLE new_orders ADD COLUMN
(customer_id INT FOREIGN KEY REFERENCES customers(customer_id));
```

컬럼 정의 안에 `FOREIGN KEY REFERENCES ...`를 인라인 속성처럼 붙이는 문법입니다. 일반적으로 FK는 `CONSTRAINT ... FOREIGN KEY (col) REFERENCES ...` 형태의 테이블 레벨 제약으로 선언하며, 컬럼 정의 안에 `PRIMARY KEY`처럼 붙일 수 있는 것은 PK 정도이고 FK를 이런 식으로 인라인 선언할 수 있는지는 CUBRID 문법상 불확실합니다.

**구체 예제**

```sql
-- 예시 20 원문 (컬럼 레벨 인라인 FK - 문법적으로 의문)
ALTER TABLE new_orders ADD COLUMN
(customer_id INT FOREIGN KEY REFERENCES customers(customer_id));

-- 일반적으로 통용되는 형태 (테이블 레벨 CONSTRAINT)
ALTER TABLE new_orders ADD COLUMN (customer_id INT),
ADD CONSTRAINT FOREIGN KEY (customer_id) REFERENCES customers(customer_id);
```

**예제 설명**

만약 실제 csql이 예시 20의 문법을 지원하지 않는다면, 이 스펙을 참고해 마이그레이션 스크립트를 작성한 응용 개발자나 DBA가 그대로 복사해서 쓰다가 구문 오류를 만나게 됩니다. 이 기능 자체(FK 참조 대상의 복제 여부 검증)와는 무관한 오류이지만, 스펙 문서의 신뢰도를 깎는 요인입니다.

**제안**

이 문법이 실제로 지원되는지 csql로 직접 검증한 뒤, 지원되지 않는다면 테이블 레벨 CONSTRAINT 문법으로 예제를 교체해야 합니다.

## 리뷰 17

**[심각도: 보통] REPLICATION 조회 결과의 표기 형식이 두 인터페이스 간에 통일되어 있지 않다**

- **대상**: 예시 8, 예시 9

**문제 설명**

예시 8(`show create table`)의 결과 문자열에는 `... REPLICATION ON'`처럼 등호나 콜론 없이 공백으로 이어 붙인 형태로 나오고, 예시 9(`select * from db_class`)에서는 `replication : ON`처럼 콜론과 공백으로 구분된 key-value 형태로 나옵니다. 값 자체는 둘 다 대문자 `ON`으로 일치하지만, 표현 형식이 인터페이스마다 다릅니다.

**구체 예제**

```text
-- 예시 8 스타일 (show create table 결과 문자열 일부)
... REUSE_OID, COLLATE utf8_bin, REPLICATION ON

-- 예시 9 스타일 (db_class 조회 결과)
replication       : ON
```

**예제 설명**

사람이 눈으로 읽을 때는 큰 문제가 아니지만, 운영 스크립트가 `show create table` 결과 문자열을 파싱해서 REPLICATION 값을 추출하려 할 경우 정규식을 두 형태에 맞춰 따로 짜야 하는 번거로움이 생깁니다. 값 자체의 대소문자·표현이 db_class 조회 결과와 완전히 일치하는지도 스펙만으로는 확신할 수 없습니다.

**제안**

두 조회 경로에서 REPLICATION 값의 표기(대소문자, 구분자)를 통일하거나, 최소한 스펙 문서에 "이 두 표현은 항상 동일한 문자열 집합(ON/OFF)을 사용한다"는 점을 명시해야 합니다.

## 리뷰 18

**[심각도: 보통] unloaddb 시 복제 제외 테이블의 데이터 자체가 백업에 포함되는지 불명확하다**

- **대상**: §8, 1번째 항목

**문제 설명**

§8은 "unload 시 복제 테이블의 여부를 함께 저장한다"고만 되어 있습니다. 이는 REPLICATION ON/OFF라는 플래그 하나를 추가로 저장한다는 뜻으로 읽히지만, "복제 제외 테이블"의 실제 행 데이터 자체는 여전히 unloaddb의 정상 대상(전체 DB 백업이므로)인지, 아니면 이 기능을 계기로 복제 제외 테이블은 백업에서 제외하는 옵션이 함께 생기는 것인지 스펙이 침묵합니다. 이는 백업 용량 산정, 백업/복원 소요 시간 산정이라는 실무적으로 중요한 질문입니다.

**구체 예제**

```text
[운영자가 답을 알아야 하는 질문]
전체 DB 크기 10TB 중 REPLICATION=OFF 테이블이 총 8TB를 차지한다면,

(a) unloaddb 는 여전히 10TB 전체를 백업 대상으로 삼는가?
    -> 이 기능과 무관하게 백업 시간/용량은 그대로
(b) 혹은 unloaddb 에 "-exclude-non-replicated" 같은 옵션이 새로 생겨서
    복제 제외 테이블 데이터를 백업에서 뺄 수 있는가?
    -> 있다면 백업 정책을 재설계해 시간을 크게 단축 가능
```

**예제 설명**

복제 제외 테이블은 애초에 슬레이브로 갈 일이 없는 데이터이므로, 슬레이브 재구성 목적의 백업이라면 이 데이터를 굳이 포함할 필요가 없을 수도 있습니다. 이 스펙이 REPLICATION 플래그를 unloaddb 포맷에 새로 추가하는 김에, 이런 선택적 백업 기능까지 고려했는지, 아니면 순수하게 "여부만 저장하고 데이터는 그대로 전부 포함"인지 밝혀야 합니다.

**제안**

unloaddb의 기존 동작(전체 데이터 백업)이 이 기능으로 인해 변경되지 않는다는 점을 명시하거나, 혹은 복제 제외 테이블만 선택적으로 제외하는 백업 옵션의 추가 여부를 스펙에 밝혀야 합니다.

## 리뷰 19

**[심각도: 사소] 예시 16의 DROP INDEX 대상이 UNIQUE 인덱스인지 일반 인덱스인지 불명확하다**

- **대상**: 예시 16

**문제 설명**

```sql
csql> DROP INDEX idx_id ON tbl;
ERROR
```

설명은 "복제키 후보가 없다면 삭제 불가"라고 되어 있는데, `idx_id`라는 이름만으로는 이것이 UNIQUE 제약에 연결된 인덱스인지, 단순 조회 성능용 일반(비UNIQUE) 인덱스인지 알 수 없습니다. 일반 인덱스는 RK 후보와 무관하므로 삭제가 항상 허용되어야 정상이지만, 예제만 보면 "인덱스라는 이름이 붙은 모든 것을 함부로 지울 수 없다"는 과잉 해석을 유발할 수 있습니다.

**구체 예제**

```sql
-- 이 두 인덱스는 근본적으로 다른데 예시 16만으로는 구분이 안 됨
CREATE UNIQUE INDEX idx_id ON tbl(a);      -- RK 후보가 될 수 있는 UNIQUE 인덱스
CREATE INDEX idx_created_at ON tbl(created_at); -- 단순 조회 성능용, RK와 무관

DROP INDEX idx_created_at ON tbl;  -- 이건 항상 허용되어야 함 (스펙엔 이 구분이 없음)
```

**예제 설명**

DBA는 인덱스 관리를 매우 빈번하게 수행하는데(쿼리 튜닝 과정에서 불필요한 인덱스 정리 등), 이 예제만 보고 "복제 대상 테이블에서는 인덱스를 함부로 못 지운다"고 오해하면 정상적인 성능 튜닝 작업까지 위축될 수 있습니다.

**제안**

예제에 `CREATE UNIQUE INDEX idx_id ...`처럼 이 인덱스가 UNIQUE 제약과 연결되어 있음을 명시하고, "일반 인덱스는 이 제약과 무관하게 항상 삭제 가능하다"는 문장을 §4-2에 추가해야 합니다.

## 리뷰 20

**[심각도: 사소] 예시 5/6의 사전 상태(tbl의 초기 REPLICATION 값)가 명시되지 않아 재현성이 떨어진다**

- **대상**: 예시 5, 예시 6

**문제 설명**

예시 5(`ALTER TABLE tbl REPLICATION=ON;` → ERROR)와 예시 6(`ALTER TABLE tbl REPLICATION=OFF;` → OK)은 나란히 배치되어 있어 마치 하나의 이어지는 시나리오처럼 보이지만, `tbl`의 최초 생성 시 REPLICATION 값이 무엇이었는지(ON이었는지, OFF였는지) 명시되어 있지 않습니다.

**구체 예제**

```text
-- 해석 A: 두 예시가 독립적이며 각각 별도의 tbl(REPLICATION=OFF)에 대한 것
예시5: tbl(OFF) 에 REPLICATION=ON 시도 -> ERROR (§2-2 규칙)
예시6: tbl(OFF) 에 REPLICATION=OFF 재적용 -> OK (자기 자신으로 재설정, 멱등성 있음)

-- 해석 B: 두 예시가 이어지는 시나리오이며 최초 tbl은 REPLICATION=ON
예시5: tbl(ON) 에 REPLICATION=ON 재적용 시도 -> ERROR? (이 경우라면 §2-2와 무관한 별도 이유)
예시6: tbl(ON) 에 REPLICATION=OFF 시도 -> OK (ON->OFF는 허용, §4와 일치)
```

**예제 설명**

해석 A와 해석 B는 각 예제가 보여주려는 규칙이 다릅니다. 문서의 문맥(HA 모드에서 OFF→ON이 금지된다는 §2-2 직후에 배치된 것)상 해석 A가 맞아 보이지만, 명시적으로 사전 상태를 적어주지 않으면 독자가 실제로 손으로 재현해볼 때 결과가 다르게 나올 수 있고, 어느 쪽이 스펙이 의도한 규칙인지 헷갈릴 수 있습니다.

**제안**

각 예시 앞에 "사전 조건: tbl은 REPLICATION=OFF로 이미 생성되어 있다고 가정" 같은 한 줄을 추가해 재현성을 높여야 합니다.
