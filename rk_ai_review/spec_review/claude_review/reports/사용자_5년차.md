# CUBRID HA 복제 개선 스펙 리뷰 — 최종 사용자(5년차) 관점

## 리뷰어 소개

SQL을 매일 직접 작성해서 운영 DB를 다루는 실무 개발자다. DBA는 아니지만 스키마 변경(ALTER TABLE), FK 설계, 장애 대응 시 1차 조치는 직접 처리하는 위치이며, CUBRID HA 환경에서 애플리케이션 코드와 DDL을 함께 배포해 본 경험이 5년 정도 있다. 엔진 내부 구현이나 복제 프로토콜의 세부 알고리즘까지는 모르지만, "내가 실행한 SQL이 왜 성공/실패하는지", "에러가 나면 무엇을 해야 하는지"는 정확히 알아야 하는 입장이다.

## 총평

이 스펙은 REPLICATION 옵션과 RK(복제 키) 자동 선택이라는 두 가지 규칙을 도입하면서, 정작 실무자가 매일 마주치는 "왜 이 SQL이 지금은 되고 아까는 안 됐는가"에 대한 답을 체계적으로 주지 못하고 있다. 문서 전반에 걸쳐 에러 상황이 그냥 `ERROR`라는 한 단어로만 표기되어 실제 에러 메시지가 무엇인지 알 수 없고(§4-2, §5), UK가 여러 개 존재할 때 실제로 어떤 UK가 RK로 선택되었는지 조회할 방법도 제시되지 않는다(§2-3). 더 심각한 것은 §1의 "복제 제외 테이블은 RK 유무와 무관하게 생성 가능"이라는 원칙과 §5의 "FK가 참조하는 테이블은 반드시 복제 대상이어야 한다"는 원칙이 충돌하는 지점, 그리고 이미 맺어진 FK 관계의 참조 테이블을 사후에 REPLICATION=OFF로 전환하는 시나리오처럼 스펙이 침묵하는 조합이 여럿 남아 있다는 점이다. 전체적으로 "정상 케이스가 어떻게 동작하는가"는 설명되어 있지만, "경계에서 무슨 일이 일어나는가"와 "실패했을 때 사용자가 무엇을 보고 무엇을 해야 하는가"에 대한 서술이 부족하다.

## 리뷰 1

**[심각도: 치명] UK가 여러 개일 때 RK 선택 기준이 재현 불가능하고, 재선정 시점이 정의되지 않았다**

**대상**: §1 "복제키는 다음 기준에 의해 결정된다" — "UK가 여러개 존재한다면 큐브리드 엔진에 의해 이 중 하나가 선택된다(ex. 테이블내에 명시된 순서 중 가장 빠른 순서)"

**문제 설명**: "테이블 내에 명시된 순서"가 무엇을 기준으로 하는지 정의되어 있지 않다. CREATE TABLE 문에서 컬럼이 선언된 순서인지, UNIQUE 제약이 선언된 순서인지, 내부 인덱스 생성 순서(OID 순서)인지 알 수 없다. 게다가 이 "순서"는 어디까지나 예시(`ex.`)로만 제시되어 있어서, 실제로 채택된 규칙인지 예시 중 하나에 불과한지도 불분명하다. 더 큰 문제는 ALTER TABLE로 UK를 추가/삭제한 뒤에 RK가 재선정되는 시점이다. "즉시"인지 "다음 HA 재시작 시"인지에 대한 언급이 스펙 어디에도 없다.

**구체 예제(시나리오)**:
```sql
-- 싱글 모드
CREATE TABLE tbl (
    a INT NOT NULL UNIQUE,
    b INT NOT NULL UNIQUE,
    c INT
);
-- 이 시점 RK 후보는 a, b 두 개. 스펙에 따르면 "가장 빠른 순서"인 a가 RK로 추정된다.

-- 운영 중 컬럼 순서를 바꾸는 것은 아니지만, UK를 재정의하면?
ALTER TABLE tbl DROP CONSTRAINT u_tbl_a;
ALTER TABLE tbl ADD CONSTRAINT UNIQUE (a);
-- a의 UK 제약을 지웠다가 다시 만들었다. 이제 "명시된 순서"로는 a가 b보다 뒤에 온 것 아닌가?
-- RK가 b로 바뀌는가, 여전히 a인가?
```

**예제 설명**: 위 시나리오는 컬럼 자체는 하나도 안 바꾸고 제약만 지웠다 다시 만든 것이다. 이런 조작만으로 "복제 키가 되는 컬럼"이 바뀔 수 있는지 스펙만 봐서는 판단할 수 없다. 만약 RK가 조용히 a에서 b로 바뀐다면, 슬레이브에 이미 적용된 과거 로그와 새 RK 기준이 어긋나는 정합성 문제로 이어질 수 있다. 실무자 입장에서는 "내가 지금 실행하는 DDL이 RK를 바꾸는 DDL인지 아닌지"조차 사전에 알 수 없다는 뜻이다.

**제안**: RK 선택 기준을 컬럼 순서(ordinal position) 같은 결정론적이고 조회 가능한 값으로 명문화하고, ALTER TABLE로 인해 RK가 재선정되는 정확한 트리거 시점(트랜잭션 커밋 시점인지, HA 재시작 시점인지)을 §4-2에 명시해야 한다.

## 리뷰 2

**[심각도: 중요] REPLICATION 옵션 생략 시 기본값 ON이 "지연된 실패"를 만든다**

**대상**: §2-1 "이 옵션은 생략 가능하며 생략시 ON으로 자동으로 복제 테이블로 생성된다. 주의할 점은 복제 키가 없는 테이블은 싱글 모드에서만 생성 가능하고, HA 전환시 에러가 발생한다."

**문제 설명**: REPLICATION 옵션을 아예 모르는(또는 잊어버린) 사용자가 평소처럼 PK 없는 임시 테이블이나 로그 테이블을 만들면 기본값 ON으로 조용히 생성된다. 문제는 이 시점엔 아무 에러도 나지 않는다는 것이다. 에러는 한참 뒤 "HA 모드로 전환하는 시점"에 가서야 발생한다. 즉 원인(옵션 생략)과 결과(HA 전환 실패)가 시간적으로 완전히 분리되어 있어서, 실제 운영에서는 전환 실패 시점에 "대체 언제 만든 테이블 때문이지?"를 역추적해야 하는 상황이 반복될 것이다.

**구체 예제**:
```sql
-- 1일차, 싱글 모드에서 편하게 로그 테이블 하나 만듦 (REPLICATION 옵션 신경 안 씀)
CREATE TABLE tmp_log (
    msg VARCHAR(200),
    ts  DATETIME
);
-- 별문제 없이 생성됨. 내부적으로는 REPLICATION=ON, RK 없음 상태.

-- 30일 후, 운영 배포를 위해 HA 모드 전환
-- $ cubrid hb start
-- ERROR: (§7에 따르면) 제약사항 위반 파일 리스트 출력 -- 여기서 tmp_log 가 걸림
```

**예제 설명**: `tmp_log`를 만들 때는 아무 경고도 뜨지 않는다. 30일 뒤 전혀 다른 작업자가 HA를 켜려다가 실패 메시지를 받는데, 실패 원인이 된 테이블은 이미 그 존재조차 잊혀진 임시 테이블일 수 있다. 기본값이 "가장 안전한 선택"이 아니라 "가장 늦게 터지는 선택"으로 되어 있는 셈이다.

**제안**: 최소한 CREATE TABLE 시점에 "RK 없이 REPLICATION=ON(기본값)으로 생성됨 — HA 전환 시 실패함"이라는 경고(WARNING)를 즉시 출력하도록 해야 한다. 또는 기본값을 RK 유무에 따라 동적으로 결정(RK가 없으면 기본 OFF)하는 방안도 검토할 가치가 있다.

## 리뷰 3

**[심각도: 중요] §1의 두 원칙이 "확인 절차" 없이 나열되어 실행 순서를 알 수 없다**

**대상**: §1 "HA 모드 실행 시 복제 테이블은 ... RK가 존재하지 않으면 HA모드를 실행 할 수 없다" 및 "복제 제외 테이블은 복제 키의 유무와 상관 없이 생성 가능하다"

**문제 설명**: 이 두 문장을 그대로 읽으면 "HA를 켜는 행위" 자체가 RK 없는 테이블이 하나라도 있으면 실패한다는 뜻이다. 그런데 이미 데이터가 잔뜩 쌓인 운영 DB에 RK 없는 테이블이 여러 개 있다면, 사용자는 HA를 켜기 전에 그것들을 전부 찾아서 REPLICATION=OFF로 바꾸거나 RK를 추가해야 한다. 이 "사전 점검을 어떻게 하는가"에 대한 절차나 조회 도구가 §1에는 전혀 없고, §7에 가서야 "에러와 함께 파일 리스트를 출력한다"는 사후 대응만 등장한다. 즉 실무자는 HA를 켜보기 전까지는 자신의 스키마가 통과할지 알 방법이 없다.

**구체 예제(시나리오)**:
```sql
-- 싱글 모드, 서비스 운영 3년 차 DB. 테이블 200개 존재.
-- 이 중 몇 개가 RK 없이 REPLICATION=ON(기본값) 상태인지 아무도 정확히 모른다.

-- HA를 처음 켜는 순간
-- $ cubrid hb start
-- ERROR + 파일 리스트 (§7)
```

**예제 설명**: 200개 테이블 중 RK 없는 테이블이 몇 개인지 사전에 확인할 SQL(예: `db_class`, `db_constraint` 조인 쿼리)이 스펙에 예시로 제공되지 않는다. 사용자가 직접 카탈로그를 뒤져 알아내야 하는데, 이는 신규 도입 사용자에게 상당한 진입장벽이다.

**제안**: HA 전환 전에 위반 대상을 미리 확인할 수 있는 조회용 SQL 예시(또는 전용 유틸리티)를 §1 또는 §7에 명시해야 한다.

## 리뷰 4

**[심각도: 사소] 예제 SQL 문법 오류 — 트레일링 콤마**

**대상**: 예시 2, 예시 23

**문제 설명**: 예시 2의 `CREATE TABLE repl_table_without_rk(a INT,);` 그리고 예시 23의 `CREATE TABLE new_orders(order_id INT PRIMARY KEY,);` 는 모두 컬럼 목록 마지막에 불필요한 콤마가 붙어 있다. 일반적인 SQL 문법에서는 트레일링 콤마가 파싱 에러의 원인이 된다.

**구체 예제**:
```sql
-- 예시 2 원문 그대로
CREATE TABLE repl_table_without_rk(
    a INT,
);

-- 예시 23 원문 그대로
CREATE TABLE new_orders(
    order_id INT PRIMARY KEY,
);
```

**예제 설명**: 사용자 매뉴얼의 예제는 실무자가 복사해서 그대로 실행해보는 경우가 많다. 이 상태로 실행하면 REPLICATION 관련 로직을 검증하기도 전에 문법 에러부터 만나게 되어, 예제의 신뢰도를 떨어뜨린다.

**제안**: 예제의 트레일링 콤마를 제거하고, 배포 전 모든 SQL 예제를 실제로 실행해 문법 검증을 거쳐야 한다.

## 리뷰 5

**[심각도: 보통] 예시 5/6에서 모드(싱글/HA)를 명시하지 않아 결과가 상황에 따라 달라지는 것처럼 오독된다**

**대상**: §2-2 예시 5 (`ALTER TABLE tbl REPLICATION=ON;` → ERROR), 예시 6 (`ALTER TABLE tbl REPLICATION=OFF;` → OK)

**문제 설명**: 바로 앞 문장에서 "HA 모드에서는 복제 제외 테이블이 복제 테이블로 변경될 수 없다"고 조건을 걸어놓고도, 정작 예시 5/6에는 "이것은 HA 모드에서 실행한 예시"라는 표시가 전혀 없다. 문서를 훑어보는 실무자는 "REPLICATION=ON으로 바꾸는 건 항상 에러구나"라고 오해하기 쉽다. 그러나 싱글 모드에서는 예시 5도 당연히 OK가 되어야 한다(§3에 따르면 REPLICATION 옵션은 싱글 모드에서도 사용 가능하므로).

**구체 예제**:
```sql
-- 싱글 모드에서
ALTER TABLE tbl REPLICATION=ON;
-- 스펙 §2-2만 보면 이것도 예시 5처럼 ERROR로 오해할 수 있으나,
-- 실제로는 OK 여야 정상이다 (§3, HA 제약이 적용되지 않으므로)
```

**예제 설명**: 예시 5/6에 모드 표기가 없으면, 같은 SQL이 모드에 따라 성공/실패가 갈리는 이 스펙의 핵심 동작을 예제만으로는 검증할 수 없다.

**제안**: 모든 ALTER TABLE REPLICATION 예제 앞에 "(HA 모드에서 실행)" 또는 "(싱글 모드에서 실행)"을 명시해야 한다.

## 리뷰 6

**[심각도: 보통] 예시 7 "Multiple ALTER"가 실제 컬럼명·제약명 없이 생략 문법(`...`)으로만 제시되어 따라 할 수 없다**

**대상**: §2-2 "HA 환경에서 PK를 복제키로 사용하던 중 다른 컬럼으로 변경해야한다면" — 예시 7 `ALTER TABLE tbl DROP CONSTRAINT ..., ADD CONSTRAINT ...;`

**문제 설명**: 다른 예시들(예시 1~6, 11~23)은 전부 실행 가능한 완전한 SQL을 제공하는데, 유독 예시 7만 `...` 자리표시자로 되어 있다. 이 예시가 다루는 시나리오(RK를 다른 컬럼으로 바꾸는 것)는 스펙에서 가장 자주 재확인되는 핵심 동작(예시 13과 동일 계열)임에도, 정작 최초 소개 지점에서는 실행 가능한 형태가 아니다.

**구체 예제**:
```sql
-- 예시 7 원문 (실행 불가능한 형태)
ALTER TABLE tbl DROP CONSTRAINT ..., ADD CONSTRAINT ...;

-- 실무자가 실제로 원하는 완전한 형태 (예시 13에 가서야 등장)
ALTER TABLE table_name DROP CONSTRAINT PRIMARY KEY,
ADD CONSTRAINT PRIMARY KEY(a);
```

**예제 설명**: 실무자가 문서를 위에서 아래로 읽다가 예시 7에서 "아 이렇게 하면 되는구나"하고 그대로 콘솔에 입력하면 문법 에러만 만난다. 완전한 예제는 한참 뒤 예시 13에 가서야 나온다.

**제안**: 예시 7을 예시 13과 동일하게 완전한 SQL로 채우거나, 최소한 "완전한 예시는 예시 13 참고"라는 문구를 남겨야 한다.

## 리뷰 7

**[심각도: 중요] REPLICATION 상태는 조회 가능하지만, 실제 RK가 무엇인지 조회할 방법이 없다**

**대상**: §2-3 예시 8 (`show create table`), 예시 9 (`select * from db_class`)

**문제 설명**: 두 예시 모두 `REPLICATION ON/OFF` 여부는 결과에 보여주지만, "현재 이 테이블의 RK가 어떤 제약(PK인지, 어느 UK인지)인지"는 결과에 전혀 나타나지 않는다. §1에서 UK가 여러 개면 그중 하나만 RK가 된다고 했으므로, UK가 2개 이상인 테이블을 운영하는 실무자는 자신의 테이블에서 실제로 복제에 사용되는 컬럼이 무엇인지 확인할 방법이 스펙상 없다.

**구체 예제**:
```sql
CREATE TABLE tbl (
    a INT NOT NULL UNIQUE,
    b INT NOT NULL UNIQUE
) REPLICATION = ON;

show create table tbl;
-- REPLICATION ON 은 보이지만, a와 b 중 무엇이 RK인지는 결과에 없다

select * from db_class where class_name = 'tbl';
-- replication : ON 은 보이지만 역시 RK 컬럼 정보는 없다
```

**예제 설명**: RK가 PK/UK 중 엔진이 자동으로 고르는 값이라면, 그 선택 결과를 사용자가 확인할 수 있어야 §4-2의 "복제키 후보가 1개면 관련 DDL이 제한된다"는 규칙을 실무자가 스스로 예측하고 대비할 수 있다. 지금 구조로는 DDL을 실행해보고 에러가 나야만 "아, 이게 RK였구나"를 알게 된다.

**제안**: `show create table` 또는 `db_class`류 카탈로그 뷰에 현재 활성 RK의 제약명/컬럼을 명시적으로 노출해야 한다.

## 리뷰 8

**[심각도: 사소] §3의 서술이 "요구사항 문장"이라 실제 절차가 아니다**

**대상**: §3 "싱글 모드에서 생성된 복제 키가 없는 테이블은 HA모드 전환 시 복제 키를 추가하거나 복제 제외 테이블로 변경할 수 있어야한다."

**문제 설명**: "~할 수 있어야한다"는 개발팀 내부의 요구사항 명세 문장이지, 사용자가 실제로 무엇을 입력해야 하는지 알려주는 사용자 매뉴얼 문장이 아니다. 이 문장 하나만 봐서는 "전환 실패 시 자동으로 안내가 뜨는지", "수동으로 §2-2 문법을 다시 찾아 적용해야 하는지"가 불명확하다.

**구체 예제(시나리오)**:
```sql
-- HA 전환 실패 후 (§7)
-- 사용자가 다음 중 무엇을 해야 하는지 §3만 봐서는 알 수 없다:

-- (a) RK 추가
ALTER TABLE tbl ADD CONSTRAINT PRIMARY KEY(a);
-- (b) 혹은 복제 제외로 전환
ALTER TABLE tbl REPLICATION = OFF;
```

**예제 설명**: 두 조치 모두 유효해 보이지만, 스펙은 "할 수 있어야 한다"고만 말하지 어느 쪽이 권장되는지, 혹은 자동으로 어느 쪽이 선택되는지 언급이 없다.

**제안**: 사용자 매뉴얼에서는 "다음 두 SQL 중 하나를 실행하십시오"처럼 행동 지향 문장으로 바꿔야 한다.

## 리뷰 9

**[심각도: 치명] 복합 ALTER(예시 13)의 원자성이 명시되지 않아 "RK가 0개인 순간"의 존재 여부를 알 수 없다**

**대상**: §4-2 예시 12 (DROP PRIMARY KEY 단독 → ERROR) vs 예시 13 (DROP CONSTRAINT + ADD CONSTRAINT 동시 → OK)

**문제 설명**: 예시 12는 "RK가 되는 PK를 지우려는 시도"가 그 자체로 막힌다는 걸 보여준다. 그런데 예시 13은 같은 PK를 지우면서 동시에 새 PK를 추가하는데 OK가 나온다. 이 두 예시를 나란히 놓으면 자연스럽게 드는 의문은 "예시 13이 실행되는 그 찰나에, 옛 PK는 이미 지워졌고 새 PK는 아직 안 걸린 상태 — 즉 RK가 0개인 중간 상태가 실제로 존재하는가?"이다. 만약 이 문장이 원자적(하나의 트랜잭션으로 all-or-nothing)으로 처리되지 않는다면, 두 번째 ADD CONSTRAINT 절이 실행되기 전에 서버가 죽거나 동시에 다른 트랜잭션이 그 테이블에 DML을 수행하면 어떻게 되는지 스펙이 침묵한다.

**구체 예제(시나리오)**:
```sql
-- 세션 A
ALTER TABLE table_name DROP CONSTRAINT PRIMARY KEY,
ADD CONSTRAINT PRIMARY KEY(a);
-- 이 문장이 실행되는 도중, DROP은 반영되고 ADD를 반영하기 직전
-- 프로세스가 강제 종료(kill -9)된다면?

-- 재기동 후 세션 B
select * from db_class where class_name = 'table_name';
-- replication 컬럼과 실제 RK 상태는 일치하는가?
-- applylogdb는 이 중간 상태의 로그를 어떻게 처리하는가?
```

**예제 설명**: 이는 "실패 중간 상태"를 파고드는 전형적인 경계 조건이다. 단일 ALTER 문 안에 여러 제약 변경을 묶는 것이 허용된다는 것 자체는 편리하지만, 그 원자성이 보장되지 않으면 장애 상황에서 데이터베이스가 "RK 없는 복제 테이블"이라는, 스펙이 애초에 금지하려던 바로 그 상태로 남을 위험이 있다.

**제안**: 복합 ALTER 문의 원자성(전부 성공 또는 전부 롤백)을 명시적으로 보장한다고 기술하고, 중간에 장애가 발생했을 때의 복구 동작(재기동 후 상태 점검)을 별도로 서술해야 한다.

## 리뷰 10

**[심각도: 중요] 에러 메시지 텍스트가 예제마다 있다가 없다가 해서, 실무자가 "무엇이 틀렸는지" 알 방법이 일관되지 않는다**

**대상**: 예시 11 (`ERROR: Primary key "pk_tbl_a" already defined for class "dba.tbl".`) vs 예시 12, 16 등 (그냥 `ERROR`)

**문제 설명**: 예시 11은 실제 에러 메시지 전문을 보여주는데, 이 메시지는 사실 "PK 중복 정의 금지"라는 기존(RK 도입 이전부터 있던) 규칙에서 나오는 것이라고 스펙 자신이 밝히고 있다("기존의 연산 결과와 동일한 경우 ... 비교하기위한 예시만 표기"). 반면 이번 스펙이 새로 추가하는 진짜 RK 관련 제약(예시 12: RK로 쓰이는 PK 삭제 금지, 예시 16: RK 후보가 없으면 인덱스 삭제 금지)에 대해서는 정작 에러 메시지 텍스트가 하나도 제공되지 않는다.

**구체 예제(시나리오)**:
```sql
-- 예시 12: RK로 사용 중인 PK 삭제 시도
ALTER TABLE table_name DROP PRIMARY KEY;
-- 스펙: "ERROR" (메시지 본문 없음)

-- 실무자는 이 에러가 다음 중 무엇인지 메시지를 봐야 구분할 수 있다:
--  (1) "PK가 복제 키로 사용 중이라 삭제할 수 없습니다" 같은 RK 특화 메시지인가?
--  (2) 혹은 기존에도 있던 일반적인 제약 위반 메시지인가?
```

**예제 설명**: 실무자가 운영 중 이 에러를 실제로 만나면, 화면에 뜨는 문구를 보고 원인을 파악하고 §4-2의 어느 규칙에 해당하는지 매뉴얼에서 찾아야 한다. 매뉴얼 자체에 메시지 텍스트가 없으면, 그 매핑 작업을 사용자가 직접 시행착오로 해야 한다.

**제안**: 신규로 추가되는 모든 RK 관련 제약 위반에 대해 실제 에러 메시지 문구(가칭 "Column "b" is currently used as a replication key and cannot be dropped." 같은 형태)를 스펙에 명시하고, 예시 11처럼 전문을 보여주는 방식으로 통일해야 한다.

## 리뷰 11

**[심각도: 중요] UK가 여러 개 존재할 때, "RK로 선택되지 않은" UK를 삭제하는 경우가 스펙에 없다**

**대상**: §4-2 "테이블에 하나의 복제키만 존재한다면 복제키를 수정하는 DDL이 제한되지만, 다른 복제키 후보가 함께 존재한다면 모든 DDL은 허용된다" 및 예시 15 (UNIQUE 삭제 → ERROR)

**문제 설명**: 예시 15는 "복제키 후보가 1개인 경우"만 다룬다고 스펙 스스로 전제하고 있다("복제키 후보가 1개인 경우(= 복제키) 제약사항은 다음과 같다" 하위에 예시 14~16이 나열됨). 그렇다면 UK가 2개 있는 테이블에서, 그중 RK로 선택되지 않은 쪽 UK를 삭제하는 경우는 "모든 DDL이 허용된다"는 규칙에 따라 OK여야 할 것 같은데, 이 조합에 대한 예제가 스펙에 전혀 없다. 더구나 리뷰 7에서 지적했듯 사용자는 애초에 어느 UK가 RK로 선택된 것인지 조회조차 할 수 없으므로, "이 UK는 지워도 되는 UK인가?"를 실행 전에는 판단할 수 없다.

**구체 예제(시나리오)**:
```sql
CREATE TABLE tbl (
    a INT NOT NULL UNIQUE,   -- 스펙 규칙상 아마도 RK로 선택
    b INT NOT NULL UNIQUE,   -- RK 후보이지만 비활성
    c INT
);

-- b의 UNIQUE 제약만 삭제
ALTER TABLE tbl DROP CONSTRAINT u_tbl_b;
-- 결과가 OK인가 ERROR인가? a만 남아 "RK 후보 1개" 상태가 되는 이 시도 자체는
-- "삭제 시점엔 후보가 2개였다"는 이유로 허용되는가?
```

**예제 설명**: 이 시나리오는 "삭제 결과 RK 후보가 1개로 줄어드는 DDL"이 삭제 직전 시점의 후보 개수를 기준으로 판정되는지, 삭제 직후 결과 상태를 기준으로 판정되는지를 묻는다. 스펙은 이런 "RK 후보 개수가 DDL 실행 도중에 줄어드는" 경계 상황에 대해 판정 기준 자체를 언급하지 않는다.

**제안**: RK 후보가 2개 이상인 상태에서 그중 하나를 삭제해 후보가 1개로 줄어드는 케이스를 별도 예제로 추가하고, 판정이 "실행 전 상태 기준"인지 "실행 후 상태 기준"인지 명시해야 한다.

## 리뷰 12

**[심각도: 보통] RK(PK)가 있는 테이블도 REPLICATION=OFF면 FK 참조 대상이 될 수 없다는 규칙이 직관에 어긋난다**

**대상**: §5 예시 18, §1 "복제 제외 테이블은 복제 키의 유무와 상관 없이 생성 가능하다"

**문제 설명**: §1은 "RK가 있어도 없어도 복제 제외 테이블을 만들 수 있다"고 명시해 마치 RK 유무가 REPLICATION 여부와 독립적인 것처럼 서술한다. 그런데 예시 18을 보면 `non_repl_customers`는 PK(즉 RK)가 멀쩡히 있는데도 REPLICATION=OFF라는 이유만으로 FK 참조 자체가 ERROR가 된다. 즉 "RK가 있어도 소용없고, REPLICATION 속성만 본다"는 규칙인데 이게 §5 본문에서 명시적으로 강조되지 않고 예제를 통해서만 간접적으로 드러난다.

**구체 예제**:
```sql
CREATE TABLE non_repl_customers(
    customer_id INT PRIMARY KEY,   -- RK(PK) 존재
    country INT
) REPLICATION = OFF;

CREATE TABLE orders(
    order_id INT PRIMARY KEY,
    customer_id INT,
    CONSTRAINT fk_customer_id FOREIGN KEY (customer_id)
    REFERENCES non_repl_customers(customer_id)
);
-- ERROR
```

**예제 설명**: `non_repl_customers`는 PK가 버젓이 있어서 "RK가 없어서 참조가 막혔다"는 흔한 오해를 하기 쉽지만, 실제로는 RK 유무와 전혀 무관하게 REPLICATION=OFF라는 사실 하나만으로 막힌다. 사용자가 "PK를 추가하면 해결되겠지"라고 잘못 접근할 가능성이 크다.

**제안**: §5 본문에 "이 제약은 참조 테이블의 RK 유무와 무관하며, 오직 REPLICATION 속성만으로 판정된다"는 문장을 명시적으로 추가해야 한다.

## 리뷰 13

**[심각도: 치명] FK 관계가 이미 맺어진 뒤, 참조 테이블을 사후에 REPLICATION=OFF로 바꾸는 경로가 완전히 열려 있다**

**대상**: §5 (FK 생성 시점 검증만 다룸), §4 "복제 제외 테이블은 ... 복제 테이블로 변경하는것 외의 모든 DDL을 사용할 수 있다" (즉 복제 대상 → 복제 제외 방향 전환은 항상 허용)

**문제 설명**: §5는 FK를 "새로 추가"하는 시점의 검증(예시 18, 23)만 다룬다. 그런데 §4에 따르면 이미 복제 대상이던 테이블을 복제 제외로 바꾸는 것(ON→OFF)은 HA 모드에서도 항상 허용된다. 이 둘을 조합하면, `customers`를 참조하는 `orders`가 이미 정상적으로 구성된 뒤에, 아무도 막지 않는 `ALTER TABLE customers REPLICATION=OFF`를 실행하는 순간 정확히 이 스펙이 해결하려던 원래 장애 시나리오(작업지시 배경의 FK 참조 테이블 누락 문제, 원본 다이어그램의 상황)가 재현된다.

**구체 예제(시나리오)**:
```sql
-- 1) 정상적으로 FK 관계 구성 (예시 17과 동일)
CREATE TABLE customers(
    customer_id INT PRIMARY KEY,
    country INT
);
CREATE TABLE orders(
    order_id INT PRIMARY KEY,
    customer_id INT,
    CONSTRAINT fk_customer_id FOREIGN KEY (customer_id) REFERENCES customers(customer_id)
);
-- 여기까지는 §5 예시 17 그대로. customers, orders 둘 다 REPLICATION=ON(기본값).

-- 2) 운영 중, 누군가 customers를 복제에서 빼려고 한다 (§4 규칙상 항상 허용됨)
ALTER TABLE customers REPLICATION = OFF;
-- OK (§4: 복제 대상 -> 복제 제외 전환은 막지 않음)

-- 3) 이제 orders는 여전히 복제 대상, customers는 복제 제외.
-- Failover 발생 -> 슬레이브에는 orders만 있고 customers 데이터가 없음
-- => §5가 막으려던 바로 그 상황이 "생성 시점 검증"을 우회해서 재현된다.
```

**예제 설명**: §5는 "FK 테이블을 만들 때" 참조 테이블 상태를 확인하지만, "이미 만들어진 FK 관계의 참조 테이블 상태가 나중에 바뀌는 것"은 아무도 확인하지 않는다. §7에서 "HA 실행 시 외래키 테이블에서 참조하는 테이블의 상태도 확인해 ... 에러를 출력할 수 있어야한다"는 문장이 있긴 하지만, 이는 "HA 전환 시점"의 검사이지 "운영 중 REPLICATION=OFF로 바꾸는 그 순간"의 검사가 아니다. 즉 이미 HA가 켜져서 운영 중인 상태에서 이 ALTER 한 줄이 통과되면, 다음 Failover까지는 아무도 눈치채지 못한 채 데이터 불일치 폭탄을 안고 가게 된다.

**제안**: `ALTER TABLE ... REPLICATION=OFF`를 실행할 때, 그 테이블을 참조하는 FK가 복제 대상 테이블에 걸려 있다면 즉시 에러를 내도록 §4와 §5의 규칙을 상호 참조해서 재정의해야 한다.

## 리뷰 14

**[심각도: 보통] 복제 제외 테이블을 포함하는 뷰 생성 시 경고조차 없다**

**대상**: §6 "복제 제외 테이블이 뷰에 포함되어 있을 경우 ... 수행의 결과는 두 노드가 일치하지 않는다. 이 부분에대해 큐브리드 복제 모듈은 책임지지 않는다."

**문제 설명**: "책임지지 않는다"는 표현 자체가 이미 사용자 경험 관점에서 불친절하다. 더 큰 문제는 CREATE VIEW 시점에 아무런 경고(WARNING)도 뜨지 않는다는 점을 스펙이 암묵적으로 전제하고 있다는 것이다. 리뷰 13과 마찬가지로, 뷰를 만든 시점과 실제로 문제가 드러나는 시점(Failover 후 SELECT 결과가 마스터와 다름을 사람이 알아챌 때) 사이에 아무 신호가 없다.

**구체 예제(시나리오)**:
```sql
CREATE TABLE non_repl_customers(
    customer_id INT PRIMARY KEY,
    country INT
) REPLICATION = OFF;

CREATE VIEW v_customer_country AS
SELECT customer_id, country FROM non_repl_customers;
-- 스펙상 아무 경고 없이 OK로 추정됨

-- Failover 이후, 슬레이브에서
SELECT * FROM v_customer_country;
-- 결과가 텅 비어있거나 마스터와 다름. 이 시점에야 문제를 발견한다.
```

**예제 설명**: 뷰는 여러 테이블을 조합하는 특성상 어떤 원본 테이블이 REPLICATION=OFF인지 뷰 정의만 보고는 한눈에 파악하기 어렵다. 최소한 CREATE VIEW 시점에 "이 뷰는 복제 제외 테이블을 포함하고 있어 Failover 후 결과가 다를 수 있습니다"라는 경고라도 있어야 사용자가 인지하고 대응할 수 있다.

**제안**: CREATE VIEW 시 원본 테이블 중 REPLICATION=OFF가 있으면 WARNING을 출력하도록 하고, `show create view` 또는 카탈로그 조회에서도 이 사실을 표시해야 한다.

## 리뷰 15

**[심각도: 사소] "파일 리스트"라는 용어가 무엇을 가리키는지 불명확하다**

**대상**: §7 "제약사항 위반 시 에러와함께 파일 리스트를 출력한다"

**문제 설명**: 문맥상 위반 대상은 "테이블"(RK 없는 복제 테이블, FK 참조 대상이 복제 제외인 테이블)인데, 출력되는 것은 "파일 리스트"라고 되어 있다. 큐브리드에서 "파일"이라는 단어는 일반적으로 unloaddb가 생성하는 `.unl` 파일 같은 물리 파일을 연상시키는데, 이 맥락에서는 테이블 목록을 잘못 표현한 것인지, 실제로 어떤 파일(로그 파일 등)에 목록을 기록한다는 뜻인지 구분이 안 된다.

**구체 예제(시나리오)**:
```text
$ cubrid hb start
ERROR: replication constraint violation.
파일 리스트: ???
```

**예제 설명**: 실무자는 이 메시지를 보고 화면에 표 형태로 위반 테이블 목록이 뜨는 것을 기대할지, 아니면 로그 디렉토리에서 별도 파일을 찾아봐야 하는지 판단할 수 없다.

**제안**: "파일 리스트"를 "위반 테이블 목록"처럼 명확한 용어로 교정하고, 실제 출력 형식(콘솔 출력인지 로그 파일 경로인지)의 예시를 §7에 추가해야 한다.

## 리뷰 16

**[심각도: 중요] §7이 발동하는 실제 시나리오가 스펙 안에서 모호하다**

**대상**: §7 "HA 실행시 다음 사항을 제약사항을 확인하며 ... 이 경우 싱글모드에서 ALTER TABLE… 을 이용해 ... 변경한 후 HA를 재시작해야한다"

**문제 설명**: §4-2는 "HA 모드에서는 RK를 깨는 DDL 자체가 차단된다"고 이미 규정하고 있다. 그렇다면 "HA가 이미 정상적으로 도입되어 운영 중인 상태"에서는 RK 없는 테이블이 새로 생길 수 없어야 하므로, §7의 위반 상황은 사실상 다음 두 경우로만 한정될 것으로 보인다: (1) 이 스펙을 도입하는 최초 시점에 기존 싱글 모드 스키마를 그대로 HA로 전환하려는 경우, (2) §8의 unloaddb/loaddb 마이그레이션 이후. 그런데 §7 본문은 이 두 경우를 명시적으로 언급하지 않고 그냥 일반론으로 서술되어 있어서, 실무자는 "평소에 정상 운영하다가도 이 에러를 만날 수 있는 것인지" 불안하게 된다.

**구체 예제(시나리오)**:
```text
시나리오 A (최초 도입): 기존 싱글 모드로 3년 운영한 DB에 이번 패치 적용 후 최초로 HA 시작
  -> §7 위반 다수 발생 가능성 높음

시나리오 B (정상 운영 중): 이미 HA로 잘 돌아가던 DB에서 어느 날 갑자기 hb start 시 §7 위반?
  -> §4-2가 RK를 깨는 DDL을 이미 막고 있다면, 이 경로로는 위반이 발생할 수 없어야 하는데
     스펙이 이를 명시적으로 보장한다고 말하지 않는다.
```

**예제 설명**: 만약 시나리오 B가 실제로 발생 가능하다면(예: HA가 잠깐 다운되어 있는 사이 싱글 모드로 기동해서 DDL을 친 경우), §7은 "운영 중 상시 발생 가능한 리스크"가 되고, 발생 가능하지 않다면 그렇다는 보장을 스펙이 명시해야 한다. 지금은 어느 쪽인지 알 수 없다.

**제안**: §7에 "이 검사는 주로 (a) 최초 HA 도입, (b) HA 다운 중 싱글 모드로 스키마를 변경한 뒤 재기동, (c) §8 마이그레이션 이후에 발생한다"처럼 구체적 트리거를 명시해야 한다.

## 리뷰 17

**[심각도: 치명] §8 "자동으로 RK를 할당한다"는 문장이 §1/§4의 원칙과 정면으로 모순되는 것처럼 읽힌다**

**대상**: §8 "복제 테이블의 경우 큐브리드는 자동으로 RK를 할당한다." vs §1 "복제 키는 큐브리드 엔진에 의해 Primary Key 혹은 Not Null Unique Key들 중 하나로 선택된다", §4-1 "HA 모드에서는 CREATE TABLE 시 복제키가 없는 복제 테이블을 생성할 수 없다"

**문제 설명**: §1과 §4에서 말하는 "RK 선택"은 어디까지나 "이미 존재하는 PK/UK 중에서 고른다"는 뜻이었다. 그런데 §8의 "자동으로 RK를 할당한다"는 문장은 마치 PK/UK가 전혀 없는 테이블에도 큐브리드가 RK를 새로 만들어(예: 내부 OID 기반 키를 생성해서) 부여한다는 것처럼 읽힌다. 만약 후자가 맞다면 이는 MySQL식 "PK 없으면 전체 컬럼을 키로 쓰는" 방식과 사실상 유사한 것을 loaddb 한정으로 허용하는 셈이 되어, 작업지시 배경에서 "성능 문제로 명시적으로 배제했다"고 밝힌 방식과 충돌한다. 반대로 전자(기존 PK/UK 중 선택)가 맞다면, RK 후보가 아예 없는 테이블(PK도 UK도 없는 테이블)을 unload한 데이터를 "복제 테이블"로 load하려 할 때 §4-1의 "RK 없는 복제 테이블은 생성 불가" 규칙과 충돌해서 로드 자체가 실패해야 하는데, 그 경우에 대한 언급이 없다.

**구체 예제(시나리오)**:
```sql
-- 싱글 모드, PK도 UK도 없는 테이블
CREATE TABLE plain_tbl (
    x INT,
    y INT
);  -- REPLICATION 옵션 생략 -> 기본 ON, RK 없음 (§2-1, §4-1에 따르면 싱글모드라 생성은 됨)

-- unloaddb로 덤프
-- $ unloaddb -i ... plain_tbl ...

-- 다른 DB(혹은 같은 DB 재구성)에 loaddb
-- $ loaddb ...
-- §8: "복제 테이블의 경우 큐브리드는 자동으로 RK를 할당한다"
-- => plain_tbl에 RK가 없는데 무엇을 "할당"하는가?
--    (a) 내부적으로 숨은 키를 새로 만들어 RK로 쓰는가?
--    (b) 아니면 이 문장은 "PK/UK가 있는 테이블에 한해 그중 하나를 RK로 지정한다"는
--        뜻이고, PK/UK가 없으면 load 자체가 §4-1처럼 실패하거나 강제로 REPLICATION=OFF가 되는가?
```

**예제 설명**: 이 모호함은 단순한 표현 문제가 아니라, "PK/UK 없는 테이블을 복제 테이블로 취급할 수 있는가"라는 이 스펙 전체의 핵심 전제와 직결된 문제다. §8 한 문장 때문에 전체 설계 원칙이 흔들리는 것처럼 보인다.

**제안**: "자동으로 RK를 할당한다"를 "기존 PK/UK 중 하나를 RK로 지정한다"로 명확히 바꾸고, PK/UK가 전혀 없는 테이블을 복제 테이블로 load하려는 경우의 동작(실패, 자동 OFF 전환, 혹은 다른 처리)을 명시적으로 추가해야 한다.

## 리뷰 18

**[심각도: 중요] 하위 버전에서 덤프한 파일을 로드하면 무조건 복제 테이블이 되는데, 그 직후 HA 전환 시 무더기 실패가 예상되는데도 사전 점검 안내가 없다**

**대상**: §8 "특히 하위 버전에서 unload 한 데이터 파일에는 복제 여부를 저장하는 변수가 설정되어있지 않으므로 (싱글 모드에서) load 시 모두 복제 테이블로 설정된다."

**문제 설명**: 구버전에서 넘어온 사용자는 자신의 모든 테이블이 (RK 유무와 무관하게) 일괄적으로 "복제 대상"으로 설정된다. 이 중 PK도 UK도 없는 테이블이 하나라도 있으면, 리뷰 3에서 지적한 것과 동일하게 나중에 HA를 켜는 순간 무더기 에러를 만나게 된다. 이는 버전 업그레이드라는, 실무에서 가장 조심스럽게 다뤄야 할 작업의 직후에 발생하는 문제인데, §8에는 이를 예방하거나 사전에 확인하라는 안내가 전혀 없다.

**구체 예제(시나리오)**:
```text
1) 구버전 CUBRID에서 unloaddb 실행 (REPLICATION 개념 자체가 없던 시절 덤프)
2) 신버전으로 마이그레이션, loaddb 실행
   -> §8 규칙에 따라 싱글 모드에서 모든 테이블이 REPLICATION=ON으로 강제 설정됨
3) 이 상태 그대로 서비스를 재개하기 위해 HA 시작
   $ cubrid hb start
   -> RK 없는 테이블이 하나라도 있으면 §7에 따라 에러 + (불명확한) 파일 리스트
```

**예제 설명**: 업그레이드 작업자는 loaddb까지 성공했으니 마이그레이션이 끝났다고 판단하기 쉽지만, 실제로는 HA 전환이라는 다음 관문이 남아 있고 이 관문에서 실패할 위험이 구버전 스키마일수록 높다(RK 개념이 없던 시절 설계된 테이블일수록 PK 없는 보조 테이블이 많을 수 있다).

**제안**: loaddb 완료 직후, RK 없이 REPLICATION=ON으로 설정된 테이블 목록을 자동으로 출력하는 사후 점검 단계를 추가하거나, 최소한 매뉴얼에 "loaddb 후 HA 전환 전 반드시 리뷰 3의 점검 쿼리를 실행하라"는 안내를 넣어야 한다.

## 리뷰 19

**[심각도: 중요] §9 SUMMARY가 §5의 실질적 제약을 감춰서 요약만 읽은 사용자를 오도할 수 있다**

**대상**: §9 세 번째 항목 "RK가 있는 테이블 역시 복제 제외대상이 될 수 있음" vs §5 예시 18 (RK 있는 참조 테이블도 REPLICATION=OFF면 FK 참조 불가)

**문제 설명**: SUMMARY만 훑어보는 실무자(바쁜 실무자는 본문 대신 요약만 보고 넘어가는 경우가 많다)는 "RK 유무와 REPLICATION은 완전히 독립적이니 RK가 있어도 자유롭게 복제 제외로 만들 수 있겠구나"라고 이해하게 된다. 하지만 리뷰 13에서 지적했듯, 그 테이블이 FK로 참조되고 있다면 실제로는 자유롭지 않다(혹은 자유롭지만 데이터 정합성이 깨진다). SUMMARY는 이 조건부 진실을 숨기고 있다.

**구체 예제(시나리오)**:
```text
SUMMARY만 읽은 사용자의 머릿속 규칙:
  "RK가 있든 없든 REPLICATION=OFF로 바꾸는 건 자유롭다"

실제로 발생 가능한 상황 (리뷰 13과 동일):
  customers(RK 있음, FK로 orders가 참조 중)를 REPLICATION=OFF로 전환
  -> §4 규칙상 문법적으로는 허용됨
  -> 그러나 §5의 취지(FK 참조 테이블은 복제 대상이어야 함)를 정면으로 위반하는 결과
```

**예제 설명**: SUMMARY가 조건("단, FK로 참조되고 있지 않다면")을 빠뜨린 채 결론만 서술해서, 문서를 요약 중심으로 훑는 사용자에게 실제보다 더 자유로운 규칙으로 각인될 위험이 있다.

**제안**: SUMMARY 항목에 "단, 다른 복제 대상 테이블의 FK가 이를 참조하고 있는 경우는 예외"라는 단서를 명시해야 한다.

## 리뷰 20

**[심각도: 보통] RK 재선정이 "언제" 반영되는지 스펙 전체에 걸쳐 한 번도 명시되지 않는다**

**대상**: 전체 개념(§1 RK 선택 규칙, §4-2 DDL 허용 규칙)

**문제 설명**: 스펙은 "RK가 무엇으로 결정되는가"(정적 규칙)는 여러 번 설명하지만, "그 결정이 실제로 언제 재계산/반영되는가"(동적 시점)는 한 번도 정면으로 다루지 않는다. 이는 리뷰 1, 9, 11에서 각각 다른 각도로 이미 지적한 문제의 공통 뿌리다. 트랜잭션 커밋 시점인지, DDL 문장 실행 즉시인지, HA 재시작 시점인지에 따라 실무자가 운영 중 겪을 수 있는 위험의 크기가 완전히 달라진다.

**구체 예제(시나리오)**:
```sql
-- HA 운영 중, RK 후보가 2개(a: PK, b: UK)인 테이블에서 PK를 제거하고 UK만 남기는 경우
ALTER TABLE tbl DROP CONSTRAINT PRIMARY KEY;
-- §4-2 규칙상 "다른 복제키 후보(b)가 함께 존재하면 모든 DDL은 허용된다" 이므로 OK로 추정

-- 이 순간부터 실제 복제에 쓰이는 컬럼이 a에서 b로 전환되는데,
-- (1) 이 ALTER 문이 커밋되는 즉시 전환되는가?
-- (2) applylogdb가 이미 처리 중이던, a를 키로 사용한 이전 로그 레코드와
--     이 전환 시점 사이에 순서 보장이 되는가?
-- (3) 슬레이브 쪽에서도 동일한 시점에 전환이 일어난다는 보장이 있는가
--     (마스터/슬레이브 간 반영 시점이 어긋나면 그 사이 도착한 로그를
--      슬레이브가 어떤 키로 매칭해야 하는지 모호해진다)?
```

**예제 설명**: 이 시나리오는 "RK 전환"이라는, 이 스펙에서 가장 자주 등장하는 조작(예시 7, 13)이 복제 파이프라인 관점에서 원자적이고 순서가 보장되는 사건인지, 아니면 마스터와 슬레이브 사이에 시차가 생길 수 있는 사건인지를 묻는다. 최종 사용자 입장에서는 "내가 이 ALTER를 실행하는 순간 잠깐이라도 복제가 꼬일 위험이 있는가"를 알아야 운영 타이밍(트래픽이 적은 시간대 등)을 잡을 수 있는데, 스펙은 이에 대해 아무런 힌트도 주지 않는다.

**제안**: RK 전환이 마스터에서 커밋되는 즉시 슬레이브에도 동일 시점 기준으로 반영됨을 명시하고, 전환 시점 전후로 발생한 DML 로그의 처리 순서(구 RK 기준으로 처리할지, 신 RK 기준으로 처리할지)를 규정해야 한다.
