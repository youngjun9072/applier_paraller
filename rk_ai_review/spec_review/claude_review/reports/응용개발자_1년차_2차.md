# CUBRID HA 복제(REPLICATION 옵션/RK) 스펙 리뷰 — 응용 개발자(DB 사용) · 1년차 관점 · 2차 라운드

## 2차 라운드 개요

1차에서는 RK 선택 규칙, FK-복제 정합성, 마이그레이션 도구와의 충돌, 카탈로그 조회 등 스펙 본문이 직접 다루는 흐름을 따라갔다. 2차에서는 1차와 최종보고서(40개 통합 이슈)가 이미 짚은 지점(RK 비결정성, FK 부모 사후 OFF 전환, RK 조회 불가, "파일 리스트", §8/§9 기본값 모순, trailing comma, fail-late 구조, 다중 절 ALTER 원자성, 업그레이드 경로 등)은 모두 제외하고, 스펙이 **아예 언급조차 하지 않는 인접 영역**—트랜잭션/커밋 동작, 표준 SQL 메타데이터 노출, 권한(GRANT) 모델, TDE·REUSE_OID 같은 기존 CUBRID 기능과의 상호작용, FK의 CASCADE 액션, 물리 백업 도구(backupdb/restoredb)의 적용 범위, 그리고 문서 자체의 구조적 결함(예시 번호 누락, 예시가 아예 없는 절)—을 훑었다. 개수를 채우기보다 실제로 배포 자동화·CI/CD 파이프라인·권한 설계 업무에서 부딪힐 만한 지점만 추렸다.

### 리뷰 21

**[심각도: 중요] 여러 ALTER 문을 묶은 마이그레이션 스크립트에서 DDL 실패 시 트랜잭션이 통째로 롤백되는지, 문장 단위로만 실패하는지 불명확하다**

**대상**: §2-2(예시 5, 6), §4-2(예시 10~16) — 모든 "ERROR" 예시가 단일 SQL 문 기준으로만 서술됨

**문제 설명**: Flyway/Liquibase 같은 마이그레이션 도구는 보통 하나의 배포 단위(changeSet, migration 파일)에 여러 개의 `ALTER TABLE` 문을 담고, 그중 하나라도 실패하면 전체를 롤백해 "부분 적용"을 방지하려 합니다. 그런데 이 스펙에 나오는 모든 에러 예시(예시 5, 10, 12, 15, 16 등)는 SQL 문 하나만 딱 떼어 "ERROR"라고 표시할 뿐, 그 문장이 트랜잭션 안에서 실행됐을 때 앞서 이미 실행된 다른 문장들까지 함께 롤백되는지(트랜잭션 전체 실패), 아니면 CUBRID가 DDL을 즉시 커밋(auto-commit)해버려서 실패한 문장만 빠지고 앞 문장들은 이미 확정되어버리는지에 대한 언급이 전혀 없습니다. 이 차이는 배포 스크립트가 "전부 성공 아니면 전부 실패"를 전제로 설계됐는지 여부를 완전히 뒤집습니다.

**구체 예제(SQL, 마이그레이션 스크립트 관점)**:
```sql
-- migration_0043.sql — 하나의 배포 단위로 묶어 실행한다고 가정
START TRANSACTION;

ALTER TABLE orders REPLICATION=OFF;          -- (1) 성공
ALTER TABLE order_events REPLICATION=OFF;    -- (2) 성공
ALTER TABLE inventory DROP PRIMARY KEY;      -- (3) ERROR (§4-2 예시 12, RK로 쓰이는 PK라 삭제 불가)

COMMIT;
-- (3)이 실패했을 때, (1)과 (2)는 이미 반영된 상태로 남는가?
-- 아니면 COMMIT을 안 했으니 자동으로 (1)(2)까지 함께 취소되는가?
```

**예제 설명**: 만약 CUBRID의 DDL이 MySQL처럼 각 문장마다 암묵적 커밋(implicit commit)을 한다면, (3)에서 스크립트가 멈춰도 (1)·(2)는 이미 운영 DB에 반영된 채로 남아 배포 도구가 기대하는 "원자적 배포"가 깨집니다. 반대로 PostgreSQL처럼 DDL도 트랜잭션에 포함된다면 `COMMIT` 전까지는 아무것도 반영되지 않아 안전합니다. 이 스펙이 다루는 모든 제약 위반은 결국 "운영 배포 스크립트가 실행되다가 중간에 걸리는" 상황을 전제로 하는데, 정작 그 중간 실패가 배포 전체에 어떤 영향을 주는지는 스펙 어디에도 없습니다. 1년차 개발자가 배포 스크립트에 트랜잭션을 감싸 넣을지 말지조차 이 문서만으로는 결정할 수 없습니다.

**제안**: DDL 문의 커밋 동작(자동 커밋 여부, 트랜잭션 포함 가능 여부)을 §2 또는 별도의 "DDL 실행 모델" 절로 명시하고, 특히 REPLICATION 관련 제약 위반이 발생했을 때 이전에 성공한 DDL까지 함께 롤백되는지를 예제로 보여줘야 합니다.

### 리뷰 22

**[심각도: 중요] REPLICATION/RK 정보가 표준 SQL 메타데이터(information_schema 등)로 노출되지 않아 스키마 형상관리 도구가 이 기능 자체를 인식하지 못한다**

**대상**: §2-3 (예시 8: show create table, 예시 9: select * from db_class)

**문제 설명**: 스펙이 제시하는 두 조회 수단은 모두 CUBRID 전용 문법(`show create table`)이거나 CUBRID 내부 시스템 카탈로그(`db_class`)입니다. 반면 Liquibase의 `diff`/`generateChangeLog`, Flyway의 스키마 비교 확장, 대부분의 데이터베이스 리버스 엔지니어링 도구(JPA의 스키마 검증 모드 등)는 벤더 중립적인 표준 뷰인 `information_schema`(또는 JDBC의 `DatabaseMetaData`)를 통해 테이블·컬럼·제약을 읽어 "환경 A와 환경 B의 스키마가 같은가"를 자동으로 비교합니다. 스펙에는 `REPLICATION` 옵션이나 RK가 이런 표준 경로로도 노출되는지에 대한 언급이 전혀 없습니다.

**구체 예제(시나리오)**:
```sql
-- 스테이징 환경: orders 테이블이 실수로 REPLICATION=OFF로 배포됨
-- 운영 환경: orders 테이블은 REPLICATION=ON (의도한 상태)

-- 배포 파이프라인이 두 환경의 스키마 드리프트(설정 불일치)를 감지하려고
-- 표준 스키마 비교 도구(예: Liquibase diff)를 돌린다.
-- 이 도구가 information_schema.tables/columns/table_constraints 정도만 비교한다면,
-- REPLICATION 옵션 차이는 diff 결과에 전혀 나타나지 않는다.
```

**예제 설명**: 만약 REPLICATION 옵션이 CUBRID 고유 카탈로그(`db_class`)에만 존재하고 표준 `information_schema`에는 없다면, 범용 스키마 비교 도구를 그대로 쓰는 조직에서는 이 스펙이 새로 도입한 가장 중요한 속성(복제 대상 여부)이 드리프트 탐지에서 완전히 사각지대가 됩니다. 결국 "스테이징에서는 복제되던 테이블이 운영에서는 조용히 복제 제외 상태"인 사고를 표준 도구로는 절대 잡아낼 수 없고, 오직 CUBRID 전용 스크립트를 따로 짜야만 알 수 있습니다.

**제안**: `REPLICATION` 옵션과 RK 후보 정보를 CUBRID의 `information_schema` 대응 뷰(또는 이에 준하는 표준 조회 경로)에도 노출하거나, 최소한 "이 정보는 표준 메타데이터로는 조회 불가능하며 반드시 `db_class`를 직접 조회해야 한다"는 점을 명시해야 합니다.

### 리뷰 23

**[심각도: 보통] "생략 시 ON"과 "명시적으로 REPLICATION=ON을 쓴 경우"를 조회 결과로 구분할 수 없어, 스키마 diff 도구가 항상 거짓 드리프트를 보고할 수 있다**

**대상**: §2-1 "이 옵션은 생략 가능하며 생략시 ON으로 자동으로 복제 테이블로 생성된다" / §2-3 예시 8

**문제 설명**: 예시 8은 `show create table`의 출력이 원래 DDL에 `REPLICATION` 옵션을 썼는지 여부와 상관없이 항상 `REPLICATION ON`을 명시적으로 붙여서 보여줍니다. 그런데 마이그레이션 이력 파일(예: Liquibase changelog)에는 보통 `REPLICATION` 옵션을 아예 생략한 원본 DDL이 그대로 저장되어 있습니다. 스키마 비교 도구가 "이력 파일에 적힌 DDL 텍스트"와 "현재 운영 DB에서 리버스 엔지니어링한 DDL 텍스트"를 문자열 단위로 비교하는 방식을 쓴다면, 옵션을 생략한 원본과 옵션이 항상 채워져 나오는 조회 결과가 매번 다르게 보여 실제로는 아무 문제가 없는데도 계속 "드리프트 발견"으로 오탐될 수 있습니다.

**구체 예제(시나리오)**:
```sql
-- 마이그레이션 이력에 저장된 원본 DDL (REPLICATION 옵션 생략)
CREATE TABLE orders(
    order_id INT PRIMARY KEY,
    customer_id INT
);

-- 운영 DB에서 show create table로 리버스 엔지니어링한 결과 (예시 8과 동일 패턴)
-- 'CREATE TABLE [orders] (...) REUSE_OID, COLLATE utf8_bin, REPLICATION ON'

-- 문자열 비교 도구: "이력 파일에는 REPLICATION이 없는데 실제 DB엔 REPLICATION ON이 있다"
-- → 매번 거짓 드리프트로 보고됨
```

**예제 설명**: 도구가 단순 텍스트 비교가 아니라 의미 단위로 파싱해서 비교한다면 문제가 없겠지만, 스펙 어디에도 "생략과 명시적 ON은 완전히 동일하게 취급되므로 도구가 이를 정규화해야 한다"는 안내가 없습니다. 신입 개발자가 처음 스키마 비교 도구를 이 옵션과 함께 설정할 때, 계속되는 거짓 경고의 원인을 스펙만 보고는 짐작하기 어렵습니다.

**제안**: 문서에 "생략된 REPLICATION 옵션은 저장 시점에 ON으로 확정되며, 이후 조회 결과는 항상 명시적으로 표시된다"는 점과, 스키마 비교 도구 작성 시 이를 정규화 규칙으로 반영해야 한다는 안내를 추가해야 합니다.

### 리뷰 24

**[심각도: 중요] REPLICATION 옵션을 변경/조회하는 데 필요한 권한(GRANT) 모델이 전혀 정의되지 않았다**

**대상**: §2-2 (ALTER TABLE ... REPLICATION), §2-3 (조회)

**문제 설명**: CI/CD 파이프라인은 보통 "DBA 계정"이 아니라 필요한 권한만 부여받은 별도의 배포 전용 서비스 계정으로 DDL을 실행합니다. 이 스펙은 `REPLICATION` 옵션을 다루는 새 SQL 문법을 추가했는데, 이 문법을 실행하는 데 기존의 `ALTER TABLE` 권한만으로 충분한지, 아니면 복제라는 클러스터 전체에 영향을 주는 작업의 특성상 DBA 권한(혹은 별도의 새 권한)이 필요한지에 대한 언급이 전혀 없습니다. 마찬가지로 §2-3의 조회(`db_class`)도 테이블 소유자가 아닌 일반 사용자가 다른 스키마의 REPLICATION 정보를 볼 수 있는지 불명확합니다.

**구체 예제(시나리오)**:
```sql
-- CI/CD 파이프라인 전용 계정 (제한된 권한, DBA 아님)
GRANT ALTER ON orders TO deploy_user;

-- deploy_user로 접속해 배포 스크립트 실행
csql> ALTER TABLE orders REPLICATION=OFF;
-- 일반 ALTER TABLE 권한만으로 성공하는가?
-- 아니면 "복제 설정 변경은 DBA만 가능"이라는 별도 제약에 걸려 ERROR가 나는가?
```

**예제 설명**: 만약 REPLICATION 옵션 변경에 더 높은 권한이 필요하다면, 배포 자동화를 설계하는 응용 개발자는 서비스 계정에 DBA 권한을 통째로 줄지, 아니면 이 기능만을 위한 세분화된 권한을 신청해야 하는지 미리 알아야 조직의 보안 정책과 충돌 없이 파이프라인을 설계할 수 있습니다. 이 정보가 없으면 실제로 배포를 시도해봐야만 권한 문제인지 다른 문제인지 알 수 있습니다.

**제안**: `REPLICATION` 옵션 변경과 조회에 필요한 최소 권한을 명시하고, 기존 `ALTER TABLE` 권한 체계에 포함되는지 별도 권한이 신설되는지를 §2에 표기해야 합니다.

### 리뷰 25

**[심각도: 보통] TDE(투명한 데이터 암호화)가 걸린 테이블과 REPLICATION/RK의 상호작용이 전혀 언급되지 않는다**

**대상**: §2-3 예시 9 (`tde_algorithm : 'NONE'` 필드가 카탈로그 출력에 존재함)

**문제 설명**: 예시 9의 `db_class` 조회 결과에는 `tde_algorithm`이라는 필드가 함께 출력됩니다. 즉 CUBRID에는 테이블 단위로 컬럼 데이터를 암호화하는 TDE 기능이 이미 존재한다는 뜻인데, 이 스펙은 TDE가 걸린 테이블을 복제 대상으로 설정할 때 슬레이브 쪽에도 같은 암호화 키가 준비되어 있어야 하는지, 준비되어 있지 않으면 무슨 일이 벌어지는지(복제 실패? 평문으로 복제?) 한 줄도 언급하지 않습니다. 배포를 담당하는 응용 개발자 입장에서는 "암호화된 테이블도 그냥 REPLICATION=ON으로 만들면 되는가"라는 매우 기초적인 질문에 답을 찾을 수 없습니다.

**구체 예제(시나리오)**:
```sql
-- TDE가 적용된 민감정보 테이블
CREATE TABLE customer_secrets(
    customer_id INT PRIMARY KEY,
    ssn VARCHAR(20)
) ENCRYPT='AES';   -- (TDE 문법은 예시이며, 실제 CUBRID 문법은 스펙에 없음)

-- 이 테이블을 HA 복제 대상으로 두려면(REPLICATION=ON, 기본값)
-- 슬레이브 노드에도 동일한 암호화 키/설정이 필요한가?
-- 배포 담당자가 슬레이브 구성 시 별도로 준비해야 할 것이 있는가?
```

**예제 설명**: 암호화 키 배포는 보안팀과 응용팀이 함께 챙겨야 하는 배포 체크리스트 항목인데, 이 스펙에는 TDE와의 접점 자체가 없어 "복제 설정만 하면 끝"이라고 오해하고 넘어갈 위험이 있습니다. 나중에 슬레이브에서 암호화된 데이터를 읽지 못하는 장애가 나서야 이 문제를 알게 될 수 있습니다.

**제안**: TDE 적용 테이블의 복제 대상 설정 시 필요한 사전 조건(키 배포 등)을 별도로 문서화하거나, "이번 기능은 TDE와 무관하게 동작한다"는 점을 명확히 선언해야 합니다.

### 리뷰 26

**[심각도: 보통] REUSE_OID 옵션과 RK/FK-복제 규칙의 상호작용이 언급되지 않는다**

**대상**: §2-3 예시 8, 9 (`REUSE_OID`, `is_reuse_oid_class`가 카탈로그에 함께 표시됨)

**문제 설명**: 예시 8의 `show create table` 결과에는 `REUSE_OID`라는 기존 CUBRID 테이블 옵션이 `REPLICATION ON`과 나란히 출력되고, 예시 9의 `db_class`에도 `is_reuse_oid_class` 필드가 함께 있습니다. `REUSE_OID`는 삭제된 행의 내부 식별자(OID)를 재사용하도록 하는 기존 옵션인데, 이 스펙은 `REUSE_OID`가 설정된 테이블에서 RK 선택이나 FK-복제 제약(§5)이 평소와 다르게 동작하는지에 대해 아무 말도 하지 않습니다. 두 옵션이 같은 `CREATE TABLE` 문에 함께 등장할 수 있다는 것은 예시 8에서 이미 확인되므로, 최소한 "이 둘은 독립적이라 서로 영향을 주지 않는다"는 확인이라도 필요합니다.

**구체 예제(SQL)**:
```sql
CREATE TABLE session_cache(
    session_id INT PRIMARY KEY,
    payload VARCHAR(4000)
) REUSE_OID, REPLICATION=ON;

-- REUSE_OID 테이블도 RK 선택 규칙(§1)이 동일하게 적용되는가?
-- REUSE_OID 특성상 삭제 후 재사용된 OID가 복제 로그의 행 식별에
-- (RK와 별개로) 다른 영향을 줄 가능성은 없는가?
```

**예제 설명**: `REUSE_OID`는 캐시성 테이블이나 임시 데이터 테이블에서 흔히 사용되는 성능 최적화 옵션입니다. 이런 테이블은 동시에 복제 대상으로 지정될 가능성도 높은데, 두 옵션의 조합이 검증되지 않은 조합이라면 실제 운영에서 예기치 못한 조합별 버그를 만날 위험이 있습니다.

**제안**: `REUSE_OID`와 `REPLICATION` 옵션의 조합이 지원되는 조합인지, RK 선택이나 복제 로그 기록 방식에 특별한 예외가 있는지 명시해야 합니다.

### 리뷰 27

**[심각도: 중요] FK의 ON DELETE/ON UPDATE CASCADE 같은 참조 액션이 복제 로그에 어떻게 반영되는지 전혀 언급되지 않는다**

**대상**: §5 (외래키) 전체 — CASCADE, SET NULL, RESTRICT 등 참조 액션에 대한 언급 없음

**문제 설명**: 스펙의 모든 FK 예시(17~23)는 참조 액션을 지정하지 않은 기본 FK만 다룹니다. 그러나 실무에서는 `ON DELETE CASCADE`처럼 부모 행 삭제 시 자식 행이 자동으로 함께 삭제되는 FK가 매우 흔합니다. 이 경우 마스터에서 부모 테이블의 한 행을 지우면 CASCADE로 인해 자식 테이블에서도 여러 행이 "사용자가 직접 실행하지 않은" DELETE로 지워지는데, 이 간접 삭제가 복제 로그에 개별 DELETE 문으로 기록되어 슬레이브에 전달되는지, 아니면 슬레이브가 부모 테이블의 DELETE만 받고 자신의 CASCADE 제약을 이용해 "독자적으로" 자식 삭제를 재현하는지에 따라 결과가 달라질 수 있습니다. 특히 자식 테이블이 `REPLICATION=OFF`이거나 §5의 FK-복제 규칙에 따라 아예 생성이 불가능한 조합이라면 CASCADE 동작 자체가 다른 의미를 가질 수 있습니다.

**구체 예제(SQL)**:
```sql
CREATE TABLE customers(
    customer_id INT PRIMARY KEY,
    country INT
);   -- REPLICATION=ON (기본값)

CREATE TABLE orders(
    order_id INT PRIMARY KEY,
    customer_id INT,
    CONSTRAINT fk_o_c FOREIGN KEY (customer_id) REFERENCES customers(customer_id)
        ON DELETE CASCADE
);   -- REPLICATION=ON (기본값)

-- 마스터에서 고객 한 명을 삭제하면 관련 주문도 CASCADE로 모두 삭제됨
DELETE FROM customers WHERE customer_id = 100;
-- orders에서 customer_id=100인 행 5건이 CASCADE로 함께 삭제됨

-- 이 5건의 삭제가 슬레이브에 어떻게 반영되는가?
-- (1) 복제 로그에 5건의 개별 DELETE가 기록되어 그대로 재생되는가?
-- (2) customers의 DELETE 1건만 로그에 남고, 슬레이브가 자신의 CASCADE로 재현하는가?
```

**예제 설명**: (1)과 (2)는 평소에는 결과가 같아 보이지만, 만약 슬레이브의 `orders`에 마스터와는 다른 이유로 이미 데이터 차이가 있었다면(예: 리뷰 6에서 지적한 것처럼 한때 `REPLICATION=OFF`였다가 다시 켜진 이력이 있는 등) 두 방식은 서로 다른 최종 상태를 만들 수 있습니다. 또한 (2) 방식이라면 슬레이브 쪽 CASCADE 제약이 마스터와 동일하게 설정되어 있어야 한다는 전제가 추가로 필요한데, 이런 전제 자체가 스펙에 없습니다.

**제안**: CASCADE/SET NULL 등 참조 액션으로 발생하는 간접 DML이 복제 로그에 기록되는 방식(개별 로그 vs 재현 위임)을 명시하고, 관련 예제를 §5에 추가해야 합니다.

### 리뷰 28

**[심각도: 보통] backupdb/restoredb(물리 백업)가 unloaddb/loaddb(§8)의 REPLICATION 규칙과 같은 적용 범위인지 불명확하다**

**대상**: §8(UNLOADDB & LOADDB) 전체 — backupdb/restoredb 언급 없음

**문제 설명**: §8은 오직 `unloaddb`/`loaddb`(테이블을 텍스트/바이너리 형태로 논리적으로 내보내고 불러오는 도구)만 다룹니다. 그런데 CUBRID에는 이와 별개로 데이터베이스 볼륨 전체를 통째로 복사하는 물리 백업 도구(`backupdb`/`restoredb`)도 존재합니다. 재해 복구(DR) 절차를 준비하는 응용 개발자 입장에서는 "이 스펙에서 새로 생긴 복제 관련 규칙이 물리 백업/복원에도 똑같이 적용되는지(카탈로그가 통째로 복사되므로 자동으로 보존될 것 같다), 아니면 이 절이 명시적으로 다루지 않는 별개의 영역인지" 판단할 근거가 스펙에 없습니다.

**구체 예제(시나리오)**:
```
-- 재해복구 리허설 절차서를 작성 중인 상황
-- 방법 A: unloaddb로 논리 백업 → §8 규칙 적용 (복제 여부 변수 저장/복원)
-- 방법 B: backupdb로 물리 백업 → §8이 명시적으로 언급하지 않음

$ backupdb -B /backup/vol1 mydb
$ restoredb -B /backup/vol1 mydb_restored

-- 복원된 mydb_restored의 각 테이블 REPLICATION 값은
-- 원본과 100% 동일하게 보존된다고 봐도 되는가?
-- (물리 백업이니 카탈로그까지 그대로 복사될 것 같지만, 스펙에 확인 문구가 없다)
```

**예제 설명**: 물리 백업은 볼륨 파일을 그대로 복사하는 방식이라 REPLICATION 설정이 자동으로 보존될 가능성이 높아 보이지만, 이는 어디까지나 추정입니다. DR 훈련 문서에 "확인되지 않은 가정"을 그대로 적어 넣는 것은 실제 재해 상황에서 위험한 습관이며, 스펙이 이 부분을 짚어주지 않으면 신입 개발자는 절차서에 근거 없는 문장을 쓰게 됩니다.

**제안**: §8에 "본 절은 unloaddb/loaddb(논리 백업)에만 적용되며, backupdb/restoredb(물리 백업)는 볼륨을 그대로 복사하므로 REPLICATION 설정이 자동으로 보존된다"는 식으로 적용 범위를 명시적으로 밝혀야 합니다.

### 리뷰 29

**[심각도: 사소] §5-2 "복제 제외 테이블 참조 예시" 중 첫 번째 예시가 번호가 빠져 있고, FK 컬럼도 앞선 예시들과 다르게 잘못 지정되어 있다**

**대상**: §5-2 (예시 21과 예시 23 사이, "복제 제외 테이블 참조 예시" 하위 "외래키 추가" 항목)

**문제 설명**: §5-2는 "복제 테이블을 참조예시"(예시 19~22)와 "복제 제외 테이블 참조 예시"(예시 23 포함) 두 그룹으로 나뉩니다. 그런데 두 번째 그룹의 첫 항목인 "외래키 추가" 예제에는 "예시 22." 같은 번호가 전혀 붙어 있지 않고 다음 예제가 바로 "예시 23"으로 건너뜁니다. 게다가 이 번호 없는 예제의 SQL 자체도 이상합니다. 앞선 예시 19~22는 모두 `new_orders` 테이블에 `customer_id`라는 새 컬럼/FK를 추가하는 패턴인데, 이 예제만 `FOREIGN KEY(order_id) REFERENCES non_repl_customers(customer_id)`처럼 이미 존재하는 PK 컬럼 `order_id`를 FK로 재사용하고 있어 앞뒤 문맥과 어긋납니다.

**구체 예제(원문 그대로)**:
```sql
-- 번호 없는 예제 (원문)
csql> CREATE TABLE new_orders(
    order_id INT PRIMARY KEY
);

// customers 는 예시 18의 테이블
csql> ALTER TABLE new_orders ADD CONSTRAINT FOREIGN KEY(order_id)
REFERENCES non_repl_customers(customer_id);

ERROR
```

**예제 설명**: 문서를 순서대로 따라가며 실습하는 신입 개발자는 앞선 예시 19~22와 패턴이 같을 것이라 기대하고 이 블록을 읽다가, 갑자기 `customer_id` 컬럼이 등장하지 않고 `order_id`(PK 컬럼)를 FK로 쓰는 것을 보고 "이게 오타인지, 아니면 PK 컬럼도 동시에 FK로 쓸 수 있다는 새로운 규칙을 보여주는 의도적 예제인지" 혼란을 겪습니다. 번호까지 빠져 있어 다른 사람과 "예시 몇 번 얘기하는 거예요?"라고 소통할 때도 지칭할 수단이 없습니다.

**제안**: 이 예제에 번호(예: "예시 22.")를 부여하고, FK 컬럼을 앞선 예시들과 일관되게 `customer_id`(신규 컬럼)로 정정해야 합니다.

### 리뷰 30

**[심각도: 보통] SQL 예시가 전혀 없는 절(§1, §3, §6, §8, §9)에 스펙의 모호성이 집중되어 있다**

**대상**: §1(제약 사항), §3(Single 제약사항), §6(뷰), §8(UNLOADDB & LOADDB), §9(SUMMARY) — 이 5개 절에는 "예시 N" 형식의 SQL 예제가 하나도 없음

**문제 설명**: 이 스펙은 §2, §4, §5처럼 규칙을 설명한 뒤 반드시 "예시 N"이라는 번호가 붙은 SQL 코드로 결과(OK/ERROR)를 보여주는 문서 스타일을 갖고 있습니다. 그런데 정작 §1(RK 자동 선택 규칙 — 최종보고서에서 가장 심각한 문제로 꼽힌 비결정성 문제가 바로 여기서 나옴), §3(싱글 모드 제약), §6(뷰), §8(UNLOADDB/LOADDB — 재해복구와 직결), §9(요약)는 SQL 예제가 하나도 없이 프로즈(줄글)로만 서술되어 있습니다. 실제로 신입 개발자가 이 스펙을 검토하며 "이해가 안 된다"고 느끼는 지점은 대부분 이 5개 절에 몰려 있는데(다른 리뷰들이 지적한 §1의 RK 선택 비결정성, §8/§9의 기본값 모순 등이 전부 여기 속함), 우연이 아니라 "예제로 검증되지 않은 서술은 필연적으로 모호해진다"는 문서 작성 방식 자체의 문제로 보입니다.

**구체 예제(비교)**:
```
예제가 있는 절(§4-2)의 문장:
"PK를 복제키로 사용하는 경우 ... 하나의 테이블에는 여러 PK가 존재할 수 없다."
→ 예시 11의 실제 SQL과 에러 메시지로 즉시 검증 가능

예제가 없는 절(§1)의 문장:
"UK가 여러개 존재한다면 큐브리드 엔진에 의해 이 중 하나가 선택된다
(ex. 테이블내에 명시된 순서 중 가장 빠른 순서)"
→ 이 문장이 정확히 어떤 SQL 결과를 내는지 확인할 예제가 없어
  "ex."가 확정 규칙인지 아닌지조차 알 수 없음 (최종보고서 C-1)
```

**예제 설명**: 위 비교는 같은 문서 안에서도 예제가 붙은 서술과 그렇지 않은 서술의 신뢰도 차이를 보여줍니다. §1, §8, §9처럼 이 기능의 핵심 규칙과 기본값을 규정하는 절일수록 예제 없이 문장만으로 처리된 것은 우선순위가 거꾸로 됐다고 볼 수 있습니다.

**제안**: 특히 §1(RK 선택 규칙)과 §8(UNLOADDB/LOADDB 기본값)에는 최소 1개 이상의 번호 붙은 SQL/CLI 예제를 추가해, 다른 절과 동일한 검증 가능성을 확보해야 합니다.

### 리뷰 31

**[심각도: 중요] 복합(다중 컬럼) UNIQUE 키가 RK 후보가 되려면 참여 컬럼 전부가 NOT NULL이어야 하는지 스펙이 명시하지 않는다**

**대상**: §1 "PK가 없이 UK가 존재한다면 UK가 복제 키가 됨" — "UK"의 정의가 단일 컬럼 기준으로만 서술됨

**문제 설명**: 스펙은 "Not Null Unique Key(UK)"를 계속 하나의 개념처럼 뭉뚱그려 쓰는데, 실제 CUBRID(다른 RDBMS와 마찬가지로)에서는 `UNIQUE(a, b)`처럼 여러 컬럼을 묶은 복합 UNIQUE 제약을 만들 수 있고, 이때 `a`와 `b` 각각의 NOT NULL 여부는 독립적으로 설정할 수 있습니다. "NOT NULL UNIQUE"라는 표현이 복합 키에 적용될 때 "참여 컬럼 전부가 NOT NULL이어야 RK 후보로 인정"인지, 아니면 "그중 한 컬럼만 NOT NULL이어도 후보로 쳐주는지"가 스펙에 없습니다. ORM이 `@Table(uniqueConstraints=...)`로 복합 유니크를 선언할 때 각 필드의 nullable 속성을 따로따로 지정하는 것이 흔한 만큼, 이 모호함은 실제 배포에서 "왜 이 복합 UK가 RK 후보로 안 잡히지?"라는 의문으로 바로 이어질 수 있습니다.

**구체 예제(SQL)**:
```sql
CREATE TABLE shipments(
    shipment_id INT,
    warehouse_id INT NOT NULL,
    tracking_no VARCHAR(30),              -- NULL 허용
    CONSTRAINT uk_shipments UNIQUE(warehouse_id, tracking_no)
);
-- PK 없음. UK는 (warehouse_id, tracking_no) 복합 키.
-- warehouse_id는 NOT NULL이지만 tracking_no는 NULL 허용.

-- 이 복합 UK가 "NOT NULL UNIQUE" 자격을 만족해 RK 후보가 되는가?
-- 아니면 tracking_no가 NULL 허용이라는 이유로 RK 후보에서 아예 제외되어
-- 이 테이블은 §1에 의해 "복제 키가 없는 테이블"로 취급되는가?
```

**예제 설명**: 만약 복합 키의 일부 컬럼만 NULL을 허용해도 전체가 RK 후보에서 탈락한다면, 이 테이블은 HA 모드에서 복제 테이블로 만들 수 없습니다(§4-1, 예시 10과 동일한 상황). 개발자가 로컬에서는 이 사실을 모른 채(§3에 의해 싱글 모드에서는 제약이 없으므로) 테이블을 만들고, HA 전환 시점에야 비로소 이 복합 키가 RK 후보로 인정되지 않는다는 사실을 알게 될 수 있습니다.

**제안**: 복합 UNIQUE 제약이 RK 후보가 되는 조건(참여 컬럼 전부 NOT NULL 필요 여부)을 §1에 명시하고, 단일 컬럼 예제뿐 아니라 복합 컬럼 예제도 §2 또는 §4에 추가해야 합니다.

## 조사 종료 선언

이번 2차 라운드에서는 (1) DDL 트랜잭션/커밋 동작, (2) 표준 SQL 메타데이터·스키마 비교 도구와의 연동, (3) 권한(GRANT) 모델, (4) TDE·REUSE_OID 같은 기존 CUBRID 기능과의 상호작용, (5) FK CASCADE 등 참조 액션, (6) 물리 백업 도구의 적용 범위, (7) 문서 자체의 구조적 결함(예시 번호·예시 부재 절)을 응용 개발자 관점에서 훑었다. 이 외에 뷰 확장, 파티션, 트리거, 시리얼(SERIAL), 컬럼 단위 필터링, 멀티 슬레이브, 성능/락 등은 최종보고서(40개 통합 이슈) 또는 1차 리뷰에서 이미 다뤄졌거나, 다른 직군(엔진 개발자·DBA·PM)의 관점이 더 적합해 본 라운드에서는 다시 다루지 않았다. 남은 후보 중 (a) 커넥션 풀/브로커의 prepared statement 캐시 무효화, (b) 다중 UK ALTER 시점의 TOCTOU 경쟁 조건 재검증, (c) 구버전 클라이언트 파서의 REPLICATION 키워드 인식 여부는 최종보고서에 이미 등재됐거나(엔진 개발자 고유 항목, 롤링 업그레이드 항목) 근거 없는 추측에 가까워 신규 리뷰로 채택하지 않았다. 이 관점에서 30개를 채우기보다, 실제 배포 자동화 업무에서 부딪힐 근거가 있는 11개만 남겼다.
