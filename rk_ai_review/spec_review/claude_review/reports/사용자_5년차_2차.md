# CUBRID HA 복제 개선 스펙 리뷰 — 최종 사용자(5년차) 관점 · 2차 라운드

## 2차 라운드 개요

1차에서는 RK 선택 규칙의 비결정성, FK 부모 사후 전환, 조회 불가, 에러 메시지 부재 등 스펙 본문에 명시된 시나리오의 허점을 주로 팠다. 2차에서는 1차와 최종보고서 40개 통합 이슈가 다루지 않은 영역 — TRUNCATE·백업 도구·파티션·권한·컬럼 RENAME·동시성·FK 부모의 RK 변경 충돌·뷰/시노님 경계·복합 UNIQUE 자격 기준 — 을 실무자가 실제로 마주칠 법한 순서로 훑었다. 트리거 간접 DML, SERIAL/AUTO_INCREMENT 페일오버 동기화, collation 기반 행 매칭처럼 이미 다른 직군이 지적했거나 근거를 확보하지 못한 후보는 제외했다(맨 아래 조사 종료 선언 참조).

## 리뷰 21

**[심각도: 치명] TRUNCATE TABLE이 "DDL"인지 "데이터 복제 대상"인지 스펙이 정의하지 않는다**

**대상**: §1 "모든 DDL은 슬레이브로 복제되며 테이블의 REPLICATION 옵션은 데이터 복제 여부를 결정한다."

**문제 설명**: 이 문장은 세상의 모든 SQL 문을 "DDL"과 "데이터(즉 DML)" 두 그룹으로만 나눈다. DDL은 REPLICATION 옵션과 무관하게 항상 복제되고, 데이터는 REPLICATION=ON일 때만 복제된다는 것이다. 그런데 `TRUNCATE TABLE`은 이 이분법에서 애매한 위치에 있다. 이 명령은 결과적으로 "테이블의 모든 행을 지운다"는 점에서 데이터 연산처럼 보이지만, 많은 데이터베이스 엔진에서 TRUNCATE는 트랜잭션 로그를 행 단위로 남기지 않고 저장 공간을 통째로 재할당하는 방식으로 구현되어 있어 오히려 DDL에 가깝게 취급된다(실제로 CUBRID를 포함한 여러 엔진에서 TRUNCATE는 롤백 불가능하거나 스키마 객체 수준 잠금을 요구하는 등 DDL과 유사한 성격을 보인다). 이 스펙이 TRUNCATE를 어느 쪽으로 분류하는지 한 줄도 언급하지 않는다.

**구체 예제(시나리오)**:
```sql
-- REPLICATION = ON 인 배치 로그 테이블
CREATE TABLE batch_log (
    id INT PRIMARY KEY,
    msg VARCHAR(200)
);

-- 매일 새벽 배치 작업 전, 통상적으로 로그 테이블을 비움
TRUNCATE TABLE batch_log;

-- 질문 1: 이 TRUNCATE는 "DDL"로 분류되어 무조건 슬레이브에 반영되는가,
--         아니면 "데이터"로 분류되어 REPLICATION 옵션을 따르는가?
-- 질문 2: 만약 batch_log가 REPLICATION = OFF 였다면,
--         TRUNCATE가 DDL로 분류될 경우 슬레이브에서도 강제로 비워지는 부작용이 생기는가?
--         (OFF 테이블은 애초에 슬레이브에 데이터가 없어야 정상인데,
--          만약 슬레이브 쪽에 우연히 남아있던 잔여 데이터가 있다면 이 TRUNCATE로 지워질 수도, 안 지워질 수도 있다)
```

**예제 설명**: 실무자는 배치 작업 전 테이블을 비우는 용도로 TRUNCATE를 매일 쓰는데, 이 문장 하나가 RK 매칭이 필요한 UPDATE/DELETE 경로(§4-2에서 그렇게 공들여 설계한 RK 기반 식별)를 완전히 우회하는 특수 경로라는 사실은 스펙 어디에도 언급되지 않는다. INSERT/UPDATE/DELETE만 예로 들었을 뿐, "행 단위 식별이 필요 없는 대량 삭제 연산"이 이 RK 체계와 어떻게 맞물리는지는 침묵하고 있다.

**제안**: §1 또는 §4에 "TRUNCATE TABLE은 (DDL / 데이터 복제) 중 어느 쪽으로 분류되며, REPLICATION 옵션의 영향을 받는지 여부"를 명시적으로 한 문장 추가해야 한다.

## 리뷰 22

**[심각도: 중요] `CREATE TABLE ... LIKE`나 `CREATE TABLE ... AS SELECT`로 테이블을 복제할 때 REPLICATION 옵션이 원본에서 상속되는지 불명확하다**

**대상**: §2-1 (REPLICATION 옵션의 CREATE TABLE 적용 범위)

**문제 설명**: §2-1은 REPLICATION 옵션을 CREATE TABLE에 직접 명시하거나 생략(기본 ON)하는 경우만 다룬다. 그런데 실무에서는 기존 테이블의 구조를 그대로 복사해 새 테이블을 만드는 `CREATE TABLE ... LIKE`나, 쿼리 결과로 테이블을 즉석에서 만드는 `CREATE TABLE ... AS SELECT`(CTAS)를 스테이징 테이블 생성, 백업용 스냅샷 테이블 생성 등에 흔히 사용한다. 원본 테이블이 REPLICATION=OFF로 설정된 테이블이었을 때, 이렇게 파생된 새 테이블이 그 속성을 물려받는지, 아니면 옵션을 생략한 것으로 취급되어 기본값 ON으로 새로 생성되는지 스펙에 전혀 없다.

**구체 예제**:
```sql
CREATE TABLE non_repl_customers(
    customer_id INT PRIMARY KEY,
    country INT
) REPLICATION = OFF;

-- 구조만 복사
CREATE TABLE customers_staging LIKE non_repl_customers;
-- customers_staging의 REPLICATION 값은? OFF 상속인가, 기본값 ON인가?

-- 데이터까지 복사
CREATE TABLE customers_snapshot AS SELECT * FROM non_repl_customers;
-- 이쪽도 마찬가지로 REPLICATION 값이 불명확
```

**예제 설명**: 만약 상속되지 않고 기본값 ON으로 조용히 만들어진다면, 원본은 의도적으로 복제에서 뺀 테이블인데 그 복사본은 RK가 있는지 없는지도 모른 채 복제 대상으로 편입되어 HA 전환 시점에 갑자기 걸릴 수 있다(1차 리뷰 2와 같은 "지연된 실패" 패턴이 LIKE/CTAS라는 새로운 경로로 또 발생한다). 반대로 상속된다면, 원본을 참고하지 않고 코드만 보고 CREATE TABLE 문을 읽는 사람은 REPLICATION 값을 전혀 예측할 수 없다.

**제안**: §2-1에 "LIKE, AS SELECT로 생성된 테이블의 REPLICATION 값은 원본을 상속하지 않고 항상 기본 정책(생략 시 ON)을 따른다"는 식으로 명시적 규칙을 추가해야 한다.

## 리뷰 23

**[심각도: 치명] 파티션 테이블에서 파티션 키를 포함하지 않는 UNIQUE 제약이 애초에 허용되는지, RK 자동 선택과 어떻게 맞물리는지 스펙이 침묵한다**

**대상**: §1 (RK 선택 규칙), §2-3 예시 9의 `db_class` 출력에 등장하는 `partitioned` 필드

**문제 설명**: 스펙은 파티션 테이블(하나의 논리 테이블을 여러 물리 조각으로 나누어 저장하는 기능)을 한 번도 언급하지 않지만, 정작 §2-3 예시 9의 `db_class` 조회 결과에는 `partitioned: 'NO'`라는 필드가 이미 등장한다. 즉 이 카탈로그 뷰 자체가 파티션 테이블의 존재를 전제하고 있다는 뜻인데, RK 규칙이 파티션 테이블에 그대로 적용되는지는 어디에도 서술이 없다. 많은 관계형 DB 엔진(예: MySQL 계열)에는 "파티션 키로 사용하는 컬럼은 그 테이블의 모든 UNIQUE(및 PK) 제약에 포함되어야 한다"는 제한이 존재한다. 만약 CUBRID도 동일한 제한을 가진다면, 사용자가 원하는 컬럼 하나만으로 UK를 걸어 그것을 RK로 쓰고 싶어도, 파티션 키를 강제로 그 UK에 끼워 넣어야 하는 상황이 생길 수 있다. 이 상호작용이 스펙에 전혀 언급되지 않는다.

**구체 예제(시나리오)**:
```sql
-- region 컬럼으로 해시 파티셔닝된 매출 테이블
CREATE TABLE sales (
    sale_id INT,
    region VARCHAR(20),
    amount INT,
    CONSTRAINT uk_sale UNIQUE (sale_id)   -- 파티션 키(region)를 포함하지 않는 UK
)
PARTITION BY HASH(region) PARTITIONS 4;

-- 만약 "파티션 키는 모든 UNIQUE 제약에 포함되어야 한다"는 일반적인 제한이 CUBRID에도 있다면
-- 이 CREATE TABLE 자체가 (RK 규칙과 무관하게) 거부될 수 있다.
-- 그렇다면 sale_id 단독으로는 RK 후보를 만들 수 없고,
-- (region, sale_id) 복합 UK로 우회해야 하는데, 이 복합 UK가 RK로 선택될 때
-- 슬레이브 쪽 행 식별에 region까지 필요해지는 셈이다.
-- 이런 안내가 스펙 어디에도 없다.
```

**예제 설명**: 파티션 테이블은 대용량 로그·매출·이벤트 데이터처럼 HA 복제가 가장 절실한 테이블 유형에 자주 쓰인다. 그런데 이 스펙의 예제는 전부 파티션 없는 단순 테이블만 다루고 있어서, 실제로 대용량 파티션 테이블을 이 스펙에 맞춰 재설계해야 하는 실무자는 참고할 예제가 하나도 없는 상태로 시행착오를 거쳐야 한다.

**제안**: 스펙에 "파티션 테이블에 대한 RK 규칙은 (기존 파티션 제약과 동일하게 / 별도로) 적용된다"는 절을 신설하고, 최소 하나의 파티션 테이블 예제를 추가해야 한다.

## 리뷰 24

**[심각도: 중요] REPLICATION 옵션을 변경하는 데 필요한 권한 수준이 명시되지 않아, 테이블 소유자가 DBA 승인 없이 단독으로 복제 정책을 바꿀 수 있다**

**대상**: §2-2 (ALTER TABLE ... REPLICATION), §4 (HA 제약사항)

**문제 설명**: 이 스펙 전체에서 "누가 이 옵션을 바꿀 수 있는가"에 대한 언급이 전혀 없다. 일반적으로 CUBRID를 포함한 대부분의 RDB에서, 테이블 소유자(owner)는 DBA 권한이 없어도 자신이 만든 테이블에 대해 ALTER TABLE을 실행할 권한을 기본적으로 가진다. 그렇다면 REPLICATION 옵션도 같은 규칙을 따를 경우, 애플리케이션 배포 계정처럼 DBA가 아닌 계정이 이 옵션을 마음대로 켰다 껐다 할 수 있다는 뜻이 된다. 이 옵션은 단순한 스키마 속성이 아니라 "마스터-슬레이브 데이터 일치 여부"라는 클러스터 전체의 무결성에 영향을 미치는 운영 정책인데, 일반 사용자 권한으로 통제 없이 바꿀 수 있다면 DBA가 파악하지 못한 사이에 리뷰 13(1차)의 FK 부모 사후 전환 같은 사고가 발생할 수 있다.

**구체 예제(시나리오)**:
```sql
-- app_user 계정(비-DBA)이 자신의 스키마에 테이블 생성
CREATE TABLE customers (
    customer_id INT PRIMARY KEY,
    country INT
);  -- 소유자 = app_user, REPLICATION 기본값 ON

-- 이 테이블을 참조하는 orders는 다른 팀이 DBA 승인을 받아 REPLICATION=ON으로 운영 중

-- app_user가 자기 권한 범위에서 단독으로 실행
ALTER TABLE customers REPLICATION = OFF;
-- DBA 승인이나 알림 없이 실행된다면, 리뷰 13(1차)에서 지적한 FK 정합성 붕괴가
-- DBA 모르게 조용히 발생한다.
```

**예제 설명**: 실무에서는 "누가 이 명령을 실행할 수 있는가"가 곧 "누가 사고를 낼 수 있는가"와 직결된다. REPLICATION 옵션처럼 파급 범위가 테이블 하나를 넘어 클러스터 전체 정합성에 영향을 주는 설정은, 일반적인 ALTER TABLE(예: 컬럼 추가)보다 더 높은 권한(예: DBA 전용)을 요구하는 것이 합리적일 수 있는데, 스펙은 이 문제 자체를 인지하지 못한 것처럼 보인다.

**제안**: REPLICATION 옵션 변경에 필요한 권한 수준(테이블 소유자로 충분한지, DBA 권한이 필요한지)을 명시하고, 최소한 변경 시 감사 로그(누가 언제 어떤 테이블의 REPLICATION을 바꿨는지)를 남기도록 권고해야 한다.

## 리뷰 25

**[심각도: 보통] §8이 unloaddb/loaddb(논리 백업)만 다루고, 실무에서 더 흔한 backupdb/restoredb(물리 백업) 경로에는 REPLICATION 관련 언급이 전혀 없다**

**대상**: §8 UNLOADDB & LOADDB

**문제 설명**: §8은 "unload 시 복제 테이블의 여부를 함께 저장한다", "하위 버전에서 unload 한 데이터 파일에는 ..." 처럼, 텍스트 형태로 데이터를 통째로 뽑아냈다가 다시 넣는 unloaddb/loaddb 유틸리티만 대상으로 서술한다. 그런데 실무에서 DR(재해복구)이나 서버 이전을 위한 백업은 대개 `cubrid backupdb`/`cubrid restoredb` 같은 물리적(바이너리 수준) 백업 도구를 사용한다. 물리 백업은 데이터 파일을 그대로 복사하는 방식이라 REPLICATION 메타데이터도 함께 그대로 보존될 것으로 추정되지만, 문제는 §8이 다루는 "하위 버전 호환성" 이슈 — 즉 이 기능이 없던 구버전에서 만든 백업을 신버전에 복원했을 때 REPLICATION 컬럼 자체가 카탈로그에 없는 상황 — 이 물리 백업 경로에서는 어떻게 처리되는지 전혀 언급이 없다는 점이다.

**구체 예제(시나리오)**:
```text
1) 구버전 CUBRID(REPLICATION 개념 도입 이전)에서 물리 백업
   $ cubrid backupdb -D /backup_path olddb

2) 신버전 CUBRID 바이너리로 교체 후 복원
   $ cubrid restoredb -B /backup_path olddb

3) 복원된 olddb의 각 테이블은 REPLICATION 컬럼이 카탈로그 스키마 자체에 없던 상태에서
   신버전 카탈로그 구조로 어떻게 마이그레이션되는가?
   §8은 unloaddb/loaddb 경로의 이 상황(모두 복제 대상으로 설정)만 규정하고,
   backupdb/restoredb 경로에 대해서는 규정이 없다.
```

**예제 설명**: 실무자 입장에서 "테이블 몇 개만 옮길 때"는 unloaddb/loaddb를 쓰지만, "DB 전체를 재해복구하거나 새 서버로 이전할 때"는 거의 항상 backupdb/restoredb를 쓴다. 후자가 훨씬 자주 쓰이는 경로인데도 스펙은 전자만 다루고 있어, 실제로 많은 사용자가 마주치게 될 마이그레이션 경로에 대한 안내가 빠져 있다.

**제안**: §8에 backupdb/restoredb 경로에서의 카탈로그 마이그레이션 동작(신규 REPLICATION 컬럼의 초기값 부여 방식)을 unloaddb/loaddb와 동일한 수준으로 명시해야 한다.

## 리뷰 26

**[심각도: 중요] RK로 쓰이는 컬럼의 이름만 바꾸는 것(RENAME COLUMN)이 "복제키를 직접 수정할 수 없다"는 규칙에 해당하는지 불명확하다**

**대상**: §4-2 "복제키는 큐브리드 엔진에 의해 결정되며, 사용자는 복제키를 직접 수정할 수 없다."

**문제 설명**: §4-2가 열거하는 금지 대상(예시 12: PK 삭제, 예시 15: UK 삭제)은 모두 "제약 자체를 없애는" 조작이다. 그런데 컬럼의 이름만 바꾸고 제약·값·자료형은 그대로 두는 `RENAME COLUMN`은 이 열거에 들어있지 않다. 이 조작이 "복제키를 직접 수정하는 것"에 해당하는지(그래서 금지되는지), 아니면 제약 자체는 손대지 않았으니 허용되는지 스펙에 답이 없다. 만약 허용된다면, 복제 로그(마스터에서 슬레이브로 전달되는 변경 기록)가 RK를 컬럼 이름으로 참조하는 방식으로 구현되어 있을 경우, RENAME이 슬레이브에 반영되는 시점과 그 RENAME 이전에 만들어졌지만 아직 슬레이브에 도착하지 않은 DML 로그가 뒤섞이는 순간에 무슨 일이 일어나는지가 궁금해진다.

**구체 예제(시나리오)**:
```sql
CREATE TABLE tbl (
    a INT PRIMARY KEY,
    b INT
);
-- RK = a (PK)

-- HA 운영 중, 컬럼명만 바꾸고 싶다. 제약도 값도 그대로.
ALTER TABLE tbl RENAME COLUMN a TO a_id;
-- 이 문장이 성공한다고 가정하면:
--   RENAME이 슬레이브에 DDL로 반영되어 슬레이브 카탈로그의 컬럼명이 a_id로 바뀐 직후,
--   RENAME 이전에 "a" 기준으로 기록된 UPDATE/DELETE 로그가 뒤늦게 도착하면
--   슬레이브는 이 로그를 무엇으로 처리하는가?
```

**예제 설명**: 컬럼 이름 변경은 실무에서 매우 흔한 리팩터링이다(예: 레거시 컬럼명을 팀 컨벤션에 맞게 정리). 특히 RK로 쓰이는 컬럼은 대개 `id`, `pk` 같은 이름에서 더 의미 있는 이름으로 바꾸고 싶은 경우가 많은데, 이 조작이 §4-2의 "직접 수정 금지" 규칙 대상인지조차 스펙에서 판단할 수 없다.

**제안**: RENAME COLUMN이 RK 컬럼에 대해 허용되는지 명시하고, 허용된다면 복제 로그가 컬럼을 이름이 아닌 내부 식별자로 참조해 RENAME과 무관하게 동작함을 보장한다고 서술해야 한다.

## 리뷰 27

**[심각도: 중요] `ALTER TABLE ... REPLICATION=OFF`가 커밋되는 시점과, 그 이전에 시작되어 아직 커밋되지 않은 트랜잭션의 귀속 관계가 정의되지 않았다**

**대상**: §2-2 예시 6, §4 "HA 환경 복제 제외테이블은 ... 변경하는것 외의 모든 DDL을 사용할 수 있다"

**문제 설명**: 예시 6은 `ALTER TABLE tbl REPLICATION=OFF;` 한 줄이 OK로 처리된다고만 보여준다. 그런데 이 ALTER 문이 실행되어 커밋되기 전에, 이미 다른 세션에서 그 테이블에 대량의 INSERT/UPDATE를 포함한 트랜잭션을 시작해 놓고 아직 커밋하지 않은 상태라면 어떻게 되는지 스펙이 다루지 않는다. 이는 리뷰 9(1차)에서 지적한 "복합 ALTER의 원자성" 문제와는 다른 층위의 동시성 문제다. 리뷰 9는 하나의 ALTER 문 내부(RK 제약을 지웠다 새로 만드는 것) 원자성을 다뤘다면, 이번 문제는 REPLICATION 플래그 자체가 전환되는 순간과 그 테이블에 대한 별도 트랜잭션의 커밋 순서 사이의 관계를 다룬다.

**구체 예제(시나리오)**:
```sql
-- 세션 A: 대량 배치 삽입 시작 (아직 커밋 전)
START TRANSACTION;
INSERT INTO logs (id, msg) VALUES (1, 'x');
INSERT INTO logs (id, msg) VALUES (2, 'y');
-- ... 수천 건 계속 삽입 중, 아직 COMMIT 안 함

-- 세션 B: 그 사이 logs 테이블을 복제 제외로 전환
ALTER TABLE logs REPLICATION = OFF;
-- 이 문장이 커밋됨

-- 세션 A: 한참 뒤에 커밋
COMMIT;

-- 질문: 세션 A가 삽입한 수천 건은 슬레이브로 복제되는가?
--   (a) 세션 A의 트랜잭션이 "시작될 때" ON이었으므로 복제된다
--   (b) 세션 A가 "커밋될 때" 이미 OFF였으므로 복제되지 않는다
--   (c) 부분적으로 걸쳐서 일부만 복제되는 미정의 상태가 된다
```

**예제 설명**: 배치 작업은 흔히 트랜잭션 하나로 오래 묶여 실행되는데, 그 실행 도중 다른 팀이나 자동화 스크립트가 REPLICATION 옵션을 바꾸는 것은 스펙상 막을 근거가 없다(§4에 따르면 ON→OFF 전환은 항상 허용). 이 경계가 정의되지 않으면 "내 배치가 슬레이브에 반영됐는지 안 됐는지"를 실무자가 예측할 수 없는 상태로 남는다.

**제안**: REPLICATION 플래그 전환을 스키마 잠금을 통해 진행 중인 트랜잭션과 직렬화하고, "커밋 시점의 플래그 값을 기준으로 그 트랜잭션 전체의 복제 여부가 결정된다"는 식으로 판정 기준을 명시해야 한다.

## 리뷰 28

**[심각도: 치명] 예시 13류의 "PK를 다른 컬럼으로 바꾸는" DDL을, 그 PK가 다른 테이블의 FK로 참조되고 있는 상태에서 실행하면 어떻게 되는지 스펙이 전혀 고려하지 않는다**

**대상**: §4-2 예시 13 (`ALTER TABLE table_name DROP CONSTRAINT PRIMARY KEY, ADD CONSTRAINT PRIMARY KEY(a);` → OK), §5 (외래키)

**문제 설명**: 예시 13은 RK를 PK에서 다른 컬럼으로 옮기는 "권장 방법"으로 스펙 전체에서 여러 번 재확인되는 핵심 패턴이다(§2-2에서 먼저 예시 7로 소개되고, §4-2에서 예시 13으로 완성형이 제시된다). 그런데 이 예시가 다루는 테이블 `table_name`이 다른 테이블의 FK로부터 참조받고 있는 "부모 테이블"인 경우는 한 번도 고려되지 않는다. 일반적으로 관계형 DB에서는 다른 테이블이 FK로 참조하고 있는 PK를 삭제하려면, 먼저 그 FK를 삭제(또는 CASCADE 지정)해야 하는 제약이 있다. 만약 CUBRID도 이런 제약을 갖고 있다면, §5에서 정성껏 구성한 FK 관계(customers를 참조하는 orders)를 가진 상태에서는 예시 13의 방법 자체가 애초에 실행 불가능할 수도 있다는 뜻이 된다. 즉 이 스펙이 "RK를 바꾸는 표준 방법"이라고 제시한 패턴이, 이 스펙이 다른 곳(§5)에서 강조한 FK 규칙과 충돌해 실무에서 가장 흔히 필요한 상황(FK로 참조되는 부모 테이블의 RK를 바꾸는 것)에는 아예 쓸 수 없는 방법일 가능성이 있다.

**구체 예제(시나리오)**:
```sql
-- §5 예시 17과 동일한 정상 FK 구성
CREATE TABLE customers(
    customer_id INT PRIMARY KEY,
    country INT
);
CREATE TABLE orders(
    order_id INT PRIMARY KEY,
    customer_id INT,
    CONSTRAINT fk_customer_id FOREIGN KEY (customer_id) REFERENCES customers(customer_id)
);

-- 운영 중, customers의 RK(PK)를 country로 바꾸고 싶다 (예시 13과 동일한 패턴을 그대로 적용)
ALTER TABLE customers
    DROP CONSTRAINT PRIMARY KEY,
    ADD CONSTRAINT PRIMARY KEY(country);

-- 이 시점에 orders.customer_id를 참조하던 PK(customer_id)가 사라지고,
-- customer_id 컬럼은 이제 아무 제약도 없는 평범한 컬럼이 된다.
-- orders의 FK는 이제 "제약이 없는 컬럼"을 참조하는 셈인데,
-- (1) 이 ALTER 자체가 FK 의존성 때문에 ERROR로 막히는가?
-- (2) 아니면 예시 13처럼 OK가 나면서 orders의 FK 무결성이 깨지는가?
-- 스펙은 둘 중 어느 쪽도 언급하지 않는다.
```

**예제 설명**: 이 스펙이 해결하려는 원래 문제(작업지시 배경)는 "PK 컬럼 속성을 바꾸다가 복제가 깨지는 것"이었다. 그런데 정작 그 해결책으로 제시된 예시 13이, FK로 참조되는 부모 테이블에 적용될 때 무슨 일이 일어나는지를 스펙 스스로 검증하지 않았다는 것은, 가장 실무적인 사용 사례(참조되는 마스터 테이블의 키를 재설계하는 것)에서 이 스펙의 핵심 해법이 검증되지 않은 채로 남아있다는 뜻이다.

**제안**: 예시 13을 FK로 참조되는 부모 테이블에 적용하는 경우를 별도 예제로 추가하고, (a) FK가 걸려있으면 이 DDL 자체를 차단하는지, (b) 차단한다면 사용자가 취해야 할 순서(자식 FK를 먼저 어떻게 처리해야 하는지)를 §5 또는 §4-2에 명시해야 한다.

## 리뷰 29

**[심각도: 보통] §7이 열거한 두 가지 위반 유형 중, FK 위반에 대한 해결 절차는 서술되지 않는다**

**대상**: §7 HA 전환 — "복제 테이블에 복제키가 존재하지 않는 경우" / "외래키를 포함하는 복제 테이블의 참조 테이블이 복제 대상이 아닌경우" 두 가지를 위반 유형으로 열거한 뒤, "이 경우 싱글모드에서 ALTER TABLE… 을 이용해 복제 키에 해당하는 제약을 추가하거나 복제 제외 대상으로 변경한 후 HA를 재시작해야한다"

**문제 설명**: §7은 위반 유형을 두 가지로 나눠 제시하지만, 뒤이어 나오는 해결 절차 문장은 "복제 키에 해당하는 제약을 추가하거나 복제 제외 대상으로 변경"이라고만 되어 있다. 이 표현은 첫 번째 유형(RK가 없는 경우 — RK 제약을 추가하거나 그 테이블을 복제 제외로 바꾼다)에는 정확히 들어맞지만, 두 번째 유형(FK 테이블은 정상인데 그 참조 대상이 복제 제외인 경우)에 대해서는 무엇을 해야 하는지 이 문장만으로는 알 수 없다. "참조 테이블을 복제 대상으로 바꿔라"는 것인지, "FK 자체를 없애라"는 것인지, "FK를 가진 테이블도 복제 제외로 내려라"는 것인지 구분이 안 된다.

**구체 예제(시나리오)**:
```sql
-- HA 전환 시도, §7 위반 유형 2에 걸린 상황
-- orders(복제 대상, FK 보유) -> non_repl_customers(복제 제외)를 참조

-- $ cubrid hb start
-- ERROR: replication constraint violation (참조 테이블이 복제 대상이 아님)

-- §7 해결 절차 문장을 그대로 따르면: "복제 키에 해당하는 제약을 추가하거나 복제 제외 대상으로 변경"
-- 그런데 orders는 이미 RK(PK)가 있다. 이 문장이 말하는 "제약 추가"는 이 상황에 적용되지 않는다.
-- 실무자는 다음 중 무엇을 해야 하는지 §7만 봐서는 알 수 없다:
ALTER TABLE non_repl_customers REPLICATION = ON;   -- (a) 참조 대상을 복제 대상으로 승격
-- 또는
ALTER TABLE orders DROP FOREIGN KEY fk_customer_id;  -- (b) FK 자체를 제거
-- 또는
ALTER TABLE orders REPLICATION = OFF;              -- (c) FK를 가진 쪽을 복제 제외로 내림
```

**예제 설명**: 위반 유형을 두 가지로 명확히 구분해 놓고, 해결 절차는 첫 번째 유형에만 맞는 문장 하나로 뭉뚱그린 것은 문서 작성상의 누락으로 보인다. 실무자가 새벽에 HA 전환 실패를 마주쳤을 때, 위반 유형에 따라 서로 다른 조치가 필요하다는 사실 자체를 이 문서에서 알아채기 어렵다.

**제안**: §7의 해결 절차를 위반 유형별로 나누어, 유형 1(RK 없음)과 유형 2(FK 참조 대상 문제) 각각에 대한 조치를 별도 문장으로 명시해야 한다.

## 리뷰 30

**[심각도: 사소] REPLICATION 옵션이 테이블 전용인지, VIEW 등 다른 객체에도 적용을 시도할 수 있는지 스펙이 명시하지 않는다**

**대상**: §2-1 (REPLICATION 옵션은 "CREATE TABLE과 ALTER TABLE 시" 제공한다고만 서술), §6 (뷰)

**문제 설명**: §6은 뷰가 복제 제외 테이블을 포함할 때 결과가 어긋날 수 있다는 문제를 상세히 설명한다. 이 절을 읽은 사용자가 자연스럽게 떠올릴 만한 다음 질문은 "그러면 이 뷰 자체에도 REPLICATION 옵션을 걸어서 문제를 회피할 수 있지 않을까"이다. §2-1은 "CREATE TABLE과 ALTER TABLE 시" 옵션을 제공한다고만 말할 뿐, VIEW·SYNONYM 같은 다른 객체 타입에 이 옵션을 사용하려고 하면 무슨 일이 일어나는지(문법 오류, 조용한 무시, 혹은 예상 못한 동작) 언급이 없다.

**구체 예제**:
```sql
-- §6에서 언급된 문제를 사용자가 스스로 회피해보려는 시도
CREATE VIEW v_customers (customer_id, country)
AS SELECT customer_id, country FROM customers
REPLICATION = OFF;
-- 이 문법이 파싱 단계에서 명확한 문법 오류로 거부되는지,
-- 아니면 VIEW 정의에 이런 옵션 자체가 존재하지 않아 혼란스러운 에러 메시지로 이어지는지 불명확하다
```

**예제 설명**: 이 자체는 사소한 문서 완결성 문제이지만, §6처럼 "이 부분은 책임지지 않는다"는 식으로 사용자에게 주의를 당부하는 절 바로 다음에는, 사용자가 대안을 찾아 헤매다가 실행할 법한 이런 시도에 대해 최소한 "REPLICATION 옵션은 오직 TABLE에만 적용되며 VIEW/SYNONYM에는 적용할 수 없다"는 한 줄을 남겨주는 것이 학습 곡선을 낮춘다.

**제안**: §2-1 또는 §6에 "REPLICATION 옵션은 TABLE 전용이며 다른 스키마 객체에는 적용되지 않는다"는 문장을 명시적으로 추가해야 한다.

## 리뷰 31

**[심각도: 중요] 복합(다중 컬럼) UNIQUE 제약에서 "NOT NULL UNIQUE"라는 RK 자격 기준이 어떻게 적용되는지 정의되지 않는다**

**대상**: §1 "복제 키는 큐브리드 엔진에 의해 Primary Key ... 혹은 Not Null Unique Key ... 들 중 하나로 선택된다"

**문제 설명**: 스펙의 모든 예제(예시 1, 14, 15 등)에서 UK는 항상 "단일 컬럼"에 대해서만 등장한다. 그런데 UNIQUE 제약은 여러 컬럼을 묶어서 정의하는 복합 제약도 가능하다. 이 경우 "NOT NULL UNIQUE"라는 자격 기준이 (a) 그 복합 제약에 참여하는 모든 컬럼이 각각 NOT NULL이어야 자격이 있다는 뜻인지, (b) 그중 일부만 NOT NULL이어도(나머지는 NULL 허용) 제약 자체는 유효한 UK이므로 자격이 있다는 뜻인지 구분되지 않는다. 이는 단순한 표현 문제가 아니라, RK로 선택되었을 때 실제로 행을 안정적으로 식별할 수 있는지와 직결된다. 만약 (b)처럼 일부 컬럼이 NULL을 허용하는 복합 UK가 RK로 선택된다면, 그 컬럼에 실제로 NULL이 들어있는 행은 복제 시 어떻게 식별되는가?

**구체 예제**:
```sql
CREATE TABLE tbl (
    a INT NULL,        -- NULL 허용
    b INT NOT NULL,
    c INT,
    CONSTRAINT uk_ab UNIQUE (a, b)   -- 복합 UNIQUE. a는 NULL 허용, b만 NOT NULL
);

-- uk_ab는 "NOT NULL UNIQUE"의 자격 기준을 만족하는 RK 후보인가?
-- (1) a가 NULL 허용이므로 자격 없음 (전체 컬럼이 NOT NULL이어야 함)
-- (2) b 하나라도 NOT NULL이면 자격 있음

INSERT INTO tbl VALUES (NULL, 1, 100);
-- 만약 (2)가 맞아서 uk_ab가 RK로 선택되었다면,
-- 이 행은 a=NULL, b=1 이라는 값으로 슬레이브에서 식별되어야 하는데
-- RK 값에 NULL이 섞여 있는 행을 어떻게 UPDATE/DELETE로 정확히 찾아내는가?
```

**예제 설명**: 이 스펙의 모든 예제가 단일 컬럼 UK만 다루기 때문에 실무자는 "내 테이블의 복합 UK는 이 규칙에 어떻게 적용되는지" 판단할 근거를 얻을 수 없다. 특히 복합 키를 쓰는 테이블(예: 다대다 연결 테이블, 이력 테이블)은 실무에서 드물지 않으므로 이 공백은 작지 않다.

**제안**: §1에 복합 UNIQUE 제약의 RK 자격 기준(모든 참여 컬럼이 NOT NULL이어야 하는지)을 명시적으로 정의하고, 최소 하나의 복합 UK 예제를 추가해야 한다.

## 조사 종료 선언

이번 2차 라운드에서는 다음 영역을 훑었다: TRUNCATE 등 DDL/DML 경계에 걸친 SQL 문의 분류, 테이블 복제 도구(CREATE TABLE LIKE/AS SELECT, backupdb/restoredb), 파티션 테이블과의 상호작용, 권한·감사(누가 REPLICATION을 바꿀 수 있는가), 컬럼 RENAME과 RK 정체성, REPLICATION 플래그 전환과 동시 트랜잭션의 경합, FK 부모 테이블에 RK 변경 표준 패턴(예시 13)을 적용할 때의 충돌, VIEW/SYNONYM 등 비-테이블 객체와의 옵션 경계, 복합 UNIQUE 제약의 RK 자격 기준.

다음 후보들은 검토했으나 최종 채택하지 않았다: (1) 트리거가 유발하는 간접 DML의 복제 귀속 — 이미 최종보고서에서 엔진 개발자 관점 고유 지적으로 다뤄짐. (2) SERIAL/AUTO_INCREMENT 값의 페일오버 후 동기화 — 역시 엔진 개발자 관점 고유 지적으로 이미 다뤄짐. (3) 문자열 RK 컬럼의 collation(대소문자·발음 구별 무시 등) 차이가 슬레이브 측 행 매칭에 영향을 줄 수 있다는 가설 — 검토 결과 UNIQUE 제약 자체가 이미 그 collation 규칙으로 중복을 막고, DDL(테이블 정의 및 collation)도 항상 복제되므로 마스터·슬레이브가 같은 규칙을 공유해 실질적 파손 경로를 구체적으로 구성하지 못했다. 근거 없는 추측을 남기지 않기 위해 이 항목은 리뷰로 작성하지 않았다.

이 세 영역 외에 성능·락(§2-2 옵션 변경의 락 범위), 멀티 슬레이브(슬레이브별 차등 복제), 국제화·용어 일관성 문제는 최종보고서의 M-10/M-9/T-6에서 이미 폭넓게 다뤄지고 있어 5년차 최종 사용자 관점에서 추가로 발굴할 만한 새로운 실패 모드를 찾지 못했다. 이상으로 이 관점에서 추가로 조사할 가치 있는 내용은 없다고 판단해 11건으로 마무리한다.
