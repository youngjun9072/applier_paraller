# CUBRID HA 복제 개선 스펙 리뷰 — PM 1년차 관점

## 리뷰어 소개

프로덕트 매니지먼트 1년차이며, 데이터베이스 엔진 내부 구현보다는 요구사항 완전성·하위 호환성·릴리스 리스크·문서 자체의 이해 가능성을 확인하는 역할을 맡고 있다. CUBRID 엔진 소스코드는 직접 다루지 않으며, 이 스펙 문서(user_spec_extracted.md)만 읽고 "이 문서 하나로 QA·영업·기존 고객 대응까지 설명할 수 있는가"를 기준으로 검토했다.

## 총평

이 스펙은 핵심 아이디어(RK를 PK 또는 NOT NULL UNIQUE 중에서 엔진이 선택하고, REPLICATION 옵션으로 복제 대상을 구분한다)는 명확하지만, 문서를 끝까지 읽었을 때 **§8과 §9가 서로 정반대의 기본값을 서술하는 정면 모순**이 발견되는 등 내부 일관성 검증이 안 된 상태로 보인다. 또한 이 기능이 해결하려는 문제(FK 참조 테이블이 복제 제외일 때 failover 후 데이터 불일치, 도입부 다이어그램 참고)를 정작 §4/§5의 운영 중 제약사항이 완전히 막지 못하는 허점이 있고, 기존 고객이 신규 버전으로 업그레이드할 때 무엇이 달라지는지에 대한 마이그레이션 경로 서술이 전혀 없다. SQL 예제에도 문법 오류(trailing comma)가 섞여 있어, 신입 엔지니어가 그대로 따라 실행하면 실패하는 부분이 있다. 컨셉 자체는 타당하지만, 릴리스 승인 전에 반드시 명확히 해야 할 공백이 다수 존재한다.

## 리뷰 1. [심각도: 치명] §8과 §9가 "복제 여부 미표시 시 기본값"을 정반대로 서술함

**대상**: §8 UNLOADDB & LOADDB / §9 SUMMARY

**문제 설명**: unload/load란 CUBRID의 데이터베이스 전체를 텍스트 형태의 파일로 내보내고(unload) 다시 적재하는(load) 유틸리티다. §8은 "복제 여부를 저장하는 변수가 설정되어 있지 않다면 **복제 대상(Default)으로 간주한다**"라고 명시하고, 바로 다음 문장에서 "하위 버전에서 unload한 파일에는 이 변수가 없으므로 load 시 **모두 복제 테이블로 설정된다**"고 재확인한다. 그런데 §9 SUMMARY 마지막 항목은 "UNLOADDB 시 복제 대상 여부를 함께 출력해야 하며, **이를 포함하지 않는 테이블은 모두 복제 제외 테이블이다**"라고 정반대로 적는다. 하나는 "표시 없음 = ON(복제 대상)", 다른 하나는 "표시 없음 = OFF(복제 제외)"다. 같은 문서 안에서 정반대의 기본값을 말하고 있다.

**구체 예제**:
```text
[시나리오] 구버전(REPLICATION 개념 도입 전) CUBRID로 unload한 데이터 파일을
신버전 CUBRID에 loaddb로 적재하는 경우

1. 구버전에서 orders 테이블을 unload → 생성된 파일에는 "복제 여부" 필드 자체가 없음
2. 신버전에서 loaddb 실행
3. §8을 따르면: orders는 REPLICATION ON(복제 대상)으로 생성됨
4. §9를 따르면: orders는 REPLICATION OFF(복제 제외)로 생성됨
   → 어느 쪽이 맞는지 이 문서만으로는 결정할 수 없음
```

**예제 설명**: 이 시나리오는 실제로 발생할 수 있는 가장 흔한 케이스(구버전→신버전 업그레이드 시 데이터 이관)인데, 결과가 "전체 복제됨"이냐 "전체 복제 안 됨"이냐로 완전히 갈린다. 전자라면 기존 고객의 모든 테이블이 조용히 복제 대상이 되어 성능 영향이 생기고, 후자라면 기존에 복제되던 데이터가 조용히 복제에서 빠져 마스터-슬레이브 불일치가 발생한다. 둘 다 이 기능이 애초에 막으려던 사고와 같은 종류다.

**제안**: 두 절 중 하나는 오기(誤記)일 가능성이 높다. 담당 엔지니어에게 실제 구현 의도를 확인하여 한쪽으로 통일하고, "기본값 정책"을 별도 표로 한 곳에만 명시한 뒤 §8/§9에서는 그 표를 참조하도록 구조를 바꿔야 한다.

## 리뷰 2. [심각도: 치명] 운영 중 REPLICATION=OFF 전환이 FK 참조 무결성을 다시 깨뜨릴 수 있음

**대상**: §4 HA 제약사항, §5 외래키

**문제 설명**: 이 기능 전체의 도입 배경(다이어그램 설명)은 "FK로 참조되는 테이블이 복제 제외면 failover 후 참조 데이터가 없어 문제가 생긴다"는 것이었다. §5는 **테이블을 생성/변경할 때** FK가 복제 제외 테이블을 참조하지 못하도록 막는다(예시 18, 22-1 참고 시나리오). 그런데 §2-2는 "ALTER TABLE … REPLICATION은 테이블을 복제 테이블 혹은 복제 제외 테이블로 변경한다. 단, HA 모드에서는 **복제 제외 테이블이 복제 테이블로 변경될 수 없다**"라고만 제한한다. 즉 반대 방향인 "복제 대상 → 복제 제외" 전환은 아무 제약 없이 허용되며, §4는 이 방향에 대해 "복제 제외 테이블은 REPLICATION=ON 전환 외 모든 DDL 사용 가능"이라고만 말할 뿐, "이미 다른 복제 대상 테이블이 FK로 참조 중인 테이블을 OFF로 바꾸는 것"을 막는 규정이 어디에도 없다.

**구체 예제**:
```sql
-- 1) HA 운영 중, 예시 17과 동일한 스키마가 이미 존재한다고 가정
--    customers (REPLICATION=ON, PK customer_id)
--    orders    (REPLICATION=ON, FK customer_id -> customers.customer_id)

-- 2) 운영자가 customers 테이블 자체는 그대로 두고 "복제 대상에서만 빼고 싶다"며 실행
csql> ALTER TABLE customers REPLICATION=OFF;
-- 스펙 어디에도 이 명령을 막는 규정이 없으므로 결과 예상: OK

-- 3) 이제 orders(ON, FK 참조)는 그대로 복제되지만 customers(OFF)는 복제되지 않음
--    → 도입부 다이어그램과 완전히 동일한 상황이 "운영 중 ALTER 한 줄"로 재현됨
```

**예제 설명**: §5가 CREATE/ALTER 시점에만 FK-복제 조합을 검사하기 때문에, 이미 통과된 스키마라도 참조 테이블 쪽을 나중에 OFF로 바꾸는 경로는 검증되지 않는다. §7(HA 전환)에서는 이런 위반을 검사한다고 되어 있지만, 이는 **HA를 재시작할 때**만 확인하는 것이므로, HA가 계속 켜져 있는 상태에서 이 ALTER를 실행하면 다음 재시작 전까지 아무도 이 위반을 알아채지 못한다.

**제안**: "이미 다른 ON 테이블에서 FK로 참조되고 있는 테이블은 REPLICATION=OFF로 전환할 수 없다"는 제약을 §4-2(혹은 새 §4-3)에 명시하고, 강제로 전환하려면 참조하는 쪽 FK를 먼저 제거하도록 순서를 규정해야 한다.

## 리뷰 3. [심각도: 치명] 기존 고객의 업그레이드/마이그레이션 경로가 문서에 없음

**대상**: 스펙 전체(특히 §1, §7)

**문제 설명**: 배경 설명에 따르면 기존 CUBRID HA는 PK가 있는 테이블만 복제해왔다. 즉 오늘 운영 중인 고객 데이터베이스에는 **PK도 UK(NOT NULL UNIQUE)도 없는 테이블**이 이미 다수 존재할 수 있다(지금까지는 그런 테이블은 그냥 복제가 안 됐을 뿐 에러는 아니었다). 그런데 §1은 "HA 모드 실행 시 복제 테이블은 RK가 존재하지 않으면 HA 모드를 실행할 수 없다"고 못박는다. 이 둘을 조합하면, **신버전으로 업그레이드한 기존 고객은 `cubrid hb start` 자체가 실패**할 가능성이 있다. 이 문서에는 "업그레이드 전에 무엇을 점검해야 하는지", "일괄로 문제 테이블을 찾아주는 도구가 있는지", "무중단으로 전환할 방법이 있는지"에 대한 서술이 전혀 없다.

**구체 예제**:
```text
[시나리오] 기존 고객 상황
- 운영 DB에 legacy_log 테이블 존재: PK 없음, UK 없음 (지금까지는 정상 운영 중, 단순히 복제 대상에서 제외되어 있었음)
- 고객이 신버전으로 엔진 바이너리만 교체
- 재시작: cubrid hb start
- §1 규칙 적용: legacy_log는 REPLICATION 옵션 생략 시 기본 ON으로 간주되고, RK가 없으므로
  HA 모드 기동이 실패해야 함(§1 첫 문장)
- 그런데 §7은 "HA 실행 시 제약사항을 확인하며 위반 시 에러와 함께 파일 리스트를 출력한다"고만
  되어 있어, 이 시점에 서비스가 이미 중단된 뒤임
```

**예제 설명**: 이 시나리오가 보여주는 것은 "신규 기능이 실행 중에는 안전하지만, 그 실행 전 단계(업그레이드 순간)에 대한 안전장치가 없다"는 점이다. 업그레이드 전에 미리 점검할 수 있는 오프라인 진단 도구(예: 마스터가 켜진 상태에서도 실행 가능한 "RK 없는 테이블 목록 조회" 명령)가 없다면, 고객은 업그레이드 후 서비스 중단을 겪고 나서야 문제를 알게 된다.

**제안**: (1) 업그레이드 전 사전 점검 스크립트/명령 제공, (2) 하위 호환을 위해 "RK 없는 기존 테이블은 업그레이드 시 자동으로 REPLICATION=OFF로 마이그레이션"하는 정책을 검토(§9 요약이 정말 이 의도였다면 §8과 통일), (3) 마이그레이션 가이드 문서를 스펙에 별도 절로 추가.

## 리뷰 4. [심각도: 중요] 실제로 어떤 컬럼이 RK로 선택됐는지 조회할 방법이 없음

**대상**: §2-3 REPLICATION 조회, 예시 8·9

**문제 설명**: 예시 8(`show create table`)과 예시 9(`select * from db_class`)는 모두 "REPLICATION ON/OFF" 여부만 보여줄 뿐, **엔진이 실제로 어떤 PK/UK를 RK로 선택했는지는 어디에도 나오지 않는다**. §1은 UK가 여러 개면 "엔진이 그중 하나를 선택한다"고 했고, §4-2는 "사용자는 복제키를 직접 수정할 수 없다"고 했다. 즉 사용자는 RK 선택에 관여할 수 없는데, 그 선택 결과를 확인할 방법조차 스펙에 없다.

**구체 예제**:
```sql
csql> CREATE TABLE tbl(
    a INT NOT NULL UNIQUE,
    b INT NOT NULL UNIQUE,
    c INT
);
-- PK가 없고 UK가 2개 존재. §1 규칙에 따라 엔진이 a 또는 b 중 하나를 RK로 선택한다.

csql> show create table tbl;
-- 예시 8 형식이면 'REPLICATION ON' 만 보일 뿐, a와 b 중 무엇이 RK인지는 출력에 없음

csql> select * from db_class where class_name = 'tbl';
-- 예시 9 형식도 'replication: ON' 만 보일 뿐 동일
```

**예제 설명**: 운영자가 UK 중 하나를 DROP하려고 할 때(§4-2, 예시 15), 그 UK가 현재 RK로 쓰이고 있는지 아닌지에 따라 결과(성공/에러)가 달라진다. 그런데 사전에 "지금 어떤 컬럼이 RK인지" 조회할 방법이 없으므로, 사용자는 DDL을 실행해보고 에러가 나야만 비로소 알 수 있다. 이는 장애 대응이나 스키마 변경 계획 수립 시 실무적으로 매우 불편하다.

**제안**: `show create table`/`db_class` 출력 혹은 별도 카탈로그 뷰(예: `db_index`에 RK 여부 플래그 추가)에 "현재 RK로 선택된 제약 이름"을 명시적으로 노출해야 한다.

## 리뷰 5. [심각도: 중요] UK가 여러 개일 때의 선택 규칙이 "확정 규칙"인지 "예시"인지 불명확함

**대상**: §1

**문제 설명**: 원문은 "UK가 여러개 존재한다면 큐브리드 엔진에 의해 이 중 하나가 선택된다**(ex. 테이블내에 명시된 순서 중 가장 빠른 순서)**"라고 되어 있다. "ex."라는 표현은 이것이 하나의 예시일 뿐이라는 뉘앙스이지, 확정된 알고리즘 명세가 아니다. 신입 개발자나 QA가 이 문서만 보고 "선언 순서가 빠른 UK가 항상 선택된다"라고 테스트 케이스를 작성해도 되는지, 아니면 이후 실제 구현이 다른 기준(예: 컬럼 개수가 적은 UK 우선, 인덱스 생성 시각 기준 등)을 쓸 수도 있는지 알 수 없다.

**구체 예제**:
```sql
csql> CREATE TABLE tbl(
    a INT NOT NULL UNIQUE,
    b INT NOT NULL UNIQUE
);
-- 질문 1: a가 RK로 선택되는가? ("선언 순서가 빠르므로"라는 예시를 따른다면 그렇다)

csql> ALTER TABLE tbl ADD CONSTRAINT UNIQUE(c);
-- c 컬럼을 나중에 UNIQUE로 추가. 이때도 "선언 순서"는 CREATE TABLE 시점 기준인가,
-- 아니면 "제약이 실제로 걸린 시각" 기준인가?
-- 질문 2: 기존 RK(a)가 유지되는가, 아니면 재계산되는가?
```

**예제 설명**: 이 예제는 "선언 순서"라는 표현 자체가 이미 애매하다는 것을 보여준다. CREATE TABLE 내부의 컬럼 나열 순서인지, 제약이 걸린 시점(alter 이력) 순서인지 명시되어 있지 않다. RK가 언제 바뀌는지도 알 수 없다면, 운영 중 사용자가 UK를 하나 추가했을 뿐인데 RK가 조용히 다른 컬럼으로 옮겨갈 위험이 있고, 이는 복제 로직의 키 기준이 바뀌는 것이므로 성능/정합성에 영향을 줄 수 있다.

**제안**: "ex."를 제거하고 확정 알고리즘을 명문화한다. 또한 "한번 선택된 RK는 명시적 DDL(§4-2) 없이는 재계산되지 않는다"는 안정성 보장(불변식)을 별도로 명시해야 한다.

## 리뷰 6. [심각도: 중요] 경쟁 제품 대비 "탈출구(fallback)"가 없는 설계

**대상**: 컨셉 전체(§1), 배경 문단

**문제 설명**: 배경 설명에 따르면 MySQL 방식(PK 없으면 전 컬럼을 키로 사용)은 성능 문제로 배제하고 PostgreSQL의 REPLICA IDENTITY 개념 일부를 채용했다고 한다. 그런데 PostgreSQL의 REPLICA IDENTITY는 `DEFAULT`(PK/UK 사용), `USING INDEX`, `FULL`(전 컬럼 사용, MySQL과 유사), `NOTHING`(UPDATE/DELETE 복제 자체를 제한)까지 **네 가지 옵션을 제공해 사용자가 상황에 맞게 선택**할 수 있게 한다. 이 스펙은 그중 "PK 또는 UK 선택"이라는 한 가지 모드만 채용했고, "PK/UK가 전혀 없지만 그래도 데이터를 복제하고 싶다"는 요구에는 **선택지가 REPLICATION=OFF(데이터 복제 포기) 뿐**이다. 즉 MySQL 대비 성능은 얻었지만, PostgreSQL 대비 유연성은 잃은 상태다.

**구체 예제**:
```text
[시나리오] 성능이 중요하지 않은 소규모 설정 테이블 app_config(컬럼 3개, PK/UK 없음)를
그래도 복제하고 싶은 고객

- MySQL: PK 없어도 전 컬럼 키로 복제 가능 (성능은 나쁘지만 기능은 됨)
- PostgreSQL: REPLICA IDENTITY FULL 지정 시 전 컬럼 키로 복제 가능
- 이 스펙(CUBRID): PK/UK가 없으면 HA 모드에서 아예 생성 불가(예시 10) 또는
  REPLICATION=OFF로 복제 자체를 포기해야 함 → "일단 느려도 복제는 되게 해달라"는
  요구를 충족할 방법이 없음
```

**예제 설명**: 이 예제는 "성능"과 "기능 가용성" 중 하나만 선택해야 하는 상황을 보여준다. 경쟁 제품은 사용자에게 트레이드오프를 선택하게 하는데, 이 스펙은 트레이드오프 자체를 없애버렸다(PK/UK 없으면 복제 불가로 고정). 마케팅/영업 관점에서 "MySQL은 되는데 CUBRID는 안 된다"는 비교를 받을 수 있는 지점이다.

**제안**: 최소한 로드맵 상에 "전 컬럼 키 기반 폴백 모드"를 향후 옵션으로 명시하거나, 왜 폴백을 의도적으로 제공하지 않는지에 대한 설계 근거를 스펙에 한 문단 추가해 향후 문의에 대비해야 한다.

## 리뷰 7. [심각도: 중요] 제약 위반 검사가 "HA 전환 시점"에만 이뤄지고 운영 중 실시간 검사가 없음

**대상**: §4, §7

**문제 설명**: §7은 "HA 실행 시 다음 사항을 확인하며, 위반 시 에러와 함께 파일 리스트를 출력한다"고 되어 있다. 즉 검사 시점은 **HA를 시작(재시작)하는 순간**이다. 반면 §4는 운영 중(HA가 이미 켜진 상태) 허용되는 DDL 목록만 나열할 뿐, "운영 중에 §7의 조건을 위반하는 상태로 만드는 DDL 자체를 막는다"는 문장이 없다(리뷰 2에서 지적한 FK 사례가 대표적 구멍이다). 결국 "위반 여부 검사"와 "위반을 만드는 행위 차단"이 서로 다른 시점에 분리되어 있고, 그 사이의 간극이 방치되어 있다.

**구체 예제**:
```text
1. HA 운영 중 (정상 상태, 모든 제약 만족)
2. 운영자가 실수로 §4-2 규칙을 우회하는 애매한 DDL 조합을 실행
   (예: 리뷰 2의 "ON -> OFF 전환" 또는 리뷰 8의 "UK 컬럼 NOT NULL 해제")
3. 이 시점에는 즉시 에러가 나지 않고 DDL이 성공함 (스펙에 이를 막는 규정이 없으므로)
4. 이후 몇 주간 정상적으로 서비스 운영 (사용자는 문제를 모름)
5. 장애 발생 → HA 재시작(cubrid hb start) → 이제야 §7 검사에 걸려 에러 발생
   → 하필 장애 복구가 가장 급한 순간에 처음 발견됨
```

**예제 설명**: 이 시나리오는 검사 시점이 "가장 필요 없을 때(평상시)"가 아니라 "가장 급할 때(재시작/장애복구 시점)"로 몰려 있는 설계 위험을 보여준다. 운영 중 문제가 누적되어도 알림이 없다가, 정작 failover로 서비스를 살려야 하는 순간에 처음 에러를 마주치게 되는 것은 최악의 타이밍이다.

**제안**: DDL 실행 시점(§4)에도 §7과 동일한 검사를 적용해 위반을 원천 차단하거나, 최소한 운영 중 주기적으로 위반 여부를 점검해 경고를 내보내는 모니터링 기능을 스펙에 추가해야 한다.

## 리뷰 8. [심각도: 중요] NOT NULL 해제(MODIFY COLUMN)로 UK-RK 자격이 조용히 깨지는 경로가 누락됨

**대상**: §4-2

**문제 설명**: §4-2는 UK를 복제키로 쓰는 경우의 제약을 "UNIQUE 제약 삭제(예시 15)"와 "컬럼 삭제(예시 15)" 두 경로로만 설명한다. 그런데 RK 자격의 정의 자체가 "Not Null **Unique** Key"이므로, UNIQUE 제약을 건드리지 않고 **컬럼의 NOT NULL 속성만 해제**해도 더 이상 "NOT NULL UNIQUE" 조건을 만족하지 못하게 된다. 이 경로(NOT NULL 해제)에 대한 제약이 스펙에 전혀 없다.

**구체 예제**:
```sql
-- tbl에 UK(a)만 있고 PK는 없어서 a가 현재 RK로 선택되어 있다고 가정
csql> CREATE TABLE tbl(
    a INT NOT NULL UNIQUE,
    b INT
);

-- UNIQUE 제약은 그대로 둔 채, NOT NULL만 제거 시도
csql> ALTER TABLE tbl MODIFY COLUMN a INT;  -- NOT NULL 속성 제거

-- 이 DDL이 §4-2의 어떤 제약에도 명시적으로 걸리지 않음
-- 결과는? OK인가 ERROR인가 -- 스펙에 답이 없음
-- 만약 OK라면: a는 이제 nullable UNIQUE가 되어 RK 정의(§1)를 더 이상 만족하지 않음
--   -> RK가 사라진 복제 대상 테이블이 운영 중에 만들어짐 (§1의 "HA 모드는 RK 없이 실행 불가"와 충돌)
```

**예제 설명**: 이 예제는 "제약을 삭제하는 것"과 "제약의 전제조건(NOT NULL)만 몰래 제거하는 것"이 결과적으로 같은 효과(RK 자격 상실)를 내는데, 스펙은 전자만 다루고 후자는 다루지 않는다는 것을 보여준다. 이런 우회 경로가 남아있으면 §1의 핵심 불변식("HA 모드의 복제 대상 테이블은 항상 RK를 가진다")이 실제로는 보장되지 않는다.

**제안**: §4-2의 "UK를 복제키로 사용하는 경우" 제약 목록에 "해당 컬럼의 NOT NULL 속성 해제도 UNIQUE 제약 삭제와 동일하게 취급하여 제한한다"는 항목을 명시적으로 추가해야 한다.

## 리뷰 9. [심각도: 중요] §9에 갑자기 등장하는 "SA" 모드가 §1의 모드 이분법과 충돌함

**대상**: §1, §9

**문제 설명**: §1은 "HA 모드는 'cubrid hb start'로 큐브리드를 실행시킨 상태를 의미하며 **나머지는 모두 싱글모드**"라고 정의한다. 즉 이 문서 안에서 CUBRID의 실행 모드는 "HA" 아니면 "싱글" 둘 뿐이라고 명시적으로 선언한 것이다. 그런데 §9 SUMMARY는 "이 키워드는 **싱글이나 SA**에서도 사용 가능"이라고 하여, "싱글"과 별도로 "SA"라는 모드를 언급한다. "SA"가 무엇의 약자인지(스탠드얼론 등으로 추정되나 문서에 정의가 없다) 이 문서 어디에도 설명이 없고, §1의 "나머지는 모두 싱글모드"라는 선언과도 모순된다(SA가 싱글의 하위 개념인지, 완전히 다른 제3의 모드인지 알 수 없음).

**구체 예제**:
```text
질문: 다음 중 어느 것이 맞는가?
(a) SA는 싱글모드의 한 종류이며, §1의 "나머지는 모두 싱글모드"에 이미 포함된다
    -> 그렇다면 §9에서 "싱글이나 SA"라고 굳이 나눠 쓴 이유는 무엇인가?
(b) SA는 싱글모드와 별개의 제3의 실행 모드다
    -> 그렇다면 §1의 "HA 아니면 싱글" 이분법은 틀린 서술이다
이 문서만으로는 (a)와 (b) 중 무엇이 맞는지 결정할 근거가 없다.
```

**예제 설명**: 이 질문은 이 스펙을 처음 읽는 사람이 실제로 부딪히는 지점이다. "SA"라는 용어가 정의 없이 딱 한 번 등장하고, 그 등장 방식이 앞서 정의한 모드 체계와 어긋난다. 신입 엔지니어라면 이 시점에서 CUBRID의 전체 실행 모드 체계(HA/CS/SA 등)를 별도로 찾아봐야 하는데, 스펙 문서가 자기 완결적이지 않다.

**제안**: §1에서 CUBRID의 실행 모드를 처음부터 정확히(HA/CS/SA 등 실제로 존재하는 모드 전부) 정의하고, 각 모드에서 이 기능이 어떻게 동작하는지 표로 정리해야 한다.

## 리뷰 10. [심각도: 보통] "~할 수 있어야 한다"는 약한 표현이 요구사항 전반에 반복되어 MUST/MAY 구분이 안 됨

**대상**: §3, §5, §8 전반

**문제 설명**: 스펙 문서에서 동작을 규정하는 문장은 "반드시 ~해야 한다(MUST)"와 "~할 수 있다(MAY, 선택적 기능)"를 구분해서 써야 구현자와 QA가 무엇을 필수로 테스트해야 하는지 안다. 그런데 이 문서는 "~할 수 있어야 한다"는 표현을 필수 요구사항 자리에 반복해서 쓴다. 예를 들어 §5는 "HA 모드 실행 시 외래키 테이블에서 참조하는 테이블의 상태도 확인해 복제 제외 테이블을 참조할 경우 **에러를 출력할 수 있어야한다**"고 쓰는데, 이는 문맥상 반드시 에러를 내야 하는 필수 검증으로 보이지만, 표현만 보면 "그런 기능이 있으면 좋다"는 선택 사항처럼도 읽힌다.

**구체 예제**:
```text
§5 원문: "HA 모드 실행 시 외래키 테이블에서 참조하는 테이블의 상태도 확인해
          복제 제외 테이블을 참조할 경우 에러를 출력할 수 있어야한다."

해석 A (MUST): "이 검사는 항상 수행되어야 하고, 위반 시 반드시 에러가 난다"
해석 B (MAY):  "이런 기능을 구현할 능력이 있어야 한다는 것이지, 매번 검사한다는 뜻은 아니다"

QA 담당자가 해석 B로 읽으면, "위반 상황을 만들었는데 에러가 안 났다"는 케이스를
버그로 등록하지 않을 수도 있다.
```

**예제 설명**: 이 예제는 문장 하나의 서법(mood) 차이가 QA의 테스트 판정 기준을 바꿔버릴 수 있음을 보여준다. 스펙 문서에서 요구사항 문장의 서법은 사소한 문체 문제가 아니라 "이게 버그냐 아니냐"를 가르는 기준이 된다.

**제안**: RFC 2119 스타일(반드시=MUST, 해야 한다=SHALL, 할 수 있다=MAY)처럼 문서 전체에서 서법을 통일하고, 필수 요구사항은 전부 "~한다/~해야 한다"로 단정적으로 바꿔야 한다.

## 리뷰 11. [심각도: 보통] 예시 2, 23의 SQL에 trailing comma 문법 오류가 있음

**대상**: 예시 2, 예시 23

**문제 설명**: 예시 2는 다음과 같다.
```sql
csql> CREATE TABLE repl_table_without_rk(
    a INT,
);
```
컬럼 목록이 `a INT,` 하나뿐인데 콤마 뒤에 바로 닫는 괄호가 온다. 대부분의 SQL 방언(그리고 문서 내 다른 모든 예시)은 이런 trailing comma(마지막 항목 뒤에 불필요하게 남은 쉼표)를 문법 오류로 처리한다. 예시 23도 동일한 패턴("order_id INT PRIMARY KEY," 뒤에 바로 닫는 괄호)을 갖고 있다.

**구체 예제**:
```sql
-- 예시 2 원문 그대로 실행 시
csql> CREATE TABLE repl_table_without_rk(
    a INT,
);
-- 예상: 대부분의 SQL 파서에서 문법 오류(SYNTAX ERROR) 발생 가능성

-- 올바른 형태
csql> CREATE TABLE repl_table_without_rk(
    a INT
);
```

**예제 설명**: 이 문서는 §2-1에서 "복제 키가 없는 테이블은 싱글 모드에서만 생성 가능하다"는 중요한 규칙을 보여주기 위해 예시 2를 제시하는데, 정작 그 예시의 SQL 자체가 문법 오류라면 신입 엔지니어가 그대로 복사해서 실행했을 때 "RK가 없어서 나는 에러"인지 "문법이 틀려서 나는 에러"인지 구분할 수 없다. 학습 자료로서의 신뢰도가 떨어진다.

**제안**: 모든 SQL 예제를 실제로 실행해보고(또는 최소한 문법 검사기로 확인하고) trailing comma를 제거해야 한다.

## 리뷰 12. [심각도: 보통] 예시 7만 유일하게 "..." 로 얼버무린 템플릿이라 실습 불가능

**대상**: §2-2, 예시 7

**문제 설명**: 예시 7("Multiple ALTER")은 다음과 같다.
```sql
csql> ALTER TABLE tbl DROP CONSTRAINT ..., ADD CONSTRAINT ...;
```
이 문서의 다른 모든 예시(1~6, 8~23)는 실제로 실행 가능한 구체적인 컬럼명·제약명·테이블명을 사용하는데, 예시 7만 유일하게 "..."라는 생략 표시를 그대로 남겨두었다. 그런데 바로 뒤 §4-2의 예시 13이 사실상 이 예시 7의 완성된 형태("ALTER TABLE table_name DROP CONSTRAINT PRIMARY KEY, ADD CONSTRAINT PRIMARY KEY(a);")를 보여주므로, 예시 7은 정보량 없이 자리만 차지하는 중복 예제가 되어버렸다.

**구체 예제**:
```sql
-- 예시 7 (원문, 실행 불가)
csql> ALTER TABLE tbl DROP CONSTRAINT ..., ADD CONSTRAINT ...;

-- 예시 13 (§4-2, 실제로는 이것이 예시 7이 말하고자 한 완성형)
csql> ALTER TABLE table_name DROP CONSTRAINT PRIMARY KEY,
ADD CONSTRAINT PRIMARY KEY(a);
```

**예제 설명**: 신입 독자 입장에서 예시 7을 먼저 읽으면 "PK를 다른 컬럼으로 바꾸려면 어떤 SQL을 써야 하지?"라는 궁금증이 해소되지 않은 채 넘어가게 되고, 한참 뒤 §4-2에 가서야 답을 얻는다. 문서 순서상 비효율적이다.

**제안**: 예시 7을 삭제하거나, 예시 13과 동일한 구체적인 SQL로 대체해야 한다.

## 리뷰 13. [심각도: 보통] §7 "파일 리스트"가 무엇을 의미하는지 정의되어 있지 않음

**대상**: §7 HA 전환

```text
[시나리오] HA 재시작 시 제약 위반 발견

질문: 출력되는 "파일 리스트"의 실제 형태는 다음 중 무엇인가?
(a) violating tables: dba.orders, dba.legacy_log
(b) /cubrid/databases/testdb/testdb_violations.log
(c) unload된 스키마 파일 경로 목록
```

**예제 설명**: 운영자가 장애 상황에서 이 메시지를 처음 보고 무엇을 열어봐야 하는지 즉시 알 수 있어야 하는데, 현재 서술로는 그럴 수 없다. 에러 메시지의 정확한 포맷은 사용성에 직결된다.

**제안**: "파일 리스트"의 정확한 출력 예시(실제 에러 메시지 샘플)를 §7에 추가해야 한다.

## 리뷰 14. [심각도: 보통] 예시 8 출력에 본 기능과 무관한 미정의 키워드(REUSE_OID, COLLATE)가 등장함

**대상**: §2-3, 예시 8

**문제 설명**: 예시 8의 `show create table` 결과에는 `REUSE_OID`, `COLLATE utf8_bin` 같은 키워드가 `REPLICATION ON`과 함께 나열되어 있다. 이 스펙은 REPLICATION 옵션을 설명하는 문서인데, 관련 없는 기존 키워드들이 아무 설명 없이 함께 노출되면 독자는 "이것도 이번에 새로 추가된 것인가?"라고 오해할 수 있다.

**구체 예제**:
```text
예시 8 출력 발췌:

(실제로는 REPLICATION 이전부터 있던 기존 CUBRID 옵션으로 추정되지만, 이 문서는
그 사실을 언급하지 않는다.)
```

**예제 설명**: 예시가 실제 출력 그대로를 보여주려는 의도는 이해하지만, 리뷰 대상 스펙 문서에 처음 등장하는 낯선 키워드는 "이 기능과 무관한 기존 옵션"이라는 각주 한 줄만 있어도 혼란을 없앨 수 있다.

**제안**: 예시 8에 "REUSE_OID, COLLATE는 REPLICATION과 무관한 기존 옵션" 각주를 추가하거나, REPLICATION 부분만 부각한 축약 예시를 별도로 제공한다.

## 리뷰 15. [심각도: 보통] 다단계 FK 체인 및 자기참조 FK에 대한 규정이 없음

**대상**: §5, §7

**문제 설명**: §5는 "외래키 테이블에서 참조하는 모든 테이블이 복제 대상이어야 한다"는 1단계 관계만 다룬다. 그런데 실제 스키마에는 A→B→C처럼 참조가 여러 단계로 이어지는 경우가 흔하다. A(복제 대상)가 B(복제 대상)를 참조하고, B가 다시 C(복제 제외)를 참조하는 경우, A 입장에서는 직접 참조하는 B가 복제 대상이므로 §5 규칙을 통과하지만, B의 데이터 정합성 자체가 C 없이는 깨질 수 있다. 또한 자기 자신을 참조하는 FK(예: 조직도의 상위관리자 컬럼)에 대해서도 언급이 없다.

**구체 예제**:
```sql
-- C: 복제 제외
csql> CREATE TABLE countries(
    country_id INT PRIMARY KEY
) REPLICATION=OFF;

-- B: 복제 대상, C를 참조
csql> CREATE TABLE customers(
    customer_id INT PRIMARY KEY,
    country_id INT,
    CONSTRAINT fk_country FOREIGN KEY (country_id) REFERENCES countries(country_id)
);
-- 이 시점에 이미 §5 위반(customers가 복제 제외 테이블 countries를 참조)이지만,
-- 편의상 §5 예시 18과 동일한 패턴으로 ERROR 처리된다고 가정하고 넘어가면...

-- A: 복제 대상, B(customers)를 참조 -- customers는 복제 대상이므로 §5상 문제 없음
csql> CREATE TABLE orders(
    order_id INT PRIMARY KEY,
    customer_id INT,
    CONSTRAINT fk_customer FOREIGN KEY (customer_id) REFERENCES customers(customer_id)
);
-- orders -> customers 관계만 보면 통과하지만, customers -> countries 관계의 건전성은
-- §5, §7 어디에서도 재귀적으로 검사한다는 언급이 없음
```

**예제 설명**: 이 예제는 §5의 검사가 "직접 참조"만 보고 "간접 참조(체인)"는 검사 범위에 포함하는지 불명확하다는 점을 보여준다. 실제로는 위 예제에서 customers 생성 시점에 이미 걸러지겠지만, 그보다 복잡한 체인(3~4단계)이나 순환 참조, 자기참조 FK에 대해서는 검사 알고리즘의 범위(직접만인지 재귀적인지)를 명시해야 한다.

**제안**: §5에 "참조는 재귀적으로(체인 전체에 대해) 검사한다"는 문장을 명시하고, 자기참조 FK 케이스에 대한 예제를 추가해야 한다.

## 리뷰 16. [심각도: 보통] 파티션 테이블과 REPLICATION/RK의 상호작용이 전혀 언급되지 않음

**대상**: 스펙 전체(요구사항 완전성 관점)

**문제 설명**: 예시 9의 `db_class` 출력에는 `partitioned: 'NO'`라는 필드가 이미 존재한다. 즉 CUBRID에는 파티션 테이블(하나의 논리적 테이블을 여러 물리적 조각으로 나누어 저장하는 기능)이 이미 있다는 뜻인데, 이 스펙은 파티션 테이블에 REPLICATION 옵션을 어떻게 적용하는지, 파티션마다 다른 RK를 가질 수 있는지, 파티션 키와 RK가 다를 때 어떻게 되는지에 대해 한 마디도 언급하지 않는다.

**구체 예제**:
```sql
csql> CREATE TABLE sales(
    sale_id INT,
    sale_date DATE NOT NULL,
    amount INT,
    PRIMARY KEY(sale_id, sale_date)
) PARTITION BY RANGE(sale_date) (
    PARTITION p2025 VALUES LESS THAN (DATE'2026-01-01'),
    PARTITION p2026 VALUES LESS THAN (DATE'2027-01-01')
) REPLICATION=ON;

-- 질문: REPLICATION 옵션은 sales 테이블 전체에 적용되는가, 파티션별로 따로 설정 가능한가?
-- 질문: 파티션 하나만 REPLICATION=OFF로 바꿀 수 있는가?
-- 이 스펙에는 답이 없다.
```

**예제 설명**: 파티션 테이블은 대용량 데이터를 다루는 고객이 흔히 사용하는 기능이므로, 이 기능과의 상호작용이 정의되지 않으면 해당 고객군에게는 이 스펙 전체가 "적용 가능한지조차 알 수 없는" 상태로 남는다.

**제안**: 파티션 테이블에 대한 REPLICATION/RK 정책을 별도 절로 추가하거나, 최소한 "이번 릴리스에서는 파티션 테이블을 지원 범위에서 제외한다"는 명시적 스코프 제한 문구를 넣어야 한다.

## 리뷰 17. [심각도: 사소] "모든 DDL이 슬레이브로 복제된다"는 문장이 §1과 §4에 상호 참조 없이 중복 서술됨

**대상**: §1, §4

**문제 설명**: §1은 "모든 DDL은 슬레이브로 복제되며 테이블의 REPLICATION 옵션은 데이터 복제 여부를 결정한다"고 쓰고, §4는 "HA 환경에서 마스터에서 수행된 DDL은 모두 슬레이브로 복제된다. 단, 복제 옵션이 ON인 경우의 데이터만 슬레이브로 복제되며..."라고 사실상 동일한 내용을 다시 서술한다.

**구체 예제**:
```text
§1: "모든 DDL은 슬레이브로 복제되며 테이블의 REPLICATION 옵션은
     데이터 복제 여부를 결정한다."
§4: "HA 환경에서 마스터에서 수행된 DDL은 모두 슬레이브로 복제된다.
     단, 복제 옵션이 ON인 경우의 데이터만 슬레이브로 복제되며..."
```

**예제 설명**: 내용이 서로 모순되지는 않으므로 심각한 문제는 아니지만, 같은 규칙이 두 곳에 따로 적혀 있으면 나중에 이 규칙이 바뀔 때(예: 특정 DDL은 복제 예외로 두기로 결정하는 등) 한쪽만 수정되고 다른 쪽이 갱신되지 않을 위험이 있다.

**제안**: 규칙은 한 곳(§1)에만 정의하고, §4에서는 "§1의 DDL 복제 규칙 참고"처럼 상호 참조만 남긴다.

## 리뷰 18. [심각도: 사소] 예시 11의 에러 메시지 테이블명이 앞뒤 플레이스홀더 표기와 어긋남

**대상**: §4-2, 예시 11

**문제 설명**: 예시 11의 SQL은 일반화된 이름인 `table_name`을 사용한다("ALTER TABLE table_name ADD CONSTRAINT PRIMARY KEY(b);"). 그런데 바로 아래 표시된 에러 메시지는 `'Primary key "pk_tbl_a" already defined for class "dba.tbl".'`처럼 구체적인 이름 `tbl`을 사용한다. SQL 문에서 쓴 이름(`table_name`)과 에러 메시지에서 나온 이름(`tbl`)이 다르다.

**구체 예제**:
```sql
csql> ALTER TABLE table_name ADD CONSTRAINT PRIMARY KEY(b);
-- ERROR: Primary key "pk_tbl_a" already defined for class "dba.tbl".
--                                                          ^^^ table_name이 아니라 tbl로 표기됨
```

**예제 설명**: 사소하지만, 문서를 따라 실습하는 신입 입장에서는 "내가 만든 테이블 이름을 실행문에 넣었는데 왜 에러 메시지에는 다른 이름이 나오지?"라는 불필요한 혼란을 겪을 수 있다.

**제안**: SQL 예시와 그 아래 결과 메시지에서 테이블/제약 이름을 일관되게 맞춘다(둘 다 `table_name`이거나 둘 다 `tbl`).

## 리뷰 19. [심각도: 사소] §8의 "RK를 할당한다"는 표현이 §1의 "RK가 선택된다"는 표현과 달라 오독 소지가 있음

**대상**: §1, §8

**문제 설명**: §1은 RK 결정 방식을 일관되게 "**선택**된다"(기존에 존재하는 PK/UK 중 하나를 고른다는 뜻)로 표현한다. 그런데 §8은 "복제 테이블의 경우 큐브리드는 자동으로 RK를 **할당**한다"고 다른 동사를 쓴다. "할당(assign)"이라는 단어는 "새로 만들어서 부여한다"는 뉘앙스를 줄 수 있어, loaddb가 PK/UK 없는 테이블에도 대리 키(surrogate key)를 임의로 만들어 준다는 뜻으로 오해될 수 있다.

**구체 예제**:
```text
§1: "복제 키는 큐브리드 엔진에 의해 Primary Key 혹은 Not Null Unique Key들 중
     하나로 선택된다"
§8: "복제 테이블의 경우 큐브리드는 자동으로 RK를 할당한다."

질문: loaddb로 적재되는 테이블에 PK도 UK도 없다면, §8의 "자동으로 RK를 할당한다"는
문장에 따라 큐브리드가 새 대리 키 컬럼을 만들어서라도 RK를 부여해주는 것인가?
(§1을 따르면 그런 후보가 없으면 RK 자체가 없어야 하므로, 이 해석은 모순된다.)
```

**예제 설명**: 단어 선택 하나 때문에 "기존 키 중 고른다"는 규칙과 "없으면 새로 만들어 준다"는 규칙이 혼동될 수 있다. 실제로는 §1과 같은 의미(선택)일 가능성이 높지만, 문서만 보고는 확신할 수 없다.

**제안**: §8의 "할당한다"를 §1과 동일하게 "선택한다"로 통일하고, 필요하다면 "loaddb 시에도 §1과 동일한 선택 규칙을 적용한다"고 명시적으로 상호 참조한다.

## 리뷰 20. [심각도: 보통] 무중단 롤링 업그레이드(마스터/슬레이브 버전 혼재) 시나리오가 다뤄지지 않음

**대상**: 스펙 전체(릴리스 리스크 관점)

**문제 설명**: HA 클러스터를 무중단으로 업그레이드하려면 통상 마스터를 먼저 내리기 전에 슬레이브부터 새 버전으로 교체하거나, 잠시 구버전 마스터와 신버전 슬레이브가 함께 동작하는 구간이 생긴다. 이 스펙은 REPLICATION 옵션이라는 새로운 DDL 속성과 새로운 복제 로직을 도입하는데, "구버전 마스터가 신버전 슬레이브에게 보내는 복제 로그에는 REPLICATION/RK 관련 정보가 없을 텐데 신버전 슬레이브(혹은 반대로 신버전 마스터-구버전 슬레이브)가 이를 어떻게 처리하는지"에 대한 언급이 전혀 없다.

**구체 예제**:
```text
[시나리오] 무중단 업그레이드 절차 (가정)
1. 슬레이브를 먼저 신버전으로 교체 (마스터는 아직 구버전)
2. 구버전 마스터 -> 신버전 슬레이브로 복제 로그 전송 (기존 프로토콜, REPLICATION 개념 없음)
3. 신버전 슬레이브는 모든 수신 테이블에 대해 REPLICATION 여부/RK를 무엇으로 판단해야 하는가?
4. 이후 마스터도 신버전으로 교체, 이 시점부터 REPLICATION 옵션이 반영된 로그 전송 시작
   -> 3번 구간과 4번 구간 사이에 정책이 바뀌는데, 그 전환이 안전한지 스펙에 서술 없음
```

**예제 설명**: 이 시나리오는 "기능이 켜진 이후"의 동작은 스펙에 잘 정의되어 있지만, "기능이 도입되는 과도기(버전이 섞여 있는 구간)"의 동작은 전혀 정의되어 있지 않다는 것을 보여준다. 프로덕션 환경의 고객은 대부분 무중단 업그레이드를 요구하므로, 이 구간의 동작이 불명확하면 실제 배포 시 예기치 못한 데이터 불일치가 재발할 수 있다(바로 이 기능이 막으려는 문제와 같은 종류의 사고).

**제안**: 릴리스 노트/운영 가이드에 "이 기능이 포함된 버전으로 업그레이드할 때는 마스터와 슬레이브를 동시에 교체해야 한다(혼재 운영 비허용)"는 제약을 명시하거나, 혼재 구간을 지원한다면 그 구체적인 호환 규칙을 정의해야 한다.
