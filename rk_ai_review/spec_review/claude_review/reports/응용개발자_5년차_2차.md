# CUBRID HA 복제 개선 스펙 리뷰 — 응용 개발자(5년차) 관점 · 2차 라운드

## 2차 라운드 개요

1차 리뷰(20건)와 최종 통합보고서(40개 병합 이슈)를 먼저 정독하고, 그 두 문서가 다루지 않은 지점만 추려냈다. 구체적으로는 (1) §5 외래키 규칙이 실제로 "HA 모드에서만" 적용되는지 아니면 상시 적용되는지의 문면 자체의 범위 모호성, (2) `UNLOADDB`/`LOADDB`가 라이브 SQL 파서를 우회하는 별도 코드 경로일 가능성, (3) `REPLICATION` 옵션 변경에 대한 권한·감사 모델의 부재, (4) 파티션·복합 UK 정의·트랜잭션 경계·코드 생성 도구(JDBC 표준 메타데이터, jOOQ류) 등 스펙과 실무 도구 생태계가 맞닿는 미개척 지점을 훑었다. 최종 통합보고서 4절("직군별 관점 요약")에 이미 같은 직군의 다른 연차 리뷰어가 남긴 지적(예: `@Column(unique=true)`의 nullable 기본값 문제)은 확인 즉시 제외했다.

이번 라운드는 개수를 채우는 대신, 실제로 다른 실패 모드를 짚는 지적만 남겼다. 그 결과 9건으로 마무리한다.

### 리뷰 21

**[심각도: 치명] LOADDB가 라이브 HA 클러스터에 로드될 때 §4-1의 "RK 없는 복제 테이블 생성 금지" 검증을 실제로 거치는지 스펙이 침묵한다**

**대상**: §4-1 "HA 모드에서는 CREATE TABLE 시 복제키가 없는 복제 테이블을 생성할 수 없으며", §8 UNLOADDB & LOADDB

**문제 설명**: §4-1은 `CREATE TABLE` 문(SQL 파서를 통해 들어오는 DDL)에 대해서만 "RK 후보가 없으면 에러"를 명시한다. 그런데 `loaddb`는 csql 프롬프트에 SQL 문을 입력하는 것이 아니라, 별도의 바이너리 유틸리티가 스키마 정의 파일(unload 파일)을 읽어 클래스(테이블)를 카탈로그에 직접 생성하는 벌크 적재 도구다. 실무에서 이 도구는 "운영 DB 일부를 스테이징으로 복제(clone)"하거나 "특정 스키마만 다른 DB로 이관"하는 자동화 스크립트에 흔히 쓰이는데, 이 스크립트가 대상 DB가 **이미 HA로 가동 중인 상태**에서 `loaddb`를 실행하는 경우가 있다(예: 운영 중인 슬레이브에 신규 파티션 데이터셋을 추가 적재). 이때 unload 파일에 RK 후보가 없는(과거에 싱글 모드에서 만들어진) 테이블 정의가 포함되어 있다면, §4-1과 동일한 검증이 `loaddb` 경로에서도 걸리는지, 아니면 `loaddb`가 SQL DDL 파서를 거치지 않는 내부 API를 사용하기 때문에 이 검증을 우회해 카탈로그에 그대로 들어가 버리는지 스펙에 근거가 없다.

**구체 예제**:
```
# 운영 HA 클러스터가 가동 중인 상태에서, 다른 소스(예: 인수합병으로 편입된 레거시 DB)의
# 스키마를 이관하기 위한 자동화 스크립트
$ unloaddb -s legacy_schema.unload -c legacy_orders old_legacy_db
# legacy_orders는 PK도 UK(NOT NULL UNIQUE)도 없는 테이블이라고 가정

$ cubrid hb status prod_db
# -> Active (HA 가동 중)

$ loaddb -s legacy_schema.unload -d legacy_data.unload prod_db
# 이 시점에 §4-1과 동일한 "RK 없는 복제 테이블 생성 불가" 에러가 나야
# 스펙의 안전장치가 일관되게 동작하는 것인데, loaddb가 CREATE TABLE SQL 파서를
# 거치지 않는 별도 경로라면 이 검증 자체가 적용되지 않을 수 있다.
```

**예제 설명**: 만약 `loaddb`가 이 검증을 우회한다면, 사용자는 `csql`로 직접 `CREATE TABLE`을 치는 것보다 `loaddb`로 스키마를 밀어 넣는 것이 오히려 "더 쉽게" RK 없는 테이블을 살아있는 HA 클러스터에 심을 수 있는 뒷문이 된다. 이는 이 스펙 전체가 막으려는 원래 배경 결함(복제 누락 + fail_count 증가)을 `loaddb` 경로로 그대로 재현시키는 것과 같다. 반대로 `loaddb`가 이 검증을 그대로 따른다면, 이번엔 로드 도중 일부 테이블만 실패했을 때 이미 로드된 다른 테이블들의 데이터를 어떻게 처리하는지(전체 롤백/부분 유지)가 또 다른 질문으로 남는다.

**제안**: `loaddb`가 CREATE TABLE과 동일한 검증 코드 경로를 공유하는지(혹은 공유해야 하는지)를 §8에 명시하고, 검증 실패 시 `loaddb`의 부분 적재 처리 방침(전체 중단 vs 해당 클래스만 스킵)도 함께 규정해야 한다.

### 리뷰 22

**[심각도: 중요] §5 외래키 규칙의 첫 문장이 "HA 모드에서"로 한정되어 있어, 예시 17~23의 검증이 싱글 모드에서도 적용되는지 문면상 불명확하다**

**대상**: §5 "사용자가 **HA 모드에서** 외래키를 포함한 테이블을 생성한다면 참조 테이블 역시 반드시 복제 대상 테이블이여야한다.", 예시 17~23

**문제 설명**: §5의 도입 문장은 명시적으로 "HA 모드에서"라는 조건을 달고 있다. 반면 REPLICATION 옵션 자체는 §3에 따라 싱글 모드에서도 자유롭게 쓸 수 있다("REPLICATION 옵션 사용은 싱글 모드에서도 가능하다"). 그렇다면 싱글 모드에서 `REPLICATION=OFF` 테이블을 FK로 참조하는 테이블을 만드는 것(예시 18과 동일한 구조)은 허용되어야 하는가, 아니면 §5의 검증이 모드와 무관하게 상시 적용되는 불변 규칙이어서 싱글 모드에서도 동일하게 에러가 나야 하는가? 예시 17~23은 어느 것도 "이것은 싱글 모드 예시" 혹은 "이것은 HA 모드 예시"라는 표기가 없어, §4의 예시들(모두 "HA 모드에서"라는 전제가 절 제목에 명시됨)과 비교하면 애매함이 두드러진다.

**구체 예제**:
```sql
-- 싱글 모드에서 실행한다고 가정
csql> CREATE TABLE non_repl_customers(
    customer_id INT PRIMARY KEY,
    country INT
) REPLICATION = OFF;

csql> CREATE TABLE orders(
    order_id INT PRIMARY KEY,
    customer_id INT,
    CONSTRAINT fk_c FOREIGN KEY (customer_id) REFERENCES non_repl_customers(customer_id)
);
-- §5 도입문의 문자 그대로라면("HA 모드에서 ... 생성한다면") 이 검증은 HA 모드 전용이므로
-- 싱글 모드에서는 통과(OK)해야 한다.
-- 하지만 예시 18은 모드 구분 없이 그냥 "ERROR"라고만 적혀 있어, 싱글 모드에서도
-- 똑같이 막힐 것처럼 읽힌다. 두 해석이 서로 충돌한다.
```

**예제 설명**: 테스트/스테이징 환경은 대개 싱글 모드로 구성된다(1차 리뷰 3, 최종보고서 M-4 참고). 만약 실제 구현이 "HA 모드에서만" 이 FK 검증을 적용하는 쪽으로 만들어진다면, 싱글 모드 CI에서는 예시 18과 같은 잘못된 FK 구성이 **에러 없이 통과**하고, HA로 전환한 뒤 §7의 사전 점검에서야(그것도 재시작 시점에만) 뒤늦게 걸리게 된다. 반대로 실제 구현이 모드 무관 상시 규칙이라면, §5의 서두 문장은 오해를 유발하는 표현이다. 어느 쪽이든 문서를 고쳐야 한다.

**제안**: §5의 도입 문장에서 "HA 모드에서"라는 한정어를 없애거나(상시 규칙이라면), 혹은 "이 검증은 REPLICATION 옵션이 처음 도입되는 규칙이므로 모드와 무관하게 항상 적용된다"는 문장을 명시적으로 추가해야 한다. 아울러 예시 17~23 각각에 실행 전제(싱글/HA)를 표기해야 한다.

### 리뷰 23

**[심각도: 중요] `ALTER TABLE ... REPLICATION={ON|OFF}` 실행에 필요한 권한(GRANT) 모델과 변경 이력(감사 로그)이 스펙에 전혀 없다**

**대상**: 스펙 전체 — §2-2 ALTER 옵션, §1

**문제 설명**: `REPLICATION` 옵션은 단순한 스키마 속성이 아니라 "이 테이블의 데이터가 재해 복구(DR) 사이트나 슬레이브에 존재하는지 여부"를 결정하는, 데이터 거버넌스 관점에서 상당히 민감한 스위치다. 그런데 스펙 어디에도 이 옵션을 바꾸는 데 필요한 권한이 일반 `ALTER TABLE`과 동일한지(즉 테이블 소유자 권한이면 충분한지), 아니면 DBA 전용 권한이 별도로 필요한지 언급이 없다. 실무에서는 마이그레이션 도구(Flyway/Liquibase)의 서비스 계정에 스키마 변경을 위한 폭넓은 `ALTER` 권한을 부여하는 경우가 많은데, 이 계정이 실수(오타, 잘못된 테이블명 복사-붙여넣기)로 중요 테이블의 `REPLICATION`을 `OFF`로 바꾸는 마이그레이션 스크립트를 실행해도, 일반 컬럼 추가와 똑같은 권한 체크만 통과하면 그대로 적용된다. 게다가 이 변경이 언제, 누구에 의해 일어났는지 조회할 수 있는 표준 감사 로그(카탈로그 변경 이력)도 스펙에 없다.

**구체 예제**:
```sql
-- 마이그레이션 서비스 계정(스키마 변경 전반에 ALTER 권한 보유)이 실행하는 스크립트
-- 의도: sessions_temp 테이블을 복제 제외로 전환
-- 실수: 복사-붙여넣기 과정에서 테이블명이 잘못 들어감
csql> ALTER TABLE customers REPLICATION = OFF;
-- OK (일반 ALTER TABLE과 동일한 권한 체크만 통과)

-- 이 실수는 다음 HA 재시작 전까지는 아무 에러도 내지 않고(§7은 "재시작 시점"에만 검사),
-- 그 사이 customers 테이블은 계속 슬레이브에 반영되지 않는 상태로 운영된다.
-- 누가, 언제 이 ALTER를 실행했는지 표준 조회 수단이 스펙에 없어
-- 사후 원인 추적(postmortem)도 어렵다.
```

**예제 설명**: PK/컬럼 추가 같은 일반적인 스키마 변경은 잘못 실행해도 대개 에러가 나거나(문법/제약 위반) 데이터 손상이 즉시 드러나지만, `REPLICATION=OFF`는 **문법적으로 완전히 유효하고 즉시 성공하며, 부작용이 다음 failover가 실제로 일어날 때까지 드러나지 않는다**는 점에서 훨씬 위험하다. 이런 "지연 발현형 위험 스위치"일수록 일반 스키마 변경보다 더 엄격한 권한 분리나 최소한 변경 이력 기록이 필요하다.

**제안**: `REPLICATION` 옵션 변경에 대해 (a) 일반 `ALTER TABLE`과 동일한 권한으로 충분한지 명시하고, 필요하다면 별도 권한(`ALTER REPLICATION` 류)을 신설하며, (b) `db_class` 변경 이력 또는 별도 시스템 카탈로그에 "누가 언제 어떤 테이블의 REPLICATION을 바꿨는지"를 기록하는 감사 추적 수단을 제공해야 한다.

### 리뷰 24

**[심각도: 보통] "Not Null Unique Key"의 정의가 복합(다중 컬럼) UK에서 "모든 컬럼이 NOT NULL"을 요구하는지 "일부만 NOT NULL이어도 되는지" 불명확하다**

**대상**: §1 "복제 키는 큐브리드 엔진에 의해 Primary Key(이후 PK로 표기) 혹은 Not Null Unique Key(이후 UK로 표기)들 중 하나로 선택된다"

**문제 설명**: 스펙의 모든 UK 예시(예시 1, 14, 15 등)는 전부 **단일 컬럼** `NOT NULL UNIQUE`만 다룬다. 그런데 실무에서는 다중 테넌트(멀티 테넌시) 서비스에서 `UNIQUE(tenant_id, email)` 같은 복합 UK를 흔히 쓴다. 이때 "Not Null Unique Key"라는 정의가 "복합 UK를 이루는 컬럼 전부가 NOT NULL이어야 RK 후보가 된다"는 뜻인지, 아니면 "그중 일부(예: 첫 컬럼)만 NOT NULL이면 후보로 인정한다"는 뜻인지 스펙 문장만으로는 판단할 수 없다. UNIQUE 제약의 SQL 표준 동작(NULL은 유일성 비교에서 서로 다른 값으로 취급되어 여러 행에 NULL이 함께 존재할 수 있음)을 생각하면, 복합 키의 일부 컬럼만 NULL을 허용해도 이미 "완전한 유일성"이 깨질 수 있어 RK로 쓰기에 부적합하다는 점에서 "전체 NOT NULL"이 상식적인 해석이지만, 스펙이 명시하지 않았다는 사실 자체가 문제다.

**구체 예제**:
```sql
-- 멀티 테넌트 서비스에서 흔한 패턴: 테넌트별 이메일 유일성
csql> CREATE TABLE tenant_user(
    id INT,
    tenant_id INT NOT NULL,
    email VARCHAR(255),              -- NOT NULL 지정을 깜빡함(레거시 이관 데이터 중 이메일 없는 사용자 존재)
    CONSTRAINT uk_tenant_email UNIQUE(tenant_id, email)
);
-- PK가 없고 UK는 하나뿐인데, 그 UK를 구성하는 컬럼 중 email이 NULL을 허용한다.
-- 이 UK는 RK 후보인가, 아닌가?
-- - "전체 NOT NULL 요구" 해석: 후보 아님 -> 이 테이블은 RK 후보 0개 -> HA 전환 불가
-- - "일부만 NOT NULL이어도 됨" 해석: 후보로 인정 -> HA 전환 가능하지만
--   email이 NULL인 여러 행이 존재할 경우 RK로 행을 유일하게 식별하지 못하는 모순 발생
```

**예제 설명**: 두 해석 중 어느 쪽이든 실무적으로 문제가 생긴다. 전자라면 개발자는 "UNIQUE 제약이 분명히 있는데 왜 RK 후보가 없다고 하지?"라는 혼란을 겪고, 후자라면 엔진 내부적으로 모순(유일 식별 불가능한 컬럼 조합을 RK로 사용)이 생긴다. 어느 경우든 이 판단 기준이 명문화되어야 개발자가 복합 UK를 설계할 때 "이 조합이 RK 후보가 되려면 어떤 컬럼에 NOT NULL을 걸어야 하는지"를 미리 알 수 있다.

**제안**: §1에 "복합 UK가 RK 후보가 되려면 그 UK를 구성하는 모든 컬럼이 NOT NULL이어야 한다"는 문장을 명시적으로 추가하고, 복합 UK 예시를 최소 1개 포함해야 한다.

### 리뷰 25

**[심각도: 중요] §7이 권고하는 복구 절차(싱글 모드에서 수동 ALTER)가 Flyway/Liquibase 같은 마이그레이션 이력 관리 체계를 완전히 벗어난다**

**대상**: §7 "이 경우 싱글모드에서 ALTER TABLE… 을 이용해 복제 키에 해당하는 제약을 추가하거나 복제 제외 대상으로 변경한 후 HA를 재시작해아한다"

**문제 설명**: 많은 팀은 "모든 스키마 변경은 반드시 Flyway/Liquibase 마이그레이션 파일을 거쳐 CI/CD 파이프라인으로만 적용한다"는 원칙을 운영 규율(때로는 DB 계정 권한으로 강제)로 삼는다. 그런데 §7이 명시하는 HA 전환 실패의 유일한 복구 절차는 "HA를 내리고 싱글모드로 만든 뒤, 사람이 직접 `csql`에 접속해 `ALTER TABLE`을 손으로 실행하고, 다시 HA를 재시작하라"는 것이다. 이는 정확히 팀이 금지하려는 "마이그레이션 도구를 거치지 않은 수동 DDL"에 해당한다. 이 수동 조치를 실행한 뒤 실제 운영 DB 스키마와 Flyway의 `schema_history` 테이블(어떤 마이그레이션이 적용되었는지 기록하는 이력 테이블)이 서로 어긋나게 되고, 이후 정식 마이그레이션 파이프라인이 이 어긋남을 인지하지 못한 채 그 위에 계속 변경을 쌓게 된다.

**구체 예제**:
```
# 신버전으로 업그레이드 후 HA 재시작 시도
$ cubrid hb start prod_db
ERROR: HA 전환 제약사항 위반 (RK 없는 복제 테이블 존재)
파일 리스트: legacy_sessions

# §7이 권고하는 절차: 싱글모드로 전환 후 수동 ALTER
$ cubrid service stop
$ cubrid server start prod_db   # 싱글 모드
csql> ALTER TABLE legacy_sessions REPLICATION = OFF;   -- 사람이 직접 실행, Flyway 이력에 없음
$ cubrid hb start prod_db       -- 정상 기동

# 다음날 정기 배포에서 Flyway가 실행됨
$ flyway migrate
# Flyway의 schema_history에는 위 ALTER가 기록되어 있지 않으므로,
# 이후 누군가 로컬에서 스키마를 재현(flyway clean && flyway migrate)하면
# legacy_sessions는 REPLICATION=OFF로 재현되지 않는다 (드리프트 발생).
```

**예제 설명**: 이 드리프트(운영 DB의 실제 상태와 마이그레이션 이력 파일이 서술하는 상태가 어긋나는 현상)는 한 번 발생하면 이후 "이 환경을 처음부터 다시 만들 수 있는가"라는 재현성(reproducibility) 자체를 깨뜨린다. 특히 재해 복구 훈련이나 신규 환경 구축 시 Flyway 이력만 재생해서는 운영과 동일한 상태를 만들 수 없다는 사실을 나중에야 깨닫게 된다.

**제안**: §7의 복구 절차에 "이 ALTER TABLE 실행 내용을 정식 마이그레이션 스크립트로도 별도 기록해 이력 관리 도구에 반영해야 한다"는 안내를 추가하거나, 더 나아가 HA 미기동 상태에서도 마이그레이션 도구가 정상적으로 접속해 이 조치를 수행할 수 있는 표준 절차(싱글 모드에서도 Flyway를 그대로 돌릴 수 있음을 명시)를 문서화해야 한다.

### 리뷰 26

**[심각도: 보통] 파티션 테이블의 파티션 추가/삭제가 RK·REPLICATION 검증과 어떻게 상호작용하는지 스펙이 전혀 언급하지 않아, 무인 자동화 배치의 실패 반경을 예측할 수 없다**

**대상**: 스펙 전체 (파티션에 대한 언급 자체가 없음)

**문제 설명**: 대용량 이력 테이블(주문, 로그 등)을 월 단위로 파티셔닝하고, 매월 말 "다음 달 파티션을 미리 추가하고 오래된 파티션을 삭제"하는 배치 작업을 크론(cron)이나 스케줄러로 무인 실행하는 것은 흔한 운영 패턴이다. 이 스펙은 파티션이라는 단어를 한 번도 언급하지 않으므로, 파티션이 있는 테이블에서 새 파티션을 추가하는 DDL(`ALTER TABLE ... ADD PARTITION`류)이 RK 재검증 대상인지, 각 파티션이 부모 테이블과 별도로 REPLICATION 속성을 가질 수 있는지(예: 오래된 파티션만 복제 제외로 두고 최근 파티션만 복제) 전혀 알 수 없다. 이 배치 작업은 사람이 실시간으로 출력을 지켜보지 않는 무인 자동화이기 때문에, 만약 파티션 추가/삭제 DDL이 예상치 못한 방식으로 §4의 RK 검증에 걸려 실패한다면(혹은 반대로 검증을 우회해 파티션마다 RK 상태가 어긋난다면), 그 실패는 다음 달 파티션이 없어 INSERT가 실패하는 형태로 뒤늦게, 그것도 애플리케이션 장애로만 드러난다.

**구체 예제**:
```sql
-- HA 운영 중, 월별 파티션 테이블
csql> CREATE TABLE order_log(
    id INT,
    order_date DATE,
    payload VARCHAR(1000),
    PRIMARY KEY(id, order_date)
) PARTITION BY RANGE (order_date) (
    PARTITION p202601 VALUES LESS THAN ('2026-02-01'),
    PARTITION p202602 VALUES LESS THAN ('2026-03-01')
);

-- 매월 말 무인 배치가 실행하는 DDL (사람이 결과를 안 봄)
csql> ALTER TABLE order_log ADD PARTITION p202603 VALUES LESS THAN ('2026-04-01');
-- 이 DDL이 §4-2의 "복제키 후보 검증"을 다시 거치는가?
-- 새 파티션은 부모 테이블의 복합 PK(id, order_date)를 그대로 상속하는가,
-- 아니면 별도로 RK 후보 유무를 재확인해야 하는 새로운 단위인가?
-- 스펙에 언급이 전혀 없어 구현이 어느 쪽으로 되어 있는지 예측 불가능하다.
```

**예제 설명**: 사람이 직접 실행하는 1회성 DDL이라면 에러가 나도 그 자리에서 바로 인지하고 대응할 수 있지만, 크론으로 매월 자동 실행되는 파티션 관리 스크립트는 실패해도 알림 로직이 별도로 갖춰져 있지 않으면 다음 달 초 INSERT 실패(파티션 없음 에러)로 애플리케이션 계층에서야 발견된다. 이 스펙이 다루는 다른 모든 DDL(CREATE/ALTER/DROP)은 예시가 있지만 파티션 관련 DDL은 예시조차 없어, 구현자와 사용자 모두 파티션이 이 검증 체계 안에 있는지 밖에 있는지 짐작만 해야 한다.

**제안**: 파티션 테이블이 이번 스펙의 적용 범위에 포함되는지(포함된다면 파티션 단위 검증 규칙, 제외된다면 "파티션 테이블은 이번 버전에서 지원하지 않는다"는 명시적 배제)를 §1 또는 별도 절에 추가해야 한다.

### 리뷰 27

**[심각도: 보통] RK가 표준 JDBC `DatabaseMetaData` API(`getPrimaryKeys`/`getIndexInfo`)로 노출되지 않으면, 이를 사용하는 코드 생성 도구(jOOQ, MyBatis Generator 등)가 RK 정보를 전혀 알지 못한 채로 엔티티/DAO 코드를 생성한다**

**대상**: §2-3 REPLICATION 조회 (예시 8, 9), 최종보고서 C-3과는 다른 소비 경로

**문제 설명**: 최종 통합보고서는 사람이 `show create table`이나 `select * from db_class`로 RK를 확인할 수 없다는 점(C-3)을 지적했다. 그런데 이것과는 별개로, 애플리케이션 개발 생태계에는 사람이 아니라 **도구가 자동으로** 스키마를 읽어 코드를 생성하는 워크플로우가 있다. jOOQ의 코드 생성기, MyBatis Generator, 각종 리버스 엔지니어링 플러그인은 대체로 CUBRID 전용 SQL(`db_class`)이 아니라 JDBC 표준 인터페이스인 `java.sql.DatabaseMetaData`의 `getPrimaryKeys()`, `getIndexInfo()`, `getColumns()` 같은 메서드를 통해 스키마 메타데이터를 수집한다. 이 표준 API들은 "PK가 무엇인지", "인덱스가 UNIQUE인지"는 알려주지만 "그중 어떤 것이 REPLICATION의 RK로 선택되었는지" 같은 CUBRID 고유 개념은 애초에 표현할 방법이 없는 범용 인터페이스다. RK라는 개념 자체가 새로 생긴 것이므로, 이 표준 API 경로로는 애초에 RK를 조회할 방법이 없다.

**구체 예제**:
```java
// jOOQ 코드 생성기가 내부적으로 사용하는 방식(개념적 예시)
DatabaseMetaData meta = connection.getMetaData();
ResultSet pks = meta.getPrimaryKeys(null, "dba", "product");
// PK 컬럼 목록은 얻을 수 있다.

ResultSet indexes = meta.getIndexInfo(null, "dba", "product", true, false);
// UNIQUE 인덱스 목록도 얻을 수 있다.
// 하지만 "이 여러 UK 중 어느 것이 지금 RK로 선택되어 있는가"는
// 표준 JDBC 인터페이스 어디에도 담을 자리가 없다.
```

**예제 설명**: C-3이 지적한 문제(사람이 직접 조회 불가)를 해결하기 위해 CUBRID 전용 시스템 뷰나 `show create table` 출력 포맷을 확장하더라도, 그것만으로는 이 문제가 자동으로 해결되지 않는다. jOOQ 같은 범용 도구는 CUBRID 전용 확장을 알지 못하므로, 표준 JDBC API 경로 자체에 이 정보를 실을 방법(예: 벤더별 확장 프로퍼티, `getClientInfo` 류)을 CUBRID JDBC 드라이버 차원에서 별도로 제공하지 않는 한, 코드 생성 도구를 쓰는 팀은 영원히 "지금 RK가 무엇인지"를 도구 차원에서 알 수 없다.

**제안**: CUBRID JDBC 드라이버에 RK 조회를 위한 벤더 확장 메서드(또는 표준 API의 특정 필드에 관례적으로 실어 보내는 방식)를 제공하는 것을 검토 대상으로 명시하고, 최소한 "표준 JDBC 메타데이터로는 RK를 알 수 없다"는 제약을 문서에 남겨 도구 개발자들이 헛수고하지 않도록 해야 한다.

### 리뷰 28

**[심각도: 중요] 자동 커밋을 끈 하나의 JDBC 트랜잭션 안에서 여러 개의 별도 `ALTER TABLE` 문을 실행했을 때, DDL이 트랜잭션 롤백 대상인지 스펙이 정의하지 않는다**

**대상**: §4-2 (예시 13과는 다른 층위 — 예시 13은 **한 문장** 안의 여러 절, 여기서는 **여러 문장**을 하나의 트랜잭션으로 묶는 경우), 최종보고서 C-7과 구분됨

**문제 설명**: 최종보고서 C-7은 "쉼표로 연결된 하나의 ALTER TABLE 문 안에서 여러 절이 원자적인가"를 다룬다. 이것과 별개로, 일부 마이그레이션 코드는 JDBC `Connection.setAutoCommit(false)`로 수동 커밋 모드를 켠 뒤, **여러 개의 개별 `Statement.execute()` 호출**(즉 별도의 SQL 문 여러 개)을 실행하고 마지막에 한 번만 `commit()`을 호출하는 방식으로 "여러 DDL을 하나의 논리적 단위로 묶으려" 시도한다. 이때 CUBRID의 DDL이 일반 DML처럼 이 커밋/롤백의 영향을 받는지(즉 트랜잭션 안에서 실행한 `ALTER TABLE`들이 최종 `commit()` 전까지는 확정되지 않고, 예외가 나면 `rollback()`으로 스키마 변경 자체가 취소되는지), 아니면 각 DDL 문이 실행되는 순간 암묵적으로 커밋(implicit commit)되어 버려서 뒤이은 문장이 실패해도 앞서 실행된 DDL은 이미 확정되어 되돌릴 수 없는지가 스펙에 없다.

**구체 예제**:
```java
conn.setAutoCommit(false);
try (Statement stmt = conn.createStatement()) {
    // Step 1: 기존 PK 제거
    stmt.execute("ALTER TABLE tbl DROP CONSTRAINT PRIMARY KEY");
    // Step 2: 새 컬럼 추가 (여기서 예외 발생, 예: 컬럼명 중복)
    stmt.execute("ALTER TABLE tbl ADD COLUMN dup_col INT");   // 이미 존재해서 실패한다고 가정
    // Step 3: 새 PK로 재설정
    stmt.execute("ALTER TABLE tbl ADD CONSTRAINT PRIMARY KEY(a2)");
    conn.commit();
} catch (SQLException e) {
    conn.rollback();
    // Step 1의 "PK 제거"가 이 rollback으로 함께 취소되는가?
    // 만약 DDL이 암묵적 커밋이라면, 지금 tbl은 RK 후보 0개인 상태로 영구히 남는다.
    // 예시 12(단독 DROP PK는 즉시 에러)와도 결과가 달라지는 셈이다.
}
```

**예제 설명**: 이 패턴은 "예시 13처럼 한 문장으로 묶어야 하는 것"을 모르는(혹은 알아도 컬럼명이 동적으로 계산되어 한 문장으로 조립하기 번거로운) 마이그레이션 코드에서 실제로 나타난다. DDL이 트랜잭션 롤백 대상이 아니라면, 예외 처리 후 `rollback()`을 호출해도 이미 실행된 `DROP CONSTRAINT PRIMARY KEY`는 그대로 남아 테이블이 RK 없는 상태로 방치되고, 그 사실을 애플리케이션 코드는 "롤백했으니 원상복구됐겠지"라고 오판하게 된다.

**제안**: CUBRID에서 DDL이 트랜잭션(커밋/롤백)의 영향을 받는지 여부를 §4-2 또는 별도 절에 명시하고, 받지 않는다면(암묵적 커밋이라면) "여러 ALTER 문을 하나의 JDBC 트랜잭션으로 묶어도 원자성이 보장되지 않는다"는 경고를 마이그레이션 도구 가이드에 남겨야 한다.

### 리뷰 29

**[심각도: 중요] 대용량 테이블에 무중단으로 PK/RK를 바꾸기 위한 "그림자 테이블(shadow table) 생성 후 이름 교체" 기법과 RK·REPLICATION 상태의 상호작용이 다뤄지지 않는다**

**대상**: §4-2 (직접적인 ALTER 경로만 전제), §2-1 CREATE TABLE 기본값

**문제 설명**: 예시 13(`DROP CONSTRAINT PRIMARY KEY, ADD CONSTRAINT PRIMARY KEY(a)`)은 작은 테이블에서는 문제없지만, 행이 수억 건인 대용량 운영 테이블에서 PK를 다른 컬럼으로 바꾸는 작업은 인덱스 재구성 비용 때문에 오랜 시간 테이블 잠금을 유발할 수 있다(최종보고서 M-10). 이런 이유로 대용량 테이블의 스키마를 무중단으로 바꿔야 하는 팀은 (CUBRID 전용 도구가 없다면) 자체적으로 "새 스키마의 그림자 테이블을 별도 이름으로 만들고, 데이터를 배치로 복사한 뒤, 트리거나 애플리케이션 이중 쓰기로 최신 데이터를 따라잡고, 마지막에 테이블 이름을 서로 바꾸는" 기법(MySQL 생태계의 `gh-ost`/`pt-online-schema-change`가 널리 알려진 이 기법을 채택하고 있다)을 직접 스크립트로 구현하는 경우가 있다. 이 기법을 CUBRID HA 운영 중인 테이블에 적용하면, 새로 만든 그림자 테이블은 §2-1 기본값에 따라 `REPLICATION=ON`으로 생성되고 데이터 복사가 끝나기 전까지는 RK 후보가 없거나 인덱스가 아직 없는 과도기 상태를 거칠 수 있는데, 이 과도기 동안 그림자 테이블도 이미 "복제 대상"으로 취급되어 §4-1의 검증을 받는지, 이름 교체(rename) 시점에 원래 테이블이 갖고 있던 RK·REPLICATION 상태가 새 테이블로 정확히 승계되는지 스펙에 근거가 없다.

**구체 예제**:
```sql
-- 원본: HA 운영 중인 대용량 테이블, PK=order_id
-- Step 1: 그림자 테이블 생성 (아직 인덱스/제약 구성 전)
csql> CREATE TABLE orders_shadow(
    order_id INT,
    customer_id INT,
    new_key VARCHAR(32)
);
-- 이 시점 orders_shadow는 REPLICATION=ON(기본값)이지만 RK 후보가 0개.
-- HA 운영 중인데 이 CREATE TABLE 자체가 §4-1에 걸려 즉시 에러 나는가?
-- 아니면 데이터 적재와 제약 추가가 끝날 때까지는 유예되는가?

-- Step 2: 배치로 데이터 복사 (오래 걸림, 그 사이 원본은 계속 갱신됨)
-- Step 3: 제약 추가
csql> ALTER TABLE orders_shadow ADD CONSTRAINT UNIQUE(new_key) NOT NULL;

-- Step 4: 이름 교체
csql> RENAME TABLE orders TO orders_old, orders_shadow TO orders;
-- 원본 orders가 갖고 있던 REPLICATION 상태·RK 선택 이력이 새 orders(구 orders_shadow)로
-- 그대로 이어지는가, 아니면 orders_shadow 생성 시점에 결정된 것을 그대로 쓰는가?
```

**예제 설명**: 이 기법은 이 스펙이 예상하는 "테이블 하나를 대상으로 ALTER를 직접 실행"하는 모델과 다르게, "완전히 새로운 테이블 객체를 만들어 기존 것과 바꿔치기"하는 모델이다. 스펙의 모든 예시는 전자만 다루고 있어, 후자의 경로(이름 교체를 통한 사실상의 스키마 치환)에서 RK·REPLICATION 규칙이 어떻게 적용되는지 전혀 예측할 수 없다. Step 1에서 즉시 에러가 난다면 이 무중단 기법 자체가 HA 운영 중에는 봉쇄되는 것이고, 반대로 유예된다면 그 유예 조건(언제까지, 어떤 기준으로)이 정의되어야 한다.

**제안**: 스펙 범위에 "그림자 테이블+이름 교체"와 같은 간접적 스키마 치환 기법까지 포함할 것인지 결정하고, 최소한 `RENAME TABLE`이 REPLICATION·RK 상태를 어떻게 승계하는지(원본 것을 유지/새로 계산) 한 문장으로 명시해야 한다.

## 조사 종료 선언

이번 라운드에서는 §5의 "HA 모드에서"라는 문면 범위, §8 UNLOADDB/LOADDB가 SQL DDL 검증 경로를 공유하는지, REPLICATION 옵션의 권한·감사 모델, 복합 UK의 NOT NULL 적용 범위, 파티션·트리거·소유자 권한·TDE·collation·REUSE_OID 등 스펙이 침묵하는 객체와의 상호작용, JDBC 표준 메타데이터/코드 생성 도구 생태계, 여러 DDL 문을 하나의 트랜잭션으로 묶는 경우의 원자성, 대용량 테이블의 무중단 스키마 치환 기법까지 훑었다.

이 과정에서 다음 두 가지 이유로 추가 항목을 더 채우지 않았다.

1. **트리거·CDC·컬럼 단위 필터·복합키 RK 성능·SERIAL 동기화 등 상당수 후보는 이미 최종보고서 4절("직군별 관점 요약")의 엔진/PM 고유 지적과 본질적으로 같은 메커니즘**(예: "트리거로 인한 간접 DML의 복제 귀속", "파티션 스코프 명시 요구", "복합 UK의 성능 영향")을 다른 시나리오로 포장한 것에 불과해, 신규로 인정하기 어려웠다. 이런 항목은 의도적으로 제외했다.
2. **COLLATE 변경이 UK 인덱스 재구성에 미치는 영향, TDE 키 배포와 복제의 관계** 등 나머지 미개척 영역은 CUBRID 엔진 내부 동작에 대한 확인되지 않은 추측 없이는 구체적인 실패 시나리오를 제시할 수 없었다. 근거 없는 추측을 리뷰로 남기지 않는다는 원칙에 따라 제외했다.

이 관점(ORM/마이그레이션 도구, dev/prod parity, FK 설계, DDL 배포 자동화, 커넥션/드라이버, 테스트 환경)에서 1차 리뷰·최종보고서와 겹치지 않으면서 근거를 댈 수 있는 지적은 이 9건으로 소진되었다고 판단한다.
