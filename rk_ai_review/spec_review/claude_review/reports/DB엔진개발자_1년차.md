# CUBRID HA 복제 개선 스펙 리뷰 — DB 엔진 개발자(1년차) 관점

## 리뷰어 소개

CUBRID 엔진 개발팀에 입사한 지 1년 된 개발자다. 아직 복제 모듈(applylogdb, 카탈로그 매니저) 전체를 손에 익힌 것은 아니지만, 이번 스펙을 실제로 구현하라는 티켓을 받았다고 가정하고 코드로 옮기는 사람의 눈으로 문서를 읽었다. 신입이기 때문에 "고참이면 당연히 알겠거니" 하고 넘어가는 부분을 넘기지 못하고, 스펙에 명시되지 않은 세부 규칙이 나올 때마다 구현이 막히는 지점을 그대로 기록했다.

## 총평

이 스펙은 사용자에게 보여줄 SQL 문법과 성공/실패 예시는 비교적 풍부하지만, 그 뒤에서 엔진이 실제로 무엇을 해야 하는지(카탈로그 구조 변경, 복제 로그 포맷, 동시성 제어, 실패 시 롤백)는 대부분 생략되어 있다. 특히 복제 키(RK, Replication Key: 슬레이브에서 어떤 행을 갱신/삭제할지 특정하기 위해 쓰는 유일성 보장 컬럼 조합) 후보의 정의 자체가 명문화되어 있지 않아, 여러 예시가 "결과"만 보여줄 뿐 "왜 그렇게 판정하는지" 알고리즘을 재구성할 수 없다. §8과 §9 사이에는 명백히 모순되는 서술도 있고, 예시 SQL 중 일부는 구문 오류(trailing comma)를 그대로 포함하고 있다. 신입 개발자 입장에서 이 문서만으로 티켓을 완료하려면, 최소 5곳 이상에서 선임에게 "이거 A입니까 B입니까"를 물어봐야 하는 상태다. 컨셉 자체(PostgreSQL REPLICA IDENTITY 일부 채용, REPLICATION 테이블 옵션)는 방향성은 합리적이나, 파티션 테이블·트리거·시리얼 같은 CUBRID의 기존 객체와의 상호작용이 전혀 언급되지 않아 "언급 안 된 것 = 안 바뀐다"인지 "언급 안 된 것 = 미정"인지조차 구분할 수 없다.

## 리뷰 1

**[심각도: 치명] "복제 키 후보"의 정의가 스펙 어디에도 명문화되어 있지 않다**

**대상**: §1 "복제키는 다음 기준에 의해 결정된다", §4-2 "복제키 후보가 1개인 경우 / 함께 존재한다면"

**문제 설명**: 스펙은 RK를 "PK 또는 UK 중 엔진이 선택"한다고만 말하고, §4-2에서는 "복제키 후보"라는 표현을 당연한 듯 사용한다. 그런데 "후보"에 다음이 포함되는지 전혀 정의하지 않는다.
- `ALTER TABLE ... ADD CONSTRAINT UNIQUE(...)`로 만든 UNIQUE 제약과, `CREATE UNIQUE INDEX ...`로 만든 UNIQUE 인덱스가 CUBRID 내부적으로는 다른 카탈로그 경로를 탈 수 있는데 둘 다 후보에 포함되는가?
- NULL을 허용하지 않는 UNIQUE 인덱스가 여러 컬럼(복합키)일 때도 후보로 인정되는가?
- 이미 RK로 선택되어 사용 중인 PK/UK 자체도 "후보 개수"에 포함해서 세는가, 아니면 "후보"는 현재 RK를 제외한 나머지만 가리키는가?

이 정의가 없으면 §4-2의 "복제키 후보가 1개인 경우"와 "다른 후보가 함께 존재하는 경우"를 가르는 카운팅 로직을 구현할 수 없다.

**구체 예제**:
```sql
CREATE TABLE tbl (
    a INT PRIMARY KEY,
    b INT NOT NULL,
    c INT NOT NULL
);
CREATE UNIQUE INDEX idx_bc ON tbl(b, c);   -- 제약이 아니라 인덱스로 생성

-- 질문: 이 테이블의 "복제키 후보"는 1개(PK만)인가, 2개(PK + 복합 UNIQUE 인덱스)인가?
ALTER TABLE tbl DROP PRIMARY KEY;
```

**예제 설명**: `CREATE UNIQUE INDEX`로 만든 유니크 인덱스는 `ADD CONSTRAINT UNIQUE`와 결과적으로 유사한 유일성 제약을 걸지만, 문법상 "제약(CONSTRAINT)"이 아니라 "인덱스"로 분류된다. §4-2의 여러 예시(예시 11~16)는 전부 `CONSTRAINT`/`COLUMN` 문법만 다루고 인덱스 문법(`CREATE INDEX`, `DROP INDEX`)은 예시 16 한 건뿐이라, 인덱스 기반 UK가 후보 판정에 들어가는지 알 수 없다. 이 상태로 `DROP PRIMARY KEY`를 실행했을 때 엔진이 "후보 1개 남음(OK)"이라고 판단할지 "후보 0개(ERROR)"라고 판단할지가 정의에 따라 갈린다.

**제안**: §1 또는 §4-2 앞에 "RK 후보"를 정식으로 정의하는 절을 추가한다. 예: "RK 후보란 PK 제약, 혹은 NOT NULL 컬럼으로만 구성된 UNIQUE 제약/UNIQUE 인덱스 중 카탈로그에 유효하게 존재하는 것을 말하며, 생성 방법(CONSTRAINT 문법 vs INDEX 문법)에 관계없이 동일하게 취급한다" 같은 명시적 문장이 필요하다.

## 리뷰 2

**[심각도: 치명] §8과 §9의 unloaddb 기본값(default)이 정반대로 서술되어 있다**

**대상**: §8 "복제 여부를 저장하는 변수가 설정되어 있지 않다면 복제 대상(Default)으로 간주한다" vs §9 "이를 포함하지 않는 테이블은 모두 복제 제외 테이블이다"

**문제 설명**: unloaddb는 DB의 스키마와 데이터를 파일로 내보내는 CUBRID 유틸리티이고, loaddb는 그 파일을 다시 읽어 DB를 복원하는 유틸리티다. §8은 "REPLICATION 정보가 없는 unload 파일을 load하면 복제 대상(ON)으로 간주한다"고 말하고, 바로 이어서 "하위 버전에서 unload한 파일에는 이 정보가 없으므로 모두 복제 테이블로 설정된다"고 재차 못박는다. 그런데 §9 요약에서는 "REPLICATION 정보를 포함하지 않는 테이블은 모두 복제 제외 테이블이다"라고 정반대로 적혀 있다. 하나는 오탈자이거나 개정 과정에서 누락된 것으로 보이지만, 신입 개발자는 어느 쪽이 최신 결정인지 판단할 근거가 없다.

**구체 예제**:
```
# CUBRID 8.x (REPLICATION 개념이 없는 버전)에서
$ unloaddb -i mydb          # 결과 파일에 REPLICATION 필드 없음

# CUBRID 신버전에서
$ loaddb -d mydb mydb_schema mydb_objects

# §8을 따르면: 복제 테이블(ON)로 생성됨
# §9를 따르면: 복제 제외 테이블(OFF)로 생성됨
```

**예제 설명**: 같은 입력(구버전 unload 파일)을 신버전 loaddb로 읽어들일 때, §8과 §9 중 어느 쪽을 구현 기준으로 삼느냐에 따라 결과 테이블의 REPLICATION 값이 완전히 반대가 된다. 이는 단순 오탈자 문제가 아니라, HA 업그레이드 시나리오에서 "기존 테이블이 복제되는지 여부"라는 핵심 동작을 좌우하므로 반드시 하나로 확정해야 한다.

**제안**: 두 문장 중 하나를 정정하고, 왜 그 기본값을 택했는지(하위 호환 우선 vs 안전한 기본값 우선) 근거를 한 줄 덧붙인다.

## 리뷰 3

**[심각도: 치명] "UK가 여러 개일 때 가장 빠른 순서" 선택 기준이 비결정적(non-deterministic)이라 재현 불가능할 위험이 있다**

**대상**: §1 "UK가 여러개 존재한다면 큐브리드 엔진에 의해 이 중 하나가 선택된다(ex. 테이블내에 명시된 순서 중 가장 빠른 순서)"

**문제 설명**: "명시된 순서"가 (a) `CREATE TABLE` 문에 컬럼/제약이 등장한 텍스트 순서인지, (b) 카탈로그에 제약이 실제로 삽입된 시각/OID 순서인지, (c) 인덱스 ID 순서인지 스펙이 규정하지 않는다. 이 차이는 평상시엔 안 보이다가, ALTER TABLE로 UK를 나중에 추가하거나 삭제할 때 드러난다. 게다가 마스터와 슬레이브는 별개의 카탈로그를 갖는 두 개의 프로세스이므로, "순서"의 물리적 근거(예: 내부 OID 발급 순서)가 서버마다 미세하게 달라질 수 있다면 마스터가 선택한 RK와 슬레이브가 (failover 이후 스스로) 다시 계산한 RK가 어긋날 위험이 있다. failover란 마스터에 장애가 생겼을 때 슬레이브가 새 마스터 역할을 이어받는 것을 말하는데, 이 순간 슬레이브가 카탈로그만 보고 RK를 "재계산"한다면 반드시 마스터와 동일한 결정 함수를 사용해야 한다.

**구체 예제**:
```sql
CREATE TABLE tbl (
    a INT NOT NULL,
    b INT NOT NULL
);
ALTER TABLE tbl ADD CONSTRAINT UNIQUE(b);   -- UK1 먼저 추가
ALTER TABLE tbl ADD CONSTRAINT UNIQUE(a);   -- UK2 나중에 추가

-- 이 시점에서 RK는 b인가, a인가?
-- "테이블에 명시된 순서"가 CREATE TABLE 시점의 컬럼 정의 순서(a가 먼저)를 뜻한다면 a가 RK가 되고,
-- "제약이 추가된 순서"를 뜻한다면 b가 RK가 된다. 스펙 문장만으로는 둘 다 해석 가능하다.
```

**예제 설명**: 두 해석이 실제로 다른 결과를 내는 최소 반례다. 최초 `CREATE TABLE`에는 UK가 하나도 없다가, 운영 중에 ALTER로 UK를 순서대로 추가한 경우 "테이블 내 명시 순서"의 기준점(컬럼 정의 시점 vs 제약 추가 시점)이 결과를 바꾼다. 이 기준이 코드로 고정되어 있지 않으면, 같은 스펙 문장을 구현한 마스터와 슬레이브 코드가 서로 다른 컬럼을 RK로 계산할 수 있고, 그 결과 복제 로그의 행 식별자 해석이 어긋나 데이터 불일치가 재발한다(스펙이 원래 해결하려던 문제와 동일한 종류의 버그).

**제안**: RK 선택 기준을 "카탈로그 내부 식별자(예: 제약 OID) 오름차순"처럼 구현 가능한 단일 기준으로 명문화하고, 이 값이 마스터의 DDL 복제 로그를 통해 슬레이브로 그대로 전달되어 슬레이브는 "재계산"이 아니라 "전달받은 값을 그대로 사용"하도록 설계할 것을 제안한다.

## 리뷰 4

**[심각도: 치명] RK가 PK → UK(또는 그 반대)로 전환되는 순간, 전환 이전에 생성된 복제 로그와의 정합성이 정의되지 않았다**

**대상**: §4-2 예시 13(PK를 다른 컬럼으로 변경), 예시 14(PK 추가)

**문제 설명**: 복제 로그는 마스터에서 DML(데이터를 바꾸는 INSERT/UPDATE/DELETE 명령)이 실행될 때마다 "어떤 행을, 어떤 키 값으로 식별해서, 어떻게 바꿨는지" 기록해 슬레이브(applylogdb)에 전달하는 로그다. 예시 13처럼 `DROP CONSTRAINT PRIMARY KEY(a), ADD CONSTRAINT PRIMARY KEY(a')`로 RK 컬럼이 바뀌면, 이 DDL 커밋 이전에 컬럼 a를 키로 기록해 둔 복제 로그가 아직 슬레이브에 적용되지 않은 채 큐에 남아있을 수 있다. DDL 복제 로그가 슬레이브에 먼저 적용되어 카탈로그가 바뀌어 버리면, 뒤이어 도착하는 "옛 RK(a) 기준" DML 로그를 슬레이브가 어떻게 매칭해야 하는지 스펙에 없다.

**구체 예제**:
```sql
-- T1(마스터, 트랜잭션 1): 커밋 전
UPDATE tbl SET c = 100 WHERE a = 5;     -- 이 시점 RK는 a. 복제 로그에 "a=5인 행의 c를 100으로" 기록

-- T2(마스터, 트랜잭션 2, T1과 거의 동시에 커밋)
ALTER TABLE tbl DROP CONSTRAINT PRIMARY KEY, ADD CONSTRAINT PRIMARY KEY(a2);  -- RK가 a2로 교체

-- 슬레이브에 로그가 다음 순서로 도착했다고 가정:
--   1) ALTER TABLE ... (RK: a -> a2)   <- 먼저 적용됨
--   2) UPDATE tbl SET c=100 WHERE a=5  <- 뒤늦게 도착
```

**예제 설명**: 슬레이브가 ALTER 로그를 먼저 적용해 카탈로그의 RK를 a2로 바꿔버린 뒤, "a=5" 조건으로 걸린 UPDATE 로그가 나중에 도착하면 이 UPDATE는 이제 RK가 아닌 일반 컬럼(a)을 조건으로 삼아야 하는데, applylogdb 내부적으로 "RK 컬럼 기준으로 행을 찾는" 경로를 쓰고 있었다면 오동작할 수 있다. 반대로 두 트랜잭션의 커밋 순서(LSA, Log Sequence Address: 로그가 기록된 물리적 위치 겸 순서 번호)가 보장되어 있어 이런 재정렬이 절대 없다면, 스펙에 "DDL과 DML은 동일 LSA 순서로 직렬 적용되며 RK 전환 DDL 커밋 시점 이전의 모든 DML은 반드시 먼저 적용됨이 보장된다"는 한 줄이 있어야 신입 개발자가 안심하고 구현할 수 있다. 지금은 그 보장이 문서 어디에도 명시되지 않았다.

**제안**: DDL(특히 RK를 바꾸는 ALTER)과 DML의 복제 순서 보장을 명문화하고, 가능하다면 "RK 전환 DDL은 해당 테이블에 대한 이전의 모든 DML이 슬레이브에 적용 완료된 뒤에만 적용한다"는 배리어(barrier) 규칙을 스펙에 추가한다.

## 리뷰 5

**[심각도: 중요] 예시 7 "Multiple ALTER"의 DROP/ADD 처리 순서와 중간 상태가 정의되지 않았다**

**대상**: §2-2 예시 7 `ALTER TABLE tbl DROP CONSTRAINT ..., ADD CONSTRAINT ...;`

**문제 설명**: 하나의 ALTER TABLE 문에 DROP과 ADD를 콤마로 나열하는 다중 절(multiple clause) 문법이다. 이 문이 원자적(atomic, 전체가 성공하거나 전체가 실패하거나 둘 중 하나만 있는 성질)으로 처리되는지, 아니면 절 단위로 순차 실행되어 중간에 "RK가 0개인 테이블" 상태를 거치는지 스펙에 없다. §4-1은 "HA 모드에서는 복제키가 없는 복제 테이블을 생성할 수 없다"고 명시했으므로, 같은 원칙이 ALTER의 중간 상태에도 적용되는지가 매우 중요하다.

**구체 예제**:
```sql
-- HA 모드, tbl의 RK는 현재 PK(a) 하나뿐
ALTER TABLE tbl DROP CONSTRAINT PRIMARY KEY, ADD CONSTRAINT PRIMARY KEY(b);
```

**예제 설명**: 만약 엔진이 이 문장을 "DROP 먼저 적용 → 이 시점에 카탈로그 검사 → RK 0개라 즉시 ERROR"로 처리한다면, 사실상 예시 13(같은 문형)이 항상 실패해야 하는데 스펙은 예시 13을 OK로 명시하고 있다. 즉 절 단위 순차 검사를 하면 스펙 내부 모순이 발생한다. 반대로 "문장 전체를 임시로 적용한 뒤 마지막에 한 번만 검사"하는 방식이라면 구현이 가능하지만, 이 경우 두 번째 ADD 절이 실패했을 때(예: b에 중복값 존재) DROP까지 함께 롤백되는지, 부분 반영된 상태로 남는지도 정의가 필요하다.

**제안**: "다중 절 ALTER TABLE은 모든 절을 임시로 적용한 뒤 문장 종료 시점에 RK 존재 여부 등 제약을 일괄 검사하며, 검사 실패 시 문장 전체를 롤백한다"는 원자성 규칙을 명문화한다.

## 리뷰 6

**[심각도: 중요] 파티션 테이블과 REPLICATION/RK의 상호작용이 전혀 언급되지 않았다**

**대상**: 스펙 전체(§1~§9에 "파티션" 언급 없음)

**문제 설명**: CUBRID는 PARTITION BY를 지원하며, 파티션 테이블의 PK/UNIQUE 제약은 파티션 키를 반드시 포함해야 하는 등 일반 테이블과 다른 제약을 갖는다. 이번 스펙은 파티션 테이블에 대해 한 마디도 하지 않는데, 이는 "파티션 테이블도 일반 테이블과 동일하게 취급한다"는 뜻인지 "파티션 테이블은 이번 기능 범위 밖(지원 안 함)"인지 알 수 없다. REPLICATION 옵션을 파티션 테이블 전체에 걸어야 하는지, 파티션(자식 테이블) 단위로 따로 걸 수 있는지도 불명이다.

**구체 예제**:
```sql
CREATE TABLE sales (
    sale_id INT,
    sale_date DATE NOT NULL,
    amount INT,
    PRIMARY KEY (sale_id, sale_date)
)
PARTITION BY RANGE (sale_date) (
    PARTITION p2025 VALUES LESS THAN (DATE'2026-01-01'),
    PARTITION p2026 VALUES LESS THAN (DATE'2027-01-01')
) REPLICATION = OFF;

-- p2025 파티션만 REPLICATION = ON 으로 별도 지정 가능한가?
```

**예제 설명**: 파티션 테이블은 논리적으로는 하나의 테이블이지만 물리적으로는 파티션별 서브 테이블로 저장된다. REPLICATION 옵션이 논리 테이블 단위로만 걸리는지, 물리 파티션 단위로도 걸 수 있는지에 따라 카탈로그 스키마 설계(어느 테이블에 REPLICATION 컬럼을 두는지)가 완전히 달라진다. 스펙에 언급이 없으므로 신입 개발자는 이 기능을 파티션 테이블에 어떻게 확장할지 스스로 결정할 수 없다.

**제안**: 최소한 "이번 스펙 범위는 비파티션 테이블에 한정하며, 파티션 테이블 지원은 후속 과제다"라는 한 줄이라도 명시한다.

## 리뷰 7

**[심각도: 중요] 트리거(TRIGGER)에 의해 발생하는 변경의 복제 처리가 언급되지 않았다**

**대상**: 스펙 전체(§1~§9에 "트리거" 언급 없음)

**문제 설명**: CUBRID는 `CREATE TRIGGER`로 특정 DML 발생 시 다른 테이블에 연쇄적으로 DML을 일으킬 수 있다. 트리거가 REPLICATION=OFF 테이블에서 REPLICATION=ON 테이블로 데이터를 옮기는 경우, 혹은 그 반대의 경우 복제 로그에 어떻게 기록되어야 하는지 스펙이 다루지 않는다. 특히 트리거로 인해 간접적으로 변경된 행에 RK가 없다면(트리거 대상 테이블 자체가 RK 미보유·복제 제외라면) 이 상호작용이 §5의 외래키 문제와 유사한 "슬레이브 데이터 결손" 문제를 일으킬 수 있다.

**구체 예제**:
```sql
CREATE TABLE audit_log (
    seq INT,
    msg VARCHAR(100)
) REPLICATION = OFF;   -- RK 없이 복제 제외로 생성

CREATE TABLE orders (
    order_id INT PRIMARY KEY,
    status INT
) REPLICATION = ON;

CREATE TRIGGER trg_order_audit
AFTER UPDATE ON orders
EXECUTE INSERT INTO audit_log VALUES (1, 'order updated');

UPDATE orders SET status = 2 WHERE order_id = 10;
-- orders의 UPDATE는 복제되지만, 트리거가 만든 audit_log INSERT는 어떻게 되는가?
```

**예제 설명**: orders는 복제 대상이라 UPDATE 자체는 슬레이브로 복제되어야 한다. 그런데 이 UPDATE가 트리거를 발동시켜 audit_log(복제 제외)에 INSERT를 일으킨다. 이 INSERT는 애초에 복제 제외 테이블에 대한 것이므로 복제되지 않는 것이 §1의 원칙과 일관되지만, 스펙에 명시적으로 언급되지 않았기 때문에 "트리거가 만든 부수 효과도 원본 트랜잭션과 함께 무조건 복제된다"는 오해가 구현 중 발생할 수 있다.

**제안**: 트리거로 인한 간접 DML도 대상 테이블의 REPLICATION 옵션을 그대로 따른다는 원칙을 명시한다.

## 리뷰 8

**[심각도: 중요] SERIAL(자동 증가) 컬럼이 RK일 때, RK 전환 과정에서 값 일관성이 어떻게 보장되는지 언급이 없다**

**대상**: §4-2 예시 13, 예시 14 (RK 전환 시나리오 전반)

**문제 설명**: CUBRID의 SERIAL은 AUTO_INCREMENT와 유사하게 서버가 자동으로 증가하는 값을 채번한다. 마스터와 슬레이브는 각각 독립적인 SERIAL 채번기를 가질 수 있는데(구현에 따라 다름), 만약 어떤 컬럼이 SERIAL로 채워지는 PK였다가 RK가 다른 UK로 전환된 뒤 다시 그 SERIAL 컬럼이 일반 컬럼으로 남는다면, 복제 로그 상의 값 자체는 문제 없지만 "복제 키가 아니게 된 SERIAL 컬럼"에 대한 채번 동기화 책임(마스터 채번 값을 슬레이브가 그대로 따라가는가)이 이 스펙의 RK 전환 로직과 얽혀 있는지 확인할 수 없다.

**구체 예제**:
```sql
CREATE TABLE tbl (
    id INT DEFAULT NEXT VALUE FOR tbl_seq PRIMARY KEY,
    b INT NOT NULL UNIQUE,
    c INT
);
-- RK = id (PK)

ALTER TABLE tbl DROP CONSTRAINT PRIMARY KEY, ADD CONSTRAINT PRIMARY KEY(?);
-- 사실 id 외에 다른 PK 후보가 없으므로 이 예시 자체는 실행 불가 -> 대신
ALTER TABLE tbl ADD CONSTRAINT UNIQUE(c);
ALTER TABLE tbl DROP CONSTRAINT PRIMARY KEY;  -- RK가 PK(id, SERIAL 기반)에서 UK(b)로 전환됨

INSERT INTO tbl(b, c) VALUES (99, 1);  -- id는 여전히 SERIAL로 채번됨, 이제는 RK 아님
```

**예제 설명**: id 컬럼은 RK 자격을 잃었지만 여전히 SERIAL로 채번되는 컬럼이다. 이 컬럼 값이 마스터/슬레이브 간에 다르게 채번되어도(RK가 아니므로) 복제 행 식별에는 영향을 주지 않지만, 애플리케이션이 이 값에 의존한다면(과거에는 PK/RK로서 유일성이 보장되었다는 암묵적 신뢰) 예상치 못한 동작을 겪을 수 있다. 스펙은 이런 "RK 자격을 잃은 컬럼의 후속 취급"에 대해 아무 언급이 없다.

**제안**: RK 전환이 SERIAL/DEFAULT 채번 동작 자체에는 영향을 주지 않는다는 점, 그리고 RK 자격을 잃은 컬럼의 유일성 제약(UNIQUE)이 유지되는 한 채번 값의 유일성은 계속 보장된다는 점을 명시해 오해를 차단한다.

## 리뷰 9

**[심각도: 중요] RK 변경 DDL과 동시에 실행되는 DML 트랜잭션 사이의 동시성 제어(락)가 정의되지 않았다**

**대상**: §4-2 전체 (동시 DML에 대한 언급 없음)

**문제 설명**: ALTER TABLE로 RK를 바꾸는 도중, 다른 세션이 그 테이블에 INSERT/UPDATE/DELETE를 실행하면 어떤 순서로 처리되는지, ALTER가 테이블에 배타적 락(exclusive lock: 다른 트랜잭션의 접근을 막는 잠금)을 걸어 DML을 블로킹하는지 스펙에 없다. 기존 CUBRID의 일반적인 ALTER TABLE 동작을 그대로 따른다고 가정할 수도 있지만, 이번 기능은 "RK가 없으면 안 된다"는 새로운 불변조건(invariant)을 추가했기 때문에, 그 불변조건이 깨지는 찰나의 순간이 동시 트랜잭션에 노출되는지 여부는 새로 검토해야 하는 사항이다.

**구체 예제**:
```
-- 세션 A (RK 전환)
A> ALTER TABLE tbl DROP CONSTRAINT PRIMARY KEY, ADD CONSTRAINT PRIMARY KEY(b);

-- 세션 B (동시에 실행)
B> UPDATE tbl SET c = 1 WHERE a = 5;
```

**예제 설명**: 세션 A가 아직 커밋 전이고, DROP은 처리했지만 ADD는 처리하지 않은 내부 처리 시점이 존재한다고 가정하면, 이 순간 세션 B의 UPDATE가 실행될 때 tbl에 RK가 하나도 없는 상태에서 복제 로그를 어떻게 만들어야 하는지 알 수 없다. 반대로 A가 테이블 전체에 배타 락을 걸어 B를 블로킹한다면 이 문제는 사라지지만, 그 경우 락 보유 시간(ALTER TABLE 전체 처리 시간)이 길어질 때의 서비스 영향(타 트랜잭션 대기)에 대한 언급도 필요하다.

**제안**: RK를 변경하는 ALTER TABLE은 테이블 전체에 대해 스키마 락을 유지한 채 원자적으로 처리하며, 그동안 동시 DML은 대기한다는 동시성 규칙을 명시한다.

## 리뷰 10

**[심각도: 중요] §5의 "에러를 출력할 수 있어야한다"는 표현이 필수 요구사항인지 선택 기능인지 불명확하다**

**대상**: §5 "HA 모드 실행 시 외래키 테이블에서 참조하는 테이블의 상태도 확인해 복제 제외 테이블을 참조할 경우 에러를 출력할 수 있어야한다"

**문제 설명**: "~할 수 있어야한다"는 능력(capability)을 서술하는 표현이지, "반드시 ~한다(MUST)"는 강제 규칙 표현이 아니다. 그런데 바로 위 문장은 "외래키 테이블에서 참조하는 모든 테이블은 복제 대상이여야한다"고 단정적으로 말한다. 이 둘을 합치면 "위반하면 반드시 막아야 하는 규칙"인지 "위반을 감지해서 경고만 하고 실행은 허용하는 기능"인지 구분이 안 된다. §7에서는 "제약사항 위반 시 에러와함께 파일 리스트를 출력한다"고 단정형으로 쓰여 있어, HA 전환(HA 모드로 최초 진입하는 시점) 때는 확실히 강제로 막는 것 같은데, HA가 이미 실행 중인 상태에서 ALTER TABLE로 새로 위반 상황을 만드는 경우도 즉시 막아야 하는지는 §5 문장만으로 판단 불가능하다.

**구체 예제**:
```sql
-- HA 실행 중
CREATE TABLE non_repl_customers (
    customer_id INT PRIMARY KEY
) REPLICATION = OFF;

CREATE TABLE new_orders (
    order_id INT PRIMARY KEY,
    customer_id INT
) REPLICATION = ON;

ALTER TABLE new_orders ADD CONSTRAINT FOREIGN KEY(customer_id)
    REFERENCES non_repl_customers(customer_id);
-- 예시 22 계열에 따르면 이 문장은 ERROR로 처리됨(즉시 검사)
-- 그런데 만약 참조 테이블을 "나중에" REPLICATION=OFF로 바꾼다면?

-- 순서를 바꿔서:
CREATE TABLE customers2 (id INT PRIMARY KEY) REPLICATION = ON;
CREATE TABLE orders2 (
    order_id INT PRIMARY KEY,
    cust_id INT,
    FOREIGN KEY(cust_id) REFERENCES customers2(id)
) REPLICATION = ON;

ALTER TABLE customers2 REPLICATION = OFF;
-- 이제 orders2(복제 대상)가 복제 제외 테이블(customers2)을 참조하게 됨.
-- 이 ALTER 문 자체가 즉시 ERROR가 나야 하는가, 아니면 성공하고 다음 HA 재시작 때만 걸리는가?
```

**예제 설명**: 예시 18/22/23은 "생성 시점"에 이미 위반이 존재하는 경우만 다룬다. 위 예제의 두 번째 시나리오처럼 "정상 상태에서 나중에 참조 테이블 쪽을 OFF로 바꿔서" 위반을 만드는 경로는 스펙 예시에 전혀 없다. §5의 모호한 표현 때문에 이 ALTER를 막아야 하는지(그렇다면 예시 6 "ALTER TABLE tbl REPLICATION=OFF; OK"라는 무조건 성공 예시와 모순), 아니면 허용하고 §7의 HA 전환 검사(사실 이미 HA 실행 중이므로 재전환 없이는 검사 기회가 없음)에만 맡기는지가 완전히 불명확하다.

**제안**: "복제 대상 테이블이 참조하는 테이블을 복제 제외로 바꾸는 ALTER는 (a) 즉시 거부한다 / (b) 허용하되 런타임에 경고만 남긴다" 중 하나로 확정하고, 각각의 예시를 §5에 추가한다.

## 리뷰 11

**[심각도: 보통] REPLICATION=OFF로의 전환(예시 6)이 참조 무결성 검사 없이 항상 OK로 서술되어 있다**

**대상**: §2-2 예시 6 `ALTER TABLE tbl REPLICATION=OFF; → OK`

**문제 설명**: 리뷰 10과 이어지는 문제로, 예시 6은 어떤 전제조건도 없이 "REPLICATION=OFF 전환은 항상 성공"이라고 단정한다. 하지만 tbl이 다른 복제 대상 테이블의 FK 참조 대상이라면, 이 전환은 §5가 금지하려는 상황(복제 제외 테이블을 참조하는 복제 대상 테이블 존재)을 만들어낸다. 예시 6이 이런 예외 케이스를 감안하지 않은 "가장 단순한 경우"만 보여준 것인지, 아니면 실제로 무조건 허용하고 무결성 검사는 다른 시점(§7)에만 미루는 설계인지 이 예시만으로는 알 수 없다.

**구체 예제**:
```sql
CREATE TABLE customers (customer_id INT PRIMARY KEY) REPLICATION = ON;
CREATE TABLE orders (
    order_id INT PRIMARY KEY,
    customer_id INT,
    FOREIGN KEY (customer_id) REFERENCES customers(customer_id)
) REPLICATION = ON;

ALTER TABLE customers REPLICATION = OFF;   -- 예시 6에 따르면 "OK"
```

**예제 설명**: 예시 6을 문자 그대로 적용하면 이 ALTER는 성공한다. 그 순간부터 orders(복제 대상)는 이제 복제 제외 상태가 된 customers를 참조하는 셈이 되어, §5가 경고하는 "Failover 후 참조 테이블이 슬레이브에 없다"는 정확히 그 문제 상황이 재현된다. 즉 예시 6은 이 예제와 같은 부작용 케이스를 고려하지 않고 작성된 것으로 보인다.

**제안**: 예시 6에 "단, 이 테이블을 참조하는 복제 대상 테이블이 없을 때"라는 전제를 명시하거나, 참조 관계가 있을 때의 동작을 별도 예시로 추가한다.

## 리뷰 12

**[심각도: 중요] 현재 RK가 어느 컬럼인지 조회하는 방법이 스펙에 없다**

**대상**: §2-3 REPLICATION 조회 (예시 8, 예시 9)

**문제 설명**: 예시 8(`show create table`)과 예시 9(`select * from db_class`)는 모두 "REPLICATION ON/OFF 여부"만 보여줄 뿐, 여러 UK 후보 중 "지금 실제로 RK로 선택되어 있는 것이 어느 제약인지"를 알려주는 항목이 없다. 사용자가 §4-2의 여러 제약사항(RK는 직접 수정 불가, RK 삭제 금지 등)을 지키려면 애초에 지금 RK가 무엇인지 알아야 하는데, 이를 조회할 SQL/카탈로그 뷰가 스펙에 전혀 없다.

**구체 예제**:
```sql
CREATE TABLE tbl (
    a INT PRIMARY KEY,
    b INT NOT NULL UNIQUE,
    c INT NOT NULL UNIQUE
);
-- RK는 PK(a)로 자동 결정됨. 그런데...

ALTER TABLE tbl DROP PRIMARY KEY;
-- 이제 RK는 b, c 중 하나로 자동 재선택된다(§1 "UK 여러개 → 엔진이 선택").
-- 사용자는 지금 RK가 b인지 c인지 무엇으로 확인하는가?
SHOW CREATE TABLE tbl;      -- REPLICATION ON/OFF만 나옴, RK 컬럼명은 안 나옴
SELECT * FROM db_class;     -- 역시 replication 컬럼만 있음
```

**예제 설명**: PK가 사라지면 엔진이 b, c 중 하나를 알아서 RK로 재선택하는데, 이 재선택 결과를 사용자가 확인할 방법이 스펙에 없다. §4-2의 규칙(RK는 직접 수정 불가, RK를 삭제하려면 등)을 지키려는 사용자·운영자 입장에서 "지금 무엇이 RK인지" 조회가 안 되면, 실수로 RK인 줄 모르고 UNIQUE 제약을 삭제하려다 에러를 만나는 시행착오를 반복하게 된다.

**제안**: `db_class` 계열 카탈로그 뷰나 `SHOW` 문에 현재 RK로 선택된 제약명/컬럼 목록을 노출하는 항목을 추가한다.

## 리뷰 13

**[심각도: 보통] 예시 2와 예시 23의 CREATE TABLE 문에 trailing comma(구문 오류)가 그대로 들어있다**

**대상**: §2-1 예시 2, §5-2 "외래키 컬럼 추가"(복제 제외 참조) 예시

**문제 설명**: 예시 2는 `CREATE TABLE repl_table_without_rk( a INT, );` 로, 컬럼 정의 마지막에 불필요한 콤마가 붙어 있다. 예시 23도 `CREATE TABLE new_orders( order_id INT PRIMARY KEY, );` 동일한 문제가 있다. 대부분의 SQL 방언은 이런 trailing comma를 문법 오류로 거부한다. CUBRID csql이 이를 허용하는지 여부와 무관하게, 스펙 문서에 실리는 예시 코드에 구문 오류가 있으면 문서를 그대로 베껴 쓴 신입/사용자가 동일한 오류를 재현하게 된다.

**구체 예제**:
```sql
-- 스펙 원문 그대로
CREATE TABLE repl_table_without_rk(
    a INT,
);
```

**예제 설명**: 컬럼 목록의 마지막 항목 뒤에 콤마가 있고 곧바로 닫는 괄호가 온다. 표준 SQL 문법상 이는 "콤마 다음에 컬럼 정의가 하나 더 와야 하는데 안 왔다"는 구문 오류로 해석되는 것이 일반적이다.

**제안**: 두 예시 모두 trailing comma를 제거해 `CREATE TABLE repl_table_without_rk( a INT );` 형태로 수정한다.

## 리뷰 14

**[심각도: 보통] 예시 10의 테이블명이 실제 스키마와 모순되어 혼란을 준다**

**대상**: §4-1 예시 10 "복제 테이블에는 반드시 복제 키 후보가 1개 이상 필요하다"

**문제 설명**: 예시 10은 `CREATE TABLE repl_table_with_rk( a INT );`로, 테이블 이름은 "RK가 있는 복제 테이블(with_rk)"인데 실제 정의에는 PK도 UK도 없어 RK가 없는 테이블이다(그래서 ERROR가 나는 것이 스펙의 의도). 같은 테이블명 `repl_table_with_rk`가 §2-1 예시 1에서는 실제로 PK/UK를 가진 테이블로 이미 등장했다. 동일 이름이 서로 다른(심지어 상반된) 스키마로 두 번 나오는 것은 문서 읽는 사람의 혼란을 유발한다.

**구체 예제**:
```sql
-- 예시 1 (§2-1): 이 이름의 테이블은 PK/UK가 있다
CREATE TABLE repl_table_with_rk(
    a INT PRIMARY KEY,
    b INT NOT NULL UNIQUE,
    c INT
);

-- 예시 10 (§4-1): 같은 이름인데 이번엔 PK/UK가 전혀 없다
CREATE TABLE repl_table_with_rk(
    a INT
);
-- ERROR
```

**예제 설명**: 두 예시는 서로 다른 절(§2-1과 §4-1)에 독립적으로 등장하지만, 이름이 같아서 "왜 같은 이름의 테이블이 한 번은 성공하고 한 번은 에러가 나는가"라는 오해를 만들 수 있다. 실제로는 두 문장의 컬럼 정의 자체가 다르기 때문에 결과가 다른 것뿐이지만(이름만 보고 착각하기 쉬움), 문서 품질 관점에서 좋은 예시는 아니다.

**제안**: 예시 10의 테이블명을 `repl_table_without_rk_in_ha` 등 실제 내용과 일치하는 이름으로 바꾼다.

## 리뷰 15

**[심각도: 보통] 예시 16(DROP INDEX)이 "인덱스"와 "UNIQUE 제약"을 구분하지 않고 서술한다**

**대상**: §4-2 예시 16 "DROP INDEX: 복제키 후보가 없다면 삭제 불가"

**문제 설명**: `DROP INDEX`는 CUBRID에서 일반 비유일(non-unique) 인덱스에도 쓸 수 있는 문법이다. 그런데 예시 16의 설명은 "복제키 후보가 없다면 삭제 불가"라고만 되어 있어, 이 규칙이 "UNIQUE 인덱스를 지워서 RK 후보가 사라지는 경우"에만 적용되는지, 아니면 `DROP INDEX`라는 문법 자체가 (인덱스의 유일성 여부와 무관하게) 전부 이 제약을 받는지 구분이 안 된다. 만약 후자로 오독하면, RK와 전혀 무관한 일반 보조 인덱스 하나 지우는 것조차 막히는 과도한 제약으로 잘못 구현될 위험이 있다.

**구체 예제**:
```sql
CREATE TABLE tbl (
    a INT PRIMARY KEY,
    b INT NOT NULL
);
CREATE INDEX idx_b ON tbl(b);   -- 일반 인덱스(유일성 없음), RK 후보 아님

DROP INDEX idx_b ON tbl;
-- 이 DROP은 RK 후보를 전혀 건드리지 않는데도 예시 16의 제약 대상인가?
```

**예제 설명**: `idx_b`는 유일성 제약이 없는 일반 인덱스이므로 RK 후보였던 적이 없다. 이 인덱스를 지운다고 해서 RK 후보 개수는 전혀 줄지 않는다. 그런데 예시 16의 설명 문구만 보면 "DROP INDEX는 복제키 후보가 없어지면 안 된다"는 규칙이 이 케이스에도 적용되는 것으로 오해할 수 있다.

**제안**: 예시 16의 설명을 "DROP INDEX 대상이 UNIQUE 인덱스이고, 이를 삭제하면 RK 후보가 0개가 되는 경우에만 삭제 불가"로 명확히 좁혀 서술한다.

## 리뷰 16

**[심각도: 보통] §4-2 "기존의 제약사항은 유지된다"가 무엇을 가리키는지 참조가 불명확하다**

**대상**: §4-2 "다른 복제키 후보가 함께 존재한다면 모든 DDL은 허용된다(단, 기존의 제약사항은 유지된다.)"

**문제 설명**: "기존의 제약사항"이 (a) 이 스펙이 새로 추가하기 이전부터 CUBRID에 있던 일반 DDL 규칙(예: 한 테이블에 PK는 하나만 가능)을 가리키는지, (b) 바로 앞에서 설명한 "RK 후보가 1개일 때의 제약사항(예시 11~16)"을 가리키는지, (c) 이 문서 전체에서 지금까지 언급된 모든 제약을 가리키는지 지시 대상이 애매하다. 직후 문장이 "복제키 후보가 1개인 경우 제약사항은 다음과 같다"로 이어지기 때문에 (b)로 읽힐 여지도 있지만, 그러면 "후보가 여럿이라 모든 DDL이 허용된다"는 앞 문장과 "그런데 후보가 1개일 때의 제약은 유지된다"는 뒷 문장이 서로 모순된다.

**구체 예제**:
```sql
CREATE TABLE tbl (
    a INT PRIMARY KEY,
    b INT NOT NULL UNIQUE,   -- RK 후보 2개 (PK a, UK b)
    c INT
);

-- RK 후보가 2개이므로 "모든 DDL 허용"
ALTER TABLE tbl DROP CONSTRAINT PRIMARY KEY;
-- 이 DROP 이후 RK 후보는 1개(UK b)만 남는다.
-- "기존 제약사항"이 예시 11~16(후보 1개일 때 규칙)을 가리킨다면,
-- 이 DROP 직후부터는 b에 대해 DROP CONSTRAINT 등이 막혀야 하는가?
-- 아니면 이 ALTER문 자체는 "후보가 여럿이던 시점"에 실행됐으므로 무조건 허용되는가?
```

**예제 설명**: "허용 여부 판정"이 DDL 실행 이전 상태(후보 2개)를 기준으로 하는지, 실행 이후 상태(후보 1개)를 기준으로 하는지에 따라 이 DROP 자체의 성패가 갈릴 수 있다. 스펙 문장은 이 판정 시점(before/after)을 명시하지 않는다.

**제안**: "기존의 제약사항"이 정확히 무엇을 가리키는지 명시하고, RK 후보 개수에 대한 판정이 DDL 실행 전 상태 기준인지 실행 후 상태 기준인지 규정한다.

## 리뷰 17

**[심각도: 보통] HA 모드에서 CREATE TABLE ... REPLICATION=OFF가 RK 없이 허용되는지 §4-1에 명시적으로 나오지 않는다**

**대상**: §4-1 "HA 모드에서는 CREATE TABLE 시 복제키가 없는 복제 테이블을 생성할 수 없으며, 나머지 기능은 2-1과 동일하다"

**문제 설명**: §4-1은 "복제 테이블(REPLICATION=ON)"에 대한 제약만 명시적으로 말한다. §1 마지막 문단에 "복제 제외 테이블은 복제 키의 유무와 상관 없이 생성 가능"이라는 일반 원칙이 있어서 HA 모드에서도 RK 없는 REPLICATION=OFF 테이블 생성이 될 것이라고 유추는 가능하지만, §4-1 문장 자체는 "복제 테이블"의 경우만 다루고 "나머지 기능은 2-1과 동일"이라고만 해서, 이 "나머지"에 복제 제외 테이블 생성 규칙까지 포함되는지 독자가 스스로 짜맞춰야 한다.

**구체 예제**:
```sql
-- HA 모드(cubrid hb start로 기동된 상태)
CREATE TABLE log_tbl (
    msg VARCHAR(200)
) REPLICATION = OFF;
-- 이 문장이 HA 모드에서 성공하는지는 §4-1을 읽어도 직접적으로 확인되지 않는다.
-- §1의 일반 원칙을 §4-1에 재적용해서 유추해야 함.
```

**예제 설명**: 이 CREATE TABLE에는 PK도 UK도 없다. §1만 보면 "복제 제외 테이블은 RK 유무와 무관하게 생성 가능"이라 성공해야 할 것 같지만, §4-1 "HA 제약사항"이라는 절 제목 안에 있는 문장이라 "HA 모드에서는 특별히 더 엄격하게 막는 것 아닌가"라는 의심을 배제할 수 없다. §4-1이 직접 "복제 제외 테이블은 이 절의 제약을 받지 않는다"라고 한 번 더 못박아주지 않으면, 신입 개발자는 코드에서 REPLICATION=OFF 분기를 HA 제약 검사보다 먼저 두어도 되는지 스펙만으로 확신할 수 없다.

**제안**: §4-1에 "단, REPLICATION=OFF로 생성하는 경우 이 절의 RK 필수 규칙은 적용되지 않는다(§1 참조)"는 문장을 명시적으로 추가한다.

## 리뷰 18

**[심각도: 사소] §1의 "HA 모드 / 나머지는 모두 싱글모드" 이분법이 §9의 SA(Standalone) 언급과 어긋나 보인다**

**대상**: §1 "HA 모드는 'cubrid hb start' 로 큐브리드를 실행시킨 상태를 의미하며 나머지는 모두 싱글모드", §9 "이 키워드는 싱글 이나 SA에서도 사용 가능"

**문제 설명**: CUBRID에는 실행 모드로 CS(Client-Server, 사실상 여기서 말하는 "싱글모드"에 해당하는 일반 서버 모드)와 SA(Standalone, 서버 프로세스 없이 단일 프로세스로 동작하는 모드, 주로 unloaddb/loaddb/백업 등 유틸리티 작업에 쓰임)가 별도로 존재한다. §1은 "HA 모드가 아니면 전부 싱글모드"라고 이분법으로 서술해 SA 모드의 존재를 언급하지 않다가, §9에 가서야 "싱글이나 SA에서도 사용 가능"이라며 갑자기 세 번째 범주를 등장시킨다. CUBRID 실행 모드 체계를 모르는 신입이 §1만 읽으면 SA 모드가 "싱글모드"에 포함되는 것으로 이해하게 되는데, §9의 병기 방식은 SA를 싱글모드와 대등한 별개 범주처럼 취급하고 있어 앞뒤가 안 맞는다.

**구체 예제**:
```
$ cubrid server start mydb        # "싱글모드"(CS, 서버 프로세스로 기동)
$ cubrid hb start                 # "HA 모드"
$ csql -S -u dba mydb             # SA 모드로 직접 접속 (서버 프로세스 없이)

-- §1 이분법대로면 SA도 "나머지 = 싱글모드"에 속해야 하는데,
-- §9는 "싱글 이나 SA"라고 굳이 병렬 나열한다. SA가 싱글모드의 부분집합이면 왜 따로 적었는가?
```

**예제 설명**: 세 가지 실제 실행 방식(CS, HA, SA)이 스펙 안에서 "HA vs 싱글" 이분법과 "싱글 vs SA" 병렬 언급으로 일관성 없이 섞여 서술된다. 이번 REPLICATION 옵션·RK 규칙이 SA 모드에서 동작할 때 CS(싱글모드)와 완전히 동일한 규칙을 따르는지, 아니면 SA 특유의 제약(예: 트리거 비활성화 등 SA 모드의 기존 제한)이 추가로 적용되는지도 확인할 수 없다.

**제안**: §1에서 처음부터 "실행 모드는 HA / CS(싱글) / SA 세 가지이며, 이 문서에서 '싱글모드'는 HA가 아닌 CS와 SA를 모두 포괄한다"처럼 범주를 명확히 정의한다.

## 리뷰 19

**[심각도: 사소] 예시 12·15·16 등 다수 예시가 실제 에러 메시지 없이 "ERROR"로만 표기되어, 정상 동작 여부를 텍스트로 검증할 수 없다**

**대상**: §4-2 예시 12, 15, 16 등 ("ERROR"만 표기)

**문제 설명**: 같은 절의 예시 11은 `ERROR: Primary key "pk_tbl_a" already defined for class "dba.tbl".`처럼 실제 에러 메시지 문구를 담고 있다. 반면 예시 12, 15, 16 등 다수는 그냥 "ERROR"라고만 되어 있다. 신입 개발자나 QA 담당자가 이 스펙을 기준으로 "정상적으로 구현되었는지" 검증하려면 최소한 어떤 에러 코드/메시지가 나와야 하는지 알아야 하는데, 대부분의 예시가 이를 생략해 검증 가능한 인수 기준(acceptance criteria)이 되지 못한다.

**구체 예제**:
```sql
-- 예시 12 원문 그대로
ALTER TABLE table_name DROP PRIMARY KEY;
-- ERROR   <- 어떤 에러 메시지인지 불명. "PK가 RK라서 삭제 불가"라는 전용 메시지가 있는가,
--            아니면 기존 CUBRID의 일반적인 "제약을 찾을 수 없음" 류 메시지가 재사용되는가?
```

**예제 설명**: 이번 기능은 기존에 없던 새로운 제약("RK이므로 삭제 불가")을 추가하는 것이므로, 이 제약을 위반했을 때 나오는 메시지도 새로 설계해야 할 가능성이 높다. 그런데 예시에 실제 문구가 없으니 신입 개발자는 이 에러 메시지를 새로 만들어야 하는지, 기존 CUBRID 에러 코드를 재사용해도 되는지조차 판단할 근거가 없다.

**제안**: 모든 ERROR 예시에 실제로 노출될 에러 메시지(혹은 최소한 에러 코드)를 예시 11처럼 채워 넣는다.

## 리뷰 20

**[심각도: 보통] unloaddb 파일 포맷에서 REPLICATION 정보가 저장되는 위치·형식과, 이를 모르는 구버전 파서가 신규 필드를 만났을 때의 동작이 기술되지 않았다**

**대상**: §8 "unload 시 복제 테이블의 여부를 함께 저장한다"

**문제 설명**: unloaddb는 스키마 정의를 텍스트 형태의 `_schema` 파일로 출력한다. 이번 기능으로 이 파일에 REPLICATION 여부를 나타내는 새 필드/구문이 추가되어야 하는데, 스펙은 "함께 저장한다"고만 서술할 뿐 (a) 스키마 파일의 어느 위치에 어떤 키워드로 저장되는지, (b) 이 필드가 CREATE TABLE 문 자체에 `REPLICATION=ON/OFF` 절로 인라인되는지 별도 메타 라인으로 저장되는지, (c) 이 신규 필드를 모르는 구버전 loaddb 파서가 신버전 unload 파일을 읽었을 때(반대 방향의 하위 호환) 무시하고 넘어가는지 파싱 에러를 내는지 전혀 다루지 않는다. §8은 "구버전 → 신버전" 방향의 호환성만 다루고, "신버전에서 만든 파일을 구버전이 읽는" 반대 방향은 언급이 없다.

**구체 예제**:
```
# 신버전에서 unload
$ unloaddb -i newdb
$ head newdb_schema
CREATE TABLE tbl (
    a INT PRIMARY KEY
) REUSE_OID, COLLATE utf8_bin, REPLICATION ON;   -- 예시 8 출력 형태를 그대로 가정

# 이 파일을 구버전(REPLICATION 개념이 없는) loaddb로 읽으면?
$ old_loaddb -d olddb newdb_schema newdb_objects
```

**예제 설명**: 만약 REPLICATION 절이 `CREATE TABLE` 구문 안에 그대로 인라인된다면, 이 키워드를 모르는 구버전 SQL 파서는 문법 오류로 전체 로드를 실패시킬 가능성이 크다. 이는 다운그레이드(신버전에서 만든 백업을 구버전에 복원)나 이기종 버전 간 운영(예: 롤링 업그레이드 중 일부는 구버전) 시나리오에서 치명적인 문제가 될 수 있다. 스펙은 "구버전 파일을 신버전이 읽는" 시나리오만 다뤄서 이 반대 경로의 위험을 놓치고 있다.

**제안**: unload 파일 포맷 변경의 정확한 문법을 명시하고, 구버전 loaddb가 신버전 unload 파일을 읽을 때의 동작(오류로 명확히 실패 vs 옵션 무시하고 진행)도 함께 규정한다.
