# CUBRID HA 복제 개선 스펙 리뷰 — DB 엔진 개발자(5년차) 관점 (2차 라운드)

## 2차 라운드 개요

1차 리뷰(20건)는 RK 자동 선택의 결정성, 다중 절 ALTER의 원자성, 복제 로그와 DDL 순서, unloaddb/loaddb
재계산 문제 등 스펙의 핵심 알고리즘 층위를 주로 팠다. 2차에서는 1차와 최종보고서(40개 통합 이슈)가
다루지 않은 영역, 특히 스펙이 예시에서 값만 슬쩍 보여주고 아무 설명도 하지 않은 필드들(TDE 알고리즘,
소유자, 콜레이션)과의 상호작용, CUBRID 고유의 클래스 상속 기능, 그리고 "HA 전환 검사(§7)" 자체의
시간적 경계에서 발생하는 레이스를 집중적으로 조사했다. 특히 배경에서 설명한 원래 버그(fail_count 증가로
인한 HA 정지)가 이번 스펙이 새로 만든 REPLICATION=OFF 경로를 통해 그대로 재발할 수 있다는 지점(리뷰 28)이
가장 심각하다고 판단했다.

### 리뷰 21

**[심각도: 치명] TDE 암호화 대상 컬럼이 RK로 선택되면 복제 로그에 평문 값이 노출된다**

**대상**: §2-3 예시 9 (`tde_algorithm` 필드), §1 RK 선택 규칙, 배경 (PostgreSQL REPLICA IDENTITY 채용)

**문제 설명**: TDE(Transparent Data Encryption, 투명한 데이터 암호화)는 디스크에 저장되는 데이터 파일을
암호화해 파일 탈취 공격에 대비하는 기능이다. `db_class`에 `tde_algorithm` 필드가 이미 존재한다는 것은
CUBRID가 테이블 단위(혹은 컬럼 단위)로 TDE를 지원한다는 뜻이다. 그런데 복제는 "이 값을 가진 행을 찾아
바꿔라"는 조건을 슬레이브에 전달해야 동작하므로, RK로 선택된 컬럼의 값은 복제 로그(네트워크로 전송되는
스트림과 마스터·슬레이브 양쪽의 로그 볼륨)에 반드시 평문으로 실려야 한다. RK 자동 선택 규칙(§1)은
"PK 우선, 없으면 UK, 여러 UK면 순서상 가장 빠른 것"만 볼 뿐 TDE 적용 여부는 전혀 고려하지 않는다. 만약
사용자가 TDE로 보호하려던 민감 컬럼(주민등록번호, 카드번호 등)에 UNIQUE 제약을 걸어뒀고 그것이 유일한
RK 후보라면, 엔진은 그 컬럼을 그대로 RK로 선택해버린다.

**구체 예제**:
```sql
CREATE TABLE customer_secure (
    ssn CHAR(13) NOT NULL UNIQUE,   -- 주민등록번호, 디스크 상 암호화하고 싶은 컬럼
    name VARCHAR(50)
) REPLICATION = ON;
-- 이 테이블에 TDE를 적용한다고 가정 (문법은 예시)
ALTER TABLE customer_secure TDE_ALGORITHM = AES;

-- PK가 없고 UK가 ssn 하나뿐이므로 RK = ssn 으로 자동 선택된다.
UPDATE customer_secure SET name = '홍길동' WHERE ssn = '9001011234567';
-- 슬레이브가 행을 식별하려면 복제 로그에 "ssn = '9001011234567'"이 평문으로 실려야 한다.
```

**예제 설명**: 데이터 파일 자체는 TDE로 암호화되어 디스크 탈취에는 안전하지만, 복제 로그는 별도의
저장·전송 경로다. 이 스펙 어디에도 "RK 후보 선택 시 TDE 적용 컬럼은 배제한다"거나 "TDE 컬럼이 RK가
되면 복제 로그도 암호화한다"는 규정이 없다. 결과적으로 TDE를 켜는 이유(디스크 유출 대비)가 복제
경로에서는 그대로 뚫려 있을 수 있다.

**제안**: RK 후보 선택 시 TDE 적용 컬럼의 우선순위를 낮추거나(비-TDE UK가 있으면 그것을 우선 선택),
TDE 컬럼이 불가피하게 유일한 후보라면 복제 로그 자체도 암호화 경로를 타도록 명시해야 한다. 최소한
이 상호작용을 "알려진 제약"으로 문서화해야 한다.

### 리뷰 22

**[심각도: 중요] REPLICATION 옵션 변경에 필요한 권한 수준이 정의되지 않았다**

**대상**: §2-2 (ALTER TABLE … REPLICATION), §2-3 예시 9 (`owner_name` 필드)

**문제 설명**: `db_class` 출력에 `owner_name`이 별도 컬럼으로 존재한다는 것은 CUBRID가 테이블 소유자
개념을 갖고 있다는 뜻이며, 통상 ALTER TABLE은 그 테이블의 소유자(혹은 DBA)면 실행할 수 있다. 그런데
REPLICATION 옵션 변경은 그 테이블 하나의 문제가 아니라 HA 클러스터 전체의 데이터 일치성 보장 범위를
바꾸는 시스템 차원의 결정이다(다른 테이블의 FK 무결성, failover 후 애플리케이션 동작에도 영향을 준다).
스펙은 이 옵션 변경을 일반 ALTER TABLE 권한(소유자 권한)만으로 할 수 있는지, 별도의 상위 권한이
필요한지 전혀 언급하지 않는다.

**구체 예제**:
```sql
-- 일반 사용자 app_user가 소유한 테이블
CREATE TABLE app_user.orders (
    order_id INT PRIMARY KEY,
    customer_id INT,
    CONSTRAINT fk_c FOREIGN KEY(customer_id) REFERENCES dba.customers(customer_id)
) REPLICATION = ON;

-- app_user 본인 계정으로 접속해서
ALTER TABLE app_user.orders REPLICATION = OFF;
-- 이 한 줄이 dba가 관리하는 HA 전체의 마스터/슬레이브 일치성 보장 범위를 바꾼다.
-- app_user는 자신이 소유한 테이블에 대한 통상적 ALTER 권한만으로 이 옵션을 바꿀 수 있는가?
```

**예제 설명**: 컬럼 추가·삭제 같은 일반 ALTER는 그 테이블에만 영향을 주므로 소유자 권한으로 충분하다.
그러나 REPLICATION=OFF는 "이 테이블은 이제 슬레이브에 없어도 됩니다"라는 클러스터 수준의 계약을
깨는 결정이라 성격이 다르다. 소유자 권한만으로 바꿀 수 있다면, DBA가 관리하는 HA 운영 정책을 개별
애플리케이션 계정이 인지하지 못한 채 깨뜨릴 수 있다.

**제안**: REPLICATION 옵션 변경에는 일반 ALTER 권한과 별도의 명시적 권한(HA 관리 권한 또는 DBA 승인)을
요구하거나, 최소한 이 변경이 감사 로그에 별도로 남도록 규정해야 한다.

### 리뷰 23

**[심각도: 중요] 복합 UNIQUE 제약의 "NOT NULL" 요건이 선언 수준인지 데이터 수준인지 불명확하다**

**대상**: §1 "Not Null Unique Key(UK)" 정의

**문제 설명**: 스펙은 RK 후보를 "PK 또는 Not Null Unique Key"라고만 정의한다. 단일 컬럼 UK는 그
컬럼 자체에 NOT NULL이 선언되어 있는지로 판단이 명확하다. 그러나 여러 컬럼을 묶은 복합 UNIQUE
제약의 경우, "묶인 컬럼 전부가 각각 NOT NULL로 선언되어 있어야 후보 자격이 있는가", 아니면 "일부만
NOT NULL이어도 상관없는가"가 정의돼 있지 않다. 일반적인 UNIQUE 인덱스는 NULL을 허용하는 컬럼이
섞여 있어도 생성 가능하며, 이때 NULL은 서로 달라도 유일하다고 취급되는 것이 보통의 SQL 관례다. 그
결과 특정 컬럼이 NULL인 행이 여러 개 공존할 수 있어, "이 값 조합으로 행을 유일하게 식별한다"는
RK의 근본 전제가 깨질 수 있다.

**구체 예제**:
```sql
CREATE TABLE t3 (
    x INT NOT NULL,
    y INT,              -- NOT NULL 미선언
    UNIQUE (x, y)
) REPLICATION = ON;

INSERT INTO t3 VALUES (1, NULL);
INSERT INTO t3 VALUES (1, NULL);   -- UNIQUE(x,y) 위반이 아닐 수 있음(y가 NULL이라 서로 다르게 취급)
-- 두 행이 공존 가능하다면 "x=1, y=NULL" 조건으로는 행을 하나로 특정할 수 없다.
-- 이 UNIQUE(x, y)는 RK 후보가 될 수 있는가?
```

**예제 설명**: PK 없이 이 UNIQUE(x, y)만 있는 테이블에서 y가 NULL을 허용하면, y가 NULL인 행이
여러 개 존재할 수 있어 (x, y) 값만으로 행을 특정하지 못하는 경우가 생긴다. 이런 UK를 RK로 그대로
선택하면 복제 로그의 UPDATE/DELETE 조건이 여러 행에 매치되거나 대상을 특정하지 못하게 된다.

**제안**: "복합 UK가 RK 후보가 되려면 구성 컬럼 전부가 개별적으로 NOT NULL 제약을 가져야 한다"를
§1에 명시하고, 이를 만족하지 않는 UK는 §4-2의 후보 판정 로직에서 아예 제외해야 한다.

### 리뷰 24

**[심각도: 중요] RK 컬럼의 COLLATE 변경이 허용되는지, 허용된다면 RK 동치성 판단에 미치는 영향이 없다**

**대상**: §2-3 예시 8 (`COLLATE utf8_bin` 출력), §4-2 (RK 컬럼 보호 규칙)

**문제 설명**: 콜레이션(collation)은 문자열의 비교·정렬 규칙을 결정한다. 예를 들어 대소문자를
구분하는 콜레이션에서는 `'A'`와 `'a'`가 다른 값이지만, 대소문자를 무시하는 콜레이션에서는 같은
값으로 취급된다. RK가 문자열 컬럼일 때, 그 컬럼의 콜레이션을 바꾸는 ALTER는 §4-2가 나열하는
보호 규칙(제약 삭제 금지, 컬럼 삭제 금지) 목록에 없다. 콜레이션이 바뀌면 UNIQUE 인덱스가 "유일하다"고
판단하는 기준 자체가 바뀌는데, 그 컬럼이 RK라면 복제 로그가 행을 식별하는 동치 기준도 암묵적으로
바뀌게 된다.

**구체 예제**:
```sql
CREATE TABLE t4 (
    code VARCHAR(20) NOT NULL UNIQUE COLLATE utf8_bin   -- 대소문자 구분
) REPLICATION = ON;
-- RK = code (대소문자 구분 콜레이션 기준으로 유일성 보장: 'ABC'와 'abc'는 다른 값)
INSERT INTO t4 VALUES ('ABC');
INSERT INTO t4 VALUES ('abc');   -- utf8_bin에서는 둘 다 허용(서로 다른 값)

ALTER TABLE t4 MODIFY COLUMN code VARCHAR(20) COLLATE utf8_ci;  -- 대소문자 무시로 변경
-- 이제 기존에 저장된 'ABC'와 'abc'는 새 콜레이션 기준으로는 "같은 값"인데
-- 이미 유니크 인덱스에 별개 항목으로 존재한다. RK로서의 유일성 전제가 깨진 채 남는다.
```

**예제 설명**: 콜레이션 변경 전에 저장된 데이터가 새 콜레이션 기준으로는 더 이상 유일하지 않을 수
있다. §4-2는 RK 컬럼에 대해 "제약 삭제·컬럼 삭제"만 막을 뿐, "비교 규칙을 바꿔 유일성의 의미 자체를
흔드는 변경"은 언급하지 않는다. 슬레이브가 콜레이션 변경 전 데이터를 그대로 갖고 있다면, 마스터와
슬레이브가 "같은 행"으로 판단하는 기준이 어긋날 위험도 있다.

**제안**: RK로 사용 중인 컬럼의 COLLATE 변경 시, 변경 후 콜레이션 기준으로 기존 데이터의 유일성을
재검증하고 위반이 있으면 예시 15와 동일하게 에러 처리하도록 §4-2에 추가해야 한다.

### 리뷰 25

**[심각도: 보통] 클래스 상속(UNDER)을 사용한 서브클래스의 REPLICATION 옵션 상속 규칙이 없다**

**대상**: 스펙 전체 (상속 관련 절 없음)

**문제 설명**: CUBRID는 `CREATE TABLE … UNDER superclass` 구문으로 한 테이블이 다른 테이블의
컬럼·제약을 물려받는 상속 기능을 지원한다. 이 스펙은 REPLICATION 옵션이 부모에서 자식으로
상속되는지, 자식이 독립적으로 재설정할 수 있는지, 부모가 OFF인데 자식만 ON으로 만들 수 있는지에
대해 전혀 언급하지 않는다.

**구체 예제**:
```sql
CREATE TABLE base_entity (
    id INT PRIMARY KEY
) REPLICATION = OFF;

CREATE TABLE derived_entity (
    extra_field INT
) UNDER base_entity;
-- derived_entity는 REPLICATION 옵션을 생략했다.
-- (1) base_entity가 OFF이므로 derived_entity도 자동으로 OFF가 되는가?
-- (2) 생략 시 기본값 규칙(§2-1, "생략시 ON")이 그대로 적용되어 derived_entity만 ON이 되는가?
```

**예제 설명**: 상속 관계는 부모와 자식이 물리적으로 연결된 스키마 구조를 이루므로, 복제 대상
여부가 부모/자식 간에 어긋나면 부모 데이터는 없는데 자식 데이터만 슬레이브에 존재하는 반쪽짜리
상태가 될 수 있다. §5의 FK 규칙과 비슷한 문제이지만, 상속은 FK보다 강한 결합(자식이 부모 컬럼을
그대로 포함)이라 영향 범위가 다르다.

**제안**: 상속 관계에서 REPLICATION 옵션의 상속·독립 여부를 명시하고, 필요하다면 §5의 FK 검증과
유사하게 "자식이 ON이면 부모도 ON이어야 한다"는 규칙을 추가한다.

### 리뷰 26

**[심각도: 치명] §7 HA 전환 검사와 HA 모드 진입 완료 사이에 검사-실행 시차(레이스)가 존재한다**

**대상**: §7 전체

**문제 설명**: §7은 "HA 실행시 다음 사항을 제약사항을 확인하며"라고 해서, `cubrid hb start` 시점에
카탈로그 전체를 스캔해 RK 유무·FK 참조 대상을 검사하는 것으로 읽힌다. 그런데 이 검사가 수행되는
시점과 "HA 모드가 완전히 활성화되어 이제부터 모든 DML이 복제되기 시작하는 시점" 사이에는 반드시
시간 간격이 있다(카탈로그 전체 스캔은 순간적으로 끝나지 않는다). 이 간격 동안, 아직 완전히 HA로
전환되지 않았다는 이유로 §3의 "싱글 모드에서는 RK 관련 제약이 없다"는 규칙이 여전히 적용된다면,
검사를 통과한 테이블의 RK를 그 사이에 없애버리는 DDL이 성립할 수 있다.

**구체 예제**:
```
[시각 T0]      cubrid hb start 명령 실행, §7 검사 시작 (카탈로그 전체 스캔)
[시각 T0+1ms]  tbl_a 검사 통과 (RK 있음 확인)
[시각 T0+2ms]  (아직 싱글 모드 규칙이 적용되는 짧은 창에서) 다른 세션이
               ALTER TABLE tbl_a DROP CONSTRAINT u_tbl_a; 실행 — 성공(§3상 허용)
[시각 T0+5ms]  카탈로그 스캔 완료, HA 모드 활성화 선언
-- tbl_a는 RK가 없는 상태로 HA에 편입되었다.
```

**예제 설명**: §3은 싱글 모드에서는 RK 없는 ON 테이블의 생성·유지가 자유롭다고 규정하므로, "HA
전환 검사 시작"과 "HA 모드 완전 활성화" 사이의 창은 여전히 싱글 모드 규칙이 적용되는 회색지대일
수 있다. 검사가 한 번 훑고 끝나는 스냅샷 방식이라면 이 창에서 발생한 변경을 놓친다.

**제안**: §7 검사를 "카탈로그 전체에 대한 배타적 잠금을 잡은 채 수행하고, 통과 즉시 원자적으로
HA 모드를 활성화"하는 하나의 절차로 명시하거나, 최소한 이 창의 존재와 처리 방식을 스펙에 남겨야
한다.

### 리뷰 27

**[심각도: 치명] 마스터와 슬레이브가 §7 검사를 각자 독립적으로 수행할 때 한쪽만 통과하는 비대칭 기동이 가능하다**

**대상**: §7, 배경 (복제 누락으로 인한 마스터/슬레이브 카탈로그 불일치)

**문제 설명**: 이 스펙이 풀려는 원래 배경 문제 자체가 "복제가 조용히 누락되어 마스터와 슬레이브의
카탈로그·데이터가 어긋나는 상황"이다. §7은 "HA 실행시" 검사한다고만 할 뿐, 클러스터의 각 노드(마스터가
될 노드, 슬레이브가 될 노드)가 각자 자신의 로컬 카탈로그를 보고 독립적으로 검사하는 것인지, 마스터의
판정 결과만으로 클러스터 전체의 HA 진입 여부를 결정하는 것인지가 불명확하다. 만약 노드별 독립
검사라면, 과거의 복제 누락으로 두 노드의 카탈로그가 이미 미묘하게 어긋난 상태(정확히 이 기능이
고치려는 상황)에서는 한쪽은 통과, 다른 쪽은 실패하는 반쪽짜리 기동이 이론적으로 가능하다.

**구체 예제**:
```
-- 과거(패치 이전) 버전에서 마스터의 DDL이 복제 누락으로 슬레이브에 반영되지 못해
-- 이미 두 노드 카탈로그가 어긋나 있다고 가정 (배경에서 설명한 실제 장애 유형)
[마스터]   ALTER TABLE legacy_tbl ADD CONSTRAINT UNIQUE(b);  -- 반영됨, RK 후보 생김
[슬레이브] (복제 누락으로 이 ALTER가 반영 안 됨)              -- RK 후보 없음, 옛 상태 그대로

-- 패치된 버전으로 업그레이드 후 cubrid hb start 실행
[마스터]   §7 검사: legacy_tbl에 RK 있음 → 통과
[슬레이브] §7 검사: legacy_tbl에 RK 없음 → 실패
-- 마스터는 HA로 진입하는데 슬레이브는 진입 거부되는 상황이 생기는가?
```

**예제 설명**: 이 시나리오는 가상이 아니라, 이 스펙이 고치려는 정확히 그 유형의 과거 장애가 남긴
흔적이다. 새 기능이 "HA 진입 시 RK를 검증한다"는 안전장치를 추가했지만, 그 검증 자체가 노드별
로컬 판단이라면 이미 어긋난 카탈로그를 갖고 있는 클러스터에서는 검증 결과마저 노드마다 달라 어느
쪽을 신뢰해야 할지 애매한 상태가 될 수 있다.

**제안**: §7 검사가 클러스터 전체 관점(마스터 카탈로그를 기준으로 슬레이브도 동일한지 함께 검증)에서
수행되는지, 노드별 독립 검사인지 명시하고, 후자라면 "노드 간 카탈로그 불일치 자체를 감지해 에러로
보고"하는 절차를 추가해야 한다.

### 리뷰 28

**[심각도: 치명] REPLICATION=OFF 테이블의 DDL 복제 실패가 fail_count 문제를 그대로 재현할 수 있다**

**대상**: §4 "HA 환경에서 마스터에서 수행된 DDL은 모두 슬레이브로 복제된다", §1 "REPLICATION OFF로
인한 데이터 불일치는 책임지지 않는다", 배경 (fail_count 증가 문제)

**문제 설명**: §1의 면책 조항은 "데이터 불일치"에 대한 것이고, §4는 "DDL은 REPLICATION 여부와
무관하게 항상 복제된다"고 명시한다. 즉 OFF 테이블도 DDL 복제·적용의 성공은 여전히 보장되어야 하는
대상이다. 그런데 OFF 테이블은 정의상 슬레이브의 데이터가 마스터와 달라도 되는(오히려 그것이 허용된
동작인) 테이블이므로, 그 어긋난 데이터 위에서 DDL을 실행하면 마스터에서는 성공한 DDL이 슬레이브에서는
실패할 수 있다. 이는 배경에서 설명한 원래 버그(복제 실패로 fail_count 증가, HA 정지)와 완전히 같은
실패 모드가 "이 기능이 새로 만든 OFF 테이블"이라는 새 경로를 통해 재발하는 것이다.

**구체 예제**:
```sql
-- customers는 REPLICATION=OFF, 슬레이브 데이터는 OFF 전환 시점에 멈춘 상태(리뷰 6, 1차 참고)
-- 마스터에서는 그 후 정리 작업을 거쳐 country 컬럼에 중복이 전혀 없는 상태
ALTER TABLE customers ADD CONSTRAINT UNIQUE(country);
-- 마스터: 성공 (현재 마스터 데이터에는 country 중복 없음)

-- 이 DDL은 §4에 따라 슬레이브로도 복제된다.
-- 슬레이브의 customers는 OFF 전환 시점 스냅샷이라 country에 중복값이 남아있을 수 있다.
-- 슬레이브에서 같은 ALTER 재생 시 UNIQUE 위반으로 실패
-- -> applylogdb가 이 DDL 적용에 실패, fail_count 증가, HA 정지
```

**예제 설명**: OFF 테이블은 "데이터가 달라도 책임지지 않는다"는 면책이 있을 뿐, "DDL 적용 실패에
대한 면책"은 없다. 그런데 데이터가 다르면 그 데이터에 의존하는 제약 추가 DDL(UNIQUE, CHECK, NOT
NULL 등)은 얼마든지 마스터·슬레이브에서 다른 결과를 낼 수 있다. 결국 이 스펙이 도입한
REPLICATION=OFF 기능 자체가, 원래 고치려던 fail_count 문제의 새로운 발생 경로가 된다.

**제안**: OFF 테이블에 대한 DDL 적용 실패 시의 동작(예: 그 테이블에 한해 DDL 적용 실패를 무시하고
넘어가는 별도 모드)을 정의하거나, 최소한 "OFF 테이블도 DDL 실패는 여전히 fail_count를 올리고
HA를 정지시킬 수 있다"는 위험을 명시하고 운영 가이드를 제공해야 한다.

### 리뷰 29

**[심각도: 중요] 단일 ALTER TABLE MODIFY COLUMN 문이 내부적으로 인덱스 재생성을 거칠 때 RK 후보 0개 구간이 생길 수 있다**

**대상**: §4-2 (복제키 후보 개수에 따른 제약), 1차 리뷰 3(콤마로 묶은 다중 절의 원자성)

**문제 설명**: 1차 리뷰 3에서는 사용자가 명시적으로 콤마로 여러 절을 묶은 ALTER TABLE의 원자성을
문제 삼았다. 이 리뷰는 다른 경로를 짚는다 — 사용자 입장에서는 한 문장짜리 단일 ALTER인데, 엔진
내부 구현이 이를 여러 단계(예: 컬럼 타입 변경 시 기존 UNIQUE 인덱스를 내부적으로 삭제하고 새
타입에 맞춰 인덱스를 재생성)로 처리하는 경우다. 이런 내부 다단계 구현이 §4-2가 말하는 "복제키
후보 개수" 판정 로직과 어떻게 상호작용하는지 스펙에 없다. 내부적으로 잠깐 인덱스를 지웠다가 다시
만드는 구현이라면, 그 순간 후보 개수가 0이 되어 §4-2 규칙에 걸려 실패해야 하는데, 사용자 관점에서는
"그냥 컬럼 타입을 바꾸는 것"뿐이라 왜 실패하는지 이해할 수 없는 에러를 만날 수 있다.

**구체 예제**:
```sql
-- b가 유일한 RK 후보(UK)인 테이블
CREATE TABLE tbl (a INT, b INT NOT NULL UNIQUE) REPLICATION = ON;

-- 컬럼 타입만 바꾸는, 사용자 입장에서는 "단일" ALTER
ALTER TABLE tbl MODIFY COLUMN b BIGINT NOT NULL UNIQUE;
-- 내부 구현이 "UNIQUE(b) 인덱스 삭제 -> 컬럼 타입 변경 -> UNIQUE(b) 인덱스 재생성" 순서로
-- 처리한다면, "인덱스 삭제" 단계에서 §4-2의 "복제키 후보 0개" 상태를 잠깐 거친다.
-- 이 문장이 예시 15(복제키 후보 유일한 UK 삭제 금지)에 걸려 ERROR가 나야 하는가,
-- 아니면 "최종 상태 기준"으로 판단해 OK가 되어야 하는가?
```

**예제 설명**: 사용자는 예시 15의 규칙(유일한 RK 후보인 UK를 삭제할 수 없다)이 자신의 "타입만
바꾸는" 요청에 왜 적용되는지 모른 채 에러를 받을 수 있다. 반대로 엔진이 이를 허용하려면 "이
문장은 최종 상태만 보고 판단한다"는 원칙이 §4-2에 명시되어 있어야 하는데, 현재는 없다.

**제안**: §4-2에 "단일 ALTER 문이 내부적으로 여러 단계를 거치더라도, RK 후보 판정은 문장 실행
전/후의 최종 상태만 비교한다"는 원칙을 명시해, 명시적 다중 절(1차 리뷰 3)과 암묵적 다단계 구현
(이 리뷰) 모두를 하나의 규칙으로 커버해야 한다.

### 리뷰 30

**[심각도: 보통] loaddb 시 RK 후보가 전혀 없는 복제 테이블을 만났을 때 "자동 할당"이 불가능한 경우의 처리가 없다**

**대상**: §8 "복제 테이블의 경우 큐브리드는 자동으로 RK를 할당한다"

**문제 설명**: 이 문장은 마치 RK가 항상 성공적으로 자동 할당되는 것처럼 들리지만, 그 전제는
"테이블에 PK나 UK 후보가 하나라도 있다"는 것이다. 언로드된 스키마 파일이 REPLICATION=ON이면서
PK/UK가 하나도 없는 테이블 정의를 담고 있을 수 있다(예: 애초에 싱글 모드에서 §3 규칙에 따라
그렇게 만들어진 테이블). 이 경우 loaddb는 "자동으로 할당"할 RK 후보 자체가 없으므로, 이 문장을
문자 그대로 구현하면 무엇을 해야 할지 정의되지 않는다.

**구체 예제**:
```
# 원본 스키마 파일에 다음 정의가 있다고 가정 (싱글 모드에서 생성된, RK 후보 없는 ON 테이블)
CREATE TABLE no_rk_tbl (a INT) REPLICATION = ON;

loaddb -d schema_file -u data_file targetdb
# no_rk_tbl 생성 시 §8 "자동으로 RK를 할당한다"를 적용하려 해도 할당할 PK/UK 후보가 없다.
# (1) loaddb 자체를 실패시키는가?
# (2) 경고만 내고 RK 없는 상태로 테이블을 만드는가(§7에서 나중에 걸림)?
# (3) 자동으로 REPLICATION=OFF로 강등시키는가?
```

**예제 설명**: §8은 "복제 여부를 저장하는 변수가 없으면 ON으로 간주"만 다룰 뿐, "ON인데 RK 후보가
없는 상태"를 loaddb가 어떻게 처리할지는 침묵한다. 이 상태 자체는 §3에 따르면 싱글 모드에서는
합법적이므로 loaddb가 실패해서는 안 될 수도 있지만, 그렇다고 "자동 할당"이라는 표현이 실제로
무엇을 하는지는 알 수 없다.

**제안**: §8에 "RK 후보가 없는 ON 테이블을 loaddb할 경우의 동작(허용 후 §7에서 걸리도록 둔다/경고
출력)"을 명시적으로 추가한다.

### 리뷰 31

**[심각도: 사소] §3의 "전환 시 변경할 수 있어야 한다"와 §7의 "재시작 전에 고쳐야 한다"가 시점 표현에서 어긋난다**

**대상**: §3, §7

**문제 설명**: §3은 "싱글 모드에서 생성된 복제 키가 없는 테이블은 HA모드 전환 시 복제 키를
추가하거나 복제 제외 테이블로 변경할 수 있어야한다"고 해서, 마치 "HA로 전환하는 그 순간에" 고칠
수 있는 것처럼 읽힌다. 반면 §7은 "이 경우 싱글모드에서 ALTER TABLE… 을 이용해 복제 키에 해당하는
제약을 추가하거나 복제 제외 대상으로 변경한 후 HA를 재시작해야한다"고 해서, 고치는 시점이 "전환
시도가 실패한 뒤, 싱글 모드로 남아 있는 동안"임을 분명히 한다. 두 절을 따로 읽으면 §3은 "전환
도중 고칠 수 있는 기능"을 암시하고, §7은 "전환은 그냥 실패하고 사전에 고쳐야 한다"는 다른 그림을
준다.

**구체 예제**:
```
-- §3만 읽은 사용자의 기대
$ cubrid hb start mydb
(RK 없는 테이블 발견 -> 대화형으로 고칠 기회를 준다?)

-- §7이 실제로 규정하는 동작
$ cubrid hb start mydb
ERROR: ... (파일 리스트)
$ # 사용자는 반드시 싱글 모드로 있는 상태에서 별도로 ALTER TABLE 실행 후 재시도해야 한다
```

**예제 설명**: 이 자체는 치명적인 기술적 결함이라기보다 문서 두 절이 같은 절차를 다른 시점의
그림으로 설명하는 표현상 불일치다. 그러나 매뉴얼화·QA 테스트케이스 작성 시 "전환 실패 시 즉시
인터랙티브하게 고칠 수 있는 기능이 있는가"를 놓고 오해가 생길 수 있다.

**제안**: §3의 "전환 시"라는 표현을 "전환 시도가 거부되었을 때, 싱글 모드로 되돌아가"처럼 §7과
동일한 시점 표현으로 통일한다.
