# CUBRID HA 복제 개선 스펙 리뷰 — DB 엔진 개발자 (3년차) 관점

## 리뷰어 소개

CUBRID 엔진 코드(특히 복제 모듈 applylogdb, 카탈로그, DDL 처리 경로)를 3년째 다루고 있는 개발자다. 트랜잭션 로그를 읽어 슬레이브에 적용하는 코드와 unloaddb/loaddb 유틸리티 코드를 실제로 만져본 경험을 기준으로, "이 스펙대로 구현하면 어디서 코드가 막히는가", "어떤 입력值에서 정의되지 않은 동작이 나오는가"를 따진다. 신입만큼 기초 개념을 처음부터 설명하되, 5~10년차만큼 아키텍처 전체를 재설계하지는 않고 지금 스펙 문장이 구현 가능한 수준으로 구체적인지에 집중했다.

## 총평

이 스펙은 "복제 키(RK)를 PK 또는 UK 중 하나로 엔진이 자동 선택한다"는 컨셉 자체는 PostgreSQL REPLICA IDENTITY의 취지를 잘 요약하고 있지만, 정작 구현자가 코드를 짤 때 마주치는 결정적 순간들 — RK가 바뀌는 트랜지션 구간, 다중 절 ALTER의 원자성, unloaddb 하위 호환, 파티션/트리거/시리얼 같은 스펙이 아예 언급하지 않은 객체 — 에 대한 규정이 비어 있다. 예시 문장 다수는 "OK / ERROR" 결과만 보여줄 뿐 그 사이에 카탈로그와 복제 로그에 무슨 일이 일어나는지는 설명하지 않는다. 실무적으로도 컬럼 타입 변경이나 인덱스 재구성처럼 하루에도 몇 번씩 나오는 DDL 패턴이 이 스펙 하에서 어떻게 되는지 명시가 없어, 구현팀이 스펙 문서만 보고 코드를 짜면 각자 다른 동작을 만들어낼 위험이 크다. 아래 20개 항목은 컨셉 수준의 결함부터 절별 세부 모순, 예제 오탈자까지 심각도순으로 나열했다.

## 리뷰 1

**[심각도: 치명] RK 자동 선택 규칙의 "가장 빠른 순서"가 결정적이지 않다**

**대상**: §1 제약 사항 — "UK가 여러개 존재한다면 큐브리드 엔진에 의해 이 중 하나가 선택된다(ex. 테이블내에 명시된 순서 중 가장 빠른 순서)"

**문제 설명**: 복제(replication)란 마스터에서 일어난 데이터 변경을 슬레이브(대기계)에 그대로 재현하는 것을 말한다. 이때 마스터와 슬레이브가 "어느 컬럼 조합으로 행(row)을 식별할지"에 대해 서로 다른 결론을 내리면, 슬레이브가 엉뚱한 행을 갱신하거나 삭제하는 대형 사고로 이어진다. 그런데 스펙은 "테이블 내에 명시된 순서 중 가장 빠른 순서"라는 표현만 쓰고, 이것이 (a) `CREATE TABLE` 문에 UK 제약이 텍스트로 등장한 순서인지, (b) 카탈로그에 저장된 내부 OID/생성 순서인지, (c) ALTER로 UK를 추가/삭제한 히스토리를 반영한 "현재 시점 정렬 순서"인지 전혀 정의하지 않는다. 카탈로그 내부 저장 순서는 unloaddb/loaddb, 리빌드, 버전 업그레이드 과정에서 재정렬될 수 있는 값이라 "안정적인 순서 키"로 쓰기에 위험하다.

**구체 예제**:
```sql
CREATE TABLE t (
    a INT NOT NULL UNIQUE,
    b INT NOT NULL UNIQUE
);
-- 이 시점 RK는 스펙대로라면 a(먼저 명시됨)

ALTER TABLE t DROP CONSTRAINT u_t_a;   -- a의 UK 제거
ALTER TABLE t ADD CONSTRAINT UNIQUE(a); -- a에 새 UK 다시 추가

-- 이제 "명시된 순서"로 보면 b가 a보다 먼저 만들어진 UK다.
-- RK가 a에서 b로 자동으로 바뀌는가?
```

**예제 설명**: 위 시나리오는 컬럼을 하나 뺐다가 그대로 다시 추가했을 뿐인데, "명시된 순서"의 정의에 따라 RK가 조용히 a→b로 바뀔 수 있는지를 보여준다. RK가 바뀐다는 것은 이전에 만들어진 복제 로그의 키 필드 해석이 통째로 달라진다는 뜻이다. 사용자는 아무 것도 잘못한 게 없는데 내부적으로 RK가 뒤바뀌면, 그 순간 이후의 복제 로그와 이전 로그가 서로 다른 키 기준을 갖게 되어 슬레이브 쪽 인덱스 매칭이 깨질 수 있다.

**제안**: RK 선택 규칙을 카탈로그 내부 안정적 식별자(예: 제약조건 생성 시 부여되는 단조 증가 ID) 기준으로 명문화하고, ALTER로 후보가 추가/삭제되어도 "이미 RK로 선택된 것은 다른 후보가 생겨도 재선택하지 않는다(sticky)"는 규칙을 명시해야 한다. 지금 스펙은 그 부분이 완전히 비어 있다.

## 리뷰 2

**[심각도: 치명] 다중 절 ALTER(예시 13)의 원자성이 명시되지 않았다**

**대상**: §4-2 예시 13 "PK 를 다른 컬럼으로 변경" — `ALTER TABLE table_name DROP CONSTRAINT PRIMARY KEY, ADD CONSTRAINT PRIMARY KEY(a);`

**문제 설명**: 원자성(atomicity)이란 여러 단계로 이루어진 작업이 "전부 성공" 아니면 "전부 실패"로만 끝나고, 중간 상태가 외부에 보이지 않아야 한다는 성질이다. 이 예시는 "PK 제거"와 "새 PK 추가"를 한 문장에 담아 "OK"라고만 결과를 보여주는데, 카탈로그 내부적으로 이 두 단계 사이에 순간적으로 RK 후보가 0개인 상태(구 PK는 이미 지워졌고 신 PK는 아직 안 만들어진 상태)를 거치는지, 아니면 하나의 스키마 변경 트랜잭션 안에서 원자적으로 처리되는지 스펙에 아무 언급이 없다. HA 모드에서 RK가 0개인 테이블은 §4-1에 따르면 존재해서는 안 되는 상태이므로, 이 중간 상태를 다른 세션이 관측하거나 그 사이에 DML이 끼어들면 어떤 일이 일어나는지가 구현의 핵심 쟁점이다.

**구체 예제**:
```sql
-- 세션 A
ALTER TABLE tbl DROP CONSTRAINT PRIMARY KEY, ADD CONSTRAINT PRIMARY KEY(a);

-- 정확히 같은 순간, 세션 B (별도 커넥션)
UPDATE tbl SET c = c + 1 WHERE b = 3;
```

**예제 설명**: 세션 B의 UPDATE가 세션 A의 두 절(DROP, ADD) 사이 타이밍에 끼어들면, 그 UPDATE에 대한 복제 로그는 "RK가 없는" 순간에 기록되는 것인지, 옛 PK 기준으로 기록되는 것인지, 새 PK 기준으로 기록되는 것인지가 정의되어 있지 않다. 이는 곧 슬레이브가 이 UPDATE를 적용할 때 어떤 키로 대상 행을 찾을지 모르는 상황으로 이어진다.

**제안**: "복제키를 변경하는 ALTER는 카탈로그 갱신과 함께 단일 스키마 잠금(schema lock) 구간 안에서 원자적으로 처리되며, 그 구간 동안 해당 테이블에 대한 DML은 대기한다"는 문장을 명시해야 한다. 그렇지 않으면 이 스펙은 "무엇을 구현해야 하는지"가 아니라 "성공했을 때의 결과"만 적어놓은 것이다.

## 리뷰 3

**[심각도: 치명] RK 전환 시점에 이미 만들어진 복제 로그와의 정합성 문제**

**대상**: §4-2 전체 (예시 11~16), applylogdb 동작(작업지시 배경)

**문제 설명**: applylogdb는 마스터의 트랜잭션 로그를 읽어 슬레이브에 재생하는 프로세스인데, 마스터 로그 기록 시점과 슬레이브 적용 시점 사이에는 항상 지연(lag)이 있다. RK가 PK에서 다른 UK로 바뀌는 ALTER가 마스터에서 커밋된 순간, 그 이전에 기록되었지만 아직 슬레이브에 적용되지 않은 로그 레코드들은 "옛 RK" 기준으로 기록되어 있다. 슬레이브가 이 지연된 로그들을 처리하는 도중에 ALTER 로그를 만나면, 그 시점 이후의 로그는 새 RK를 기대해야 하는데 기존 미적용 로그 큐에는 옛 RK 기준 레코드가 섞여 있을 수 있다. 스펙은 이 트랜지션 구간의 로그 포맷/처리 순서를 전혀 다루지 않는다.

**구체 예제**:
```
[마스터 타임라인]
t1: UPDATE tbl SET x=1 WHERE a=10;   -- RK=PK(a) 기준으로 로그 기록
t2: ALTER TABLE tbl DROP CONSTRAINT PRIMARY KEY, ADD CONSTRAINT PRIMARY KEY(b);
t3: UPDATE tbl SET x=2 WHERE b=20;   -- RK=PK(b) 기준으로 로그 기록

[슬레이브: applylogdb 지연으로 t1 처리 중 커밋 랙 발생]
t1 로그 적용 시도 -> 이 시점 슬레이브 카탈로그는 아직 옛 RK(a)인가 새 RK(b)인가?
```

**예제 설명**: applylogdb는 로그를 순서대로(commit LSA 순서) 적용해야 하므로 t1, t2, t3를 이 순서로 처리해야 정확하다. 그런데 스펙은 ALTER(t2)가 로그 스트림 안에서 어떤 형태로 표현되는지, 그리고 그 ALTER 로그가 적용된 순간부터 이후 DML 로그의 키 해석이 바뀐다는 규약을 명시하지 않는다. 병렬 적용(현재 사내에서 논의 중인 applylogdb 병렬화)까지 고려하면 이 순서 보장은 더욱 취약해진다.

**제안**: "RK를 변경하는 DDL 로그 레코드는 그 이전/이후의 DML 로그와 순서가 뒤섞이지 않는 배리어(barrier)로 취급한다"는 규칙을 스펙에 명시하고, 그 배리어가 병렬 적용 경로에서도 강제되는지 별도로 규정해야 한다.

## 리뷰 4

**[심각도: 중요] RK 변경 DDL과 동시 DML의 락(lock) 범위가 정의되지 않았다**

**대상**: §4-2, 작업지시 배경 3항 "동시 DDL/DML 경합"

**문제 설명**: 락이란 여러 세션이 같은 데이터에 동시에 접근할 때 순서를 강제해 일관성을 지키는 장치다. 이 스펙의 모든 ALTER 예시는 단일 세션·단일 문장 기준으로만 결과(OK/ERROR)를 보여준다. 하지만 실제 운영 환경에서는 RK를 바꾸는 DDL이 실행되는 동안에도 다른 트랜잭션이 해당 테이블에 INSERT/UPDATE/DELETE를 계속 시도한다. 이 DML들이 DDL과 어떤 락 레벨로 직렬화되는지, DDL이 스키마 잠금을 못 얻어 대기하다 타임아웃되는지, 아니면 DML이 밀려나는지 스펙에 없다.

**구체 예제**:
```sql
-- 세션 A: 장기 실행 트랜잭션
BEGIN;
UPDATE tbl SET c = 1 WHERE a = 5;
-- 커밋하지 않고 대기

-- 세션 B: 같은 시각 RK 변경 시도
ALTER TABLE tbl DROP CONSTRAINT PRIMARY KEY, ADD CONSTRAINT PRIMARY KEY(b);
```

**예제 설명**: 세션 A가 PK(a)로 식별되는 행을 잠근 채 커밋하지 않고 있을 때, 세션 B가 그 PK 자체를 제거하려 한다. 세션 A의 트랜잭션이 커밋되기 전까지 세션 B는 블록되어야 정상이지만, 스펙에는 "RK 변경은 해당 테이블에 대한 배타적 스키마 잠금을 요구하며 진행 중인 트랜잭션 커밋을 기다린다"는 문장이 없다. 이 부분이 비어 있으면 구현자마다 낙관적/비관적 락 전략을 다르게 선택할 수 있고, 그 결과 배포마다 동시성 동작이 달라진다.

**제안**: RK 변경 DDL의 락 레벨(테이블 단위 배타 잠금 여부)과 대기 중인 DML/트랜잭션과의 우선순위 규칙을 §4-2에 명시해야 한다.

## 리뷰 5

**[심각도: 중요] 카탈로그 스키마 변경(예시 9의 `replication` 컬럼)에 대한 마이그레이션 규정 없음**

**대상**: §2-3 예시 9 — `db_class` 조회 결과에 `replication: ON` 필드 추가

**문제 설명**: 카탈로그란 테이블/컬럼/제약조건 등 스키마 정보 자체를 저장하는 시스템 내부 테이블들을 말한다. 이 스펙은 `db_class`(시스템 카탈로그의 하나)에 `replication`이라는 새 컬럼이 추가된다는 것을 예시로 보여주지만, 기존 버전에서 업그레이드하는 경로에서 이 컬럼이 언제·어떻게 채워지는지(카탈로그 마이그레이션 스크립트, 기본값 결정 시점)를 규정하지 않는다. §8은 unloaddb/loaddb 관점의 하위 호환만 다루고, in-place 업그레이드(같은 DB 볼륨을 그대로 새 버전 엔진으로 여는 경우)에 대해서는 전혀 언급이 없다.

**구체 예제**:
```
[시나리오]
1. 구버전(REPLICATION 옵션 없음) CUBRID로 만든 DB 볼륨이 있다.
2. 새 버전 엔진 바이너리로 그대로 기동한다 (unloaddb/loaddb를 거치지 않음).
3. select * from db_class; 를 실행한다.
   -> replication 컬럼 값은 무엇인가? ON? NULL? 컬럼 자체가 없어 에러?
```

**예제 설명**: unloaddb 경로(§8)는 "복제 여부를 저장하는 변수가 없으면 복제 대상(Default)"이라고 명시했지만, 이는 텍스트 언로드 파일 포맷 얘기다. 실제로 운영에서 더 흔한 것은 볼륨을 그대로 두고 엔진만 업그레이드하는 in-place 방식인데, 이 경로에서 카탈로그 스키마 자체(`db_class` 테이블 구조)를 어떻게 마이그레이션할지가 스펙에서 빠졌다.

**제안**: in-place 업그레이드 시 카탈로그 스키마 버전업 절차와, 기존 테이블들에 대해 `replication` 값을 채우는 기본 규칙(모두 ON으로 간주하되 RK 없는 테이블은 예외 처리하는 방식 등)을 별도 절로 추가해야 한다.

## 리뷰 6

**[심각도: 치명] unloaddb/loaddb 하위 호환 규칙이 §4-1과 정면으로 충돌할 수 있다**

**대상**: §8 UNLOADDB & LOADDB — "복제 테이블의 경우 큐브리드는 자동으로 RK를 할당한다", "하위 버전에서 unload 한 데이터 파일에는 복제 여부를 저장하는 변수가 설정되어있지 않으므로 (싱글 모드에서) load 시 모두 복제 테이블로 설정된다"

**문제 설명**: 이 두 문장을 §4-1("HA 모드에서는 CREATE TABLE 시 복제키가 없는 복제 테이블을 생성할 수 없다")과 겹쳐 읽으면 모순이 드러난다. "자동으로 RK를 할당한다"는 표현은 마치 엔진이 없던 PK/UK를 새로 만들어낼 수 있는 것처럼 읽히지만, RK는 §1에 따르면 "기존 PK 또는 UK 중에서 선택"하는 것이지 없는 것을 만들어내는 게 아니다. 그렇다면 로드하는 테이블에 애초에 PK/UK가 하나도 없다면 "자동 할당"할 RK 후보 자체가 없다. 게다가 "하위 버전 unload 파일은 (싱글 모드에서) load 시 모두 복제 테이블로 설정된다"는 문장은 싱글 모드로 한정되어 있어, HA 모드에서 구버전 unload 파일을 loaddb 하면 어떻게 되는지가 완전히 빠져 있다.

**구체 예제**:
```
[시나리오]
1. 구버전(REPLICATION 개념 없음) CUBRID에서 PK가 없는 테이블 legacy_tbl을 unloaddb로 언로드한다.
2. 신버전 CUBRID를 HA 모드("cubrid hb start")로 이미 기동한 상태에서 loaddb로 legacy_tbl을 적재한다.

$ loaddb -d mydb legacy_tbl.data
```

**예제 설명**: §8 문장을 그대로 따르면 "복제 여부 변수가 없으므로 복제 대상(Default)"이 되어 legacy_tbl은 REPLICATION=ON으로 생성되어야 한다. 그런데 legacy_tbl은 PK/UK가 없으므로 RK 후보가 없고, §4-1에 따르면 HA 모드에서 RK 없는 복제 테이블은 생성될 수 없어 에러가 나야 한다. 결국 이 loaddb 명령이 "OK(복제 대상으로 로드됨)"인지 "ERROR(RK 없음)"인지 스펙만 봐서는 알 수 없다. 게다가 하위 호환 문장은 "싱글 모드에서 load 시"라고 조건을 달아놓아, HA 모드에서의 동작은 정의역 밖에 있다.

**제안**: loaddb 동작을 (a) 언로드 파일에 복제 여부 변수가 있는 경우, (b) 없는 경우 × (i) 싱글/SA 모드, (ii) HA 모드의 2x2 매트릭스로 전부 명시하고, RK 후보가 없는 경우의 에러 처리(로드 실패, 혹은 자동으로 REPLICATION=OFF로 강등)를 결정해야 한다.

## 리뷰 7

**[심각도: 중요] 파티션 테이블이 스펙에서 완전히 누락되었다**

**대상**: 스펙 전체 (§1~§9에 "파티션" 언급 0회)

**문제 설명**: 파티션 테이블은 하나의 논리 테이블을 여러 물리 파티션으로 나눠 저장하는 기능이다(예시 9의 `db_class` 조회 결과에도 `partitioned` 필드가 이미 존재하는 것으로 보아 엔진이 이 개념을 알고 있다). CUBRID의 파티션 테이블은 부모 테이블과 자식 파티션이 카탈로그 상 별도 엔트리를 갖는 구조인데, RK와 REPLICATION 옵션이 부모 단위로만 적용되는지, 자식 파티션 각각에도 독립적으로 적용될 수 있는지 스펙이 전혀 정의하지 않는다.

**구체 예제**:
```sql
CREATE TABLE sales (
    sale_id INT PRIMARY KEY,
    sale_date DATE,
    amount INT
) PARTITION BY RANGE (sale_date) (
    PARTITION p2025 VALUES LESS THAN (DATE'2026-01-01'),
    PARTITION p2026 VALUES LESS THAN (DATE'2027-01-01')
);

ALTER TABLE sales REPLICATION = OFF;
-- 이 REPLICATION=OFF는 p2025, p2026 파티션에도 각각 적용되는가?
-- 특정 파티션만 REPLICATION=OFF로 만드는 것은 애초에 불가능한가?
```

**예제 설명**: 파티션 단위로 복제 여부를 나누고 싶은 요구(예: 오래된 파티션은 복제 제외, 최신 파티션만 복제)가 실무에서 흔히 나올 수 있는데, 스펙은 이런 세분화가 가능한지 아예 언급하지 않는다. 또한 파티션 프루닝(partition pruning, 조건에 맞는 파티션만 골라 처리하는 최적화)이 적용된 DML의 복제 로그가 부모 테이블 RK 기준으로 기록되는지 자식 파티션 RK 기준인지도 불명이다.

**제안**: 파티션 테이블에 대해 REPLICATION 옵션과 RK 선택이 부모 레벨에서만 유효하고 자식 파티션은 부모를 그대로 상속한다는 식으로 명시적으로 범위를 제한하거나, 세분화를 허용한다면 그 규칙을 별도 절로 추가해야 한다.

## 리뷰 8

**[심각도: 보통] 트리거가 REPLICATION=OFF 테이블을 갱신하는 경우의 복제 동작 미정의**

**대상**: 스펙 전체 (트리거 언급 없음), §6 뷰(VIEW) 절과 유사한 성격의 누락

**문제 설명**: 트리거는 특정 테이블에 DML이 발생했을 때 자동으로 실행되는 절차를 말한다. CUBRID의 복제는 로그 기반(트랜잭션 로그를 읽어 재생)이므로, 트리거가 만들어낸 부가 변경(예: 감사 로그 테이블에 INSERT)도 결과적으로 로그에 남아 복제 대상이 될 수 있다. 그런데 트리거가 REPLICATION=ON 테이블에 걸려 있고 그 트리거 본문이 REPLICATION=OFF 테이블을 갱신하는 경우, 혹은 반대로 OFF 테이블의 트리거가 ON 테이블을 갱신하는 경우 각각 어떤 데이터가 슬레이브에 반영되는지 스펙에 규정이 없다. §6에서 뷰에 대해 "복제 제외 테이블이 포함되면 결과가 불일치할 수 있고 책임지지 않는다"고 명시한 것과 동일한 논리를 트리거에도 적용해야 하는데 빠져 있다.

**구체 예제**:
```sql
CREATE TABLE audit_log (
    id INT PRIMARY KEY,
    msg VARCHAR(100)
) REPLICATION = OFF;

CREATE TABLE orders (
    order_id INT PRIMARY KEY,
    status VARCHAR(20)
) REPLICATION = ON;

CREATE TRIGGER trg_order_update
AFTER UPDATE ON orders
EXECUTE INSERT INTO audit_log VALUES (..., 'order updated');

-- Failover 후 슬레이브에서 orders.status 갱신 이력은 남지만
-- audit_log는 비어 있다. 이게 "책임지지 않는" 범위에 포함되는지 스펙에 없음.
```

**예제 설명**: 이 예시는 뷰에서 이미 인정한 "REPLICATION=OFF 테이블이 섞이면 결과가 갈라진다"는 문제가 트리거 체인에서도 똑같이 발생함을 보여준다. 뷰는 명시적으로 절이 있지만 트리거는 언급조차 없어, 구현팀이 "트리거는 신경 안 써도 된다"고 오해할 소지가 있다.

**제안**: §6과 동일한 취지의 면책 조항을 트리거에도 명시적으로 추가하거나, 최소한 "본 스펙은 트리거로 인한 연쇄 변경의 복제 일관성을 보장하지 않는다"는 한 문장을 §9 SUMMARY에 넣어야 한다.

## 리뷰 9

**[심각도: 보통] 시리얼(SERIAL/AUTO_INCREMENT) 컬럼이 RK의 일부일 때 시퀀스 동기화 문제 미언급**

**대상**: 스펙 전체 (시리얼 언급 없음), §1 RK 정의

**문제 설명**: 시리얼(다른 DBMS의 AUTO_INCREMENT에 해당)은 새 행이 삽입될 때 엔진이 자동으로 증가하는 값을 채워주는 컬럼 속성이다. RK로 선택되는 PK/UK 컬럼에 시리얼이 걸려 있는 경우가 실무에서 매우 흔하다(예시 8, 9의 `tbl(a INTEGER NOT NULL, ... PRIMARY KEY(a))`도 실무에서는 보통 시리얼로 채워진다). 시리얼 값 자체는 마스터에서 슬레이브로 시퀀스 상태를 동기화해야 failover 후에도 값 충돌이 없는데, 이 스펙은 REPLICATION=OFF였던 테이블을 나중에 ON으로 전환할 때 그 테이블의 시리얼 현재값이 슬레이브에 어떻게 동기화되는지 다루지 않는다.

**구체 예제**:
```sql
CREATE TABLE t (
    id INT AUTO_INCREMENT PRIMARY KEY,
    v INT
) REPLICATION = OFF;

-- OFF 상태에서 대량 INSERT, id는 1~100000까지 증가 (슬레이브엔 아무것도 없음)
ALTER TABLE t REPLICATION = ON;
-- 이 시점 이후 마스터에서 INSERT하면 id는 100001부터 계속되지만
-- 슬레이브 t 테이블은 텅 비어 있다가 갑자기 100001부터 데이터가 들어옴.
-- 시리얼 카운터 자체가 슬레이브에도 100000으로 맞춰져 있는가?
```

**예제 설명**: 이 시나리오는 REPLICATION 전환이 데이터뿐 아니라 시퀀스 발생기 상태처럼 "테이블에 딸려 있지만 행 데이터는 아닌" 부가 상태에도 영향을 준다는 것을 보여준다. failover가 이 전환 직후에 일어나면 애플리케이션이 새 마스터(구 슬레이브)에서 시리얼 값을 다시 1부터 채번할 위험도 있다.

**제안**: REPLICATION OFF→ON 전환 시 해당 테이블이 참조하는 시리얼 객체의 현재값도 슬레이브로 동기화하는 절차를 명시해야 한다.

## 리뷰 10

**[심각도: 사소] 예시 2, 20, 23의 컬럼 목록에 불필요한 trailing comma로 인한 문법 오류**

**대상**: §2-1 예시 2, §5-2 예시 20/23

**문제 설명**: 다음은 스펙 원문 그대로다.
```sql
CREATE TABLE repl_table_without_rk(
    a INT,
);
```
컬럼이 `a INT` 하나뿐인데 그 뒤에 쉼표(,)가 붙어 있다. SQL 문법상 쉼표 뒤에는 다음 컬럼 정의가 와야 하므로, 이 문장을 CUBRID csql에 그대로 입력하면 문법 오류(syntax error)가 나서 애초에 "복제키가 존재하지 않는 테이블을 생성"하는 예시 자체가 실행되지 않는다. 같은 실수가 §5-2 예시 20("customer_id INT FOREIGN KEY REFERENCES customers(customer_id))")의 앞 CREATE 문과 예시 23에도 반복된다.

**구체 예제**:
```sql
-- 스펙 원문 (오류)
CREATE TABLE repl_table_without_rk(
    a INT,
);

-- 실제로 실행 가능한 형태
CREATE TABLE repl_table_without_rk(
    a INT
);
```

**예제 설명**: 이 예시는 스펙 문서가 실제로 csql에 붙여넣어 검증된 적이 없다는 정황 증거다. 신입 개발자나 QA가 이 스펙을 보고 회귀 테스트 스크립트를 그대로 옮겨 적으면 "복제키 없는 테이블 생성 시도"라는 테스트 케이스 자체가 문법 오류로 실패해, 정작 확인하려던 동작(생성 성공 여부)을 검증하지 못한다.

**제안**: 스펙에 실린 모든 SQL 예시를 실제 csql에 한 번씩 실행해보고 결과를 캡처해 문서에 반영해야 한다. 단순 트레일링 콤마 수정만으로 해결된다.

## 리뷰 11

**[심각도: 보통] 컬럼 레벨 FOREIGN KEY 인라인 문법(예시 20, 23)이 실제 지원되는 문법인지 의심스럽다**

**대상**: §5-2 예시 20, 23 — `ADD COLUMN (customer_id INT FOREIGN KEY REFERENCES customers(customer_id))`

**문제 설명**: 일반적으로 SQL 표준 및 CUBRID 문법에서 컬럼 정의에 인라인으로 참조 제약을 걸 때는 `REFERENCES` 절만 쓰고(`customer_id INT REFERENCES customers(customer_id)`), `FOREIGN KEY` 키워드는 테이블 레벨 제약(`CONSTRAINT ... FOREIGN KEY (col) REFERENCES ...`)에서 쓰는 것이 관례다. 스펙 예시처럼 컬럼 정의 안에 `FOREIGN KEY` 키워드까지 함께 쓰는 문법이 실제 CUBRID 파서에 존재하는지 스펙만으로는 확인할 수 없고, 오히려 오탈자로 보인다(예시 17, 19는 정상적으로 `CONSTRAINT fk_... FOREIGN KEY (...) REFERENCES ...` 형태를 쓰고 있어 같은 문서 안에서 문법 표기가 일관되지 않는다).

**구체 예제**:
```sql
-- 예시 20 원문 (의심스러운 문법)
ALTER TABLE new_orders ADD COLUMN
(customer_id INT FOREIGN KEY REFERENCES customers(customer_id));

-- 예시 17/19와 일관된 표기라면
ALTER TABLE new_orders ADD COLUMN
(customer_id INT REFERENCES customers(customer_id));
```

**예제 설명**: 같은 스펙 문서 안에서 외래키를 표현하는 두 가지 다른 문법이 섞여 있다는 것 자체가 검증되지 않은 문서라는 신호다. 이 문법이 실제로 파서에서 통과하지 않는다면, 예시 20/23이 보여주려던 "복제 제외 테이블을 참조하는 컬럼 추가는 에러"라는 결론이 진짜 REPLICATION 로직 때문에 ERROR가 나는 것인지, 그냥 문법 오류로 ERROR가 나는 것인지 독자가 구분할 수 없다.

**제안**: 예시 20, 23의 문법을 예시 17, 19와 통일하고, 실제 csql 실행 결과를 캡처해 검증한 뒤 반영해야 한다.

## 리뷰 12

**[심각도: 중요] "복제키 후보"라는 용어의 정의 누락으로 §4-2 규칙 적용 범위가 불명확하다**

**대상**: §4-2 "복제키 후보가 1개인 경우(= 복제키) 제약사항은 다음과 같다", 예시 11~16

**문제 설명**: §4-2는 "복제키 후보가 1개인 경우"와 "다른 복제키 후보가 함께 존재하는 경우"를 나눠 규칙을 다르게 적용한다고 선언하지만, "복제키 후보"가 정확히 무엇을 세는 단위인지 정의하지 않는다. PK 1개 + NOT NULL UK 1개가 공존하면 "후보 2개"로 보아 이 UK를 제거해도 되는지, 아니면 PK가 이미 RK로 확정된 이상 PK만 "진짜" 후보이고 UK는 "잠재 후보"로 별도 취급해야 하는지 예시 11~16만으로는 판단할 수 없다. 이 구분이 흐릿하면 예시 12("PK가 복제키로 사용될 경우 이 PK는 삭제할 수 없다")가 "PK 외에 다른 UK가 하나라도 있어도 무조건 금지"인지 "다른 후보가 없을 때만 금지"인지 모호해진다.

**구체 예제**:
```sql
CREATE TABLE tbl (
    a INT PRIMARY KEY,
    b INT NOT NULL UNIQUE,
    c INT
);
-- RK = PK(a). 이 테이블은 "복제키 후보 1개"인가 "2개"인가?

ALTER TABLE tbl DROP PRIMARY KEY;
-- 예시 12에 따르면 "PK가 복제키로 사용될 경우 삭제 불가"이므로 ERROR가 나야 할 것 같지만,
-- b라는 NOT NULL UNIQUE 후보가 남아있으므로 §4-2 서문의
-- "다른 복제키 후보가 함께 존재한다면 모든 DDL은 허용된다"를 적용하면 OK여야 한다.
```

**예제 설명**: 위 예제는 §4-2의 서문 규칙과 예시 12를 나란히 놓았을 때 서로 다른 결론이 나올 수 있음을 보여준다. 서문만 읽으면 "PK 외에 UK b가 있으니 DROP PRIMARY KEY는 허용"이라고 해석되지만, 예시 12는 조건 없이 "PK가 복제키로 사용될 경우 삭제할 수 없다"고 단정한다. 이 두 문장이 같은 상황을 가리키는지, 예시 12가 "후보가 정말 1개뿐인 경우"만을 전제한 것인지 스펙에는 구분할 근거가 없다.

**제안**: "복제키 후보"를 "RK 선택 규칙(§1)에 의해 RK가 될 자격이 있는 PK/NOT NULL UK 제약의 개수"로 명확히 정의하고, 예시 11~16 각각에 그 테이블이 후보를 몇 개 갖고 있다고 가정하는지 전제 조건을 표기해야 한다.

## 리뷰 13

**[심각도: 보통] FK 참조 무결성 검사의 강제성(MUST/MAY)이 불명확하고 순환/자기참조 FK가 다뤄지지 않았다**

**대상**: §5 외래키 — "복제 제외 테이블을 참조할 경우 에러를 출력할 수 있어야한다"

**문제 설명**: "출력할 수 있어야한다"는 표현은 능력(구현 가능해야 한다)을 말하는 것인지, 반드시 그래야 한다는 의무(MUST)인지 국어적으로 모호하다. 스펙 전체에서 유사한 제약(§4-1, §4-2)은 전부 "ERROR"로 단정적으로 표기하는데 반해, 유독 §5의 이 문장만 "~할 수 있어야한다"는 완곡한 표현을 써서 강제 사항인지 권고 사항인지 헷갈린다. 또한 스펙은 A가 B를 참조하는 단순 FK만 예시로 들 뿐, 자기 자신을 참조하는 자기참조 FK(self-referencing FK, 예: 조직도 테이블의 상위 부서 컬럼)나 A→B, B→A로 서로 참조하는 순환 FK의 경우 REPLICATION 검사가 어떻게 이루어지는지 언급이 없다.

**구체 예제**:
```sql
CREATE TABLE employees (
    emp_id INT PRIMARY KEY,
    manager_id INT,
    CONSTRAINT fk_mgr FOREIGN KEY (manager_id) REFERENCES employees(emp_id)
) REPLICATION = OFF;

-- employees는 REPLICATION=OFF이면서 스스로를 참조한다.
-- §5의 "외래키 테이블에서 참조하는 모든 테이블은 복제 대상이여야한다"는
-- REPLICATION=ON 테이블에만 적용되는 규칙인데,
-- 이 테이블은 OFF이므로 규칙 적용 대상이 아니어서 문제없이 생성되는가?
-- 만약 나중에 REPLICATION=ON으로 바꾼다면 자기 자신을 참조 테이블로 보는가?
```

**예제 설명**: 자기참조 FK는 "참조 테이블 = 자기 자신"이라는 특수 케이스다. §5 규칙을 문자 그대로 적용하면 "자기 자신이 복제 대상인지" 검사해야 하는데, ALTER TABLE employees REPLICATION=ON 실행 시점에 이미 검사 중인 대상과 참조 대상이 동일 테이블이라 검사 로직이 자기 자신의 아직 반영되지 않은 상태를 봐야 하는 특수 처리가 필요할 수 있다. 스펙은 이런 경우를 고려하지 않았다.

**제안**: "출력할 수 있어야한다"를 "출력해야 한다"로 바꿔 강제 사항임을 명확히 하고, 자기참조·순환 참조 FK에 대한 검사 순서를 별도로 규정해야 한다.

## 리뷰 14

**[심각도: 중요] 복합(composite) PK/UK가 RK일 때 로그 포맷·성능 영향과 "순서" 기준이 불명확하다**

**대상**: §1 RK 선택 기준, 작업지시 배경 "복제 로그 포맷 영향"

**문제 설명**: 복합 키란 하나의 제약이 여러 컬럼으로 구성된 키를 말한다(예: `UNIQUE(col1, col2)`). RK가 복합 키로 선택되면 복제 로그에는 행을 식별하기 위해 여러 컬럼 값을 함께 기록해야 하므로, 단일 컬럼 RK 대비 로그 레코드 크기가 커지고 슬레이브에서 매칭 조건도 다중 컬럼 비교로 바뀐다. 스펙은 이 성능/포맷 영향을 전혀 언급하지 않을 뿐 아니라, "UK가 여러 개 존재한다면 가장 빠른 순서"라는 규칙이 단일 컬럼 UK와 복합 컬럼 UK가 섞여 있을 때 어느 것을 우선하는지도 정의하지 않는다.

**구체 예제**:
```sql
CREATE TABLE t (
    a INT NOT NULL,
    b INT NOT NULL,
    c INT NOT NULL,
    CONSTRAINT u1 UNIQUE (a, b),   -- 복합 UK, 먼저 명시됨
    CONSTRAINT u2 UNIQUE (c)       -- 단일 컬럼 UK, 나중에 명시됨
);
-- "명시된 순서 중 가장 빠른 순서" 규칙을 그대로 적용하면 RK = u1(a,b)가 된다.
-- 성능상으로는 단일 컬럼 u2(c)가 훨씬 가벼운 RK인데,
-- 스펙은 컬럼 개수/성능을 고려 대상에 넣지 않는다.
```

**예제 설명**: 이 예제는 "명시된 순서"라는 단순 규칙이 성능 관점에서 최악의 선택(복합 키를 RK로 선택)을 할 수 있음을 보여준다. MySQL 방식(전체 컬럼 사용)을 배제한 이유가 "성능"이라고 배경 문서에 명시했으면서, RK 선택 규칙 자체는 성능을 전혀 고려하지 않는 모순이 있다.

**제안**: RK 선택 우선순위에 "컬럼 개수가 적은 키를 우선한다"는 기준을 "명시된 순서"보다 앞에 추가하거나, 최소한 복합 키가 RK로 선택됐을 때의 로그 크기/성능 영향을 별도로 문서화해야 한다.

## 리뷰 15

**[심각도: 중요] RK로 쓰이던 UK 컬럼을 NULL 허용으로 바꾸는 ALTER가 §4-2 목록에서 빠졌다**

**대상**: §4-2 (예시 11~16), §1 "Not Null Unique Key"

**문제 설명**: RK 자격 조건 중 하나는 "NOT NULL"이다(§1). 그런데 §4-2는 UK를 아예 삭제하는 경우(예시 15)만 다루고, UK 제약은 그대로 둔 채 컬럼의 NULL 허용 여부만 바꾸는 `ALTER TABLE ... MODIFY`류의 DDL은 언급하지 않는다. NOT NULL 속성이 사라지면 그 UK는 더 이상 RK 자격 조건(NOT NULL UNIQUE)을 만족하지 못하게 되므로, 사실상 예시 15(UNIQUE 제약 삭제)와 동일한 효과를 갖는 엣지케이스인데 스펙에서 빠져 있다.

**구체 예제**:
```sql
CREATE TABLE tbl (
    a INT,
    b INT NOT NULL UNIQUE
);
-- PK가 없으므로 RK = UK(b)

ALTER TABLE tbl MODIFY COLUMN b INT NULL;
-- b의 UNIQUE 제약 자체는 그대로 있지만 NOT NULL이 사라졌다.
-- 이제 b는 §1 정의상 RK 자격(NOT NULL UNIQUE)을 잃는다.
-- 이 ALTER는 예시 15(UNIQUE 제약 삭제)와 마찬가지로 ERROR가 나야 하는가?
```

**예제 설명**: 이 예제는 제약조건 자체를 건드리지 않고도 RK 자격을 무력화시킬 수 있는 우회 경로를 보여준다. 예시 15가 "UK를 직접 삭제하는 것"만 막아 놓았다면, 이 우회로를 통해 사실상 같은 결과(RK 없는 복제 테이블)에 도달할 수 있어 §4-1의 제약이 구멍이 생긴다.

**제안**: RK 자격에 영향을 주는 모든 DDL 경로(제약 삭제뿐 아니라 컬럼 NULL 속성 변경, 컬럼 삭제, 컬럼 타입 변경 등)를 전수 조사해 §4-2 제약 목록에 포함해야 한다.

## 리뷰 16

**[심각도: 치명] RK 컬럼의 타입을 변경하는 흔한 실무 시나리오가 스펙에서 완전히 빠졌다**

**대상**: §4-2 전체, 실무 관점(컬럼 타입 변경)

**문제 설명**: 3년차 실무에서 컬럼 타입 변경(예: `INT`로 만든 PK가 데이터량이 늘어나 `BIGINT`로 바꿔야 하는 상황, 혹은 `VARCHAR(20)`을 `VARCHAR(50)`으로 늘리는 상황)은 매우 흔한 DDL이다. §4-2는 PK/UK를 "제거"하거나 "추가"하는 관점의 예시만 다룰 뿐, 제약은 그대로 두고 컬럼 타입만 바꾸는 `ALTER TABLE ... MODIFY/CHANGE COLUMN`이 RK 컬럼에 적용될 때 허용되는지 전혀 언급하지 않는다.

**구체 예제**:
```sql
CREATE TABLE tbl (
    a INT PRIMARY KEY,
    b VARCHAR(20)
);
-- RK = PK(a)

-- 흔한 운영 시나리오: id 범위가 int 최댓값(약 21억)에 근접해 타입을 늘려야 함
ALTER TABLE tbl MODIFY COLUMN a BIGINT;
```

**예제 설명**: 이 ALTER는 PK 제약 자체를 건드리지 않고 컬럼의 저장 타입만 바꾼다. 그런데 이 변경은 카탈로그상 컬럼 정의를 바꾸는 것이고, 이미 만들어진 복제 로그 레코드(옛 INT 폭으로 인코딩된 값)와 이후 로그(BIGINT 폭으로 인코딩된 값)의 이진 포맷이 다를 수 있다. 특히 슬레이브에 지연된 로그가 남아있는 상태에서 이 ALTER가 커밋되면, 슬레이브가 옛 로그를 새 스키마로 잘못 해석할 위험이 있다. §4-2가 이 케이스를 아예 다루지 않는다는 것은, "RK를 바꾸지 않는 컬럼 속성 변경은 항상 안전하다"고 암묵적으로 가정한 것인데, 그 가정이 맞는지 검증된 바가 없다.

**제안**: RK 컬럼의 타입/길이 변경을 허용할지, 허용한다면 진행 중인 복제 로그 적용에 미치는 영향(§리뷰3과 동일한 배리어 필요성)을 §4-2에 명시적으로 추가해야 한다. 이는 예제 개수로 보나 실무 빈도로 보나 이 스펙에서 가장 큰 구멍이다.

---

## 리뷰 17

**[심각도: 중요] 인덱스 재구성(DROP 후 CREATE) 두 문장 사이의 중간 상태가 실무 스크립트를 깨뜨릴 수 있다**

**대상**: §4-2 예시 16 "DROP INDEX: 복제키 후보가 없다면 삭제 불가"

**문제 설명**: 실무에서 인덱스를 재구성할 때는 흔히 "기존 인덱스 DROP → 새 인덱스 CREATE"를 별개의 두 문장(때로는 별개의 트랜잭션)으로 실행하는 운영 스크립트를 쓴다. 예시 16은 "복제키 후보가 없다면(=그 인덱스가 마지막 남은 RK 후보라면) DROP 자체가 에러가 난다"는 것만 보여준다. 그런데 만약 그 인덱스가 RK 후보가 아니라 일반 보조 인덱스라면 DROP은 통과하고, 이후 재구성용 CREATE INDEX 문장을 실행하기 전 짧은 시간 동안 다른 세션이 알 수 없는 이유로 실패할 경우(스크립트 중단, 네트워크 단절 등) 그 인덱스가 실제로는 RK 후보였는데도 스펙이 그 사실을 사전에 알리지 않아 운영자가 실수로 마지막 RK를 지워버릴 위험이 있다.

**구체 예제**:
```sql
-- 운영팀이 흔히 쓰는 인덱스 재구성 스크립트
DROP INDEX idx_tbl_b ON tbl;   -- b 위의 UK 인덱스였다고 하자 (RK 후보였음)
-- 스크립트가 여기서 네트워크 문제로 중단됨

-- (재개 전) 다른 세션에서 확인
SELECT * FROM tbl WHERE b = 5;   -- 이제 RK 후보가 사라진 상태로 남아있음
-- 이 테이블이 HA 복제 대상이었다면, 이 시점부터 복제가 불가능한 상태인가?
-- 아니면 예시 16대로 애초에 DROP 자체가 막혔어야 하는가?
```

**예제 설명**: 예시 16은 "복제키 후보가 없다면 DROP 불가"라고 했으므로, b가 유일한 RK 후보였다면 DROP 자체가 애초에 ERROR가 나서 이 시나리오는 발생하지 않아야 한다. 하지만 스펙은 "RK 후보 유무"를 DROP 시점에 어떻게 판별하는지(그 인덱스가 실제로 RK로 선택되어 있었는지, 아니면 선택되지 않은 여분의 UK였는지 구분 없이 "후보"라는 표현만 쓴다) 애매하게 서술해 실제 구현이 이 실무 패턴을 안전하게 막아주는지 확신할 수 없다.

**제안**: "RK 후보"의 판정 기준을 명시하고, 인덱스 재구성처럼 여러 DDL이 연속으로 실행되는 흔한 운영 패턴에 대해 "DROP 시점에 마지막 후보라면 즉시 차단"이라는 동작이 모든 인덱스 삭제 경로(DROP INDEX, DROP CONSTRAINT, DROP COLUMN)에서 일관되게 적용됨을 예제로 보여줘야 한다.

## 리뷰 18

**[심각도: 보통] 데이터 이관 시 REPLICATION 옵션 생략의 기본값(ON)이 의도치 않은 복제 부하를 유발할 수 있다**

**대상**: §2-1 "이 옵션은 생략 가능하며 생략시 ON으로 자동으로 복제 테이블로 생성된다"

**문제 설명**: 실무에서 다른 서버의 스키마를 덤프해 옮기거나(`unloaddb`/`loaddb`가 아니라 DDL 스크립트를 직접 손으로 재실행하는 경우), 배치성 스테이징 테이블을 만들 때는 보통 REPLICATION 여부를 신경 쓰지 않고 `CREATE TABLE ... (기존 DDL 그대로)`를 실행한다. 이 스펙은 옵션을 생략하면 기본값이 ON이라고 정했는데, 이는 "복제하지 않아도 될 대용량 임시/스테이징 테이블"이 아무 것도 명시하지 않았다는 이유만으로 복제 대상에 포함되어, HA 운영 중 대량 이관 작업이 슬레이브 쪽 복제 부하로 그대로 전이되는 결과를 낳는다.

**구체 예제**:
```sql
-- 개발자가 다른 환경에서 옮겨온 DDL을 그대로 실행 (REPLICATION 옵션 없음)
CREATE TABLE staging_import (
    id INT PRIMARY KEY,
    raw_data VARCHAR(4000)
);
-- 기본값 ON이므로 복제 테이블로 생성됨

-- 이후 이 테이블에 수백만 건을 COPY/INSERT ... SELECT 로 적재
INSERT INTO staging_import SELECT * FROM external_source;
-- 이 대량 삽입이 그대로 슬레이브 복제 트래픽으로 흘러들어간다.
```

**예제 설명**: 이 예제는 REPLICATION 옵션을 "안전한 기본값"으로 설계했다고 보기 어려운 이유를 보여준다. 마이그레이션/스테이징처럼 일회성·대용량 성격의 테이블은 오히려 복제 제외가 자연스러운 기본값에 가까운데, 스펙은 하위 호환(§8의 "변수 없으면 Default=복제 대상")과 일관성을 맞추기 위해 ON을 기본값으로 택한 것으로 보인다. 이 트레이드오프 자체를 스펙이 논의하지 않고 결론만 던져놓았다.

**제안**: 최소한 "대량 데이터 이관 시에는 명시적으로 REPLICATION=OFF를 지정한 뒤 이관을 완료하고 필요하면 나중에 ON으로 전환하라"는 운영 가이드를 문서에 권고 사항으로 추가해야 한다(스펙 자체의 기본값을 바꾸는 것은 하위 호환성과 상충하므로 신중해야 한다).

## 리뷰 19

**[심각도: 보통] 복제 제외 테이블을 복제 테이블로 되돌리는 것을 HA 모드에서 무조건 금지하는 근거가 없다**

**대상**: §2-2 "단, HA 모드에서는 복제 제외 테이블이 복제 테이블로 변경될 수 없다", §9 SUMMARY "RK가 있는 테이블 역시 복제 제외대상이 될 수 있음"

**문제 설명**: §2-2는 조건 없이 "HA 모드에서는 OFF→ON 전환이 불가능하다"고 단정한다. 그런데 §9는 "RK가 있는 테이블도 복제 제외 대상이 될 수 있다"고 명시하므로, RK를 이미 갖춘 REPLICATION=OFF 테이블이 존재할 수 있다는 뜻이다. 이런 테이블이라면 ON으로 전환해도 §4-1(RK 필요)이 요구하는 조건을 이미 만족하는데, 왜 HA 모드에서는 무조건 금지되는지 근거가 스펙에 없다. 구현자 입장에서 "왜 안 되는가"를 모르면, 이 제약이 "기술적으로 불가능해서"인지 "설계상 보수적으로 막아둔 것"인지 구분할 수 없어 향후 이 제약을 완화해도 되는지 판단할 근거가 없다.

**구체 예제**:
```sql
CREATE TABLE tbl (
    a INT PRIMARY KEY,
    b INT
) REPLICATION = OFF;
-- RK 후보(PK a)는 이미 있음. §9에 따르면 이런 테이블도 존재 가능.

-- HA 모드에서
ALTER TABLE tbl REPLICATION = ON;
-- 예시 5, §2-2에 따르면 이건 ERROR다.
-- 그런데 이 테이블은 RK가 이미 있어서 §4-1 요구조건을 만족하는데
-- 왜 막혀야 하는지 스펙에 설명이 없다.
```

**예제 설명**: 이 예제는 "RK 유무만으로 HA 전환 가능 여부를 판단한다"는 §1의 원칙과, "OFF→ON은 HA에서 무조건 불가"라는 §2-2의 원칙이 서로 다른 축(RK 유무 vs 모드)으로 판단 기준을 두고 있어 왜 후자가 전자를 무시하고 우선하는지 설명이 빠졌음을 보여준다. 만약 이유가 "OFF 테이블은 그동안 데이터가 슬레이브에 없어서 ON으로 바꿔도 초기 스냅샷 동기화가 필요한데 HA 운영 중에는 그 방법이 없기 때문"이라면, 그 이유를 스펙에 문장으로 남겨야 구현자와 이후 유지보수자가 이 제약의 완화 가능성을 오판하지 않는다.

**제안**: §2-2의 "HA 모드에서 OFF→ON 전환 불가" 규칙에 그 근거(슬레이브 초기 데이터 부재로 인한 스냅샷 동기화 불가 등)를 한 문장 추가해야 한다.

## 리뷰 20

**[심각도: 사소] 예시 12와 예시 13의 PK 삭제 구문 표기가 서로 다르다**

**대상**: §4-2 예시 12 "DROP PK" vs 예시 13 "PK 를 다른 컬럼으로 변경"

**문제 설명**: 예시 12는 PK를 삭제하는 구문으로 `ALTER TABLE table_name DROP PRIMARY KEY;`를 쓰는 반면, 바로 다음 예시 13은 같은 동작(PK 삭제)의 앞부분에 `ALTER TABLE table_name DROP CONSTRAINT PRIMARY KEY, ADD CONSTRAINT PRIMARY KEY(a);`처럼 `DROP CONSTRAINT PRIMARY KEY`라는 다른 키워드 조합을 쓴다. `DROP CONSTRAINT`는 일반적으로 이름이 있는 제약조건(`pk_tbl_a`처럼 예시 11의 에러 메시지에 등장하는 이름)을 지정해서 지우는 구문이지, `PRIMARY KEY`라는 제약 종류 키워드를 이름 자리에 바로 쓰는 것이 실제 CUBRID 문법에 존재하는지 스펙만으로는 알 수 없다.

**구체 예제**:
```sql
-- 예시 12
ALTER TABLE table_name DROP PRIMARY KEY;

-- 예시 13 (바로 다음 예시인데 다른 키워드 사용)
ALTER TABLE table_name DROP CONSTRAINT PRIMARY KEY,
ADD CONSTRAINT PRIMARY KEY(a);
```

**예제 설명**: 같은 절(§4-2) 안에서 인접한 두 예시가 동일한 동작(PK 제거)에 대해 서로 다른 구문을 사용하고 있다. 이것이 CUBRID가 실제로 두 가지 문법을 다 지원한다는 뜻인지, 아니면 예시 13이 오탈자(원래 `DROP PRIMARY KEY, ADD CONSTRAINT PRIMARY KEY(a)`여야 함)인지 문서만으로는 판단할 수 없다.

**제안**: 예시 13의 구문을 실제 csql로 검증하고, 예시 12와 표기를 통일하거나 두 문법이 모두 유효하다면 그 사실을 각주로 명시해야 한다.
