# CUBRID HA 복제 개선 스펙 리뷰 — PM(5년차) 관점

## 리뷰어 소개

5년차 프로덕트 매니저로서 DB 엔진/미들웨어 계열 제품의 스펙 검토와 릴리스 게이팅을 담당해 왔다. 코드를 직접 짜지는 않지만 스펙이 "요구사항으로서 완전한가", "기존 사용자를 깨뜨리지 않는가", "운영 중 릴리스했을 때 사고가 날 지점이 있는가"를 기준으로 문서를 읽는다. 이번 리뷰는 CUBRID HA 복제에 복제 키(RK, Replication Key: 슬레이브에 반영할 행을 유일하게 식별하는 데 쓰는 컬럼 집합)와 `REPLICATION` 테이블 옵션을 도입하는 스펙(`user_spec_extracted.md`)을 대상으로 한다.

## 총평

이 스펙은 "PK 없는 테이블이 HA 복제를 막는다"는 실제 장애를 해결하려는 방향성은 타당하지만, 문서 자체가 **구현 세부사항을 검증할 수 있는 수준의 완전성에 도달하지 못했다.** 특히 (1) RK 후보가 여러 개 존재할 때 엔진이 언제·어떻게 RK를 전환하는지에 대한 서술이 없고, (2) 같은 절(§4-2) 안에서 "다른 복제키 후보가 있으면 모든 DDL이 허용된다"는 원칙과 "PK가 복제키면 무조건 삭제 불가"라는 예시가 서로 충돌하며, (3) 이 스펙이 해결하려는 원래 버그(참조 테이블 미복제로 인한 FK 데이터 불일치)가 `CREATE TABLE` 경로만 막고 `ALTER TABLE ... REPLICATION=OFF`로 부모 테이블을 나중에 복제 제외로 바꾸는 경로는 막지 않아, 같은 버그가 다른 문으로 재발할 위험이 남아 있다. 또한 기존 운영 클러스터의 롤링 업그레이드·카탈로그 마이그레이션 경로가 전혀 서술되지 않아, 릴리스 리스크 관점에서 이 문서만으로는 배포 계획을 세울 수 없다. 예제 SQL의 트레일링 콤마 같은 사소한 오류부터, 절 간 상호 참조 부재, 용어집 부재까지 문서 품질 이슈도 다수 발견된다. 아래 20개 리뷰에서 심각도순으로 상세히 다룬다.

### 리뷰 1

**[심각도: 치명] RK 후보가 여러 개일 때 "전환 시점"이 스펙 어디에도 정의되어 있지 않다**

**대상**: §1 "복제키는 다음 기준에 의해 결정된다", §4-2 "다른 복제키 후보가 함께 존재한다면 모든 DDL은 허용된다"

**문제 설명**: 스펙은 RK 선택 "기준"(PK 우선, 없으면 UK, UK가 여럿이면 선언 순서상 가장 빠른 것)만 정의하고, 이미 운영 중인 테이블에서 현재 RK가 사라지고 다른 후보로 **넘어가는 순간**이 언제인지 말하지 않는다. DDL 문장이 커밋되는 시점인지, 복제 로그(트랜잭션 로그에 남는 DDL 레코드)가 슬레이브에 적용되는 시점인지, 아니면 그 사이 어느 지점인지가 불명확하다. 이는 사용자에게 사소한 문서 흠결이 아니라 **마스터와 슬레이브가 서로 다른 RK로 같은 트랜잭션을 처리할 수 있는 정합성 위험**이다.

**구체 예제(시나리오)**:
```sql
-- t1: 마스터에 PK(a)와 UK(b) NOT NULL 두 후보가 공존, 현재 RK=PK(a)
CREATE TABLE tbl(
    a INT PRIMARY KEY,
    b INT NOT NULL UNIQUE,
    c INT
);

-- t2: 애플리케이션이 계속 tbl에 UPDATE를 흘려보내는 중 (복제 로그 생성 중)
UPDATE tbl SET c = c + 1 WHERE a = 100;   -- 마스터: RK=a로 로그 기록

-- t3: 운영자가 PK를 UK로 교체 (예시 13 방식, RK가 PK -> UK로 전환되는 트랜잭션)
ALTER TABLE tbl DROP CONSTRAINT PRIMARY KEY,
                ADD CONSTRAINT PRIMARY KEY(b);  -- b를 새 PK로

-- t4: 위 DDL 커밋 직후 다시 UPDATE
UPDATE tbl SET c = c + 1 WHERE b = 55;    -- 마스터: RK=b로 로그 기록

-- t5(슬레이브, applylogdb): t2, t3, t4 로그를 순서대로 받아 적용해야 한다.
-- applylogdb가 t2 로그(RK=a 기준 UPDATE)를 아직 처리하지 못한 상태에서
-- t3의 DDL을 먼저 적용해버리면, t2 로그를 "b 컬럼 기준"으로 재해석하려다
-- 어떤 값으로 매칭해야 할지 알 수 없는 상태가 된다.
```

**예제 설명**: applylogdb는 CUBRID HA에서 마스터의 트랜잭션 로그를 읽어 슬레이브에 순차 적용하는 백그라운드 프로세스다. 위 시나리오에서 t2 시점의 UPDATE 로그는 "RK=a"라는 문맥에서 만들어졌는데, t3의 RK 전환 DDL이 슬레이브에 먼저 반영되면 t2 로그를 적용할 시점에 이미 RK 정의가 바뀌어 있다. 로그에 RK 값 자체(예: a=100)는 남아있으니 실제로는 적용 가능할 수도 있지만, **스펙은 이 순서 보장(RK 전환 DDL과 그 전후의 DML 로그가 슬레이브에서 반드시 원래 마스터 순서대로 적용된다는 것)을 명시적으로 약속하지 않는다.** "복제키는 엔진이 결정한다"는 문장만으로는 구현자도, 이 스펙을 검증하는 QA도 "언제 전환되는가"를 재현 테스트로 확인할 방법이 없다.

**제안**: RK 전환이 "해당 DDL을 포함하는 트랜잭션이 마스터에 커밋되는 순간 논리적으로 발생"하며, "슬레이브는 그 DDL 로그를 적용하기 전까지 이전 RK 정의를 유지한다"는 순서 보장 문장을 §4-2에 명시적으로 추가할 것을 요청한다. 최소한 "RK 전환 시점의 DML 순서 보장" 항목을 별도 소절로 분리해야 한다.

### 리뷰 2

**[심각도: 치명] §4-2 본문과 예시 12가 서로 다른 규칙을 말하고 있다(내부 모순)**

**대상**: §4-2 "테이블에 하나의 복제키만 존재한다면 복제키를 수정하는 DDL이 제한되지만, 다른 복제키 후보가 함께 존재한다면 모든 DDL은 허용된다" vs 예시 12

**문제 설명**: 본문 원칙은 "다른 RK 후보가 있으면 PK를 지우는 DDL도 허용된다"는 취지로 읽힌다. 그런데 바로 이어지는 예시 12는 조건 없이 "HA 환경에서 PK가 복제키로 사용될 경우 이 PK 혹은 PK 컬럼은 삭제할 수 없다"고 단정한다. 예시 12 앞에 나온 예시 테이블(`repl_table_with_rk`, 예시 1)은 사실 PK(a)와 UK(b) 두 후보를 모두 가진 테이블이다. 본문 원칙대로라면 이 테이블은 "다른 후보(UK b)가 있는" 케이스이므로 PK 삭제가 허용되어야 하는데, 예시 12는 이를 ERROR로 규정한다. 즉 **같은 페이지, 같은 절 안에서 두 문장이 정반대의 결론을 낸다.**

**구체 예제(시나리오)**:
```sql
-- 예시 1과 동일한 테이블: RK 후보 2개(PK a, UK b) 존재
CREATE TABLE repl_table_with_rk(
    a INT PRIMARY KEY,
    b INT NOT NULL UNIQUE,
    c INT
);

-- 본문 원칙 적용 시 기대값: "다른 후보(b)가 있으므로 모든 DDL 허용" -> OK
-- 예시 12 적용 시 기대값: "PK가 RK로 쓰이면 무조건 삭제 불가" -> ERROR
ALTER TABLE repl_table_with_rk DROP PRIMARY KEY;
```

**예제 설명**: 위 한 줄 SQL에 대해 스펙 본문과 스펙 예시가 서로 다른 답(OK 또는 ERROR)을 내놓는다. 이는 스펙을 읽는 개발자가 실제로 어떤 동작을 구현해야 하는지 결정할 수 없다는 뜻이다. 가능성은 두 가지다. (a) 예시 12가 실제로는 "복제키 후보가 1개인 경우"에 한정된 것인데 그 조건이 예시 11~13 앞에 나온 소제목("복제키 후보가 1개인 경우(=복제키) 제약사항은 다음과 같다")에만 있고 각 예시 캡션에는 재기술되지 않아 독자가 놓치기 쉽거나, (b) 실제로 "PK가 후보로 존재하는 한 다른 후보 유무와 무관하게 삭제 금지"가 진짜 규칙이고 본문 원칙 문장 자체가 부정확한 것이다. 둘 중 무엇이 맞는지 문서만으로는 판단할 수 없다.

**제안**: 예시 11~16 각각의 캡션 앞에 전제조건("이 테이블은 RK 후보가 1개뿐이다")을 명시하고, 후보가 여러 개일 때의 대응 예시(PK+UK 공존 테이블에서 PK 삭제가 실제로 OK인지)를 별도로 최소 1개 추가해야 한다.

### 리뷰 3

**[심각도: 치명] FK 참조 무결성 검증이 `CREATE TABLE` 시점에만 있고, 이미 존재하는 FK 관계의 부모 테이블을 나중에 `REPLICATION=OFF`로 바꾸는 경로는 막지 않는다**

**대상**: §5(외래키), §4(HA 제약사항 - "복제 제외 테이블이 복제 테이블로 변경될 수 없다"만 언급), §7(HA 전환 시 검증)

**문제 설명**: 배경 설명(1절)과 다이어그램은 "FK로 참조되는 테이블이 복제 제외라서 슬레이브에 데이터가 없다"는 문제를 명시적으로 그리고 있고, §5의 예시 17/18은 `CREATE TABLE` 시점에 이를 막는다. 그런데 스펙 어디에도 **"이미 REPLICATION=ON으로 FK 참조를 받고 있는 부모 테이블을, 운영 중에 REPLICATION=OFF로 바꾸는 것"을 막는 규칙이 없다.** §4는 반대 방향(OFF→ON 금지)만 규정하고, §7의 검증은 "HA 전환 시"에만 동작한다. 즉 HA가 이미 켜진 상태에서 이 ALTER를 실행하면 스펙상 허용되는 것으로 읽히고, 이는 정확히 이 스펙이 해결하려는 원래 버그(마스터/슬레이브 데이터 불일치, FK 참조 대상 부재)를 다른 경로로 재현시킨다.

**구체 예제(SQL)**:
```sql
-- 1) 정상적으로 FK 관계 수립 (예시 17과 동일, 둘 다 REPLICATION=ON)
CREATE TABLE customers(
    customer_id INT PRIMARY KEY,
    country INT
);

CREATE TABLE orders(
    order_id INT PRIMARY KEY,
    customer_id INT,
    CONSTRAINT fk_customer_id FOREIGN KEY (customer_id) REFERENCES customers(customer_id)
);
-- 여기까지는 §5 예시 17 그대로. HA가 이미 실행 중이라고 가정.

-- 2) 스펙에 명시적 금지 규정이 없는 문장 실행
ALTER TABLE customers REPLICATION = OFF;
-- 스펙 §4는 "OFF -> ON 전환만 HA에서 금지"라고 했으므로,
-- 이 문장(ON -> OFF)은 §4 조건에 해당하지 않아 OK로 읽힌다.

-- 3) 이 시점부터 customers는 더 이상 슬레이브로 복제되지 않지만
--    orders는 여전히 복제되고 FK 제약(참조하는 대상이 있어야 한다는 규칙)은 마스터에만 유효하다.
INSERT INTO orders VALUES (1, 42);  -- 마스터: FK 체크 통과, 슬레이브로 복제됨

-- 4) Failover 발생, 애플리케이션이 슬레이브로 전환
--    슬레이브에는 orders(1, 42)는 있지만 customers에는 42가 없음
--    -> 배경 설명의 다이어그램과 완전히 동일한 장애 재현
```

**예제 설명**: 이 시나리오는 스펙이 막으려던 문제(§5, 다이어그램)를 `CREATE TABLE` 단계가 아니라 **운영 중 `ALTER TABLE ... REPLICATION=OFF`** 단계에서 그대로 재현한다. 스펙 저자가 "복제 대상 테이블이 참조하는 모든 테이블은 복제 대상이어야 한다"는 불변조건(invariant, 상태가 어떻게 바뀌든 항상 유지되어야 하는 조건)을 세웠다면, 이 불변조건은 `CREATE TABLE`뿐 아니라 기존 FK 관계에 영향을 주는 모든 `ALTER TABLE ... REPLICATION` 문에도 적용되어야 하는데 스펙은 생성 시점만 방어하고 있다.

**제안**: §4의 "복제 제외 → 복제 대상 전환 금지" 규칙 옆에 "복제 대상인 부모 테이블을, 그 테이블을 참조하는 복제 대상 자식 FK가 하나라도 남아있는 동안에는 복제 제외로 전환할 수 없다"는 대칭 규칙을 추가해야 한다. 혹은 자식 FK를 먼저 제거해야 부모의 OFF 전환이 가능하다는 순서를 명시해야 한다.

### 리뷰 4

**[심각도: 치명] 기존 운영 클러스터의 롤링 업그레이드·카탈로그 마이그레이션 경로가 스펙에 전혀 없다**

**대상**: §8(UNLOADDB & LOADDB), §9(SUMMARY) — 오프라인 덤프/로드 경로만 서술, 온라인 업그레이드 언급 없음

**문제 설명**: §8은 `unloaddb`/`loaddb`(데이터를 파일로 내보내고 다시 적재하는 오프라인 도구)를 통한 하위 버전 데이터 이관만 다룬다. 그러나 실제 릴리스에서는 **이미 HA로 운영 중인 클러스터를 무중단으로 새 버전으로 올리는 것(롤링 업그레이드: 슬레이브부터 순서대로 새 버전으로 교체한 뒤 마스터를 전환하는 방식)**이 훨씬 흔한 시나리오다. 이 스펙에는 (a) 카탈로그(테이블/컬럼 메타데이터 저장소)에 `REPLICATION` 컬럼이 새로 추가되어야 하는데 이 스키마 변경을 온라인으로 어떻게 적용하는지, (b) 구버전 슬레이브가 신버전 마스터가 보낸 `CREATE TABLE ... REPLICATION=ON` DDL 로그를 받았을 때 파싱 가능한지, (c) 롤링 업그레이드 도중 마스터/슬레이브 버전이 섞인 구간에서 RK 관련 DDL을 실행하면 무슨 일이 일어나는지에 대한 언급이 전혀 없다.

**구체 예제(시나리오)**:
```text
[클러스터 상태: 구버전(RK 개념 없음) 마스터 M, 슬레이브 S1, S2]

1단계: S2를 새 버전(RK 스펙 포함)으로 재설치, HA 재합류
2단계: 이 상태에서 M(구버전)이 다음 DDL을 실행:
        CREATE TABLE t (a INT PRIMARY KEY) REPLICATION=ON;
   -> 구버전 M은 REPLICATION 문법 자체를 모르므로 이 DDL은 애초에 나올 수 없다.
   반대로:
3단계: S2(신버전)만 새 기능을 이해하고, S1/M(구버전)은 REPLICATION 컬럼이 없는
   상태로 계속 DDL 로그를 만들어 보낸다.
4단계: 전체가 신버전으로 전환된 시점, 이관 전 생성된 모든 기존 테이블의
   REPLICATION 값은 어디서/언제 채워지는가?
   (§8은 "unload/load 경로"만 규정하지, in-place 업그레이드 시
    카탈로그에 컬럼을 추가하고 기본값 ON을 채우는 마이그레이션 스크립트에
    대해서는 침묵한다.)
```

**예제 설명**: 이 시나리오는 "덤프해서 다시 적재"가 아니라 "파일시스템의 기존 DB 볼륨을 그대로 둔 채 바이너리만 새 버전으로 교체하는" 일반적인 인플레이스 업그레이드 경로를 그린 것이다. §8이 다루는 것은 전혀 다른 경로(전체 재구축)이고, 실무에서 대부분의 고객은 재구축 없이 업그레이드하길 원한다. 이 부분이 스펙에 없으면 릴리스 노트/업그레이드 가이드를 작성할 수 없고, QA도 이 경로를 테스트 계획에 넣을 근거가 없다.

**제안**: "기존 버전에서 인플레이스 업그레이드 시 카탈로그 마이그레이션" 절을 §8 옆에 별도로 추가하고, 최소한 "업그레이드 직후 최초 기동 시 시스템이 자동으로 모든 기존 테이블에 `REPLICATION=ON`을 채운다"는 문장 정도는 §9 SUMMARY 수준이라도 명시해야 한다.

### 리뷰 5

**[심각도: 치명] RK 선택 기준 "테이블 내에 명시된 순서 중 가장 빠른 순서"의 정의가 ALTER 이후에는 무너진다**

**대상**: §1 "UK가 여러개 존재한다면 큐브리드 엔진에 의해 이 중 하나가 선택된다(ex. 테이블내에 명시된 순서 중 가장 빠른 순서)"

**문제 설명**: "명시된 순서"가 `CREATE TABLE` 문 안에서의 컬럼/제약 선언 순서를 뜻한다면, 이는 테이블 생성 시점에만 자연스럽게 정의된다. 그런데 UK는 `ALTER TABLE ... ADD CONSTRAINT`로 나중에 추가될 수 있고(예시 14 참고), 기존 UK가 삭제되었다가 다시 추가될 수도 있다(예시 15, 16 관련). 이때 "순서"의 기준이 (a) 원래 `CREATE TABLE`에서의 컬럼 위치인지, (b) 제약이 카탈로그에 추가된 시각(생성 순서)인지, (c) 카탈로그 내부 저장 순서(예: OID 순서)인지 스펙은 규정하지 않는다. 이 모호함은 정확히 "심화 리뷰"가 요구하는 엣지케이스, 즉 RK 후보가 여러 개일 때 결정 규칙 자체가 재현 불가능(non-deterministic으로 보일 수 있음)하다는 문제로 이어진다.

**구체 예제(시나리오)**:
```sql
-- t1: UK 없이 생성, 나중에 UK 두 개를 순서대로 추가
CREATE TABLE tbl(a INT, b INT, c INT) REPLICATION=ON;  -- 싱글 모드에서만 가능(§2-1)

-- t2: b에 UK 추가 (카탈로그상 첫 번째로 추가된 UK)
ALTER TABLE tbl ADD CONSTRAINT u_tbl_b UNIQUE(b);
-- 이 시점 RK = b (유일한 후보)

-- t3: c에도 UK 추가
ALTER TABLE tbl ADD CONSTRAINT u_tbl_c UNIQUE(c);
-- RK는 여전히 b인가? "명시된 순서"가 컬럼 선언 순서(b가 a 다음)를 뜻한다면
-- b, c 둘 다 원래 CREATE TABLE에 있던 컬럼이라 "가장 빠른 순서"는 b가 맞다고
-- 볼 수도 있지만, b도 c도 CREATE TABLE 시점엔 UK가 아니었으므로
-- "명시된 순서"라는 개념 자체가 애초에 이 컬럼들엔 적용되지 않았을 수 있다.

-- t4: u_tbl_b를 DROP 후 다시 생성
ALTER TABLE tbl DROP CONSTRAINT u_tbl_b;
ALTER TABLE tbl ADD CONSTRAINT u_tbl_b UNIQUE(b);
-- 이제 카탈로그 생성 순서 기준으로는 c가 b보다 먼저 추가된 제약이 된다.
-- RK가 c로 넘어가는가? 이 전환은 예시 12처럼 "RK 변경은 사용자가 직접 못 한다"는
-- 원칙과 충돌하는 부작용(우회 경로로 RK를 사실상 조작 가능)이 생긴다.
```

**예제 설명**: t4의 DROP 후 재생성은 사용자가 의도적으로 "RK를 직접 바꿀 수 없다"(§4-2)는 제약을 우회해 특정 컬럼을 RK로 강제 지정하는 데 악용될 수 있는 경로를 보여준다. 스펙이 "순서"의 정확한 정의(선언 순서 vs 생성 시각 vs 카탈로그 내부 ID)를 명시하지 않으면, 이 우회가 스펙 위반인지조차 판단할 수 없다.

**제안**: RK 선택 순서 기준을 "제약이 카탈로그에 최초로 생성된 시각(생성 순서)이며, DROP 후 재생성은 새로운 생성 시각을 부여받는다"처럼 검증 가능한 방식으로 명문화하고, "사용자가 DROP+ADD로 RK 우선순위를 실질적으로 조작하는 것을 허용/금지할지"를 명시적으로 결정해야 한다.

### 리뷰 6

**[심각도: 중요] §8 "자동으로 RK를 할당한다"는 §1의 "RK는 선택되는 것"이라는 원칙과 용어가 충돌한다**

**대상**: §8 "복제 테이블의 경우 큐브리드는 자동으로 RK를 할당한다" vs §1 "복제 키는 큐브리드 엔진에 의해 PK 혹은 UK들 중 하나로 선택된다"

**문제 설명**: §1은 RK가 "기존에 존재하는 PK/UK 제약 중에서 선택"되는 것이라고 규정한다. 즉 PK도 UK도 없는 테이블에는 RK가 존재할 수 없다(§1 첫 문장: "복제 키가 존재하지 않으면 HA모드를 실행 할 수 없다"). 그런데 §8은 `loaddb` 시 "복제 테이블의 경우 큐브리드는 자동으로 RK를 할당한다"고 말한다. "할당(assign)"이라는 단어는 기존에 없던 키를 새로 만들어 부여한다는 뉘앙스를 갖는데, 이는 §1의 "선택(select)" 원칙과 다르다. 만약 로드 대상 데이터에 PK도 UK도 없다면, §8의 "자동 할당"은 §1의 "RK 없으면 HA 불가" 규칙과 정확히 무엇을 하겠다는 것인지 알 수 없다(surrogate key, 즉 데이터에 없던 내부 전용 식별 컬럼을 새로 만들어 붙이겠다는 뜻인지, 아니면 단순히 오기(誤記)이고 "선택한다"의 의미인지 불명).

**구체 예제(시나리오)**:
```text
[구버전에서 unload한 파일: PK/UK 정보 없이 컬럼 (a INT, b INT)만 있는 테이블 old_tbl]

loaddb 실행 (§8: "복제 여부를 저장하는 변수가 없으면 복제 대상(Default)으로 간주"
             + "복제 테이블의 경우 큐브리드는 자동으로 RK를 할당한다")

질문:
1) old_tbl에 PK/UK가 전혀 없는데 "RK를 자동으로 할당"한다는 것은
   내부적으로 숨겨진 대리키(surrogate key) 컬럼을 새로 만든다는 뜻인가?
2) 그렇다면 이 대리키는 §1의 "PK 또는 UK 중에서 선택"이라는 정의를 벗어난
   제3의 RK 종류인가? §1에는 이런 종류가 정의되어 있지 않다.
3) 만약 단순히 "PK/UK가 있으면 그중에서 선택한다"는 뜻이었을 뿐이라면,
   old_tbl처럼 PK/UK가 아예 없는 테이블은 load 후 HA 모드로 못 올라가야
   하는데, §8 어디에도 이 실패 케이스가 언급되지 않는다.
```

**예제 설명**: 이 시나리오는 "할당"이라는 단어 하나가 스펙 전체의 핵심 개념(RK는 반드시 기존 제약에서 나온다)과 충돌할 수 있음을 보여준다. 구현자가 이 문장을 문자 그대로 읽으면 "PK/UK가 없어도 엔진이 뭔가 만들어준다"고 오해할 수 있고, 반대로 §1을 우선시하면 "load 실패 케이스가 §8에 누락됐다"고 봐야 한다. 어느 쪽이든 문서 수정이 필요하다.

**제안**: §8의 "할당"을 "선택"으로 통일하고, PK/UK가 전혀 없는 테이블을 복제 대상으로 load하려는 경우의 처리(에러 또는 자동으로 복제 제외 전환)를 명시적으로 추가해야 한다.

### 리뷰 7

**[심각도: 중요] 예제 SQL 자체에 트레일링 콤마 등 문법 오류가 있다**

**대상**: 예시 2, 예시 20, 예시 23

**문제 설명**: 스펙의 예제는 사용자가 그대로 복사해 실행해볼 자료로 쓰이는 경우가 많다. 그런데 예시 2와 예시 23의 `CREATE TABLE` 문에는 컬럼 목록 마지막에 불필요한 콤마(trailing comma)가 있다. 일반적인 SQL 파서는 `(a INT,)`처럼 콤마 뒤에 아무것도 없는 구문을 문법 오류로 처리한다. 스펙에 실린 예제 자체가 파싱 실패할 코드라면, 이 문서를 기반으로 만들어질 사용자 매뉴얼/테스트 케이스에 오류가 그대로 전파된다.

**구체 예제(원문 인용)**:
```sql
-- 예시 2 원문 그대로
CREATE TABLE repl_table_without_rk(
    a INT,
);

-- 예시 23 원문 그대로
CREATE TABLE new_orders(
    order_id INT PRIMARY KEY,
);
```

**예제 설명**: 두 예제 모두 컬럼 정의 목록의 마지막 항목 뒤에 콤마가 남아있다. CUBRID의 SQL 파서가 이런 트레일링 콤마를 관대하게 허용하는지는 이 리뷰의 범위 밖이지만(엔진 개발 관점 리뷰에서 확인할 사항), 표준 SQL 문법 관점에서는 오류로 보는 것이 일반적이다. PM 관점에서 중요한 것은, 이 오류가 스펙 검토 과정에서 아무도 걸러내지 못한 채 통과됐다는 사실 자체가 **문서 리뷰 프로세스의 허술함을 드러낸다**는 점이다.

**제안**: 모든 예제 SQL을 실제 CUBRID 인스턴스에 붙여넣어 실행 확인(dry-run)한 뒤 스펙에 반영하는 검수 단계를 추가해야 한다.

### 리뷰 8

**[심각도: 중요] 예시 5/6의 캡션과 결과가 뒤바뀐 것처럼 보여 오독 위험이 크다**

**대상**: §2-2, 예시 5, 예시 6

**문제 설명**: 원문 구조는 다음과 같다.

```
예시 5. REPLICATION = ON  csql> ALTER TABLE tbl REPLICATION=ON;
ERROR
예시 6. REPLICATION = OFF  csql> ALTER TABLE tbl REPLICATION=OFF;
OK
```

캡션("예시 5. REPLICATION = ON")만 보면 "REPLICATION=ON으로 바꾸는 것 자체가 스펙상 정상 동작"이라고 오해하기 쉽지만 실제 결과는 ERROR다. 이는 오타가 아니라 의도된 결과(HA에서는 OFF→ON 전환이 금지되므로)이지만, 캡션 표기 방식이 "이 예시가 보여주는 것은 무엇인가"를 직접 설명하지 않고 단순히 "어떤 옵션값을 썼는가"만 표기해서, 빠르게 훑어보는 독자는 정반대로 이해하기 쉽다. 앞서 나온 예시 1~4도 "REPLICATION = ON" / "REPLICATION = OFF"라는 소제목을 예시 그룹 전체의 표제로 쓰다가, 예시 5/6에서는 같은 표기 패턴을 개별 예시 캡션으로 재사용해 두 가지 다른 용법이 뒤섞여 있다.

**구체 예제**: 위 원문 그대로가 예제이며 별도 SQL 작성이 필요 없다. 이 표기 스타일 문제 자체가 리뷰 대상이다.

**예제 설명**: 문서의 시각적 구조(캡션이 옵션값을 나타내는지, 실행 결과를 나타내는지)가 절 내에서 일관되지 않으면, 독자는 "예시 5는 ON으로 바꾸는 방법을 보여준다"고 잘못 결론 내릴 위험이 있다. 실제로는 "예시 5는 ON으로 바꾸는 것이 (이 조건에서는) 금지된다는 것을 보여준다"가 맞는 해석이다.

**제안**: 캡션을 "예시 5. REPLICATION=OFF -> ON 전환 시도(HA 모드, 금지됨)"처럼 결과까지 포함해 명확히 다시 쓸 것을 제안한다.

### 리뷰 9

**[심각도: 중요] ORM/마이그레이션 도구가 생성하는 다단계 ALTER 시퀀스와 §4-2 규칙의 충돌 가능성이 검토되지 않았다**

**대상**: §4-2, 예시 13(단일 문장 안에서 DROP+ADD)

**문제 설명**: 스펙은 "PK를 다른 컬럼으로 바꾸려면 예시 13처럼 하나의 `ALTER TABLE` 문 안에서 `DROP CONSTRAINT` + `ADD CONSTRAINT`를 함께 써야 한다"는 것을 전제로 규칙을 짜놓았다. 그런데 실제 배포 환경에서는 Flyway나 Liquibase 같은 스키마 마이그레이션 도구가 이런 변경을 자동 생성할 때, 안전성을 이유로 **DROP과 ADD를 별개의 트랜잭션/문장으로 나누는 경우**가 흔하다(예: 한 문장이 실패해도 롤백 범위를 좁히기 위해, 혹은 도구가 지원하는 단일 ALTER 문법의 한계 때문에). 이 스펙은 "한 문장으로 묶은 경우"만 정상 경로로 제시하고, "두 문장으로 나뉜 경우"에 무슨 일이 벌어지는지(중간에 RK가 아예 없는 상태가 잠깐 존재하게 됨) 다루지 않는다.

**구체 예제(시나리오)**:
```sql
-- 마이그레이션 도구가 자동 생성한 2단계 스크립트 (예시 13을 문장 2개로 분리한 경우)
-- Step 1
ALTER TABLE table_name DROP CONSTRAINT PRIMARY KEY;
-- 이 시점: 테이블에 RK 후보가 0개. §4-2 원칙("복제키가 없는 복제 테이블은
-- HA 모드에서 생성 불가")과 유사한 상태가 ALTER로 만들어짐.
-- 이 문장 자체가 §4-2에 의해 거부되어야 하는가, 아니면 다음 Step 2가
-- 바로 이어지길 "믿고" 일단 허용해야 하는가?

-- Step 2 (별도 커밋, 별도 트랜잭션)
ALTER TABLE table_name ADD CONSTRAINT PRIMARY KEY(a);
```

**예제 설명**: Step 1만 놓고 보면 "복제 대상 테이블에서 마지막 남은 RK 후보를 제거하는 DDL"이므로 §4-2 취지상 거부되어야 한다. 그런데 이렇게 되면 마이그레이션 도구가 이런 패턴을 생성하는 순간 실패하게 되고, 사용자는 도구를 못 쓰거나 도구 설정을 CUBRID 전용으로 커스터마이징해야 한다. 반대로 Step 1을 허용하고 Step 2가 뒤따르길 기대한다면, Step 1과 Step 2 사이(별도 트랜잭션이므로 임의로 긴 시간이 벌어질 수 있음)에 그 테이블에 대한 복제가 어떻게 처리되는지(복제 중단? 큐잉? 에러 누적?) 스펙이 침묵한다.

**제안**: "RK 후보가 0개가 되는 중간 상태를 허용할 것인지"를 명시적으로 결정하고, 허용하지 않는다면 그 이유를 사용자에게 명확히 전달하는 에러 메시지 요구사항을 추가해야 한다(이는 실제로 스키마 마이그레이션 도구 생태계와의 호환성 문제이므로 GA 이전에 반드시 검증이 필요하다).

### 리뷰 10

**[심각도: 중요] §6(뷰)의 "책임지지 않는다"는 표현이 반복되지만, 사용자에게 무엇이 통지되는지 정의가 없다**

**대상**: §1 "REPLICATION OFF 로 인한 데이터 불일치는 책임지지 않는다", §6 "이 부분에대해 큐브리드 복제 모듈은 책임지지 않는다"

**문제 설명**: "책임지지 않는다"는 법적/정책적 면책 문구이지, 기능 요구사항이 아니다. PM 입장에서 스펙에 있어야 할 것은 "이런 상황이 발생했을 때 시스템이 어떤 신호(로그, 경고, 에러)를 내는가"이다. 스펙은 두 번이나 "책임지지 않는다"고만 말하고, 뷰가 복제 제외 테이블을 포함할 때 (a) `CREATE VIEW` 시점에 경고를 낼지, (b) 아무 신호 없이 조용히 다른 결과를 낼지 규정하지 않는다. "조용히 다른 결과를 낸다"는 최종 사용자 입장에서는 버그로 인식될 수 있는 행동이며, 이는 지원팀 문의로 이어질 릴리스 리스크다.

**구체 예제(시나리오)**:
```sql
CREATE TABLE t_repl(a INT PRIMARY KEY, b INT) REPLICATION=ON;
CREATE TABLE t_norepl(a INT PRIMARY KEY, b INT) REPLICATION=OFF;

CREATE VIEW v_combined AS
SELECT t_repl.a, t_norepl.b
FROM t_repl JOIN t_norepl ON t_repl.a = t_norepl.a;
-- 이 CREATE VIEW 시점에 t_norepl이 REPLICATION=OFF임을 검사해서
-- 경고를 내는가? 아니면 그냥 성공(OK)하고 넘어가는가?

-- Failover 이후 슬레이브에서:
SELECT * FROM v_combined;
-- t_norepl에 데이터가 없으므로 결과는 마스터와 다르지만
-- 에러 없이 "빈 결과" 혹은 "부분 결과"가 조용히 반환된다.
```

**예제 설명**: 이 시나리오는 사용자가 `CREATE VIEW`를 실행하는 순간에도, 나중에 failover 후 조회하는 순간에도 아무런 경고를 받지 못한 채 잘못된(불일치하는) 데이터를 정상 응답처럼 받게 됨을 보여준다. "책임지지 않는다"는 스펙 저자의 의도이지만, 이 의도가 사용자에게 어떻게 드러나는지가 스펙에 빠져 있으면 QA는 이 케이스를 "정상"과 "버그" 중 무엇으로 판정해야 할지 알 수 없다.

**제안**: 최소한 `CREATE VIEW`/`ALTER VIEW` 시점에 복제 제외 테이블이 참조되면 경고성 메시지를 출력하도록 요구사항을 추가하거나, 그렇게 하지 않기로 결정했다면 "의도적으로 경고하지 않는다"는 문장을 명시해 모호함을 없애야 한다.

### 리뷰 11

**[심각도: 중요] §7 "에러와 함께 파일 리스트를 출력한다"의 출력 형식이 정의되어 있지 않다**

**대상**: §7 HA 전환

**문제 설명**: "제약사항 위반 시 에러와함께 파일 리스트를 출력한다"는 문장은 운영자가 장애를 해결하기 위해 가장 먼저 보게 될 화면인데도, 출력 매체(표준 출력? 로그 파일? 별도 리포트 파일?), 형식(테이블 이름만? 위반 사유까지?), 개수 제한(수천 개 테이블 중 수백 개가 위반이면 전부 나열하는가?)이 전혀 정의되어 있지 않다. PM 관점에서 이는 "요구사항 완전성" 결함이다 — 이 한 문장만으로는 UX 담당자도 문서 작성자도 다음 단계를 진행할 수 없다.

**구체 예제(시나리오)**:
```text
[상황: 100개 테이블 중 12개가 RK 없음, 3개는 FK 참조 대상이 복제 제외]

cubrid hb start mydb

기대되는 출력 예시(스펙에 없는 것을 리뷰어가 가정해 본 것):
  ERROR: HA mode startup failed due to 15 constraint violation(s).
  [No Replication Key]
    - dba.tbl_a
    - dba.tbl_b
    ... (12개)
  [FK references non-replicated table]
    - dba.orders -> dba.customers (REPLICATION=OFF)
    ... (3개)

-- 스펙은 이런 구조를 전혀 보장하지 않는다. 실제로는 한 줄 요약과 함께
-- 별도 로그 파일 경로만 안내될 수도 있고, 12개 중 처음 1개만 보여주고
-- 멈출 수도 있다. 이 셋 중 무엇이 맞는지 문서로는 알 수 없다.
```

**예제 설명**: 이 가상의 출력 예시는 "이런 정보가 있으면 운영자가 바로 조치할 수 있다"는 것을 보여주기 위한 것이다. 스펙에 이 정도의 상세함이 없으면, 실제 구현이 "위반 테이블 총 개수만 출력"하는 수준으로 끝나도 스펙 위반이 아니게 되어, 사용자 경험이 구현자 재량에 완전히 맡겨진다.

**제안**: 출력 대상(표준 에러 vs 로그 파일), 각 위반 항목에 포함될 필드(테이블명, 위반 사유 코드), 위반이 많을 때의 페이징/제한 정책을 §7에 구체적으로 추가해야 한다.

### 리뷰 12

**[심각도: 중요] §3의 "전환 시" 문장이 능동/피동이 불분명하고, §7과의 관계가 상호 참조 없이 방치되어 있다**

**대상**: §3 "싱글 모드에서 생성된 복제 키가 없는 테이블은 HA모드 전환 시 복제 키를 추가하거나 복제 제외 테이블로 변경할 수 있어야한다"

**문제 설명**: 이 문장은 "~할 수 있어야한다"로 끝나는데, 이것이 (a) "사용자가 HA 전환 전에 미리 이 작업을 해둘 수 있는 기능/권한이 있어야 한다"는 뜻인지, (b) "시스템이 HA 전환 시점에 사용자에게 이를 강제한다"는 뜻인지 구분되지 않는다. §7은 "HA 실행시 제약사항을 확인하며 위반 시 에러를 낸다"고 명확히 사후 검증 방식을 규정하고 있어, §3이 말하는 "전환 시 변경할 수 있어야 한다"와 사실상 같은 내용을 다루는 것으로 보인다. 그런데 두 절이 서로를 참조하지 않아, 독자는 §3과 §7이 같은 요구사항의 다른 표현인지, 별개의 요구사항인지 스스로 추론해야 한다.

**구체 예제(시나리오)**:
```text
독자 A의 해석: "§3은 사용자가 HA 전환 이전 싱글 모드에서 사전 조치를
  취할 수 있다는 안내이고, §7은 그 조치를 안 했을 때 엔진이 막아준다는
  뜻이다. 즉 §3은 권장 워크플로우, §7은 안전장치."

독자 B의 해석: "§3은 'HA 전환 시점에' 시스템이 자동으로 복제 키를
  추가해주거나 복제 제외로 바꿔준다는 뜻이다(마이그레이션 자동화)."

-- 두 해석 모두 문장만으로는 배제되지 않는다. 그런데 §7의 실제 동작
-- ("에러를 내고 파일 리스트 출력") 은 독자 A의 해석과만 일치하고
-- 독자 B의 "자동 변환" 시나리오는 스펙 어디에도 실제로 없다.
```

**예제 설명**: 이 시나리오는 같은 문장을 놓고 두 명의 숙련된 독자가 정반대의 기능(수동 사전 조치 vs 자동 마이그레이션)을 상상할 수 있음을 보여준다. 요구사항 문서에서 이런 이중 해석 여지는 구현 착수 전에 반드시 제거되어야 한다.

**제안**: §3 문장을 "사용자는 HA 전환 이전에 싱글 모드에서 ALTER TABLE로 사전 조치해야 하며, 하지 않을 경우 §7에 정의된 절차에 따라 HA 전환이 실패한다"처럼 §7을 명시적으로 참조하는 문장으로 다시 쓸 것을 제안한다.

### 리뷰 13

**[심각도: 중요] PostgreSQL REPLICA IDENTITY 대비 세분화된 지정 옵션(USING INDEX)이 빠져 있어 경쟁 포지셔닝이 약하다**

**대상**: 배경 설명("PostgreSQL의 REPLICA IDENTITY 컨셉 일부를 채용"), §1

**문제 설명**: PostgreSQL의 `REPLICA IDENTITY`는 `DEFAULT`(PK 자동 사용), `USING INDEX idx_name`(사용자가 특정 UNIQUE 인덱스를 명시적으로 RK로 지정), `FULL`(전체 컬럼 사용), `NOTHING`(RK 없음, UPDATE/DELETE 복제 제한) 네 가지 모드를 제공해, 사용자가 원하는 컬럼 조합을 직접 지정할 수 있다. 이 스펙은 그중 "엔진이 PK 또는 UK 중 하나를 자동으로 고른다"는 `DEFAULT`에 해당하는 부분만 채용했고, **사용자가 명시적으로 "이 UK를 RK로 써라"라고 지정하는 기능(PostgreSQL의 USING INDEX에 해당)이 없다.** 이는 §1의 "UK가 여러 개면 엔진이 순서로 정한다"는 규칙과 맞물려, 사용자가 원하는 RK를 얻으려면 다른 UK들을 모두 없애거나 순서를 조작(리뷰 5 참고)하는 수밖에 없다는 사용성 저하로 이어진다.

**구체 예제(시나리오)**:
```sql
-- 사용자 의도: b를 RK로 쓰고 싶지만 a도 업무상 UNIQUE 제약이 필요함
CREATE TABLE tbl(
    a INT NOT NULL UNIQUE,   -- 업무 규칙상 필요, RK로 쓰이길 원하지 않음
    b INT NOT NULL UNIQUE,   -- 이걸 RK로 쓰고 싶음 (예: 더 안정적인 자연키)
    c INT
);
-- 이 스펙 하에서는 "가장 빠른 선언 순서"인 a가 RK로 자동 선택된다.
-- 사용자가 b를 RK로 지정할 방법이 없다.

-- PostgreSQL이라면:
-- ALTER TABLE tbl REPLICA IDENTITY USING INDEX idx_b;
-- 로 명시적 지정이 가능하다. 이 스펙에는 대응 문법이 없다.
```

**예제 설명**: 이 예제는 사용자가 비즈니스 로직상 두 개의 UNIQUE 제약이 모두 필요하지만 복제 관점에서는 특정 하나만 RK로 쓰고 싶은, 실무에서 드물지 않은 요구를 보여준다. 현재 스펙 설계로는 이 요구를 충족할 방법이 없고, 우회하려면 "원치 않는 컬럼의 UK를 없앤다"는 비즈니스 요구사항 훼손이 필요하다.

**제안**: 최소 기능 출시(MVP) 범위에서 자동 선택만 지원하더라도, 로드맵 상 "명시적 RK 지정 문법"을 향후 버전 계획에 언급해 경쟁 제품 대비 갭이 의도된 단계적 출시임을 문서에 남길 것을 제안한다.

### 리뷰 14

**[심각도: 중요] 하위 버전 unload 파일을 HA 모드로 직접 load하는 경로가 정의되지 않았다**

**대상**: §8 "하위 버전에서 unload 한 데이터 파일에는 복제 여부를 저장하는 변수가 설정되어있지 않으므로 (싱글 모드에서) load 시 모두 복제 테이블로 설정된다"

**문제 설명**: 괄호 안의 "(싱글 모드에서)"라는 조건이 이 문장이 성립하는 유일한 전제인 것처럼 보이는데, 그렇다면 **HA 모드에서 직접 이 하위 버전 덤프 파일을 load하려고 시도하면 어떻게 되는지**가 스펙에 없다. §1에 따르면 RK 없는 테이블은 HA 모드에서 생성 자체가 안 되므로, 하위 버전 덤프에 PK/UK 없는 테이블이 하나라도 섞여 있으면 HA 모드로의 load는 실패해야 할 것 같지만, 이것이 "테이블 단위로 그 테이블만 실패"인지 "전체 load 작업이 중단"되는지 불명확하다.

**구체 예제(시나리오)**:
```text
[하위 버전에서 만든 덤프 파일 old_dump.unl: 테이블 20개, 그중 3개는 PK/UK 없음]

-- 싱글 모드에서 load (스펙이 규정하는 경로)
loaddb -d mydb old_dump.unl
-- §8 규칙대로 20개 모두 REPLICATION=ON, RK 없는 3개 테이블도 일단 생성됨.
-- 이후 HA 전환 시 §7 검증에서 3개가 걸려 에러 + 파일 리스트 출력 (일관성 있음)

-- HA 모드에서 곧바로 load 시도 (스펙에 없는 경로)
cubrid hb start mydb
loaddb -d mydb old_dump.unl
-- RK 없는 3개 테이블을 REPLICATION=ON으로 만들려는 시도는
-- §1 원칙("RK 없으면 HA 모드에서 복제 테이블 생성 불가")과 충돌한다.
-- 이 3개 테이블만 실패하고 나머지 17개는 성공하는가?
-- 아니면 loaddb 전체가 롤백되는가? 스펙은 답이 없다.
```

**예제 설명**: 이 시나리오는 스펙이 명시한 경로(싱글 모드 load 후 HA 전환)를 우회해 곧바로 HA 모드에서 load를 시도하는, 사용자가 충분히 시도할 법한 대안 경로를 보여준다. `loaddb`가 부분 성공/부분 실패를 허용하는 도구인지에 따라 결과가 크게 달라지는데, 스펙은 이 도구의 기존 동작 방식에 기대어 아무 말도 하지 않고 있다.

**제안**: "HA 모드에서 RK 없는 테이블이 포함된 덤프를 load하면 해당 테이블만 실패하고 나머지는 계속 진행한다" 또는 "전체 load가 실패한다" 중 하나를 명시적으로 선택해 기술해야 한다.

### 리뷰 15

**[심각도: 보통] "MySQL 방식은 성능이 느려서 배제"라는 근거가 정량화되어 있지 않다**

**대상**: 배경 설명("MySQL처럼 'PK가 없으면 모든 컬럼을 키로 사용'하는 방식은 성능이 느려서 배제")

**문제 설명**: 이 문장은 스펙 본문이 아니라 리뷰 배경 설명에 있지만, 이 스펙 전체의 설계 근거이자 사용자에게 "왜 CUBRID는 MySQL과 다르게 동작하는가"를 설명할 때 반드시 필요한 근거다. 그런데 "성능이 느려서"라는 정성적 서술 외에 벤치마크 수치, 측정 방법론, 어느 정도 느린지에 대한 정량 데이터가 전혀 없다. 경쟁 제품 대비 포지셔닝 문서(세일즈/마케팅 자료, 기술 백서)를 만들려면 이 근거가 구체적이어야 하는데, 현재로서는 "설계자가 그렇게 판단했다"는 것 외에 검증 가능한 근거가 없다.

**구체 예제(시나리오)**:
```text
[경쟁사 비교 자료를 요청받은 세일즈 엔지니어의 상황]

고객 질문: "MySQL은 PK 없어도 다 복제되던데, CUBRID는 왜 안 됩니까?"

세일즈 엔지니어가 참조할 수 있는 자료: 이 스펙 문서 뿐.
스펙에 있는 답변 재료: "성능이 느려서 배제했다" (수치 없음)

고객의 후속 질문: "얼마나 느린데요? 벤치마크 있나요?"
-> 답변 불가
```

**예제 설명**: 이 시나리오는 기술적으로는 사소해 보이는 근거 부족이 실제 영업/고객 대응 국면에서 바로 막히는 지점이 됨을 보여준다. PM 입장에서는 이 설계 결정의 근거가 되는 벤치마크(예: "전체 컬럼을 키로 쓸 때 UPDATE 처리량이 N% 저하됨")를 스펙 부록이나 별도 근거 문서로 반드시 남겨야 한다고 판단한다.

**제안**: MySQL 방식 대비 성능 벤치마크(측정 조건, 수치)를 스펙 부록 또는 별도 설계 근거 문서로 첨부할 것을 요청한다.

### 리뷰 16

**[심각도: 보통] "복제키 후보"의 집계 범위가 §1과 §4-2에서 다르게 읽힐 수 있다**

**대상**: §1 "UK가 여러개 존재한다면...", §4-2 "다른 복제키 후보가 함께 존재한다면"

**문제 설명**: §1은 "RK 결정" 맥락에서 후보를 말하고, §4-2는 "DDL 제약 완화" 맥락에서 후보를 말한다. PK 하나와 UK 여러 개가 공존하는 테이블에서, RK는 PK로 확정되지만(§1) 이때 UK들도 "복제키 후보"로 카운트되어 §4-2의 "다른 후보가 있으면 모든 DDL 허용" 조건을 만족시키는지, 아니면 "복제키 후보"는 §4-2 맥락에서 "RK 자리를 이어받을 수 있는 대기열" 개념이라 PK가 있는 한 UK는 후보 취급을 안 받는지 불명확하다. (리뷰 2의 모순과 맞물려 있는 문제이지만, 리뷰 2가 예시 12의 직접적 모순을 다뤘다면 이 리뷰는 "후보"라는 용어 자체의 정의 범위를 별도로 지적한다.)

**구체 예제(시나리오)**:
```sql
CREATE TABLE tbl(
    a INT PRIMARY KEY,        -- 현재 RK
    b INT NOT NULL UNIQUE,    -- "후보"로 카운트되는가?
    c INT NOT NULL UNIQUE     -- 이것도 "후보"로 카운트되는가?
);
-- 이 테이블은 §4-2 관점에서 "복제키 후보가 1개"인가 "3개"인가?
-- 답에 따라 예시 12(PK 삭제 금지)의 적용 여부가 달라진다.
```

**예제 설명**: 이 예제는 하나의 테이블 정의만으로도 §4-2의 "후보 개수"를 세는 방식에 따라 정반대의 DDL 허용 여부가 나올 수 있음을 보여준다. 리뷰 2가 지적한 모순을 해소하려면 결국 이 "후보"라는 용어의 카운팅 규칙부터 명확히 정의해야 한다.

**제안**: "복제키 후보"를 "RK로 사용되지 않고 있는, RK와 동일한 자격 요건(PK 또는 NOT NULL UNIQUE)을 만족하는 제약"으로 정의하고, PK가 RK인 상태에서 NOT NULL UNIQUE 제약들이 후보로 카운트되는지 여부를 명문화해야 한다.

### 리뷰 17

**[심각도: 보통] 용어집이 없어 "복제 테이블", "복제 대상 테이블", "RK", "복제키 후보"가 문맥마다 다르게 읽힌다**

**대상**: 스펙 전반(§1, §2, §4, §9)

**문제 설명**: 스펙 전체를 통틀어 "복제 테이블"(§2-1, §3), "복제 대상 테이블"(§1, §5, §9), "복제 제외 테이블"(§1, §2-1)이라는 표현이 혼용된다. 문맥상 "복제 테이블"과 "복제 대상 테이블"은 같은 의미(`REPLICATION=ON`)로 쓰인 것으로 보이지만, 스펙 어디에도 이 둘이 동의어라는 선언이 없다. 짧은 문서에서는 큰 문제가 아닐 수 있지만, 이 스펙을 기반으로 매뉴얼, API 문서, 에러 메시지 문자열을 파생시킬 때 번역자/작성자마다 다른 용어를 골라 쓰게 되는 원인이 된다.

**구체 예제(시나리오)**:
```text
§1: "복제 대상 테이블은 복제 키(RK)가 존재하지 않으면..."
§2-1: "REPLICATION 옵션은 복제 테이블 생성 여부를 설정한다"
§3: "복제 대상 및 복제 제외 테이블을 생성할 수 있다"
§9: "RK가 있는 테이블 역시 복제 제외대상이 될 수 있음"

-- 독자가 "복제 테이블"과 "복제 대상 테이블"이 같은 것인지 확인하려면
-- 네 군데를 모두 대조해서 문맥으로 추론해야 한다. 명시적 동의어 선언이 없다.
```

**예제 설명**: 이 인용 모음은 같은 개념을 가리키는 것으로 보이는 세 가지 표현이 스펙 전체에 흩어져 있음을 보여준다. 신규 합류 개발자나 QA가 테스트 케이스 이름을 지을 때, 혹은 에러 메시지 문자열을 정할 때 이 혼용이 그대로 코드에 반영될 위험이 있다.

**제안**: 스펙 맨 앞에 "용어" 절을 추가해 "복제 테이블 = 복제 대상 테이블 (REPLICATION=ON)", "복제 제외 테이블 (REPLICATION=OFF)", "복제키 후보" 등을 한 번에 정의할 것을 제안한다.

### 리뷰 18

**[심각도: 보통] Oracle GoldenGate 등 PK 없는 테이블을 다루는 대안 방식과의 비교가 문서에 없다**

**대상**: 배경 설명 전반

**문제 설명**: 이 스펙은 MySQL 방식만 비교 대상으로 언급하지만, Oracle GoldenGate나 상용 CDC(Change Data Capture, 변경 데이터 캡처) 솔루션은 PK가 없는 테이블에 대해 "supplemental logging"이라는 방식으로 특정 컬럼 조합을 로그에 추가로 남겨 유사한 문제를 해결한다. 이런 대안이 이 스펙의 접근법(PostgreSQL 방식 채택)보다 CUBRID에 부적합한 이유가 무엇인지 문서화되어 있지 않다. 경쟁 포지셔닝 문서로서는 "왜 PostgreSQL 방식을 골랐고 Oracle 방식은 고려하지 않았는가"에 대한 답이 있어야 향후 고객 문의나 경쟁 비교표 작성에 대응할 수 있다.

**구체 예제(시나리오)**:
```text
[경쟁 비교표를 작성해야 하는 상황]

  제품            | PK 없는 테이블 복제 지원 방식
  ---------------|--------------------------------
  MySQL          | 전체 컬럼을 키로 사용 (성능 저하)
  PostgreSQL     | REPLICA IDENTITY (DEFAULT/USING INDEX/FULL/NOTHING)
  Oracle GoldenGate | Supplemental logging (컬럼 조합 명시 가능)
  CUBRID(신규)    | RK 자동 선택(PK 또는 UK), REPLICATION 옵션 (?)

-- 이 스펙만으로는 CUBRID 행을 채울 수는 있지만, Oracle 행과 비교했을 때
-- "왜 CUBRID는 Oracle처럼 컬럼 조합을 명시하는 방식을 택하지 않았는가"에
-- 대한 답이 스펙에 없어 비교표에 각주를 달 수 없다.
```

**예제 설명**: 이 비교표는 PM이 실제로 만들어야 할 산출물의 예시다. 스펙에 대안 검토 근거가 없으면 이 표의 CUBRID 행 옆에 붙일 설명을 스펙 저자에게 별도로 물어봐야 하고, 이는 문서가 자기 완결적이지 않다는 뜻이다.

**제안**: 배경 설명에 "Oracle GoldenGate류의 supplemental logging 방식은 [이러이러한 이유로] 이번 범위에서 배제했다"는 한두 문장을 추가할 것을 제안한다.

### 리뷰 19

**[심각도: 사소] "5-1. CRATE TABLE 예시" 오타**

**대상**: §5-1 제목

**문제 설명**: 소제목이 "CREATE TABLE"이 아니라 "CRATE TABLE"로 오타가 나 있다. 기능적 영향은 없으나, 공식 스펙 문서에 남는 오타는 문서의 신뢰도를 떨어뜨리고, 이 문서를 번역하거나 재가공할 때 그대로 복사되어 전파될 수 있다.

**구체 예제**:
```text
원문: "5-1. CRATE TABLE 예시"
수정안: "5-1. CREATE TABLE 예시"
```

**예제 설명**: 단순 오타이지만, 앞서 §2-1의 제목이 "CREATE TABLE 옵션 추가"로 정확히 쓰여 있는 것과 대조되어, 같은 문서 안에서도 교정 일관성이 없었음을 보여준다.

**제안**: 전체 문서에 대한 맞춤법 검사 1회를 배포 전 체크리스트에 추가할 것을 제안한다.

### 리뷰 20

**[심각도: 사소] 예시 번호 매김과 소제목 배치가 절마다 형식이 달라 가독성이 떨어진다**

**대상**: §2-2(예시 5, 6 사이에 "HA 환경에서 PK를 복제키로..." 문장이 번호 없이 삽입됨), §4-2(예시 14 앞에 "UK 를 복제키로 사용하는 경우"라는 소제목이 예시 11~13 뒤에만 붙고 앞의 "PK를 복제키로 사용하는 경우"와 들여쓰기/강조 방식이 다름)

**문제 설명**: 어떤 절에서는 소제목이 예시 그룹 앞에 붙고(§4-2의 "PK를 복제키로 사용하는 경우"), 어떤 절에서는 소제목 없이 바로 본문 설명 문장이 예시 사이에 끼어 있다(§2-2의 "HA 환경에서 PK를 복제키로 사용하던 중..." 문장은 예시 6과 예시 7 사이에 있으면서도 독립된 번호나 제목이 없다). 이런 형식 불일치는 큰 의미 손실은 없지만, 문서를 처음 읽는 신규 인원이 "이 문장이 예시 6에 속한 설명인지, 예시 7의 도입부인지" 헷갈리게 만든다.

**구체 예제**:
```text
...
예시 6. REPLICATION = OFF
csql> ALTER TABLE tbl REPLICATION=OFF;
OK

HA 환경에서 PK를 복제키로 사용하던 중 다른 컬럼으로 변경해야한다면    <- 소제목 없음
다음 SQL문을 사용해 변경할 수 있다.
예시 7. Multiple ALTER
...
```

**예제 설명**: 위 인용에서 굵게 표시할 만한 전환 문장("HA 환경에서 PK를...")이 예시 6의 결과(OK) 바로 뒤, 예시 7의 캡션 바로 앞에 소제목 없이 끼어 있어, 이 문장이 예시 6에 대한 부연 설명인지 예시 7의 도입부인지 시각적으로 구분되지 않는다.

**제안**: 모든 절에서 "설명 문단 -> 소제목 -> 예시" 순서를 통일된 형식(예: 굵은 소제목 + 번호)으로 재구성할 것을 제안한다. 사소하지만 문서 전체의 일관성을 위해 최종 편집 단계에서 처리할 것을 권장한다.
