# CUBRID HA 복제 개선 스펙 리뷰 — DB 엔지니어(운영/DBA) 1년차 관점

## 리뷰어 소개

나는 입사 1년차 DB 엔지니어로, 아직 대규모 장애를 혼자 처리해본 경험은 없고 선임의 런북(runbook, 장애 대응 절차서)을 따라 움직이는 단계다. 평소 업무는 백업/복원(unloaddb/loaddb), 복제 지연 모니터링, HA(High Availability, 이중화를 통해 장애 시에도 서비스를 계속하는 구성) 상태 점검, 그리고 스키마 변경 요청 처리다. 이 리뷰는 "이 문서만 들고 당직 중 새벽에 장애를 처리할 수 있는가"를 기준으로 본다.

## 총평

이 스펙은 REPLICATION 옵션과 RK(Replication Key, 복제를 위해 각 행을 식별하는 키)라는 개념 자체는 합리적이고, PostgreSQL의 REPLICA IDENTITY 컨셉을 참고했다는 설명도 납득이 간다. 그러나 문서는 "무엇이 되고 안 되는가"라는 DDL(Data Definition Language, 테이블 구조를 정의/변경하는 SQL) 문법 규칙에는 공을 들인 반면, 정작 운영자가 매일 마주치는 질문들 — 언제 RK가 재선택되는가, HA 전환 실패 시 어디서 로그를 봐야 하는가, 신규 슬레이브를 어떻게 조인시키는가, 백업 복원 순서는 어떻게 되는가 — 에는 답을 주지 않는다. 게다가 §8과 §9 사이에는 명백히 서로 모순되는 문장이 존재해서(리뷰 2 참조), 신입인 내가 읽어도 어느 쪽을 믿어야 할지 판단이 서지 않는다. 예제 코드에도 SQL 문법 오류와 테이블명 재사용 충돌이 섞여 있어, 이 문서를 그대로 신입 교육 자료나 운영 매뉴얼로 쓰기는 위험하다고 판단한다.

리뷰 1

**[심각도: 치명] 복제 키(RK)가 "정적으로 한 번 정해지는지" "스키마 변경마다 재평가되는지"에 대한 정의가 스펙 전체에 없다**

대상: §1(제약 사항), §4-2(ALTER TABLE)

문제 설명: §1은 "PK가 존재한다면 PK가 복제 키가 됨", "PK가 없이 UK가 존재한다면 UK가 복제 키가 됨"이라고 규칙만 나열한다. 그런데 §4-2 예시 14에서는 UK를 RK로 쓰던 테이블에 PK를 새로 추가하는 것이 허용(OK)된다고 나온다. PK를 추가하는 순간, §1의 규칙에 따르면 이제 이 테이블의 RK는 "PK가 존재하므로 PK"가 되어야 한다. 즉 RK가 UK에서 PK로 자동으로 바뀐 것이다. 그런데 이 "재선택이 언제, 어떤 트리거로 일어나는가"에 대한 설명이 스펙 어디에도 없다. 테이블 생성 시 한 번만 결정되고 이후 고정되는 값인지(그렇다면 예시 14는 모순), 아니면 매 DDL마다 엔진이 재평가하는 값인지(그렇다면 그 재평가 시점과 절차, 그리고 그 순간 진행 중이던 복제 트랜잭션의 처리 방식) 알 수 없다.

구체 예제:
```sql
-- 1단계: UK만 있는 복제 테이블 생성 (RK = UK 'b')
csql> CREATE TABLE tbl(
    a INT,
    b INT NOT NULL UNIQUE
);

-- 2단계: 여기에 PK를 추가 (예시 14에 따르면 OK)
csql> ALTER TABLE tbl ADD CONSTRAINT PRIMARY KEY(a);

-- 이 시점에 tbl의 RK는 무엇인가? 여전히 b(UK)인가, 새로 생긴 a(PK)인가?
-- 만약 a(PK)로 바뀌었다면, 그 사이 슬레이브로 이미 전송된 b 기준 UPDATE/DELETE 로그는
-- 어떻게 처리되는가?
csql> UPDATE tbl SET a = 100 WHERE b = 1;
```

예제 설명: 이 시나리오는 "RK가 UK였던 테이블에 나중에 PK가 추가되는" 아주 흔한 스키마 진화 패턴을 보여준다. 신입 운영자 입장에서는 이 ALTER 문이 성공(OK)했다는 것만 스펙에서 확인할 수 있을 뿐, 그 결과로 RK가 바뀌었는지 여부를 `show create table`이나 `db_class` 조회로 언제 다시 확인해야 하는지조차 판단 기준이 없다. RK 전환 시점을 모르면, 복제 지연 모니터링 중 이상 신호가 떴을 때 "지금 RK가 바뀌는 순간이라 일시적인 현상인지" "진짜 장애인지"를 구분할 수 없다.

제안: RK는 (a) 테이블 생성 시 1회 고정, (b) DDL마다 재평가되는 동적 값 중 어느 쪽인지 명시하고, 재평가되는 경우라면 재평가가 일어나는 정확한 트리거(어떤 DDL 종류)와 전환 시점의 로그/알림 방법을 §4-2에 추가해야 한다.

리뷰 2

**[심각도: 치명] §8과 §9의 "복제 여부 미설정 시 기본값" 서술이 서로 모순된다**

대상: §8(UNLOADDB & LOADDB) vs §9(SUMMARY)

문제 설명: §8은 "복제 여부를 저장하는 변수가 설정되어 있지 않다면 복제 대상(Default)으로 간주한다"고 명시한다. 그런데 §9 SUMMARY 마지막 항목은 "UNLOADDB 시 복제 대상 여부를 함께 출력해야하며, 이를 포함하지 않는 테이블은 모두 복제 제외 테이블이다"라고 정반대로 말한다. 하나는 "값이 없으면 복제 대상(ON)", 다른 하나는 "값이 없으면 복제 제외(OFF)"다. 이는 단순 오탈자 수준이 아니라 백업/복원 운영 절차의 핵심을 뒤집는 모순이다.

구체 예제(장애 복구 시나리오):
```
1) 하위 버전 CUBRID(REPLICATION 옵션 미지원)에서 운영 중이던 DB를 unloaddb로 백업한다.
   $ unloaddb -o backup.unl -i backup.idx mydb

2) 새 버전으로 업그레이드 후, 이 백업을 loaddb로 복원한다.
   $ loaddb -d mydb -o backup.unl -i backup.idx mydb

3) 이 백업 파일에는 REPLICATION 여부를 저장하는 변수가 애초에 존재하지 않는다
   (하위 버전 포맷이므로).

4) §8을 믿으면: 복원된 모든 테이블은 REPLICATION=ON(복제 대상)이 된다.
   §9를 믿으면: 복원된 모든 테이블은 REPLICATION=OFF(복제 제외)가 된다.
```

예제 설명: 이 시나리오는 업그레이드 후 첫 복원이라는, 실제로 매우 자주 발생하는 운영 작업이다. §8대로라면 모든 테이블이 복제 대상이 되어 곧바로 HA 전환을 시도할 수 있지만(RK가 없는 테이블이 있으면 §7에 따라 실패), §9대로라면 모든 테이블이 복제 제외가 되어 HA로 전환해도 아무 데이터도 슬레이브에 복제되지 않는, 훨씬 위험한 조용한 실패(silent failure)가 발생한다. 1년차인 내가 이 문서만 보고 복구 작업을 한다면 어느 결과를 기대해야 할지 알 수 없고, 실제 검증 없이 운영에 반영했다가 "슬레이브에 데이터가 하나도 안 갔는데 왜?"라는 사고로 이어질 수 있다.

제안: 두 문장 중 하나가 오기(誤記)임이 명백하므로 즉시 통일해야 한다. 겸사겸사 §8 문장도 "하위 버전에서 unload한 데이터는 (싱글 모드에서) load 시 모두 복제 테이블로 설정된다"고 뒤에서 재확인하고 있으므로, §9가 오기일 가능성이 높아 보인다. 다만 이는 추정이며 스펙 작성자의 확인이 필요하다.

리뷰 3

**[심각도: 중요] §4-1 예시 10이 §2-1 예시 1과 같은 테이블명을 재사용해 실제로는 다른 에러가 날 수 있다**

대상: §4-1 예시 10, §2-1 예시 1

문제 설명: 예시 1은 `CREATE TABLE repl_table_with_rk(...)`로 PK가 있는 테이블을 만드는 예제다. 예시 10은 "복제 테이블에는 반드시 복제 키 후보가 1개 이상 필요하다"는 것을 보여주려고 `CREATE TABLE repl_table_with_rk( a INT );`(RK 없음)를 실행해 ERROR가 난다고 서술한다. 그런데 두 예제는 완전히 동일한 테이블 이름(`repl_table_with_rk`)을 쓴다. 문서 순서대로 두 예제를 그대로 실습하면, 예시 10의 ERROR는 "RK가 없어서"가 아니라 "테이블이 이미 존재해서"(이미 예시 1에서 같은 이름으로 만들었으므로) 발생한다. 즉 예제가 보여주려는 인과관계(RK 없음 → 에러)와 실제로 재현되는 인과관계(이름 중복 → 에러)가 다르다.

구체 예제:
```sql
-- 예시 1 (§2-1)
csql> CREATE TABLE repl_table_with_rk(
    a INT PRIMARY KEY,
    b INT NOT NULL UNIQUE,
    c INT
);
-- OK

-- 예시 10 (§4-1), 같은 세션/같은 DB에서 그대로 이어서 실행하면
csql> CREATE TABLE repl_table_with_rk(
    a INT
);
-- 실제 에러 메시지는 "table repl_table_with_rk already exists" 계열이지,
-- "RK 후보 없음" 에러가 아니다.
```

예제 설명: 이 예제는 문서를 위에서부터 순서대로 따라 하며 배우는 신입 입장에서 특히 문제가 된다. 나는 이 문서를 교육 자료 삼아 테스트 DB에 예제를 순서대로 실행해볼 텐데, 예시 10에서 기대한 에러 메시지(RK 부재)와 실제 에러 메시지(이름 충돌)가 다르면 "내가 뭔가 잘못 이해했나"하고 스스로를 의심하게 되고, 결과적으로 RK 필수 제약이 실제로 어떻게 동작하는지 검증하지 못한 채 넘어가게 된다.

제안: 예시 10의 테이블명을 `repl_table_with_rk`가 아닌 새 이름(예: `repl_table_no_rk_fail`)으로 바꾸거나, "예시 1을 실행하지 않은 새 DB에서"라는 전제를 명시해야 한다.

리뷰 4

**[심각도: 치명] §7 "HA 전환 실패 시 파일 리스트 출력"이 구체적으로 어디에 어떤 형식으로 남는지 전혀 알 수 없다**

대상: §7(HA 전환)

문제 설명: §7은 "HA 실행시 다음 사항을 제약사항을 확인하며, 제약사항 위반 시 에러와함께 파일 리스트를 출력한다"고만 되어 있다. 신입 운영자가 실제로 알아야 할 것은: (1) 이 출력이 콘솔 표준출력인지, 로그 파일인지, 로그 파일이라면 경로는 어디인지, (2) "파일 리스트"라는 표현이 왜 나왔는지 — 위반 대상은 "테이블"인데 왜 "파일"이라고 부르는지(CUBRID 내부적으로 테이블이 파일 단위로 관리되는 것을 아는 사람만 이해 가능한 표현), (3) 이 리스트에 담기는 정보가 테이블명뿐인지 아니면 위반 사유(RK 없음 vs FK 참조 테이블 미복제)까지 구분되어 나오는지, 이다.

구체 예제(장애 대응 시나리오):
```
[당직 중 새벽 3시]
1) 운영자가 신규 버전 적용 후 HA 재기동을 시도한다.
   $ cubrid hb start mydb

2) 스펙에 따르면 제약 위반 시 "에러와 함께 파일 리스트"가 출력된다.
   하지만 운영자는 다음 중 무엇을 봐야 하는지 알 수 없다:
   - 콘솔에 즉시 출력되는가?
   - $CUBRID/log/mydb 아래 어떤 로그 파일인가?
   - cubrid hb status 로 확인 가능한가?

3) "파일 리스트"에 10개 테이블이 있다고 가정하자.
   그 중 몇 개는 "RK 없음"이 원인이고 몇 개는 "FK 참조 테이블 미복제"가 원인인데,
   이 둘을 구분해서 조치(RK 추가 vs REPLICATION=OFF 참조 테이블 승격)해야 하지만
   스펙은 원인 구분 표시 여부를 언급하지 않는다.
```

예제 설명: 이 시나리오는 실제 새벽 장애 대응에서 "명령을 실행했더니 실패했다"까지는 알겠는데, "그래서 무엇을 어디서 봐야 하는지" 모르는 상황을 보여준다. 1년차인 나는 이런 상황에서 선임에게 전화를 걸거나 소스코드를 뒤져야 하는데, 이는 스펙 문서가 운영 매뉴얼 역할을 못 한다는 뜻이다.

제안: 출력 위치(표준출력/로그 파일 경로), 출력 형식(테이블명만인지 사유 포함인지), 그리고 이 정보를 스크립트로 파싱해 자동화할 수 있는 형식(JSON 등)인지 여부를 §7에 명시해야 한다.

리뷰 5

**[심각도: 치명] 이미 HA로 운영 중인 상태에서 "ON 테이블이 참조하는 테이블을 OFF로 바꾸는" 경로가 막혀 있지 않다**

대상: §4(HA 제약사항), §5(외래키)

문제 설명: §5는 CREATE TABLE 시점과 HA 전환(hb start) 시점에 "FK가 참조하는 테이블이 복제 대상이 아니면 에러"라고 명시한다. 그런데 이미 HA가 정상적으로 실행 중이고, `orders`(REPLICATION=ON, FK가 `customers`를 참조)와 `customers`(REPLICATION=ON)가 모두 잘 돌고 있는 상태에서, 누군가 `ALTER TABLE customers REPLICATION=OFF;`를 실행하면 어떻게 되는지에 대한 언급이 없다. §4는 "HA 환경 복제 제외테이블은 REPLICATION=ON으로 변경하는 것 외의 모든 DDL을 사용할 수 있다"고 하는데, 이는 이미 OFF인 테이블 얘기이고, ON→OFF 전환 자체를 FK 참조 관계 기준으로 막는다는 서술은 어디에도 없다. 즉 스펙이 그림(diagram)으로까지 그려 강조한 "FK 참조 테이블이 슬레이브에 없어서 애플리케이션이 실패하는" 바로 그 사고를, CREATE TABLE 경로는 막아놓고 ALTER TABLE 경로는 막아놓지 않은 것으로 읽힌다.

구체 예제:
```sql
-- 이미 HA로 정상 운영 중이라고 가정 (§5 예시 17과 동일한 스키마)
-- customers: REPLICATION=ON, orders: REPLICATION=ON, FK orders.customer_id -> customers.customer_id

-- 운영자가 customers 테이블을 무심코 복제 제외로 전환
csql> ALTER TABLE customers REPLICATION=OFF;
-- 이 문장이 OK로 성공하는가, ERROR가 나는가? 스펙에 답이 없다.

-- 만약 OK라면, 이제 orders는 여전히 REPLICATION=ON이고 customers를 FK로 참조하는데
-- customers 데이터는 더 이상 슬레이브로 복제되지 않는다.

-- 이후 Failover 발생
-- 애플리케이션이 슬레이브의 orders에 접근 -> customer_id로 customers를 조인/참조하려는 순간
-- 그림(image.png)에서 경고한 것과 동일한 "참조 테이블 없음" 상황 재현
```

예제 설명: 이 예제는 스펙이 CREATE TABLE 시점에만 검증하고 이미 운영 중인 테이블의 상태 변경(ALTER)에는 같은 검증을 적용하지 않을 경우, 결국 스펙이 막으려던 사고가 ALTER라는 뒷문으로 그대로 재현됨을 보여준다. 신입 운영자 입장에서 이건 특히 위험한데, "REPLICATION=OFF로 바꾸는 것 자체는 항상 허용된다"(§4)는 문장만 읽으면 이 ALTER가 당연히 성공할 거라 믿게 되고, FK 관계를 일일이 손으로 확인하지 않으면 실수로 이 사고를 낼 수 있다.

제안: §4 또는 §5에 "다른 ON 테이블의 FK가 참조하는 테이블은 ALTER TABLE ... REPLICATION=OFF로 전환할 수 없다"는 제약을 명시하거나, 만약 의도적으로 허용한다면 그 근거와 이때의 사후 감지/경고 방법을 §5 마지막 문단에 추가해야 한다.

리뷰 6

**[심각도: 중요] 신규 슬레이브 노드를 HA 그룹에 새로 추가(조인)할 때 REPLICATION=OFF 테이블의 초기 데이터 처리 방법이 전혀 없다**

대상: 문서 전체(운영 시나리오 공백)

문제 설명: 스펙은 "이미 돌아가는 복제 스트림에서 REPLICATION 옵션에 따라 어떤 변경분을 보내느냐"만 다룬다. 그런데 실무에서 매우 흔한 작업인 "신규 슬레이브 노드 추가"(예: 기존 슬레이브를 백업해서 새 서버에 복사 후 HA 그룹에 편입) 시나리오가 전혀 언급되지 않는다. 이 절차에서는 보통 마스터의 전체 데이터를 백업(unloaddb 등)해서 새 슬레이브에 복원한 뒤 복제를 이어붙이는데, 이때 REPLICATION=OFF 테이블도 초기 스냅샷에는 포함되는가? 포함된다면 이후 계속 복제되지 않을 테이블의 데이터가 신규 슬레이브에만 "일회성으로" 존재하게 되어, 기존 슬레이브와 신규 슬레이브 간에도 데이터가 어긋난다.

구체 예제:
```
[신규 슬레이브 추가 절차 (일반적인 CUBRID HA 운영 방식 가정)]
1) 마스터에서 전체 백업
   $ unloaddb -o full.unl mydb   -- customers(OFF), orders(ON) 모두 포함해서 덤프됨

2) 신규 서버에 복원
   $ loaddb -d mydb -o full.unl mydb
   -- 이 시점 신규 슬레이브에는 customers(OFF)의 "그 순간" 데이터가 들어있음

3) 신규 슬레이브를 HA 그룹에 편입, 복제 스트림 연결 시작
   $ cubrid hb start mydb

4) 이 시점 이후 customers는 REPLICATION=OFF이므로 변경분이 더 이상 오지 않음
   -> 신규 슬레이브의 customers는 "편입 시점에 멈춘 스냅샷"으로 영구히 고정됨
   -> 기존에 이미 떠 있던 슬레이브의 customers(만약 그 슬레이브도 과거 언젠가
      스냅샷을 떴다면 그 시점이 다름)와 서로 다른 데이터를 가지게 됨
```

예제 설명: 이 시나리오는 REPLICATION=OFF가 "복제하지 않는다"는 것 이상으로, 백업/복원 기반의 신규 노드 추가 절차와 결합했을 때 슬레이브들 사이에서조차 데이터가 제각각이 되는 문제를 보여준다. 1년차 운영자가 매뉴얼대로 신규 슬레이브를 추가했다가, 나중에 "왜 슬레이브1과 슬레이브2의 customers 데이터가 다르지?"라는 질문에 답할 근거가 이 스펙에는 없다.

제안: 신규 슬레이브 조인 절차에서 REPLICATION=OFF 테이블을 어떻게 처리할지(제외하고 복사할지, 복사하되 문서화만 할지) 별도로 명시해야 한다.

리뷰 7

**[심각도: 중요] "어떤 테이블이 복제 제외인지" 한눈에 확인하는 일괄 조회 수단이 없다**

대상: §2-3(REPLICATION 조회)

문제 설명: §2-3은 특정 테이블 하나에 대해 `show create table`이나 `select * from db_class`로 REPLICATION 값을 확인하는 예시만 보여준다. 그런데 운영자가 실제로 궁금한 질문은 "이 DB 전체에서 REPLICATION=OFF인 테이블이 몇 개이고 무엇무엇인지"다. 테이블이 수백 개인 운영 DB에서 테이블마다 `show create table`을 실행하는 것은 비현실적이다. `db_class`를 직접 `WHERE replication = 'OFF'`로 조회할 수 있다는 보장도 스펙에 명시돼 있지 않다(카탈로그 뷰의 컬럼명과 조회 가능 여부는 예시에서 결과로만 보여줄 뿐, "조회 가능하다"고 문서화하지 않았다).

구체 예제:
```sql
-- 운영자가 원하는 질의: 이 DB에서 복제 제외 테이블 전체 목록
csql> SELECT class_name, owner_name, replication
      FROM db_class
      WHERE replication = 'OFF';

-- 스펙 예시 9는 이 컬럼이 db_class 결과에 존재함을 "결과 화면"으로만 보여줄 뿐,
-- 이런 WHERE 절 사용이 공식적으로 지원되는 조회 방법인지 명시하지 않는다.
-- 또한 시스템 카탈로그 테이블(db_ 로 시작)이나 뷰까지 이 목록에 섞여 나오는지,
-- 필터링이 필요한지도 알 수 없다.
```

예제 설명: 이 예제는 "예시로 보여준 단일 조회"와 "운영자가 실제로 필요로 하는 전수 점검성 조회"의 간극을 보여준다. 모니터링/점검 스크립트를 짜야 하는 나로서는, 이 컬럼이 정식으로 문서화된 조회 인터페이스인지 우연히 결과에 노출된 내부 필드인지 구분이 안 되면, 향후 버전에서 필드명이 바뀌어도 알림을 못 받을 위험이 있다.

제안: §2-3에 "복제 제외 테이블 전체 목록을 조회하는 공식 방법"(전용 카탈로그 뷰 또는 `cubrid` 유틸리티 명령)을 명시하고, `db_class.replication` 컬럼이 안정적인 공개 인터페이스임을 확인해야 한다.

리뷰 8

**[심각도: 중요] 업그레이드 후 첫 HA 전환에서 대량 실패가 발생할 수 있는데, 사전 점검(dry-run) 수단이 없다**

대상: §7(HA 전환), §8(UNLOADDB & LOADDB)

문제 설명: §8에 따르면 하위 버전에서 unload한 데이터를 싱글 모드에서 load하면 모든 테이블이 "복제 테이블"로 설정된다(§9와 모순되는 점은 리뷰 2 참조하되, 여기서는 §8 쪽을 기준으로 본다). 그런데 하위 버전 스키마에는 RK가 없는 테이블(PK도 UK도 없는 테이블)이 얼마든지 존재할 수 있다. 이 상태에서 HA로 전환하면 §7에 따라 "RK 없는 복제 테이블"이 전부 실패 목록에 걸린다. 문제는 이게 테이블 1~2개가 아니라 스키마 전체에 걸쳐 수십~수백 개가 될 수 있다는 점인데, 이걸 실제로 HA를 기동해보기 전에는(§7의 실패 시점에만 확인 가능) 미리 알 방법이 스펙에 없다.

구체 예제(업그레이드 런북 시나리오):
```
1) 구버전(REPLICATION 미지원) 운영 DB를 unloaddb로 백업
2) 신버전으로 업그레이드, 싱글 모드에서 loaddb로 복원
   -> §8에 따라 전 테이블이 REPLICATION=ON(복제 테이블)로 생성됨
3) 곧바로 HA 전환 시도
   $ cubrid hb start mydb
   -> RK 없는 테이블이 예를 들어 120개 존재한다면, 이 120개가 한꺼번에
      §7의 "제약 위반 파일 리스트"에 실패로 잡힌다.
4) 그런데 이 스펙 어디에도 "HA 기동 전에 미리 RK 유무를 스캔하는 명령"이 없다.
   운영자는 실제로 hb start를 실행해 실패를 겪은 뒤에야 문제 테이블 목록을 안다.
```

예제 설명: 이 예제는 "실패하고 나서야 무엇이 문제인지 안다"는 구조 자체가 업그레이드처럼 다운타임이 걸린 작업에서는 치명적임을 보여준다. 실패 후 리스트를 받아서 120개 테이블에 일일이 RK를 추가하거나 REPLICATION=OFF로 바꾸는 작업을 하는 동안 서비스는 싱글 모드로 방치된다. 사전에 "지금 이 스키마로 HA 전환하면 몇 개 테이블이 실패할지" 미리 알 수 있었다면 업그레이드 작업 시간을 정확히 산정하고 사전에 조치할 수 있었을 것이다.

제안: HA를 실제로 기동하지 않고도 현재 스키마의 제약 위반 테이블을 미리 나열해주는 점검(예: `cubrid hb check` 류) 기능과 그 사용법을 §7에 추가해야 한다.

리뷰 9

**[심각도: 중요] unloaddb/loaddb 시 "스키마(제약조건) 복원"과 "REPLICATION 속성 복원"의 순서 관계가 불명확하다**

대상: §8(UNLOADDB & LOADDB)

문제 설명: §8은 "복제 테이블의 경우 큐브리드는 자동으로 RK를 할당한다"고 하는데, RK는 §1에 따르면 PK/UK 제약조건이 있어야 존재할 수 있는 파생 개념이다. 즉 RK 자체를 loaddb가 직접 만드는 게 아니라, 스키마 파일(.schema, .object 등 unloaddb가 만드는 여러 파일 중 스키마 정의 파일)에 있는 PK/UK 제약조건이 먼저 만들어져야 그 결과로 RK가 자동으로 정해지는 구조일 것이다. 그런데 "복제 테이블 여부를 저장하는 변수"가 스키마 파일과 별도 파일에 있는지, 같은 파일 안에 있는지, 그리고 이 두 정보(제약조건, REPLICATION 여부)의 로드 순서가 어떻게 보장되는지에 대한 설명이 없다. 만약 REPLICATION=ON 표시를 제약조건보다 먼저 적용하는 구현이라면, "복제 테이블인데 RK 후보가 아직 없는" 중간 상태가 loaddb 도중 발생할 수 있고, 이는 §4-1에서 정의한 "RK 없는 복제 테이블은 생성 불가"라는 규칙과 충돌한다.

구체 예제:
```
$ unloaddb -o mydb.unl -s mydb.schema mydb
-- mydb.schema (스키마 정의 파일) 안에 아래와 같은 내용이 있다고 가정
CREATE TABLE tbl(
    a INT,
    CONSTRAINT pk_tbl_a PRIMARY KEY(a)
) REPLICATION = ON;

$ loaddb -d mydb -s mydb.schema -o mydb.unl mydb
-- 질문: loaddb 내부적으로 이 CREATE TABLE 문이 실행되는 순간, PRIMARY KEY 제약과
-- REPLICATION=ON이 "동시에" 하나의 CREATE TABLE 문으로 적용되는가?
-- 아니면 내부적으로 "테이블 생성(제약없음) -> REPLICATION 속성 설정 -> 제약 추가"처럼
-- 단계가 나뉘어 그 사이에 RK 없는 복제 테이블 상태를 통과하는가?
```

예제 설명: 겉보기엔 사소해 보이지만, 이 순서가 명시되지 않으면 loaddb 도중 프로세스가 죽거나 중단됐을 때(예: 디스크 풀, 강제 종료) 어떤 중간 상태로 DB가 남는지 예측할 수 없다. 장애 복구 중인 운영자가 "loaddb가 절반쯤 실행되다 멈췄는데, 지금 이 DB 상태가 정합한지" 판단하려면 이 순서 보장이 문서화되어 있어야 한다.

제안: unloaddb가 생성하는 파일 구성과 loaddb의 적용 순서(스키마 제약조건 → REPLICATION 속성, 혹은 그 역순)를 §8에 명시하고, 중단 시 재시도/복구 절차도 함께 기술해야 한다.

리뷰 10

**[심각도: 중요] "HA 실행 시" 확인한다는 FK 참조 무결성 검사가 이후 런타임 변화(테이블 신규 추가 등)에 대해서는 언제, 누가, 어떻게 재검사하는지 불명확하다**

대상: §5(외래키), §7(HA 전환)

문제 설명: §5는 "HA 모드 실행 시 외래키 테이블에서 참조하는 테이블의 상태도 확인해 ... 에러를 출력할 수 있어야한다"고 되어 있다. 이 문장의 주어인 "HA 모드 실행 시"는 §1의 정의("cubrid hb start로 큐브리드를 실행시킨 상태")를 따르면 딱 그 기동 시점의 검사로 읽힌다. 그렇다면 이미 HA가 잘 돌고 있는 도중에 새로운 FK 관계가 추가되는 경우(§5-2 예시 19, 22처럼 ALTER로 FK를 추가/제거하는 경우)는 §5-2에서 이미 개별 DDL 단위로 막고 있어 괜찮다고 쳐도, "이미 존재하던 FK 관계의 참조 테이블 상태가 바뀌는" 리뷰 5의 시나리오(ON→OFF 전환)는 기동 시점 검사로는 절대 잡히지 않는다. 즉 §5의 "확인"이 1회성 기동 검사인지 상시 감시인지 스펙이 답을 주지 않는다.

구체 예제:
```
[운영 중 모니터링 관점 시나리오]
1) HA가 6개월째 정상 운영 중
2) 그 사이 누군가 customers 테이블을 REPLICATION=OFF로 바꿈(리뷰5의 경로가 실제로 열려있다면)
3) 운영자가 "지금 이 순간 FK 무결성 위반 상태의 테이블이 있는지" 확인하고 싶다.
   -> cubrid hb status 로 확인 가능한가? 별도 점검 명령이 있는가?
   -> 아니면 다음 Failover가 실제로 터져서 애플리케이션 에러가 나야만 알게 되는가?
```

예제 설명: 이 예제는 모니터링 관점에서 "사전에 위험 상태를 감지"하는 것과 "사고가 터진 뒤에 원인을 안다"는 것의 차이를 보여준다. HA의 존재 이유가 장애 대응인데, 그 장애 대응 능력 자체를 무너뜨리는 상태(FK 참조 무결성 깨짐)를 상시 감시할 방법이 없다면, 운영자는 언제 터질지 모르는 잠재 장애를 안고 사는 셈이다.

제안: FK 참조 무결성 검사를 HA 기동 시점뿐 아니라 상시(또는 주기적) 점검 명령으로 제공하고, 위반 상태를 모니터링 지표(예: 기존 fail_count와 유사한 카운터)로 노출해야 한다.

리뷰 11

**[심각도: 중요] UK가 여러 개일 때 "테이블내에 명시된 순서 중 가장 빠른 순서"라는 기준이 모호하다**

대상: §1(제약 사항)

문제 설명: "UK가 여러개 존재한다면 큐브리드 엔진에 의해 이 중 하나가 선택된다(ex. 테이블내에 명시된 순서 중 가장 빠른 순서)"라는 문장에서 "명시된 순서"가 무엇을 기준으로 하는지 알 수 없다. 후보는 최소 세 가지다: (1) CREATE TABLE 문에서 컬럼/제약이 나열된 순서, (2) UK 제약이 실제로 생성(ALTER로 추가)된 시간 순서, (3) 카탈로그 내부의 인덱스 ID 순서. 이 셋은 서로 다른 결과를 낼 수 있다.

구체 예제:
```sql
csql> CREATE TABLE tbl(
    a INT NOT NULL UNIQUE,   -- CREATE TABLE 문에서는 b보다 먼저 나열
    b INT NOT NULL UNIQUE
);

-- 이후
csql> ALTER TABLE tbl DROP CONSTRAINT u_tbl_a;   -- a의 UK 제거
csql> ALTER TABLE tbl ADD CONSTRAINT UNIQUE(a);  -- a의 UK 다시 추가 (b보다 나중에 "생성"됨)

-- 지금 tbl의 RK는 a인가 b인가?
-- "CREATE TABLE 문에서의 나열 순서" 기준이면 a (원래 먼저 썼으니까)
-- "생성 시각(제약이 실제로 만들어진 시간)" 기준이면 b (a를 나중에 다시 만들었으니까)
```

예제 설명: 이 예제는 "명시된 순서"라는 표현이 정적인 텍스트상 위치를 말하는지, 동적인 생성 이력을 말하는지에 따라 답이 갈리는 상황을 인위적으로 만들어본 것이다. 운영자가 RK가 어떤 컬럼인지 예측하지 못하면, 예시 15(RK로 쓰이는 UK 컬럼은 삭제 불가)와 같은 제약이 "왜 이 UK는 삭제가 막히고 저 UK는 되는지" 이해할 수 없게 된다.

제안: "명시된 순서"의 정확한 기준(제약 생성 시각의 내부 순번 등)을 정의하고, 이를 `show create table`이나 `db_class` 조회 결과로 사용자가 직접 확인할 수 있게 해야 한다(현재 예시 8/9는 RK로 어떤 제약이 선택됐는지를 명시적으로 보여주지 않는다 — 리뷰 14 참조).

리뷰 12

**[심각도: 보통] 여러 CREATE TABLE 예제에 트레일링 콤마(trailing comma) SQL 문법 오류가 있다**

대상: §2-1 예시 2, §5-2 예시 20·23

문제 설명: 예시 2의 `CREATE TABLE repl_table_without_rk( a INT, );`와 예시 20/23의 `CREATE TABLE new_orders( order_id INT PRIMARY KEY, );`는 마지막 컬럼 뒤에 불필요한 콤마가 붙어 있다. 표준 SQL 문법상 컬럼 목록 마지막에 콤마가 오면 문법 오류(syntax error)로 처리되는 것이 일반적이다.

구체 예제:
```sql
-- 예시 2 원문 그대로
csql> CREATE TABLE repl_table_without_rk(
    a INT,
);
-- 이 문장을 실제로 csql에 입력하면 "RK가 없어서" 나는 에러보다 먼저
-- "syntax error near ')'" 류의 문법 에러가 날 가능성이 높다.
```

예제 설명: 이 예제가 보여주려는 핵심은 "PK 없이 REPLICATION=ON을 생략한 테이블은 싱글 모드에서만 생성 가능"이라는 규칙인데, 트레일링 콤마 때문에 애초에 파싱 단계에서 걸려서 그 규칙을 확인하기도 전에 다른 에러를 보게 된다. 신입이 이 예제를 그대로 복사해 테스트하면 엉뚱한 에러 메시지를 받고 혼란스러워진다.

제안: 세 예제 모두 마지막 컬럼 뒤 콤마를 제거해야 한다.

리뷰 13

**[심각도: 보통] 예시 5·6이 대상 테이블(tbl)의 사전 상태를 보여주지 않아 "왜 하나는 에러고 하나는 성공인지" 예제만 봐서는 알 수 없다**

대상: §2-2(ALTER 옵션 및 SQL 추가) 예시 5, 6

문제 설명: 예시 5는 `ALTER TABLE tbl REPLICATION=ON;`이 ERROR, 예시 6은 `ALTER TABLE tbl REPLICATION=OFF;`가 OK라고만 나온다. 본문에는 "HA 모드에서는 복제 제외 테이블이 복제 테이블로 변경될 수 없다"는 규칙이 앞서 서술되어 있어 유추는 가능하지만, 이 두 예제 자체에는 (1) 지금 HA 모드인지 싱글 모드인지, (2) tbl이 지금 REPLICATION=OFF 상태(그래서 예시5가 막히는 것)인지에 대한 명시가 없다. 즉 예제만 뚝 떼어놓고 보면 "같은 테이블에 대해 한쪽은 되고 한쪽은 안 되는" 것처럼 보여 혼란스럽다.

구체 예제(현재 스펙 예제를 보완한 버전):
```sql
-- [전제] 현재 HA 모드로 운영 중이며, tbl은 REPLICATION=OFF 상태다.

-- 예시 5: OFF -> ON 시도 (HA 중에는 금지)
csql> ALTER TABLE tbl REPLICATION=ON;
-- ERROR

-- 예시 6: 이미 OFF인 테이블을 다시 OFF로? 혹은 ON인 다른 테이블을 OFF로?
csql> ALTER TABLE tbl REPLICATION=OFF;
-- OK
```

예제 설명: 위처럼 "전제"를 한 줄 붙여야만 두 예제가 왜 다른 결과를 내는지 즉시 이해된다. 원문에는 이 전제가 빠져 있어, 독자가 본문 규칙 문장을 다시 찾아 역으로 유추해야 한다.

제안: 각 예제 코드 블록 앞에 "이 예제 실행 전 tbl의 상태(HA/싱글 여부, 현재 REPLICATION 값)"를 한 줄 주석으로 명시해야 한다.

리뷰 14

**[심각도: 보통] 예시 8(show create table)이 PK가 RK인 경우만 보여줄 뿐, UK가 RK로 선택된 경우 그 사실을 어떻게 확인하는지 예제가 없다**

대상: §2-3(REPLICATION 조회) 예시 8, 9

문제 설명: 예시 8의 출력은 `CONSTRAINT [pk_tbl_a] PRIMARY KEY ([a]))... REPLICATION ON`으로, PK가 있으니 그게 곧 RK임을 유추할 수 있다. 하지만 UK가 여러 개 있고 그중 하나가 엔진에 의해 RK로 "선택"된 케이스(§1에서 명시적으로 언급한 상황)에서, 그 조회 결과가 "어떤 UK가 선택되었는지"를 구분해서 보여주는지 예제가 전혀 없다. `show create table`은 테이블에 정의된 모든 UK 제약을 나열할 텐데, 그중 무엇이 RK인지 표시가 안 되면 리뷰 11에서 지적한 "선택 기준 모호성"과 겹쳐 운영자가 현재 RK를 특정할 방법이 없다.

구체 예제:
```sql
csql> CREATE TABLE tbl2(
    a INT NOT NULL UNIQUE,
    b INT NOT NULL UNIQUE
);
-- PK가 없으므로 a, b 중 하나가 RK로 선택됨 (§1 규칙)

csql> show create table tbl2;
-- 스펙에 이 경우의 출력 예제가 없다. 만약 출력이 아래처럼 두 UK를 그냥 나열만 한다면
-- 'CREATE TABLE [tbl2] (... CONSTRAINT [u_tbl2_a] UNIQUE ([a]), 
--                            CONSTRAINT [u_tbl2_b] UNIQUE ([b])) REPLICATION ON'
-- 어느 것이 RK인지 이 출력만으로는 알 수 없다.
```

예제 설명: 운영자가 예시 15(RK로 쓰이는 UK는 삭제 불가) 같은 제약을 실제로 맞닥뜨렸을 때, "지금 이 컬럼이 RK인지 아닌지"를 먼저 확인하고 작업해야 안전한데, 확인할 조회 수단의 예제가 스펙에 없으면 실제로 DROP을 시도해보고 에러가 나야만 "아, 이게 RK였구나"를 알게 되는 시행착오 방식이 된다.

제안: UK가 여러 개인 테이블에서 `show create table` 또는 `db_class`류 조회 시 어떤 제약이 실제 RK로 선택되었는지 구분 표시하는 방법을 예제로 추가해야 한다.

리뷰 15

**[심각도: 중요] UK→PK 전환 절차("UK 추가 후 PK 제거"로 가이드)에서 두 DDL 사이의 순서와 중간 상태가 불명확하다**

대상: §4-2

문제 설명: 본문은 "복제키를 PK에서 UK로 변경하는 경우, ... UK 추가(ADD CONSTRAINT), PK 제거(DROP CONSTRAINT)로 가이드 됨"이라고만 말한다. 이걸 하나의 ALTER 문(예시 13처럼 `DROP ..., ADD ...`를 한 문장에)으로 실행하라는 것인지, 두 개의 별도 문장으로 나눠 실행하되 "UK 추가가 먼저, PK 제거가 나중"이라는 순서만 지키라는 것인지 문장이 모호하다. 만약 별도의 두 문장이라면, 그 사이(UK는 이미 있고 PK도 아직 있는 중간 상태)에 RK 후보가 2개(PK, UK)가 되어 §4-2 규칙("복제키 후보가 1개인 경우"의 제약)이 일시적으로 완화되는 것인지, 아니면 여전히 RK는 PK로 고정된 채인지도 리뷰 1의 문제와 맞물려 알 수 없다.

구체 예제:
```sql
-- 현재 tbl: PK(a)만 있고 RK=a(PK)

-- 방법 A: 두 문장으로 분리 (본문 서술을 문자 그대로 읽으면 이렇게 보임)
csql> ALTER TABLE tbl ADD CONSTRAINT UNIQUE(b);     -- 1단계: UK 추가
-- 이 순간 tbl은 PK(a) + UK(b) 두 후보 상태. RK는 여전히 a인가?
csql> ALTER TABLE tbl DROP CONSTRAINT PRIMARY KEY;  -- 2단계: PK 제거
-- 이 순간부터 RK가 b(UK)로 바뀜?

-- 방법 B: 예시 13처럼 한 문장
csql> ALTER TABLE tbl DROP CONSTRAINT PRIMARY KEY, ADD CONSTRAINT UNIQUE(b);
```

예제 설명: 두 방법 중 어느 쪽이 맞는 절차인지에 따라 운영 스크립트 작성 방식이 완전히 달라진다. 방법 A라면 1단계와 2단계 사이에 잠깐이라도 트랜잭션이 열려 있으면 그 사이 들어오는 복제 트래픽이 어떤 RK 기준으로 처리되는지가 중요해지고(리뷰 1과 동일한 문제), 방법 B라면 원자적(atomic, 한 번에 전부 적용되거나 전부 취소되는 성질)으로 처리되어 중간 상태 자체가 없다. 스펙은 둘 중 뭘 권장하는지조차 명시하지 않는다.

제안: PK→UK 전환 절차를 예시 13과 동일한 형식의 "예제 22-1" 같은 구체적 SQL로 추가하고, 반드시 단일 ALTER 문으로 실행해야 하는지 명시해야 한다.

**[심각도: 사소] §5의 예제들(17~23)이 앞선 예제의 테이블이 그대로 남아있다는 것을 전제하는데, 이 전제가 문서 전체에 일관되게 명시되지 않는다**

리뷰 17

**[심각도: 사소] 예시 8 결과에 REPLICATION과 무관한 미설명 용어(REUSE_OID, COLLATE)가 그대로 노출되어 초심자의 집중을 흐린다**

대상: §2-3 예시 8

문제 설명: `CREATE TABLE ... REUSE_OID, COLLATE utf8_bin, REPLICATION ON` 출력에서 REPLICATION 조회 예제를 보여주려는 목적과 무관한 `REUSE_OID`(OID 재사용 여부 옵션), `COLLATE`(문자열 정렬/비교 규칙) 같은 용어가 설명 없이 등장한다. 이 스펙은 REPLICATION 기능만 다루는 문서이므로 다른 옵션이 결과에 섞여 나오는 것 자체는 실제 동작을 정확히 보여주는 것이라 나쁘지 않지만, 신입이 "이 문서만 읽고 이해"해야 하는 요구 수준에서는 최소한 각주로 "REUSE_OID, COLLATE는 본 스펙과 무관한 기존 옵션"이라는 안내가 있어야 헷갈리지 않는다.

구체 예제:
```
'CREATE TABLE [tbl] ([a] INTEGER NOT NULL, [b] INTEGER, 
  CONSTRAINT [pk_tbl_a] PRIMARY KEY ([a])) 
  REUSE_OID, COLLATE utf8_bin, REPLICATION ON'
```

예제 설명: 이 결과를 처음 보는 신입은 REUSE_OID와 COLLATE도 이 스펙에서 새로 추가된 옵션인가 헷갈릴 수 있다. 실제로는 REPLICATION ON만 이번 변경사항이다.

제안: 예시 8 아래에 "REUSE_OID, COLLATE는 REPLICATION과 무관한 기존 CUBRID 옵션이며 본 스펙 대상이 아니다"라는 각주 한 줄을 추가한다.

리뷰 18

**[심각도: 중요] 이 스펙이 원래 배경 문제(PK 컬럼 변경 시 fail_count 증가)를 UK 기반 RK에서도 재발시키지 않는지에 대한 명시적 확인이 없다**

대상: 문서 전체(배경 대비 해결 완결성)

문제 설명: 작업지시의 배경 설명에 따르면 원래 문제는 "HA 실행 중 사용자가 PK 컬럼 속성을 변경하면 복제 누락 + applylogdb 에러(fail_count 증가) + 데이터 불일치"였다. 이번 스펙은 §4-2에서 "RK로 쓰이는 PK/UK 컬럼의 삭제·속성 변경을 DDL 차원에서 막는" 방식으로 이 문제를 예방하려 한다. 그런데 이 예방은 "정상적으로 CUBRID를 통해 ALTER TABLE을 실행하는 경우"에만 적용되는 것으로 보인다. 만약 RK로 쓰이는 UK 컬럼에 대해 §4-2가 다루지 않는 경로로 UNIQUE 제약이 깨지는 상황(예: 대량 데이터 적재 중 유니크 제약 위반이 발생해 엔진이 내부적으로 제약을 비활성화하는 경우, 혹은 스펙에 언급 안 된 다른 DDL 조합)이 있다면, 원래 문제가 UK 버전으로 재발할 수 있다. 스펙은 "복제키는 사용자가 직접 수정할 수 없다"고만 선언할 뿐, 이 선언이 실제로 모든 경로를 커버하는지에 대한 근거(엣지케이스 분석)를 제시하지 않는다.

구체 예제:
```sql
-- RK가 UK인 테이블
csql> CREATE TABLE tbl(
    a INT,
    b INT NOT NULL UNIQUE
);
-- HA 모드, RK = b

-- §4-2가 명시적으로 다루는 경로(DROP CONSTRAINT, DROP COLUMN)는 막혀 있다(예시 15).
-- 그런데 예를 들어 컬럼 타입 변경(CHANGE COLUMN)으로 b의 NOT NULL 속성을 제거하는
-- 시도는 스펙 어디에도 언급이 없다.
csql> ALTER TABLE tbl MODIFY COLUMN b INT NULL;
-- 이게 허용되면, b는 더 이상 "NOT NULL UNIQUE"가 아니게 되어 UK 정의(§1)를
-- 만족하지 못하게 되므로 사실상 RK 속성이 깨지는 것과 같은 효과다.
-- 이 케이스가 막히는지 스펙에 언급이 없다.
```

예제 설명: 이 예제는 스펙이 명시적으로 나열한 몇 가지 DDL(DROP CONSTRAINT, DROP COLUMN, ADD 계열)만 봉쇄하고 있고, "NOT NULL 속성 제거"처럼 열거되지 않은 경로로 동일한 결과(RK 자격 상실)에 도달할 수 있는 경우를 다루는지 확인할 길이 없음을 보여준다. 원래 배경 문제가 "PK 컬럼 속성 변경"이었던 것을 생각하면, 이 케이스는 정확히 같은 유형의 문제가 UK에서 재발하는 것이다.

제안: RK 자격을 잃게 만들 수 있는 모든 DDL 경로(제약 삭제, 컬럼 삭제뿐 아니라 NOT NULL 해제, 컬럼 타입 변경 등)를 전수 조사해 §4-2에 명시하고, 열거되지 않은 경로는 기본적으로 차단한다는 원칙을 선언해야 한다.

리뷰 19

**[심각도: 치명] Failover 이후 REPLICATION=OFF 테이블의 데이터를 실제로 어떻게 준비해야 하는지, 운영자를 위한 절차가 전혀 없이 "책임지지 않는다"로만 끝난다**

대상: §1, §6(뷰)

문제 설명: 이 스펙이 해결하려는 문제의 핵심 리스크는 사실 "복제 제외 테이블의 데이터가 슬레이브에 없다"는 것 자체다(그림에서도 이걸 강조한다). 스펙은 이 현상 자체는 "정상 동작"이라 선언하고 "REPLICATION OFF로 인한 데이터 불일치는 책임지지 않는다"(§1), "이 부분에 대해 복제 모듈은 책임지지 않는다"(§6)고 두 번이나 면책 조항만 남긴다. 그런데 실제로 Failover가 일어나면 애플리케이션은 슬레이브를 새 마스터 삼아 계속 서비스를 해야 하고, 이때 REPLICATION=OFF 테이블에 대한 읽기/쓰기가 들어오면 어떻게 되는지(테이블 자체는 존재하되 데이터가 없는 상태로 남는지, 아니면 스키마조차 없는지)에 대한 최소한의 설명도 없다. "책임지지 않는다"는 컨셉 차원의 선언이지, 그 상태에서 운영자가 무엇을 해야 하는지(예: Failover 전 미리 이 테이블들을 수동으로 동기화해두는 절차, 혹은 Failover 후 이 테이블들에 대한 접근을 애플리케이션 레벨에서 차단하는 방법)에 대한 런북이 전혀 없다.

구체 예제(그림의 시나리오를 운영자 관점 절차로 재구성):
```
[사전 준비 없이 Failover가 발생한 경우]
1) Master: customers(REPLICATION=OFF), orders(REPLICATION=ON, FK->customers)
2) Failover 발생, Slave가 새 Master로 승격
3) Slave의 customers 테이블: 스키마(구조)는 DDL 복제로 존재하지만 데이터(row)는 없음
4) 애플리케이션이 orders를 통해 customers를 조인하는 쿼리 실행
   SELECT o.order_id, c.country FROM orders o JOIN customers c
     ON o.customer_id = c.customer_id WHERE o.order_id = 1;
   -- customers에 실제 데이터가 없으므로 결과가 비거나 애플리케이션 로직상
   -- "고객 정보 없음" 오류로 이어짐. 그런데 이게 "SQL 에러"가 아니라
   -- "조용히 빈 결과"이기 때문에 운영자가 장애를 자각하기까지 더 오래 걸린다.

[운영자가 알고 싶은 것]
- Failover 전에 이런 OFF 테이블들의 데이터를 수동으로 슬레이브에 미리 복사해두는
  것이 권장 절차인가?
- 만약 그렇다면 그 복사 작업과 실제 Failover 발생 시점 사이의 데이터 정합성은
  누가 보장하는가?
- 애초에 이런 상황을 막기 위해 "복제 제외 테이블은 Failover 후보 마스터에서
  읽기 전용으로 막는다"같은 운영 가드가 필요한 것 아닌가?
```

예제 설명: 이 시나리오는 스펙이 "위험하다"는 경고만 하고 "그래서 운영자가 뭘 해야 안전한지"는 답하지 않는 전형적인 사례를 보여준다. SQL 에러가 아니라 조용한 빈 결과로 나타나는 데이터 불일치는 모니터링으로 잡기 어렵고, 이는 배경에서 언급된 원래 문제(마스터/슬레이브 데이터 불일치)와 본질적으로 같은 종류의 사고를, 이번엔 "의도된 기능"이라는 이름으로 재도입하는 셈이다.

제안: REPLICATION=OFF 테이블을 FK로 참조하지 못하게 막는 것(§5)만으로는 부족하다. REPLICATION=OFF 테이블이 애플리케이션 쿼리에서 참조될 가능성이 있는 모든 경우(뷰, JOIN, 애플리케이션 코드의 직접 쿼리)에 대해 운영자가 취할 수 있는 최소한의 가드(예: Failover 후보 승격 전 체크리스트, 또는 OFF 테이블 접근 시 경고 로그)를 §6과 §9에 추가해야 한다.

리뷰 20

**[심각도: 보통] 복제 지연(replication lag)이 있는 상태에서 RK 변경 DDL(예시 13)이 실행되면, 아직 슬레이브에 반영되지 않은 이전 RK 기준 트랜잭션의 처리가 불명확하다**

대상: §4-2, 운영 모니터링(복제 지연)

문제 설명: 실제 운영에서는 마스터와 슬레이브 사이에 복제 지연이 존재할 수 있다(네트워크 지연, 슬레이브 부하 등으로 applylogdb가 실시간을 못 따라가는 상황). 이 상태에서 마스터가 RK를 변경하는 DDL(예시 13: PK를 다른 컬럼으로 변경)을 실행하면, 슬레이브의 applylogdb는 여전히 지연된 옛 로그(옛 RK 기준으로 기록된 UPDATE/DELETE 로그)를 처리하고 있는 도중일 수 있다. 이 옛 로그들은 이제 마스터에서는 사라진 RK(옛 PK)를 기준으로 슬레이브의 행을 찾아야 하는데, DDL도 함께 복제되어 슬레이브의 스키마가 이미 새 RK로 바뀐 뒤라면, 지연된 옛 로그가 슬레이브에 도착했을 때 무엇을 기준으로 대상 행을 찾을지 불명확하다.

구체 예제:
```
[타이밍 시나리오]
T1: Master에서 UPDATE tbl SET c = 1 WHERE a = 5;  (RK=a(PK) 기준으로 로그 기록)
T2: Master에서 ALTER TABLE tbl DROP CONSTRAINT PRIMARY KEY, ADD CONSTRAINT PRIMARY KEY(d);
    (RK가 a에서 d로 변경, 이 DDL도 슬레이브로 복제됨)
T3: 슬레이브의 applylogdb가 지연되어 아직 T1 시점 로그(a=5 UPDATE)를 처리 못한 상태에서
    T2의 DDL(RK 변경)이 먼저 도착해 적용됨
T4: 지연됐던 T1의 UPDATE 로그가 뒤늦게 슬레이브에 도착
    -> 이 로그는 "RK=a, 값 5"로 대상 행을 찾으라고 기록되어 있는데
       슬레이브 스키마는 이미 RK=d로 바뀐 뒤다. 대상 행을 여전히 a=5로 찾는 것이
       맞는지, 아니면 이 로그 자체가 처리 불가능한 것으로 fail_count가 증가하는지
       스펙에 언급이 없다.
```

예제 설명: 이 시나리오는 배경에서 지적된 원래 버그(fail_count 증가)와 정확히 같은 증상을, 이번엔 "RK를 바꾸는 정상 DDL"과 "복제 지연"의 조합으로 재현할 수 있음을 보여준다. RK 변경 자체를 막을 수는 없으니(정당한 운영 요구), 복제 지연이 있는 상태에서 RK 변경 DDL을 실행하는 것 자체를 막거나 경고해야 하는데, 스펙에는 그런 안전장치나 최소한 "복제 지연 중에는 RK 변경 DDL을 실행하지 말라"는 운영 가이드조차 없다.

제안: RK 변경 DDL 실행 전 복제 지연 상태를 확인하도록 권고하는 운영 가이드를 추가하거나, 엔진 차원에서 복제 지연이 일정 수준 이상일 때 RK 변경 DDL을 거부/경고하는 안전장치를 검토해야 한다.
