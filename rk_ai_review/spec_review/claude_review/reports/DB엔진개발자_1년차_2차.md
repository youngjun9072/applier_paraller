# CUBRID HA 복제 개선 스펙 리뷰 — DB 엔진 개발자(1년차) 관점 · 2차 라운드

## 2차 라운드 개요

1차에서는 RK(복제 키) 정의 부재, §8/§9 모순, RK 선택 비결정성, 복합 ALTER 원자성, 파티션·트리거·시리얼 등 "스펙이 아예 언급하지 않은 기존 객체"를 훑었다. 2차에서는 1차와 최종보고서(40개 통합 이슈)가 다루지 않은 지점을 우선순위로 삼아, (1) "NOT NULL UNIQUE"라는 정의 자체의 허점, (2) RK 값 자체를 바꾸는 순수 DML(DDL이 아님), (3) TDE·권한·시스템 카탈로그·VIEW처럼 스펙이 침묵하는 나머지 객체, (4) §7 검사의 성능/MTTR 영향, (5) RENAME TABLE·FK CASCADE처럼 스펙에 등장하지 않는 SQL 기능과의 상호작용을 새로 팠다. 1차에서 이미 지적한 내용(복제키 후보 정의, RK 조회 불가, DDL 기반 RK 전환과 로그 정합성, 파티션/트리거/시리얼/동시성 락)과 겹치는 변주는 의도적으로 배제했다.

## 리뷰 21

**[심각도: 치명] 복합 UNIQUE 키의 "일부 컬럼만 NOT NULL"인 경우, "NOT NULL UNIQUE"라는 정의만으로는 행 유일성이 보장되지 않는다**

**대상**: §1 "복제 키는 ... Primary Key 혹은 Not Null Unique Key 들 중 하나로 선택된다"

**문제 설명**: 스펙은 RK 후보 조건을 "Not Null Unique Key"라고만 표기한다. 그런데 CUBRID의 UNIQUE 제약은 여러 컬럼을 묶는 복합(composite) 형태로도 만들 수 있고, 각 컬럼에 NOT NULL을 걸지 걸지 않을지는 컬럼별로 독립적으로 선택 가능하다. "Not Null Unique Key"라는 표현이 "이 UNIQUE 제약을 구성하는 모든 컬럼이 각각 NOT NULL이어야 한다"는 뜻인지, 아니면 "UNIQUE 제약이면서 그중 아무 컬럼이나 하나라도 NOT NULL이면 된다"는 뜻인지 스펙 문장만으로는 정해지지 않는다. 표준 SQL에서 복합 UNIQUE 제약은 구성 컬럼 중 하나라도 NULL이면 그 행 전체를 "비교 불가"로 취급해 유일성 검사를 건너뛰는 것이 일반적이다. 즉 컬럼 하나라도 NULL을 허용하면, 나머지 컬럼 값이 같은 행이 여러 개 존재해도 UNIQUE 위반으로 잡히지 않는다.

**구체 예제**:
```sql
CREATE TABLE tbl (
    b INT NOT NULL,
    c INT,                    -- NULL 허용 (NOT NULL 아님)
    CONSTRAINT uk_tbl_bc UNIQUE (b, c)
);

-- uk_tbl_bc 는 "Unique Key"이고 구성 컬럼 중 b는 NOT NULL이다.
-- 스펙 문구("Not Null Unique Key")만 보면 이 제약이 RK 후보인지 애매하지만,
-- 만약 "적어도 하나는 NOT NULL이면 후보로 인정"하는 쪽으로 구현되었다고 가정하면:

INSERT INTO tbl VALUES (1, NULL);
INSERT INTO tbl VALUES (1, NULL);   -- c가 NULL이라 (b,c) 유일성 검사에서 제외되어 OK로 통과
-- 이제 tbl에는 (b=1, c=NULL) 행이 두 개 존재한다.
```

**예제 설명**: `uk_tbl_bc`가 RK로 선택되었다고 가정하면, 복제 로그는 두 행 모두를 "RK = (b=1, c=NULL)"이라는 동일한 값으로 식별해야 한다. 그런데 실제로는 서로 다른 두 개의 물리적 행이 존재하므로, 슬레이브에서 이 RK 값으로 `UPDATE ... WHERE b=1 AND c IS NULL`을 실행하면 두 행이 동시에 걸리거나(의도한 한 행이 아니라 두 행 모두 갱신), DELETE라면 두 행이 한꺼번에 지워질 수 있다. 이는 이 스펙이 처음부터 막으려던 "슬레이브에서 어떤 행을 특정할 수 없는" 문제가, PK가 없어서가 아니라 "NOT NULL 조건이 컬럼 전체에 걸리지 않은 복합 UK"를 RK로 잘못 채택했을 때 그대로 재현되는 경우다.

**제안**: "Not Null Unique Key"를 "구성하는 모든 컬럼이 개별적으로 NOT NULL로 선언된 UNIQUE 제약"으로 명확히 정의하고, RK 후보 판정 로직에서 복합 UK는 전체 컬럼이 NOT NULL인지 전수 검사하도록 명문화한다. 이미 존재하는 부분-NOT NULL 복합 UK는 애초에 후보 목록에서 제외되어야 한다.

## 리뷰 22

**[심각도: 중요] 함수 기반(표현식) UNIQUE 인덱스가 RK 후보인지, 후보라면 복제 로그에 무엇을 값으로 실어야 하는지 정의가 없다**

**대상**: §1 "복제 키는 ... UK 들 중 하나로 선택된다", §4-2 (RK 후보 논의 전반)

**문제 설명**: CUBRID는 컬럼 값이 아니라 식(expression)의 계산 결과에 유일성을 거는 함수 기반 인덱스를 지원하며, 이는 UNIQUE로도 만들 수 있다. 이런 함수 기반 UNIQUE 인덱스는 "컬럼"이 아니라 "표현식"에 걸린 제약이기 때문에, 이 인덱스가 RK 후보에 포함되는지부터 불명확하다(1차 리뷰 1에서 지적한 "CREATE UNIQUE INDEX vs CONSTRAINT" 문제와는 다른 축이다 — 그쪽은 문법 차이였고, 여기는 "값 자체가 원본 컬럼 값이 아니라 계산된 값"이라는 구조적 차이다). 만약 이런 인덱스가 후보로 인정된다면, 복제 로그(마스터가 슬레이브에게 "어느 행을 바꿔라"라고 알려주는 메시지)에 원본 컬럼 값을 실어야 하는지, 계산된 함수 값을 실어야 하는지, 아니면 둘 다 실어야 하는지가 정의되어야 하는데 스펙에는 이에 대한 언급이 전혀 없다.

**구체 예제**:
```sql
CREATE TABLE tbl (
    email VARCHAR(100) NOT NULL,
    name VARCHAR(50)
);
CREATE UNIQUE INDEX idx_email_lower ON tbl(LOWER(email));  -- 함수 기반 유니크 인덱스

-- email 컬럼 자체는 UNIQUE 제약이 없다. 유일성은 LOWER(email) 값에만 걸려 있다.
-- 이 idx_email_lower 가 RK 후보인가?
UPDATE tbl SET name = 'X' WHERE email = 'Alice@Example.com';
-- 복제 로그는 email 원본값('Alice@Example.com')을 RK로 기록해야 하는가,
-- 아니면 LOWER(email) 계산값('alice@example.com')을 기록해야 하는가?
```

**예제 설명**: 슬레이브가 이 UPDATE를 재현하려면 결국 "어떤 행을 찾을지" 키가 필요하다. 원본 컬럼값(email)을 기준으로 찾는다면 이는 사실 email 컬럼 자체의 유일성에 의존하는 것인데, email 컬럼에는 UNIQUE 제약이 없으므로(대소문자만 다른 두 값이 공존할 수 있음) 원본값 기준 검색이 유일한 행을 보장하지 못할 수 있다. 반대로 계산값(LOWER(email))을 기준으로 찾으려면 슬레이브 쪽 applylogdb가 함수 인덱스의 정의(LOWER)를 알고 있어야 하고, 이 함수가 결정적(deterministic)이라는 보장도 필요하다. 둘 중 어느 쪽으로 구현해야 하는지 스펙에 근거가 없다.

**제안**: RK 후보를 "테이블의 실제 저장 컬럼(physical column) 값만으로 구성된 UNIQUE 제약/인덱스"로 한정해 함수 기반 인덱스를 명시적으로 후보에서 제외하거나, 포함시키기로 한다면 복제 로그 포맷에 계산값과 원본값 중 무엇을 싣는지 규정한다.

## 리뷰 23

**[심각도: 치명] RK 컬럼 자체의 값을 바꾸는 평범한 UPDATE 문에서, "이전 키로 행을 찾고 새 값으로 갱신"하는 old-key/new-key 정보를 복제 로그가 어떻게 구분해 기록하는지 정의가 없다**

**대상**: §4-2 전체(RK 컬럼을 바꾸는 DDL 시나리오만 다룸), 복제 로그 포맷(스펙에 별도 절 없음)

**문제 설명**: 이 항목은 1차 리뷰 4·최종보고서 C-8(둘 다 "RK를 바꾸는 ALTER TABLE"이라는 DDL이 얽힌 시나리오)과는 다른 문제다. 여기서는 DDL이 전혀 없다 — RK로 쓰이는 컬럼(PK 또는 UK)의 "값"을 그냥 UPDATE 문으로 바꾸는, 지극히 평범한 DML 상황이다. PK/UK 컬럼도 그 값 자체는 UPDATE로 변경할 수 있는 것이 일반적인 관계형 DB의 동작이다(새 값이 다른 행과 중복되지만 않으면 허용됨). 복제 로그가 "행 이미지"만 담아 마스터가 바뀐 후의 값만 슬레이브에 전달한다면, 슬레이브는 "어떤 행을 찾아서 바꿔야 하는지"의 근거(옛 키 값)를 잃어버린다.

**구체 예제**:
```sql
CREATE TABLE customers (
    customer_id INT PRIMARY KEY,
    country INT
);
-- RK = customer_id

-- 마스터에서 실행
UPDATE customers SET customer_id = 9001 WHERE customer_id = 5;
-- 이 UPDATE는 RK(customer_id) 자체의 값을 5 -> 9001 로 바꾼다.
```

**예제 설명**: 슬레이브 쪽 applylogdb는 이 한 번의 UPDATE를 반영하기 위해 "customer_id=5인 행을 찾아서, customer_id를 9001로, 그리고 다른 변경된 컬럼도 함께 반영"해야 한다. 만약 복제 로그에 변경 후의 새 행 이미지(customer_id=9001, country=...)만 담겨 있다면, 슬레이브는 이미 customer_id=9001인 행을 찾으려 시도하게 되는데 그런 행은 존재하지 않으므로 "대상 행 없음" 오류가 나거나, 최악의 경우 엉뚱한 매칭 로직으로 잘못된 행을 건드릴 수 있다. 이는 배경 설명에 나온 원래 버그("PK 컬럼 속성을 변경하면 복제가 깨진다")와 증상은 비슷하지만 원인은 완전히 다르다 — 이번엔 스키마(DDL)가 아니라 데이터(DML)가 원인이며, 이 신규 스펙이 새로 만들려는 RK 메커니즘 자체가 처음부터 이 케이스를 감안하지 않으면 재발할 수 있다.

**제안**: 복제 로그 레코드 포맷에 "갱신 전 RK 값(search key)"과 "갱신 후 전체 행 이미지"를 분리해서 담도록 명시하고, RK 컬럼이 UPDATE의 SET 절에 포함되는 경우를 별도 테스트 케이스로 §4 또는 별도 복제 로그 포맷 절에 예시로 추가한다.

## 리뷰 24

**[심각도: 중요] §7의 HA 전환 검사(전체 카탈로그의 RK 존재 여부 + FK 참조 그래프 순회)가 위반이 하나도 없어도 대규모 스키마에서 얼마나 걸리는지, 이 지연이 failover 시간에 미치는 영향이 검토되지 않았다**

**대상**: §7 "HA 실행시 다음 사항을 제약사항을 확인하며"

**문제 설명**: §7이 규정한 검사는 두 가지다 — (1) 복제 대상 테이블마다 RK 존재 여부 확인, (2) FK를 포함한 복제 대상 테이블마다 그 참조 테이블이 복제 대상인지 확인. 이 검사는 "HA 실행 시"(§7 원문) 수행된다고 되어 있는데, 이는 최초 HA 진입뿐 아니라 장애로 인한 failover 이후 재기동, 유지보수를 위한 정기 HA 재시작에도 매번 해당된다고 읽힌다. 테이블 수가 수천 개에 이르는 실서비스 DB(멀티 테넌트 환경 등)에서는 이 검사가 카탈로그 전체를 스캔하고, FK가 있는 테이블마다 참조 테이블 체인을 따라가야 한다. 위반이 하나도 없는 "정상" 상황에서도 이 검사에 걸리는 시간이 얼마나 되는지, 그리고 이 시간이 HA의 존재 이유인 "빠른 장애 복구(짧은 MTTR, Mean Time To Recovery: 장애 발생부터 서비스 정상화까지 걸리는 평균 시간)"를 얼마나 늦추는지 스펙은 전혀 언급하지 않는다.

**구체 예제**:
```
-- 가정: 테이블 5,000개, 그 중 FK를 가진 테이블 800개, FK 체인 평균 깊이 3단계
$ cubrid hb start proddb
-- 5,000개 테이블 각각 RK 존재 검사 + 800개 테이블 각각 FK 참조 테이블 확인
-- (FK가 다단계로 연쇄되어 있다면 참조 테이블의 참조 테이블까지 따라가야 할 수도 있음, 최종보고서 M-8 참고)
-- 이 전체 검사에 걸리는 시간 = ?
-- 장애로 슬레이브가 새 마스터로 승격되는 failover 경로에서도 동일 검사가 반복되는가?
```

**예제 설명**: 위반이 없다면 이 검사는 통과 후 바로 서비스가 시작되어야 하지만, 검사 자체의 시간 복잡도(테이블 수 × FK 체인 깊이)가 스펙에 규정되어 있지 않으므로, 구현이 단순 순차 스캔으로 되어 있다면 대규모 스키마에서 초 단위, 심하면 분 단위의 추가 지연이 HA 기동/재기동/failover마다 상수 비용으로 붙을 수 있다. 이는 "위반을 어떻게 사용자에게 보여줄지"(최종보고서 C-4, 파일 리스트 포맷 문제)나 "사전에 위반을 점검할 도구가 없다"(최종보고서 M-4)와는 다른 층위의 문제로, 위반이 전혀 없어도 지불해야 하는 상시 비용에 대한 것이다.

**제안**: §7 검사의 비용을 카탈로그 캐시(예: RK/FK 그래프를 매 DDL마다 갱신해두는 인덱스)로 상수 시간에 가깝게 만들 것을 요구사항에 명시하거나, 최소한 "이 검사가 HA 기동 시간에 미치는 영향은 테이블 수에 비례하며 대규모 스키마에서는 O(초) 단위가 될 수 있다"는 성능 특성을 문서화해 운영자가 failover SLA(서비스 수준 목표)를 설계할 때 반영하게 한다.

## 리뷰 25

**[심각도: 중요] `ALTER TABLE ... REPLICATION={ON|OFF}` 실행에 필요한 권한 체계가 정의되어 있지 않다**

**대상**: §2-2 (ALTER TABLE ... REPLICATION 옵션), 스펙 전체(권한/GRANT 언급 없음)

**문제 설명**: CUBRID는 일반적인 ALTER TABLE에 테이블 소유자(owner) 또는 DBA 권한을 요구한다. 그런데 이번에 추가되는 `REPLICATION=OFF` 전환은 일반적인 스키마 변경(컬럼 추가/삭제 등)과 성격이 다르다 — 이 한 줄의 DDL이 §7의 HA 전환 검사 결과를 바꾸고(예: 이 테이블을 참조하던 FK 관계를 위반 상태로 만들 수 있음, 리뷰 10·11·최종보고서 C-2 참고), 나아가 클러스터 전체의 HA 기동 가부에 영향을 줄 수 있는 "블라스트 반경(영향 범위)"이 넓은 명령이다. 스펙은 이 명령이 기존 ALTER TABLE과 동일한 권한 요구사항을 갖는지, 아니면 더 엄격한(예: DBA 전용) 권한이 필요한지 한 마디도 하지 않는다.

**구체 예제**:
```sql
-- 일반 애플리케이션 개발 계정(DBA 아님, customers 테이블의 소유자)으로 접속한 상태
-- HA 운영 중인 프로덕션 DB에서:
ALTER TABLE customers REPLICATION = OFF;
-- 이 계정은 customers 테이블에 대한 일반 ALTER 권한(컬럼 추가 등)은 원래도 있었다.
-- 그런데 이 한 줄로 customers를 참조하는 다른 복제 대상 테이블들이
-- (최종보고서 C-2가 지적한 미차단 경로를 통해) 잠재적 FK 위반 상태에 놓이고,
-- 다음 HA 재시작 시 클러스터 전체가 기동 실패할 수 있다.
```

**예제 설명**: 일반적인 컬럼 추가/삭제는 그 테이블 자체의 스키마만 바꾸지만, REPLICATION 옵션 전환은 그 테이블을 참조하는 다른 테이블들의 HA 안전성, 나아가 클러스터 전체의 다음 재시작 성패에까지 영향을 미친다. 이런 "전역 영향력을 가진 로컬 권한"을 테이블 소유자 수준의 일반 ALTER 권한과 동일하게 취급해도 되는지는 순수한 구현 편의가 아니라 운영 정책의 문제인데, 스펙에 이에 대한 결정이 없으므로 신입 개발자는 권한 검사 코드를 기존 ALTER TABLE 경로 그대로 재사용해도 되는지 판단할 수 없다.

**제안**: `REPLICATION` 옵션 변경에 필요한 최소 권한(테이블 소유자로 충분한지, DBA 전용인지, 혹은 별도의 새로운 권한 항목을 도입할지)을 명시하고, 그 근거(운영 리스크 대비 개발 편의성)를 한 문단 덧붙인다.

## 리뷰 26

**[심각도: 중요] TDE(투명한 데이터 암호화)로 암호화된 테이블이 REPLICATION=ON일 때, 마스터/슬레이브 간 암호화 키 상태가 다르면 RK 값 비교와 복제 로그 처리가 어떻게 되는지 정의가 없다**

**대상**: §2-3 예시 9 (`tde_algorithm : 'NONE'` — db_class에 이미 존재하는 컬럼)

**문제 설명**: 예시 9의 `select * from db_class` 결과에는 `tde_algorithm` 컬럼이 이미 존재한다. TDE(Transparent Data Encryption)는 디스크에 저장되는 데이터를 암호화하는 CUBRID의 기존 기능이다. 이번 스펙은 REPLICATION/RK 기능과 TDE의 상호작용을 전혀 언급하지 않는다. 그런데 복제는 본질적으로 "마스터가 값을 읽어서 슬레이브에 값을 전달"하는 과정이므로, TDE로 암호화된 컬럼이 RK로 선택된 경우 (a) 복제 로그에 담기는 RK 값이 평문인지 암호문인지, (b) 마스터와 슬레이브의 TDE 키(또는 키 회전 상태, 즉 암호화 키를 주기적으로 바꾸는 보안 관행의 적용 시점)가 서로 다르면 슬레이브에서 이 값으로 행을 올바르게 찾을 수 있는지가 불명확하다.

**구체 예제**:
```sql
-- TDE가 활성화된 테이블(가정: CUBRID의 TDE 기능으로 컬럼 또는 테이블 단위 암호화 적용)
CREATE TABLE secure_accounts (
    account_no VARCHAR(20) PRIMARY KEY,   -- TDE 암호화 대상 컬럼이라 가정
    balance INT
);
-- account_no 가 PK이자 RK

UPDATE secure_accounts SET balance = balance - 100 WHERE account_no = 'ACC-0001';
-- 마스터는 디스크에서 이 값을 복호화해 처리한다.
-- 복제 로그에는 account_no 값이 평문('ACC-0001')으로 실리는가, 암호화된 채로 실리는가?
-- 슬레이브가 마스터와 다른 TDE 키(또는 키 회전 이력)를 갖고 있다면 이 값을 올바르게 해석할 수 있는가?
```

**예제 설명**: 만약 복제 로그가 평문 값을 담는다면 이는 "저장 시에는 암호화하지만 전송 경로(복제 로그)에서는 평문이 노출된다"는 뜻이 되어 TDE 도입 취지(디스크 유출 대비)와 별개로 복제 채널을 통한 정보 노출 경로가 새로 생기는 셈이다. 반대로 암호문 그대로 싣는다면, 마스터와 슬레이브가 반드시 동일한 암호화 키를 공유해야 하는데 이 키 동기화·배포·회전 절차가 스펙에 없다. 어느 쪽이든 문서화가 필요한데 스펙은 TDE라는 단어 자체를 언급하지 않는다.

**제안**: TDE 대상 컬럼이 RK 후보가 될 수 있는지 여부를 결정하고(허용한다면 복제 로그의 값 처리 방식과 키 동기화 요구사항을, 허용하지 않는다면 그 제약을 §4-2에 명시), 최소한 이번 릴리스 범위에 TDE와의 상호작용이 포함되는지 여부를 한 줄로 확정한다.

## 리뷰 27

**[심각도: 중요] RENAME TABLE을 이용한 "그림자 테이블 스왑" 패턴에서 FK/REPLICATION 검증이 테이블 이름 기준인지 내부 클래스 식별자 기준인지 불명확하다**

**대상**: §5 (외래키 검증), §7 (HA 전환 검사), 스펙 전체(RENAME TABLE 언급 없음)

**문제 설명**: 대용량 테이블의 스키마를 무중단으로 바꾸는 흔한 운영 기법 중 하나가 "그림자 테이블(shadow table) 스왑"이다 — 원본과 동일한 스키마의 새 테이블을 만들어 데이터를 옮긴 뒤, `RENAME TABLE`로 이름을 맞바꿔 순간적으로 교체하는 방식이다. CUBRID는 `RENAME TABLE`을 지원한다. 이번 스펙은 CREATE TABLE·ALTER TABLE 시점의 FK/RK 검증(§5)만 다루는데, RENAME은 이 둘 중 어디에도 속하지 않는 제3의 DDL이다. FK 제약이나 §7의 참조 그래프 검사가 "테이블 이름"을 기준으로 맺어져 있다면, 이름이 스왑된 이후에도 검증이 올바른 대상(실제로는 새로 만든 그림자 테이블)을 가리키는지, 혹은 검증이 이름 변경 시점에 다시 수행되는지 알 수 없다.

**구체 예제**:
```sql
-- 기존: customers(복제 대상, PK customer_id) 를 orders(복제 대상)가 FK로 참조 중

-- 온라인 스키마 변경 작업: 새 컬럼을 추가한 그림자 테이블 생성
CREATE TABLE customers_new (
    customer_id INT PRIMARY KEY,
    country INT,
    tier VARCHAR(10)              -- 신규 컬럼
) REPLICATION = OFF;              -- 데이터 이관 중에는 우선 복제 제외로 생성

-- (데이터를 customers 에서 customers_new 로 이관하는 배치 작업 ... 생략)

-- 이관 완료 후 이름 스왑
RENAME TABLE customers TO customers_old;
RENAME TABLE customers_new TO customers;
-- customers_new 는 REPLICATION=OFF 로 생성되었는데, 스왑 이후 이 테이블이
-- 실질적으로 orders(REPLICATION=ON)가 참조하는 "customers"가 된다.
```

**예제 설명**: 최종보고서 C-2는 "FK 참조 대상을 사후에 ALTER TABLE ... REPLICATION=OFF로 바꾸는 경로가 차단되지 않는다"는 문제를 지적했다. 이 예제는 그와 다른 경로로 같은 결과(복제 대상 orders가 복제 제외 상태의 customers를 참조)에 도달한다 — ALTER TABLE이 아니라 RENAME TABLE을 통해서다. §5의 검사가 "지금 이 이름을 가진 테이블이 REPLICATION=ON인가"를 스왑 시점에 재확인하지 않는다면, RENAME은 §5·§7이 막으려는 상황을 우회하는 손쉬운 뒷문이 된다. 게다가 이 시나리오는 실제로 매우 흔한 무중단 스키마 변경 패턴이라는 점에서, 특수 케이스가 아니라 자주 발생할 수 있는 경로다.

**제안**: RENAME TABLE 수행 시에도 §5·§7과 동일한 FK/REPLICATION 정합성 검사를 트리거하도록 명시하고, "RENAME 이후에도 그 이름으로 맺어진 모든 FK 관계에 대해 참조 테이블의 REPLICATION 상태를 재검증한다"는 규칙을 추가한다.

## 리뷰 28

**[심각도: 중요] FK의 참조 액션(ON DELETE/UPDATE CASCADE)으로 발생하는 연쇄 DML이 복제 로그에 어떻게 기록되는지 정의가 없다 — 트리거와는 다른 별도의 엔진 경로다**

**대상**: §5 (외래키 전반 — CASCADE/SET NULL/RESTRICT 등 참조 액션에 대한 언급 없음)

**문제 설명**: 1차 리뷰 7에서는 사용자가 `CREATE TRIGGER`로 명시적으로 만든 트리거가 다른 테이블에 부수 효과를 일으키는 경우를 다뤘다. 이 리뷰는 그와 다른, FK 자체의 내장 기능인 참조 액션(`ON DELETE CASCADE`, `ON UPDATE CASCADE` 등)을 다룬다. 트리거는 사용자가 SQL로 명시적으로 작성한 별도의 실행 경로(트리거 엔진)를 타지만, CASCADE는 FK 제약을 선언할 때 옵션으로 붙이는 것으로 제약 검사 엔진(constraint enforcement)의 일부이며 완전히 다른 코드 경로다. 일반적으로 슬레이브에 로그를 적용하는 모듈(applylogdb)은 이미 마스터에서 검증·확정된 결과를 그대로 반영하는 것이 목적이므로, 트리거나 참조 액션 같은 "2차 효과를 스스로 만들어내는 로직"은 슬레이브 쪽에서 다시 실행되지 않고 비활성화되는 것이 일반적인 복제 설계다. 그렇다면 마스터에서 CASCADE로 인해 자동 삭제/갱신된 자식 테이블의 행들은, 슬레이브가 스스로 재현할 수 없으므로 마스터가 이를 명시적인 행 단위 로그 레코드로 펼쳐서 전달해야 한다. 스펙은 이 점을 전혀 언급하지 않는다.

**구체 예제**:
```sql
CREATE TABLE customers (
    customer_id INT PRIMARY KEY,
    country INT
);   -- REPLICATION=ON (기본값)

CREATE TABLE orders (
    order_id INT PRIMARY KEY,
    customer_id INT,
    CONSTRAINT fk_customer_id FOREIGN KEY (customer_id)
        REFERENCES customers(customer_id) ON DELETE CASCADE
);   -- REPLICATION=ON, customers 삭제 시 관련 orders 행도 자동 삭제

DELETE FROM customers WHERE customer_id = 5;
-- 마스터: customers의 5번 행 삭제 + CASCADE로 orders의 customer_id=5인 행들도 자동 삭제
-- 복제 로그에는 무엇이 기록되는가?
--   (a) "customers에서 customer_id=5 삭제" 한 건만 기록되고,
--       슬레이브가 자신의 CASCADE 제약을 재실행해 orders 행도 알아서 지우는가?
--   (b) 마스터가 CASCADE로 지워진 orders의 각 행까지 전부 개별 DELETE 로그로 펼쳐 보내는가?
```

**예제 설명**: (a) 방식이라면 슬레이브가 DML 적용 시 자신의 제약 엔진(트리거·CASCADE 포함)을 활성화해 두어야 하는데, 이는 일반적인 복제 설계 원칙(슬레이브는 이미 결정된 결과만 반영)과 어긋나며, 만약 슬레이브 쪽에서 별도의 이유로 이 CASCADE 제약이 아직 반영되지 않은 상태(예: DDL 복제 지연)라면 orders 행이 삭제되지 않고 남아 데이터 불일치가 생긴다. (b) 방식이라면 구현이 더 안전하지만, CASCADE가 여러 단계로 연쇄(A→B→C)될 경우 이를 전부 풀어서 로그로 만드는 로직이 필요하고, 이는 §5가 이미 다루는 FK 참조 그래프 순회(최종보고서 M-8)와도 얽힌다. 어느 쪽으로 할지 스펙에 근거가 없다.

**제안**: FK 참조 액션(CASCADE/SET NULL 등)으로 인한 연쇄 DML은 마스터에서 개별 행 단위 로그로 명시적으로 펼쳐서 전달하며, 슬레이브 쪽 적용 시에는 참조 액션을 재실행하지 않는다는 원칙을 §5에 명시한다.

## 리뷰 29

**[심각도: 중요] 시스템 카탈로그 클래스(db_class 등)에도 "복제 테이블은 RK 필수" 불변식이 그대로 적용되는지 스펙이 침묵한다**

**대상**: §1 "HA 모드 실행 시 복제 테이블은 ... RK가 존재하지 않으면 HA모드를 실행 할 수 없다", §2-3 예시 9 (db_class의 `is_system_class` 컬럼)

**문제 설명**: 예시 9의 `select * from db_class` 결과에는 `is_system_class : 'NO'`라는 필드가 이미 존재한다. 즉 CUBRID의 카탈로그는 일반 사용자 테이블과 시스템 카탈로그 테이블(db_class, db_attribute, db_index, db_serial 등 CUBRID가 내부적으로 스키마 정보를 관리하기 위해 쓰는 테이블들)을 이미 `is_system_class` 플래그로 구분하고 있다. 이번 스펙이 새로 추가하는 "복제 테이블은 RK가 반드시 있어야 한다"는 불변식(§1, §4-1, §9)이 이 시스템 카탈로그 테이블들에도 예외 없이 적용되는지, 아니면 `is_system_class='YES'`인 대상은 애초에 이 규칙의 검사 범위에서 빠지는지 스펙에 한 마디도 없다.

**구체 예제**:
```sql
-- 가정: 시스템 카탈로그 테이블(예: db_serial)이 내부적으로 PK/UK가 없는 구조로 구현되어 있다면
SELECT class_name, is_system_class FROM db_class WHERE is_system_class = 'YES';
-- db_class, db_attribute, db_serial, ... 등이 나열됨

$ cubrid hb start proddb
-- §7 규칙("복제 테이블에 복제키가 존재하지 않는 경우 에러")이 이 시스템 테이블들에도
-- 그대로 적용된다면, 사용자 스키마와 무관하게 CUBRID 자체의 내부 구조 때문에
-- 모든 DB에서 HA 기동이 항상 실패하는 상황이 생길 수 있다.
```

**예제 설명**: 이 예제가 실제로 문제를 일으키는지는 시스템 카탈로그 테이블들의 내부 스키마(PK/UK 존재 여부)에 달려 있어 스펙만으로는 단정할 수 없다. 하지만 바로 그 점이 문제다 — 이 신규 불변식을 구현하는 신입 개발자가 "테이블 하나하나를 순회하며 RK 검사"라는 코드를 작성할 때, 순회 대상에 시스템 클래스를 포함할지 제외할지는 스펙에 규정된 바가 없으므로 임의로 정해야 한다. 잘못 판단하면 최악의 경우 CUBRID 자체의 부트스트랩(시스템 카탈로그 자체가 만들어지는 초기화 과정)이나 HA 기동 전체가 막히는 회귀를 만들 수 있고, 반대로 안전하게 항상 제외하도록 짰는데 나중에 실제로는 특정 시스템 테이블도 검사 대상이어야 한다는 요구가 뒤늦게 나오면 재작업이 필요하다.

**제안**: §7(및 §1, §4-1의 RK 필수 불변식)의 검사 대상을 "`is_system_class = 'NO'`인 사용자 테이블에 한정한다"는 문장을 명시적으로 추가한다.

## 리뷰 30

**[심각도: 보통] VIEW도 db_class에 속하는 클래스인데, 새로 추가되는 replication 컬럼이 VIEW 레코드에 어떤 값으로 채워지는지 정의가 없다**

**대상**: §2-3 예시 9 (db_class 스키마 — `class_type` 컬럼으로 CLASS/VIEW 구분), §6 뷰

**문제 설명**: 예시 9를 보면 db_class는 `class_type` 컬럼으로 일반 테이블(CLASS)과 뷰(VIEW)를 구분해 하나의 카탈로그 테이블에 함께 저장하는 구조로 보인다. 이번 기능이 db_class에 `replication` 컬럼을 새로 추가한다면(예시 9에 이미 `replication : ON`으로 표시됨), 이 컬럼이 `class_type = 'VIEW'`인 레코드에도 예외 없이 채워지는지, 채워진다면 그 값의 의미가 무엇인지 불명확하다. VIEW는 §2-1의 CREATE TABLE 옵션 대상이 아니므로 사용자가 VIEW에 대해 `REPLICATION=ON/OFF`를 지정할 SQL 문법 자체가 없다.

**구체 예제**:
```sql
CREATE VIEW v_orders AS SELECT * FROM orders;

SELECT class_name, class_type, replication FROM db_class WHERE class_name = 'v_orders';
-- class_type : VIEW
-- replication : ?   (ON / OFF / NULL / 표시 없음 중 무엇이 나오는가?)
```

**예제 설명**: §9는 "REPLICATION 표시를 포함하지 않는 테이블은 모두 복제 대상(혹은 최종보고서가 지적하듯 §8과 상충되어 복제 제외일 수도 있음)으로 간주한다"는 취지의 기본값 규칙을 두고 있다. 만약 이 기본값 규칙이 VIEW 레코드에도 무차별 적용된다면, VIEW가 "RK 없는 복제 대상 테이블"로 오인되어 §7의 HA 전환 검사(혹은 이를 참고해 만들어질 모니터링 스크립트)가 모든 VIEW를 위반 대상으로 잘못 나열하는 결과를 낳을 수 있다. VIEW는 §6에서 별도로 다뤄지지만, §6은 "밑단 테이블이 복제 제외일 때 결과가 불일치할 수 있다"는 논리적 문제만 다룰 뿐 카탈로그 스키마 레벨에서 replication 컬럼 값이 어떻게 채워지는지는 다루지 않는다.

**제안**: db_class의 replication 컬럼은 `class_type = 'CLASS'`(일반 테이블)에만 의미를 가지며 VIEW에는 NULL 또는 해당 없음으로 남는다는 점을 명시하고, §7의 검사 로직이 VIEW를 애초에 순회 대상에서 제외한다는 문장을 추가한다.

## 조사 종료 선언

이번 2차 라운드에서는 1차·최종보고서가 다루지 않은 다음 영역을 훑었다: (1) RK 후보 정의의 세부 허점(복합 키의 부분 NOT NULL, 함수 기반 인덱스), (2) RK 값 자체를 바꾸는 순수 DML과 복제 로그 old-key/new-key 문제, (3) §7 검사의 성능/MTTR 영향, (4) 권한 체계, (5) TDE·시스템 카탈로그·VIEW의 db_class 스키마 취급, (6) RENAME TABLE·FK CASCADE처럼 스펙에 등장하지 않는 SQL 기능과의 상호작용. 이 과정에서 collation(문자 비교 규칙)과 REUSE_OID(OID 재사용 옵션)도 검토했으나, NOT NULL UNIQUE 제약이 이미 collation 규칙에 따라 유일성을 강제하므로 별도의 새로운 실패 모드를 찾지 못했고, REUSE_OID는 이번 기능이 애초에 OID가 아닌 PK/UK 값 기반으로 설계되어 있어 상호작용 지점이 근거 없이 추측성으로만 구성될 위험이 있어 제외했다. fail_count 지표·다중 슬레이브·컬럼 단위 필터링·성능 벤치마크 등은 최종보고서에 이미 명시적으로 실려 있어 재탕으로 판단해 배제했다. 이 이상으로는 근거 있는 신규 실패 모드를 찾지 못해 10건에서 조사를 마친다. 남은 여지가 있다면 실제 CUBRID 소스코드(카탈로그 매니저, applylogdb 구현)를 직접 열람해 "시스템 카탈로그 클래스의 실제 PK/UK 존재 여부"(리뷰 29) 같은 항목을 사실 확인하는 것인데, 이는 스펙 문서만으로 하는 리뷰의 범위를 벗어난다.
