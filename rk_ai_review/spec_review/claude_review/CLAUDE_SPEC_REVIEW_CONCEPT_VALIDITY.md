# CUBRID HA 복제 개선 스펙 — 컨셉 타당성 리뷰

> 이 문서는 스펙(개념) 수준만 리뷰한 것이다. 구현 코드 대조는 별도 트랙(code_review)에 있으며 여기엔 포함하지 않는다.
> 5개 직군 × 4개 연차 = 20개 관점으로 스펙 문서를 검토했다. **1차**는 스펙 정면 리뷰(통합 이슈 40건), **2차**는 1차와 겹치지 않는 인접 영역 신규 리뷰(30건)다.

---

## 1차 — 스펙 정면 리뷰

작성: 수석 아키텍트 종합 · 대상 문서: `user_spec_extracted.md` (CUBRID HA 복제 키(RK) / REPLICATION 옵션 스펙)
근거: 5개 직군(PM · DB엔지니어(운영) · 최종사용자 · 응용개발자 · 엔진개발자) × 4개 연차(1·3·5·10년차) = **20개 독립 리뷰, 리뷰당 20건 = 총 400개 지적**

> 이 보고서는 개별 리뷰의 지적을 병합·중복 제거하고, 각 이슈를 **몇 개 직군·연차가 동일하게 지적했는지(합의도)**와 함께 심각도별로 정리한 것이다. 문체는 개별 리뷰와 동일하게 입문서 수준으로 용어를 풀어 쓰고, 이슈마다 대표 예제를 하나씩 붙였다.
>
> 용어 약속(스펙에는 정의가 없어 이 보고서가 임시로 고정): **RK**(Replication Key, 복제 키) = 슬레이브에서 어떤 행을 갱신·삭제할지 식별하는 키. 엔진이 PK 또는 NOT NULL UNIQUE(UK) 중 하나를 자동 선택한다. **RK 후보** = RK가 될 자격이 있는 PK/UK 제약. **REPLICATION 옵션** = 테이블 단위로 복제 대상(ON)/제외(OFF)를 정하는 새 옵션.

## 1. 요약 (릴리스 판정)

### 1.1 스펙의 현재 상태

이 스펙이 풀려는 문제(PK 없는 테이블 때문에 HA 복제가 조용히 깨지고 마스터/슬레이브 데이터가 불일치하는 실제 장애)와 큰 방향(PostgreSQL REPLICA IDENTITY 일부 채용 + REPLICATION 테이블 옵션)은 20개 리뷰 전원이 "타당하다"고 평가했다. 그러나 **문서를 실제 시나리오에 대입하면 컨셉·구현·문서 세 층위 모두에서 릴리스를 막는 결함이 나온다.**

- **내부 모순이 존재한다.** §8과 §9가 "복제 여부 표시가 없는 테이블의 기본값"을 각각 ON과 OFF로 **정반대로** 규정한다. 이 한 곳 때문에 구버전→신버전 업그레이드 결과가 "전부 복제됨" 또는 "전부 복제 안 됨"으로 갈린다 — 둘 다 이 기능이 애초에 막으려던 사고와 같은 종류다.
- **핵심 목표를 스펙 스스로 무력화한다.** FK(외래키) 참조 대상이 복제 제외면 failover 후 참조 데이터가 없어 애플리케이션이 깨진다는 것이 이 기능의 출발점인데, 스펙은 이를 `CREATE TABLE`/FK 추가 시점에만 막는다. 이미 맺어진 관계에서 부모 테이블을 나중에 `ALTER TABLE ... REPLICATION=OFF`로 바꾸는 경로는 아무도 막지 않아, 막으려던 그 장애가 ALTER 한 줄로 그대로 재현된다.
- **핵심 개념이 비결정적이다.** RK 자동 선택 규칙이 "ex.(예를 들어) 테이블 내 명시된 순서 중 가장 빠른 순서"라는 예시 수준으로만 적혀 있다. 확정 알고리즘이 아니라 마스터와 슬레이브가, 혹은 원본과 복원본(unload/load)이 서로 다른 컬럼을 RK로 고를 수 있다.
- **기존 고객 마이그레이션 경로가 통째로 비어 있다.** in-place 업그레이드, 롤링 업그레이드(버전 혼재 구간), 카탈로그 스키마 마이그레이션에 대한 서술이 전혀 없다.

### 1.2 릴리스 가능 여부 — **불가 (NEEDS_FIX)**

20개 리뷰가 매긴 "치명" 등급 지적이 리뷰당 평균 3~5건이며, 그중 상당수가 서로 다른 직군에서 **독립적으로 같은 지점**을 짚었다. 특히 아래 두 가지는 컨셉 차원의 결함이므로 문서 교정만으로는 해소되지 않는다.

1. §8/§9 기본값 모순 (즉시 하나로 확정 필요)
2. FK 참조 대상의 사후 REPLICATION=OFF 전환 미차단 (규칙 자체를 대칭으로 다시 설계해야 함)

**결론: 현재 문서로는 QA 테스트케이스 작성도, 구현 착수도, 사용자 매뉴얼화도 불가능하다. 아래 Top 10을 반영해 개정한 뒤 재검토해야 한다.**

### 2.1 치명 (Critical) — 릴리스 차단

---

#### C-1. RK 자동 선택 규칙이 비결정적 — "ex. 명시된 순서"

**합의도: ~20/20 (전 직군·전 연차)** · 대상: §1

"UK가 여러개 존재한다면 큐브리드 엔진에 의해 이 중 하나가 선택된다(ex. 테이블내에 명시된 순서 중 가장 빠른 순서)" — `ex.`라는 표현부터 이것이 확정 규칙인지 예시인지 불명확하고, "명시된 순서"가 (a) CREATE TABLE 텍스트 순서, (b) 카탈로그 내부 OID/생성시각 순서, (c) 컬럼 선언 순서 중 무엇인지 정의가 없다. 이 셋은 ALTER로 UK를 추가·삭제·재생성하면 서로 다른 결과를 낸다. 엔진개발자 리뷰들은 여기에 "마스터와 슬레이브가 각자 카탈로그를 보고 재계산하면 두 노드가 서로 다른 RK를 고를 수 있다(split-brain)"는 더 무거운 함의를 붙였다.

**대표 예제** (DB엔지니어·엔진개발자 공통):
```sql
CREATE TABLE t (a INT NOT NULL UNIQUE, b INT NOT NULL UNIQUE);
-- 텍스트 순서 기준이면 RK = a

ALTER TABLE t DROP CONSTRAINT u_t_a;   -- a의 UK 제거
ALTER TABLE t ADD CONSTRAINT UNIQUE(a); -- a의 UK를 다시 생성(카탈로그상 b보다 나중)
-- 이제 RK는 a인가 b인가? 기준 정의에 따라 갈린다. 사용자는 아무것도 "바꾸지" 않았다.
```

**예상 시나리오**
1. (전제) 마스터·슬레이브 2노드 HA 구성. 테이블 t는 PK 없이 NOT NULL UNIQUE 컬럼 a, b 두 개를 가진 복제 테이블이다. 마스터와 슬레이브가 각자 자기 카탈로그를 보고 복제 키를 계산한다(스펙에 "마스터가 정한다"는 규정이 없어 노드별 재계산으로 가정 — 스펙 미정의라 가정).
2. (조작) 운영자가 위 예제처럼 a의 UNIQUE 제약을 지웠다가 다시 추가한다. 마스터는 재계산해도 여전히 a를 복제 키로 고르지만, 슬레이브는 카탈로그상 생성 순번이 뒤바뀌어 b를 복제 키로 고른다.
3. (예상 결과) 이후 마스터에서 `UPDATE t SET c=... WHERE a=1`이 실행되면, 마스터는 a 값을 행 식별자로 삼아 복제 로그를 남긴다. 슬레이브는 자신이 고른 b를 식별자로 기대하므로 로그의 a 값만으로는 갱신할 행을 찾지 못한다. applylogdb는 대상 행을 찾지 못해 조용히 건너뛰거나 fail_count가 올라간다.
4. (사용자 증상) 마스터에 반영된 변경이 슬레이브에는 반영되지 않아 두 노드 데이터가 서서히 어긋난다. Failover 후 애플리케이션이 슬레이브를 읽으면 옛 값이 나온다. 정작 이 스펙이 없애려던 "조용한 복제 누락"이 복제 키 선택 규칙 자체에서 다시 생긴다.

**권고**: 선택 기준을 "제약이 카탈로그에 생성된 순번(단조 증가 ID) 오름차순" 같은 조회 가능한 단일 규칙으로 명문화하고, "한번 선택된 RK는 명시적 DDL 없이는 재선택되지 않는다(sticky)"는 불변식을 추가한다. 마스터가 결정한 RK를 DDL 복제 로그에 실어 슬레이브가 **재계산하지 않고 그대로 사용**하도록 아키텍처를 확정한다.

#### C-2. FK 참조 부모 테이블의 사후 REPLICATION=OFF 전환 미차단

**합의도: ~18/20 (PM·DBA·사용자·응용·엔진 전 직군)** · 대상: §2-2, §4, §5

이 기능의 존재 이유(도입부 다이어그램: orders는 복제되는데 참조 대상 customers가 복제 제외라 failover 후 FK가 깨짐)를 스펙이 스스로 뚫는 가장 심각한 컨셉 결함이다. §5는 FK를 **생성/추가하는 시점**에만 참조 대상이 복제 대상인지 검사한다. 반면 §2-2는 "OFF→ON 전환 금지"라는 한 방향만 규정하고, 반대 방향인 "이미 FK로 참조받는 ON 테이블을 OFF로 내리는 것"은 아무 규칙이 없어 예시 6("ALTER ... REPLICATION=OFF → OK")대로 통과한다. §7 검사는 HA 재시작 시점에만 동작하므로, HA를 계속 켜둔 채 운영하면 다음 재시작 전까지 위반이 감지되지 않는다.

**대표 예제** (거의 모든 리뷰가 동일 형태로 제시):
```sql
-- 예시 17과 동일한 정상 구성 (둘 다 REPLICATION=ON), HA 운영 중
CREATE TABLE customers(customer_id INT PRIMARY KEY, country INT);
CREATE TABLE orders(order_id INT PRIMARY KEY, customer_id INT,
  CONSTRAINT fk FOREIGN KEY(customer_id) REFERENCES customers(customer_id));

ALTER TABLE customers REPLICATION=OFF;   -- 이를 막는 규칙이 스펙에 없음 → OK로 읽힘
-- 이 순간부터 orders(ON)는 복제되지만 customers(OFF)는 복제 안 됨.
-- Failover → 슬레이브에 orders만 있고 customers 데이터 없음 = 도입부 다이어그램 그대로 재현
```

**권고**: `ALTER TABLE ... REPLICATION=OFF` 실행 시, 그 테이블을 참조하는 FK가 있는 복제 대상 테이블이 하나라도 있으면 에러로 차단한다(예시 18의 대칭 규칙). §5의 검사를 "생성 시점"이 아니라 "불변식(항상 유지)"으로 재정의한다.

#### C-3. 현재 RK가 무엇인지 조회할 방법이 없다

**합의도: ~18/20** · 대상: §2-3 (예시 8·9)

`show create table`과 `select * from db_class`는 REPLICATION ON/OFF 여부만 보여줄 뿐, PK/UK가 여러 개일 때 **엔진이 실제로 무엇을 RK로 골랐는지**는 출력하지 않는다. RK는 사용자가 수정할 수 없고(§4-2) 자동으로 바뀔 수도 있는 값인데(C-1), 그 결과를 확인할 수단이 없다. 그 결과 사용자는 §4-2의 제약(RK로 쓰이는 UK는 삭제 불가 등)에 걸릴지 아닐지를 **DDL을 실행해 에러가 나야만** 알게 된다. 장애 디버깅(관측성), 배포 사전검증(응용), 스키마 감사(엔진 리뷰의 규제산업 관점) 모두 이 정보에 의존한다.

**대표 예제**:
```sql
CREATE TABLE t(a INT NOT NULL UNIQUE, b INT NOT NULL UNIQUE);  -- PK 없음, UK 2개
show create table t;      -- 'REPLICATION ON' 만 보임. a와 b 중 무엇이 RK인지 안 나옴
select * from db_class where class_name='t';  -- replication: ON 만 있음
```

**예상 시나리오**
1. (전제) HA 운영 중. 테이블 t는 PK 없이 NOT NULL UNIQUE 컬럼 a, b 두 개. 엔진이 둘 중 하나를 복제 키로 자동 선택했지만(§1), 어느 것을 골랐는지 조회할 수단이 없다.
2. (조작) 운영자가 스키마 정리 작업으로 a 컬럼의 UNIQUE 제약을 지우려 한다. 사전에 `show create table t`와 `db_class`를 확인했지만 `REPLICATION ON`만 보이고 a가 복제 키인지는 나오지 않아, 그냥 삭제 DDL을 실행한다.
3. (예상 결과) 만약 a가 실제 복제 키였다면 이 DDL은 §4-2 예시 15 규칙("복제 키로 쓰는 UNIQUE는 삭제 불가")에 걸려 ERROR로 거부된다. 운영자는 DDL을 실제로 실행해 에러가 나야만 a가 복제 키였음을 뒤늦게 알게 된다.
4. (사용자 증상) 배포 스크립트가 이 지점에서 처음 멈춘다. 사전 점검이나 스키마 감사 단계에서는 위험을 미리 알 방법이 없어, 위험이 항상 운영 반영 시점의 예기치 못한 실패로 나타난다.

**권고**: `db_class`(또는 신규 시스템 뷰 `db_replication_key`)에 RK로 선택된 제약명·컬럼 목록·RK 후보 개수 컬럼을 추가하고, `show create table` 출력에도 `REPLICATION ON (RK: pk_t_a)` 형태로 표기한다.

#### C-4. §7 "파일 리스트"의 정체·포맷·exit code 미정의

**합의도: ~18/20** · 대상: §7

"제약사항 위반 시 에러와함께 파일 리스트를 출력한다" — (1) "파일"이 위반 테이블 목록인지, OS 파일 경로인지, 로그 파일인지 불명확하고(CUBRID에서 위반 단위는 테이블이지 파일이 아님), (2) 출력 매체(표준에러/로그파일), 위반 사유 구분(RK 없음 vs FK 참조 위반), 개수 제한, exit code가 전혀 정의되지 않았다. 신입 운영자는 새벽 장애 시 무엇을 봐야 할지 모르고, 자동화 스크립트는 성공/실패를 문자열 grep으로 추측해야 하며, 대량 위반 시(수백~수천 테이블) 콘솔 한 번 출력으로는 처리 불가능하다.

**대표 예제** (DB엔지니어 3년차):
```bash
$ cubrid hb start testdb
ERROR: replication constraint violation
tbl_a
tbl_b
$ echo $?   # 0인가 1인가? 스펙에 없음 → HA가 안 떴는데도 트래픽이 전환되는 사고 가능
```

**예상 시나리오**
1. (전제) 신버전으로 교체한 HA 클러스터. 복제 테이블 여러 개에 복제 키가 없어 §7 검사에 걸리는 상태다. 장애 대응 자동화 스크립트가 `cubrid hb start`의 성공/실패로 트래픽 전환 여부를 결정한다.
2. (조작) 새벽에 스크립트가 슬레이브를 승격시키려 `cubrid hb start`를 실행하고, 반환된 exit code로 성공 여부를 판정한다.
3. (예상 결과) 제약 위반으로 HA는 실제로는 기동되지 않았지만, exit code 규약이 스펙에 없어(스펙 미정의라 가정) 스크립트가 0(성공)으로 오판할 수 있다. 위반 테이블 목록은 콘솔에 텍스트로만 찍혀 스크립트가 구조적으로 파싱하지 못한다.
4. (사용자 증상) HA가 뜨지 않은 노드로 트래픽이 넘어가 서비스가 중단된다. 운영자는 콘솔 로그의 테이블 이름을 눈으로 훑어야 하고, 위반이 수백 개면 원인 테이블을 추려 내는 데만 한참이 걸린다.

**권고**: "파일 리스트"→"위반 테이블 목록(스키마.테이블명 + 위반 사유 코드)"으로 정정, 기계 판독 가능한 포맷과 실패 시 비정상 exit code를 명시.

#### C-5. §8 vs §9 기본값 정면 모순 (표시 없음 = ON vs OFF)

**합의도: ~10/20 (PM·DBA·사용자·엔진; 문서 대조가 업무인 직군에서 집중 포착)** · 대상: §8, §9

- §8: "복제 여부를 저장하는 변수가 설정되어 있지 않다면 **복제 대상(Default)**으로 간주" + "하위 버전 unload 파일은 load 시 **모두 복제 테이블로** 설정"
- §9: "UNLOADDB 시 ... 이를 포함하지 않는 테이블은 **모두 복제 제외 테이블**이다"

같은 조건에 정반대 결과. §8이 두 번 반복 서술하므로 §9가 오기일 가능성이 높지만, 문서만으로는 확정 불가.

**대표 예제**:
```
구버전 unload 파일(REPLICATION 필드 없음)을 신버전 loaddb
 - §8 적용: orders → REPLICATION=ON (기존 복제 유지, 단 RK 없으면 HA 기동 실패)
 - §9 적용: orders → REPLICATION=OFF (조용히 복제에서 빠져 마스터/슬레이브 불일치)
```

**권고**: 담당 엔지니어에게 의도 확인 후 한쪽으로 통일. "기본값 정책"을 §1의 표 하나에만 정의하고 §8/§9는 참조만.

#### C-6. 기존 클러스터 업그레이드 / 롤링 업그레이드 / 카탈로그 마이그레이션 경로 부재

**합의도: ~14/20 (PM 전원 + DBA + 엔진)** · 대상: 스펙 전체(특히 §7, §8)

스펙은 "기능이 켜진 뒤"만 기술하고 도입 과도기를 다루지 않는다. 구체적으로 (a) in-place 업그레이드(볼륨 그대로 새 바이너리로 재기동) 시 `db_class`에 새로 생기는 `replication` 컬럼을 무엇으로 채우는지, (b) 롤링 업그레이드에서 신버전 마스터가 만든 `REPLICATION=OFF` DDL을 구버전 슬레이브가 어떻게 파싱하는지(파싱 실패 → fail_count 증가 = 원래 버그 재발), (c) 기존 고객이 업그레이드 직후 `cubrid hb start`가 RK 없는 테이블 때문에 아예 기동 거부되는데 이를 **사전에** 점검할 도구가 없다는 점이 모두 비어 있다.

**대표 예제** (PM 10년차):
```
1. 구버전 HA 운영 중, orders는 PK 없이 운영(구버전은 허용, 복제만 누락)
2. 신버전 바이너리로 교체 후 cubrid hb start
3. §7 규칙에 걸려 HA 기동 거부 → 이미 서비스 중단된 뒤에야 문제를 앎
```

**권고**: 업그레이드 전용 절 신설 — 인플레이스 시 카탈로그 마이그레이션 규칙("기존 테이블은 모두 ON으로 간주"), 롤링 업그레이드 호환 정책(또는 "마스터/슬레이브 동시 교체 필수" 명시), HA 기동 전 사전 점검 명령(`cubrid hb check`류) 제공.

#### C-7. 복합 ALTER(예시 13)의 원자성·중간 상태·동시 DML 처리 미정의

**합의도: ~14/20 (사용자·응용·엔진 집중)** · 대상: §2-2 예시 7, §4-2 예시 13

예시 13(`DROP CONSTRAINT PRIMARY KEY, ADD CONSTRAINT PRIMARY KEY(a)`)은 "OK"만 보여준다. 그런데 (1) 이 문장이 원자적으로 처리되는지, 아니면 DROP 후 ADD 사이에 "RK 0개" 상태를 거치는지, (2) 그 찰나에 동시 세션이 DML을 실행하면 복제 로그가 어느 RK 기준으로 기록되는지, (3) ADD가 실패하면 DROP까지 롤백되는지가 전혀 없다. 이는 스펙 내부 모순으로도 이어진다 — 절 단위 순차 검증이라면 DROP 직후 RK 0개가 되어 예시 13은 항상 실패해야 하는데 스펙은 OK라고 한다. 즉 "문장 전체 최종 상태 기준 검증 + 원자성"을 전제해야만 예시 13이 성립하는데, 그 전제가 문서에 없다.

**대표 예제** (엔진 5년차):
```sql
-- table_name.a 컬럼에 이미 중복값이 있는 상태
ALTER TABLE table_name DROP CONSTRAINT PRIMARY KEY, ADD CONSTRAINT PRIMARY KEY(a);
-- ADD 단계 실패 시 DROP은 롤백되는가? 그 사이 복제 로그에 무엇이 남았는가?
```

**예상 시나리오**
1. (전제) HA 운영 중. 복제 테이블 table_name은 복제 키가 PK 하나뿐이고, a 컬럼에는 이미 중복 값이 들어 있다.
2. (조작) 운영자가 예시 13처럼 한 문장으로 PK를 지우고 a로 새 PK를 만든다(`DROP CONSTRAINT PRIMARY KEY, ADD CONSTRAINT PRIMARY KEY(a)`). 동시에 다른 세션이 같은 테이블에 INSERT/UPDATE를 실행하고 있다.
3. (예상 결과) 문장 처리가 절 단위 순차라면 DROP 직후 복제 키가 0개인 순간이 생기고, ADD는 a의 중복 값 때문에 실패한다. 이때 DROP까지 되돌려지는지, 그 찰나에 들어온 동시 DML이 어느 키를 기준으로 복제 로그에 남는지가 스펙에 없다(스펙 미정의라 가정).
4. (사용자 증상) 되돌림이 보장되지 않으면 테이블이 복제 키 없는 상태로 남아 이후 변경이 슬레이브에 반영되지 않거나, 다음 HA 재시작이 §7 검사로 거부된다. 동시 DML이 옛 키 기준으로 기록됐다면 슬레이브가 대상 행을 찾지 못해 마스터와 슬레이브가 어긋난다.

**권고**: "쉼표로 연결된 다중 ALTER 절은 하나의 원자적 트랜잭션·단일 복제 로그 레코드로 처리하며, 최종 상태 기준으로 RK 제약을 검증하고, 일부 절 실패 시 전체 롤백한다. RK 변경 DDL은 테이블 배타 스키마 잠금을 잡아 동시 DML을 대기시킨다"를 §4-2에 명시.

#### C-8. RK 전환 DDL과 복제 로그의 순서·정합성 미정의

**합의도: ~9/20 (엔진 전 연차 + PM 5년차 + 사용자·DBA 일부)** · 대상: §4-2, 복제 로그 포맷

복제 로그는 커밋 순서(LSA)대로 슬레이브에 적용되는데, RK를 바꾸는 DDL이 커밋되기 전 옛 RK 기준으로 기록된 DML 로그가 슬레이브에 아직 적용되지 않고 큐에 남아 있을 수 있다. DDL이 먼저 적용되어 슬레이브 카탈로그의 RK가 바뀐 뒤 옛 RK 기준 로그가 도착하면, applylogdb가 어떤 컬럼으로 대상 행을 찾을지 정의가 없다. 특히 복제 지연(lag)이 있거나 병렬 적용(사내 논의 중)이면 순서 보장이 더 취약하다. 복제 로그가 RK를 컬럼 참조로만 담는지, 값 스냅샷·스키마 버전 태그를 함께 담는지도 불명확하다.

**대표 예제** (엔진 1년차):
```
T1(마스터): UPDATE tbl SET c=100 WHERE a=5;   -- RK=a 기준으로 로그 기록
T2(마스터): ALTER ... RK를 a→a2로 교체
슬레이브 도착 순서: (1) ALTER 먼저 적용(RK=a2) → (2) "a=5" UPDATE 뒤늦게 도착
→ RK가 a2로 바뀐 슬레이브에서 "a=5" 조건을 어떻게 처리하나?
```

**예상 시나리오**
1. (전제) HA 운영 중이며 슬레이브에 복제 지연이 있어 아직 적용하지 못한 로그가 큐에 쌓여 있다. 테이블 tbl의 복제 키는 a다.
2. (조작) 마스터에서 먼저 `UPDATE tbl SET c=100 WHERE a=5`가 커밋되고(옛 키 a 기준으로 로그 기록), 곧이어 복제 키를 a에서 a2로 바꾸는 ALTER가 커밋된다.
3. (예상 결과) 슬레이브에는 DDL(ALTER)이 먼저 적용되어 카탈로그의 복제 키가 a2로 바뀐 뒤, 뒤늦게 도착한 "a=5" UPDATE 로그가 적용을 시도한다. 슬레이브가 a2를 식별자로 기대하면 a 값만으로는 대상 행을 찾지 못한다. applylogdb가 이를 어떻게 처리할지 스펙에 없어(스펙 미정의라 가정), 대상 행을 못 찾아 조용히 건너뛸 가능성이 크다.
4. (사용자 증상) 마스터의 `c=100` 변경이 슬레이브에서 누락되어 두 노드가 어긋난다. 위반이 조용한 건너뜀이라 로그에도 뚜렷한 에러가 남지 않아, Failover 후에야 값 불일치로 발견된다. 병렬 적용 경로에서는 순서 보장이 더 취약해 재현 빈도가 높아진다.

**권고**: RK 변경 DDL을 배리어(barrier)로 취급 — 그 이전 모든 DML이 슬레이브에 적용 완료된 뒤에만 활성화. 복제 로그 레코드에 RK 스키마 버전을 함께 기록. 병렬 적용 경로에서도 이 순서를 강제.

#### C-9. NOT NULL 해제·컬럼 타입 변경 등 "열거되지 않은 경로"로 RK 자격 조용히 상실

**합의도: ~7/20 (PM·DBA·응용·엔진; 원래 배경 버그와 직결)** · 대상: §4-2

§4-2는 UK를 RK로 쓸 때 "UNIQUE 제약 삭제"와 "컬럼 삭제"(예시 15)만 막는다. 그런데 RK 자격은 "**NOT NULL** UNIQUE"이므로, UNIQUE는 그대로 두고 `ALTER TABLE ... MODIFY COLUMN a INT NULL`로 NOT NULL만 풀어도 RK 자격이 사라진다. 또 RK 컬럼 타입을 `INT → BIGINT`로 바꾸는 흔한 작업(정작 원래 배경 버그인 "PK 컬럼 속성 변경"과 정확히 같은 유형)도 §4-2에 없다. 열거식 차단이라 우회로가 남고, "HA 복제 대상은 항상 RK를 가진다"는 §1 불변식이 실제로는 보장되지 않는다.

**대표 예제**:
```sql
CREATE TABLE tbl(a INT, b INT NOT NULL UNIQUE);  -- RK = b
ALTER TABLE tbl MODIFY COLUMN b INT NULL;        -- UNIQUE는 유지, NOT NULL만 제거
-- 스펙 어느 규칙에도 안 걸림. b는 이제 RK 자격 상실 → 운영 중 RK 없는 복제 테이블 발생
```

**예상 시나리오**
1. (전제) HA 운영 중. 테이블 tbl은 PK가 없고 b가 NOT NULL UNIQUE라 b가 복제 키다.
2. (조작) 운영자가 UNIQUE 제약은 그대로 둔 채 NOT NULL만 푼다(`ALTER TABLE tbl MODIFY COLUMN b INT NULL`). §4-2는 UNIQUE 삭제와 컬럼 삭제만 막으므로, 이 문장은 어느 규칙에도 걸리지 않고 통과한다.
3. (예상 결과) b는 "NOT NULL UNIQUE"라는 복제 키 자격을 잃는다. 다른 후보가 없으면 복제 키가 0개가 되지만, HA는 이미 켜져 있고 §7 검사는 HA 기동 시점에만 도므로 재시작 전까지는 위반이 감지되지 않는다.
4. (사용자 증상) 이후 이 테이블의 변경이 슬레이브에 제대로 반영되지 않거나(식별자 부재), 다음 HA 재시작에서 갑자기 기동이 거부된다. 배경 장애였던 "PK 컬럼 속성 변경으로 인한 복제 누락"과 사실상 같은 현상이 다른 경로로 재발한다.

**권고**: "RK 자격에 영향을 주는 모든 DDL 경로(제약 삭제·컬럼 삭제·NOT NULL 해제·타입 변경 등)를 전수 조사해 §4-2에 포함하고, 열거되지 않은 경로는 기본 차단"을 원칙으로 선언.

#### M-1. §4-2 "복제키 후보" 용어 미정의 + "모든 DDL 허용(단 기존 제약 유지)"이 예시 12와 모순

**합의도: ~14/20** · 대상: §4-2

§1은 단수 "복제 키"만 설명하다가 §4-2에서 갑자기 "복제키 후보"를 정의 없이 쓴다. "후보 = PK 하나 + 모든 UK"인지, "현재 RK를 제외한 나머지"인지 불명확해 카운팅 로직을 구현할 수 없다. 게다가 본문 "다른 복제키 후보가 함께 존재한다면 모든 DDL은 허용된다"와 예시 12("PK가 복제키면 무조건 삭제 불가")가 PK+UK 공존 테이블에서 정반대 결론(OK vs ERROR)을 낸다. 또 "기존의 제약사항은 유지된다"의 "기존"이 무엇을 가리키는지, 검증 시점이 DDL 실행 전 상태인지 후 상태인지도 없다.

**대표 예제**:
```sql
CREATE TABLE tbl(a INT PRIMARY KEY, b INT NOT NULL UNIQUE, c INT);
ALTER TABLE tbl DROP PRIMARY KEY;
-- 본문("다른 후보 b 있음 → 허용") → OK / 예시12("PK는 삭제 불가") → ERROR. 어느 쪽?
```

**권고**: §1에 "복제키 후보"를 정식 정의하고, "검증은 문장 전체 적용 후 최종 상태 기준"임을 명시, 예시 11~16 각각에 "이 테이블은 후보 N개" 전제를 표기.

#### M-2. 뷰(§6)와 FK(§5)의 검증 강도 불일치 — VIEW는 경고조차 없음

**합의도: ~12/20 (사용자·응용에서 특히 강함)** · 대상: §5, §6

동일한 근본 위험("복제 제외 테이블의 부재 데이터에 의존")인데 FK는 생성 시점 하드 에러(예시 18)로 막고, VIEW는 아무 검사 없이 통과시킨 뒤 "책임지지 않는다"로 끝낸다. VIEW는 SQL 에러도 없이 failover 후 "조용히 축소된 결과"(예: LEFT JOIN에서 country가 전부 NULL)를 반환해 오히려 더 위험하다 — 리포팅·대시보드가 잘못된 숫자를 사용자에게 보여준다.

**대표 예제** (응용 10년차):
```sql
CREATE TABLE customers(...) REPLICATION=OFF;
CREATE VIEW order_summary AS SELECT o.order_id, c.country FROM orders o LEFT JOIN customers c ON ...;
-- CREATE VIEW: 경고 없이 OK. Failover 후 SELECT: 에러 없이 country 전부 NULL
```

**권고**: 최소한 `CREATE/ALTER VIEW` 시 복제 제외 테이블 참조를 감지해 WARNING 출력. FK와 정책 차이가 의도라면 그 근거를 문서화.

#### M-3. PostgreSQL REPLICA IDENTITY 대비 사용자 명시 지정·FULL 폴백 없음 (경쟁·유연성 열위)

**합의도: ~10/20 (PM·엔진·응용 상위 연차)** · 대상: 배경, §1

PostgreSQL은 `DEFAULT`/`USING INDEX`(사용자 지정)/`FULL`(전 컬럼)/`NOTHING` 네 모드를 제공하는데, 이 스펙은 "엔진 자동 선택"만 채용하고 사용자 지정 수단(`USING INDEX` 상당)을 뺐다. UK가 여럿일 때 값이 안 바뀌는 안정적 키를 RK로 강제하고 싶어도 방법이 없다. 또 PK/UK가 없으면 `FULL` 같은 "느려도 복제는 됨" 폴백 없이 오직 "복제 포기(OFF)"뿐이라, MySQL 대비 성능은 얻었지만 유연성은 더 낮아졌다. 엔진·PM 리뷰는 "왜 폴백/명시지정을 뺐는지 근거를 남기지 않으면 향후 재설계 비용이 크다"고 지적.

**대표 예제**:
```sql
-- PostgreSQL: ALTER TABLE t REPLICA IDENTITY USING INDEX t_stable_key;  (명시 지정 가능)
-- 이 스펙: 대응 문법 없음. 순서를 조작하거나 다른 UK를 다 지우는 우회뿐
```

**권고**: 로드맵에 명시 지정 문법(`REPLICATION KEY USING (...)`) 검토를 명기하고, 이번 릴리스에서 폴백을 뺀 설계 근거를 스펙에 한 문단 추가.

#### M-4. 개발/스테이징(싱글)에서 통과한 DDL이 운영(HA)에서만 실패 — 사전점검(dry-run) 도구 부재

**합의도: ~10/20 (응용·DBA 집중)** · 대상: §3, §4, §7

§3은 싱글 모드에 RK 제약이 "없다"고 하고, 검사는 §7(HA 기동 시점)에만 걸린다. CI가 싱글 스테이징에서 통과시킨 마이그레이션이 운영 HA 배포 시점에 처음 실패한다(dev/prod parity 붕괴). Flyway/Liquibase 이력 테이블과 실제 스키마가 어긋나는 부분 적용 문제도 파생된다.

**대표 예제** (응용 3년차):
```sql
-- 로컬/스테이징(싱글): ALTER TABLE customers DROP CONSTRAINT u_customers_email;  → OK
-- 운영(HA): 같은 문장 → ERROR (email UK가 유일 RK였다면, 예시 15)
```

**예상 시나리오**
1. (전제) 애플리케이션 팀이 싱글 모드 스테이징에서 스키마 마이그레이션을 검증한다. 대상 테이블 customers는 email UK가 유일한 복제 키이며, 싱글 모드에는 복제 키 제약이 없다(§3).
2. (조작) CI 파이프라인이 스테이징에서 `ALTER TABLE customers DROP CONSTRAINT u_customers_email`을 실행한다. 제약이 없어 통과하고, 파이프라인은 초록불로 운영 배포를 승인한다.
3. (예상 결과) 같은 문장을 운영 HA에 적용하면 email이 유일 복제 키였으므로 §4-2 예시 15 규칙에 걸려 ERROR로 거부된다. 검사가 HA 운영·기동 시점에만 걸리므로(§4·§7) 스테이징에서는 결코 드러나지 않는다.
4. (사용자 증상) 마이그레이션이 운영 배포 도중에야 처음 실패한다. 여러 문장 중 일부만 적용된 채 멈추면 Flyway·Liquibase 같은 도구의 이력과 실제 스키마가 어긋나, 되돌리거나 다시 적용하기가 까다로워진다.

**권고**: `cubrid hb check --dry-run` 또는 싱글 모드용 `--strict-ha` 시뮬레이션 제공. 문서에 "싱글 통과 ≠ HA 통과" 경고 명시.

#### M-5. REPLICATION=OFF↔ON 전환 시 슬레이브 데이터 처리·재동기화 방침 없음, HA중 OFF→ON 금지 근거 없음

**합의도: ~10/20** · 대상: §2-2, §4

(a) ON→OFF 전환 시 슬레이브에 이미 쌓인 데이터가 삭제되는지 "박제된 옛 스냅샷"으로 남는지 없음(stale read 위험). (b) OFF→ON은 HA 중 아예 금지인데(예시 5), 그렇다면 그동안 마스터에만 쌓인 데이터를 슬레이브에 어떻게 최초 동기화하는지 절차가 없다. (c) OFF→ON 금지의 "근거"(초기 스냅샷 부재로 추정)가 명시되지 않아 의도된 제약인지 불명. 응용 리뷰들은 "일단 OFF로 벌크 적재 후 ON" 및 "점진적 롤아웃" 패턴이 운영 중 봉쇄된다고 지적.

**대표 예제**:
```sql
ALTER TABLE big_orders REPLICATION=OFF;  -- 한 달간 500만건 INSERT (슬레이브 미반영)
ALTER TABLE big_orders REPLICATION=ON;   -- 예시5: HA에서 ERROR. 과거분은 영영 갭으로 남나?
```

**예상 시나리오**
1. (전제) HA 운영 중. big_orders는 복제 테이블(REPLICATION=ON)이다.
2. (조작) 운영자가 대량 적재 성능을 위해 `ALTER TABLE big_orders REPLICATION=OFF`로 복제를 끄고 한 달간 500만 건을 INSERT한 뒤, 다시 `REPLICATION=ON`으로 되돌리려 한다.
3. (예상 결과) OFF 구간 동안 슬레이브에는 이 500만 건이 반영되지 않는다. 되돌리는 `ALTER ... REPLICATION=ON`은 HA 모드에서 금지되어(예시 5) ERROR로 거부된다. OFF→ON 전환 시 그동안 마스터에만 쌓인 데이터를 슬레이브에 처음으로 맞춰 넣는 절차가 스펙에 없다(스펙 미정의라 가정).
4. (사용자 증상) 복제를 다시 켤 방법이 없어 운영 중에는 되돌리지 못한다. 억지로 되돌리더라도 과거 500만 건은 슬레이브에 영영 빈 구간으로 남아, Failover 후 그만큼의 데이터가 사라진 것처럼 보인다.

**권고**: 전환 시 슬레이브 데이터 처리(유지/TRUNCATE)를 명시, OFF→ON 시 재동기화 공식 절차 제공, 금지 근거를 문서화.

#### M-6. 에러 메시지가 대부분 "ERROR"만 — 실제 문구·에러 코드 없음

**합의도: ~10/20 (사용자·응용에서 강함)** · 대상: §4-2, §5 예시 다수

예시 11만 실제 메시지를 보여주고 예시 5·10·12·15·16·18·22·23은 "ERROR"만 적혀 있다. 사용자는 무엇을 검색해야 할지 모르고, 자동화 파이프라인은 "RK 위반"과 "문법 오류"를 구분할 코드가 없어 예외 처리 분기를 짤 수 없다.

**대표 예제**:
```sql
ALTER TABLE table_name DROP PRIMARY KEY;
-- ERROR  ← "PK가 RK라 삭제 불가"인지 기존 일반 에러인지 문구·코드 없음
```

**권고**: RK/FK 신규 제약 위반마다 고유 에러 코드·메시지("Column ... is used as replication key ...") 부여, 모든 예시를 예시 11 수준으로 통일.

#### M-7. 복제 제외 테이블 전수 조회 수단 없음 + 업그레이드 후 대량 위반 일괄정비 도구 없음

**합의도: ~9/20 (DBA 집중)** · 대상: §2-3, §7, §8

`show create table`/`db_class`는 테이블 하나씩만 조회한다. "이 DB에 REPLICATION=OFF/RK 없는 테이블이 몇 개인지"를 한 번에 뽑는 표준 조회가 없고, `db_class.replication`이 WHERE로 필터 가능한 공개 인터페이스인지 명시도 없다. 구버전 백업 load 시 전 테이블이 ON으로 잡혀 HA 기동 시 수십~수백 개가 한꺼번에 위반되는데, 이를 일괄 정비할 도구·목록이 없다.

**권고**: 전수 조회 뷰 + `loaddb` 후 "RK 없는 ON 테이블 목록" 자동 리포트 + 일괄 처리 유틸.

#### M-8. 다단계/자기참조/순환 FK, 복합키 RK, FK-UK 겸용 컬럼의 검증 규칙 부재

**합의도: ~8/20** · 대상: §5, §4-2

§5는 "직접 참조 1단계"만 다룬다. A→B→C 체인에서 C가 OFF일 때 전이적으로 검사하는지, 자기참조(`employee.manager_id→employee`)나 순환 FK를 어떻게 다루는지 없다. 엔진 리뷰는 복합 UK가 RK로 뽑히면 로그가 커지는 성능 영향(MySQL을 성능으로 배제해놓고 정작 RK 선택은 성능을 안 봄)을, 응용 리뷰는 FK이면서 동시에 유일 UK인 컬럼 삭제 시 예시 22(허용)와 예시 15(금지)의 우선순위 미정을 지적.

**권고**: 재귀 검사 범위·자기참조/순환 처리·복합키 우선순위·다중역할 컬럼 우선순위를 명시하고 각 예제 추가.

---

#### M-9. 멀티 슬레이브·체인 복제 확장성 — 테이블 전역 플래그의 한계

**합의도: ~6/20 (PM·엔진 상위 연차)** · 대상: 컨셉 전체

REPLICATION은 테이블당 값 하나인 전역 속성이라 "슬레이브 A(DR)에는 전체, 슬레이브 B(분석용)에는 PII 제외" 같은 슬레이브별 차등 복제를 표현할 수 없다. RK 계산이 노드별 로컬 재계산이면 체인 복제·지연 구간에서 노드마다 RK가 어긋날 수 있다.

**권고**: 최소한 "이번 범위는 테이블 단위 전역 복제 여부만이며 슬레이브별 차등·컬럼 단위 필터는 out of scope"라고 스코프를 명시.

---

#### M-10. REPLICATION 옵션 변경의 락·성능 영향, in-place 여부 미정의

**합의도: ~5/20 (PM·엔진)** · 대상: §2-2, §4

`ALTER TABLE ... REPLICATION=OFF`가 메타데이터 전용 O(1) 연산인지, 대용량 테이블에서 락을 얼마나 오래 잡는지 없다. 대량 이관 시 여러 테이블을 일괄 전환하는 스크립트의 서비스 영향을 평가할 수 없다.

**권고**: 옵션 변경이 메타데이터 전용임을 명시(아니면 소요 시간·락 범위 문서화).

### 2.3 보통 (Minor)

- **N-1. 예시 SQL trailing comma 문법 오류 (예시 2, 20, 23)** — 합의도 **~20/20**. 심각도는 낮지만 전원이 지적. 예제가 실행 불가라 "RK 때문에 난 에러"인지 "문법 오류"인지 구분 못 함. → 전 예제를 실제 csql로 검증.
- **N-2. 예시 7 "..." 템플릿은 실행 불가 + 예시 13과 중복** (~8). → 구체 SQL로 대체하거나 예시 13 참조.
- **N-3. 예시 10 테이블명 `repl_table_with_rk`가 내용(RK 없음)과 반대 + 예시 1과 이름 충돌** (~5). → 순차 실행 시 "이미 존재" 에러가 나 인과관계가 뒤바뀜.
- **N-4. 예시 19/21 FK 자동 명명 규칙 미문서화** (`fk_new_orders_customer_id`가 어디서 나왔나) (~5).
- **N-5. 예시 16 DROP INDEX가 UNIQUE/일반 인덱스 구분 없음** (~5). → 일반 인덱스 삭제까지 막힌다는 오해.
- **N-6. 예시 8 출력에 REUSE_OID/COLLATE 등 무관 키워드 각주 없음** (~3).
- **N-7. REPLICATION 표기 3종 혼용**(`REPLICATION=ON` / `REPLICATION ON` / `replication : ON`), OFF일 때 `show create table` 예시 없음 (~5).
- **N-8. 컬럼 단위 복제 제외(PII 마스킹) 요구 미지원** (응용 5년차 고유, ~2).
- **N-9. 읽기/쓰기 분리 아키텍처에서 OFF 테이블이 슬레이브로 라우팅되면 조용히 빈 결과** (응용 5년차 고유, ~1).
- **N-10. FK 강제복제가 정적 코드 테이블 OFF 설계를 봉쇄**(무결성 vs 비용 이분법) (응용, ~3).
- **N-11. DROP TABLE 후 동일명 재생성으로 OFF→ON 금지 우회** (응용 5년차, ~1).
- **N-12. unload 파일 포맷 미명세**(변수 필드명·위치, 클래스 단위인지, 구버전 파서가 신규 토큰 만나면?) (~6, 엔진·응용).

### 2.4 사소 (Trivial)

- **T-1. §5-1 제목 오타 "CRATE TABLE" + §7 "재시작해아한다" 등 오탈자** — 합의도 **~8/20**. SQL 키워드 오타는 문서 검색에도 지장.
- **T-2. §9 "SA" 모드가 정의 없이 처음 등장, §1의 "HA 아니면 싱글" 이분법과 충돌** — 합의도 **~7/20**. HA/CS/SA 관계를 §1에서 정의 필요.
- **T-3. §1 첫 문장 주술 비문**("복제 테이블은 ... HA모드를 실행 할 수 없다"), §4-2 "기존의 연산 결과와 동일한 경우 ..." 비문 (사용자 리뷰).

- **T-5. REPLICATION 예약어 승격 시 기존 `replication` 컬럼명 충돌** (~2).
- **T-6. "복제 테이블 / 복제 대상 테이블 / 복제키 후보 / 복제키" 용어 혼용, 용어집 부재** (~6).

## 4. 직군별 관점 요약 (그 직군에서 고유하게 나온 지적)

- **PM (요구사항·릴리스 리스크)**: 문서 내부 모순(§8/§9)을 가장 먼저 포착. 마이그레이션 경로 부재, 무중단 롤링 업그레이드, MUST/MAY 서법 미구분, 경쟁 포지셔닝 근거("MySQL이 왜 느린지" 정량 데이터 없음), Oracle GoldenGate 대비 미언급, 파티션 스코프 명시 요구가 PM 고유.

- **DB 엔지니어 (운영/DBA)**: "새벽 3시 장애 대응" 관점. §7 출력의 exit code·파싱 가능성, 신규 슬레이브 조인 시 OFF 테이블 초기 데이터, 스위치오버 전 사전점검 체크리스트, unloaddb가 OFF 테이블 데이터를 백업에 포함하는지(DR의 유일 안전망), 다중 슬레이브 구성, 다운그레이드(신→구 버전) 경로, fail_count 지표와 신규 위반의 관계가 DBA 고유.

- **최종 사용자 (사용성)**: "이 문서만으로 csql 앞에서 따라할 수 있나". 에러 메시지 실물 부재, 예시 12 vs 13의 반직관성("PK 삭제는 되는데 왜 한 문장으로 묶어야 하나"), §1 첫 문장 비문, 예시 3 어순 오류("복제 제외 PK"), "RK 유무와 REPLICATION 여부는 독립 축"이라는 개념이 문서 초반에 강조 안 됨이 사용자 고유.

- **응용 개발자 (ORM/마이그레이션)**: dev/prod parity 붕괴, Flyway/Liquibase가 DROP·ADD를 별도 changeSet으로 쪼개면 예시 13 요구와 충돌, ORM이 `@Column(unique=true)`를 nullable로 만들어 RK 후보 자격 조용히 미달, RK 자동선택이 ORM DDL 생성 순서에 취약, 컬럼 단위 PII 필터 미지원, 읽기/쓰기 분리 라우팅에서 OFF 테이블 빈 결과, `@Id`(PK) 의미와 RK 전환의 무관함 보장 필요가 응용 고유.

- **엔진 개발자 (구현)**: RK를 마스터가 정해 로그로 전파해야 함(노드 재계산 금지), 복제 로그 포맷에 RK 스키마 버전 필요, RK 후보 0개로 떨어지는 동시성 경쟁(TOCTOU) 재검증, 카탈로그에 RK 포인터 명시 저장, 트리거로 인한 간접 DML의 복제 귀속, SERIAL/AUTO_INCREMENT failover 동기화, REUSE_OID와 복제 로그의 독립성, 복합키 RK 성능, in-place 카탈로그 스키마 마이그레이션이 엔진 고유. **가장 깊고 구현 착수를 직접 막는 지적이 이 직군에 집중.**

## 5. 상충 의견 (리뷰어끼리 반대 방향)

1. **REPLICATION 기본값 ON vs OFF**
   - 사용자 3·5년차, PM 10년차: 기본값 ON은 "아무것도 안 하면 나중에 HA에서 터지는" 지뢰 → RK 없는 테이블은 기본 OFF로 하거나 최소한 CREATE 시 경고.
   - 엔진 3년차: 기본값을 OFF로 바꾸면 하위 호환(구버전은 사실상 전부 복제되던 동작)을 깨므로 ON 유지가 맞고, 대신 운영 가이드로 보완.
   - → **미해결 트레이드오프. "안전한 기본값" vs "하위 호환"이 정면 충돌.**

2. **FK-복제 결합을 느슨하게 vs 더 엄격하게**
   - 응용 3·10년차: 정적 코드 테이블을 OFF로 두고도 FK를 걸 수 있도록 예외 옵션(`NOT ENFORCED ON SLAVE` 류)을 달라 — **규칙 완화** 요구.
   - 대다수(PM·DBA·엔진·사용자): 오히려 ALTER OFF 경로까지 막아 FK-복제 불변식을 **강화**하라(C-2).
   - → 같은 §5를 두고 한쪽은 문을 더 열자, 다른 쪽은 더 잠그자.

3. **§8 기본값 중 어느 것이 오기인가**
   - 대다수: §8(ON)이 맞고 §9(OFF)가 오기.
   - DB엔지니어 5년차: "unload 시점 기본 OFF(§9), load 시점 기본 ON(§8)"이라는 비대칭 규칙일 가능성도 배제 못 함(그렇다면 비대칭 근거를 밝혀야).
   - → 다수는 오기로 보나, 소수가 "의도된 비대칭일 수 있다"며 확정을 유보.

4. **MySQL식 전 컬럼 폴백(FULL)을 되살릴 것인가**
   - 엔진 10·DB엔지니어 10·PM 여러: 배경에서 성능으로 배제했지만 "느려도 복제는 됨"이라는 선택지를 로드맵에 남기라 — **부분 복원** 제안.
   - 스펙 배경: 성능상 명시적 배제.
   - → 설계 결정 자체에 대한 재검토 요구(직접 충돌은 아니나 방향 이견).

## 2차 — 인접 영역 신규 리뷰 (1차 미포함분)

작성: 수석 아키텍트 종합 · 대상: `user_spec_extracted.md` (CUBRID HA 복제 키(RK) / REPLICATION 옵션 스펙)
기준선: `최종보고서.md`의 **1차 통합 이슈 40개**(치명 9 · 중요 10 · 보통 12 · 사소 6 + 소수 고유). 이 문서는 그 40개와 **겹치지 않는 것만** 신규로 인정한다.
근거: 20개 리포트(5직군 × 4연차)의 **2차 라운드**, 리뷰 총 **197건**.

> 용어는 1차 보고서와 동일하게 쓴다. **RK**(Replication Key, 복제 키) = 슬레이브에서 어떤 행을 갱신·삭제할지 식별하는 키(엔진이 PK 또는 NOT NULL UNIQUE 중 자동 선택). **RK 후보** = RK가 될 자격이 있는 PK/UK. **REPLICATION 옵션** = 테이블 단위 복제 대상(ON)/제외(OFF) 스위치. **applylogdb** = 슬레이브가 복제 로그를 실제로 반영하는 모듈.

## 1. 요약

### 1.1 2차에서 나온 양

- **신규 리뷰 총 197건** (20개 리포트, 리포트당 7~12건). 1차의 "20개 × 20건 = 400건"과 달리, 2차는 각 페르소나가 "1차·최종보고서가 다룬 지점을 빼고 새 실패 모드만" 골라 적었기 때문에 리포트당 개수가 줄었다. 이 자체가 정상 신호다 — 1차가 스펙의 정면(正面) 결함을 이미 대부분 덮었다는 뜻이다.
- **1차 40개와 실질 중복이라 걸러낸 것: 약 42건.** 예: "RK가 조용히 바뀌는데 조회할 수 없다"의 이력(history) 각도(1차 C-3), 플래그 전환 중 in-flight DML(1차 C-8), 한 문장 다중 절 원자성 재론(1차 C-7), 국제화 용어(1차 T-6의 확장), 예시 번호·표기 흠(1차 N-1~N-6), 다중 슬레이브·성능/락 재포장(1차 M-9/M-10). 이들은 페르소나 스스로 "조사 종료 선언"에서 제외했거나, 각도만 다르고 뿌리가 같아 신규로 세지 않았다.
- **나머지 ~155건이 30개의 신규 통합 이슈로 수렴**했다(아래 §2). 2차의 특징은 "**스펙이 정면에 쓴 문장의 결함**"(1차)이 아니라 "**스펙이 아예 침묵한 인접 기능과의 충돌**"이라는 점이다. `db_class` 예시(예시 9)에 값만 노출되고 본문이 한 마디도 하지 않은 필드들 — `tde_algorithm`(TDE 암호화), `partitioned`(파티션), `owner_name`(소유자 권한), `collation`, `is_reuse_oid_class` — 이 2차 신규 이슈의 주요 광맥이었다.

### 1.2 1차 판정(NEEDS_FIX)이 바뀌는가 — **아니오. 오히려 강화됨.**

2차는 릴리스 판정을 뒤집을 근거를 하나도 내놓지 않았다. 반대로 **1차가 컨셉 결함으로 지목한 뿌리(RK 비결정성·FK 불변식·복제 로그 정합성)가 스펙이 언급조차 안 한 기능들에서 재발한다**는 것을 보여, "문서만 교정해서는 못 고친다"는 결론을 더 굳혔다. 특히 다음 세 가지가 새로 드러났다.

1. **막으려던 배경 버그(복제 누락 + fail_count 증가)가 이 스펙이 새로 만든 경로로 재현된다.** REPLICATION=OFF 테이블의 DDL 적용 실패(2C-6), loaddb의 단계적 스키마 재현(2C-3), 트리거 기반 참조 무결성(엔진10-22) 모두 스펙의 방어망(§4·§5·§7) 바깥에서 같은 사고를 낸다.
2. **RK 유일성이라는 대전제가 스펙이 침묵한 기능에서 성립하지 않는다.** 파티션-로컬 UNIQUE(2C-1), 부분 NOT NULL 복합 UK(2C-4), 필터/함수 기반 UNIQUE 인덱스(2M-8)가 "RK 값으로 행을 하나로 특정한다"는 전제를 깨뜨린다.
3. **안전장치가 작동하는 시점이 너무 좁다.** §7 검사는 `cubrid hb start`에만 걸리고, 실제로 마스터가 바뀌는 failover·switchover·failback에는 재검증이 없다(2C-2).

**결론: 판정 유지 = 불가(NEEDS_FIX).** 1차 Top 10 + 아래 2차 신규 치명 이슈를 함께 반영해 개정 후 재검토해야 한다.

## 2. 신규 통합 이슈 목록 (1차 40개와 미중복)

### 2.1 치명 (Critical)

#### 2C-1. 파티션 테이블에서 파티션-로컬 UNIQUE가 RK로 뽑히면 행 유일 식별이 깨진다
**합의도: ~13** · 대상: §1, §4 (스펙에 "파티션" 단어 자체가 없음)

파티션 테이블의 UNIQUE 제약은 파티션 키를 포함하지 않으면 "파티션 하나 안에서만 유일"(local)할 수 있다. 즉 같은 값이 서로 다른 파티션에 하나씩 공존한다. RK는 "이 값으로 슬레이브에서 행을 하나로 특정한다"를 전제하는데, 이 전제가 성립하지 않는다. 엔진 개발자 리뷰들이 이를 정합성 파괴(치명)로, 나머지 직군은 "스코프 침묵"(중요)으로 지적했다. 1차는 파티션을 Phase 3 "스코프 명시" 권고로만 스쳤을 뿐, 이 유일성 파괴 메커니즘은 새로 나왔다.

```sql
CREATE TABLE sales (region_id INT, sale_id INT NOT NULL UNIQUE, amount INT)
PARTITION BY RANGE (region_id) (
    PARTITION p1 VALUES LESS THAN (100), PARTITION p2 VALUES LESS THAN (200));
-- PK 없음 → RK = sale_id(UK)
INSERT INTO sales VALUES (10, 555, 1000);   -- p1
INSERT INTO sales VALUES (150, 555, 2000);  -- p2 (파티션-로컬 유일이면 통과)
-- 슬레이브에 "sale_id=555 행 갱신" 로그가 오면 두 행이 걸려 대상을 특정 못 함
```

**예상 시나리오**
1. (전제) HA 두 노드(마스터·슬레이브)가 정상 복제 중이다. sales 테이블은 PK가 없어 NOT NULL UNIQUE인 sale_id가 복제 키로 선택되어 있다. 이 테이블은 region_id 범위로 두 파티션(p1, p2)으로 나뉘고, UNIQUE 제약은 파티션 키(region_id)를 포함하지 않아 파티션 하나 안에서만 유일하다.
2. (조작) 마스터에서 sale_id=555인 행을 서로 다른 파티션에 두 번 INSERT 한다(region_id=10 → p1, region_id=150 → p2). 파티션-로컬 유일성만 검사되므로 두 INSERT 모두 성공한다. 이후 그중 한 행을 UPDATE 한다.
3. (예상 결과) 마스터: 두 행이 정상 공존하고 UPDATE도 정상 수행된다. 슬레이브: 복제 로그에는 "sale_id=555인 행을 갱신하라"만 담기므로, applylogdb가 복제 키로 대상을 찾으면 두 행이 동시에 걸린다. 두 행 모두 갱신되어 마스터에 없는 변경이 슬레이브에 생기거나, 대상이 하나로 특정되지 않아 적용이 실패해 fail_count가 증가한다(둘 중 어느 동작인지는 스펙 미정의라 가정).
4. (사용자 증상) failover 후 슬레이브를 읽는 애플리케이션이 마스터와 다른 데이터를 보게 되거나, fail_count 누적으로 복제가 멈춰 슬레이브가 마스터를 따라가지 못한다. 원인이 "정상적으로 보이던 INSERT 두 건"이라 운영자가 즉시 알아채기 어렵다.

**권고**: "파티션 테이블에서는 파티션 키를 포함하거나 전역 유일성이 보장되는 PK/UK만 RK 후보"라고 §1에 명문화. 파티션 단위 REPLICATION 지정 가부, ADD/DROP PARTITION의 복제 처리도 함께 규정하거나 명시적 out-of-scope 선언.

#### 2C-2. Failover / switchover / failback가 §7 제약 검증을 우회한다
**합의도: ~6 (DBA·엔진·사용자 상위 연차)** · 대상: §7, §1(HA 모드 = `cubrid hb start` 정의)

§7 검사는 "HA 실행 시"(=`cubrid hb start`)에만 걸린다. 그런데 실제로 마스터가 바뀌는 가장 흔한 사건은 재기동이 아니라 **failover**(슬레이브가 마스터로 승격)다. 이는 `hb start`가 아니라 이미 떠 있는 프로세스의 역할 전환이므로 §7 검사가 재실행되지 않는다. 운영 중 어떤 경로로든(예: 1차 C-9의 NOT NULL 해제) RK를 잃은 테이블이 있으면, failover 직후 새 마스터가 검증 없이 그 상태로 쓰기를 받아 배경 버그가 즉시 재현된다. 장애로 복구된 구 마스터가 재합류하는 **failback** 시 x→y→z로 여러 번 바뀐 RK 이력을 순서대로 재생하는지도 미정의(엔진10-29).

```
정상 HA 운영 중 order_items가 RK 후보를 모두 잃음(§7은 시작 시점에만 검사)
→ 마스터 하드웨어 장애 → 슬레이브 승격(hb start 아님, §7 미적용)
→ 새 마스터가 RK 없는 상태로 쓰기 수신 → 복제 누락 + fail_count 재현
```
**권고**: §7 검증 대상을 "마스터 역할을 맡는 모든 시점(failover·switchover·failback 포함)"으로 확장. 승격 전 검증 실패 시 그 노드로의 승격 거부 또는 즉시 경고. failback catch-up 시 스키마(RK 전환) 로그를 중간 상태 건너뛰지 않고 순서대로 재생.

#### 2C-3. loaddb의 "스키마→데이터→인덱스" 단계적 파이프라인이 §4-1과 구조적으로 충돌 (검증 우회 뒷문)
**합의도: ~6 (엔진·응용)** · 대상: §8, §4-1

unloaddb/loaddb는 성능을 위해 (1) 제약 없는 빈 테이블 생성 → (2) 인덱스 없이 대량 적재 → (3) 이후 PK/UK·인덱스 추가 순으로 스키마를 재현한다. (1)단계는 정확히 "RK 후보가 하나도 없는 테이블"이다. §4-1("HA 모드에서 RK 없는 복제 테이블 생성 금지")을 그대로 적용하면 이 표준 복원 절차가 1단계에서 막혀 HA 운영 중 복원 자체가 불가능해진다. 반대로 loaddb가 SQL 파서를 거치지 않는 내부 경로라 §4-1 검증을 건너뛴다면, csql로는 못 만드는 "RK 없는 복제 테이블"을 loaddb로는 살아있는 HA에 심을 수 있는 뒷문이 된다. 어느 쪽이든 문서 교정이 아니라 유틸리티 구현을 바꿔야 하는 사안이다.

**예상 시나리오**
1. (전제) HA 운영 중인 데이터베이스를 unloaddb로 받아 두었다가 loaddb로 복원한다. loaddb는 성능을 위해 (1) 제약 없는 빈 테이블 생성 → (2) 인덱스 없이 대량 적재 → (3) PK/UK·인덱스 추가 순으로 스키마를 재현한다.
2. (조작) HA 모드에서 loaddb를 실행한다. 1단계에서 복제 대상(REPLICATION=ON) 테이블이 아직 복제 키 후보가 하나도 없는 상태로 만들어진다.
3. (예상 결과) 두 갈래가 가능하다(스펙 미정의라 가정). 갈래 A — loaddb가 §4-1의 "HA 모드에서 복제 키 없는 복제 테이블 생성 금지" 검증을 그대로 받으면, 1단계에서 막혀 복원 자체가 실패한다. 갈래 B — loaddb가 SQL 파서를 거치지 않는 내부 경로라 그 검증을 건너뛰면, csql로는 만들 수 없는 "복제 키 없는 복제 테이블"이 살아있는 HA에 그대로 심긴다.
4. (사용자 증상) 갈래 A라면 운영자는 HA를 내리지 않고서는 백업을 복원할 수 없다. 갈래 B라면 복원은 되지만 그 테이블은 복제 키가 없어, 이후 그 테이블의 DML이 슬레이브에 반영되지 못하고 복제 누락·fail_count 증가라는 배경 버그가 다시 나타난다.

**권고**: loaddb가 1단계 CREATE를 항상 REPLICATION=OFF로 내보내고 마지막에 원래 값으로 전환하도록 출력 형식을 바꾸거나, §4-1과 동일 검증 경로를 공유함을 §8에 명시. RK 후보가 없는 ON 테이블을 만났을 때의 처리(실패/경고/OFF 강등)도 규정.

#### 2C-4. 부분 NOT NULL 복합 UK가 RK로 선택되면 행 유일 식별이 불가능
**합의도: ~8** · 대상: §1 "Not Null Unique Key" 정의

스펙의 UK 예시는 모두 단일 컬럼이다. 복합 UNIQUE에서 일부 컬럼만 NOT NULL이면(SQL 관례상 NULL은 서로 다른 값 취급), 같은 값 조합의 행이 여러 개 공존할 수 있어 RK로 쓸 수 없다. "NOT NULL UNIQUE"가 "구성 컬럼 전부 NOT NULL"인지 "하나라도 NOT NULL"인지 스펙에 정의가 없다. 1차 M-1("복제키 후보" 용어 미정의)과는 다른 층위 — 여기는 **후보 자격 판정 기준의 정합성** 문제다.

```sql
CREATE TABLE t3 (x INT NOT NULL, y INT, UNIQUE (x, y));  -- y는 NULL 허용
INSERT INTO t3 VALUES (1, NULL);
INSERT INTO t3 VALUES (1, NULL);  -- 위반 아님 → (x=1,y=NULL) 행이 둘
-- 이 UK가 RK면 "x=1 AND y IS NULL" 조건이 두 행에 매치
```

**예상 시나리오**
1. (전제) 복제 대상 테이블 t3에 PK가 없고 (x, y) 복합 UNIQUE만 있다. x는 NOT NULL이지만 y는 NULL을 허용한다. 복제 키 후보 판정이 "구성 컬럼 전부 NOT NULL"인지 "하나라도 NOT NULL"인지 스펙에 없어, 이 복합 UK가 복제 키로 뽑혔다고 본다(스펙 미정의라 가정).
2. (조작) 마스터에서 (x=1, y=NULL) 행을 두 번 INSERT 한다. SQL 표준상 NULL은 서로 다른 값으로 취급되어 UNIQUE 위반이 아니므로 두 행 모두 들어간다. 이후 이 값 조합을 조건으로 하는 UPDATE 또는 DELETE를 수행한다.
3. (예상 결과) 마스터: 두 행이 공존하고 정상 동작한다. 슬레이브: applylogdb가 "x=1 AND y IS NULL"로 대상 행을 찾으면 두 행이 함께 걸려, 2C-1과 같은 오적용 또는 적용 실패(fail_count 증가)가 일어난다.
4. (사용자 증상) 마스터/슬레이브 데이터가 어긋나거나 복제가 멈춘다. 사용자는 표준 SQL 규칙대로 유효한 데이터를 넣었을 뿐이라, 스펙만 봐서는 이 값 조합이 위험하다는 것을 알 수 없다.

**권고**: "복합 UK가 RK 후보가 되려면 구성 컬럼 전부가 개별적으로 NOT NULL이어야 한다"를 §1에 명시, §4-2 후보 판정에서 부분 NOT NULL 복합 UK를 제외, 복합 UK 예시 최소 1개 추가.

#### 2C-5. RK 컬럼 값 자체를 바꾸는 순수 UPDATE의 old-key/new-key 로그 처리 미정의
**합의도: ~3 (엔진)** · 대상: 복제 로그 포맷(스펙에 절 없음)

1차 C-8은 RK를 바꾸는 **DDL**의 순서 문제였다. 여기는 DDL이 전혀 없다 — PK/UK 컬럼의 **값**을 평범한 UPDATE로 바꾸는 경우다. 복제 로그가 "변경 후 행 이미지"만 담으면, 슬레이브는 "어떤 행을 찾을지"의 근거(옛 키 값)를 잃는다.

```sql
UPDATE customers SET customer_id = 9001 WHERE customer_id = 5;  -- RK 값 5→9001
-- 슬레이브가 customer_id=9001 행을 찾으려 하면 그런 행은 없음 → 대상 없음/오매칭
```

**예상 시나리오**
1. (전제) 복제 대상 customers 테이블에서 customer_id가 복제 키다. 마스터와 슬레이브에 customer_id=5인 행이 동일하게 존재한다.
2. (조작) 마스터에서 `UPDATE customers SET customer_id = 9001 WHERE customer_id = 5`를 실행해, DDL 없이 복제 키 값 자체를 5에서 9001로 바꾼다.
3. (예상 결과) 마스터: 해당 행의 키가 9001로 정상 변경된다. 슬레이브: 복제 로그가 "변경 후 행 이미지"만 담아 갱신 후 값(9001)으로 대상을 찾으면, 슬레이브에는 아직 5만 있어 대상이 없다. 대상 없음이면 조용히 건너뛰어(무성 skip) 슬레이브에는 여전히 5가 남고, 잘못 매칭되면 엉뚱한 행을 건드린다(둘 중 어느 동작인지는 스펙 미정의라 가정). 어느 쪽이든 마스터=9001, 슬레이브=5로 갈라진다.
4. (사용자 증상) failover 후 슬레이브를 읽는 애플리케이션이 이미 9001로 바뀐 고객을 여전히 5로 보게 되어, 그 키로 연결된 주문·정산이 어긋난다. 조용한 skip이면 fail_count조차 오르지 않아 운영자가 불일치를 감지할 신호가 없다.

**권고**: 복제 로그에 "갱신 전 RK 값(search key)"과 "갱신 후 행 이미지"를 분리 기록. RK 컬럼이 SET 절에 포함되는 케이스를 테스트 케이스로 명시.

#### 2C-6. REPLICATION=OFF 테이블의 DDL 복제 실패가 배경 버그(fail_count)를 새 경로로 재현
**합의도: ~2 (엔진5, 응용/DBA 일부)** · 대상: §4(DDL은 항상 복제), §1(OFF 데이터 불일치 면책)

§1의 면책은 "데이터 불일치"에 대한 것이고, §4는 "DDL은 REPLICATION 여부와 무관하게 항상 복제·적용되어야 한다"고 한다. 그런데 OFF 테이블은 슬레이브 데이터가 마스터와 다른 것이 허용된 상태이므로, 그 어긋난 데이터 위에서 제약 추가 DDL을 실행하면 마스터에선 성공한 DDL이 슬레이브에선 실패한다 = applylogdb 실패, fail_count 증가, HA 정지. 이 스펙이 새로 만든 OFF 기능 자체가 원래 고치려던 버그의 새 발생 경로다.

```sql
-- customers: REPLICATION=OFF, 슬레이브는 OFF 전환 시점 스냅샷(country 중복 잔존)
ALTER TABLE customers ADD CONSTRAINT UNIQUE(country);  -- 마스터 성공(중복 없음)
-- §4대로 슬레이브 재생 → 슬레이브엔 country 중복 → UNIQUE 위반 실패 → fail_count↑
```
**권고**: OFF 테이블에 대한 DDL 적용 실패 시의 동작을 정의(그 테이블에 한해 DDL 실패를 격리/무시하는 모드 등)하거나, "OFF 테이블도 DDL 실패는 여전히 HA를 정지시킨다"는 위험을 명시하고 운영 가이드 제공.

#### 2C-7. TDE 암호화 테이블 × RK/복제 로그 상호작용 미정의 (정합성 + 보안)
**합의도: ~18 (전 직군)** · 대상: §2-3 예시 9의 `tde_algorithm` 필드, §1

`db_class`에 `tde_algorithm`이 이미 있는데도 본문은 TDE를 한 마디도 안 한다. 두 갈래 위험이 겹친다. **(정합성)** 마스터/슬레이브가 서로 다른 TDE 키를 쓰면 슬레이브가 RK 값으로 행을 찾지 못하거나 적용 실패(→ 또 fail_count). **(보안)** RK 값·복제 로그가 평문으로 실리면, 디스크는 암호화했는데 복제 로그 파일과 네트워크 전송 구간에서 평문이 새어 TDE 도입 취지가 무력화된다. 대부분 중요로 매겼으나 보안+정합성 이중 위험이라 치명으로 승격한다.

```sql
CREATE TABLE payment_cards (card_number CHAR(16) NOT NULL UNIQUE, holder VARCHAR(50))
  /* TDE 적용 */ REPLICATION=ON;   -- RK = card_number(암호화 대상)
-- 복제 로그에 card_number가 평문인가 암호문인가? 슬레이브 키가 다르면 매칭되는가?
```

**예상 시나리오**
1. (전제) 복제 대상 payment_cards 테이블이 TDE로 디스크 암호화되어 있고, NOT NULL UNIQUE인 card_number가 복제 키다. 스펙이 TDE를 다루지 않으므로 마스터·슬레이브의 TDE 키 공유 여부와 복제 로그의 암호화 여부는 미정의다(스펙 미정의라 가정).
2. (조작) 마스터에서 payment_cards에 행을 INSERT/UPDATE 하면 복제 로그가 생성되어 슬레이브로 전송·적용된다.
3. (예상 결과) 두 위험이 겹친다. 정합성 갈래 — 마스터와 슬레이브의 TDE 키가 다르면 슬레이브가 복제 키 값(card_number)으로 행을 찾지 못해 적용이 실패하고 fail_count가 증가한다. 보안 갈래 — 복제 로그가 논리(평문) 레벨로 만들어지면 card_number가 복제 로그 파일과 네트워크 전송 구간에 평문으로 남는다.
4. (사용자 증상) 정합성 갈래면 복제가 멈춰 슬레이브가 뒤처진다. 보안 갈래면 디스크는 암호화했는데 복제 경로에서 카드번호 평문이 새어, 규제 심사에서 TDE 도입 취지가 무력화됐다는 지적을 받는다.

**권고**: 복제 로그가 논리(평문) 레벨에서 생성됨을 명시하고 마스터/슬레이브 TDE 키 공유·로테이션 정책을 규정. 전송 구간 암호화(TLS 등) 강제 여부 명시. 불가하면 "TDE 테이블 복제는 이번 릴리스 검증 범위 밖"이라고 최소한 스코프 선언.

### 2.2 중요 (Major)

#### 2M-1. REPLICATION 변경 권한·감사(audit) 모델이 전무 — 2차 최다 합의
**합의도: ~18 (전 직군·전 연차)** · 대상: §2-2, 예시 9의 `owner_name`

`ALTER TABLE ... REPLICATION=OFF`를 누가 실행할 수 있는지 스펙에 한 줄도 없다. 일반 ALTER 권한(테이블 소유자)만으로 가능하다면, DBA가 아닌 애플리케이션 계정이 승인 없이 DR 보장 범위를 바꾸고 다른 테이블의 FK 무결성(1차 C-2)까지 흔들 수 있다. 부작용이 즉시 안 보이고(다음 failover까지) 변경 이력을 조회할 표준 수단도 없어, 규제 산업(금융·의료) 컴플라이언스 심사에서 바로 걸린다.
```sql
GRANT ALTER ON customers TO app_user;  -- 일반 개발 계정
-- app_user 세션: ALTER TABLE customers REPLICATION=OFF;  성공? 누가 언제 바꿨는지 추적?
```

**예상 시나리오**
1. (전제) DBA가 orders(복제 대상)와 그 FK 부모인 customers(복제 대상)로 HA를 구성했다. 애플리케이션 계정 app_user는 customers에 일반 ALTER 권한을 갖고 있다. REPLICATION 변경에 별도 권한이 필요하다는 규정이 스펙에 없으므로, 일반 ALTER 권한만으로 가능하다고 본다(스펙 미정의라 가정).
2. (조작) app_user가 승인 절차 없이 `ALTER TABLE customers REPLICATION=OFF`를 실행한다.
3. (예상 결과) 마스터: customers가 복제 제외로 바뀌어 이후 customers 데이터가 슬레이브로 가지 않는다. 슬레이브: customers는 전환 시점 스냅샷에서 갱신이 멈춘다. 변경 이력을 남기는 표준 수단이 없어 누가·언제 바꿨는지 카탈로그나 감사 로그에서 확인되지 않는다.
4. (사용자 증상) 부작용이 즉시 보이지 않다가 다음 failover 때 새 마스터의 customers에 최신 데이터가 없어 orders의 FK 참조가 깨진다. 원인을 추적하려 해도 변경 주체·시각을 알 수 없어, 금융·의료 같은 규제 산업의 컴플라이언스 심사에서 바로 걸린다.

**권고**: REPLICATION 변경을 일반 ALTER와 분리된 권한(DBA 또는 신규 `REPLICATION` 권한)으로 제한하거나 최소한 변경 이력(계정·시각·이전/이후 값)을 감사 로그·카탈로그에 기록.

#### 2M-2. REPLICATION=OFF의 로그 계층(마스터 생성 skip vs 슬레이브 필터) 미정의 → 성능·용량 오판
**합의도: ~5 (DBA·PM)** · 대상: §1, §4

OFF 차단이 (a) 마스터가 애초에 복제 로그를 안 만드는지, (b) 로그는 다 만들되 전송 전 필터인지, (c) 슬레이브 적용 단계에서 버리는지 스펙에 없다. 셋은 사용자에게 보이는 결과(슬레이브에 데이터 없음)는 같지만 네트워크 대역폭·슬레이브 디스크·복제 지연 지표가 100배까지 갈린다. "성능 때문에 MySQL식을 배제했다"는 설계 근거를 내세운 문서인 만큼 이 계층을 밝혀야 한다.
```
audit_log(OFF, 500GB/일) vs orders(ON, 5GB/일)
경로 A(마스터 필터): 복제 트래픽 ~5GB/일 / 경로 B(슬레이브 필터): ~505GB/일, 500GB 버려짐
```
**권고**: OFF 테이블 변경분이 트랜잭션 로그·복제 로그·적용 단계 중 어디서 제외되는지 §1/§4에 명시하고 각 경우의 성능·용량 영향을 표로 정리.

#### 2M-3. §7 검사 blast radius — 전체 vs 부분 기동, DB단위 vs 그룹, 검증 비용
**합의도: ~7 (DBA·엔진)** · 대상: §7

세 가지가 미정의다. (1) 위반 발견 시 클러스터 전체가 안 뜨는지, 위반 테이블만 제외하고 나머지는 뜨는지 — 전자면 테이블 1개가 SPOF, 후자면 "또 다른 조용한 복제 누락". (2) 한 서버의 여러 DB 중 하나만 위반해도 그룹 전체가 막히는지. (3) 수천~수만 테이블 카탈로그 전수 스캔이 위반이 없어도 failover 시간(RTO)에 얼마나 붙는지. 또한 §7 검사 시작~HA 완전 활성화 사이에 싱글 모드 규칙으로 RK를 없애는 레이스(엔진5-26), 노드별 독립 검사 시 마스터 통과·슬레이브 실패의 비대칭 기동(엔진5-27)도 여기 묶인다.
**권고**: §7의 실패 상태·적용 단위(단일 DB/그룹)·성능 특성을 명시. 검사를 배타 잠금 하에 원자적으로 수행하고 통과 즉시 HA 활성화. 노드 간 카탈로그 불일치 자체를 에러로 보고.

#### 2M-4. 물리 백업(backupdb/restoredb)·PITR와 REPLICATION 미정의
**합의도: ~6 (DBA·PM·응용)** · 대상: §8 (unloaddb/loaddb만 다룸)

실무 백업·DR은 논리 백업(§8이 다루는 unloaddb)보다 물리 백업(backupdb/restoredb)이 훨씬 흔한데 스펙이 침묵한다. PITR(시점 복구)은 옛 시점의 REPLICATION 카탈로그 상태를 되살려 현재 클러스터와 어긋날 수 있고(DBA3-21), 슬레이브에서 백업을 뜨면 OFF 테이블은 항상 빈 채로 백업된다(DBA3-22 → §2.4로). 구버전 물리 백업을 신버전에 복원할 때의 카탈로그 마이그레이션도 §8이 다루지 않는다.
**권고**: §8을 "논리 백업 / 물리 백업"으로 나눠 각각의 REPLICATION·RK 저장·복원·마이그레이션 규칙을 명시. PITR 복구 후 REPLICATION 전수 점검을 절차화.

#### 2M-5. 도구 생태계(표준 메타데이터·JDBC·ORM·스키마 diff)에 RK·REPLICATION 미노출 → 조용한 되돌림·드리프트
**합의도: ~6 (응용·PM)** · 대상: §2-3

조회 수단이 CUBRID 전용(`show create table`, `db_class`)뿐이라 표준 경로로는 안 보인다. 결과: (a) Liquibase/Flyway 스키마 diff가 REPLICATION 차이를 못 잡아 환경 드리프트가 사각지대(응용1-22). (b) ORM 자동 스키마 동기화(`hbm2ddl=update`)나 테이블 재생성 경로가 REPLICATION 옵션을 몰라 DBA가 건 OFF를 배포마다 조용히 ON으로 되돌림(응용10-27, 치명). (c) jOOQ/MyBatis Generator가 표준 `DatabaseMetaData`로는 RK를 알 수 없음(응용5-27). (d) 자동 롤백 생성기가 OFF→ON 비대칭(HA 중 금지)을 몰라 롤백 자체가 실패(응용10-29). 1차 C-3(사람이 조회 불가)과 달리 여기는 **도구가 자동으로 소비하는 경로**의 부재다.

**예상 시나리오**
1. (전제) DBA가 customers 테이블을 규제상 슬레이브로 내보내면 안 되어 `REPLICATION=OFF`로 설정해 두었다. 애플리케이션은 ORM(예: Hibernate)의 자동 스키마 동기화(hbm2ddl=update)나 테이블 재생성 경로로 배포되며, ORM은 REPLICATION 옵션의 존재를 알지 못한다.
2. (조작) 다음 배포에서 ORM이 customers를 재생성하거나 동기화하며, REPLICATION 옵션을 생략한 CREATE/ALTER를 낸다. 스펙상 옵션 생략은 기본값 ON이다.
3. (예상 결과) 마스터: customers가 다시 REPLICATION=ON이 된다. 슬레이브: customers 데이터가 다시 복제되기 시작한다. 표준 스키마 diff 도구(Liquibase/Flyway)나 JDBC 표준 메타데이터로는 REPLICATION 차이가 보이지 않아 이 되돌림이 감지되지 않는다.
4. (사용자 증상) DBA가 건 복제 제외 정책이 배포마다 조용히 풀려, 슬레이브로 내보내면 안 되는 데이터가 규제를 위반한 채 복제된다. 아무도 명시적으로 바꾸지 않았기에 원인 파악이 늦어진다.

**권고**: REPLICATION·RK를 표준 메타데이터 뷰/JDBC 확장에 노출. REPLICATION 걸린 테이블은 ORM 자동 동기화·자동 롤백 대상에서 제외하도록 가이드. `show create table` 출력 포맷 변경을 "인터페이스 변경"으로 릴리스 노트에 명시.

#### 2M-6. LIKE / CTAS / RENAME TABLE(그림자 스왑)에서 REPLICATION·RK 상속·승계 미정의 + §5 우회
**합의도: ~7 (사용자·응용·엔진)** · 대상: §2-1, §5

`CREATE TABLE ... LIKE`/`AS SELECT`로 만든 사본이 원본의 REPLICATION을 상속하는지, 옵션 생략으로 간주해 기본값 ON이 되는지 없다. CTAS는 제약이 안 따라와 "RK 없는 복제 대상"이 손쉽게 생긴다. 더 심각한 것은 **RENAME TABLE 기반 그림자 스왑**(무중단 스키마 변경의 표준 기법): OFF로 만든 그림자 테이블을 운영 이름으로 RENAME하면 REPLICATION=OFF가 그대로 승계되어 조용히 복제가 끊기거나(엔진10-25), RENAME이 §5 FK 검증을 재실행하지 않아 "복제 대상이 복제 제외를 참조"하는 1차 C-2 상황이 ALTER 없이 재현된다(엔진1-27).

**예상 시나리오**
1. (전제) 무중단 스키마 변경을 위해 운영 테이블 orders(복제 대상)를 그대로 두고, 새 구조의 그림자 테이블 orders_new를 만들어 데이터를 옮긴 뒤 이름만 바꿔치기하는 기법(그림자 스왑)을 쓴다. 그림자 테이블은 적재 중 복제 부하를 피하려 REPLICATION=OFF로 만들어 두는 일이 흔하다.
2. (조작) orders_new에 데이터를 다 채운 뒤 `RENAME`으로 orders_new를 운영 이름 orders로 바꾼다. RENAME이 §5·§7의 FK·REPLICATION 정합성 재검증을 다시 트리거하는지는 스펙에 없다(스펙 미정의라 가정).
3. (예상 결과) 마스터: 운영 이름 orders가 REPLICATION=OFF 상태를 그대로 승계해 복제가 조용히 끊긴다. 슬레이브: 이름은 orders지만 RENAME 이후의 신규 주문이 더 이상 도착하지 않는다. 재검증이 없으면 "복제 대상이 복제 제외를 참조"하는 FK 위반 상태도 검사 없이 성립한다.
4. (사용자 증상) 애플리케이션은 평소처럼 orders에 쓰지만 슬레이브에는 반영되지 않다가, failover 후 새 마스터에서 스왑 이후의 주문이 통째로 사라진 것을 발견한다.

**권고**: LIKE/CTAS/RENAME의 REPLICATION·RK 승계 규칙을 명문화. RENAME 시 §5·§7과 동일한 FK/REPLICATION 정합성 재검증을 트리거.

#### 2M-7. FK 참조 액션(ON DELETE/UPDATE CASCADE 등)의 복제 처리 미정의
**합의도: ~4 (응용·엔진)** · 대상: §5 (CASCADE/SET NULL 언급 없음)

부모 삭제·갱신이 CASCADE로 자식에 연쇄 DML을 일으킬 때, 복제 로그에 (a) 부모 변경 1건만 남고 슬레이브가 자신의 CASCADE로 재현하는지, (b) 마스터가 자식 변경까지 개별 행 로그로 펼쳐 보내는지 미정의. (a)면 슬레이브 제약이 어긋나 있을 때 불일치. 엔진 리뷰는 UK를 RK로 쓰는 테이블이 CASCADE FK의 부모일 때 "순서 보존 로직이 PK 전용으로만 존재"한다는 실제 코드 흔적까지 지적(엔진3-21).
**권고**: 참조 액션 연쇄 DML은 마스터에서 개별 행 로그로 펼쳐 전달하고 슬레이브는 재실행하지 않음을 §5에 명시. 순서 보존 로직을 "PK/UK 불문 현재 RK"로 일반화.

#### 2M-8. 온라인/비활성/필터/함수 기반 UNIQUE 인덱스가 RK 후보 판정을 흔든다
**합의도: ~3 (엔진·응용 상위)** · 대상: §1, §4-2

RK 후보를 "카탈로그에 UNIQUE가 있는가"로만 판정하면: 온라인 빌드 중(유일성 검증 미완)인 UK를 근거로 진짜 RK를 지우는 DDL이 통과했다가 빌드가 실패하면 RK 0개가 됨(엔진3-27); soft-delete용 필터드 부분 UNIQUE(`WHERE deleted_at IS NULL`)는 삭제된 행끼리 값 중복 가능한데 표면상 "NOT NULL UNIQUE" 조건을 충족(응용10-22); 함수 기반 UNIQUE(`LOWER(email)`)는 로그에 원본값/계산값 중 무엇을 실을지 미정의(엔진1-22).
**권고**: RK 후보를 "빌드 완료·검증 끝난, 필터 없는, 실제 저장 컬럼 값 기반 완전 UNIQUE"로 한정. 온라인 빌드 중 UK를 근거로 한 RK 제거 DDL은 대기/거부.

#### 2M-9. 여러 문장 DDL을 한 트랜잭션으로 묶었을 때 부분 실패·롤백 미정의
**합의도: ~3 (응용)** · 대상: §2, §4-2

1차 C-7은 "한 문장 안 다중 절"이었다. 여기는 마이그레이션 파일이 별도 문장 여러 개를 묶고(또는 JDBC `setAutoCommit(false)`) 실행하다 중간 문장이 RK 위반으로 실패하는 경우다. DDL이 암묵적 커밋이면 앞 문장은 확정되어 롤백해도 안 되돌아가고, 도구가 기록한 상태(실패)와 실제 DB(일부 반영)가 어긋나 마이그레이션 이력이 꼬인다. 사용자 관점에선 단일 ALTER인데 엔진 내부가 인덱스 재생성으로 다단계 처리하며 RK 0개 구간을 거치는 경우(엔진5-29)도 같은 뿌리.
**권고**: DDL의 커밋 모델(암묵 커밋/트랜잭션 포함 여부)을 명시. "RK 후보 판정은 문장 실행 전/후 최종 상태 기준"이라는 원칙으로 명시적 다중 절·암묵 다단계·다중 문장을 하나로 커버.

#### 2M-10. 멀티프로세스 카탈로그 캐시 전파 지연 → 옛 RK로 로그 기록
**합의도: ~1 (엔진10)** · 대상: §4-2, CUBRID 멀티프로세스 구조

RK 변경 ALTER가 커밋된 뒤에도, 커넥션 풀에 오래 유지된 세션이 자신의 로컬 스키마 캐시(옛 RK)로 DML을 실행하면 복제 로그가 비적용된 RK 기준으로 기록될 수 있다. ALTER 자체의 정확성과 무관한 "캐시 무효화 전파" 계열 버그.
**권고**: RK 변경 DDL 커밋 시 전 활성 세션 카탈로그 캐시 무효화 브로드캐스트를 수반함을 명시, 완료 전 해당 테이블 DML 지연 여부 규정.

#### 2M-11. collation 차이·변경이 RK 유일성·행 매칭을 흔든다 (이견 있음)
**합의도: ~5, 단 상당수 페르소나가 "무영향"으로 명시 제외** · 대상: §1, 예시 8 `COLLATE`

대소문자 무시 collation에서 `'ABC'`와 `'abc'`는 같은 값 → UK가 이 둘을 충돌로 볼 수 있고, RK 컬럼의 COLLATE를 사후 변경하면 기존 데이터가 새 규칙으로는 중복이 되어 유일성 전제가 깨진다(응용3-26, 엔진5-24, 엔진10-23). 마스터/슬레이브가 다른 collation으로 초기화됐을 때 applylogdb의 행 매칭이 어긋날 수 있다는 지적(사용자10-21)도 있다. **반면 DBA·사용자5·엔진3 등 다수는 "UNIQUE 제약 자체가 그 collation으로 유일성을 강제하고 DDL(스키마·collation)이 항상 복제되므로 실질 파손 경로가 없다"며 명시 제외**했다. → 이견이 살아 있는 항목. 최소한 "RK 컬럼 COLLATE 변경 시 유일성 재검증"과 "applylogdb 매칭이 컬럼 collation을 따름"을 못박아 논쟁을 종결할 것.

#### 2M-12. ADD PRIMARY KEY 한 줄이 무경고로 RK를 UK→PK로 재할당
**합의도: ~3 (사용자·엔진)** · 대상: §1(PK 우선), §4-2 예시 14

UK가 RK인 테이블에 PK를 추가하면(예시 14: OK) §1의 "PK 우선" 규칙에 의해 RK가 그 즉시 새 PK로 조용히 넘어간다. "사용자는 RK를 직접 수정할 수 없다"는 §4-2 원칙이 무색해지고, 사용자는 "PK 하나 추가"만 의도했는데 복제 식별 기준이 바뀐다. 로그 볼륨(단일→복합)도 변하고 email 기준 외부 연동이 조용히 깨진다. 1차 C-1/C-3과 인접하나 "무경고 부작용"이라는 각도가 새롭다.
**권고**: PK 추가로 RK가 대체되면 무경고 OK 대신 "RK가 X에서 Y로 변경됨" NOTICE/WARNING을 반환하도록 §4-2에 명시.

#### 2M-13. 릴리스 거버넌스 메타데이터 부재 (버전·에디션·성숙도·백포트·킬스위치·다운그레이드)
**합의도: ~9 (PM 집중 + 사용자·응용 일부)** · 대상: 문서 전체

적용 최소 버전·에디션(오픈소스/상용) 미표기(PM1-23, 사용자1-29, 응용3-30 버전 스큐), 성숙도 등급(GA/Beta) 미정(PM3-29), 배경 버그의 하위 버전 백포트 정책 부재(PM10-26), 문제 발생 시 검증을 한시 완화할 킬스위치·다운그레이드 경로 부재(PM10-27, PM3-24)가 한 다발로 묶인다. 1차 C-6(마이그레이션 경로)이 "업그레이드 절차"였다면, 여기는 "이 기능을 언제·누구에게·어떤 형태로 내보내고, 사고 시 어떻게 물러나는가"라는 릴리스 전략 메타데이터다.
**권고**: 문서 서두에 적용 버전/에디션/타깃 릴리스/성숙도 등급을 명시. 카탈로그 스키마 변경과 다운그레이드 호환성, RK 검증을 한시 완화하는 시스템 파라미터(킬스위치)를 최소 한 릴리스 제공 검토.

#### 2M-14. "RK 추가"의 실제 비용 — 중복 데이터 정리·대용량 인덱스 락·클라이언트 타임아웃
**합의도: ~4 (사용자·DBA·응용)** · 대상: §3, §7, §9

스펙은 "RK 없으면 ALTER로 추가하면 된다"고 한 줄로 넘긴다. 그러나 PK 없이 오래 운영된 테이블엔 중복값이 쌓여 있어 UNIQUE 추가가 실패하며, 이를 정리하는 것은 비즈니스 로직 판단이 필요한 별도 프로젝트다(사용자3-21). 새 UK를 DEFAULT 상수로 추가하면 두 번째 행부터 중복 위반(사용자3-22). 수천만 건 테이블의 인덱스 생성은 장시간 락 → 다운타임 산정 실패(DBA1-28)와 JDBC socketTimeout 초과 → 재시도가 락 경합을 부름(응용10-28).
**권고**: §7/§9에 "RK 추가는 데이터 정리 선행이 필요할 수 있고 테이블 크기에 비례하는 무거운 DDL"임을 경고. 사전 점검 시 위반 테이블의 행 수 규모를 함께 제공, 온라인(무중단) 인덱스 생성 지원 여부 명시.

### 2.3 보통·사소 (Minor/Trivial) — 신규

- **2m-1. 클래스 상속(UNDER)과 REPLICATION/RK 상속 규칙 부재** (사용자10-28, 엔진5-25). 부모 OFF·자식 ON 시 반쪽 상태. CUBRID 고유 기능이라 참고 사례 없음. → 상속·독립 규칙 명시 또는 out-of-scope 선언.
- **2m-2. 기존 HA 설정파일 메커니즘과의 관계 / 레거시 우회 이중적용** (PM10-25, PM3-22). `cubrid_ha.conf`류의 기존 복제 제어와 새 SQL 옵션의 우선순위 불명. 과거 PK 없는 테이블용 트리거/섀도 우회가 새 네이티브 복제와 겹쳐 이중 반영. → 관계·마이그레이션 가이드 명시.
- **2m-3. 다중 스키마 FK 검증·소유자 교차 영향** (PM5-25, PM10-21). §5 예시가 전부 단일 소유자라, 동명이표(異表) 스키마 한정 검증이 검증되지 않고, alice가 자기 테이블을 OFF로 바꿔 bob의 FK를 깨는 교차 영향의 권한 경계가 없음.
- **2m-4. TRUNCATE 등 DDL/DML 경계 SQL의 분류 미정의** (사용자5-21). TRUNCATE가 "DDL(항상 복제)"인지 "데이터(REPLICATION 따름)"인지 불명.
- **2m-5. 정합성 점검 오탐 + 슬레이브 백업 시 OFF 테이블 빈값** (PM1-25, DBA3-22). 기존 행수/체크섬 점검 스크립트가 OFF 테이블을 "불일치"로 오탐 → 알람 피로. 슬레이브에서 백업 시 OFF 테이블은 구조적으로 항상 빈 백업.
- **2m-6. VIEW/시스템 클래스의 db_class.replication 값 처리** (엔진1-29·30, 사용자5-30). VIEW·시스템 클래스도 db_class에 있는데 replication 컬럼 값과 §7 순회 대상 포함 여부가 불명. VIEW에 REPLICATION 옵션을 시도하면? → 검사 대상을 `is_system_class='NO'` 사용자 테이블로 한정, VIEW는 NULL/제외 명시.
- **2m-7. DB/세션 레벨 REPLICATION 기본값 부재** (사용자1-32, 응용10-30). 스키마 전체를 OFF로 두려 해도 테이블마다 명시해야 하고 하나 빠뜨리면 조용히 ON.
- **2m-8. 카탈로그 컬럼 추가 하위호환** (PM1-28, 응용3-29, 응용10-32). `db_class`에 `replication` 신규 컬럼이 어느 위치에 추가되는지 불명 → `SELECT *` 위치기반 파싱 레거시 스크립트·구버전 드라이버가 깨질 수 있음. → "신규 컬럼은 항상 끝에 추가" 원칙 명시.
- **2m-9. 국제화 영문 용어 매핑** (PM1-24, PM3-31, PM5-29, 사용자3-29, 사용자10-29). "복제 대상/제외 테이블", "복제키 후보"의 공식 영문 역어 미확정 → 영문 매뉴얼 용어 분열. 1차 T-6(한국어 내부 통일)의 번역 단계 확장. "REPLICATION" 옵션명이 HA 복제 기능 전체와 이름이 겹쳐 진단·검색 혼란(사용자10-29)도 포함.
- **2m-10. 문서 구조 결함** (PM1-21 예시 번호 누락, 사용자1-27·28 DROP CONSTRAINT PRIMARY KEY 표기 모호·BNF 표기 설명 부재, 응용1-30 §1/§8/§9에 예시 전무, 엔진5-31 §3/§7 시점 표현 불일치). 문서를 QA·매뉴얼로 옮길 때 색인·검증을 막는 구조적 흠.

## 3. 1차 이슈의 보강 (새 각도·예제만 간단히)

2차가 신규는 아니지만 1차 이슈에 새 예제/각도를 더한 것:

- **1차 C-1(RK 비결정성) 보강**: unload/load 왕복만으로도(ALTER 없이) RK가 재계산되어 원본과 달라질 수 있음 — 백업/복원 무결성 각도(엔진10-24). RK 자동선택 규칙이 unload 스키마 파일의 제약 나열 순서에 의존하는데 그 순서 보장이 없음.
- **1차 C-2(FK 사후 OFF 미차단) 보강**: 같은 결과를 **RENAME TABLE**(2M-6)과 **트리거 기반 참조 무결성**(엔진10-22)으로도 도달 — §5가 선언적 FOREIGN KEY만 검사하므로 트리거로 구현한 참조는 방어망 밖. 규제(PII 국외반출 제한)로 부모를 OFF로 둬야 하는 요구와 §5 강제가 정면 충돌(PM3-27).
- **1차 C-3(RK 조회 불가) 보강**: "현재 값"뿐 아니라 "변경 이력(언제·무엇에서 무엇으로)"도 없음(사용자1-30). 표준 JDBC/ORM 경로로는 애초에 조회 불가(2M-5).
- **1차 C-4(§7 파일 리스트) 보강**: 실패 후 DB가 어떤 상태로 남는지(DBA1-23), 신규 제약 위반이 클라이언트 화면 밖 서버 에러 로그에도 남는지(DBA10-28), 위반 유형별(RK 없음 vs FK) 해결 절차 구분(사용자5-29)이 없음.
- **1차 C-7(복합 ALTER 원자성) 보강**: 두 개의 독립 트랜잭션이 각자 "다른 후보 있음"으로 통과하지만 합쳐지면 RK 0개가 되는 TOCTOU 경쟁(엔진3-23), 단일 ALTER의 암묵적 다단계 내부 구현이 RK 0개 구간을 거침(엔진5-29).
- **1차 M-5(OFF↔ON 재동기화) 보강**: RK 위반 하나를 고치려 HA 전체를 내려야 하는지, 문제 테이블만 OFF로 임시 격리 가능한지 §7이 대안을 안내하지 않음(DBA1-21).

## 4. 조사 소진 판정

### 4.1 페르소나별 exhausted 선언 현황

20개 리포트 **전부**가 명시적 "조사 종료 선언"을 달았고, 하나도 30건을 채우지 않았다(7~12건). 공통 논리는 동일했다: **(1)** 1차·최종보고서가 스펙 정면을 촘촘히 덮어 남은 것은 인접 기능과의 충돌뿐이다, **(2)** 그중 근거를 코드/문면으로 댈 수 있는 것만 남기고 추측성은 배제했다, **(3)** 개수 채우기용 재포장은 지시가 금지했으므로 하지 않았다.

- 명시적으로 "추가 여지 없음/소진"을 선언: PM 4개, DBA 4개, 사용자 4개, 응용 4개, 엔진 1·5·10년차.
- "코드를 열어봐야 확정되는 영역이 남아있다"고 조건부로 남긴 것: 엔진 3년차(병렬 applylogdb 결합), 엔진10(카탈로그 캐시·TDE를 소스로 검증), DBA1(엔진 내부 락 순서). 이들은 "스펙 문서 리뷰의 범위를 벗어난다"고 스스로 선을 그었다.
- 다수 페르소나가 **의도적으로 제외**한 것이 겹친다: 트리거 간접 DML, SERIAL/AUTO_INCREMENT failover 동기화, REUSE_OID, 멀티 슬레이브 차등 복제, 에러 코드 체계, 성능/락 — 모두 1차 최종보고서(엔진 고유 지적·M-6·M-9·M-10)에 이미 실려 재탕이 되기 때문. collation은 다수가 "무영향"으로 제외했으나 소수가 남겨 2M-11의 이견으로 남았다.

### 4.2 "이 스펙에서 더 짜낼 리뷰가 있는가" — 나의 판단

**문서(스펙 텍스트)만을 대상으로 하는 리뷰는 사실상 소진됐다.** 근거: (1) 2차 197건이 1차 40개와 겹치지 않는 신규를 30개로 수렴시켰는데, 그 30개조차 대부분 "스펙이 침묵한 인접 기능"이라는 **단일 뿌리의 변주**다(권한·TDE·파티션·collation·백업도구·상속·RENAME·loaddb — 전부 "본문에 없다"). (2) 서로 다른 5개 직군이 독립적으로 같은 상위 3개(권한 ~18, TDE ~18, 파티션 ~13)에 수렴한 것은 탐색 공간이 좁아졌다는 신호다. (3) 남은 미탐색은 전부 페르소나들이 "스펙 문서로는 확인 불가, CUBRID 소스를 열어야 한다"고 지목한 구현 검증 영역이다.

**따라서 다음 단계는 3차 리뷰가 아니라 두 갈래다.** (a) 스펙 저자에게 미정의 항목(§8/§9 기본값, RK 확정 알고리즘, 파티션·TDE·권한 스코프)을 확정받아 문서를 개정하고, (b) 개정된 스펙과 실제 CUBRID 카탈로그/복제/loaddb **코드를 대조**하는 코드 분석 라운드로 넘어가는 것. 같은 스펙 텍스트에 리뷰어를 더 투입하는 것은 한계효용이 급감한다.
