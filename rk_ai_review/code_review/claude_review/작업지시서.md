## 4. 리뷰 규칙

1. 페르소나당 문제점 **최대 50개**. **더 이상 찾을 수 없으면 그 시점에서 "추가 문제점 없음"을
   판단 근거와 함께 명시하고 종료해도 된다.** 개수를 채우기 위한 억지 지적 금지.
2. **키워드 검색만으로 분석 금지.** clangd LSP(정의 점프·참조 추적·콜체인)로 **로직 자체를 따라가며** 분석한다.
   (worktree에 compile DB 준비됨. LSP 실패 시에만 grep 폴백)
3. 각 문제점: [심각도] 제목 → 위치(file:line) → 로직 설명(코드가 실제로 뭘 하는지) → 문제 시나리오 → 제안.
4. **PR 히스토리(§6, `pr_히스토리.md`)를 반드시 참조**해 리뷰에 반영한다 — 왜 이렇게 구현됐는지,
   과거 리뷰에서 오간 결정(암묵지)을 알고 지적해야 이미 논의된 사안의 재탕을 피하고 회귀를 잡는다.
5. 스펙 필터링에서 승격된 확정 18건(`spec_review/claude_review/필터링_결과표.md` §3)은 알려진
   출발점이다 — 재확인은 좋으나 그 목록의 복창만으로 50개를 채우지 마라.

## 5. develop 대비 걸러내기 (2단계)

모든 페르소나의 문제점 수집이 끝나면, 병합·중복 제거 후 **각 문제점을 develop 코드와 비교**해
한 차례 걸러낸다:
- **신규**: 이 기능 diff가 만든 문제 (코드 리뷰 지적으로 유효)
- **기존**: develop에도 동일하게 존재하던 문제 (이 기능 책임 아님 — 별도 표기, 참고용 보존)
- 원문은 지우지 않고 판정을 표기한다 (스펙 필터링과 동일 원칙).
