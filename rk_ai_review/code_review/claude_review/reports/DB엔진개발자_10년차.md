# RK/REPLICATION 기능 코드 리뷰 — DB엔진 개발자 10년차 관점

> **2차 재리뷰(기준 734f4959d)** — fork를 CUBRID upstream과 동기화(#7678 SBR/checksumdb,
> #7697 인터럽트 수정 흡수)한 뒤의 재검증본입니다. 1차 리포트의 각 문제를 새 HEAD에서
> 유지/해소/폐기로 분류하고(문서 끝 재검증 요약), 동기화 델타와 전체 diff에서 신규 문제를
> 추가 발굴했습니다. 유지 문제는 1차 번호를 그대로 두고 위치(file:line)만 갱신했습니다.

## 페르소나 소개

저는 스토리지·트랜잭션·복제 엔진을 10년 다뤄 온 DBMS 엔진 개발자입니다. 리뷰할 때 보는 것은
"이 코드가 문법적으로 맞느냐"가 아니라 **"어떤 실행 순서·어떤 입력에서 락이 꼬이거나, 자원이 새거나,
에러가 조용히 삼켜지거나, 마스터와 슬레이브가 서로 다른 판단을 내리느냐"** 입니다.
특히 복제(replication)는 "틀려도 아무도 즉시 모른다"는 성질 때문에, 위반이 무성(silent)으로 지나가는
경로를 최우선으로 봅니다.

## 총평

이 기능(테이블별 REPLICATION 옵션 + RK 제약)은 파서·카탈로그·DDL·복제 로그·유틸리티를 두루 건드리는
넓은 변경입니다. 파서/카탈로그/유틸 골격은 대체로 기존 관례(ENCRYPT·COMMENT 옵션)를 잘 따라갔습니다.

이번 동기화로 두 축이 정리됐습니다. 인터럽트를 삼키던 복제-클래스 판정 함수는 #7697에서 int 반환 +
out-parameter 구조로 근본 수정되어 흡수됐고(INSERT/DELETE 경로), checksumdb의 행 기반 복제 억제/재개
반환값 처리도 #7678에서 리뷰 지적대로 보완됐습니다. 그 결과 1차에서 짚었던 치명 결함 한 건과 사소
결함 한 건은 해소됐습니다(재검증 요약 참조).

그러나 **복제의 정확성을 좌우하는 핵심 결함 한 건이 여전히 남아 있습니다.** RK "후보 판정"이 마스터
측(생성 게이트)과 서버 측(복제 로그 생성)에서 서로 다른 규칙을 씁니다. 마스터는 "구성 컬럼 중 하나라도
NOT NULL이면 RK"로 보고 CREATE를 통과시키는데, 실제 복제 로그를 만드는 서버 측은 "구성 컬럼이 전부
NOT NULL이어야 RK"로 봅니다. 그 사이에 낀 테이블은 **생성은 되지만 복제 로그가 아예 안 생기는** 무성
데이터 유실 구간이 됩니다.

나머지는 멀티-clause ALTER의 재검사 게이트 누락, 유틸리티 NULL 역참조, 예약어화 회귀, 카탈로그/enum
중간 삽입 등입니다. 아래에서 콜체인과 함께 하나씩 풉니다.

분석은 clangd LSP(정의 점프·참조 추적)로 각 함수의 호출자/피호출자를 확인하고, 지적 대상은 모두
본문을 읽어 검증했습니다.

## 문제 1

**[심각도: 치명] RK 후보 판정 규칙이 마스터(생성 검사)와 서버(복제 로그 생성)에서 서로 다르다 — 통과했는데 복제가 안 되는 무성 유실**

**위치**
- 마스터 측: `src/object/class_object.c:95-98` (`IS_HA_REPLICATION_KEY_CONSTRAINT` 매크로) → `src/object/schema_manager.c:16114-16130` (`sm_has_non_null_attribute`)
- 서버 측: `src/base/object_representation_sr.c:4694-4722` (`or_is_replication_candidate_key`)

**로직 설명 (LSP로 확인한 콜체인)**
- 마스터 측 RK 존재 검사 `IS_HA_REPLICATION_KEY_CONSTRAINT(c)`는 제약이 PK이거나
  `SM_IS_CONSTRAINT_UNIQUE_FAMILY(type) && sm_has_non_null_attribute(c->attributes)`이면 RK로 인정합니다
  (class_object.c:95-98). 그런데 `sm_has_non_null_attribute()`는 주석 그대로 "**적어도 하나(at least one)**"의
  컬럼이 NOT NULL이면 1을 돌려줍니다(schema_manager.c:16121-16127, 첫 NOT NULL 발견 즉시 `return 1`).
  이 매크로는 `classobj_has_class_repl_key_constraint()`(class_object.c:2285)와
  `classobj_find_cons_replication_key()`(:3985)에서 쓰이고, 이들은 다시
  - `check_ha_repl_constraint()` → `do_create_entity()`/`do_alter()`의 **CREATE/ALTER 통과 게이트**
  - `rkcheck` 유틸리티
  - `truncate_need_repl_log()`(execute_statement.c:376)
  에서 호출됩니다.
- 반면 실제 복제 로그를 만들 때 어떤 인덱스를 복제 키로 쓸지 고르는 서버 측
  `or_is_replication_candidate_key()`는 UNIQUE일 때 **모든 구성 컬럼이 NOT NULL이어야만**
  (object_representation_sr.c:4712-4719, `!attr->is_notnull`이면 즉시 false) RK로 인정합니다. 이 함수는
  INSERT/DELETE 경로 `locator_add_or_remove_index_internal()`(locator_sr.c:8041), UPDATE 경로
  `locator_update_index()`, 슬레이브 준비 경로가 쓰는 `btree_get_rkey_btid()`(btree.c:8294)에서 복제 키
  선택 기준으로 쓰입니다.

**문제 시나리오**
`CREATE TABLE t (x INT NOT NULL, y INT, UNIQUE(x, y)) REPLICATION=ON;`을 HA 모드에서 실행하면:
1. 마스터 게이트는 `sm_has_non_null_attribute({x,y})` → x가 NOT NULL이므로 1 → "RK 있음"으로
   판정하여 **CREATE가 성공**합니다.
2. 그런데 실제 DML이 들어오면 `or_is_replication_candidate_key()`는 이 UNIQUE(x,y)를 y가 NULL 허용이라
   RK로 인정하지 않습니다. 테이블에 다른 PK/완전-NOT-NULL UNIQUE가 없으면 `btree_get_rkey_btid`는
   NULL btid를 돌려주고, 복제 로그 생성 조건이 어떤 인덱스에서도 참이 되지 않아 **복제 로그가 한 건도
   안 생깁니다.**
3. 결과적으로 마스터에는 데이터가 쌓이는데 슬레이브에는 아무것도 안 넘어가는 무성 유실이 됩니다.
   `rkcheck`도 같은 관대한 규칙을 쓰므로 이 위반을 사전에 못 잡습니다.

**제안**
RK 후보 판정을 **단일 함수 하나**로 통일해야 합니다. 마스터 게이트가 서버보다 관대하면
"통과했는데 복제 안 됨"이, 반대면 "쓸 수 있는데 생성 거부"가 됩니다. 스펙 의도가 "부분 NOT NULL UK는
RK 자격 없음"(유일 식별 불가)이라면 `sm_has_non_null_attribute`를 "구성 컬럼 전부 NOT NULL" 검사로
바꾸고, 그 로직을 `or_is_replication_candidate_key`와 공유하십시오. (스펙 리뷰 확정 2C-4의 코드 근거이며,
여기서는 두 규칙의 **불일치**가 핵심입니다.)

## 문제 3

**[심각도: 중요] 멀티-clause ALTER의 RK 재검사 게이트가 "첫 절 코드"만 본다 — 뒤쪽 절의 RK 제거를 놓친다**

**위치** `src/query/execute_schema.c:2051`

**로직 설명 (LSP로 확인)**
`do_alter()`는 `for (crt_clause = alter; ...; crt_clause = crt_clause->next)`로 각 절을 처리하며,
각 절 코드는 루프 안에서 `alter_code = crt_clause->info.alter.code`로 뽑습니다(1854). 그런데 재검사 필요
여부를 세팅하는 줄은:
```c
if (!need_check_repl_constraint && IS_REPL_CONSTRAINT_RELATED_ALTER (alter->info.alter.code))
```
로, 루프 변수 `crt_clause`가 아니라 **리스트 머리 `alter`(=첫 번째 절)의 코드**를 매 반복마다
똑같이 검사합니다. 즉 루프를 돌며 누적한다는 코드의 의도와 달리, 실제로는 첫 절 코드만 반영됩니다.

**문제 시나리오**
`ALTER TABLE t MODIFY c1 VARCHAR(10), DROP CONSTRAINT uk_rk;`처럼 **첫 절이 게이트 목록에 없고
(PT_CHANGE_ATTR) 뒤쪽 절이 RK를 제거**(PT_DROP_CONSTRAINT)하는 경우, `alter->info.alter.code`는
PT_CHANGE_ATTR이라 `need_check_repl_constraint`가 끝까지 false로 남습니다. 결과적으로 RK가 사라진
복제 테이블이 만들어져도 HA 제약 검사가 실행되지 않습니다. 반대로 첫 절만 목록에 있으면 뒤 절과
무관하게 검사가 돌아, 검사 여부가 절의 **작성 순서**에 좌우되는 비결정적 동작이 됩니다.

**제안** `alter->info.alter.code`를 `crt_clause->info.alter.code`(또는 이미 뽑아 둔 `alter_code`)로
바꾸십시오.

## 문제 4

**[심각도: 중요] RK 재검사 게이트 매크로가 MODIFY/DROP INDEX/RENAME 경로를 누락 — RK가 조용히 사라진다**

**위치** `src/query/execute_schema.c:109-114` (`IS_REPL_CONSTRAINT_RELATED_ALTER`)

**로직 설명**
이 매크로는 `PT_ADD_ATTR_MTHD`, `PT_DROP_ATTR_MTHD`, `PT_DROP_CONSTRAINT`, `PT_DROP_PRIMARY_CLAUSE`
네 가지만 "복제 제약 재검사가 필요한 ALTER"로 봅니다. 그런데 RK 자격을 잃게 만드는 다른 경로가 빠져 있습니다.
- `PT_CHANGE_ATTR`(MODIFY/CHANGE COLUMN): NOT NULL을 떼거나 타입을 바꿔 NOT NULL UNIQUE의 RK 자격을
  없앨 수 있음 → 재검사 안 됨.
- `PT_DROP_INDEX_CLAUSE`: NOT NULL 컬럼의 UNIQUE **인덱스**(제약이 아닌)를 RK로 쓰던 경우, 이를
  `DROP INDEX`로 제거하면 RK가 사라지는데 게이트에 없음. `or_is_replication_candidate_key`는
  `BTREE_UNIQUE` 인덱스를 RK 후보로 인정하므로 이 경로는 실재합니다.
- `PT_RENAME_ENTITY`: OFF 테이블을 운영 이름 자리로 밀어 넣는 그림자 스왑(2M-6) — 재검사 없음.

**문제 시나리오**
`ALTER TABLE t MODIFY x INT;`(x가 NOT NULL UNIQUE RK의 컬럼) → NOT NULL이 풀려 RK 자격 상실 →
게이트 미포함이라 검사 없이 통과 → 이후 이 테이블의 DML은 RK를 못 찾아 복제 로그가 안 생김
(문제 1과 결합 시 무성 유실). HA 기동 시 rkcheck가 마지막 방어선이지만, ALTER 시점엔 아무 경고가 없습니다.

**제안** 최소한 `PT_CHANGE_ATTR`, `PT_DROP_INDEX_CLAUSE`를 게이트에 추가하고, RENAME도 재검증 대상에
넣을지 결정하십시오. (스펙 확정 C-9·2M-6의 코드 근거)

## 문제 5

**[심각도: 중요] rkcheck: 위반 목록 파일 열기 실패 시 NULL FILE*에 fprintf — 크래시**

**위치** `src/executables/util_cs.c` — `open_violation_list_file()`(2856-2863), 사용부 `rkcheck()`(3320 열기, 3332 이후 사용)

**로직 설명**
`rkcheck()`는 `fp = open_violation_list_file(...)`로 `.list` 파일을 엽니다(3320). 이 함수는 내부적으로
`fopen(file_path, "w")` 결과를 그대로 돌려줍니다(NULL 가능, 2863). 그런데 반환값 `fp`를 **NULL 검사
없이** 곧바로 `PRINT_SECTION_TITLE(fp, ...)`(3332), `check_repl_constraint_violations(classes, fp, ...)`(3333),
`PRINT_MESSAGE(fp, ...)` 등에 넘깁니다. 이 매크로/함수는 모두 `fprintf(fp, ...)`를 호출합니다. (3322의
`classes == NULL` 검사만 있고 `fp == NULL` 검사는 없습니다.)

**문제 시나리오**
로그 디렉터리에 쓰기 권한이 없거나, 디스크가 가득 찼거나, 경로가 너무 긴 경우 `fopen`이 NULL을
돌려주고, 첫 `fprintf(NULL, ...)`에서 세그폴트가 납니다. rkcheck는 `cubrid hb start` 경로에서
자동 호출되므로, 이 크래시가 HA 기동 자체를 좌초시킬 수 있습니다.

**제안** `fp == NULL`일 때 에러 로그를 남기고 EXIT_FAILURE로 정상 종료하도록 방어 코드를 추가하십시오.

## 문제 6

**[심각도: 중요] TRUNCATE가 REPLICATION=OFF를 무시하고 복제 로그를 남긴다**

**위치** `src/query/execute_statement.c:342-384` (`truncate_need_repl_log`), 호출부 `:16674`

**로직 설명 (LSP로 확인)**
`do_replicate_statement()`가 `PT_TRUNCATE`를 만나면 `truncate_need_repl_log()`로 복제 여부를
판단합니다. 이 함수는 대상 클래스에서 `classobj_find_cons_replication_key()`로 RK가 있으면 true를
돌려주는데(376-380), **`SM_CLASSFLAG_DATA_REPLICATION_OFF` 플래그는 전혀 확인하지 않습니다.**
일반 DML 경로가 복제-클래스 여부(`heap_get_class_repl_on()`)를 보는 것과 대조적입니다.

**문제 시나리오**
`REPLICATION=OFF`로 만든 테이블이라도 PK나 NOT NULL UNIQUE만 있으면 `TRUNCATE t;`가 statement 복제
로그를 남겨 슬레이브에서 재실행됩니다. 사용자는 "이 테이블은 복제 안 됨"으로 알고 있는데 TRUNCATE만
넘어가, 마스터/슬레이브 상태가 어긋납니다(마스터엔 데이터 있고 이후 TRUNCATE, 슬레이브엔 데이터 없이
TRUNCATE만).

**제안** `truncate_need_repl_log`에 `sm_is_replication_class(class_mop)` 검사를 추가하십시오.
(스펙 확정 2m-4)

## 문제 7

**[심각도: 중요] 파티션 승격 시 두 번째 이후 NOT NULL UNIQUE 컬럼의 UNIQUE 플래그가 지워진다 — 속성/프로퍼티 불일치**

**위치** `src/query/execute_schema.c:7943-7985` (`do_promote_partition`)

**로직 설명**
승격 대상 속성 루프가 이렇게 되어 있습니다(7948-7956).
```c
if (!has_notnull_unique && has_notnull_unique_constraints (smattr))
  has_notnull_unique = true;
else {
  smattr->flags &= ~(SM_ATTFLAG_UNIQUE);
  smattr->flags &= ~(SM_ATTFLAG_REVERSE_UNIQUE);
}
```
`has_notnull_unique`는 "하나라도 찾았는가"를 나타내는 플래그인데, 이를 **per-attribute 가드로
재사용**하는 바람에 첫 NOT NULL UNIQUE 컬럼만 플래그를 유지하고, **두 번째 이후의 NOT NULL UNIQUE
컬럼은 `!has_notnull_unique`가 false라 else로 빠져 UNIQUE 플래그가 지워집니다.** 반면 함수 끝의
프로퍼티 처리(7978-7982)는 `if (!has_notnull_unique)`일 때만 UNIQUE 프로퍼티를 드롭하므로,
`has_notnull_unique==true`이면 **클래스 프로퍼티 목록에는 두 번째 UNIQUE가 그대로 남습니다.**

**문제 시나리오**
NOT NULL UNIQUE 컬럼이 둘 이상인 파티션을 일반 테이블로 승격하면, 두 번째 컬럼은
"프로퍼티 목록엔 UNIQUE인데 attribute 플래그엔 UNIQUE 아님"이라는 불일치 상태가 됩니다. 이 상태에서
후속 스키마 연산·복제 판정이 attribute 플래그를 신뢰하면 유일성 보장이 조용히 빠집니다.

**제안** per-attribute 판정은 `has_notnull_unique_constraints(smattr)` 자체로 하고, "적어도 하나
찾았는가"를 나타내는 누적 변수는 별도로 두십시오(둘을 분리).

## 문제 8

**[심각도: 중요] REPLICATION이 완전 예약어가 되어 기존 `replication` 식별자 사용 불가 (하위호환 회귀)**

**위치** `src/parser/csql_lexer.l:918`(토큰 반환), `src/parser/csql_grammar.y:1669`(토큰 선언), 비예약 식별자 목록(20740-20883)

**로직 설명**

## 문제 9

**[심각도: 중요] REPLICATION=OFF 테이블의 DDL(SBR)이 플래그와 무관하게 항상 복제된다**

**위치** `src/query/execute_statement.c` — `is_data_repl_log_enabled()`(3304, `default: return true`),
게이트 `do_statement():3405`, `do_execute_statement():4113`

**로직 설명 (LSP로 확인)**
동기화(#7678)로 게이트가 `!HA_DISABLED() && is_stmt_based_repl_type(statement) && is_data_repl_log_enabled(parser, statement)`로
강화되어, **INSERT/UPDATE/DELETE(USE_SBR)** 경로는 이제 실제 수정 대상 spec의 복제 클래스 여부를 봅니다
(replication-off 테이블이면 SBR 억제). 그러나 `is_data_repl_log_enabled()`의 `switch`는 INSERT/UPDATE/DELETE만
개별 처리하고 **그 외(특히 DDL)는 여전히 `default: return true`**입니다. `is_stmt_based_repl_type`은 모든
DDL에 대해 true이므로, **DDL은 대상 테이블이 OFF든 ON이든 항상 statement 복제 로그를 남깁니다.**

**문제 시나리오**
`REPLICATION=OFF` 테이블에 대한 `ALTER TABLE`, `CREATE INDEX`, `TRUNCATE` 등이 슬레이브에서
재실행됩니다. 슬레이브엔 데이터 자체가 없거나 다를 수 있어(OFF라 DML은 안 넘어왔으므로) DDL 적용이
실패하고, 이를 격리·무시하는 경로가 없어 applylogdb의 fail_count로 이어질 수 있습니다. (DML 측 무성
유실은 #7678로 좁혀졌지만, DDL 측 정책 공백은 그대로입니다.)

**제안** DDL이라도 단일 대상 클래스가 OFF면 statement 복제를 억제할지 정책을 정하고, 필요한 곳에
클래스 플래그 검사를 넣으십시오. 최소한 이 동작을 스펙에 명시해야 합니다. (스펙 확정 2C-6)
