# RK/REPLICATION 기능 코드 리뷰 — DB 엔지니어(DBA/운영) 10년차

> **2차 재리뷰 (기준 HEAD `734f4959d` = `44468ed73` + #7678(`3b6ebd1a9`) + #7697(`9e094324b`) 동기화 머지)**
> 1차 리포트(기준 `44468ed73`)의 14개 문제를 새 HEAD에서 전부 재검증했다. 결과: **유지 12건 / 해소 1건(문제 4) / 오판 폐기 0건**,
> 여기에 델타 자체 검토로 신규 1건을 추가했다.

## 페르소나 소개

10년째 CUBRID를 포함한 상용 RDBMS를 운영해 온 DBA다. 신규 기능이 배포되면 "이 기능이 우리 운영 환경에서
자정에 장애를 낼 수 있는가"부터 본다. 관심사는 크게 네 가지다.

1. **rkcheck 같은 운영 유틸리티의 견고성** — 잘못된 입력, 대량 테이블, 다중 노드 환경에서 죽지 않고
   명확한 종료 코드와 로그를 남기는가.
2. **HA 전환·failover 경로의 동작** — 장애 조치 순간에 이 기능이 안전망 역할을 실제로 하는가.
3. **장애 발생 시 원인을 추적할 수 있는 로그/에러 메시지**인가.
4. **대량 스키마에서의 검사 비용**과, 10년차답게 **설계 일관성·중복 추상화·유지보수 비용·과거에
   고친 버그의 재발 가능성**(회귀)도 함께 본다.

## 총평 (2차)

upstream 동기화로 들어온 #7697이 실제로 고친 것은 정확히 1차 문제 5가 지적했던 그 지점
(`heap_is_replication_class`의 bool 반환·인터럽트 삼킴)이었고, 그 수정이 `locator_add_or_remove_index_internal()`의
호출 순서 자체도 바꿔놓아 1차 문제 4(인덱스 개수만큼 반복 heap scan)까지 사실상 함께 해소시켰다 — 두 문제가
같은 `if` 조건식 재작성으로 한 번에 정리된 셈이다. 다만 이 두 지점을 리뷰 대상에서 다루는 방식은 작업지시서
지시에 따라 문제 5는 완전히 제거하고, 문제 4는 "해소"로 재분류해 그 경위를 남겼다.

반면 **나머지 치명/중요 문제들은 이번 동기화로 전혀 손대지지 않았다.** `do_alter()`의 다중 절 게이트가
"첫 번째 절"만 보는 문제(문제 1)와 `rkcheck`가 위반 파일을 못 열면 NULL `FILE*`로 `fprintf`하는 문제(문제 2)는
줄 번호까지 그대로다 — #7678/#7697은 checksumdb·SBR·인터럽트 쪽만 건드렸을 뿐, RK/FK DDL 재검증 경로나
rkcheck 유틸리티 자체는 이번 동기화의 관심사가 아니었기 때문이다.

새로 들어온 델타(#7678의 `spec_has_replication_class`/`is_data_repl_log_enabled` 재작성) 자체는 코드 흐름을
직접 따라가며(파서 플래그 설정 시점까지 추적) 검토했으나, 저자가 커밋 메시지에 이미 명시한 한계
(조인으로 참조되는 REPLICATION=OFF 테이블 문제) 외에 새로운 확신 있는 결함은 찾지 못했다. 대신 그 코드가
1차 문제 12(재조회 비효율)의 패턴을 그대로 내장하고 있음을 확인해 해당 문제 설명을 갱신했고, #7697이 남긴
아주 좁은 잔여 비효율(REPLICATION=OFF 테이블에 RK 후보 인덱스가 2개 이상일 때만 발생)을 신규 사소 항목으로
추가했다.

## 문제 1 — [심각도: 치명] 다중 절 ALTER TABLE에서 RK/FK 재검증 게이트가 사실상 "첫 번째 절"만 본다

**상태: 유지 (변경 없음)**

**위치**: `src/query/execute_schema.c:2051`(게이트 판정), `:1837-1839`(entity_name/vclass 초기화), `:2059-2073`(검증 실행)

**로직 설명**

`do_alter()`는 한 `ALTER TABLE` 문에 여러 절(clause)이 나열된 경우 이를 순회하며 하나씩 적용한다.

```c
for (crt_clause = alter; crt_clause != NULL; crt_clause = crt_clause->next)
  {
    ...
    if (!need_check_repl_constraint && IS_REPL_CONSTRAINT_RELATED_ALTER (alter->info.alter.code))
      {
        need_check_repl_constraint = true;
      }
    do_semantic_checks = true;
  }

if (need_check_repl_constraint)
  {
    vclass = db_find_class (entity_name);
    ...
    error_code = check_ha_repl_constraint (vclass);
  }
```

`for` 루프는 `crt_clause`를 `crt_clause->next`로 전진시키며 절을 하나씩 처리하지만, 게이트 조건은
`crt_clause->info.alter.code`가 아니라 **함수 인자로 받은 고정 포인터 `alter`의 `info.alter.code`**를
검사한다. `alter`는 루프 내내 절대 바뀌지 않는 리스트의 head이므로, `alter->info.alter.code`는
"첫 번째 절의 alter 코드" 한 값으로 루프 전체에서 고정된다. 즉 이 `if`문은 루프 안에 있을 뿐,
실제로는 매 반복마다 똑같은 값을 반복 검사하는 것과 같다 — 두 번째 이후의 절이 무엇이든 결과에
영향을 줄 수 없다.

이 검사가 `do_alter()`로 옮겨진 배경 자체가 PR #6637("멀티 ALTER TABLE을 이용한 PK 변경 허용")이다.
당시 목적은 `DROP PRIMARY KEY, ADD PRIMARY KEY(...)` 처럼 **여러 절에 걸쳐 RK를 교체하는 문장**을
최종 상태 기준으로 한 번만 검사하도록 만드는 것이었다. 그런데 실제 구현은 "최종 상태를 본다"가 아니라
"첫 번째 절의 종류를 본다"로 되어 있다.

**문제 시나리오**

`IS_REPL_CONSTRAINT_RELATED_ALTER`에 없는 코드(예: `PT_RENAME_ATTR_MTHD`, `PT_CHANGE_ATTR`,
`PT_CHANGE_TABLE_COMMENT` 등)가 **첫 번째 절**이고, RK를 실제로 제거하는 절(`PT_DROP_CONSTRAINT`,
`PT_DROP_PRIMARY_CLAUSE`)이 **두 번째 이후**에 오면 재검증이 통째로 스킵된다.

```sql
-- u_orders_email 이 orders 테이블의 유일한 RK(NOT NULL UNIQUE)라고 가정
ALTER TABLE orders
  RENAME COLUMN note TO note2,     -- 1절: PT_RENAME_ATTR_MTHD (게이트 목록에 없음)
  DROP CONSTRAINT u_orders_email;  -- 2절: PT_DROP_CONSTRAINT (게이트 목록에 있지만 검사되지 않음)
```

`alter->info.alter.code`는 첫 절인 `PT_RENAME_ATTR_MTHD`로 고정되므로 `need_check_repl_constraint`는
끝까지 `false`로 남고, `check_ha_repl_constraint()`가 전혀 호출되지 않는다. 결과적으로 HA 운영 중인
복제 테이블에서 RK가 완전히 사라지는 DDL이 **에러 없이 성공**한다. 이후 벌어지는 일은 이 EPIC이 원래
막으려던 바로 그 상황이다 — applylogdb에서 해당 테이블 관련 로그 적용 시 fail_count가 증가하거나,
마스터·슬레이브 데이터가 소리 없이 어긋난다. `rkcheck`가 언젠가 다시 실행돼야 비로소 발견된다.

단일 절 ALTER(`ALTER TABLE t DROP PRIMARY KEY;`)에서는 `alter == crt_clause`이므로 이 버그가 드러나지
않는다 — 정확히 이 기능이 새로 지원하려 했던 "여러 절을 묶은 ALTER"에서만 재발한다는 점이 더 문제다.

**제안**: 게이트 조건을 `crt_clause->info.alter.code`로 바꾸거나(루프 중 한 번이라도 해당 코드가
나오면 플래그를 세우는 원래 의도대로), 혹은 아예 매 절마다 코드 종류를 배열에 모아뒀다가 루프 종료 후
한 번에 판정하는 방식으로 바꿔야 한다. RENAME으로 바뀐 최종 테이블명을 추적하는 기존 로직(entity_name
갱신)은 그대로 살릴 수 있다.

## 문제 2 — [심각도: 치명] rkcheck 위반 목록 파일을 열지 못하면 NULL FILE\*로 fprintf를 호출한다

**상태: 유지 (변경 없음)**

**위치**: `src/executables/util_cs.c:2855-2864`(`open_violation_list_file`), `:92-109`(`PRINT_SECTION_TITLE`/`PRINT_MESSAGE`/`PRINT_BLANK_LINE` 매크로), `:3320-3391`(`rkcheck()` 본문)

**로직 설명**

```c
fp = open_violation_list_file (database_name, arg->command_name, violation_list_file, PATH_MAX);
classes = db_get_all_classes ();
...
PRINT_SECTION_TITLE (fp, RK_CONSTRAINT_VIOLATIONS_SECTION_TITLE);
err = check_repl_constraint_violations (classes, fp, check_rk_constraint, &rk_violation_count);
```

`open_violation_list_file()`은 내부에서 `fopen(file_path, "w")`을 호출해 그 결과를 그대로 반환한다.
`fopen`이 실패하면(로그 디렉터리 권한 없음, 디스크 풀, 파일명에 쓸 수 없는 문자 등) `fp`는 `NULL`이
된다. 그런데 `rkcheck()`는 이 반환값을 **한 번도 NULL 체크하지 않고** 곧바로 `PRINT_SECTION_TITLE`,
`check_repl_constraint_violations()`(내부에서 `check_rk_constraint()`가 위반 클래스마다
`fprintf (fp, "%s\n", ...)` 호출), `PRINT_MESSAGE`, `PRINT_BLANK_LINE`에 전부 넘긴다. 이 매크로들은
전부 `fprintf ((stream), ...)`를 그대로 감싼 것이라 `stream`이 NULL이면 그대로 UB(정의되지
않은 동작, glibc 기준 사실상 세그폴트)로 이어진다.

**문제 시나리오**

`rkcheck`는 `cubrid hb start` 시 `us_hb_process_rkcheck()`를 통해 **자동으로** 실행된다
(`util_service.c:3969`). 로그 디렉터리(`$CUBRID/log` 등)의 권한이 잘못됐거나 디스크가 꽉 찬 노드에서
HA를 기동하면, `db_restart()`까지는 성공하고(서버는 이미 붙었으므로) 위반 목록 파일 오픈만 실패한다.
이 경우 사용자가 기대하는 동작은 "파일을 못 만들었다"는 명확한 에러이지만, 실제로는 rkcheck
프로세스가 세그폴트로 죽는다. hb start 자동화 스크립트 입장에서는 "rkcheck가 비정상 종료(core dump)"
와 "RK 위반 발견"을 구분할 수 없고, 코어 파일이 HA 기동 시도마다 쌓이면서 정작 원인(로그 디렉터리
문제)을 찾기 더 어렵게 만든다.

**제안**: `fp == NULL`이면 `PRINT_AND_LOG_ERR_MSG`로 명확한 에러(`.err` 로그에는 이미 `er_init`으로
경로가 잡혀 있으니 그쪽에 남기면 된다)를 남기고 `ER_FAILED`로 즉시 종료하도록 가드를 추가해야 한다.

## 문제 3 — [심각도: 중요] `cubrid hb start`가 rkcheck보다 먼저 서버를 띄운다 — "반쪽 HA 마스터" 상태

**상태: 유지 (변경 없음)**

**위치**: `src/executables/util_service.c:3947-3979`(`us_hb_process_start`), `:3848-3903`(`us_hb_server_start`), `:3194-3250`(`us_hb_process_rkcheck`)

**로직 설명**

```c
status = us_hb_server_start (ha_conf, db_name);   // 1) cub_server 프로세스를 기동
if (status != NO_ERROR) goto ret;

status = us_hb_process_rkcheck (ha_conf, db_name); // 2) RK/FK 위반 검사
if (status != NO_ERROR) goto ret;

status = us_hb_copylogdb_start (pids, ha_conf, db_name, NULL, NULL); // 3) 복제 데몬 기동
```

`us_hb_server_start()`는 `process_server (START, ...)`를 호출해 **실제 cub_server 프로세스를
기동**시킨다. rkcheck는 그 다음 단계(2단계)에서 실행되고, 위반이 발견되면 `goto ret`으로
`us_hb_copylogdb_start()`(3단계, 실제 복제 데몬 기동)만 건너뛴다.

사용자 스펙 §7 "HA 실행시 다음 사항을 제약사항을 확인하며, 제약사항 위반 시 에러와 함께 파일 리스트를
출력한다"는 문장은 "HA 자체를 기동하지 않는다"는 전제를 깔고 있고, PR 히스토리(#6658)도 "위반이 있으면
HA 자체를 기동하지 않도록 막는다"고 명시한다. 하지만 실제 순서는 **DB 서버 프로세스가 이미 살아서
클라이언트 연결을 받는 상태에서** rkcheck가 실행된다.

**문제 시나리오**

RK 위반 테이블이 있는 노드에서 `cubrid hb start`를 실행하면: cub_server는 정상 기동해 클라이언트
연결·쓰기를 받아들이지만, `us_hb_process_rkcheck()`가 실패해 `us_hb_copylogdb_start()`는 아예
호출되지 않는다. 즉 **"복제 데몬 없이 쓰기를 받는 마스터"** 라는, 순수 싱글 모드보다 더 위험한 상태가
만들어진다. 애플리케이션/로드밸런서가 "hb start 명령이 실패했으니 이 노드는 서비스 불가"라고 정확히
판단하지 못하면(예: 헬스체크가 단순히 CUBRID 포트 응답만 본다면), 이 반쪽 상태의 노드로 트래픽이
흘러들어가 데이터가 쌓이고, 이후 정상적으로 HA를 재구성해도 그 사이 쓰인 데이터는 복제되지 않는다.

**제안**: 최소한 rkcheck를 서버 기동 **이전**에(별도 커넥션으로 카탈로그만 조회하거나, 서버를
"HA 후보"로만 띄우고 하트비트 등록 전에) 실행하거나, rkcheck 실패 시 이미 띄운 서버를 다시
내리는 보정 로직이 필요하다.

## 문제 4 — [심각도: 사소, 하향] 인덱스 루프 안 반복 heap scan — #7697 동기화로 대부분 해소, 좁은 잔여만 남음

**상태: 재분류(치명→사소). 핵심 지적은 해소로 판단, 잔여 케이스만 신규 관점으로 재기술**

**위치**: `src/transaction/locator_sr.c:8041-8055`(`locator_add_or_remove_index_internal`)

**1차 지적(요약)**: `heap_is_replication_class(thread_p, class_oid)`가 `&&` 체인의 맨 앞에서 평가되어
`!replicated`, `or_is_replication_candidate_key(index)` 같은 훨씬 저렴한 조건보다 먼저 실행되므로,
인덱스 개수만큼(짧은 회로 평가로도 걸러지지 않고) 매번 heap scan이 반복된다는 지적이었다. 이는 PR #6908
리뷰의 MAJOR 코멘트와 동일한 자리였다.

**2차 재검증 결과 — #7697이 정확히 이 자리를 재작성했다**

```c
if (error_code == NO_ERROR && need_replication && !replicated
    && or_is_replication_candidate_key (index)
    && !LOG_CHECK_LOG_APPLIER (thread_p) && log_does_allow_replication () == true)
  {
    bool repl_on = false;

    error_code = heap_get_class_repl_on (thread_p, class_oid, &repl_on);
    if (error_code == NO_ERROR && repl_on)
      {
        error_code = repl_log_insert (...);
        replicated = true;
      }
  }
```

이제 클래스 레코드 fetch(구 `heap_is_replication_class`, 현 `heap_get_class_repl_on`)는 **`or_is_replication_candidate_key(index)`
(이 인덱스가 PK/UK인지, 순수 비트 검사)와 `!replicated`가 먼저 통과한 뒤에만** 호출된다. 즉 인덱스가
10개인 테이블이라도 PK/UK가 아닌 일반 인덱스 8개는 애초에 이 호출에 도달하지 않는다 — 1차 지적의
핵심(인덱스 전체 개수만큼 반복)은 이 재작성으로 해소됐다.

**남아 있는 좁은 잔여**: `REPLICATION=OFF`인 클래스에 RK 후보 인덱스(PK 또는 NOT NULL UNIQUE)가
**2개 이상** 있으면, 첫 RK 후보에서 `repl_on`이 `false`로 나와 `replicated`가 끝내 `true`가 되지 않으므로
두 번째 RK 후보에서도 다시 `heap_get_class_repl_on`이 호출된다(`class_oid`가 같으므로 결과는 항상 동일한데도).
1차 지적이 "인덱스 전체 개수"였던 것에 비하면 사실상 무시할 수준(테이블당 RK 후보는 보통 1~2개)이라
심각도를 사소로 낮췄다.

**제안**: 굳이 고치려면 `repl_on` 조회 결과를 루프 진입 전 또는 첫 조회 시점에 한 번만 캐싱해 재사용하면
되지만, 비용 대비 우선순위는 낮다.

## 문제 6 — [심각도: 중요] "복구 가능한 실패"에 `assert(false)`로 덮는 패턴이 신규 코드 곳곳에 반복 이식됐다

**상태: 유지 (범위 조정 — heap_file.c의 `heap_is_replication_class` 사례는 #7697로 전환되어 이 항목에서 제외. 나머지 3곳은 그대로)**

**위치**: `src/object/schema_manager.c:3394-3407`(`sm_is_replication_class`), `src/query/execute_statement.c:3200-3218`(`is_replication_class`), `src/object/schema_template.c:120,5134-5160`(`find_index_catalog_class`, 문제 13과 연계)

**로직 설명**

이번 diff가 새로 추가한 함수 중 최소 3개가 동일한 모양을 하고 있다: "정상적으로는 거의 항상 성공하지만
동시성·인터럽트 상황에서는 실패할 수 있는 호출"이 실패하면 `assert(false)`를 찍고 조용히 안전한
기본값(`false`/`NULL`)을 반환한다.

```c
// schema_manager.c
bool sm_is_replication_class (MOP op)
{
  SM_CLASS *class_;
  if (op != NULL && au_fetch_class_force (op, &class_, AU_FETCH_READ) == NO_ERROR)
    { return !(class_->flags & SM_CLASSFLAG_DATA_REPLICATION_OFF); }
  assert (false);
  return false;
}

// execute_statement.c
static bool is_replication_class (const char *classname)
{
  ...
  class_obj = db_find_class (classname);
  if (class_obj == NULL) { assert (false); return false; }
  return sm_is_replication_class (class_obj);
}
```

`au_fetch_class_force()`나 `db_find_class()`는 클래스가 동시에 DROP되거나, 권한 문제, 트랜잭션
충돌 등으로 **정상적인 운영 중에도** 실패할 수 있는 호출이다. `assert(false)`는 "여기 도달하면
프로그램에 버그가 있다"는 불변조건 확인용인데, 여기서는 사실상 정상적인 실패 경로를 표현하는 데
쓰이고 있다. 이는 정확히 PR #7697이 "이전 수정이 남긴 주석의 전제가 사실과 다르다"고 지적했던 것과
같은 계열의 실수다 — #7697은 정확히 이 패턴을 `heap_is_replication_class` 한 곳에서 근본적으로
고쳤지만(→ `heap_get_class_repl_on`, 에러코드+out-parameter 반환), 같은 EPIC 안에서 같은 안티패턴이
최소 3곳 더 남아 있고, 이번 동기화 대상 밖이라 그대로다.

`is_replication_class()`는 이번 동기화(#7678)로 새로 추가된 `spec_has_replication_class()`
(`execute_statement.c:3271-3301`)를 통해 **모든 `USE_SBR` 힌트 DML(INSERT/UPDATE/DELETE)마다** 호출되도록
노출 범위가 넓어졌다 — 문제 12에서 다루는 재조회 경로가 바로 이 `assert(false)` 트리거 지점이기도 하다.

**문제 시나리오**: DEBUG 빌드(QA/CI에서 흔히 사용)에서는 이 조건에 걸리면 `assert`가 프로세스를
그대로 abort시킨다 — 운영에서는 드물지만 QA에서 동시 DDL(예: 다른 세션이 같은 클래스를 DROP하는
레이스)을 재현하는 테스트를 돌리면 서버/클라이언트가 죽는 이유를 알기 어려운 크래시로 나타난다.
반대로 RELEASE 빌드(assert가 no-op)에서는 이 실패가 "복제 대상 아님"으로 조용히 해석되어, DDL
복제 판단(`is_data_repl_log_enabled`)이나 RK 판정이 실제와 다르게 내려질 수 있다.

**제안**: 이 3곳 모두 `assert(false)` 대신 에러를 호출자에게 전파하거나(반환 타입을 에러코드+out
파라미터로 바꾸거나), 최소한 "실패 시 안전한 기본값으로 처리하되 assert는 제거"하는 방향으로
정리해야 한다. 이미 존재하는 `heap_get_class_repl_on()`의 패턴(에러코드 반환 + out-parameter)을
다른 3곳에도 동일하게 적용하는 것이 일관성 있는 해법이다.

## 문제 7 — [심각도: 중요] rkcheck의 `tmp_database_name` 버퍼가 긴 DB 이름을 못 담는다 (PR #6934 MAJOR가 TODO로만 남음)

**상태: 유지 (변경 없음, TODO 주석도 그대로)**

**위치**: `src/executables/util_cs.c:3273`, `:3297-3302`

**로직 설명**

```c
char tmp_database_name[CUB_MAXHOSTNAMELEN];   // 256
...
if (strchr (database_name, '@') == NULL)
  {
    /* TODO: Handle truncation explicitly here; keep this in sync with applyinfo() local_database_name build path. */
    snprintf (tmp_database_name, sizeof (tmp_database_name), "%s@localhost", database_name);
    database_name = tmp_database_name;
  }
```

`CUB_MAXHOSTNAMELEN`은 256이다. CUBRID DB 이름 최대 길이는 255자이므로,
`"%s@localhost"`(`@localhost` 10바이트)를 합치면 최대 265바이트가 필요할 수 있는데 버퍼는 256바이트뿐이다.
`snprintf`라 버퍼 오버런은 나지 않지만, **DB 이름이 길면 뒷부분이 잘려서 다른(혹은 존재하지 않는)
데이터베이스 이름으로 `db_restart()`를 시도**하게 된다. 이 문제는 PR #6934 리뷰에서 vimkim이 MAJOR로
지적했고, 저자도 "마이너한 리뷰라 바로 머지, 버퍼 크기 이슈는 TODO"라고 명시적으로 남겼다 — 코드에도
그 TODO 주석이 그대로 남아 있다.

**문제 시나리오**: 조직의 명명 규칙상 DB 이름이 길게 지어지는 환경(예: `<서비스>_<리전>_<역할>_<환경>`
조합으로 240자 이상)에서 `cubrid rkcheck <긴 DB 이름>`을 실행하면, 잘린 이름으로 `db_restart()`가
실패하거나 — 최악의 경우 우연히 다른 짧은 이름의 접두어와 일치해 **엉뚱한 데이터베이스를 검사**하는
결과로 이어질 수 있다. 에러가 나더라도 "DB를 찾을 수 없음"류의 메시지만 보이므로, 운영자가 "내가
입력한 이름이 잘렸다"는 사실을 바로 알아채기 어렵다.

**제안**: `database_name`의 길이를 `snprintf` 호출 전에 명시적으로 검사해, `strlen(database_name) +
strlen("@localhost") >= sizeof(tmp_database_name)`이면 오류 메시지와 함께 즉시 실패 처리해야 한다.
동일한 패턴이 쓰이는 `applyinfo()`의 `local_database_name` 빌드 경로(코드 내 주석이 이미 언급)도
같이 점검할 필요가 있다.

1차 리뷰에서 지적했던 "이미 이름 해석이 끝난 캐시(`flat_entity_list`)가 바로 옆에 있는데도 이름으로

안에 **①번 경로로 그대로 들어와 정식화**됐다. 더 눈에 띄는 점은 이 함수가 ①을 먼저 시도하고 실패하면
②(캐시 사용, 더 저렴함)로 넘어간다는 순서다 — 저렴한 경로가 있는데 비싼 경로를 먼저 taken 것이다.

**문제 시나리오**: `is_data_repl_log_enabled()`는 `USE_SBR` 힌트가 붙은 모든 INSERT/UPDATE/DELETE
문마다 `spec_has_replication_class()`를 호출한다(1차 대비 호출 지점이 INSERT/UPDATE/DELETE 세 갈래로
넓어졌다). `checksumdb`처럼 짧은 시간에 같은 문장을 반복 실행하는 도구(이번 동기화의 checksumdb.c도
REPLACE/UPDATE 문에 `USE_SBR`를 명시적으로 붙인다), 또는 응용 코드에서 `USE_SBR` 힌트를 자주 쓰는
경우 불필요한 카탈로그 조회가 누적된다. 또한 문제 6에서 지적한 `assert(false)` 경로(`class_obj == NULL`)도
바로 이 ① 재조회 지점에서 발생한다 — 이름 재해석 과정에서 클래스가 그 사이 DROP됐다면 트리거될 수 있는
경로다.

**제안**: `spec_has_replication_class()`의 순서를 뒤집어 `flat_entity_list`(②, 캐시된 객체) 검사를
먼저 하고, 거기서 못 찾을 때만 `get_spec_classname()`/`is_replication_class()`(①, 이름 재조회)로
폴백하도록 바꾸는 편이 일관되고 효율적이다.

## 문제 13 — [심각도: 사소] `find_index_catalog_class()`가 선언·정의만 되고 호출되지 않는 죽은 코드로 남아 있다

**상태: 유지 (변경 없음)**

**위치**: `src/object/schema_template.c:120`(전방 선언), `:5134-5160`(정의)

**로직 설명**

```c
static MOP find_index_catalog_class (const char *name);   // 120행
...
static MOP
find_index_catalog_class (const char *index_name)          // 5134행
{
  ...
}
```

파일 전체를 검색해도 이 함수의 호출부는 존재하지 않는다(전방 선언과 정의, 두 곳뿐). `static`
함수이므로 다른 파일에서도 호출할 수 없다.

**문제 시나리오**: 당장 기능 결함은 아니지만, 컴파일러의 `-Wunused-function` 경고 대상이며(빌드
설정에 따라 경고를 에러로 승격하면 빌드가 깨질 수 있다), 리뷰어/후임자가 "이 함수가 어디서 쓰이는지"
찾다가 시간을 낭비하게 만든다. 정확히 이런 종류의 잔재(dead code)가 PR #6908 리뷰에서도 한 차례
지적된 바 있다("호출부가 사라진 `chksum_set_repl_info_and_demote_table_lock` 선언만 남음") — 같은
실수가 다른 파일에서 재발한 셈이다.

**제안**: 실제로 필요 없다면 삭제하고, 향후 사용할 계획이 있다면 커밋 메시지나 이슈에 근거를 남긴 뒤
남겨야 한다.

## 문제 14 — [심각도: 사소] `do_alter()`에서 일반 클래스를 가리키는 변수 이름이 `vclass`로 되어 있어 CUBRID 관례와 반대로 읽힌다

**상태: 유지 (변경 없음)**

**위치**: `src/query/execute_schema.c:1837`(선언), `:2061-2068`(사용)

**로직 설명**

```c
DB_OBJECT *vclass;
...
vclass = db_find_class (entity_name);
if (!sm_is_replication_class (vclass)) { return NO_ERROR; }
error_code = check_ha_repl_constraint (vclass);
```

CUBRID 코드베이스 전반에서 `vclass`는 관례적으로 "virtual class(뷰)"를 가리킨다(`db_is_vclass()`,
`PT_VCLASS` 등). 그런데 여기서 `entity_name`은 지금 막 ALTER TABLE로 수정을 마친 **일반 테이블**을
가리키는 클래스 객체이며 뷰와는 무관하다.

**문제 시나리오**: 실제 버그로 이어지지는 않지만, 이 함수를 처음 읽는 사람이 "여기서 뷰를 다루고
있나?"라고 오해해 시간을 쓰게 만든다. 10년 차원에서 볼 때 이런 사소한 명명 불일치가 누적되면
"관례를 믿을 수 없는 코드베이스"가 되어 리뷰·유지보수 비용을 은근히 높인다.

**제안**: `vclass` → `altered_class` 또는 `class_obj` 등으로 이름을 바꾼다.

## 문제 15 — [심각도: 사소] [신규] `heap_get_class_repl_on()`이 RK 후보 인덱스가 여러 개면 여전히 반복 호출될 수 있다 (문제 4의 잔여, #7697 완전 미커버)

**상태: 신규 (2차 델타 검토)**

**위치**: `src/transaction/locator_sr.c:8041-8055`

**로직 설명**: 문제 4에서 다룬 것과 같은 자리다. #7697이 `heap_get_class_repl_on()` 호출을
`or_is_replication_candidate_key(index) && !replicated` 뒤로 옮겨 "인덱스 전체 개수만큼" 반복되던
문제는 해소했지만, `replicated`는 `repl_on == true`일 때만 세워진다.

```c
error_code = heap_get_class_repl_on (thread_p, class_oid, &repl_on);
if (error_code == NO_ERROR && repl_on)
  {
    ...
    replicated = true;
  }
```

`repl_on`이 `false`(즉 해당 클래스가 `REPLICATION=OFF`)이면 `replicated`는 끝까지 `false`로 남으므로,
**같은 트랜잭션의 같은 INSERT/DELETE 안에서 RK 후보 인덱스(PK 또는 NOT NULL UNIQUE)가 2개 이상**이면
두 번째 RK 후보에서도 동일한 `class_oid`에 대해 `heap_get_class_repl_on()`이 다시 호출된다.
`class_oid`가 바뀌지 않는 한 결과는 항상 같으므로 이 두 번째 호출은 불필요하다.

**문제 시나리오**: `REPLICATION=OFF`로 지정한 테이블에 PK 외에 NOT NULL UNIQUE 제약을 추가로 몇 개
더 둔 스키마(복제는 끄되 애플리케이션 무결성 목적으로 UNIQUE는 유지하는 흔한 설계)에서 대량
INSERT/DELETE 배치가 도는 경우, RK 후보 개수만큼 불필요한 클래스 레코드 heap fetch가 반복된다.
1차 문제 4가 지적했던 "인덱스 전체 개수"에 비하면 영향 범위가 훨씬 좁아(RK 후보만, 보통 1~3개)
운영에 체감될 정도는 아니라고 판단해 심각도를 사소로 매겼다.

**제안**: 우선순위는 낮지만, 고친다면 `repl_on` 조회 결과 자체를 `!replicated`와 별도로 한 번만
캐싱하는 지역 변수(예: `repl_on_checked`)를 두어 두 번째 이후 호출을 완전히 생략하면 된다.

`execute_statement.c`, `checksumdb.c`)은 diff 단위로 전부 읽고, `spec_has_replication_class`/

`db_set_suppress_repl_on_transaction` 실패 처리 경로도 상위 호출부의 `db_abort_transaction()`까지
따라가 트랜잭션 롤백으로 안전하게 수습됨을 확인했다.

**더 찾지 않은 근거**: #7678의 커밋 메시지가 스스로 명시한 한계("조인/서브쿼리로 참조되는
REPLICATION=OFF 테이블은 여전히 슬레이브에서 빈 테이블 기준으로 재실행됨")는 저자가 이미 인지하고
있는 기술 부채이지 이번 리뷰가 새로 발굴할 지점이 아니라고 판단해 별도 항목화하지 않았다. `checksumdb.c`의
`db_ha_checksum_schema` INSERT에 `USE_SBR` 힌트가 빠져 있다는 PR #6908의 미해결 논쟁도 코드로 재확인은
했으나, 저자·리뷰어 사이에서도 "의도적인지 불명"으로 남은 사안이라 확신 없는 추측성 지적을 더하지
않았다. 이 지점에서 새로운 확신 있는 지적을 더 찾기 어렵다고 판단해 조사를 마친다.
