## 문제 16 — [심각도: 사소, 신규] 중복 REPLICATION 옵션 에러 메시지가 "replication = on/off" 대신 "replication = 1/0"으로 출력된다

**위치**: `src/parser/parse_tree_cl.c:8013-8079`(`pt_print_table_option`, REPLICATION 분기는 8041-8043) — 값 생성부는 `src/parser/csql_grammar.y:19890-19906`(`class_replication_spec`), 호출부는 `src/parser/semantic_check.c:8506-8519`(`pt_check_create_entity`의 `PT_TABLE_OPTION_REPLICATION` 중복 검사)

**로직 설명**: `CREATE TABLE`에서 `REPLICATION` 옵션 값은 파서가 `ON_`/`OFF_`/생략 세 가지만 받아 `opt_replication_option`에서 정수 1/0으로 변환한 뒤(`csql_grammar.y:19987-19997`), `class_replication_spec`이 이 정수를 `PT_VALUE` 노드(`type_enum = PT_TYPE_INTEGER`, `data_value.i = 1|0`)에 담습니다(`csql_grammar.y:19890-19906`). 이 노드가 `pt_table_option(..., PT_TABLE_OPTION_REPLICATION, $1)`으로 감싸져 `table_option_list`에 들어갑니다.

같은 리스트를 검사하는 `pt_check_create_entity()`는 `REPLICATION`이 두 번 이상 명시되면(예: `CREATE TABLE t (...) REPLICATION=ON REPLICATION=OFF`) `MSGCAT_SEMANTIC_DUPLICATE_TABLE_OPTION` 에러를 내면서, 그 옵션 노드를 `parser_print_tree(parser, tbl_opt)`로 사람이 읽을 문자열로 바꿔 메시지에 끼워 넣습니다(`semantic_check.c:8506-8519`). `parser_print_tree`는 노드 타입(`PT_TABLE_OPTION`)에 등록된 프린터 함수, 즉 `pt_print_table_option()`을 호출합니다(`parse_tree_cl.c:5404`).

그런데 `pt_print_table_option()`은 `ENCRYPT`(TDE 알고리즘 정수 값을 `tde_get_algorithm_name()`으로 사람이 읽는 이름으로 변환해서 출력, 8060-8070번 줄)와 달리 `REPLICATION`에는 그런 변환이 없습니다. 8041-8043번 줄에서 "replication = "만 붙이고, 값 부분은 아무 특별 처리 없이 맨 아래 `else` 분기(8071-8074번 줄) `pt_print_bytes_l(parser, p->info.table_option.val)`로 떨어집니다. 이 값 노드의 `type_enum`은 `PT_TYPE_INTEGER`이므로, 정수 값을 그대로("1" 또는 "0") 문자열로 찍습니다.

**문제 시나리오**: `CREATE TABLE t (i INT) REPLICATION=ON, REPLICATION=OFF;`처럼 REPLICATION을 두 번 쓰면, 에러 메시지가

```
ERROR: Duplicate table option: replication = 1
```

처럼 나옵니다. 사용자는 방금 `ON`이라고 쳤는데 에러 메시지에는 `1`이 찍혀 있으니 "내가 뭘 잘못 쳤길래 1이 나오지?"라고 혼란스러울 수 있습니다. `charset`/`collate`/`comment`/`encrypt`는 모두 사용자가 입력한 표기와 같은 형태(문자열 원문 또는 알고리즘 이름)로 되돌아오는데, `replication`만 내부 인코딩(정수)이 그대로 노출되는 셈입니다. 참고로 이 정수 형태(`replication = 1`)는애초에 `opt_replication_option` 문법에 존재하지 않는 표기라(문법은 `ON_`/`OFF_`/생략만 허용, 19987-19997번 줄), 이 에러 메시지 텍스트를 그대로 복사해 다시 실행해도 문법 에러가 납니다 — 사용자가 에러 메시지를 참고해 재시도할 때 혼란을 더할 수 있습니다.

**제안**: `ENCRYPT` 처리와 같은 방식으로, `PT_TABLE_OPTION_REPLICATION`일 때는 `p->info.table_option.val->info.value.data_value.i`가 1이면 `"on"`, 0이면 `"off"`로 명시적으로 매핑해서 출력하도록 `pt_print_table_option()`에 분기를 추가합니다.

## 조사 종료 선언

**추가 훑은 영역과 판단 근거**:

- `class_object.h`/`schema_manager.h`/`execute_schema.h`/`btree.h`/`heap_file.h` — 모두 함수 선언 추가/개명이며, 대응 정의부는 이미 기존 리포트(문제 4) 및 K-7/K-8/K2-2에서 다뤄진 함수들(`sm_is_replication_class`, `heap_get_class_repl_on`, `btree_get_rkey_btid`)이라 헤더만 보고 새 문제로 셀 것이 없었음.
- `util_admin.c`(`RKCHECK` 옵션 맵 추가) — `-r`/`-f` 두 boolean 옵션과 위치 인자(DB명) 등록 방식이 인접한 다른 유틸리티(`MEMMON`, `TDE`) 등록 패턴과 동일해 구조적 결함 없음. 실제 옵션 파싱·기본 동작 문서화 이슈는 이미 K-60/K-65가 다룸.
- `error_code.h`(1375~1378 신규 에러코드, `ER_LAST_ERROR` 1379로 갱신) — `dbi_compat.h`가 `error_code.h`를 직접 include하는 구조라 별도 동기화 누락 없음을 확인. 메시지 카탈로그(`msg/*.msg`) 4건 모두 en/ko 존재 확인.
- `px_worker_manager.cpp` — 빈 줄 1줄 추가뿐인 포맷팅 잡음, 실질 변경 없음.
- 파티션 자식 테이블에 대한 `ALTER TABLE ... REPLICATION=...` 직접 허용 여부는 코드 정적 분석만으로 결론 내리기 어려워(런타임 확인 필요) 근거 미달로 보류.

**결론**: 잔여 쿼터(50 − 15 = 35) 중 근거를 확보해 추가한 문제는 **1건(문제 16, 사소)** 뿐이다. 나머지 34건은 위 영역들을 실제로 Read + 콜체인 추적까지 마쳤지만, 이미 병합된 67건 또는 자기 리포트 15건과 동일한 뿌리이거나(예: 파티션 헤더 함수들), 코드만으로는 확증할 수 없는 가설(파티션 ALTER 직접 허용 여부)이라 등록하지 않았다. 쿼터를 채우기 위한 표현 트집·가능성 나열은 하지 않았다. 이 지점에서 3차 재수색을 종료한다.
