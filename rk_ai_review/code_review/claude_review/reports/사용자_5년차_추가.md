## 문제 11

**[심각도: 보통] `CREATE TABLE`에서 `REPLICATION` 옵션을 중복 명시했을 때 뜨는 에러 메시지가 사용자가 입력한 `ON`/`OFF`가 아니라 내부 정수 인코딩(`1`/`0`)을 그대로 노출한다**

위치: `src/parser/semantic_check.c:8506-8517`(`pt_check_create_entity`의 `PT_TABLE_OPTION_REPLICATION` 분기),
`src/parser/csql_grammar.y:19890-19906`(`class_replication_spec` — 값 노드를 `PT_TYPE_INTEGER`로 생성),
`src/parser/parse_tree_cl.c:8038-8046`(`pt_print_table_option`의 `PT_TABLE_OPTION_REPLICATION` 케이스 — 값 특수 처리 없음),
비교 대상 `src/parser/parse_tree_cl.c:8060-8070`(`PT_TABLE_OPTION_ENCRYPT`는 정수를 알고리즘 이름 문자열로 변환해서 출력)

로직 설명: `CREATE TABLE t (...) REPLICATION=ON, REPLICATION=OFF;`처럼 `REPLICATION` 옵션을
같은 문장에서 두 번 쓰면 어떻게 되는지 확인했다. 문법 규칙(`csql_grammar.y:9041-9047`
`table_option_list : table_option_list ',' table_option | table_option_list table_option`)은
`REPLICATION` 옵션이 여러 번 나오는 것 자체는 허용하므로 파싱은 통과하고, 의미 분석 단계
(`pt_check_create_entity`)가 이를 잡아낸다.

```c
/* semantic_check.c:8506 */
case PT_TABLE_OPTION_REPLICATION:
  {
    if (found_tbl_replication)
      {
	PT_ERRORmf (parser, node, MSGCAT_SET_PARSER_SEMANTIC, MSGCAT_SEMANTIC_DUPLICATE_TABLE_OPTION,
		    parser_print_tree (parser, tbl_opt));
	return;
      }
    ...
  }
```

`MSGCAT_SEMANTIC_DUPLICATE_TABLE_OPTION`(204번, `msg/en_US.utf8/cubrid.msg:1859`)의 문구는
`Duplicate table option '%1$s'`이고, `%1$s` 자리에 `parser_print_tree(parser, tbl_opt)`의
결과, 즉 두 번째로 나온 `REPLICATION` 옵션 노드 자체를 출력한 문자열이 들어간다. 이 출력은
`pt_print_func_array[PT_TABLE_OPTION] = pt_print_table_option`을 거치는데, 문제는 이 값
노드가 애초에 `PT_TYPE_INTEGER`로 만들어졌다는 데 있다.

```c
/* csql_grammar.y:19890 — class_replication_spec */
node->type_enum = PT_TYPE_INTEGER;
node->info.value.data_value.i = $3;   /* opt_replication_option: 기본/ON=1, OFF=0 */
```

그리고 `pt_print_table_option`은 이 값을 사람이 읽을 문자열로 변환하는 특수 처리를
`REPLICATION`에는 넣지 않았다.

```c
/* parse_tree_cl.c:8041 */
case PT_TABLE_OPTION_REPLICATION:
  q = pt_append_nulstring (parser, q, "replication = ");
  break;
...
/* 8060 — ENCRYPT는 정수를 알고리즘 이름으로 바꿔서 출력하는 특수 케이스가 이미 존재 */
else if (p->info.table_option.option == PT_TABLE_OPTION_ENCRYPT)
  {
    tde_algo_name = tde_get_algorithm_name ((TDE_ALGORITHM) p->info.table_option.val->info.value.data_value.i);
    ...
  }
else
  {
    r1 = pt_print_bytes_l (parser, p->info.table_option.val);   /* REPLICATION은 여기로 빠진다 */
  }
```

`ENCRYPT` 옵션도 값이 내부적으로는 정수(알고리즘 enum)이지만, 바로 이 이유 때문에
"정수를 그대로 보여주면 사용자가 못 알아본다"고 판단해 이름 문자열로 변환하는 특수
분기가 이미 존재한다. `REPLICATION`은 같은 성격(사용자는 `ON`/`OFF`라는 텍스트로 입력했지만
내부값은 정수)임에도 이 특수 처리가 빠져 있어, `pt_print_bytes_l`이 `PT_VALUE`의 정수값을
그대로("1" 또는 "0") 문자열화한다.

문제 시나리오: 실무에서 스크립트를 합치다가 실수로 옵션을 중복 기재하는 경우는 드물지
않다.

```sql
CREATE TABLE orders (id INT) REPLICATION=ON, REPLICATION=OFF;
```

를 실행하면 에러가 나는 것 자체는 맞지만, 화면에 뜨는 문구는

```
ERROR: Duplicate table option 'replication = 0'
```

처럼 사용자가 입력한 적 없는 `0`이라는 숫자가 나온다(두 번째로 쓴 게 `OFF`이므로 0).
사용자는 `ON`/`OFF`라는 텍스트만 타이핑했을 뿐 `0`/`1`이라는 내부 인코딩을 알 방법이
없으므로, "내가 뭘 잘못 썼길래 0이 나오지?"라고 오독하기 쉽다. `COMMENT`(문자열 그대로
출력), `AUTO_INCREMENT`(정수 그대로가 실제로 사용자가 입력한 값), `ENCRYPT`(이름으로 변환)
등 다른 옵션들은 전부 사용자가 이해할 수 있는 형태로 에러에 되비치는데, `REPLICATION`만
내부 구현 디테일이 새어나오는 유일한 옵션이다.

제안: `pt_print_table_option`의 `PT_TABLE_OPTION_REPLICATION` 케이스에도 `ENCRYPT`와
동일한 패턴으로 `p->info.table_option.val->info.value.data_value.i`가 0이면 `"off"`,
0이 아니면(또는 1이면) `"on"`을 붙이는 분기를 추가해야 한다.

**dedup 확인**: 기존 67건 중 `K-20`(ALTER TABLE의 중복 REPLICATION 절 자체를 세만틱
검사하지 않는 문제, `csql_grammar.y`/`semantic_check.c`)과 제 1차 리포트 문제 6(같은
주제)은 "CREATE는 중복을 잡아내지만 ALTER는 아예 잡아내지 못한다"는 **검사 유무**에 대한
지적이다. 이번 문제 11은 그와 반대로 **CREATE가 이미 정상적으로 중복을 잡아낸 이후,
그 에러 메시지 문구 자체가 틀린 값을 보여준다**는, 검증된 적 없는 별개의 코드 경로
(`parse_tree_cl.c:pt_print_table_option`)와 별개의 버그 뿌리(정수→문자열 변환 특수 케이스
누락)를 가리키므로 중복이 아니다.
