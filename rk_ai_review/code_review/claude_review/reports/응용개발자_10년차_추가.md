## 문제 17 (신규 — parse_tree 재출력 경로)

**[심각도: 사소] pt_print_table_option이 REPLICATION 옵션을 키워드(ON/OFF)가 아니라 원시 정수(1/0)로 재출력 — 파스트리→SQL 재구성이 재파싱 불가능한 문장을 만든다**

- 위치: `src/parser/parse_tree_cl.c:8041-8043`(라벨 출력) + `:8071-8075`(값 출력 else 분기)

- 로직 설명(LSP·정의 추적):
  - 문법 `class_replication_spec`(`csql_grammar.y:19890-19903`)은 REPLICATION 옵션을 **`PT_VALUE` 정수 노드**로 저장합니다. `node->type_enum = PT_TYPE_INTEGER; node->info.value.data_value.i = $3;`이고 `$3`은 `opt_replication_option`이 돌려주는 `1`(ON)·`0`(OFF)입니다. `PT_NODE_PRINT_VALUE_TO_TEXT`로 그 값의 텍스트 표현("1"/"0")이 세팅됩니다.
  - 파스트리를 다시 SQL 텍스트로 찍는 `pt_print_table_option`은 이 옵션에 대해 라벨 `"replication = "`만 붙이고(`:8041-8043`), 값은 `PT_TABLE_OPTION_CHARSET/COLLATION`(따옴표 없는 문자열)·`PT_TABLE_OPTION_ENCRYPT`(정수→알고리즘명 변환) 같은 특수 처리를 받지 못한 채 마지막 `else`에서 `pt_print_bytes_l`로 흘러(`:8071-8075`) **정수 텍스트 "1"/"0"을 그대로 출력**합니다. 결과 문자열은 `... replication = 1`입니다.
  - 대조: 같은 함수의 `PT_TABLE_OPTION_ENCRYPT`는 내부 정수를 `tde_get_algorithm_name()`으로 되돌려 사람이 읽고 재파싱 가능한 이름을 찍습니다(`:8060-8070`). REPLICATION만 이 대칭 처리가 빠져 있습니다.

- 문제 시나리오:
  1. `CREATE TABLE t (...) REPLICATION=ON`의 파스트리가 재출력(statement reconstruction — 예: `parser_print_tree`로 로그·에러 컨텍스트에 문장을 되찍거나, 파스트리 기반으로 DDL 텍스트를 다시 만드는 경로)되면 `... replication = 1`이 나옵니다.
  2. 이 텍스트를 다시 파서에 태우면 `opt_replication_option` 규칙은 `ON_`/`OFF_`/빈 값만 받으므로 `1`은 **문법 에러**로 거부됩니다. 즉 라운드트립(파싱→재출력→재파싱)이 깨집니다.
  3. 사람이 읽는 진단·로그에도 "replication = 1"이라는, 사용자가 적은 `REPLICATION=ON`과 다른 낯선 표기가 노출됩니다.

- 이미 병합된 지적과의 구분: K-50(SHOW CREATE/unload의 `=` 표기)·K-27·문제 7은 `object_printer.cpp`/`unload_schema.c`의 **별도 출력 경로**(직접 `", REPLICATION=ON/OFF"` 문자열)이고, 이 두 경로는 오히려 키워드를 바르게 찍습니다. 본 건은 **`parse_tree_cl.c`의 pt_print 재구성 경로**로 파일·원인·증상이 다릅니다(정수 미변환).

- 제안: `PT_TABLE_OPTION_ENCRYPT`처럼 REPLICATION 값을 전용 분기에서 `val->info.value.data_value.i ? "ON" : "OFF"`로 변환해 출력하도록 하십시오. 그러면 재파싱 가능한 대칭 표기가 됩니다.
