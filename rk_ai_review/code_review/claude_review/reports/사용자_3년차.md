- `CREATE TABLE`/`ALTER TABLE`을 흔히 쓰는 방식(여러 절을 콤마로 묶기, `LIKE`로 복제,

## 총평

이번 기능(테이블별 `REPLICATION` 옵션 + RK 제약)은 단일 절짜리 표준 시나리오
(`CREATE TABLE ... REPLICATION=OFF`, `ALTER TABLE ... DROP PRIMARY KEY` 하나만 있는 경우)는
검사 로직이 잘 짜여 있습니다. 문제는 실무에서 실제로 자주 나오는 **조합 상황**과
**에러가 난 다음 사용자가 뭘 해야 하는지**에서 발생합니다.

가장 심각한 것은 두 가지입니다. 첫째, 콤마로 여러 절을 묶은 `ALTER TABLE`에서 RK 재검사가
"맨 앞 절이 뭐였는지"에 따라 아예 실행되지 않을 수 있어, RK를 지우는 절이 앞에 오지 않으면
검사를 통째로 건너뜁니다. 둘째, `rkcheck` 유틸리티가 정작 자신이 찾아야 할 위반(참조 대상
테이블에 PK가 없는 FK 위반)을 로그로 남기려는 순간 널 포인터 역참조로 죽습니다 — 검사
도구가 검사 대상 상황에서 죽는 구조적 모순입니다. 두 건 모두 이번 동기화로도 전혀 손대지
않은 코드라 그대로 남아 있습니다.

그 외에도 에러 메시지가 발생 상황과 맞지 않거나(생성 시점 문구인데 ALTER에서도 뜸), 같은
메시지가 시키는 해결책이 다른 규칙과 충돌해서 실행 불가능하거나, 평범한 영단어
`replication`이 예약어가 되어 기존 컬럼/테이블명을 깨는 문제 등을 확인했습니다.

아래 문제들은 모두 본 리포(`/home/youngjun/Workspace/cubrid`, HEAD `734f4959d`)의 실제
코드를 Read/grep으로 재확인한 것입니다. 1차 리포트 작성 이후 이 코드 영역은 한 글자도

현재 줄 번호로 재확인·표기했습니다.

## 문제 1

**[심각도: 치명] 콤마로 여러 절을 묶은 ALTER TABLE에서 HA 복제키 재검사가 "맨 앞 절의 종류"에만 반응한다**

위치: `src/query/execute_schema.c:2051`(게이트), `:1854`(루프/절 코드 추출), `:109-114`(매크로)

로직 설명:
`do_alter()`는 `ALTER TABLE t 절1, 절2, ...` 문에서 절들을 연결 리스트로 받아
`for (crt_clause = alter; crt_clause != NULL; crt_clause = crt_clause->next)`로 순회합니다.
각 반복에서 지금 처리 중인 절의 종류는 지역변수 `const PT_ALTER_CODE alter_code =
crt_clause->info.alter.code;`(1854행)에 담겨 switch로 실행됩니다. 모든 절을 처리한 뒤
루프를 빠져나와 딱 한 번 `check_ha_repl_constraint()`로 "테이블에 RK가 남아있는지"를
재검사하는데(2059행 이하), 이 재검사를 할지 말지 정하는 게이트가 다음과 같습니다.

```c
if (!need_check_repl_constraint && IS_REPL_CONSTRAINT_RELATED_ALTER (alter->info.alter.code))
```

여기서 `alter`는 함수 인자로 받은 **리스트의 첫 번째 노드 자체**이고, 루프 안에서 한 번도
재대입되지 않습니다. 즉 `alter->info.alter.code`는 루프가 몇 바퀴를 돌든 항상 **첫 번째
절의 종류**를 가리킵니다. 정작 지금 처리 중인 절의 종류는 같은 줄 위에서 이미 뽑아 놓은
지역변수 `alter_code`(=`crt_clause->info.alter.code`)인데, 게이트는 그걸 안 쓰고
`alter->info.alter.code`를 씁니다. 매크로 자체(`IS_REPL_CONSTRAINT_RELATED_ALTER`)가 다루는
절 목록(`PT_ADD_ATTR_MTHD`, `PT_DROP_ATTR_MTHD`, `PT_DROP_CONSTRAINT`,
`PT_DROP_PRIMARY_CLAUSE`)에 `PT_CHANGE_ATTR`(MODIFY/CHANGE COLUMN)이 빠져 있다는 점은
스펙 필터링에서 이미 C-9로 확정됐지만, 이 버그는 그보다 더 근본적입니다 — 목록에 있는
절이라도 **맨 앞이 아니면 검사 자체가 걸리지 않습니다.**

문제 시나리오:
HA 모드에서 RK가 `NOT NULL UNIQUE` 하나뿐인 테이블 `orders`에 대해 실무에서 흔히 쓰는
"코멘트/컬럼 정리와 제약 정리를 한 문장에 같이 넣는" 패턴을 실행합니다.

```sql
ALTER TABLE orders COMMENT='2026 정리', DROP CONSTRAINT u_orders_no;
```

- 첫 절은 `PT_CHANGE_TABLE_COMMENT`로 매크로 목록에 없습니다. `alter->info.alter.code`는
  이 값으로 고정되므로, 두 번째 절(`DROP CONSTRAINT`, 매크로에 있음)이 실제로 그 테이블의
  유일한 RK를 지웠는데도 `need_check_repl_constraint`는 끝까지 `false`로 남습니다.
- 결과: `ALTER TABLE`이 아무 에러 없이 성공하고, `orders`는 `REPLICATION=ON`인데 RK가 없는
  상태가 됩니다. 이는 이 기능 전체가 막으려던 바로 그 상태(PR #6477 "HA 모드에서 RK 없는
  복제 테이블 금지")입니다. 이후 이 테이블에 대한 INSERT/UPDATE/DELETE는 슬레이브로 정상
  복제되지 않거나 applylogdb 쪽에서 조용히 스킵됩니다.
- 절 순서를 바꾸기만 해도(`DROP CONSTRAINT ..., COMMENT=...`) 우연히 검사가 걸리므로,
  똑같은 의도의 문장인데 절 순서에 따라 결과가 달라지는 재현이 까다로운 버그입니다.

제안: 게이트를 `alter->info.alter.code`가 아니라 현재 절의 지역변수 `alter_code`로
바꿔야 합니다. 그래야 리스트 전체를 도는 동안 매크로에 걸리는 절이 한 번이라도 나오면
플래그가 켜집니다. 여기에 C-9(매크로에 `PT_CHANGE_ATTR` 누락)도 함께 고쳐야 MODIFY/CHANGE
COLUMN으로 NOT NULL을 해제하는 경로까지 막힙니다.

## 문제 2

**[심각도: 치명] rkcheck가 FK 위반을 로그에 남기려는 순간 참조 테이블에 PK가 없으면 널 포인터 역참조로 죽는다**

위치: `src/query/execute_schema.c:9818-9839`(`log_ha_repl_fk_ref_all_replicated`, 특히
:9837-9839), 호출부 `src/executables/util_cs.c:2911`(`check_fk_constraint`) →
`rkcheck()`(`util_cs.c:3267` 이하)

로직 설명:
`cub_admin rkcheck -f`(또는 `cubrid hb start`가 내부적으로 호출)는 FK 위반을 찾을 때
클래스별로 `check_fk_constraint()` → `log_ha_repl_fk_ref_all_replicated()`를 호출합니다.
이 함수는 대상 클래스의 FK 제약을 순회하며 참조 대상 테이블(`ref_class_mop`)이 복제
클래스가 아니면(즉 `REPLICATION=OFF`이면) 위반으로 기록합니다.

```c
if (!sm_is_replication_class (ref_class_mop))
  {
    DB_CONSTRAINT *pk_c = db_constraint_find_primary_key (db_get_constraints (ref_class_mop));
    fprintf (fp, "%s(%s) -> %s(%s)\n", sm_get_ch_name (class_obj), tmp_c->name,
             sm_get_ch_name (ref_class_mop), pk_c->name);
    ret++;
  }
```

`db_constraint_find_primary_key()`는 자체 문서 주석에 "PK가 없으면 NULL을 반환한다"고
명시돼 있습니다(`src/compat/db_info.c:1998-2003`). 그런데 이 반환값을 NULL 체크 없이 바로
`pk_c->name`으로 역참조합니다.

문제 시나리오:
`REPLICATION=OFF`인 테이블은 애초에 RK(PK/NOT NULL UNIQUE)가 있을 필요가 없습니다
(이 기능의 규칙 자체가 그렇습니다). 그래서 코드성 참조 테이블처럼 "PK 없이 UNIQUE만 있거나
제약이 전혀 없는 `REPLICATION=OFF` 테이블"은 실무에서 아주 흔한 설계입니다. 이런 테이블을
FK로 참조하는 `REPLICATION=ON` 테이블이 하나라도 있으면:

1. `cub_admin rkcheck db_name -f`를 실행 (또는 `cubrid hb start`가 사전 점검으로 자동 실행)
2. 위반을 실제로 찾아서 로그에 적으려는 순간 `pk_c`가 NULL이라 `pk_c->name`에서 세그폴트
3. HA를 켜려던 DBA/운영자는 "위반 몇 건"이라는 정상적인 리포트 대신 rkcheck 자체의
   크래시를 만나고, `.list` 파일도 불완전하게 남습니다. `cubrid hb start`가 이 크래시로
   막히면 정상적인 위반 안내(`ER_HA_REPLICATION_CONSTRAINT_VIOLATION`, `-1378`) 대신
   원인을 알 수 없는 실패가 됩니다.

이 유틸리티는 PR #6658에서 코멘트 50개 이상, 리뷰 6주가 걸린 곳인데도 "검사 도구가 검사
대상 상황 자체에서 죽는" 이 경로는 리뷰에서 걸러지지 않았습니다.

제안: `pk_c == NULL`인 경우(참조 테이블이 PK 없이 NOT NULL UNIQUE만 가지거나 RK가 전혀 없는
경우)를 별도로 처리해 `pk_c->name` 대신 대체 문구("PK 없음"이나 실제 RK 제약명 조회)를
출력하도록 고쳐야 합니다.

## 문제 3

**[중요] `CREATE TABLE ... LIKE ...`에서 명시적으로 붙인 REPLICATION 옵션이 아무 경고 없이 무시된다**

위치: `src/query/execute_schema.c:10258-10264`

로직 설명:

```c
if (create_like)
  {
    is_replication_on = !(source_class->flags & SM_CLASSFLAG_DATA_REPLICATION_OFF);
  }
else
  {
    is_replication_on = IS_CREATE_STMT_SET_REPL_OPTION (tbl_opt_replication);
  }
```

`create_like` 분기에서는 사용자가 `CREATE TABLE ... LIKE ...` 문에 `tbl_opt_replication`을
직접 적었는지 여부를 아예 확인하지 않고, 무조건 원본 테이블(`source_class`)의 플래그를
그대로 씁니다. `semantic_check.c`에도, `do_create_entity()` 어디에도 "LIKE와 REPLICATION을
동시에 쓰면 에러"라는 검사는 없습니다(grep으로 `create_like`와 `REPLICATION` 관련 전수
확인, 해당 에러 검사 없음).

문제 시나리오: PR #6943 리뷰 논점(`pr_히스토리.md`)에는 "REPLICATION 옵션과 LIKE를 동시에
명시하면 에러라는 규칙이 PR 본문에서 확정됐다"고 적혀 있는데, 실제 코드에는 그 규칙이
구현되어 있지 않습니다. 사용자가

```sql
CREATE TABLE t_copy LIKE t_orig REPLICATION=OFF;
```

를 실행하면 파서는 이 옵션을 정상적으로 받아들이고, `pt_check_create_entity()`의 중복
검사도 통과하지만, 실제로는 `t_orig`가 `REPLICATION=ON`이면 `REPLICATION=OFF`라고 명시한
`t_copy`가 조용히 `ON`으로 만들어집니다. 에러도, 경고도 없습니다. `SHOW CREATE TABLE
t_copy`를 쳐 보기 전까지는 사용자가 자기가 명시한 옵션이 무시됐다는 걸 알 방법이 없습니다.

제안: `create_like`가 참이면서 `tbl_opt_replication != NULL`인 경우를 검사해 명확한 에러
(또는 최소한 WARNING)를 내야 합니다. PR 본문에서 이미 합의된 규칙이므로 문서-코드 괴리를
없애는 게 맞습니다.

## 문제 4

**[중요] RK 판정 기준이 DDL 시점과 런타임 시점에서 서로 달라, CREATE는 성공하지만 실제 복제에는 그 키가 쓰이지 않을 수 있다**

위치: `src/object/class_object.c:95-98`(`IS_HA_REPLICATION_KEY_CONSTRAINT` 매크로),
`src/object/schema_manager.c:16115-16130`(`sm_has_non_null_attribute`, "하나라도" NOT NULL),
대조: `src/base/object_representation_sr.c:4685-4720`(`or_is_replication_candidate_key`,
전체 컬럼 NOT NULL을 for 루프로 검사), 사용처 `src/storage/btree.c:8264-8307`
(`btree_get_rkey_btid`)

로직 설명:
CREATE/ALTER 시점에 "이 테이블에 RK가 있는가"를 판단하는 `classobj_has_class_repl_key_constraint()`
(`class_object.c:2285` 부근)는 `IS_HA_REPLICATION_KEY_CONSTRAINT` 매크로를 씁니다.

```c
#define IS_HA_REPLICATION_KEY_CONSTRAINT(c) \
  ((c)->type == SM_CONSTRAINT_PRIMARY_KEY || \
    (SM_IS_CONSTRAINT_UNIQUE_FAMILY((c)->type) && \
     sm_has_non_null_attribute((c)->attributes)))
```

`sm_has_non_null_attribute()`는 함수 주석에 명시된 대로 "구성 컬럼 중 **하나라도**
NOT NULL이면 1"을 반환하는, 원래 다른 용도로 쓰이던 기존 함수입니다(diff에 새로 추가된
함수가 아니라 이 매크로가 새로 갖다 쓴 것). 즉 `UNIQUE(col_a, col_b)`에서 `col_a`만
NOT NULL이고 `col_b`가 NULL 허용이어도 이 매크로는 "RK 있음"으로 판단합니다.

반면 실제 복제 시점에 RK btid를 고르는 `btree_get_rkey_btid()`(마스터/슬레이브 양쪽에서
카탈로그를 재계산할 때 쓰임, `btree.c:8264`)는 `or_is_replication_candidate_key()`를
쓰는데, 이 함수는 UNIQUE 인덱스의 **모든** 구성 컬럼이 NOT NULL인지 for 루프로 확인합니다.
하나라도 NULL 허용이면 그 인덱스는 후보에서 제외됩니다. 후보가 하나도 없으면
`btree_get_rkey_btid()`는 에러 없이 `rkey_btid`를 NULL로 둔 채 조용히 리턴합니다.

문제 시나리오:
```sql
CREATE TABLE t (a INT NOT NULL, b INT, UNIQUE(a, b)) REPLICATION=ON;  -- HA 모드
```
- CREATE 시점: `check_ha_repl_constraint()` → `classobj_has_class_repl_key_constraint()`가
  "`a`가 NOT NULL이니 RK 있음"으로 판단해 **정상적으로 성공**합니다.
- 실제 복제 시점: 마스터/슬레이브가 `btree_get_rkey_btid()`로 RK를 다시 계산하는데, 이
  UNIQUE(a,b)는 `b`가 NULL 허용이라 후보에서 탈락하고, 다른 RK가 없으므로 RK btid가
  NULL이 됩니다. 결과적으로 이 테이블은 "RK가 있다고 승인받아 만들어졌지만 실제로는
  RK 없이 동작하는" 상태가 됩니다.
- 사용자 입장에서는 `CREATE TABLE`이 성공했으니 RK가 있다고 믿지만, 실제 복제 동작은
  RK가 없는 테이블과 동일하게 흘러갑니다. 이 간극을 알아챌 방법이 사용자 화면에는
  전혀 없습니다(`SHOW CREATE TABLE`도 `REPLICATION=ON`만 보여줄 뿐 RK가 뭔지는 안
  보여줍니다 — 이건 스펙 필터링 C-3으로 이미 확정된 별도 갭).

제안: 두 판정 기준을 하나로 통일해야 합니다. `IS_HA_REPLICATION_KEY_CONSTRAINT` 매크로도
`or_is_replication_candidate_key()`처럼 "제약을 구성하는 모든 컬럼이 NOT NULL"인지 확인하도록
고쳐야, CREATE 시점에 승인된 RK가 런타임에도 실제로 쓰입니다.

## 문제 7

**[중요] `REPLICATION`이 비예약어(identifier) 허용 목록에서 빠져 완전한 예약어가 됐다 — 기존 컬럼/테이블명을 깬다**

로직 설명: `csql_lexer.l`은 `replication`(대소문자 무관)을 무조건 `REPLICATION` 토큰으로
반환합니다. CUBRID 문법에서 `CREATE TABLE`/`COMMENT`/`ENCRYPT` 등 다른 테이블 옵션

(예: 복제 상태를 기록하는 애플리케이션 테이블 `replication_log`가 아니라 정확히

제안: `REPLICATION`을 비예약 identifier 목록에 추가해 다른 테이블 옵션 키워드들과 같은
수준의 하위 호환성을 유지해야 합니다.

이 함수만 실패와 "정상적으로 OFF임"을 구분하지 못합니다.

제안: 조회 실패를 `assert(false)`로 다루지 말고 별도 out-parameter나 에러 코드로 호출자에
알려, `SHOW CREATE TABLE`/unloaddb가 실패를 "OFF"로 오인해 출력하지 않게 해야 합니다.

## 문제 13

**[사소] 신규 `RKCHECK` 메시지 카탈로그 항목이 파일 끝에 개행 없이 끝난다**

위치: `msg/en_US.utf8/utils.msg`, `msg/ko_KR.utf8/utils.msg` 파일 말미(`MSGCAT_UTIL_SET_RKCHECK`
섹션 뒤)

로직 설명: 두 파일 모두 새로 추가된 rkcheck 사용법 메시지 뒤에 공백 줄과 함께
파일이 개행 없이 끝납니다(`git diff`에서 "`\ No newline at end of file`"로 표시,
`tail -c`/`xxd`로 직접 재확인). 메시지 카탈로그 컴파일 도구(`gencat`/`msgfmt` 계열)에
따라 파일 끝 개행 누락이 마지막 항목 파싱에 영향을 줄 수 있습니다.

문제 시나리오: 실제로 `rkcheck --help` 출력이 깨지는지는 정적 분석만으로는 확정할 수
없어(런타임 검증 필요) 사소로 분류했지만, 다른 언어 카탈로그 파일들이 개행으로 끝나는
관례와 다르므로 빌드 스크립트/린트에서 걸릴 여지가 있습니다.

제안: 두 `utils.msg` 파일 말미에 개행을 추가해 기존 파일들과 형식을 통일해야 합니다.

## 조사 종료 선언

**재검증**: 1차 리포트의 문제 1~14를 새 HEAD(`734f4959d`)에서 파일을 다시 열어 한 줄 한 줄
대조했습니다. `git diff 44468ed73..734f4959d --stat`로 확인한 결과, 1차 리뷰 이후 실제로
바뀐 파일은 `src/storage/heap_file.c`, `src/storage/heap_file.h`,
`src/transaction/locator_sr.c` 3개뿐이며, 그 내용은 구 문제 3(`heap_is_replication_class`
KILL QUERY 무시 회귀)이 지적했던 지점을 `heap_get_class_repl_on` 전환으로 근본 수정한
것입니다. 이 3개 파일 외의 모든 코드는 1차 리뷰 시점과 완전히 동일했으므로, 구 문제 3이
해소된 것을 제외한 나머지 13건은 전부 코드 변경 없이 "유지"로 재확인됐습니다. 이 과정에서
새롭게 오판으로 드러나 폐기한 문제는 없습니다.

**신규 발굴**: 동기화 델타 자체(#7678/`3b6ebd1a9`, #7697/`9e094324b`)를 별도로 diff해
검토했습니다. `3b6ebd1a9`는 커밋 메시지상 "(#6908) (#7678)"로 표기된 대로, 실제로는
1차 리뷰 시점에 이미 병합돼 있던 `44468ed73`(#6908)와 내용이 완전히 동일한 커밋이
동기화 과정에서 별도 해시로 재적용된 것입니다(`git diff 44468ed73..3b6ebd1a9`가
비어 있지 않은 이유는 병합 베이스가 그보다 앞선 `d603a6989`이기 때문이며, `44468ed73`
자체와는 실질적으로 동일 내용). 따라서 이 커밋은 사용자 관점에서 "새 코드"가 아니라
1차 리뷰 때 이미 검토한 `is_data_repl_log_enabled`/`spec_has_replication_class` 계열
SBR 판정 로직 그대로입니다. `9e094324b`(#7697)는 앞서 말한 대로 구 문제 3을 해소한
영역입니다. 즉 이번 2차 재리뷰의 실제 diff 범위(`b646647ec...HEAD`, 35파일)
안에서 "1차 리뷰 이후 새로 생기고 아직 다루지 않은" 코드는 존재하지 않았습니다.

이 시점에서 2차 재리뷰를 종료합니다. 억지로 신규 문제를 만들어내지 않았습니다.
