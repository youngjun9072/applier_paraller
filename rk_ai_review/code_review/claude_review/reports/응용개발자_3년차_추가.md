# RK/REPLICATION 코드 리뷰 — 응용개발자 3년차 관점 (3차 전수 재수색)

> **3차 전수 재수색(기준 734f4959d)** — 기존 리포트(`응용개발자_3년차.md`)의 유지 12건과
> 병합된 67건(dedup_existing.json)을 모두 참조해, **아직 아무도 다루지 않은 파일/함수부터**
> 전체 diff(35파일)를 다시 훑었습니다. 문제 번호는 기존 리포트(1~13, 문제 6 결번)에 이어
> **14번부터** 붙입니다. 근거 없는 지적으로 쿼터를 채우지 않았고, 새로 세운 것은 아래 2건입니다.
>
> - 잔여 쿼터 = 50 − 12 = 38. 그러나 이 diff는 병합 67건 + 유지 12건 = 79건으로 이미
>   대부분의 코드 경로가 커버되어 있어, **근거가 서는 신규는 2건**에 그쳤습니다.

## 문제 14

**[심각도: 보통] CREATE TABLE의 REPLICATION 옵션을 파스트리에서 재출력할 때 `ON/OFF`가 아니라 정수 `1/0`으로 찍혀 재파싱 불가능한 DDL이 된다** *(신규)*

위치: `src/parser/parse_tree_cl.c:8041-8043`(`pt_print_table_option`의 REPLICATION 케이스),
값 출력부 `:8071-8075`(default `else` 분기 `pt_print_bytes_l`)

로직 설명 (콜체인):
`CREATE TABLE ... REPLICATION=ON`은 파서에서 `class_replication_spec`
(`csql_grammar.y:19891`)을 타고, 옵션 값을 **PT_VALUE 정수**(ON=1, OFF=0;
`opt_replication_option`, `csql_grammar.y:19987-19998`)로 저장합니다. 그런데 파스트리를
다시 SQL 텍스트로 되돌리는 `pt_print_table_option()`은 REPLICATION 케이스에서
`"replication = "` 접두어만 붙이고(8042행), 값은 공통 `else` 분기(8073행)에서
`pt_print_bytes_l(parser, val)`로 **정수를 그대로** 출력합니다. 결과는 `replication = 1`
/`replication = 0`입니다.

문제는 문법 규칙 `opt_replication_option`이 **`ON_`/`OFF_`/생략만** 받고 정수 리터럴은
받지 않는다는 점입니다(`csql_grammar.y:19987-19998`에서 확인). 따라서 재출력된
`replication = 1`을 다시 파싱하면 **문법 에러**가 납니다.

바로 옆의 ENCRYPT 옵션은 같은 함정을 피하려고 정수를 알고리즘 이름으로 되돌립니다
(8060-8069행, `tde_get_algorithm_name`). REPLICATION만 이 변환을 빠뜨려 raw 정수를 출력합니다
— **동일 기능 영역에서 형제 옵션(ENCRYPT)은 처리했는데 REPLICATION은 누락한** 전형적 불일치입니다.
(참고로 `SHOW CREATE TABLE`(`object_printer.cpp`)과 unloaddb(`unload_schema.c`)는 별도 경로라
`REPLICATION=ON`으로 올바르게 찍으며, 이 둘은 재파싱됩니다 — 즉 세 출력 경로 중
`pt_print_table_option`만 깨져 있습니다.)

문제 시나리오:
파스트리를 텍스트로 재구성하는 클라이언트측 경로(문장 에코/트레이스, 파스트리 기반 DDL
재조립을 하는 스키마 툴링)에서 `CREATE TABLE t(a INT PRIMARY KEY) REPLICATION=ON`이
`create table t(...) replication = 1`로 나오고, 이 텍스트를 그대로 다시 실행하면 문법 에러로
실패합니다. 마이그레이션 도구가 "파스→재출력→재적용" 사이클을 돌리는 경우가 여기 걸립니다.

DDL의 HA 스키마 복제 경로(`do_replicate_statement`, `execute_statement.c:16519`)는
파스트리 재출력이 아니라 **원문 `sql_user_text`**를 실어 나르므로(엔티티 이름만 `pt_print_bytes`
사용) 슬레이브 복제 자체는 깨지지 않습니다 — 그래서 치명이 아니라 보통으로 봅니다.

제안: ENCRYPT처럼 REPLICATION 값도 정수를 `"ON"`/`"OFF"` 문자열로 변환해 출력하는 전용
분기를 `pt_print_table_option`에 추가.

## 문제 15

**[심각도: 사소] ALTER TABLE ... REPLICATION 절이 pt_print_alter_one_clause의 switch에 없어, 파스트리 재출력 시 해당 절이 통째로 사라진다** *(신규)*

위치: `src/parser/parse_tree_cl.c:5784-5811`(`pt_print_alter_one_clause`의 alter code switch)

로직 설명 (콜체인):
`ALTER TABLE ... REPLICATION=OFF`는 파서에서 `alter.code = PT_CHANGE_REPLICATION`,
값은 `alter_clause.replication.tbl_replication`(PT_VALUE)로 저장됩니다
(`csql_grammar.y:5862-5871`, `parse_tree.h:1299,1888-1891`). ALTER 문을 텍스트로 되돌리는
`pt_print_alter_one_clause()`의 code switch에는 `PT_CHANGE_TABLE_COMMENT`(5793행)와
`PT_CHANGE_COLLATION`(5798행) 케이스는 있지만 **`PT_CHANGE_REPLICATION` 케이스가 없습니다**.
따라서 이 코드는 `default: break`(5786행)로 빠져, REPLICATION 절이 재출력 결과에서
**아무 것도 남기지 않고 사라집니다**.

이 기능의 같은 영역이 CREATE 옵션 재출력(문제 14의 `pt_print_table_option`)은 케이스를
추가했으면서 ALTER 재출력은 빠뜨렸고, 형제 절(COMMENT/COLLATION)은 재출력을 지원하는
것과도 대비됩니다.

문제 시나리오:
`ALTER ... REPLICATION`은 비HA 모드에서만 허용되므로(do_alter_change_replication이
HA 모드에서 -1376으로 거부, `execute_schema.c:11740`) HA 복제를 깨뜨리지는 않습니다.
그러나 비HA에서 파스트리를 재출력하는 트레이스/에코/DDL 재조립 툴링은 이 ALTER 문을
"클래스명만 있고 본문이 비어 있는" 형태로 잘못 재구성합니다. 실제 재현 경로가 좁아 사소로 둡니다.

제안: `pt_print_alter_one_clause`에 `case PT_CHANGE_REPLICATION`을 추가해
`" replication = ON|OFF"`를 출력. (`alter_clause.replication.tbl_replication`의 정수를
문제 14와 동일하게 ON/OFF로 변환.)
