# RK/REPLICATION 코드 리뷰 — 응용개발자 1년차 관점

> **2차 재리뷰(기준 `734f4959d`)** — 1차 리포트(기준 `44468ed73`) 이후 fork가 upstream과 동기화되어(#7678 `3b6ebd1a9`, #7697 `9e094324b` 머지) 기준이 `734f4959d`로 바뀌었습니다. 1차 문제들을 새 HEAD에서 재검증하고, 동기화 델타와 전체 diff에서 새 문제를 추가 발굴했습니다.
>
> 재검증 방법은 1차와 동일합니다(LSP/정의·참조 추적으로 로직을 따라감, 키워드 grep 단독 판단 금지, 억지 지적 금지).

## 페르소나 소개

저는 자바/파이썬으로 업무 애플리케이션을 만드는 1년차 개발자입니다. DB는 "쓰는" 쪽이지 엔진을 짜 본 적은 없습니다. 제가 이 코드에서 신경 쓰는 것은 두 가지입니다.

1. **DDL 조합 시나리오** — 저는 마이그레이션 도구(Liquibase/Flyway 같은)나 ORM이 자동 생성한 DDL을 그대로 흘려보냅니다. `CREATE TABLE ... LIKE`, `CREATE TABLE AS SELECT`, `RENAME`, 파티션, 한 문장에 여러 절을 붙인 멀티 `ALTER TABLE`, 그리고 트랜잭션 중간에 하나가 실패하는 상황 — 이런 "정상 경로가 아닌" DDL 순서에서 로직에 구멍이 없는지 봅니다.
2. **처음 읽는 눈** — 저는 이 코드베이스를 처음 봅니다. 그래서 오히려 오타·복붙 흔적·잘못된 변수·주석과 코드가 어긋나는 곳·이름이 실제 동작과 다른 함수가 눈에 띕니다. 엔진 개발자에게는 "당연"해서 안 보이는 것들입니다.

## 총평 (2차)

동기화로 들어온 #7697이 1차 리포트의 **치명 문제(에러를 `false`로 삼켜 KILL QUERY가 무시되던 결함)를 근본 수정**했습니다(bool 반환 함수를 에러코드 반환 + out-parameter 구조로 재설계). 이 계열 지적은 재리뷰 대상에서 제외되어 본 리포트에서 빠졌습니다.

남은 그림은 1차와 크게 다르지 않습니다. 여전히 **"같은 개념(무엇이 복제 키인가, 무엇이 복제 대상 클래스인가)을 여러 곳에서 각자 다시 판정하는" 구조**가 곳곳에 있고, 그 판정 규칙이 미묘하게 어긋납니다. 특히:

- **복제 키를 "무엇으로 볼지"가 클라이언트(스키마 검증)와 서버(런타임 복제) 사이에서 다릅니다.** "생성은 됐는데 복제가 안 되는" 형태로 조용히 터집니다. (문제 2 — 유지)
- **멀티 `ALTER TABLE`에서 재검사 트리거가 첫 번째 절만 봅니다.** 마이그레이션 도구가 흔히 만드는 "한 문장에 여러 절" DDL이 검사를 우회합니다. (문제 3 — 유지)
- **파티션 승격 시 컬럼 속성 보존 로직에 새로운 구멍**을 찾았습니다. NOT NULL UNIQUE가 둘 이상이면 두 번째 이후의 UNIQUE 속성 플래그가 조용히 벗겨집니다. (문제 17 — 신규)

아래는 심각도 순으로 정리한 문제 목록입니다. 1차 번호를 유지하고(제외된 문제 번호는 결번), 신규 문제는 이어서 번호를 붙였습니다. 각 항목은 코드가 실제로 무엇을 하는지 따라간 뒤 적었습니다.

## 문제 2 (유지)

**[심각도: 중요] 복제 키(RK) 판정 규칙이 클라이언트(스키마 검증)와 서버(런타임 복제)에서 서로 다름 — "생성은 됐는데 복제가 안 되는" 표면**

- 위치: `src/object/class_object.c:95-98` (`IS_HA_REPLICATION_KEY_CONSTRAINT` → `sm_has_non_null_attribute`), `src/object/schema_manager.c:16115` (`sm_has_non_null_attribute`), `src/base/object_representation_sr.c:4694` (`or_is_replication_candidate_key`)

로직 설명: 복제 키가 될 수 있는 UNIQUE인지 판정하는 코드가 두 곳에 있는데 기준이 다릅니다.

- **클라이언트 쪽**(CREATE/ALTER 검증, rkcheck): `IS_HA_REPLICATION_KEY_CONSTRAINT`는 `SM_IS_CONSTRAINT_UNIQUE_FAMILY && sm_has_non_null_attribute((c)->attributes)`로 판정합니다. `sm_has_non_null_attribute()`(schema_manager.c:16115)는 주석 그대로 **"구성 컬럼 중 하나라도 NOT NULL이면 1"**을 반환합니다(루프에서 `SM_ATTFLAG_NON_NULL` 하나라도 걸리면 즉시 `return 1`).
- **서버 쪽**(런타임 복제 키 선택): `or_is_replication_candidate_key()`(object_representation_sr.c:4694)는 UNIQUE에 대해 `for` 루프로 **모든** 키 컬럼이 `attr->is_notnull`인지 확인하고, 하나라도 아니면 `false`를 반환합니다. (콜체인: `btree_get_rkey_btid`(btree.c) → `locator_repl_prepare_force`)

문제 시나리오: `CREATE TABLE t (a INT NOT NULL, b INT, CONSTRAINT uk UNIQUE(a, b)) REPLICATION=ON;`처럼 **일부만 NOT NULL인 복합 UNIQUE**를 만들면, 클라이언트 검증 `check_ha_repl_constraint()`는 "RK 있음"으로 통과시키고 HA 기동 시 `rkcheck`도 통과시킵니다. 그런데 실제 복제가 일어날 때 서버의 `btree_get_rkey_btid()`는 "모든 컬럼 NOT NULL" 기준을 못 만족하는 이 UNIQUE를 RK 후보로 인정하지 않아 **RK를 못 찾습니다.** 사용자 입장에서는 "생성도 되고 HA도 떴는데 이 테이블만 복제가 안 되는" 원인 불명 상황이 됩니다.

제안: 두 판정을 하나의 함수/규칙으로 통일해야 합니다. 스펙상 "NOT NULL UNIQUE"가 RK 후보이므로, 클라이언트 쪽도 서버와 동일하게 **구성 컬럼 전부 NOT NULL**을 요구해야 합니다(`sm_has_non_null_attribute`를 "전부 NOT NULL" 검사로 교체하거나 별도 함수 사용).

## 문제 3 (유지)

**[심각도: 중요] 멀티 `ALTER TABLE`의 RK 재검사 게이트가 첫 번째 절(`alter->info.alter.code`)만 검사 — 후순위 절의 RK 삭제가 검사를 우회**

- 위치: `src/query/execute_schema.c:2051`

로직 설명: `do_alter()`는 `for (crt_clause = alter; ...; crt_clause = crt_clause->next)` 루프로 각 절을 처리하고, 루프 안에서 각 절의 코드는 `alter_code`(= `crt_clause->info.alter.code`)로 읽어 switch합니다(예: RENAME 절은 `crt_clause`로 처리, 2005행). 그런데 루프 안에서 RK 재검사를 켤지 정하는 게이트(2051행)는 다음과 같습니다.

```c
if (!need_check_repl_constraint && IS_REPL_CONSTRAINT_RELATED_ALTER (alter->info.alter.code))
  {
    need_check_repl_constraint = true;
  }
```

여기서 `alter->info.alter.code`는 **첫 번째 절(리스트 헤드)의 코드**입니다. 루프 변수 `crt_clause`(또는 `alter_code`)가 아니라 헤드 노드 `alter`를 참조하고 있어서, 매 반복 게이트는 오로지 첫 절만 봅니다. (루프 종료 뒤 2059행에서 `if (need_check_repl_constraint)`로 실제 검사)

문제 시나리오: 마이그레이션 도구가 흔히 뽑는 `ALTER TABLE tbl CHANGE COLUMN a a INT COMMENT 'x', DROP CONSTRAINT rk_uk;`를 생각해 봅시다. 첫 절은 `PT_CHANGE_ATTR`(게이트 목록에 없음), 두 번째 절이 `PT_DROP_CONSTRAINT`(RK를 삭제하는, 목록에 있는 코드)입니다. 게이트는 첫 절 코드만 보므로 `need_check_repl_constraint`가 `false`로 남고, **복제 키를 삭제했는데도 `check_ha_repl_constraint()`가 호출되지 않습니다.** HA 모드에서 RK 없는 복제 테이블이 조용히 만들어져, 이후 복제가 깨집니다. 반대로 첫 절이 목록에 있으면 뒤에 무관한 절만 있어도 불필요하게 검사가 돕니다.

제안: 게이트를 루프 안에서 각 절 기준으로 평가해야 합니다. 즉 `IS_REPL_CONSTRAINT_RELATED_ALTER(alter_code)`(현재 절)로 바꾸십시오. 전형적인 "헤드 노드와 순회 노드를 혼동한" 실수입니다.

## 문제 4 (유지)

**[심각도: 중요] RK 재검사 트리거 목록에 `PT_CHANGE_ATTR`/`PT_MODIFY_ATTR_MTHD` 누락 — MODIFY로 NOT NULL을 풀면 RK 자격이 조용히 사라짐**

- 위치: `src/query/execute_schema.c:109-114` (`IS_REPL_CONSTRAINT_RELATED_ALTER` 매크로)

로직 설명: RK 재검사를 트리거하는 ALTER 코드 목록은 다음 넷뿐입니다.

```c
#define IS_REPL_CONSTRAINT_RELATED_ALTER(code)              \
  ( ((code) == PT_ADD_ATTR_MTHD)         ||                 \
    ((code) == PT_DROP_ATTR_MTHD)        ||                 \
    ((code) == PT_DROP_CONSTRAINT)       ||                 \
    ((code) == PT_DROP_PRIMARY_CLAUSE)                     \
  )
```

그런데 `do_alter()`의 switch에는 `PT_CHANGE_ATTR`, `PT_MODIFY_ATTR_MTHD` 같은 컬럼 속성 변경 코드가 엄연히 존재합니다. 이들은 목록에 없습니다.

문제 시나리오: 어떤 테이블의 복제 키가 `b INT NOT NULL UNIQUE`(즉 NOT NULL UNIQUE가 유일한 RK)라고 합시다. 사용자가 `ALTER TABLE tbl MODIFY b INT;`로 NOT NULL을 풀면, `b`는 더 이상 RK 후보가 아니게 됩니다(UNIQUE지만 NOT NULL이 아니므로). 하지만 이 코드는 `PT_CHANGE_ATTR`/`PT_MODIFY_ATTR_MTHD`이라 재검사 게이트에 걸리지 않아, **RK를 잃은 복제 테이블이 검사 없이 통과**합니다. `DROP INDEX`(`PT_DROP_INDEX_CLAUSE`)도 목록에 없어, RK가 인덱스 형태로 제거될 수 있는 경우 동일한 구멍이 있는지 확인이 필요합니다.

제안: 컬럼 속성을 바꾸는 코드(`PT_CHANGE_ATTR`, `PT_MODIFY_ATTR_MTHD`)와 `PT_DROP_INDEX_CLAUSE`를 목록에 추가하십시오.

## 문제 5 (유지)

**[심각도: 중요] `rkcheck`가 위반 목록 파일 열기에 실패(`fp == NULL`)해도 NULL 검사 없이 `fprintf` → 크래시**

- 위치: `src/executables/util_cs.c:3320` (`fp` 대입), `:3332` 등에서 사용

로직 설명: `rkcheck()`는 서버 접속 성공 후 위반 목록 파일을 엽니다.

```c
fp = open_violation_list_file (database_name, arg->command_name, violation_list_file, PATH_MAX);

classes = db_get_all_classes ();
...
PRINT_SECTION_TITLE (fp, RK_CONSTRAINT_VIOLATIONS_SECTION_TITLE);   // fprintf(fp, ...)
```

`open_violation_list_file()`(util_cs.c:2856)는 내부에서 `fopen(...,"w")` 결과를 그대로 반환하는데, `rkcheck()`는 **반환값이 NULL인지 검사하지 않고** 곧바로 `PRINT_SECTION_TITLE`/`PRINT_MESSAGE`(모두 `fprintf(fp, ...)` 매크로, 92행)로 사용합니다. `classes == NULL`은 방어하지만 `fp == NULL`은 방어하지 않습니다.

문제 시나리오: 로그 디렉토리에 쓰기 권한이 없거나, 디스크가 꽉 찼거나, 경로가 없으면 `fopen`이 NULL을 반환합니다. 이 `rkcheck`는 `cubrid hb start` 시 자동 호출되므로(util_service.c), 운영 중 흔한 "로그 디렉토리 문제" 하나로 **HA 기동 절차가 깔끔한 에러 대신 세그폴트로 죽습니다.** 신입 입장에서 "왜 hb start가 코어를 남기지?"의 원인을 찾기 매우 어렵습니다.

제안: `fp` 대입 직후 NULL 검사를 넣고, 실패 시 에러 메시지와 함께 정상 종료(또는 stdout으로만 출력)하도록 하십시오.

## 문제 6 (유지)

**[심각도: 보통] `log_ha_repl_fk_ref_all_replicated()`가 PK 조회 결과(NULL 가능)를 무검사로 역참조**

- 위치: `src/query/execute_schema.c:9837-9839`

로직 설명: FK 위반을 파일로 찍는 함수에서, 참조 대상 클래스의 PK를 찾아 그 이름을 출력합니다.

```c
DB_CONSTRAINT *pk_c = db_constraint_find_primary_key (db_get_constraints (ref_class_mop));
fprintf (fp, "%s(%s) -> %s(%s)\n", sm_get_ch_name (class_obj), tmp_c->name,
         sm_get_ch_name (ref_class_mop), pk_c->name);
```

`db_constraint_find_primary_key()`는 PK가 없으면 **NULL을 반환**합니다. 그런데 `pk_c->name`을 NULL 검사 없이 바로 씁니다. (`ref_class_mop = ws_mop(...)` 결과도 NULL 가능성을 방어하지 않고 바로 `sm_is_replication_class()`/`sm_get_ch_name()`에 넘깁니다.)

문제 시나리오: CUBRID는 FK 생성 시 참조 테이블에 PK를 요구하므로 대부분은 `pk_c`가 NULL이 아닙니다. 다만 이 코드는 그 전제를 **방어하지 않습니다.** PK 조회가 NULL을 반환하는 경로가 하나라도 성립하면(예: 카탈로그 일관성이 깨진 상태, 향후 FK-대-UNIQUE 참조 확장 등) rkcheck가 세그폴트로 죽습니다. 위반을 "알려주는" 코드가 위반 상황에서 죽는 것은 특히 나쁩니다.

제안: `pk_c`(및 `ref_class_mop`)가 NULL일 수 있음을 가정하고, NULL이면 PK 이름 없이 출력하거나 대체 키 이름을 쓰도록 방어하십시오.

## 문제 7 (유지)

**[심각도: 보통] `sm_is_replication_class()`가 `au_fetch_class_force()` 실패를 `assert(false)` + `false`로 삼킴 — 복제 판정·표기·검사가 조용히 오판**

- 위치: `src/object/schema_manager.c:3395`

로직 설명: 이 기능 전반의 "이 클래스가 복제 대상인가"는 대부분 `sm_is_replication_class()`로 판정합니다. 구현은:

```c
if (op != NULL && au_fetch_class_force (op, &class_, AU_FETCH_READ) == NO_ERROR)
  return !(class_->flags & SM_CLASSFLAG_DATA_REPLICATION_OFF);
assert (false);
return false;
```

즉 `op`가 NULL이거나 fetch가 실패하면 **"복제 대상 아님(false)"**으로 처리하고 디버그 빌드에서는 `assert(false)`로 죽습니다. 이 함수는 `do_alter()`의 최종 RK 재검사(execute_schema.c:2063), `object_printer::describe_class`(SHOW CREATE TABLE), `unload_schema.c`의 `emit_schema()`, `rkcheck`의 순회, 그리고 이번에 #7678이 추가한 SBR 판정 경로(`spec_has_replication_class`, execute_statement.c:3288)에서까지 쓰입니다.

문제 시나리오: #7697이 서버측 `heap_get_class_repl_on()`은 에러 전파형으로 고쳤지만, **클라이언트 계층의 이 판정 함수는 여전히 "에러를 false로 뭉개는" 옛 패턴**입니다. fetch가 인터럽트/락 경합 등으로 일시 실패하면:
- `do_alter()`(2063): `!sm_is_replication_class(vclass)`가 `true`가 되어 `return NO_ERROR;` — **RK 검사를 건너뛰고 성공 처리**합니다.
- `object_printer`/`unload`: 실제로는 REPLICATION=ON인 테이블을 `REPLICATION=OFF`로 표기·출력합니다. unload 결과를 스키마 원본으로 삼아 다른 DB에 재적재하는 사람에게는 **복제 설정이 뒤집힌 채 마이그레이션되는** 조용한 사고입니다.

제안: 최소한 fetch 실패와 "복제 아님"을 구분해야 합니다. 판정 함수가 에러 코드를 반환하거나 out-parameter로 성공/실패를 알리도록 바꾸고, 호출부(특히 do_alter의 재검사, 스키마 출력 경로)는 실패 시 안전한 쪽으로 처리하십시오. (#7697이 서버측에 적용한 패턴을 클라이언트측에도 확장)

**[심각도: 보통] `do_promote_partition()`의 새 helper가 "PK 보존"이라 주석하지만 실제로는 NOT NULL UNIQUE만 감지 — PK-only 파티션 승격 동작이 불명확**

## 문제 17 (신규)

**[심각도: 보통] `do_promote_partition()` 컬럼 속성 보존 루프의 latch 조건 오류 — NOT NULL UNIQUE가 둘 이상이면 두 번째 이후 컬럼의 UNIQUE 플래그가 조용히 벗겨짐**

- 위치: `src/query/execute_schema.c:7948-7955`

로직 설명: 파티션을 일반 테이블로 승격할 때, 부모에서 물려받은 컬럼 속성 중 NOT NULL UNIQUE는 보존하고 나머지 UNIQUE 흔적은 지우려고 각 attribute를 순회합니다.

```c
for (smattr = ctemplate->attributes; smattr != NULL; smattr = (SM_ATTRIBUTE *) smattr->header.next)
  {
    smattr->auto_increment = NULL;
    smattr->flags &= ~(SM_ATTFLAG_AUTO_INCREMENT);
    if (!has_notnull_unique && has_notnull_unique_constraints (smattr))   // ← 문제
      {
        has_notnull_unique = true;
      }
    else
      {
        smattr->flags &= ~(SM_ATTFLAG_UNIQUE);
        smattr->flags &= ~(SM_ATTFLAG_REVERSE_UNIQUE);
      }
    smattr->flags &= ~(SM_ATTFLAG_FOREIGN_KEY);
    smattr->flags &= ~(SM_ATTFLAG_PARTITION_KEY);
  }
```

여기서 `has_notnull_unique`는 "적어도 하나 찾았다"를 기억하는 latch입니다. 그런데 **이 latch가 per-attribute 플래그 유지 여부를 결정하는 조건에 그대로 섞여 있습니다.** 조건 `!has_notnull_unique && has_notnull_unique_constraints(smattr)`는 latch가 한 번 `true`가 되면 그 뒤 모든 attribute에 대해 `!has_notnull_unique`가 `false`라서 항상 `else`로 빠집니다. 즉 **첫 번째로 발견된 NOT NULL UNIQUE 컬럼만 UNIQUE 플래그를 유지하고, 그 뒤에 오는 NOT NULL UNIQUE 컬럼은 자기 자신이 자격이 있어도 `SM_ATTFLAG_UNIQUE`/`SM_ATTFLAG_REVERSE_UNIQUE`가 벗겨집니다.**

문제 시나리오:
- 파티션 테이블에 서로 독립적인 NOT NULL UNIQUE 컬럼이 둘(`a NOT NULL UNIQUE`, `b NOT NULL UNIQUE`) 있는 경우, 승격 후 `a`는 UNIQUE 플래그를 유지하지만 `b`는 벗겨집니다.
- 마찬가지로 복합 `UNIQUE(a, b)`(둘 다 NOT NULL)에서도, 루프에서 먼저 만난 컬럼만 플래그를 유지하고 나머지 구성 컬럼은 벗겨져, **같은 제약을 구성하는 컬럼들 사이에 per-attribute 플래그가 불일치**하게 됩니다.

property 정리 분기(`if (!has_notnull_unique)`)는 latch가 `true`이므로 UNIQUE property 자체는 drop하지 않아 제약 객체는 살아남지만, 컬럼 단위 플래그(`SM_ATTFLAG_UNIQUE`)와 property가 어긋난 상태로 카탈로그에 반영됩니다. 마이그레이션 중 파티션을 승격한 뒤 `SHOW CREATE TABLE`이나 `db_attribute`로 스키마를 뽑아 재적재하는 사람에게는 **컬럼의 UNIQUE 표기가 실제 제약과 어긋나 보이는** 메타데이터 표면 문제가 됩니다.

제안: latch 유지와 per-attribute 플래그 결정을 분리하십시오. 플래그 유지 여부는 `has_notnull_unique_constraints(smattr)` 단독으로 판단하고(`!has_notnull_unique` 제거), latch(`has_notnull_unique |= has_notnull_unique_constraints(smattr)`)는 뒤쪽 property drop 결정용으로만 별도 갱신하면 됩니다.
