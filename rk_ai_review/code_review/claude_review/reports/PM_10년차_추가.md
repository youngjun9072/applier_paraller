## 이번 라운드에 조사했으나 "문제 없음"으로 판단한 지점 (근거)

1. **`heap_get_class_repl_on()`(`heap_file.c:11074`)** — `heap_get_class_record()` 실패를 `ASSERT_ERROR_AND_SET`으로 처리한다. 이 매크로는 `er_errid()`가 `NO_ERROR`이면 강제로 `ER_FAILED`를 대입하므로(release 빌드에서도) 기존 K-7/K-8류의 "에러를 삼켜 false로 위장" 안티패턴이 재발하지 않았음을 코드로 확인했다. 새로 도입된 함수는 오히려 K-7 패턴을 올바르게 고친 사례다.
2. **`checksumdb.c`의 `db_set_suppress_repl_on_transaction(true)`→`db_execute()`→`db_set_suppress_repl_on_transaction(false)` 왕복** — `db_set_suppress_repl_on_transaction()`이 실제로 서버 RPC(`net_client_request(NET_SERVER_LOG_SET_SUPPRESS_REPL_ON_TRANSACTION, ...)`)라서 네트워크 장애로 실패할 수 있는 지점임을 확인했고, "resume(false) 호출이 실패하면 억제 플래그가 트랜잭션 내내 눌어붙어 후속 청크까지 복제가 조용히 억제되는 것 아닌가"라는 가설을 세워 추적했다. 결과: `chksum_calculate_checksum()`이 `NO_ERROR`가 아닌 값을 반환하면 호출자 루프(`checksumdb.c:2008-2022`)가 `db_abort_transaction()` 후 `break`하고, `logtb_clear_tdes()`(`log_tran_table.c:1575`, 커밋/롤백 시 항상 호출)가 `tdes->suppress_replication = 0`으로 리셋하므로 플래그가 트랜잭션 경계를 넘어 누수되지 않는다. 오탐으로 배제.
3. **`is_data_repl_log_enabled()`가 `do_statement()`(:3405)와 `do_execute_statement()`(:4113) 두 곳에 동일 조건으로 복붙됐다** — diff 전후 대조 결과 이 두 호출부의 중복 구조 자체는 이번 기능이 만든 게 아니라 기존 `is_stmt_based_repl_type(statement)` 단일 조건이 원래도 두 곳에 나뉘어 있던 구조이며, 이번 diff는 그 기존 두 지점에 동일하게 `&& is_data_repl_log_enabled(...)`를 추가했을 뿐이다. 새로운 중복을 만든 게 아니라 기존 중복 지점을 일관되게 갱신한 것이므로 지적하지 않았다.
4. **`or_is_replication_candidate_key()`가 `BTREE_UNIQUE`만 인정하고 `REVERSE_UNIQUE`를 RK 후보에서 배제하는 반면, DDL 쪽 `IS_HA_REPLICATION_KEY_CONSTRAINT` 매크로(`class_object.c:95-98`)는 `SM_IS_CONSTRAINT_UNIQUE_FAMILY`를 통해 REVERSE_UNIQUE도 허용한다** — 이는 기존 리포트의 **K-5**(RK 후보 판정이 DDL 검증과 런타임 복제에서 불일치, 위치에 `class_object.c:95-98`·`object_representation_sr.c:4694-4722` 명시)와 정확히 같은 코드 위치·같은 뿌리이므로 신규로 세지 않았다.
5. **`class_replication_spec`을 `alter_clause_for_alter_list`에 추가하며 `alter_node->info.alter.code != PT_CHANGE_REPLICATION`일 때만 대입하는 가드**(`csql_grammar.y:5862-5871`) — 같은 ALTER 절에 REPLICATION 옵션이 중복되면 세만틱 에러 없이 조용히 처리된다는 동일 지점을 확인했으나, 이는 기존 **K-20**(ALTER TABLE의 중복/혼합 REPLICATION 절 세만틱 체크 부재)과 위치·원인이 동일하다. `alter_clause_for_alter_list`가 콤마로 구분된 절 하나당 한 번씩만 호출됨(`csql_grammar.y:4182` 참조)을 grammar 구조로 확인해, "한 절 안에 COMMENT와 REPLICATION이 뒤섞여 들어갈 수 있는" 별도 시나리오는 성립하지 않음도 확인했다.
6. **`schema_system_catalog_install_query_spec.cpp`의 `is_replication_class` 뷰 컬럼 추가**(`sm_define_view_class_spec()` :74) — 새 `%d`(`SM_CLASSFLAG_DATA_REPLICATION_OFF`)와 그에 대응하는 vararg가 포맷 문자열 중간에 위치 매칭 방식으로 삽입된 것을 확인했으나, 이는 기존 **K-42**(포맷 문자열-vararg 수동 위치 매칭 취약)·**K-19**(db_class 뷰 중간 삽입)와 동일한 설계 취약점의 반복 사례이지 이 삽입 자체가 위치를 잘못 맞춘 새로운 버그는 아니다(현재 순서상 올바르게 대응됨을 확인).
7. **`util_admin.c`의 `ua_Rkcheck_Option_Map`/`ua_Rkcheck_Option`, `utility.h`의 `RKCHECK_CHECK_RK_CONSTRAINT_S='r'`/`RKCHECK_CHECK_FK_CONSTRAINT_S='f'`** — getopt 짧은 옵션 문자가 `ua_Rkcheck_Option` 배열 내에서만 유일하면 되고 실제로 유일함을 확인. 다른 유틸리티(TDE, FLASHBACK, MEMMON)의 옵션 맵 구조와 일관되게 작성되어 새로운 결함을 찾지 못했다.
8. **`parse_tree.h`/`parse_tree_cl.c`의 `PT_CHANGE_REPLICATION`/`PT_TABLE_OPTION_REPLICATION` enum·프린터 추가** — 신규 enum 값이 기존 `PT_TABLE_OPTION_TYPE`/`pt_alter_code` 목록 맨 끝에 추가되었고(끝 삽입 원칙 준수), `pt_print_table_option()`의 신규 `case`가 다른 옵션과 동일한 패턴(`"replication = "` 출력)을 따름을 확인해 지적하지 않았다.
9. **`btree_get_pkey_btid` → `btree_get_rkey_btid` 리네임 + 판정 로직을 `curr_idx->type == BTREE_PRIMARY_KEY`에서 `or_is_replication_candidate_key(curr_idx)`로 교체**(`btree.c:8291`) — 이 함수의 유일한 호출자 `locator_repl_prepare_force()`(`locator_sr.c:6848`)까지 추적했다. 인덱스 배열에서 첫 매치를 반환하는 구조는 기존 **K-58**(RK 자동 선택이 인덱스 배열 순서에 의존)과 동일 뿌리라 신규로 세지 않았다.

## 조사 종료 선언 (3차 전수 재수색)

**훑은 범위**: `git diff b646647ec...HEAD --stat`의 35개 파일 전부. 이 중 1차·2차 리포트 및 67건 병합 리스트가 명시적으로 다루지 않았던 10개 파일(`csql_lexer.l`, `util_admin.c`, `parse_tree.h`, `parse_tree_cl.c`, `error_code.h`, `schema_manager.h`, `heap_file.h`, `btree.h`, `class_object.h`, `execute_schema.h`)을 처음부터 끝까지 새로 읽었고, 나머지 파일들도 diff hunk 단위로 재확인하며 이미 알려진 이슈의 위치·콜체인이 현재 HEAD에서도 정확히 일치하는지 검증했다. 특히 신규 함수 6개(`heap_get_class_repl_on`, `or_is_replication_candidate_key`, `btree_get_rkey_btid`, `classobj_copy_pk_and_uk_notnull_constraints`, `is_data_repl_log_enabled`/`spec_has_replication_class`, `us_hb_process_rkcheck`)는 정의부터 호출부까지 LSP 없이(grep+Read로 직접 정의·호출자 대조, 작업지시서 §2 규정대로 콜체인을 따라감) 전수 추적했다.

**더 없다고 보는 근거**: 위 "문제 없음으로 판단한 지점" 8건 모두 구체적인 가설(에러 삼킴, 억제 플래그 누수, 중복 조건, 위치 불일치, 배제 로직 불일치 등)을 세우고 실제 코드·호출 경로·자료구조 수명주기(`logtb_clear_tdes`)까지 확인한 뒤에야 기각했다 — 키워드 검색만으로 지레짐작하지 않았다. 이번 라운드에서 발견한 모든 후보는 조사 결과 (a) 기존 67건 중 하나와 코드 위치·원인이 동일하거나, (b) 실제로는 안전하게 처리되어 있음(예: `logtb_clear_tdes`의 플래그 리셋, `ASSERT_ERROR_AND_SET`의 강제 실패 처리)을 확인했다. PM 페르소나 관점(요구사항 완전성·에러 메시지 품질·하위호환·미완성 흔적·회귀)에서 35개 파일 전체를 커버했고, 남은 미검토 영역(메시지 카탈로그 문구, 헤더 선언 전용 diff)은 이미 대응 구현부에서 다뤄진 내용의 1:1 반영이라 별도 결함 소지가 없다.

따라서 이번 3차 라운드는 **신규 문제 0건, 추가 문제점 없음**으로 종료한다. 잔여 쿼터 39건 중 채운 것은 0건이지만, 이는 작업지시서 §4-1이 명시한 "더 이상 찾을 수 없으면 그 시점에서 종료"에 해당하는 정상적인 결과다.
