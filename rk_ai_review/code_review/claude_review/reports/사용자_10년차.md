# 코드 리뷰 — 사용자(SQL 실무자) · 10년차

> **2차 재리뷰 (기준 `734f4959d`)** — upstream 동기화(#7678 `3b6ebd1a9`, #7697 `9e094324b`) 이후
> 1차 리포트(기준 `44468ed73`)를 재검증했다. 14건은 번호를 유지한 채 그대로 남았고, 새 문제
> 17~18을 이어서 추가했다.

## 페르소나

나는 CUBRID로 서비스 DB를 10년째 운영해 온 SQL 실무자다. 새 기능이 나오면 제일 먼저 확인하는 건
"내가 짜던 DDL이 그대로 통하는가", "에러가 나면 왜 났는지 메시지로 알 수 있는가", "성공했다고
나온 결과가 내가 기대한 상태와 같은가"이다. 동시에 10년을 버틴 만큼 CUBRID의 기존 관례(같은
종류의 옵션이면 같은 방식으로 처리된다, 예약어를 함부로 늘리지 않는다, 유틸리티는 실패해도
죽지 않는다)를 알고 있고, 새 코드가 그 관례를 깨면 바로 눈에 걸린다.

## 총평 (2차 재검증 결과)

1차에서 지적한 문제 대부분이 이번 동기화에서 **전혀 건드려지지 않은 채 그대로** 남아 있다.
동기화 델타(#7678/#7697)는 SBR/checksumdb 버그와 `heap_is_replication_class`의 인터럽트
삼킴 문제(INSERT/DELETE 경로)만 좁게 고쳤을 뿐, 이번 리뷰가 지적한 "게이트 로직이 실제로는
안 걸리는" 종류의 버그나 "NULL을 확인 안 하고 역참조하는" 종류의 버그에는 손을 대지 않았다.

1. **"검사를 걸어놨다고 믿었는데 실제로는 안 걸리는" 게이트 버그** — `do_alter()`의 다중
   ALTER 절 처리에서 여전히 "첫 번째 절의 코드"만 보고 HA 복제 제약 검사 여부를 판정한다
   (문제 1, 치명, 위치 불변).
2. **NULL/에러를 확인하지 않고 바로 역참조하는 방어 누락** — rkcheck 유틸리티의 로그 파일
   오픈 실패(문제 2)와 FK 위반 로깅 함수의 PK-없는 참조 테이블 처리(문제 3) 모두 코드가
   그대로다.
3. **과거 PR에서 합의되거나 지적된 사항이 merge 결과물에 반영되지 않은 사례** — `CREATE
   TABLE ... LIKE ... REPLICATION=x`가 여전히 에러 없이 조용히 무시된다(문제 6).
4. **동기화 델타 자체가 새로 심은 문제** — #7678이 새로 추가한 `is_data_repl_log_enabled()`
   보조 함수 `is_replication_class()`가, 바로 그 동기화가 다른 곳(heap 계층)에서 근본
   수정한 것과 **똑같은 "조회 실패를 assert(false)로 봉인한다" 안티패턴**을 client 계층에
   그대로 재도입했다(신규 문제 17). 팀이 방금 배운 교훈이 같은 커밋 세트 안에서 다른
   레이어에 재발한 사례다.

## 문제 1 — [심각도: 치명] 다중 ALTER TABLE 절에서 HA 복제 제약 게이트가 "첫 번째 절"의 코드만 검사한다

**재검증: 유지 (변경 없음)**

**위치**: `src/query/execute_schema.c:2051` (매크로 정의 `:109-114`, 루프 변수 선언
`:1838`, 루프 시작 `:1851-1854`) — 1차 리포트와 동일한 위치.

**로직 설명**: `do_alter()`는 콤마로 이어진 여러 ALTER 절을 `for (crt_clause = alter;
crt_clause != NULL; crt_clause = crt_clause->next)` 루프로 순회한다. PR #6637이 "PK를
DROP하고 바로 ADD하는" 멀티 ALTER TABLE을 허용하기 위해, HA 복제 제약 검사
(`check_ha_repl_constraint`)를 개별 절 처리 함수가 아니라 이 루프가 다 끝난 뒤 한 번만
하도록 옮겨 놓았다. 그런데 "이 문에 검사가 필요한 절이 하나라도 있었는가"를 판단하는
코드가 다음과 같다.

```c
const PT_ALTER_CODE alter_code = crt_clause->info.alter.code;   /* 매 반복마다 현재 절의 code로 갱신됨 */
...
if (!need_check_repl_constraint && IS_REPL_CONSTRAINT_RELATED_ALTER (alter->info.alter.code))
  {
    need_check_repl_constraint = true;
  }
```

`alter_code`(지역 변수, 매 반복마다 `crt_clause->info.alter.code`로 올바르게 갱신됨)를 써야
할 자리에 `alter->info.alter.code`를 쓰고 있다. `alter`는 루프 내내 **head 노드를 가리킨 채
바뀌지 않으므로**, `alter->info.alter.code`는 항상 **리스트의 첫 번째 절의 code**다. 즉 이
판정은 사실상 "이 ALTER TABLE 문의 첫 번째 절이 게이트 대상 코드(PT_ADD_ATTR_MTHD/
PT_DROP_ATTR_MTHD/PT_DROP_CONSTRAINT/PT_DROP_PRIMARY_CLAUSE)인가"만 보고, 두 번째 이후
절이 무엇이든 전혀 반영하지 못한다.

**문제 시나리오**: HA 모드에서
```sql
ALTER TABLE t COMMENT = 'x', DROP PRIMARY KEY;
```
첫 번째 절은 `PT_CHANGE_TABLE_COMMENT`(게이트 목록에 없음)이고, 두 번째 절이 실제로 PK를
제거하는 `PT_DROP_PRIMARY_CLAUSE`(게이트 목록에 있음)다. 하지만 매 반복마다 `alter->info
.alter.code`(=첫 절의 코드)만 보므로 `need_check_repl_constraint`는 끝까지 `false`로
남고, 루프가 끝난 뒤 `check_ha_repl_constraint()` 호출 자체가 생략된다. 결과적으로 다른
복제 후보 키가 없는 테이블에서 PK를 지워 **RK가 하나도 없는 복제 테이블이 HA 모드에서
그대로 만들어진다.** `DROP PRIMARY KEY, ADD PRIMARY KEY(...)`처럼 게이트 대상 절이
**첫 번째**로 오는 조합(스펙 예시 13)만 우연히 정상 동작하고, 순서를 바꾸거나 앞에 무해해
보이는 절(COMMENT, COLLATION 등)을 하나 끼워 넣으면 검사가 통째로 빠진다.

**제안**: `alter->info.alter.code`를 `alter_code`(또는 `crt_clause->info.alter.code`)로
수정한다. 회귀 테스트에는 "게이트 대상 절이 앞/뒤/중간 어디에 와도 검사가 걸리는지"를
조합별로 넣어야 한다.

## 문제 2 — [심각도: 치명] rkcheck 유틸리티가 로그 파일 오픈 실패 시 NULL FILE*에 그대로 fprintf해 죽는다

**재검증: 유지 (변경 없음)**

**위치**: `src/executables/util_cs.c:3320` (`fp = open_violation_list_file(...)`), 이후
`PRINT_SECTION_TITLE`/`PRINT_MESSAGE`/`check_repl_constraint_violations` 등에서 `fp`를
곧바로 사용. NULL 체크는 종료부(`:3403`, `if (fp != NULL) { fclose(fp); }`)에만 있다.

**로직 설명**: `rkcheck()`는 `open_violation_list_file()`로 위반 목록 파일을 연 뒤, 그
`FILE *fp`를 `PRINT_SECTION_TITLE(fp, ...)`(=`fprintf(fp, ...)`로 전개되는 매크로),
`check_repl_constraint_violations(classes, fp, ...)`, `PRINT_MESSAGE(fp, ...)` 등에 계속
넘겨서 쓴다. `open_violation_list_file()`은 내부에서 `fopen(file_path, "w")`의 결과를
그대로 반환하는데, 이 반환값이 실패 시 `NULL`이라는 점에 대해 `rkcheck()` 쪽에서 **호출
직후 단 한 번도 확인하지 않는다.**

**문제 시나리오**: `$CUBRID/log` 디렉터리가 존재하지 않거나, 권한이 없거나, 디스크가 꽉 찬
상태 — 즉 HA 기동을 시도할 만큼 장애가 누적된 바로 그런 환경에서 `fopen`이 실패한다.
`cubrid hb start` 시 자동으로 호출되는 rkcheck 프로세스가 `fprintf(NULL, ...)`로 즉시
세그폴트하며 죽는다. 사용자는 "RK 제약 위반"이라는 정상적인 에러 메시지 대신 코어덤프/
원인불명 크래시를 보게 된다.

**제안**: `open_violation_list_file()` 반환 직후 `fp == NULL`을 확인해 적절한 에러(예:
`ER_GENERIC_ERROR` + `db_error_string`/`strerror(errno)` 안내)로 조기 종료한다.

## 문제 3 — [심각도: 치명] FK 위반 로깅 함수가 참조 테이블에 PK가 없으면(UK만 RK인 경우) NULL 역참조한다

**재검증: 유지 (변경 없음)**

**위치**: `src/query/execute_schema.c:9837-9840` (`log_ha_repl_fk_ref_all_replicated()`)

**로직 설명**:
```c
if (!sm_is_replication_class (ref_class_mop))
  {
    DB_CONSTRAINT *pk_c = db_constraint_find_primary_key (db_get_constraints (ref_class_mop));
    fprintf (fp, "%s(%s) -> %s(%s)\n", sm_get_ch_name (class_obj), tmp_c->name,
             sm_get_ch_name (ref_class_mop), pk_c->name);
    ret++;
  }
```
이 함수는 "FK가 참조하는 테이블이 REPLICATION 대상이 아니면 위반 1건"으로 기록하면서,
참조 테이블 이름을 보여주는 용도로 그 테이블의 **PK 이름**을 출력에 끼워 넣는다. 그런데
`db_constraint_find_primary_key()`는 PK 제약이 없으면 `NULL`을 반환하는 함수이고, 그
반환값을 곧바로 `pk_c->name`으로 역참조한다.

**문제 시나리오**: 이 기능의 핵심 전제 자체가 "RK는 PK 또는 NOT NULL UNIQUE 중 하나일 수
있다"(스펙 1장, PR #6467)이다. 즉 참조 테이블이 **PK 없이 NOT NULL UNIQUE만으로 RK를
구성**하는 것은 스펙이 명시적으로 허용하는 정상 스키마다. 이런 테이블을 REPLICATION=OFF로
두고 다른 테이블에서 FK로 참조한 뒤 `cub_admin rkcheck -f`(또는 `cubrid hb start`가 자동
실행하는 rkcheck)를 돌리면, `pk_c`가 `NULL`이 되어 그대로 세그폴트한다. 정상적인(PK 대신
UK를 쓰는) 스키마 구성이 오히려 rkcheck를 죽이는, HA 기동을 막는 것도 아니고 아예
크래시시키는 결과다.

**제안**: `pk_c == NULL`일 때는 RK를 담당하는 제약을 찾는 계열 함수로 대체하거나, 최소한
"PK 없음"을 감지해 이름 없이 출력하도록 방어 코드를 넣는다.

## 문제 6 — [심각도: 중요] `CREATE TABLE ... LIKE ... REPLICATION=x`가 에러 없이 조용히 무시된다 (PR #6943에서 "동시 사용 시 에러"로 확정했던 규칙과 다르다)

**재검증: 유지 (변경 없음)**

**위치**: `src/query/execute_schema.c:10258-10264`

**로직 설명**:
```c
if (create_like)
  {
    is_replication_on = !(source_class->flags & SM_CLASSFLAG_DATA_REPLICATION_OFF);
  }
else
  {
    is_replication_on = IS_CREATE_STMT_SET_REPL_OPTION (tbl_opt_replication);
  }
```
`create_like`(즉 `CREATE TABLE new LIKE old`)가 참이면 사용자가 문에 `REPLICATION=...`을
같이 적었는지 여부(`tbl_opt_replication`)는 아예 확인하지 않고, 무조건 원본 테이블
(`source_class`)의 플래그를 그대로 가져온다. `semantic_check.c`의 `pt_check_create_entity()`
에도, `execute_schema.c` 어디에도 "LIKE와 REPLICATION 옵션을 함께 쓰면 에러"라는 검사가
없다.

**문제 시나리오**: `pr_히스토리.md`(PR #6943)에는 "REPLICATION 옵션과 LIKE를 동시에
명시하면 에러라는 규칙도 이때 PR 본문(Remarks)에서 확정됐다"고 명시돼 있다. 그런데 실제
코드는 에러를 내는 대신, 사용자가 명시적으로 쓴 옵션을 그냥 버린다.
```sql
CREATE TABLE new_t LIKE old_t REPLICATION=OFF;
```
사용자는 "이 문장이 성공했으니 `new_t`는 REPLICATION=OFF로 만들어졌다"고 믿게 되지만,
실제로는 `old_t`의 REPLICATION 값을 그대로 물려받는다(`old_t`가 ON이면 `new_t`도 ON이
되어, 의도와 정반대로 복제 대상이 되어버릴 수 있다). 에러도 안 나고 경고도 없어서, 사용자가
나중에 `SHOW CREATE TABLE new_t`를 찍어보기 전까지는 자신이 지정한 옵션이 무시됐다는
사실조차 알 수 없다 — "직관에 어긋나는 성공 케이스"의 전형이다.

**제안**: PR #6943에서 확정한 대로 `tbl_opt_replication != NULL && create_like != NULL`이면
파싱/세만틱 단계에서 에러를 내거나, 정책을 바꿀 것이면 최소한 사용자가 명시한 옵션이 우선
적용되도록 고쳐야 한다.

## 문제 7 — [심각도: 중요] ALTER TABLE에서 REPLICATION 옵션 중복 지정에 대한 세만틱 체크가 없다 (CREATE TABLE 경로에는 있음)

**재검증: 유지 (변경 없음)**

**위치**: 참고 대조 — CREATE 경로 중복 체크는 `src/parser/semantic_check.c:8506-8519`
(`PT_TABLE_OPTION_REPLICATION` case, `found_tbl_replication`). ALTER 경로는
`src/parser/csql_grammar.y:5862-5871`(`class_replication_spec` 처리) 및
`src/query/execute_schema.c:11730-11834`(`do_alter_change_replication`) 어디에도 대응하는
검사가 없다.

**로직 설명**: `CREATE TABLE`은 같은 옵션을 두 번 쓰는 걸 `pt_check_create_entity()`가
`found_tbl_replication` 플래그로 검사해 `MSGCAT_SEMANTIC_DUPLICATE_TABLE_OPTION` 에러를
낸다. 반면 `ALTER TABLE`의 `REPLICATION=...` 절은 `alter_clause_list`(콤마로 연결되는
리스트, PR #6637이 멀티 ALTER를 위해 확립한 구조)의 한 항목이며, 콤마로 구분된 절 각각은
독립된 `PT_ALTER` 노드를 얻는다. 즉 `ALTER TABLE t REPLICATION=ON, REPLICATION=OFF;`
처럼 같은 옵션을 두 번(콤마로) 쓰면, `do_alter()`의 절 순회 루프에서
`do_alter_change_replication()`이 두 번 실행돼 마지막 값이 그냥 덮어쓴다 — 중복이라는
진단 없이.

**문제 시나리오**: (HA가 꺼진) 싱글/SA 모드에서
```sql
ALTER TABLE t REPLICATION=ON, REPLICATION=OFF;
```
을 실행하면 별다른 에러 없이 성공하고 결과는 REPLICATION=OFF(뒤에 쓴 값)가 된다. CREATE
TABLE에서는 같은 실수를 하면 바로 에러로 알려주는 것과 비교하면 일관성이 없다. (HA
모드에서는 `do_alter_change_replication()` 맨 앞에서 즉시 에러 처리되므로 이 시나리오는
싱글/SA 모드에 한정된다.)

**제안**: `do_alter()`가 절을 순회하는 동안 `PT_CHANGE_REPLICATION`이 이미 한 번 나왔는지
추적해, 두 번째부터는 CREATE TABLE과 동일한 "중복 옵션" 에러를 내도록 맞춘다.

## 문제 8 — [심각도: 보통] `SHOW CREATE TABLE`/`unloaddb` 출력이 스펙 문서의 표기(`REPLICATION ON`)와 다르게 `REPLICATION=ON`으로 나온다

**재검증: 유지 (변경 없음)**

**위치**: `src/object/object_printer.cpp:1137-1145`(`describe_class()`),
`src/executables/unload_schema.c:1794-1801`(`emit_schema()`)

**로직 설명**: 두 곳 모두 `m_buf(", REPLICATION=ON")` / `output_ctx(", REPLICATION=OFF")`
처럼 `=`를 붙여 출력한다.

**문제 시나리오**: 스펙 예시(`show create table`)는 결과를
```
CREATE TABLE [tbl] (...) REUSE_OID, COLLATE utf8_bin, REPLICATION ON
```
로 명시하고 있다 — `REPLICATION`과 `ON` 사이가 `=` 없이 공백이다. 문법상
`REPLICATION`/`REPLICATION ON`/`REPLICATION=ON`을 모두 입력으로 받아주므로 이 표기 차이가
재입력을 막지는 않지만, 스펙을 그대로 QA 기준(출력 문자열 diff 테스트, 매뉴얼 캡처)으로
삼을 경우 그대로 실패한다.

## 문제 10 — [심각도: 보통] `do_promote_partition()`의 NOT NULL UNIQUE 보존 로직이 "가장 먼저 발견된 컬럼"만 보존하고 나머지 컬럼의 UNIQUE 플래그를 무조건 지운다

보존해야 한다. 그런데 실제 순회는 다음과 같다.
```c
for (smattr = ctemplate->attributes; smattr != NULL; smattr = ...)
  {
    ...
    if (!has_notnull_unique && has_notnull_unique_constraints (smattr))
      {
        has_notnull_unique = true;                       /* 처음 만난 후보만 살린다 */
      }
    else
      {
        smattr->flags &= ~(SM_ATTFLAG_UNIQUE);            /* 그 외 전부 UNIQUE 플래그 제거 */
        smattr->flags &= ~(SM_ATTFLAG_REVERSE_UNIQUE);
      }
    ...
  }
```

**문제 시나리오**: 파티션 테이블에 `b INT NOT NULL UNIQUE, c INT NOT NULL UNIQUE`처럼

**제안**: "이미 하나를 찾았으면 나머지 컬럼의 플래그를 지운다"는 조건을, 제거 대상 판단과
"이미 보존을 확정했는지" 여부를 분리해, 서로 다른 유효한 RK 후보가 여러 개 있으면 전부
보존하도록 고친다.

## 문제 17 — [심각도: 보통, 신규] 동기화 델타(#7678)가 새로 추가한 `is_replication_class()`가, 같은 델타가 다른 레이어에서 방금 근본 수정한 "조회 실패=assert(false)" 안티패턴을 그대로 재도입했다

**위치**: `src/query/execute_statement.c:3199-3216` (`is_replication_class()`, 신규 함수 —
#7678 커밋 "Detect replication class for derived vclass INSERT/UPDATE/DELETE targets"에서
추가됨), 호출 체인 `get_spec_classname()` → `is_replication_class()` ←
`spec_has_replication_class()` ← `is_data_repl_log_enabled()` ← `do_statement()`/
`do_execute_statement()`

**로직 설명**:
```c
static bool
is_replication_class (const char *classname)
{
  DB_OBJECT *class_obj;

  if (classname == NULL)
    {
      return false;
    }

  class_obj = db_find_class (classname);
  if (class_obj == NULL)
    {
      assert (false);
      return false;
    }

  return sm_is_replication_class (class_obj);
}
```
이 함수는 `db_find_class()`(클라이언트 계층에서 카탈로그 캐시/서버 조회를 거쳐 클래스
객체를 찾는 함수)가 실패하면 `assert(false)`로 "있을 수 없는 일"로 취급하고 `false`를
반환한다. `is_data_repl_log_enabled()`가 `PT_INSERT`/`PT_UPDATE`/`PT_DELETE`가
`USE_SBR` 힌트를 달고 있을 때 실제 SBR 로그를 남길지 판정하는 경로에 이 함수가 들어간다.

바로 이 동기화 델타(#7697, 같은 커밋 세트 안의 다른 파일)가 정확히 이 패턴 — "조회
실패를 assert(false)로 봉인해, 정상적으로 발생 가능한 실패(인터럽트 등)를 서버 크래시 또는
신호 삼킴으로 만든다" — 를 `heap_file.c`의 `heap_is_replication_class()`에서 근본
수정했다는 사실(PR 히스토리 #7697, 실측 14회 중 8회 인터럽트 유실 증명)과 정면으로
대비된다. `#7697`이 고친 원인은 "heap 페이지 fetch가 인터럽트로 실패할 수 있는데 이를
'불가능'으로 가정했다"는 것이었는데, 이번에 새로 추가된 `is_replication_class()`는
계층만 다를 뿐(heap 페이지 fetch 대신 client-side 카탈로그 조회) 논리적으로 동일한
가정 — "이 조회는 절대 실패하지 않는다" — 을 다시 코드에 박아 넣었다.

**문제 시나리오**: `db_find_class()`는 일반적으로는 성공하지만(spec이 이미 파서 단계에서
resolve된 이름이므로), 다음과 같은 경우 실패할 수 있다 — 동시성 환경에서 다른 세션이 같은
트랜잭션 윈도우 사이에 해당 클래스를 DROP/RENAME한 경우, 권한 캐시가 갱신되는 과도기,
또는 연결 오류/인터럽트로 서버 왕복이 실패하는 경우. 이런 상황이 발생하면:
- **debug 빌드**: `assert(false)`가 그대로 프로세스를 abort시킨다. 사용자 입장에서는 평범한
  `INSERT /*+ USE_SBR */ ...` 문 하나가 클라이언트(csql/broker CAS)를 통째로 죽이는 것으로
  보인다.
- **release 빌드**: assert가 비활성화되므로 조용히 `false`(복제 대상 아님)를 반환하고,
  실제로는 REPLICATION=ON인 테이블을 대상으로 한 SBR 문이 복제 로그 없이 넘어가 **슬레이브가
  그 변경을 놓치는 조용한 데이터 불일치**로 이어질 수 있다 — 바로 이 동기화 델타가 고치려던
  "SBR이 조용히 빠지는" 부류의 버그가 새 코드에서 다른 경로로 재발하는 셈이다.

같은 커밋 세트 안에서 한쪽(heap 계층)은 "조회 실패는 실제로 발생할 수 있으니 에러로
전파하라"는 교훈을 얻었는데, 다른 쪽(신규 client 계층 헬퍼)은 그 교훈이 적용되지 않은 채
같은 실수를 반복했다 — 리뷰/교훈 전파 프로세스의 공백을 보여주는 사례다.

**제안**: `is_replication_class()`가 `db_find_class()` 실패를 `assert(false)` 대신 실제
에러로 처리하도록 바꾼다. 최소한 `is_data_repl_log_enabled()`가 `bool`이 아니라 에러코드를
반환하도록 시그니처를 바꿔 호출부(`do_statement`/`do_execute_statement`)가 "조회 실패"와
"복제 대상 아님"을 구분해서 처리할 수 있게 해야, #7697이 방금 정리한 원칙("조회는 실패할
수 있다, 삼키지 말고 전파하라")과 일관성이 맞는다.

## 문제 18 — [심각도: 보통, 신규] REPLICATION=OFF 테이블을 `USE_SBR` 문의 소스로 참조(JOIN/서브쿼리)하면 슬레이브가 조용히 다른 데이터로 갈라진다 (동기화 델타가 스스로 "known limitation"으로 명시)

**위치**: `src/query/execute_statement.c:3277-3295` (`is_data_repl_log_enabled()`의
`PT_INSERT` 케이스 — "INSERT...SELECT 소스 테이블은 의도적으로 검사하지 않는다"는 주석),
`PT_UPDATE`/`PT_DELETE` 케이스도 동일 구조(수정/삭제 **대상** spec만 검사, JOIN에 등장하는
다른 spec은 검사하지 않음)

**로직 설명**: #7678(3b6ebd1a9)의 "Gate SBR on actual modify-target specs" 커밋은
`is_data_repl_log_enabled()`가 UPDATE/DELETE에서 "수정/삭제 대상" spec만 보고 SBR
여부를 판정하도록 고쳤다(이전에는 첫 FROM spec만 보거나 JOIN-only spec까지 봐서 오판하던
버그였음). 이 수정 자체는 올바르다. 다만 커밋 메시지가 스스로 명시하듯, "수정 대상은
REPLICATION=ON인데, 그 문이 JOIN이나 `INSERT ... SELECT`로 참조하는 **원본** 테이블이
REPLICATION=OFF인 경우"는 여전히 처리되지 않는다.

**문제 시나리오**:
```sql
CREATE TABLE t_off (id INT PRIMARY KEY, v INT) REPLICATION=OFF;
CREATE TABLE t_on  (id INT PRIMARY KEY, v INT) REPLICATION=ON;
-- 마스터에서:
INSERT /*+ USE_SBR */ INTO t_on SELECT id, v FROM t_off;
```
`t_on`이 수정 대상이고 REPLICATION=ON이므로 SBR 로그는 정상적으로 남는다. 그런데 슬레이브
에서는 `t_off`가 REPLICATION=OFF라 애초에 마스터와 동일하게 유지되지 않는(비어 있거나
오래된 데이터인) 테이블이다. SBR은 "같은 문장을 슬레이브에서 재실행"하는 방식이므로,
슬레이브의 `INSERT ... SELECT ... FROM t_off`는 슬레이브에 있는(마스터와 다른) `t_off`
데이터를 읽어 `t_on`에 넣는다 — **마스터와 슬레이브의 `t_on` 내용이 조용히 갈라진다.**
에러도, 경고도 없다. UPDATE/DELETE에서 JOIN으로 REPLICATION=OFF 테이블을 참조하는 경우도
동일한 구조적 위험을 안는다.

이 시나리오는 커밋 메시지에 "Known limitation (unchanged): a statement that modifies a
replication target while referencing a replication-off table by join (or INSERT...SELECT
source) still re-executes against an empty/divergent table on the replica."라고 저자
스스로 명시한 바로 그 한계다 — 즉 저자도 알고 있는 채로 남겨둔 위험이지만, 어느 리포트에도
아직 사용자 관점의 "성공했지만 결과가 갈라진다"는 형태로 기록된 적이 없어 이번 리뷰에서
새 항목으로 남긴다. `USE_SBR`는 사용자가 명시적으로 붙이는 힌트라 완전히 우발적이지는
않지만, REPLICATION=OFF 테이블을 참조 전용(읽기 소스)으로 두는 것은 스펙상 허용되는
정상적인 구성이므로, 그런 테이블을 소스로 쓰는 SBR 문이 "성공"으로 보고되면서 실제로는
슬레이브 데이터를 갈라놓는다는 점은 이 페르소나(반직관적 성공 케이스)가 가장 경계하는
유형이다.

**제안**: 최소한 문서/매뉴얼에 "USE_SBR 문에서 참조하는 모든 테이블이 REPLICATION=ON이
아니면 슬레이브 데이터가 갈라질 수 있다"는 제약을 명시한다. 가능하면 `spec_has_
replication_class()`를 대상 spec뿐 아니라 JOIN/서브쿼리에 등장하는 모든 소스 테이블에도
적용해, 하나라도 REPLICATION=OFF면 경고(또는 에러)를 내는 방향을 검토한다.
