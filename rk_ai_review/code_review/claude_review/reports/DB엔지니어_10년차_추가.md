## 문제 16 — [심각도: 사소] checksumdb의 복제 억제 해제(`db_set_suppress_repl_on_transaction(false)`) 실패 시 원인 메시지가 남지 않는다

**상태: 신규**

**위치**: `src/executables/checksumdb.c:1727-1741` (`chksum_calculate_checksum`)

**로직 설명**

이번 diff가 `chksum_calculate_checksum()`에 새로 추가한 코드는 "SBR 복제 로그를 먼저 기록한 뒤, 로컬
체크섬 계산 쿼리 자체는 행 단위 복제가 되지 않도록 억제했다가 실행 직후 다시 푸는" 패턴이다.

```c
error = db_set_suppress_repl_on_transaction (true);     // 1727행
if (error != NO_ERROR)
  {
    snprintf (err_msg, LINE_MAX, "Failed to suppress the row-based replication log." " (table name: %s, chunk id: %d)",
              table_name, chunk_id);
    er_set (ER_ERROR_SEVERITY, ARG_FILE_LINE, ER_CHKSUM_GENERIC_ERR, 2, err_msg, error);
    return error;
  }

res = db_execute (query, &query_result, &query_error);

/* resume row-based replication right after the local execution; keep its result as the error baseline,
 * an actual execution failure below supersedes it */
error = db_set_suppress_repl_on_transaction (false);     // 1741행 — 반환값 검사·er_set 없음

if (res >= 0)
  {
    db_query_end (query_result);
    res = chksum_update_master_checksum (parser, table_name, chunk_id);
    if (res < 0) { error = res; }
  }
else
  {
    ... er_set (... res); error = res; }
```

`true`로 켤 때(1727행)는 실패 시 구체적인 `er_set` 메시지("Failed to suppress the row-based
replication log...")를 남기고 즉시 반환하는데, 정확히 대칭이어야 할 `false`로 끌 때(1741행)는
반환값을 `error`에 담기만 하고 **어떤 `er_set`도 호출하지 않는다**. 그 뒤 흐름은 `res`(쿼리 실행
결과)만 검사하므로, `db_execute()`와 `chksum_update_master_checksum()`이 둘 다 성공(`res >= 0`)하면
`error`는 1741행에서 대입된 값(즉 억제 해제 실패 코드) 그대로 함수 밖으로 반환된다.

**문제 시나리오**

`db_set_suppress_repl_on_transaction()`은 내부적으로 `CHECK_CONNECT_ERROR()` → 서버 왕복(`logtb_set_suppress_repl_on_transaction`)
경로를 타므로, 서버와의 연결이 그 짧은 순간에 끊기거나(네트워크 hiccup, 서버 재시작) 트랜잭션이
동시에 강제 종료되는 등 흔치는 않지만 실제로 있을 수 있는 상황에서 실패할 수 있다. 이 경우:

- 호출부(`chksum_check_and_calculate_checksum` 루프, `:2005-2022`)는 `error != NO_ERROR`를 보고
  `db_abort_transaction()`을 호출해 해당 청크 처리를 안전하게 되돌리므로 **데이터 정합성 자체는
  깨지지 않는다.**
- 다만 `error != ER_INTERRUPTED`이면 루프가 `break`로 checksumdb 전체를 중단하는데, 이때 터미널/로그에
  남는 메시지는 이 특정 실패에 대한 설명이 아니라 이전에 `er_set`된(또는 비어 있는) 에러 상태뿐이다.
  운영자 입장에서는 "checksumdb가 도중에 멈췄는데 왜 멈췄는지"를 알려주는 단서가 하나 빠지는 셈이다 —
  같은 함수 안 바로 위(1727행)의 대칭 코드와 비교하면 명백한 누락이다.

`true`/`false` 두 호출이 실질적으로 같은 실패 가능성(연결 문제)을 공유하는데 한쪽만 진단 메시지를
남기는 비대칭은, 리포트가 반복적으로 지적해 온 "장애 원인 추적 가능한 로그" 원칙(총평 §3)에
어긋나는 사소한 결함이다. 데이터 정합성에 영향이 없고 발생 빈도도 낮아 심각도는 사소로 평가한다.

**제안**: 1741행도 1727행과 대칭으로 `error != NO_ERROR`일 때 "Failed to resume the row-based
replication log. (table name: %s, chunk id: %d)" 같은 `er_set` 메시지를 추가한다.
