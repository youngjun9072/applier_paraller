## 문제 14

**[중요] `ALTER VIEW`/`ALTER VCLASS`에 `REPLICATION` 옵션을 지정해도 아무 검증 없이 성공해, 뷰에 의미 없는 복제 플래그가 영구히 남는다**

위치:
- 문법: `src/parser/csql_grammar.y` `alter_stmt`(3565-3625행, `opt_class_type`로 받은
  `entity_type`을 각 alter 노드에 그대로 채움 — `CLASS`/`TABLE`→`PT_CLASS`,
  `VCLASS`/`VIEW`→`PT_VCLASS`, 5717-5738행), `alter_clause_for_alter_list`의
  `class_replication_spec` 분기(5862-5871행, entity_type을 전혀 보지 않고 무조건
  `PT_CHANGE_REPLICATION` 코드를 세팅)
- 세만틱 체크: `src/parser/semantic_check.c` `pt_check_alter()`(4785행 이하). 4858-4871행에서
  `entity_type`이 실제 객체 종류(`db_is_class`/`db_is_vclass`)와 일치하는지만 확인하고, 이후
  4882행부터 시작하는 `switch (code)`에는 `PT_CHANGE_REPLICATION`에 대응하는 `case`가 아예
  없다(`PT_CHANGE_OWNER`(5268), `PT_CHANGE_COLLATION` 등은 각각 case가 있는데 REPLICATION만
  없음 — grep 전수 확인). 즉 REPLICATION 절이 붙은 ALTER는 이 함수를 그냥 통과한다.
- 실행: `src/query/execute_schema.c` `do_alter_change_replication()`(11729-11827행).
  이 함수 전체에 `alter->info.alter.entity_type`을 읽거나 검사하는 코드가 단 한 줄도 없다.
  `entity_name`으로 `db_find_class()`(11763행, VCLASS도 그대로 찾아짐)를 호출하고,
  `dbt_edit_class()`/`sm_set_class_flag(class_mop, SM_CLASSFLAG_DATA_REPLICATION_OFF, ...)`
  (11783행, 11796행)로 곧장 플래그를 세팅한다. `SM_CLASS`는 일반 테이블과 뷰가 같은 구조체를
  쓰므로(`class_object.h`) 이 호출은 뷰에 대해서도 에러 없이 성공한다.

로직 설명(콜체인): `ALTER VIEW v REPLICATION=OFF;` 실행 시
`csql_grammar.y`가 `entity_type=PT_VCLASS`, `code=PT_CHANGE_REPLICATION`인 alter 노드를 만들고
→ `pt_check_alter()`가 "`v`가 실제로 VCLASS인가"만 확인하고 통과시키고(REPLICATION 전용 검사
없음) → `do_alter()`가 `case PT_CHANGE_REPLICATION: do_alter_change_replication(...)`으로
디스패치(`execute_schema.c:2033-2034`) → `do_alter_change_replication()`이 entity_type을
한 번도 안 보고 `v`의 `SM_CLASS.flags`에 `SM_CLASSFLAG_DATA_REPLICATION_OFF`를 그대로 세팅한다.
`CREATE TABLE ... LIKE`(문제 3, K-21)나 파티션 상속처럼 REPLICATION이 실제로 의미를 갖는
경로들과 달리, VIEW는 애초에 자기 데이터(heap)가 없어 DML 복제 대상이 될 수 없는데도
이 경로만 문지기가 아예 없다.

문제 시나리오:
- 실무에서 흔한 상황: HA를 쓰지 않는(`HA_DISABLED()==true`, 즉 기본 SA/CS 단일 모드 — 대부분의
  설치 환경) DB에서, 사용자가 테이블에 걸어 온 습관대로 뷰에도 `ALTER VIEW my_view
  REPLICATION=OFF;`를 실행하거나, 스크립트에서 테이블/뷰를 구분하지 않고 일괄로 REPLICATION
  옵션을 붙이는 마이그레이션을 짠 경우.
- 문법·세만틱·실행 어디에서도 "뷰에는 적용할 수 없다"는 에러가 나지 않고 그냥 성공한다.
  이후 `SHOW CREATE VIEW my_view`나 `unloaddb` 덤프에는 `REPLICATION=OFF`가 찍힌다(이미
  K-68/문제 8류 지적이 다루는 "뷰에 REPLICATION이 출력된다"는 증상의 실제 발생 경로가 바로
  이것이다 — 원래는 뷰 생성 문법 자체에 REPLICATION 옵션이 없어 이 값이 항상 기본값(ON)이어야
  하는데, ALTER 경로로 우회해 OFF까지 심을 수 있다).
- 사용자는 "뷰에 복제 옵션을 껐다"고 믿지만 뷰는애초에 DML 복제 대상이 아니므로 아무 실질
  효과가 없다. 나중에 이 뷰를 기반으로 `CREATE TABLE ... LIKE view_name`류 작업을 하거나
  `db_class`를 스크립트로 점검하는 운영자는 "왜 뷰에 REPLICATION 플래그가 있고 심지어 OFF로
  꺼져 있지?"라는 혼란을 겪는다. HA가 나중에 켜지면 이 플래그 자체는 여전히 무해하지만,
  뷰 스키마를 unload/reload하는 도구 체인에서 예상 못 한 REPLICATION 절이 계속 따라다닌다.

제안: `do_alter_change_replication()` 진입 시(또는 `pt_check_alter()`의
`PT_CHANGE_REPLICATION` case를 새로 만들어) `alter->info.alter.entity_type == PT_VCLASS`
(또는 `db_is_vclass(class_obj) > 0`)이면 "REPLICATION 옵션은 TABLE에만 적용 가능합니다" 류의
명확한 에러로 거부해야 한다. `PT_ADD_ATTR_MTHD`가 `type == PT_VCLASS`일 때 AUTO_INCREMENT나
컬럼 visibility 설정을 막는 것(`semantic_check.c:4885-4901`)과 동일한 패턴을 REPLICATION에도
적용하면 된다.
