# 코드 리뷰 리포트 — 사용자(SQL 실무자) · 1년차

> **2차 재리뷰(기준 `734f4959d`)** — upstream 동기화(#7678, #7697 반영) 이후 재검증. 1차 리포트(기준 `44468ed73`)의 문제 1~14를 새 HEAD에서 전부 재확인했고, 동기화 델타(#7678/#7697)가 새로 들여온 코드에서 문제 15를 추가로 발굴했다.

## 페르소나 소개

저는 CUBRID를 실무에서 쓴 지 1년 된 SQL 실무자입니다. C++ 코드를 매일 짜는 사람은 아니지만, `CREATE TABLE` / `ALTER TABLE`을 치고 결과를 보는 건 매일 하는 일입니다. 이번 리뷰에서는 두 가지 눈으로 코드를 봤습니다.

1. **사용자 눈**: 이 DDL을 쳤을 때 성공/실패 메시지가 정확한가, `SHOW CREATE TABLE`/`db_class` 출력이 사실과 맞는가, 문법을 대소문자·생략·중복으로 써도 똑같이 동작하는가.
2. **1년차 개발자 눈**: 코드를 처음 읽으면서 "이 변수 이름이 왜 이렇지", "이 주석이랑 코드가 다른데", "이 함수 어디서 쓰는 거지" 싶은 지점을 그냥 넘기지 않고 clangd로 실제 호출 관계까지 따라가 확인했습니다.

## 총평 (2차 재리뷰)

기준 diff가 `23789cbfa...44468ed73`(40파일)에서 `b646647ec...734f4959d`(35파일, +1,444/−57)로 바뀌었지만, 실제로 제가 1차에서 짚었던 14건이 살아 있던 파일(`execute_schema.c`, `schema_manager.c`, `class_object.c`, `util_cs.c`, `checksumdb.c` 등)은 이번 동기화(#7678/#7697)에서 손을 대지 않았습니다. clangd로 14건 전부를 새 HEAD 코드에서 한 줄 한 줄 다시 확인한 결과 **14건 모두 그대로 살아 있고(위치 이동 없음), 동기화로 해소되거나 오판으로 폐기된 건은 하나도 없습니다.**

동기화 델타(#7678 SBR/checksumdb 버그 수정, #7697 KILL QUERY 무시 버그 근본 수정)는 그 자체로는 잘 만들어졌습니다 — 특히 #7697이 `heap_is_replication_class()`(bool 반환 + `assert(false)`)를 `heap_get_class_repl_on()`(에러코드 반환 + out-parameter)으로 교체한 것은 정확히 문제 4에서 제가 우려했던 바로 그 수정 패턴입니다. 그런데 **바로 그 옆 동기화 커밋(#7678)이 새로 추가한 `is_replication_class()`(execute_statement.c)가 똑같은 "에러를 삼키는 bool + assert(false)" 패턴을 그대로 반복**하고 있는 것을 새로 발견했습니다(문제 15). 한쪽에서 부채를 갚는 동안 다른 쪽에서 같은 모양의 빚을 새로 내는 패턴이 이 기능 영역에서 세 번째(구 `heap_is_replication_class`, `sm_is_replication_class`, 이번 `is_replication_class`)로 반복되고 있다는 점을 다시 한 번 강조합니다.

그 외 총평은 1차와 동일합니다: `do_alter()`의 HA 복제 제약 재검사 로직(문제 1)이 여전히 "맨 처음 절"만 보고 있고, 파티션 승격 시 복합 UNIQUE 키가 부분적으로 깨지는 문제(문제 3), `rkcheck`가 로그 파일을 못 열면 죽는 문제(문제 2) 등도 그대로 남아 있습니다.

## 문제 1 — [심각도: 치명, 재검증: 유지] `do_alter()`가 ALTER 절을 여러 개 나열해도 항상 "첫 번째 절"의 종류만 보고 RK 재검사 여부를 결정한다

**위치**: `src/query/execute_schema.c:1838-2065` (특히 1854번 줄과 2051번 줄 비교) — *새 HEAD에서도 줄 번호 동일, 코드 변경 없음*

**로직 설명**: `do_alter()`는 `for (crt_clause = alter; crt_clause != NULL; crt_clause = crt_clause->next)`로 ALTER 문의 각 절을 순회합니다. 매 반복마다 1854번 줄에서
```c
const PT_ALTER_CODE alter_code = crt_clause->info.alter.code;
```
로 "지금 처리 중인 절의 종류"를 지역변수 `alter_code`에 정확히 담습니다. 그런데 정작 RK 재검사가 필요한지 판단하는 2051번 줄은
```c
if (!need_check_repl_constraint && IS_REPL_CONSTRAINT_RELATED_ALTER (alter->info.alter.code))
```
로, 방금 만든 지역변수 `alter_code`를 쓰지 않고 함수 파라미터 `alter`(=ALTER 문의 **첫 번째** 절, 루프 내내 절대 바뀌지 않음)의 코드를 봅니다. `alter`와 `crt_clause`는 이름이 비슷하지만 전혀 다른 포인터입니다. clangd로 확인해보면 `alter_code`는 1854, 1874, 1997번 줄 세 곳에서만 쓰이고 2051번 줄에서는 정작 쓰이지 않습니다.

**문제 시나리오**: `check_ha_repl_constraint()`를 다시 부를지 여부(`need_check_repl_constraint`)가 "ALTER 문에 포함된 절 중 하나라도 RK를 건드리는 종류인가"가 아니라 "**맨 처음 절**이 RK를 건드리는 종류인가"로 결정됩니다.
- `ALTER TABLE t CHANGE COLUMN c c INT, DROP CONSTRAINT uk_c;` — 첫 절이 `PT_CHANGE_ATTR`(매크로 목록에 없음)이므로 `need_check_repl_constraint`가 **절대 true가 되지 않습니다.** 두 번째 절이 명백히 RK를 제거하는 `DROP CONSTRAINT`인데도 최종 검사가 실행되지 않고 통과됩니다.
- 반대로 `ALTER TABLE t DROP PRIMARY KEY, ADD PRIMARY KEY(new_col);`처럼 **우연히** 첫 절이 매크로 목록에 있는 종류(`PT_DROP_PRIMARY_CLAUSE`)면 정상 동작하는 것처럼 보입니다.
- 이 검사는 애초에 #6637에서 "여러 절을 한 문장에 나열해도 최종 상태 기준으로 한 번만 검사하자"는 목적으로 `do_alter_one_clause_with_template()`에서 `do_alter()`로 옮겨졌던 코드입니다. 지금 버그는 그 목적 자체를 무력화합니다.

**제안**: 2051번 줄의 `alter->info.alter.code`를 `alter_code`로 바꿉니다.

## 문제 2 — [심각도: 치명, 재검증: 유지] `rkcheck` 유틸리티가 위반 목록 파일을 열지 못하면 NULL `FILE*`에 그대로 `fprintf`를 호출한다

**위치**: `src/executables/util_cs.c` — `open_violation_list_file()`(2856번 줄) 및 `rkcheck()` 본문(3267번 줄~, `fp` 사용부는 3320-3376번 줄) — *새 HEAD에서도 줄 번호 동일*

**로직 설명**: `rkcheck()`에서
```c
fp = open_violation_list_file (database_name, arg->command_name, violation_list_file, PATH_MAX);
```
을 호출한 뒤, 반환값 `fp`가 `NULL`인지 **한 번도 검사하지 않고** 곧바로
```c
PRINT_SECTION_TITLE (fp, RK_CONSTRAINT_VIOLATIONS_SECTION_TITLE);   // fprintf(fp, ...)
...
err = check_repl_constraint_violations (classes, fp, check_rk_constraint, &rk_violation_count);
```
로 넘어갑니다. `open_violation_list_file()` 내부는 결국 `fopen(file_path, "w")`을 그대로 리턴하는 함수라서, 로그 디렉터리 권한 문제·디스크 풀·경로 이슈 등으로 `fopen`이 실패하면 `fp == NULL`이 됩니다.

**문제 시나리오**: `rkcheck`은 `cubrid hb start` 실행 전에 RK/FK 위반을 미리 잡아서 HA 기동 자체를 막는 안전장치입니다. 그런데 정작 로그 디렉터리에 쓸 수 없는 상황(운영 환경에서 디스크가 꽉 찼거나 권한이 꼬였을 때)이 되면, 이 안전장치가 "위반 없음/있음"을 알려주는 대신 NULL 포인터 역참조로 그냥 죽어버립니다. 안전장치가 필요한 바로 그 순간에 안전장치 자체가 크래시하는 셈입니다.

**제안**: `fp == NULL`이면 `PRINT_AND_LOG_ERR_MSG`로 명확한 에러를 남기고 `err = ER_FAILED`로 `end1`으로 점프하도록 방어 코드를 추가합니다.

## 문제 3 — [심각도: 중요, 재검증: 유지] 파티션 승격(`do_promote_partition`)에서 복합 NOT NULL UNIQUE 키의 두 번째 이후 컬럼이 잘못 초기화된다

**위치**: `src/query/execute_schema.c:7884-7981` (특히 7943-7959번 줄 루프, `has_notnull_unique_constraints()`는 7837-7864번 줄) — *새 HEAD에서도 줄 번호 동일*

**로직 설명**: 파티션을 일반 테이블로 승격할 때, PK와 "NOT NULL UNIQUE" 속성은 보존해야 합니다. 코드는 함수 진입부에서 `bool has_notnull_unique = false;`를 선언하고, 속성 리스트를 순회하며
```c
if (!has_notnull_unique && has_notnull_unique_constraints (smattr))
  {
    has_notnull_unique = true;
  }
else
  {
    smattr->flags &= ~(SM_ATTFLAG_UNIQUE);
    smattr->flags &= ~(SM_ATTFLAG_REVERSE_UNIQUE);
  }
```
로 처리합니다. 문제는 `has_notnull_unique`가 "테이블 전체에 NOT NULL UNIQUE가 하나라도 있었는지"를 기억하는 **전역 플래그**로 쓰이면서 동시에 "이번 컬럼을 보존할지"를 결정하는 가드로도 재사용된다는 점입니다.

**문제 시나리오**: `UNIQUE(col_a, col_b)`처럼 **두 컬럼으로 구성된** 복합 UNIQUE 제약이 있고 두 컬럼 모두 NOT NULL이면, 루프가 `col_a`를 만날 때 `has_notnull_unique`가 true로 세팅되어 `col_a`는 보존되지만, 곧이어 `col_b`를 만날 때는 `!has_notnull_unique`가 이미 거짓이라 else 분기로 빠져 `col_b`의 `SM_ATTFLAG_UNIQUE`/`SM_ATTFLAG_REVERSE_UNIQUE`가 제거됩니다. 결과적으로 승격된 테이블에는 `col_a`만 UNIQUE 플래그를 가진 반쪽짜리 메타데이터가 남습니다.

**제안**: "이번 컬럼을 보존할지"와 "테이블에 RK가 하나라도 있었는지"를 별도 변수로 분리합니다.

## 문제 4 — [심각도: 중요, 재검증: 유지·범위 확대] `sm_is_replication_class()`가 #7697에서 지적됐던 "에러를 삼키는 bool 반환 + assert(false)" 패턴을 그대로 반복한다

**위치**: `src/object/schema_manager.c:3389-3407` (정의, 줄 번호 동일) — 호출부는 재검증 결과 **3곳에서 4곳으로 늘었습니다**: `src/query/execute_schema.c:2063`, `:9796`, `:9835`, 그리고 새로 확인한 `src/object/object_printer.cpp:1138`(`describe_class()` — **`SHOW CREATE TABLE`의 REPLICATION 절 출력부**)

**로직 설명**: 이 함수는 1차 리뷰 이후로 전혀 수정되지 않았습니다.
```c
bool
sm_is_replication_class (MOP op)
{
  SM_CLASS *class_;

  if (op != NULL && au_fetch_class_force (op, &class_, AU_FETCH_READ) == NO_ERROR)
    {
      return !(class_->flags & SM_CLASSFLAG_DATA_REPLICATION_OFF);
    }

  assert (false);
  return false;
}
```
`op`가 `NULL`이거나 `au_fetch_class_force()`가 실패(권한 오류, 인터럽트 등)하면 에러 코드를 호출자에게 전혀 알리지 않고 `assert(false)` 후 그냥 `false`를 리턴합니다. 이는 정확히 PR #7697이 `heap_is_replication_class()`에서 근본 수정한 결함(인터럽트로 조회가 실패해도 그냥 false로 뭉개져 `KILL QUERY`가 무시된다)과 같은 모양의 코드인데, `heap_is_replication_class()`가 이번 동기화로 `heap_get_class_repl_on()`(에러코드+out-parameter)으로 교체된 것과 대조적으로 **`sm_is_replication_class()`는 손대지 않은 채 그대로 남아 있습니다.**

새로 확인한 호출부(`object_printer.cpp:1138`)는 특히 이 페르소나(사용자) 관점에서 중요합니다 — `SHOW CREATE TABLE`이 클래스의 REPLICATION 옵션을 표시할 때 바로 이 함수를 호출합니다:
```c
if (sm_is_replication_class (class_op))
  {
    m_buf (", REPLICATION=ON");
  }
else
  {
    m_buf (", REPLICATION=OFF");
  }
```

**문제 시나리오**: `au_fetch_class_force()`가 인터럽트나 권한 문제로 실패하는 경계 상황에서, 디버그 빌드는 `assert(false)`로 죽고 릴리스 빌드는 조용히 `false`(REPLICATION=OFF)를 반환합니다. `do_alter()` 경로(문제 1과 동일 위치)에서는 RK 재검사가 스킵되어 위험한 상태로 ALTER가 통과할 수 있고, `SHOW CREATE TABLE`(`describe_class`) 경로에서는 실제로는 REPLICATION=ON인 테이블이 화면에는 `REPLICATION=OFF`로 표시될 수 있습니다 — 이 페르소나가 가장 민감하게 보는 "출력 정확성" 문제로 직결됩니다.

**제안**: `bool` 대신 에러 코드를 리턴하고 결과는 out-parameter로 주는 형태(#7697이 실제로 적용한 패턴)로 바꿉니다. 이 기능 영역에 리뷰 체크리스트로 "bool만 반환하는 조회 함수 신규 추가 금지"를 넣는 것을 다시 한번 제안합니다.

## 문제 5 — [심각도: 중요, 재검증: 유지] 파티션 승격 전용으로 보이는 PK/UK 상속 로직이 클래스 정의 플래트닝·FK 속성 복사 등 범용 경로에도 그대로 연결되어 있다

**위치**: `src/object/class_object.c` — `classobj_copy_pk_and_uk_notnull_constraints()`(561번 줄), `classobj_init_attribute()`(4817번 줄, 신규 호출 삽입) — *새 HEAD에서도 동일*

**로직 설명**: `classobj_init_attribute(src, dest, copy=1)`에 이번 기능 diff가
```c
if (src->constraints != NULL)
  {
    error = classobj_copy_pk_and_uk_notnull_constraints (src, dest);
    ...
  }
```
를 추가했습니다. clangd로 `classobj_copy_attribute()`(이 로직을 타는 진입점)의 호출자를 추적하면 3곳이 나옵니다.
- `class_object.c:4945` — `classobj_copy_attlist()` 내부, 파티션 승격(`do_promote_partition`)이 쓰는 경로.
- `schema_manager.c:8102` — `make_component_from_candidate()`, **모든 클래스 정의에서 속성을 플래트닝(상속 해석)할 때** 호출되는 함수. `UNDER` 상속을 쓰는 일반 `CREATE TABLE`에서도 실행됩니다.
- `schema_manager.c:11595` — `allocate_disk_structures()`가 FK 제약의 참조 속성 배열을 복사할 때.

**문제 시나리오**: 파티션 승격이 아닌 **일반 `CREATE TABLE ... UNDER parent`** 상속 상황에서, `parent`에 NOT NULL UNIQUE 컬럼이 있으면 자식 속성에도 부모 BTID를 가리키는 제약 객체가 조용히 붙습니다. 이 정보가 이후 스키마 조회·제약 카운트 등에서 참조되면 "자식 테이블이 실제로 갖고 있지 않은 인덱스(BTID)를 가진 것처럼" 오인될 위험이 있습니다.

**제안**: 이 로직을 `do_promote_partition()` 경로에 한정하거나, 최소한 다른 두 호출 경로에 대해서도 의도된 것인지 확인/문서화가 필요합니다.

## 문제 6 — [심각도: 보통, 재검증: 유지] `do_alter_change_replication()`이 `do_alter_change_tbl_comment()`의 세이브포인트 이름을 복붙해서 그대로 쓴다

**위치**: `src/query/execute_schema.c:11747`(`do_alter_change_replication`), 비교 대상 `:11505`(`do_alter_change_tbl_comment`) — *새 HEAD에서도 줄 번호 동일*

**로직 설명**: REPLICATION 옵션 변경을 처리하는 `do_alter_change_replication()`은
```c
error = tran_system_savepoint (UNIQUE_SAVEPOINT_CHANGE_TBL_COMMENT);
...
(void) tran_abort_upto_system_savepoint (UNIQUE_SAVEPOINT_CHANGE_TBL_COMMENT);
```
로 `UNIQUE_SAVEPOINT_CHANGE_TBL_COMMENT`를 그대로 사용합니다. `execute_schema.c` 안의 다른 모든 `do_alter_change_*` 함수는 각자 자기 이름을 딴 전용 세이브포인트 상수를 갖는데, REPLICATION 처리 함수만 옆 함수 것을 그대로 갖다 썼습니다.

**문제 시나리오**: `ALTER TABLE t COMMENT='x', REPLICATION=OFF;`처럼 코멘트 변경과 REPLICATION 변경을 한 문장에 같이 쓰면, 같은 이름의 세이브포인트가 한 트랜잭션 안에서 두 번 찍힙니다. 당장 크래시는 없지만 코드 가독성·유지보수 위험이 있습니다.

**제안**: `UNIQUE_SAVEPOINT_CHANGE_REPLICATION` 같은 전용 상수를 새로 정의해서 사용합니다.

## 문제 15 — [심각도: 중요, 신규] 동기화(#7678)가 새로 추가한 `is_replication_class()`(execute_statement.c)도 같은 "에러를 삼키는 bool + assert(false)" 패턴을 반복한다

**위치**: `src/query/execute_statement.c:3200-3218`(정의), 호출부 `:3282`(`spec_has_replication_class()` 내부, `is_data_repl_log_enabled()`가 모든 `USE_SBR` 힌트 INSERT/UPDATE/DELETE에서 호출)

**로직 설명**: 이번 동기화로 들어온 #7678(SBR 로그 복제 버그 수정, PR #6908)이 "REPLICATION=OFF 테이블은 SBR 로그도 만들지 않는다"는 규칙을 구현하면서 `is_data_repl_log_enabled()` / `spec_has_replication_class()` / `is_replication_class()`를 새로 추가했습니다. 그런데 그중 `is_replication_class()`는 이렇습니다.
```c
static bool
is_replication_class (const char *classname)
{
  DB_OBJECT *class_obj;

  if (classname == NULL)
    {
      return false;
    }

  class_obj = db_find_class (classname);
  if (class_obj == NULL)
    {
      assert (false);
      return false;
    }

  return sm_is_replication_class (class_obj);
}
```
`classname`이 `NULL`이 아닌데 `db_find_class()`가 클래스를 찾지 못하면(동시성 DDL로 테이블이 사라졌거나, 캐시된 실행계획을 재실행하는 중 등) `assert(false)` 후 `false`를 반환합니다. 이는 이 리포트의 **문제 4**(`sm_is_replication_class`)와 정확히 같은 결함 모양이고, PR 히스토리(#7697)가 "이 함수만 fetch 실패를 assert(false)로 봉인한다, 나머지 27곳은 전부 에러로 정상 전파한다"고 진단하며 근본 수정했던 바로 그 안티패턴이, 그 수정이 반영된 **동일한 동기화 커밋 안에서 다른 이름으로 다시 만들어졌습니다.**

**문제 시나리오**: `is_data_repl_log_enabled()`는 `USE_SBR` 힌트가 붙은 모든 INSERT/UPDATE/DELETE에서 실행되며, `checksumdb`가 매 청크마다 실행하는 REPLACE/UPDATE 문도 여기에 포함됩니다(#7678이 바로 이 경로에 `USE_SBR`을 강제했습니다). 이 경로 도중 대상 클래스 이름 조회에 실패하면(디버그 빌드는 `assert(false)`로 서버가 죽고, 릴리스 빌드는 조용히 "복제 대상 아님"으로 처리되어) 이 커밋이 고치려던 것과 같은 종류의 "REPLICATION 여부 오판으로 SBR 로그가 스킵/오생성되는" 문제가 이 좁은 실패 경로를 통해 재발할 수 있습니다.

**제안**: 문제 4와 동일한 처방 — `bool` 대신 에러코드+out-parameter 형태로 바꾸거나, 최소한 실패 시 `assert(false)`로 죽이지 말고 호출자가 실패를 구분할 수 있게 합니다. `heap_is_replication_class → heap_get_class_repl_on` 리팩토링을 이 함수와 `sm_is_replication_class()`에도 그대로 적용하는 것을 다시 한번 제안합니다.
