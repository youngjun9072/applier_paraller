## 총평

이 기능의 핵심 규칙은 단순합니다 — "HA에서 복제 대상 테이블은 반드시 복제 키(RK: PK 또는
NOT NULL UNIQUE)를 가져야 한다." 단일 절 DDL(예: `ALTER TABLE t DROP CONSTRAINT rk_only;`
단독 실행)에서는 이 규칙이 잘 지켜집니다. 문제는 제가 실무에서 실제로 쓰는 패턴들, 즉
**여러 절을 콤마로 묶은 ALTER**, **파티션 승격 같은 부가 경로**, **에러가 난 뒤 사용자에게
보여주는 메시지 문구**로 내려가면 구멍이 보인다는 점입니다. 특히 발견한 것 중 가장 심각한
두 가지는 (1) 다중 절 `ALTER TABLE`에서 RK 재검사 자체가 절 순서에 따라 통째로 스킵될 수
있다는 것, (2) RK 후보를 판정하는 로직이 DDL 검증 시점과 실제 복제 시점에 서로 다른 기준
(하나라도 NOT NULL vs 전부 NOT NULL)으로 따로 구현돼 있어서, **`CREATE TABLE`은 성공하지만
그 테이블은 실제로는 복제될 수 없는** 모순 상태를 만들 수 있다는 것입니다. 두 건 모두 이번
동기화로도 전혀 손대지지 않아 그대로 남아 있습니다.

세 번째로 심각했던 문제("에러를 삼키는 `assert(false); return false;` 패턴이 PR #7697이 고친
바로 그 자리에 세 곳이나 새로 있다")는 이번 동기화로 **절반만** 해소됐습니다. 서버(스토리지)
계층의 `heap_file.c` 함수는 정확히 #7697이 의도한 방식(에러 코드 반환 + out-parameter)으로
교체됐지만, 클라이언트 계층의 나머지 두 함수(`schema_manager.c`의 `sm_is_replication_class()`,
`execute_statement.c`의 정적 함수 `is_replication_class()`)는 여전히 같은 "삼키는" 패턴
그대로입니다 — 아래 문제 3 참조.

## 문제 1

**[심각도: 치명] 다중 절 ALTER TABLE에서 RK 재검사 게이트가 "첫 번째 절"만 보고 판단한다 — 절 순서에 따라 통째로 스킵된다**

위치: `src/query/execute_schema.c:1838`(변수 선언), `:2051-2054`(게이트), `:109-114`(매크로) — HEAD `734f4959d`에서도 동일 위치

로직 설명: `do_alter()`는 콤마로 이어진 여러 ALTER 절을 `for (crt_clause = alter; ...; crt_clause = crt_clause->next)`로
순회하며 각 절을 처리합니다. 이때 각 절이 실제로 뭘 하는지는 지역변수 `const PT_ALTER_CODE
alter_code = crt_clause->info.alter.code;`(1852행)로 구해서 switch 분기에 씁니다. 여기까지는
절별로 정확합니다. 그런데 "모든 절 처리가 끝난 뒤 RK/FK 제약을 다시 검사할지" 여부를 켜는
코드는 다음과 같습니다.

```c
if (!need_check_repl_constraint && IS_REPL_CONSTRAINT_RELATED_ALTER (alter->info.alter.code))
  {
    need_check_repl_constraint = true;
  }
```

여기서 쓰인 것은 방금 처리한 `crt_clause`나 지역변수 `alter_code`가 아니라 **함수 인자로 받은
`alter`, 즉 절 목록의 맨 처음(head) 노드**입니다. `alter`는 루프 내내 재대입되지 않으므로,
루프를 몇 바퀴 돌든 이 조건은 **첫 번째 절의 종류만 매번 다시 확인**합니다. `IS_REPL_CONSTRAINT_RELATED_ALTER`
목록(`PT_ADD_ATTR_MTHD`/`PT_DROP_ATTR_MTHD`/`PT_DROP_CONSTRAINT`/`PT_DROP_PRIMARY_CLAUSE`)에
첫 절이 안 들면, 뒤에 오는 절이 실제로 RK를 없애더라도 `need_check_repl_constraint`는 끝까지
`false`로 남아 최종 검사(2059행 `check_ha_repl_constraint`) 자체가 실행되지 않습니다.

문제 시나리오: HA 모드, `REPLICATION=ON`이고 RK가 PK 하나뿐인 테이블 `orders`에 대해 실무에서
흔한 패턴인 "코멘트도 갱신하면서 제약도 정리"하는 문장을 씁니다.

```sql
ALTER TABLE orders COMMENT='2026-08 정리', DROP PRIMARY KEY;
```

첫 절은 `PT_CHANGE_TABLE_COMMENT`로 게이트 목록에 없으므로 `need_check_repl_constraint`가
켜지지 않습니다. 두 번째 절 `DROP PRIMARY KEY`는 정상 실행되어 테이블의 유일한 RK가 사라지지만,
문장은 **에러 없이 성공**합니다. 결과적으로 `REPLICATION=ON`인데 RK가 전혀 없는 테이블이
만들어지고, 이후 이 테이블에 대한 DML은 슬레이브로 정상 복제되지 않거나 log applier가 대상을
찾지 못해 에러를 냅니다 — 이 기능 전체가 막으려던 바로 그 상황입니다. 절 순서만 바꿔
`DROP PRIMARY KEY, COMMENT='2026-08 정리'`로 쓰면(첫 절이 `PT_DROP_PRIMARY_CLAUSE`) 우연히
검사가 걸려 에러가 나므로, **똑같은 의도의 문장이 절 순서만 바뀌어도 성공/실패가 갈리는**
비직관적인 동작입니다.

제안: 게이트 조건을 현재 처리 중인 절의 코드(`alter_code`, 즉 `crt_clause->info.alter.code`)로
바꿔야 합니다. `IS_REPL_CONSTRAINT_RELATED_ALTER (alter_code)`. 검사 자체는 루프 밖에서 최종
상태를 1회만 보는 지금 구조(PR #6637의 취지)를 유지하되, "검사가 필요한지" 판정만 절별로 OR
되도록 고쳐야 합니다.

**재검증**: 유지. `git diff 44468ed73 HEAD`로 확인한 결과 `execute_schema.c`는 이번 동기화에서
전혀 변경되지 않았다 — 코드가 1바이트도 다르지 않다.

## 문제 2

**[심각도: 치명] RK가 있는지 판정하는 로직이 두 군데 따로 있고 기준이 다르다 — CREATE는 통과하는데 실제로는 복제되지 않는 테이블이 만들어질 수 있다**

위치: DDL 검증 경로 `src/object/class_object.c:95-98`(매크로 `IS_HA_REPLICATION_KEY_CONSTRAINT`),
`:2285`, `src/object/schema_manager.c:16108-16128`(`sm_has_non_null_attribute`) /
실제 복제 경로 `src/base/object_representation_sr.c:4687-4722`(`or_is_replication_candidate_key`)
— HEAD `734f4959d`에서도 동일 위치

로직 설명: `CREATE TABLE ... REPLICATION=ON`이 HA에서 통과하려면 `check_ha_repl_constraint()`
(`execute_schema.c:9861`)가 `classobj_has_class_repl_key_constraint()`를 호출해 RK 유무를
판정합니다. 이 함수는 제약 목록을 돌며 매크로 `IS_HA_REPLICATION_KEY_CONSTRAINT(c)`로 각
제약이 RK 자격이 있는지 봅니다.

```c
#define IS_HA_REPLICATION_KEY_CONSTRAINT(c) \
  ((c)->type == SM_CONSTRAINT_PRIMARY_KEY || \
    (SM_IS_CONSTRAINT_UNIQUE_FAMILY((c)->type) && \
     sm_has_non_null_attribute((c)->attributes)))
```

`sm_has_non_null_attribute()`는 함수 자신의 주석에 "적어도 하나(at least one)"라고 명시돼
있는 것처럼, 제약에 속한 컬럼 중 **단 하나라도** NOT NULL이면 참을 반환합니다. 즉
`UNIQUE(a, b)`에서 `a`만 NOT NULL이고 `b`는 NULL 허용이어도 이 매크로는 "RK 있음"으로
판정합니다.

반면 실제로 마스터가 슬레이브에 보낼 RK를 서버(스토리지) 레벨에서 고르는 함수는
`btree_get_rkey_btid()`(`btree.c:8264`)가 인덱스마다 호출하는 `or_is_replication_candidate_key()`입니다.
이쪽은 UNIQUE 계열이면 **인덱스에 속한 모든 컬럼**을 순회하며 하나라도 `is_notnull`이
아니면 그 자리에서 false를 반환합니다(전부 NOT NULL이어야 RK 후보). 즉 같은 코드베이스
안에 "RK 자격 있음"을 판단하는 기준이 **DDL 시점(하나라도 NOT NULL)** 과
**복제 시점(전부 NOT NULL)** 으로 서로 다르게 두 벌 존재합니다.

문제 시나리오: HA 모드에서

```sql
CREATE TABLE t (a INT NOT NULL, b INT, UNIQUE(a, b)) REPLICATION=ON;
```

을 실행하면, PK가 없어도 `check_ha_repl_constraint()`는 "RK 있음"으로 보고 **생성에
성공**합니다(`SHOW CREATE TABLE`에도 `REPLICATION=ON`으로 정상 표시됩니다). 그러나 이 테이블에
`INSERT`/`UPDATE`가 발생하면 `locator_add_or_remove_index_internal()`/`locator_update_index()`가
호출하는 `or_is_replication_candidate_key()`는 `b`가 NULL 허용이라는 이유로 이 UNIQUE를 RK
후보에서 탈락시킵니다. PK도 없으므로 `btree_get_rkey_btid()`는 끝내 RK BTID를 찾지 못하고
복제 로그의 검색 키가 비게 됩니다. 사용자 입장에서는 "분명 DDL 검증을 통과시킨 REPLICATION=ON
테이블"인데 실제로는 슬레이브에서 행을 특정할 방법이 없는, DDL 성공과 런타임 동작이 어긋나는
상태가 됩니다. (rkcheck의 `check_rk_constraint()`도 같은 `classobj_has_class_repl_key_constraint()`를
쓰므로, HA 기동 전 사전 점검에서도 이 케이스는 걸러지지 않습니다.)

제안: `sm_has_non_null_attribute()`를 RK 판정에 재사용하지 말고, `or_is_replication_candidate_key()`와
동일하게 "제약에 속한 모든 컬럼이 NOT NULL"인지 확인하는 전용 함수로 교체해 두 판정 기준을
하나로 합쳐야 합니다.

**재검증**: 유지. `class_object.c`/`schema_manager.c`/`object_representation_sr.c` 모두 이번
동기화 대상 파일이 아니며, 코드가 그대로다.

## 문제 3

**[심각도: 치명 → 중요로 하향] 복제 클래스 판별 함수의 "에러를 삼키는" 패턴 — 서버 계층은 #7697로 해소됐으나 클라이언트 계층 두 곳은 그대로 남아 있다**

위치(유지): `src/object/schema_manager.c:3394-3407`(`sm_is_replication_class`),
`src/query/execute_statement.c:3200-3216`(정적 함수 `is_replication_class`)
위치(해소): `src/storage/heap_file.c` — 옛 `heap_is_replication_class()`는 삭제되고
`heap_get_class_repl_on()`(`:11084-11115`, `heap_file.h:469`)으로 교체됨

로직 설명: PR 히스토리(#6467, #6908, #7697)를 보면 이 코드베이스는 이미 한 번 값비싼 교훈을
치렀습니다. `heap_is_replication_class()`가 bool만 반환하다가, `pgbuf_fix()`가 인터럽트
(`KILL QUERY`)로 실패했을 때 이를 그냥 "복제 대상 아님(false)"으로 뭉개버려 트랜잭션 취소
자체가 무시되는 크래시/데이터 정합성 버그로 이어졌던 자리입니다.

**서버 계층은 실제로 고쳐졌습니다.** `git diff 44468ed73 HEAD -- src/storage/heap_file.c
src/storage/heap_file.h src/transaction/locator_sr.c`로 직접 대조한 결과, 이번 동기화가
정확히 이 함수를 다음과 같이 재작성했습니다.

```c
int
heap_get_class_repl_on (THREAD_ENTRY * thread_p, const OID * class_oid, bool * repl_on)
{
  ...
  if (heap_get_class_record (thread_p, class_oid, &recdes, &scan_cache, PEEK) != S_SUCCESS)
    {
      ASSERT_ERROR_AND_SET (error_code);
      heap_scancache_end (thread_p, &scan_cache);
      return error_code;   /* assert(false) 제거, 에러를 그대로 반환 */
    }
  *repl_on = or_class_is_replication_on (&recdes);
  ...
  return NO_ERROR;
}
```

호출부 `locator_add_or_remove_index_internal()`(`locator_sr.c:8038-8062`)도 `error_code`를
받아 `error_code != NO_ERROR`이면 곧바로 `goto error`로 전파하도록 함께 바뀌어, 1차 리포트가
지적한 대로 정확히 #7697이 택한 해법(에러 코드 반환 + out-parameter)으로 교체됐습니다.
1차 리포트가 지적했던 세 곳 중 이 한 곳은 완전히 해소됐다고 판단합니다.

**그런데 나머지 두 곳은 이번 동기화 대상 파일이 아니라 손대지지 않고 그대로 남아 있습니다.**

```c
/* schema_manager.c:3394 */
bool
sm_is_replication_class (MOP op)
{
  SM_CLASS *class_;
  if (op != NULL && au_fetch_class_force (op, &class_, AU_FETCH_READ) == NO_ERROR)
    {
      return !(class_->flags & SM_CLASSFLAG_DATA_REPLICATION_OFF);
    }
  assert (false);
  return false;
}
```

```c
/* execute_statement.c:3200 */
static bool
is_replication_class (const char *classname)
{
  DB_OBJECT *class_obj;
  if (classname == NULL) { return false; }
  class_obj = db_find_class (classname);
  if (class_obj == NULL)
    {
      assert (false);
      return false;
    }
  return sm_is_replication_class (class_obj);
}
```

이 두 함수는 heap_file.c 케이스와 성격이 조금 다릅니다 — `pgbuf_fix` 인터럽트가 아니라
`au_fetch_class_force()`(권한/캐시 조회 실패, 클래스 스키마 변경으로 인한 캐시 무효화 등)와
`db_find_class()`(클래스 조회 실패)의 실패를 삼킵니다. 하지만 "조회 실패를 assert로 봉인하고
`false`(=복제 대상 아님)로 대체한다"는 근본 패턴은 동일합니다. 실사용 경로로는:

- `sm_is_replication_class()`는 `do_alter()`의 최종 재검사(`execute_schema.c:2063`,
  문제 1과 같은 지점), FK 참조 검사(`check_ha_repl_fk_ref_all_replicated`,
  `execute_schema.c:9796`), `log_ha_repl_fk_ref_all_replicated`(`:9835`, rkcheck용) 등에서
  호출됩니다. 릴리스 빌드에서 `au_fetch_class_force()`가 실패하면(assert가 no-op이므로) 이
  함수는 조용히 `false`를 반환하고, `do_alter()`는 `!sm_is_replication_class(vclass)`가
  참이 되어 **RK 재검사 자체를 건너뜁니다**(`return NO_ERROR`) — 문제 1과 겹쳐서 발생하면
  RK 검사가 이중으로 무력화됩니다. FK 참조 검사 쪽은 반대로 정상적인 `CREATE TABLE ...
  FOREIGN KEY ...`를 "참조 대상이 복제 안 됨" 오탐으로 거부할 수 있습니다.
- `is_replication_class()`는 SBR 여부 판정 경로(`spec_has_replication_class`,
  `execute_statement.c:3282`)에서 쓰입니다.
- 디버그 빌드에서는 두 함수 모두 이런 조회 실패 상황에서 `assert(false)`로 서버가 그 자리에서
  abort합니다.

제안: 이 두 함수도 #7697/`heap_get_class_repl_on()`과 동일한 방식(에러 코드 반환 +
out-parameter, `assert(false)` 제거)으로 통일해야 합니다. 서버 계층 한 곳만 고치고 클라이언트
계층 두 곳을 그대로 두면, "에러를 삼키는 함수"라는 같은 결함이 여전히 절반 남아 있는
반쪽짜리 수정입니다.

**재검증**: 부분 해소. heap_file.c 부분은 `#7697`(정확히는 커밋 `9e094324b`)로 완전히
해소되어 리포트에서 제거했다. `schema_manager.c`/`execute_statement.c` 두 곳은 미해결로
유지하되, 서버 계층 한 곳이 이미 정석대로 고쳐진 선례가 존재하는 만큼(같은 파일 내 리팩토링
난이도가 낮다는 근거가 생겼으므로) 심각도를 치명에서 중요로 한 단계 낮췄다 — 인터럽트로
인한 서버 전체 크래시(치명급 가용성 문제)는 이제 heap_file.c 경로에서는 발생하지 않고,
남은 두 함수의 실패 경로(권한/캐시 조회 실패)는 더 드물고 파급 범위도 단일 DDL 문/세션에
가깝기 때문이다.

**[심각도: 보통] CREATE TABLE은 REPLICATION 옵션 중복 명시를 에러 처리하지만, ALTER TABLE은 같은 문장 안의 중복 REPLICATION 절을 조용히 허용한다**

ALTER TABLE t REPLICATION=OFF, REPLICATION=ON;

## 문제 7

**[심각도: 보통] 파티션 승격(promote) 시 복합(다중 컬럼) NOT NULL UNIQUE의 두 번째 이후 컬럼에서 UNIQUE 속성 플래그가 사라질 수 있다**

위치: `src/query/execute_schema.c:7837-7864`(`has_notnull_unique_constraints`),
`:7943-7959`(`do_promote_partition`의 순회 루프) — HEAD에서도 동일 위치

로직 설명: 이 diff는 파티션을 일반 테이블로 승격할 때 PK/NOT NULL UNIQUE 속성이 유실되던
기존 버그(PR #6552)를 마저 다듬으려는 목적으로, 속성을 하나씩 순회하며 "복제 키 자격이 있는
속성인지"를 판단하는 헬퍼를 새로 만들었습니다.

```c
static bool
has_notnull_unique_constraints (const SM_ATTRIBUTE * smattr)
{
  ...
  for (c = smattr->constraints; c != NULL; c = c->next)
    {
      if (c->type == SM_CONSTRAINT_UNIQUE || c->type == SM_CONSTRAINT_REVERSE_UNIQUE)
	{ has_unique = true; break; }
    }
  return has_not_null && has_unique;
}
```

그리고 호출부는 다음과 같이 **전역 1회성 플래그**로 씁니다.

```c
if (!has_notnull_unique && has_notnull_unique_constraints (smattr))
  { has_notnull_unique = true; }
else
  { smattr->flags &= ~(SM_ATTFLAG_UNIQUE); smattr->flags &= ~(SM_ATTFLAG_REVERSE_UNIQUE); }
```

`UNIQUE(a, b)`처럼 여러 컬럼에 걸친 복합 제약이 RK 후보인 경우, 이 제약은 컬럼 `a`의
`constraints`에도, 컬럼 `b`의 `constraints`에도 똑같이 걸려 있습니다. 순회 중 `a`를 먼저
만나면 `has_notnull_unique_constraints(a)`가 참이 되어 전역 플래그 `has_notnull_unique`가
`true`로 바뀝니다. 이어서 `b`를 처리할 차례가 되면, `b` 자신이 이 복합 제약의 정당한
구성 컬럼이고 NOT NULL이더라도 조건식 앞부분 `!has_notnull_unique`가 이미 거짓이므로
무조건 `else` 분기로 빠져 `b`의 `SM_ATTFLAG_UNIQUE`/`SM_ATTFLAG_REVERSE_UNIQUE` 플래그가
지워집니다. 즉 "같은 하나의 복합 RK 제약"인데 순회 순서상 나중에 오는 컬럼만 속성 플래그가
벗겨지는 비대칭적인 결과가 나옵니다.

문제 시나리오: 파티션 테이블에서 RK가 `PRIMARY KEY(a)`가 아니라 복합 `UNIQUE(a, b)`(둘 다
NOT NULL)로 설계된 테이블을 승격(`ALTER TABLE ... PROMOTE` 계열 동작)하면, 승격된 일반
테이블의 컬럼 `b`에서 UNIQUE 관련 속성 플래그만 소실됩니다. 실제 제약 정의(`ctemplate->properties`의
`SM_PROPERTY_UNIQUE` 목록)는 `has_notnull_unique`가 true인 동안은 드롭되지 않으므로 제약
자체가 완전히 사라지는지, 아니면 컬럼별 캐시 플래그만 어긋난 채로 남는지는 정적 분석만으로는
100% 단정하기 어려워 실제 승격 후 `db_class`/`SHOW CREATE TABLE`로 컬럼 속성이 정확히
일치하는지 실행 확인이 필요합니다. 다만 로직 자체가 "복합 제약의 구성 컬럼을 각각 독립된
것처럼 처리"하는 설계 결함인 것은 코드로 확정됩니다.

제안: "이 속성이 RK 후보 제약에 속하는가"는 컬럼 단위가 아니라 제약(constraint) 단위로
한 번만 판정하고, 그 제약에 속한 모든 컬럼에 동일하게 적용해야 합니다. 또한
`has_notnull_unique_constraints()`는 `SM_CONSTRAINT_UNIQUE`/`REVERSE_UNIQUE`만 보고
`SM_CONSTRAINT_PRIMARY_KEY`는 확인하지 않는데, PK 케이스는 이 함수가 아니라 별도 경로로
보존되고 있어 당장은 우연히 문제가 없어 보이지만, 이름(`has_notnull_unique_constraints`)과
실제로 커버하는 범위가 어긋나 있어 향후 유지보수 시 혼동의 소지가 있습니다.

**재검증**: 유지. 변경 없음.

## 문제 8

**[심각도: 보통] `REPLICATION`이 비예약 식별자 목록에서 빠져 완전한 예약어가 됐다 — 기존 컬럼/테이블명과 충돌**

```sql
SELECT replication FROM some_table;   -- syntax error
CREATE TABLE replication (...);       -- syntax error (따옴표 없이는)
```

가 문법 에러로 깨집니다. 우회하려면 `` `replication` `` 처럼 항상 따옴표로 감싸야 하는데,
기존에 배포된 애플리케이션 코드/마이그레이션 스크립트를 전부 고쳐야 하는 하위 호환성 문제입니다.
(스펙 리뷰 T-5로 이미 지적된 사안이지만, 코드를 직접 대조해 "고쳐지지 않고 그대로"임을
재확인했습니다.)

제안: `identifier` 규칙에 `| REPLICATION {{ SET_CPTR_2_PTNAME($$, $1, @$.buffer_pos); }}`를
추가해 다른 신규 키워드들과 동일하게 비예약어로 만들어야 합니다.

**재검증**: 유지. `csql_grammar.y` 변경 없음.

## 문제 9

**[심각도: 사소] `or_class_is_replication_on()`이 클래스 플래그 비트를 상수 대신 매직넘버로 하드코딩하고, 주석의 상수 이름도 실제와 다르다**

위치: `src/base/object_representation_sr.c:782-791` — HEAD에서도 동일 위치

로직 설명:

```c
bool
or_class_is_replication_on (RECDES * record)
{
  int flags = 0;
  int replication_off_flag = 32;	/* SM_CLASSFLAG_REPLICATION_OFF = 32 */
  ...
}
```

실제 플래그 상수는 `class_object.h`에 `SM_CLASSFLAG_DATA_REPLICATION_OFF = 32`로 정의돼
있습니다(이 이름 자체가 PR #6477에서 `SM_CLASSFLAG_REPLICATION_OFF` → `SM_CLASSFLAG_DATA_REPLICATION_OFF`로
리네임된 결과입니다). 그런데 이 서버 저수준 함수는 `class_object.h`를 include해서 상수를 쓰는
대신 값 `32`를 직접 박아 넣고, 주석에는 **리네임 이전의 옛 이름**을 적어 놓았습니다.

문제 시나리오: 지금 당장 잘못된 값을 읽는 것은 아니지만(현재는 32가 맞음), 향후 `SM_CLASS_FLAG`
enum에 새 플래그가 하나 더 끼어들어 값이 재배치되거나, 누군가 주석만 보고 "이 상수는 이미
`SM_CLASSFLAG_DATA_REPLICATION_OFF`로 이름이 바뀌었으니 여기 코드도 그거겠지"라고 잘못
판단해 값만 보고 넘어가면, 서버(스토리지) 계층이 읽는 REPLICATION on/off 판정이 클라이언트
계층의 실제 플래그 값과 소리 없이 어긋날 수 있습니다. `SHOW CREATE TABLE`/`db_class`(클라이언트
계층, `sm_is_replication_class` 경유)와 실제 복제 로그 생성 여부(서버 계층, 이제는
`heap_get_class_repl_on`이 경유하는 `or_class_is_replication_on`)가 서로 다른 값을 참조하게
되는 것이라 파급력이 작지 않습니다.

제안: 매직넘버 대신 `class_object.h`의 `SM_CLASSFLAG_DATA_REPLICATION_OFF`를 직접
참조하도록 고쳐야 합니다(빌드 의존성 문제로 헤더를 못 쓴다면 최소한 주석의 상수 이름을
현재 이름으로 갱신해야 합니다).

**재검증**: 유지. `object_representation_sr.c`의 이 함수 자체는 이번 동기화(같은 파일 내
`heap_get_class_repl_on`이 호출하는 `or_class_is_replication_on`은 변경 없음, 새로 생긴 것은
호출부인 `heap_file.c`뿐)로 바뀌지 않았다.

## 문제 10

**[심각도: 보통] checksumdb가 복제 억제 플래그를 원복하는 호출의 반환값을 무조건 최종 결과로 덮어써, 계산 자체는 성공했는데 실패로 보고될 수 있다**

위치: `src/executables/checksumdb.c:1716-1758`(`chksum_calculate_checksum`) — HEAD에서도
동일 위치, 바이트 단위로 동일

로직 설명: 이 함수는 체크섬 계산 쿼리를 실행하기 직전에 로우 기반 복제를 잠깐 억제했다가
실행 직후 다시 켭니다.

```c
error = db_set_suppress_repl_on_transaction (true);
...
res = db_execute (query, &query_result, &query_error);

/* resume row-based replication right after the local execution; keep its result as the error baseline,
 * an actual execution failure below supersedes it */
error = db_set_suppress_repl_on_transaction (false);

if (res >= 0)
  {
    db_query_end (query_result);
    res = chksum_update_master_checksum (parser, table_name, chunk_id);
    if (res < 0) { error = res; }
  }
else
  { ... error = res; }

return error;
```

주석은 "복제 재개 호출의 결과를 에러 기준값으로 두되, 아래의 실제 실행 실패가 그걸
덮어쓴다(supersede)"는 의도를 밝히고 있습니다. 그런데 실제 코드는 `res >= 0`(체크섬 계산
성공) 분기에서 `chksum_update_master_checksum()`도 성공(`res >= 0`)하면 `error`를 다시
쓰지 않습니다. 즉 "성공 경로에서는 덮어쓰지 않는다"는 뜻이 되어, 주석이 말한 "실패가
덮어쓴다"는 성립하지만 **"성공은 덮어쓰지 않는다"** 는 문제로 남습니다.

문제 시나리오: `db_set_suppress_repl_on_transaction (true)`는 성공했지만(그래서 체크섬 쿼리
자체는 정상 실행됨) 곧바로 이어지는 `db_set_suppress_repl_on_transaction (false)` 호출이
어떤 사유로 실패하는 드문 경우, `error`에는 이 실패 코드가 남습니다. 이후 체크섬 계산과
마스터 체크섬 갱신이 전부 정상 종료되어도 `error`는 갱신되지 않고 그대로 반환되어,
`checksumdb` 유틸리티는 **이 청크의 데이터 자체는 정상 비교가 끝났는데도** 사용자에게
실패로 보고합니다. 운영자는 존재하지 않는 데이터 불일치를 의심하며 원인을 찾느라 시간을
쓰게 됩니다.

제안: 성공 경로 진입 직후(`if (res >= 0)` 블록 시작 지점)에 `error = NO_ERROR;`로 명시적으로
초기화하거나, `db_set_suppress_repl_on_transaction(false)`의 반환값을 별도 변수에 담아
실행 결과와 독립적으로 로깅만 하는 방식으로 분리해야 합니다.

**재검증**: 유지. `git diff 44468ed73 HEAD -- src/executables/checksumdb.c`는 완전히
비어 있다(변경 없음) — 1차 리뷰 당시 이미 이 파일이 최종 형태였다.
