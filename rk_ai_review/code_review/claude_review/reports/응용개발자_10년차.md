## 페르소나 소개

저는 오라클·MySQL·CUBRID를 오가며 10년간 애플리케이션을 만들어 온 개발자입니다. 제가 코드를
볼 때 늘 떠올리는 질문은 세 가지입니다. (1) 마이그레이션 도구(스키마 diff, unload/load, ORM
자동생성)가 만들어 내는 **DDL 시퀀스**가 이 기능 앞에서 깨지지 않는가, (2) `CREATE ... LIKE`,
`CREATE ... AS SELECT`(CTAS), `RENAME`, 여러 절을 한 문장에 나열한 `ALTER`처럼 **DDL을 조합**했을
때 로직에 구멍이 없는가, (3) JDBC `DatabaseMetaData`나 카탈로그 뷰 같은 **드라이버가 보는 표면**이
바뀌어 기존 앱이 조용히 오작동하지 않는가. 여기에 연차에서 오는 관점 하나를 더합니다 — 같은 개념을
가리키는 코드가 **여러 군데에 서로 다르게 구현**되어 있으면 언젠가 회귀 버그로 돌아온다는 것입니다.

## 총평

이 기능은 "복제 키(RK) = PK **또는** NOT NULL UNIQUE"라는 새 개념을 도입하면서, 그 개념을
**생성 검사**, **DML 복제 로그 생성**, **rkcheck 유틸리티**, **TRUNCATE**, **SBR(문장기반 복제)**
등 여러 진입점에 흩뿌려 넣었습니다. 문제는 이 진입점들이 "RK 후보"를 판정하는 **정의가 서로
다르다**는 데 있습니다. 가장 심각한 것은 생성 시점(`sm_has_non_null_attribute` — 컬럼 중
"하나라도" NOT NULL)과 실제 DML 복제 시점(`or_is_replication_candidate_key` — 키 컬럼이 "전부"
NOT NULL)의 판정 기준이 어긋나, 생성은 통과했지만 DML이 조용히 복제되지 않는 상태를 만들 수
있다는 점입니다(문제 1). 이것은 데이터가 마스터와 슬레이브에서 달라지는데도 아무 에러가 나지 않는,
응용 입장에서 가장 무서운 종류의 결함입니다.

그다음으로, 조합 DDL을 막는 재검사 로직에 실제 구멍이 여럿 있습니다. 다중 절 `ALTER`의 재검사
게이트가 첫 절만 본다(문제 2), `MODIFY/CHANGE COLUMN`과 `RENAME`이 게이트에서 빠져 있다(문제 3, 9).
드라이버 표면에서는 `db_class` 뷰 중간에 컬럼이 끼어들어 위치 기반 파싱을 깨고(문제 5), `REPLICATION`이
예약어가 되어 기존 스키마 복원을 깨며(문제 6), unload 출력에 버전 가드가 없어 구버전 loaddb를
깹니다(문제 7).

이번 2차 재리뷰에서 새로 들어온 #7678(SBR 게이팅 재설계)은 다중 테이블 UPDATE/DELETE의 복제
판정 대상 spec을 바로잡고 derived vclass·NULL 역참조를 방어하는 등 여러 실 버그를 고쳤습니다.
다만 저자 스스로 커밋 메시지에 남긴 "known limitation" — SBR 문장이 **복제되지 않는 원본 테이블을
JOIN/SELECT로 참조**할 때 슬레이브가 빈/불일치 테이블에 재실행되어 조용히 갈라지는 경로 — 는
그대로 남아 있어 신규 문제 16으로 추가합니다. 아래에 심각도순으로 정리합니다. 각 항목은 LSP·정의
추적으로 콜체인을 확인한 결과이며, 재검증으로 갱신된 위치를 반영했습니다.

## 문제 1

**[심각도: 치명] "RK 후보" 판정이 생성 시점과 DML 복제 시점에서 서로 다르다 — 복합 UK가 조용히 복제 누락** *(유지)*

- 위치:
  - 생성/rkcheck/TRUNCATE 판정: `src/object/class_object.c:95-98`(`IS_HA_REPLICATION_KEY_CONSTRAINT`) → `src/object/schema_manager.c:16114-16130`(`sm_has_non_null_attribute`)
  - DML 복제 판정: `src/base/object_representation_sr.c:4694-4722`(`or_is_replication_candidate_key`)

- 로직 설명(LSP 콜체인 재확인): 생성 시점 `IS_HA_REPLICATION_KEY_CONSTRAINT`는 UNIQUE 계열 제약에 대해 `sm_has_non_null_attribute(attributes)`를 부르는데, 이 함수는 배열을 돌다 **하나라도** `SM_ATTFLAG_NON_NULL`이면 곧바로 `return 1`입니다(`schema_manager.c:16121-16126`). 반면 DML 시점 `or_is_replication_candidate_key`는 UNIQUE에 대해 키 구성 컬럼을 **전부** 돌면서 하나라도 `!attr->is_notnull`이면 `return false`입니다(`object_representation_sr.c:4712-4719`) — 즉 "모든 컬럼이 NOT NULL"을 요구합니다. 함수 주석 자체가 "UNIQUE with all key attributes NOT NULL"(4689)이라고 못박아, 두 정의의 어긋남이 코드에 그대로 드러나 있습니다.

- 문제 시나리오: HA 모드에서 `CREATE TABLE t (x INT NOT NULL, y INT, CONSTRAINT uk UNIQUE(x, y)) REPLICATION=ON`. 복합 UK의 `x`만 NOT NULL이고 `y`는 nullable입니다.
  1. 생성 검사: `sm_has_non_null_attribute`가 `x`를 보고 곧장 참 → RK 있음으로 판정 → 테이블이 REPLICATION=ON으로 **정상 생성**됩니다.
  2. 이후 이 테이블에 INSERT/UPDATE/DELETE: 마스터의 `or_is_replication_candidate_key`는 `y`가 not-null이 아니라서 이 UK를 RK 후보로 **거부** → `replicated`가 계속 false → **복제 로그가 아예 생성되지 않습니다**. 슬레이브에는 이 테이블의 DML이 전혀 반영되지 않습니다.
  3. rkcheck도 `sm_has_non_null_attribute` 기준이라 HA 기동 전 점검에서도 걸리지 않습니다.
  결과: 에러 한 줄 없이 마스터·슬레이브 데이터가 갈라집니다. 마이그레이션 도구가 복합 UK를 흔히 만들기 때문에 실제로 밟기 쉬운 경로입니다.

- 제안: 두 판정을 **하나의 함수**로 통일하십시오(둘 다 서버·클라이언트에서 부를 수 있는 공용 헬퍼로). 복제 정확성 관점에선 "전부 NOT NULL"이 맞습니다(부분 NOT NULL UK는 행을 유일 식별하지 못함, 문제 4 참고). 생성/rkcheck/TRUNCATE 쪽 `sm_has_non_null_attribute`(ANY) 사용을 "구성 컬럼 전부 NOT NULL"로 바꿔야 합니다.

## 문제 2

**[심각도: 중요] 다중 절 ALTER의 복제 재검사 게이트가 "첫 절"만 본다** *(유지)*

- 위치: `src/query/execute_schema.c:2051`

- 로직 설명(재확인): `do_alter()`는 `for (crt_clause = alter; crt_clause; crt_clause = crt_clause->next)`(`:1851`)로 절을 하나씩 돌며, 각 절의 코드를 `const PT_ALTER_CODE alter_code = crt_clause->info.alter.code;`(`:1854`)로 받아 처리합니다. 그런데 복제 재검사를 켤지 정하는 게이트는
  ```c
  if (!need_check_repl_constraint && IS_REPL_CONSTRAINT_RELATED_ALTER (alter->info.alter.code))
  ```
  로(`:2051`), 현재 절 `crt_clause`(또는 `alter_code`)가 아니라 리스트의 **머리 노드 `alter`**의 코드를 봅니다. `alter`는 고정이므로 루프를 몇 번 돌든 항상 첫 절의 코드만 평가됩니다. 바로 위 switch 두 곳(`:1874`, `:1997`)은 이미 올바르게 `alter_code`(현재 절)를 쓰는데, 이 게이트만 `alter`(머리 노드)를 써서 불일치가 코드상 확연합니다.

- 문제 시나리오: `ALTER TABLE t MODIFY col1 VARCHAR(20), DROP PRIMARY KEY;` (REPLICATION=ON 테이블).
  - 첫 절 = `PT_MODIFY_ATTR_MTHD` → `IS_REPL_CONSTRAINT_RELATED_ALTER`(`:109-114`) 목록에 없음 → 게이트가 끝까지 false.
  - 둘째 절 `DROP PRIMARY KEY`는 `PT_DROP_PRIMARY_CLAUSE`로 목록에 있지만, 게이트가 머리 노드만 보므로 **무시**됩니다.
  - 결과: PK가 사라져 RK 후보가 없어졌는데도 `check_ha_repl_constraint`가 호출되지 않아 에러 없이 통과. 복제 불가 상태의 테이블이 만들어집니다.

- 제안: `alter->info.alter.code`를 `alter_code`(= `crt_clause->info.alter.code`)로 교체하십시오.

## 문제 3

**[심각도: 중요] MODIFY/CHANGE COLUMN이 복제 재검사 게이트에서 누락 — NOT NULL 해제·타입 변경으로 RK 조용히 상실** *(유지)*

- 위치: `src/query/execute_schema.c:109-114`(`IS_REPL_CONSTRAINT_RELATED_ALTER`)

- 로직 설명(재확인): 이 매크로는 `PT_ADD_ATTR_MTHD`, `PT_DROP_ATTR_MTHD`, `PT_DROP_CONSTRAINT`, `PT_DROP_PRIMARY_CLAUSE` 네 코드만 "복제 제약에 영향을 주는 ALTER"로 간주합니다. `PT_CHANGE_ATTR`(`ALTER ... CHANGE`)와 `PT_MODIFY_ATTR_MTHD`(`ALTER ... MODIFY`)는 빠져 있습니다. (참고: `do_alter` switch에는 `PT_MODIFY_ATTR_MTHD`/`PT_CHANGE_ATTR` 케이스가 엄연히 존재해(`:1877-1878`, `:2018`) 이 두 코드가 유효한 절임을 확인.)

- 문제 시나리오: RK가 `NOT NULL UNIQUE(email)` 하나뿐인 REPLICATION=ON 테이블에서 `ALTER TABLE u MODIFY email VARCHAR(320) NULL;`. `email`의 NOT NULL이 풀리면 이 UK는 더 이상 RK 후보가 아닙니다(`or_is_replication_candidate_key` 기준). 그러나 `PT_MODIFY_ATTR_MTHD`가 게이트에 없어 재검사가 돌지 않으므로, RK 없는 복제 테이블이 조용히 만들어집니다. 타입 변경으로 유니크 인덱스가 재생성되며 자격을 잃는 경우도 마찬가지입니다.

- 제안: 매크로에 `PT_CHANGE_ATTR`, `PT_MODIFY_ATTR_MTHD`를 추가하십시오. 재검사는 최종 상태를 보는 `check_ha_repl_constraint` 한 번이므로 비용도 낮습니다.

## 문제 4

**[심각도: 중요] RK 후보 판정이 filter_predicate·함수 기반 인덱스를 구분하지 않음 — 부분/함수 UNIQUE가 RK로 오인** *(유지)*

- 위치: `src/base/object_representation_sr.c:4694-4722`(`or_is_replication_candidate_key`)

- 로직 설명(재확인): 이 함수는 `index->type`이 `BTREE_PRIMARY_KEY`거나(`:4702`), `BTREE_UNIQUE`이면서 키 컬럼이 전부 NOT NULL이면(`:4707-4721`) RK 후보로 인정합니다. `OR_INDEX`에는 `filter_predicate`(부분 인덱스 조건)와 `func_index_info`(함수 기반 인덱스) 필드가 있는데, 이 함수는 이 둘을 전혀 보지 않습니다.

- 문제 시나리오: `CREATE UNIQUE INDEX ux ON t(a) WHERE status = 'ACTIVE'` 같은 **부분(filtered) 유니크**는 `status='ACTIVE'`인 행들 사이에서만 유일합니다. 이 인덱스가 NOT NULL 컬럼 위에 있으면 `or_is_replication_candidate_key`가 RK 후보로 채택하고 `btree_get_rkey_btid`가 이를 복제 키로 고릅니다. 그러나 `status <> 'ACTIVE'`인 두 행은 `a` 값이 같아도 공존할 수 있어, 슬레이브에서 UPDATE/DELETE가 엉뚱한 행을 잡거나 못 잡습니다. 함수 기반 유니크(`UNIQUE(UPPER(name))`)도 슬레이브가 원본 컬럼 값으로 매칭하려 하면 어긋납니다.

- 제안: `filter_predicate != NULL`이거나 함수 기반 인덱스이면 RK 후보에서 제외하고, 생성 시점(`IS_HA_REPLICATION_KEY_CONSTRAINT`)에서도 동일하게 걸러 두 경로를 맞추십시오.

## 문제 5

**[심각도: 중요] db_class 뷰 중간에 신규 컬럼 삽입 — 위치 기반으로 카탈로그를 읽는 드라이버/도구가 깨짐** *(유지)*

- 위치: `src/object/schema_system_catalog_install.cpp:1313`, `src/object/schema_system_catalog_install_query_spec.cpp:74`

- 로직 설명(재확인): `db_class` 시스템 뷰의 컬럼 정의(install.cpp:1312-1314)와 SELECT 목록(query_spec.cpp:73-75) 양쪽에서 `is_replication_class`가 기존 컬럼 `is_system_class`와 `tde_algorithm` **사이**에 삽입돼 있습니다. 즉 뷰 끝이 아니라 중간에 컬럼이 하나 끼어들어 그 뒤 모든 컬럼의 서수(ordinal)가 한 칸씩 밀렸습니다.

- 문제 시나리오: `SELECT * FROM db_class`를 실행하고 결과를 **컬럼 번호**로 읽는 코드(레거시 앱, CUBRID Manager, 스키마 비교 도구, 모니터링 스크립트)는 이제 `tde_algorithm` 자리에서 `is_replication_class` 값을 읽고, 그 뒤 컬럼들이 전부 한 칸씩 어긋나 오독합니다. 컬럼이 "항상 끝에 추가"라는 카탈로그 진화 관례를 어긴 것으로, 신·구 버전을 함께 다루는 도구에서 조용한 오작동을 냅니다.

- 제안: 신규 컬럼을 뷰 정의의 **맨 끝**으로 옮기십시오(두 파일 모두). 이미 배포돼 순서 유지가 불가피하다면 릴리스 노트에 명시적 호환성 경고가 필요합니다.

## 문제 6

**[심각도: 중요] REPLICATION이 완전 예약어가 됨 — 기존 스키마의 replication 식별자 복원 불가** *(유지)*

- 위치: `src/parser/csql_grammar.y:1669`(`%token <cptr> REPLICATION`), 비예약 식별자 목록(약 20740-20910 구간)

- 로직 설명(재확인): 렉서가 `replication`을 전용 토큰 `REPLICATION`으로 뽑고, 문법이 이 토큰을 선언(`:1669`)·사용(`:5866-5868`, `:9095`, `:19891`)합니다. 그런데 이웃 키워드들(`DISK_SIZE`는 `:20755`, `REUSE_OID`/`REVERSE` 등)은 모두 식별자로도 쓰이도록 `| <TOKEN> {{ SET_CPTR_2_PTNAME(...) }}` 목록에 등재돼 있는데, **`REPLICATION`만 이 목록에 없습니다**(재확인: 20740-20910 구간에 `SET_CPTR_2_PTNAME` 항목 171개가 있으나 `REPLICATION`을 동반한 항목은 0건). 결과적으로 REPLICATION은 따옴표 없이는 식별자로 못 씁니다.

- 문제 시나리오: 기존 앱이 `replication`이라는 이름의 컬럼·테이블을 갖고 있으면(흔한 도메인 단어입니다), 이 버전에서 그 스키마를 unload→load 하거나 애플리케이션 SQL을 실행할 때 `column "replication"` 참조가 문법 에러로 깨집니다. 마이그레이션 시 갑자기 나타나는 회귀입니다.

- 제안: 비예약 식별자 규칙에 `| REPLICATION {{ SET_CPTR_2_PTNAME($$, $1, @$.buffer_pos); }}`를 추가해, 이웃 키워드들과 동일하게 비예약어로 두십시오.

## 문제 7

**[심각도: 중요] unloaddb/SHOW CREATE가 REPLICATION 절을 무조건 출력 — 버전 가드 없어 구버전 loaddb·다운그레이드에서 파싱 실패** *(유지)*

- 위치: `src/executables/unload_schema.c:1794-1800`(`emit_schema`), `src/object/object_printer.cpp:1137-1144`(`describe_class`)

## 문제 16 (신규 — #7678 동기화 델타)

**[심각도: 보통] USE_SBR 문장이 복제-OFF 테이블을 JOIN/SELECT 소스로 참조하면 슬레이브가 빈/불일치 데이터에 재실행 — 조용한 데이터 갈림 (문서화된 known limitation, 가드 없음)**

- 위치: `src/query/execute_statement.c:3304-3348`(`is_data_repl_log_enabled`), 특히 INSERT 분기 `:3315-3318` 및 UPDATE/DELETE 분기 `:3320-3343`

- 로직 설명(#7678 신규 코드 분석): #7678은 SBR(문장기반 복제) 판정을 "수정 대상 spec"으로 바로잡았습니다. INSERT는 `statement->info.insert.spec`(단일 대상)만, UPDATE/DELETE는 `PT_SPEC_FLAG_UPDATE`/`PT_SPEC_FLAG_DELETE`가 붙은 spec만 봅니다. **수정 대상 중 하나라도 복제 클래스면** `is_data_repl_log_enabled`가 true를 반환하고, 상위(`do_statement:3405`, `do_execute_statement:4113`)에서 `db_set_suppress_repl_on_transaction(true)`로 행 기반(row-based) 복제 로그를 억제한 뒤 문장 하나만 SBR로 남깁니다. 슬레이브는 그 문장을 **재실행**합니다.
  - INSERT 분기 주석(`:3316-3317`)은 "INSERT...SELECT의 소스 테이블은 수정 대상이 아니므로 의도적으로 검사하지 않는다"고 못박고 있고, 저자가 커밋 메시지에도 "Known limitation (unchanged): a statement that modifies a replication target while referencing a replication-off table by join (or INSERT...SELECT source) still re-executes against an empty/divergent table on the replica"라고 명시했습니다.

- 문제 시나리오: HA 모드에서 대량 적재에 흔히 권장되는 USE_SBR 힌트를 쓴 `INSERT /*+ USE_SBR */ INTO repl_target SELECT ... FROM offrepl_staging`(또는 `UPDATE /*+ USE_SBR */ repl_t a JOIN offrepl_ref b ...`).
  1. 마스터: 실제 소스 데이터로 INSERT/UPDATE가 수행되고, SBR 문장 로그가 딱 한 번 남으며, 행 기반 복제는 억제됩니다.
  2. 슬레이브: SBR 문장을 재실행하는데, `offrepl_staging`/`offrepl_ref`는 복제되지 않으므로 슬레이브 쪽에서는 **비어 있거나 오래된** 상태입니다. 재실행 결과가 마스터와 달라져 `repl_target`이 조용히 갈립니다.
  결과: 에러 없이 마스터·슬레이브가 어긋납니다. USE_SBR은 대량 DML에서 로그량을 줄이려 실무에서 실제로 권장·사용되는 힌트라 응용/마이그레이션 관점에서 밟기 쉬운 경로입니다.

- 제안: 최소한 SBR 문장이 복제-OFF(또는 복제 판정 안 되는) 테이블을 소스/JOIN으로 참조하면 **경고를 내거나 SBR을 거부**(행 기반으로 폴백)하도록 검토하십시오. 지금처럼 조용히 진행하면 정합성 붕괴가 사용자에게 보이지 않습니다. 최소한 릴리스 문서·USE_SBR 사용 가이드에 이 제약을 굵게 명시해야 합니다. (참고: 이 판정 대상 spec을 바로잡은 #7678 자체는 다중 테이블 UPDATE/DELETE의 오판·derived vclass 누락·NULL 역참조를 실제로 고친 개선입니다 — 문제 16은 그 개선이 남긴 잔여 갭입니다.)

## 재검증 요약

- **재검증 대상**: 1차 리포트 15건(문제 1~15).
- **유지**: 15건 — 문제 1~15 전원 새 HEAD(734f4959d)에서 성립 확인. 위치가 밀린 항목은 갱신(문제 7 unload_schema 1794→1794-1800, 문제 8 11722→11730, 문제 10 3200-3216→3200-3218, 문제 11 779-792→782-792, 문제 12 11748/11822→11747/11823, 문제 13 9835-9840→9837-9839, 문제 14 5862-5871→5864-5872, 문제 15 10262-10273→10258-10269, 문제 6 식별자 목록 구간 재확인).
- **하향**: 문제 10 — #7678이 `spec_has_replication_class`에 `flat_entity_list` 해석 MOP 폴백을 추가해 릴리스 빌드의 "SBR 조용히 미복제" 위험을 backstop함. 남은 것은 디버그 `assert(false)` abort 잔여뿐이라 [보통]→[사소] 하향. 문제 자체(함수의 `assert(false)`/이름 해석 실패 처리)는 미수정이라 유지.
- **해소(동기화가 고침)**: 0건.
- **폐기(오판)**: 0건.
- **신규**: 1건 — 문제 16(#7678 SBR 게이팅이 남긴 USE_SBR+복제-OFF 소스 참조 시 슬레이브 재실행 갈림, 문서화된 known limitation).

## 조사 종료 선언

동기화 델타 #7678(SBR/checksumdb)과 #7697(인터럽트 수정)을 로직 추적으로 재검토했습니다.
- **#7697**(`heap_get_class_repl_on` + `locator_add_or_remove_index_internal` 에러 전파): 에러코드 out-param 전환과 `goto error` 전파가 올바르게 들어갔고, `!replicated`를 fetch 앞으로 옮겨 복제-ON 테이블의 반복 fetch도 오히려 줄었습니다. 이 커밋에서 제 관점의 신규 결함은 없습니다.
- **#7678의 suppress-repl 브래킷**(`do_statement`, `do_execute_statement`, `checksumdb.c`): `db_set_suppress_repl_on_transaction(true)`→실행→`(false)` 재개 경로에서, do_statement/do_execute_statement의 상태 switch 내부에 `goto end` 조기 이탈이 없어(재확인) 억제 플래그가 후속 문장으로 새지 않음을 확인. checksumdb도 실행 실패 시 실제 에러가 재개 결과를 supersede하도록 처리됨. 이 경로들에서 신규 결함 없음.
- **MERGE + USE_SBR**: `is_stmt_based_repl_type`이 MERGE를 SBR 대상에 넣지 않아 MERGE는 항상 행 기반 복제로 처리됨 — 정합성상 문제 아님(USE_SBR 힌트가 조용히 무시되는 미미한 이슈만 있으나 이 diff가 만든 회귀가 아니라 제외).

제 관점(DDL 조합·트랜잭션 중간 상태·드라이버/메타데이터 표면·마이그레이션 시퀀스)에서 새 HEAD를
훑은 결과, 유지 15건 + 신규 1건(문제 16)이 확인 가능한 실질 결함의 전부입니다. 개수를 채우기 위한
억지 지적은 넣지 않았으며, 이 시점에서 조사를 종료합니다.
