## 페르소나 소개

나는 DB를 5년째 다뤄 온 애플리케이션 개발자다. 스키마를 직접 설계하고, 배포 때마다
마이그레이션 도구(Flyway/Liquibase 유사물, 사내 스크립트)가 뱉어내는 DDL 시퀀스를 운영에
흘려보내는 게 일상이다. 그래서 내가 코드에서 보는 것은 "정상적인 CREATE 한 방"이 아니라,
**DDL을 여러 개 조합했을 때**, **트랜잭션 중간에 실패했을 때**, **드라이버·메타데이터로 스키마를
되읽을 때**, **구버전에서 만든 스키마를 신버전에 부을 때** 같은 "이음새"다. 이번 RK/REPLICATION
기능은 "테이블마다 복제 여부를 켜고 끄는" 단순해 보이는 옵션이지만, 그 판정 로직이
**생성 시 검사 경로 / DML 시 복제 로그 경로 / 사전점검(rkcheck) 경로 / unload 경로**로 네 갈래로
흩어져 있어서, 이 갈래들이 서로 다른 기준을 쓰면 "검사는 통과했는데 실제로는 복제가 안 되는"
조용한 데이터 불일치가 난다. 이게 이 기능의 존재 이유(마스터/슬레이브 불일치 방지)를 정면으로
배신하는 지점이라 집중해서 팠다.

## 2차 재검증 총평

동기화(#7697)로 **가장 위험했던 "에러를 삼키는 bool 반환" 축이 근본 수정**됐다. INSERT/DELETE
복제 경로(`locator_add_or_remove_index_internal`)의 조회 실패가 이제 에러코드로 호출자에게
전파되고, 값비싼 클래스 레코드 조회가 `!replicated`/후보키 판정 뒤로 밀려 단축평가된다.
1차의 문제 2·8이 여기서 해소됐다.

그러나 **"무엇이 복제 키(RK)인가"의 정의가 코드 경로마다 다르다**는 최대어(문제 1)는 그대로다.
생성/rkcheck는 "구성 컬럼 중 하나라도 NOT NULL이면 RK"로 보고, 서버 DML 판정은 "전부
NOT NULL이어야 RK"로 본다 — 부분 NOT NULL 복합 UNIQUE 테이블이 "검사는 통과/복제는 누락"
상태로 잠복한다. 멀티 절 ALTER 재검사 게이트가 첫 절 코드만 보는 문제(문제 3), RK 자격을
소리 없이 잃는 DDL 경로가 재검사 대상에서 빠진 문제(문제 4), rkcheck의 방어 코드 부재로 인한
크래시(문제 5·6), REPLICATION 완전 예약어화(문제 7)도 전부 유지된다.

동기화 델타(#7678 SBR 게이트 재작성, checksumdb 억제·재개, #7697 에러 전파)는 대체로 견고하게
구현돼 있어 이 델타에서 새로 성립하는 결함은 확인되지 않았다(상세는 "조사 종료 선언" 참조).

## 문제 1

**[심각도: 치명] 복제 키(RK)의 정의가 "생성/검사 경로"와 "DML 복제 경로"에서 서로 달라, 부분 NOT NULL 복합 UNIQUE 테이블의 데이터가 조용히 복제 누락된다**

**위치**
- 생성·검사 판정: `src/object/class_object.c:95-98` (`IS_HA_REPLICATION_KEY_CONSTRAINT`), 이를 쓰는 `classobj_has_class_repl_key_constraint()` (`class_object.c:2279`)
- NOT NULL 판정: `src/object/schema_manager.c:16114-16130` (`sm_has_non_null_attribute` — "하나라도" NOT NULL이면 1)
- DML 복제 판정: `src/base/object_representation_sr.c:4694-4722` (`or_is_replication_candidate_key` — 구성 컬럼 "전부" NOT NULL이어야 true)

**로직 설명**
CREATE TABLE / ALTER TABLE의 HA 제약 검사(`check_ha_repl_constraint` → `classobj_has_class_repl_key_constraint`)와
rkcheck 유틸리티(`check_rk_constraint`, `util_cs.c`)는 복제 키 존재 여부를 `IS_HA_REPLICATION_KEY_CONSTRAINT`로 판정한다.
이 매크로는 PK이거나 `SM_IS_CONSTRAINT_UNIQUE_FAMILY(type) && sm_has_non_null_attribute(attributes)` 인데,
`sm_has_non_null_attribute`는 배열을 돌다 **하나라도** NOT NULL이면 1을 돌려준다(schema_manager.c:16121-16126, 함수 주석도 "at least one").
반면 실제 마스터가 DML을 슬레이브로 복제할지 정하는 서버 측 판정(`locator_add_or_remove_index_internal`의
`or_is_replication_candidate_key(index)`, locator_sr.c:8042)은 UNIQUE 인덱스의 **모든** 키 컬럼이 `is_notnull`이어야
true다(object_representation_sr.c:4712-4720, 하나라도 nullable이면 즉시 false). 동기화(#7697)로 조회 함수는
`heap_get_class_repl_on`으로 바뀌었지만, 이 후보키 게이트 `or_is_replication_candidate_key`는 그대로라 판정 불일치가 유지된다.

**문제 시나리오**
HA 모드에서
```
CREATE TABLE t (a INT NOT NULL, b INT, CONSTRAINT uk UNIQUE(a,b)) REPLICATION=ON;
```
- 생성 검사: `sm_has_non_null_attribute({a,b})` → a가 NOT NULL이라 1 → "복제 키 있음" → **CREATE 성공, 에러 없음**.
- rkcheck: 같은 판정 → **위반 없음** → HA 기동 통과.
- INSERT/UPDATE/DELETE 실행 시 서버: 이 UNIQUE 인덱스는 b가 nullable → `or_is_replication_candidate_key` = false →
  테이블에 다른 PK/전부-NOT-NULL UK가 없다면 복제 후보 인덱스가 하나도 안 잡힘 → `repl_log_insert` 호출 안 됨 →
  **복제 로그가 아예 생성되지 않는다**.
- 결과: 마스터에는 데이터가 쌓이는데 슬레이브에는 이 테이블 데이터가 한 줄도 안 넘어간다. Failover 후 데이터 증발.
  이 기능이 막으려던 바로 그 "조용한 마스터/슬레이브 불일치"가 발생한다.

단일 컬럼 NOT NULL UNIQUE(흔한 케이스)는 두 판정이 우연히 일치해 문제가 안 드러나므로, 복합 UNIQUE를
쓰는 스키마에서만 잠복하다 터진다 — 발견이 가장 늦는 종류의 버그다.

**제안**
두 경로가 **하나의 판정 함수**를 공유하게 하라. 생성/rkcheck 쪽 `IS_HA_REPLICATION_KEY_CONSTRAINT`도
"구성 컬럼 전부 NOT NULL"(all)로 강화해 `or_is_replication_candidate_key`와 의미를 일치시키는 것이 정답이다.
`sm_has_non_null_attribute`("any")는 RK 판정에 쓰면 안 된다 — 이름 그대로 "아무거나 하나"를 확인하는 함수다.
(신규 코드 — 이 기능 책임. 2차 재검증에서도 유지됨)

## 문제 3

**[심각도: 치명] 멀티 절 ALTER의 RK 재검사 게이트가 "첫 번째 절 코드"만 보고 판단해, 뒤 절에서 복제 키를 없애면 검사가 통째로 새어나간다**

**위치** `src/query/execute_schema.c:2051` (게이트), 대비 절 순회는 `crt_clause = crt_clause->next` 루프

**로직 설명**
`do_alter()`는 절(clause)들을 `for (crt_clause = alter; ...; crt_clause = crt_clause->next)`로 순회하며
각 절을 `crt_clause->info.alter.code`로 디스패치한다. 그런데 매 절 처리 직후 RK 재검사를 걸지 결정하는 게이트는
```c
if (!need_check_repl_constraint && IS_REPL_CONSTRAINT_RELATED_ALTER (alter->info.alter.code))
  need_check_repl_constraint = true;
```
로 되어 있다(execute_schema.c:2051). 여기서 `alter->info.alter.code`는 **첫 번째 절**의 코드로 고정이다
(루프 변수 `crt_clause`가 아니라 헤드 노드 `alter`를 참조). 즉 두 번째 이후 절의 종류는 게이트가 절대 못 본다.
명백히 `crt_clause->info.alter.code`를 봐야 할 자리를 잘못 참조한 것이다.

**문제 시나리오**
마이그레이션 도구가 흔히 만드는 다음 DDL:
```
ALTER TABLE t CHANGE a a INT, DROP CONSTRAINT uk_rk;
```
- 첫 절 = `PT_CHANGE_ATTR` → `alter->info.alter.code` = PT_CHANGE_ATTR → `IS_REPL_CONSTRAINT_RELATED_ALTER`에 없음 →
  `need_check_repl_constraint`가 끝까지 false.
- 두 번째 절이 유일한 복제 키였던 `uk_rk`를 제거했는데도 **RK 재검사가 실행되지 않는다**(execute_schema.c:2059 블록 스킵).
- HA 모드에서 복제 테이블이 복제 키를 잃은 채로 ALTER가 성공한다 → 이후 DML이 복제 후보 인덱스를 못 찾아
  (문제 1과 연쇄) 조용히 복제 누락.

반대로 `ALTER TABLE t DROP CONSTRAINT uk_rk, CHANGE a a INT;`(순서만 바꿈)은 첫 절이 PT_DROP_CONSTRAINT라
검사가 걸린다. **절 순서에 따라 무결성 검사가 켜졌다 꺼졌다 하는** 것은 그 자체로 결함이다.

**제안** 게이트를 `IS_REPL_CONSTRAINT_RELATED_ALTER (crt_clause->info.alter.code)`로 고쳐 매 절을 검사하라.
(신규 코드 — 유지됨)

## 문제 4

**[심각도: 중요] RK 자격을 소리 없이 상실시키는 DDL 경로(MODIFY/CHANGE COLUMN, RENAME)가 재검사 대상 매크로에서 빠져 있다**

**위치** `src/query/execute_schema.c:109-114` (`IS_REPL_CONSTRAINT_RELATED_ALTER`)

**로직 설명**
매크로는 `PT_ADD_ATTR_MTHD`, `PT_DROP_ATTR_MTHD`, `PT_DROP_CONSTRAINT`, `PT_DROP_PRIMARY_CLAUSE`
네 가지만 "복제 제약 관련 ALTER"로 본다(execute_schema.c:110-113). 그런데 `do_alter()`의 switch는
`PT_CHANGE_ATTR`(MODIFY/CHANGE COLUMN)와 `PT_RENAME_ENTITY`도 정식으로 처리한다.

**문제 시나리오**
- `ALTER TABLE t MODIFY a INT;` — a가 NOT NULL UNIQUE 조합으로 복제 키를 이루던 컬럼인데 nullable로 바뀌면,
  `or_is_replication_candidate_key`는 이제 이 UNIQUE를 후보에서 뺀다(문제 1 참조). 그러나 PT_CHANGE_ATTR가
  매크로에 없으니 재검사가 안 돌아 복제 키를 잃은 복제 테이블이 HA 모드에 그대로 남는다.
- 타입 변경으로 UNIQUE 자격이 흔들리는 경우도 동일.
- RENAME: `do_alter`는 PT_RENAME_ENTITY 때 최종 테이블명 추적까지 해두지만, 정작 RENAME은 매크로에 없어
  재검사 트리거가 아니다 — 그림자 스왑(복제 제외 테이블을 운영 이름 자리로 밀어넣기)이 무검사로 통과할 수 있다.

**제안** 매크로에 최소한 `PT_CHANGE_ATTR`, `PT_MODIFY_ATTR_MTHD`를 추가하라. RENAME은 정책 판단이 필요하지만,
"복제 테이블 이름이 바뀌면 재검증"하는 편이 안전하다. (신규 코드 — 유지됨)

## 문제 5

**[심각도: 중요] rkcheck가 위반 목록 파일을 못 열면(fopen 실패) NULL 포인터로 fprintf 하여 크래시한다 — HA 기동 사전점검이 죽음으로 끝난다**

**위치** `src/executables/util_cs.c:3320` (open_violation_list_file), `:3332/:3348/:3376` (NULL 검사 없이 `PRINT_SECTION_TITLE(fp,...)` = `fprintf(fp,...)`)

**로직 설명**
`rkcheck()`는 서버 접속(`db_restart`) 성공 후
```c
fp = open_violation_list_file (database_name, arg->command_name, violation_list_file, PATH_MAX);   /* util_cs.c:3320 */
classes = db_get_all_classes ();
...
PRINT_SECTION_TITLE (fp, RK_CONSTRAINT_VIOLATIONS_SECTION_TITLE);   /* :3332, = fprintf(fp, ...) */
```
로 진행한다. `open_violation_list_file`는 내부적으로 `fopen(file_path, "w")` 결과를 그대로 돌려주고
(util_cs.c:2856~), `rkcheck`는 그 반환값이 NULL인지 **한 번도 검사하지 않는다**(fopen 직후 검사하는 것은
`classes == NULL`뿐, fp는 아니다). 이후 모든 `PRINT_SECTION_TITLE`/`PRINT_MESSAGE`/`check_rk_constraint`/
`check_fk_constraint`가 `fprintf(fp, ...)`를 호출한다.

**문제 시나리오**
로그 디렉토리 경로가 쓰기 불가(권한, 디스크 풀, 경로 없음)이면 `fopen`이 NULL을 반환한다.
곧바로 `fprintf(NULL, ...)` → 세그폴트. rkcheck는 `cubrid hb start` 경로에서 자동 호출되므로,
운영자는 "HA가 안 켜진다"만 보고 원인이 로그 디렉토리 권한임을 알 길이 없다. 사전점검 도구가 정상적으로
"제약 위반" 또는 "정상"을 보고하는 대신 크래시로 끝난다.

**제안** `fp` 획득 직후 `if (fp == NULL) { PRINT_AND_LOG_ERR_MSG(...); err = ER_FAILED; goto end1; }`을 넣어라.
(신규 코드 — 유지됨)

## 문제 6

**[심각도: 중요] FK 위반 로깅이 참조 테이블의 PK를 무조건 역참조해, 참조 테이블에 PK가 없으면(UNIQUE 참조 등) NULL 역참조로 크래시한다**

**위치** `src/query/execute_schema.c:9837-9839` (`log_ha_repl_fk_ref_all_replicated`)

**로직 설명**
rkcheck의 FK 검사(`check_fk_constraint` → `log_ha_repl_fk_ref_all_replicated`)는 복제 제외 테이블을 참조하는
FK를 발견하면 그 내용을 파일에 남긴다:
```c
DB_CONSTRAINT *pk_c = db_constraint_find_primary_key (db_get_constraints (ref_class_mop));   /* :9837 */
fprintf (fp, "%s(%s) -> %s(%s)\n", sm_get_ch_name (class_obj), tmp_c->name,
         sm_get_ch_name (ref_class_mop), pk_c->name);                                        /* :9838-9839 */
```
`db_constraint_find_primary_key()`는 PK가 없으면 **NULL을 반환한다**. 그런데 `pk_c->name`을 NULL 검사 없이 바로 역참조한다.

**문제 시나리오**
CUBRID는 FK가 상대 테이블의 PK뿐 아니라 **NOT NULL UNIQUE 키를 참조**하는 것도 허용한다. 따라서:
```
CREATE TABLE parent (a INT NOT NULL, CONSTRAINT uk UNIQUE(a)) REPLICATION=OFF;   -- PK 없음
CREATE TABLE child (b INT, CONSTRAINT fk FOREIGN KEY(b) REFERENCES parent(a));    -- REPLICATION=ON(기본)
```
이 스키마로 rkcheck를 돌리면, parent가 복제 제외라 FK 위반으로 잡히고, `db_constraint_find_primary_key(parent)`가
NULL을 반환 → `pk_c->name` → 세그폴트. 위반을 **보고**해야 할 코드가 위반을 만나자마자 죽는다.
(참고: 크래시가 안 나는 경우에도, FK가 실제로는 UNIQUE 키를 참조하는데 메시지에는 엉뚱하게 PK 이름을
찍으므로 진단 정보가 틀린다.)

**제안** `pk_c`가 NULL일 수 있음을 처리하라. 애초에 이 함수는 FK가 참조하는 "실제 키"(`tmp_c->fk_info`의
참조 인덱스)를 찍어야지 무조건 PK를 찾으면 안 된다. NULL이면 참조 키 이름 대신 안전한 대체 문자열을 출력하라.
(신규 코드 — 유지됨)

## 문제 7

**[심각도: 중요] `REPLICATION`이 완전 예약어가 되어, 기존에 replication을 컬럼/테이블/별칭 이름으로 쓰던 스키마의 DDL이 파싱 실패한다**

**위치** `src/parser/csql_grammar.y:1669` (`%token <cptr> REPLICATION`), 비예약 identifier 목록(csql_grammar.y:20646-20905 구간)에 REPLICATION 누락

**로직 설명**
렉서에 REPLICATION 토큰이 추가됐다(csql_grammar.y:1669). 새 키워드를 기존 식별자와 공존시키려면
문법의 비예약어 identifier 규칙(`SET_CPTR_2_PTNAME`을 쓰는 목록)에 그 토큰을 등록해야 한다. 실제로 이웃 키워드들 —
`DISK_SIZE`(csql_grammar.y:20755), `REUSE_OID`(:20882), `REVERSE`(:20883) — 은 그 목록에 들어 있는데
**REPLICATION만 빠져 있다**(20646-20905 구간 grep 결과 REPLICATION 항목 없음). 즉 REPLICATION은 완전 예약어가 됐다.

**문제 시나리오**
운영 스키마에 `replication`이라는 컬럼/테이블이 이미 있는 경우,
```
SELECT replication FROM my_status;
CREATE TABLE audit (replication INT);
```
같은, 그동안 잘 돌던 DDL/DML이 신버전에서 문법 에러가 난다. 마이그레이션 도구가 스키마를 재생성하거나
기존 쿼리를 재실행하는 순간 깨진다. 따옴표(`[replication]`)로 감싸야 하는데, 이는 하위 호환 회귀다.

**제안** csql_grammar.y의 비예약 identifier 목록에 `| REPLICATION {{ SET_CPTR_2_PTNAME($$, $1, @$.buffer_pos); }}`를
추가해 이웃 키워드들과 동일하게 식별자로도 허용하라. (신규 코드 — 유지됨)

## 문제 9

`or_class_is_replication_on()`은 클래스 레코드에서 flags를 뽑아 `!(flags & replication_off_flag)`로 복제 여부를

## 문제 10

**[심각도: 보통] `sm_is_replication_class()`도 조회 실패를 bool false로 뭉갠다 — SBR/메타데이터 경로에서 복제 누락·오판 소지**

**로직 설명**
```c
if (op != NULL && au_fetch_class_force (op, &class_, AU_FETCH_READ) == NO_ERROR)

assert (false);
return false;
```

갚은 부채(조회 실패를 "복제 대상 아님"으로 등가 처리)와 동일하다. 이 함수는 SBR 복제 판정
(`is_data_repl_log_enabled` → `spec_has_replication_class` → `sm_is_replication_class`, execute_statement.c),
FK 참조 검사(`log_ha_repl_fk_ref_all_replicated`), SHOW CREATE / unload 출력에 두루 쓰인다.
동기화(#7678)로 SBR 게이트가 이 함수에 더 강하게 물리면서 호출 표면이 오히려 넓어졌다.

**문제 시나리오**
락 경합이나 인터럽트로 `au_fetch_class_force`가 실패하면, 릴리스 빌드에서 조용히 false가 되어
- SBR 경로: 복제해야 할 문장을 "복제 대상 아님"으로 처리해 슬레이브에 안 넘길 수 있고,
- FK 검사 경로: 참조 대상을 "복제 아님"으로 오판해 정상 스키마에 스퓨리어스 에러를 낼 수 있다.
debug 빌드에서는 `assert(false)`가 정상적인 일시 실패에도 서버/유틸을 죽일 수 있다.

**제안** #7697이 `heap_get_class_repl_on`에서 한 것과 동일하게, 최소한 호출 빈도가 높은 SBR 판정 경로에서는
조회 실패를 에러로 전파하도록 시그니처를 손보라. 지금처럼 "실패=OFF"는 데이터 유실 방향이라 가장 위험하다.
(신규 코드 — 유지됨)

## 조사 종료 선언

여기서 종료한다. 2차 재검증에서 훑은 영역과 근거는 다음과 같다.

**동기화 델타(#7678·#7697) 재검증**
- **#7697** (`9e094324b`): `heap_is_replication_class`(bool) → `heap_get_class_repl_on`(int 에러코드 + `repl_on`
  out-param)으로 근본 재설계됐다. 호출부 `locator_add_or_remove_index_internal`(locator_sr.c:8041-8057)에서
  조회 실패를 `error_code`로 캡처해 `goto error`로 트랜잭션에 전파하고, 조건식을
  `error_code == NO_ERROR && need_replication && !replicated && or_is_replication_candidate_key(index) && ...`로
  재배치해 값싼 판정을 앞세우고 값비싼 클래스 레코드 조회를 블록 안으로 넣었다. **1차 문제 2(에러 삼킴)와
  문제 8(비싼 힙 스캔이 !replicated보다 앞이라 반복 호출)이 이 재작성으로 해소**됐다.
- **#7678** (`3b6ebd1a9`): SBR 게이트가 `is_stmt_based_repl_type(statement) && is_data_repl_log_enabled(parser, statement)`로
  강화됐다. `is_data_repl_log_enabled`는 INSERT는 타깃 spec, UPDATE/DELETE는 `PT_SPEC_FLAG_UPDATE`/`_DELETE`가
  붙은 실제 수정 대상 spec만 보고, 파생 updatable vclass는 `pt_spec_repl_class_walk`로 derived subtree까지 훑는다.
  `is_stmt_based_repl_type`는 DDL·`PT_DROP_VARIABLE`·USE_SBR 힌트 DML에만 true를 주고, `is_data_repl_log_enabled`의
  `default: return true`는 오직 그 비-DML(DDL/DROP_VARIABLE)에만 도달하므로 "REPLICATION=OFF 테이블 SBR 유출"
  회귀는 재현되지 않는다. checksumdb는 `db_set_suppress_repl_on_transaction(true/false)`로 로컬 실행의 행 기반
  복제를 감싸 SBR 단일 로그만 남긴다 — 재개(false)가 db_execute 성공/실패와 무관하게 무조건 호출되므로 억제
  플래그 누수(leak)는 없다. **이 델타에서 새로 성립하는 결함은 확인되지 않았다.**

**훑은 영역**
- DDL 진입점 전체: `do_create_entity`(일반/CREATE LIKE/파티션/상속), `do_alter`(멀티 절 순회·게이트),
  `do_alter_change_replication`, `do_create_partition`, `do_promote_partition` — 전부 Read + 콜체인 확인.
- 복제 키 판정 4경로 대조: 생성검사(`classobj_has_class_repl_key_constraint`) / rkcheck(`check_rk_constraint`) /
  서버 DML(`or_is_replication_candidate_key`) / TRUNCATE(`truncate_need_repl_log`). 최대어 문제 1(판정 불일치)을 재확정.
- SBR 복제 게이트: `is_data_repl_log_enabled`, `spec_has_replication_class`, 파생 vclass 워크(`pt_spec_repl_class_walk`) — #7678 신규.
- 서버 복제 로그 경로: `locator_add_or_remove_index_internal`(#7697 수정 확인), `locator_repl_prepare_force`.
- rkcheck 유틸리티 전체(`rkcheck`, `check_repl_constraint_violations`, FK 로깅, 파일 열기, hb start 연결).
- 파서/문법: 렉서 토큰, `class_replication_spec`, `opt_replication_option`, 비예약어 목록.
- unload 출력, 에러코드/메시지, 카탈로그 노출.

**더 없다고 보는 근거**
- 동기화가 갚은 부채(#7697)는 정확히 1차 문제 2·8이 지적한 지점이며, 새 코드가 그 자리에 새 결함을 심지 않았다.
- #7678의 SBR 게이트는 gdb 재현까지 거친 #6908 리뷰 결론(derived vclass 대상 누락 방지)을 그대로 반영했고,
  분기 논리에 억지 지적할 구멍이 없다.
- 억지로 개수를 채우기보다, 유지된 12건 중 문제 1·3·5·6이 실제 데이터 불일치/크래시로 이어지는 핵심이라
  이들에 무게를 뒀다.
