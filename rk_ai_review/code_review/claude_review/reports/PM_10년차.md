# PM 10년차 — RK/REPLICATION 기능 코드 리뷰 (2차 재리뷰, 기준 734f4959d)

> **2차 재리뷰 안내**: 사용자가 fork를 CUBRID upstream과 동기화한 뒤(브랜치 `feature/CBRD-26246-develop`, HEAD `734f4959d` = 44468ed73 + #7678(`3b6ebd1a9`) + #7697(`9e094324b`)) 진행한 재검증이다. diff 범위는 `merge-base(upstream/develop) b646647ec...HEAD`(35파일, +1,444/−57)로, 1차 때 기준선 오류로 섞여 들어왔던 무관 커밋이 정리됐다. 1차 리포트의 문제 번호는 그대로 유지하고, 해소된 항목은 표기 후 제거, 새로 찾은 항목은 이어서 번호를 매겼다.

## 페르소나 소개

10년차 프로덕트 매니저(PM)로서 이번 리뷰에 참여했다. 나는 데이터베이스 엔진 내부 구현을 직접 고치는 사람은 아니지만, 이 기능이 "요구사항대로 빠짐없이 동작하는지", "운영자가 마주치는 에러 메시지·유틸리티 출력이 제품으로 내보내도 부끄럽지 않은 수준인지", "기존 사용자의 DDL·unload 포맷·카탈로그 조회가 이번 변경으로 조용히 깨지지 않는지", "코드에 TODO·죽은 코드·복붙 흔적 같은 미완성 자국이 남아있지 않은지"를 판별하는 데 10년을 썼다. 10년차답게 과거 PR에서 이미 고생해서 고친 버그가 이번 코드에서 다시 등장하지는 않았는지(회귀), 그리고 이번 리뷰의 "범위" 자체가 깨끗한지도 함께 본다.

## 총평 (2차 재리뷰)

1차 리포트의 13개 문제 중 12건을 새 HEAD에서 재확인했다. 그중 2건은 이번 동기화로 실제로 해소됐다: **구 문제 7**(리뷰 대상 diff에 무관한 티켓 커밋이 섞여 있던 범위 추적성 문제)은 이번 재리뷰가 정확한 `merge-base`(`b646647ec`)를 기준선으로 잡으면서 저절로 해소됐고, **구 문제 11**(`checksumdb`가 `db_set_suppress_repl_on_transaction(false)` 실패를 점검하지 않던 문제)은 #7678 커밋 메시지에 명시된 대로 "Per review, ... handle db_set_suppress_repl_on_transaction errors" 수정이 반영되어 반환값이 `error` 변수에 실려 함수 최종 리턴값까지 전파됨을 코드로 직접 확인했다.

나머지 **10건은 새 HEAD에서도 코드 위치까지 동일하게(또는 미세한 라인 이동만 있는 채로) 그대로 재현**된다 — `sm_is_replication_class()`의 에러 삼킴 안티패턴, `do_alter()`의 "첫 절 alter_code만 보는" RK 재검증 게이트 누락, `rkcheck`의 `fopen` 실패 미점검, 파티션 승격 시 복합 UNIQUE 플래그가 지워지는 로직 결함, 매직 넘버·죽은 코드·세이브포인트 복붙·TODO 잔재·enum 중간 삽입·`localtime_r` 실패 미방어까지 전부 그대로다. 이번 동기화(#7678/#7697)가 손댄 코드 자체(SBR 판정 로직, `heap`/`locator` 복제 클래스 체크)를 새로 훑는 과정에서, 과거 PR(#6908) 리뷰에서 이미 "MAJOR"로 지적됐던 "인덱스 순회 루프 안에서 클래스 복제 여부를 매번 다시 조회한다"는 비효율이 #7697이 그 코드를 다시 손보고 지나간 뒤에도 여전히 남아 있음을 새로 확인해 문제 14로 추가했다.

즉 2차 재리뷰의 결론은: **이번 동기화는 스펙에서 벗어난 범위 문제(구 문제 7)와 이미 알려진 checksumdb 버그(구 문제 11)를 걷어냈을 뿐, PM 관점에서 지적한 "릴리스 품질" 결함 10건은 손대지 않고 그대로 지나갔다.** 아래 문제들은 모두 clangd LSP/grep으로 현재 HEAD(`734f4959d`)의 실제 코드를 다시 열어 확인한 뒤 작성했다.

## 문제 2 — [치명] `sm_is_replication_class()`가 에러를 삼키는 bool 함수 안티패턴 (변동 없음)

**위치**: `src/object/schema_manager.c:3390-3407`

**로직 설명**:
```c
bool
sm_is_replication_class (MOP op)
{
  SM_CLASS *class_;
  if (op != NULL && au_fetch_class_force (op, &class_, AU_FETCH_READ) == NO_ERROR)
    {
      return !(class_->flags & SM_CLASSFLAG_DATA_REPLICATION_OFF);
    }
  assert (false);
  return false;
}
```
`au_fetch_class_force()`(`src/object/authenticate_access_class.cpp:667`)는 내부적으로 `fetch_class()`를 호출하는 에러 코드 반환 함수이며, 클래스 삭제·락 타임아웃·인터럽트 등 다양한 사유로 `NO_ERROR`가 아닌 값을 돌려줄 수 있다. `sm_is_replication_class()`는 이 실패를 구분하지 않고 무조건 `false`(비복제 클래스)로 처리한다. release 빌드에서는 `assert(false)`가 no-op이므로 이 상황이 조용히 지나간다.

LSP로 호출부를 재확인하면 현재도 동일하게 11곳에서 쓰인다: `execute_schema.c:2063`(`do_alter()`의 RK 재검증 게이트), `execute_schema.c:9796,9835`(FK 참조 대상 검증), `execute_statement.c:3217,3254,3288`(#6908/#7678이 도입한 SBR 복제 여부 판정), `util_cs.c:2943`(rkcheck), `unload_schema.c:1794`, `object_printer.cpp:1138`. 특히 이번 동기화(#7678)가 새로 만든 `is_replication_class(const char*)`(`execute_statement.c:3200-3218`)도 내부에서 `sm_is_replication_class()`를 그대로 호출하므로, 동일한 실패-삼킴 지점이 하나 더 얹혔다.

**문제 시나리오**: `do_alter()`에서 RK를 제거하는 절이 있어 재검증이 필요한 상황인데, `sm_is_replication_class()`가 락 대기 중 인터럽트나 일시적 오류로 실패하면 "복제 대상 아님"으로 판정해 `check_ha_repl_constraint()`를 건너뛰고 성공 처리해버린다. HA 운영 중인 복제 테이블에서 마지막 RK가 제거된 채로 ALTER TABLE이 "성공"할 수 있다 — 이 기능 전체가 막으려던 바로 그 상황이다.

**제안**: `sm_is_replication_class()`를 `int sm_get_class_replication(MOP, bool *is_replication)` 형태로 바꿔 에러를 명시적으로 전파하고, 모든 호출부에서 에러 발생 시 "복제 아님"으로 조용히 넘어가지 않고 상위로 에러를 전달하도록 수정. 최소한 `do_alter()`의 재검증 게이트에서는 에러를 삼키지 말아야 한다. (#6467, #6908 — 동일 패턴 재발, 서버 측 대응 사례인 #7697이 있음에도 클라이언트 측 이 함수는 그대로 남음)

## 문제 3 — [치명] `do_alter()`의 RK 재검증 트리거가 "여러 절 중 첫 번째 절의 alter_code"만 보고 판단함 (변동 없음)

**위치**: `src/query/execute_schema.c:1839`(`entity_name` 및 게이트 판정에 쓰이는 `alter` 파라미터), `:2051-2059`

**로직 설명**: `do_alter(PARSER_CONTEXT *parser, PT_NODE *alter)`에서 `alter`는 콤마로 나열된 ALTER 절 리스트의 **첫 번째 노드**를 가리키는 고정 포인터다. 함수 내부의 `for (crt_clause = alter; crt_clause != NULL; crt_clause = crt_clause->next)` 루프는 각 절을 `crt_clause`로 순회하며 `const PT_ALTER_CODE alter_code = crt_clause->info.alter.code;`로 절별 코드를 얻지만(`:1854`), RK 재검증이 필요한지 판단하는 다음 코드는 `crt_clause`나 `alter_code`가 아니라 **루프 밖에서 고정된 `alter` 자체**를 참조한다:
```c
if (!need_check_repl_constraint && IS_REPL_CONSTRAINT_RELATED_ALTER (alter->info.alter.code))
  {
    need_check_repl_constraint = true;
  }
```
`alter->info.alter.code`는 루프가 몇 바퀴를 돌든 항상 **리스트의 첫 번째 절의 코드**로 고정되어 있다. `IS_REPL_CONSTRAINT_RELATED_ALTER`는 `PT_ADD_ATTR_MTHD`/`PT_DROP_ATTR_MTHD`/`PT_DROP_CONSTRAINT`/`PT_DROP_PRIMARY_CLAUSE` 네 가지만 인정한다(`:109` 매크로 정의).

**문제 시나리오**: `ALTER TABLE t COMMENT='x', DROP PRIMARY KEY;` 같이, RK와 무관한 절(COMMENT 변경)이 **먼저** 오고 RK를 제거하는 절이 **뒤에** 오는 다중 절 ALTER TABLE 문을 실행하면, `alter->info.alter.code`는 첫 절의 코드로 고정되어 있어 `need_check_repl_constraint`는 끝까지 `false`로 남는다. 결과적으로 `check_ha_repl_constraint()`가 전혀 호출되지 않아 PK를 제거해 RK가 하나도 없는 복제 테이블이 만들어져도 통과한다.

**제안**: `alter->info.alter.code` 대신 루프 안에서 `crt_clause->info.alter.code`(또는 `alter_code` 지역 변수)로 매 절을 검사하도록 수정. 즉 `need_check_repl_constraint |= IS_REPL_CONSTRAINT_RELATED_ALTER(alter_code);`로 바꿔 절 전체에 대해 OR 누적해야 한다. (#6637 관련 회귀)

## 문제 4 — [치명] `rkcheck` 유틸리티가 위반 목록 파일 오픈 실패를 점검하지 않아 크래시 가능 (변동 없음, 라인 이동)

**위치**: `src/executables/util_cs.c:3320`(`rkcheck()`의 `fp = open_violation_list_file(...)` 호출), `:2855-2864`(`open_violation_list_file`), `PRINT_SECTION_TITLE`/`PRINT_MESSAGE`/`PRINT_BLANK_LINE` 매크로(`:92-110`)

**로직 설명**: `rkcheck()`는 `db_restart()`로 서버 연결이 확인된 뒤 `fp = open_violation_list_file(database_name, arg->command_name, violation_list_file, PATH_MAX);`를 호출한다. `open_violation_list_file()`은 내부적으로 `fopen(file_path, "w")`의 결과를 그대로 반환하는데, 호출부인 `rkcheck()`는 **`fp`가 `NULL`인지 전혀 검사하지 않고** 곧바로 `classes = db_get_all_classes();` 이후 `PRINT_SECTION_TITLE (fp, RK_CONSTRAINT_VIOLATIONS_SECTION_TITLE);`(내부적으로 `fprintf(fp, ...)`)를 호출한다.

**문제 시나리오**: `rkcheck`는 `util_service.c`의 `us_hb_process_rkcheck()`를 통해 `cubrid hb start` 시 **자동으로** 기동 전 사전 점검으로 실행된다(#6658). 로그 디렉터리 권한 문제, 디스크 풀 등으로 `fopen()`이 실패하면 `fp`는 `NULL`인 채로 이어서 `fprintf(NULL, ...)`를 호출해 정의되지 않은 동작(대부분 세그폴트)이 발생한다. "HA 기동을 막아야 할 사전 점검 도구"가 오히려 원인 불명의 크래시로 `hb start` 전체를 막아버릴 수 있다.

**제안**: `fp == NULL`을 즉시 확인해 `PRINT_AND_LOG_ERR_MSG`로 명확한 에러를 남기고 `err = ER_FAILED; goto end1;`로 빠지도록 수정.

## 문제 5 — [중요] `do_promote_partition()`의 복합 NOT NULL UNIQUE 제약 승격 로직이 두 번째 컬럼부터 UNIQUE 플래그를 지워버림 (변동 없음, 라인 이동)

**위치**: `src/query/execute_schema.c:7837-7873`(`has_notnull_unique_constraints()`), `:7940-7959`(`do_promote_partition()`의 속성 순회 루프)

**로직 설명**: 파티션을 일반 테이블로 승격할 때, "PK 또는 NOT NULL UNIQUE(RK)"까지 속성을 넘기도록 확장한 반복문:
```c
for (smattr = ctemplate->attributes; smattr != NULL; smattr = ...)
  {
    ...
    if (!has_notnull_unique && has_notnull_unique_constraints (smattr))
      {
        has_notnull_unique = true;
      }
    else
      {
        smattr->flags &= ~(SM_ATTFLAG_UNIQUE);
        smattr->flags &= ~(SM_ATTFLAG_REVERSE_UNIQUE);
      }
    ...
  }
```
`has_notnull_unique`는 함수 전체에서 공유되는 **단일 bool 플래그**다. 컬럼을 순서대로 순회하다가 NOT NULL UNIQUE 제약을 만족하는 **첫 번째** 컬럼에서 `has_notnull_unique`가 `true`로 바뀌면, 그 뒤로 순회하는 모든 컬럼은 `!has_notnull_unique` 조건이 항상 거짓이 되어 무조건 `else` 분기로 빠져 `SM_ATTFLAG_UNIQUE`/`SM_ATTFLAG_REVERSE_UNIQUE` 플래그가 제거된다 — **해당 컬럼이 같은 복합 UNIQUE 제약의 일부인지 여부와 무관하게.**

**문제 시나리오**: `(col_a, col_b)`에 대한 복합 `NOT NULL UNIQUE` 제약(RK)을 가진 파티션 테이블을 승격하면, `col_a`는 UNIQUE 플래그가 보존되지만 바로 다음 `col_b`는 `has_notnull_unique_constraints(col_b)` 평가조차 되지 않고 `else`로 빠져 UNIQUE 플래그가 제거된다. `ctemplate->properties`(실제 제약 정의)는 별도로 유지되므로 제약 자체가 사라지진 않지만, 속성 플래그와 제약 정의가 불일치하는 상태로 클래스가 생성된다.

**제안**: "이 테이블에 RK가 하나라도 있는가"(전체 판정)와 "이 특정 컬럼의 UNIQUE 플래그를 지울 것인가"(컬럼별 판정)를 분리. 컬럼별 플래그 클리어는 `has_notnull_unique_constraints(smattr)` 자체의 참/거짓으로만 결정하고, 전체 판정용 `has_notnull_unique`는 별도 OR 누적 변수로 관리.

## 문제 6 — [중요] `or_class_is_replication_on()`이 클래스 플래그 비트를 매직 넘버로 하드코딩, 주석은 리네임 전 이름을 참조 (변동 없음, 라인 이동)

**위치**: `src/base/object_representation_sr.c:782-792`

**로직 설명**:
```c
bool
or_class_is_replication_on (RECDES * record)
{
  int flags = 0;
  int replication_off_flag = 32;    /* SM_CLASSFLAG_REPLICATION_OFF = 32 */
  ...
  return !(flags & replication_off_flag);
}
```
실제 플래그 정의는 `src/object/class_object.h:312`에 `SM_CLASSFLAG_DATA_REPLICATION_OFF = 32`로 있다. 이 이름은 PR #6477에서 "데이터 복제라는 의미를 강조"하려고 리네임된 이름인데, 이 함수는 값 32를 직접 박아 넣고 주석에는 **리네임 전의 옛 이름**을 적어놨다.

**문제 시나리오**: 향후 `SM_CLASSFLAG_*` 열거형에 재배치나 추가가 있을 때, 이 함수만 손으로 동기화해야 하는 구조라 불일치가 나기 쉽다. 실제로 지금 시점에도 주석 문구 자체가 이미 한 세대 뒤처져 있다는 것이 이를 방증한다.

**제안**: 매직 넘버 대신 `SM_CLASSFLAG_DATA_REPLICATION_OFF`를 직접 참조하거나, 최소한 주석을 현재 이름으로 갱신.

## 문제 8 — [보통] `do_alter_change_replication()`이 세이브포인트 이름을 다른 기능("COMMENT 변경")과 그대로 재사용 (변동 없음, 라인 이동)

**위치**: `src/query/execute_schema.c:11730-11753`, `:11823`(`do_alter_change_replication`), 대조: `:11505,11571`(`do_alter_change_tbl_comment`)

**로직 설명**: `do_alter_change_replication()`은 자신의 트랜잭션 저장점을 만들 때 `tran_system_savepoint (UNIQUE_SAVEPOINT_CHANGE_TBL_COMMENT)` / `tran_abort_upto_system_savepoint (UNIQUE_SAVEPOINT_CHANGE_TBL_COMMENT)`로, **테이블 코멘트 변경용으로 이미 존재하는** 매크로를 그대로 갖다 썼다. 정작 이 함수는 REPLICATION 옵션을 바꾸는 함수이지 코멘트를 바꾸는 함수가 아니다.

## 문제 14 — [보통] `heap_get_class_repl_on()`이 인덱스 순회 루프 안에서 매번 재호출됨 — #6908에서 이미 "MAJOR"로 지적됐던 비효율이 #7697의 리팩토링 이후에도 그대로 남음 (신규)

**위치**: `src/transaction/locator_sr.c:8041-8057`(`locator_add_or_remove_index_internal()`), 루프 헤더 `:7860`(`for (i = 0; i < num_btids; i++)`)

**로직 설명**: `locator_add_or_remove_index_internal()`은 한 행(row)의 INSERT/DELETE를 처리하면서 그 클래스가 가진 **모든 B-tree 인덱스**를 순회한다(`for (i = 0; i < num_btids; i++)`). 이번 동기화가 가져온 #7697은 이 루프 안의 복제 로그 생성 분기를 다음과 같이 고쳤다:
```c
if (error_code == NO_ERROR && need_replication && !replicated
    && or_is_replication_candidate_key (index)
    && !LOG_CHECK_LOG_APPLIER (thread_p) && log_does_allow_replication () == true)
  {
    bool repl_on = false;

    error_code = heap_get_class_repl_on (thread_p, class_oid, &repl_on);
    if (error_code == NO_ERROR && repl_on)
      {
        error_code = repl_log_insert (...);
        replicated = true;
      }
  }
```
`heap_get_class_repl_on()`은 내부적으로 `heap_get_class_record()`로 카탈로그 페이지를 fetch하는 비용이 있는 호출이다. `class_oid`는 이 함수 호출 전체에서 동일한 하나의 클래스이므로 복제 여부(`repl_on`)는 루프가 몇 바퀴를 돌든 바뀔 수 없는 값인데, `replicated`는 오직 `repl_on == true`이고 `repl_log_insert()`까지 성공했을 때만 `true`로 설정된다. 즉 **`REPLICATION=OFF`인 테이블일수록(`repl_on`이 계속 `false`) `replicated`가 끝까지 `false`로 남아, PK/UNIQUE-NOT-NULL(RK 후보) 인덱스가 여러 개 걸린 테이블이면 그 인덱스 개수만큼 매번 카탈로그 페이지를 다시 fetch한다.**

이 정확히 같은 지점(당시는 `heap_is_replication_class()`)에 대해 PR #6908 리뷰에서 "같은 `class_oid`에 대해서는 결과가 항상 동일하므로 루프 밖으로 빼야 한다"는 MAJOR 코멘트가 이미 나왔었다(`pr_히스토리.md` #6908 항목 참조). 이번 재리뷰에서 확인한 바로는, #7697이 바로 이 블록을 함수 시그니처까지 바꿔가며(`bool` → `int` 에러 코드 + out-param) 다시 손봤음에도 불구하고, "루프 밖으로 빼자"는 제안 자체는 반영되지 않고 그대로 남아 있다. 함수 상단 TODO(`:8039-8040`, "we need to review a method to record replication logs only when the RK has already been determined, instead of checking all RK candidates")도 이 부채를 그대로 인정하고 있다.

**문제 시나리오**: `REPLICATION=OFF`이면서 PK 외에 NOT NULL UNIQUE 인덱스를 여러 개 가진 테이블에 대량 INSERT/DELETE를 수행하면, 행 하나당 해당 인덱스 개수만큼 `heap_get_class_record()` 카탈로그 fetch가 반복된다. 정합성 버그는 아니지만, 대량 적재·배치 삭제 워크로드에서 불필요한 페이지 fetch가 인덱스 수에 비례해 누적되는 성능 저하이며, 이미 한 차례 팀 리뷰에서 지적됐던 개선 요청이 두 번째 손질 기회(#7697)에서도 반영되지 않았다는 점에서 "과거 리뷰 피드백이 반복적으로 이월되는" 패턴으로 기록해둔다.

**제안**: `class_oid`가 바뀌지 않는 한 `heap_get_class_repl_on()` 결과를 루프 진입 전에 한 번만 조회해 지역 변수에 캐시하고, 루프 안에서는 그 값을 재사용하도록 리팩토링. (#6908 리뷰 피드백 반영 필요, TODO `:8039-8040`과 함께 EPIC CBRD-26096 후속 정리 대상으로 명시 권장)
