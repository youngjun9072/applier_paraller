# RK/REPLICATION 코드 리뷰 — 응용개발자 1년차 관점 (3차 전수 재수색 추가분)

> **3차 전수 재수색 (기준 `734f4959d`)** — merge-base `b646647ec`...HEAD 전체 35파일을 다시 훑었습니다.
> 기존 리포트(`응용개발자_1년차.md`)의 유지 문제 15건과, 1·2차 병합본 67건(`dedup_existing.json`)에
> 아직 안 잡힌 뿌리만 신규로 셌습니다. 잔여 쿼터 = 50 − 15 = 35.
>
> 재수색 방법은 1·2차와 동일합니다(diff를 Read로 직접 읽고 콜체인을 따라감, 키워드 grep 단독 판단 금지,
> 억지 지적 금지). 신규 문제 번호는 기존 리포트(…17)에 이어서 붙입니다.

## 결론 요약

전체 diff는 이미 매우 촘촘하게 파헤쳐져 있습니다(병합 67건 + 제 유지 15건). 3차에서 제가 새로 연 파일들을
콜체인까지 따라간 결과, **파서 언파스(parse-tree 재출력) 경로에서 REPLICATION 옵션 처리가 빠진 곳 2건**을
찾았습니다. 둘 다 실행/복제 자체를 깨뜨리진 않지만(스키마 DDL 복제는 `sql_user_text` 원문을 실어 나르므로),
진단·트레이스·에러 컨텍스트에서 파스트리를 다시 문자열로 찍을 때 REPLICATION 절이 **엉뚱한 값으로 찍히거나
아예 사라집니다.** 처음 읽는 눈으로 "COMMENT는 되는데 REPLICATION만 왜 안 되지?"라는 비대칭이 눈에 띄었습니다.

나머지 영역에서는 근거 있는 신규 결함을 추가로 찾지 못했습니다(근거는 맨 끝 커버리지 요약 참조).

## 문제 18 (신규)

**[심각도: 사소] `pt_print_table_option()`의 REPLICATION 재출력이 ON/OFF가 아니라 원시 정수 `1`/`0`으로 찍힘 — 파스트리 언파스가 사용자 표기와 어긋남**

- 위치: `src/parser/parse_tree_cl.c:8041-8043` (REPLICATION case), 값 출력 분기 `:8048-8075`

로직 설명: CREATE TABLE의 테이블 옵션을 다시 문자열로 찍는 `pt_print_table_option()`은 switch에서 옵션 종류별로
접두어를 붙인 뒤(8018~8046), switch **밖**에서 `p->info.table_option.val`을 이어 붙입니다(8048~).
이때 CHARSET/COLLATION은 따옴표 없는 문자열로(8050), ENCRYPT는 **알고리즘 이름 문자열**로(8060, `tde_get_algorithm_name` → "AES"/"ARIA") 예쁘게 찍고, 그 외에는 전부 `pt_print_bytes_l()`로 값을 그대로 찍습니다(8071-8074).

REPLICATION 옵션의 `val`은 `class_replication_spec` 문법이 만든 **PT_VALUE 정수 노드**(`ON→1`, `OFF→0`, csql_grammar.y `opt_replication_option`)입니다. 이 case(8041)는 접두어 `"replication = "`만 붙이고 값 출력은 일반 분기(8073)로 떨어지므로, 결과는 **`replication = 1`** 또는 **`replication = 0`**이 됩니다. ENCRYPT처럼 정수를 사람이 읽는 키워드로 되돌리는 처리가 없습니다.

문제 시나리오: 스키마 DDL 복제 자체는 `do_replicate_statement()`가 파스트리 재출력이 아니라 `statement->sql_user_text` 원문(execute_statement.c:16519)을 실어 나르므로 복제가 깨지진 않습니다. 다만 파스트리를 문자열로 되돌리는 다른 경로(에러 컨텍스트 재출력, 트레이스/디버그 출력 등)에서 사용자가 `REPLICATION = ON`으로 쓴 옵션이 `replication = 1`로 보입니다. 문법의 `opt_replication_option`은 `ON`/`OFF` 키워드만 받고 정수 `1`은 받지 않으므로, 이 재출력 문자열을 그대로 다시 파싱하면 문법 오류가 됩니다(재파싱 왕복이 성립하지 않음). 처음 이 코드를 읽는 사람은 ENCRYPT/COLLATION은 이름으로 찍는데 REPLICATION만 숫자로 찍히는 비대칭에 걸려 넘어집니다.

제안: REPLICATION case에서 값을 사람이 읽는 키워드로 되돌리십시오(예: `val->info.value.data_value.i ? "on" : "off"`를 접두어와 함께 출력). ENCRYPT가 `tde_get_algorithm_name()`으로 정수를 이름으로 바꾸는 것과 같은 방식입니다.

## 문제 19 (신규)

**[심각도: 사소] `pt_print_alter_one_clause()`에 `PT_CHANGE_REPLICATION` case 부재 — `ALTER TABLE … REPLICATION=…`의 파스트리 재출력이 절을 통째로 누락 (COMMENT는 되는데 REPLICATION만 사라짐)**

- 위치: `src/parser/parse_tree_cl.c:5784-5787` (`switch (p->info.alter.code)`의 `default: break;`), 대조 case `:5793-5797`(`PT_CHANGE_TABLE_COMMENT`)

로직 설명: ALTER 절 하나를 문자열로 되돌리는 `pt_print_alter_one_clause()`는 `p->info.alter.code`로 switch합니다(5784). 여기에는 `PT_CHANGE_OWNER`(5788), `PT_CHANGE_TABLE_COMMENT`(5793), `PT_CHANGE_COLLATION`(5798) 등 코멘트·소유자·콜레이션 변경 절의 출력 case가 각각 있습니다. 그런데 이번에 추가된 `PT_CHANGE_REPLICATION`(parse_tree.h:1299, 문법 `alter_clause_for_alter_list`가 `alter.code = PT_CHANGE_REPLICATION` + `alter_clause.replication.tbl_replication`로 채움) 에 대한 case가 **없습니다.** 따라서 이 코드는 `default: break;`(5786-5787)로 떨어져 **아무것도 출력하지 않습니다.**

REPLICATION 절은 COMMENT 절을 본떠 설계됐는데(parse_tree.h의 `alter_clause.replication`가 `alter_clause.comment`와 나란히 추가됨), 출력 함수에는 COMMENT case(5793)만 따라 만들어지고 REPLICATION case는 빠졌습니다. 전형적인 "패턴을 반쯤만 복제한" 누락입니다. (참고: apply-walk 쪽 `pt_apply_alter`(5784 위쪽 switch)는 COMMENT도 `default`로 두므로 REPLICATION을 안 걷는 것이 COMMENT와 대칭이라 문제 없음 — 비대칭은 **print 함수에서만** 발생합니다.)

문제 시나리오: `ALTER TABLE t REPLICATION=OFF`의 파스트리를 문자열로 되돌리면 `ALTER TABLE t`처럼 **복제 절이 사라진 문장**이 나옵니다(코멘트 변경이었다면 ` comment = '…'`이 정상적으로 붙는 것과 대비). 실행·복제는 원문(`sql_user_text`)을 쓰므로 안전하지만, 진단/에러 메시지에서 이 문장을 재출력하는 순간 "복제 옵션을 바꾸는 ALTER"가 마치 아무 절도 없는 no-op ALTER처럼 보여, 원인 추적을 어렵게 합니다.

제안: COMMENT case(5793-5797)와 동형으로 `PT_CHANGE_REPLICATION` case를 추가해 ` replication = on|off`를 출력하도록 하십시오(문제 18과 함께 값→키워드 변환을 통일).

## 조사 종료 선언

여기서 3차 재수색을 종료합니다. 잔여 쿼터(35)를 다 채우지 못했으나, **억지로 개수를 채우지 않았습니다.**
현 시점 응용개발자 1년차 누적 = 유지 15 + 신규 2 = **17건**.

### 3차에서 새로 훑은 영역과 판단 근거

- **파서 언파스 경로**(`parse_tree_cl.c`) — 이번 신규 2건의 출처. `pt_print_table_option`/`pt_print_alter_one_clause`를 콜체인(문법 `class_replication_spec`/`alter_clause_for_alter_list` → PT_VALUE 노드 → 재출력)까지 따라가 확인. COMMENT/ENCRYPT 대조로 비대칭을 근거화.
- **문법·세만틱**(`csql_grammar.y`, `csql_lexer.l`, `semantic_check.c`, `parse_tree.h`) — REPLICATION 토큰·`opt_replication_option`·CREATE 중복옵션 세만틱 체크(`MSGCAT_SEMANTIC_DUPLICATE_TABLE_OPTION`) 추가를 확인. CREATE 중복 방어는 있으나 ALTER 다중 REPLICATION 절 조용한 무시는 이미 병합본(K-20)에 존재하여 신규 아님.
- **`class_object.c`의 제약 복사**(`classobj_copy_pk_and_uk_notnull_constraints`) — "PK 미복사" 가설을 세워 `SM_IS_CONSTRAINT_UNIQUE_FAMILY`(class_object.h:111) 정의를 확인한 결과 **PK를 포함**하므로 PK도 복사됨 → 오판. 신규 아님(주석/함수명 불일치는 병합본 K-35 계열).
- **`do_create_entity`의 create_like + RK 검사 순서** — check_ha_repl_constraint가 do_copy_indexes보다 먼저 실행되어 PK를 못 볼 것이라는 가설을 세웠으나, `smt_copy_class`가 PK/UK/FK를 미리 복사하고(`do_copy_indexes`가 순수 INDEX/REVERSE_INDEX만 처리하며 "These should have been copied already" 주석) 검사 시점에 이미 제약이 존재 → 오판. 신규 아님.
- **`do_create_entity` 복제 OFF 경로의 `break` vs 복제 ON 경로의 `goto error_exit`** — 비대칭이나, `break`는 switch 이후 `if (error != NO_ERROR) goto error_exit`로 수렴하고 AU/savepoint 누수 없음. 관련 `assert(error==NO_ERROR)`(10351) 취약은 tde/collation 등 기존 `break` 경로와 동일한 develop 수준 패턴 → 신규 결함으로 세지 않음.
- **에러코드 신설**(`error_code.h` -1375~-1378, `ER_LAST_ERROR`=-1379) — 메시지(`cubrid.msg` en/ko 1375~1378)와 매핑·문구 정합 확인. `dbi_compat.h`는 애초에 `#define ER_` 항목을 하나도 두지 않는 파일이라(0건) 이 계열 미러링 대상이 아님 → 지적 없음.
- **`util_service.c`/`util_cs.c`/`checksumdb.c`/`unload_schema.c`/`object_printer.cpp`/`locator_sr.c`/`heap_file.c`/`btree.c`/`schema_manager.c`/카탈로그** — 병합본 K-2·K-7·K-8·K-19·K-26·K-28~K-30·K-42·K-44·K-45·K-50·K-55~K-58·K2-2 및 제 유지 문제(5·6·7·9·11·12·17)로 포화 상태. 콜체인 재확인만 하고 신규 없음. (§7 지침대로 `locator_update_index`의 `heap_is_replication_class` 잔존 호출은 수정 완료 간주하여 미지적.)

### 더 없다고 보는 근거

제 직무 관심(DDL 조합·마이그레이션 표면·처음 읽는 눈의 오타/복붙/비대칭)에서 아직 안 잡힌 뿌리는
파서 언파스 비대칭 2건으로 소진했습니다. 나머지 diff는 스토리지/런타임 복제/유틸 계층으로, 이미 20페르소나의
1·2차 병합(67건)과 제 유지 15건이 촘촘히 덮고 있어 근거 있는 신규를 더 뽑기 어렵다고 판단합니다.
