> 기준 HEAD가 `734f4959d`(= `44468ed73` + #7678 `3b6ebd1a9` + #7697 `9e094324b`)로 바뀌었습니다.
> 아래는 1차 13건을 새 HEAD에서 재검증(유지/해소/폐기)하고, 동기화 델타(#7678 SBR 게이트,

## 페르소나 소개

저는 3년차 애플리케이션 개발자입니다. 하루 대부분을 JDBC/ORM 위에서 CRUD를 짜고,
운영 중에는 마이그레이션 도구(Flyway/Liquibase류)나 손으로 만든 DDL 스크립트를 돌려
스키마를 바꿉니다. 그래서 제 관심사는 "엔진이 얼마나 정교한가"보다 **흔한 DDL 조합이
정상 경로를 타는가**입니다. 구체적으로:

- 한 문장에 여러 절을 붙이는 멀티 `ALTER TABLE`(PK 교체, 컬럼 추가+제약 삭제 동시)
- `CREATE TABLE ... LIKE`, `CREATE TABLE ... AS SELECT`(CTAS), `RENAME`, 상속(`UNDER`), 파티션
- `MODIFY`/`CHANGE COLUMN`으로 컬럼 속성(NOT NULL 등)만 바꾸는 경우
- 마이그레이션 도구가 자동 생성하는 DDL 시퀀스가 예약어·문법 변화로 깨지는 지점
- 트랜잭션 중간 실패 시 남는 상태, 그리고 드라이버/메타데이터로 사용자에게 보이는 표면

## 총평 (2차)

동기화 델타의 핵심인 #7678(SBR 복제 게이트 재정비)은 잘 만들어졌습니다. `is_data_repl_log_enabled`가
INSERT/UPDATE/DELETE의 **실제 수정 대상 spec**(`PT_SPEC_FLAG_UPDATE`/`PT_SPEC_FLAG_DELETE`)만 보도록
바뀌었고, updatable vclass가 파생 테이블로 재작성되는 경우까지 `spec_has_replication_class()`로
걷어냅니다. 단일 테이블 UPDATE도 `pt_process_spec_for_update()`가 대상 spec에 플래그를 확실히
찍으므로 정상 경로에서 SBR이 누락되는 회귀는 없었습니다(확인 완료). #7697은 서버측 인터럽트
전파를 int+out-param으로 근본 수정했고, 이 영역은 제 직무 밖(DB엔진개발자 관점)이라 표면만 확인했습니다.

그럼에도 1차에서 지적한 **DDL 조합 게이트의 구멍**은 새 HEAD에도 그대로 남아 있습니다. 멀티
`ALTER TABLE`의 재검사 트리거가 여전히 "첫 번째 절의 종류"만 보고(문제 1), MODIFY/CHANGE로
NOT NULL만 떼는 RK 상실 경로가 게이트에 빠져 있으며(문제 2), `rkcheck`의 파일 열기 실패
무방비(문제 3)도 유지됩니다. `REPLICATION`이 완전 예약어가 되어 마이그레이션을 깨뜨리는 점(문제 10),
상속(`UNDER`)이 부모 복제 옵션을 안 물려받는 점(문제 8)도 코드에서 재확인했습니다.

1차 문제 6(SBR default 분기)은 재검증 결과 **오판**으로 판명되어 폐기했습니다(사유는 재검증 요약 참조).
동기화 델타에서 제 직무 관점의 **새 결함은 발견하지 못했습니다** — 조사 종료를 선언합니다.

## 문제 1

**[심각도: 중요] 멀티 ALTER TABLE의 RK 재검사 게이트가 "첫 번째 절"의 종류만 본다** *(유지)*

위치: `src/query/execute_schema.c:2051`(게이트), `:1851-2057`(루프), 매크로 `:109-114`

로직 설명:
`do_alter()`는 한 `ALTER TABLE` 문에 붙은 여러 절을 `for (crt_clause = alter; ...; crt_clause = crt_clause->next)`
로 순회합니다(1851행). 각 절의 종류는 지역변수 `alter_code = crt_clause->info.alter.code`(1854행)입니다.
모든 절을 처리한 뒤 마지막에 딱 한 번 `check_ha_repl_constraint()`로 "RK가 아직 있는지 / FK 참조
대상이 복제 대상인지"를 재검사합니다(2059-2073행). 이 재검사 여부를 정하는 게이트가 2051행입니다:

```c
if (!need_check_repl_constraint && IS_REPL_CONSTRAINT_RELATED_ALTER (alter->info.alter.code))
```

여기서 `alter->info.alter.code`는 **루프 헤드(=첫 번째 절)의 종류**입니다(`alter`는 함수 진입 시
고정된 첫 절 노드). 정작 지금 처리 중인 절은 `crt_clause`(=`alter_code`)인데, 게이트는 매 반복마다
항상 첫 절 코드만 재평가합니다. 새 HEAD에서도 2051행이 `alter->info.alter.code` 그대로입니다.

문제 시나리오:
HA 모드에서 RK가 NOT NULL UNIQUE 하나뿐인 테이블 `t`에 대해
`ALTER TABLE t CHANGE c1 c1 INT COMMENT '...', DROP CONSTRAINT u_t_rk;` 처럼
**첫 절은 RK 무관(PT_CHANGE_ATTR)**, **두 번째 절이 RK 제거(PT_DROP_CONSTRAINT)**하는 조합을 실행하면:
- 첫 절 코드 `PT_CHANGE_ATTR`는 게이트 목록(ADD_ATTR_MTHD / DROP_ATTR_MTHD / DROP_CONSTRAINT /
  DROP_PRIMARY_CLAUSE)에 없어 `need_check_repl_constraint`가 끝까지 false로 남습니다.
- 두 번째 절이 실제로 RK를 없앴는데도 최종 재검사가 건너뛰어져, RK 없는 복제 테이블이 남습니다.
  이후 이 테이블의 DML이 슬레이브로 복제되지 못하거나 applylogdb가 에러를 냅니다(이 기능이 막으려던 상황).

`DROP CONSTRAINT`나 `ADD COLUMN`이 첫 절로 오면 우연히 검사가 걸리므로, 절 순서에 따라 결과가
달라지는 비결정적 버그입니다.

제안: 게이트를 지역변수 `alter_code`(현재 절)로 바꿔 절별로 OR 누적해야 합니다:
`IS_REPL_CONSTRAINT_RELATED_ALTER (alter_code)`. 검사를 `do_alter`로 옮긴 PR #6637의 취지
(모든 절 처리 후 최종 상태 1회 검증)를 살리려면 트리거는 절별로 OR 되어야 합니다.

## 문제 2

**[심각도: 중요] MODIFY/CHANGE COLUMN이 재검사 게이트에서 빠져 있어 NOT NULL 해제로 RK를 조용히 잃는다** *(유지)*

위치: `src/query/execute_schema.c:109-114`(`IS_REPL_CONSTRAINT_RELATED_ALTER` 정의)

로직 설명:
RK 후보 판정은 "PK, 또는 모든 구성 컬럼이 NOT NULL인 UNIQUE"입니다
(`IS_HA_REPLICATION_KEY_CONSTRAINT` → `sm_has_non_null_attribute`). 즉 UNIQUE 컬럼에서 NOT NULL이
사라지면 그 UNIQUE는 더 이상 RK가 될 수 없습니다. 그런데 컬럼 속성을 바꾸는 경로인
`PT_CHANGE_ATTR`(CHANGE COLUMN), `PT_MODIFY_ATTR_MTHD`(MODIFY COLUMN)는 게이트 목록(109-114행)에
아예 없습니다. do_alter의 switch(1874행~)에서 이 두 코드는 처리되지만 RK 재검사를 트리거하지 못합니다.

문제 시나리오:
HA 모드, RK가 `b INT NOT NULL UNIQUE` 하나뿐인 테이블에서 `ALTER TABLE t MODIFY b INT UNIQUE;`
(NOT NULL 제거)를 실행하면, UNIQUE는 남지만 NOT NULL이 사라져 RK 자격을 잃습니다. 하지만 게이트에
MODIFY/CHANGE가 없어 재검사가 돌지 않고 RK 없는 복제 테이블이 통과합니다.

제안: `IS_REPL_CONSTRAINT_RELATED_ALTER`에 `PT_CHANGE_ATTR`, `PT_MODIFY_ATTR_MTHD`를 추가.
NOT NULL 제거는 RK 상실의 흔한 경로이므로 반드시 포함해야 합니다.

## 문제 3

**[심각도: 중요] rkcheck가 위반 목록 파일 열기 실패(fopen==NULL)를 검사하지 않아 크래시한다** *(유지)*

위치: `src/executables/util_cs.c` `open_violation_list_file()`(2856행, `return fopen(...)` 2863행),
`rkcheck()`의 사용부(3320행 오픈 / 3332행 첫 사용)

로직 설명:
`rkcheck()`는 서버 접속 후 `fp = open_violation_list_file (...)`로 로그 파일을 엽니다(3320행).
`open_violation_list_file`은 마지막에 `return fopen (file_path, "w");`만 하고(2863행), 호출부도
반환값 NULL 여부를 전혀 확인하지 않습니다. 이후 곧바로 `PRINT_SECTION_TITLE (fp, ...)`(3332행,
내부적으로 `fprintf(fp, ...)`)와 `check_repl_constraint_violations(classes, fp, ...)`(3333행)가
실행됩니다. `fp`가 NULL이면 `fprintf(NULL, ...)`로 즉시 세그폴트입니다. 3320↔3332 사이에 NULL 검사가
없음을 새 HEAD에서 재확인했습니다.

콜체인 확인: `util_service.c`가 `cubrid hb start` 시 rkcheck를 자동 호출하므로(PR #6658, #6934),
이 크래시는 HA 기동 경로에서 발생합니다.

문제 시나리오:
로그 디렉터리에 쓰기 권한이 없거나, 디스크가 가득 찼거나, 경로가 없으면 `fopen`이 NULL을 반환합니다.
운영자가 권한을 조금만 잘못 잡아도 HA 기동이 "명확한 에러 메시지"가 아니라 유틸리티 크래시로 실패합니다.

제안: `fp == NULL`이면 에러 메시지를 출력하고 `err = ER_FAILED; goto end1;`로 정상 종료해야 합니다.
`check_database_name` 실패 경로(#6934에서 지적된 er_set 누락)와도 톤을 맞출 것.

## 문제 4

**[심각도: 보통] 재검사 게이트 목록이 불완전 — DROP INDEX 등 다른 RK 영향 경로 누락** *(유지)*

위치: `src/query/execute_schema.c:109-114`

로직 설명:
문제 1·2의 근본은 게이트 목록(`PT_ADD_ATTR_MTHD, PT_DROP_ATTR_MTHD, PT_DROP_CONSTRAINT,
PT_DROP_PRIMARY_CLAUSE`)이 "RK에 영향을 줄 수 있는 모든 절"을 열거하지 못한다는 데 있습니다.
스펙 예시 16은 "복제 키 후보가 없어지는 DROP INDEX는 막아야 한다"고 명시하는데, do_alter의 switch에서
인덱스 삭제는 `PT_DROP_INDEX_CLAUSE`로 처리되며 게이트 목록에는 없습니다. RK를 뒷받침하는 UNIQUE
인덱스를 인덱스 경로로 제거하는 조합에서 재검사가 누락될 소지가 있습니다.

문제 시나리오:
RK가 UNIQUE 인덱스 하나뿐인 복제 테이블에서 그 UNIQUE를 인덱스 삭제 계열 절로 제거하는 멀티 ALTER를
구성하면, 문제 1과 같은 경로로 최종 재검사가 돌지 않을 수 있습니다.

제안: 게이트를 "허용 목록(열거)"이 아니라 "제외 목록"으로 뒤집는 편이 안전합니다. RK와 확실히 무관한
절(COMMENT, AUTO_INCREMENT, OWNER 등)만 빼고, 스키마를 건드리는 나머지는 최종 재검사를 한 번 도는
쪽이 누락 위험이 적습니다(`check_ha_repl_constraint`는 ALTER당 1회 비용이라 무시할 만하며, #6637
주간회의에서 이미 합의된 판단과 일치).

## 문제 5

**[심각도: 보통] TRUNCATE 복제 판정이 REPLICATION=OFF 플래그를 무시하고 RK 유무만 본다** *(유지)*

위치: `src/query/execute_statement.c:342-384`(`truncate_need_repl_log`), 판정식 `:376`

로직 설명:
`truncate_need_repl_log()`는 대상 테이블의 제약을 보고 `cons = classobj_find_cons_replication_key
(class_->constraints)`가 non-NULL이면 `true`(복제 로그 생성)를 반환합니다(376-380행). #6826에서
`classobj_find_cons_primary_key` → `classobj_find_cons_replication_key`로 확장한 것은 "PK뿐 아니라
NOT NULL UNIQUE도 RK"라는 취지 반영이지만, **테이블의 `SM_CLASSFLAG_DATA_REPLICATION_OFF` 여부는
전혀 확인하지 않습니다.** 새 HEAD에도 OFF 플래그 검사가 없음을 재확인했습니다.

문제 시나리오:
`CREATE TABLE t(a INT PRIMARY KEY) REPLICATION=OFF;`처럼 RK는 있지만 복제 제외인 테이블에
`TRUNCATE t;`를 하면 RK가 있으므로 복제 로그가 생성되어 슬레이브로 TRUNCATE가 전파됩니다. OFF 테이블은
슬레이브가 독립 데이터를 가질 수 있는데 그 데이터가 TRUNCATE로 지워집니다. "OFF = 데이터 복제 안 함"
약속과 어긋납니다.

제안: `truncate_need_repl_log`에 `sm_is_replication_class(class_mop)`(또는 플래그 직접 확인)를 AND
조건으로 추가.

## 문제 7

**[심각도: 보통] ON·OFF 테이블을 함께 건드리는 SBR 문장은 전체가 슬레이브에서 재실행되어 결과가 어긋난다** *(유지 — 저자가 known limitation으로 명문화)*

위치: `src/query/execute_statement.c:3319-3344`(`is_data_repl_log_enabled`의 UPDATE/DELETE 루프),
`spec_has_replication_class`(3283-3316)

로직 설명:
#7678로 재작성된 `is_data_repl_log_enabled`는 멀티 테이블 UPDATE/DELETE에서 `PT_SPEC_FLAG_UPDATE`/
`PT_SPEC_FLAG_DELETE`가 붙은 **수정 대상 spec** 중 하나라도 복제 클래스이면 `return true`입니다(OR 의미,
3326/3338행). SBR은 슬레이브가 원문을 재실행하는 방식이라, 이 경우 문장 전체가 슬레이브에서 다시 돌면서
문장이 참조하는 OFF 테이블(조인 또는 `INSERT ... SELECT` 소스)의 데이터에 의존한 결과가 나옵니다.

이 동작은 #7678 커밋 메시지에 "Known limitation (unchanged): a statement that modifies a replication
target while referencing a replication-off table by join (or INSERT...SELECT source) still re-executes
against an empty/divergent table on the replica"로 **저자가 명시적으로 문서화**했습니다. 다만 커밋
메시지에만 있고 사용자 문서/릴리스 노트로는 아직 표면화되지 않았습니다.

문제 시나리오:
`DELETE /*+ USE_SBR */ a FROM on_orders a, off_customers b WHERE a.cid=b.id AND ...`
— on_orders가 삭제 대상(ON)이라 SBR이 켜지고, 슬레이브가 같은 DELETE를 재실행하면서 슬레이브의
off_customers 데이터(마스터와 다를 수 있음)로 조인 결과가 달라져 예측 불가한 삭제가 일어납니다.
`INSERT /*+ USE_SBR */ INTO on_t SELECT ... FROM off_src`도 같은 부류입니다.

제안: 최소한 이 known limitation을 사용자 문서/릴리스 노트로 끌어올려 "USE_SBR + OFF 테이블 참조" 조합의
동작을 명시. 가능하면 혼합 대상 SBR 문장에 대한 경고/거부 정책 정의.

## 문제 8

**[심각도: 보통] 상속(CREATE TABLE ... UNDER)이 부모의 REPLICATION 옵션을 물려받지 않는다** *(유지)*

위치: `src/query/execute_schema.c:10258-10277`(do_create_entity의 복제 옵션 결정부)

로직 설명:
새 HEAD에서 복제 여부 결정부는 이렇게 갈립니다(10258-10264행):

```c
if (create_like)
  is_replication_on = !(source_class->flags & SM_CLASSFLAG_DATA_REPLICATION_OFF);
else
  is_replication_on = IS_CREATE_STMT_SET_REPL_OPTION (tbl_opt_replication);
```

즉 `CREATE ... LIKE`는 원본 플래그를 상속하지만(#6943), 일반 CREATE(상속 `UNDER` 포함)는 문장에
명시된 옵션(생략 시 기본 ON)만 봅니다. `UNDER`의 super_class는 9984행에서 조회되지만 그 복제 플래그는
`is_replication_on` 결정에 전혀 참조되지 않습니다. 반면 파티션 자식은 부모 플래그를 상속합니다
(do_create_partition, 4809/4957/5189행)—대비됩니다.

문제 시나리오:
`CREATE TABLE parent(...) REPLICATION=OFF;` 뒤에 `CREATE TABLE child UNDER parent;`(옵션 생략)를 하면
child는 부모가 OFF인데도 기본 ON이 됩니다. 운영자는 "부모가 복제 제외니 자식도 그렇겠지"라고 기대하지만
실제로는 child가 복제 대상이 되어, HA에서 부모 데이터는 슬레이브에 없는데 자식만 복제되는 불일치가 생깁니다.

제안: 상속 생성 시 super_class의 `SM_CLASSFLAG_DATA_REPLICATION_OFF`를 참조해 기본값을 결정하거나,
최소한 상속과 REPLICATION 조합에 대한 규칙을 정의.

## 문제 10

**[심각도: 보통] REPLICATION이 예약어가 되어, 이름이 replication인 기존 테이블/컬럼과 마이그레이션 스크립트가 깨진다** *(유지)*

위치: `src/parser/csql_grammar.y:1669`(`%token REPLICATION`), 비예약 identifier 목록(≈20640-20920)

로직 설명:
lexer가 `replication`을 전용 토큰 `REPLICATION`으로 반환합니다(grammar 1669행). 이웃 테이블 옵션
키워드들(REUSE_OID, REVERSE, DISK_SIZE 등)은 비예약 identifier 목록에 `{{ SET_CPTR_2_PTNAME ... }}`로
들어 있어 식별자로도 쓸 수 있지만, **REPLICATION은 이 목록에 없습니다**(20640-20920 구간에서
REPLICATION 항목 부재를 새 HEAD에서 재확인). 결과적으로 `REPLICATION`은 완전 예약어가 됩니다.

문제 시나리오:
기존 스키마에 `replication`이라는 컬럼/테이블이 있으면, 따옴표 없이 그 이름을 쓰던 모든 애플리케이션
쿼리와 마이그레이션 스크립트가 업그레이드 직후 문법 에러로 실패합니다. 업그레이드 호환성 회귀입니다.

제안: grammar의 비예약 identifier 목록에 `REPLICATION` 추가(REUSE_OID/REVERSE와 동일하게).
그러면 옵션으로도, 식별자로도 쓸 수 있습니다.

## 문제 12

**[심각도: 사소] do_alter 최종 재검사가 db_find_class 실패(NULL)를 방어하지 않아 릴리스 빌드에서 검사가 조용히 생략된다** *(유지)*

위치: `src/query/execute_schema.c:2059-2073`

로직 설명:
```c
vclass = db_find_class (entity_name);        /* 2061 */
if (!sm_is_replication_class (vclass))       /* 2063: vclass가 NULL일 수 있음 */
  { return NO_ERROR; }
error_code = check_ha_repl_constraint (vclass);  /* 2068 */
```
`db_find_class`가 NULL을 반환하면 `sm_is_replication_class(NULL)`이 호출됩니다. 이 함수는 NULL 가드로
`assert(false)` 후 false를 반환하므로, **릴리스 빌드에선 false → `!false`=true → `return NO_ERROR`**로
빠져나가 RK 재검사가 조용히 생략됩니다. 새 HEAD 2061-2066행 그대로입니다.

문제 시나리오:
이름 해석/락 경쟁 등 예외 상황에서 `db_find_class`가 NULL을 주면, 오류를 알리는 대신 검사만 건너뜁니다.
"실패를 false로 뭉갠다"는 안티패턴입니다.

제안: `vclass == NULL`이면 `er_errid()`로 에러를 잡아 `goto error_exit`. 성공/실패/미해당을 명확히 구분.

## 문제 13

**[심각도: 사소] is_replication_class가 조회 실패를 assert 후 false로 반환해 SBR 판정을 조용히 왜곡한다** *(유지 — #7678이 새로 넣은 코드에도 동일 패턴 잔존)*

위치: `src/query/execute_statement.c:3201-3216`(`is_replication_class`)

로직 설명:
#7678이 새로 추가한 클라이언트측 헬퍼 `is_replication_class(classname)`은:
```c
class_obj = db_find_class (classname);
if (class_obj == NULL) { assert (false); return false; }
return sm_is_replication_class (class_obj);
```
`db_find_class`가 NULL이면 "복제 클래스 아님"으로 처리합니다(3208-3212행). 이 값은
`spec_has_replication_class` → `is_data_repl_log_enabled`를 거쳐 SBR 복제 여부를 최종 결정합니다.

문제 시나리오:
릴리스 빌드에서 권한/락/일시적 조회 실패가 나면 "에러"가 아니라 "복제 대상 아님"으로 해석되어 USE_SBR
로그가 조용히 생략될 수 있습니다. 복제 누락은 즉시 보이지 않고 슬레이브 데이터 불일치로 뒤늦게 드러나
원인 추적이 어렵습니다.

제안: 조회 실패는 "복제 아님"으로 뭉개지 말고 에러로 전파하는 형태(에러코드 반환 + out-parameter)로 정리.
동기화 델타의 서버측 인터럽트 전파 수정이 지향한 것과 같은 방향(실패를 삼키지 말 것)입니다.

## 조사 종료 선언 (2차)

동기화 델타(#7678 SBR 게이트 재정비, #7697 인터럽트 전파)와 전체 diff를 제 직무 관점
(DDL 조합·트랜잭션 중간 실패·메타데이터 표면·마이그레이션 시퀀스)에서 다시 훑었습니다.

**추가로 확인하고 신규 결함이 아니라고 판단한 것들**
- **단일 테이블 UPDATE/DELETE의 SBR 누락 회귀 의심**: #7678이 게이트를 "첫 FROM spec"에서
  "`PT_SPEC_FLAG_UPDATE`/`PT_SPEC_FLAG_DELETE`가 붙은 수정 대상 spec"으로 바꿨는데, 단일 테이블
  UPDATE도 `pt_process_spec_for_update()`(`parser_support.c:8686`)가 대상 spec에 플래그를 확실히
  찍으므로 정상 경로 SBR 누락은 없었습니다(콜체인 확인). 회귀 아님.
- **`is_data_repl_log_enabled`의 `default: return true`(3345행)**: 이 게이트는 `is_stmt_based_repl_type`이
  true인 경우에만 도달합니다. `is_stmt_based_repl_type`은 DDL/`PT_DROP_VARIABLE`/USE_SBR가 붙은
  INSERT·UPDATE·DELETE만 true를 주고 **MERGE 등 다른 DML은 포함하지 않으므로**, default 분기에
  도달하는 것은 DDL·DROP_VARIABLE뿐입니다. 이들은 REPLICATION=OFF와 무관하게 항상 스키마 복제되어야
  하므로 default=true가 맞습니다. → **1차 문제 6(MERGE가 default=true로 새어나간다)은 오판이라 폐기.**
- **파생 vclass 대상의 SBR 과탐(spec_has_replication_class의 서브트리 walk)**: 대상 파생 테이블 안에
  복제 클래스가 하나라도 있으면 SBR을 켜므로 과복제 방향(누락보다 안전)이며, 남는 위험은 문제 7의
  known limitation 범주에 포함됩니다. 별도 신규 지적으로 세우지 않았습니다.
- **#7697(서버측 인터럽트 전파, int+out-param 전환)**: 제 직무(클라이언트/DDL 표면) 밖의 서버 하부
  로직이라 표면만 확인했습니다. 정밀 검토는 DB엔진개발자 페르소나 몫입니다.

이상으로 제 관점에서 **새로 세울 결함은 없습니다.** 억지로 늘리지 않고, 실제 재현 경로가 서는 유지 12건만
남기고 조사를 마칩니다.
