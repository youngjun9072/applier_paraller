## USER1-01 성공한 CREATE가 실제로는 복제 불가능할 수 있다

- 심각도/신뢰도: **Critical / High**; 영향: SQL 사용자
- feature 근거: CREATE의 client 판정은 `class_object.c:95-98` 및 `schema_manager.c:16115-16129`에서 복합 UNIQUE 중 하나만 NOT NULL이어도 성공한다(`execute_schema.c:10267-10273`). 서버 DML은 모두 NOT NULL인 경우만 후보로 삼는다(`object_representation_sr.c:4712-4719`, `locator_sr.c:8041-8049`).
- develop 비교: develop PK-only에는 없던 feature 신규 문제.
- PR 이력: #6477/#6739/#7370 관련.
- 재현/불변식: 일부 nullable 복합 UNIQUE로 ON table을 생성하고 insert/update/delete. SQL 성공은 “실제로 복제 가능”을 의미해야 한다.
- 수정·테스트: 동일 판정 함수를 공유하고 DDL 성공 직후 DML 복제를 e2e로 시험.

## USER1-02 UNIQUE가 둘 이상이면 사용자가 어느 것이 RK인지 알 수도 고정할 수도 없다

- 심각도/신뢰도: **Critical / High**
- feature 근거: source 첫 후보 `locator_sr.c:8039-8049,8418-8426`; replica 첫 후보 `btree.c:8285-8298`; RK 이름 전달 필요 TODO `object_representation_sr.c:4692`.
- develop 비교: 단일 PK 의미에서 다중 후보로 확장하며 신규.
- PR 이력: #7370/CBRD-26096.
- 재현/불변식: UNIQUE 두 개를 다른 순서로 재생성한 노드에서 동일 DML. 사용자가 같은 SHOW CREATE를 보고 같은 식별 결과를 기대하지만 보장되지 않는다.
- 수정·테스트: 명시 RK 문법 또는 canonical 선택을 catalog에 노출·고정.

## USER1-03 조건부 UNIQUE 밖의 행은 조용히 복제 로그가 없어진다

- 심각도/신뢰도: **High / High**
- feature 근거: 후보 판정은 filter를 무시한다(`class_object.c:95-98`, `object_representation_sr.c:4702-4721`). predicate false면 `locator_sr.c:7863-7876`에서 로그 생성 `8041-8049` 전에 건너뛴다.
- develop 비교: UNIQUE RK feature가 신규 노출.
- PR 이력: #7370 관련.
- 재현/불변식: `UNIQUE(a) WHERE flag=1` ON table에 flag=0 행 추가. 성공한 INSERT가 replica에 나타나야 한다.
- 수정·테스트: filtered/function index를 RK에서 제외하고 명확한 오류 제공.
