## 1. 목적과 범위

`upstream/develop...upstream/feature/CBRD-26246-develop`에서 추가·변경된 HA replication key(RK) 및
`REPLICATION={ON|OFF}` 기능 코드를 실제 로직 기준으로 리뷰한다. 단순히 diff의 키워드를
찾는 데 그치지 않고, 변경 함수의 caller/callee, class representation, DDL 검증, DML log 생성,
log apply, HA 시작, unload/checksum 경로까지 추적한다.

리뷰 대상은 기능 브랜치가 새로 만든 결함 또는 기존 결함을 사용자에게 새롭게 노출·악화한 경우다.
기능과 무관하게 `develop`에도 동일하게 존재한 문제도 문서에서 삭제하지 않는다. 후보 원문을
`develop 기존 문제/비회귀`로 표시해 보존하고, feature 신규 finding 집계에서만 분리한다.

## 4. 분석 방법

1. `git diff develop...HEAD`와 관련 commit을 사용해 기능 변경 진입점을 정한다.
2. feature worktree의 `compile_commands.json`과 clangd LSP로 정의·참조·호출 관계를 추적한다.
3. LSP 결과는 실제 source와 preprocessor mode(SERVER_MODE/SA_MODE/CS_MODE)를 대조한다.
4. 의심 경로는 같은 코드를 `develop`에서 다시 읽어 기능 도입 전에도 같은 문제였는지 판정한다.
5. 관련 closed PR의 본문, review comment, 후속 수정 이력을 확인하여 코드만으로 드러나지 않는
   설계 의도와 이미 수정된 결함을 반영한다.
6. 가능하면 정적 검사·빌드·표적 테스트로 검증한다. 실행 환경이 없으면 필요한 재현 절차를 남긴다.

현재 compile DB는 source 경로가 `/home/youngjun/Workspace/claude`로 재지정돼 있지만 build directory와 생성 헤더는
develop debug build를 사용한다. 따라서 clangd는 탐색 보조이며, 진단 결과만으로 결함을 확정하지 않는다.

## 6. finding 판정 기준

각 finding은 다음 필드를 가진다.

- ID와 제목
- 심각도: Critical / High / Medium / Low
- 신뢰도: High / Medium / Low
- 영향받는 페르소나
- feature 근거: 절대 또는 repo-relative `file:line`, 함수와 실행 경로
- develop 비교: 없음 / 동일 / feature에서 악화 / 판정불가
- PR 이력: 관련 PR 번호와 설계·후속 수정 맥락
- 재현 시나리오 또는 실패 불변식
- 권장 수정과 필요한 회귀 테스트

코드 리뷰 finding으로 채택하려면 다음을 모두 만족해야 한다.

1. RK 기능과 인과관계가 있다.
2. 실행 가능한 경로 또는 명확한 상태 불변식 위반이 있다.
3. 코드 위치가 특정된다.
4. `develop` 비교 결과 신규/악화임을 설명한다.
5. 이미 후속 PR에서 해결됐다면 현재 HEAD에도 남아 있는지 다시 확인한다.

모든 후보는 삭제하지 않고 다음 상태 중 하나를 부여한다.

- `채택`: feature 신규 또는 악화 결함으로 최종 finding에 포함
- `develop 기존`: 기준 브랜치에도 같은 문제가 있어 feature 회귀 집계에서는 분리
- `후속 PR 해결`: 중간 snapshot에는 있었지만 최종 HEAD에서 해결
- `기각`: 실행 경로 대조 결과 코드가 이미 처리하거나 전제가 틀림
- `판정불가`: 정적 분석만으로 결론을 내릴 수 없음
- `비적용/코드무관`: CUBRID 구조 또는 코드 리뷰 범위에 맞지 않음
- `중복 병합`: 다른 채택 finding과 root cause가 같음

문서 요구, 제품 정책 선호, 근거 없는 가능성, CUBRID에 없는 기능 전제도 원문 후보와 판정 사유를
`CANDIDATE_AUDIT.md`에 남기고 채택 finding 집계에서만 분리한다.
